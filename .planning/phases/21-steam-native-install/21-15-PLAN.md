<objective>
Close UAT gap D-UAT-03 (SNI-01/SNI-03 perf): native Steam installs are throughput-capped and freeze the UI because the pure-JS `lzma` VZ decompressor (~5 MB/s single-threaded) runs on the Electron **main thread** inside `fetchChunk`. The 32-way network concurrency (FILE_CONCURRENCY×CHUNK_CONCURRENCY) is wasted — every chunk's decompress serializes onto one core. A 15 GB all-LZMA game projects to ~51 min of pure decompression single-threaded → ~5 min with a pool.

Move the CPU section (decrypt → decompress → sha1-verify) off the main thread onto a `worker_threads` pool sized ≈ `min(os.cpus().length, 8)`, using **transferable ArrayBuffers** and the **pure-JS `lzma` codec** (native `lzma-native` is REJECTED — CLAUDE.md no-native-modules constraint). Preserve the T-21-03 integrity gate and cross-server retry exactly, preserve memory-bound streaming (bounded in-flight chunks only), and fall back to inline main-thread decode if the pool cannot initialize.

Purpose: make native install usable at real game sizes without blocking the event loop.
Output: a worker pool wired into the existing `downloadDepotFiles` loop with a graceful fallback, plus build wiring that resolves the worker in both `yarn dev` and a packaged asar build.
</objective>

<architecture_note>
CPU-bound split (decision to implement, justified): only decrypt+decompress+sha1 are CPU work.
- `fetch` is network I/O — it does NOT block the event loop and must STAY on the main thread so the existing cross-server retry loop (fetchChunk) keeps orchestrating retries where the sockets live.
- `steamDecrypt` (AES, node:crypto, native/fast) and `sha1` (native/fast) are individually cheap, but they sit in the same CPU section as the slow LZMA decompress. Moving the WHOLE section (decrypt → decompress → sha1) into the worker is cleaner than splitting mid-section: it keeps the integrity gate co-located with the bytes it verifies, and avoids shipping the decrypted plaintext back across the boundary only to re-decompress. So: main thread does fetch + retry orchestration; worker does decrypt + decompress + sha1-verify + size-check and returns ONLY verified, decompressed bytes.
</architecture_note>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| CDN → main thread | Steam CDN chunk bytes are attacker-influenceable (spoofed/corrupt edge); untrusted until sha1-verified |
| main thread → worker | The depot decryption key and encrypted bytes cross the worker_threads boundary (same OS process, separate V8 isolate) |
| worker → disk | Only sha1-verified, decompressed bytes are returned to be written to the install root |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-21-15-01 | Tampering | decodeChunk / worker decode | mitigate | The `sha1(decompressed) === chunk.sha` gate + `length === cb_original` check live INSIDE decodeChunk (single-sourced), enforced in the worker before any buffer is returned; a chunk that fails is never returned → fetchChunk retries a different content server (T-21-03 preserved, relocated not removed) |
| T-21-15-02 | Information Disclosure | key crossing worker boundary | mitigate | Key is copied into its own ArrayBuffer per message (never transferred/detached), never logged, never posted back from the worker; workers are same-process isolates so no new external exposure surface is created |
| T-21-15-03 | Denial of Service | malformed VZ/PK buffer hangs/crashes a worker | mitigate | Per-task timeout on the main side terminates + replaces the stalled worker and rejects the task so fetchChunk retries; worker wraps decode in try/catch and posts {error} rather than crashing the pool |
| T-21-15-04 | Tampering | ArrayBuffer transfer correctness | mitigate | sha1 verification runs AFTER decompress inside the worker, so any transfer/detach corruption is caught by the same integrity gate before bytes reach disk |
| T-21-15-SC | Tampering | package installs | accept | No new package installed this plan — `lzma` (pure-JS, already audited/approved in 21-RESEARCH Package Legitimacy Audit) and Node built-ins only; no supply-chain surface added |
</threat_model>
