# Phase 48 — UI Design Contract

> Visual and interaction contract for the focus-row insertion and its `FOCUS ROW` tier-2 panel
> section. Generated by gsd-ui-researcher, verified by gsd-ui-checker. Read alongside
> `48-SPEC.md` (locked requirements) and `48-CONTEXT.md` (locked implementation decisions D-01
> through D-12) — this file does not restate those, it fills the gaps they leave open: the
> strip's internal spacing, the forward/back control's appearance and states, the panel section's
> internal shape, and the copy.

## Spacing Scale

This phase does not introduce a new spacing scale — it draws from the project's existing `em`-based
scale (`src/frontend/styles/_spacing.scss`), which is not the standalone 4px-multiple px scale this
template section models. Declared for reference, with the one fixed-px exception this phase relies on:

| Token | Value | Usage in this phase |
|-------|-------|----------------------|
| `--space-3xs` | 0.25em | Checkbox/box corner radius (reused, not new) |
| `--space-2xs` | 0.375em | Row/header vertical padding inside `FOCUS ROW` (reused from `FilterFacetRow`) |
| `--space-sm` | 0.75em | `--tier2-row-padding-inline` (reused — do not redeclare locally) |
| `--space-md-fixed` | fixed px (see `_spacing.scss:17`) | Strip's outer inline padding — must match `.gameList.firstLane`'s existing `0 var(--space-md-fixed) var(--space-md-fixed)` exactly, so the strip's left/right edges line up with the grid below it |

**Exceptions:**
- **156px card width** (D-01, fixed, not a scale token) — locked by SPEC R3.
- **24px (`1.5rem`) horizontal gap between strip cards** — this is not a new value, it is `.gameList`'s existing `grid-gap: 1.5rem` (`Library/index.css:5`) reused verbatim so the strip's card spacing visually matches the grid's directly below it. Do not invent a different gap.
- **36px forward/back control diameter** — a new value, justified below under "Strip — Layout, Overflow, and Controls" → "Forward / back controls". Clears the 44px icon-only touch-target guidance only partially; see that section for why a smaller size is deliberate here (it sits over game art, not a bare touch surface, and gamepad/keyboard are the primary path per D-07, with pointer as a convenience).

## Color

This is a 10-theme application (`themeTokens.test.ts:172`); no single hex is the "dominant" colour
across all of them. Values below are expressed as the tokens to consume, with `midnightMirage`
(the default theme) given for illustration only — do not hardcode the illustrative hex.

| Role | Token | `midnightMirage` value | Usage |
|------|-------|--------------------------|-------|
| Dominant (60%) | `var(--body-background)` | `var(--background-darker)` → `var(--neutral-01)` | Library content surface behind both the strip and the grid — unchanged |
| Secondary (30%) | `var(--navbar-background)` / `var(--background)` | `var(--neutral-02)` | Tier-2 panel surface the `FOCUS ROW` section sits in — unchanged, inherited from `NavShell__tier2` |
| Accent (10%) | `var(--accent)` | `#e0ab40` (global `:root` default, not overridden by `midnightMirage`) | **Reserved for, and only for:** the active `FOCUS ROW` entry's checked-row treatment (via `--filter-active-color`'s existing chain, see below), the forward/back controls' icon and focus ring, and the strip's own focus ring on a focused card (already `GameCard`'s existing outline behaviour, unchanged) |
| Destructive | `var(--danger)` | `#a62b2b` | **Not used anywhere in this phase.** Clearing a focus-row selection is a non-destructive, instantly-reversible toggle (re-click to restore), not a delete — do not colour the clear interaction with `--danger`. Noted per the measured landmine: `--danger` is 3.55:1 against this panel's background, under WCAG AA, so it would be the wrong choice here even if a destructive framing were considered. |

**`--border-color` is explicitly excluded from this contract.** It resolves to ~1.08:1 against its
background in most themes despite its own in-source comment calling it "universal" — anything in
this phase that must be *seen* (the active `FOCUS ROW` row, the forward/back controls, a focused
card) uses `--accent` via the existing `--filter-active-color` chain, never `--border-color`.

**No new CSS custom property is introduced by this contract.** Every token named above already
exists in `src/frontend/themes.scss` or the shared `_spacing.scss`/`_typography.scss` files. If
planning or implementation finds a need for a token not named here, it must be verified to exist
(or explicitly declared "new token, must be defined by this phase") before use — an undefined
custom property is silently dropped at computed-value time and is now gated.

**`--navbar-active` consumer obligation carries forward.** If the forward/back controls' stylesheet
(new file, see below) ends up consuming `--navbar-active` directly (it should not need to — it
should consume `--accent` directly, which resolves in all 10 theme blocks, not just 4) — if it
does, it must be added to `NAVBAR_ACTIVE_CONSUMERS` in `themeTokens.test.ts:92-99` and must
redeclare the full `var(--navbar-active, var(--accent-overlay, var(--accent)))` chain locally. The
contract's default choice (`--accent` directly) avoids this obligation entirely and is the
recommended path.

## Panel Section Shape — `FOCUS ROW`

Builds directly on CONTEXT.md D-08/D-09/D-10/D-11 (collapsible `FilterFacetGroup`, collapsed by
default, no `Dropdown`-style select, positioned in its own group div between
`Header__categoriesGroup` and `Header__filtersGroup`). This section specifies what D-08–D-11 leave
open: the section's *internal* shape.

**Container:** a new `<div className="Header__focusRowGroup" data-tour="...">` sibling to
`Header__categoriesGroup` and `Header__filtersGroup`, inserted between them at
`Header/index.tsx:284-298`, wrapping one `FilterFacetGroup`.

**No selection-count badge.** Unlike Store/Runnability/More-filters (multi-select facets that show
`selectedCount`), `FOCUS ROW` is single-select-or-off — follow `FilterCollectionList`'s precedent
(`FilterFacetGroup` called with `title` only, no `selectedCount`/`selectedCountLabel` props,
`FilterCollectionList/index.tsx:63-66`). A "1 selected" badge on a single-select section is noise;
the strip itself (always visible above the grid, per D-12) is where the active pick is communicated
— see the "where the user sees the state" note below.

**Internal structure — 4 sub-groups, fixed order, divider labels, no nested collapse:**

```
▸ FOCUS ROW                              (collapsed by default — FilterFacetGroup)
  ┌─────────────────────────────
  │ Views                                 ← new micro-label, --text-xs, --regular, --text-secondary
  │   ○ All games
  │   ○ Installed
  │   ○ Recently played
  │   ○ Favourites
  │ Collections                           ← omitted entirely if customCategories is empty
  │   ○ <user collection 1>
  │   ○ <user collection 2>
  │   ○ Uncategorized
  │ Store                                 ← omitted entirely if connectedStores is empty
  │   ○ GOG
  │   ○ Steam
  │   …
  │ Runnability                           ← mirrors FilterRunnabilityFacet's own platform gating
  │   ○ Runs natively
  │   ○ Runs via bottle
  │   ○ Won't run
  │   ○ Not yet checked
  └─────────────────────────────
```

- **Fixed order** (satisfies the locked acceptance criterion "the section's groups render in a
  fixed order"): Views, then Collections, then Store, then Runnability — this is the same
  top-to-bottom order the panel itself already uses above `FOCUS ROW` (Views → Collections →
  Store → Runnability facets), so the section reads as a miniature index of the panel it sits
  inside, reinforcing D-10's rationale for its position.
- **Divider labels are non-interactive text, not another `FilterFacetGroup`.** No second level of
  collapse — the whole section is already one disclosure (D-08); nesting a second would bury the
  content two clicks deep for a feature this phase's own motivation was "get it out of hiding."
- **Rows are `NavItem` (button branch, `active` prop), not `FilterFacetRow`.** Selection is
  single-value-or-off, not a checkbox — reuse `FilterCollectionList`'s row shape and its
  `selectCollection`-style clear-by-reclick handler (`FilterCollectionList/index.tsx:58-60`)
  against a single `focusRow` state value instead of `currentCollection`.
- **Empty sub-groups are omitted wholesale** (divider label included) rather than shown with an
  empty-state message — this differs deliberately from `FilterCollectionList`'s own
  `FilterCollectionList__empty` message ("No custom categories...") because that message belongs
  to the *management* surface for collections; `FOCUS ROW` is a picker over whatever already
  exists, and a picker with one empty option group should look like a picker with three groups,
  not like a feature asking the user to go create something. Mirrors `FilterStoreFacet`'s own
  `connectedStores.length === 0 → return null` convention (`FilterStoreFacet/index.tsx:29-31`) at
  the sub-group level.
- **Store rows render store name text only, no logo.** Default/discretion call: `StoresPanel`
  elsewhere uses `NavItem`'s `iconElement` slot for store SVG logos, but `FOCUS ROW`'s rows match
  `FilterCollectionList`/`FilterViewList`'s existing text-only row convention instead, since this
  section already sits beside two text-only sibling sections. An executor may add logos as a
  non-required enhancement without conflicting with this contract, but plain text is the default
  and nothing in the acceptance criteria requires an icon.
- **Where the user sees the current state without opening the panel:** the strip's own header,
  always rendered above the grid when a focus row is active (D-12, "echoes the pick"), is the
  visible state surface — satisfying the sketch's "do not hide filter state in the panel alone"
  rule in spirit, even though the focus row is not a filter and does not get a chip (SPEC R4: the
  focus row is independent of filter state, and the sketch's chip row answers "why did the grid
  shrink," which is a different question than "what is the focus row set to").

## Strip — Layout, Overflow, and Controls

Builds on D-01 through D-07 (fixed 156px cards, 20-item cap, forward/back over wheel-only,
gamepad-scroll-into-view). This section specifies the container mechanics, the controls'
appearance/states, and what is explicitly dropped from the grid's own CSS.

### Header

Reuse `.library-section-header` + `h3.libraryHeader` exactly as the Favourites lane does today
(`Library/index.tsx:1228-1230`, `Library/index.css:42-50`) — same sticky positioning
(`position: sticky; top: 0; z-index: 9`), same padding, same background gradient. **No new header
treatment.** Text content is the echoed pick (see Copywriting Contract above), not a constant
"Focus row" label.

### Track container — new CSS, not `.gameList`

The strip is **not** `.gameList` with a layout override — it needs single-row flex/scroll
mechanics `.gameList`'s `display: grid; grid-template-columns: repeat(auto-fill, minmax(156px,
1fr))` cannot express (a `grid` wraps; this must never wrap, per the locked acceptance criterion
"narrowing the window reduces the visible card count without wrapping to a second row"). New
classes, following this file's existing flat/compound-class convention (`.gameList.firstLane`,
not NavShell's `__` BEM):

```css
.focusRowStrip {
  position: relative;            /* positions the overlay controls */
  padding: 0 var(--space-md-fixed) var(--space-md-fixed);  /* matches .gameList.firstLane exactly */
}

.focusRowTrack {
  display: flex;
  gap: 1.5rem;                   /* == .gameList's grid-gap, reused verbatim, not a new value */
  overflow-x: auto;
  scroll-behavior: smooth;
  /* Scrollbar hidden, not reserved: forward/back controls are the primary,
     keyboard/gamepad-reachable mechanism (D-07); native wheel/trackpad scroll
     is left as a pointer convenience on top of them, not the contract. No
     `scrollbar-gutter: stable` here — that reserves the PLATFORM scrollbar
     width (~17px on macOS) regardless of this bar's own width and would shift
     every card right by that amount for no visual benefit once the native
     bar is hidden. */
  scrollbar-width: none;
}
.focusRowTrack::-webkit-scrollbar {
  display: none;
}

.focusRowTrack > * {
  flex: 0 0 156px;               /* fixed width, D-01 — never a fraction of the container */
}
```

- **No `grid-column: span 2` emphasis for the first just-played card.** `.gameList.firstLane >
  div:has(.justPlayed) { grid-column: span 2 }` (`Library/index.css:14-16`) is **not carried
  forward** — it is structurally inapplicable, not merely dropped by choice, because the strip is
  not a CSS grid and has no grid-column axis. `GameCard`'s own internal just-played visual (the
  "PLAY" label overlay driven by the `isRecent`/index-0 logic `GamesList` already has,
  `GamesList/index.tsx:143,166-168`) is unaffected and still renders — only the *double-width*
  emphasis is gone.
- **`min-width: 0` is not needed on `.focusRowTrack` itself** the way `library-filtering.md`
  warns for a flex child with grid content — the track's children are `flex: 0 0 156px` (fixed
  basis, not shrinkable grid content), so there is no analogous overflow risk from the track side.
  The risk this phase must still avoid is the *container* (`.focusRowStrip`) needing `min-width:
  0` if it ever sits inside another flex row — verify at implementation time against
  `Library/index.tsx`'s actual DOM ancestry.

### Forward / back controls

**Appearance:** circular, 36px diameter, positioned absolutely at the vertical center of the
track, overlaid on the game art at each edge (left edge for back, right edge for forward) —
Netflix/Steam convention, the one the operator named directly (D-05). Semi-transparent dark scrim
background (`color-mix` of `--body-background` at reduced opacity, or `rgba(0,0,0,.55)` as a
fallback if `color-mix` support is a concern — this project's `--focus-ring-fill` already uses
`color-mix()` at `themes.scss:77`, so the mechanism is established) so the chevron icon
(`faChevronLeft` / `faChevronRight` from `@fortawesome/free-solid-svg-icons`, matching the
`faChevronDown` already used by `FilterFacetGroup`) stays legible over any artwork. Icon colour
`var(--accent)`.

- **36px, not the 44px icon-only touch-target default:** this is a deliberate, named exception.
  The control sits over a 156×275-ish card's full-height art, is reachable by pointer, keyboard
  (real `<button>`, tab-focusable) and gamepad (D-06/D-07), and 44px at this position would start
  visually colliding with the card's own corner radius and hover outline at 156px card width.
  Flag this row if a future accessibility pass wants to revisit it.
- **Present only when there is overflow to show.** Per the locked acceptance criterion "strip
  content narrower than the available width shows no overflow affordance" — when the pick's game
  count (capped at 20) fits entirely within the track's visible width, **neither control
  renders**, not even disabled. Controls only mount once the track's scrollable width exceeds its
  visible width.
- **Disabled-but-rendered at the ends, not hidden.** Once scrolling is possible: the back control
  renders disabled (native `disabled` attribute, removed from tab order — standard button
  semantics, not a D-07 violation since there is genuinely nothing to activate) at the start of the
  track, and dims using the same `opacity: 0.38` convention `.FilterFacetRow--zero` already uses
  (`FilterFacetGroup/index.scss:286-288`) rather than a new opacity value. The forward control
  mirrors this at the end of the track. This differs from the "no affordance at all" case above —
  that case has no scrolling at all; this case has scrolling in one direction only.
- **Click/activation behaviour:** scrolls the track by one "page" — the number of fully-visible
  cards at the current container width — with `scroll-behavior: smooth`, not by a single card.
  This matches the forward/back convention named in D-05 and avoids a control that barely moves
  content at wide window sizes.
- **Focus ring:** outset (not the panel's inset recipe — these controls are not inside the
  scroll-clipped tier-2 column, so an outset ring is not clipped), reusing the project's existing
  focus tokens: `outline: var(--focus-ring-width, 3px) solid var(--focus-ring-color,
  var(--accent, #0080ff))` with positive `outline-offset` (e.g. `2px`), plus the
  `body.controllerLayout` gamepad-focus arm every other interactive element in this codebase
  carries (`NavItem/index.scss:84-92` is the pattern to copy) — Tauri gamepad focus is a script
  `.focus()` call that `:focus-visible` alone can miss.
- **Gamepad overflow (D-06):** `helpers/gamepad.ts` already navigates `.gameCard` elements
  directly and `GamesList/index.tsx:47-79` already implements a vertical "scroll the focused card
  into view" handler (`scrollCardIntoView`, keyed off `main.content`'s vertical `scrollTop`). The
  strip needs a **horizontal analogue of this, not a reuse of the vertical one** — gamepad focus
  moving to a card past the track's visible edge must scroll the **track's own `scrollLeft`**
  (not the page's vertical scroll) so the focused card is fully visible, matching the same
  "focused element's rect relative to its own scroll container's rect" approach the vertical
  version uses, adapted to the horizontal axis. This is new code, not a prop change to the
  existing handler — flag it for the plan/executor as a net-new interaction, not an extension.
