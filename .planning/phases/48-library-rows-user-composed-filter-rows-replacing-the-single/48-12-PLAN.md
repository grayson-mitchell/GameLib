**What stays locked.** SPEC R3's "the grid's output is unchanged against a pre-phase baseline": the
grid is the reference and is not touched (`Library/index.css`, `GameCard/index.css`, `GamesList`).
D-03 (a container change, never a card change), D-04 (at most 20 cards), D-05 and D-07 (real

**Root cause (from 48-UAT.md, orchestrator-verified).** The strip pins every card at
`flex: 0 0 156px` (`FocusRowStrip/index.css`) while the grid is
`grid-template-columns: repeat(auto-fill, minmax(156px, 1fr))` (`Library/index.css:4`), so grid
cards stretch to fill each row and are 156px only at the narrowest fit.

**Design decision: derive, do not read.** The strip's card width is computed by the grid's own
arithmetic over the strip's content box, not read from the rendered grid. Reasons:
1. Same input, so identical by construction. `.focusRowStrip` and the grid's `.gameList` are both
   direct children of `.listing` (`Library/index.tsx:1129-1197`, a column flexbox, so both stretch
   to its width), and both pad inline by `var(--space-md-fixed)`. The strip's content box C is the
   track's border-box width less the list's two inline paddings, because the viewport bleeds out by
   exactly that padding (48-10 Test G). Same C, same 156px minimum, same 1.5rem gap gives the same
   column.
2. Reading the grid would tie the strip to grid state. The grid is not mounted for a zero-result
   filter (`FilterZeroResult`), during a refresh, and has no columns in list layout. SPEC R4 makes the
   focus row independent of filter state, and SPEC requires that "a filter state yielding zero grid
   results still renders the focus row". A strip that shrank to 156px whenever a filter emptied the
   grid would quietly break that.
3. Testable here. The Frontend jest project is `testEnvironment: 'node'` with no CSS engine, so a
   pure function plus stubbed-DOM sync is provable at the desk, and the live check confirms parity
   within 1px.

Pure CSS cannot express it portably. The column count needs a length divided by a length, which
WebKit does not support. The alternative is a breakpoint per column count, which has no upper
bound, and it is rem-sensitive. The width is written as an inline `--focus-row-card-width`
custom property on `.focusRowTrack`. CSS consumes it as `flex: 0 0 var(--focus-row-card-width, 156px)`,
so 156px (the grid's floor) remains the fallback before the first measurement and when
measurement is impossible.

**What the wider cards cost, and how each cost is paid.**
- *Page count (Task 1).* Matched cards fill the content box exactly (n x w + (n - 1) x gap = C), and
  the track is C + 2 x 12px, which equals n x pitch when the gap is 24px. That leaves zero slack.
  `floor(clientWidth / pitch)` therefore paged n - 1 cards at about half of all widths. A desk
  sweep measured it: C from 150 to 4000px in 0.37px steps, widths under 156 skipped (about 10,400
  samples), `clientWidth` rounded. It found 4951 mismatches with no tolerance and 0 with a 1px
  tolerance. `pageScrollDelta` gains the existing `SUBPIXEL_EPSILON` as a
  whole-card tolerance.
- *Ring clearance (Task 2).* 48-10's 12px list padding and bleed cover a ring reach of
  (w/2 + 5) x 1.05 - w/2 = 0.025w + 5.25. That is 9.15px at 156px but 13.65px at the widest grid
  card. The supremum is 2 x 156 + 24 = 336px: one column, just before a second fits. Vertically the
  1em list margin covers 11.45px at 156px but not 18.60px at 336px. Both overruns happen only in
  the single-column band, card wider than about 270px (on the UAT item 4 macOS geometry, a window
  of about 592-658px). The clearance N goes from 12px to 15px. That is fixed, so Tests F-H keep
  parsing px and keep bleed = padding, and 15 is still under the 16px gutter. Headroom is at least
  1.35px. The vertical room becomes `max(1em, card-width-scaled calc)`, which stays 1em at
  typical widths. Both are proven by a gate that parses the ring width, offset, scale and card
  ratio from the shipped stylesheets.
- *A resize feedback loop (Task 3).* Card height follows width (`aspect-ratio`), and the main
  scroller `.App .content` has `overflow-y: auto` with a 10px styled scrollbar (`index.scss:57-60`)
  that takes layout space. So a library whose content height sits within a few px of the
  viewport can flip the scrollbar every frame: a wider strip leads to a scrollbar, then narrower
  cards, then no scrollbar, then wider cards again. The ResizeObserver delivers that one frame
  late, as a `ResizeObserver loop` error each time. The sync writes only on a change of 0.5px or
  more, and it holds a write that would undo the write before last within 250ms.
