# Phase 23.2: Code Review Report

**Reviewed:** 2026-08-19
**Depth:** standard
**Files Reviewed:** 12
**Status:** clean

## Summary

This phase does two things: (1) gates the catch-path `finalize()` in `downloadSteamDepots` behind a new fail-closed predicate (`shouldFinalizeAfterThrow`) so a plan-build failure that never attempted a download can no longer clobber a complete `.acf` with a zero-byte stub, and (2) adds a skip-and-warn policy that drops a single `EResult 40` (Blocked) depot from the plan instead of aborting the whole install, threading the skipped set through to a user-facing completion notice.

I traced every path the review brief asked about and did not find a defect:

- **Data destruction (focus 1).** `shouldFinalizeAfterThrow` is a pure, fail-closed boolean gate (`downloadAttempted === true`, nothing else resolves true). `downloadAttempted` is set immediately before the `downloadDepotFiles` await, so a throw with bytes already on disk (Case B, the Phase 21 1026 verify-handoff) still finalizes, and a throw before that point (Case A — `buildDepotPlan` itself failing, including the new all-skipped guard) does not. Verified against the real, unmocked `getBottleDir`/`getBottleSteamappsDir` bottle-path shape in `depot.finalize.test.ts`, with exact-text-equality assertions (not a substring/key-presence match) proving a seeded complete manifest survives byte-for-byte. The one sibling path this doesn't gate — the zero-depot early return when `buildDepotPlan` resolves successfully with `descriptors.length === 0` — genuinely cannot reproduce the destructive stub shape: `lastResult` is still `undefined` there, so `finalizeToSteam` receives `outcome: undefined ?? 'cancelled'`, which fails `canWriteFullOwnership` closed to `StateFlags 1026`; `buildid` is still the real PICS-captured value (never zeroed) and `SizeOnDisk` is independently *measured* from disk (`measureInstalledBytes`), never zeroed either. That's the same shape as the pre-existing, legitimate Phase 21 1026 verify-handoff, not the D-08 stub (`StateFlags 1026` + `buildid "0"` + `SizeOnDisk "0"`) — Steam's own verify pass is designed to reconcile exactly this state. It does force an unnecessary verify pass on a previously-`StateFlags=4` install if this path is ever hit against one (see Info finding below), but it does not destroy data.
- **Fail-open inversion (focus 2).** The skip trigger is a literal `eresult === 40` check, never the broader `isNonRetryableDepotError`/`NON_RETRYABLE_ERESULTS` set — confirmed by a parameterized RED-proof test (`it.each([8,9,15,17,42,43])`) that fails against a temporarily-widened implementation. `wrapDepotKeyError` only copies `.eresult` onto the wrapped error when `typeof eresult === 'number'`, so a non-numeric/absent eresult can never coerce to `40`. `DepotPlanAbortedError` (the abort path) carries no `.eresult` at all, so a cancel mid-loop cannot be misclassified as a skip — confirmed by a dedicated test aborting between two depot fetches. `withPlanBuildRetry` fails fast on `eresult 40` (it's still a member of `NON_RETRYABLE_ERESULTS`) rather than retrying it into a different error shape, so the eresult that reaches the skip check is always the original, unretried one.
- **Silent incomplete install (focus 3).** The `!depots.length && skippedDepots.length` guard at the end of the plan-build loop is the only way to reach zero depots *because* of a skip, and it throws before `buildDepotPlan` can ever return an all-skipped plan — closing the path that would otherwise fall into the zero-depot early return and report `status: 'done'`. The adjacent "genuinely zero owned depots" case (no skip involved at all) is pre-existing Phase 21 behavior, unchanged by this phase, and is a different, non-destructive shape as noted above.
- **Byte accounting (focus 4).** `totalBytes` accumulation happens after the `continue` for a skipped depot, so it excludes skipped bytes for free. `InstalledDepots`/`BytesToDownload`/`BytesDownloaded` all derive from `attempted`, built from the *reduced* `plan.depots` (skipped depots are never pushed into that array), and `SizeOnDisk` is independently measured from the real filesystem, not summed from the plan — so none of these can drift from what's actually on disk regardless of what was skipped. Verified end-to-end in `depot.finalize.test.ts`'s Task 3 tests, which assert `BytesToDownload`/`BytesDownloaded`/`SizeOnDisk` all equal the sum of only the three kept depots' real byte content.
- **Injection/shape validation (focus 5).** Skipped depot ids never reach the VDF-serialized manifest at all (they're omitted from `InstalledDepots`, which is the whole point of the feature) — `manifest.ts`'s pre-existing `assertNumericId` guard on `depotId`/`manifest` (unchanged by this phase) still applies to every depot that *is* written. The only place a skipped depot id is used is a `logInfo` line and an i18next interpolation value rendered through the native `notify()` dialog (not `dangerouslySetInnerHTML`/`innerHTML`), both sourced from `descriptor.id`, which flows from Steam's own PICS/CM data the exact same way every *kept* depot's id already does elsewhere in this file. This is not a new trust boundary this phase introduces.
- **Secrets in logs (focus 6).** The new skip-branch `logInfo` and the `steam-flags-census` line addition (`skipped=${skippedDepots.join(',')}`) log only depot id / owning appId / eresult — never a decryption key, manifest GID, or account identifier.
- **Test quality (focus 7).** The new tests are consistently non-vacuous: the D-01 boundary is proven in both directions with a demonstrated RED-proof against a widened implementation (not just "40 skips"); the manifest-preservation assertions use exact text equality (not `toMatch(/InstalledDepots/)`, which would pass trivially since `buildAppManifestText` emits that key unconditionally even when empty); the `InstalledDepots` absence assertion for the skipped depot targets the block-key regex, not a bare substring; the i18n copy census and the "no `{{count}}`"/"skip guard isn't shared with `notifiedWaiting`" assertions each carry a paired RED case proving the predicate can fail. I ran the three most load-bearing suites directly (`depot.test.ts`, `depot.finalize.test.ts`, `steamDepotSkipCopyCensus.test.ts`) — 172/172 passed.

No BLOCKER or WARNING findings. Two INFO-level observations below, neither of which requires action for this phase to ship.

## Info

### IN-01: The zero-depot early return still forces an unnecessary Steam verify pass if ever hit against a previously-complete install

**File:** `src/backend/storeManagers/steam/depot.ts:2880-2900` (the `if (!plan.depots.length) { ... }` branch, unchanged by this phase)
**Issue:** As analyzed above, this path cannot destroy data (buildid and SizeOnDisk stay honest), but it does write `StateFlags 1026` with an empty `InstalledDepots` block over whatever `.acf` was previously there, including a prior `StateFlags 4` full-ownership manifest — which would force Steam into an unnecessary verify-and-repair pass the next time it scans this app. This is reachable if `selectAllDepots` ever returns zero descriptors for an app/OS combination that a user has already fully installed (e.g. a PICS staleness/platform-filter edge case, not something this phase's own test suite covers since it's explicitly out of scope per the SUMMARY). This is pre-existing Phase 21 behavior, not introduced or worsened by this phase, and the phase's own docs (23.2-02-SUMMARY.md) name it as a deliberately-deferred sibling case with a stated rationale ("resolving a dangling prior partial attempt"). Flagging only because the review brief specifically asked to confirm this path "genuinely cannot clobber" — it cannot destroy the underlying data, but it can needlessly downgrade a trustworthy manifest.
**Fix:** No action required for this phase. If this is ever observed live (the same way the D-08 stub was), the same `shouldFinalizeAfterThrow`-style pattern could be extended to skip finalize() when the plan is honestly empty AND a StateFlags=4 manifest already exists at the target path — worth a future todo, not a blocker here.

### IN-02: Skipped depot ids are not numeric-shape-validated before being logged/interpolated, unlike the manifest-write path's precedent

**File:** `src/backend/storeManagers/steam/depot.ts:769-792` (skip branch); `src/backend/storeManagers/steam/library.ts:2110-2119` (notice interpolation)
**Issue:** `descriptor.id` is pushed into `skippedDepots` and later joined into a log line and an i18next `{{depots}}` interpolation value with no shape guard, whereas `manifest.ts`'s `assertNumericId` precedent guards `depotId` before any VDF interpolation. In practice this is low-risk: skipped ids never reach the VDF-serialized manifest (the actual injection-sensitive sink), the value only reaches a `logInfo` line and a native OS notification body (not HTML rendering), and `descriptor.id` is sourced from Steam's own PICS/CM data the same way every *kept* depot id already is elsewhere in this file without a matching guard. Not a new trust boundary this phase introduces.
**Fix:** No action required. If a numeric-shape guard is ever added for depot ids at the PICS-ingestion boundary (upstream of `selectAllDepots`), it would cover this for free.
