# Manifest-write taxonomy — failure paths through `downloadSteamDepots`

**Created:** 2026-08-19, phase 23.2 plan 01, Task 1.
**Purpose:** settle D-08 sub-item 1 (which of three standing records about `.acf` writes on a
failed native install is correct) and hand plan 23.2-02 a source-anchored statement of which
failure-path behaviours are load-bearing and which is the defect.

**Method:** read `downloadSteamDepots` (`depot.ts:2706-2856`), `finalizeToSteam`
(`depot.ts:2468-2523`), `measureInstalledBytes` (`depot.ts:2439-2457`), `buildAppManifestText`
(`depot/manifest.ts:145-187`), `writeAppManifest` (`depot/manifest.ts:198-219`), and
`runNativeDepotDownload`'s target-dir resolution (`games.ts:1448-1591`, override at
`games.ts:1525-1526`). No hardware was run; every claim below is anchored to a function name and
line range a reader can re-derive.

## The three cases

`downloadSteamDepots` declares `attempted: FinalizeDepotEntry[] = []` and `buildid: string |
undefined` at its top (`depot.ts:2710,2715`), and a `finalize()` closure (`depot.ts:2731-2745`)
that always calls `finalizeToSteam(appId, { depots: attempted, buildid, ... })`. There are exactly
three call sites that can terminate the function, and therefore exactly three distinguishable
outcomes for whether and what gets written.

### Case A — `buildDepotPlan` throws (plan-build failure, zero bytes downloaded)

**Call site:** the `catch (err)` block, `depot.ts:2832-2855`, specifically the unconditional
`await finalize()` at `depot.ts:2836`.

When `buildDepotPlan(appId, opts)` (`depot.ts:2748`) throws — e.g. a depot decryption-key request
returns `EResult 40 Blocked` before any file write begins — control jumps straight to the catch
block. The `for (const d of plan.depots) { attempted.push(...) }` loop at `depot.ts:2752-2758`
never runs, because `plan` was never assigned. Its accumulation loop is INSIDE the `try`, after
the `buildDepotPlan` await that threw. So at the moment `finalize()` runs:

- `attempted` is still `[]` (the declaration-time empty array, `depot.ts:2710`).
- `buildid` is still `undefined` (the declaration-time value, `depot.ts:2715`) — it is only ever
  assigned from `plan.buildid` at `depot.ts:2750`, one line after the `buildDepotPlan` await that
  never returned.

`finalizeToSteam` receives `depots: []` and `buildid: undefined`. Inside it (`depot.ts:2493-2499`),
`canWriteFullOwnership` is evaluated with `outcome: opts.outcome ?? 'cancelled'` (there is no
`lastResult`, so `opts.outcome` is `undefined`, defaulting to `'cancelled'`) — this fails closed,
so `canWrite4` is `false`. `writeAppManifest` (`depot.ts:2508-2522`) is then called with
`stateFlags: undefined`, `bytes: undefined`, `buildid: undefined`, and
`installedDepots: [].map(...)` → `[]`.

`buildAppManifestText` (`depot/manifest.ts:145-187`) applies its own unconditional defaults:
`stateFlags = params.stateFlags ?? '1026'` (`manifest.ts:154`), `buildid = params.buildid ?? '0'`
(`manifest.ts:149`), `bytes = params.bytes ?? '0'` (`manifest.ts:155`). The `InstalledDepots` block
(`manifest.ts:174-177`) is written UNCONDITIONALLY regardless of whether `installedDepots` is
empty — `buildInstalledDepotsBlock([])` (`manifest.ts:120-137`) returns `''` for zero entries, so
the emitted text is `"InstalledDepots"\n\t{\n\t}` — a **present but EMPTY** block, not an absent
key.

**Result for case A:**
- `attempted` = `[]`
- `buildid` = `undefined`
- written `StateFlags` = `"1026"`
- written `buildid` = `"0"`
- written `InstalledDepots` block = present, zero entries
- `SizeOnDisk` = whatever `measureInstalledBytes(installRoot)` measures on disk RIGHT NOW (see
  "Size accounting" below) — NOT `0`, because case A can run against a directory that already has
  a complete prior install sitting in it.

**This is the D-08 defect.** A run that attempted nothing still overwrites whatever `.acf` was
already at that path (`writeAppManifest`'s atomic rename, `manifest.ts:216`, replaces the file
unconditionally) with a stub carrying no record of the prior install's depots.

### Case B — a graceful failure or cancel AFTER the plan was built

**Call sites:** the main-path `await finalize()` at `depot.ts:2816` (reached after
`downloadDepotFiles` resolves, whether that resolution is a clean completion, a partial failure,
or a `cancelled` outcome), OR the same catch-block `await finalize()` at `depot.ts:2836` when the
throw originates from `getContentServerHosts` (`depot.ts:2783`) or from `downloadDepotFiles`
(`depot.ts:2803`) — i.e. AFTER `buildDepotPlan` already returned and the `for` loop at
`depot.ts:2752-2758` already populated `attempted` for every planned depot.

At the moment `finalize()` runs here, `attempted` holds one entry per planned depot (real
`depotId`/`gid`/`size`), and `buildid` holds the real plan-time PICS value assigned at
`depot.ts:2750`. `lastResult` (`depot.ts:2812`, only reachable on the main path — the
catch-from-`getContentServerHosts`/`downloadDepotFiles` sub-case never reaches it) supplies
`outcome`/`failures`/`allFilesVerified`/`allModesApplied` to `canWriteFullOwnership`. This is the
legitimate Phase 21 `1026` verify-handoff (commit `eacbc7ccf`, 2026-07-15, "add finalizeToSteam
single 1026 handoff for cancel/failure/success") — a real, honest record of what was actually
attempted, defaulting to fail-closed `1026` unless every completeness input is satisfied (in which
case it is the Phase 23 `StateFlags=4` full-ownership path, `depot.ts:2500-2506`).

**Result for case B:** `InstalledDepots` is populated with every attempted depot; `buildid` is
real; `StateFlags` is `1026` (verify-handoff) or `4` (full-ownership, when `canWriteFullOwnership`
is satisfied). Not a defect — this is the manifest write Phase 23 spent ten plans hardening.

### Case C — the process dies (`kill -9`, crash, power loss)

**No call site** — this is the case where NO code in `downloadSteamDepots` runs to completion,
including `finalize()` itself, because the JS runtime that would run it has been killed. No `.acf`
is written; whatever was already at that path (if anything) is untouched.

23-UAT.md Gate 3 (`23-UAT.md:544-546`) is the recorded instance of this: GameLib was force-quit
(`kill -9` on the app AND its node sidecar) at 15,538/18,809 files, and
`appmanifest_1124300.acf` was confirmed ABSENT on disk afterward. The same gate also records that
resume worked correctly from that state (`23-UAT.md:550-560`) via `reconcilePartialState` /
`buildResumeFinalizeOpts`, a separate code path from `downloadSteamDepots` entirely (startup-time
resume, not this function).

## Size accounting — `SizeOnDisk` is not depot-plan-derived in ANY case

`finalizeToSteam` (`depot.ts:2479`) computes `sizeOnDisk` via
`measureInstalledBytes(installRoot)` — a recursive `readdir`/`stat` walk of
`resolve(targetSteamappsDir, 'common', installdir)` (`depot.ts:2439-2457`). This call happens
identically in cases A and B (case C never reaches `finalizeToSteam` at all) and has **no
knowledge of `plan.depots` or `attempted`** — it sums real bytes physically present on disk at
that path, whatever put them there. See `.planning/todos/pending/2026-08-19-failed-plan-build-writes-1026-stub-manifest-clobbering-a-complete-install.md`'s `## Resolution` section (added by
Task 2 of this plan) for the full accounting of why the 2026-08-19 KCD2 stub's `SizeOnDisk`
matched the official client's figure.

## What plan 23.2-02 must not regress

- **Case B is load-bearing.** It is the Phase 21 `1026` verify-handoff (and the Phase 23
  `StateFlags=4` full-ownership path layered on top of it) — the single completeness-gate call
  site inside `finalizeToSteam` (`depot.ts:2493-2499`), fed by real `attempted`/`buildid`/
  `lastResult` values. Any change to the D-08 fix must leave this path's inputs and defaults
  untouched for the case where `buildDepotPlan` succeeded and something was actually attempted.
- **Case C is already-correct behaviour that needs no change.** No code runs on a hard process
  kill; nothing this plan or 23.2-02 does can affect it, because `finalize()` itself never
  executes.
- **Case A is the only case D-08's fix targets.** The fix must distinguish "nothing was attempted
  this run" (`attempted === []` AND `buildid === undefined`, both only true when `buildDepotPlan`
  itself threw before its loop ran) from "downloaded but unverified" (case B, where `attempted` is
  populated even on failure/cancel). A correct fix does not touch the catch block's unconditional
  `await finalize()` call itself (`depot.ts:2836`) — Pattern 5 (manifest write always the last
  filesystem action, never rethrows) is a separate, still-load-bearing invariant documented at
  `depot.ts:2700-2705` and `depot.ts:2832-2835`. The fix is about what `finalize()`/`finalizeToSteam`
  do with an empty `attempted` + undefined `buildid`, not about whether `finalize()` runs.
