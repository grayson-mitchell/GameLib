# Phase 23.2: Steam depot selection — required-vs-optional depots and skip-and-warn on a Blocked key - Context

**Gathered:** 2026-08-19
**Status:** Ready for planning

<domain>
## Phase Boundary

When Steam refuses a decryption key for one owned depot, GameLib finishes the install without that
depot instead of aborting the whole install — and says so. Closes gap **G-23-01**.

**In scope:** the skip-and-warn policy in depot selection/error handling, the manifest that a
skip produces, the user-facing message, and (folded in) the failure-path manifest write that can
clobber a complete install's `.acf`.

**Out of scope:** selecting depots GameLib currently misses (there are none — proven, see below),
any retry/repair path for a skipped depot, delta-patching, and any new user-facing toggle.
</domain>

<decisions>
## Implementation Decisions

### Skip trigger

- **D-01: Only `EResult 40` (`Blocked`) triggers skip-and-warn.** The other members of
  `NON_RETRYABLE_ERESULTS` (`{8, 9, 15, 17, 42, 43}`) continue to abort the install exactly as
  today. Rationale: 15 (`AccessDenied`) and 17 (`Banned`) plausibly signal a genuine account or
  ownership problem, and silently downgrading those to "skipped a depot" would hide something the
  user needs to act on. Widening the set is an explicit future decision requiring an observed
  real-world failure — **do not widen it speculatively.**

- **D-02: No essentiality guard — any blocked depot is skippable.** GameLib does not attempt to
  decide whether a depot is "required". Rationale: Steam itself decides which depots an account is
  entitled to, so a key Steam refuses is one the official client would not install either. This is
  evidenced, not assumed: for KCD2 (1771300), GameLib's selected set **minus the blocked depot**
  equals the official client's installed set **exactly**. Explicitly rejected alternatives —
  "never skip the largest depot" (arbitrary; 735 MB vs 82 GB was a coincidentally clear case, a
  mid-size essential depot would slip through) and "require a positive optional signal in appinfo"
  (**no such signal exists** — this would block the fix indefinitely).

### Manifest outcome

- **D-03: A skip still earns `StateFlags=4`, with the skipped depot omitted from
  `InstalledDepots`.** This **reframes D-01-of-Phase-23 rather than overriding it**: once a depot is
  skipped, the *plan* is the reduced set, and completeness is measured against the **post-skip
  plan**, not the pre-skip selection. GameLib did completely install what it set out to install.
  Planner note: this means the plan must be reduced **before** the completeness gate runs, so
  `allFilesVerified` / `allModesApplied` / byte totals are all computed over the reduced plan —
  **not** a special-case escape hatch bolted onto `canWriteFullOwnership`.

- **D-04: Every other `canWriteFullOwnership` input is unchanged and still fails closed.** A skip
  alone does not disqualify a `4`, but any other completeness doubt (failed sha1, unapplied mode,
  missing/zero buildid, non-`completed` outcome) still falls back to `1026` as today. **No new
  escape hatch.**

- **D-05: No recovery path if the depot later becomes available.** Consistent with Phase 23's D-05
  (updates are Steam's job). Once the manifest is adopted, Steam owns the app and will fetch the
  depot itself if entitlement changes. GameLib adds no repair logic and does not re-check.

### User signalling

- **D-06: The install reports success AND names the skipped depot** — a completion notice, at the
  moment the user is actually paying attention. Log-only was explicitly rejected: a silently
  incomplete install is precisely the failure class this project has repeatedly been bitten by.

- **D-07: Repurpose 23-09's `steam.download.error.depotBlocked` copy as the skip warning.** This
  change makes that string **unreachable for the case it was written for** six days ago (EResult 40
  no longer aborts), so it gets a deliberate disposition rather than quietly becoming dead code.
  Rewrite it from "install failed, try Steam" to "installed without depot N".
  **It MUST get a NEW i18n key** — renaming a label via the `t()` default argument is a silent
  no-op when the key already exists, and this repo has been bitten by that. Localisation is a
  standing requirement for all fork-added user-facing strings.

### Claude's Discretion

- Where exactly the reduced plan is produced (inside selection vs. at the key-resolution failure
  site), how the skipped-depot list is threaded to the completion notice, and the shape of the
  regression tests. All implementation — planner's call.

### Folded Todos

- **`.planning/todos/pending/2026-08-19-failed-plan-build-writes-1026-stub-manifest-clobbering-a-complete-install.md`**
  (major) — **FOLDED IN FULL (D-08).** A native install that fails at plan-build and downloads
  **zero bytes** still writes an `appmanifest_*.acf`: `StateFlags 1026`, `buildid 0`, and **no
  `InstalledDepots` at all** (402 bytes replacing a 989-byte real manifest). Observed 2026-08-19
  against KCD2's real 90 GB bottle install; Steam would have treated a complete install as needing
  a full verify or re-download.

  **Why it belongs here rather than in its own phase:** same code path, and this phase is already
  editing failure handling. More pointedly — fixing selection **removes the one reproduction we know
  how to trigger** (EResult 40 stops aborting), so leaving it would ship a live data-destructive
  defect that just got harder to find.

  Three sub-items travel with it:
  1. **Settle the contradiction.** Two standing records claim a failed install writes no manifest —
     the 2026-08-16 aborted-residue todo (whose reconciler argument *depends* on it) and 23-UAT.md
     Gate 2 Attempt 1. Today's run contradicts both. Most likely explanation: the 2026-07-21 check
     looked in the **macOS** `steamapps` while this Windows title installs into the **CrossOver
     bottle**. Confirm which, and correct whichever record is wrong.
  2. **Follow the size lead first.** The stub's `SizeOnDisk` is `96,422,090,071` — exactly the
     selected-depot sum **minus the blocked depot**, and byte-identical to the official client's
     figure for its complete 3-depot install. **The reduced-plan size accounting D-03 needs may
     already exist.** Establish where that number is computed before building anything.
  3. **Do not regress the Phase 21 `1026` verify-handoff**, which legitimately writes `1026` on
     paths that *did* download.
</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- **`selectDepots`'s existing skip machinery** — already filters candidates on `oslist`, `osarch`
  and `language`, and logs **every** skip with its reason. Verified live 2026-08-19: 1771305
  (czech), 1771307 (french), 1771308 (german), 1771309 (japanese), 3118101 (spanish) all correctly
  skipped. **This phase adds a required-vs-optional axis to a filter that already exists and is
  already observable — it does not build classification from nothing.**
- **23-09's observability half is already shipped** — `classifyDepotError` has a dedicated EResult 40
  branch naming the specific blocked depot id, and `wrapDepotKeyError` logs depot id / owning appId /
  EResult at the failure site. Only the *policy* is missing. Do not rebuild either.
- **`selectAllDepots`' two ownership channels** (direct `depotids`, and DLC-app ownership) plus its
  existing `depotfromapp`/`sharedinstall` exclusion — a precedent for "owned but deliberately not
  installed", which is structurally what a skipped depot is.

### Established Patterns
- **Fail-closed completeness** (`canWriteFullOwnership`) — a single pure predicate, exact boolean AND,
  no partial-credit path, defaults on every input so an omitting caller fails closed. D-03/D-04 must
  preserve this shape.
- **Census logging before the fact is needed** — `stage=plan-build` fires at `buildDepotPlan` return
  *before any bytes download*, which is what made this phase's decisive evidence free to collect. Any
  new diagnostic should follow that placement rule.

### Integration Points
- Key-request failure site (`wrapDepotKeyError`) → plan reduction → completeness gate → manifest write.
  The reduction must land **upstream of** the completeness gate (D-03).
- Completion reporting → the new skip-warning string (D-06/D-07).
</code_context>

<specifics>
## Specific Ideas

- **The KCD2 evidence is the acceptance benchmark.** GameLib's selected set is
  `{1771302, 1771303, 1771304, 1771306}`; the official Windows Steam client's installed set is
  `{1771302, 1771303, 1771306}` at `StateFlags 4`, `SizeOnDisk 96,422,090,071`, `buildid 23914554`.
  **After this phase, a GameLib install of 1771300 should produce that same depot set and the same
  SizeOnDisk.** That is an unusually concrete, externally-authored target — use it.

- **The diagnostic is DONE — do not re-run it.** The verdict came from the official client's own
  artifacts (bottle `appmanifest_1771300.acf` + `content_log.txt`, which never mentions 1771304
  across the entire 2026-07-11→08-15 install). Re-installing KCD2 in the official client would cost
  90 GB and regenerate identical data.

- **Honesty limit to preserve:** the evidence proves 1771304 is not *needed*; it does **not** prove
  Steam would have granted its key to the official client — that client never asked.

- **Anti-vacuity requirements**, both learned the hard way in this repo:
  - A test for the folded manifest bug must run against the **bottle** path for a Windows title, not
    only the macOS `steamapps` — checking the wrong directory is the likeliest reason this went
    unnoticed for a month. Assert on manifest **content** (`InstalledDepots` present, `buildid`
    non-zero), never on mere file presence.
  - Any grep/process/skip assertion must be demonstrated to **fail against a known-bad input**
    before it is trusted. A vacuous check that returned a clean result for 72 consecutive samples
    was caught in this phase's own prep only by asking "could this ever fire?".
</specifics>
