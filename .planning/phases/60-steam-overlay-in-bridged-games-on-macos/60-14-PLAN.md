<objective>
Close G4 (UAT item 7). On two shim-missing launches, the backend logged
`[bridge-notice] appId=3205720 reason=overlay-shim cause=overlay-shim-missing` and handed the notice to
tauri-plugin-notification, but the operator saw nothing. The overlay notice is OS-notification only
(games.ts `notifyOverlaySetupFailed`). Phase 59 hit the same wall (59-UAT G6) and fixed it with the
in-app, non-modal `SteamEngineLaunchNotice`, fed by the `steamEngineStateChanged` push and its
seq-tracked `launchNotice`. This plan reuses that surface for overlay failures. D-08's "never a
dialog" stays intact (no `showEngineDialog`, no `showDialogBoxModalAuto`, no `raiseMainWindow`),
and so does D-09's "every affected launch" (a new seq per failure).

Discretion choice (CONTEXT "toast component and copy, following the existing bridge-notice patterns"):
the overlay notice reuses the existing catalogue strings `steam.overlay.toast.title`,
`steam.overlay.toast.body` and `steam.overlay.step.*`, so no new copy is needed. Unlike the engine
notice, its 8 s auto-hide starts only once GameLib is visible and focused. Overlay failures fire as
the game comes to the front, so a plain 8 s timer would expire unseen.

Output: an overlayNotice field, a backend publisher, a games.ts call, and the frontend rendering, each with tests.
</objective>
