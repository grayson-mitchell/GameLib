## Legend

Owner tokens, one per cell:

- `SC`: the sidecar (TypeScript store classes over `store_backend.ts` (conf) for persisted state (the Phase 27 sidecar file store never ran in production and was deleted by quick 261121-pwt, 2026-11-21), a TS object in the sidecar for in-memory state). Sole writer.
- `RH`: the Rust `StoreHost` in `gamelib-core`. Sole disk writer; the TS store class becomes a read-mostly write-through mirror (writes are ordered frames to Rust) until the mirror-deletion slice in the "TS mirror deleted" column.
- `R`: a Rust domain owner (the actor or crate named in the "Rust owner" column of the in-memory table). `X`: deleted, no owner (the state has no Rust equivalent).
- `ext`: written by a process outside GameLib (the Steam client, the legendary binary); GameLib only reads. `per-channel`: owned channel by channel, never as one object (the IPC handler table).
- A trailing `*` marks the one cell where the row flips. After the flip the token is unchanged through 99. A row with two `*` marks would be a double move; there is none, with the one conditional exception recorded under "Sequencing rule".

Kinds: `cache` (discarded on a shape-changing version bump) and `user-state` (migrated, never discarded) per D-01 and Phase 68.

Slices: 83 seam/core, 84 logger, 85 store host, 86 leaves, 87 engine, 88 launch, 89 libraryState, 90 Steam services, 91 Epic, 92 GOG/Amazon/sideload, 93 download manager, 94 Humble/shortcuts, 95 bridge install, 96 bridge launch, 97 bridge DRM/overlay, 98 shell cutover, 99 sidecar deletion.

## In-memory owners

Tier follows ARCHITECTURE 2.4: "domain" is long-lived state owned by one Rust actor or `Arc<Mutex>`, "scratch" is per-request state (single-flight maps, abort handles) that lives inside the crate using it and is never a global. A mirror is allowed only for persisted state (above); in-memory state flips whole, with the TS object deleted in the same slice (the Phase 80 libraryState event path is the existing example).

## Sequencing rule

No owner moves twice. Each row above carries at most one `*`; the owner tokens before it are one value and after it one value through 99. Rows keyed by the same boot step but different state items (for example `steam-bridge-runtime:redist-install` and `steam-bridge-runtime:clones`) flip independently at their own slices, because ownership is per state item, not per boot step.

Assumptions the table rests on, stated so the operator can contradict them:

- A1: every registry store flips to `RH` at 85, in one slice, not per subsystem as its consumers port. Reason: 85's success criteria delete the TypeScript `storeVersioning`, `storeMigrations` and `migration/*`, so a store left on the sidecar after 85 would have no TS versioning engine; ARCHITECTURE 2.5 item 3 (per-subsystem flips, config last) predates the roadmap and conflicts with 85's goal ("Rust is the only disk writer for settings, caches and per-game config"). The table follows the roadmap. If the operator prefers the per-subsystem order, rows flip at their "TS mirror deleted" slice instead and the TS versioning engine must survive past 85.
- A2: a "TS mirror deleted" slice is the slice that ports the last TS consumer of that store; it is a cache deletion, not an ownership move (the writer is `RH` throughout).

### Roadmap risks (operator decision needed)

- R1, the only row that can force a double move: `uploadedLogs`. Phase 84 requires log upload and delete-uploaded to work against the native logger, which must read and write this store's list, but the store host arrives in 85. Options: (a) 84 carries the minimal `StoreHost` core (open, atomic write, change event) for this one store and 85 widens the same owner, so the row flips once, at 84 (this table's choice); (b) the native logger keeps its own private file for 84 and 85 adopts it, which is a second move; (c) the logger calls back into TS for the list, rejected by ARCHITECTURE anti-pattern 2 (no Rust calling into TS for state).
- R2: `steamConfigStore` and `steamBottleConfigStore` share one file (`steam_store/config.json`, one in-process cell). They must flip together at 85; their TS consumers split between 90 and 96, so the TS mirror of that single file lives until 96. Not a double move, but a file with two TS-side names for one `RH` owner.
- R3: `global-config` flips to Rust at 85 while the TS `settingChanged` event bus is deleted only at 98. Between those, every TS subscriber needs Rust to push the change (event inversion, ARCHITECTURE 2.5 item 4), a temporary two-sided structure that is a cache of a Rust-owned value and has a named deletion point (98).
- R4: `steam-session-state` builds `libraryState` and `gameSession` (flip 89) and the sign-in state (flip 90) as one object consumed together by every manager's deps. During 89 the object is half Rust-owned by item. Do not "fix" this by splitting libraryState across phases (ARCHITECTURE 4.3 forbids it).
- R5: `isEpicServiceOffline`, the launcher's Epic gate (88), needs the 86 connectivity leaf, and `sendGameStatusUpdate` and `sendProgressUpdate` (inventory) keep a TS emitter until the last TS caller (97); no state changes owner, but slices 88-97 each need both the Rust `FrontendEmitter` and the TS bus emit to keep working for their respective callers.

Conclusion for the roadmap: with option (a) for R1 the table has zero double moves. Under (b) the single row `uploadedLogs` moves twice; no other row is exposed.
