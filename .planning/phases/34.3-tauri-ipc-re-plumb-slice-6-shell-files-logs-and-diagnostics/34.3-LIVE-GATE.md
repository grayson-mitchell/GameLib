### Deviation: SEA sidecar build was broken by a pre-existing (Phase 34.2) defect, fixed here as a Rule 3 blocking-issue auto-fix

`pnpm build:sidecar-sea` failed on first run with:
```
Error: COMPILE GATE FAILED (D-06): esbuild SEA bundle exited 1:
✘ [ERROR] Top-level await is currently not supported with the "cjs" output format
    node_modules/i18next-fs-backend/esm/writeFile.js:7:20
    node_modules/i18next-fs-backend/esm/readFile.js:8:20
```

**Root cause (confirmed, not guessed):** `src/backend/sidecar/bootstrap.ts` does
`import Backend from 'i18next-fs-backend'` (added by commit `a8e7c8093`,
`feat(34.2-01): initialize i18next in sidecar bootstrap (D-02)` — **Phase 34.2, not this phase**).
`i18next-fs-backend`'s `package.json` `"exports"` map resolves the `import` condition to
`./esm/index.js` regardless of the bundle's own `--format=cjs` output (a dual-package hazard —
esbuild picks the condition based on how the specifier is referenced in source, not the bundle's
target format). The ESM variant's `writeFile.js`/`readFile.js` use a top-level
`await import('node:fs')` Deno-detection guard, which is illegal in a cjs bundle. This has been
silently broken since 2026-07-25 (Phase 34.2) — nobody had re-run `build:sidecar-sea` since, so
this is the first time it surfaced. **None of 34.3's own 25 touched files caused this.**

**Fix applied (Rule 3 — blocking build-config error, no package install involved):** added
`'--alias:i18next-fs-backend=i18next-fs-backend/cjs'` to `meta/buildSidecarSea.ts`'s
`buildEsbuildArgv()` flags, forcing esbuild to resolve the package's own genuinely-CJS `./cjs`
subpath export (confirmed by direct inspection: `cjs/writeFile.js` uses plain
`require('node:fs')`, no top-level await) — mirroring the existing `--alias:electron=...` entry in
the same array. Also added the new flag to `meta/__tests__/buildSidecarSea.test.ts`'s
"carries the required bundling flags" `arrayContaining` assertion (44/44 tests in that suite still
green). Re-ran `pnpm build:sidecar-sea`: **PASS**, produced
`src-tauri/binaries/gamelib-sidecar-aarch64-apple-darwin`. Standalone smoke-tested with
`PATH=/usr/bin:/bin` (no system Node, no reachable `node_modules`), stdin held open: printed
`__GAMELIB_SIDECAR_READY__` with no crash, mirroring 34-02's original verification protocol
exactly.

**Files modified by this fix:** `meta/buildSidecarSea.ts`, `meta/__tests__/buildSidecarSea.test.ts`
(commit recorded separately from this document's own commit — see Task 1 commit list).

**Evidence — process count (attested):** Tester ran `pgrep -fl gamelib-sidecar` before and ~10s

Verbatim output not retained. Tester confirmed the app **restarted** rather than quitting and

This empirically confirms plan 34.3-03's Q1 finding — read directly from tauri 2.11.5 source — that

It also closes research Assumption A1 (the untraced `request_exit` delivery guarantee inside
`tauri-runtime-wry`). Threat T-34.3-33 (orphaned sidecar retaining an authenticated Steam session)
is therefore not realised on the packaged path.

**Evidence — post-conditions (machine-verified, reproducible):**
- `~/Library/Application Support/GameLib/GamesConfig/` — **absent** ✅
- `~/Library/Application Support/GameLib/config.json` — **present, but pristine factory-default**:

  Every value matches `getFactoryDefaults()` in `src/backend/config.ts:340-380`, including the two

  `enableSteamNativeInstall: false` (L374). Also `steamGridDbApiKey: ""`, `customWinePaths: []`,

- Sibling stores (Steam token + library, the 10 Humble stores, download manager, Wine and

**Correction to this plan's stated acceptance criterion.** The plan required both that the app

### Defect found by this item and FIXED in-phase (commit `44232d3e`)

On the first run the dialog reported *"Uploaded to (URL copied to your clipboard)"* but the
clipboard still held the previous step's contents — the message was false under Tauri.

**Root cause:** `LogFileUploadDialog/index.tsx:43` used `navigator.clipboard.writeText(url)` — the
**Web Clipboard API**, not this app's clipboard channel. Under Electron the Chromium renderer grants
clipboard-write so it works; under Tauri the renderer is WKWebView, which resolves the promise
without writing. It did not *reject* — `setUploadUrl(url)` still ran, which is why the success
message rendered at all. Not a capability issue: the zero-grant D-02 stance gates Tauri IPC, not Web
APIs.

**Fix:** routed both surviving `navigator.clipboard` call sites through the channels THIS PHASE
built and unit-proved —
- `LogFileUploadDialog` → `window.api.clipboardWriteText`
- `EditGameDialog` → `window.api.clipboardReadText`

Both are registered in **both** builds (`main.ts:1425`/`1427` under Electron,
`clipboardFlowRegistration.ts:77`/`90` under the sidecar → the Rust arms), so the change is
parity-safe in each direction. Zero `navigator.clipboard` call sites remain in the codebase.
Verified: `tsc --noEmit` clean, prettier clean, Frontend 200/200, Backend unchanged at 2400/2401.

This is a genuine Tauri-parity regression that only an OS-level observation could surface — jest
asserts channel dispatch, and this code path never touched a channel. Precisely the class of defect
D-13 made this gate blocking for.
**Observed at:** 2026-07-27, during the tauri:dev gate session
