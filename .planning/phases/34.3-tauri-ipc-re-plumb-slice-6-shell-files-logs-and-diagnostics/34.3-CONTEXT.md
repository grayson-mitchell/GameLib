**Gathered:** 2026-07-26

## Phase Boundary

Port the **shell, files, logs and diagnostics** IPC cluster (29 channels) onto the Tauri
build, following SEAM.md's Incremental-Port Checklist. This is the sixth re-plumb slice.
Additive and reversible — `npm start` (Electron) and `pnpm tauri:dev` must both work when
the phase closes.

**Shape of the work — established during scouting:**

Channel homes: **23 in `src/backend/main.ts`**, **5 in `logger/ipc_handler.ts`**
(`logInfo`, `showLogFileInFolder`, `uploadLogFile`, `deleteUploadedLogFile`,
`getUploadedLogFiles`), **1 in `utils/ipc_handler.ts`** (`copySystemInfoToClipboard`).

Functional grouping (this is the useful decomposition, not the file split):

| Group | Count | Channels |
|---|---:|---|
| Link/reveal openers | 15 | `openExternalUrl`, `openFolder`, `openSupportPage`, `openWeblate`, `openLoginPage`, `openDiscordLink`, `openPatreonPage`, `openKofiPage`, `openGithubSponsorsPage`, `openWinePrefixFAQ`, `openWikiLink`, `openSidInfoPage`, `showConfigFileInFolder`, `showItemInFolder`, `showLogFileInFolder` |
| Clipboard | 3 | `clipboardReadText`, `clipboardWriteText`, `copySystemInfoToClipboard` |

| Logger + upload | 4 | `logInfo`, `uploadLogFile`, `deleteUploadedLogFile`, `getUploadedLogFiles` |

**Three findings that make this slice CHEAPER than 34.1/34.2:**

1. **The 15 openers are nearly free.** All reduce to `openUrlOrFile()` / `showItemInFolder()`
   in `utils.ts` — a module **already in the sidecar's import graph** (34.1,
   `appShellFlowRegistration.ts:106`) and already baselined in the electron-reach ledger.
   They reach the **already-built** `open_external` / `shell_open_path` /
   `reveal_item_in_dir` Rust arms. 12 of the 15 share one code path.
2. **Zero new store plumbing.** `uploadedLogFileStore` is already registered
   (`storeRegistration.ts:115`, Phase 29 D-15's fourth extraction) and so is
   `gogAchievementStore`.
3. **`resetHeroic`'s lifecycle seam already exists.** Phase 33 Plan 04 (D-05) built
   `app.quit()`/`app.relaunch()` → `RUST_APP_EXIT`/`RUST_APP_RELAUNCH`, and its docstring
   explicitly names *"resetHeroic's relaunch+quit"* as an intended caller.

**And the finding that makes it harder — the slice's one genuinely missing platform seam:**
`electronStub.clipboard.writeText` is a **logged no-op** (`electronStub.ts:579`, marked
"deferred to Phase 33" — Phase 33 never collected it), `clipboard.readText()` returns `''`
**silently**, and there is **no clipboard plugin in `Cargo.toml`**. Three channels need it,
and it is load-bearing on the shipped Humble key-claim flow.

**In scope — all 29 channels, no reassignments:**
- The 5 functional groups above, ported at parity.
- **A real clipboard seam** (**D-01**, **D-02**): `tauri-plugin-clipboard-manager` + two new
  `dispatch_rust_channel` arms, called Rust-side with **zero** renderer capability grant.
- **A relaunch-teardown fix** (**D-05**, **D-06**): verify whether `AppHandle::restart()`
  fires `RunEvent::Exit`; if not, kill the sidecar child before restarting, and guard
  `electronStub.app.quit()` against the relaunch race.
- **Cargo tests + a jest existence gate** for both Rust changes (**D-07**).
- **Extending `electronReachLedger.test.ts`** with this slice's entry points (**D-10**).
- `34.3-PORTED-CHANNELS.md` declared list + SEAM.md §3→§1 move.
- **A narrow, blocking live gate** (**D-11**, **D-12**, **D-13**) — this slice deliberately
  breaks the D-11/D-15/D-04 unit-proven-only precedent.

**Explicitly OUT of scope:**
- **Log redaction** (**D-09**) — logs reach a public paste unredacted; pre-existing in both
  builds, security todo filed, no audit this slice.
- **Fixing the lying delete button** (**D-08**) — `deleteUploadedLogFile` is dead in *both*
  builds; ported at parity and declared, the UI fix is a separate todo.
- **Adding a cargo step to CI** — the root cause behind the awkward Rust proof story;
  deferred (**D-07** rejected option).
- **Re-registering `logError`** — ported early by 34.2 gap cycle 2 (plan 34.2-16). Must NOT
  be registered a second time.
- Any change to the Electron build's *behavior*. As in 34.1/34.2 this slice may touch
  Electron-side files; the invariant is behavioral, not textual.

## Implementation Decisions

### The clipboard seam — the slice's one new platform capability

- **D-01 — BUILD the real clipboard seam.** Do not ship no-ops. Clipboard genuinely *is* a
  platform capability, so this is a legitimate answer to 34.2's standing "expect zero new
  Rust arms; if it needs new Rust work, stop and ask why" rider. **Load-bearing evidence
  from scouting:** `clipboardWriteText`'s callers include `HumbleClaimWizard/index.tsx:120`
  and `:366`, which copy a **revealed Humble game key** — the guided-claim flow that is the
  core deliverable of milestone v0.3. A no-op there means the user reveals a key and the
  Copy button silently loses it. `clipboardReadText`'s only caller is the Epic SID login
  paste (`SIDLogin/index.tsx:137`), which today receives `''` with no diagnostic at all.
  Also pays off `electronStub`'s own "deferred to Phase 33" debt, which Phase 33 never
  collected. Rejected: write-only real with read left as a no-op (ships a structurally-dead
  channel, exactly what Phase 32 **D-01** and 34.1 **D-11** refused); deferring all 3 to
  Phase 35 (blocks the Phase 35 gate and knowingly ships a broken Copy on the v0.3 flow).
  **Honest bookkeeping rider:** unlike 34.2's D-02/D-07, this missing seam has **never
  silently degraded a shipped Tauri path** — the only backend consumers of
  `clipboard.writeText`/`readText` are this slice's own 3 channels. The no-op was purely
  precautionary. Do not describe this as a latent shipped defect.

- **D-02 — `tauri-plugin-clipboard-manager`, called from RUST, with ZERO renderer grant.**
  Add the plugin to `Cargo.toml` + `.plugin(tauri_plugin_clipboard_manager::init())`, and
  call `app.clipboard().write_text()` / `read_text()` from inside `dispatch_rust_channel`.
  Add **no** `clipboard-manager:*` permission to `src-tauri/capabilities/default.json`.
  **Rationale is that file's own stated principle:** "Tauri v2 capabilities gate
  WEBVIEW→Rust IPC only; they are not consulted for Rust-side plugin API calls" — which is
  exactly why Phase 33 **WR-03** refused `dialog:allow-open` and routes the file picker
  through Rust instead. The capability is scoped `"windows": ["main"]`, and GameLib renders
  **untrusted remote content in that same window** (the store-search surface today, the
  Humble login flow in 34.4) with no `<webview>` isolation boundary. Granting clipboard
  *read* would hand a credential-exfiltration primitive to that remote content. Rejected:
  granting `clipboard-manager:default` and calling the plugin from the frontend (contradicts
  the capability file's own principle for a small convenience); the `arboard` crate directly
  (defensible — the `keyring` arms use their crate directly — but we would own X11
  clipboard-ownership and Wayland quirks ourselves for no gain over the official plugin).

- **D-03 — Clipboard write failures are LOG-ONLY, at Electron parity.** Fire-and-forget the
  `requestRustInvoke` and log on rejection — exactly the shape `shell.showItemInFolder`
  already uses (`electronStub.ts:437`). Real Electron's `clipboard.writeText` is `void` and
  cannot surface failure either, so matching it keeps the builds behaviorally identical and
  adds nothing to unwind at cutover. Rejected: a user-visible failure toast (better UX on
  the key-copy path, but behavior Electron does not have — a divergence to declare and later
  reconcile, and arguably a feature rather than a port). **Declaration rider:** record the
  Humble key-copy silent-failure risk in `34.3-PORTED-CHANNELS.md` as a known accepted risk,
  so it reads as a decision rather than an oversight.

- **D-04 — The read path awaits Rust in the HANDLER, not through the sync stub.**
  `electronStub.clipboard.readText()` is synchronous (`(): string`) and structurally cannot
  await a Rust invoke. But `clipboardReadText` is registered with `addHandler` (async), so
  the sidecar registration can `await requestRustInvoke(...)` itself and never touch the
  stub. Leave the stub's sync `readText` in place as a **documented, deliberately-dead**
  no-op — no backend module other than `main.ts`'s handler calls it. Rejected: making the
  stub's `readText` return `Promise<string>` (the stub exists to mimic real Electron's
  shape for hook-rescued modules; real `readText` IS sync, so this would make the stub lie
  about the API it impersonates); deleting `readText` from the stub (a future hook-rescued
  caller would hit a TypeError instead of a degraded-but-safe return).

### resetHeroic — the destructive channel

**What it actually does** (`utils.ts:466`, 11 lines): deletes `configPath`
(`~/…/GameLib/config.json`, global settings) and `gamesConfigPath`
(`~/…/GameLib/GamesConfig/`, per-game settings), then after a 1s `setTimeout` calls
`app.relaunch()` + `app.quit()`. It is the "Reset GameLib" button in Settings → Advanced
behind a Yes/No confirm (`GlobalState.tsx:552`). **It is much narrower than its UI copy
suggests:** the ~20 `electron-store` files (Steam token + library, all 10 Humble stores,
download manager, Wine, wiki/crossover caches) are *siblings* of `config.json` in
`appFolder` and are **not** deleted. The dialog's "removes all Settings and Caching" already
overclaims in Electron. `config.json` is **not** electron-store-managed — it is owned by the
`GlobalConfig` singleton, which holds settings in memory and writes the file back. That is
what the `// wait a sec to avoid racing conditions` setTimeout weakly hedges against.

- **D-05 — VERIFY whether `AppHandle::restart()` fires `RunEvent::Exit`; if not, kill the
  sidecar child in the `app_relaunch` arm before restarting.** The only thing that kills the
  sidecar is the `RunEvent::Exit` handler (`main.rs:1042`), added by Phase 34 **WR-03**
  precisely because an unkilled sidecar "can be left running as an orphan… retaining an
  authenticated Steam session, open network sockets, and file handles." But
  `app_relaunch` calls `app.restart()`, which **never returns** (`-> !`) and exits the
  process directly rather than through the event loop. **If it bypasses `RunEvent::Exit`,
  `resetHeroic` under Tauri orphans the old sidecar AND the restarted shell spawns a second
  one — and the orphan holds a live `GlobalConfig` that can rewrite the `config.json` the
  reset just deleted.** In Electron that race window is ~1s and then the process dies; under
  Tauri it would be indefinite. Fix = `state.shutdown_child()` before `app.restart()` — a
  small contained change that makes relaunch honest for every future caller, same class of
  fix as WR-03 itself. **This inference is from Tauri's API semantics, NOT from a test —
  research MUST verify it empirically before the fix is written.** If `restart()` *does*
  fire `RunEvent::Exit`, drop the fix and record the verification. Rejected: porting at
  parity and declaring the risk (a reset that silently restores the settings it deleted is a
  confusing bug, and the orphan keeps an authenticated Steam session alive); delete-then-quit
  with no relaunch (deterministic and safe, but a declared UX divergence); not porting
  resetHeroic (leaves a channel blocking the Phase 35 gate).

- **D-06 — Resolve the `relaunch(); quit()` race INSIDE `electronStub`.** In real Electron
  `app.relaunch()` only *registers* a restart and `app.quit()` performs it — both needed,
  ordered, in one process. Under Tauri `app.restart()` alone does everything, and the stub
  forwards both calls as **separate fire-and-forget frames** dispatched on spawned worker
  threads (see the `app_relaunch` docstring, `main.rs:576`), so `app_exit` can be processed
  **first** and the app quits instead of restarting, nondeterministically. Fix: a
  module-scope "relaunch in flight" flag set by `electronStub.app.relaunch()`, after which
  `app.quit()`/`app.exit()` become logged no-ops. **This keeps `resetHeroic`'s shared body
  byte-identical for both builds — no `isTauri()` branch in `utils.ts`** — and contains the
  whole divergence in the stub, where every other Electron-shape impedance mismatch already
  lives. Rejected: branching inside `resetHeroic` (puts a build conditional in shared backend
  code, one more thing for Phase 35 to unwind); serializing `dispatch_rust_channel`
  (fixes it for all callers but touches the hot path for every `rustInvoke`); accepting the
  race (ships known nondeterminism on a destructive action).

### Proving the Rust

- **D-07 — Cargo tests + a jest existence gate. No CI change.** `main.rs`'s own docstring
  records that **this project's CI runs no cargo step at all** — `.github/workflows/*.yml`
  contains neither `cargo test` nor `cargo check`. This slice adds more new Rust than 34.1
  and 34.2 combined (two clipboard arms + the D-05 teardown fix). Follow the precedent 34.2
  plan 22 set for `timeout_for()`: write real `#[cfg(test)]` tests, run them manually
  (`cd src-tauri && cargo test`), record the **hand-verified RED proof in the SUMMARY**, and
  pin their continued existence with a jest source gate. Rejected: adding a cargo step to CI
  (highest long-term value and this slice is the natural forcing function, but it is
  CI/infrastructure work inside a port slice — **kept as a deferred idea**); a live gate
  instead of Rust tests (leaves no regression net); doing both (largest scope expansion).

### Log upload

- **D-08 — Port all 3 log-upload channels at parity; DECLARE `deleteUploadedLogFile`'s
  structural deadness.** `uploader.ts:74-77` hardcodes `const token = '1'` with the comment
  *"dpaste.com does not support deleting files, there's not token… I'll hide the delete
  option."* **The delete option was never hidden** —
  `UploadedLogFilesList/index.tsx:60` still wires a live button to it. So it POSTs a bogus
  token to the paste URL and either fails, or falsely reports success and drops the local
  store entry while the paste stays public. **Key distinction from 34.2 D-07:** that channel
  was dead *only under Tauri* (a port-introduced gap, so fixing it was in scope). This one is
  **equally dead in both builds** — an inherited upstream Heroic defect the port neither
  introduces nor worsens. So port it faithfully, record per-row in
  `34.3-PORTED-CHANNELS.md` that "ported" does **not** mean "delete works", and file the
  UI-lies-to-the-user bug as a separate todo. Rejected: fixing the button here (a frontend
  behavior fix riding inside a port slice, and it changes Electron's behavior); leaving the
  channel rejecting (blocks the Phase 35 gate).

- **D-09 — Log redaction is OUT OF SCOPE; file a security todo, run no audit.**
  `uploadLogFile` sends up to **10 MiB of log content** to dpaste.com as a public paste with
  a 2-day expiry, and there is **no redaction anywhere in `src/backend/logger/`**. GameLib
  adds Steam refresh tokens and revealed Humble key values that upstream Heroic never had.
  The threat surface is identical in both builds and predates this slice, and the upload is
  behind a confirm dialog (`LogFileUploadDialog`). **User explicitly declined a bounded audit
  of whether a token or key value can actually reach a log line** — do not perform one, and
  do not treat this as an open question during planning. File the security todo and move on.
  Rejected: the bounded audit; adding redaction in this slice.

- **D-10 — EXTEND `electronReachLedger.test.ts` with this slice's entry points.**
  `logger/uploader.ts:1` imports `app` from `electron`, so porting these channels adds
  modules to the electron-reach graph. The ledger's `ENTRY_POINTS` currently lists only
  34.2's four game-details files, yet its docstring states the committed baseline **"IS the
  Phase 35 cutover work-list"** — which only holds if it covers the whole ported surface.
  Add this slice's entry points and **regenerate the baseline at execution time, not from
  planning-time prose** (the ledger's own instruction). Preserve its growth-only/subset
  semantics and its anti-vacuity tests. Rejected: a new slice-scoped ledger file (fragments
  the Phase 35 work-list, and each slice adds another); a depth-1 import gate only (the
  ledger's docstring exists *specifically* to record that depth-1 regexes cannot see a
  two-hop edge — this would repeat the mistake it documents).

### Sign-off

- **D-11 — A NARROW, NAMED LIVE GATE is a phase-closing condition.** This slice
  **deliberately breaks** the Phase 30 **D-04** → 34.1 **D-15** → 34.2 **D-11**
  unit-proven-only precedent, and the reason must be stated plainly rather than copied:
  34.2 could honestly claim "data in / data out with assertable return shapes." This slice
  cannot. Most of its channels' *entire purpose* is an observable OS side effect — jest can
  only assert that `requestRustInvoke` was called with a URL, never that a browser opened or
  Finder revealed anything. Add two Rust arms CI never compiles, plus a destructive channel
  whose failure mode is only visible in the process table, and assertion-only evidence is not
  enough. This is the gate 34.2 deferred as its **"highest-value optional gate."**
  **~5 named items, NOT a 29-channel UAT** (the 12 link openers share one code path, so one
  proves the path):
  1. One opener actually opens a browser.
  2. `showItemInFolder` actually reveals in Finder.
  3. Clipboard write → paste into a text field, and `clipboardReadText` round-trips.
  4. `resetHeroic` leaves **exactly ONE** sidecar process, with `config.json` still gone.
  5. `uploadLogFile` returns a real dpaste URL.
  Rejected: carrying D-11 forward unchanged (consistent, but this is precisely the slice
  where jest sees least); a full 29-channel live UAT (heavily redundant, and expensive
  enough that it tends to get deferred anyway — which is how UAT debt accumulated in Phases
  21/30/34.2).

- **D-12 — Gate build split: `tauri:dev` for most items, a PACKAGED build for the reset
  check.** `main.rs` has two different sidecar spawn paths — `spawn_sidecar_dev()` (L668)
  and `spawn_sidecar_packaged()` (L698), selected by `use_dev_sidecar()` (L660) — and
  `app.restart()` re-execs a different binary in each mode. The orphan question is
  specifically about *which child process gets killed*, so items 1/2/3/5 run under
  `tauri:dev` (fast loop, build-independent paths) while **item 4 must be verified on a
  packaged build**. Same family as 34.2 **D-02**'s packaged-build caveat and the
  `publicdir-getapppath-chunking` gotcha. Rejected: `tauri:dev` for everything (would verify
  the orphan fix against a path users never run); packaged for all items (slow enough that
  failures get expensive to chase).

- **D-13 — Gate failure is BLOCKING: findings become a gap cycle inside 34.3.** A failed
  gate means the phase does not close. This is exactly what Phase 33's **D-13** gate did —
  it surfaced three latent Tauri-parity gaps (notification-capability startup crash, sidecar
  "App offline" from an unwired `initOnlineMonitor`, `windowControlsOverlay` TypeError), all
  fixed in-phase rather than deferred. Rejected: advisory (turns the gate into documentation
  and re-creates the UAT-debt pattern); blocking-with-an-explicit-override-path (the 34.2
  closure mechanism — deliberately not pre-authorized here, though a human override always
  remains available as a conscious act).

### Claude's Discretion

- **The extraction shape for the 23 `main.ts` registrations.** 34.1 **D-07/D-08** and 34.2
  **D-03** established extract-the-body / keep-the-registration. **But this slice needs far
  less extraction than either** — most of the 23 are one-line delegations to functions
  already exported from `utils.ts`, which is **already in the sidecar graph**. Whether to
  register directly against those exports (no extraction) or create a `shell/`-style module
  family for symmetry with `appshell/` is a planner call, provided: registrations stay in
  `main.ts`, D-14's curated-import discipline holds, and nothing new is re-implemented twice.
  The genuinely inline bodies needing attention are `checkDiskSpace`, `clearCache`'s dialog
  wrapper, `showConfigFileInFolder`, and `pathExists`.
- **D-14 — the curated-import rule, inherited unchanged** (Phase 30 **D-08** → 34.1
  **D-09** → 34.2 **D-04**): import the UNDERLYING module, never a feature module's
  `ipc_handler.ts`. **This slice must be especially careful:** `logger/ipc_handler.ts`
  registers **two channels that are already ported** (`getLogContent`, and `logError` via
  34.2-16) alongside three of this slice's. Side-effect-importing it would double-register
  them *and* drag `backend/ipc` in. Import `logger/uploader.ts`, `logger/paths.ts`
  (`getLogFilePath`) and `utils.ts` (`showItemInFolder`) directly. Same for
  `utils/ipc_handler.ts`, whose other channels (`abort`, `getSystemInfo`, `hasExecutable`,
  `isIntelMac`) are all already ported — import `formatSystemInfo`/`getSystemInfo` from
  `utils/systeminfo` directly.
- **`logInfo` must mirror the already-ported `logError` exactly** — same `send` shape, same
  `LogPrefix.Frontend`. A `send` channel registered with `ipcMain.handle` (or the reverse)
  **fails 100% silently** (Phase 31 Pitfall 2, and the `sidecar-send-channels-fail-silently`
  gotcha). Cross-check every registration against `main.ts`'s own
  `addHandler`/`addListener` call for that exact channel.
- **`clearCache`'s `showDialogBoxModalAuto` call and its `sendFrontendMessage('refreshLibrary')`
  push** should ride the existing dialog stub and generic `frontend_message` relay. **The
  dialog stub must RESOLVE a safe default, never reject** — see the
  `sidecar-dialog-reject-crashes` gotcha: making a dialog stub reject hard-crashes the
  sidecar via unguarded fire-and-forget `await`ers. Expect **zero** new Rust arms for these.
- **How the clipboard/teardown Rust work is sliced into plans/waves** is a planner call, but
  D-05's verification must precede D-05's fix in dependency order.
- **Whether `tauri-plugin-clipboard-manager` auto-injects an init IIFE** that invokes a
  plugin command at webview load. **Research MUST check this.** `tauri-plugin-notification`
  does exactly that, and it **crashed startup with an unhandled rejection** until
  `notification:allow-is-permission-granted` was granted (see the capability file's own
  description, and `phase-33-complete`). If clipboard-manager behaves the same way, D-02's
  zero-grant stance needs a narrowly-scoped exception — discover this before writing code,
  not during the live gate.

- **This is the cheapest slice so far on channels and the most expensive on platform work.**
  15 of 29 channels are one code path that already exists end-to-end. The phase's real
  content is three things: a new clipboard seam, a relaunch-teardown bug, and the first

  misread it in the opposite direction from the 34.2 warning.
- **The clipboard no-op is NOT a latent shipped defect** — unlike 34.2's i18next finding.
  Its only backend consumers are this slice's own three channels, so nothing has been
  silently degrading. Say that plainly; do not inflate it into a 34.2-style "already broken
  in production" narrative.
- **`electronStub.clipboard` is the direct descendant of Phase 31 D-04**, which chose a
  logged no-op and wrote "deferred to Phase 33." Phase 33 never collected it. This slice
  closes a two-phase-old promise — worth noting so the change reads as completion rather
  than churn.
- **`resetHeroic` is narrower than everyone thinks.** It deletes `config.json` +
  `GamesConfig/` only. Steam tokens, all 10 Humble stores, and every cache survive as
  siblings in the same folder. The dialog copy overclaims. Anyone reasoning about "reset
  blast radius" should start from that table, not from the button label.

  never returning strongly suggests it bypasses `RunEvent::Exit`, but nothing in this repo

  the plan present the orphan as established fact.
- **The live gate exists because jest structurally cannot see this slice's deliverable.**
  That is the same honest tension 34.1's D-15 named — but 34.1 concluded "defer anyway" and
  this slice concludes the opposite, because it also ships two Rust arms CI never compiles
  and one destructive channel. State the difference; do not present D-11 as a routine
  carry-forward.
- **Check the clipboard plugin for an auto-injected init IIFE before writing any code.**
  `tauri-plugin-notification` crashed startup this way. Discovering the same thing during
