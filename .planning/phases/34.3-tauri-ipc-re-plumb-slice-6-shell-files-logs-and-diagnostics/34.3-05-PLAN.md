<objective>
Give `electronStub.clipboard.writeText` real behavior (D-01/D-02/D-03), keep `readText` a documented
dead no-op (D-04), and fix the `relaunch(); quit()` ordering race inside the stub (D-06).

Purpose (clipboard): the stub's `writeText` is a logged no-op and `readText()` returns `''`
silently. `clipboardWriteText`'s callers include `HumbleClaimWizard/index.tsx:120,366`, which copy a
revealed Humble game key. **Framing:** this has never silently degraded a shipped Tauri path — the
only backend consumers are this slice's own three channels, so the no-op was purely precautionary.
It is the direct descendant of Phase 31 D-04, which wrote "deferred to Phase 33"; Phase 33 never
collected it. This closes a two-phase-old promise.

Purpose (race): in real Electron `app.relaunch()` only *registers* a restart and `app.quit()`
performs it — both needed, ordered, in one process. Under Tauri `app.restart()` alone does
everything, and the stub forwards both calls as **separate fire-and-forget frames dispatched on
spawned worker threads**, so `app_exit` can be processed first and the app quits instead of
restarting, nondeterministically. `resetHeroic` is the caller that hits this. **This is independent
of plan 34.3-03's Q1 finding** — that finding concerned Rust-side teardown; this is a JS-side
sequencing defect and remains fully in scope.

Output: a real clipboard write path, an explicitly-dead read stub, a module-scope in-flight guard,
and updated coverage in the two existing stub test files.
</objective>

- `RUST_CLIPBOARD_WRITE_TEXT = 'clipboard_write_text'`
- `RUST_CLIPBOARD_READ_TEXT = 'clipboard_read_text'`
- both already members of `RUST_INVOKE_CHANNELS`

The exact template for the write path — `electronStub.ts:436-443` (`shell.showItemInFolder`):
a `(arg: string): void` member that calls `requestRustInvoke(CHANNEL, [arg])` and attaches a
`.catch((error) => console.warn(...))` naming the member, the channel constant, and
`error instanceof Error ? error.message : String(error)`. No `await`, no re-throw.

Why log-only (D-03): real Electron's `clipboard.writeText` is `void` and cannot surface failure
either, so matching it keeps both builds behaviorally identical and adds nothing to unwind at
cutover. A user-visible failure toast would be behavior Electron does not have — a divergence to
declare and later reconcile, and arguably a feature rather than a port. The residual Humble
key-copy silent-failure risk is a **known accepted risk**, recorded per-row in
`34.3-PORTED-CHANNELS.md` by plan 34.3-08.

Why `readText` stays dead (D-04): `common/types/ipc.ts:417` types `clipboardReadText` in the
sync/handler block returning `string`, and real Electron's `clipboard.readText()` IS synchronous —
a sync function structurally cannot await a Rust round-trip. The channel is registered with
`addHandler` (async), so plan 34.3-06's sidecar handler awaits `requestRustInvoke` **itself** and
never calls this stub member. Making the stub async would make it lie about the Electron API it
impersonates; deleting it would make a future hook-rescued caller hit a TypeError instead of a
degraded-but-safe return.

Current `app` block — `electronStub.ts:154-190`: `quit()` at L164 and `relaunch()` at L180, both
already `requestRustInvoke`-with-log-only-catch shapes (`RUST_APP_EXIT` / `RUST_APP_RELAUNCH`).
`exit()` also forwards `RUST_APP_EXIT`.

Existing tests to update, not replace:
