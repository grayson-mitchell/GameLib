## Q1 — Does `AppHandle::restart()` fire `RunEvent::Exit`? — RESOLVED: YES (in this codebase's call pattern)

**Confidence: HIGH.** Answer derived by reading the exact vendored source for `tauri = 2.11.5`
(the version `Cargo.lock` resolves), not from documentation prose or inference.

### Evidence

**1. `AppHandle::restart()` branches on the calling thread** (`~/.cargo/registry/src/index.crates.io-*/tauri-2.11.5/src/app.rs:582-612`):

```rust
/// Restarts the app by triggering [`RunEvent::ExitRequested`] with code [`RESTART_EXIT_CODE`]
/// and [`RunEvent::Exit`].
///
/// When this function is called on the main thread, we cannot guarantee the delivery of those
/// events, so we skip them and directly restart the process.
///
/// If you want to trigger them reliably, use [`Self::request_restart`] instead
pub fn restart(&self) -> ! {
  if self.event_loop.lock().unwrap().main_thread_id == std::thread::current().id() {
    // MAIN THREAD: skips the events entirely, restarts immediately.
    self.cleanup_before_exit();
    crate::process::restart(&self.env());
  } else {
    // BACKGROUND THREAD: sets restart_on_exit=true, requests exit through the real
    // event loop, then blocks this thread forever (safe — the whole process is
    // about to go away regardless).
    self.manager.restart_on_exit.store(true, atomic::Ordering::Relaxed);
    match self.runtime_handle.request_exit(RESTART_EXIT_CODE) {
      Ok(()) => loop { std::thread::sleep(Duration::MAX); },
      Err(e) => { self.cleanup_before_exit(); crate::process::restart(&self.env()); }
    }
  }
}
```

**2. `dispatch_rust_channel` (which contains the `app_relaunch` arm) always runs on a spawned
worker thread, never the main thread** (`src-tauri/src/main.rs:748-760,872-873`):

```rust
// start_reader spawns a thread (main.rs:760):
fn start_reader(...) {
    thread::spawn(move || {
        // ...for each "rustInvoke" frame:
        thread::spawn(move || {
            let result = dispatch_rust_channel(&channel, &args, &worker_app);  // line 873
            // ...
        });
    });
}
```

So `app.restart()` called from inside the `app_relaunch` arm is **always** the background-thread
branch — it sets `restart_on_exit = true`, calls `request_exit(RESTART_EXIT_CODE)`, and blocks
that worker thread (harmlessly) while the **main thread's event loop** processes the exit
request.

**3. `App::run` (the exact method `main.rs` calls) and `App::run_return` share one callback path**
(`app.rs:1366-1374` and `1415-1443`):

```rust
pub fn run<F: FnMut(&AppHandle<R>, RunEvent) + 'static>(mut self, callback: F) {
  self.handle.event_loop.lock().unwrap().main_thread_id = std::thread::current().id();
  self.runtime.take().unwrap().run(self.make_run_event_loop_callback(callback));
}

fn make_run_event_loop_callback<F: ...>(mut self, mut callback: F) -> impl FnMut(...) {
  move |event| match event {
    RuntimeRunEvent::Exit => {
      let event = on_event_loop_event(&app_handle, RuntimeRunEvent::Exit, &manager);
      callback(&app_handle, event);              // <-- main.rs's own RunEvent::Exit handler runs HERE
      app_handle.cleanup_before_exit();           // <-- runs AFTER the user callback
      if self.manager.restart_on_exit.load(...) {
        crate::process::restart(&self.env());     // <-- process re-exec happens LAST
      }
    }
    ...
  }
}
```

**4. `main.rs`'s own registered callback (`~L1041-1047`) is exactly the user callback invoked at
the point marked above:**

```rust
.run(|app_handle, event| {
    if let tauri::RunEvent::Exit = event {
        if let Some(state) = app_handle.try_state::<Arc<SidecarState>>() {
            state.shutdown_child();   // <-- kills the sidecar child process
        }
    }
});
```

### Conclusion

The ordering is: **worker thread calls `restart()`** → sets `restart_on_exit` → requests exit →
**main thread's event loop fires `RuntimeRunEvent::Exit`** → **`main.rs`'s callback runs FIRST**
(`shutdown_child()` kills the sidecar) → THEN `cleanup_before_exit()` → THEN (because
`restart_on_exit` is true) `crate::process::restart()` re-execs the binary. By the time the
process actually restarts, the old sidecar child is already dead. **There is no orphan window
under Tauri's actual behavior for this codebase's calling pattern.**

D-05's proposed fix (explicitly calling `state.shutdown_child()` inside the `app_relaunch` arm
before `app.restart()`) is **unnecessary** — the existing `RunEvent::Exit` handler (built by
Phase 33 WR-03) already does this, and it fires reliably because `dispatch_rust_channel` never
runs on the main thread. **Recommendation: drop D-05's Rust code change entirely.** Add a short
code comment above the `app_relaunch` arm recording this verified finding (so a future reader
does not re-open the question), and use D-11 item 4 (packaged-build live gate: `resetHeroic`
leaves exactly ONE sidecar process) as the empirical confirmation — this is cheaper and more
convincing than a Cargo unit test, which cannot exercise the real winit/tao event loop.

**One residual caveat (why this is HIGH, not ABSOLUTE, confidence):** the exact behavior of
`self.runtime_handle.request_exit(...)` inside `tauri-runtime-wry` (i.e., that it reliably
delivers `RuntimeRunEvent::Exit` back to the main thread in all cases, including if the window has
already been closed) was not traced into the `tauri-runtime-wry` crate itself — this is standard,
widely-relied-upon Tauri v2 plumbing (the same mechanism every `app.exit()` call in this codebase
already depends on, proven working via Phase 33's hardware-verified live gate for `app.quit()`),
not a novel code path. D-11 item 4's live, packaged-build gate is the correct place to close this
residual gap empirically, exactly as D-12 already specifies.

## Q2 — Does `tauri-plugin-clipboard-manager` auto-inject an init IIFE that invokes a command at webview load? — RESOLVED: NO

**Confidence: HIGH.** Determined by directly reading `tauri-plugin-clipboard-manager`'s `lib.rs`
(fetched from `tauri-apps/plugins-workspace`, `v2` branch, `Cargo.toml` pins `version = "2.3.2"`
— confirmed to match the currently-published crates.io/npm version), and comparing against the
exact mechanism that DOES make `tauri-plugin-notification` misbehave.

### Evidence — how the notification plugin's landmine actually works

`tauri-plugin-notification` (already installed, v2.3.3, source available locally at
`~/.cargo/registry/src/.../tauri-plugin-notification-2.3.3/`) calls `.js_init_script(...)` in its
`lib.rs`:

```rust
.js_init_script(include_str!("init-iife.js").replace(
    "__TEMPLATE_windows__",
    if cfg!(windows) { "true" } else { "false" },
))
```

`init-iife.js` (a hand-written file distinct from the npm guest-js bindings) is a top-level IIFE
that overrides `window.Notification` and, at its own top level (not inside an exported function),
runs:

```js
void isPermissionGranted().then(function (response) { ... })
```

where `isPermissionGranted()` on non-Windows unconditionally calls
`invoke('plugin:notification|is_permission_granted')`. `.js_init_script(...)` is a Tauri
mechanism that injects arbitrary JS into **every webview at load**, independent of whether the
JS/npm guest bindings are ever imported by the app's own code — this is exactly what crashed
GameLib's startup until `notification:allow-is-permission-granted` was granted (confirmed
verbatim in this project's own `src-tauri/capabilities/default.json` description field).

### Evidence — clipboard-manager has no such mechanism

`tauri-plugin-clipboard-manager`'s entire `lib.rs` (fetched directly via `curl`, not summarized):

```rust
pub fn init<R: Runtime>() -> TauriPlugin<R> {
    Builder::new("clipboard-manager")
        .invoke_handler(tauri::generate_handler![
            commands::write_text, commands::read_text, commands::read_image,
            commands::write_image, commands::write_html, commands::clear
        ])
        .setup(|app, api| { /* constructs the Clipboard<R> state, no JS emitted */ Ok(()) })
        .on_event(|_app, _event| {
            #[cfg(desktop)]
            if let RunEvent::Exit = _event { _app.clipboard().cleanup(); }
        })
        .build()
}
```

**There is no `.js_init_script(...)` call anywhere in this file.** The `Builder` chain has only
`.invoke_handler(...)`, `.setup(...)`, and `.on_event(...)` — no JS is injected into the webview
at all. The npm guest-js bindings (`@tauri-apps/plugin-clipboard-manager`'s `guest-js/index.ts`)
were separately confirmed to contain zero module-scope `invoke()` calls — every exported function
(`writeText`/`readText`/`writeImage`/`readImage`/`writeHtml`/`clear`) only calls `invoke()` when
explicitly invoked by consuming code. Since D-02 also never imports these npm bindings (the calls
are Rust-side only, via `app.clipboard()`), this second confirmation is belt-and-suspenders — the
plugin genuinely has no init-time behavior of any kind on either side.

### Conclusion

**No amendment to D-02's zero-grant stance is needed.** `tauri-plugin-clipboard-manager` does not
behave like `tauri-plugin-notification` — it injects nothing into the webview, requests nothing at
load, and (per its own `permissions/default.toml`, fetched and confirmed: `permissions = []`)
grants zero capabilities by default. Ship it with **zero** `clipboard-manager:*` entries in
`capabilities/default.json`, exactly as D-02 specifies, with no landmine to discover during the
live gate.

**Bonus finding, load-bearing for D-04/planning:** the plugin's own `desktop.rs` docstrings on
`read_text()`/`read_image()` warn: *"This method should not be used on the main thread! Otherwise
the underlying libraries may deadlock on Linux, freezing the whole app."* This codebase's
architecture already satisfies this by construction — `dispatch_rust_channel` (which will host
the new `clipboard_read_text`/`clipboard_write_text` arms) always runs on a `thread::spawn`'d
worker thread (see Q1 evidence #2), never the main/reader thread. **Call out this safety property
explicitly in the plan** so a future refactor that moves dispatch onto the reader thread does not
silently reintroduce a Linux clipboard-read deadlock.

### Pattern 1: Rust-side platform-capability call via `dispatch_rust_channel`

**What:** A sidecar `rustInvoke` request dispatched to a `dispatch_rust_channel` match arm that
calls a plugin's `AppHandle` extension trait method directly (never a renderer `invoke` command).
**When to use:** Any new platform capability where the JS side must never receive a capability
grant (established by Phase 28 keyring, Phase 30/31 dialog, Phase 33 notification/shell/app).
**Example (the shape D-02's two new arms should copy — modeled on the existing `keyring_get`/`shell_open_path` arms):**
```rust
// Source: src-tauri/src/main.rs:353-421 (existing keyring_* arms), 550-562 (shell_open_path)
"clipboard_write_text" => {
    let text = args.first().and_then(|v| v.as_str()).ok_or("clipboard_write_text:bad-args")?;
    app.clipboard().write_text(text).map_err(|e| e.to_string())?;
    Ok(Value::Null)
}
"clipboard_read_text" => {
    // Runs on the existing spawned worker thread — required, per the plugin's own
    // desktop.rs docstring warning against calling read_text() on the main thread
    // (Linux deadlock risk). dispatch_rust_channel already satisfies this (Q2 finding).
    app.clipboard().read_text().map(Value::String).map_err(|e| e.to_string())
}
```
Requires `use tauri_plugin_clipboard_manager::ClipboardExt;` at the top of `main.rs` (the trait
that provides `.clipboard()` on any `Manager`, confirmed in the plugin's `lib.rs`:
`pub trait ClipboardExt<R: Runtime> { fn clipboard(&self) -> &Clipboard<R>; }`).

### Pattern 2: Fire-and-forget void forward from `electronStub`, log-only failure

**What:** A `send`-kind Electron API forwarded to a Rust `rustInvoke` channel without awaiting or
surfacing failure to the caller.
**When to use:** Any Electron API whose real signature is `void`/fire-and-forget (D-03's basis).
**Example (copy exactly — `electronStub.shell.showItemInFolder`, `src/backend/sidecar/electronStub.ts:436-443`):**
```typescript
// Source: src/backend/sidecar/electronStub.ts:436-443 — the exact template D-03 names
showItemInFolder: (fullPath: string): void => {
  requestRustInvoke(RUST_SHELL_SHOW_ITEM_IN_FOLDER, [fullPath]).catch((error) => {
    console.warn(
      `[electronStub] shell.showItemInFolder(): ${RUST_SHELL_SHOW_ITEM_IN_FOLDER} failed:`,
      error instanceof Error ? error.message : String(error)
    )
  })
}
```
D-03's `clipboard.writeText` should be byte-shape-identical to this, substituting a new
`RUST_CLIPBOARD_WRITE_TEXT` constant.

### Pattern 3: Async handler awaiting `requestRustInvoke` directly, bypassing the stub

**What:** For an `addHandler`-kind (async) channel whose Electron API member is itself
synchronous, the sidecar registration awaits the Rust round-trip directly rather than calling the
(necessarily-sync, necessarily-dead) stub member (D-04's shape).
**Example (modeled on `getShellPath`'s existing async handler shape, `main.ts:1421`):**
```typescript
// New sidecar registration — clipboardReadText is addHandler(async), NOT the sync
// electronStub.clipboard.readText() stub, which stays a documented dead no-op (D-04).
addHandler('clipboardReadText', async () => {
  try {
    const text = await requestRustInvoke(RUST_CLIPBOARD_READ_TEXT, [])
    return typeof text === 'string' ? text : ''
  } catch (error) {
    console.warn('[clipboardFlowRegistration] clipboardReadText failed:', error)
    return ''
  }
})
```

### Pattern 4: Module-scope "action in flight" guard for a fire-and-forget race

**What:** D-06's relaunch-vs-quit race fix — no test file exists yet for this exact shape in this
codebase, but the pattern (module-scope mutable state gating subsequent calls) is standard.
**Example:**
```typescript
// New code inside electronStub.ts's app block (D-06)
let relaunchInFlight = false

export const app = {
  // ...
  relaunch: (): void => {
    relaunchInFlight = true
    requestRustInvoke(RUST_APP_RELAUNCH, []).catch((error) => { /* existing log-only catch */ })
  },
  quit: (): void => {
    if (relaunchInFlight) {
      console.warn('[electronStub] app.quit(): suppressed — a relaunch is already in flight')
      return
    }
    requestRustInvoke(RUST_APP_EXIT, []).catch((error) => { /* existing log-only catch */ })
  },
  exit: (): void => {
    if (relaunchInFlight) {
      console.warn('[electronStub] app.exit(): suppressed — a relaunch is already in flight')
      return
    }
    requestRustInvoke(RUST_APP_EXIT, []).catch((error) => { /* existing log-only catch */ })
  }
  // ...
}
```
This keeps `resetHeroic`'s call order (`app.relaunch()` then `app.quit()`,
`src/backend/utils.ts:472-475`) safe regardless of which of the two dispatched
`dispatch_rust_channel` worker threads reaches Rust first — `quit()`'s no-op path means even if
its RPC frame is sent, the flag already suppressed the actual side effect before the request was
issued.

### Anti-Patterns to Avoid

- **Adding a Rust code change for D-05.** Per Q1, `RunEvent::Exit` already fires reliably for
  `app_relaunch`'s call pattern; an explicit `shutdown_child()` call inside the `app_relaunch` arm
  would be redundant (harmless, since `shutdown_child()` is idempotent-safe per its own
  docstring, but it is dead code that invites the next reader to wonder why it's duplicated).
- **Granting any `clipboard-manager:*` capability "just in case."** Confirmed unnecessary by Q2;
  granting one would contradict D-02's own stated minimal-exposure rationale for zero benefit.
- **Side-effect-importing `logger/ipc_handler.ts` or `utils/ipc_handler.ts`.** Both already
  register already-ported channels (`getLogContent`/`logError` and four others respectively) —
  a side-effect import double-registers them (Invariant: `dispatchSend` iterates ALL listeners,
  so a duplicate registration duplicates every frontend log line or, worse, silently breaks the
  single-registration assumption other code relies on).
- **Calling `app.clipboard().read_text()`/`.read_image()` from the main/reader thread.** The
  plugin's own docs warn of a Linux deadlock. Not a risk today (dispatch already runs on a
  spawned worker thread) but must not regress.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Cross-platform clipboard access | A raw `arboard`/X11/Win32-clipboard wrapper | `tauri-plugin-clipboard-manager` (D-02) | The plugin already wraps `arboard` with the exact `wayland-data-control` feature enabled and handles the Linux main-thread-deadlock hazard in its own docs; zero benefit to reimplementing |
| Detecting whether `AppHandle::restart()` bypasses the event loop | An empirical guess-and-check in production | Direct source read of the pinned `tauri` crate (this research) | The crate's own doc comments and thread-branching logic fully answer this; guessing risks either an unnecessary Rust change (dead code) or, worse, missing a real orphan bug |
| Relaunch/quit ordering | A `setTimeout`-based delay hack in `electronStub` | A module-scope boolean flag (D-06, Pattern 4) | `resetHeroic`'s existing 1s `setTimeout` is ALREADY a delay hack for a different reason (racing `rmSync` against Electron's own quit) — stacking a second timing hack on top of it would compound fragility instead of fixing the actual ordering defect |

**Key insight:** every piece of new platform capability this slice needs (clipboard) already has a
first-party, already-installed-sibling-pattern Tauri plugin. The relaunch/quit ordering problem is
not a platform-capability problem at all — it is a pure JS-side sequencing bug fixable with a
boolean flag, and should not be over-engineered into a Rust-side serialization change (D-06's own
rejected-alternatives list already reaches this conclusion).

## Common Pitfalls

### Pitfall 1: Conflating "restart() never returns" with "restart() bypasses RunEvent::Exit"

**What goes wrong:** CONTEXT.md's own D-05 language ("`restart()`, which never returns (`-> !`)
and exits the process directly rather than through the event loop") is a plausible-sounding but
incomplete reading of the doc comment. The `-> !` return type only means the function's Rust type
signature promises never to return control to its caller — it says nothing about whether the
*process* exits by bypassing the event loop.
**Why it happens:** the doc comment's "when called on the main thread, we skip them" clause is
easy to read as universal if you stop after the type signature and the first line of prose.
**How to avoid:** trace the actual calling thread. This codebase's `dispatch_rust_channel` always
runs on a `thread::spawn`'d worker (Q1 evidence #2) — the "main thread" branch never applies here.
**Warning signs:** any reasoning about `AppHandle` lifecycle methods that doesn't first establish
which thread the call site actually runs on.

### Pitfall 2: A `send` channel registered as a `handle` (or vice versa) fails 100% silently

**What goes wrong:** no error, no marker, no console line — the channel is simply unreachable.
**Why it happens:** `dispatchSend`/`dispatchInvoke` are structurally different dispatch paths in
`electronStub.ts`'s `ipcMain` shim; registering the wrong kind means the frame that arrives is
never matched.
**How to avoid:** cross-check every registration against `main.ts`'s own `addHandler`/
`addListener` call, confirmed line-by-line in this research:
`checkDiskSpace`/`getShellPath`/`clipboardReadText`/`pathExists` are `addHandler` (invoke);
ALL 12 openers + `showConfigFileInFolder`/`removeFolder`/`clearCache`/`clearAchievementCache`/
`resetHeroic`/`showItemInFolder`/`clipboardWriteText`/`logInfo`/`showLogFileInFolder` are
`addListener` (send); `uploadLogFile`/`deleteUploadedLogFile`/`getUploadedLogFiles` are
`addHandler` (invoke); `copySystemInfoToClipboard` is `addListener` (send).
**Warning signs:** a channel that "ports clean" in code review but the frontend feature it backs
never visibly does anything and no rejection/warning appears anywhere.

### Pitfall 3: Side-effect-importing a feature module's `ipc_handler.ts` to reach one clean function

**What goes wrong:** double-registers channels this slice does not own (`getLogContent`,
`logError` via `logger/ipc_handler.ts`; `abort`/`getSystemInfo`/`hasExecutable`/`isIntelMac` via
`utils/ipc_handler.ts`) and drags `backend/ipc` (which imports real `electron`) into the sidecar
graph.
**Why it happens:** `logger/ipc_handler.ts` and `utils/ipc_handler.ts` both co-locate a registration
side effect with genuinely reusable functions this slice needs (`uploadLogFile` et al.,
`formatSystemInfo`/`getSystemInfo`), making the file *look* like the natural single import.
**How to avoid:** import `logger/uploader.ts`, `logger/paths.ts`, `utils/systeminfo` directly —
already confirmed clean exports by direct file read in this research.
**Warning signs:** a new test failure about a channel being registered twice, or
`electronReachLedger.test.ts`'s baseline unexpectedly including `backend/ipc.ts` from a new entry
point that shouldn't reach it.

### Pitfall 4: Treating "ported" as "works" for `resetHeroic`, `deleteUploadedLogFile`, or the anticheat-style riders

**What goes wrong:** `resetHeroic` is far narrower than its own UI copy claims (deletes only
`config.json` + `GamesConfig/` — confirmed by direct read of `utils.ts:466-476`; ~20 other
`electron-store` files, including the Steam token/library and all 10 Humble stores, are untouched
siblings in `appFolder`). `deleteUploadedLogFile` cannot actually delete anything in either build
(`uploader.ts:74-77`'s hardcoded `token = '1'`) yet its UI button is live.
**Why it happens:** the channel names and dialog copy overclaim relative to the actual code.
**How to avoid:** declare both facts explicitly, per-row, in `34.3-PORTED-CHANNELS.md` — this is
D-08's own explicit requirement, and the "resetHeroic is narrower than everyone thinks" framing is
CONTEXT.md's own specific instruction to future readers.
**Warning signs:** a verification round or code review flags "reset doesn't actually reset
everything" as if it were a defect this slice introduced — it is inherited Electron behavior,
ported faithfully.
