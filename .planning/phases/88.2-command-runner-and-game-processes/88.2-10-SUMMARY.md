# Phase 88.2 Plan 10: Game-class runner calls Summary

**A runner call with `spawnClass: game` now spawns through `spawn_game_tracked` into its own session writing a private 0600 capture file that Rust tails into the log writers, the observer and the 50-chunk window, with the run registered in a Rust tracked registry and a stub-game smoke showing launch and survival of the parent's SIGKILL**

## Performance

- **Duration:** about 65 min (cargo builds, including a 4.5 min Windows-gnu clippy, dominate)
- **Completed:** 2026-11-26 (machine clock)
- **Tasks:** 2 (a tracer, then the parent-SIGKILL arm)
- **Files modified:** 11 in the two code commits (6 created, 5 modified)

## Accomplishments

- `game/capture.rs`: `capture_file`/`capture_path` build `<app_folder>/launches/<runner>-<safe name>.out` with every character outside `[A-Za-z0-9._-]` mapped to `_` (T-88.2-16); `create_capture` makes the folder, truncates and sets 0600 on unix (also on a file an earlier run left with another mode); `tail` follows growth every 100 ms in reads of up to 64 KiB, holds a split multi-byte character for its rest, replaces invalid bytes, and drains to the end of the file after `done`.
- `game/end.rs`: `GameEnd::{Close, Exit}` and `wait_end`: `Close` waits for the leader and then for its group (unix) or Game Job (Windows) to empty, polled every 250 ms; `Exit` waits the leader plus the TS 250 ms drain grace; a fired shutdown token returns `Ended::Shutdown` with nothing signalled; the leader is reaped through `GameHandle::reap_status` once it is gone.
- `game/registry.rs`: `TrackedRegistry` with `register_game(runner, key, handle) -> EntryId`, `unregister`, `entry`, `contains`, `len`, and `GameGuard` (unregisters on drop, including a dropped future or a panic). `LaunchCtx` gains `registry`.
- `call_runner`'s game arm (`Run::execute_game`): creates the capture file, spawns with a std `Command` carrying the merged environment with replace semantics, `current_dir` and no pipe, sends `spawned(pid)`, registers under `{ runner, track key }`, tails into the chunk callback (so the log writers get the sanitizer's text and the observer and window the raw one, exactly as the helper path), waits `GameEnd::Close`, then reuses the helper's classification (`settle`: signal, non-zero code, or the window text). The header and `Game Output:` entries are written before the spawn, as before.
- `launch_runner_call` no longer refuses the game class (the op's `game-class-not-ported` answer and call_runner's fixed refusal are gone).
- `gamelib-launch-stub-game` (feature `harness`): `game`, `idle` and `shell` modes. `tests/stub_game.rs`: `launch_tails_output_and_waits_for_the_grandchild` (20 lines to stdout and stderr, capture file 0600 and holding them, the sink and the log writer received them in order, `runnerSpawned` named the leader, the call resolved only after a child that outlived the leader by 500 ms had ended) and `parent_sigkill_leaves_the_game_running` (the shell stand-in runs the real op, is SIGKILLed, game and child stay alive, the capture file keeps growing across polls, then `kill_game_tree` with the stamp probed at launch answers `Killed` and both pids end).

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 - Blocking] The leader is polled, not waited on with a blocking `wait_leader_exit`**
- **Found during:** Task 1 (design of `wait_end`)
- **Issue:** The plan has `wait_end(&mut GameHandle, ...)` run `wait_leader_exit` on a blocking thread, and 88.2-11 kills a registered game through `GameHandle::kill_tree` (also `&mut`). A blocking wait holding the handle (or its lock) would make a kill through the registry impossible while the run waits, and the handle cannot be both in the registry and moved into a blocking thread.
- **Fix:** The registry holds `Arc<Mutex<GameHandle>>`; `wait_end(&SharedGame, ...)` polls `probe::is_alive(pid)` every 100 ms outside the lock. The leader stays an unreaped zombie until `reap_status`, so its pid and pgid cannot be recycled (the property `waitid(WNOWAIT)` gave).
- **Files modified:** src/game/end.rs, src/game/registry.rs
- **Commit:** 2241ef180

**2. [Rule 3 - Blocking] `GameHandle::reap_status` added to gamelib-proc**
- **Found during:** Task 1
- **Issue:** The plan classifies the run ("unregisters and classifies") but `GameHandle::reap(self)` discards the exit status and consumes the handle, which the shared handle cannot give up.
- **Fix:** Additive `reap_status(&mut self) -> io::Result<ExitStatus>`; `reap` is unchanged. `src-tauri/crates/gamelib-proc/src/spawn.rs` is not in the plan's `files_modified`.
- **Commit:** 2241ef180

**3. [Rule 3 - Blocking] lib.rs op refusal removed**
- **Found during:** Task 1
- **Issue:** 88.2-07 left two refusals of the game class, one in call_runner and one in the `launch_runner_call` op (`launch_runner_call:game-class-not-ported`). lib.rs, ctx.rs and Cargo.toml were in the plan's file list; the refusal at the op was not mentioned but would have made the game arm unreachable from the wire.
- **Fix:** Removed both; the op passes the call through.
- **Commit:** 2241ef180

**4. [Plan note] The stub's `shell` mode landed in Task 2**
- The plan's Task 1 action describes only the `game` and `idle` modes; the shell mode and its imports were held back from the Task 1 commit (clippy `-D warnings` clean at both commits) and added in Task 2, as the plan lists it there. The stub game also gained `--child-exit-ms` (the child's lifetime) and `idle --for-ms`, which the launch arm needs for "the child exiting 500 ms after the leader", and a 100 ms delay before it creates its child so that on Windows it is created after the Job assignment.

**5. [Rule 3 - Blocking] `clippy::zombie_processes` on the stub's child**
- **Found during:** Task 1 verify
- **Fix:** `#[allow(clippy::zombie_processes)]` with the reason beside it: the child is meant to outlive the leader's interest in it and the test ends it from outside.
- **Commit:** 2241ef180

**Total deviations:** 4 auto-fixed (all blocking, one a design choice in the plan's own words) plus 1 plan note. **Impact:** no change to what the plan's truths promise; deviations 1 and 2 are what lets 88.2-11 kill a registered game through its handle while the run is waiting.

## Issues Encountered

- **Nothing here ran on Linux or Windows.** The session is macOS. The Windows code (the stub, the shell mode, the test arms) is type-checked by `cargo clippy -p gamelib-launch --all-targets --features harness --target x86_64-pc-windows-gnu -D warnings` (clean), and the host arms passed three consecutive runs. The windows-latest and Linux legs in 88.2-25 are the first real runs; the Windows arm also leans on 88.2-06's flagged assumptions A5 and A6 and on the stub's 100 ms delay being enough for the Game Job assignment (a child created before it escapes the Job).
- **Not tested, stated plainly:** `GameEnd::Exit`, the shutdown path of `wait_end` (a fired token returns without signalling) and the dropped-future behaviour have no test in this plan; only the Close path is exercised end to end. The plan's acceptance did not ask for them.
- **macOS zombie-leader limit stands (88.2-02):** a leader that exits with a surviving grandchild leaves no readable stamp, so a pid-only kill of such a game answers `Gone`; this plan's runs use the unreaped handle and the stamp probed while the leader was alive, so it does not arise here. 88.2-11 kills through the handle for the same reason.
- `npx prettier --check` was not run: the written files are `.rs` and `Cargo.toml`, which prettier has no parser for, so the check would prove nothing; `cargo fmt -p gamelib-launch --check` is the formatter check.
- The concurrency edge (the sidecar dying while a runner call is in flight) is a backstop truth with no wired check; the design is that the game run lives in the Rust call's own future, independent of the sidecar.

## Notes for the plans that follow

- **88.2-11:** a game run is in `ctx.registry` (`entry(id).handle` is the `Arc<Mutex<GameHandle>>`), not in `RunnerTables.aborts`/`tracked`, so `run_abort` and `kill_tracked` do not find a game today. The kill must lock the handle, call `GameHandle::kill_tree`, and set a `killed_by_us` flag the run reads: `execute_game` already answers `{ abort: true }` with the `Abort command` line when `self.abort.is_cancelled()`, which is where the flag plugs in. `wait_end` polls outside the lock, so the kill and the wait do not contend. golden_runner's launch cases still replay through the helper path; re-pointing them at a scripted capture source is 88.2-11.
- **88.2-15/16:** `RunnerCallArgs` has no `resolveOn`; if the TS caller needs `exit` for a game it must be added there (the end is `GameEnd::default()` now).
- A result's `stderr` is always empty for a game and the observer sees every chunk as `stdout` (one shared capture file).
