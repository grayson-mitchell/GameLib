# Phase 88.2 Plan 22: The last TS call sites of the runner Summary

**The auth log sanitizers are named (`'gogAuth' | 'nileAuth'`) and applied in Rust, the legendary, nile and sideload `stop()` end a Rust-launched game through `trackedKill`, and gog's and the launcher's folder-missing prompts run through the `askForceUninstall` shim**

## Performance

- **Duration:** ~40 min
- **Tasks:** 2 (a tracer, then one auto task)
- **Files modified:** 16 (1 created, 15 modified)

## Accomplishments

- Task 1 (tracer): `stop()` in legendary, nile and sideload awaits `trackedKill({ requestRustInvoke: this.deps.requestRustInvoke }, filter)` with the same four filters and the same position. The four `deps.runner.killTracked` calls are gone from the three manager files; `steam/games.ts` is untouched and still calls the TS one.
- Task 2: `CallRunnerOptions.logSanitizer` is the string union; gog/user.ts passes `'gogAuth'` at both calls and nile/user.ts `'nileAuth'`. `runnerAdapter.ts` forwards the name directly (the identity table and the refusal for a stranger function are gone, as are the boot's two TS sanitizer imports). gog/games.ts sends `{ runner: 'gog', appName }` through `askForceUninstall` (not awaited, as before) and launcher.ts does the same through an aliased import, keeping its done status and abort.
- `runnerCallSites.test.ts` (11 tests): the four stop() filters over real manager classes whose TS runner throws on any use, the Steam source pin, the sanitizer names (type and the three call sites), gog's deleted-folder path, the launcher's ask-then-done order, and a no-import check for `errorHandler` and the utils `askForceUninstall`.
