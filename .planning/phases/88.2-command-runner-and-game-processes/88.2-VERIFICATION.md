### Code Review Weighing (88.2-REVIEW.md, advisory)

**CR-01 (Windows descendant walk re-seeds its root from a bare pid).** I read `kill_tree.rs` and the code matches the review. `terminate_stamped_leader` verifies the creation time on one handle and drops it. `collect_descendants(pid, stamp)` is then called again for up to three passes over roughly 1 s of waits, seeding `accepted = [(root, root_stamp)]` with no re-check that `root` is still the stamped process. After the leader is terminated its pid is free. A recycled pid whose new owner spawns children would have those children accepted (`ppid == pid`, created later than the stamp) and passed to `TerminateProcess`. That is the exact thing prohibition 5 exists to prevent, and the module doc's claim that a recycled pid is never followed is false for the root. The snapshot-to-`OpenProcess` race also accepts any newer process that took a child's pid.

Does it defeat the prohibition or the phase goal? On the evidence, not in 88.2:
- `kill_game_tree` has no non-test caller in the workspace (`grep` over `src-tauri/crates` and `src-tauri/src`). It is the mechanism 88.3's re-adoption and stamped quit-kill will call.
- 88.2's actual quit-kill goes through `GameEntry::kill` -> `GameHandle::kill_tree`, which holds the `Child` and Game Job handles, so the pid is pinned for the life of the call. That path is sound.
- The window is small (a pid recycled within about a second, to a process that then spawns children).

So it does not fail truths 3 or 4 as 88.2 ships. It does mean SC2's "stamp-checked tree kill" on Windows is not fully stamp-checked, and prohibition 5's "wrong-stamp orphan arms" test only the leader check, not the walk. I am raising it as a **WARNING requiring a human decision**, not passing it silently. It should be fixed before any 88.3 plan routes re-adoption through `kill_game_tree` on Windows. WR-04 (same function ignores `TerminateJobObject` failure) and IN-05 share that call-site and should ride with it.
