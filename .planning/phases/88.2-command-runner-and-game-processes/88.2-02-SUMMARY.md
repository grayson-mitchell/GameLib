**Stamp-checked game tree kill in gamelib-proc (GameHandle, kill_game_tree, group_alive, ChildSet::terminate_one), each proved by an orphan-harness arm that probes liveness from outside.**

## Accomplishments

- A game spawned through `spawn_game_tracked` survives its parent's SIGKILL, and `kill_game_tree(pid, stamp, grace)` from a different process then removes the game and its grandchild. A wrong stamp answers `NotOurs` and the game keeps writing its log (prohibition 5 at the mechanism, T-88.2-03).
- `GameHandle` watches the leader's exit with `waitid(WEXITED | WNOWAIT)`, so the leader stays an unreaped zombie and its pgid cannot be recycled, then `group_alive`, `kill_tree` and `reap` finish the job. `reap` succeeding after the kill is the proof the leader was never reaped.
- `ChildSet::terminate_one(pid, grace)` ends one helper's whole tree and unregisters it; the arm shows the two other helpers and the game still alive afterwards (T-88.2-04).
- No new crate, no `PR_SET_PDEATHSIG`, no `libc::kill` outside `kill_tree.rs`, and no fixed sleep in a test (every wait polls to a deadline).

**3. [Rule 1 - Bug] Plan assumption disproved: macOS cannot read a zombie leader's start stamp**
- **Found during:** Task 2
- **Issue:** The plan's flagged assumption said `start_time` still reads the leader after `waitid(WNOWAIT)`. On macOS `proc_pidinfo(PROC_PIDTBSDINFO)` returns nothing for a zombie, so `start_time(pid)` is `None` there (Linux reads it from `/proc`). The same applies to a game that has already exited when its stamp is read right after spawn, so `GameHandle.stamp` can be `None`.
- **Fix:** The `waitid(WNOWAIT)` half of the assumption holds and is proved on macOS (the leader is a zombie, `group_alive` is true, `kill_tree` reaches the grandchild, `reap` succeeds). The stamp half is asserted on Linux only, behind `cfg(target_os = "linux")`, with the measured fact recorded in the arm and in the `wait_leader_exit` and `stamp` docs. The own-handle path needs no stamp, so nothing in the mechanism depended on it.
- **Files modified:** `tests/orphans.rs`, `spawn.rs`
- **Commit:** `297099ef3`

**4. [Rule 1 - Bug] Trailing SIGKILL made conditional**
- **Found during:** Task 1
- **Issue:** The plan's `kill_game_tree` ended with an unconditional `kill_process_group(pid)`. Once the group has emptied by SIGTERM, that id may have been recycled, so the unconditional kill could signal an unrelated group.
- **Fix:** `terminate_known_group` re-checks `group_alive` and SIGKILLs only if members remain after the grace, then waits at most 1 s for the group to empty. `Killed` is still the answer.
- **Files modified:** `kill_tree.rs`
- **Commit:** `d8d5a4c60`

**5. [Rule 3 - Blocking] Windows clippy failure from an unused import**

## Issues Encountered

- **Pid-only kill cannot reach a leaderless group.** `kill_game_tree` answers `Gone` when the recorded leader is no longer alive, and with the leader reaped (by init after a parent SIGKILL) or a macOS zombie there is no stamp to check, so a game whose leader exited while a grandchild lives is not reachable by pid and stamp alone. That is the plan's specified semantics (`Gone` when `is_alive(pid)` is false), and the own-handle `kill_tree` covers a handle that is still held. A caller that re-adopts a game after a GameLib restart (the quit-kill and re-adoption work later in this phase) must decide what leader death means for a game before relying on this primitive.
- The Linux and Windows legs of the new arms were type-checked with clippy (`x86_64-unknown-linux-gnu`, `x86_64-pc-windows-gnu`) but only run on macOS; the orphan harness runs on all three in CI.
- The orphan suite passed on three consecutive runs after the Task 2 stand-in fix (an early Task 2 run failed on the disproved stamp assumption, deviation 3); no flake was seen.
