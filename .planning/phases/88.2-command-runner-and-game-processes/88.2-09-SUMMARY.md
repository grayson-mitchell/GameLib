# Phase 88.2 Plan 09: errorHandler, askForceUninstall and the ManagerHooks seam Summary

**errorHandler and askForceUninstall ported to Rust over a new ManagerHooks trait (game_title, force_uninstall), the production runner error handler, and the launch_ask_force_uninstall op, replayed against all 108 TS goldens**

## Accomplishments

- `hooks.rs`: `ManagerHooks` with exactly `game_title` and `force_uninstall` (owned `BoxFuture`s), `HookError(&'static str)` (a fixed category word), and `testing::RecordingHooks` that scripts a title and a result and records the calls in order. `LaunchCtx` gains `hooks` and `with_hooks`.
- `error_handler.rs`: `ask_force_uninstall` takes the title from the hook (the app name on a hook error, no hooks or an empty title), asks `box.error.folder-not-found.title` with buttons [box.no, box.yes] through `prepare::dialogs::ask`, and calls `force_uninstall` only on answer 1 (a failed hook writes the fixed line `forceUninstall hook failed (<runner>)`). `error_handler` is the exact port: empty error and the two ignore-list texts return; the deleted-folder text with an app name asks; the JS regex `legendary.*\.py` (dot stops at LF, CR, U+2028 and U+2029) shows `box.error.legendary.generic` unless `MemoryError: `; `No saved credentials` shows `box.error.credentials.message`; the modal is the in-app `showDialog` frame with the main window raised first.
- `call_runner` now reaches the real handler by default, in a background task that holds a `launch-error-handler` shutdown registrant and gives way to the shutdown token.
- Op `launch_ask_force_uninstall` takes `[{ runner, appName }]` (a `deny_unknown_fields` struct, app name 1 to 256 units) and answers the clicked index or `null`; every bad argument answers the fixed `launch_ask_force_uninstall:bad-args`.
- `golden_error_handler` prints `compared 108 floor 108`; the dismissal cases replay with no forceUninstall call. A mutation (Yes index 0) fails 24 cases, so the replay is not vacuous.
- Crate and CLI tests, clippy (`-D warnings`) and fmt are clean.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 - Blocking] The production handler is `errors: None`, not a value set in LaunchCtx::new**
- **Found during:** Task 1
- **Issue:** The plan says to implement `RunnerErrors` with `error_handler` and set it as the default in `LaunchCtx::new`. The handler needs the context (dialogs, hooks, UI, i18n), and those are set after `new` by `with_dialogs` and `with_hooks`; a handler built in `new` would either capture stale pieces or hold the context it is stored in (an `Arc` cycle).
- **Fix:** `Run::error_handler` runs `error_handler::handle_in_background(&ctx, ..)` when `ctx.errors` is `None`; `with_errors` still installs a recorder (golden_runner and runner_real do). The `errors` doc and the `RunnerErrors` doc say so.
- **Files modified:** src-tauri/crates/gamelib-launch/src/runner/call_runner.rs, ctx.rs, runner/mod.rs
- **Verification:** golden_runner (92 of 93) and runner_real (8) still pass unchanged
- **Commit:** fe396edef

**2. [Rule 3 - Blocking] ManagerHooks is keyed by RunnerName**
- **Found during:** Task 1
- **Issue:** The plan writes `runner: Runner`; the `RunnerErrors` seam, `RunnerCallArgs` and the new op already use `runner::RunnerName`, and `Runner` (knownfix) is a separate type.
- **Fix:** The trait and `RecordingHooks` use `RunnerName`.
- **Commit:** fe396edef

**3. [Rule 3 - Blocking] The replay compares through documented differences**
- **Found during:** Task 1
- **Issue:** The TS goldens answer a dismissal with the dialog's `cancelId` 0 and record a main-window raise only for in-app modals, while the Rust dialog seam answers a dismissal as `None` and raises the window before every question.
- **Fix:** Two named differences in the replay (`dismissal-is-none`, `main-window-raises`), each required to be used by at least one case.
- **Commit:** 5bcd985ef

## Open notes for later plans

- The shell's `LaunchDialogs` implementation blocks its worker thread until the user answers (88.1-14). The background handler is a task on that runtime, so a dialog left open at app exit holds its `launch-error-handler` registrant until the process ends; the shell's exit budget reports it as still running. 88.2-18 (the shell's ManagerHooks transport) and 88.2-20 (the channel) are where this is exercised for real.
- The shell does not implement `ManagerHooks` yet (88.2-18): until it does, a deleted-folder ask in the app shows the app name as the title and a "Yes" removes nothing.
