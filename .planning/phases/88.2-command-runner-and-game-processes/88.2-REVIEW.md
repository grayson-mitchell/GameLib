## Summary

Reviewed the phase's own hunks. The priority files got a full read: gamelib-proc (`kill_tree`, `job`, `spawn`, `spec`, `children`, `probe`), the gamelib-launch `runner/*` and `game/*` modules, `launch_dispatch.rs` and the `lib.rs` op table. The necessity rubric was read and no necessity finding survived its evidence rule (`necessity: 0`).

The core mechanisms are well built: the unix stamp, group and unreaped-leader reasoning is sound, `signal_group` refuses pgid <= 1, and the `ended` flag is set under the handle lock. The defects are concentrated in the Windows descendant-walk fallback added in c7ec52d1e, in asymmetries between the unix and Windows helper kill semantics, and in the new TS `stop()` and quit paths now depending on a Rust round trip that can reject.

## Critical Issues

### CR-01: Windows descendant walk re-seeds its root from a bare pid after the leader is dead, so a recycled pid's children can be terminated

**File:** `src-tauri/crates/gamelib-proc/src/kill_tree.rs:103-129` and `:134-176`
**Issue:** `terminate_stamped_tree` verifies the leader's creation time only once, inside `terminate_stamped_leader` (`:228`). It then drops that handle and calls `collect_descendants(pid, stamp)` again at `:126`, up to `WALK_PASSES` times and across up to about 2 s of `WaitForSingleObject` waits. `collect_descendants` seeds `accepted = vec![(root, root_stamp)]` at `:139` without checking that `root` is still the stamped process. Once the leader has been terminated and no handle to it is held, its pid is free for reuse. Windows reuses pids quickly. If an unrelated process `U` gets that pid and spawns children, those children have `ppid == pid` and `created >= stamp`, so `:168` accepts them and `:118` calls `TerminateProcess` on them. The module comment ("a pid that was recycled to an unrelated, newer process is therefore never followed", `:97-98`) is false for the root, and the function exists to enforce "nothing is terminated unless the pid's creation time equals `stamp`" (`:53`).

The same class of race exists between the snapshot (`process_table`) and `OpenProcess` at `:153`. If the snapshot's `child_pid` died and was recycled in between, the creation-time check (`created < parent_created`) still passes for any newer process, so an unrelated process is accepted.

The probability is low, but the consequence is killing an unrelated user process, which is the exact thing the stamp check exists to prevent.

**Fix:** Keep the leader handle (and its verified stamp) alive for the whole walk and re-check it before every pass, instead of dropping it in `terminate_stamped_leader`:
```rust
// terminate_stamped_leader returns the verified handle (or None), kept until the walk ends.
let leader = open_verified_leader(pid, stamp)?;      // OpenProcess + creation_time == stamp
...
for _ in 0..WALK_PASSES {
    // The held handle pins the pid, so it cannot be recycled for the life of the walk.
    batch = collect_descendants(pid, stamp);
    ...
}
drop(leader);
```
While the leader handle is open the pid cannot be reassigned, so the root seed is sound. For the snapshot-to-open race, re-read `probe::creation_time` and also confirm the opened process's parent still equals `parent_pid`, for example via `NtQueryInformationProcess` `ProcessBasicInformation.InheritedFromUniqueProcessId`. Alternatively, accept that residual race and document it.

## Warnings

### WR-01: `ChildSet::terminate_all` treats a helper as finished when its leader exits, so group members that ignore SIGTERM survive and the reaper is told to forget them

**File:** `src-tauri/crates/gamelib-proc/src/children.rs:158-171`, `:191-218`, `:104-106`
**Issue:** `terminate_entries` decides completion with `exited()`, which tests only the leader (`try_wait` or `is_alive(pid)`). Once the leader exits, the entry leaves `pending`, so the SIGKILL phase (`:205-218`) never runs for descendants that survived the SIGTERM. `terminate_all` then calls `unregister_with_reaper` for every pid (`:104-106`), so the reaper no longer tracks those groups either. A helper whose child ignores or is slow to handle SIGTERM (a wine tree, a download helper) is orphaned past a graceful quit. The sibling `terminate_entry` (`:263-273`) correctly uses `probe::group_alive`, so the two exit paths disagree.
**Fix:** Make `exited` group-based on unix, as `terminate_entry` is:
```rust
fn exited(pid: u32, e: &mut Entry) -> bool {
    if let Some(child) = e.owned.as_mut() { let _ = child.try_wait(); } // reap the leader
    !crate::probe::group_alive(pid)
}
```
SIGKILL any group still alive at the deadline, whether or not its leader has gone.

### WR-02: `wait_end` takes a blocking `std::sync::Mutex` on a 2-worker async runtime while a registry kill holds the same lock for up to ~2.5 s

**File:** `src-tauri/crates/gamelib-launch/src/game/end.rs:62`, `:75`; `src-tauri/crates/gamelib-launch/src/game/registry.rs:86-99`; `src-tauri/crates/gamelib-launch/src/lib.rs:602-612`
**Issue:** `GameEntry::kill` locks the handle for the whole `kill_tree(grace)`. That is the SIGTERM poll up to `KILL_GRACE` (1.5 s) plus the 1 s SIGKILL settle in `terminate_known_group`. It runs on a blocking-pool thread. Meanwhile every running game's `wait_end` calls `lock(game).group_alive()` and `lock(game)` for the reap directly inside an `async fn` that runs on the crate's runtime. That runtime has only two worker threads (`worker_threads(2)`). A quit-kill with a couple of games therefore stalls both workers for up to 2.5 s. During that stall every other launch op (including `launch_games_running`, which the quit check awaits) cannot progress. This is the path where a slow exit costs the Steam restore for everyone behind it.
**Fix:** Do the locked work off the async workers. For example, wrap the `group_alive` poll and the reap in `tokio::task::spawn_blocking`. Or avoid holding the handle lock across the kill wait (take the pid and ended flag under the lock, signal, then re-lock to record the outcome). At minimum raise `worker_threads`, but the blocking call is the real defect.

### WR-03: On Windows the helper's kill-on-close Job fires on a normal exit too, killing background processes that a script, installer or runner left running

**File:** `src-tauri/crates/gamelib-proc/src/children.rs:66-69` (with `spawn.rs:89-106`); consequences in `gamelib-launch/src/runner/script.rs:142` and `spawn_async.rs`
**Issue:** `spawn_helper_tokio` stores the Job in the `ChildSet` entry. `HelperGuard::drop` calls `unregister`, which removes the entry, closes the Job handle, and so kills every member. That happens when `run_spec` returns after any outcome, including a clean exit. The `spec.rs` comment only names the timeout and cancel cases. The consequence is a unix/Windows asymmetry. On unix a pre or post launch script that backgrounds a service (explicitly anticipated by `script.rs`, which resolves "not when every background process it started lets go of the pipes"), or a `spawnAsync` installer bootstrapper that hands off to a child and exits, keeps running. On Windows the child is killed within the `PostExit` window, mid-install. The old Node runner did not do this.
**Fix:** Distinguish "ended by GameLib" from "ended on its own". On a normal exit, detach the Job so closing it does not kill (clear `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` with `SetInformationJobObject`, or release the handle with `mem::forget` and let the process-wide ChildSet cover exit). Keep kill-on-close for timeout, cancel and shutdown. If the kill is intended, document it in `script.rs` and `spawn_async.rs` and mark the golden deltas.

### WR-04: `kill_game_tree` ignores `TerminateJobObject` failure and reports `Killed`

**File:** `src-tauri/crates/gamelib-proc/src/kill_tree.rs:70-78`
**Issue:** `job.terminate()` returns `bool` but the result is discarded. The code then waits and returns `KillOutcome::Killed` even when termination failed (for example access denied on a Job opened with only `TERMINATE|QUERY`, or an unrelated squatted Job of that name). The caller (`GameEntry::kill`) then treats the run as ended by us (`killed_by_us` stays true) and the quit proceeds, although the tree is still running. `GameHandle::kill_tree` (`spawn.rs:308-312`) handles the same failure properly by falling back to `Child::kill`. `kill_game_tree` should fall back to the stamped-tree walk.
**Fix:**
```rust
Some(job) => {
    if !job.terminate() {
        diag("game job terminate failed; walking the descendants of the stamped leader");
        return terminate_stamped_tree(pid, stamp, grace);
    }
    ...
}
```

### WR-05: `stop()` now awaits a Rust round trip that can reject, which skips `shutdownWine` and rejects the stop

**File:** `src/backend/storeManagers/legendary/games.ts:1226`, `src/backend/storeManagers/nile/games.ts:671`, `src/backend/storeManagers/sideload/games.ts:129` and `:132`
**Issue:** The old `this.deps.runner.killTracked(...)` was synchronous and could not throw. The replacement is `await trackedKill(...)`, a `rustInvoke` that rejects on a 60 s transport timeout, `launch_tracked_kill:not-ready`, `:shutdown`, `:panic`, or a lost reply. None of the four call sites catches. When it rejects, `stop()` rejects before the `if (stopWine && !this.isNative())` block, so `shutdownWine` never runs. In `sideload`, a rejection of the first call also skips the `wine` key kill. A Stop click during boot or shutdown now leaves the wine server running.
**Fix:** Keep the old best-effort semantics:
```ts
await trackedKill(rustDeps, { runner: 'legendary', key: this.appName }).catch(
  (e) => logWarning(['trackedKill failed:', e], LogPrefix.Legendary)
)
```
Do the same at each site so the wine shutdown always runs.

### WR-06: The PowerShell argument wrapper builds an expandable string, so `$` and backtick in a value are expanded instead of passed through

**File:** `src-tauri/crates/gamelib-launch/src/runner/call_runner.rs:267-286`
**Issue:** Each part becomes `"`"<part>`""`, a PowerShell double-quoted (expandable) string. Only backslashes are doubled. In an expandable string `$name`, `$(...)` and a backtick escape are interpreted. A value such as a GOG private-branch `--password` containing `$` or a backtick, or a path with `$`, reaches `gogdl` mangled (or runs a subexpression). This is a port of the TS shape, but it is still a correctness and injection-surface defect on the Windows-only path.
**Fix:** Escape for an expandable string before wrapping: backtick to double backtick, `$` to `` `$ ``, `"` to `` `" ``. Alternatively emit single-quoted literals (`'...'` with `'` doubled). Update the redaction pattern (`redact_wrapped`) and the golden vectors to match.

### WR-07: Windows `is_alive` treats exit code 259 as "still running", so a game that exits with 259 is never reaped

**File:** `src-tauri/crates/gamelib-proc/src/probe.rs:196`
**Issue:** `ok != 0 && code == STILL_ACTIVE_CODE`. `STILL_ACTIVE` (259) is also a legal exit code. `wait_end` (`end.rs:55`) loops on `probe::is_alive(pid)`, and the no-Job `group_alive` falls back to it. A game or script that exits with code 259 leaves `wait_end` polling forever, the registry shows a running game forever, and the quit dialog keeps asking. This is the canonical `GetExitCodeProcess` pitfall.
**Fix:** Test liveness with `WaitForSingleObject(h, 0) == WAIT_TIMEOUT` (needs `SYNCHRONIZE` access on the handle opened in `is_alive`).

### WR-08: `quitHandler` swallows a failed `killTrackedRust` with no log after the user chose "Yes"

**File:** `src/backend/quitHandler.ts:98`
**Issue:** `await deps.killTrackedRust().catch(() => 0)` discards the error entirely. The user confirmed "end everything", the Game-class games survive a plain sidecar exit (the file's own header says so), and the app then calls `deps.exit()`. If the invoke rejects, the user is left with orphaned games and the log has nothing. The `isGameRunning` side already fails safe (it asks), but this side fails silent.
**Fix:** Log the failure before continuing, for example by injecting a `logError` dep and calling `.catch((e) => { deps.logError(['killTrackedRust failed', e]); return 0 })`. Keep the "must not strand the quit" behaviour.

### WR-09: The `spawnAsync` abort retry window is about 1 s, after which an abort is lost and the run continues for as long as the program takes

**File:** `src/backend/spawnAsync.ts:66-67`, `:149-160`
**Issue:** An abort that reaches Rust before the run registers is retried `KILL_RETRIES = 40` times at 25 ms, about 1 s. The adjacent comment says the call is processed "within milliseconds", but the launch runtime has only two workers and the shell dispatches sync ops through them (see WR-02). If registration is delayed past ~1 s (for example while a quit-kill or another op stalls the workers), the abort is silently dropped. The caller's `signal` has aborted, but the child, which the file says runs installers "for hours", runs to completion and the call settles late with a normal result.
**Fix:** Retry until the call settles instead of a fixed count, since the timer is already `unref`'d and cleared in `finally`. Or have Rust honour an abort for a stream id that has not registered yet (record a pending kill keyed by stream id).

## Info

### IN-01: `callRunner` mutates the caller's `options.logWriters`, so a reused options object hands off the runner writer repeatedly

**File:** `src/backend/runnerAdapter.ts:181-182`
**Issue:** `options.logWriters ??= []; options.logWriters.push(...)` appends the runner's writer to the caller's array on every call. This matches the old TS, but the new `handOff()` per writer claims rotation and sends a target per entry. A caller that reuses one options object (retry loops) gets the same target several times, and every chunk is written once per copy.
**Fix:** Build a local array: `const writers = [...(options.logWriters ?? []), deps.getRunnerLogWriter(...)]`, and iterate that.

### IN-02: Game output capture files are left on disk after the run

**File:** `src-tauri/crates/gamelib-launch/src/game/capture.rs:66-86`
**Issue:** The 0600 `launches/<runner>-<name>.out` file holds the game's raw stdout and stderr. The log copy goes through the named sanitizer, but this file is raw. It is only truncated by the next launch of the same name and never removed when the run ends. The files persist across sessions (and `safe_name` maps distinct names, for example `a b` and `a_b`, to one file).
**Fix:** Remove the file once the tail has drained and the run has settled, or document the retention. Consider including a run serial in the name.

### IN-03: Unreachable `registry.entry(id) == None` branch would orphan the game it just registered

**File:** `src-tauri/crates/gamelib-launch/src/runner/call_runner.rs:545-547` and `wine_command.rs:464-466`
**Issue:** `entry(id)` runs immediately after `register_game` with nothing able to remove the entry in between. If it were ever hit, the function returns with the game running, `GameGuard` unregistering it, and the leader unreaped. The branch is dead code.
**Fix:** Take the `GameEntry` from the registration instead of re-reading it (`register_game` can return `(EntryId, GameEntry)`), removing the branch.

### IN-04: Credential redaction masks only the first occurrence of a flag and not the `--flag=value` form

**File:** `src-tauri/crates/gamelib-launch/src/runner/redact.rs:100-117`
**Issue:** `position()` finds the first match, so a second `--token X` is left in the logged command line, and `--token=X` (one argv element) never equals the flag. No current caller does either (checked the `--code`, `--token`, `--password`, `--client-id` call sites), so this is latent. The port was meant to be exact, but the env list is also logged unredacted (`:121-126`). Anything credential-like a future caller puts in `options.env` goes to `gamelib.log`.
**Fix:** Redact every occurrence and handle the `=` form. Consider redacting env values whose key matches `/token|secret|password|key/i`.

### IN-05: `terminate_stamped_tree` discards a `Gone` leader outcome and always reports `Killed`

**File:** `src-tauri/crates/gamelib-proc/src/kill_tree.rs:105-108`, `:128`
**Issue:** Only `NotOurs` returns early. If the leader exited between the liveness check and the open (`Gone`), the function still returns `Killed`, even when no descendant was found either. The `KillOutcome` contract says `Gone` means nothing was signalled, and `GameEntry::kill` uses that distinction to restore `killed_by_us`.
**Fix:** Return `Gone` when the leader outcome is `Gone` and the first batch is empty.
