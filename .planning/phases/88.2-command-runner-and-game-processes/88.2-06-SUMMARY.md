# Phase 88.2 Plan 06: gamelib-proc Windows game tree kill Summary

**Windows half of the Game-class primitives in gamelib-proc: a GetProcessTimes start stamp, a named Game Job without kill-on-close, a stamp-checked `kill_game_tree` over it, `GameHandle` and `terminate_one` on Windows, each with an orphan arm that first runs on the windows-latest leg.**

- **Completed:** 2026-11-26T17:12:05Z (machine clock)

## Accomplishments

- `probe::start_time(pid)` on Windows reads the creation FILETIME through `GetProcessTimes` as `(high << 32) | low`, so the stamp check of `kill_game_tree` now exists on all three OSes. A crate-private `probe::creation_time(handle)` reads it through an already-open handle.
- `GameJob` (job.rs): `Local\GameLib-Game-<pid>-<stamp>`, no limit flags (so no `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`), `create_for` / `open` / `terminate` / `active_processes`. `open` asks only for `JOB_OBJECT_TERMINATE | JOB_OBJECT_QUERY`.
- `spawn_game_tracked` on Windows creates the game with `CREATE_BREAKAWAY_FROM_JOB`, retries plainly on access denied with the diag line `game spawn: breakaway refused; created inside the parent's job`, then reads the stamp and creates the Game Job. The unix path is the 88.2-02 one.
- `kill_game_tree` on Windows: `Gone` / `NotOurs` first, then open the Game Job by name and `TerminateJobObject`; with no Job it terminates the stamped leader only and logs `game job not found; leader only`.
- `GameHandle::{group_alive, kill_tree}` now exist on both OSes with one doc meaning (Windows: the Job's active process count, `Child::kill` when there is no Job). `ChildSet::terminate_one`'s Windows arm was already the helper's own Job terminate from 88.2-02 (`terminate_entry`); it now has a Windows test.
- Three Windows orphan arms named exactly as the plan requires, sharing bodies with their unix siblings. The host (macOS) orphan suite is unchanged at 13 passing, three consecutive runs green.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 - Blocking] Stand-in game child could be created before the Job assignment**
- **Found during:** Task 3
- **Issue:** The Windows arm needs the game's grandchild inside the Game Job. The `game` stand-in spawned its child at once, racing `spawn_game_tracked`'s Job assignment; a grandchild created first escapes the Job (the documented limit), so `kill_game_tree` would leave it alive and the arm would flake. A pipe to the game would fix it but is forbidden (Pitfall 5).
- **Fix:** `game` accepts `--wait-for <path>`; `parent --game-stamp` passes the stamp-record path, which it writes only after `spawn_game_tracked` has returned. Applies on unix too, harmlessly.
- **Files modified:** `src/bin/standin.rs`
- **Commit:** `78cd5be11`

**2. [Rule 2 - Missing critical] Refuse a Game Job name that already exists**
- **Found during:** Task 1 (T-88.2-08)
- **Issue:** `CreateJobObjectW` on an existing name returns a handle to that object with `ERROR_ALREADY_EXISTS`; assigning the game to it and later terminating it would act on a Job that is not ours.
- **Fix:** `create_for` clears the last error, closes the handle and answers `None` with a diag line in that case.
- **Files modified:** `src/job.rs`
- **Commit:** `ef29cfe5e`

**3. [Rule 3 - Blocking] `spawn_game` split into `prepare_game` plus spawn**
- **Found during:** Task 1
- **Issue:** The tracked path must set creation flags and retry the spawn, which `spawn_game` (returning the `Child` after its own spawn) cannot do.
- **Fix:** Moved the stdio and `setsid` setup into a private `prepare_game`; `spawn_game` is `prepare_game` then `spawn`, behaviour unchanged.
- **Files modified:** `src/spawn.rs`
- **Commit:** `ef29cfe5e`

**4. [Rule 3 - Blocking] The unread `job` field**
- **Found during:** Task 1
- **Issue:** Task 1 stores the Job in `GameHandle`, but its readers are Task 2's methods, so `-D warnings` on the Windows target would fail on dead code at the Task 1 commit.
- **Fix:** A temporary `#[allow(dead_code)]` in Task 1, removed in Task 2.
- **Files modified:** `src/spawn.rs`
- **Commit:** `ef29cfe5e`, `0d7d4d5ac`

**5. [Plan note] Task 2's `terminate_one` work was already done**
- **Found during:** Task 2
- **Issue:** 88.2-02 already wrote `terminate_entry`'s `#[cfg(windows)]` arm (terminates the entry's Job, `Child::kill` without one), matching what the plan asks for.
- **Fix:** No code change; the arm gained its test in Task 3.

**Total deviations:** 4 auto-fixed (1 missing critical, 3 blocking) plus 1 plan note. **Impact:** none on the plan's goal.

## Issues Encountered

- **Nothing here ran on Windows.** This session is macOS. The Windows code was type-checked with `cargo clippy --all-targets --target x86_64-pc-windows-gnu -D warnings` (clean), and the shared scenario bodies run on macOS through the unix wrappers. First real run is the windows-latest leg in 88.2-25, which must find `terminate_parent_spares_game_then_stamped_kill_removes_its_tree` in its log.
- **Flagged assumptions stand, unverified:** A5 (a named Job without kill-on-close can be reopened by name after its last handle closed while its processes run) and A6 (creation time is stable across a GameLib restart) are the Windows arms' job to prove. A grandchild the game creates before the Job assignment still escapes the Job (the same documented limit as the helper Job).
- **A dead leader answers `Gone` on Windows too**, as the plan specifies and as unix does, although on Windows the Game Job (named by pid and stamp, so unambiguous) could still be reopened and its surviving grandchild killed. A launcher-style game whose leader exits first (common on Windows) is therefore unreachable by pid and stamp alone; the own-handle `kill_tree` covers a held handle. 88.2-19 (re-adoption, quit-kill) should decide whether `kill_game_tree` should try the Job when the leader is dead.
- **`spawn_game_tracked` replaces any creation flags** the caller set on the `Command` on Windows (std offers no getter to merge them). Documented on the function; no caller sets any yet.
- SVC-03's edge-coverage row stays `unclassified`; the D-14 matrix stands in for edge coverage and is not claimed as a verified edge.
- `npx prettier --check` was not run: the written files are `.rs` and `Cargo.toml`, which prettier has no parser for, so the check would prove nothing.
