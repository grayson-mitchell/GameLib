# Phase 88.2 Plan 12: Wine launch variant Summary

**`launch_wine_command` runs a wine command for a launch the way the TS did: a sideload launch is a Game-class child writing a capture file that Rust tails into the `Wine Command:` header, the log writers and the stream, tracked as `{ wine, key }`, ended on close or exit, followed by a 30-minute helper `wineserver --wait`; all 41 recorded launch cases and gamelib-wine's 16 `wine_command` cases replay through it with none of 87's three deltas applied**

## Performance

- **Duration:** about 95 min
- **Completed:** 2026-11-27 (machine clock)
- **Tasks:** 2 (a tracer, then every case)
- **Files modified:** 9 in the two code commits (2 created, 7 modified)

## Accomplishments

- `prepare_wine_command` / `PreparedWine` in gamelib-wine: the prefix check, `validWine`, the env merge, umu, the proton verb, the wrappers and the argv, answering the early `Invalid wine` as `Err`. `run_wine_command` calls it and runs the unchanged spawn, so golden_wine_core's 16-case replay and its `deltas.json` did not change. `spawn` is public for the launch variant's wait.
- `runner/wine_command.rs`: `launch_wine_command(ctx, args, host, sink) -> WineLaunchResult`. The game arm spawns through the game spawner into a capture file, tails it into the log writers, the observer and the 50-chunk window, registers `{ runner: "wine", key }` (key = `trackKey ?? installFolderName ?? winePrefix`) for the run's life and ends on `GameEnd::Close` or, with `resolveOnExit`, `Exit`. The helper arm is a streamed `SpecRunner` run with a helper registry entry, ending on `PostExit::UntilClosed` or `Grace(250 ms)`. Both write the header and every chunk raw (no sanitiser, no trim), answer the last 50 chunks of each stream joined with `''`, log a failed spawn as `Wine command failed to run:` and answer an empty result with a `null` code, and wait `wineserver --wait` as a Helper capped at 30 minutes with the TS warning (naming the prefix). The caller's lists are only read.
- `PostExit { Drain, Grace(d), UntilClosed }` on `ProcSpec` (gamelib-core) and honoured in `SpecProcRunner::drive` (gamelib-proc): the TS `resolveOn: 'close'` needs a wait for every pipe holder, which the 2 s bounded drain never gave. The default is unchanged for every other caller.
- Op `launch_wine_command` `[args, host]` (OPS 18 -> 19), with the fixed `<op>:bad-args`; `LaunchWineCommandArgs` is strict (`deny_unknown_fields`) and reads the `options` fields the 87 struct ignored (`wrappers`, `trackKey`, `env`, log targets, `spawnClass`, `observe`).
- golden_wine_launch.rs: `compared 41 floor 41` (the tracer, 21 named titles, 19 pairwise rows) and `compared 16 floor 16` (gamelib-wine's cases, read from `../gamelib-wine/tests/fixtures/golden/wine_command`), manifests and floors, a guard that a changed call fails the replay, the op's wire shape, and a real-child proof of close versus exit.

## Interpretations the plan left open

- **"never mutates the caller's list" versus "NO delta applied".** The TS golden's `commandPartsAfter` is the list the TS mutated; the Rust op takes its arguments by value. The replay compares the main spawn's argv with `commandPartsAfter` (they are the same list, built in place by the TS) and so closes 87's `command-parts-not-mutated` delta by comparison. The D-20 todo (`options.wrappers.shift()` shortening the caller's array) stays a TS bug the Rust op does not reproduce.
- **`onSpawn`.** The one recorded case that sets it is helper class, where the spawn seam reports no pid; its callback count is not compared (`helper-spawn-not-reported`). 87 did not carry it either.
- **The 16 cases' header.** The TS oracle's wine_command runs never called `onSpawn`, so the recorded events hold no header; the replay checks the header is the first write, with the spawned program and argv, and compares everything after it to the recorded `logWriter` events.

## Issues Encountered

- A game run's two streams share one capture file, so a launched wine game answers everything it printed as stdout (the `game-merged-streams` delta). The TS split is not recoverable without a second capture file, which D-29 rejected.
- The helper arm's header timing (first chunk or end) differs from the TS at spawn for a command that prints late. A launch uses the game class, where the header is written at spawn.
- Not wired in this plan (outside its files): the shell's `launch_dispatch.rs` arm and the renderer shim for the op (88.2-17), and a caller cancel for the game arm (`WineHost.cancel` ends a helper run; a game is ended through the tracked kill or the abort id).
