# Phase 88.2 Plan 19: The quit dialog's running-game condition Summary

**The quit handler asks when the Rust running-game registry reports a game (a failed read asks too) and Yes ends every Rust-tracked game tree through gamelib-proc via `trackedKillAll`, between the TS kill and `abortAll`; recorded as the D-27 behaviour change**

## Accomplishments

- `QuitHandlerDeps` gains `isGameRunning(): Promise<boolean>` and `killTrackedRust(): Promise<number>`. `handleExit` reads `await deps.isGameRunning().catch(() => true)`, opens the dialog on `isLocked || isRunning || isBridgeHosting || isGameRunning`, shows the bridge-hosting message only when bridge hosting is the sole condition, and keeps `cancelId: 0` with its CR-04 comment. Yes runs `teardownAll`, `killAllTracked`, `killTrackedRust`, `abortAll`, then the unchanged routed-quit tail.
- `bootstrap.ts` binds both deps lazily to `gamesRunning` and `trackedKillAll` over `requireHost(state).requestRustInvoke` (a non-boolean answer reads as not running, a rejection is the handler's to treat as running).
- `quitHandler.test.ts` went from 5 to 13 tests: the tracer, No, dismissal, rejected read, running game with a lock, with bridge hosting, no game, and a failed Rust kill. `quitTeardownWiring.test.ts` gained a gate that pins the bootstrap binding.
- `88-VALIDATION.md` carries `### Behaviour changes (88.2)` with the new dialog condition, its UAT row (88-HUMAN-UAT.md item 2), the leader-death decision, and the D-31 items left to 88.3.

## Leader death (flagged by 88.2-02 and 88.2-06)

`kill_game_tree` answers Gone once the recorded leader is dead. The registry keeps a game entry until its run reaps the leader (`GameGuard` drop), so a game whose leader exits while a grandchild lives is no longer registered: `gamesRunning` reads false and the quit neither asks about nor kills the grandchild. This plan leaves that unchanged and records it in 88-VALIDATION.md. It is the same reach as the TS-tracked child the Rust run replaces, and a tree-wide "still running" probe would need a pid-and-stamp-proven descendant check that 88.2-02 and 88.2-06 do not provide (on Windows the named Game Job could still be reopened). Whether that gap matters for launcher-style games is a question for 88.3 and the UAT.
