# Phase 88.2 Plan 18: The shell's ManagerHooks over the sidecar Summary

**SidecarManagerHooks implements ManagerHooks over one long-running Rust-to-sidecar channel, launchManagerCall ([op, { runner, appName }], game_title and force_uninstall), each call on its own thread, installed on the shell's LaunchCtx and failing safe to HookError("sidecar") when the sidecar is missing, closed or errors**

## Performance

- **Duration:** about 35 min (start time not captured; estimated)
- **Completed:** 2026-11-27
- **Tasks:** 2 (a tracer, then the EOF task; see Deviations for the single commit)
- **Files modified:** 3, all modified

## Accomplishments

- `SidecarManagerHooks` (in `launch_dispatch.rs`): `game_title` and `force_uninstall` each start a thread named `launch-manager-hook` that calls the sidecar over `launchManagerCall` with `[op, { runner, appName }]` and answers through a small one-shot slot, so the returned future owns everything it needs and the caller's borrow ends at the call. A title decodes a string; `force_uninstall` accepts any success reply.
- Failure is one fixed word: `HookError("sidecar")` for no sidecar, a closed sidecar, an error reply, a thread that would not start or one that panicked; `HookError("bad-reply")` for a title that is not a string. The runner, the app name and the sidecar's error text never appear in it (tested with an error text that names all three and a path).
- `launchManagerCall` is in `LONG_RUNNING_CHANNELS` with a rationale (88.3's funnel `launch` hook spans a session), in `longRunningChannels.test.ts` in the same commit, and pinned by a `launch_manager_call_is_long_running` shell test beside the existing loop test.
- The installed context gets `with_hooks` next to `with_dialogs` through `with_shell_hooks`; the runner's `errors` stays `None`, the 88.2-09 production handler, which reads the dialogs and hooks set here.
- EOF: over a real `SidecarState` (a silent child, killed on drop) a pending hook answers `HookError("sidecar")` as soon as `drain_pending_invokes` runs; a Yes through `launch_ask_force_uninstall` over such hooks takes the app name as the dialog title, writes `forceUninstall hook failed (legendary)` and no other line, and the op answers the clicked index (the uninstall itself did not happen).

## Decisions Made

- One channel with the op as its first argument (D-26); 88.3 adds its ops to the same channel.
- The hooks reach the sidecar through a per-call lookup (`store_dispatch::sidecar_state()`), because `run_setup` builds the launch context before it spawns the sidecar.
- No tokio dependency is added to the shell for the one-shot: a Mutex, a value and a waker are enough, and `cargoFeatures.test.ts` pins the crate set.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 - Blocking] The hooks cannot hold an `Arc<SidecarState>` at install**
- **Found during:** Task 1
- **Issue:** The plan has `struct SidecarManagerHooks { state: Arc<SidecarState> }` and installs it "when the sidecar state exists". `run_setup` calls `launch_dispatch::install` before `spawn_sidecar_state`, so the state never exists then, and a `OnceLock<Arc<LaunchCtx>>` cannot be rebuilt later.
- **Fix:** The struct holds an invoke function (`HookInvoke`); production passes `sidecar_invoke`, which looks the state up per call and answers an error before it exists. The context always carries the hooks. This also gives tests a scripted invoke seam without a child process.
- **Files modified:** src-tauri/src/launch_dispatch.rs
- **Commit:** c40054242

**2. [Plan reading] Task 2 has no commit of its own**
- The Task 2 tests (a pending hook at EOF, a Yes over hooks the sidecar never answers, the context carrying hooks and dialogs) share the `SilentSidecar` helper, `ctx_built` and the `block_on` helper with Task 1's tests and were written in the same pass, so they landed in `c40054242`. Task 2 needed no production change. Its `<verify>` (`launch` and `drain` filters, fmt) was run and is green; a second commit would have been empty.

**3. [Plan reading] The `launchManagerCall` count in main.rs**
- The Task 1 acceptance reads "contains `launchManagerCall` [HEAD=0 EXPECT==1]"; the name appears three times in main.rs (the array entry, its rationale comment and the new test). The intent, membership of `LONG_RUNNING_CHANNELS`, is checked by the test and the jest mirror.
