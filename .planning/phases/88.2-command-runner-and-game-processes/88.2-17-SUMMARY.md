# Phase 88.2 Plan 17: The rest of the runner transport Summary

**The wine command, winepath, launch script, spawnAsync, tracked-kill, kill-all and games-running channels run end to end (zod, generated contract, shell arm over the wine or runner host, shim, schedule row), and the adapter now has commandRunner's `runWineCommand`, `getWinePath` and `runScriptForGame`; nothing is wired at boot**

## Accomplishments

- Seven channels: `launch_wine_command`, `launch_wine_path` (shell appends `wine_run_host()`), `launch_script_run` (appends `runner_host()`), `launch_spawn_async` (`[args]` only, no host), `launch_tracked_kill`, `launch_tracked_kill_all`, `launch_games_running`. Each arm decodes with the generated type and checks arity first, so a wrong call is the same fixed `<op>:bad-args` before and after the install and never echoes the value; before the install every arm answers `<op>:not-ready`. A failed script's or spawn's `Err(text)` passes through as the dispatch error.
- Schemas: `launch_wine_command` is the `WineCommandArgs` fields with `options` reduced to `{ env, wrappers, trackKey }`, `logTargets` as typed hand-offs, `streamId`/`observe`, `spawnClass`; `gameSettings` is opaque (`x-rust-value`) and checked to be an object in the arm. `launch_script_run` takes `settingsJson`/`infoJson` as strings. `launch_spawn_async` takes `timeoutMs` as `number | null`.
- Shims in `launchrust/runner.ts` (now 10): `wineCommandRun` (schedule 97), `winePathGet` (92), `scriptRun` (88.3), `spawnAsyncRun` (98), `trackedKill` (92), `trackedKillAll` (98), `gamesRunning` (98).
- Adapter: `runWineCommand` copies `commandParts`, never touches the caller's `wrappers`/`options`, opens a stream for `onOutput` or `onSpawn`, flushes logs, hands the caller's writers off once, sends `spawnClass: options.spawnClass ?? 'helper'`, closes the stream in `finally` and narrows the reply with `settleWineCommandResult` (`code` absent for a refused wine). `getWinePath` answers the string. `runScriptForGame` sends `JSON.stringify(gameSettings)` and `JSON.stringify(gameInfo)` verbatim and rethrows Rust's text as an `Error`. The adapter is assignable to the `CommandRunner` type (checked in the test and by codecheck).
- Pins: `UNBOUNDED_RUST_CHANNELS` 47 -> 51 (twenty-fourth and twenty-fifth paragraphs), 210 -> 217 channels and arms in `rustInvokeSchemas.test.ts` and `tauriShellSource.test.ts`, proven-arms list extended, seven schedule rows.

**3. [Rule 2 - Missing critical] Arity check on the no-argument arms**
- The generated decode of an empty tuple accepts any arguments, so `launch_tracked_kill_all` and `launch_games_running` check `args.is_empty()` themselves and answer the fixed bad-args literal (tested before and after the install).

**4. [Plan reading] The kill-all arm needs no extra thread**
- The plan says the kill-all arm runs off the reply thread. As 88.2-15 established, every `rustInvoke` already runs on its own spawned worker thread, so the arm is the same shape as the others and its wait (up to the child grace) holds neither the reader nor another call.

**5. [Plan reading] The script's writer is handed off only when verbose**
- The plan sends "the writer's hand-off". Rust reads the target only with verbose logs on; handing it off otherwise would claim the writer's owed rotation for a script whose output is dropped. The adapter hands off (after the flush) only when `verboseLogs` is on, and tests assert the rotation is still owed otherwise.
