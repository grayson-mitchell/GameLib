# Phase 88.2 Plan 21: Boot the runner adapter and send games as Game class Summary

**Every runner command and every spawnAsync child now runs in Rust: the boot step builds `createRunnerAdapter` and a spawnAsync adapter over one shared stream table, and the five game launch spawns carry `spawnClass: 'game'`**

## Performance

- **Duration:** ~55 min
- **Tasks:** 3 (a tracer, then two auto tasks)
- **Files modified:** 17 (2 created, 1 deleted, 14 modified)

## Accomplishments

- `bootstrap.ts` 'command-runner' step: `runnerStreams` is built once (`createRunnerStreams` with `kill` to `runnerKill`) and stored in the new `BootServices.runnerStreams`; `commandRunner` is `createRunnerAdapter` with a getter-backed `requestRustInvoke` (the host is read per call), `getRunnerLogWriter` honouring `disableLogs`, `flushLogForwarder`, and the gog and nile `authLogSanitizer`s (the adapter finds Rust's sanitizer name by function identity and refuses any other function). `createCommandRunner`, the `errorHandlerDeps` binding, `validWine` and the imports that fed only the TS runner's wine bindings (the launch builder shims, `settleEnvMap`, the umu helpers, `searchForExecutableOnPath`) left the file.
- The 'abort-registry' step builds `createAbortRegistry({ forwardAbort })` to `runnerAbort`, so `aborts.call(id)` ends a Rust run whose id no local controller holds. `handlers.ts` calls `registerRunnerOutputListener(ipc, services.runnerStreams)` once.
- `CallRunnerOptions.spawnClass?: 'game'` (D-05) is forwarded by the adapter's `callRunner` (it forwarded only the wine variant before). The legendary, gog and nile `launch()` calls and the sideload native and wine launches set it; a source gate counts the name across all of `storeManagers/`, so no install, auth, list or bridge call can.
- `createSpawnAsync({ requestRustInvoke, streams })` keeps the `SpawnAsync` type and the `ALLOWED_KEYS` TypeError and runs the child through `spawnAsyncRun`; the boot builds it over the same table. `spawnAsync.oracle.test.ts` is removed (its `golden/spawn_async` fixtures stay; `golden_spawn_async` replays them, green).

- **Files modified:** `src/backend/testUtils/runnerSpawnAsync.ts` (new), `spawnTrace.ts`, `windowsElevation.test.ts`

**4. [Plan reading] "kill right after the spawned frame" for an already-aborted signal**
- The plan has an already-aborted signal send `runnerKill` after the spawned frame. A helper-class `spawnAsync` reports no spawned frame (88.2-14/17), and a kill sent behind the call can reach Rust before the run is registered, so it would do nothing. The adapter instead resolves `{ code: null, stdout: '', stderr: '', timedOut: false, aborted: true }` without sending a call (the old runner spawned and killed immediately; the result is the same, no child runs). For an abort that arrives while the call is in flight it re-asks the kill for at most 40 x 25 ms when Rust answers "no such run", with an unref'd timer that stops as soon as the call settles (sidecar exit contract: bounded, no in-flight work at boot).

**5. [Plan reading] A stream is opened for `signal` as well as `onOutput`**
- The kill needs a `streamId` to name the run; the plan opens one only for `onOutput`. The adapter opens one when either is given and sends `observe: true` only for `onOutput`.

**6. [Plan reading] `launch_wine_command` for the sideload wine launch**
- `runnerLaunchClass.test.ts` proves the adapter and the two sideload sites separately (adapter over the channel schema; a source gate for the site) because `launchGame` and the managers' `launch()` cannot be driven without a launcher, a prefix and a game; the existing launch tests (`launchFailure.test.ts`) use the same source-gate shape.
