# Phase 88.2 Plan 13: Launch scripts and winepath Summary

**`launch_script_run` runs a user's pre or post launch script as a Helper with the TS env, cwd and verbose-log behaviour, and `launch_wine_path` answers getWinePath through 88.1's `get_wine_path`; all 18 script cases and 16 winepath cases replay at floors equal to their counts**

## Accomplishments

- `runner/script.rs`: `run_script_for_game(ctx, ScriptRunArgs, &RunnerHost) -> Result<bool, String>`. The script is the program (empty argv, never a shell), cwd the install path, the env is `HEROIC_GAME_APP_NAME/EXEC/PREFIX/RUNNER/SCRIPT_STAGE/TITLE` plus `HEROIC_GAME_SETTINGS` and `HEROIC_GAME_INFO` (the strings the sidecar stringified, untouched) with the host env laid over them, `replace_env` on, no timeout, `PostExit::Grace(250 ms)` (the TS `resolveOn: 'exit'`), a shutdown registrant (`launch-script`) held for the run and the shutdown token as its cancel. Verbose chunks go raw to the handed-off game log target; a spawn failure is written there first as an `Error: ...` line (rotate on the first write) and answered as `Err`. A non-zero exit answers `true`.
- `runner/wine_path.rs`: `WinePathArgs { path, gameSettings, variant }` (strict, `variant` defaults to `unix`) over `get_wine_path`.
- Ops `launch_script_run` and `launch_wine_path` (OPS 19 -> 21, sorted), each with a fixed `<op>:bad-args`.
- `golden_script`: `compared 18 floor 18` (spawn program, argv, the whole env, cwd, replaceEnv, timeout, class, resolveOn; the chunks and the error entry with rotate flags; an empty general log; the answer). `golden_wine_path`: `compared 16 floor 16`. Both read their MANIFEST and fail if the floor is lowered below the count, and each has a guard that a changed call or answer fails the replay.
- `script_real.rs`: real `/bin/sh` scripts prove the cwd, the env under the host env (HOME is the fake profile's), exit 2 answering `true`, a quiet run writing nothing, a background process holding the pipes not delaying resolution, and a missing script answering an error with its error entry.

## Interpretations the plan left open

- **What the op answers for a failed script.** The plan says "a failure answers the error text". The op returns it as the dispatch `Err` (the same channel as bad-args), so the 88.2-17 shim sees a thrown error with the OS's text, as the TS caller saw one. The dispatch doc comment in lib.rs now says so.
- **Cancel by shutdown.** The TS had none. A script stopped by the app shutdown answers a fixed `Err` (no log write) rather than `true`, so a launch does not carry on past a closing app.
- **Optional facts.** `executable`, `prefix` and `installPath` are optional in `ScriptRunArgs` (the TS left the env var or cwd unset when `gameInfo`/`gameSettings` had none), a superset of the plan's field list.
