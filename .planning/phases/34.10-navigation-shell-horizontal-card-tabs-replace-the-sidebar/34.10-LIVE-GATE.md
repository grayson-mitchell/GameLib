# Phase 34.10 Live Gate

## 0. Why this gate exists

Project-standing lesson, restated because it is the whole reason a "blocking" checkpoint plan
exists in this project's workflow: **a live gate has beaten a green test suite three times.**
Every automated check this phase shipped (34.10-01 through -10) is a mocked, `testEnvironment:
'node'` structural test -- the `Frontend` jest project has **no jsdom and no component
rendering** (`34.10-VALIDATION.md` § Test Infrastructure). None of them can see a pixel, move a
window, or prove a filter control is wired to anything real. This document is the first and only
check in this phase that can.

**Two rules this project has paid for twice** (`live-gate-contract-authoring.md` § Section 4),
restated here because both apply directly to this run:

1. Never use a transcript's silence to prove a path did NOT run -- if an item can't be reached,
   record it NOT ATTEMPTED and say why, never infer a PASS or a FAIL from an absence of evidence.
2. A green test suite never closes a live gate. `pnpm jest --runInBand --silent --forceExit`
   passing (modulo the one known external failure below) proves nothing about any of the five
   items below -- that is their entire reason to exist.

#### F-34.10-01 — tier-2 dropdown controls are unusable in the 204px column

**Observed** (operator, live, `pnpm tauri:dev`): hovering Categories or Filters renders a dark
panel resembling the old menu, positioned outside the left margin of the window. At least half of
it — including every checkbox — is not visible and cannot be clicked. Expected behaviour: expand
**on click**, rendered **inside the tier-2 side panel**, not as a detached popup.

**Diagnosed cause** (orchestrator, from source — not operator-supplied):

- `src/frontend/components/UI/Dropdown/index.scss` — `.dropdown { position: absolute; top: 100%;
  right: 0px; min-width: 250px; }`. Anchored to `right: 0` of a container whose width is
  `--tier2-width: 204px` (set in `NavShell/index.scss` by 34.10-02), a 250px-min-width popup
  extends ~46px past the container's left edge. Because the tier-2 column is flush to the left of
  the window, that overflow leaves the viewport entirely.
- `popUpOnHover` is passed at `CategoryFilter/index.tsx:78` and `LibraryFilters/index.tsx:265`,
  producing the mouseover trigger.
- The "black window" appearance is `background: var(--background)` plus the `box-shadow` on
  `.dropdown.expanded`.

**Why no automated check caught it:** the `Frontend` jest project is `testEnvironment: 'node'`
with no jsdom and no component rendering, so no test in this phase can observe geometry, overflow,
or a hover trigger. This is precisely the class of defect §0 of this document exists to catch.

**Scope note:** plans 34.10-01…10 portalled `<Header />` into a narrow vertical column but never
adapted `Dropdown`'s trigger or popup geometry to that context. `LibrarySearchBar` is not a
`Dropdown`, which is why search passes and only the two `Dropdown`-based controls fail — the
portal seam is correct and is not implicated. Note also that `sketch-findings-gamelib` specifies a
Games library filter panel (search, views, collections, cross-store facets, filter chips); the
gap cycle should re-read it, since the shipped controls are the old header dropdowns relocated
rather than the panel the sketch describes.

## 5. No-partial-pass rule and the NOT ATTEMPTED rule

  directly implements the pairwise review's finding in §3 (item (d)'s row) that verdicts live in
  this document, not in ephemeral state that a later item's process restart could destroy.
