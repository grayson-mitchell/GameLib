> ⚠ **HARD CONSTRAINT — no DOM.** Every jest project here is `testEnvironment: 'node'`.
> There is **no jsdom, no `react-test-renderer`, no `@testing-library/react`**, and therefore
> no component rendering and no CSS engine. `render()`, `screen.getBy*` and `userEvent` are
> **unexecutable in this repo**. Every frontend assertion uses one of two established idioms:
> direct function invocation + walking the returned React-element graph, or a source-text gate
> over SCSS/TSX/CSS read with `fs`.

> ⚠ **A grep assertion must be proven to FAIL against a known-bad input.** An unmatchable
> pattern passes vacuously. Every source-text gate in this phase carries a committed `SANITY:`
> sibling test that re-runs the same detector against a deliberately-bad input and asserts it
> flips — see `appShellLayout.test.ts` (the `--divider` theme-universality counter-check, the
> grid-shape counter-check, the literal-px reserve counter-check), `appShellMount.test.ts`
> (both mutation counter-checks) and `genI18nGateScope.test.ts` (the fabricated-stale-snapshot
> counter-check).

### M4 detail — why the staleness guard is committed skipped

`meta/__tests__/genI18nGateScope.test.ts`'s pre-existing coverage checks that every path **in**
the snapshot still **exists on disk** — the rename/delete direction. It says nothing about the
reverse: a real fork-touched file that exists on disk but was never added to the snapshot. That
reverse direction is precisely REQ-34.10-14's own named blocking trap.

The guard added by this audit re-derives "what should be in scope" through the **production call
shape** — a real `git diff --name-status <upstream.baseCommit> HEAD -- src/frontend` fed through
the real `buildScopeSnapshot`, not a hand-rolled parallel glob — and is guarded to skip when the
merge-base is unreachable, matching the CI limitation `genI18nGateScope.ts`'s own header documents.
Its non-vacuity counter-check is live and green.

It fails against real HEAD, naming six files:

```
src/frontend/screens/Library/components/FilterChipRow/chipLabels.ts
src/frontend/screens/Library/components/GamesList/index.tsx
src/frontend/screens/Library/engineWiring.ts
src/frontend/screens/Library/facetLabels.ts
src/frontend/screens/Library/filterEngine.ts
src/frontend/screens/Settings/sections/GamesSettings/index.tsx
```

All six landed in **Phase 34.11** commits dated 2026-08-10, *after* the snapshot's last
regeneration — none has ever been scanned by the blocking gate. **Phase 34.10's own contribution
is clean** (17/17 `NavShell/` files present), so this is an out-of-phase defect surfaced by a
correct test, not a Phase 34.10 gap.

The obvious fix — `pnpm gen-i18n-gate-scope` — is **blocked on WR-17** (`34.11-REVIEW.md`): the
snapshot's `generatedBy`/`baseCommit` provenance is already false (hand-edited across three
commits), and `pnpm i18n` carries pre-existing catalog drift that must be triaged **first**, or a
regeneration silently drops the 8 new panel files from the localisation gate along with the
catalog keys. Committing the guard red would have taken `pnpm test:ci` from green to one failing
suite, masking unrelated regressions.

**Un-skip (delete the `.skip`) the moment WR-17 is triaged and the snapshot is legitimately
regenerated.**
