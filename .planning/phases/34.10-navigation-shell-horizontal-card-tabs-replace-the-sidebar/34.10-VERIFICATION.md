### One-cause-or-several verdict (governing hypothesis)

**Verdict: at least TWO distinct causes, not one.** Evidence does not support folding F-34.10-03,
-04 and -06 into a single gap-cycle plan.

- **F-34.10-06 (navbar scrolls away) — CONFIRMED single, distinct, source-provable cause.**
  `git show 0000baf94` (`feat(34.10-08): restructure App grid into four areas for the nav shell`)
  deletes the old `.App .Sidebar { grid-area: sidebar; max-height: 100vh; position: sticky; top:
  0px; }` rule. Its own commit message states the intent: *"layout ownership for navbar/tier2 stays
  in NavShell/index.scss (plan 02), not duplicated here."* `NavShell/index.scss` was read in full
  for this verification and contains no `position: sticky`, `position: fixed`, or `max-height:
  100vh` rule anywhere. The stated relocation never happened — this is a clean, single-line
  regression. `.App` itself is `min-height: 100vh` (a floor) with no `overflow` restriction, so a
  tall route grows the whole grid (navbar row included) and the document scrolls as one unit,
  exactly matching the report.
- **F-34.10-03 (10px seam) — a SEPARATE, distinct candidate cause, unrelated to scroll pinning.**
  The sketch's own reference recipe (`navigation-shell.md` § "Card / folder tab") specifies
  `.navbar { ...; border-bottom: 1px solid var(--color-border); }` as the load-bearing partner to
  the active tab's erasure border. The shipped `.NavShell__navbar` rule (read in full) has **no**
  `border-bottom` at all. Without a navbar border to erase, the erasure mechanic (`top: 1px` +
  `.Mui-selected { border-bottom: 1px solid var(--body-background) }`, confirmed present in
  `NavTabs/index.scss`) has nothing to act on. This is a plausible, source-confirmed omission that
  would persist regardless of scroll state — it is not fixed by adding `position: sticky`.
- **F-34.10-04 (logo/ring wrap to second row) — NOT conclusively explained from static source.**
  `flex-wrap` is not set anywhere in the shell (grep of `NavShell/index.scss` and
  `NavTabs/index.scss` confirms this; default is `nowrap`), so a genuine line-wrap symptom cannot be
  explained by source reading alone. MUI's `<Tabs>` root (`overflow: hidden; minHeight: 48; display:
  flex;`, confirmed in `node_modules/@mui/material/Tabs/Tabs.js`) and the interaction between the
  tier-2 column's `min-content` track sizing and `.NavShell__navbar`'s two-column `navbar navbar`
  span are both plausible candidates but neither is confirmed. **This finding needs a live
  devtools measurement before a fix is attempted — it should not be assumed to share F-34.10-06's
  cause, and a planner should not guess.**

**Practical implication:** the gap cycle needs at minimum two plans (one for the confirmed
sticky/pinning fix behind F-34.10-06, one for the confirmed missing border-bottom behind
F-34.10-03), plus a diagnosis-first step for F-34.10-04 that may or may not fold into either of
those once its actual cause is known — not a single plan assuming one shared root cause, and not
four independent plans assumed without evidence either.

**Blast-radius caution for whichever plan touches `.App`'s grid or `.NavShell__navbar`'s
positioning:** this project has a standing, hardware-confirmed trap here — a WKWebView computing a
percentage height/`min-height` against a `1fr` grid row previously produced a garbage
`23323.0625px` row (F-10, `34.4.1-F10-DIAGNOSIS.md`; the fractional `.0625` is the tell). Any fix
must be live-tested under Tauri/WKWebView, not only judged in a desktop browser.
