## Coordinator Review Correction

**The originally committed fix for F-34.10-03 (Task 1, commit `1139bf1db`) was itself defective, and the defect was caught by coordinator review, not by this plan's own gate suite.**

- **What was wrong:** Task 1 painted `.NavShell__navbar`'s `border-bottom` with `var(--divider)`, reasoning (incorrectly) that `--divider` was "the same relational token `.Mui-selected` already uses for `border-color`" and therefore theme-safe. It is not: `--divider` is declared in exactly **2 of the 11 real theme blocks** in `src/frontend/themes.scss` (`body.midnightMirage` and `body.classic`/`.cyberSpaceOasis`/`.cyberSpaceOasisAlt`), confirmed both by `grep -n "^\s*--divider:" src/frontend/themes.scss` and by a structural nested-brace parse of every theme block (not string counting). Per the CSS custom-properties spec, `var(--divider)` with an undefined property and no fallback is **invalid at computed-value time**, which drops the entire `border-bottom` shorthand — not "falls back to some default colour", the declaration disappears and `border-bottom-style` reverts to its initial `none`. **No border painted at all** in the other 9 themes, including `gruvbox_dark` and `dracula`/`dracula-classic` — 3 of the 4 themes plan 34.10-21/-22's live gate actually sweeps. `src/frontend/components/UI/Dropdown/index.scss:12`'s own no-fallback `var(--divider)` `box-shadow` already demonstrated this exact collapse live, in this same phase: `34.10-F04-DIAGNOSIS.md`'s capture measured it painted in midnightMirage and `box-shadow: none` in dracula. The pattern was already proven broken in this codebase before Task 1 repeated it.
- **The fix would have shipped invisible in 3 of 4 gate themes** despite `appShellLayout.test.ts`'s original gate suite passing 100% — because that gate asserted the literal string `var(--divider)` was present, which is exactly the bug, not a check that it resolves.
- **What changed:** `.NavShell__navbar`'s `border-bottom` now uses `var(--body-background)` instead — verified (structurally, via the same nested-brace parse) to be declared in **all 11** real theme blocks. This is also a *stronger* erasure guarantee than the original relational-but-distinct `--divider` choice would have given even in the 2 themes where it resolved: the active tab's own erasure border is already `var(--body-background)` (`NavTabs/index.scss:71`), so the navbar's border and the erasure border are now colour-**identical** in every theme, not merely "close by design intent."
- **Gate suite corrected and hardened**, not just re-pinned to the new string:
  1. The existing navbar-half gate now asserts `var(--body-background)`.
  2. A new gate fails if a no-fallback `var(--divider)` is reintroduced specifically into `.NavShell__navbar` (scoped to that one rule, not the whole file or subtree — see Findings below for why a wider scope would have failed on pre-existing, out-of-scope usages).
  3. A new gate structurally proves `var(--body-background)` resolves in all 11 real theme blocks in `themes.scss` by parsing the file itself (`REAL_THEME_BLOCK_PATTERNS` + `tokenResolvesInEveryTheme`), rather than asserting a belief.
  4. A negative-control sanity test proves the same checker correctly reports `--divider` as failing (`tokenResolvesInEveryTheme('divider')` is `false`) — so the new gate is not vacuously true.

## Findings (new, recorded for future scoping — not fixed by this plan except where noted)

**`var(--divider)` is used with no CSS fallback in 4 locations app-wide**, meaning the affected borders/shadows are invisible in the ~9 themes lacking `--divider` (all except `midnightMirage` and `classic`/`cyberSpaceOasis`/`cyberSpaceOasisAlt`):

| Location | Property | In this plan's scope? | Disposition |
|---|---|---|---|
| `src/frontend/screens/DownloadManager/components/DownloadManagerItem/index.css:58` | `border-top: 1px solid var(--divider)` | No | Reported only, out of scope — a different screen entirely |
| `src/frontend/components/UI/Dropdown/index.scss:12` | `box-shadow: inset 0 0 0 1px var(--divider)` | No | Reported only, out of scope — already live-measured collapsing in `34.10-F04-DIAGNOSIS.md` (cited as evidence above); a pre-existing, independently discovered defect, not new |
| `src/frontend/components/UI/NavShell/components/NavTabs/index.scss:68` (`.Mui-selected { border-color: var(--divider) }`) | `border-color` | This plan's scope touches the *seam*, but this file is **plan 34.10-19's**, not this plan's, to edit | **Does matter for the seam recipe's visual completeness** (see analysis below) — recorded for plan 34.10-19, not fixed here |
| `src/frontend/components/UI/NavShell/index.scss:101` (`.NavShell__tier2 { border-inline-end: 1px solid var(--divider) }`) | `border-inline-end` | Yes — same file this plan already edits | **Judged NOT in scope for F-34.10-03** and left unchanged — see reasoning below |

**Why `NavTabs/index.scss:68` matters (recorded for plan 34.10-19, not fixed here, per this plan's explicit file-ownership boundary):** `.MuiTab-root` sets `border: 1px solid transparent` as its base (all four sides). `.Mui-selected` overrides `border-color: var(--divider)` — intended to make the active tab's top/left/right border visible, framing it as a raised "card" — then separately overrides `border-bottom` with the (correct, unaffected) `var(--body-background)` erasure colour. In the 9 themes without `--divider`, `border-color: var(--divider)` is itself invalid at computed-value time and drops, so the cascade falls back to `.MuiTab-root`'s own `border: 1px solid transparent` — the active tab's top/side framing border stays fully **transparent**. This does NOT break the core F-34.10-03 merge illusion (background colour match and bottom-edge erasure both still work, since neither uses `--divider`), but it does mean the "card" visual's top/side framing is invisible in most themes — a real, but secondary, defect distinct from F-34.10-03's own scope. Plan 34.10-19 should pick a token here using the same verify-in-`themes.scss` discipline this correction round established, not assume `--divider` (or any other token) is safe from its name alone.

**Why `NavShell/index.scss:101`'s `.NavShell__tier2` border was left unchanged, despite being in this plan's own file:** it draws the tier-2 sidebar column's vertical divider (between the nav column and the content area), a structurally different visual element from the horizontal navbar/content seam F-34.10-03 addresses. Fixing it is not required to close F-34.10-03, and this plan's charter (per the coordinator's reopening message) is the seam border correction plus the already-shipped scroll relocation — not a general `--divider` sweep. Left as a recorded finding rather than fixed, to avoid scope creep beyond what was requested.

## Decisions Made

- **Container-relative arithmetic for `scrollCardIntoView`, not a target swap alone.** The plan explicitly warned that swapping only the scroll target while keeping `offsetTop`-based math would convert a silent no-op into a silent wrong-offset scroll. Both destinations are now computed as `container.scrollTop + (element rect delta from container rect)`, using the `rect`/`containerRect` already available in the function.
- **Proximity thresholds compare against the container's own rect, not `window.innerHeight`.** The scroll container no longer spans the full window (navbar above it, controller row below it), so a window-relative "too close to the edge" test would fire at the wrong point. Documented in a comment at the call site.
- **`position: sticky` on the navbar was not attempted**, per the plan's explicit prohibition — documented as a dead end directly in `App.css` so a future "improvement" doesn't re-add it.
- **`var(--body-background)` chosen as the navbar border token, replacing an initial (defective) `var(--divider)` choice.** See "Coordinator Review Correction" above for the full incident and evidence.

## Issues Encountered

The coordinator review that caught the `var(--divider)` defect noted this is the **second time in this phase** a source-level inference about theme-token availability was contradicted by a live measurement (the first being `34.10-F04-DIAGNOSIS.md`'s own findings). The lesson applied going forward in this plan: any new relational CSS custom-property choice for a cross-theme surface must be verified against `themes.scss`'s actual per-theme block structure (grep + a nested-brace parse), never assumed safe from the property's name, its use elsewhere, or "this sounds like the kind of thing that would be relational." The new `tokenResolvesInEveryTheme` gate operationalizes this check as a permanent regression test rather than a one-time manual verification.
