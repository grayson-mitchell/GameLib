# Phase 34.10: Navigation shell — horizontal card tabs replace the sidebar - Context

**Gathered:** 2026-08-07
**Status:** Ready for planning

<domain>
## Phase Boundary

Replace the left sidebar with a two-tier navigation shell: tier 1 is a horizontal row of four
card/folder tabs (`Manage Accounts`, `Games`, `Stores`, `Settings`) whose active tab merges into
the content surface below it; tier 2 is a vertical contextual panel scoped to the selected tab.
`Sidebar` and `SidebarLinks` are retired and the ~14 destinations they carry are redistributed.

This phase **relocates** navigation. It does not redesign what any destination does. The Games
tier-2 panel carries today's filter controls across; the filter *redesign* is Phase 34.11.

**Note on `34.10-UI-SPEC.md`:** the `check_spec` glob matches it, but it is a **design contract**
from `/gsd-ui-phase`, not a requirements SPEC from `/gsd-spec-phase`. No requirements are locked by
it — REQUIREMENTS.md still has no 34.10 entries, and requirements are minted at `/gsd-plan-phase`.
Treat the UI-SPEC as locked *design* input (tokens, colour roles, typography, states), listed under
Canonical References below.

</domain>

<decisions>
## Implementation Decisions

### Titlebar inset & frameless mode

- **D-01: Conditional inset, no window-chrome change.** The navbar's leading inset is driven by
  whether traffic lights actually overlay the content — which is **0px today under Tauri** — rather
  than a hardcoded 78px. This phase does **not** adopt Tauri's `titleBarStyle: Overlay` /
  `hiddenTitle`. Rationale: the sketches' 78px reserve assumes an overlaid macOS titlebar that this
  branch never produces. `framelessWindow` defaults to `false` (`src/backend/config.ts:367`), so the
  default user has a native titlebar; when frameless *is* on, Tauri's `setDecorations(false)`
  removes the traffic lights entirely. Adopting overlay mode would be a chrome change riding along
  in a nav phase, and 34.1's frameless work already produced pre-paint/decoration defects (CR-02).
  Build the inset so that if overlay mode ever lands, it becomes a value change rather than a
  re-layout.

- **D-02: The tier-1 navbar row is the window drag region, gated on `isFrameless`.** Empty space in
  the tab bar drags the window; tabs, the Downloads ring and window controls stay no-drag. A
  decorated window gets **no** drag surface, since its native titlebar already provides one.
  **This is load-bearing, not cosmetic:** `src/preload/api/tauriWindowChrome.ts:333` falls back to
  `start.closest('.Sidebar') !== null` to decide what drags, and because WKWebView does not support
  `-webkit-app-region`, that fallback is the **active** path under Tauri on macOS. Retiring
  `.Sidebar` without updating this selector silently kills window dragging in frameless mode. The
  `-webkit-app-region: drag` rule at `Sidebar/index.scss:21` and its `no-drag` companions move too.

- **D-03: Tauri is the target shell; Electron must keep working, not look perfect.** Design and
  verify against Tauri. Under Electron the new nav must render and navigate correctly, but cosmetic
  imperfection is **accepted and recorded, not fixed** — notably that Electron's
  `titleBarStyle: 'hidden'` + `titleBarOverlay: true` (`src/backend/main_window.ts:45-49`) *keeps*
  macOS traffic lights, so a frameless Electron user may see them overlap the tab bar. Phase 35
  deletes Electron; do not spend effort there.

- **D-04: Theme survival is a blocking gate on three themes.** `midnightMirage` (default), `dracula`
  (inverts the relationship — navbar `#44475a` is *lighter* than body `#282a35`,
  `themes.scss:277-280`) and `gruvbox_dark` must each be visually confirmed — the active tab reads
  as merged into the content surface in all three — before the phase can close. Active states must
  be defined relationally (tab bg == content bg), never as "the navbar is the dark band".

### Top-right cluster (Downloads ring + window controls)

- **D-05: The ring lives in the navbar; the navbar reserves space for the window controls.** The
  Downloads ring sits in a nav-right cluster inside the tab bar. When frameless is on, the navbar
  adds trailing padding so `WindowControls` never overlaps it, reusing the existing
  `--overlay-controls-width` custom property (`src/frontend/index.scss:39-41`). `WindowControls`
  itself is **not** moved or restructured — 34.1 owns it and it stays at `grid-area: content;
  justify-self: right` (`WindowControls/index.scss:1-8`).
  - Corollary: the equivalent hack already in `Header/index.css:14-18`
    (`.frameless:not(.fullscreen) .Header { padding-right: ... }`) becomes dead once `Header` moves
    into tier 2 — remove it rather than leaving it to rot.

- **D-06: Ring fills with the current download's percent; the badge shows the queue count.** Both
  sources already exist — percent from the `hasProgress(appName, runner)` hook (consumed at
  `CurrentDownload/index.tsx:22`), count from the DM queue (`getDMQueueInformation` /
  `handleDMQueueInformation`, plumbed at `Sidebar/index.tsx:26-44`). Do **not** invent an aggregate
  progress source: per-item sizes vary enough that an aggregate would move unevenly and sometimes
  backwards.

- **D-07: The ring is always present — dimmed and unfilled when idle.** This **changes** today's
  behaviour, where the indicator is hidden entirely when `libraryStatus.length === 0`
  (`CurrentDownload/index.tsx:50-52`). Holding the slot avoids an element popping in and out of a
  fixed-height navbar and makes Downloads a reliably findable destination instead of one that only
  exists mid-download.

### Games tier-2 panel

- **D-08: Only `<Header>` moves into tier 2** — `LibrarySearchBar`, `CategoryFilter`,
  `LibraryFilters`. `LibraryHeader` (game count, sync status, `ActionIcons` view/sort toggles,
  `AddGameButton`) and the horizontal `<AlphabetFilter>` strip **stay above the grid**. `<Header>`
  has exactly one consumer (`Library/index.tsx:817`), so the move is clean.

- **D-09: Stack in sketch 004 variant C's order so 34.11 swaps contents in place.** Variant C
  already fixes the panel's vertical order (search on top, then views, then collections, then
  collapsed facets — `library-filtering.md:12-24`), so 34.10 stacks `LibrarySearchBar` →
  `CategoryFilter` → `LibraryFilters` in that same order. The `Header` *wrapper* loses its
  `position: sticky` and horizontal `space-between` layout to become a vertical stack; the three
  controls themselves keep their own styling. Restyling the controls to fit the column is **34.11's
  job**, not this phase's.

- **D-10: Tier-2 width is a `--tier2-width` token defaulting to 204px.** The two sketches conflict —
  003 says 204px (`navigation-shell.md:59,156`), 004's panel CSS says 218px
  (`library-filtering.md:109-111`). 34.10 builds the slot, 34.11 fills it with facet rows carrying a
  tabular-nums count column, so express the width once as a token and let 34.11 retune it in one
  place rather than hunting through the navbar, the collapse transition and the content
  `min-width: 0` rules.

### Homeless destinations

- **D-11: `HeroicVersion` moves intact to the Settings tier-2 footer.** It is **not** just a version
  label — it clears the cache on a version change (`HeroicVersion/index.tsx:33-38`) and hosts the
  `ChangelogModal` that auto-shows on startup (`index.tsx:65-73`). Dropping it from the shell would
  silently kill both. Moving the whole component preserves the behaviour with no split. (The
  UI-SPEC's suggested default — drop the label and rely on the About window — is superseded. The
  About window does exist, built in 34.1 as D-12, but it is not where the cache-clear or changelog
  live.)

- **D-12: System Information and Quit both go into the Settings tier-2 panel.** `System Information`
  (`/settings/systeminfo`, `SidebarLinks/index.tsx:228-236`) appends to the Settings nav list after
  Logs. `QuitButton` sits at the panel's bottom next to the version display — roughly where it was
  in the old sidebar. Neither is dropped; no new affordance is invented.

- **D-13: The onboarding tour is DISABLED in this phase; its rework is a separate phase.** The tour
  is not carried over, not renamed, and not rebuilt here. `SidebarTour.tsx` string-anchors
  `data-tour="sidebar-*"` selectors that will no longer resolve once the sidebar is retired, so
  leaving it live would ship silently broken steps. Turn it off (or skip its steps) and let the
  dedicated phase rebuild it against the two-tier shell. See Deferred Ideas.

### Claude's Discretion

None — every question asked was answered with a specific choice. Where the UI-SPEC's Open Questions
are not superseded by a decision above, its recommended defaults stand:
- **Wordmark** (UI-SPEC OQ5): icon only at ~28–32px, matching current shipped behaviour.
- **Search icon / avatar in `nav-right`** (UI-SPEC OQ6): omit both. No global cross-app search
  exists, and GameLib has no unified "logged in user" — stores authenticate independently.

<specifics>
## Specific Ideas

- The sketches are the reference, not a mood board: sketches `001`–`004` are committed, interactive,
  and rendered in the app's real tokens. `003`'s winning synthesis fixed tier-2 behaviour; `001`
  selected the card/folder tab style on **theme survival**, not looks.
- Two cross-artifact conflicts were found and resolved during this discussion rather than left for
  the planner to trip over: the **204px vs 218px** tier-2 width (→ D-10) and the UI-SPEC's
  assumption that the **78px inset applies today** (→ D-01, it does not).
- Two silent-breakage traps were found in the code and must be handled explicitly, not discovered
  during execution: the **`.Sidebar` drag-region fallback** (→ D-02) and **`HeroicVersion`'s
  cache-clear + changelog side effects** (→ D-11).

</specifics>

<deferred>
## Deferred Ideas

- **Onboarding tour rework — its own phase (user decision).** The current tour walks a flat sidebar
  list; the two-tier shell has tier-2 content that only exists once a tab is active, so some steps
  cannot be reached without driving the tabs. Rebuilding it against the new structure is a feature
  in its own right. 34.10 disables the tour (D-13); the new phase re-enables it. Needs a ROADMAP
  entry — `SidebarTour.tsx` and the `data-tour="sidebar-*"` selector set are its work-list.
- **macOS overlay titlebar** (`titleBarStyle: Overlay` + `hiddenTitle`) — would deliver the
  sketches' look exactly, with traffic lights floating over the navbar and the 78px reserve becoming
  real. Deliberately not adopted here (D-01) to keep window chrome out of a nav phase. D-01's
  conditional inset is built so this lands as a value change later.
- **User-collapsible tier-2 rail** (`«` shrinks to a 50px icon rail) — sketch 003 variant C,
  rejected for now, explicitly "a real option if width pressure appears later"
  (`navigation-shell.md:82`).
- **Restyling the filter controls to fit the 204px column** — deliberately 34.11's, so polish isn't
  done twice (D-09).
- **Renaming `data-tour="sidebar-*"` to `nav-*`** — honest naming, but it belongs with the tour
  phase, not here.
