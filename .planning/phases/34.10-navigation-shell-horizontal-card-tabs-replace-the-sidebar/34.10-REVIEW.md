## Summary

Reviewed the full 50-file navigation-shell changeset (NavShell root, NavTabs,
NavItem, DownloadsRing, GamesPanel/StoresPanel/SettingsPanel, Tier2PortalContext,
the scroll-container relocation in App.css/Library/GamesList, the Dropdown

(F-34.10-01 through -06, the dropdown overflow, the Downloads ring paint, the
seam/wordmark alignment, and the scroll-container relocation) were re-verified
in source and are genuinely fixed and well-guarded — no re-litigation of those
is included below.

Two BLOCKER-level defects were found that the live gate's own scope could not
have caught: an undefined CSS custom property with no fallback that makes the
active tab's label illegible in 8 of 11 themes (including one of the three
gate-scored themes), and a real Electron frameless-dragging regression caused
by the Sidebar→NavShell migration dropping a CSS declaration the retired
component had. Both are the *same class* of defect (`var()` with no fallback,
and a ported-then-silently-dropped platform affordance) that this phase's own
commit history already paid for multiple times elsewhere in the same files —
these are the instances that slipped through anyway. Two WARNING-level
robustness gaps were also found: a bypassable regression guard, and two
untranslatable store-name labels reachable through a Steam session (the
project's own primary use case). One INFO-level dead-code item rounds out the
findings.

## Critical Issues

### CR-01: Active tab's text colour is undefined (illegible) in 8 of 11 themes, including a live-gate-scored theme

> **PARTIALLY CLOSED 2026-08-23** — Phase 34.11 decision D-31, plan `34.11-03`, fix commit
> `126b9c458`; status assessed by quick task `260823-v3k`.
>
> **Closed half (1 of the 8 themes — the scored one).** `themes.scss:210` declares
> `--navbar-active: var(--navbar-accent)` inside `body.gruvbox_dark`, sourced from the theme's own
> accent rather than a literal hex. Not merely shipped: `34.11-09`'s live three-theme sweep
> returned **APPROVED 6/6** for `gruvbox_dark`, with the operator answering the contrast question
> deliberately and on purpose rather than letting it pass as a side effect of a general "selected
> is distinguishable" check — superseding plan 03's own "recommendation, not a measured result"
> hedge. This discharges this finding's own demand to re-measure rather than fix-and-assume.
>
> **Corrected diagnosis.** At `NavItem/index.scss:20-23` the fallback chain never breaks, so the
> symptom *there* was a WRONG colour (`--accent-overlay`, mustard `#d79921`), not a dropped
> declaration. This report's "falls through to inherited" analysis holds for `NavTabs`, which has
> no fallback — two elements, two failure modes, one shared root token.
>
> **STILL OPEN — the other 7 themes, i.e. the majority of this finding.** A census at HEAD finds
> `--navbar-active` still undeclared in `classic`/`cyberSpaceOasis`/`cyberSpaceOasisAlt`,
> `high-contrast`, `nord-dark`, `marine`/`marine-classic`, `zombie`/`zombie-classic`,
> `old-school`, `sweet`/`sweet-dark`; and the consuming site (now line 246 — the line moved, the
> declaration did not) still has no fallback chain. Tracked as a pending todo. **Do not read the
> D-31 discharge as closing this finding as a whole** — D-31 undertook the scored theme and
> delivered exactly that.

**File:** `src/frontend/components/UI/NavShell/components/NavTabs/index.scss:229`
**Issue:** `.MuiTab-root.Mui-selected` sets `color: var(--navbar-active);` with
no fallback. `--navbar-active` is declared in only 3 of the 11 real theme
blocks in `src/frontend/themes.scss` (`midnightMirage` line 92, `dracula` line
281, `nord-light` line 340) — it is **not** declared in `gruvbox_dark`, one of
the exact three themes the phase's own live gate scores (per
`34.10-LIVE-GATE.md` item 1), nor in `classic`/`cyberSpaceOasis*`,
`high-contrast`, `nord-dark`, `marine*`, `zombie*`, `old-school`, or
`sweet*`. Per the CSS custom-properties spec, `var()` referencing an
undefined property with no fallback is invalid at computed-value time; for an
inherited property like `color`, the browser does not fall through to a
lower-specificity rule in the same cascade (e.g. `.MuiTab-root`'s own
`color: var(--navbar-inactive)`) — it uses the **inherited** value from the
ancestor chain instead. Nothing in `.NavShell__navbar`, `.App`, or `body` sets
an explicit `color`, so the active tab's label text in `gruvbox_dark` (and the
7 other affected themes) renders in the browser's default inherited/initial
text colour instead of a theme-appropriate one, against the `--body-background`
fill this same rule paints on the tab (`background: var(--body-background)`
two lines above) — a low/zero-contrast, effectively illegible active-tab
label. Concrete failure scenario: a user on the default-scored `gruvbox_dark`
theme clicks any tier-1 tab; the tab visually "merges" correctly (background
and border both use the safe `--body-background` token), but the tab's own
label text is unreadable because `color` silently reverted to an unstyled
inherited value.

This is the exact defect class (`var()` referencing an undefined,
no-fallback custom property) that this same file and its sibling
`NavShell/index.scss` already diagnosed and fixed **twice** for
`border-color`/`border-bottom` (both extensively documented in the
surrounding comments, lines 230–252 of this file and the header comment of
`NavShell/index.scss`) — yet this one `color` declaration, three lines above
that fix, was never given the same treatment. The sibling file
`NavItem/index.scss:21-24` (same phase, same PR family) demonstrates the
author was aware `--navbar-active` needs a fallback chain
(`var(--navbar-active, var(--accent-overlay, var(--accent)))`), so the
omission here is an inconsistency within the phase's own code, not a novel
unknown. No test in the reviewed suite (including
`appShellLayout.test.ts`'s `tokenResolvesInEveryTheme` helper, built for
exactly this purpose) checks `--navbar-active`.

**Fix:**
```scss
&.Mui-selected {
  background: var(--body-background);
  color: var(--navbar-active, var(--navbar-accent));
  ...
```
(`--navbar-accent` is confirmed declared in all 11 real theme blocks —
verified directly against `themes.scss`.) Add a
`tokenResolvesInEveryTheme('navbar-active')`-style assertion, or an explicit
fallback-presence assertion on this declaration, to `appShellLayout.test.ts`
so the fix is guarded the same way `--body-background` already is.

### CR-02: Electron frameless-window dragging by the navbar is broken — no `-webkit-app-region: drag` ported to `.NavShell__navbar`

> **CLOSED 2026-08-23** — Phase 34.11 decision D-32, plan `34.11-03`, fix commit `75e3785da`;
> status assessed by quick task `260823-v3k`.
>
> `NavShell/index.scss:85` declares `-webkit-app-region: drag`, with `no-drag` added to `.NavTabs`
> and to `.NavShell__navRight .DownloadsRing` so the restored drag region cannot swallow tab or
> Downloads clicks. `WindowControls` already carried its own and was left unchanged.
>
> **SOURCE-VERIFIED-ONLY, PERMANENTLY — never restate this as live-confirmed.**
> `-webkit-app-region` is inert under WKWebView, and this project's dev and live-gate host is
> macOS running Tauri, so no live drag test on this host can ever exercise this CSS; the drag that
> does work there is `tauriWindowChrome.ts`'s untouched `closest('.NavShell__navbar')` path.
> `34.11-09-SUMMARY.md` records this as a **permanent accepted limitation, not a gap awaiting
> future closure.** The `themeTokens.test.ts` source-text gate is this finding's only possible
> evidence, by construction rather than by omission.

**File:** `src/frontend/components/UI/NavShell/index.scss` (whole file — the
declaration is simply absent); collateral: `src/frontend/components/UI/NavShell/components/HeroicVersion/index.scss:35`
**Issue:** The retired `.Sidebar` (deleted in commit `0559bc0d0`, feat 34.10-09)
declared `-webkit-app-region: drag` on itself, with `no-drag` overrides on two
interactive children — confirmed via `git show 0559bc0d0~1:src/frontend/components/UI/Sidebar/index.scss`,
which shows `-webkit-app-region: drag` at line 21 and two `no-drag` overrides
at lines 40/50. This was Electron's (Chromium's) **native, CSS-only**
mechanism for making the sidebar draggable when `settings.framelessWindow` is
enabled (`src/backend/main_window.ts:45-49` sets `titleBarStyle: 'hidden'` in
exactly that case). `.NavShell__navbar`, the component that structurally
replaces `.Sidebar` as the draggable chrome region, never received an
equivalent `-webkit-app-region: drag` declaration — confirmed by grepping the
entire `src/frontend` tree: the only two occurrences of `-webkit-app-region`
anywhere in the reviewed tree (and the whole frontend) are both `no-drag`
(`HeroicVersion/index.scss:35`, ported verbatim from the old Sidebar, and
`WindowControls/index.scss:6`). There is no JS-based fallback available to
Electron: `installDragRegionHandlers`/`resolveDragRegion` in
`src/preload/api/tauriWindowChrome.ts` is gated behind `if (!isTauri()) return`
(line 359) and is never installed under Electron at all — that mechanism was
built specifically because Tauri's WKWebView does *not* honour
`-webkit-app-region`, whereas Chromium (Electron) does and has always relied
on it exclusively.

Concrete failure scenario: a user on Electron (still shipped, not deleted
until Phase 35) enables Settings → General → "Frameless window". The titlebar
hides (`titleBarStyle: 'hidden'`), and the user now has no way to drag the
window by empty navbar space, because no ancestor of that space declares
`-webkit-app-region: drag`. The vestigial `no-drag` on
`HeroicVersion/index.scss:35`'s links is now dead CSS with nothing above it to
override.

The live gate did not catch this: Item 2 ("Real window dragging under
WKWebView") explicitly scoped itself to `pnpm tauri:dev` only, and Item 5
(the Electron item) tested only shell render, tab navigation, and the
traffic-light overlap observation — dragging was never exercised under
Electron in any of the four gate runs.

**Fix:**
```scss
.NavShell__navbar {
  grid-area: navbar;
  height: var(--navbar-height);
  background: var(--navbar-background);
  -webkit-app-region: drag; /* restores Electron's native drag affordance,
                                lost when .Sidebar was retired (34.10-09) */
  display: flex;
  ...
```
plus `-webkit-app-region: no-drag` on `NavTabs`, `DownloadsRing`, and any
other interactive nav-right control (mirroring what the old `.Sidebar` did
for its own children, and what `HeroicVersion`'s already-present `no-drag`
assumes exists above it). Tauri is unaffected either way since its WKWebView
ignores the property and uses the separate JS mechanism.

### WR-01: `muiTabsSelectorScoping.test.ts`'s guard is bypassable by wrapping the unscoped selector in `@media`/`@supports`

> **CLOSED 2026-08-23** — quick task `260823-tct`, commit `4f44ef280`. The
> single brace-depth counter is replaced by a stack of block kinds: scope depth
> is the number of `rule` frames, and `@media`/`@supports`/`@container`/
> `@layer`/`@document` push a `transparent` frame that does not satisfy the
> "scoped" condition. `@keyframes`/`@font-face` stay opaque — their contents
> are not selectors, so treating them as transparent could only manufacture
> false positives on `from`/`to`/percentage preludes.
>
> **Proven in both directions, which is the point of this finding.** All 11 new
> cases were run against the *unmodified* scanner first: the 7 detection cases
> failed with `Expected length: 1 / Received length: 0 / Received array: []` —
> reproducing this finding's own empirical claim exactly, in the file rather
> than in an extracted copy — and the 4 silence proofs passed both before and
> after. This finding's fix went further than the prescribed one in a way worth
> recording, per the project's own `review-prescribed-fix-can-carry-the-same-defect`
> lesson: the recommended "at-rule depth counter" would have closed the
> `@media`/`@supports` bypass while leaving `@container`/`@layer`/`@document`
> and the second miss below untouched.
>
> **Second, independent miss found while fixing this one.** `selectorStart` was
> only reset when depth returned to 0, so a preceding top-level declaration or
> SCSS variable was swept into the selector text: `$leak: 8px;` before
> `.MuiTabs-root {` made the first compound read `$leak:`, and the offender went
> unreported. The prelude is now taken as the text after the last `;`. Not part
> of WR-01 as filed — same guard, same bypass shape, so it is closed here rather
> than filed separately.
>
> Every pre-existing test in the file is unmodified and green; the repo-wide
> sweep stays green (no stylesheet is newly convicted, confirmed against the
> `@supports` blocks in `GamePage/index.css:811-882`, which sit under two real
> rule frames); full `Frontend` jest project 122 suites / 2005 tests green.

**File:** `src/frontend/__tests__/muiTabsSelectorScoping.test.ts:109-125` (the `findUnscopedMuiTabsSelectors` brace-depth walk)
**Issue:** This is the repo-wide regression guard against F-34.10-03/-04's
root cause recurring (an unscoped `.MuiTabs-root` selector leaking padding
into every `<Tabs>` in the app). Its brace-depth counter treats **any**
opening `{` as incrementing depth, including an `@media (...) {` or
`@supports (...) {` at-rule wrapper — so a selector nested one level inside
either at-rule is evaluated at depth 1, which the algorithm treats as
"already ancestor-scoped" and never flags. Verified empirically by extracting
the function and running it against:
```css
@media (max-width: 600px) {
  .MuiTabs-root {
    padding-bottom: 8px;
  }
}
```
which returns zero offenders — identical in effect to the exact top-level
form this guard exists to catch (an at-rule provides no ancestor-element
scoping; `.MuiTabs-root` still matches every `<Tabs>` in the app whenever the
media query is active). The same is true for `@supports`. This is currently
dormant — no file in the reviewed tree wraps a `MuiTab*`/`MuiTabs*` selector
in `@media`/`@supports` at the top level — but the guard's stated promise
("no frontend stylesheet declares an unscoped MuiTab*/MuiTabs* selector") does
not actually hold for at-rule-wrapped rules, and this is exactly the kind of
guard the project has already had fail silently once (F-34.10-07/-08 record
two prior instances of an authored-but-never-adversarially-exercised check in
this same phase).

**Fix:** Track a separate "at-rule depth" that does not count toward the
"ancestor scoping" depth, or only treat depth-0-under-non-at-rule braces as
truly unscoped (i.e. increment a counter for `@`-prefixed preludes separately
and don't let it satisfy the "scoped" condition). Add a bypass regression test
mirroring the existing `PRE_FIX_SPECIMEN` test, wrapping the same specimen in
`@media (min-width: 1px) { ... }` and asserting it still yields one offender.

### WR-02: `LibraryFilters`'s Steam and ZOOM Platform filter labels are untranslatable — `t()` called with a computed key that is never registered

**File:** `src/frontend/components/UI/LibraryFilters/index.tsx:216-219` (`RunnerToStore` table used at line ~218, `t(RunnerToStore[store])`)
**Issue:** `storeToggle` calls `t(RunnerToStore[store])` with no default value
and no extraction-hint comment for the `steam` and `zoom` entries.
`RunnerToStore.steam = 'Steam'` and `RunnerToStore.zoom = 'ZOOM Platform'` are
used as translation keys, but neither `'Steam'` nor `'ZOOM Platform'` exists
as a top-level key in `public/locales/en/translation.json` (verified directly
against the JSON) — unlike `'Epic Games'`, `'GOG'`, and `'Amazon Games'`,
which **are** registered and which this same file explicitly annotates with
extraction hints three lines above (`// t('Epic Games', 'Epic Games')` etc.,
lines 203-205) specifically because the i18next static extractor cannot see a
computed template-literal/object-lookup key. Concrete failure scenario: any
user with a connected Steam account (the primary audience for this project,
per `CLAUDE.md`) opens the Library Filters dropdown — `{steam.username &&
storeToggle('steam')}` at line 270 fires unconditionally for them. The
"Steam" toggle label falls back to the raw i18next key (`'Steam'`, which
happens to read correctly in English by coincidence) and can never be
translated into any other locale, because it was never captured by the
extractor and never registered in `meta/i18nGateScope.json`'s scan surface.
Same for a ZOOM-enabled, logged-in user's ZOOM Platform toggle. This predates
phase 34.10 (traced via `git log --follow` to `925bc3129`/`490721ed2`,
well before this phase) and this phase's only touch to the file was the
click-vs-hover dropdown fix (`0b005b190`), but the file is in this review's
scope and the standing project convention (`CLAUDE.md`'s localisation
requirement) treats this as a real, currently-shipping gap.

**Fix:** Add the same extraction-hint pattern already used for the other
three entries:
```ts
// t('Steam', 'Steam')
// t('ZOOM Platform', 'ZOOM Platform')
const RunnerToStore = { ... }
```
and register both keys via the project's `pnpm i18n` extraction pass so they
land in `translation.json` and become translatable.

## Info

### IN-01: Dead `data-tour` props passed to `Dropdown`, which does not accept or forward them

**File:** `src/frontend/components/UI/CategoryFilter/index.tsx:76`, `src/frontend/components/UI/LibraryFilters/index.tsx:264`
**Issue:** Both call sites still pass `data-tour="library-categories"` /
`data-tour="library-filters"` to `<Dropdown>`. `Dropdown`'s `Props` type
(`src/frontend/components/UI/Dropdown/index.tsx:4-9`) declares only `title`,
`children`, `className`, `buttonClass` — `data-tour` is accepted by TypeScript
only because JSX special-cases `data-*`/`aria-*` attributes, but `Dropdown`'s
function body never reads or forwards it to any rendered DOM node, so it is
silently dropped and has no effect. Per this phase's D-13 (tour disabled),
every other file that carried a tour-anchor prop explicitly removed it
(`NavItem/index.tsx`'s own header comment states this outright, and
`tourDisabled.test.ts` structurally proves no `NavShell/` source file
references `data-tour`) — these two call sites, outside the `NavShell/`
directory, were missed and are not covered by that test's scope. Harmless at
runtime, but misleading: a future reader (or a future tour-rework phase) could
reasonably assume this wiring already routes to the DOM when it does not.
**Fix:** Remove both `data-tour` props, or add `className`/a real anchor
mechanism if a future tour rework needs them.
