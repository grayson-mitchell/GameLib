# F-34.10-02 cause (b) — live discriminator diagnosis

Root-causing: `--dl-progress` never leaves `0turn` in `DownloadsRing` during a real, active
download (34.10-LIVE-GATE.md, Item 4, F-34.10-02 defect 2). This file does not re-measure the
already-recorded ring-visibility defect (defect 1 / cause (a), closed by plan 34.10-14). It
discriminates between six hypotheses for cause (b) using a live measurement taken BEFORE any
source is read for a fix, per this project's standing lesson ("when two readings both fit, build
the discriminator").

The gate author's own suggested cause — a keying/remount or timing difference vs. the retired
`CurrentDownload` — is already FALSIFIED at planning time: `git show 0559bc0d0^:src/frontend/
components/UI/Sidebar/index.tsx` shows the retired component subscribed to the identical channel,
took the identical `elements[0]`, and rendered with the identical `key={...params.appName}`. That
hypothesis is not re-tested below.

## Preconditions

**Single-process precondition: initially FAILED, then remediated before the measurement run.**

At preparation time, both precondition commands returned PIDs (expected: both empty):

```
$ pgrep -f 'tauri dev'
82361
82413
$ pgrep -f 'target/debug/gamelib'
75433
82506
```

Inspection (orchestrator, `ps -o pid,ppid,etime,command`):

| PID | PPID | Elapsed | Command |
|---|---|---|---|
| 75433 | 1 | 02:48:24 | `target/debug/gamelib-shell` |
| 82361 | 82347 | 01:47:52 | `sh -c electron-vite build && pnpm build:sidecar && tauri dev` |
| 82413 | 82361 | 01:47:46 | `node .../node_modules/.bin/tauri dev` |
| 82506 | 82413 | 01:47:46 | `target/debug/gamelib-shell` |

There were TWO separate `gamelib-shell` processes alive at that point: PID 75433 (no parent —
orphaned or independently launched, PPID 1) and the 82361/82413/82506 tree (a live
`pnpm tauri:dev` build+run chain, ~1h48m old). This is exactly this project's recorded
capture-integrity trap (F-34.4.2-15/-18): a concurrent second instance can silently split the
`[shell]` log sink and produce a half-observed run that looks fully measured.

**Remediation: the human stopped both existing instances before measuring.** Both `pgrep -f
'tauri dev'` and `pgrep -f 'target/debug/gamelib'` were confirmed empty, then a single fresh
`pnpm tauri:dev` was launched for the measurement run below. The initial failure is recorded here
honestly rather than omitted; the run itself proceeded single-process.

**Installable-game precondition:** met — a real download was started and run to completion of the
three-question measurement.

## Live measurement (run 1)

Ask in this order (Q1, then Q3, then Q2 — minimises navigation: Q1 and Q3 are both answered from
`/download-manager` without leaving the screen; Q2 requires switching to the Games tab).

| # | Question | Why it discriminates | Answer |
|---|---|---|---|
| Q1 | During the SAME active download, does the `/download-manager` screen's own per-item percent readout advance past 0%? | `DownloadManagerItem/index.tsx:91` calls `hasProgress(appName, runner)` with the identical key shape. Advancing => the `progressUpdate` -> `InstallProgress` -> `hasProgress` path is ALIVE and the fault is local to `DownloadsRing`. Stuck at 0% => the fault is upstream and app-wide, and is NOT a 34.10 regression at all. | YES — the readout advances past 0% |
| Q3 | On `/download-manager`, is the FIRST item in the queue list the game that is actually downloading, or is a different (queued, not started) item first? | `DownloadsRing` binds to `elements[0]`. If the actively-downloading element is not `elements[0]`, the ring is correctly reading a genuinely-zero-percent element and the bug is the binding, not the data. | YES — the downloading item was at the top of the queue; `elements[0]` genuinely is the actively-downloading element |
| Q2 | During the same download, does the game's card in the Games grid show advancing install progress? | `GameCard/index.tsx:147` is a third, independent consumer of the same hook. Two agreeing surfaces beat one. | YES — the game's card in the Games grid shows advancing install progress |

All three answers recorded as exactly `YES` — no blank and no unfilled placeholder of any kind.

**What these answers mean, and what they FORECLOSE:**
- The `progressUpdate` -> `InstallProgress` store -> `hasProgress` path is ALIVE. Two independent
  consumers (`DownloadManagerItem/index.tsx:91`, `GameCard/index.tsx:147`) using the identical key
  shape both advance during the same download. Any hypothesis of the form "the transport is dead",
  "the store never updates", "the listener never registers", or "the key shape is wrong app-wide"
  is REJECTED by this live observation (Q1, Q2).
- `elements[0]` IS the downloading element (Q3). The hypothesis "the ring binds to the wrong queue
  element / a genuinely-zero-percent queued item" is REJECTED by this live observation.
- Combined with the two hypotheses already falsified at planning time (lost `appName` key;
  different remount behaviour — both dead per `git show 0559bc0d0^:src/frontend/components/UI/
  Sidebar/index.tsx`), the surviving cause MUST be local to `DownloadsRing/index.tsx` itself — in
  how `RingProgress` consumes/derives the percent, or in how `--dl-progress` is computed and
  applied from it.

## Verification steps for the developer

Roughly five minutes, one download.

1. Stop both existing app instances found above (PIDs 75433 and 82361/82413/82506's tree), then
   confirm `pgrep -f 'tauri dev'` and `pgrep -f 'target/debug/gamelib'` both print nothing.
2. Run `pnpm tauri:dev`.
3. Start any real download from any store.
4. **Q1** — go to `/download-manager` (click the Downloads indicator in the navbar). Watch the
   downloading item's own percent readout for ~20 seconds. Report: does the number advance past
   0%, or does it sit at 0%?
5. **Q3** — while still on `/download-manager`, report whether the item at the TOP of the queue
   list is the one actually downloading, or whether a different, not-yet-started item is listed
   first.
6. **Q2** — go to the Games tab. Find the downloading game's card in the grid. Report whether it
   shows advancing install progress.

Answer each question yes/no. If a question could not be reached, say "not attempted" and why —
do not guess.
