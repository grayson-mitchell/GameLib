## F-34.10-05 verdict

Two readings evaluated against `dropdownPanel.computed['background-color']`,
`dropdownPanel.tier2Computed['background-color']` and `tokens.background`/`tokensOnPanel.background`
from both theme captures.

**W1 (wrong token for the new surface) — SURVIVES, reproduces in dracula (measurable), consistent
in midnightMirage (invisible by coincidence).**

- Dracula: `dropdownPanel.computed['background-color']` = `rgb(9, 11, 28)` = `#090b1c` exactly
  equals `tokensOnPanel['--background']` = `#090b1c` (and every ancestor in
  `backgroundTokenChainFromPanel`, all ten levels down to `<body class="dracula">`, resolve to the
  identical `#090b1c` — the custom-property chain is fully healthy, nothing fails to inherit).
  `dropdownPanel.tier2Computed['background-color']` = `rgb(68, 71, 90)` = `#44475a` equals
  `tokensOnPanel['--navbar-background']` = `#44475a` — the tier-2 column paints a **different**
  token than the panel does. Confirmed at source: `src/frontend/components/UI/Dropdown/index.scss:23`
  declares `.dropdown { background: var(--background); }`, while
  `src/frontend/components/UI/NavShell/index.scss:78` declares
  `.NavShell__tier2 { background: var(--navbar-background); }` — the panel and the column it lives
  in name two different surface tokens. `--background` (`#090b1c`, near-black navy) on top of the
  column's `#44475a` (mid grey-purple) is the reported "black block".
- midnightMirage: `dropdownPanel.computed['background-color']` = `rgb(22, 28, 30)` and
  `dropdownPanel.tier2Computed['background-color']` = `rgb(22, 28, 30)` — **identical** in this

  `#161c1e` = `rgb(22,28,30)`, same as `--navbar-background` in midnightMirage) — the bug is
  invisible here purely because the two tokens happen to coincide in this one theme, exactly the
  trap the multi-theme rule exists to catch. (Capture 1's own custom-property *token* read was
  bugged — see harness note above — but its raw `background-color` computed values are unaffected
  by that bug and are used here.)

**W2 (custom property fails to resolve in the portalled context) — REJECTED in both themes.** The

## Surviving hypotheses

**F-34.10-04 — one cause: `NavTabs/index.scss`, unset `min-height` on `.NavTabs .MuiTab-root`.**
The fix belongs in `src/frontend/components/UI/NavShell/components/NavTabs/index.scss`, as a
`.NavTabs .MuiTab-root { min-height: ...; }` override that constrains MUI's default `72px`
icon+label height down toward (not below) content, **not** as a `--navbar-height` change in
`NavShell/index.scss`. Raising `--navbar-height` to 72px+ would grow the whole navbar band
(wordmark, ring, and the tier-2 column's top edge all key off it) just to accommodate one child's
default sizing, and would not by itself fix the 8px erasure-border gap identified under H5, which
is about where the *tab* sits within its own 80px-tall container, not the navbar's own height. A
`min-height` override on `.MuiTab-root` must not make the tab shorter than its own label+icon
content (would clip or wrap the label text) and must preserve the `top: 1px` overlap the seam
recipe depends on (`NavTabs/index.scss:29`) — the override should bring the tab's rendered height
down close to `--navbar-height` (56px) while leaving enough for the icon-row layout, and should be
verified against the same live capture technique afterward, not against source alone.

**F-34.10-05 — one cause: `Dropdown/index.scss:23`, `.dropdown { background: var(--background); }`
names the wrong token for a panel now living inside the tier-2 column.** The fix belongs in
`src/frontend/components/UI/Dropdown/index.scss` (or a `.NavShell__tier2`-scoped override, if
`Dropdown` is reused outside the tier-2 context elsewhere and a blanket token swap would regress
that other usage — not checked by this plan, flagged for plan 34.10-20 to verify before choosing
between a component-level change and a scoped override). The panel's background should resolve
relationally to the surface it now sits on (`var(--navbar-background)`, matching
`.NavShell__tier2`'s own declaration at `NavShell/index.scss:78`) rather than to `--background`,
which was correct for the panel's old full-width-header context and is wrong inside a column
painted a different token. Both surviving causes are inside
`src/frontend/components/UI/NavShell/` and `src/frontend/components/UI/Dropdown/` respectively —
neither falls outside those directories, so no plan's scope needs to change on that account.
