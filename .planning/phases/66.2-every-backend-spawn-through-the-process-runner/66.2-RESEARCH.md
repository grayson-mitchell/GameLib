## Summary

The census is exact and small enough to plan against: **27 non-sanctioned files** under `src/backend` import `child_process`/`node:child_process` (28 per `pnpm backend-di-ceilings`, which also counts the sanctioned runner `src/backend/process/runner.ts`). `src/common` and `src/frontend` production code import it nowhere. `meta/` (about 30 build/CI scripts) imports it legitimately and is outside the ceilings and the ban. The gate counts static import/export-from, `import x = require()`, `require()` and dynamic `import()` of the two module names, type-only imports excluded, per file, in non-test files only. There are no `.js/.cjs/.mjs` production files under `src/backend` and no `execa`/`cross-spawn`/`shelljs`/`node-pty` dependency, so WR-05's npm-package bypasses are theoretical today; the real unclosed bypasses are `process.getBuiltinModule('child_process')`, `createRequire(...)('child_process')` and computed specifiers (all return 0 in the current counter - verified).

The runner (`src/backend/process/runner.ts`, 391 lines) already provides everything needed: `run` (timeout default 30 s, SIGKILL on expiry, `timeout:{none,reason}` opt-out, `signal`, `onStdout/onStderr`, `stdin`, `resolveOn`, `maxBufferBytes`, `replaceEnv`), `spawnLongLived`, `runSync` (required timeout + reason), `openDetached`. Every spawn in the 27 files maps onto one of the four. The hard parts are not the spawns, they are (a) **sync call sites with no context available** (`config.ts` factory defaults, `getDefaultWine`, `pathShim`/`knownFolders`, `nativeImageShim`) where no runner instance can reach the code without new module state, (b) the **cascade of callers** each conversion forces (R3: dependency becomes the first parameter, the cascade ends at a registration, boot step or manager constructor), and (c) **behavioural deltas between `execFile`/`spawn`/`spawnSync` and `run`** that silently break code (open stdin pipe, spawn errors reject instead of calling back, non-zero exit resolves instead of rejecting, `stdio` option rejected by the injected `spawnAsync`).

**Primary recommendation:** do the gate hardening first (plan 01, alone, so later plans lower from a true baseline), then convert in dependency order (utils.ts, engine, shims in parallel; DRM and the leaf utils; compat/config and Steam probes; tools and the mac Steam client), and land the ban last as an ESLint `error` scoped to `src/backend` production code **plus** a dependency-cruiser rule (which sees `require()`/`import()` natively - verified) **plus** the hardened AST census as a jest gate. Resolve OQ-1 (config.ts/getDefaultWine) with the user before planning plan 03.

### Recommended structure (no new directories)
Each converted module exports `createX(deps)` when it has three or more dep-taking functions or closure state, otherwise a `deps`-first parameter (README R3). Narrow slices are typed with `Pick`/`AppContext['runner']`, never the whole context (R1). No `deps = defaultDeps` default arguments (R3/R4): replace `defaultEngineDecisionDeps()`, `defaultMacSteamOfflineDeps()`, `defaultRunTool`, `defaultRunCodesign`, `defaultRunUnzip`, `defaultRunPs`, `defaultDeps()` (download monitor).

### Pattern 1: A spawn site on the runner (template used by 66.1 for `spawnAsync`)
**What:** replace a bespoke `new Promise` + `spawn` + timer + unref block with one `runner.run` and a result mapper.
```ts
// Source: src/backend/process/runner.ts (read this session); shape follows 66.1 spawnAsync.ts
export function createIsMacSteamRunning(deps: { runner: AppContext['runner'] }) {
  return async (timeoutMs = MAC_STEAM_PROBE_TIMEOUT_MS): Promise<boolean> => {
    const profile = createFakeHomeProfile({ prefix: 'gamelib-drm-steam-probe-' })
    try {
      const r = await deps.runner.run('/usr/bin/pgrep', ['-x', 'steam_osx'], {
        env: profile.childEnv(),
        replaceEnv: true, // the profile env is the whole env, as with the old spawn
        stdin: '', // old stdio:'ignore' => immediate EOF; an open stdin pipe is the runner default
        timeoutMs
      })
      if (r.timedOut) throw new Error(`pgrep timed out after ${timeoutMs} ms`)
      if (r.code === 0) return true
      if (r.code === 1) return false
      throw new Error(`pgrep exited ${r.code}`)
    } finally {
      profile.dispose()
    }
  }
}
```

### Pattern 2: Spawn error mapping
`run` rejects on spawn `error` (ENOENT/EACCES) and resolves everything else (non-zero exit, signal, timeout, abort). Callers written against `execFile`'s callback `(err, stdout)`, `exec`'s rejection, or `spawn`'s `child.on('error')` need the same three-way mapping: `rejection -> failure`, `timedOut -> failure`, `code !== 0 -> failure (or a domain meaning, e.g. pgrep 1)`.

### Pattern 3: scripted-runner test replacing `jest.mock('child_process')`
```ts
// Source: src/backend/process/README.md "Writing a test"

Use `createRealRunner` (fake HOME) only for the loop-drain measurement in the `boundedListing` test and the existing real-child `childWatchdog` test.

### Anti-Patterns to Avoid
- **Reaching for a module-level runner.** No `getRunner()`, no `let runner` binder: it adds census module state (251 must not rise) and re-creates the locator D-01 forbids. Use the existing `bindTransport` seam only where a module is a singleton by construction (`platform/index.ts`).
- **Dropping `stdin: ''`.** See Pitfall 1.
- **Passing `stdio`/`detached`/`shell` options** to the injected `spawnAsync` (throws) or expecting them on `run` (does not exist).
- **Raising a ceiling to admit growth.** Each plan lowers its shard entries in the same commit.
- **Editing the legacy `AbortError` semantics silently.** None of the 66.2 callers pass a `signal` to the legacy `spawnAsync`, so there is nothing to preserve there; but `tools` winetricks and `bridge*Lifecycle` do pass `signal` to the injected one and already handle `aborted`.

Not a rename/migration phase. Stated explicitly for the one adjacent concern, runtime state that survives a code conversion:

## Common Pitfalls

### Pitfall 1: Open stdin pipe by default (66.1 A-IN-3, unfixed)
**What goes wrong:** `run`/`spawnLongLived` use `stdio:'pipe'`; stdin stays open unless `stdin` is passed. Sites that used `stdio:['ignore',…]` relied on immediate EOF.
**Why it happens:** `execFile`/`spawn` call sites in `runTool`, `demoStatus`, `drm*`, `valveClient`, `steamclientLayerInstall`, `runningFromFolder`, `macSteamAdoption` all used `'ignore'` for stdin.
**How to avoid:** pass `stdin: ''` (writes nothing and ends the stream; verified in `runner.ts:290-296`). Mandatory for `unzip` (prompts on overwrite), advisable for every `'ignore'` site. Add a scripted-runner assertion that `opts.stdin === ''` for these sites.
**Warning signs:** a probe that now always times out; an `unzip` that hangs to its 120 s cap.

### Pitfall 2: `execFile`/`exec` rejected on non-zero exit, `run` does not
**What goes wrong:** code that did `try { await execAsync(...) } catch { treat as missing }` now treats every non-zero exit as success.
**How to avoid:** write one local helper per module (or reuse a shared `ok(result)` = `!timedOut && !aborted && code === 0`) and use it at every converted site; the shell-string table above lists the intended outcome per call. A scripted test with `result: { code: 1 }` for each.

### Pitfall 3: `run` rejects on spawn failure while old code swallowed or hung
**What goes wrong:** `os/path` (`which` ENOENT had no `error` listener = uncaught exception risk), `getCometVersion`, `config.ts`. A converted site that does not `catch` would now surface an exception where the old code resolved `null`/`'invalid'`.
**How to avoid:** every converted site documents its rejection arm (Pattern 2) and has a scripted `error: {code:'ENOENT'}` test.

### Pitfall 4: Injected `spawnAsync` rejects unknown option keys
`moveOnWindows`/`moveOnUnix` pass `{ stdio: 'pipe' }`. Left as-is they throw `TypeError` at runtime (`spawnAsync.ts:68-74`) and **no type error** appears if the legacy `SpawnOptions` type is still in scope. Remove the key; assert `options` has no extra keys in the unit test.

### Pitfall 5: Default env differs
`run` merges `baseEnv` (process.env in production, `pinnedEnv` last in the test arm) unless `replaceEnv: true`. Sites that passed a complete env (`profile.childEnv()`, `{ WINEPREFIX }`, `envs`) need `replaceEnv: true`; sites that passed `{...process.env, X}` need not. `steamDownloadMonitor` passed no env (so it inherited): leave unset.

### Pitfall 6: Kill signal changes SIGTERM -> SIGKILL
`genericSpawnWrapper` (`spawn` `timeout` = SIGTERM), the legacy `child_process` `timeout` option in general. The runner SIGKILLs. Harmless for probes; note in SUMMARY for `winetricks`/`tar` callers (they have no timeout so unaffected). `killedByUs`/`signal` exits are not failures (README).

### Pitfall 7: sync -> async changes ordering and re-entrancy
`runningPoll` ticks every 5 s: an async `pollRunningOnce` can overlap itself if a probe is slow (reg 2 s cap, ps 1 s) -> add an in-flight flag. `getFolderSize` (two callers), `machOArchsOf` (one), vulkan helpers (tools) and `readRunningAppId` (two dep types) all change return type: update the dep interfaces and every test double.

### Pitfall 8: Sidecar exit contract
No converted site may start unbounded or ref'd work at boot. The runner's child, pipes and timers are unref'd, so a `run` that never settles at stdin EOF is the intended behaviour (it matches `boundedListing`'s documented "never settles if the loop drains first"). Boot-adjacent spawners to re-verify with `pnpm build:sidecar && pnpm smoke:sidecar` (which misses slow exit, per CLAUDE.md): `checkRosettaInstall`, `getCometVersion`, `genericSpawnWrapper` probes, `searchForExecutableOnPath`, `listSteamClientPids` at boot when hold records exist, `restoreMacSteamOnlineIfOwed`, `startRunningPoll`. Any new timer uses `ctx.clock` (unref'd by default; `keepAlive` needs a non-empty reason). Hard-won reminder from the exit contract: `unref()` is the wrong tool for in-flight work; the bound is the tool.

### Pitfall 9: `fakeHomeIsolation.test.ts` interaction
Its `SPAWN_CALL_RE` is `\b(?:spawn|spawnSync|fork|exec|execSync|execFile|execFileSync)\s*\(` on comment-stripped source. `runner.run(`, `runSync(` and `spawnLongLived(` do **not** match it. After conversion the gate is therefore vacuous for backend files; this is fine for the ban (a spawn there is already impossible) but means a converted site could hand-roll a home/config env literal and the gate would not see it. Optional hardening (a one-line regex addition for `\.(run|runSync|spawnLongLived)\s*\(`) is cheap; decide in the ban plan. The runner's test arm applies `pinnedEnv` last on every spawn, so scripted and real-runner tests are isolated regardless. The gate scans `src` and `meta`, so converting backend files cannot turn it red; its `ALLOWED_TO_ASSIGN` and `EXEMPTIONS` tables name specific files, so re-run `pnpm jest src/backend/__tests__/fakeHomeIsolation` after any plan that deletes or rewrites a spawn site.

### Pitfall 10: Windows- and Linux-only paths cannot be live-tested on macOS
Windows: `robocopy`, `reg`, `tasklist`, `powershell` (VC redist, shortcut writer, `steamClientProcess`, filesystem/gpu/os probes), `where`, `taskkill` (runner). Linux: `flatpak`, `lspci`, `free`, `ps` reaper scan, vulkan helper, winetricks. CI is ubuntu-only, so only Linux-guarded code is exercised. Mitigations: scripted-runner assertions on exact argv/env/timeout/`stdin`; characterise the **old** parse behaviour with the existing parse tests (the parsers are pure and unchanged); file one `platform: windows`, `ready: live-gate` todo (three frontmatter keys, bare lowercase, in that order) listing the Windows paths for the operator's Windows machine.

### Pitfall 11: shard JSON contention and the Steam line ceiling
Eleven steam files share `storeManagers.steam.json`; plans in one wave edit different lines but the same file. Run `node meta/backendDiCeilings.cjs --shard <name>` per plan and the full gate at wave end. Conversions that add closures can grow files: `pnpm steam-line-ceiling` (shrink-only per-file line ceiling for `storeManagers/steam/`, in `.husky/pre-push` and CI) must be in every Steam plan's verify list.

### Pitfall 12: dead-code ratchet
Removing `execAsync`, `execOptions`/`getShell` (`constants/others.ts`), `spawnOpenDetached` (both), legacy `spawnAsync`/`memoryLog`, `machOArchsOf` leaves exports with no users. `pnpm find-deadcode` (knip ratchet, `meta/knip-baseline.txt`) "fails on a new finding AND on a vanished one": lower the baseline in the same commit as the deletion.

## Open Questions

1. **OQ-1: How do `config.ts` and the sync `getDefaultWine()` spawn without a runner? (blocks plan 03; needs a user decision.)**
   - What we know: `getFactoryDefaults()` runs from `new GlobalConfigV0()` inside `GlobalConfig.get()`, the first time any module reads settings, which can precede `createAppContext` (the logger imports config; `GlobalConfig.get()` has about 50 importers). It does two things that spawn: `getSteamCompatFolder()` (`flatpak info`, Linux only, only if the flatpak Steam dir exists) and `getDefaultWine()` (`which wine`, `wine --version`, Linux/mac, sync). Both are sync, once per process. 66.3 owns converting `GlobalConfig` into an injected service, so injecting a runner into it in 66.2 would be touched twice.
   - What's unclear: whether a small behaviour change is acceptable.
   - Options: **A (recommended)** make the factory-defaults path spawn-free: flatpak via fs checks (A2); `getDefaultWine()` splits into a pure PATH scan for the binary (fs) used by the sync defaults, plus an async `getDefaultWine({runner})` used by `getLinuxWineSet` (already async) for the version string. Cost: the persisted default `wineVersion.name` on a fresh Linux profile becomes the binary name instead of `wine --version` output until the wine list is read. No new module state, no runner dependency in `config.ts`, nothing for 66.3 to redo. **B** pass the runner into `GlobalConfig` at boot (a new `GlobalConfig` holder): +1 `moduleState` (251 -> 252, forbidden by D-16 unless offset in the same commit), redone by 66.3. **C** keep both as `runSync` via a second runner built inside `config.ts`: bypasses the injected runner (no scripted fake, no `pinnedEnv`), rejected.
2. **OQ-2: Windows shell folders (`knownFolders`) and `nativeImage` (sync Electron-shaped APIs, no context).**
   - What we know: `getPath('desktop'|'documents')` is sync and imported by constants at module load for other names; the two registry-backed names are only used by async flows (`shortcuts.ts shortcutFiles`, `save_sync.ts:146`). `nativeImage` chains synchronously at two production sites.
   - Recommendation: `knownFolders`: make `readWindowsShellFolder` async over `run` and have those two async callers `await` it first on win32 (the sync `getPath` keeps the non-Windows arms and the `homedir` fallback). `nativeImage`: keep it sync with `runSync` (reason: mirrors Electron's synchronous `NativeImage`), supplied through the **existing** `bindTransport` seam, not a new holder.
