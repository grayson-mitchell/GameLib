## Summary

The review covered the change set `0e899fda2..HEAD`, limited to hunks from the `66.2-*` commits and
the orchestrator commits `3b1f0ef79` and `a6e934a48`. Hunks from the concurrent quick tasks
(261111-9b7, 261111-9mj: `psOutputPidsInFolder`, `findPidsRunningFromFolder`, the launch-watch
wiring) were left out. Each converted spawn was checked against the runner contract in
`src/backend/process/runner.ts`: `timeoutMs`/`timeout.none`, `replaceEnv` merging, `stdin`,
`resolveOn`, `maxBufferBytes` truncation, SIGKILL on timeout, and unref.

The conversion is mechanically careful:

- **Sync-to-async callers:** these are awaited — `shutdownWine` in `SideloadGame.stop`,
  `shortcutsExistOnDisk`, `removeShortcuts`, `machOArchsOfAsync`, `getFolderSize`, `readRunningAppId`
  in `decideSteamNativeDelete`, and the win32 registry folder in `shortcutFiles` and `save_sync`.
  `detectVCRedist` is async now, and its rejection is caught.
- **Env handling:** it matches the old spawns. `replaceEnv: true` is used exactly where the old
  call passed a full `env`: winetricks, wine `--version`, `wineserver -k`, the PowerShell `.lnk`
  writer and `free`. `demoStatus` correctly merges when no `baseEnv` is given.
- **Shell-to-argv:** the `mdfind` conversions keep the shell's word splitting
  (`kMDItemCFBundleIdentifier`, `=`, `*.wine`). `which wine` and `wine --version` became a PATH scan
  plus one argv probe.
- **Exit contract:** it holds. The monitors use `spawnLongLived` and stdin EOF still stops them.
  `runningPoll` uses an unref'd clock interval. The `macSteamOffline` timers are clock timers.
- **Single instances:** the DRM single-flight Maps have one instance, built once inside
  `createSteamProcesses`. The `macSteamOffline` instance is shared by `SteamUser`, the boot
  restore and the guided flows.

Nothing rises to BLOCKER. Two of the three warnings are holes in the new `child_process` ban:

- The dependency-cruiser npm-package arm can never match. This was verified by running depcruise.
- `src/backend/testUtils/` is exempt from all three detectors, yet production imports from it.

The third warning is a user-visible regression in the Linux default-wine factory setting.

## Warnings

### WR-01: dependency-cruiser's npm spawn-package arm never matches (gate is dead for execa/cross-spawn)

**File:** `.dependency-cruiser.cjs:125-127`
**Issue:** The rule `no-child-process-outside-runner` matches `to.path` against
`^(execa|cross-spawn|shelljs|node-pty)($|/)`. In dependency-cruiser, `to.path` is the *resolved*
path. A core module resolves to its bare name (`child_process`), so that half of the rule works.
An npm package resolves to `node_modules/<pkg>/...`. Running depcruise on `valveClient.ts` confirms
it: `@node-steam/vdf => node_modules/@node-steam/vdf/lib/index.js`. The `^execa` anchor therefore
can never match.

`execa` and `cross-spawn` are both present in `node_modules` as transitive dependencies. A
production `import { execa } from 'execa'` in `src/backend` would pass all three gates:
dependency-cruiser, ESLint (which lists only `child_process`, `node:child_process` and
`createRequire`), and the AST census (which counts only `child_process` specifiers). The README's
66.2 end-state claims the npm spawn packages are covered ("the npm spawn packages").
**Fix:**
```js
to: {
  path: '^(node:)?child_process$|(^|/)node_modules/(execa|cross-spawn|shelljs|node-pty)/'
}
```
Also add the same names to the ESLint `paths` list in the backend block, so the editor catches it
too. Then add a negative fixture test: a scratch module under `src/backend` importing `execa` must
fail `pnpm depcruise`.

### WR-02: `src/backend/testUtils/` is exempt from every child_process detector while production imports from it

**File:** `eslint.config.mjs:124`, `.dependency-cruiser.cjs:120`, `meta/backendDiCeilings.cjs:70`
**Issue:** All three detectors skip `src/backend/testUtils/**`: the ESLint `ignores`, the depcruise
`from.pathNot`, and the census `SKIP_PATHS`. That exemption is safe only if production never
value-imports testUtils, and it does. At least seven production modules value-import
`backend/testUtils/fakeHomeProfile`:

- `engine/runTool.ts`
- `macSteamOffline.ts`
- `macSteamAdoption.ts`
- `runningFromFolder.ts`
- `drmLaunchSetup.ts`
- `valveClient.ts`
- `steamclientLayerInstall.ts`

So testUtils is part of the production bundle. Nothing stops a helper added there, which
production then imports, from calling `spawn` directly and bypassing the runner. That reopens the
exact hole 66.2 closes. Today no testUtils file imports `child_process`, so this is a latent
bypass, not a live one.
**Fix:** Choose one:
- Move `fakeHomeProfile.ts`, the only testUtils module production needs, out of `testUtils`
  (e.g. `src/backend/process/fakeHomeProfile.ts` or `src/backend/utils/fakeHomeProfile.ts`).
  Then add a depcruise rule forbidding non-test `src/backend` from importing `^src/backend/testUtils/`.
- Or keep the location but drop `testUtils` from all three exemptions, and allow only the
  specific test-only files (`realRunner.ts` etc.) by name.

### WR-03: Factory-default wine name is now the binary basename, so the persisted default no longer matches the wine list

**File:** `src/backend/utils/compatibility_layers.ts:67-72`, `src/backend/config.ts:285-287`
**Issue:** `getDefaultWineBinary()` returns `name: basename(wineBin)`, i.e. `"wine"`. The old
`getDefaultWine()` returned the first line of `wine --version`, e.g. `"wine-9.0"`.
`getFactoryDefaults()` feeds this into `wineVersion`, and the first `flush()` persists it (any
setting change, or `resetToDefaults`). Meanwhile `getLinuxWineSet` resolves the real version, so
the list entry for the same binary is named `"wine-9.0"`.

`WineVersionSelector.tsx:151-154` matches the selection by name
(`value={wineVersion.name}`, `altWine.find(({ name }) => name === event.target.value)`). On a
fresh Linux profile with system wine, the global wine selector therefore shows no matching option,
or falls back to the first entry. `InstalledInfo.tsx:90` shows "wine" instead of the version. The
code comment says "until then the name is the binary name", but nothing ever updates the persisted
factory value afterwards.
**Fix:** Either resolve the version name once the runner exists (for example, a boot step that
probes `wine --version` and rewrites a stored `wineVersion` whose `name === basename(bin)`), or
match the selector by `bin`:
```tsx
value={wineVersion.bin}
onChange={(e) => { const s = altWine.find(({ bin }) => bin === e.target.value); if (s) setWineVersion(s) }}
// and <option value={bin}>{name}</option>
```

## Info

### IN-01: detectVCRedist's "no false nag on a killed probe" guard narrowed from any signal to timeout only

**File:** `src/backend/utils.ts:764-780`
**Issue:** The old `close` handler returned early on any `signal` (D5, 260922-v2e). The new code
returns early only on `timedOut`. If the PowerShell probe is killed by anything else, the result
is `code: null` and `timedOut: false`, which falls through `if (code)` to the "< 4 installations"
dialog. The quit path's `killAllTracked` is one such case; on win32 it usually yields exit code 1,
but a `child.kill()` yields a signal. That is the false nag D5 was written to prevent. The
comment still claims the old guarantee.
**Fix:** `if (timedOut || result.signal !== null || result.killedByUs) { logWarning(...); return }`.

### IN-02: Boot builds steamProcesses on `ctx.runner` even when a prebuilt runner is supplied

**File:** `src/backend/sidecar/bootstrap.ts:1133-1142`
**Issue:** `state.services.runner = prebuilt.runner ?? ctx.runner`, but `createSteamProcesses` is
always given `ctx.runner`, and `clock` always `ctx.clock`. With a prebuilt runner but no prebuilt
`steamProcesses`, the pgrep/nettop/ps children run on a different registry than
`services.runner.killTracked`/`killAllTracked`. This is test-only today (production prebuilds
nothing).
**Fix:** Build with `state.services.runner` (and `prebuilt.clock ?? ctx.clock`).

### IN-03: `SteamUser.releaseForShutdown()` now throws synchronously when the instance is unbound

**File:** `src/backend/storeManagers/steam/user.ts:70-78,770`; `src/backend/sidecar/stdinEofRelease.ts:74`
**Issue:** `this.macSteamOffline()` throws if `bindStores` never received the instance. The old
module function could not throw. `releaseOnStdinEof` calls `void SteamUser.releaseForShutdown()`
outside a try, so a synchronous throw would skip `destroyOutboundHttp()` and the residual-holder
diagnostic. Boot order makes this unreachable in production today.
**Fix:** Wrap the call in `try { void SteamUser.releaseForShutdown() } catch {}`, or make
`releaseForShutdown` return `Promise.resolve('not-darwin')` when unbound.

### IN-04: runTool abort now sends SIGTERM and waits for exit, not SIGKILL plus an immediate resolve

**File:** `src/backend/engine/runTool.ts:66-80`
**Issue:** The old implementation SIGKILLed on abort and resolved at once. The runner's `signal`
path uses Node's default kill signal, SIGTERM, and resolves only after `exit` plus the drain grace.
A tool that ignores SIGTERM now holds an aborted clone or resign step until `timeoutMs`. That is
benign for ditto/cp/codesign, but it is a semantic change the 66.2-03 summary does not record.
**Fix:** Either document it, or have the runner pass `killSignal: 'SIGKILL'` when `signal` is set.

### IN-05: maxBuffer overrun no longer ends the child early (steamInstallApp, boundedListing)

**File:** `src/backend/storeManagers/steam/steamInstallApp.ts:58-72`, `src/backend/storeManagers/steam/bridge/drm/boundedListing.ts:30-38`
**Issue:** `execFile`'s maxBuffer killed the child as soon as it overran. Runner truncation keeps
the child running and only drops output. A chatty helper therefore runs to its timeout (30 s
helper, 3 s listing) before mapping to `code: null`/`error: true`. The outcome is the same; only
latency changes.
**Fix:** Optional. Use `onStdout` to `handle.kill('SIGKILL')` once the cap is exceeded, where
early exit matters.

### IN-06: mdfind is now bounded at an unmeasured 10 s

**File:** `src/backend/utils/compatibility_layers.ts:25-26`
**Issue:** The old shell `exec('mdfind ...')` was unbounded. If Spotlight is cold or rebuilding
and takes longer than 10 s, `getCrossover` logs "CrossOver not found".
`resolveCrossoverBinDirAsync` then returns undefined for a CrossOver outside the standard
`/Applications` candidates, and installs and launches surface `CROSSOVER_REQUIRED_MESSAGE`. The
value is marked "unmeasured (research A1)".
**Fix:** Measure it on a cold index, or log a distinct warning on `timedOut`, so the failure is
distinguishable from "not installed".
