<objective>
Land the Rust half of the sidecar→Rust channel: add the `keyring` crate, implement
`dispatch_rust_channel()` with four keyring arms, and extend `start_reader()`'s frame dispatch so
`rustInvoke` frames get answered — while also fixing the pre-existing gap where sidecar
`openExternal` frames are silently discarded.

Purpose: REQ-28-05 requires the dropped-frame path be fixed rather than left broken, and REQ-28-01
requires keyring-native Keychain storage (D-01), lifting spike 011's proven `Entry::new` →
`set_password` / `get_password` / `delete_credential` shape into production.

Output: `src-tauri` compiles with `keyring` and answers four named channels over stdio.

**Open Question 2 decision (planner's call, per D-10 discretion):** `openExternal` gets the
MINIMAL fix — a dedicated `kind == "openExternal"` reader branch that keeps fire-and-forget
semantics. It is NOT converted to a `rustInvoke` request/response call. Rationale: converting it
would change `electronStub.shell.openExternal`'s contract and ripple into the launch flow, which
is outside this phase's stated boundary; the minimal fix closes the verified drop without a
behavior change. Additionally an explicit `else` diagnostic is added so no future frame kind can
be dropped silently again.
</objective>

    In `src-tauri/Cargo.toml`, add `keyring = { version = "3", features = ["apple-native"] }` to the
    existing `[dependencies]` block. Stay pinned to `"3"` (resolves to 3.6.3, the version spike 011
    compiled and ran) — do NOT use v4. Legitimacy: RESEARCH.md's Package Legitimacy Audit records
    this crate as Approved (crates.io-verified, 17.4M downloads, `open-source-cooperative/keyring-rs`),
    so no legitimacy checkpoint is required.

    In `src-tauri/src/main.rs`, next to the existing constants (L39-49) add:
    `const KEYRING_SERVICE: &str = "com.gamelib.launcher";` and
    `const KEYRING_ACCOUNT: &str = "steam-refresh-token";` with a comment explicitly stating these
    must NOT be spike 011's throwaway `com.gamelib.spike011` values (Pitfall 3).

    Add `fn dispatch_rust_channel(channel: &str, args: &[Value]) -> Result<Value, String>` with a
    `match` over exactly four arms and a catch-all:
    - `"keyring_get"` — `Entry::new(KEYRING_SERVICE, KEYRING_ACCOUNT)` then `get_password()`.
      `Ok(s)` → `Ok(Value::String(s))`. `Err(keyring::Error::NoEntry)` → `Ok(Value::Null)` (this
      means "backend works, nothing stored yet" — Pitfall 1: it MUST NOT be reported as
      unavailable). Any other `Err(e)` → `Err(format!("keyring:unavailable:{e}"))`.
    - `"keyring_set"` — take `args[0]` as a `&str` (missing/non-string → `Err("keyring:bad-args".into())`),
      `set_password(...)`, `Ok(Value::Bool(true))`, other errors → `Err(format!("keyring:unavailable:{e}"))`.
    - `"keyring_delete"` — `delete_credential()`; both `Ok(())` and `Err(NoEntry)` → `Ok(Value::Bool(true))`
      (deleting a non-existent entry is success); other errors → `Err(format!("keyring:unavailable:{e}"))`.
    - `"keyring_available"` — attempt `Entry::new(...)` + `get_password()`; `Ok(_)` or
      `Err(NoEntry)` → `Ok(Value::Bool(true))`; any other error → `Ok(Value::Bool(false))` (a
      *successful* report of unavailability, not an error — this is D-06's honest-unavailable signal).
    - catch-all `_` → `Err(format!("rustInvoke:unknown-channel:{channel}"))`.

    The Keychain service/account are compile-time constants — never read them from `args` (threat
    T-28-03: the sidecar must not be able to address arbitrary Keychain entries).

    In every non-`NoEntry` error arm, also `eprintln!("[shell] keyring {channel} failed: {e:?}")`
    using the `{:?}` debug format so the manual Deny click in plan 28-05 captures the exact
    `keyring::Error` variant (this is what resolves RESEARCH Assumption A1 / Open Question 1).
    Never log the secret value itself (threat T-28-04) — log the channel name and the error only.
  </action>

    Generalize the outbound writer: add `fn write_raw(&self, value: &Value) -> Result<(), String>`
    to `SidecarState` that serializes an arbitrary `serde_json::Value` and writes it as one
    newline-terminated line to the child's stdin, and refactor the existing `write_frame` to
    delegate to it (or keep both side by side — do not duplicate the locking logic).

    In `start_reader()`, after the existing `frontendMessage` branch, add these branches, each
    ending in `continue;`:

    1. `kind == "rustInvoke"` — extract `id` (string), `channel` (string), `args` (array, default
       empty). Clone what is needed and `thread::spawn` a short-lived worker that calls
       `dispatch_rust_channel(&channel, &args)` and then writes back
       `{"id": id, "ok": true, "result": v}` or `{"id": id, "ok": false, "error": e}` via
       `state.write_raw(...)`. **Spawn a worker rather than dispatching inline** — a Keychain
       access prompt blocks until the user clicks, and dispatching on the reader thread would stall
       every other sidecar response behind it, timing out unrelated renderer invokes at 60s
       (threat T-28-05, head-of-line blocking). `SidecarState` is already `Arc`-shared, so clone the
       `Arc` into the worker.
    2. `kind == "openExternal"` — read `args[0]` as a string URL and call
       `app.opener().open_url(url, None::<&str>)` exactly as `open_external` (L162-166) does,
       logging any `Err` via `eprintln!`. Keep fire-and-forget: write NO response frame. This is the
       minimal fix for the verified pre-existing drop (27-02-SUMMARY.md: "the frame is currently
       silently ignored on the Rust side").
    3. A final `else` — `eprintln!("[shell] unrecognized sidecar frame kind: {kind:?} id={id:?}")`.
       Log only `kind` and `id`, never `channel` args or `result` (threat T-28-04).

    Ensure the existing `frontendMessage` branch also ends in `continue;` so the new `else` cannot
    fire for it.

    Update `start_reader()`'s doc comment (L237-239) to describe all four recognized frame shapes.

    Do NOT wrap `dispatch_rust_channel` in `tauri::async_runtime::spawn_blocking` — the reader
    thread and its workers are plain OS threads already off the async runtime (RESEARCH.md
    Anti-Patterns). That wrapper is only for `#[tauri::command]` bodies.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| sidecar (Node) → Rust shell stdio | Sidecar-authored JSON drives native OS Keychain and URL-open operations |
| Rust shell → macOS Keychain (Security.framework) | The OS credential store; access is ACL-gated on the binary's signing identity |
| Rust shell → `/usr/bin/open` via tauri-plugin-opener | A URL from sidecar frame args reaches a system URL handler |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-28-03 | Elevation of Privilege | `dispatch_rust_channel(channel, args)` | mitigate | `channel` is matched against exactly four literal arms with a catch-all returning `rustInvoke:unknown-channel`; `KEYRING_SERVICE`/`KEYRING_ACCOUNT` are compile-time constants and are never sourced from `args`, so the sidecar cannot address an arbitrary Keychain item. |
| T-28-04 | Information Disclosure | keyring error logging on stderr | mitigate | Error logs print `channel` + `{:?}` of the `keyring::Error` only; the secret passed to `keyring_set` and the value returned by `keyring_get` are never written to stderr. |
| T-28-05 | Denial of Service | reader-thread head-of-line blocking on a Keychain prompt | mitigate | `rustInvoke` dispatch runs on a spawned worker thread so a blocking user prompt cannot stall `frontendMessage` relay or pending-invoke correlation. |
| T-28-07 | Tampering | `openExternal` URL from a sidecar frame | accept | Unchanged from Phase 27's T-27-02/T-27-08 posture: URLs are constructed by `buildSteamProtocolUrl`'s numeric-appId guard in the sidecar, not from renderer free-text. This task only restores the delivery that was already intended. |
| T-28-02 | Information Disclosure | plaintext token persistence on Keychain failure | mitigate | The Rust side has no fallback write path: a failing `keyring_set` returns `Err(keyring:unavailable:…)` and stores nothing anywhere. |
| T-28-SC | Tampering | `keyring` crate supply chain (cargo install) | mitigate | RESEARCH.md § Package Legitimacy Audit records the crate as Approved via the crates.io API (17.4M downloads, `open-source-cooperative/keyring-rs`) plus this repo's own spike-011 compile+run proof; pinned to `version = "3"`, the exact line spike 011 resolved. No `[ASSUMED]`/`[SUS]`/`[SLOP]` packages in this phase, so no blocking legitimacy checkpoint is required. |
