    There is no login channel in the Tauri build this phase (D-03), so nothing naturally triggers a
    keyring write — the human verifier needs a deliberate trigger.

    Add a `fn keyring_self_check()` in `main.rs` that runs once during `setup()`, gated behind the
    env var `GAMELIB_KEYRING_SELFCHECK=1` so it is inert in every normal run. When enabled it
    performs, against `KEYRING_SERVICE`/`KEYRING_ACCOUNT` + the literal suffix `-selfcheck` on the
    ACCOUNT (so the self-check never writes to the production entry): `keyring_set` a synthetic
    value `gamelib-selfcheck-<uuid-or-timestamp>`, `keyring_get` it back, compare byte-for-byte, then
    `keyring_delete`. Print each step and the byte-comparison verdict to stderr with a
    `[shell][keyring-selfcheck]` prefix, and on any error print the full `{:?}` debug of the
    `keyring::Error`.

    This env var is a DIAGNOSTIC TRIGGER, not an escape hatch: it must not change which storage
    backend is used, must not enable any fallback, and must not affect the token path. State that
    explicitly in a comment so it is not mistaken for the D-08 violation it superficially resembles.
    It writes only to the `-selfcheck` account and never reads or writes the production entry.

    This code is SCAFFOLDING WITH AN OWNER: Task 4 of this same plan deletes it once Task 2's
    hardware checkpoint has produced its recorded output, so nothing env-var-gated and
    Keychain-touching ships. Mark the whole block with a `// SCAFFOLDING (28-06 Task 1) — removed by
    28-06 Task 4` banner comment on the `fn keyring_self_check`, on the `setup()` call site, and on
    the env-var read, so the removal task has three unambiguous grep anchors and cannot miss one.

    Print the value only for the synthetic self-check secret (which is not a real token); never
    print the production entry's value.
