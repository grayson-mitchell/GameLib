<objective>
Build the sidecar→Rust request/response leg on the TypeScript side: a new `rustInvoke` frame
discriminant on the shared transport contract, and a `requestRustInvoke(channel, args)` function
in `sidecarRpc.ts` that correlates a `Promise` against a Rust-written response frame, with a
bounded timeout and a channel allowlist.

Purpose: D-05 requires this channel as reusable infrastructure (keyring is only its first
consumer; `dialog`/`clipboard`/`notification`/`screen` ports all need the same shape). Today
`ElectronStubTransport` is fire-and-forget only — there is no way for sidecar code to await an
answer from Rust.

Output: extended transport contract, `requestRustInvoke()`, and a Jest transport-shape test that
stubs the Rust responder entirely (this plan proves framing, not Keychain behavior).
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| sidecar (Node) → Rust shell over stdio | Sidecar-authored frames instruct the native shell to perform OS-level operations |
| Rust shell → sidecar over stdio | Shell-authored frames drive sidecar handler dispatch; a malicious/confused shell frame must not gain new capability |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-28-03 | Elevation of Privilege | `requestRustInvoke()` channel argument | mitigate | Channel must be a member of `RUST_INVOKE_CHANNELS`; non-members reject without emitting a frame. Keychain service/account are Rust-side constants (plan 28-02) and are never accepted as frame args. |
| T-28-03b | Spoofing | `handleFrame()` inbound direction | mitigate | `isValidRequest()` deliberately does NOT accept `kind: 'rustInvoke'`, so the shell cannot drive a rustInvoke into the sidecar; direction is enforced, not assumed. |
| T-28-04 | Information Disclosure | stderr diagnostics for unrecognized frames | mitigate | The new unrecognized-frame log prints only the frame `kind`/`id`, never `args` or `result` (token material travels in those fields). |
| T-28-05 | Denial of Service | unanswered rustInvoke wedging sidecar code | mitigate | `RUST_INVOKE_TIMEOUT_MS = 60_000` setTimeout rejects the pending promise and removes the map entry; mirrors Rust's `INVOKE_TIMEOUT`. |
| T-28-06 | Denial of Service | oversized/malformed frames on the new kind | accept | Existing `MAX_LINE_LENGTH` (10 MiB) already guards the newline framing generically for all kinds; no new per-kind guard added and none bypassed. |
</threat_model>
