## Warnings

### A-WR-01: The bridge-helper exit teardown moved module state onto a process global, which the "no module state" gate cannot see

**File:** `src/backend/storeManagers/steam/bridge/helperRegistry.ts:98-112` (and the `installExitTeardownOnce` wiring at `:154-158`)

**Issue:** `helperRegistry.ts` is on `OWNED_66_3`, and `diPhaseGates.test.ts` pins it as "has no module
state". The old module flag `exitTeardownInstalled` and the module `helpers` map did become per-instance,
but the process-exit fan-out is now a mutable `Set<() => void>` hung off
`process[Symbol.for('gamelib.bridgeHelperExitTeardown')]`. That is still process-wide mutable state with
module lifetime; it just lives where the source-text detector does not look.

Nothing ever removes from the Set. Every registry that spawns a helper adds its `shutdownAll` closure,
which keeps that registry's `helpers` Map and the `LongLivedHandle`s inside it alive until the process
exits. The `Symbol.for` key is realm-global on purpose, so any registry created anywhere in the process
joins the same fan-out.

**Failure scenario:** a process that builds more than one boot. Today that is the jest worker
(`testBridgeHelpers.ts` builds real registries, and `helperIntegration` really spawns); it would also be
any future in-process restart. Every registry built earlier is retained, and at `process.exit` each one's
`shutdownAll` runs and calls `entry.child.kill()` on whatever entries it still holds. Production builds a
single registry, so its behaviour there matches the old module flag. The defect is that the per-boot
ownership the phase claims, and pins with a gate, is not real for this piece of state, and the gate
reports green regardless.

**Fix:** make the teardown removable and owned by the registry, or record it as a sanctioned exception
instead of leaving it invisible to the gate. Two options:

```ts
// helperRegistry.ts — return a disposer and drop the registry from the fan-out once it is empty/disposed
function registerProcessExitTeardown(shutdownAll: () => void): () => void {
  const holder = process as unknown as Record<symbol, Set<() => void>>
  let teardowns = holder[EXIT_TEARDOWN_TAG]
  if (!teardowns) {
    const created = new Set<() => void>()
    teardowns = holder[EXIT_TEARDOWN_TAG] = created
    process.on('exit', () => { for (const t of created) t() })
  }
  teardowns.add(shutdownAll)
  return () => teardowns!.delete(shutdownAll)
}
// …and expose `dispose()` on BridgeHelperRegistry (call shutdownAll + the disposer), invoked by the
// boot's teardown / test afterEach.
```

The alternative is to inject the `process.on('exit')` registration through the boot context, as the
clock is, so the global is created by the boot rather than by the module. Either way, add the symbol to
the `diPhaseGates` sanctioned list explicitly if it stays, so the gate stays honest.

### A-IN-02: `SteamUser.releaseForShutdown()` no longer completes the shutdown alone, and only its doc comment says so

**File:** `src/backend/storeManagers/steam/user.ts:713-745`

**Issue:** Before this change, `releaseForShutdown()` released the anonymous CM socket itself
(`releaseAnonymousForShutdown()`). After D-66.3-14 it does not. Its doc says the caller must release the
anonymous client first, and both current callers do (`stdinEofRelease.ts:82`, and the quit handler's

of it.

A future third shutdown path, for example a crash handler or a restart-in-place, that calls only
`steamUser.releaseForShutdown()` would leave an anonymous steam-user WebSocket open with
`shuttingDown=false`. That breaks the sidecar exit contract: the process does not drain at stdin EOF, and
`get()` can still reconnect afterwards.

That item is about test coverage; this one is about the API shape that makes the omission easy.

**Fix:** give shutdown one entry point that releases both, for example a
`releaseSteamForShutdown({ anonymousClient, steamUser })` helper that both callers use. The other option
is a `shutdownPeers` dep on SteamUser, so `releaseForShutdown()` still releases the anonymous client
itself. Then pin that helper, not the two call sites.

### B-WR-01: The process-tag dedupe silently disconnects a second guards instance's log-sink setters

**File:** `src/backend/sidecar/processGuards.ts:147-155, 294-302` (with the setters at `:134` and `:257`)

**Issue:** `installUnhandledRejectionGuard` and `installUncaughtExceptionGuard` now return early
when the process already has a listener tagged `Symbol.for('gamelib.processGuards')`. That listener
closes over the `logSink`/`uncaughtExceptionLogSink`/`exit` of whichever `createProcessGuards()`
instance installed it first.

A second instance therefore installs nothing, but its `setUnhandledRejectionLogSink` and
`setUncaughtExceptionLogSink` still accept a sink and report no error. That sink is never read.
`bootstrap.ts`'s `logger` step binds the sinks on the instance passed through `init({ guards })`
(`io.guards`). If that is not the instance that owns the live listener, unhandled rejections go to
the first instance's sink (stale or `null`, which means stderr only), and the now-fatal
uncaught-exception path awaits the wrong flush promise. Either way nothing reaches `gamelib.log`,
and nothing signals that this happened.

The other two installers, `installStdioErrorGuards` and `installConsoleStdoutRedirect`, are not
deduplicated by process tag. Two instances add two stdio `'error'` listeners, so the four
installers have inconsistent idempotence rules.

**Failure scenario:**
- Production builds exactly one instance (`src/sidecar/installRejectionGuard.ts:65`), so the
  shipped sidecar is unaffected today.
- A test suite that uses `bootFresh()`/`jest.isolateModules` builds a fresh instance in each
  module registry. Every boot after the first then binds sinks that are never used. A test that
  asserts a rejection lands in the log sink passes or fails depending on which suite installed the
  listener first in that Jest worker.
- The same applies to any future second entry point.

**Fix:** Keep the sink slot on the process-global tag instead of in the instance closure. Then
whichever instance binds a sink is the one the live listener reads:

```ts
const SINKS = Symbol.for('gamelib.processGuards.sinks')
type Sinks = { rejection: UnhandledRejectionLogSink | null; uncaught: UncaughtExceptionLogSink | null }
function sinks(target: object): Sinks {
  const t = target as Record<symbol, Sinks | undefined>
  return (t[SINKS] ??= { rejection: null, uncaught: null })
}
// setUnhandledRejectionLogSink(sink)  -> sinks(process).rejection = sink
// the listener reads sinks(target).rejection at call time
```

If that is not wanted, make `install*` throw or log a warning to stderr when it finds another
instance's tagged listener, so the disconnected setters are visible. Apply the same rule to
`installStdioErrorGuards` and `installConsoleStdoutRedirect`.

### B-WR-02: A `prebuilt` Humble or SteamGridDB service leaves an unused keyring store that the `secret-stores` step still migrates

**File:** `src/backend/sidecar/bootstrap.ts:1425-1439` (steamgrid-secrets), `:1611-1630` (humble-services), `:2150-2168` (secret-stores keyring arm)

**Issue:** The `steamgrid-secrets` and `humble-services` steps always build a keyring store into
`state.steamGridKeyringStore` / `state.humbleKeyringStore` when no dev vault is selected, even when
`prebuilt.steamGridSecrets` or `prebuilt.humble` replaces the service that would use it. The
`secret-stores` step then runs `startSidecarHumbleSecretStore` and
`startSidecarSteamGridDbSecretStore` on those unused stores.

Both migrations do real work:
- They read plaintext from `stores.humble.configStore` or `config.steamGridDbApiKey`.
- They write it to the keyring via `requestRustInvoke`.
- On a successful readback, they delete the plaintext and set `steamGridDbApiKey` to `''`.

So the migrated secret ends up in a store the prebuilt service never reads, and the service loses
the plaintext copy it was reading.

**Failure scenario:** This is test-only, because production `prebuilt` is `{}`. A suite that hands
the boot a fake `humble` but real `stores` triggers the migration's `requestRustInvoke` against the
test's output stream. That leaves a pending rustInvoke (with a timeout timer) and can delete the
fixture's plaintext secret behind the fake's back. The result is order-dependent test state.

**Fix:** Build the keyring store only when it will be used, and record that, so `secret-stores`
skips the migration otherwise:

```ts
if (prebuilt.humble) { state.services.humble = prebuilt.humble; return }
// ...existing keyring/vault selection + createHumbleServices
```

Do the same in `steamgrid-secrets`. `secret-stores` should then call `start*` only for stores that
are non-null, instead of throwing.

Those guards always saw the truthy `fakeWindow`, and `fakeWindow.hide()` was a no-op, so dropping them changes nothing. Host `dialogs.*` never rejects, so the `void deps.dialogs.showErrorBox(...)` fallbacks are safe.
- **Process polyfills.** `os.release()` is exactly what the old `process.getSystemVersion` polyfill returned. `memory/windows.ts` used to call `process.getSystemMemoryInfo()`, which was never polyfilled, so it threw on Windows. The new `os.totalmem()/freemem()` code is in bytes and is correct. That change fixes a bug rather than introducing one.
- **Engine state.** The publisher is wired at construction to the same `engineStateChanged` channel the old `setEngineStatePublisher` call used. Every caller supplies `globalSettings`, which the derived-engine path now requires, and every `buildFallbackGameSettings` caller now passes an explicit base.
- **DXMT listeners and the winetricks queue.** Both now register at the same boot point the old `bindDxmtStores` / import-time code effectively armed. Each is registered exactly once per boot.
- **Type moves.** `hostTypes.ts` is field-for-field identical to the old `platform/types.ts` declarations. The preload/renderer contract is unchanged.

The two warnings are:

- **WR-01:** a guaranteed throw on the Linux system-info path that this refactor rewrote and kept.
- **WR-02:** the new "construct per boot" owners still subscribe through process-global holders and do not hand back or use a disposer.

## Warnings

### C-WR-01: Linux `getGpuInfo_linux` now throws a ZodError every time, so `getSystemInfo` always rejects on Linux

**File:** `src/backend/utils/systeminfo/gpu/linux.ts:30-32`

**Issue:** The refactor replaced `await app.getGPUInfo('basic')` with a literal `const gpuInfo: unknown = {}`, followed by `GPUInfoSchema.parse(gpuInfo)`. The schema requires `gpuDevice: z.array(...)`, so `parse({})` throws `ZodError: gpuDevice Required` on every call. The rest of the function, including the `lspci` enrichment, can never run. `gpu/index.ts:19-20` does not catch the error, and neither does `fetchSystemInfo` (`systeminfo/index.ts:119`). As a result, `getSystemInfo()` rejects on every Linux host. That breaks the System Information dump, the boot system-info log line, and any consumer such as `getSteamDeckInfo(cpus, gpus)`.

The old stub's comment claimed "the caller already tolerates an empty result", which was false. The bug is inherited from the stub, but this refactor rewrote the line and fixed the failure in place with a comment ("so the parse below throws, as it did") instead of fixing it. It is no longer a stand-in quirk: it is now explicit first-party code.

**Failure scenario:** A Linux user opens Settings → System Information, or the frontend boot calls `getSystemInfo`. The promise rejects, the memoized in-flight promise is cleared, and every retry rejects the same way. Steam Deck detection, which depends on `gpus`, never runs.

**Fix:** Stop parsing a constant. Without Electron's GPU list, either return no GPUs or enumerate them from `lspci` directly:

```ts
async function getGpuInfo_linux(deps: ProbeDeps): Promise<PartialGpuInfo[]> {
  // No Electron getGPUInfo under Tauri; enumerate display controllers via lspci instead.
  if (!(await hasExecutable('lspci'))) return []
  const { stdout } = await genericSpawnWrapper(deps, 'lspci', ['-mm', '-n', '-d', '::0300'])
  // parse vendor/device per line, then getLspciInfo(deps, device, vendor) for each
  ...
}
```

At minimum, use `return []` in place of the constant and the `parse`, so the function matches the old comment's stated intent ("tolerates an empty result").

### C-WR-02: Owners built per boot still subscribe through process-global holders with no teardown, so a second construction silently steals or duplicates subscriptions

**Files:**

- `src/backend/tools/winetricksQueue.ts:73-75` (calls `onEnvironmentChanged`, which is a single-slot setter at `src/backend/tools/winetricksEnvironment.ts:22-26`: `changeListener = listener`)
- `src/backend/tools/dxmt.ts:284-297` (registers on the process-global `backendEvents`; the disposer is discarded at `src/backend/sidecar/bootstrap.ts:2110`)

**Issue:** The phase turns these into boot-owned instances: "a boot owns exactly one", "registered once when the boot-owned queue is built". Their subscriptions, however, still go to process-wide holders:

- `createWinetricksQueue` calls `onEnvironmentChanged(...)`, which **overwrites** a module-level `changeListener`. Building a second queue (another in-process boot, or a test that builds two) silently re-points every environment-report change to the newest queue's `push`, `getState`, `snapshotRevision` and `currentRun`. The first queue's renderer pushes stop, and the pushes that do go out carry the wrong revision counter. The 261011-nqe ordering guard relies on that counter being monotonic per renderer.
- `registerDxmtListeners` adds three listeners to the module-level `backendEvents` emitter and returns a disposer, but the 'secret-stores' boot step drops it. Every in-process boot adds three more listeners. One `releasesInfoReady` then runs `DXMT.getLatest` and `copyLatestDXMTFiles` N times concurrently against the same `-DXMT` wine copies.

Production boots once per process, so this is latent today. It is still a regression in what the instances guarantee. Before this change, both registrations ran once per *process*, at import. Now they run once per *construction*, and nothing makes construction idempotent or reversible. Boot-level tests that call `bootSidecar` repeatedly in one Jest file are exposed now.

**Fix:**

- Make `onEnvironmentChanged` return an unsubscribe and support more than one listener (a `Set`). Have `createWinetricksQueue` keep the unsubscribe and expose `dispose()`.
- In bootstrap, store the `registerDxmtListeners(...)` return value on boot state and call it from the same teardown that releases the other boot-owned services.

```ts
// winetricksEnvironment.ts
const listeners = new Set<(r: Runner, a: string) => void>()
export function onEnvironmentChanged(l: (r: Runner, a: string) => void): () => void {
  listeners.add(l)
  return () => listeners.delete(l)
}
// bootstrap 'secret-stores'
state.disposeDxmtListeners = registerDxmtListeners({ ... })
```
