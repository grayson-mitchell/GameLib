## Phase Boundary

D-15 step 3 of Phase 66 (ROADMAP "### Phase 66.3"), for module state. The D-06 module-state
count goes to zero outside the sanctioned list (runner, logger sink, boot entry), and the census
becomes a test (D-13, D-16). Then come the live smokes.

Census on 2026-11-11 (`meta/backendDiCeilings/*.json`, `moduleState`): **230 sites in 114
files**. The largest are `steam/user.ts` 11, `platform/index.ts` 8, and `online_monitor`,
`engineState`, `processGuards`, `steam/anonymousClient` and `steam/bridge/helperRegistry` with
5–7 each. Then comes a long tail of about 70 files with 1–2 sites each.

**Split by stage (D-66.3-04).** Phase 66.3 covers dissolving the platform shim, injecting the
config, the D-05 process-wide owners and the boot-bound static holders. Phase 66.4 covers the
long tail, the census-to-test flip, the RunningAppID poller revive and the live smokes. 66.4
inherits this CONTEXT the way 66.1 and 66.2 inherited 66's.

Out of scope: any behaviour change the user can see, except the folded poller revive (D-66.3-07).
Frontend state belongs to Phase 69.

## Implementation Decisions

**All of Phase 66's D-01..D-17 apply unchanged**, and the 66.1/66.2 carry-overs still stand.
Read `.planning/phases/66-backend-dependency-injection-replacing-module-level-singleto/66-CONTEXT.md`
in full. The ones most relevant here:
- D-01: narrow slices, no locator, no `deps = defaultDeps`.
- D-05: process-wide state is owned by the context, and there is no allowlist for it.
- D-06: the census definition.
- D-13 and D-16: the ceiling only goes down, ends at zero, and then becomes a test.
- D-14: the Rust-overlap exemption table stays empty unless Phase 75 is re-scoped.
- D-15: each file is converted once, completely.
- D-17: the live macOS smoke is the last plan and is not autonomous.

### The platform shim (`src/backend/platform/index.ts`)
- **D-66.3-01: Dissolve the Electron facade into Tauri-native services, and don't sanction it.**
  `platform/index.ts` stands in for Electron's API. Phase 27 created it, and Phase 35 moved it
  into place and rewrote every `from 'electron'` import to point at it. Under Tauri, few of its
  parts do real work: `app.getPath`/`getAppPath`, the `ipcMain` handler/listener registries,
  `shell.openExternal`, `dialog.showOpenDialog` (which forwards to Rust), notifications, and the
  window push path. The rest (`BrowserWindow`, `Tray`, `Menu`, `screen`, `session`, `net`,
  `protocol`, and the dead `safeStorage`) are no-ops that only keep imports from throwing.
  Replace the facade with narrow services. Each is built once at boot and injected through
  slices (D-01). There are roughly six:
  - `paths`, merged into the existing `ctx.paths`.
  - The IPC handler/listener registry, owned next to `sidecarRpc` dispatch, which is where
    Phase 67's boundary validation already lives.
  - `openExternal`, on the runner's `openDetached` (D-66.2-02).
  - `dialogs`.
  - `notifications`.
  - A small window/app-state object: relaunch-in-flight, the hidden-by-GameLib flag and the
    in-app dialog raise count.

  Delete the no-op stand-ins, and with them the Electron-shaped names (`platformApi.app.*`,
  `BrowserWindow`, …). The bound `transport` becomes a dependency of those services and is not
  a sanctioned entry. Comments that still describe a `Module._load` interception (for example
  `enrichmentFlowRegistration.ts:103`, `handlers.ts:412`) are stale, because no such hook has
  been installed since Phase 35. Correct them in the plan that touches each file.
  **Why:** the user chose the maximum-effort option because it serves the long-term direction.
  GameLib is a Tauri app, Phase 67 generates the IPC contract into Rust, and the Rust ports need
  one swap point per concern. An Electron-shaped facade hides which capability a module really
  uses.
- **D-66.3-02: The shim is dissolved first, before the long tail.** The services land in 66.3,
  so every long-tail file in 66.4 takes `paths`/`dialogs`/`ipc`/… slices when it is converted.
  No file is touched twice (D-15). Ripple measured 2026-11-11: about 73 non-test backend files
  import the shim. By API: `ipcMain` 28, `app.*` 27, `shell` 9, `dialog` 7, `Notification` 3,
  everything else 0–2.

### Config
- **D-66.3-03: `GlobalConfig` and `GameConfig` are built at boot and injected.** Boot constructs
  one `GlobalConfig` and one `GameConfig` registry, and the per-game cache moves into that
  registry. Consumers take narrow `config`/`gameConfigs` slices. `static get()`,
  `globalInstance` and the per-game static cache are deleted, and no static delegator facade
  survives (that would be a locator, which D-01 forbids). Ripple: `GlobalConfig.get()` in 44
  non-test files and `GameConfig.get(` in 19. Each touch belongs to whichever plan converts that
  file (D-15). Boot ordering is load-bearing: the first `GlobalConfig` read must stay after
  `initLogger()` and the config-version upgrade (see the comments at `bootstrap.ts` ~1417).
  66.2 deferred `GlobalConfig.globalInstance` to this phase (D-66.2-01/03).

### Phase shape
- **D-66.3-04: Split by stage into 66.3 and 66.4.** Adding the shim dissolution (about 3–4
  plans) and the folded todos to the roadmap's 15–18 plans gives about 20–24.
  - **66.3:** the shim services, config injection, the D-05 process-wide owners (`online_monitor`,
    `anonymousClient`, `processGuards` (read its WR-04 header), `engineState`,
    `gameSessionState`/`userSignInState`/`authTrigger`/`steam/state`, `shimCoverage`,
    `winetricksQueue`, `helperRegistry`, `signInProbe/*`, `humble/*`) and the static boot-bound
    holders (C-WR-2): `SteamUser` statics (`bindStores`), `bindBottleStores`,
    `bindHumbleStores`, `bindDxmtStores`, `bindSteamGridDbSecretDeps`, and the humble user /
    config / game_config statics. Also the `registerHumbleFlows`/`registerHumbleLoginFlows` MH-3
    allowlist entries.
  - **66.4:** the long tail of about 70 files, including the 66.2 deferrals: the `utils.ts`
    `default*Path` lets, `installingComponent`/`catalogCache`/`scriptMetadataCache` in
    `tools/index.ts`, `engineNoticeStore`, the two `pci_ids` stores, and retiring the win32 sync
    fallbacks in `knownFolders`/`pathShim`. Then the census becomes a test and the
    `moduleState` ceiling is deleted (D-13/D-16), followed by the poller revive (D-66.3-07) and
    the live smokes (D-66.3-05, D-66.3-06).

  Each half has its own done-when. 66.3 ends with every site it owns at zero and the ceilings
  lowered.

### Live macOS smoke (D-17, the last plan of 66.4, not autonomous)
- **D-66.3-05: Coverage, checker and defect policy.**
  - **Launches:** one installed game each from Epic, GOG and Amazon; a native Mac Steam game
    (rungameid); and a Steam bridge (bottled) game. Sideload and Humble are not in the smoke.
    Humble stays on jest and `smoke:sidecar`.
  - **Steam Refresh and an install start/cancel stay in, as D-17 says.** They exercise the
    anonymous and authenticated CM client, the download queue and cancel teardown. Then quit.
  - **The orphan/exit check is a scripted checker,** a small `meta/` script. It snapshots the
    sidecar's process tree before quit, waits a bounded time after quit, and reports any
    surviving child plus the sidecar's exit latency at stdin EOF. The operator runs it, and
    later phases can reuse it. Its own spawns follow the fake-HOME rule where it runs in tests.
  - **Defects:** the phase does not verify until the smoke passes. A regression caused by the
    DI conversion gets a gap-closure plan inside 66.4. A pre-existing defect unrelated to the
    conversion becomes a todo with triage frontmatter (gamelib-conventions).
  - Smoke UAT items follow the UAT item shape convention. Network-off steps follow the memory
    rule: turn the network off only for the action itself.

### Non-macOS verification
- **D-66.3-06: Windows gets an operator live UAT; Linux relies on CI.** A non-autonomous
  Windows UAT plan sits beside the macOS smoke in 66.4. The operator runs it on a Windows
  machine with Steam installed. It covers the folded spawn paths (D-66.3-08) and the revived
  poller's Playing state (D-66.3-07). The phase does not verify until it has been run. An item
  that cannot be reached is marked `blocked` with a reason. Linux has no Linux-only path in this
  work, so the jest suites plus `smoke:sidecar` on CI are enough.

### Folded Todos
- **D-66.3-07: Revive the Steam RunningAppID poller under Tauri**
  (`.planning/todos/pending/2026-11-11-revive-steam-runningappid-poller-under-tauri.md`).
  `startRunningPoll()` runs only from `SteamLibraryManager.init()`, and nothing calls that under
  Tauri, so Windows `steam://launch` launches never show Playing. It fits here because
  `steam/library/pollState.ts` is module state (3 sites) that has to become a boot-owned object
  anyway. The fix is a boot step that starts the poller and stops it at stdin EOF or quit, with
  its timer on the injected clock (`unref()`'d, as the exit contract requires) and no dependency
  on the dead `init()`. This is a recorded exception to Phase 66's "no user-visible behaviour
  change", and it lands in 66.4. Verify it on Windows (D-66.3-06).
- **D-66.3-08: Live-check the Windows spawn paths from 66.2**
  (`.planning/todos/pending/2026-11-10-66.2-windows-spawn-paths-live-gate.md`). The checks are
  robocopy `moveOnWindows`, reg.exe `readWindowsShellFolder` (OneDrive-redirected Desktop
  included), the tasklist/powershell Steam client probes, the powershell `.lnk` write/remove,
  the `detectVCRedist` dialog, the PATH-scan `where` replacement, a taskkill tree kill on
  cancel, and the wmic/systeminfo hardware panel with and without wmic. They become items in
  the D-66.3-06 Windows UAT, which re-checks the knownFolders/pathShim paths that 66.4 changes.
  When the UAT passes, close the todo.

### Plan-time decisions (2026-11-11, answered at /gsd-plan-phase from RESEARCH Open Questions)
- **D-66.3-09: Constant lookup Sets are converted, not exempted.** The 18 sites of the form
  `const X: ReadonlySet = new Set([...])` become frozen arrays or objects. The D-06 census
  definition is unchanged: top-level `new X` still counts.
- **D-66.3-10: `processGuards` becomes a factory built by the entry, not a sanctioned site.**
  `createProcessGuards()` is built in `src/sidecar/installRejectionGuard.ts` (still zero-import,
  still installed before `bootstrap` evaluates, per its WR-04 header) and passed into
  `init({guards})`. The Group 3 first-import matcher in `sidecarRejectionGuard.test.ts` is
  updated to match, and every task touching it gates on `pnpm build:sidecar && pnpm smoke:sidecar`.
  The sanctioned list stays runner, logger sink and boot entry.
- **D-66.3-11: D-15 is read with the 66.2 cascade convention.** A stateful long-tail file that
  imports the shim or config gets only its import/call-site lines changed in 66.3. Each SUMMARY
  lists these as cascade edits. The file's own module state is converted once, completely, in
  66.4. "Converted once" refers to a file's own state, not to its import lines.

### Claude's Discretion

- Whether short-lived caches (`pci_ids`, `crossover_index`, `cheapshark`, `images_cache`) get

- The game picks for each store in the smoke. Use whatever is installed on the operator's

## Existing Code Insights

### Reusable Assets
- `createAppContext` and the `ctx.paths` it builds (`src/backend/process/context.ts`): `paths` is already there, so it absorbs `app.getPath`/`getAppPath`.
- The runner's `openDetached` already backs `shell.openExternal` (D-66.2-02), and the `openExternal` service wraps it.
- `scriptedRunner`, `fakeClock`, `captureLog` and `createTestContext` (`src/backend/testUtils/`). Tests of the new services build only their slice.
- `bootFresh()` / `reuseRegistry` for sidecar boot tests (66-06-SUMMARY).

### Established Patterns
- `createX(deps)` factories and boot steps in `bootSidecar(ctx)`. A new process-wide owner becomes a named boot step plus a context field.
- Ceilings drop in the same commit as the conversion. A census-definition change has to name every newly counted site.
- `ipcMain.handle`/`.on` registrations live in the `sidecar/*FlowRegistration.ts` files. Seven of them read the shim's registries directly (`shellFiles`, `storeWrite`, `logger`, `appShell`, `settings`, `eosOverlay`, plus `sidecarRpc`).

### Integration Points
- `sidecarRpc` dispatch is where the IPC registry is consumed.
- The quit / stdin-EOF path is where the revived poller and the boot-owned objects with timers are torn down.
- The Rust shell (`src-tauri/src/sidecar.rs`) receives dialog and notification requests over the transport. The service API changes, but the wire protocol does not.
</code_context>
