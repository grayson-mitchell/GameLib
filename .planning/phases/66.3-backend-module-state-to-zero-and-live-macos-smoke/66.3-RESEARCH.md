## Summary

The census (`pnpm backend-di-ceilings`) reports **moduleState = 233 sites in 116 files**, of which 3 sites sit in the two sanctioned files already (`sidecar/bootstrap.ts` 1, `logger/index.ts` 2), leaving **230 in 114 files** to convert, matching CONTEXT. Per CONTEXT D-66.3-04, 66.3 owns **103 sites in 29 files** (the D-05 owners, the C-WR-2 static holders, config, game_config, humble/*, signInProbe/*) plus the **platform shim (8 sites, 71 importers)**; the remaining **127 sites in 85 files** are the 66.4 long tail. The shim and config are not "just" 9 sites: they carry the largest ripple in the phase (shim: 71 non-test importers and about 119 test import/mock references; config: 63 non-test files, 21+8 test files using `.get(`, 64 `jest.mock` of config). 47 of the shim's importers and 27 config-only consumers have **no module state of their own**, so they belong to no other plan: the shim/config plans must own them as cascade edits.

The defining planning insight is how to read D-15 ("each file converted once") when five cross-cutting migrations (shim, config, `online_monitor`, `SteamUser`, `steam/state`, `bottle`) touch overlapping consumer files. 66.2 resolved the same situation with a **"files owned = converted completely" plus "cascade call-site edits (list in SUMMARY)"** column. Reuse that: a file is *owned* by the plan that converts its own module state or definition; a consumer that merely changes an import line or a call is a *cascade edit*, recorded in the owning plan's SUMMARY, and plans that share cascade files must not run in the same wave.

Two things in the census definition will bite the zero flip and must be decided before plan 01: (1) **18 of the 230 sites are constant lookup Sets** (`const X: ReadonlySet<...> = new Set([...])`) that D-06 counts because `new Set` is always counted; they have no mutable state, but they cannot be left (no allowlist, D-05). Convert them to frozen arrays/records (recommended) rather than loosening the census. (2) `processGuards.ts` (7 sites) must stay installed before `bootstrap.ts` evaluates (zero static imports, WR-04), so it cannot become a boot step; the recommended conversion is a zero-import `createProcessGuards()` factory whose instance is created by the entry module and passed into `init()`.

**Primary recommendation:** Plan 66.3 as ~14 plans in 8 waves: gate/roadmap prep, then shim services, then config objects, then three parallel cascade plans (sidecar registrations; managers; root/utils/other), then the D-05 owners ordered by measured ripple, then a final plan that deletes the shim and the static `get()`s and pins the 66.3 end state in `diPhaseGates.test.ts`. Keep the `moduleState` ceiling as a ceiling through 66.3 (it is the per-commit gate); the census-to-test flip and `moduleState` ceiling deletion happen in 66.4 once the long tail is converted, exactly as 66.2 did for `childProcess`. Split `steam/*` only inside 66.3 by cluster (not into a third phase): it is already split across the 66.3/66.4 boundary.

## Architectural Responsibility Map

GameLib's backend is a Node sidecar speaking newline-delimited JSON RPC to a Rust/Tauri shell. The browser tier is untouched by this phase (frontend state is Phase 69). Tiers here are sidecar-internal.

| Capability | Primary Tier | Secondary Tier | Rationale |
|------------|-------------|----------------|-----------|
| IPC handler/listener registry (`ipc` service) | Sidecar RPC layer (`sidecar/sidecarRpc.ts` neighbour) | Boot (`bootstrap.ts` constructs) | The only production reader is `sidecarRpc` dispatch; flow registrations only write. Phase 67 `ipcValidation` runs at the same point. |
| App/user paths (`paths`) | `AppContext.paths` (`process/context.ts`) | Boot (`resolveAppPaths`) | Already on the context; absorbs `app.getPath/getAppPath`. |
| `openExternal`, dialogs, notifications, window/app state | Sidecar service layer, forwarding to Rust via `requestRustInvoke` / transport | Rust shell (`src-tauri/src/sidecar.rs`) executes | The wire protocol does not change; only the TS API does. |
| `GlobalConfig` / `GameConfig` registry | Boot-built service injected by slice | Disk (config.json, per-game json) | First read must stay after `initLogger()` and the config-version upgrade. |
| Connectivity monitor, anonymous CM client, SteamUser session, sign-in probe state, engine state | Per-boot owner objects (boot steps + context/BootServices field) | Sidecar exit path (`stdinEofRelease`) for teardown | D-05: one owner built at boot, torn down on the exit contract. |
| Process-level guards | Process entry (`src/sidecar/`) | `bootstrap.init` late-binds the log sink | Must exist before any backend module evaluates (WR-04). |
| Module-state census and its zero gate | Meta tooling (`meta/backendDiCeilings.cjs`) + a jest gate | CI | Pure static analysis. |
| Live smoke orphan/exit checker | Operator tooling (`meta/`) | OS process table | Observes the sidecar's tree from outside; cannot live in-process. |

## Architecture Patterns

### System Architecture Diagram (target end state of 66.3, boot flow)

```
src/sidecar/index.ts  (entry; first import evaluates the guard module)
        |
        |  import { guards } from './installRejectionGuard'   <- zero-import createProcessGuards(), installed here
        v
  init({guards}, stdin, stdout)
        |
        v
createAppContext({platform, paths(app roots), log, baseEnv})  ->  AppContext { paths, clock, runner, log, platform }
        |
        v
bootSidecar(ctx, ...) -> runBootSteps  (ordered list, runs once)
   logger -> (log sink late-bound into guards) -> config(GlobalConfig, GameConfig registry; after initLogger + version upgrade)
   -> shim services: ipc registry | openExternal | dialogs | notifications | appState(window)
   -> stores -> online monitor -> anonymous CM client / SteamUser session / sign-in probe / engine state / helperRegistry ...
   -> managers + launcher (slices: config, gameConfigs, ipc, dialogs, onlineMonitor, ...)
   -> registerHandlers(slices)  -- flow registrations write into ipc registry
   -> startRpcServer(ipc registry)  <-- sidecarRpc dispatchInvoke/dispatchSend read the registry (single production reader)
   -> transport/openExternal wiring -> READY
        |
 stdin EOF -> releaseOnStdinEof (SteamUser release, anonymous client release, queue pause, abort controllers)
           -> event-loop drain -> exit (no explicit process.exit)
```

### Recommended structure (no new top-level directories)
```
src/backend/
  process/context.ts         # AppContext grows only what is leaf-safe (paths); new owners go on BootServices
  ipc/ or sidecar/ipcRegistry.ts   # IPC registry service next to sidecarRpc (name is Claude's discretion)
  services/                  # dialogs / notifications / openExternal / appState factories if not merged
  config.ts, game_config.ts  # classes built at boot (constructors public), no static get()/instances
  platform/index.ts          # DELETED in the last 66.3 plan
```

### Pattern 1: owner object conversion (one per module-state file)
**What:** `let`/`Map`/static fields become closure or class instance fields built by `createX(deps)`; boot constructs it as a named boot step and stores it on `BootServices` (or `AppContext` only if leaf-safe); consumers declare a `Pick<...>` slice. Tests build a fresh instance with `fakeClock`/`scriptedRunner`; `__resetXForTests` exports are deleted (25 exist across 16 non-test files, each a module-state symptom).
**When to use:** every site in the census.
**Constraint:** timers on `ctx.clock` (unref'd); teardown registered on the stdin-EOF path (`stdinEofRelease.ts`), not on `startRpcServer`.
**Example (shape only, from 66.2's established recipe):** `createSpawnAsync(deps: { runner: ProcessRunner })` in `spawnAsync.ts`; `createProcessRunner(deps)` in `process/runner.ts`. [VERIFIED: codebase read]

### Pattern 2: cascade-edit accounting (reuse 66.2's grouping table)
Each plan lists "files owned (converted completely)" and "cascade call-site edits (list in SUMMARY)". Hot files (edited by several plans): `sidecar/bootstrap.ts`, `services/types.ts`, `sidecar/*FlowRegistration.ts`, `launcher.ts`, `storeManagers/steam/gameLaunch.ts`, `process/context.ts`. Rule: a plan listing a hot file runs in a wave where no other plan lists it. [CITED: 66.2-RESEARCH.md "Standard grouping into plans"]

### Pattern 3: ceiling-lowering in the same commit
Delete the shard entry for each file that reaches 0 (a zero entry fails; a stale entry fails), lower entries for files that shrank, never raise. Run `node meta/backendDiCeilings.cjs --shard <name>` per task and the unrestricted gate at wave end. Shards of interest: `platform.json`, `sidecar.json`, `_root.json`, `engine.json`, `signInProbe.json`, `humble.json`, `tools.json`, `storeManagers.steam.json` (shared by many files: never two same-wave plans on it), `storeManagers.steam.bridge.json`, `steamgrid.json`. [CITED: meta/backendDiCeilings.cjs header; 66.2-PATTERNS.md recipe 4]

### Anti-Patterns to Avoid
- **A static facade over the new object** (`GlobalConfig.get()` delegating to a module-held instance, or a `getIpc()` accessor). That is a locator (D-01) and a `static`/module-state site the census counts.
- **A delegating `platform/index.ts` that survives the phase.** An interim thin shim that forwards to the new services is acceptable only inside 66.3 while cascade plans run, and the last 66.3 plan must delete it and pin "file does not exist" in `diPhaseGates.test.ts`.
- **Turning `let x` into `const x = createX()` at module scope.** The census does not count a call-returning container (known residual, see Pitfall 9), but it is the same state; reviewers must reject it.
- **`__reset...ForTests` kept "for now".** Fresh-instance tests make them unnecessary; leaving them keeps tests coupled to module state.
- **Adding a timer/watcher without `unref()` or leaving unbounded in-flight work at boot** (exit contract, three prior breaks).

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Timers in owner objects | raw `setTimeout/setInterval` | `ctx.clock` (`unref()` by default) | Structural exit-contract compliance; testable with `fakeClock` |
| Spawning (orphan checker, any owner) | `child_process` import | `ctx.runner` (`run`, `spawnLongLived`, `openDetached`) or, for the `meta/` checker, `createFakeHomeProfile()`-based spawn | `child_process` is banned outside `process/runner.ts` (ESLint + depcruise + census) |
| Test isolation | `__resetForTests` exports, `jest.resetModules` ladders | fresh instances via `createTestContext`/`testServices`/`bootFresh()` | D-05: "tests get a fresh instance and never reset module state" |
| Census extension | a second AST scanner | extend `meta/backendDiCeilings.cjs` (`countModuleState`, `census`, `loadShards`, `evaluate`) | Single source of truth; sanctioned-path table is hard-coded there |
| Process-tree walk in the smoke checker | parse `ps` by hand per platform | one `ps -axo pid,ppid,pgid,etime,command` snapshot on macOS/Linux, `Get-CimInstance Win32_Process` is out of scope (smoke is macOS) | Sidecar runs in its own process group (`pgid == pid`, set at spawn in `src-tauri/src/shell_state.rs`) |

**Key insight:** the repo already built the machinery (context, runner, clock, fakes, census, sanctioned table, shard guard). 66.3 is conversion work; any new mechanism should be a small extension, not a new framework.

## Common Pitfalls (recurrence of 66.1/66.2 findings)

### Pitfall 1: exit-contract regressions when a module's timer becomes an owner's timer
**What goes wrong:** a converted owner (`online_monitor` retry timer, `anonymousClient.idleTimer`, `SteamUser.idleTimer`, `winetricksQueue`, `shimCoverage`, the revived poller later) keeps a referenced timer or an unbounded boot call; the sidecar no longer exits at stdin EOF. 66.1 A-CR-1 (boot System Information dump, unbounded untracked spawns) and the three historical breaks (installed.json watcher, `setPresence` interval, boot downloads) are the precedents.
**How to avoid:** every timer on `ctx.clock` (unref'd); anything the library cannot unref goes in `stdinEofRelease`, never `startRpcServer`; no new boot work that does I/O at construction (66.1 "download queue boot service does no I/O at construction" is the model). Add unit assertions with `fakeClock`; run `pnpm build:sidecar && pnpm smoke:sidecar` after owner plans (it misses slow exit, so also assert unref in unit tests).
**Warning signs:** `smoke:sidecar` slow but green; `process._getActiveHandles()` looks empty (JS timers multiplex onto one uv timer).

### Pitfall 2: static holders that "move" instead of disappear (66.1 C-WR-2, verification verdict 2)
**What goes wrong:** `static bound` becomes a module-level `let bound` or a registry map: the census count drops or stays while ambient state persists.
**How to avoid:** the `bindStores`/`bindBottleStores`/`bindHumbleStores`/`bindDxmtStores` holders are deleted, consumers take slices. Humble and SteamGridDB currently throw if read unbound; keep a loud failure for missing deps at construction time, not a silent default.

### Pitfall 3: silent no-ops before a boot step (66.1 C-WR-5, C-IN-2)
**What goes wrong:** a function reads an unset owner and returns quietly (e.g. `requestSignInProbePass()` before its boot step; DXMT listener skipping when unbound; `SteamUser.releaseForShutdown()` throwing synchronously when unbound, 66.2 IN-03).
**How to avoid:** the owner is constructed before any consumer can call it by construction (boot step order), and the constructor requires its deps. Add a boot-order test per new owner step.

### Pitfall 4: `processGuards` WR-04 invariants
**What goes wrong:** adding any import to `processGuards.ts` or `installRejectionGuard.ts`, or moving the install into `bootstrap.ts`, reproduces the two documented failures (sidecar dies on boot with `broken pipe`, or `installFlows.test.ts` Test 1b order failure). `sidecarRejectionGuard.test.ts` Group 3 reads `src/sidecar/index.ts` as TEXT and asserts the install import is first; `zeroImports` asserts the module has no static imports.
**How to avoid (recommended conversion):** keep `processGuards.ts` import-free and export `createProcessGuards()` returning `{ installStdioErrorGuards, installUnhandledRejectionGuard, installUncaughtExceptionGuard, installConsoleStdoutRedirect, setUnhandledRejectionLogSink, setUncaughtExceptionLogSink }` over closure state (the 7 sites become closure fields; `uncaughtExceptionHandlerDepth` and the installed latches live in the closure). `src/sidecar/installRejectionGuard.ts` creates and installs it and exports the instance; `src/sidecar/index.ts` keeps `import { guards } from './installRejectionGuard'` as its FIRST import line and calls `init({ guards })`; `bootstrap.init`'s logger step binds the two sinks on the passed instance. Update Group 3's first-import regex (it currently matches a side-effect import). Run `pnpm build:sidecar && pnpm smoke:sidecar` as a mandatory gate (attempt (a) in the header passed 176 jest suites and still broke the real build). `process.on` listeners are inherently process-global, so keep the "idempotent install" check per instance AND a guard against double-install on the real `process` (a second instance must not add a second listener).
**Warning signs:** `app.getPath()` returning undefined at boot; Test 1b red.

### Pitfall 5: the census counts constant lookup Sets (18 sites)
**What goes wrong:** `const X: ReadonlySet<string> = new Set([...])` counts (D-06: any `new X` not in `IMMUTABLE_NEW`). 18 exist: `humble/classify`, `humble/library` (1 of 3), `runsForMe/index`, `enrichmentFlowRegistration`, `engine/bottlePrimitives`, `steam/userTypes` (2 of its 2), `depotDecodeErrors`, `gameLaunchOverlay`, `depotErrors`, `authTrigger` (2 of 5), `bridge/bridgeRoute`, `shimCoverage` (2 of 5), `interfaceVersions` (2 of 2), `overlayLaunch`. Left alone they block zero; sanctioning them violates D-05.
**How to avoid:** convert to a frozen array (`as const`) with `.includes`, or a frozen lookup `Object.freeze({...})` (an unmutated object literal is not counted), or build the Set inside the function that uses it. Large sets such as `SHIM_EXPORTED_SYMBOLS` are used in hot loops: prefer the frozen object lookup. This is Open Question 1 if the user prefers a census refinement instead.

### Pitfall 6: dead-code ratchet and line ceilings
**What goes wrong:** deleting `__reset*ForTests`, `bindStores`, the shim exports and `platform` types leaves knip findings that "vanish" (ratchet fails on a vanished finding) or fails on newly unused exports; closures in `storeManagers/steam/` can push a file over `steam-line-ceiling`.
**How to avoid:** lower `meta/knip-baseline.txt` in the same commit; run `pnpm find-deadcode` and `pnpm steam-line-ceiling` in every relevant plan.

### Pitfall 7: shard JSON contention and stale entries
**What goes wrong:** two same-wave plans edit one shard (`storeManagers.steam.json`) or leave a zero/stale entry (fails the census).
**How to avoid:** per-plan `--shard` run, full gate at wave end, never raise a number; a census-definition rebaseline must name every newly counted site in the commit.

### Pitfall 8: test-double drift and gate dodges (66.1 A-WR-7, C-WR-3/4, 66.2 WR-01/02)
**What goes wrong:** helpers that erase types to keep a grep gate empty (`testServices.load`), one-directional parity checks, allowlist holes, detectors that never match (the dead depcruise npm arm), exemptions that cover production-imported directories (testUtils).
**How to avoid:** every new gate in 66.3 gets a seeded failing fixture proving it fires (the pattern 66.2-REVIEW-FIX used for `boundaryGates.test.ts`); the 66.3 `diPhaseGates` block scans a full tree (`scans a full backend tree` floor assertion) so a mis-rooted scan fails instead of passing vacuously.

### Pitfall 9: the census residual (call-returning containers)
**What goes wrong:** `const q = createQueue()` at module scope is state the census does not count; conversions can "pass" by moving state there.
**How to avoid:** the pin test in "census becomes a test" above; reviewers check each plan's diff for new top-level calls.

### Pitfall 10: async/ordering and re-entrancy when a singleton becomes an instance
**What goes wrong:** code that relied on one shared in-flight promise (`anonymousClient.inflight`, `SteamUser.connectingPromise/wrapTail`, `humble/library.syncInFlight`, `launchSingleFlight`) gets two instances in tests or boot re-entry and loses single-flight semantics; `generation`/`sessionGeneration` counters that fence stale callbacks must be per-instance but shared by every consumer of the same owner.
**How to avoid:** exactly one instance per boot (boot step runs once by construction, D-08), consumers share it through slices, tests that need two build two explicitly. Keep characterization tests for single-flight, abort-on-shutdown and generation fencing.

### Pitfall 11: platform-specific behaviour not testable on this Mac
**What goes wrong:** the shim carries win32/linux branches; 66.2's Windows live gate is still pending (`todos/pending/2026-11-10-66.2-windows-spawn-paths-live-gate.md`).
**How to avoid:** scripted-argv assertions in unit tests; changes to `knownFolders`/`pathShim` are 66.4 per CONTEXT; do not change those paths in 66.3 beyond slice plumbing.

### Pitfall 12: baseline failures
66.2's validation recorded a known baseline of "10 failing tests in 8 suites, identical at pre-66 commit" for `pnpm test:ci` [CITED: 66.2-VALIDATION.md; not re-measured here]. Plan 01 should re-measure the baseline and record the list so later plans do not chase or add to it.
