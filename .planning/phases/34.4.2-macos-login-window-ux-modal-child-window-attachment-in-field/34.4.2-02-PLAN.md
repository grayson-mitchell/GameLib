<objective>
Make the login window un-losable on macOS by attaching it to the app's `main` window as an AppKit
**child window**, and re-raise it after the parent restores from the Dock. Spike 021 measured this
directly (`login-window-ux-macos.md` § 1): a free-floating login window goes BEHIND on a parent
raise, gets orphaned on minimize, and is the bug this closes; a child window stays in front, follows
drags, follows the parent into the Dock — but comes back **behind** on restore unless explicitly
re-raised.

**SCOPE (locked user decision, 2026-08-04): the Tauri-managed `WebviewWindow` surface ONLY** —
Humble plus the GOG/Amazon OAuth runners. The pristine Epic login window
(`open_pristine_epic_login_window`) is out of scope and must be byte-unchanged; Epic ships last, after
all other runners are proven. AppKit-layer attachment is still the right mechanism rather than Tauri's
builder `.parent()` — it works on an already-live window and is detachable at runtime — and it keeps
the future Epic phase's job to one added call site rather than a redesign.

Purpose: today the login window is a `.focused(true)` one-shot raise with no persistent
relationship to the app. A user who clicks back to the library loses the login window behind it with
no way to find it again.

Output: one attach/detach pair wired into the Tauri-managed login surface, a deminiaturize re-raise
observer, and the permanent negative guards that keep sheets, `.parent()` and focus-driven re-raises
out.
</objective>

**`fn attach_login_window_as_child(app: &AppHandle, label: &str)`** — resolves the parent via
`login_window_ns_window(app, MAIN_WINDOW_LABEL)` and the child via
`login_window_ns_window(app, label)`, then hops to the main thread (`app.run_on_main_thread`, this

Contract details that are load-bearing:
- **Returns nothing and is never fatal.** A missing parent, a missing child, or a failed main-thread

Mechanism, concretely:
- In `.setup()`, after the tray block, add a `#[cfg(target_os = "macos")]` block that resolves the

  `addObserverForName_object_queue_usingBlock` with name
  `objc2_app_kit::NSWindowDidDeminiaturizeNotification`, `object` = the main `NSWindow`, `queue` =
  `None` (deliver on the posting thread, which for this notification is the main thread), and a
  `block2::RcBlock` handler. `objc2-foundation` is declared WITHOUT `default-features = false` in
  `src-tauri/Cargo.toml`, so `NSNotificationCenter` is already available; `block2` is already a
  declared macOS dependency. No Cargo.toml change.
- The handler clones the label list out of `ATTACHED_LOGIN_CHILDREN` (never holds the lock across an
  AppKit call), resolves each label's `NSWindow` via `login_window_ns_window`, and calls
  `makeKeyAndOrderFront(None)` on it. A label whose window no longer resolves is skipped silently —
  a closed window is a healthy state, not an error.
- `std::mem::forget` the returned observer token, matching the file's existing deliberate leak for
  `EpicPristineNavDelegate`, and document WHY it is acceptable here (one observer for the process

  continue — the app must still start.

  child window(s)`. Never log a label's URL.

`makeKeyAndOrderFront` every time the user deliberately clicks the main window, stealing key focus

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| remote login page → login window chrome | An untrusted page now renders in a window pinned ABOVE the app's own main window. |
| Rust shell → AppKit window graph | `addChildWindow:` mutates the process's window hierarchy. |
| NSNotificationCenter → Rust block handler | A system notification drives a raise of windows named in a process-static list. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-34.4.2-05 | Spoofing | child-window overlay / app-chrome imitation | mitigate | Attachment changes z-order ONLY. The login window keeps its full OS title bar carrying the SHELL-RESOLVED origin (`login_window_title()`, WR-07) — the one piece of chrome the page cannot forge — and this plan adds no `.decorations(false)`, no `.transparent(true)`, no `.title_bar_style` change.
