<objective>
Close **T-34.4.2-39** (OPEN, minted mid-gate by plan 12, no discharging item): a second login flow
initiated while a first is still pending gets its `beginSheet:` QUEUED by AppKit behind the first,
so the second store's sheet surfaces at the moment the user dismisses the first — not at its own
request time.

Purpose: gate run 2's operator hit this live. Amazon's sign-in was clicked first, appeared to do
nothing for 7-8 s, so Humble was clicked and opened immediately; on dismissing Humble, Amazon's sheet
appeared unrequested. The upstream delay is **F-34.4.2-06** — `src/backend/storeManagers/nile/user.ts:30`
obtains the Amazon login URL by exec'ing `nile`, a PyInstaller onefile binary, and this project's own
recorded macOS tax for those helpers is 5-13 s per exec (random `_MEI` extraction defeating the
Gatekeeper signature cache). That tax is **pre-existing and NOT a 34.4.2 regression** — this phase
merely made it visible by putting a modal in front of it, and it is explicitly not this plan's to
fix. What IS this plan's to fix is the consequence: **the concrete failure mode is typing one store's
password into another store's just-arrived sheet** (Spoofing / origin confusion, the same class the
login title's origin-first ordering exists to prevent, T-34.5-G6-22/-23).

Transcript evidence rules the sheet mechanism out as the cause: all four presentations that run
resolved `attached=true` in 570-620 ms with `deferred_elapsed` ~261 ms. The 7-8 s sits entirely
upstream of `humble_login_open`.

**This plan is scoped to the app gap. The matching CONTRACT gap** — that the six-item contract had no
item covering the pre-presentation window, because item 1(a) assumes the sheet is already up when the
check begins — **is plan 34.4.2-15's job**, which authors the new contract and gives this mitigation
its own gate item.

**Not in scope, and not to be re-litigated:** the nile spawn cost itself (F-34.4.2-06 — the only
in-repo lever is call-count reduction, out of this phase entirely); child-window attachment (D-C, off
the table forever); the deleted autofill mechanism (D-A, plan 13); Epic (D-D, byte-frozen).

Output: a shell-level guard that makes an unrequested sheet structurally impossible, bounded so it
can never become a lock-out of its own.
</objective>

    Add a `#[cfg(target_os = "macos")]` single-flight guard over VISIBLE Tauri-managed login windows.

    **1. The registry.** Declare `static PENDING_VISIBLE_LOGIN_WINDOW: Mutex<Option<(String,
    std::time::Instant)>>`, macOS-gated, holding the label and arm-time of the visible login window
    currently between request and resolution. Zero or one entry — this is a latch, not a list, and it
    must not grow.

    **2. The bounded expiry, and why it exists.** Declare
    `const PENDING_VISIBLE_LOGIN_WINDOW_TTL: Duration` derived from
    `LOGIN_SHEET_PRESENT_WATCHDOG_TIMEOUT` plus a stated margin (the watchdog already bounds the whole
    attach attempt at 15 s; the TTL must be strictly greater so the two can never race into
    disagreement). Extract the staleness decision into a pure, AppKit-free helper
    `fn pending_login_entry_is_stale(age: Duration) -> bool` so it is unit-testable without a live
    window. **This is a safety requirement, not a nicety** (T-34.4.2-41, new this plan): a latch armed
    by a flow that then panics, hangs in the upstream CLI spawn, or is killed mid-flight would
    otherwise block every future sign-in for the life of the process — converting a spoofing
    mitigation into a total denial of service. An expired entry is treated as absent and is cleared in
    passing, with its own log line naming the elapsed time.

    **3. The refuse-or-arm check.** Insert it in the `humble_login_open` arm AFTER the
    `#[cfg(target_os = "macos")] if is_epic_login { return open_pristine_epic_login_window(...) }`
    early return and BEFORE `tauri::WebviewWindowBuilder::new(`:
    - Applies **only when `visible` is true.** Hidden reveal/clear windows are never refused and never
      arm the latch — the Humble disconnect route (`src/backend/humble/user.ts:813`, the same
      `seam.open(..., {visible:false})` → `humble_login_open` path) is how gate item 6(a) is actually
      measured, and reveal-key operations must keep working while a sheet is up.
    - Refuses when EITHER a non-expired pending entry exists OR `PRESENTED_LOGIN_SHEETS` is non-empty.
      Both conditions matter: the first covers the pre-presentation window (the F-34.4.2-07 case), the
      second covers a sheet already on screen.
    - On refusal: return `Err("humble_login_open:login-already-in-progress".to_string())` **before any
      window is constructed**, and emit exactly one line naming both the refused request and the
      incumbent, e.g. `[shell] humble_login_open: REFUSED visible login window -- '{incumbent}' is
      already pending or presented (T-34.4.2-39 single-flight)`.
    - On acceptance: store `(label, Instant::now())` and emit
      `[shell] humble_login_open: visible login window '{label}' armed as the single pending login flow (T-34.4.2-39)`.

    **4. Clearing.** Add `#[cfg(target_os = "macos")] fn clear_pending_visible_login_window(label: &str)`
    which clears the latch only when the stored label MATCHES (so a late clear from an
    already-superseded flow cannot unlatch a newer one), and logs which label it cleared. Call it on
    all three resolution paths named in `<interfaces>`: sheet presentation confirmed, visible-fallback
    ran, and `WindowEvent::Destroyed`. **Do not** route any of this through
    `register_presented_login_sheet` — Plan 11's exactly-three-call-sites test would fail.

    **5. Do not disturb the debug arc's safety net.** No change to
    `SHEET_PRESENT_WKWEBVIEW_WARMUP_DELAY`, no change to where
    `LOGIN_SHEET_PRESENT_WATCHDOG_TIMEOUT` is raced, no second `present_login_window_as_sheet` call

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| user intent → presented sheet | The user must always be able to attribute the credential surface in front of them to the click that produced it. A sheet arriving at a moment the user did not request one breaks that attribution. |
| upstream CLI spawn → shell | The shell is told nothing about a login flow until `humble_login_open` is called; on the Amazon path that is ~7-8 s after the user's click. Everything before that call is outside the shell's knowledge. |
| a safety latch → the user's ability to sign in at all | Any single-flight guard is one bug away from being a total lock-out. |
