<objective>
Put the in-field autofill affordance on screen and give it a way to reach Rust. Spikes 020/022 proved
the shape: inline Password AutoFill and save-prompts are platform-blocked in both login surfaces on
loopback HTTP *and* real HTTPS, but a **synthesized right-click at the password field pops the real
system context menu with `AutoFill ›` in it**. This plan builds everything up to (but not including)
the synthesized click: the injected glyph, and the page→Rust request channel carrying the field's
geometry.

Purpose: without an in-field affordance the AutoFill route is undiscoverable — the user has to
somehow know to right-click a password box. The glyph is the whole shippable win.

Output: one shared JS glyph script generated by a pure Rust builder, injected into BOTH login
surfaces (`initialization_script()` for the Tauri-managed window; a `WKUserScript` on the pristine
`WKWebView`'s content controller), plus a cancelled-navigation sentinel handler on both surfaces that
parses the request and — for now — logs it. Plan 34.4.2-04 replaces that log with the actual
`postEvent:` pair.

**Explicitly NOT in scope, and not a deferral:** opening the AutoFill panel directly. Spike 022
proved it impossible — macOS injects the AutoFill item at menu-display time and it is absent from the
`NSMenu` object graph even when the screen shows it (`willOpenMenu:` hands over a 3-item
Cut/Copy/Paste menu; a post-display re-dump of the same retained menu is still 3 items). No task
here may attempt it.
</objective>

**The established page→Rust channel in this file is cancelled-navigation exfil.** Remote pages
CANNOT invoke app commands — `tauri-login-webview-cookies.md` § "What to Avoid" records that with
`windows: ["login-*"]` and `remote.urls: ["https://*.humblebundle.com"]` declared, an injected script
still got `rejected: report_from_page not allowed. Plugin not found`. Do not design around
`window.__TAURI__`.

The existing exfil constants and both existing consumers (`src-tauri/src/main.rs`):
```
const REVEAL_EXFIL_HOST: &str = "gamelib.invalid";           // ~L1033, RFC 2606 reserved, never resolves
fn reveal_post_script(path, body, csrf_token, exfil_host) -> String   // ~L1178
fn clear_storage_script(exfil_host) -> String                         // ~L1278, uses an @@EXFIL_HOST@@ placeholder + .replace()
```
and the interception shape both hidden-window arms use (`humble_reveal_post` ~L3206,
`humble_login_clear_storage` ~L3273):
```rust
.on_navigation(move |url| {
    if url.host_str() == Some(REVEAL_EXFIL_HOST) {
        if let Some((_, payload)) = url.query_pairs().find(|(k, _)| k == "data") {
            let _ = tx.send(payload.into_owned());
        }
        return false;   // cancel
    }
    true
})
```

**The pristine surface's equivalent hook** is `EpicPristineNavDelegate::navigation_policy`
(`webView:decidePolicyForNavigationAction:decisionHandler:`, ~L1400). It already cancels
(`WKNavigationActionPolicy::Cancel`) for Epic's localhost redirect, and its own comment records that

The script's required behavior, stated as a contract the executor implements (write the JS itself —
do not paste a snippet from this plan):
- Idempotent: bail immediately if `window.__GAMELIB_AUTOFILL_GLYPH__` is already set; set it first.
- Runs in every frame (login forms are frequently in iframes) and works when the form renders late:
  do an initial scan on `DOMContentLoaded`/immediately, plus a `MutationObserver` on
  `document.documentElement` with `{childList:true, subtree:true}`, debounced.

  the field's right-hand inside edge. Position it from `getBoundingClientRect()` with
  `position:fixed` and a maximal `z-index`; reposition on `scroll` (capture) and `resize`. Do NOT
  wrap or re-parent the input, do NOT set any attribute on the input other than a single namespaced
  data marker, and do NOT alter the input's own styles — a login form's validation logic must see an
  untouched field.
- Accessibility: `role="button"`, `aria-label="AutoFill password"`, `title` the same, `tabindex="-1"`
  so the glyph never enters the form's tab order.
- **Keyboard-transparent (REQ-34.4.2-06):** the glyph registers NO `keydown`/`keyup`/`keypress`
  listener anywhere, and calls `preventDefault()` on nothing but its own `mousedown`. Cmd+V into the
  password field must keep working in both surfaces; the pristine window's `NSEvent` local monitor
  routes `paste:` through `sendAction:to:from:` and must not be shadowed.
- On glyph activation: `field.focus()`, then read `getBoundingClientRect()`, compute the centre, call
  `document.elementFromPoint(cx, cy)` and read `id`/`tagName`/`type` off the result (the skill makes
  this MANDATORY — a title-bar-sized coordinate error otherwise silently probes the wrong field and
  its menu is misread as evidence). Build `{x,y,w,h,hitId,hitTag,hitType}` — **the field's `value` is
  never read and must not appear anywhere in the script.**
- Deliver via a **hidden `<iframe>`**, not `location.href`: create (or reuse) a `display:none`,
  1×1 iframe and set its `src` to
  `'https://' + <host> + '/autofill-request?data=' + encodeURIComponent(JSON.stringify(payload))`.
  The iframe is what makes this safe on a LIVE login form — `location.href` would navigate the main
  document (fine for the existing hidden reveal/clear windows, destructive here: it fires
  `beforeunload` and can drop half-entered form state). Both surfaces' navigation hooks fire for
  subframes, so an iframe navigation is observed and cancelled identically.
- Rate-limit itself: ignore a second activation within 750 ms.

Everything the script does must be wrapped in a single top-level `try { } catch (e) { }` so a
throwing glyph can never break a login page.
