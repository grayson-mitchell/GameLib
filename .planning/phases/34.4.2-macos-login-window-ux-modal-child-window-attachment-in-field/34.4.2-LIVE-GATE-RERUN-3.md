## Structural Reachability Review

**Gate run 2's own record names contract authoring as a defect surface**: four independent
structural impossibilities were found in its contract during EXECUTION rather than review (the
DummyStore https-only block affecting items 3/4 and precondition 4; item 6(a)'s concurrency framing
against AppKit's own sheet-blocks-parent design; item 2's OAuth-runner-only log-line requirement
Humble cannot emit — see `deferred-items.md`'s Plan 15 entry for the full four-instance list). This
section is the dedicated review step that pattern calls for, run BEFORE this contract's first live
use, not discovered live for a fifth time. It applies four defect-class tests, drawn directly from
the four confirmed instances, to every item, sub-check and precondition above.

**The four defect-class tests:**

1. **Origin/scheme reachability** — does any sub-check or precondition require a URL
   `login_window_url_arg` (`src-tauri/src/main.rs:926`, https-only, non-`https` schemes rejected
   before any window is built; test at `main.rs:5725`) will reject?
2. **Concurrency reachability** — does any sub-check require two things to be driven at once
   through a UI where a presented sheet blocks its own parent by AppKit design?
3. **Log-line emitter reachability** — for every `[shell]`/sidecar literal an item requires, is it
   grep-confirmed in current source, at the cited line, and reachable from the specific surface the
   sub-check names (not runner-gated against a surface that cannot emit it)?
4. **Absence-observability** — for every required ABSENCE, would the PRESENCE case have actually
   produced an observable signal? An absence assertion over a code path that logs nothing on
   success proves nothing.

(b) Drag the main window to a new screen position.
(c) Minimize the main window (into the Dock).
(d) Restore the main window from the Dock.
(e) **Immediately after the restore, type into the password field, then activate the cancel
strip.**

**PASS condition for each sub-check:**
- (a) The sheet **stays in front** of the main window and the main window **does not** come over
  it. A sheet BLOCKS its parent by AppKit design — the main window declining clicks while the sheet
  is up is correct sheet semantics and is **NOT** a failure. Only a sheet going BEHIND the main
  window, or the main window accepting input while the sheet is presented, would be a failure.
- (b) The sheet **moves with** the main window's drag.
- (c) The sheet **follows the parent into the Dock**.
- (d) The sheet is **visible and in front** immediately upon restore.
- (e) **Typed characters appear in the password field AND the cancel strip responds** (dismisses

  sheet mechanism.

**PASS = all five sub-checks (a)-(e) observed as above.**

### Item 5 — NEW: single-flight login initiation (T-34.4.2-39, F-34.4.2-07)

**AMENDMENT (Task 3, Structural Reachability Review — see that section above for the full
reasoning): a separately-UI-driven "Arm 2" (attempt a second login by clicking a button WHILE a
sheet is already presented) is REMOVED from this item, not deferred.** A presented sheet is
application-modal to its parent (the `main` window) by AppKit design, and every login trigger in
this app (Humble/GOG/Amazon/Zoom) lives inside that same single-page `main` window — there is no
tray, menu-bar, or secondary top-level window through which a login could be initiated while the
main window is blocked. A human operator physically cannot click a second "sign in" control once a
sheet is up. This item instead has a single scenario, whose own natural timing exercises BOTH
branches of the refuse-or-arm check's incumbent lookup (pending latch OR presented-sheets list) —
see the Structural Reachability Review's own reasoning for why.

**What to do.** Click Amazon sign-in (the slow nile path), and during its ~7-8s upstream delay
(F-34.4.2-06) click Humble sign-in. **Exactly one sheet must present**; the other initiation must
be REFUSED, with the refusal line in the transcript:
```
[shell] humble_login_open: REFUSED visible login window '{label}' -- '{incumbent_label}' is already pending or presented (T-34.4.2-39 single-flight)
```
(`src-tauri/src/main.rs:3381-3383`, confirmed present in current source). The **decisive sub-check**:
on dismissing the presented sheet, **NO second sheet may appear.** That unrequested arrival is the
precise failure gate run 2 observed (F-34.4.2-07). Also capture, when the first (accepted) request
is armed:
```
[shell] humble_login_open: visible login window '{label}' armed as the single pending login flow (T-34.4.2-39)
```
(`src-tauri/src/main.rs:3387-3389`).

**Record-only sub-check, not scored, because the log line itself does not distinguish the two
branches:** the REFUSED line's own text reads `'{incumbent_label}' is already pending or presented`
— it does not say which. Given the sub-second sheet-attach timing gate run 2's own transcript
measured (570-636ms per window), by the time Amazon's delayed (~7-8s) request finally reaches the
refuse-or-arm check, Humble's own sheet is very likely already CONFIRMED presented (its pending
latch entry already cleared by `clear_pending_visible_login_window` on the sheet-confirmed path,
`src-tauri/src/main.rs:2258`) — meaning this single scenario likely exercises the
`PRESENTED_LOGIN_SHEETS`-non-empty branch of the incumbent lookup, not only the pending-latch
branch a faster refusal would hit. Record the observed timing (how long after the Humble sheet
presented did the Amazon refusal fire) as context, but do not fail the item if this cannot be
distinguished — the code's own log line cannot distinguish it either.

**Record-only, but explicit:** what the user actually sees when this refusal happens — an error, a
toast, a spinner that stops, or nothing at all. Plan 14's own source trace found this differs by
surface: GOG/Amazon/Zoom (`captureOAuthLogin`) surface an explicit error
(`TauriLoginPanel.tsx`'s `phase === 'error'` branch, message

surfacing it would require an out-of-scope cross-platform frontend change (REQ-34.4.2-08). Record
whichever surface this scenario actually exercises as the refused party (Amazon, per the scenario
as written — record if the operator's own click order changes which store is refused).

**PASS = the scenario refuses the delayed request (with the REFUSED line present) and no
unrequested sheet arrives on dismissal.** The record-only sub-checks above (which incumbent branch
fired; what the user sees) do not affect this item's verdict.
