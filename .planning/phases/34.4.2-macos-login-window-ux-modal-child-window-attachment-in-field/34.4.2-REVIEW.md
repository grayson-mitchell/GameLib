## Summary

Reviewed the AppKit sheet-presentation delivery (`present_login_window_as_sheet` / `dismiss_login_window_sheet` / `PRESENTED_LOGIN_SHEETS`), the mandated close affordance (cancel strip + bare-Esc monitor + `request_login_sheet_cancel`), the synthesized right-click poster, `Cargo.toml`'s feature declarations, and the three Jest gate suites.

The headline finding directly addresses F-34.4.2-03 (window observed as an ordinary titled, unattached window): **the login window is ordered on screen as a normal window during `.build()` — before `beginSheet:` ever runs**. AppKit does not convert an already-visible, already-key window into an attached sheet; the call completes without error, `sheet_presented=true` is logged, the label is registered in `PRESENTED_LOGIN_SHEETS`, and nothing anywhere reads back whether attachment actually happened. This is a silent-failure pipeline end to end, and it is structurally invisible to both test suites because every gate in `tauriShellSource.test.ts` asserts source *text* and every cargo test covers only AppKit-free pure helpers. The Epic pristine surface remains untouched (scope guards verified; no coupling found).

## Critical Issues

### CR-01: `beginSheet:` is called on a window that is already visible and key — attachment silently fails (prime root-cause candidate for F-34.4.2-03)

**File:** `src-tauri/src/main.rs:3595` (`.visible(visible)`), `src-tauri/src/main.rs:3600-3601` (`.center()` / `.focused(true)`), `src-tauri/src/main.rs:3830-3835` (present call site), `src-tauri/src/main.rs:2750` (`beginSheet_completionHandler`)
**Issue:** The visible login window is built with `.visible(true)`, `.center()`, `.focused(true)` — tao orders it front and makes it key as part of window creation, which completes before `.build()` returns. Only *after* that does the arm call `present_login_window_as_sheet`, which (from the `dispatch_rust_channel` worker thread) queues a main-thread closure that calls `parent.beginSheet_completionHandler(child, None)`. AppKit's sheet API expects the sheet window to be *offscreen*; presenting a window that is already ordered in and key does not re-parent it into a sheet — the call returns having done nothing visible, leaving exactly what the operator observed: an ordinary titled, unattached window. The reverse race also exists: because the worker thread queues the present closure through the event-loop proxy, any deferred show/focus/center work that lands *after* `beginSheet:` (e.g. tao's `makeKeyAndOrderFront` for the one-shot focus) would detach a just-presented sheet. Both orderings break; neither produces an error. This defect is unreachable by the whole automated suite (cargo 131/131 tests exercise only the pure helpers; the Jest gates assert source text), which is precisely why 3735 green tests coexisted with a 0/6 live gate.
**Fix:**
```rust
// In the humble_login_open arm: never order the macOS sheet candidate in as a
// free-standing window. Build it hidden and let beginSheet: perform the reveal.
#[cfg(target_os = "macos")]
let builder_visible = false; // sheet path: beginSheet orders the window in itself
#[cfg(not(target_os = "macos"))]
let builder_visible = visible;
let mut builder = tauri::WebviewWindowBuilder::new(app, &label, tauri::WebviewUrl::External(url))
    .user_agent(user_agent)
    .visible(builder_visible);
// ... after .build():
#[cfg(target_os = "macos")]
let sheet_presented = if visible {
    let ok = present_login_window_as_sheet(app, &label);
    if !ok {
        // Fallback: never leave the user with an invisible login window.
        let _ = window.show();
    }
    ok
} else { false };
```
Also drop `.focused(true)`/`.center()` for the macOS sheet path (a sheet's position and key status are owned by `beginSheet:`; a queued one-shot focus is the detach race above). Verify on hardware that `beginSheet:` on a never-shown Tauri window both reveals and attaches it — that is the rewritten live gate's item 1.

transcribed from a SUMMARY.**

### CR-02: `sheet_presented=true` and the `PRESENTED_LOGIN_SHEETS` registration are emitted on "the call ran", with no read-back that a sheet actually attached — the success signal is unfalsifiable

**File:** `src-tauri/src/main.rs:2746-2774` (return `true` + registration after `beginSheet_completionHandler`), `src-tauri/src/main.rs:3844-3846` (`sheet_presented={sheet_presented}` machine-evidence line)
**Issue:** `present_login_window_as_sheet` returns `true` the moment the main-thread closure has executed `beginSheet_completionHandler` — a mutating call whose own completion proves nothing about effect (this repo's own repeatedly-recorded discipline: the wry cookie-delete lie, F-6 Defect B). AppKit exposes the ground truth cheaply and synchronously right there on the main thread: `parent.attachedSheet()` should be `child`, and `child.isSheet()` should be true. Because neither is read, (a) the presentation-record `eprintln!` that the live gate treats as machine evidence reports `sheet_presented=true` for a presentation that visibly did not happen, (b) the label is registered in `PRESENTED_LOGIN_SHEETS`, unlocking `post_autofill_right_click`'s "only a VISIBLE, presented login sheet" authorization gate for a window that is not a sheet, and (c) F-34.4.2-03's root cause was undiagnosable from logs. Incorrect behavior on the phase's core requirement (REQ-34.4.2-01/02) shipping with a success log is a blocker, not a style issue.
**Fix:**
```rust
parent.beginSheet_completionHandler(child, None);
// Never trust the mutating call's own report: read the attachment back.
let attached = parent
    .attachedSheet()
    .map(|s| core::ptr::eq(&*s as *const _, child as *const _))
    .unwrap_or(false);
let _ = tx.send(attached);
```
Propagate `attached` (not `()`) through the channel; return it, log it in the presentation record, and only register the label in `PRESENTED_LOGIN_SHEETS` when it is true. Requires the `NSWindow` feature's `attachedSheet`/`isSheet` accessors (already within the declared `objc2-app-kit` `NSWindow` feature).

**Resolution (2026-09-29 disposition pass): FIXED, and STRONGER than proposed. Verified in source at
HEAD.**

`src-tauri/src/main.rs:3989-3992`:

```rust
let attached = child.isSheet()
    && parent
        .attachedSheet()
        .is_some_and(|sheet| std::ptr::eq(&*sheet as *const _, child as *const _));
```

This finding proposed reading back `attachedSheet()` alone. The shipped fix requires **both**
`child.isSheet()` **and** a pointer-identity match on `parent.attachedSheet()`, and the in-situ
comment gives the reason this review did not: either signal alone could be a false positive — a
stale `isSheet()` from a previous presentation — so the conjunction is the strongest falsifiable
signal the binding exposes. The value is sent through the channel (`tx.send(attached)`), and
`main.rs:4020` carries the negative path as an explicit `WARN` naming both accessors and this
finding's own IDs:

> `[shell] WARN: login-window sheet: beginSheet did not attach '{label}' to '{MAIN_WINDOW_LABEL}' (attachedSheet/isSheet read-back false -- CR-01/CR-02)`

There is also a `read-back attached={attached}` diagnostic (`main.rs:3993-3995`), so the machine
evidence line the live gate consumes now reports measured attachment rather than "the call ran".
That read-back is what made F-34.4.2-05's terminal diagnosis possible at all — it is the
instrument, not just the fix.

Fixed in commit `751521663`, same commit as CR-01. Full record:
`.planning/debug/resolved/white-window-not-sheet-cr01.md`.

## Warnings

### WR-01: `dismiss_login_window_sheet` removes the registry entry before the AppKit call — a failed `endSheet:` hop permanently strands the parent behind a sheet with no remaining dismissal route

**File:** `src-tauri/src/main.rs:2806-2831`, `src-tauri/src/main.rs:2850-2856`
**Issue:** The label is removed from `PRESENTED_LOGIN_SHEETS` first, unconditionally (documented as T-34.4.2-08 hygiene). But if the subsequent main-thread dispatch fails or times out (lines 2850-2856), `endSheet:` never runs while the sheet stays presented — and because *both* cancel routes (`request_login_sheet_cancel` via strip and Esc) and any retry are membership-gated on that same registry, no code path can ever end the sheet again. The parent window is then document-modally blocked for the process lifetime.
**Fix:** On dispatch failure/timeout, re-insert the label (or perform removal only after `rx` confirms the closure ran), keeping the "always removed even when the window is gone" guarantee for the healthy `child_addr == None` path only.

### WR-02: Raw `NSWindow` addresses resolved on the worker thread are dereferenced later in a queued main-thread closure with no retain — use-after-free race

**File:** `src-tauri/src/main.rs:2713-2745` (present), `src-tauri/src/main.rs:2821-2848` (dismiss)
**Issue:** `login_window_ns_window` returns a bare pointer as `usize`; the closure that reconstructs it as `&NSWindow` runs whenever the event loop next turns. Between resolution and execution, the login window can be closed (user Cmd+W, `captureOAuthLogin` settling, `humble_login_close`) and the `NSWindow` released — the SAFETY comment's "resolved moments ago … live" claim is a timing assumption, not an invariant. The dismiss path is narrower (its callers are already on the main thread, so the closure runs inline), but the present path crosses a real thread boundary. A dangling dereference here is a hard crash in the shell process.
**Fix:** Resolve the addresses *inside* the main-thread closure (pass the `AppHandle` + labels in, call `login_window_ns_window` there), so resolution and use are atomic with respect to the event loop; or retain (`Retained<NSWindow>`) across the hop.

**Status (2026-09-29 disposition pass): STILL OPEN — and the CR-01/CR-02 fix WIDENED the race
window it describes, from "next main-thread turn" to "at least 250ms later". Measured at HEAD, not
inferred.**

Neither proposed remedy was applied. At HEAD the present path still resolves both addresses on the
worker thread and dereferences them later:

- `main.rs:3882`/`:3888` — `login_window_ns_window(app, MAIN_WINDOW_LABEL)` and
  `login_window_ns_window(app, label)`, both returning `Option<usize>`.
- `main.rs:3900-3903` — wrapped in a local `struct SendPtr(*mut std::ffi::c_void)` with
  `unsafe impl Send for SendPtr {}`.
- `main.rs:3965-3968` — reconstructed inside the deferred closure as
  `unsafe { &*(parent_ptr.0 as *const objc2_app_kit::NSWindow) }` and the same for the child.
- No `retain()`, and no `Retained<NSWindow>` across the hop. That omission is **deliberate and
  documented** (`main.rs:3655`): `login_window_ns_window` returns `usize` rather than a live
  `Retained<NSWindow>` precisely because `Retained<NSWindow>` is not `Send`, so it cannot cross the
  dispatch boundary as-is. Any fix has to reckon with that, which is why "just retain it" is not a
  one-line change — resolving inside the closure (this finding's first option) is the tractable one.

The SAFETY comment at `main.rs:3961-3964` still asserts the addresses "were resolved moments ago",
which is the exact timing assumption this finding identified as "not an invariant."

**What changed for the worse.** The terminal CR-01/CR-02 fix (`8b2fdb315`) replaced an
`run_on_main_thread`-style hop with `DispatchQueue::main().after(when, …)` at
`SHEET_PRESENT_WKWEBVIEW_WARMUP_DELAY` = **250ms** (`main.rs:3762`, `:3941-3943`). The addresses are
resolved before that timer is armed and dereferenced after it fires, so the interval during which a
closed login window can leave both pointers dangling grew from one run-loop turn to a wall-clock
quarter-second. Live measurement in the debug session recorded the closure actually entering at
`deferred_elapsed=260.3ms`. Every closer this finding lists — user Cmd+W, `captureOAuthLogin`
settling, `humble_login_close` — remains reachable inside that window, and the consequence is
unchanged: a dangling `NSWindow` dereference is a hard crash of the shell process.

This is not an argument against the CR-01/CR-02 fix, which was necessary and is confirmed working.
It is that the fix moved a latent race from "narrow" to "measurably wide" without the review being
updated, because WR-02 and the debug session were never read against each other.

**Not fixed here, deliberately.** This is `unsafe` Objective-C interop on a path with a nine-attempt
live-gate history, and correcting it means either restructuring how the addresses cross the dispatch
boundary or reworking the `Send` story around `Retained<NSWindow>`. It needs its own task and a live
macOS gate, not a drive-by edit inside a disposition pass. Recorded here with the measurement so the
next reader starts from evidence rather than re-deriving it. Suggested triage: `severity: major`,
`platform: macos`, `ready: live-gate`.

**Status (2026-09-30, quick task 260930-q11): DESK-COMPLETE, LIVE GATE PENDING — not resolved.**

Option 1 above was applied, to **both** paths (commit `bb567faf3`). Both `NSWindow` handles are now

**Two substrate findings, both read directly out of the vendored crate, and this finding's own "Fix"
text proposed option 1 without either of them.** They are why option 1 was the right call for a
stronger reason than the one recorded above, and why the dismiss path was fixed too rather than left

- **The handle is AUTORELEASED.** `tauri-2.11.5/src/window/mod.rs:1642` is
  `Ok(objc2::rc::Retained::autorelease_ptr(ns_window).cast())`. The returned address's guaranteed
  validity is bounded by the autorelease pool of the thread that *resolved* it, not by the login
  window's lifetime. So the resolve-early/dereference-later shape was outside `ns_window()`'s

  purely as that race, which understates it — and it removes the basis for treating an
  already-on-the-main-thread dismiss hop as safe, since the pool, not the thread, is the bound.
- **The AppKit accessor and the autorelease both ran on the WORKER thread.** In `ns_window()`, only

  `view.window()` and registers the autorelease runs on the **caller's** thread. At HEAD that was a
  worker thread. A second, independent gain from resolving inside the main-thread closure.

### WR-03: The cancel strip is injected into every frame with no top-frame guard — duplicate "Cancel sign-in" controls render inside third-party iframes

**File:** `src-tauri/src/main.rs:1603-1668` (script), `src-tauri/src/main.rs:3668-3675` (injection)
**Issue:** Tauri `initialization_script` runs in every frame (this arm's own comment at line 3639-3641 says so), and the idempotence flag `window.__GAMELIB_LOGIN_CANCEL_STRIP__` is per-frame. Spike 013 measured 5 of 8 navigations on Humble's real login page as third-party iframes — each such frame (ad frames, bot-management frames) builds its own fixed-position "Cancel sign-in" strip pinned to *its* top-right, plus its own MutationObserver. Visible duplicates inside embedded frames are a live UX defect on exactly the pages this phase targets; the autofill glyph mostly escapes this only because third-party frames rarely contain password fields.
**Fix:** First statement inside the try block: `if (window.top !== window) { return; }` (wrapped so a cross-origin `window.top` access throwing still bails via the existing catch).

### WR-04: A throw in the strip's initial `ensure()` kills the DOMContentLoaded retry and the MutationObserver for the whole document — the "only visible exit" can silently never render

**File:** `src-tauri/src/main.rs:1653-1663`
**Issue:** The script's single top-level try/catch sequences `ensure()` (which appends to `document.body || document.documentElement`) *before* the `DOMContentLoaded` listener registration and the observer setup. At document-start injection time, if the append throws (no `documentElement` yet, or a hostile/odd document state), the catch swallows it and — because `__GAMELIB_LOGIN_CANCEL_STRIP__` was already set true — nothing ever retries: no listener, no observer, no strip for that document. Separately, the delivery channel itself (hidden iframe to `https://gamelib.invalid/login-cancel`) is only proven on Humble; a login page with a strict `frame-src` CSP can block the iframe load before `on_navigation` ever sees it. In both cases the Esc backstop becomes the *sole* exit from a parent-blocking sheet, contradicting the strip's "primary route" contract (T-34.4.2-33).
**Fix:** Wrap the initial `ensure()` in its own inner try so listener + observer registration always execute; verify the iframe channel once per non-Humble runner (GOG/Amazon) on hardware, or add a `location`-free fallback delivery (e.g. `fetch` to the sentinel URL, also visible to the network layer, also cancelled).

### WR-05: The strip route destroys the window synchronously from inside its own WKWebView navigation-policy callback

**File:** `src-tauri/src/main.rs:3797-3805` (sentinel branch), `src-tauri/src/main.rs:1685-1691` (`request_login_sheet_cancel`)
**Issue:** `on_navigation` runs on the main thread inside `decidePolicyForNavigationAction`. `request_login_sheet_cancel` then runs `endSheet:` inline (tauri-runtime-wry executes `run_on_main_thread` synchronously on the main thread) and `window.close()` — which, also being a main-thread `send_user_message`, tears the window/webview down *while the webview's own delegate callback is still on the stack*, before the closure returns `false` and wry invokes WebKit's decision handler for the now-destroyed webview. The `Destroyed` window-event hook also fires reentrantly inside this frame. Refcounting probably keeps the objects alive long enough, but this is undefined-order teardown inside a WebKit delegate — a latent crash of the same shape as the minimize/restore unresponsiveness class this phase exists to fix.
**Fix:** Defer the close out of the delegate frame: have the sentinel branch schedule `request_login_sheet_cancel` (e.g. `tauri::async_runtime::spawn` or a queued main-thread task) and return `false` immediately.

### WR-06: Autofill debounce-map eviction is arbitrary (not oldest) and refusals arm the debounce

**File:** `src-tauri/src/main.rs:1834-1839` (eviction), `src-tauri/src/main.rs:1821-1840` (order)
**Issue:** `map.keys().next()` on a `HashMap` yields an arbitrary key; the code comments and threat rationale (T-34.4.2-18, "authoritative server-side gate") describe evicting the oldest. At cap, a burst of new labels can evict the *hot* label's timestamp, resetting its rate limit — the exact bypass the server-side gate exists to prevent. Additionally the timestamp is written *before* the `PRESENTED_LOGIN_SHEETS` membership check, so a refused (not-presented) request still consumes the label's 750 ms window and blocks an immediately-following legitimate one.
**Fix:** Track insertion order (e.g. evict by smallest `Instant`, a one-line `min_by_key`), and record the timestamp only after the request passes the membership gate.

### WR-07: `makeKeyAndOrderFront` on a window presented as a sheet is unmeasured and may detach it

**File:** `src-tauri/src/main.rs:1936`
**Issue:** Step 7 of `post_autofill_right_click` calls `window.makeKeyAndOrderFront(None)` on the login window. Spike 022's "menu will not appear on a non-key window" measurement was taken under the *child-window* mechanism; under sheet presentation the sheet is already key by construction, and independently reordering a presented sheet in the window list is exactly the kind of operation that broke attachment classes before (the deminiaturize re-raise history). ### IN-01: `PRESENTED_LOGIN_SHEETS` cap eviction drops a still-presented label without ending its sheet

**File:** `src-tauri/src/main.rs:2768-2770`
**Issue:** At cap (50), `list.remove(0)` evicts the oldest presented label; every later dismissal of that label is membership-gated to a no-op, so its `endSheet:` never runs. Unreachable in practice (1-2 login windows), but the failure mode is the same permanent parent lock-out as WR-01.
**Fix:** Call `dismiss_login_window_sheet`-equivalent teardown on the evicted label, or log loudly when eviction fires.

### IN-02: The cancel strip is focusable but not keyboard-activatable

**File:** `src-tauri/src/main.rs:1627-1629` (`role="button"`, `tabindex="0"`), `src-tauri/src/main.rs:1644-1647` (click-only)
**Issue:** REQ-34.4.2-06 forbids key listeners, so the strip activates on `click` only — yet it advertises `role="button"` + `tabindex="0"`, promising Enter/Space activation it cannot deliver. A keyboard user tabs to a control that does nothing. The Esc backstop covers the function, but the affordance is misleading.
**Fix:** Either drop `tabindex` (leaving it a visual/pointer control) or document in the script comment that Esc is the sanctioned keyboard route.

### IN-03: `is_login_cancel_request` ignores the URL scheme

**File:** `src-tauri/src/main.rs:1565-1567`
**Issue:** Host + path only; any scheme matches. Practically inert (the host is the reserved `gamelib.invalid`, and a hostile page force-cancelling its own window is the accepted T-34.4.2-34 threat), noted for completeness since the sibling sentinel parsers are stricter.
**Fix:** Optionally add `url.scheme() == "https"` for symmetry with the strip's own delivery URL.

### IN-04: The entire automated surface for this phase is source-text assertion — no test can observe presentation ordering or attachment

**File:** `src/backend/__tests__/tauriShellSource.test.ts:829-835`, `src/backend/__tests__/tauriShellSource.test.ts:887-955`, `src-tauri/src/main.rs:6177-6293`
**Issue:** Every Jest gate greps comment-stripped source (call counts, block placement, symbol absence), and every cargo test covers AppKit-free pure helpers (`is_login_cancel_request`, `login_cancel_strip_script`, `css_rect_center_in_view`, `clamp_point_to_view_bounds`). Nothing executes `beginSheet:`/`endSheet:` or observes their effect — which is exactly how cargo 131/131 + jest 3735/3735 stayed green through a 0/6 live gate (fourth instance of the project's "live gate beats a green suite" pattern). This is a known, documented limitation, not a defect in the tests themselves — but CR-02's `attachedSheet()` read-back is the cheapest way to give the *live* gate a trustworthy machine signal.
**Fix:** Land CR-02's read-back; have the rewritten live gate assert on the `attached=` log value, not on `sheet_presented=`.
