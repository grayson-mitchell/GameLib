plan — they are the contract plans 02 and 04 build against.

**(a) `static PRISTINE_LOGIN_WEBVIEWS: Mutex<Option<HashMap<String, usize>>> = Mutex::new(None);`**
placed beside the existing `LOGIN_WINDOW_EVENTS` static and documented in the same style. Maps a
login window label to the address of the raw `WKWebView` that `open_pristine_epic_login_window`
added as a subview. Store `Retained::as_ptr(&webview) as usize` — the address only; the superview
holds the retain, so the entry is valid exactly as long as the window is. Add two helpers beside it:
`register_pristine_login_webview(label: &str, addr: usize)` and
`unregister_pristine_login_webview(label: &str)`, both lock-poison-tolerant (`let Ok(mut guard) =
... else { return; }`, matching `push_login_window_event`'s existing shape). Cap discipline is not
needed here — entries are removed on close — but the unregister MUST be unconditional on the close
path so a closed window can never leave a dangling address behind.

**(b) Wire the registry into `open_pristine_epic_login_window` only.** Inside the existing
`run_on_main_thread` closure, immediately after `ns_view.addSubview(&webview);`, register the
webview address under `main_thread_label`. In the existing `WindowEvent::Destroyed` arm of that same
function, call `unregister_pristine_login_webview(&close_event_label)` alongside the existing
`push_login_window_event(..., login_event_value("closed", ""))` call. Do not change any other
behavior in that function, and do not touch the `monitor_slot` teardown.

**(c) `fn login_window_ns_window(app: &AppHandle, label: &str) -> Option<usize>`** — returns the
`NSWindow` address for `label`, trying `app.get_webview_window(label).and_then(|w| w.ns_window().ok())`
first and falling back to `app.get_window(label).and_then(|w| w.ns_window().ok())` (the pristine
shell is a plain `tauri::Window`, reachable only through `get_window`, which needs the already-enabled
`unstable` feature). Returns the raw address as `usize` rather than a `Retained<NSWindow>` so the
value is `Send` and callers reconstruct it inside their own main-thread closure using this file's
existing `SendPtr` convention — document that explicitly. `None` when neither lookup finds a window;
a missing window is never an error in this file (the `humble_login_close` "already closed is
healthy" convention).

**(d) `fn login_window_wk_webview(app: &AppHandle, label: &str) -> Option<usize>`** — returns the
live `WKWebView` address for `label`. For a Tauri-managed window, use
`app.get_webview_window(label)` then `with_webview(|platform| platform.inner() as usize)` — the
closure runs synchronously inline on macOS (spike 016 Q1, already relied on elsewhere in this file),
so capture the address out through a `Cell`/`Option` in the enclosing scope rather than a channel.
For the pristine window, read `PRISTINE_LOGIN_WEBVIEWS`. Try the Tauri-managed path first, then the
registry. Same `usize`/`SendPtr` rationale as (c), documented.

Both resolvers must be side-effect free and must never log a label's URL or any page content.

Non-macOS: every item above is `#[cfg(target_os = "macos")]`-gated, so Windows and Linux compile and
behave exactly as before (REQ-34.4.2-08). Do not add `#[cfg(not(target_os = "macos"))]` stubs — no

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| remote login page → login WebviewWindow/WKWebView | Untrusted third-party HTML/JS renders inside a window this process owns. |
| login window → Rust shell | Only established channel is the 34.4.1 seam (`dispatch_rust_channel` arms + the `LOGIN_WINDOW_EVENTS` queue). This plan adds a second in-process map keyed by a shell-generated label. |
| Rust shell → AppKit | Raw pointers to `NSWindow`/`WKWebView` cross a `run_on_main_thread` boundary. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-34.4.2-01 | Tampering | `PRISTINE_LOGIN_WEBVIEWS` keys | mitigate | Keys are ONLY ever `next_login_window_label()` output — never page-derived, never a URL fragment. Registration happens inside `open_pristine_epic_login_window`'s own main-thread closure using its own `main_thread_label`; no external writer exists. |
| T-34.4.2-02 | Denial of service | stale/dangling `WKWebView` address | mitigate | `unregister_pristine_login_webview` is called unconditionally from the existing `WindowEvent::Destroyed` arm, and Test 3 asserts that call site. The address is only ever reconstructed inside a main-thread closure, matching this file's existing `SendPtr` safety argument. |
| T-34.4.2-03 | Information disclosure | resolver logging | mitigate | Both resolvers are side-effect free and log nothing — no label URL, no page title, no page content (the T-34.4.1-21/T-28-04 convention this file already enforces). |
| T-34.4.2-04 | Spoofing | window lookup by label | accept | `login_window_ns_window`/`login_window_wk_webview` resolve only labels this process minted. A caller passing an attacker-chosen label is not reachable: no seam channel added by this phase forwards a caller-supplied label into these resolvers without first matching it against a live login window. |
| T-34.4.2-SC | Tampering | dependency surface | mitigate | This plan installs NOTHING: no npm, no pip, no cargo add. `src-tauri/Cargo.toml` must be byte-identical after the task (asserted). `Cargo.lock`'s `EXPECTED_LOCKFILE_CRATE_NAMES` pin in `cargoFeatures.test.ts` is therefore untouched. No Package Legitimacy Gate applies to this phase. |
