## Preconditions

Each precondition states who satisfies it: **operator-at-gate-time**, or **already-evidenced** (by
a prior plan's own recorded, source-verified work).

1. **macOS hardware, `npm run tauri:dev` (dev build).** Operator-at-gate-time. `tauri:dev` only
   rebuilds the SIDECAR on launch (`electron-vite build && pnpm build:sidecar && tauri dev`) — the
   Rust shell itself is rebuilt by `tauri dev`'s own `cargo build` step, so a genuinely fresh
   binary is expected, but confirm the new symbols are present in the built artifact before
   trusting any negative (grep the compiled binary or the build log for a string literal this
   phase introduced, e.g. `AUTOFILL_EXFIL_PATH`'s value `/autofill-request`, if any negative result
   looks surprising).
2. **The DummyStore harness running**, operator-at-gate-time:
   ```
   node .claude/skills/spike-findings-gamelib/sources/019-dummy-oauth-store/store-server.mjs
   ```
   Liveness-confirmed by `curl -s http://127.0.0.1:17940/events`. **Port 17940 must be free
   first** — a leftover instance from a prior session produces confusing "unreachable" states;
   check with `lsof -i :17940` before starting a new one.
3. **A seeded Passwords-app entry for the test origin.** Operator-at-gate-time, done BEFORE item 3.
   **Without it the AutoFill panel has nothing to offer and a negative on item 3 is
   uninterpretable.** This is the single most commonly-missed precondition in this area — stated in
   bold deliberately.
4. **Logout preamble + `/events` baseline taken AFTER it.** Operator-at-gate-time, before item 3(a).
   The login-window cookie jar persists across app restarts (the sticky-jar trap), so a second run
   silently skips the login form and any "the form was served" assertion fails for the wrong
   reason. Navigate a login window to `http://127.0.0.1:17940/logout` first, THEN read
   `/events` for the baseline count.
5. **A real store login available for item 3(b).** Operator-at-gate-time. Humble is the surface
   with the most proven path (34.4.1's own gate closed a genuine Humble login end-to-end).
6. **`GAMELIB_AUTOFILL_GLYPH` unset for the default arm.** Operator-at-gate-time, for items 1-4 and
   6. Item 5 deliberately runs the `=0` arm in the SAME binary as a second observation, not a
   separate build.

### Item 1 — Child-window attachment (REQ-34.4.2-01/02/03)

**What to do.** With a Humble/GOG/Amazon login window open and attached, perform each of the
following four actions in order, observing after each:

(a) Click the main window while the login window is open (do not close it).
(b) Drag the main window to a new screen position.
(c) Minimize the main window (into the Dock).
(d) Restore the main window from the Dock.

**PASS condition for each sub-check:**
- (a) The login window **stays in front** of the main window (does not go behind).
- (b) The login window **follows** the main window's drag.
- (c) The login window **follows the main window into the Dock** (does not stay orphaned on
  screen).
- (d) The login window is **in front** immediately upon restore, not behind. This is the
  sub-check the deminiaturize re-raise observer exists for, and the one that fails without it
  (spike 021's measured defect).

**PASS = all four sub-checks observed as above.**

**Log lines to capture** (from `gamelib.log`, via the sidecar's own logging):
```
[shell] humble_login_open: presentation requested visible=true width=900 height=700 center=true focus_once=true persistent_pin=false light_theme_requested=true child_attached={true|false}
```
`child_attached` must read `true` for a visible login window — record it explicitly. On restore
(sub-check d), also check for:
```
[shell] login-window: parent deminiaturized, re-raising {N} attached child window(s)
```
where `N` should be at least 1.

### Item 3 — The glyph and the AutoFill menu (REQ-34.4.2-04/05)

**What to do — two sub-items, both on Tauri-managed login windows. Epic is NOT part of this item**
(it is out of scope by locked user decision, REQ-34.4.2-10, and receives no glyph — see item 6(b)
for the only Epic-touching check in this whole gate).

(a) On the DummyStore `/login` form (precondition 2), in a Tauri-managed login window: locate the
key glyph inside the password field. Click it. Observe whether the real system context menu pops.
Check whether the menu contains `AutoFill ›`. Choose AutoFill → Passwords (precondition 3's seeded
entry). Observe whether the field fills.

(b) Repeat the same sequence on a real store login page (Humble, per precondition 5).

**PASS condition, per sub-item:** glyph visible AND menu popped AND `AutoFill ›` present AND field
filled. **PASS = both (a) and (b) satisfy this.**

**Instructions the operator must follow — written into this item, not assumed knowledge:**

- **Compare against a REAL right-click on the same field before concluding anything from a
  negative.** A real click yields the 3-item secure-field menu (Cut/Copy/Paste); a synthesized one
  yields the 10-item generic text menu. A synthesized-event negative is not evidence on its own —
  it may mean the synthesis reached the wrong element, not that autofill is broken.
- **To photograph the menu, region-grab the owning window's rect**: `/usr/sbin/screencapture -x -o
  -R<x,y,w,h>`. **`screencapture -l<windowID>` MISSES menus** — menus are their own windows, not
  part of the parent window's captured content. Do not use a wider region; it sweeps in unrelated
  windows on the operator's desktop.
- **Record the `[shell]` log line's `hit_id`/`hit_tag`/`hit_type`.** Expected shape:
  `{id:'password', type:'password'}`-like. If these do not match, the coordinate conversion aimed
  at the wrong element and **the item FAILS regardless of what menu appeared** — a menu popping on
  the wrong element is not a pass.
- **Expected UX cost, so it is not misfiled as a defect**: the AutoFill panel does not auto-match
  the current site, and its search box rejects typed input (it beeps — system behaviour,
  reproduced in both the DummyStore and Humble surfaces per spike 022). The user scrolls, then
  clicks the entry to fill. This is a platform limitation, not this phase's bug.

**Log lines to capture** (the poster's exactly-one success line, or a distinct refusal line):
```
[shell] humble_login_open: autofill glyph injected for '{label}'
```
and the poster's own success line (name/format per `post_autofill_right_click`'s own logging
discipline — label, four coordinates, `hit_*` fields).

### Item 5 — Kill-switch efficacy (T-34.4.2-15, REQ-34.4.2-04)

**What to do.** Open a Humble login window TWICE in one sitting, from the SAME running binary:
first with `GAMELIB_AUTOFILL_GLYPH` unset, then with `GAMELIB_AUTOFILL_GLYPH=0` (this requires
relaunching `tauri:dev` with the env var set for the second arm, since it is read once per process
start — record that this was a relaunch, not a live toggle).

**PASS condition.**
- **Arm 1 (unset):** the glyph is present in the password field, AND the login completes normally.
- **Arm 2 (`=0`):** **no glyph is injected**, AND the login STILL completes normally (Cmd+V/menu
  bar paste remain the fallback, per item 4).

**PASS = both arms observed as above.** This is the escape hatch a user needs if injection ever
trips a store's bot management and locks them out of their own library (T-34.4.2-15) — an untested
escape hatch is not one.

**Log lines to capture — one per arm, and they must DIFFER:**
```
[shell] humble_login_open: autofill glyph injected for '{label}'                                    <- arm 1 (unset)
[shell] humble_login_open: autofill glyph injection SKIPPED for '{label}' (kill switch set to 0)     <- arm 2 (=0)
```
**If this line is identical in both arms, the switch is not wired and the item FAILS regardless of
what the UI showed.**
