### Finding: the autofill glyph is injected on every platform, not gated to macOS

`autofill_glyph_script`'s call site (main.rs:3472-3480, inside `humble_login_open`'s `if visible`
block) carries **no `#[cfg(target_os = "macos")]` guard**. Neither does `parse_autofill_request`'s
call site in the `.on_navigation(` sentinel (main.rs:3585). This is a genuine, source-verified
cross-platform behaviour, not an assumption:

- **On Windows and Linux, the key glyph renders in every password field** of a visible Tauri-managed
  login window, identically to macOS (Plan 03 summary: "the glyph is not platform-gated (plan 03
  injects it everywhere visible)").
- **Clicking it does nothing observable.** The click still triggers the cancelled-navigation sentinel,
  `parse_autofill_request` still parses the payload successfully (it is platform-agnostic), but
  `post_autofill_right_click` — the only function that produces any visible effect — is
  `#[cfg(target_os = "macos")]`-gated. The `#[cfg(not(target_os = "macos"))]` arm at
  main.rs:3588-3591 silently discards the request and returns `false` (still cancelling the
  navigation), producing **no error, no log line distinguishing this from the macOS success path,
  and no visible feedback to the user** beyond nothing happening.

**This is not a defect this plan fixes** — no Windows/Linux poster exists yet, and building one is
out of this phase's scope entirely (the skill's own Constraints section: "Windows (WebView2) and
Linux (webkit2gtk) autofill and window-attachment behaviour are entirely unverified"). It is
recorded here because REQ-34.4.2-08's own text asserts "all new behaviour is
`#[cfg(target_os = "macos")]`-gated" and that assertion is **not literally true** for these two pure
helpers and their call sites — only the poster half of the feature is macOS-gated, not the
glyph-injection half. Filed as a UX-relevant finding for whoever next touches Windows/Linux support:
an inert, unlabelled key icon in every password field is a worse experience than no icon at all, and
should be gated before this phase's work is ever exercised on those platforms.

## 2. What is UNVERIFIED off macOS, and why that is acceptable

Quoting the skill reference directly (`login-window-ux-macos.md` § Constraints):

> **macOS 26 only.** Windows (WebView2) and Linux (webkit2gtk) autofill and window-attachment
> behaviour are entirely unverified, as with spikes 013–018.

No Windows or Linux hardware ran anything in this phase — plans 01-04 built exclusively against
`#[cfg(target_os = "macos")]`-gated AppKit/WebKit primitives (`objc2-app-kit`, `NSEvent`,
`NSWindow`), all of which are unavailable and untested on WebView2 (Windows) or webkit2gtk (Linux).
The correct future action for either platform is **re-measurement, not extrapolation** from this
phase's macOS results: WebView2 and webkit2gtk are separate `wry` backend implementations with their
own cookie, event-injection and window-chrome semantics, not thin ports of the WebKit backend this
phase actually exercised. This project has direct precedent for why extrapolation across `wry`
backends is unsafe: the `cookies_for_url()` defect (`tauri-cookies-for-url-drops-cookies` memory
entry) was a macOS-specific string-`==` domain-compare bug in `wry`'s own cookie code — a defect
that tells you nothing about whether the Windows/Linux cookie path has an analogous or entirely
different problem. The same caution applies here: a passing macOS live gate (plan 06) proves
nothing about Windows or Linux, and this document does not claim otherwise.

## 3. EPIC-DEFERRED

- **Decision (2026-08-04, user, LOCKED):** Epic is implemented LAST, after all other
  accounts/runners are ported successfully. Epic is removed from Phase 34.4.2 entirely.
- **Why:** Epic's problems are unresolved — the parked deterministic pre-auth 403 (anti-bot), the
  zero-injection constraint the pristine `WKWebView` surface exists specifically to satisfy, and the
  standing hCaptcha/UA constraint. The user chose to leave it alone until those are resolved.
- **What was consequently NOT built** (each item names the plan that would have built it):
  - The child-window attachment arm for the pristine surface (plan 02 — `attach_login_window_as_child`
    is never called from `open_pristine_epic_login_window`).
  - The `WKUserScript` glyph injection and its `WKUserContentController`/`WKUserScript`/
    `WKUserScriptInjectionTime` `objc2-web-kit` features (plan 03 — `tauriShellSource.test.ts`
    permanently bans all three as a negative test).
  - The sentinel arm in `EpicPristineNavDelegate::navigation_policy` (plan 03 — the pristine
    delegate's sliced body is asserted to reference none of `PHASE_34_4_2_NEW_SYMBOLS`).
  - The `post_autofill_right_click` call site for that arm (plan 04 — same scope guard, extended).
  - The `login_window_ns_window` `get_window` fallback that would make the pristine window resolvable
    at all (plan 01 — deliberately omitted, not merely unused: "an unused branch that resolves it is
    still a code path that does").
  - The Epic injection A/B gate item (plan 05, replaced by a kill-switch efficacy item — see
    `34.4.2-LIVE-GATE.md` item 5).
- **What IS still true for Epic:** its login window keeps working exactly as it does today. This
  phase changed nothing about it — REQ-34.4.2-10, enforced by `PHASE_34_4_2_NEW_SYMBOLS` (source
  assertion) and a zero-line-diff requirement on `open_pristine_epic_login_window` and
  `EpicPristineNavDelegate`, confirmed by `git diff --unified=0` in every one of plans 01-04's own
  commits (recorded in each plan's own SUMMARY).
- **Follow-up:** Epic's login-window UX gets its own phase after all other runners are ported and
  proven. That future phase inherits the attach/detach pair, the glyph script builder, the pure
  parser, and the poster — all runner-agnostic and already built. The Epic phase adds call sites and
  the `get_window` fallback, not a redesign.

See `deferred-items.md`'s first entry for the phase-local ledger record of this same decision,
cross-referenced rather than duplicated.
