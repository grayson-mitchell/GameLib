### Item 1 — Sheet presentation and survival of the minimize/restore cycle (REQ-34.4.2-01/02)

**Attachment itself is ALREADY PROVEN and is NOT being re-measured by this item.** The three-round
debug arc (`white-window-not-sheet-cr01.md`) closed the ATTACHMENT sub-mechanism live, on real
macOS hardware, with a falsifiable signal (`attached=true` from the CR-02 read-back, logged
AFTER `beginSheet_completionHandler` returned -- not the unfalsifiable `sheet_presented=true`
CR-02 itself replaced). This item's job is everything ELSE about item 1 that debug arc did not
drive: un-losability, moves-with-parent, follows-into-Dock, and -- the item's own original
reason for existing -- staying INTERACTIVE through minimize/restore.

**What to do.** With a Humble/GOG/Amazon login sheet presented, perform in order:

(a) Click the main window while the login sheet is open (do not dismiss it).
(b) Drag the main window to a new screen position.
(c) Minimize the main window (into the Dock).
(d) Restore the main window from the Dock.
(e) **Immediately after the restore, type into the password field, then activate the cancel
strip.**
(f) **NEW, WR-07 regression check.** After clicking the autofill glyph at least once (item 3's
action), re-run sub-check (a): the sheet must still be un-losable. A first glyph click
converting the sheet back into a free-floating window is exactly the mid-session detachment
WR-07 exists to prevent.

**PASS condition for each sub-check:**
- (a) The sheet **stays in front** of the main window and the main window **does not** come over
  it. Note explicitly: **a sheet BLOCKS its parent by AppKit design** -- the main window declining
  clicks while the sheet is up is correct sheet semantics and is **NOT** a failure. Only a sheet
  going BEHIND the main window, or the main window accepting input while the sheet is presented,
  would be a failure here.
- (b) The sheet **moves with** the main window's drag (a sheet is attached to its parent's frame).
- (c) The sheet **follows the parent into the Dock** -- it does not stay orphaned on screen.
- (d) The sheet is **visible and in front** immediately upon restore, not behind and not
  disappeared.
- (e) **Typed characters appear in the password field AND the cancel strip responds** (dismisses
  the sheet when activated). **This sub-check is the whole reason this item exists** -- it is
  F-34.4.2-01 (the child window's post-restore unresponsive state) turned directly into a PASS
  condition for the sheet mechanism. A sheet that types but cannot be dismissed, or dismisses but
  will not accept typed input, both FAIL this sub-check.
- (f) After at least one autofill-glyph right-click, sub-check (a) still holds -- the sheet is
  still un-losable, has not reverted to a free-floating window. Record which WR-07 branch ran
  (see item 3's own log-line capture) alongside this re-check.

**PASS = all six sub-checks (a)-(f) observed as above.**

**Log lines to capture** (from the captured `tauri:dev` transcript per the Evidence-capture
instruction above), verbatim shape:

§1-2 for the full per-symbol cfg-gate table and the standing finding that the autofill glyph itself
is **not** platform-gated even though the poster is. The cancel strip IS macOS-gated
(`#[cfg(target_os = "macos")]` on its injection call site) while the glyph's own call site is not
-- so on a future Windows/Linux run the glyph would render inertly while the strip would not
render at all, per plan 08's own SUMMARY. Windows/Linux remain entirely unverified by this gate,
on this hardware, by design.
