# Phase 53: Steam bridge coverage: modern-SDK exports, flat API - Context

**Gathered:** 2026-10-25
**Status:** Ready for planning

<domain>
## Phase Boundary

Engine-wrapper titles on the native Steam bridge get Steam initialised **inside the game**, under
phase 51's strict criterion (see D-53-13 for the per-engine evidence rule). Two defect classes:

1. **Modern-SDK `SteamInternal_*` family.** The five x64 exports already shipped in quick
   261024-i94 (confirmed by 52-07) and are taken as given. Remaining work: re-test Hell Clock
   1782460, Mining Mechs 1603180, Overlooting 3410180, Ranch Simulator 1119730 (and Colony Ship
   648410), fix whatever each hits after `SteamInternal_SteamAPI_Init` returns OK, and x86 parity
   **only if measured to matter** (D-53-09).
2. **The Steamworks flat C API** (`SteamAPI_ISteamClient_*`, `SteamAPI_ISteamUser_*`,
   `SteamAPI_ISteamUtils_*`, … and the `SteamAPI_SteamX_v0NN()` accessors) for Unity +
   Steamworks.NET: Vampire's Fall 1167950, The Planet Crafter 1284190, Rogue Waters 1691190 (hangs
   at loading on `IsSteamRunningOnSteamDeck`). Generated from the same interface manifests as the
   vtable proxies, plus a managed-assembly DllImport scan so verdicts and the census are honest.

Folded in by this discussion: the UE5 interface-versions todo (whole), the AnyCPU-arch step of the
old-SDK todo, and the census-UE-layout todo (via D-53-12).

**Roadmap correction:** the roadmap lists the Unreal bootstrap-exe scan miss as out of scope and
masking Ranch Simulator. That todo is already **closed** (quick 261024-ir1, now in
`todos/completed/`). Ranch Simulator is now gated by the j4l guard and missing interface versions,
both handled here via the folded UE5 todo.

Out of scope, unchanged: SteamStub forwarder / Grim Dawn main menu (Phase 52, deferred to
`2026-10-24-steamstub-launch-check-static-re-decision.md`), bottle Windows runtime components
(`2026-10-24-bridge-bottles-lack-windows-runtime-components-games-need.md`).

<decisions>
## Implementation Decisions

### Flat-API breadth
- **D-53-01:** **Export every method** of every manifest'd interface version as a flat
  `SteamAPI_ISteamX_Method` export, generated by `meta/gen_vtables.ts` from `meta/sdk/*.manifest.json`.
  A missing export is fatal (`EntryPointNotFoundException`), while an extra one is harmless, which is
  the existing R3 superset policy. No "measured union only" or minimum slice.
- **D-53-02:** **Flat-API generations are chosen by census.** Research reads DllImport entry
  points across the owned Unity library and targets every Steamworks.NET generation that appears
  (at least the pre-1.48 `SteamAPI_ISteamClient_GetISteamUser` style seen in Vampire's Fall and the
  1.58+ `SteamAPI_SteamUser_v023`-style accessors behind Hell Clock's `InitEx`). Nothing is fixed
  ahead of the measurement.
- **D-53-03:** **The new interface versions are added as manifests that serve both the vtable and the
  flat path** (D-09 still holds: GameLib-authored manifests, never vendored Valve header text). Each new
  version is checked slot by slot against its SDK generation, never aliased from a neighbour.
- **D-53-04:** **Managed scan: Mono now, IL2CPP flagged.** Parse the ImplMap/DllImport tables of
  `<Game>_Data/Managed/*.dll` (e.g. `com.rlabrecque.steamworks.net.dll`, `Assembly-CSharp.dll`)
  and merge their `steam_api*` entry points into the required set. IL2CPP titles (no Managed dir)
  keep `@runtime-loaded` with an explicit "il2cpp: not scanned" reason. No second parser for
  `global-metadata.dat` / `GameAssembly.dll` this phase.
  **Amended 2026-10-25 (plan-phase, user decision):** only lifecycle names and names in families the
  shim serves join the required set. Managed imports from unserved families (UGC, Input,
  Inventory, NetworkingSockets, …; ~480 of ~880 in the owned Unity sample) are reported as a count
  that does not change the coverage class. A literal merge would make every Unity title `miss`
  forever. No generic zero stubs for unserved names.

### Unmarshaled methods
- **D-53-05:** **A flat export calls the proxy object's own vtable slot.** Flat and vtable behaviour
  are identical: forwarded where `meta/sdk/wire-policy.json` says so, the slot's stub otherwise.
  One source of truth, no separate flat-only stub table.
- **D-53-06:** **Wrong zeros are fixed when measured, not audited up front.** Stubs stay at their
  default. When a sampled title's log traces a hang or crash to one method, that method is
  forwarded to the helper's real Steam answer, or given a local constant only where Steam's real
  value is a constant on this platform (e.g. `ISteamUtils::IsSteamRunningOnSteamDeck` → false on a
  Mac, the Rogue Waters case). Same evidence-driven loop as scan-miss widening (D-51-05 amendment).
  **Amended 2026-10-25 (plan-phase, user decision):** the Steamworks.NET lifecycle names ship up
  front as x64 safe no-op exports rather than waiting for live evidence: the
  `SteamAPI_ManualDispatch_*` family (`GetNextCallback` and `GetAPICallResult` answer false),
  `SteamAPI_ReleaseCurrentThreadMemory`, `SteamAPI_SetBreakpadAppID`, and the other lifecycle
  names research Open Question 4 / L309 lists that the owned Unity census imports. Being exported,
  they are covered: none of them makes a title `missing-symbols`. This resolves research Open
  Question 4 against its "only if live logs show a fault" recommendation. The measured-then-fixed
  rule above still governs interface-method stubs.
- **D-53-07:** **An unknown interface version requested through a flat accessor or flat
  `GetISteamX(..., version)` returns NULL and logs the version.** Steamworks.NET's context init
  checks `IntPtr.Zero`, so `SteamAPI.Init` returns false and the game plays offline with an honest
  init failure in its own log. The logged version names what to add next.
- **D-53-08:** **The x64 vtable path keeps its null-object fallback**
  (`SteamInternal_CreateInterface`, `FindOrCreate*`, bare `GetISteam*`). The NULL rule is for flat
  entry points only, because changing the vtable path would reopen CR-01 (restored by 52-14).
  Revisit only if a sampled title's crash is traced to the null object, as hypothesised for
  Manor Lords' 0x0 read.

### x86 parity
- **D-53-09:** **Measure, then decide** (the D-51-13 pattern). Research counts owned titles whose
  *launch* arch is x86 and that need the modern `SteamInternal_*` family or the flat API. If any
  exist, the planner includes x86 parity: `CreateInterface`, a fallback object, the five
  `SteamInternal_*` exports, and flat exports through a `__thiscall` call into the proxy vtable. If
  none exist, x86 is deferred with the count attached. Neither outcome is assumed.
- **D-53-10:** **AnyCPU .NET exes without CLR `32BITREQUIRED` are treated as x64** for coverage and
  placement (step 3 of the old-SDK todo). This is folded because it skews the x86 count D-53-09
  relies on. The rest of that todo (12 legacy CSteamworks exports, 14 old interface versions, one
  known title) stays pending.
  **Amended 2026-10-25 (plan-phase, user decision):** `32BITPREFERRED` (0x20000) also keeps an
  AnyCPU exe x86. An exe is x64 only when neither `32BITREQUIRED` nor `32BITPREFERRED` is set.

### Acceptance & evidence
- **D-53-11:** **The whole UE5 interface-versions todo is folded:** add the x64 versions still missing
  (Friends017, Utils010, UserStats012, Input006, GameServer015, GameServerStats001; User023,
  RemoteStorage016 and Networking006 already landed in 52-13), export x64
  `SteamInternal_GameServer_Init` failing like `_V2`, and lift the 261024-j4l guard for 1363080,
  427410 and 1119730 **only once the coverage scan reports them clean**.
- **D-53-12:** **The census shares the runtime scan.** `meta/bridgeCensus.ts` calls the same scan
  code `shimGenerate.ts` uses (importer-PE walk from i94, UE stub-plus-Shipping layout from ir1,
  Mono DllImports from D-53-04, AnyCPU arch from D-53-10) instead of keeping parallel logic. This
  folds `2026-10-24-bridge-census-misses-unreal-layout-steam-api.md`. The census can then never
  drift from what install does.
- **D-53-13:** **Per-engine evidence plus a bridge trace.** Research names each engine's own log
  and the census reads it: Unity `Player.log`, UE `Saved/Logs/*.log`, Godot `user://logs/godot.log`,
  GameMaker runner/extension output. Where an engine logs nothing about Steam init, a
  **game-originated** bridge call beyond init (e.g. `GetSteamID` / `GetPersonaName` arriving from
  the game process, recorded in gamelib.log) counts as the clean-init evidence. `HELLO` is still
  required. A helper-originated call never counts, and Mac Steam In-Game never counts. This
  *extends* the strict criterion for non-Unity engines; it does not relax it for Unity.
- **D-53-14:** **Sample = the roadmap's seven + Manor Lords 1363080 + Abiotic Factor 427410**,
  inside the full 51-29 re-run sample. "Majority" is counted over **all Steamworks-using rows**.
  Titles held back by out-of-phase defects (Grim Dawn SteamStub, bottle runtime components) **stay
  in the denominator** and are reported with their class, never dropped.

<code_context>
## Existing Code Insights

### Reusable Assets
- `meta/gen_vtables.ts`: `generateShimC()`, `emitVtableStub()`, `emitDispatchCase()`,
  `generateDefFile()`. The flat exports are new emitters beside these, driven by the same manifests.
- `native/steam-bridge/generated/steam_api_shim.c`: `resolve_iface_by_exact_version()`,
  `resolve_bare_iface()`, `SteamInternal_CreateInterface()`, `GameLibBridge_CreateInterface()`,
  `bridge_transact()`, and the x64 null object (`g_x64_null_object_instance`). Flat accessors should
  resolve through the exact-version lookup but return NULL on a miss (D-53-07).
- `src/backend/storeManagers/steam/bridge/shimCoverage.ts`: `SHIM64_SERVED_INTERFACE_VERSIONS`
  and the exported-symbol sets that coverage verdicts are judged against.
- `src/backend/storeManagers/steam/bridge/importScan.ts`, `importParse.ts`, `peSections.ts`:
  PE import parsing; `readPeMachineArch` (i94). The CLR header flag read for D-53-10 belongs here.
- `src/backend/storeManagers/steam/bridge/shimGenerate.ts`: the importer-PE walk (depth 4 / 512
  files, no symlinks) and the UE layout, which are the pieces D-53-12 lifts into a shared module.
- `meta/bridgeCensus.ts`: `classifyBridgeEvidence()` (f0w) already reads `HELLO` + Unity
  `Player.log`, and D-53-13 extends it per engine.

### Established Patterns
- Generated shim source and `.def` files are **committed**, `pnpm gen-vtables` must be idempotent,
  and the PE is only built at packaging time (`pnpm build-steam-bridge`, zig cc).
- Pinned tests: `meta/__tests__/gen_vtables.test.ts`, `meta/__tests__/shimAbiGate.test.ts`,
  `shimCoverage.test.ts`, `importScan.test.ts`, `bridgeCensus.test.ts`. The i94 tests pin the
  null-object fallback for FindOrCreate*, and D-53-08 keeps them valid.
- Persisted verdicts store missing symbols plus the shim export-set version (D-51-07). Widening the
  export set clears stale verdicts automatically on next install/launch.

### Integration Points
- The new manifests feed the vtable proxies, flat exports and `SHIM64_SERVED_INTERFACE_VERSIONS`
  together.
- The j4l guard (`shimGenerate.ts` / `shimCoverage.ts` / `importScan.ts`) is the gate for lifting
  UE titles (D-53-11).
- Live verification is operator-run on the Mac. Restart `tauri dev` first, since it does not rebuild
  the sidecar (check `sidecar.js` mtime).
