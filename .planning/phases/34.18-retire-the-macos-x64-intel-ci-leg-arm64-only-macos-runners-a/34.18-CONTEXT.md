# Phase 34.18: Retire the macOS x64 (Intel) CI leg — Context

**Gathered:** 2026-08-27
**Status:** Ready for planning
**Source:** `/gsd-discuss-phase 34.18` (interactive, 4 areas)

<domain>
## Phase Boundary

Make GameLib's macOS support **arm64-only** across CI, packaging, the digest manifest and the
build guards; remove the runtime Intel-Mac branch; dispose of the requirements, findings and
ledger items the two-architecture assumption left open; and state the Intel drop where a user
will encounter it.

Phase 34.16 closed PARTIAL on 2026-08-27 with its x64 half proven unachievable (`F-34.16-G`:
`macos-13` was retired by GitHub 2025-12-04 and the leg was never assigned a runner on any of
three attempts). **This phase acts on that verdict rather than retrying it.**

**Not in this phase:** retrying, migrating to `macos-15-intel`, or otherwise preserving any x64
macOS capability. That question was answered by the operator on 2026-08-27 and is closed.

</domain>

<decisions>
## Implementation Decisions

### Intel-drop disclosure (the ROADMAP's named non-negotiable)

- **D-01:** `README.md` § `## Supported Operating Systems` is the ONLY required surface.
  The line to amend is `README.md:82`, currently `- macOS 14 or newer`. In-app Settings,
  `CONTRIBUTING.md` and `CHANGELOG.md` are explicitly **not** required.
  Two facts drove this: an Intel user cannot run an arm64 build at all, so an in-app notice
  reaches nobody who needs it; and `CHANGELOG.md` is stale **upstream Heroic** content (top
  entry `## 2.2.6 Oden - Hotfix 5`), not a live GameLib surface.

- **D-02:** The verbatim string `GameLib will not support Intel Macs on macOS` must appear.
  Not a paraphrase. This is deliberate: a grep can assert it, which makes the disclosure
  requirement mechanically verifiable instead of a human judgement call. Planner must write the
  gate as a literal-string assertion and red-proof it against the pre-fix README.

- **D-03:** Fact only — no rationale in user-facing text. Do not cite GitHub's Fall 2027 x86_64
  EOL, `macos-13`'s retirement, or `F-34.16-G` in the README. The runner situation is the
  project's problem, not the reader's. Rationale belongs in the phase record and the commit body.

### Digest manifest and the pin tool

- **D-04:** `meta/pinRunnerDigests.ts` and `meta/__tests__/pinRunnerDigests.test.ts` are scope
  consumer 7 — added to the ROADMAP's list of six. **Discovered during this discussion, and
  the ROADMAP does not mention it.** The tool is hard-wired to two arches: it fetches
  `SHA256SUMS-x64` *and* `SHA256SUMS-arm64`, requires both `BUILD-MANIFEST-{arch}.json` files to
  carry a non-null and **equal** `runId`, and validates that all **six** tracked digest keys are
  covered. Because the x64 leg never ran, `SHA256SUMS-x64` does not exist in the release, so
  `pnpm pin:runner-digests` is **un-runnable today** and stays that way until it is retired to
  one arch. Leaving it two-arch is precisely the half-retired state the ROADMAP warns is "worse
  than none".

- **D-05:** Executor stops at code-ready; the developer performs the remote gestures.
  All six digest slots in `meta/runnersOnedirDigests.json` are currently `PENDING-CI-PUBLISH`,
  **including the three arm64 ones**, and `downloadOnedirAsset()` throws on a sentinel
  (`meta/downloadHelperBinaries.ts:173-180`) — which is why the post-checkout hook has been
  throwing. Retiring x64 alone does **not** fix that. So:
  - the executor retires everything to one arch and leaves three arm64 sentinels;
  - a **blocking `checkpoint:human-verify`** hands the developer the workflow dispatch and
    `pnpm pin:runner-digests`, honouring 34.16's D-03 (remote gestures are the developer's);
  - **the phase does not close on sentinels.** It closes with real arm64 digests and a working
    `pnpm download-helper-binaries` on darwin.

- **D-06:** Rewrite the sentinel error message at `meta/downloadHelperBinaries.ts:174`. It still
  reads "plan 34.9-09 must fill it in" — a plan reference two phases stale. It is the single
  most-read piece of prose in this cluster, because it is what a developer hits when the
  post-checkout hook throws. Must name 34.18 and the current procedure.

### Census boundary — which `x64` is in scope

- **D-07:** Only "macOS build/packaging arch" retires. `x64` is overloaded in this repo four
  ways and the other three are **explicit non-goals**:

  | Category | Landmarks | In scope |
  |---|---|---|
  | macOS build arch | runner-workflow matrix leg; `*_macOS_x86_64_onedir.tar.gz` keys (5 files); `--x64` in `dist:mac`/`release:mac`; `--arch=x64` guard calls; `build-base.yml`'s `macos-15` leg | **YES** |
  | win32 helper path key | `build/bin/x64/win32/*.exe` — 7 refs in `electron-builder.yml`, **including inside the `mac:` files block** | NO |
  | linux/windows download keys | `legendary_linux_x64`, `gogdl_windows_x86_64.exe` etc. — 6 in `meta/downloadHelperBinaries.ts` | NO |
  | runtime x64 fallback | `src/backend/utils.ts:553` — existence-checked box64 affordance for Linux ARM | NO |

  **Consequence for any verifier: a bare `x64` grep hit is NOT evidence of an incomplete sweep.**
  The macOS package legitimately bundles win32 x64 helpers under an `x64` path key.

- **D-08:** The boundary is enforced two ways, not one — the non-goals table above **and** a
  survivor test pinning that the three non-goal categories still exist (7 `electron-builder.yml`
  refs, 6 download keys, the `utils.ts:553` fallback). This project's record is that a sweep
  audited only for *under*-reach misses *over*-reach entirely; the survivor test is the
  other direction.

- **D-09:** Fix EVERY upload glob in `.github/workflows/build-base.yml`, not only the macOS ones.
  `electron-builder.yml:2` sets `productName: GameLib`, but the upload globs read
  `dist/Heroic*x64.dmg`, `dist/Heroic*arm64.dmg`, `dist/Heroic*.exe` and
  `dist/Heroic*x86_64.AppImage`, under `if-no-files-found: error` — so they match nothing today
  on **every** platform.
  ⚠ **Operator decision, overriding the recommendation.** The recommendation was to fix only the
  macOS globs (the lines already being edited) and defer Windows/Linux to their own owner. The
  operator chose the whole file. **Attribution caveat to carry into the plan:** Windows and Linux
  CI changes now ride inside a macOS-arch retirement, so if `build-base.yml` breaks, the phase
  boundary will not tell you which half did it. The planner should isolate the non-macOS glob
  fixes into their own task and commit so they can be reverted independently.

### Runtime Intel handling

- **D-10:** Remove `isIntelMac` completely — constant, IPC channel, types, preload and frontend
  mirror. ⚠ **This widens the phase beyond the ROADMAP's stated CI/build scope, and is an IPC
  re-plumb rather than a cleanup.** That was raised and the operator confirmed. Surface measured
  during discussion: **15 source files, ~28 sites, plus ~12 test files** —
  `src/backend/constants/environment.ts:30`; the `isIntelMac` handler registered in **both**
  `src/backend/utils/ipc_handler.ts:32` and `src/backend/sidecar/appShellFlowRegistration.ts:214`;
  `src/common/types/ipc.ts:568`; `src/preload/api/misc.ts:272`; `src/frontend/types.ts:45`,
  `state/ContextProvider.tsx:55`, `state/GlobalState.tsx:121,314,1523`,
  `screens/WineManager/index.tsx:37,61`; `src/backend/main.ts:233`,
  `src/backend/utils.ts:999,1369`, `src/backend/launcher.ts:1370`,
  `src/backend/tools/index.ts:637`, `src/backend/tools/dxmt.ts:135,142,149`.
  Justification: an arm64-only build cannot run on an Intel Mac, so the constant is permanently
  `false` in every shipped build — the code would otherwise claim a capability we do not ship.

- **D-11:** Simplify the two branches `isIntelMac` gates. `src/backend/utils.ts:999`
  (`isIntelMac || !isMacOSUpToDate` → Wine-Crossover vs GPTK) collapses to the Sonoma check
  alone; `src/backend/launcher.ts:1370` (`isMacOSUpToDate && !isIntelMac`) likewise. **Both
  remain live** — pre-Sonoma Apple Silicon still selects Wine-Crossover. The diff will read as a
  Wine/GPTK behaviour change to a later reviewer, so the plan must state in the commit body that
  it is behaviour-preserving *because* the removed operand is provably constant.

- **D-12:** Three Apple-Silicon surfaces are named MUST-SURVIVE, because a sweep for "Intel"
  reaches all three by keyword:
  1. `src/frontend/screens/Settings/components/AdvertiseAvxForRosetta.tsx` — Rosetta **on Apple
     Silicon**, not Intel.
  2. `checkRosettaInstall()` at `src/backend/utils.ts:1368` — same.
  3. `isAppleSiliconMac` (`src/backend/constants/environment.ts:42`) — a **positive** probe,
     deliberately not `!isIntelMac`, gating a **destructive** auto-removal at
     `src/backend/storeManagers/steam/games.ts:1196`.

- **D-13:** `REQ-34.1-05` is amended with a dated superseding note, never rewritten. It
  enumerates 19 sidecar-routed channels including `isIntelMac`; removing the channel takes it to
  18. Append a dated note recording that 34.18 retired it — preserving what 34.1 actually
  verified at close, and matching how 34.16's findings were handled. Also update
  `.planning/IPC-PORT-INVENTORY.md` and
  `.planning/phases/34.1-tauri-ipc-re-plumb-slice-4-app-shell-and-window-chrome/34.1-PORTED-CHANNELS.md`.

- **D-14:** `removeCopies.test.ts`'s RED-proof is rewritten to preserve the proof, not deleted.
  `src/backend/storeManagers/steam/__tests__/removeCopies.test.ts:435` proves
  `isAppleSiliconMac` must **not** be written as `!isIntelMac`, using the empty-CPU-model host
  (where `'Intel'.includes('')` is false, so the negation is wrongly `true`) — and it guards a
  destructive auto-removal. Keep the Intel-model and empty-model host cases, expressing the
  unsafe negation inline instead of via the removed constant. **The proof must outlive the
  constant it was written against.**

<code_context>
## Existing Code Insights

### Two ROADMAP claims that are stale — do not inherit them

1. **"a guard hardcoded to `--arch=arm64`" is wrong.** `package.json:46` and `:51` now run the
   guard for **both** arches (`--arch=arm64 && --arch=x64`), added by 34.16. The security
   exposure (an unverified x64 build reaching the `electron-updater` feed via `-p always`) is
   still real, but its mechanism is not what the ROADMAP describes.
2. **"three of the six sentinels would stay permanent" understates it.** All **six** are
   sentinels today, arm64 included, and `runId` is `null`. Nothing has ever been pinned.

### The guard's vacuity risk appears NOT to be real — verify before planning work against it

The ROADMAP flags that "an arch-parameterised guard given one arch can go vacuous rather than
strict." Reading `meta/verifyRunnerBundle.ts`: `findDarwinBinRoot()` **throws** when
`build/bin/${arch}/darwin` is absent (`:259-263`), and `main()` returns `summary.ok ? 0 : 1`
over a fixed three-runner list. It fails loudly on a missing tree rather than passing over an
empty one. The planner should confirm this rather than budget a fix for a risk that may not
exist — but should still red-proof the one-arch guard against a known-bad tree.

### Reusable assets
- The `checkpoint:human-verify` blocking-gate idiom (used throughout 34.13/34.16) is the vehicle
  for D-05's developer hand-off.
- `meta/__tests__/` already has the survivor/vacuity-control test idiom
  (`verifyRunnerBundle.test.ts:373` "vacuity control", `buildRunnersOnedir.test.ts:765`
  "vacuity guard") — D-08's survivor test should follow it.

### Established patterns
- **New user-facing strings go in `public/locales/en/gamelib.json`, never `translation.json`** —
  a churn guard fails CI otherwise. D-01 puts the disclosure in README, so this should not bite,
  but D-10 removes frontend code and may touch strings.
- Dispositions are written as **table rows**, never `### <ID>` sections — a `-REVIEW.*\.md$`
  closure glob harvests `^### <ID>` headings and would mis-ledger the file.

### Integration points
- Removing the `isIntelMac` channel touches the sidecar registration path, so
  `src/backend/sidecar/__tests__/` fixtures (~10 files carrying `isIntelMac: false`) all move
  together. Treat as one atomic change; a partial removal leaves the preload invoker pointing at
  an unregistered channel, which fails **silently** under the sidecar.
