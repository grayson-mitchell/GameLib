**Researched:** 2026-08-27

**Confidence:** HIGH

## Summary

This is a retirement phase, not a feature phase: every locked decision (D-01..D-14) in
`34.18-CONTEXT.md` was independently re-measured against HEAD and found **CONFIRMED**, with one
important **scope clarification** (not a contradiction) on D-11's branch-collapse guidance. No
CONTEXT claim was refuted.

**DELTA vs CONTEXT's own census (D-10):** CONTEXT hedges its `isIntelMac` count as "~15 source
files, ~28 sites, plus ~12 test files." Direct grep at HEAD measures **17 non-test files / 36
sites** and **11 test files / 25 sites** exactly. The 3 files CONTEXT's D-10 prose does not name
(`storeManagers/steam/games.ts:1171`, `sidecar/clipboardFlowRegistration.ts:38`,
`sidecar/shellFilesFlowRegistration.ts:66`) are **comment-only** mentions — no functional edit
required, but a doc-drift touch each (see Edit Surface B.3). All file:line landmarks CONTEXT does
cite verify byte-for-byte correct.

**DELTA vs D-11's prose (not D-10's census, which already lists them):** D-11 names exactly two
live conditional branches to collapse (`utils.ts:999`, `launcher.ts:1370`). Measurement shows
**at least six** live conditional branches gate behavior on `isIntelMac` being always-false:
those two, plus `tools/dxmt.ts:135`, `:142`, `:149`, `tools/index.ts:637`, `main.ts:233`, and
`WineManager/index.tsx:61`. All six are already present in D-10's file:line census — this is not
a missing-consumer problem, it is that D-11's *behavior-preservation reasoning* ("collapses
because the removed operand is provably constant") needs to be applied by the planner at all six
sites, not just the two D-11 names in prose. Flagged as an Edit Surface nuance, not a blocker.

Every other Code Insights claim (guard now covers both arches; all six digest sentinels are
`PENDING-CI-PUBLISH` with `runId: null`; the guard is not vacuous) is CONFIRMED exactly as
CONTEXT states. `meta/pinRunnerDigests.ts` (scope consumer 7, D-04) is confirmed genuinely
un-runnable today: it fetches `SHA256SUMS-x64`, which was never published because the x64 leg
never dequeued.

**Primary recommendation:** Sequence this as (1) code-complete retirement of all 8 scope
consumers + isIntelMac removal + doc dispositions, gated by static/grep/jest proofs; (2) a single
`checkpoint:human-verify` gate per D-05 for the developer's remote actions (workflow dispatch +
`pnpm pin:runner-digests`); (3) phase does not close on sentinels. Isolate D-09's non-macOS glob
fixes into their own commit per the attribution caveat.

## Section E — Gate Designs

### E.1 D-02: README disclosure — literal-string gate

**Design:** grep-based, in a jest test or a standalone CI/lint script.
```
grep -F "GameLib will not support Intel Macs on macOS" README.md
```
**RED-proof:** run the identical grep against the pre-fix README (current `README.md` at HEAD,
which lacks the string) — MUST fail (exit 1 / zero matches) to prove the assertion is
non-vacuous. A jest test doing `expect(readFileSync('README.md','utf8')).toContain('GameLib will not support Intel Macs on macOS')` satisfies this: it is RED today (string absent), GREEN after the edit.

### E.2 Six→three digest-key reduction — non-vacuity proof

**Design:** a jest test asserting `Object.keys(runnersOnedirDigests.<runner>)` (or equivalent
top-level shape) contains exactly the 3 arm64-only keys and does NOT contain any `x64` key.
**RED-proof:** run the same assertion against the current (6-key) JSON — MUST fail, proving the
test would have caught the pre-retirement shape.

### E.3 D-08 survivor test — non-goal counts stay intact

**Design:** three grep-count assertions in one jest test:
1. `electron-builder.yml` contains exactly 7 occurrences of `build/bin/x64/win32/` (win32 helper
   path key, D-07 category 2 — must NOT drop with the retirement)
2. `meta/downloadHelperBinaries.ts` contains exactly 6 non-darwin x64 keys (linux/windows, D-07
   category 3)
3. `src/backend/utils.ts` still contains the `x64Path` runtime fallback at its current line
   (D-07 category 4, explicitly declined for removal)
**RED-proof:** temporarily stub/mutate one of the three counts in a scratch copy and confirm the
assertion fails — proves the counts are load-bearing, not incidental.

### E.4 `isIntelMac` removal — both registration paths gone, no dangling invoker

**Design:** two-part gate.
1. Static grep: `grep -rn "isIntelMac" src/` returns **zero matches** anywhere in `src/` after
   the removal (constant, both IPC registrations, types, preload, frontend, and the 3
   comment-only mentions all cleared).
2. Behavioral: a sidecar RPC integration test (following `appShellFlows.test.ts`'s existing
   pattern) confirms that invoking `'isIntelMac'` over the sidecar RPC returns the
   `UNPORTED_CHANNEL_MARKER`-prefixed rejection (proving the channel is cleanly gone, not
   half-registered) — OR, if the frontend call site is also removed in the same atomic change
   (recommended), a static grep confirms `window.api.isIntelMac` has zero call sites remaining.
**RED-proof:** run gate 1 against current HEAD (36 non-test + 25 test matches) — MUST fail
loudly with a nonzero count, proving the grep is wired to the right pattern.
**Critical ordering note (from the traced silent-failure mechanism):** if the backend handler is
removed but `GlobalState.tsx:1523`'s frontend call site is left in place even temporarily, the
failure is **silent** — `bootErrorSurface.ts`'s global `unhandledrejection` handler catches the
`UNPORTED_CHANNEL_MARKER`-tagged rejection and only `console.warn`s, leaving `isIntelMac` frontend
state stuck at its default `false` with no visible error. This means gate 1 (static, all-`src/`
grep) is the load-bearing proof — do not rely on absence-of-runtime-error as evidence of a clean
removal.

### E.5 D-11 branch-collapse — behavior-preservation proof (extended scope per Section A/B.4)

**Design:** for each of the 6 identified live branches (not just the 2 D-11 names), a test
proving the removed operand's constancy does not change behavior:
- `utils.ts:999`, `launcher.ts:1370` — existing coverage likely present (D-11 explicitly named);
  verify existing tests still pass with the operand collapsed.
- `tools/dxmt.ts:135/142/149`, `tools/index.ts:637`, `main.ts:233`,
  `WineManager/index.tsx:61` — planner should audit for existing test coverage; where absent,
  add a minimal test asserting the post-collapse behavior matches the pre-collapse
  arm64-Apple-Silicon-host behavior (the only host GameLib now ships for), per the same
  "provably constant" reasoning D-11 already establishes.

### E.6 D-14 RED-proof rewrite — proof outlives the constant

**Design:** rewrite `removeCopies.test.ts:435`'s RED-proof to express the unsafe negation
inline: something like `const negatedIntel = !((cpuModel).includes('Intel'))` computed directly
from the mocked `cpus()` fixture, rather than referencing the (now-removed) `isIntelMac` import.
**RED-proof of the RED-proof:** confirm the rewritten test still fails if someone writes
`isAppleSiliconMac` as `!isIntelMac`-equivalent logic (i.e., the test must still catch the
empty-CPU-model-string false-positive it was originally written to catch) — do not let the
rewrite become a no-op assertion.

## Section G — Sequencing and Risks

### Sequencing

1. **Doc-only prep (no code dependency):** D-01/D-02/D-03 README edit; D-13's REQ-34.1-05
   amendment + IPC-PORT-INVENTORY.md + 34.1-PORTED-CHANNELS.md updates; ledger re-routing (items
   1/2/3/12/13/18). These can land in any order relative to the code work and are low-risk.
2. **CI/build retirement (consumers 1-6 + 7):** drop the x64 matrix leg, reduce the digest
   manifest to 3 keys, arch-key the downloader, fix `electron-builder.yml`/`build-base.yml`/
   `package.json` invocations, confirm the guard needs no change (or make the minimal change),
   reduce `pinRunnerDigests.ts` to single-arch. This is the ROADMAP's originally-scoped work and
   has no dependency on the `isIntelMac` removal.
3. **`isIntelMac` removal (D-10/D-11/D-12/D-14):** atomic across both IPC registration paths +
   all 17 non-test + 11 test files at once — per the traced silent-failure mechanism (Section
   E.4), a partial removal (backend handler gone, frontend call site remaining) fails silently,
   not loudly. This should be its own commit/task group, landed as one unit, gated by the
   zero-grep-match proof before merge.
4. **D-09 glob fix, attribution-isolated:** the 2 macOS-arch-driven glob fixes (in
   `build-base.yml`) should land in step 2's commit group; the 4 non-macOS glob fixes
   (Heroic→GameLib prefix on Windows/Linux artifacts) should be an **independent commit**, so a
   revert of one does not touch the other.
5. **D-05 blocking checkpoint (developer-only, last):** after all code above is merged and
   green, the developer dispatches `build-runners-onedir-macos.yml` (now arm64-only) on the
   default branch, then runs `pnpm pin:runner-digests` to replace the 3 remaining
   `PENDING-CI-PUBLISH` sentinels with real digests. **The phase does not close until this
   completes** — code-ready is not done-done.

### Risks

- **D-09 attribution risk (explicit in CONTEXT):** bundling all 6 `build-base.yml` glob fixes
  into the macOS-arch-retirement phase means a `build-base.yml` breakage cannot be attributed to
  "macOS half" vs "Windows/Linux half" without inspecting the diff. Mitigated by the isolated
  commit in step 4 above.
- **Silent-failure risk on `isIntelMac` (traced mechanism, Section E.4):** any staged/partial
  landing of the IPC removal risks a channel invoke silently resolving to
  `UNPORTED_CHANNEL_MARKER` and being swallowed by `bootErrorSurface.ts`'s global handler. This
  is the single highest-severity execution risk in the phase — mitigate by landing the removal
  atomically and gating on the zero-grep-match static proof, not on the absence of a runtime
  error during manual testing.
- **D-11 scope-creep risk:** because D-11's prose names only 2 of 6 live branches, a plan that
  reads D-11 literally may collapse only `utils.ts`/`launcher.ts` and leave `dxmt.ts`,
  `tools/index.ts`, `main.ts`, and `WineManager/index.tsx` with a dead-but-still-imported
  `isIntelMac` reference — which would then fail D-10's zero-grep-match gate (a useful
  cross-check, but better to catch at plan time).
- **Ledger item 18/C2-05 mishandling risk:** because item 18 is *already closed* with a residual
  note, a plan that treats it as "one more item to close" risks writing a duplicate/contradictory
  closure record. Correct handling is a cross-reference note, not a fresh disposition (Section
  A9).
- **Historical-record risk (34.2 docs):** a plan that "fixes" all "19 channels" mentions
  project-wide, including in already-executed `34.2-*-PLAN.md`/`SUMMARY.md` files, would falsify
  historical execution records. D-13's scope is deliberately narrow (REQUIREMENTS.md,
  IPC-PORT-INVENTORY.md, 34.1-PORTED-CHANNELS.md) — the planner should not widen it to historical
  docs (see Section B.6).
- **`.husky/pre-push` gate risk (project memory):** prettier (3 files) and `i18n --fail-on-update`
  are known RED repo-wide as of the last recorded check; if this phase's edits touch formatting
  or string tables, expect the pre-push hook to need `--no-verify` per standing project practice,
  or a fresh prettier pass — verify current state before assuming this still applies.
- **Post-checkout hook risk (project memory):** `git checkout -- <file>` fires the
  `post-checkout` hook, which runs `download-helper-binaries` and throws on sentinel digests.
  Since this phase's early state has all 6 (later 3) digests as sentinels, any executor tempted
  to `git checkout -- <file>` to discard a bad edit should restore via `cp`+shasum instead, not
  `git checkout`.
