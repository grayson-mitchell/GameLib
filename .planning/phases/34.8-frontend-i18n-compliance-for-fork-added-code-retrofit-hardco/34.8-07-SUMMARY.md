## Decisions Made

- **successWithPackage's fallback shape, restructured mid-plan:** the first draft pre-computed the fallback via string concatenation (`'Key redeemed! ' + packageName + ' has...'`) and passed a *different* literal (the `{{packageName}}` placeholder) to `t()`. `meta/hardcodedStringGate.ts`'s Pattern 3 dataflow exemption only recognises a fallback that is a single string-literal initializer later passed as that *same* binding to a `t()` call — a concatenation's pieces don't trace, and passing a different literal to `t()` breaks the trace entirely. Reworked to mirror `repairFailure.ts`'s shape verbatim: the same `message` binding holds the placeholder default and is passed unchanged to `t()`; the empty catch keeps it as-is on a throw (showing the raw `{{packageName}}` token in that rare failure path) rather than hand-rolling a second interpolation implementation. Verified via a direct `scanSource()` run: 0 violations.
- **D-22/D-21 recorded, not retrofitted:** `PlatformSupport.tsx` was read and confirmed — its `title="Windows"`/`"macOS"`/`"Linux"` literals are exact glossary matches (all three are in `meta/i18nGlossary.json`) and its prose (`info.supportedPlatforms`) is already `t()`-wrapped. `ConsoleMode`, `LogSettings`, `StoreSearch` were confirmed untouched via `git diff --stat` (empty output). **D-22: measurement-superseded audit false positive, no code change, confirmed at commit `b12e49771`.**

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] successWithPackage's fallback did not trace as gate-exempt**
- **Found during:** Task 3 (verifying `bootErrorSurface.ts`'s exemption via a direct `scanSource()` run, then re-checking `copy.ts` the same way rather than trusting `npx jest` green alone)
- **Issue:** Task 1's original implementation pre-computed the `success`-with-`packageName` fallback via string concatenation and passed a *different* literal (the `{{packageName}}`-placeholder default) to `t()`. `meta/hardcodedStringGate.ts`'s Pattern 3 dataflow exemption (the mechanism this plan's own `<action>` text names as "what keeps the gate quiet on those literals") requires the exact same binding to be both the fallback initializer and the literal `t()` default argument. Running `scanSource()` directly against the file (not just the jest test suite, which only exercises runtime behaviour, not the gate's own static analysis) surfaced 2 residual violations that the plan's listed acceptance-criteria greps did not catch.
- **Fix:** Reworked the branch so the same `message` binding holds the placeholder default and is passed unchanged to `t()`, matching `repairFailure.ts`'s shape exactly; the catch keeps the value as-is (no hand-rolled substitution, which itself introduced a second flagged literal on the first attempted fix).
- **Files modified:** `src/frontend/components/UI/RedeemSteamKeyDialog/copy.ts`
- **Verification:** Direct `scanSource()` run against the file: 0 violations (down from 2, and briefly 1 during an intermediate attempt). `npx jest --selectProjects Frontend copy.test`: 21/21 green. `npx jest --config meta/jest.config.js hardcodedStringGate -t "scope orchestration"`: green.
