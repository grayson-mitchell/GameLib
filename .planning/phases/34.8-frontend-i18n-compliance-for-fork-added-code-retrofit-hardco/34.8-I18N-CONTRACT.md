# GameLib Fork i18n Contract

**Effective:** 2026-08-07 (Phase 34.8, plan 10 — the gate went blocking in this plan).

This document is the standing contract for how fork-added frontend strings get translated, how
the enforcement gate works, and — deliberately — every decision this phase made NOT to act on.
Read it before adding a new user-facing string, before touching `meta/hardcodedStringGate.ts`,
`meta/i18nGateScope.json`, `meta/i18nGateAllowlist.json`, or `meta/i18nGlossary.json`, and before
an upstream Heroic sync that might make the gate's scope snapshot stale.

## How to add a user-facing string

Every fork-added user-facing string lives in the **`gamelib` namespace** (D-01), keyed as
`gamelib:<feature>.<slug>` (`keySeparator: '.'` is already configured; `namespaceSeparator: ':'`
routes the prefix to `public/locales/<locale>/gamelib.json`). Always call `t()` with **two
arguments**: the key, and an English default —

```ts
t('gamelib:redeemKey.rateLimited', 'Too many attempts — please wait a bit before trying again.')
```

The English default is not decorative: `fallbackLng: 'en'` + `returnEmptyString: false` +
`returnNull: false` (`src/frontend/index.tsx:137-154`) mean a key that is missing or empty in any
of the 48 non-English locales silently falls through to this string — never a blank UI, never a
raw key. This is what makes "en coverage + English fallback" a sufficient compliance bar (the
phase's own `<domain>` framing); translated coverage in the other 48 locales is polish layered on
top (see `## Known deferrals` below on machine-fill).

Two forms are established, matching where the call site lives:

- **In a component or hook:** `const { t: tGamelib } = useTranslation('gamelib')` — a SECOND,
  aliased hook call alongside any existing `useTranslation('gamepage')`/etc. (`GameCard/index.tsx:
  104-105`'s `t2` is the original precedent; the retrofit plans standardised on the `tGamelib`
  spelling — see the parser-visibility trap below on why the exact spelling matters).
- **In a plain module with no hook of its own** (a `copy.ts`-shaped helper, a `themeLabels.ts`-
  shaped data table): inject a `t: TFunction` as a parameter, supplied by the calling component's
  already-Suspense-resolved `t` (`RedeemSteamKeyDialog/copy.ts`'s `redeemOutcomeCopy()`,
  `repairFailure.ts`'s `reportRepairFailure()`). **Do not** `import { t } from 'i18next'` at
  module scope — a namespace loads lazily on first `useTranslation('gamelib')` call
  (`i18next.init` declares no `ns` array), so a module-scope call has no guarantee the `gamelib`
  namespace has resolved yet; a component's own `t`, gated behind React Suspense, does.

**The parser-visibility trap (plan 09's real finding, not hypothetical):** `i18next-parser`'s
default lexer `functions` option is exactly `['t']` — a literal identifier match, not an
i18next-aware alias resolver. `i18next-parser.config.js` now explicitly lists
`functions: ['t', 'tGamelib']` for exactly this reason: the retrofit's second-hook idiom
(`const { t: tGamelib } = useTranslation('gamelib')`) calls `tGamelib(...)`, an identifier the
default config never sees. Without this fix, 16 of the retrofit's 48 keys were silently absent
from the generated catalog — a key the parser cannot see is a key translators never receive. **If
a future retrofit spells its second-hook alias anything other than `tGamelib`** (or introduces a
third-aliased hook), it reintroduces this exact gap and must add the new identifier to
`i18next-parser.config.js`'s `lexers.ts`/`lexers.tsx` `functions` arrays, with a regression test
(see `meta/__tests__/i18nParserConfig.test.ts`). This is a standing trap, not a one-time fix.

Once the code is written: run `pnpm i18n` (wraps `i18next-parser`, `keepRemoved: true` per D-03 —
see `## Regenerating the scope after an upstream sync` for what this flag protects), then commit
only the resulting `public/locales/en/gamelib.json` diff. `pnpm i18n-churn-guard` (D-05, see
below) will fail the build if the run touched anything under `public/locales/` other than
`*/gamelib.json` — do not hand-edit around a churn-guard failure; investigate why the parser wrote
to an upstream namespace (a missing `gamelib:` prefix on a new `t()` call is the most likely
cause).

## The gate

`meta/hardcodedStringGate.ts` is a `ts-morph` AST scanner. It runs as an ordinary jest test,
`meta/__tests__/hardcodedStringGate.test.ts`, inside the **`meta` jest project** — already one of
`jest.config.js`'s five `projects` entries, already exercised by the already-blocking
`package.json` script `"test:ci": "jest --runInBand --silent"`, already run as a blocking step by
`.github/workflows/test.yml`. **No new CI YAML exists or is needed** — the test suite itself IS
the gate. `react/jsx-no-literals` was rejected (D-16/RESEARCH.md): it is structurally blind to
`.ts` files, so it could never cover `RedeemSteamKeyDialog/copy.ts`. `meta/lintTranslations.ts`
was rejected as an extension point: it lints catalog JSON, not source AST.

**What counts as user-facing (D-16's "researcher decides" resolved):** JSX text nodes, plus JSX
attribute values on `title`/`aria-label`/`alt`/`placeholder`/`label`
(`USER_FACING_ATTRIBUTES`). Everything else — `className`, `id`, `href`, `data-*`, every
`aria-*` other than `aria-label`, and a growing list of this codebase's own component-prop
conventions (`i18nKey`, `htmlId`, `extraClass`, `partition`) — is structurally excluded
(`EXCLUDED_ATTRIBUTES`/`isExcludedAttribute`). Object-property, `return`, `variable`, and bare
`argument` positions are ALSO scanned (this is what catches `copy.ts`-shaped modules with no JSX
at all). `console.*` arguments and `window.api.log*`/`window.api.logError` arguments are
deliberately excluded — they are developer-facing diagnostic text, under the Tauri sidecar
`console.*` is unreliable (stdout IS the RPC pipe) so 26+ fork files use `window.api.log*`
instead, and neither is ever rendered to a user. `new Error(...)`'s message argument is likewise
excluded for the same reason.

**The four original D-14 exemption mechanisms**, each proven in both directions by a paired
positive/negative fixture:

1. **t-alias detection** (`collectTAliases`) — any local binding that destructures a property
   named `t` (`const { t: t2 } = useTranslation()`, or a destructured function parameter
   `{ t }: Options`), or any parameter typed with `TFunction`, is a recognised alias. Extended by
   plan 06 to `isComposedTCallArgument`, which also recognises a literal composed into the call
   via a ternary, `+` concatenation, or (plan 10) `??`, and — plan 10 — a literal referenced
   inside a `${...}` template interpolation that is itself composed into a t()-argument.
2. **`[key, defaultText]` tuple tables** — a two-element array whose first string is
   dotted-key-shaped (`DOTTED_KEY_RE`), deliberately narrow so a developer cannot dodge the gate
   by wrapping two unrelated strings in a fake key-shaped pair (proven by a paired negative
   fixture).
3. **Single-scope dataflow to `t()`** (`isAssignedThenPassedToT`) — a literal assigned to a local
   binding, later passed as that SAME binding to a recognised t-alias call, anywhere in the same
   source file (`findReferencesAsNodes()`, bounded — **no cross-file dataflow**, see the
   declaration-scoped marker below for what to do when the consuming call site is in a different
   file). Plan 10 broadened what counts as "safely consumed" through this same binding: also
   exempt if the reference is a diagnostic log argument, sits inside an already-excluded JSX
   attribute, or is a technical DOM/browser-API argument — not only a `t()` call — because the
   underlying claim ("this literal, through this binding, is never rendered as untranslated
   prose") is the same regardless of which safe sink it reaches.
4. **The `i18n-gate-exempt:` comment marker** (`FILE_EXEMPT_MARKER`) — a bare marker with no
   reason is NOT an exemption (D-14's own wording: "exempted with an explanatory comment"; a
   negative fixture pins this). It now carries **two granularities**, distinguished purely by
   comment placement, never by different marker text:
   - on a source file's FIRST top-level statement → the WHOLE FILE is exempt. `bootErrorSurface.ts`
     (pre-i18n-boot, D-19) is the only real user.
   - on any OTHER top-level statement → only that ONE statement is exempt
     (`checkDeclarationExemptMarker`, 34.8-08c). `Settings/index.tsx`'s `defaultWineVersion`
     constant declaration and `StoreSearch/helpers.ts`'s `buildOwnedBadgeLabel()` function
     declaration are the two real users as of this plan. This mechanism exists specifically so a
     genuinely-compliant-but-untraceable declaration does not force a full-file exemption (which
     would blind the gate to every OTHER real string in an actively-edited file) or a
     `meta/i18nGateAllowlist.json` entry (D-18's mechanism is scoped to work deferred behind
     OTHER OPEN PHASES, not to something a plan can and does finish itself).

**Content-shape and structural-position exemptions** (never counted as a "real" candidate at all,
regardless of glossary or `t()`-wrapping — these are technical tokens, not translatable prose):
CSS custom properties/functions/lengths/attribute-selectors, hex colours, bare file extensions,
kebab/snake-case identifiers, a single lowercase-leading token (real UI prose in this codebase is
sentence-cased), URL schemes, `KeyboardEvent.key` comparisons (scoped to the literal property name
`key`, never generalized to an arbitrary comparison — see the negative fixture below), react-
i18next `<Trans i18nKey="...">` children, `<InfoBox text="...">`'s key-forwarding prop,
config-store key arguments (`configStore.get(...)`/`storeGet(...)`/etc.), and — added flipping the
gate to blocking (plan 10, closing the 62-item residual `34.8-AUDIT.md § Closure` had already
triaged as `not-user-facing`/`glossary`) — icon-size multipliers (`2x`/`3x`), single-word ALL-CAPS
enum/state discriminators, 32-character hex GUIDs, CDN query-string fragments, bare DNS hostnames,
a `??`-prefixed backend placeholder sentinel, DOM/browser API technical arguments
(`querySelector`/`querySelectorAll`/`getContext`/`setUserAgent`/`sessionStorage`
`getItem`/`setItem`), internal string-comparison arguments
(`includes`/`endsWith`/`startsWith`/`replace`), and `[...].includes()` array literal elements.

**A load-bearing negative fixture, worth calling out explicitly:** "still flags a string compared
against an unrelated property — the exemption is scoped to `.key` specifically." The gate does
NOT have, and must never grow, a general "any equality-comparison operand is exempt" rule — every
comparison-based exemption above is gated on a specific method name or property name, confirmed
against a real occurrence. A future author reaching for "just exempt anything compared with
`===`" should read this fixture first.

## Regenerating the scope after an upstream sync

`meta/i18nGateScope.json` is a committed snapshot (`files.length`, currently 136) generated from
`package.json`'s `upstream.baseCommit` (currently `b5b5cad3fa2e822602d320b70788d87240fc056e`) via
a diff against the upstream Heroic merge-base — the same D-07 mechanism used to identify
fork-added files in the first place. When `upstream.baseCommit` changes (a Heroic sync landed),
`meta/__tests__/genI18nGateScope.test.ts` goes red, because the live diff no longer matches the
committed snapshot. Run `pnpm gen-i18n-gate-scope` **locally** — it needs the `heroic` git remote,
which CI does not have — and commit the refreshed `meta/i18nGateScope.json`. Do not hand-edit the
file. The `gate is not disabled` describe block (plan 10) asserts `report.scannedFiles` equals the
snapshot's own `files.length`, so a snapshot that silently drifted out of sync with the real
scanned set fails loudly rather than passing on a stale count.

## Deliberate non-actions

Several of this phase's decisions are deliberate NON-actions. Without this section, a future
reader sees them as omissions.

**D-06 — the split-brain is intentional.** Fork keys already sitting in `en/translation.json` (80
Steam-mentioning lines, an upper bound including Heroic's own Steam-shortcut strings) and
`en/gamepage.json` (54 lines) **stay there.** The `gamelib` namespace starts from this phase
forward only — nothing is migrated. Migrating would mean DELETING keys from the upstream
catalogs, which is exactly what the D-05 churn guard blocks. Revisit only if the split-brain
becomes a real maintenance cost (D-06's own escape hatch).

**D-13 — the gate does not enforce namespace choice.** Any `t()` call passes, including one
targeting an upstream namespace instead of `gamelib`. This avoids false positives against the D-06
split-brain and against legitimate reuse of an existing upstream key from fork code. Namespace
discipline for NEW strings is a review convention, backed mechanically by D-05 (a mis-namespaced
call that writes into an upstream catalog fails the churn guard, even though the gate itself
would not have flagged the call site).

**D-20 — Weblate is deliberately not stood up.** A young fork has no translator community and it
would be an empty dashboard. Nothing here blocks adopting it later: the file format
(`public/locales/<locale>/gamelib.json`) is exactly what Weblate consumes, and the
`gamelib.mt.json` provenance manifest (D-10, machine-fill script) is what makes a future import
correct — distinguishing MT output from approved human translation — rather than silently treating
the former as the latter.

**D-21 — brand names are glossaried, not wrapped.** `ConsoleMode`'s store-label map,
`LogSettings`'s `baseFiles` titles, and `StoreSearch`'s `STORE_DISPLAY_NAME` map needed **ZERO
code change** — the fix was extending `meta/i18nGlossary.json` with the compound/variant brand
forms RESEARCH.md's pitfall analysis found (`Amazon`, `ZOOM`, `Epic/Legendary`, `Amazon/Nile`,
`Amazon Games`), confirmed by plan 07's own `git diff --stat` (empty) across all three
directories. Wrapping them would change working code purely for uniformity and put the identical
literal string in all 49 catalogs. Accepted cost: the glossary must be extended whenever a new
store/brand form is added — the gate failing on an unglossed brand name is the intended reminder,
not a bug.

**D-22 — `PlatformSupport.tsx` was dropped from the retrofit.** Measured directly: its only
literals are `title="Windows"`/`"macOS"`/`"Linux"`, exact `meta/i18nGlossary.json` matches, and
its one prose string (`info.supportedPlatforms`) is already `t()`-wrapped. Its appearance in the
2026-08-05 manual audit list — and therefore in `ROADMAP.md` and the original D-19 scope text — is
a **measurement-superseded false positive**, confirmed by plan 07's `git diff --stat` (empty).
This is not an omission; no fork-added file in this directory needed editing.

**Out of scope, unchanged from `ROADMAP.md § Phase 34.8`:** upstream-inherited Heroic strings
(~50: GOG REDmod, Gamescope, aria-labels) — churning them is pure merge-conflict surface against
upstream, with no fork-ownership justification for touching them. The backend error-code contract
(~30 English error payloads from the Steam bottle/clientSetup/bridge managers, surfacing verbatim
in the UI over IPC) needs its own design phase (codes over IPC, frontend maps codes to `t()` keys)
and must not churn live-verified Steam paths mid-Tauri-migration.

## Known deferrals

**D-17 — two files deferred behind other open phases**, tracked in
`meta/i18nGateAllowlist.json` with D-18's self-expiring `expectedCount`:

| File | Expected count | Blocked on |
|---|---|---|
| `src/frontend/screens/Login/components/SteamLogin/index.tsx` | 27 | Phase 34.4.2 (mid-`/gsd-debug`, F-34.4.2-19 undiagnosed at deferral time; `loginInFlightUiReachability.test.tsx` pins this screen's markup with 5 mutation-proven gates — retrofitting its literals means editing pins under active diagnosis) |
| `src/frontend/screens/WebView/useTauriOAuthLogin.ts` | 2 | Phase 34.5 (open gate fails at this file's render layer) |

**D-18's headline behaviour** (proven bidirectionally by `meta/__tests__/hardcodedStringGate.
test.ts`'s `stale exemption` block): the moment either file's measured violation count no longer
matches its `expectedCount` — in EITHER direction, a drop (the retrofit landed) or a rise (a new
hardcoded literal was added behind the exemption) — the gate fails with "stale exemption — remove
this entry", naming the file, expected count, and measured count. Nobody has to remember to
revisit these entries; the build will not let them go stale silently.

`TauriLoginPanel.tsx` — the RENDER half of the same OAuth login feature `useTauriOAuthLogin.ts`
implements — is **already fully `t()`-wrapped** and needed no allowlist entry; its two remaining
gate-visible literals were closed by this plan's own composed-argument/template-interpolation
scanner fix (`## The gate` above), not deferred.

**Bulk machine-fill across the other 48 non-English locales is a separate, revertible commit
(D-08), not an omission.** This phase built and proved the glossary-aware machine-fill script
contract (D-09/D-10/D-11) but deliberately did not bulk-run it — a script bug in a 48-file bulk
run ships to all 48 at once, and the phase's actual gate is "no hardcoded strings" + `en`
coverage, with `fallbackLng: 'en'` making a missing non-English key harmless in the meantime.

## An open, honest limit — do not treat this contract as fully mechanically true today

`meta/i18nCatalogChurnGuard.ts` (D-05) is built, tested, and wired into `pnpm test:ci` — it will
correctly fail the build the moment a future `pnpm i18n` run leaves uncommitted drift in any
upstream catalog. **But the working tree is not yet in a state where running `pnpm i18n` today
produces a clean diff.** Plan 09 recorded — and reverted, twice, per its own mandatory revert
discipline — real, pre-existing, unrelated drift in `en/translation.json`, `en/gamepage.json`, and
`en/login.json`: Steam bridge/client setup dialog strings, WebView OAuth login flow copy, Humble
notification plural forms, redeem-key dialog chrome, and a login-code paste button, none of it
related to this phase's own `gamelib:` content. This is real fork content added across many prior
phases that was never previously synced via `pnpm i18n` — exactly the ROADMAP item (3) gap D-04
supersedes and places out of scope for 34.8. The churn guard's job is to make sure this drift can
never land silently again, not to close the drift that already exists. Whoever eventually picks
up that ROADMAP item should expect the diff to be large and to span many prior phases' work, not
just this one — do not read the churn guard's presence as a claim that the upstream catalogs are
already clean.

## Carried-forward scanner gaps (measured, accepted, not chased further before this plan)

Two edge cases were identified by `34.8-06`'s whole-scope audit and explicitly deferred as
"low value, not chased further" — closed anyway during this plan's gate-flip work, recorded here
so the reasoning survives:

- The `classNames()`-assignment tracing gap `MacArchBadge.tsx` exposed (a CSS BEM modifier string
  assigned to a variable, then passed to `classNames()` outside any JSX attribute) — closed by
  broadening `isAssignedThenPassedToT`'s "safely consumed" check to recognise a reference nested
  in an already-excluded JSX attribute, not only a `t()` call.
- `SidebarLinks/index.tsx`'s split-brand-name taxonomy edge case (`GameLib` split across sibling
  `<span>` JSX-text nodes for CSS styling, defeating the exact-string glossary matcher) — closed
  by `isPartOfSplitGlossaryTerm`, which concatenates a JSX parent's simple-text children before
  matching against the glossary.

Any FUTURE scanner-accuracy gap of this shape (a genuinely-compliant or genuinely-non-prose
literal the gate cannot yet trace) should be fixed the same way these were: a narrow,
content-shape or structural-position check, confirmed against the real occurrence by direct read,
covered by a paired positive/negative fixture — never by widening `meta/i18nGateAllowlist.json`
(D-18's mechanism is for phase-external blockers, not scanner gaps) and never by a broad
"any comparison/any call is exempt" rule (see the load-bearing negative fixture in `## The gate`
above).
