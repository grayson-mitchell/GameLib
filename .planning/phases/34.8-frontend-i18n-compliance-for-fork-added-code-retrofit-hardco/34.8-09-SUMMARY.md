## Decisions Made

- **Fixed the `tGamelib` lexer gap rather than recording 16 keys as a documented absence.** The plan's own task 1 action anticipated the possibility of missing keys and said to "record which one and why" — but investigating found a clean, additive, config-only root cause (not a retrofit code defect requiring edits to already-closed 07/08a/08b/08c work, and not an architectural change). Rule 1 ("Auto-fix bugs... Does this affect correctness... ability to complete task? YES → Rules 1-3") applies: the plan's entire purpose is a complete, translator-visible catalog, and 16/48 keys silently missing is a broken outcome squarely within Task 1's own scope. Verified directly against the installed `i18next-parser` package (`new JavascriptLexer().functions` returns exactly `['t']`) rather than assumed from documentation.
- **Reverted the upstream-catalog churn twice rather than diagnosing or fixing its root cause.** Both `pnpm i18n` runs (pre- and post-tGamelib-fix) touched `translation.json`/`gamepage.json`/`login.json`. Read the diffs in full both times: Steam bridge/client setup dialog strings, WebView OAuth login flow copy, Humble notification plural forms (`_one`/`_other`), redeem-key dialog chrome (`redeemSteamKey.*`), a `paste` login-code button — none of it relates to `gamelib:` namespaced content or the `tGamelib` fix. This is real, pre-existing fork content that was added across many prior phases and never previously synced via `pnpm i18n` — exactly the ROADMAP item (3) gap D-04 explicitly supersedes and places out of scope for this plan. `git checkout -- public/locales/en/translation.json public/locales/en/gamepage.json public/locales/en/login.json` both times, per the plan's own mandatory revert discipline.
- **Second `pnpm i18n` run required a full reset (`rm public/locales/en/gamelib.json`), not just an upstream-catalog revert.** The first (pre-fix) run's `gamelib.json` output was itself contaminated: because `functions` was `['t']` only, the lexer's per-file namespace inference misattributed several files' *default-namespace* `t(...)` calls (e.g. `RedeemSteamKeyDialog/index.tsx`'s dialog-chrome strings, which use a plain un-namespaced `t()`) into the `gamelib` namespace whenever that same file also called a *second* `useTranslation('gamelib')` hook. Re-running with the fix in place, but reusing that contaminated `gamelib.json` as the merge base (`keepRemoved: true` never deletes), correctly reclassified those calls into `translation.json` on the next run while leaving stale, now-duplicate copies behind in `gamelib.json` — itself a second source of upstream churn. Deleting the contaminated `gamelib.json` before the final run produced a clean result: `gamelib` "Unique keys: 48, Added keys: 48, Restored keys: 0, Unreferenced keys: 0" — every key newly and correctly attributed, no leftover contamination.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] `i18next-parser`'s lexer `functions` list did not recognise the `tGamelib` alias, hiding 16 of 48 retrofit keys**
- **Found during:** Task 1, cross-checking the generated `gamelib.json` against the 48 keys named in the four retrofit SUMMARYs (a programmatic flatten-and-compare, not a visual scan) — 32/48 present on the first run
- **Issue:** `i18next-parser`'s `JavascriptLexer`/`JsxLexer` default `functions` option is exactly `['t']` (confirmed directly against the installed package). All 4 retrofit plans' extracted sibling modules (`copy.ts`, `themeLabels.ts`, `filters.ts`, `appleRating.ts`) take an injected `TFunction` parameter literally named `t`, so those calls were correctly seen. But 17 real component call sites use the second-aliased-hook idiom, `const { t: tGamelib } = useTranslation('gamelib')`, calling `tGamelib(...)` directly — an identifier the default lexer config never matches. The 16 missing keys were exactly this set: `gamepage.etaPrefix`/`wineLabel`/`tabsAriaLabel`, `login.unknownUser`, `library.storeOther`, `consoleMode.installPrevious`/`installNext`/`sortAscending`/`sortDescending`, `discounts.pegiPrefix`, `downloadManager.progressPaused`, `settings.gamescopeFsr`/`gamescopeUpscaleMethod`/`gamescopeWindowType`/`wineFlatpakPath`/`wineDefaultLabel`.
- **Fix:** Added `functions: ['t', 'tGamelib']` to both `lexers.ts` and `lexers.tsx` in `i18next-parser.config.js` (additive only, does not change which `t` calls are already recognised), plus a regression test in `meta/__tests__/i18nParserConfig.test.ts`.
- **Files modified:** `i18next-parser.config.js`, `meta/__tests__/i18nParserConfig.test.ts`
- **Verification:** Re-ran `pnpm i18n`; programmatic flatten-and-compare against the four SUMMARYs' key lists: 48/48 present, 0 missing. `npx jest --config meta/jest.config.js i18nParserConfig`: 5/5 green (new test included).
- **Committed in:** `826b127b9`

**2. [Rule 3 - Blocking issue] `pnpm lint-translations:gamelib`'s env var did not reach the piped `node` process**
- **Found during:** Task 3, running `pnpm lint-translations:gamelib` to verify its acceptance criteria
- **Issue:** The first draft wrote the script as `LINT_TRANSLATIONS_NAMESPACES=gamelib esbuild --bundle ... | node`. POSIX shell semantics only apply a bare `VAR=val` prefix to the single command it precedes — here, `esbuild` — not to `node` on the far side of the pipe, which is the process that actually reads `process.env.LINT_TRANSLATIONS_NAMESPACES`. The command silently ran with the DEFAULT (all-namespace) scope, exit 0, and its output included `translation`-namespace `Empty translation for zh_Hant.translation...` lines — failing the acceptance criterion ("its output mentions no namespace other than gamelib") without erroring.
- **Fix:** Rewrote the script as `export LINT_TRANSLATIONS_NAMESPACES=gamelib && esbuild --bundle ... | node`. `export` sets the variable in the current shell's own environment table for the rest of that shell invocation, so both sides of the subsequent pipe (forked as children of the same shell) inherit it.
- **Files modified:** `package.json`
- **Verification:** Re-ran `pnpm lint-translations:gamelib`: exit 0, output references only `gamelib.json` (as expected-missing-file `ENOENT` messages for the 48 locales that don't yet have one — ignored via the existing `if (!content) continue`), zero `translation`/`gamepage`/`login` content processed. Re-ran bare `pnpm lint-translations`: exit 0, output still covers `gamepage`/`login`/`translation`, confirming the default (unscoped) path is unaffected.
- **Committed in:** `db63d515a`
