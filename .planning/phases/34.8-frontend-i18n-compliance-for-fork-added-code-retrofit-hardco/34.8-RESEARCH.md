# Phase 34.8: Frontend i18n compliance for fork-added code - Research

**Researched:** 2026-08-07
**Domain:** i18next tooling (i18next-parser, react-i18next), TypeScript AST source-scanning
(ts-morph), CI gate design, git-based upstream diffing
**Confidence:** HIGH (D-07 mechanism, D-01 namespace loading, D-03 quantification, gate-scope
CI wiring are all directly measured against this repo) / MEDIUM (D-16 gate implementation shape
— a design recommendation, not something that pre-exists to verify) / LOW (full D-07-derived
retrofit target set beyond the files this session actually inspected — flagged explicitly below)

## Summary

This phase has almost no third-party-library risk — it needs **zero new npm packages**.
`ts-morph` (17.0.1, TypeScript compiler-API wrapper) is already an installed devDependency and
unused elsewhere in the repo; it is the correct tool to build the D-16 source-scanning gate.
`i18next-parser` (9.3.0, already configured), `i18next-http-backend`, and the existing
`meta/` + jest infrastructure need no additions. The Package Legitimacy Audit below is
consequently short: nothing to install, nothing to vet.

The three deliverables researched:

1. **D-16 gate mechanism** — recommend a **new TypeScript-AST scanner built with `ts-morph`**,
   living in `meta/` alongside `lintTranslations.ts` as a sibling (not an extension — the two
   starting constraints in CONTEXT.md are both confirmed true by direct source inspection: an
   ESLint `react/jsx-no-literals` rule structurally cannot see `.ts` files or non-JSX string
   literals like `copy.ts`'s `message: '...'` object properties or `ConsoleMode`'s
   `label: 'Epic'` map, and `lintTranslations.ts` operates on parsed JSON catalogs with zero
   source-AST capability). The gate is best implemented as a **jest test** in
   `meta/__tests__/` — `meta/` is already a jest project wired into the already-blocking
   `pnpm test:ci` (`test.yml`), so this requires **zero new CI YAML** to satisfy D-12's
   "blocking from day one."
2. **D-07's merge-base diff mechanism is directly verified working**: `origin` already points
   at upstream Heroic, the merge-base commit (`b5b5cad3f`) is fetched and reachable, and
   `git show <merge-base>:public/locales/en/translation.json` succeeds today, producing exact,
   reproducible fork-added-key counts (146 / 56 / 0 across the three catalogs). **However this
   exact mechanism will NOT work unmodified inside GitHub Actions** — `actions/checkout@v6`'s
   default shallow, single-remote checkout does not carry the Heroic upstream remote or its
   commit history. This is a load-bearing finding for planning: either add a
   remote-fetch-by-SHA CI step, or (recommended) snapshot the merge-base's fork-added-key/file
   list into a versioned repo artifact refreshed only when `package.json`'s
   `upstream.baseCommit` changes.
3. **D-03's `keepRemoved: false` landmine is now quantified, not just asserted**: a live
   `pnpm i18n` run (executed and fully reverted during this research session — verified clean
   via `git status`) deletes **36 real fork keys** across `translation.json` (33) and
   `gamepage.json` (3) that the static lexer cannot see (dynamic key construction, aliased `t`).
   `login.json` was unaffected (0 removed). `keepRemoved: true` prevents 100% of this loss at
   the cost of never auto-pruning genuinely dead keys — an accepted, already-locked tradeoff.

**Primary recommendation:** Build the gate as a `ts-morph`-based scanner exposed as a plain
function, driven by a jest test in `meta/__tests__/hardcodedStringGate.test.ts` (zero new CI
wiring, rides `pnpm test:ci`), scoped to a **static, versioned list of fork-owned files**
(not a live upstream diff at CI time), with three structural exemption categories — t()-alias
calls, `[key, defaultText]` tuple literals, and glossary-exact-match strings — plus a
comment-based full-file exemption and a count-based allowlist for the two D-17 deferred files.

### Pattern 1: t()-alias detection via `useTranslation()` destructuring

**What:** Find every local binding that resolves to i18next's `t` function, including renames,
so the gate's "is this call site exempt" check covers `t`, `t2`, `tr`, and any future alias
without a hardcoded name list.

**When to use:** Core of the gate's exemption logic — must run before literal-flagging so
`t('key', 'Default text')` calls are never flagged.

**Confirmed alias inventory in this codebase** (measured, not assumed):
```typescript
// Source: grep -rn "useTranslation" src/frontend — 3 confirmed alias sites
const { t: t2 } = useTranslation()   // src/frontend/screens/Game/GamePage/index.tsx:98
const { t: t2 } = useTranslation('gamepage')  // .../GameCard/index.tsx:105 (aliases the SECOND hook call)
const { t: tr } = useTranslation()   // .../InstallModal/DownloadDialog/index.tsx:157
const { t: tr } = useTranslation()   // .../InstallModal/DownloadDialog/BranchSelector.tsx:25
const { t: tr } = useTranslation()   // .../ModifyInstallModal/GOG/index.tsx:33
```

**AST shape (ts-morph):**
```typescript
// For each VariableStatement, find ObjectBindingPattern elements whose
// `propertyName` (or bare `name` when unrenamed) is the identifier "t".
// The BindingElement's `name` (renamed or not) is the local call-site alias.
sourceFile.getDescendantsOfKind(SyntaxKind.VariableDeclaration).forEach((decl) => {
  const nameNode = decl.getNameNode()
  if (Node.isObjectBindingPattern(nameNode)) {
    nameNode.getElements().forEach((el) => {
      const prop = el.getPropertyNameNode()?.getText() ?? el.getName()
      if (prop === 't') {
        tAliasesInScope.add(el.getName()) // 't', 't2', 'tr', ...
      }
    })
  }
})
```

### Pattern 2: `[key, defaultText]` tuple exemption (structural, not dataflow)

**What:** Both named D-14 tolerance files (`CrossoverBadge.tsx`, `LibraryFilters`) — and a
**third, previously unlisted site found during this research**, `Humble/Keys/stateLabels.ts`
(`STATE_LABEL_KEYS: Record<HumbleKeyState, [string, string]>`) — build a lookup table of
`[i18nKeyString, englishDefaultString]` pairs, then destructure and call `t(key, defaultText)`
at a DIFFERENT source location than the literal itself. A pure per-call-site check cannot see
this without dataflow tracing.

**Recommended heuristic (MEDIUM confidence — a deliberate design tradeoff, not a proof):**
exempt any 2-element array/tuple literal whose two elements are both string literals, where the
first element's text matches a dotted-or-underscored key shape
(`/^[a-zA-Z][a-zA-Z0-9]*(\.[a-zA-Z][a-zA-Z0-9_]*)+$/` — i.e. contains at least one `.`,
matching `keySeparator: '.'`). This is narrow enough that an unrelated two-string tuple
(e.g., a `[min, max]` label pair) is unlikely to accidentally match the dotted-key shape, and
it correctly exempts all three known sites without requiring real dataflow analysis.

**Example (measured, from this session's reading):**
```typescript
// Source: src/frontend/screens/Library/components/GameCard/CrossoverBadge.tsx:45-54
const labelKeyByTier: Record<Tier, [string, string]> = {
  gold: ['library.crossover_gold', 'Runs great on CrossOver (gold rating)'],
  // ... exempt: element 0 "library.crossover_gold" matches the dotted-key regex
}
```

### Pattern 3: assigned-then-passed-to-`t()` fallback (single-scope dataflow)

**What:** `repairFailure.ts`'s deliberate English fallback — a plain string literal assigned to
a `let`-declared variable, later passed as the SAME variable to a `t()`-alias call as the
default-value argument, inside a `try`/`catch` that keeps the literal if `t` throws.

```typescript
// Source: src/frontend/screens/Game/GameSubMenu/repairFailure.ts:113-121 (verbatim, read this session)
let title = 'Error'
let message = 'Repair failed. See the log for details.'
try {
  title = t('box.error.title', title)
  message = t('box.repair.error', message)
} catch {
  // keep the hardcoded English fallback -- a throwing `t` must still yield a rendered dialog
}
```

**Recommended check:** for every string-literal `VariableDeclaration`/`ExpressionStatement`
assignment within a function scope, use `ts-morph`'s `findReferencesAsNodes()` on that local
binding; if ANY reference within the same scope is an argument to a call whose callee resolves
to a known t-alias (Pattern 1), exempt the literal. This is a bounded, single-file/single-scope
check — no cross-file dataflow needed, and ts-morph's reference-finding makes it a handful of
lines.

### Pattern 4: full-file exemption via leading comment (`bootErrorSurface.ts`)

retrofit").

### Pattern 5: glossary exact-match exemption (D-02)

**What:** `PlatformSupport.tsx`'s `title="Windows"` / `title="macOS"` / `title="Linux"` (lines
23, 25, 28 — read this session) are hardcoded literals but are EXACT glossary entries per D-02
("Units and platform names stay literal too... Linux, macOS, Windows"). The gate must exempt
these by exact string match against a glossary list, independent of the t()-wrapping question.

**Concrete finding: `PlatformSupport.tsx` has ZERO real gate violations today.** Its one
non-glossary string (`"Supported platforms"`) is ALREADY `t('info.supportedPlatforms', ...)`
-wrapped. Despite being named as a D-19 retrofit target, direct inspection of the current file
found nothing to retrofit — see Open Questions for how the planner should handle this
discrepancy.

### Anti-Patterns to Avoid

- **Treating `console.*` string arguments as user-facing:** `repairFailure.ts`'s own commentary
  (T-34.2-52) explicitly designs `console.error(...)` calls to carry raw, potentially
  path/credential-adjacent backend error text that must NEVER reach a rendered dialog. If the
  gate flags `console.*` literal arguments, it directly false-positives against this exact
  D-14 tolerance file. **Recommendation: exclude all `console.*` call arguments from gate
  scope entirely** (see the "user-facing" cost table below).
- **A live upstream-remote fetch inside the CI gate itself:** couples every PR's pass/fail to
  GitHub reachability of a third-party repo and to `actions/checkout`'s shallow-clone defaults.
  Keep D-07's merge-base diff as an offline, human/`meta/`-script-run tool that produces a
  committed artifact; the CI gate reads only that artifact.

## Common Pitfalls

### Pitfall 1: D-07's merge-base diff does not survive into CI unmodified

**What goes wrong:** A CI step that runs `git show <merge-base-sha>:public/locales/en/X.json`
or `git diff <merge-base-sha> HEAD -- src/frontend` fails or silently produces an empty/wrong
result.

**Why it happens:** This session's D-07 verification worked because the LOCAL clone already
has `origin` pointing at `https://github.com/Heroic-Games-Launcher/HeroicGamesLauncher.git`
(confirmed: `git remote -v`) with the merge-base commit already fetched into local history.
`actions/checkout@v6` in GitHub Actions, by default, adds a remote named `origin` pointing at
**the checked-out repo itself** (GameLib's own fork on GitHub, not Heroic) and performs a
shallow (`fetch-depth: 1`) checkout with no other remotes configured. Neither the Heroic remote
nor the merge-base commit's history exists in that environment without an extra step.

**How to avoid:** Do not run the D-07 diff live in CI. Run it as a periodic, human/`meta/`-CLI
task (`pnpm gen-i18n-gate-scope` or similar) that commits its output (a fork-file-list and/or
fork-added-key-list JSON) into the repo. The gate itself reads only that committed artifact —
zero network dependency, zero CI-environment risk. Refresh the artifact whenever
`package.json`'s `upstream.baseVersion`/`baseCommit` changes (i.e., whenever the fork rebases
onto a newer Heroic release).

**Warning signs:** A CI-only failure of the gate that cannot be reproduced locally; `git show`
returning "fatal: invalid object name" in Actions logs.

### Pitfall 2: `console.*` and JSDoc comment text look like code to naive heuristics

**What goes wrong:** A grep/regex-based first pass (or a hastily-written AST rule that doesn't
distinguish `SyntaxKind.SingleLineCommentTrivia`/`MultiLineCommentTrivia` from real
`StringLiteral` nodes) counts comment prose as violations.

**Why it happens:** This session hit this directly — `protonRating.ts`'s
`"No compatibility data available"` and `useDebouncedStoreSearch.ts`'s `"No Analog Found"` and
`SteamSignOut.ts`'s `"Logout"` all matched a naive `grep -oE "'[A-Z]...'"` pass but turned out
to be inside `/** ... */` doc comments on inspection, not executable code.

**How to avoid:** Use `ts-morph`'s AST (which already excludes comment trivia from
`StringLiteral` node traversal) rather than any text-based heuristic for the actual gate. Text
heuristics are fine for this research document's scale-sizing estimates but must not become
the gate's implementation.

### Pitfall 3: Brand-name literals are a genuine gray zone the gate WILL hit repeatedly

**What goes wrong:** `ConsoleMode/index.tsx`'s store-label map (`{ key: 'legendary', label:
'Epic', ... }`, lines 178-189) and `LogSettings/index.tsx`'s `baseFiles` array (`{ title:
'GameLib', args: {} }`, `{ title: 'Epic/Legendary', ... }`, lines 159-165) and
`StoreSearch/helpers.ts`'s `STORE_DISPLAY_NAME` map (`{ steam: 'Steam', gog: 'GOG', legendary:
'Epic', nile: 'Amazon' }`, lines 24-29) are all hardcoded brand-name strings, structurally
identical in shape to each other, but only SOME of the individual words (`Steam`, `Epic`, `GOG`
per D-02's explicit glossary) are pinned exempt — `Amazon`, `ZOOM`, `Amazon Games`,
`Epic/Legendary`, `Amazon/Nile` are NOT in D-02's literal glossary text and would need either
(a) glossary expansion or (b) `t()`-wrapping to pass a strict gate.

**Why it happens:** D-19's named targets ("ConsoleMode store labels", "LogSettings titles")
directly identify this exact code, but D-02's glossary list was written before this file-level
inspection and doesn't cover every brand/compound-name variant actually in use.

**How to avoid:** Flag this explicitly for the planner (see Open Questions) — the retrofit
tasks for these two files need either a glossary-list expansion decision or full `t()`-wrapping
of every store-name string, and this is a real, non-trivial judgment call, not a mechanical
diff output.

### Pitfall 4: the "in-scope target set" is materially larger than the 4 named files

**What goes wrong:** Planning the retrofit wave around only `RedeemSteamKeyDialog/copy.ts`,
ConsoleMode, LogSettings, and PlatformSupport under-scopes the work.

**Why it happens:** D-19 itself flags this ("the exact target set is derived mechanically...
not from the audit list"), and this session's own mechanical file-diff against the merge-base
confirms it: **205 files under `src/frontend/**` are touched since the merge-base (104 wholly
new, 100 modified, 1 deleted)**. A bounded heuristic sweep of the 47 net-new non-test
`.ts`/`.tsx` files found at least one more confirmed real violation
(`appleRating.ts:31`'s bare `'Unrated'` return value, used as a rendered label with no `t()`
wrapping and no tuple-exemption shape) beyond the 4 named files, and did not attempt to fully
resolve every candidate to real/false-positive status (time-boxed; see Open Questions).

**How to avoid:** Treat the gate tool's own first run (in "audit," non-blocking mode) across
the full 104-file net-new set as the authoritative retrofit-target-generation step — a Wave 0
task — rather than trusting either the 2026-08-05 manual audit or this research session's
partial heuristic sweep. Both are directional, neither is exhaustive.
