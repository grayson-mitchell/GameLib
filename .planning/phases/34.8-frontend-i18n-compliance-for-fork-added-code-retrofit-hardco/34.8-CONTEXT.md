# Phase 34.8: Frontend i18n compliance for fork-added code - Context

**Gathered:** 2026-08-07
**Status:** Ready for planning

<domain>
## Phase Boundary

Every **fork-added** frontend surface becomes translatable via i18next, and a CI gate
prevents new hardcoded user-facing strings from ever landing again.

Three deliverables:

1. **Retrofit** — fork-added hardcoded strings become `t(key, 'Default')` calls, keyed into a
   new fork-owned `gamelib` namespace.
2. **Catalog tooling** — `en/gamelib.json` generated repeatably, plus a glossary-aware
   machine-fill script for the other 48 locales (built and proven, not bulk-run — see D-04).
3. **Enforcement gate** — a source-scanning check wired into CI, blocking, that fails on new
   hardcoded user-facing literals in fork code.

**Explicitly out of scope** (unchanged from ROADMAP.md § Phase 34.8):
- Upstream-inherited Heroic strings (~50: GOG REDmod, Gamescope, aria-labels) — churning them is
  pure merge-conflict surface against upstream.
- The backend error-code contract (~30 English error payloads from Steam bottle/clientSetup/bridge
  managers surfacing verbatim in the UI) — needs its own design phase (codes over IPC, frontend
  maps to `t()` keys) and must not churn live-verified Steam paths mid-Tauri-migration.

**Also out of scope by decision this session** (the split — see D-13/D-14):
- `src/frontend/screens/Login/components/SteamLogin/index.tsx` (~25 of the ~35 audited strings)
- `src/frontend/screens/WebView/useTauriOAuthLogin.ts`

**Compliance bar:** full key coverage in `en` + English fallback. `fallbackLng: 'en'` and
`returnEmptyString: false` are already set (`src/frontend/index.tsx:145-147`), so a missing key in
any of the 48 non-English locales renders its English default — never broken UI. Translated
coverage is polish, not the gate.

</domain>

<decisions>
## Implementation Decisions

### Namespace strategy (carried forward from the 2026-08-06 capture)

- **D-01:** All fork-added strings go in a **fork-owned `gamelib` namespace** —
  `public/locales/<locale>/gamelib.json`, used as `t('gamelib:steam.installQueued')`. Upstream
  Heroic catalogs (`translation`, `gamepage`, `login`) then stay byte-identical and merge cleanly
  across every future upstream sync. The parser already supports this:
  `namespaceSeparator: ':'`, `output: 'public/locales/$LOCALE/$NAMESPACE.json'`.

- **D-02:** The **glossary is non-negotiable.** Brand and platform terms are pinned
  do-not-translate: GameLib, Steam, Epic, GOG, Proton, CrossOver, Steam Deck. Units and platform
  names stay literal too (MB/s, Linux, macOS, Windows).

### Parser scope and the no-churn guarantee

- **D-03:** Flip **`keepRemoved: false` → `keepRemoved: true`** in `i18next-parser.config.js:39`.
  As configured today, `pnpm i18n` **deletes** every key the static lexer cannot see — which would
  prune upstream keys referenced dynamically or through aliased `t`, churning exactly the ~50 files
  the phase promises not to touch. With `keepRemoved: true` the parser only ever adds. Because
  every fork string is `gamelib:`-prefixed, the upstream namespaces receive nothing.
  Accepted cost: genuinely dead upstream keys stop being auto-pruned — harmless in a fork that is
  not the translation source of truth.

- **D-04:** ROADMAP.md:2204-2205's item (3) — *"run `pnpm i18n` to sync the stale en catalogs
  (en/login.json has zero Steam keys today)"* — is **SUPERSEDED** by D-01. The fork-namespace
  decision postdates that line. The item now reads: *generate `en/gamelib.json` and make that
  generation repeatable*. `en/login.json`, `en/translation.json` and `en/gamepage.json` are out of
  scope entirely, consistent with the phase's own out-of-scope section.

- **D-05:** The gate **mechanically asserts** that nothing under `public/locales/` changes except
  `*/gamelib.json`. This turns "we agreed not to touch upstream" into something CI proves after
  every parser run, and catches a mis-namespaced `t()` call that would otherwise silently write
  into `translation.json`. This is the backstop that lets D-11 stay permissive.

### Existing fork keys already in upstream namespaces

- **D-06:** Fork keys **already sit** in the upstream catalogs (`en/translation.json` has 80
  Steam-mentioning lines, `en/gamepage.json` has 54 — an upper bound that includes Heroic's own
  Steam-shortcut strings). **Leave them where they are.** The `gamelib` namespace starts from
  today forward; only newly-retrofitted text goes there. Migrating would mean DELETING keys from
  upstream catalogs — precisely what D-05 is designed to block — so leaving them lets the
  byte-identical gate switch on immediately with no exception window.
  **Accepted cost: a permanent split-brain.** Some fork strings live in upstream namespaces, some
  in `gamelib`. The phase MUST document this so it does not read as a bug later.

- **D-07:** Fork-added keys are identified by **diffing `public/locales/en/*.json` against the
  upstream Heroic merge-base**. Anything present in the fork but absent upstream is fork-added.
  Mechanical, exact, and re-runnable on every future upstream sync — which also makes it reusable
  as the allowlist source for the enforcement gate. Rejected: git blame/authorship (the fork has
  done substantial history rewriting across the Tauri phases) and the 2026-08-05 manual audit list
  (point-in-time sample, names examples with "etc.", so it cannot safely drive scope).

### Machine-fill for the 48 non-English locales

- **D-08:** **Build the script, do not bulk-run it in this phase.** 34.8 ships the glossary-aware
  machine-fill script as a repeatable `pnpm` task and proves it on one or two locales. Bulk-filling
  all 48 becomes a separate, revertible commit runnable at any time. Rationale: the phase gate is
  "no hardcoded strings" + `en` coverage; machine-fill is polish layered on top, and any script bug
  in a bulk run ships to 48 files at once.

- **D-09:** Script contract (carried forward from the 2026-08-06 capture):
  - Diffs each locale's `gamelib.json` against English; translates **only missing keys**.
  - **Never overwrites a non-empty value** — this is what lets human corrections survive re-runs.
  - Must preserve `{{interpolation}}` and `_one`/`_other` plural suffixes; pass the key path as
    context.
  - English is the only source of truth.

- **D-10:** MT provenance is tracked in a **per-locale sidecar manifest** (e.g.
  `public/locales/<locale>/gamelib.mt.json` listing MT-origin key paths). The script reads it to
  decide what it may overwrite, and a future Weblate import can turn it into "needs editing" flags
  rather than approved human translations. Chosen over a commit-message convention because
  provenance must survive rebases and squashes and be readable by the script at runtime.

- **D-11:** The script feeds the **existing upstream catalogs as read-only translation memory** —
  matching upstream values passed as few-shot context so `Install` in `gamelib.json` matches
  whatever Heroic already uses in that locale. Reads upstream catalogs, never writes them, so it
  stays inside D-05.

### Enforcement gate

- **D-12:** **Blocking in CI from day one** — no advisory grace period. Viable precisely because
  the split (D-13) defers the two hard files behind an explicit allowlist, so everything the gate
  sees on day one is already compliant. An advisory gate nobody fails is the exact failure mode
  this phase exists to prevent: hardcoded constants already shipped once.

- **D-13:** The gate **checks for hardcoded user-facing literals only — it does not enforce which
  namespace** a `t()` call targets. Any `t()` call passes. This keeps the gate simple and avoids
  false positives against the D-06 split-brain and against legitimate reuse of an existing upstream
  key from fork code. Namespace discipline for new strings is a review convention, backed
  mechanically by D-05.

- **D-14:** The gate MUST tolerate the repo's existing idioms without false positives:
  - dynamic `[key, default]` tuple tables (`CrossoverBadge`, `LibraryFilters`)
  - aliased `t` (`t2`, `tr`)
  - the deliberate English fallbacks in `repairFailure.ts`
  - `bootErrorSurface.ts`, which runs pre-i18n-boot and is **exempted with an explanatory comment**

- **D-15:** `meta/lintTranslations.ts`'s existing catalog checks (empty strings, extra keys,
  content-less tag mismatches) are **scoped to `gamelib.json` only** when wired into CI. Running
  them across all 49 locales would surface a wall of pre-existing upstream failures on
  Weblate-sourced data the fork does not own and cannot fix. Keeping the signal 100% actionable is
  what keeps the gate trusted.

- **D-16:** **Gate tooling is deliberately left OPEN for research.** ROADMAP.md:2205-2208 offers
  "either an eslint rule (`react/jsx-no-literals` with the allowlist) or a source-scanning
  extension to `meta/lintTranslations.ts`". The researcher decides, after measuring the D-14
  tolerance requirements against both.
  **Known starting constraint:** `react/jsx-no-literals` only sees JSX literals, so it cannot cover
  `.ts` files — which rules it out for `RedeemSteamKeyDialog/copy.ts` and (once un-deferred)
  `screens/WebView/useTauriOAuthLogin.ts`, both named targets. A second known factor:
  `lintTranslations.ts` today
  lints **catalogs, not source**, so extending it is a change in kind, not a simple extension.

### Scope split — deferred behind open phases

- **D-17:** **Deferred out of 34.8:** `SteamLogin/index.tsx` and `useTauriOAuthLogin.ts`.
  Reason — Phase 34.4.2 is mid-`/gsd-debug` on that exact Login screen (blocker F-34.4.2-19
  undiagnosed, live gate 0/5), and Phase 34.5's open gate fails at the `useTauriOAuthLogin`
  frontend-render layer. `loginInFlightUiReachability.test.tsx` also pins that screen's markup with
  5 mutation-proven gates, so rewriting its literals means editing pins under active diagnosis.
  Precedent: a 34.4.2 gate run was already aborted once because a concurrent session held
  uncommitted Login-screen edits.

- **D-18:** Deferred files carry **allowlist entries with expected violation counts that FAIL when
  stale.** When the retrofit eventually lands and a file's count drops to zero, the gate fails with
  "stale exemption — remove this entry". The exemption cannot outlive its reason and nobody has to
  remember. Chosen over a plain TODO comment (enforces nothing) and over a `deferred-items.md`
  ledger entry (a document cannot fail a build).

### In-scope retrofit targets (from the 2026-08-05 audit)

- **D-19:** Retrofit in this phase: `RedeemSteamKeyDialog/copy.ts`; the stray literals in
  fork-added mixed files (ConsoleMode store labels, LogSettings titles, PlatformSupport);
  `bootErrorSurface.ts` gets its exemption comment rather than a retrofit. Note the 2026-08-05
  audit names examples with "etc." — per D-07 the exact target set is derived mechanically from the
  upstream diff, not from the audit list.

### Weblate

- **D-20:** **Defer Weblate.** Do NOT stand up a GameLib project on Hosted Weblate in 34.8 — a
  young fork has no translator community and it would be an empty dashboard. Nothing here blocks
  adopting it later: the file format is exactly what Weblate consumes, and hosted.weblate.org's
  Libre plan plus its automatic-translation add-on remain available when a contributor community
  materializes. D-10's manifest is what makes that later import correct.

### Post-research micro-decisions (2026-08-07, resolving RESEARCH.md Open Questions 2 & 3)

- **D-21:** **Extend the glossary rather than `t()`-wrapping brand names.** RESEARCH.md Pitfall 3
  found compound/variant brand forms in live code that D-02's literal list does not cover:
  `Amazon`, `ZOOM`, `Epic/Legendary`, `Amazon/Nile`, `Amazon Games` (in
  `ConsoleMode/index.tsx:178-189`, `LogSettings/index.tsx:159-165`,
  `StoreSearch/helpers.ts:24-29`). These are added to the do-not-translate glossary
  (`meta/i18nGlossary.json` per D-02's spirit), **not** retrofitted. Consequence:
  **`ConsoleMode` and `LogSettings` need NO code change for their store-label/title maps** — the
  D-19 listing of them is satisfied by glossary coverage, not by a retrofit. `StoreSearch`'s
  `STORE_DISPLAY_NAME` map likewise stays literal. Rationale: brand names staying literal is
  exactly D-02's intent; wrapping them would change working code purely for uniformity and would
  put the same literal string in all 49 catalogs. Accepted cost: the glossary is a list that must
  be extended when a new store is added — the gate failing on an unglossed brand name is the
  reminder.

- **D-22:** **`PlatformSupport.tsx` is DROPPED from the retrofit.** Measured this session: its
  only literals are `title="Windows"` / `"macOS"` / `"Linux"` — exact D-02 glossary matches — and
  its one prose string is already `t()`-wrapped. Its appearance in the 2026-08-05 audit list (and
  therefore in ROADMAP.md and D-19) is a **false positive, superseded by measurement**. No code
  change. Rejected: wrapping the OS names for stylistic consistency — that would contradict D-02,
  which pins OS names literal. This keeps the phase's verification story clean: every retrofit
  task maps to a measured violation.

### Claude's Discretion

- How the `gamelib` namespace is registered with `i18next-http-backend` at runtime. `i18next.init`

  planner/researcher decides whether to add an explicit `ns` entry or rely on lazy loading via

- Key naming convention inside the `gamelib` namespace (the capture's example is

- Where the do-not-translate glossary physically lives and its file format.
- Which CI workflow hosts the gate — `lint.yml` (`pnpm lint`/`prettier`/`find-deadcode`),
  `test.yml` (`pnpm test:ci`), or `codecheck.yml` (`pnpm codecheck`). `lint-translations` is
  currently wired into none of them.
- What exactly counts as "user-facing" for the gate (aria-labels, `title` attributes, console
  strings) — not discussed; researcher/planner call.

## Existing Code Insights

### Reusable Assets
- **`i18next-parser` v9.3.0 is already installed and configured** — `pnpm i18n` works today. The
  `gamelib` namespace needs no new tooling, only `keepRemoved: true` (D-03) and `gamelib:`-prefixed
  call sites.
- **`meta/lintTranslations.ts` already exists** and already walks `public/locales` per language.
  Its `readFiles()` helper hardcodes the three upstream namespaces — adding `gamelib` there is the
  natural seam for D-15.
- **The 49 upstream locale catalogs are a free 48-language translation memory** for shared
  vocabulary (D-11) — already in the repo, no fetch required.
- **`meta/` is the established home for fork-owned build/lint scripts** (`buildCrossoverIndex.ts`,
  `downloadHelperBinaries.ts`, `verifyUpdaterSigningKey.ts`, …), all run via `esbuild --bundle |
  node` from `package.json`. The machine-fill script and any gate extension follow that pattern.

### Established Patterns
- **`t(key, 'Default')` renders correctly with no catalog entry** — `fallbackLng: 'en'` plus
  `returnEmptyString: false` plus the parser's `defaultValue: ''` means an extracted-but-empty key
  falls through to the inline default. This is what makes "en coverage + English fallback" a
  sufficient compliance bar.
- **Namespaces load lazily** — `i18next.init` declares no `ns` array, so `i18next-http-backend`
  fetches a namespace on first `useTranslation('x')`. Adding `gamelib` is additive.
- **Aliased `t` is already in use** (`t2`, `tr`) and dynamic `[key, default]` tuple tables are an
  established idiom — any source-scanning gate must model both (D-14).

### Integration Points
- `i18next-parser.config.js` — one-line `keepRemoved` change (D-03).
- `package.json` scripts — new machine-fill task, plus whatever the gate needs.
- One of the three CI workflows — the blocking wire-up (D-12).
- `meta/lintTranslations.ts` — namespace-scoped catalog checks (D-15), and possibly the gate itself
  depending on D-16's outcome.
