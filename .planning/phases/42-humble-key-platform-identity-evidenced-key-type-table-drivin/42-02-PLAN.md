<objective>
Widen the persisted local-redeemed record with an additive provenance field
(`source?: 'user' | 'ownership-exact'`, D-42-01) and expose it through the
existing `getClaimAnnotations` read side, WITHOUT yet writing any
`'ownership-exact'` record. This is the schema half only.

Purpose: D-42-01 reuses the existing REDEEMED state rather than minting a sixth
one, which conflates a user's explicit "Mark as redeemed" with a Steam-ownership
inference. The provenance field is the thing that keeps them distinguishable.
CONTEXT.md is explicit that the D-77 Undo gating must be RE-CHECKED against
records carrying the new value, not assumed to still hold — this plan performs
that re-check on the read side, so plan 42-03 can start writing the new value
into a surface that already understands it.

Output: a widened store type, a widened `ClaimAnnotation`, a provenance-writing
`markRedeemed`, and a provenance-emitting `getClaimAnnotations`.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| on-disk store -> backend | `humble_local_redeemed.json` is a mode-0600 user-writable file; its parsed contents drive UI state. |
| backend -> renderer | `getClaimAnnotations` is an IPC read channel (`humbleGetClaimAnnotations`) reachable from the renderer. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-42-05 | Information disclosure | `getClaimAnnotations` IPC payload | mitigate | The widened annotation carries only an enum discriminator. Task 2 pins the exact `Object.keys` set of every emitted annotation, so no key value or store internals can leak through the widening. The function's "Never includes a key value" docblock sentence is preserved. |
| T-42-06 | Tampering | hand-edited `source` value in the on-disk store | accept | An attacker with write access to `~/Library/Application Support/gamelib/store_cache/` already controls the whole Humble cache, including `redeemedAt` itself. The provenance field grants no new capability — the worst outcome is a mislabelled Undo affordance. Read side coerces any missing value to the SAFER default (`'user'`, the undoable-by-explicit-action case), never to `'ownership-exact'`. |
| T-42-07 | Repudiation | provenance of a state change is lost | mitigate | `markRedeemed`'s existing `appendAudit(..., 'mark_redeemed', ...)` call is untouched, so the audit trail continues to record the explicit action independently of the store field. Plan 42-03 adds the matching audit event for the inferred settle. |
| T-42-SC | Tampering | npm/pip/cargo installs | mitigate | No package-manager install in this plan. No new dependency. No `[ASSUMED]`/`[SUS]` package to gate. |
