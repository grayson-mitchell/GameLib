## PLANNER FINDING — read this before deciding this plan is optional

D-42-01 says an auto-settled key "renders under All-keys' `Redeemed` heading with
D-77's Undo affordance unchanged." That assumption is FALSE against the code.
Measured on `fix/steam-native-install-stability` @ `7bf39e3b5`:

| Link in the chain | Evidence |
|---|---|
| The Undo button is inside `{claimAction && ...}` | `HumbleKeyRow/index.tsx:114-130` |
| `claimAction` has exactly ONE supplier | `Keys/Waiting/index.tsx:222`; `Spares/index.tsx:79` passes `giftAction` only |
| The All tab's rows get `urgencyTier` and nothing else | `All/index.tsx:30` -> `HumbleKeyGroup/index.tsx:81` renders `<HumbleKeyRow humbleKey urgencyTier />` |
| The All tab never fetches annotations at all | `All/index.tsx` (44 lines, full file) has no `humbleGetClaimAnnotations` call |
| An auto-settled key can never reach Keys-waiting | `selectKeysWaiting` returns false for any `ownedElsewhere` key — `viewFilters.ts:62` |

So without this plan, an auto-settled key has NO Undo affordance anywhere in the
application, and CONTEXT.md success criterion 4 ("...and can be undone back to
REVEALED") is unreachable from the UI. The backend half already works —
`HumbleLibrary.undoRedeemed` (`library.ts:1356`) and the `humbleUndoRedeemed` IPC
handler (`ipc_handler.ts:108`) exist and are exercised by plan 42-03's tests.
Only the renderer path is missing.

This plan implements D-42-01's INTENT (undo reachable, under All-keys' Redeemed
heading, no new tab, no sixth state). The alternative — widening
`selectKeysWaiting` to admit `ownedElsewhere && state === 'REDEEMED'` keys — was
REJECTED: it changes tab membership, which D-42-01 explicitly did not sanction,
and after an undo it would render the "Finish activation" control on an owned key,
manufacturing exactly the surface the owning todo (wrongly) claimed already
existed.

Output: an annotation fetch in the All tab, one new narrow prop threaded through
`HumbleKeyGroup` to `HumbleKeyRow`, and a fourth enumerated D-22 exception.
