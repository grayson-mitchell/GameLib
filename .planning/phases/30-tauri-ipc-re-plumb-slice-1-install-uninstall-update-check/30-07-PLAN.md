<objective>
Close **G-30-02**: under the Tauri build, clicking Install on a Steam title hangs the "installing"
badge forever (live retest Test 1; also blocks the Install->Uninstall E2E, Test 4).

Root cause (ALREADY diagnosed — do NOT re-diagnose; see
`.planning/debug/steam-install-spinner-hangs-tauri-live-g3002.md` and the
`Gaps (retest cycle)` block in `30-HUMAN-UAT.md`): the native pre-download phase makes bare,
un-timed `steam-user` `getProductInfo()` PICS calls (`fetchInstalldir` via `resolveSteamInstallTarget`,
then `fetchAppInfo`/`getOwnedSets`/`fetchDlcInfos` in `buildDepotPlan`). `steam-user`'s
`getProductInfo` neither times out nor rejects when the CM socket is present-but-unresponsive — it
queues the job and the Promise **never settles**. Under Tauri the client is rehydrated from the
persisted store and `ensureConnected`'s fast-path (`user.ts:70-81`) returns `true` on any truthy
`client.steamID` without revalidating the socket, so a click-time `getProductInfo` can park forever.
`install()` therefore never returns AND never throws -> the sidecar handler's `await install()`
(`installFlowRegistration.ts:168`) never settles -> neither 30-05's `finally` (`hadError`) nor its
`catch` fires -> no terminal 'done' -> spinner stuck.

**Why 30-05 missed it:** 30-05 only handled the two SETTLED outcomes — a returned `{status:'error'}`
(the `finally`'s `hadError`) and a thrown error (the `catch`). A never-settling await is a THIRD
outcome, so neither guard can fire. 30-05's jest tests stay green because they mock the
depot/steam-user layer and resolve `install()` instantly.

**Fix strategy (two additive layers — do NOT duplicate 30-05's terminal-clear machinery, feed it):**

1. **PRIMARY — bound the CM primitives.** A small `withTimeout` wrapper on the install-path
   `getProductInfo` calls (and the pre-download `getContentServers`) converts a never-answered CM job
   into a bounded **rejection**. That rejection is already handled by the EXISTING machinery:
   `withPlanBuildRetry` retries it (bounded by `PLAN_BUILD_MAX_ATTEMPTS`) then rethrows ->
   `buildDepotPlan`/`downloadSteamDepots` fail -> `runNativeDepotDownload` returns/throws
   `{status:'error'}` -> 30-05's `finally`/`catch` pushes the terminal 'done' + surfaces the ERROR
   dialog. Zero new terminal-status logic.

2. **BELT-AND-SUSPENDERS — bound the pre-download PHASE.** Wrap the pre-download resolution portion of
   `runNativeDepotDownload` (`resolveSteamInstallTarget`) in the same `withTimeout`, returning
   `{status:'error'}` on stall. This guards against a FUTURE un-timed pre-download await that is NOT a
   `getProductInfo`, and guarantees the badge can never hang from the pre-download phase — WITHOUT
   bounding the streaming download (which runs AFTER this region and can legitimately take hours; see
   the placement note below).

**Deliberate placement deviation (recorded so a reviewer sees it is intentional, not an oversight):**
the diagnosis's belt-and-suspenders wording says "a watchdog around the handler's `await install()`."
A flat timeout on `await install()` is REJECTED here: CR-03/CR-04 deliberately REMOVED the 60s
sidecar-invoke deadline precisely because a real depot install runs far longer than any fixed bound,
and the handler cannot cheaply observe the streaming `progressUpdate` frames to disarm such a watchdog
(`ipc.ts`'s `sendFrontendMessage` is a one-way `webContents.send`, not a subscribable emitter). The
hang is specifically in the PRE-download PICS/plan-build phase (before any `progressUpdate`), so this
plan bounds THAT phase — at the `getProductInfo` layer and around `resolveSteamInstallTarget` — never
the streaming download. This satisfies the design constraint ("bound that phase, not the streaming
download") literally and is strictly safer for long installs.

**`ensureConnected` hardening — SCOPED OUT (documented follow-up).** The diagnosis lists "revalidate a
live socket in `ensureConnected`'s fast-path" as OPTIONAL ("include only if low-risk and additive").
It is NEITHER: it sits on the hot path of every steam-user caller (library sync, launch, install),
cheap socket "liveness" is not reliably detectable without an actual round-trip, and it is very hard
to test deterministically. The two timeout layers above fully close G-30-02 without it. Record it in
the SUMMARY as a deferred hardening item; do NOT implement it here.

Purpose: make the Tauri Steam install button ALWAYS leave the "installing" state — matching Electron —
even when the sidecar's long-lived steam-user CM connection has gone stale.
Output: `withTimeout` helper + bounded PICS/pre-download awaits + RED->GREEN tests + a both-builds
regression sweep proving the change is additive and non-regressive.
</objective>

async function withPlanBuildRetry<T>(signal, step, label?): Promise<T>
  for attempt 1..PLAN_BUILD_MAX_ATTEMPTS:
    try { return await step(getDepotClient()) }
    catch (err) {
      if (isNonRetryableDepotError(err)) throw err
      if (attempt === PLAN_BUILD_MAX_ATTEMPTS) break
