CM connection, calls `client.redeemKey(key)`, and classifies the outcome into the four SPEC REQ5

table-driven unit tests.

against these types and this method. Getting the reject-vs-resolve shape and the enum taxonomy right
here is what makes 3 of the 4 outcome branches work at all.

redeemKey's REAL contract (verified from node_modules/steam-user/components/apps.js:887, NOT the .d.ts):
- Resolves ONLY on EResult.OK, to { purchaseResultDetails, packageList }.
- REJECTS on every other outcome with an Error carrying err.purchaseResultDetails and err.packageList.

EPurchaseResult (node_modules/steam-user/resources/EPurchaseResult.js — 8 values, reference via
SteamUserLib.EPurchaseResult; do NOT import enums/EPurchaseResultDetail.js, a different 84-value enum
with a colliding 53):
  Unknown:-1, OK:0, AlreadyOwned:9, RegionLockedKey:13, InvalidKey:14, DuplicatedKey:15,
  BaseGameRequired:24, OnCooldown:53

Bucket mapping (SPEC REQ5):
  OK(0) -> 'success'
  AlreadyOwned(9) -> 'already-owned'
  InvalidKey(14) / DuplicatedKey(15) / RegionLockedKey(13) / BaseGameRequired(24) / Unknown(-1) -> 'invalid'
  OnCooldown(53) -> 'rate-limited'

packageList shape: Record<packageID(string), displayName(string)>; may be {} when 0 line items.
