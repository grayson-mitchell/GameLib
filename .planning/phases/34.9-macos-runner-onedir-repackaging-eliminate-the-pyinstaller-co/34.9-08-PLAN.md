<objective>
Build the tool that answers the question "did every file of every onedir runner actually make it
into the built bundle, executable and accounted for?" by looking at the artifact, rather than
inferring it from the absence of a packaging error.

Purpose: 34.9-RESEARCH.md Pitfall 2 is explicit — electron-builder issue #3940 records that binaries
inside `app.asar.unpacked` have not always been signed correctly, and that a `codesign --verify` on
the outer `.app` can pass while an individual nested binary is unsigned, with the rejection only
surfacing at `notarytool submit` time. This repo has an established lesson of exactly this shape:
a green suite has beaten a live gate three times, and a mutating call's own report is never accepted
as proof of its effect. This tool exists so the packaging claim has an artifact-level check.

Output: `meta/verifyRunnerBundle.ts`, its test, and a `pnpm verify:runner-bundle` entry point.
</objective>

<!-- Verified. -->

The shape being inspected, after plan 34.9-06's downloader and the renderer's public/ → build/ copy:

  <root>/**/build/bin/{arch}/darwin/{runner}/{runner}      <- the executable, three runners
  <root>/**/build/bin/{arch}/darwin/{runner}/**            <- ~100 sibling files, ~103 Mach-O per runner
  <root>/**/build/bin/{arch}/darwin/comet                  <- flat, OUT of scope
  <root>/**/build/bin/{arch}/{win32,linux}/...             <- flat, OUT of scope

Inside a packaged Electron `.app` the tree lands under
`Contents/Resources/app.asar.unpacked/build/bin/...` (asarUnpack), which is why the tool must SEARCH
for the `build/bin/{arch}/darwin` segment rather than assume a fixed prefix.

Measured expectation from 34.9-CONTEXT.md: a nile onedir bundle is 29MB across 108 files, 103 of
them Mach-O. Treat that as an order-of-magnitude sanity reference, not a hard equality — legendary
and gogdl have different dependency trees.

Tools available on this machine and on macOS CI runners (verified): `/usr/bin/codesign`,
`/usr/bin/file`, `xcrun notarytool` 1.1.2.

meta/downloadZig.ts is the precedent for argv-form `spawn` with no shell string (T-24-06).
</interfaces>

<signing_reality>
Do NOT write a check that asserts "signed with a Developer ID". Every real macOS CI run this repo
has ever executed shipped UNSIGNED — D-03/D-04 defer paid Apple Developer enrolment, and
34.9-RESEARCH.md Pitfall 4 names this explicitly. Signature state is therefore REPORTED as data
(`unsigned` / `adhoc` / `signed:<identity>`), never asserted as a pass condition. Presence,
executability and Mach-O-ness ARE asserted, because those are true regardless of certificates.
</signing_reality>
</context>

    - `inspectRunnerTree(root, arch)` returns, per runner in `['legendary','gogdl','nile']`: the resolved absolute path of `{runner}/{runner}`, whether it exists, whether its mode has any exec bit, whether `file` reports it as Mach-O, the total file count under the tree, the Mach-O count under the tree, and an array of `{ path, signature }` for every Mach-O found.
    - `summarise(results)` returns `{ ok, failures[] }` where `ok` is false when ANY runner is missing, non-executable or not Mach-O, or when a tree's file count is below 20 (a onefile binary smuggled in under a directory name).

    - The tool exits 0 when `ok` and 1 otherwise, and prints a human-readable table plus, when `--json` is passed, the raw structure.

  <action>
Create `meta/verifyRunnerBundle.ts` exporting `inspectRunnerTree` and `summarise` with the shapes in
`<behavior>`, plus a guarded CLI entrypoint taking `<root>` positionally and optional
`--arch=<x64|arm64>` (defaulting to `process.arch`) and `--json`.

Locate the tree by walking `root` for a directory whose path ends with
`build/bin/${arch}/darwin`, rather than assuming a fixed prefix — inside a packaged Electron `.app`
it sits under `Contents/Resources/app.asar.unpacked/`. Throw naming `root` and the arch when no such
directory is found, so a wrong path fails loudly instead of reporting three absent runners.

Determine Mach-O-ness by reading the first 4 bytes and matching the Mach-O magic values
(`0xfeedfacf`, `0xfeedface` and their byte-swapped forms, plus the fat-binary `0xcafebabe`),
falling back to argv-form `spawnSync('file', ['-b', path])` only when the read is inconclusive.
Reading magic bytes rather than shelling out per file keeps a ~300-file scan fast.

Determine signature state with argv-form `spawnSync('codesign', ['-dv', path])`, parsing stderr:
absence of a signature yields `unsigned`, an `adhoc` flag yields `adhoc`, an `Authority=` line
yields `signed:<first authority>`. Never treat any of these as a failure — record the value.

Enforce ONLY: each of the three runners exists at `{runner}/{runner}`, has an exec bit, is Mach-O,
and its tree holds more than 20 files. Do not inspect comet, do not inspect win32 or linux
directories, and do not inspect the sidecar.

Every external invocation is argv-form `spawnSync` with an argument array and no shell option.

Add a header comment recording why this tool exists: a packaging step that emits no error is not
evidence that every file arrived, and electron-builder #3940 plus tauri-apps/tauri#11992 both
produce exactly the silent-partial-success shape this inspects for.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| built application bundle → verification claim | this tool's output is what a human will rely on when deciding whether packaging succeeded |
| filesystem tree → `codesign`/`file` invocations | paths discovered by walking a directory are passed to external tools |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-34.9-07 | Tampering | nested Mach-O signature state | mitigate (detect, not prevent) | The tool enumerates every Mach-O in each runner tree and records its individual signature state, so the electron-builder #3940 failure mode — outer `.app` verifies while a nested binary is unsigned — becomes visible before `notarytool submit` rather than after. It cannot prevent the packager from skipping a file; it makes the skip observable. |
| T-34.9-23 | Tampering | absence of real certificates | accept (recorded) | No assertion in this tool depends on a Developer ID, because none is enrolled (D-03/D-04). Signature state is data, not a verdict, and a test mutation-proves that an `unsigned` file does not fail the run — so the tool cannot silently start claiming a signing guarantee it has never observed. |
| T-34.9-03 | Tampering | `codesign` / `file` invocations | mitigate | argv-form `spawnSync` with an argument array and no shell option, mirroring `meta/downloadZig.ts`'s T-24-06 control. Discovered paths are passed as a single argv element, so a filename containing shell metacharacters cannot become a command. |
| T-34.9-26 | Spoofing | a onefile binary smuggled under a directory name | mitigate | The file-count floor (>20 files per tree) plus the Mach-O magic check means a directory containing only a repackaged onefile executable fails, rather than passing as a onedir bundle and silently reintroducing the amfid tax this whole phase exists to remove. |
| T-34.9-27 | Repudiation | verification against the wrong root | mitigate | The tool throws, naming the root and the arch, when no `build/bin/{arch}/darwin` segment exists anywhere under the given path — so pointing it at the wrong directory produces a loud error rather than a clean-looking "three runners absent" report that could be misread as a packaging failure. |
| T-34.9-SC | Tampering | package installs | mitigate | This plan installs nothing; it adds one script, one test and one `package.json` entry. Mach-O detection reads magic bytes rather than pulling in a binary-format parsing dependency. No legitimacy checkpoint is owed. |
</threat_model>
