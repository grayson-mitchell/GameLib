# Phase 34.9 Gap Cycle 4: Code Review Report (Cycle 4)

**Reviewed:** 2026-08-14T21:45:00Z
**Depth:** deep (execution-verified where noted, not pattern-matching only)
**Files Reviewed:** 5

## Summary

Scope: `meta/runTs.cjs` (new compile-to-private-tmpdir wrapper, closes C3-01), its regression test
`meta/__tests__/runTs.test.ts`, `meta/lintTranslations.ts`'s C3-02 doc correction, the 15
`package.json` scripts rerouted through the wrapper, and `34.9-REVIEW-SWEEP-CHECK.cjs` (the
generalised finding-disposition sweep tool, closes C3-03).

The core claim -- concurrent invocations of the same script no longer race on a shared outfile --
is TRUE and was independently re-verified by execution (10 concurrent invocation pairs, 0
cross-contamination; a forced compile failure correctly short-circuits and exits non-zero with
correct cleanup; a forced runtime exit code, 42, propagates correctly; the `node_modules` junction
correctly restores `require.resolve()` and does not touch the real `node_modules` on cleanup;
census of 15 wrapped scripts / 0 legacy-shape survivors confirmed against the live `package.json`;
the 3 regression tests pass).

However, the wrapper has **zero signal handling**. Execution-verified: sending `SIGTERM` (or
`SIGINT`) to the wrapper process alone -- exactly the operation `34.9-WRAPPER-PROOF.md` Direction B
row 11 prescribes for `build-runners-onedir` -- kills the wrapper immediately via Node's default
signal disposition, **without running `cleanupAndExit`**, and **without killing the spawned
child**, which is orphaned and continues running, unsupervised, to completion. This both leaks the
tmpdir and directly contradicts the proof contract's own stated methodology and PASS bar for the
one direction of that contract that actually uses process termination as a control mechanism. This
is the standout finding (C4-01) and should be fixed, or the proof contract's Direction B row 11
methodology corrected to account for it, before 34.9-32 runs on real hardware.

A second, narrower cleanup gap was found by inspection and confirmed with an isomorphic
reproduction: the `node_modules` junction/symlink is created *before* the `try/catch` block that is
otherwise responsible for guaranteeing tmpdir cleanup on error, so a `symlinkSync` failure leaks the
tmpdir via an uncaught exception (C4-02). Two further diagnostics/observability gaps were confirmed
by execution (C4-03, C4-04). One narrower inconsistency was found in the sweep tool by inspection
(C4-05).

## Critical Issues

### C4-01: No signal handling in `meta/runTs.cjs` — orphans the child process and leaks the tmpdir; invalidates `34.9-WRAPPER-PROOF.md` Direction B row 11's own methodology

**File:** `meta/runTs.cjs:45-172` (no `process.on('SIGINT'|'SIGTERM', ...)` handler exists anywhere
in the file); the two exit points that assume they will always run are `meta/runTs.cjs:127-130`
(`cleanupAndExit`) and its call sites at `meta/runTs.cjs:155` and `meta/runTs.cjs:163`.

**Verified by execution** (two independent repros run against the real file in this repo, not a
mock):

1. `node meta/runTs.cjs --bundle --platform=node --target=node21 meta/__sigtest_entry.ts &` (entry
   busy-waits 6s), then `kill -INT <wrapper_pid>` after 2s. Result: wrapper exits with code `130`
   (`128+SIGINT`, i.e. Node's *default* signal disposition — no JS handler ran at all), and
   `$TMPDIR/gamelib-runts-<random>/` **survives** on disk afterward.
2. Same shape with `kill -TERM <wrapper_pid>` (targeting the wrapper PID only, not the process
   group — precisely what `34.9-WRAPPER-PROOF.md` Direction B row 11 prescribes: *"terminate the
   process (`SIGTERM`, never `SIGKILL`, to give the wrapper's own cleanup a chance to run)"*).
   Observed: the wrapper process dies immediately; `pgrep` shows the **child `node
   .../gamelib-runts-7q9YYc/__sigterm_test.cjs` process is still alive** and keeps printing its own
   output for the remainder of its 8s run, fully unsupervised, after the wrapper is already gone.
   The tmpdir is never removed.

**Concrete failure scenario this produces on real hardware (34.9-32):** `build-runners-onedir` is
network- and filesystem-destructive against the vendored runner tree. Direction B row 11's entire
methodology is to launch it, wait for its first stdout line (proving argv arrived), then `SIGTERM`
the wrapper to prevent the network/destructive work from ever starting, and score PASS only if
`git status --porcelain` for `public/bin/`/`build/bin/` is empty afterward. As written, `SIGTERM` to
the wrapper does **not** stop `meta/buildRunnersOnedir.ts`'s underlying process — it orphans it. If
the compiled script has already passed the point where it prints its first line (which is exactly
when the proof's procedure fires the kill), the underlying network fetch and destructive write can
continue running in the background, undetected, and may complete before or during the "byte
-unchanged" check the proof relies on to declare the row PASS. This is not a hypothetical: the
mechanism (default-disposition kill of the parent while a `spawnSync`-launched child keeps running)
is demonstrated above against the real file.

Secondary, lower-severity consequence of the same root cause: any interactive Ctrl-C of *any* of
the 15 wrapped scripts (a routine developer action, not an edge case) leaks a `gamelib-runts-*`
directory (including its `node_modules` junction) under `$TMPDIR` every time.

**Fix:** Install `SIGINT`/`SIGTERM` handlers in `meta/runTs.cjs` that (a) forward the signal to the
currently-running child (`compile.pid`/track the live child reference — note `spawnSync` is
synchronous, so this requires switching the relevant call to `spawn()` + `execFileSync`-style
signal-forwarding, or at minimum registering the handler before each `spawnSync` call and killing
the last-known child PID on receipt), and (b) call `cleanupAndExit` (or at least `fs.rmSync`) before
re-raising/exiting. At minimum, `34.9-WRAPPER-PROOF.md`'s Direction B row 11 procedure must be
corrected to either (i) send the signal to the whole process group instead of the wrapper PID alone,
or (ii) explicitly identify and separately kill the orphaned child PID as part of the documented
procedure, and its "vendored runner tree byte-unchanged" PASS bar should not be trusted until this
gap is closed one way or the other.

## Warnings

### C4-02: `node_modules` junction creation runs outside the `try/catch` responsible for tmpdir cleanup — a `symlinkSync` failure leaks the tmpdir via an uncaught exception

**File:** `meta/runTs.cjs:113-120` (the `fs.symlinkSync` call) vs. `meta/runTs.cjs:132` (where the
`try` block that owns cleanup-on-error actually begins).

**Issue:** `meta/runTs.cjs`'s own header comment (lines 122-126) states *"Every exit path below
therefore removes tmpDir explicitly... (T-34.9-C4-03)"*, and the `catch` block at
`meta/runTs.cjs:164-169` exists specifically to guarantee that on an unexpected throw. But the
`fs.symlinkSync(...)` call that creates the `node_modules` junction executes *before* that `try`
block starts, so it is not covered by it. If `symlinkSync` throws for any reason (a plain-file
already occupying the destination, `EPERM` on a locked-down filesystem, or a junction-unsupported
volume), the exception propagates uncaught out of `main()`, and `cleanupAndExit`/the `catch`
block's `fs.rmSync` never runs — the freshly `mkdtempSync`'d directory leaks.

**Verified by execution** (isomorphic reproduction of the exact control-flow shape, not the literal
file, since forcing a real-world `EPERM`/junction failure requires an unusual filesystem): a
minimal script mirroring `meta/runTs.cjs`'s ordering (`mkdtempSync` → `symlinkSync` outside
`try/catch` → `try { ... } catch { rmSync } `) was run with `symlinkSync` forced to throw
(`EEXIST`). Result: the process exited with the uncaught-exception stack trace and exit code `1`,
and the tmpdir **survived** on disk — confirming the control-flow gap is real, independent of the
exact error code that triggers it.

This is a real, if lower-probability-than-C4-01, gap in the "every exit path cleans up" guarantee
this plan itself exists to provide — and per `deferred-items.md` item 33 and this project's own
standing note, Windows (where junction-creation permission issues are the most plausible real-world
trigger for this exact exception) has never been gate-tested for this phase.

**Fix:** Move the `fs.symlinkSync(...)` call inside the `try` block (or wrap it in its own
`try/catch` that calls `fs.rmSync(tmpDir, ...)` before re-throwing), so no code path between
`mkdtempSync` and the end of `main()` is uncovered.

### C4-03: `spawnSync` launch failures are silently swallowed — no diagnostic is ever printed when the child never starts

**File:** `meta/runTs.cjs:145-149` (esbuild `spawnSync`) and `meta/runTs.cjs:159-161` (node
`spawnSync`); the status check at `meta/runTs.cjs:151-157` never inspects `compile.error` /
`run.error`.

**Issue:** When `spawnSync` fails to launch the target executable at all (e.g. `ENOENT` — a
realistic scenario if the platform-specific `esbuild` optional dependency failed to install, or the
binary was corrupted), Node sets `status: null`, `signal: null`, and populates an `error` field —
but because the child process never started, `stdio: 'inherit'` produces **no output whatsoever**.
`meta/runTs.cjs` maps `status === null` to a bare `cleanupAndExit(1)` and never reads
`compile.error`/`run.error`, so the user sees only a silent `exit 1` with zero explanation of why.

**Verified by execution:** `spawnSync('/nonexistent/path/to/esbuild-binary-xyz', ['--version'],
{stdio:'inherit'})` returns `{status: null, signal: null, error: Error[ENOENT]}` with nothing
printed to the terminal — reproducing exactly the code path `meta/runTs.cjs:151-157` takes for this
class of failure.

This is a real regression in debuggability versus the retired `esbuild ... && node ...` shell idiom,
which would have surfaced a shell-level "command not found" message for the same failure.

**Fix:** Check `compile.error`/`run.error` and log it (e.g. `console.error(compile.error)`) before
calling `cleanupAndExit`, so a missing/corrupt binary produces a diagnosable message instead of a
bare exit code.

### C4-04: Signal-terminated and spawn-failed children are both collapsed to a flat exit code `1`, discarding signal-number fidelity

**File:** `meta/runTs.cjs:155` and `meta/runTs.cjs:163` — both `compile.status === null ? 1 :
compile.status` and `run.status === null ? 1 : run.status`.

**Issue:** `status === null` covers two distinct cases: the process failed to launch at all (C4-03),
and the process launched successfully but was killed by a signal (e.g. a targeted `kill -9
<child_pid>`, or an OOM-killer event against the child specifically, while the wrapper itself
survives and reaches this line normally — a real, if narrower, case than C4-01's parent-killed
scenario, and independently reachable since the child's own PID is visible to any external process,
as demonstrated in the C4-01 repro's `pgrep` output). Both are reported identically as exit code `1`
to the wrapper's own caller, discarding the conventional `128+signum` exit-code fidelity the
previous shell-based idiom preserved and giving a caller no way to distinguish "killed" from
"ordinary failure" by exit code alone.

**Verified by:** reading, cross-checked against the already-executed spawnSync semantics above (the
`status === null` branch is confirmed reachable both via launch failure, C4-03, and via signal
termination of a *surviving* wrapper, C4-01's `pgrep` evidence that the child process is a
separately-signalable PID).

**Fix:** If `run.signal`/`compile.signal` is set, propagate a signal-derived exit code (conventionally
`128 + signal number`) instead of a hardcoded `1`, so callers retain the ability to distinguish the
failure mode.

### C4-05: `34.9-REVIEW-SWEEP-CHECK.cjs`'s FIXED-row self-citation ban is case-sensitive while its polarity deny-list is case-insensitive — an inconsistent evasion path in the tool that exists to close exactly this class of loophole

**File:** `.planning/phases/34.9-macos-runner-onedir-repackaging-eliminate-the-pyinstaller-co/34.9-REVIEW-SWEEP-CHECK.cjs:157`
(`const citesSummary = combined.includes('SUMMARY')` — case-sensitive substring match) vs. lines
66-75 (`POLARITY_DENY_PATTERNS`, every entry built with the `/i` flag).

**Issue:** The tool's own stated purpose for the `SUMMARY` ban is to reject a FIXED row whose only
evidence is a plan's own self-asserting summary document (never independent proof) — but the check
is an exact-case substring match. A future FIXED row citing a plan summary document with different
capitalisation in its evidence prose (e.g. "...documented in this plan's Summary." rather than the
literal token "SUMMARY") would silently evade the ban, while the polarity deny-list two functions
over in the same file is deliberately case-insensitive for the identical class of self-assertion
concern. Checked against the real `deferred-items.md`: no row currently exploits this (all
mixed-case "Summary" occurrences found are prose, not Evidence-cell citations of a `*-SUMMARY.md`
path), so this is not a live false-negative today, but it is a real inconsistency in a
purpose-built anti-loophole tool's own logic.

**Verified by:** reading (confirmed the `/i` flags on `POLARITY_DENY_PATTERNS` at lines 66-75 vs.
the bare `.includes()` at line 157 by direct inspection of both), and by grepping the real
`deferred-items.md` for mixed-case "Summary" occurrences to confirm no current row is
mis-scored by this gap.

**Fix:** Make the citation-acceptance check case-insensitive to match the polarity check's own
convention (e.g. `/SUMMARY/i.test(combined)`), so the two self-assertion guards in this file apply
the same standard.
