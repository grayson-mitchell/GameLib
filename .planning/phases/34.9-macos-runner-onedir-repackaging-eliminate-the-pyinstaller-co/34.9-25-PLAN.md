<objective>
Convert every instance in the census from the exit-code-swallowing pipe to the `&&` idiom this repo
already uses, and correct every comment the conversion makes false.

Purpose: C2-01 is the reason verification truth 8 is still FAILED. `esbuild --bundle ... meta/X.ts |
node -` runs under `sh -c` with no `pipefail`, so the pipeline's exit status is `node`'s, and `node`
exits 0 after reading empty stdin from a failed compile. A future edit that breaks
`meta/verifyRunnerBundle.ts`'s compilation makes `pnpm dist:mac` report SUCCESS with zero
framework-integrity checking and no error anywhere in the log. A guard that can silently fail to
LOAD is not a guard.

`verify:updater-key` (`package.json:73`) already does this correctly and has for some time. This is
not a new mechanism; it is the existing one, applied to the instances that were missed.

The conversion also moves each script from stdin execution to file execution, which makes several
`meta/*.ts` comments -- ones that explicitly explain the stdin behaviour and route around it --
factually false. This phase already shipped that doc-accuracy defect once (IN-01/IN-02) and had to
correct and pin it. Correct them in the same change that causes them.

This plan does NOT prove the fix. Plan 34.9-26 owns the proof, in both directions, and it is the
step that decides whether this conversion counts.

**The target idiom, verbatim from `package.json:73`.** This is the template. Do not invent a
variation, do not add `set -o pipefail` (not portable across the `sh -c` npm uses), do not read
`PIPESTATUS` (it expands EMPTY under this project's zsh -- `deferred-items.md` item 15):

```
esbuild --bundle --platform=node --target=node22 --outfile=node_modules/.cache/verify-updater-key.cjs meta/verifyUpdaterSigningKey.ts && node node_modules/.cache/verify-updater-key.cjs
```

The shape is: same `esbuild` flags as before, plus `--outfile=<cache path>`, then `&& node <same
cache path>`. The entry file argument stays where it is. Nothing else moves.

**Cache path naming.** One cache file per SCRIPT, not per entry file, named
`node_modules/.cache/<script name with ':' replaced by '-'>.cjs`. Two scripts share an entry file
(`lint-translations` and `lint-translations:gamelib` both build `meta/lintTranslations.ts`) and must
still get distinct outputs, so a concurrent or interleaved run of both cannot have one clobber the
other's output between its own `esbuild` and its own `node`.

**Flags that must be preserved exactly per instance.** `--target` is not uniform: most censused
scripts use `node21`, and at least `build:sidecar-sea` uses `node22`. Carry each script's own
`--target`, `--platform` and any other existing flag through unchanged. Changing a target silently
changes what syntax esbuild downlevels.

**Prefixes that must be preserved.** Two censused scripts are not a pure copy of the others:
`lint-translations:gamelib` begins `export LINT_TRANSLATIONS_NAMESPACES=gamelib &&` and
`build:sidecar-sea` begins `pnpm build:sidecar &&`. The prefix stays at the front; the conversion
applies to the `esbuild ... | node` segment that follows it.

**Argument passthrough.** pnpm appends extra CLI arguments to the end of the full script string, so
after conversion `pnpm verify:runner-bundle build --arch=arm64` becomes `... && node
node_modules/.cache/verify-runner-bundle.cjs build --arch=arm64`, producing the same `process.argv`
slice the `node - build --arch=arm64` form produced. Plan 34.9-23 Section 6 measured this per
instance -- read that section rather than re-deriving it. Note that scripts ending in bare `| node`
(no trailing `-`) cannot receive appended arguments correctly TODAY at all, since `node <arg>` would
treat the argument as a filename; for those the conversion fixes argument passing rather than
preserving it, which is an improvement to record, not a risk to mitigate.

**What changes and what does not.** The conversion changes behaviour in exactly one circumstance:
the entry file fails to COMPILE. A runtime throw already propagates today, because `node` is the
pipeline's last command and its own non-zero exit is the pipeline's exit. Do not describe this
change as making the scripts "fail properly" in general -- they already do, for runtime failures.

**The `node_modules/.cache/` directory.** `verify:updater-key` already writes there, so the location
and its lifecycle are established precedent. Confirm from the audit's own measurements that esbuild
creates the directory when absent and that no clean script removes it mid-chain -- `clean:dist-mac`
operates on `dist/`, not on `node_modules/`. `node_modules/` is git-ignored, so nothing here is
committed.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| build-script exit code → the `&&` chain's decision to proceed | This is the boundary the whole fix exists to repair. `dist:mac` and `release:mac` gate `electron-builder` on `pnpm verify:runner-bundle`'s exit status; if that status is structurally unable to report a failure, the gate is decorative. |
| `node_modules/.cache/*.cjs` → executed program | The converted scripts execute a file written by the immediately preceding command. Whatever is at that path when `node` runs is what runs. |
| source comment → the next maintainer's mental model | A comment asserting stdin semantics after the conversion actively misleads: it would tell a future maintainer that `__dirname` is `process.cwd()` when it is `node_modules/.cache`, which is exactly the kind of wrong that produces a silent path bug. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-34.9C3-13 | Tampering | a stale `.cjs` executing instead of freshly compiled code | mitigate | The `&&` operator is the mitigation and it is exact: `node` runs only if `esbuild` exited 0, so a compile failure aborts before execution and a previous run's leftover `.cjs` is never reached in that invocation. Acceptance criteria assert, per script, that the `--outfile` path and the `&& node` path are the same literal string, so a typo cannot produce "compile to A, execute stale B". |
| T-34.9C3-14 | Tampering | an attacker- or accident-writable cache path | accept | `node_modules/.cache/` is inside the project's own git-ignored dependency tree, already used by `verify:updater-key` for exactly this purpose, and writable only by whoever can already write `node_modules/` — i.e. anyone who can already run arbitrary code via a postinstall script. Adding this file changes no trust boundary. Rationale recorded rather than mitigated; a defence here would be theatre against an attacker who already has the stronger primitive. |
| T-34.9C3-15 | Elevation of Privilege | cache path escaping the intended directory | mitigate | Every `--outfile` is a fixed literal under `node_modules/.cache/` with a filename derived from the script name; no interpolation, no user input, no variable expansion.
