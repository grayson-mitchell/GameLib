## Critical Issues

### C2-01: A compile failure in the wired guard is invisible — `dist:mac` proceeds unguarded

**File:** `package.json:71-72` (also `:69-70`, see C2-02/C2-03) *[now `:74-75, also :72-73` — **navigation only**, the pipe idiom quoted here is gone; see Citation amendment]*
**Status:** Proven empirically by the orchestrator before this review started; recorded here verbatim
per instruction, not re-derived.

**Issue:** `verify:runner-bundle` and `clean:dist-mac` are both defined as
`esbuild --bundle --platform=node --target=node21 meta/<file>.ts | node -`. npm/pnpm run scripts via
`sh -c`, which does not set `pipefail`; a POSIX pipeline's exit status is that of its **last** command.
When `esbuild` fails (bad import, syntax error, moved file), `node -` receives empty stdin, executes
nothing, and exits 0 — the pipeline reports success.

Proven empirically by the orchestrator with the repo's real esbuild on PATH:
- real esbuild, unresolvable entry → pipeline exit 0 (should be non-zero)
- real esbuild, genuine TypeScript syntax error → pipeline exit 0 (should be non-zero)
- control: the guard failing on its own merits (bad bundle dir) → exit 1 (correct)

**Failure scenario:** Any future edit that breaks `meta/verifyRunnerBundle.ts`'s (or `cleanDistMac.ts`'s)
compilation makes the corresponding `pnpm` script silently succeed. `dist:mac`'s `&&` chain then
proceeds straight to `electron-builder` with no framework-integrity check and no error anywhere in the
log.

**Fix:** (assess and refine; do not implement here) run the bundle through a temp file or
`node --input-type`, set `set -o pipefail` where the shell supports it, or invoke via `tsx`/a prebuilt
bundle so a compile failure surfaces as a non-zero exit. Any fix must be demonstrated failing against a
deliberately broken entry file before it counts, per this project's standing rule.

**Reachability:** Confirmed live by the orchestrator against the real toolchain — not theoretical.

### C2-06: `verifyRunnerBundle`'s top-level framework stub check is asymmetric — a dangling-target stub reports nothing

**File:** `meta/verifyRunnerBundle.ts:172-181` (`inspectFramework`, unchanged by this diff) and
`:459-470` (`summarise`, the code block gap cycle 2 changed)
**Status:** Pre-existing gap (the underlying data collection in `inspectFramework` was not touched by
this diff), but its consequence is directly adjacent to — and only fully visible by tracing — the exact
lines gap cycle 2 modified, so flagging it here per the review's own instruction to check for "a
framework malformed in a way that reports NOTHING because the condition was split in two."

**Issue:** `Versions/Current` gets three independent checks: exists, is-a-symlink, AND
**resolves to a real directory** (`resolvedVersionDirExists`, computed via `existsSync(join(frameworkDir,
'Versions', versionsCurrentTarget))` at line 166-170). The top-level stub (`Python.framework/Python`)
only gets two: exists and is-a-symlink (`inspectFramework`, lines 172-181) — there is no
`resolvedTopLevelTargetExists` equivalent, and `summarise()`'s new absent/wrong-type split (lines
459-470) only ever consumes `topLevelStubExists`/`topLevelStubIsSymlink`, so a stub that IS a symlink
but points at a non-existent or garbage target reports **zero** failures for that framework.

**Failure scenario:** A vendored onedir tree (or a `restoreSymlinks` run that recreates a Guard-B-passed
but nonetheless dangling target — e.g. a target string that's contained inside `destDir` lexically but
doesn't correspond to any file that actually exists there, such as after a partial vendoring download)
produces a `Python.framework/Python` symlink pointing at nothing. `verify:runner-bundle` reports PASS.
`codesign`/Gatekeeper would very likely still reject or misbehave on such a bundle at packaging or
launch time, with no earlier signal from the tool built specifically to catch this class of defect.

**Fix:**
```ts
// in inspectFramework, mirroring the Versions/Current resolution check:
let resolvedTopLevelTargetExists = false
if (topLevelStubIsSymlink) {
  const target = readlinkSync(topLevelStubPath)
  resolvedTopLevelTargetExists = existsSync(resolve(dirname(topLevelStubPath), target))
}
// in summarise, alongside the existing topLevelStub checks:
else if (!fw.resolvedTopLevelTargetExists) {
  failures.push(`${r.runner}: framework ${fw.path} is malformed -- top-level stub target does not resolve to an existing file (F-34.9-01)`)
}
```

**Reachability:** Theoretical/plausible, not concretely observed. It requires the same general failure
class that produced the (now-fixed) WR-02 "absent stub" shape, but this specific sub-shape (symlink
present, target dangling) has no fixture or observed instance in either gate run. Downgraded from what
it would otherwise be (this checker's whole purpose is catching exactly this kind of malformation)
because of that lack of concrete evidence.

## Checked, no defect found

Recorded per the review's own dimensions, since a `standard`-depth review that traces a mechanism and
finds it sound is still useful signal, not just a gap in coverage:

- **`isContainedSymlinkTarget` bypass surface** (`meta/preserveRunnerSymlinks.ts:121-138`): traced
  against absolute paths (rejected via `isAbsolute`), `..` traversal (correctly neutralised by
  `path.resolve`'s normalisation — this is the entire point of using `resolve` over string concatenation),
  `.` segments (correctly resolves to same dir), and prefix-collision (`/tmp/build` vs `/tmp/buildEvil`,
  correctly avoided by appending `+ sep` before `startsWith`, mirroring `resolveDestPath`'s own idiom).
  Multi-hop symlink chains (a restored symlink A pointing at another restored symlink B that itself
  escapes) are safe because each record is independently validated against its own literal target text —
  a chain can only ever get as far as B being independently `rejected` on its own record, at which point A
  still points at a location inside `destDir` (just a dangling one), never outside it. Case-insensitive
  macOS filesystems and Unicode normalisation differences (NFC/NFD) could theoretically cause a **false
  reject** (safe direction) but not a bypass, since the comparison is purely lexical against both sides
  built from the same `resolve(destDir, ...)` call. Empty-string targets are theoretically accepted (Node's
  `path.resolve` treats an empty segment as a no-op, so `isContainedSymlinkTarget('', ...)` styled input
  would pass) but this is unreachable in practice — `readlinkSync` cannot return an empty string for a real
  symlink. No bypass found.

- **Does `closeBundle`'s throw actually fail the build?** Traced through the installed
  `node_modules/vite`, `node_modules/rollup`, and `node_modules/electron-vite` sources directly (not
  assumed): Rollup's `bundle.close()` (`node_modules/rollup/dist/shared/rollup.js:24223-24228`) awaits
  `pluginDriver.hookParallel('closeBundle', [])` with no enclosing try/catch of its own, so a thrown error
  rejects the returned promise. Vite's `build()` (`node_modules/vite/dist/node/chunks/dep-DBxKXgDP.js:
  46206-46230`) calls `await bundle.close()` inside a bare `finally` block (no catch) — per standard JS
  semantics, an exception thrown in `finally` propagates and (if the `try` block already succeeded, as it
  does here) becomes the async function's rejection, superseding the successful return value. Finally,
  electron-vite's `build()` (`node_modules/electron-vite/dist/chunks/lib-B8V6ILNG.cjs:19-45`) directly
  `await`s each of the three `vite.build()` calls in sequence with no `Promise.allSettled`/swallowing, and
  the CLI's `build` command (`node_modules/electron-vite/dist/cli.cjs:78-92`) wraps the whole thing in
  `try { await build(...) } catch (e) { ...; process.exit(1); }`. The chain is unbroken end to end — no
  swallowing found. This independently corroborates (via static trace of the actual installed toolchain,
  not a live run) what the module's own doc comment already claims about Guard A being provably sound in
  its failing direction, even though it remains unreachable from today's fresh-checkout state.

- **`summarise()`'s new absent/wrong-type split** (`meta/verifyRunnerBundle.ts:459-470`): the three
  reachable states of `(topLevelStubExists, topLevelStubIsSymlink)` — `(false, false)`, `(true, true)`,
  `(true, false)` — are each handled by exactly one of the `if`/`else if` branches, with no combination
  silently producing zero failures for a malformed state within the property this check actually
  measures. (See C2-06 for the adjacent, pre-existing gap this exposed: the property measured is
  incomplete, not that the measured property is mishandled.)
