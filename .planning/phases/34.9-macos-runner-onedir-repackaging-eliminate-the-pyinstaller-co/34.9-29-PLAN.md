Close C3-01: every `package.json` script that compiles a `meta/*.ts` entry and then executes it
writes its compiled output to a path keyed only by SCRIPT NAME
(`node_modules/.cache/<name>.cjs`). Two concurrent invocations of the same script race on that one
file -- the reviewer measured 60/60 cross-contamination and the verifier independently measured
20/20, both at exit 0 with no diagnostic. This is the "reports success while doing something other
than what was asked" defect class, one layer below C2-01.

cross-platform wrapper `meta/runTs.cjs` -- not a partial fix, and not a risk-acceptance. A raw
`$$`/PID shell fix is NOT viable: `package.json` scripts run under `cmd.exe` on Windows, where `$$`
is not a PID.

Purpose: remove the shared mutable compile target entirely, while preserving the exit-code
short-circuit property gap cycle 3 spent a whole cycle buying.
Output: `meta/runTs.cjs`, all exposed scripts converted, one regression pin test.
</objective>

  <action>
    Create `meta/runTs.cjs` as a plain CommonJS `.cjs` file. It is deliberately NOT TypeScript and
    NOT bundled: it is the bootstrap, so it must run under bare `node` with zero compilation.

    Argv contract, which must be documented in a module-level comment at the top of the file:
    `node meta/runTs.cjs [esbuild flags...] <entry.ts> [args forwarded to the script...]`.
    Parsing rule: walk `process.argv.slice(2)`; every leading token beginning with `--` is an
    esbuild flag; the FIRST token not beginning with `--` is the entry file; every token after the
    entry file is forwarded to the compiled script unchanged. This rule is what makes
    `pnpm verify:runner-bundle build --arch=arm64` work -- pnpm appends to the end of the resolved
    string, which lands after the entry file.

    The wrapper adds exactly ONE esbuild flag of its own: `--outfile`. Every other flag
    (`--bundle`, `--platform=node`, `--target=node21|node22`) stays in `package.json` and is passed
    through verbatim. Do not hardcode or imply any esbuild flag beyond `--outfile` -- per-script
    flags differ, and hiding them inside the wrapper would make the next census harder, not easier.

    Behaviour, in order:
    1. `fs.mkdtempSync(path.join(os.tmpdir(), 'gamelib-runts-'))` -- a private per-invocation
       directory. Use `mkdtempSync`, never a constructed or predictable path name.
    2. Compute the outfile as `<tmpdir>/<basename of entry with .ts stripped>.cjs`.
    3. Run esbuild via `spawnSync(process.execPath, [require.resolve('esbuild/bin/esbuild'), ...flags, '--outfile=' + outfile, entry], { stdio: 'inherit' })`. Resolve the binary through
       `require.resolve` rather than relying on PATH or on a `node_modules/.bin` shim, so the
       wrapper behaves identically on Windows where `.bin` entries are `.cmd` shims. Never pass
       `shell: true` anywhere in this file.
    4. If esbuild's `status` is not `0`, remove the temp directory and exit immediately with that
       same status (falling back to `1` when `status` is `null`, which is the killed-by-signal
       case). `node` must NOT be spawned. This is the exact property gap cycle 3 bought with `&&`;
       the wrapper preserves it rather than regressing it.
    5. Otherwise `spawnSync(process.execPath, [outfile, ...forwardedArgs], { stdio: 'inherit' })`.
    6. Remove the temp directory with `fs.rmSync(tmpdir, { recursive: true, force: true })` in a
       `finally` so it is cleaned up on the throw path too, then
       `process.exit(child.status === null ? 1 : child.status)` so the child's exit code propagates
       unchanged and a signal death never becomes exit 0.

    Do not reintroduce `esbuild ... | node -` anywhere in this file or in anything it spawns: a
    pipeline's exit code is the last command's, which is the defect gap cycle 3 eliminated.
  </action>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| developer shell -> meta/runTs.cjs | Local developer/CI argv crosses into the wrapper |
| meta/runTs.cjs -> os.tmpdir() | Wrapper writes executable code into a shared-tenancy directory |
| meta/runTs.cjs -> spawned node | Forwarded argv crosses into a child process |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-34.9-C4-01 | Tampering | temp dir creation in `meta/runTs.cjs` | mitigate | Use `fs.mkdtempSync` (0700, randomised suffix) -- never a constructed or predictable path. A predictable name in the shared `os.tmpdir()` is pre-creatable as a symlink by another local user, redirecting the compiled output write. |
| T-34.9-C4-02 | Elevation of Privilege | executing the compiled outfile | mitigate | The outfile path is always inside the `mkdtempSync` directory this invocation just created; the entry path comes from `package.json`, never from forwarded argv. `node` is spawned on the outfile only after esbuild exits 0. |
| T-34.9-C4-03 | Information Disclosure | leftover compiled code on abnormal exit | mitigate | `fs.rmSync(tmpdir, {recursive:true, force:true})` in a `finally` so the directory is removed on the throw path as well as the normal path. Residue is bundled repo source, not secrets, so severity is low -- but a growing set of world-readable `gamelib-runts-*` directories is avoidable hygiene. |
| T-34.9-C4-04 | Tampering | argv forwarding into the spawned child | mitigate | `spawnSync` with an argv ARRAY and no `shell: true` anywhere, so forwarded arguments are never re-parsed by a shell. Pinned by an acceptance criterion (`grep -c 'shell: *true'` returns 0). |
| T-34.9-C4-05 | Denial of Service | concurrent invocations | mitigate | This is the finding itself: per-invocation private directories remove the shared mutable target, so concurrent runs cannot corrupt each other. Proven separately in plan 34.9-32 Direction C. |
| T-34.9-C4-SC | Tampering | npm/pip/cargo installs | accept | This plan installs NO new packages. `esbuild` is already a project dependency and is resolved through `require.resolve` from the existing lockfile-managed tree; no package-manager install task exists in this plan, so the legitimacy gate has no applicable surface. |
</threat_model>
