## Prepared answers to likely maintainer pushback

**"This makes the macOS asset ~2.2-3.6x bigger."**
True and quantified per-repo in each PR body (legendary ~2.3x / 30MB, gogdl ~2.3x / 25MB, nile
~3.6x / 29MB in our builds — upstream's own release sizes may differ slightly). It's macOS-only —
Linux and Windows assets are byte-identical to before this change. The cost is disk space on a
platform where users already have plenty; the benefit is removing a ~20s-on-cold-spawn tax from
every login/install/launch action that shells out to the binary.

**"Now the macOS asset is an archive instead of a single binary — that's a breaking change for
downstream consumers."**
True, and unavoidable — `--onedir` is fundamentally a directory tree, not a file, so there is no
way to ship it as a bare downloadable binary. Consumers need to extract the archive and point their
path resolution at `<extracted>/<name>/<name>` instead of `<extracted>/<name>`. GameLib's own
`meta/downloadHelperBinaries.ts` change (this same phase, plan 34.9-04/06) is the worked example:
the vendoring downloader was updated to detect an archive asset, extract it, and preserve
executable bits recursively, with `archSpecificBinary()` extended to resolve the binary inside the
extracted directory rather than assuming a flat file. Happy to link the exact diff if useful for
review.

**"Why not do this on Linux and Windows too, for consistency?"**
Deliberately not — the mechanism is macOS-specific. `amfid`'s per-file Gatekeeper assessment is a
macOS/Gatekeeper concept; Linux has no equivalent assessment step and Windows Defender/SmartScreen
does not behave this way for extracted PyInstaller payloads either. Switching those platforms would
only add the bundle-growth cost with no corresponding win, which is why every patch in this
submission leaves the Linux and Windows build legs completely untouched — same flag, same asset
shape, same file count as today.

**"Where do these numbers come from — can I reproduce them?"**
Full methodology (adhoc-signing both builds, 400s cold-idle separation, order-interleaved runs to
rule out ordering artifacts, and an honest report of two follow-up cold-measurement attempts that
failed their own validity check on our machine) is in each PR body's "Measured evidence" section
and, in more detail, at `GameLib`'s own
`.planning/phases/34.9-macos-runner-onedir-repackaging-eliminate-the-pyinstaller-co/34.9-MEASUREMENT.md`
and `.planning/debug/evidence/onedir-vs-onefile-measurement-2026-08-06.txt` (raw timings). Happy to
share either file directly if a maintainer wants to check the working before merging.

### What this means

Declining is an anticipated, legitimate outcome of this checkpoint, not a failure. The sourcing
strategy locked in `34.9-CONTEXT.md` is build-now-in-GameLib-CI **and** upstream-in-parallel; the
first half ships the win to GameLib users on its own. The consequence of this decline is narrow and
specific:

- **GameLib's local onedir build is not droppable.** `meta/buildRunnersOnedir.ts` and
  `.github/workflows/build-runners-onedir-macos.yml` remain load-bearing indefinitely, and GameLib
  owns their maintenance against upstream drift in the three runners' own CI files. The
  "drop the local build once upstream ships them" exit named in each PR body does not open.
- **Upstream drift is now a live maintenance risk.** `extractUpstreamPyinstallerCommand()` derives
  its command from each repo's real workflow file at the pinned tag. If a future tag bump changes
  that invocation, the local builder must be re-checked — the patches here are pinned to
  `v1.1.2` / `0.20.43` / `v1.2.1` and will go stale.
- **Heroic's own macOS users keep paying the amfid tax.** Not GameLib's problem to carry, but it is
  the argument these PRs were built on, and it stays unmade.
