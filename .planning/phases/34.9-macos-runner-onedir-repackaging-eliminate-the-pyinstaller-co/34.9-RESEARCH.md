# Phase 34.9: macOS runner onedir repackaging - Research

**Researched:** 2026-08-07
**Domain:** Cross-platform build/CI pipeline (PyInstaller packaging, GitHub Actions, electron-builder + Tauri v2 macOS code-signing/notarization, Node download tooling)
**Confidence:** MEDIUM — the build-flag change itself is HIGH confidence (measured); the signing/notarization surface is MEDIUM (verified against this repo's own code + electron-builder/Tauri issue trackers, but **never live-proven on this repo's actual macOS signing path**, which has shipped unsigned in every real CI run to date)

## Summary

The onedir/onefile choice is settled and measured (CONTEXT.md, ~95x cold-spawn win). The actual
work of this phase is almost entirely in three places this research grounds concretely against the
real files: (1) `meta/downloadHelperBinaries.ts`, which today assumes one file per runner and one
upstream repo per runner — both assumptions break for a GameLib-built, directory-shaped, macOS-only
artifact; (2) `src/backend/utils.ts`'s `archSpecificBinary()`/`getNileBin()` family, which — this
research **verified against the real code**, not assumed — almost certainly survives unchanged
because `splitPathAndName()` already returns `{dir, bin}` and `callRunner()` already spawns with
`cwd: runner.dir`, which is exactly the invocation shape PyInstaller onedir needs; and (3)
macOS code-signing, where this research surfaces two concrete, previously-undocumented risks: an
electron-builder issue (nested binaries inside `app.asar.unpacked` have a history of not being
signed correctly) and a Tauri v2 issue (`externalBin`/sidecar presence has an open, unresolved
notarization bug, tauri-apps/tauri#11992) that compound with the sheer file count (~100 Mach-O
files per runner × 3 runners × 2 arches).

The single most important finding, not previously documented anywhere in this project's history,
is **R-34.5-G1-PKG is still open**: in a *packaged* Tauri build, `publicDir` never resolves
correctly (`app.path().resource_dir()` has no `public/` or `build/` child, and `electronStub.
isPackaged` is hardcoded `false` under the sidecar). This means runner-binary resolution in a
packaged Tauri app — for the CURRENT single-file runners, before any onedir change — has **never
been live-proven**, only proven in `pnpm tauri:dev`. Phase 34.9 either inherits this as a blocking
prerequisite or must explicitly scope its own gate to Electron + Tauri-dev only, deferring Tauri-
packaged proof. See Common Pitfalls #1 and Open Questions #1.

**Primary recommendation:** Extend `archSpecificBinary()` (do not add a sibling resolver) to
return `.../darwin/{runner}/{runner}` on macOS while leaving Windows/Linux untouched; solve the
"where do onedir builds come from" question by reusing this repo's own existing "rolling,
non-`v*`-tagged, self-healing prerelease" pattern (`build-crossover-index.yml`) rather than
inventing a new one; and treat electron-builder + Tauri macOS signing of ~100 nested Mach-O files
per runner as the phase's real risk surface, not the PyInstaller flag.

### Pattern 1: Rolling self-healing GitHub Release as a build-artifact drop point

**What:** A GitHub Release with a fixed, non-`v*` tag (e.g. `runners-onedir-macos`), created as a
`prerelease` with `--latest=false`, whose workflow re-asserts those flags every run
(`gh release edit ... --prerelease --latest=false`) and re-uploads assets with `--clobber`.
**When to use:** Any CI-produced artifact that needs a stable download URL but isn't tied to an
app version tag. **Already proven in this exact repo** for `crossover-index` (daily rebuild) and
`updater`/`latest.json` (per-release promotion).
**Example:**
```yaml
# Source: .github/workflows/build-crossover-index.yml (verified against the real file, this repo)
gh release view crossover-index >/dev/null 2>&1 || \
  gh release create crossover-index \
    --title "CrossOver compatibility index" \
    --notes "Rolling artifact... Not a GameLib release." \
    --prerelease \
    --latest=false
gh release edit crossover-index --prerelease --latest=false
gh release upload crossover-index dist-index/crossover-index.json.gz --clobber
```
Applying this pattern to Phase 34.9: a new `build-runners-onedir-macos.yml` workflow, triggered by
`workflow_dispatch` (RELEASE_TAGS changes rarely enough that a cron schedule like
`build-crossover-index.yml`'s daily one is unnecessary overhead), running a `macos-13` (x64) +
`macos-14`/`macos-latest` (arm64) matrix, each leg cloning the pinned upstream tag, running the
upstream repo's OWN pyinstaller invocation with `--onefile` swapped for `--onedir`, archiving the
output dir, and uploading to the rolling release — then fetched by
`meta/downloadHelperBinaries.ts`'s darwin branch via the same `gh release download` shape
`release-tauri.yml` already uses for `crossover-index`.

### Pattern 2: `{dir, bin}` split at the resolver, never at the call site

**What:** `archSpecificBinary()` is the ONLY place that knows the on-disk shape (flat file vs
nested onedir folder); every caller (`getNileBin()`, etc.) calls `splitPathAndName(fixAsarPath(...))`
on whatever `archSpecificBinary()` returns, and every consumer (`nile/library.ts`,
`legendary/library.ts`, `gog/library.ts`, `helperBinaries/index.ts`) only ever destructures
`{ dir, bin }` and calls `callRunner`/`spawnSync` — never reconstructs or inspects the raw path.
**When to use:** This is exactly why the onedir shape change can be fully contained to
`archSpecificBinary()`'s own function body.
**Example:**
```typescript
// Source: src/backend/utils.ts:499-534 (verified against the real file)
function archSpecificBinary(binaryName: string) {
  if (process.platform === 'win32') binaryName += '.exe'
  const archSpecificPath = join(publicDir, 'bin', process.arch, process.platform, binaryName)
  if (existsSync(archSpecificPath)) return archSpecificPath
  const x64Path = join(publicDir, 'bin', 'x64', process.platform, binaryName)
  if (existsSync(x64Path)) return x64Path
  throw new Error(/* ... */)
}
```
The onedir-aware extension only needs to change what path is *tried* on `darwin` for
legendary/gogdl/nile specifically (e.g. `join(publicDir, 'bin', arch, 'darwin', binaryName,
binaryName)`), leaving the win32/linux branch and the x64-fallback logic byte-for-byte identical.
`comet` must NOT go through this new branch (it stays a flat Rust binary even on macOS — out of
scope per CONTEXT.md).

### Anti-Patterns to Avoid

- **Threading an `isArchive`/`isOnedir` boolean through every call site of `downloadGithubAssets`:**
  the filename extension (`.tar.gz` vs no extension) already carries this information — detect it
  in `downloadAsset` from the filename, don't add a parameter every caller must remember to set
  correctly for exactly 3 of 5 binaries on exactly 1 of 3 platforms.
- **Assuming the Tauri packaged build "just works" because Electron's does:** they use genuinely
  different asset-staging mechanisms (electron-builder's `asarUnpack` glob vs Tauri's
  `bundle.resources`, which is currently EMPTY in this repo's `tauri.conf.json`). Do not extrapolate
  Electron's proven packaged behavior onto Tauri without separately verifying it.
- **Rebuilding onedir runners inline in `release-tauri.yml` on every `v*` tag push:** couples an
  unrelated release cadence to an expensive, rarely-needed rebuild. Use a separate, on-demand
  workflow (Pattern 1).

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|--------------|-----|
| Extracting a downloaded tar.gz archive in Node | A manual gzip+tar-header parser | `tar` (npm, already a dependency) | Pure JS, no native deps, battle-tested (it's the same library `npm install` itself uses) |
| Stable CI-artifact drop location | A new bespoke tagging/versioning scheme | The existing rolling-release pattern (`crossover-index`/`updater`) | Already solved, already tested, already has a self-healing `--latest=false` guard against GitHub's "sole release becomes Latest" surprise (a documented Phase 19 lesson: `prerelease-not-Latest`) |
| Recursive chmod after extracting an archive | A hand-written directory walker | Node's `fs.chmod`/`chmodSync` with `{ recursive: true }` is NOT a thing in Node's fs API — must walk with `fs.readdir`/`fs.stat` OR shell out to `chmod -R`. **Flag for planner:** neither `tar` extraction (which preserves the exec bit from the tarball's own stored mode, if archived correctly) nor a bare Node primitive gives you "recursive chmod" for free — verify the archived tar entries carry correct mode bits at creation time (CI archive step) rather than trying to re-chmod everything after the fact | Getting the exec bit right at `tar -czf` creation time (CI) is simpler and more reliable than trying to restore it after extraction |

**Key insight:** This phase's genuine hand-rolled-solution risk is not "how do I extract an
archive" (solved, `tar` package) — it's "how do I make sure the exec bit and Gatekeeper-relevant
file attributes survive two hops" (CI archive → GitHub Release → download → extract → Vite copy
→ electron-builder/Tauri bundle). Each hop is a place a subtle permission or quarantine-flag loss
can occur, and none of them has an existing automated test in this repo today (see Validation
Architecture, Wave 0 Gaps).

## Common Pitfalls

### Pitfall 1: R-34.5-G1-PKG — packaged Tauri asset-root resolution is an OPEN, unproven residual

**What goes wrong:** In a *packaged* Tauri build, `GAMELIB_APP_ROOT` resolves to
`app.path().resource_dir()`, but `electronStub.app.isPackaged` is hardcoded `false` under the
sidecar (`src-tauri/src/main.rs` `resolve_packaged_app_root`, confirmed by reading the real
source). `publicDir` (`src/backend/constants/paths.ts:73-76`) therefore ALWAYS appends `'public'`,
never `'build'`, regardless of dev or packaged mode — and a packaged app's `resource_dir()` has no
`public/` child at all (nothing in `tauri.conf.json`'s `bundle` config stages anything there;
there is no `resources` key today).
**Why it happens:** This was explicitly named and left open by Phase 34.5 Plan 16
(`.planning/phases/34.5-.../34.5-APP-ROOT-SWEEP.md` § 3, "What this does NOT resolve: the packaged
asset root") — Plan 16 fixed the DEV-mode app root correctly and proved it live; the packaged-mode
asset root was called out as a **named residual**, not fixed, and the live gate that ran afterward
(`34.5-20`) was explicitly dev-only.
**How to avoid:** This phase's plan must make an explicit decision: (a) treat fixing
R-34.5-G1-PKG (adding a real `bundle.resources` entry + a packaged-mode `isPackaged`/asset-root
branch) as an in-scope prerequisite task, since otherwise the onedir work being packaged for Tauri
can never be proven to actually run in a real packaged Tauri build; or (b) explicitly scope this
phase's live gate to Electron-packaged + `tauri:dev` only, and document that Tauri-packaged
proof remains deferred (same limitation the 34.5 gate already carries). **Do not silently assume
(a) is already done — it is not.**
**Warning signs:** A packaged Tauri `.app`/`.dmg` where every store login (Amazon/Epic/GOG) fails
with a spawn ENOENT identical in shape to the one 34.5's live gate already diagnosed once
(`34.5-LIVE-GATE.md` root cause).

### Pitfall 2: Nested binaries inside `app.asar.unpacked` have a documented electron-builder signing history

**What goes wrong:** electron-builder issue #3940 ("Executables within app.asar.unpacked are not
being signed correctly in OSX 10.14.5") documents that binaries inside `app.asar.unpacked` have not
always been reliably signed by electron-builder's default macOS signing pass — worse for nested
directory trees (like a PyInstaller onedir bundle's internal `.so`/`.dylib`/data files) than for a
single flat executable.
**Why it happens:** electron-builder forwards signing to `@electron/osx-sign`, which walks the app
bundle looking for signable Mach-O files; deeply nested or unusually-shaped trees (a onedir output
has ~100 files, including non-executable data files sitting alongside dylibs) are exactly the shape
that has triggered false-negatives (files silently skipped) or false-positives (attempting to sign
non-signable files like `.framework` bundles) in the past.
**How to avoid:** After adding onedir to `mac.files`/`asarUnpack` in `electron-builder.yml`
(the existing recursive globs `build/bin/${arch}/darwin/*` and `build/bin/**/*` already cover the
new nested shape with no config change), the plan MUST include a verification step that inspects
the *signed* `.app` bundle (`codesign --verify --deep --strict` and a recursive
`find ... -perm +111 -exec codesign -dv {} \;` style check) rather than trusting that "no build
error" means "every file got signed." This has never been proven for this repo's macOS build
(every real CI run to date has shipped **unsigned** — see Pitfall 4).
**Warning signs:** `codesign --verify` passing on the top-level `.app` while an individual nested
binary is unsigned or ad-hoc signed — Gatekeeper/notarization will reject the whole bundle at
`notarytool submit` time, not at `codesign` time, so this can pass a local smoke test and still
fail Apple's notarization service.

### Pitfall 3: Tauri v2 externalBin/sidecar has an open, unresolved notarization bug (tauri-apps/tauri#11992)

**What goes wrong:** A GitHub issue opened 2024-12-17 against Tauri v2.1.1 reports notarization
failing with "the signature of the binary is invalid" specifically when `externalBin` (sidecar)
binaries are present — builds without a sidecar notarize fine. GameLib's Tauri config already uses
`externalBin: ["binaries/gamelib-sidecar"]`. Status at time of research: unresolved, no official
fix or workaround documented.
**Why it happens:** Unclear from available sources (Tauri's own docs don't detail how deep/
recursive its codesign pass is for externalBin specifically); the issue is filed and open, not
explained.
**How to avoid:** This is a pre-existing risk to THIS repo's Tauri packaging independent of
Phase 34.9 (the sidecar already exists) — but Phase 34.9 compounds the total signable-file count
substantially (adding ~100 files × 3 runners × 2 arches on top of whatever the sidecar already
contributes), which increases the chance of hitting this exact failure mode the first time this
repo's macOS signing path is exercised with real certs (D-03/D-04: it has never been exercised with
real certs — every live run shipped unsigned). **Flag this to the user as a known open upstream
risk before enrolling real Apple signing secrets**, not something this phase can definitively rule
out via research alone.
**Warning signs:** `notarytool submit` returning "Invalid" with a log entry naming the main
app binary (not a runner binary) as the invalid signature — a signature of ANY nested binary can
invalidate the outer bundle's own signature under Apple's sealed-resources model.

### Pitfall 4: This repo's macOS signing/notarization path has NEVER been exercised in a real run

**What goes wrong:** Every macOS leg of the one real tag-push gate run this repo has ever executed
(`actions/runs/30123449346`, referenced in ROADMAP.md's Phase 34 completion note) shipped
**unsigned** — "macOS+Windows signing gracefully skipped" — because D-03/D-04 deliberately defers
paid Apple Developer certs. This means Pitfalls #2 and #3 above are both currently **untested
against reality** in this repo; they are risks surfaced from the general electron-builder/Tauri
issue trackers, not confirmed failures here.
**Why it happens:** Signing requires a paid Apple Developer Program enrollment ($99/yr) plus
Developer ID certs, explicitly deferred by user decision in Phase 34.
**How to avoid:** Do not write a plan task that asserts "signing works" as a checked-off outcome
unless real Apple cert secrets get enrolled and a live gate actually runs `notarytool submit`
against a built onedir bundle. If certs remain unenrolled during this phase, the plan's gate should
explicitly verify "codesign --verify --deep passes on an ad-hoc-signed bundle" (achievable without
paid certs) as a weaker but honest proxy, and name the real signed-with-real-certs proof as
still-deferred, exactly like Phase 34 already does for its own signing surface.
**Warning signs:** A plan or verification step that reports "notarization passed" without a real
`notarytool submit` transcript to point to.

### Pitfall 5: `downloadGithubAssets`'s single-`repo`-per-runner assumption breaks for macOS-only sourcing

**What goes wrong:** Today, `downloadLegendary()`/`downloadGogdl()`/`downloadNile()` each call
`downloadGithubAssets(name, repo, tag, assetNames)` with exactly ONE `repo` string used for every
platform/arch combination. Phase 34.9's sourcing decision (build in GameLib CI now, upstream PRs in
parallel) means the **macOS assets** need to come from the GameLib fork's own rolling release,
while **Windows/Linux assets for the SAME three runners** still come from the existing upstream
repos. The current function signature has no way to express "different repo for a subset of
platforms."
**Why it happens:** The existing code was written when every platform/arch for a given runner came
from one place; this phase is the first to need a platform-conditional source.
**How to avoid:** Either (a) split each runner's darwin fetch into its own
`downloadGithubAssets` call against the GameLib-fork repo/tag, leaving the existing call
win32/linux-only; or (b) extend `downloadGithubAssets`'s `assetNames` shape to also carry an
optional per-platform repo override. Either is a real code-structure decision the planner must
make explicitly — it is not mentioned in CONTEXT.md's constraints list and was not previously
documented.
**Warning signs:** A plan that treats this as "just add darwin entries to the existing map" without
addressing that those entries need a DIFFERENT `repo` value than their win32/linux siblings.

### Pitfall 6: The `.release_tags` freshness check is keyed on `RELEASE_TAGS`, not on layout shape

**What goes wrong:** `compareDownloadedTags()` (`meta/downloadHelperBinaries.ts:200-221`) compares
`public/bin/.release_tags`'s stored JSON against the current `RELEASE_TAGS` map. If a developer
who already has the OLD flat-file `nile` binary on disk pulls this phase's code changes without
bumping any tag value (constraint 7: versions must NOT change, this is a packaging-only change),
`compareDownloadedTags()` will report "up to date" and `main()` will print "Nothing to download,
binaries are up-to-date" and skip re-downloading — leaving the OLD flat-file binary in place, which
the NEW `archSpecificBinary()` darwin branch will fail to find (it now looks for
`.../nile/nile`, not `.../nile`).
**Why it happens:** The freshness marker was designed for "did the upstream version change," not
"did the packaging layout change" — this phase is the first to change layout without changing a
version.
**How to avoid:** The plan needs an explicit migration step: either bump a marker distinctly from
`RELEASE_TAGS` (e.g. a `layout_version` field alongside the tag map, or intentionally re-keying the
darwin entries under a different `.release_tags` key like `nile-darwin-onedir`) so existing dev
checkouts and CI caches are forced to re-download, or a startup check in `archSpecificBinary()`
that detects the stale flat-file shape and errors loudly (consistent with the existing "throw
naming both attempted paths" pattern) rather than silently missing it.
**Warning signs:** A developer machine or CI cache that has the old `nile` file yet reports "up to
date" and then fails at runtime with the new nested-path lookup.

```typescript
// Source: src/backend/utils.ts:499-534
function archSpecificBinary(binaryName: string) {
  if (process.platform === 'win32') binaryName += '.exe'
  const archSpecificPath = join(publicDir, 'bin', process.arch, process.platform, binaryName)
  if (existsSync(archSpecificPath)) return archSpecificPath
  const x64Path = join(publicDir, 'bin', 'x64', process.platform, binaryName)
  if (existsSync(x64Path)) return x64Path
  throw new Error(/* names both attempted paths */)
}
```

### Current downloader single-file assumption (verified against the real file)
```typescript
// Source: meta/downloadHelperBinaries.ts:46-66
async function downloadAsset(binaryName, repo, tag_name, arch, platform, filename) {
  const url = `https://github.com/${repo}/releases/download/${tag_name}/${filename}`
  const exeFilename = binaryName + (platform === 'win32' ? '.exe' : '')
  const exePath = join('public', 'bin', arch, platform, exeFilename)
  await downloadFile(url, exePath)          // single file, straight to destination
  if (platform !== 'win32') await chmod(exePath, '755')
}
```
A darwin-onedir-aware variant needs to (1) download an archive instead of the final binary,
(2) extract it to `public/bin/{arch}/darwin/{binaryName}/`, (3) recursively ensure exec bits on
the tree (or trust the archive's own stored modes — see Don't Hand-Roll table), all while leaving
this exact function's win32/linux behavior byte-for-byte identical for legendary/gogdl/nile and
completely untouched for comet/epic-integration.
