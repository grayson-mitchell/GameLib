reopen the `34.9-WRAPPER-PROOF.md` Direction B row 11 risk C4-01 raised: that procedure only signals
the wrapper after observing the child's first stdout line, by which point handler registration
(which happens before the `esbuild` child is even spawned) has long since completed.

## Warnings

### C5-01: Tmpdir leaks if a signal arrives before the signal handlers are installed (startup-only race, real but narrow)

**File:** `meta/runTs.cjs:119` (`mkdtempSync`) through `meta/runTs.cjs:159-193` (the `for` loop
installing `FORWARDED_SIGNALS` handlers) — `process.on('exit', cleanup)` is registered at line 142,
*inside* this window, but does not help (see reproduction below).

**Issue:** The header comment at `meta/runTs.cjs:121-131` states cleanup on `process 'exit'` is "a
second, independent guarantee" covering exit paths the file "forgets to route through
cleanupAndExit." That guarantee assumes Node's `'exit'` event fires for every process termination.
It does not: when a signal arrives for which *no* `process.on(sig, ...)` listener is currently
registered, Node applies the signal's OS-default disposition, which terminates the process without
emitting `'exit'` at all. Between `mkdtempSync` (line 119, where the tmpdir is created) and the
completion of the `for` loop at line 193 (where the three forwarded-signal listeners are installed),
no listener for `SIGTERM`/`SIGINT`/`SIGHUP` exists yet, so a signal delivered in that window kills
the process via default disposition, and `cleanup()` — registered on `'exit'` at line 142, itself
inside this same unprotected window — never runs. This is the same failure mode C4-01 fixed for the
"handlers exist but never fire because `spawnSync` blocks the event loop" case, recurring here in a
narrower form: "handlers are correct once installed, but installation itself isn't instantaneous
from process start."

**Verified by execution, two ways:**

1. **Isomorphic repro** (proves the general Node behavior, not this file specifically): a 6-line
   script that only does `process.on('exit', () => writeFileSync(marker))` and then idles, with *no*
   signal handler registered, sent `SIGTERM` from outside 300ms after start. Result: process dies
   immediately (`ps -p` confirms), and the exit-marker file is never written — the `'exit'` listener
   did not run.
2. **Direct repro against the real file's actual control flow**, using the same technique
   `runTsSignalFixture.ts`'s own T5 test uses for C4-02 (generate a byte-identical copy of
   `meta/runTs.cjs` with one deliberate change, run it as `meta/runTs.__probe_race__.cjs` so
   `__dirname`/`node_modules` resolution behaves exactly as in production): spliced an 800ms
   synchronous busy-wait immediately after the real `mkdtempSync` call to reliably widen the
   pre-registration window. `SIGTERM` sent 200ms after spawn (inside the widened window): wrapper
   exits `143` (a plausible-looking, "correct" code) but `$TMPDIR/gamelib-runts-*` **survives on
   disk**. Non-vacuity control: same probe copy, `SIGTERM` sent 1200ms after spawn (*after* the
   widened window closes, i.e. handlers now installed): wrapper exits `143` and the tmpdir is
   correctly removed — proving the leak is specific to the pre-registration window, not a general
   regression. Both probe artifacts (`meta/runTs.__probe_race__.cjs` and the leaked tmpdirs) were
   removed after the repro; `git status --porcelain meta/` is clean.
3. Five consecutive attempts of `spawn` immediately followed by `kill -TERM` against the real,
   **unmodified** `meta/runTs.cjs` (no artificial delay) all exited `143` with no leak — confirming
   the window in the shipped file is real but sub-practical to hit without artificially widening it;
   this is a low-probability, not a systemic, gap.

**Why this doesn't reopen C4-01's `34.9-WRAPPER-PROOF.md` concern:** Direction B row 11's procedure
signals the wrapper only after seeing the child's first stdout line. By that point the wrapper has
already completed argv parsing, `mkdtempSync`, handler installation, `node_modules` symlinking, and
spawned + is running `esbuild`/the compiled script — all of which happens *after* line 193. The
startup window this finding describes closes well before any child (let alone its first stdout line)
exists.

**Fix:** Move the `for (const sig of FORWARDED_SIGNALS) { process.on(sig, ...) }` block to the very
first statements of `main()`, before `mkdtempSync` — register the handlers first, then create the
tmpdir the handlers are supposed to protect. (The handlers already tolerate `currentChild === null`
via the "nothing live to forward to" branch, so installing them before any child exists is already a
supported state — no behavioral change needed to the handler bodies themselves, only to their
registration order relative to `mkdtempSync`.)

## Info

### C5-02: `SIGHUP` forwarding has zero regression-test coverage

**File:** `meta/__tests__/runTsSignals.test.ts` (whole file — `describe` block only exercises
`SIGTERM` (T1), `SIGINT` (T2), and an external `SIGKILL` to the child (T4); no test sends `SIGHUP`).

**Issue:** `FORWARDED_SIGNALS` in `meta/runTs.cjs:97` includes `SIGHUP` alongside `SIGTERM`/`SIGINT`,
and the fix commit's own message (`fdc5b24e7`) lists `SIGHUP` as in-scope ("the terminal-closed case
that produces the exact same orphan+leak shape" per the file's own comment at lines 94-96). Manually
verified correct by direct execution during this review (wrapper exits `129` = 128+SIGHUP, tmpdir
removed, no leak) — so this is not a live defect — but it is the one forwarded signal this
otherwise execution-first regression suite does not pin, leaving it free to regress silently in a
future edit (e.g. a refactor of `FORWARDED_SIGNALS` or the per-signal branch) with no test to catch
it.

**Fix:** Add a `T6` to `meta/__tests__/runTsSignals.test.ts` mirroring T1/T2 but sending `SIGHUP`
and asserting exit code `129`, tmpdir removal, and child death — parallel structure to the existing
two tests, minimal marginal cost.
