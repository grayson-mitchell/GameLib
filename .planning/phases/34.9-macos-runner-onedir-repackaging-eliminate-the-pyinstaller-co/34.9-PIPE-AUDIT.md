# 34.9 Gap Cycle 3 — C2-01 Pipe-Swallow Census and Impact Audit

**Dated:** 2026-08-13
**Scope:** gap cycle 3, plan 34.9-23. Census for the C2-01 defect class (`esbuild ... | node`
swallowing a compile failure's exit code) across `package.json`. Changes no code and no script.

**The defect mechanism, one paragraph:** npm/pnpm run scripts through `sh -c`, which does not set
`pipefail`. A POSIX pipeline's exit status is the exit status of its LAST command. In
`esbuild --bundle ... meta/X.ts | node` (or `| node -`), when `esbuild` fails to compile
(syntax error, unresolved import, moved file), `node`/`node -` receives empty stdin, parses and
executes nothing, and exits `0` — the pipeline as a whole reports success, and any `&&` chain
downstream (e.g. `dist:mac`) proceeds as if the guard/build step had actually run.

## 6. Caller impact of loud failure

**The conversion changes behaviour in exactly one circumstance: the entry file fails to COMPILE.**
A runtime throw already propagates today, because `node`/`node -` is the pipeline's LAST command,
and its own non-zero exit IS the pipeline's exit under `sh -c`'s last-command-wins rule — there is
no swallowing to fix for a runtime error. Only a COMPILE failure (which never lets `node` execute
anything, so `node`'s own exit is always `0` regardless of what would have happened at runtime) is
swallowed today. This distinction matters so the eventual fix (plan 34.9-25) is not over-scoped to
"catches all failures" when it specifically closes the compile-failure blind spot.

**Using Section 4's baseline:** every one of the 12 distinct entry files compiles cleanly today
(exit 0). Therefore **no caller changes behaviour today, and the conversion is behaviour-preserving
on this checkout** — every currently-reachable caller (`.husky/post-checkout`'s
`download-helper-binaries` invocation, which throws for an unrelated, already-documented reason —
the digest sentinel check, not a compile failure) sees identical pass/fail behaviour before and
after the conversion, and every CI-reachable caller is presently BLOCKED UPSTREAM regardless. **This
is a statement about TODAY's tree only** — the entire point of the fix is to catch a FUTURE compile
break in any of these 12 entry files, which today's green baseline cannot exercise. Converting the
idiom changes nothing observable right now; it exists to change behaviour the next time someone
breaks one of these files' compilation.

**Argument-passthrough analysis.** The two known arg-receiving callers are
`pnpm verify:runner-bundle build --arch=arm64` (inside `dist:mac`/`release:mac`, `package.json:44,49`)
and `pnpm build-runners-onedir --arch=${{ matrix.arch }}` (`build-runners-onedir-macos.yml:107`).
Both target scripts use the `| node -` form. Empirically measured (real Node v26.2.0, this
hardware):

```
$ cat argv-probe.js | node - build --arch=arm64
["…/node","-","build","--arch=arm64"]

$ node argv-probe.js build --arch=arm64
["…/node","…/argv-probe.js","build","--arch=arm64"]
```

`process.argv.slice(2)` is `["build","--arch=arm64"]` in BOTH cases — the leading sentinel
(`-` vs. the emitted `.cjs` path) occupies `argv[1]` either way and every parser in this codebase
reads from `argv.slice(2)`. **`process.argv` matches between the two idioms for both arg-receiving
callers** — the conversion is argument-shape-preserving for `verify:runner-bundle` and
`build-runners-onedir`.

**Scripts that currently CANNOT receive appended arguments at all under the bare `| node` form**
(no trailing `-`): `download-helper-binaries`, `lint-translations`, `lint-translations:gamelib`,
`i18n-churn-guard`, `machine-fill-gamelib`, `build-crossover-index`, `gen-i18n-gate-scope`,
`gen-vtables`, `build-steam-bridge`, `build:sidecar-sea` — all ten scripts whose pipe form is bare
`| node`. Empirically confirmed (real Node v26.2.0):

```
$ cat argv-probe.js | node --arch=arm64
node: bad option: --arch=arm64        # exit 9 -- node treats the arg as ITS OWN flag,
                                       # never reaches stdin

$ cat argv-probe.js | node somearg
Error: Cannot find module '.../somearg'   # exit 1 -- node treats the arg as a FILE
                                           # to require(), never reaches stdin
```

Bare `node <arg>` treats any appended argument as either an unrecognized Node CLI flag (crash before
stdin is even read, if the argument is flag-shaped) or a module path to `require()` (crash, if it
isn't) — in neither case does the appended argument ever reach the target script, and in neither
case does the script's own program (piped via stdin) execute at all. **None of the ten bare-`| node`
scripts' real callers append any CLI arguments today** (per Section 5's caller map — no bare-`node`
script's invocation carries trailing arguments), so this is a latent defect, not an observed one.
For those ten scripts, converting to `node <cache>.cjs [args]` **FIXES argument passing rather than
preserving it** — today it is unconditionally broken for any hypothetical future caller that tried
to append arguments; after conversion it works like any normal Node CLI invocation.
