## Warnings

### C3-01: Concurrent invocations of the same pnpm script race on the shared `node_modules/.cache/<name>.cjs` outfile — one process silently runs the other's compiled code, exit 0, no diagnostic

**File:** `package.json` (all 13 converted scripts share this shape, e.g. `:70` `build-runners-onedir`,
`:71` `verify:runner-bundle`, `:69` `build-steam-bridge`, `:72` `clean:dist-mac`)

**Issue:** Every converted script writes to a path keyed only by the *script name*
(`node_modules/.cache/build-runners-onedir.cjs`, etc.), never by process, invocation, or argument
(e.g. `--arch`). I verified live, outside the repo, that when two processes run the identical
`esbuild --outfile=SAME_PATH ... && node SAME_PATH` command concurrently with different source
content, `node`'s read of `SAME_PATH` races the other process's `esbuild` write to it — across 60
paired trials, both directions of cross-contamination occurred (the faster process's `node` invocation
reading the *slower* process's still-in-flight-or-just-finished compile output) with **100%**
reproduction and **zero** crashes (esbuild's write is fast/atomic enough that a torn/partial read was
never observed, so the failure mode is silent wrong-content execution, not an error):

```
$ for i in 1..60: run (esbuild→outfile=shared.cjs; A) & (esbuild→outfile=shared.cjs; B) concurrently, wait
CROSS on iter 1 (A ran B's content)
...
CROSS=60 ERR=0   # every trial cross-contaminated; none crashed
```

The one place in this repo's current wiring where two invocations of the *same* script name could
plausibly race is `build-runners-onedir-macos.yml`'s x64/arm64 matrix
(`pnpm build-runners-onedir --arch=${{ matrix.arch }}`, `package.json:70`) — but I confirmed that
workflow explicitly runs each leg on its **own separate host** (`macos-13` for x64, `macos-14` for
arm64, per the workflow's own header comment), so CI itself is not exposed to this hazard. `dist:mac`
and `release:mac` (`package.json:44,49`) both also chain `clean:dist-mac`, `build-steam-bridge`, and
`verify:runner-bundle` — three more script names sharing this shape.

**Failure scenario:** A local developer, needing to produce both onedir architectures before the (not
yet existing, per this phase's own recorded background) x64 CI leg lands, manually reproduces the CI
matrix by running `pnpm build-runners-onedir --arch=x64` and `pnpm build-runners-onedir --arch=arm64`
in two terminals at once — a natural thing to try given the current workflow is `workflow_dispatch`-only
and each arch must otherwise be triggered and waited on serially. Whichever process's `node
node_modules/.cache/build-runners-onedir.cjs` happens to execute against the *other* process's
just-written compiled module can silently build the wrong architecture's runners into the arch-tagged
output tarball and `BUILD-MANIFEST-${arch}.json`, with `pnpm`'s own exit code reporting success. The
same hazard applies to a developer running `pnpm dist:mac` and `pnpm release:mac` concurrently (shared
`clean-dist-mac.cjs`/`build-steam-bridge.cjs`/`verify-runner-bundle.cjs`).

**Fix:** Key each invocation's outfile by something unique per invocation, not just per script name —
e.g. `node_modules/.cache/build-runners-onedir.$$.cjs` (`$$` = shell PID, via `sh -c`), or write to a
`mktemp`-created private directory and `rm -rf` it after `node` exits. A minimal fix scoped to the
scripts that can plausibly run twice concurrently (`build-runners-onedir`, and the three chained into
both `dist:mac`/`release:mac`) would close the realistic exposure without having to touch all 13.

**Reachability:** Confirmed live by me against the real, installed esbuild binary (100% reproduction,
60/60 trials). Not reachable through the current CI wiring (verified: matrix legs run on separate
hosts) — the plausible trigger is local/manual concurrent invocation, not an automated pipeline.

### C3-02: `meta/lintTranslations.ts:26`'s pipe/argv comment is now false, and the cycle's own "exhaustive" comment audit explicitly (and incorrectly) claims no such comment exists

**File:** `meta/lintTranslations.ts:17-28` (comment, untouched by this cycle); audit claim at
`.planning/phases/34.9-.../34.9-PIPE-AUDIT.md:396-398`

**Issue:** `lint-translations` and `lint-translations:gamelib` (`package.json:62-63`) are both driven
by `meta/lintTranslations.ts` and are both among the 13 scripts this cycle converted from
`esbuild ... | node` to `esbuild --outfile=... && node <file>`
(confirmed via `git log dfadf7433^..bd49d033d -- meta/lintTranslations.ts`, which returns **no
commits** — the file was never touched this cycle). Its module-level doc comment still reads:

> "Scope is read from `LINT_TRANSLATIONS_NAMESPACES` (comma-separated), not a CLI flag: this script
> runs through an `esbuild --bundle | node` pipe, so argv never reaches it..."

This is now factually wrong in the same way the 11 comments plan 34.9-25 *did* fix were wrong — the
script no longer runs through a pipe at all. Cycle 3's own audit document
(`34.9-PIPE-AUDIT.md` Section 7, "Stale comment inventory") explicitly enumerates 12 files with stale
require.main/`__dirname`/stdin claims "so plan 34.9-25 cannot miss one," and then states:

> "`meta/lintTranslations.ts` is deliberately excluded from this table -- it carries no comment
> asserting stdin/`require.main`/`__dirname` behaviour anywhere in the file..."

That claim is false — the file has a different but adjacent claim (pipe → argv unreachability) that the
audit's own predicate (scoped only to require.main/`__dirname`) never checked for. Plan 34.9-25's commit
message states "Every meta/*.ts comment... now describes the real post-conversion invocation," which is
therefore also not quite true: 11 of 12 relevant files were fixed, one was missed because the audit that
was supposed to catch it under-scoped its own search.

**Failure scenario:** A future maintainer reading this comment while deciding how to add a CLI-flag
based scope override (instead of the current env-var convention) would be told CLI args are mechanically
unreachable here — untrue post-conversion (`node <file> [args]` populates `process.argv` exactly like
`node - [args]` always did) — and could either avoid a legitimate simplification for a wrong reason, or
waste time re-discovering that the stated mechanism doesn't hold.

**Fix:** Correct or remove the stale premise, e.g.:
```ts
// Scope is read from `LINT_TRANSLATIONS_NAMESPACES` (comma-separated), not a CLI flag -- this is a
// deliberate convention (matching meta/verifyUpdaterSigningKey.ts's own CI-facing config), not a
// mechanical necessity: CLI argv is reachable via process.argv regardless of invocation form.
```
and correct `34.9-PIPE-AUDIT.md:396-398`'s claim, since it will otherwise mislead the next person who
trusts it as "every stale comment, enumerated."

**Reachability:** Confirmed directly — `git log` proves the file was never edited this cycle, and the
comment's own text is trivially readable at the cited line.

### C3-03: `34.9-C2-SWEEP-CHECK.cjs`'s FIXED-row "Independent confirmation" check never inspects the confirmation text's polarity — a contradicting cell passes

**File:** `.planning/phases/34.9-.../34.9-C2-SWEEP-CHECK.cjs:122-133`

**Issue:** For a `disposition: FIXED` row, `confirmationOk` only checks that the Independent-
confirmation cell (a) mentions a `meta/`, `src/`, or `package.json` path and (b) doesn't contain the
substrings `.planning/` or `SUMMARY`. It never checks that the cited text actually *affirms* a fix. I
verified live that a confirmation cell reading the opposite of what's claimed still passes:
```
$ node -e '... confirmation = "not actually fixed, meta/foo.ts still has the bug, package.json unchanged"; ...'
confirmationOk: true
```
The script's own header comment describes this as "scored only from an Independent-confirmation cell
naming a non-`.planning/` artifact" — which is accurate to what it does — but the surrounding prose
("Independent confirmation") reads as stronger content-verification than the regex actually performs.
This is not a live false positive today: I ran the script against the real `deferred-items.md` and it
correctly reported `C2-SWEEP-OK 8/8 mapped, unmapped 0`, matching the phase's own recorded claim. This
is a latent gap in the check's rigor, not a currently-wrong result.

**Fix:** Not blocking. If tightened, add a lightweight negative-language deny-list (e.g. reject
confirmation cells containing "not fixed", "still", "unchanged", "broken") or require an explicit
positive marker, so a future row can't accidentally pass by citing a real path in a sentence that
denies the fix.
