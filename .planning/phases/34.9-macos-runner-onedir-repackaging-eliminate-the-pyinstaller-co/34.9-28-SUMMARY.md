- **Found during:** Task 3 (STATE.md reconciliation), while reading the frontmatter values the
  plan's `<interfaces>` section stated as the confirmed baseline (`total_plans: 297,
  completed_plans: 284, percent: 74, completed_phases: 17, total_phases: 23`, as of plan 34.9-22).
- **Issue:** At Task 3's read time, STATE.md's frontmatter showed `total_phases: 24,
  completed_phases: 16, percent: 67` — a regression on two of three fields (`total_phases` up when
  no phase was added; `completed_phases` down when no phase was un-completed) and a percent value
  never seen anywhere in this project's prior history at that point in the sequence.
  `git show 0f852a623` (the commit landing plan 34.9-25's STATE.md update) confirms the mechanism:
  the same commit reverted `status` from `executing` back to `verifying`, `stopped_at` back to a
  stale 34.9-21-era value, and the three phase-axis fields to `24/16/67` in a single diff hunk —
  characteristic of the documented recurring `gsd-sdk` corruption pattern
  (`gsd-sdk-state-writes-corrupt-state-md`), not a targeted single-field write. `git log -p --
  .planning/STATE.md` shows `total_phases` had been stable at `23` and `completed_phases` at `17`
  across every commit in this gap cycle both before and after that one anomalous commit — no other
  phase completed or was inserted in that window that would legitimately explain the change.
  Plans 34.9-25, 34.9-26 and 34.9-27 each hand-corrected `completed_plans`/`total_plans`/
  `stopped_at`/`status` after their own executions but did not notice the phase-axis fields had
  also drifted, because none of their own diffs touched those specific lines.
- **Fix:** Restored `total_phases` to `23` and `completed_phases` to `17` — the values stable
  immediately before and (at 34.9-24's own commit `1d7f5d518`) immediately after the corruption
  window, confirmed via `git log -p`. Restored `percent` to `94` — the value legitimately recorded
  by that same `1d7f5d518` commit, immediately preceding the corrupting write — rather than to the
  plan's own stated planning-time expectation of `74`. This project's `percent` field has been
  observed oscillating across many unrelated values in its history unrelated to simple
  `completed_phases`/`total_phases` arithmetic (concurrent phases and quick-fix sessions each
  recompute it via their own `gsd-sdk` calls), so `94` — the last value this specific gap cycle's
  own sequence of commits legitimately produced — is the defensible restoration point, not a
  freshly-derived figure.
- **Files modified:** `.planning/STATE.md`
- **Verification:** `git show 0f852a623 -- .planning/STATE.md` and `git log -p --
  .planning/STATE.md` (both run this session) as cited above; `total_plans`/`completed_plans`
  independently re-verified against the baseline-plus-count formulas (`297 + 6 = 303`,
  `284 + 5 + 1 = 290`) and pass.
