## Decisions Made
- **`extractUpstreamPyinstallerCommand` folds `run:` values, not raw lines.** All three real upstream repos write their pyinstaller invocation as a plain YAML scalar folded across multiple more-indented physical lines (verified by fetching all three real, pinned-tag workflow files). A raw-line reading either misses the flags entirely or matches decoy lines (a step name, a `pip install` argument). Fixed to fold `run:` continuations the way GitHub Actions does, then filter to the value whose first token is literally `pyinstaller`.
- **`node -`, not `node --`, for the esbuild-pipe entrypoint.** The plan's specified script text (`| node --`) does not actually work once CLI arguments follow it — verified live: `node --` treats the very next token as a script filename to resolve as a module (throwing `MODULE_NOT_FOUND` on `--arch=arm64`), not as `process.argv`. `node -` is the correct explicit-stdin marker and passes all following tokens through untouched. Reproduced both the broken and working forms directly before fixing.
- **Resolve `repoDir` to an absolute path before it flows into any `spawn(..., { cwd })` call.** A relative venv-binary path (e.g. `pipPath(repoDir)`) combined with `options.cwd` set to that same relative `repoDir` double-nests, because node resolves a slash-containing `command` string against the *child's* cwd, not the caller's — reproduced live with a minimal repro before fixing.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] `node --` does not forward CLI args to the piped script**
- **Found during:** Task 2's own required plan-level verification (`pnpm build-runners-onedir --arch=arm64 --runner=nile`)
- **Issue:** The plan's specified script text ended in `| node --`. Once `--arch=arm64 --runner=nile` followed, node treated `--arch=arm64` as a script filename to `require()`, throwing `MODULE_NOT_FOUND`, rather than treating it as `process.argv`.
- **Fix:** Changed to `| node -` (explicit stdin marker). Verified with a minimal `echo ... | node -- --x` vs `echo ... | node - --x` repro before applying the fix.
- **Files modified:** `package.json`
- **Verification:** Real end-to-end build run (see below) now parses `--arch=`/`--runner=` correctly.
- **Committed in:** `253b7de3d`

**2. [Rule 1 - Bug] Naive physical-line pyinstaller matching breaks on real upstream YAML**
- **Found during:** the same real end-to-end verification run, against the actually-cloned `imLinguin/nile@v1.1.2` repo
- **Issue:** `extractUpstreamPyinstallerCommand` read raw physical lines for the substring `pyinstaller`. The real nile workflow (and, verified by fetching them, legendary's and heroic-gogdl's real workflows too) write the build step's `run:` value as a plain YAML scalar folded across several more-indented lines. This produced 3 raw-line matches (a step name, a `pip install ... pyinstaller` line, and a truncated `run: pyinstaller` with none of its flags) — never the usable one-line command CONTEXT.md quotes.
- **Fix:** Rewrote the extractor to recognize `run:` keys, fold their continuation lines the same way GitHub Actions does, then keep only the run value whose first token is literally `pyinstaller` (the real invocation, not a mention of the tool). Verified this generalizes correctly by fetching and inspecting all three real, pinned-tag upstream workflow files (only nile required an actual local build per CONTEXT.md constraint 1 — x64/arm64 must each build on their own host).
- **Files modified:** `meta/buildRunnersOnedir.ts`
- **Verification:** Real build against `imLinguin/nile@v1.1.2` now succeeds; `BUILD-MANIFEST-arm64.json` records the correctly-derived command `pyinstaller --onedir --name nile nile/cli.py` and the one dropped expression. Existing 25-test suite still green unmodified (its fixtures already used single-line `run:` values, which fold-then-filter handles identically).
- **Committed in:** `253b7de3d`

**3. [Rule 1 - Bug] Relative venv-binary paths double-nest under `spawn(..., { cwd })`**
- **Found during:** the same real end-to-end verification run (first attempt failed with `spawn .../pip ENOENT` even though `pip` existed on disk)
- **Issue:** `pipPath(repoDir)`/`pythonPath(repoDir)`/`pyinstallerPath(repoDir)` were built from a repo-root-relative `repoDir`. Passing that relative command string alongside `options.cwd: repoDir` to `spawn()` caused node to resolve the command against the *child's* cwd (i.e., `repoDir` itself), producing a doubled, nonexistent path.
- **Fix:** `repoDir` is now `resolve()`d to an absolute path at construction in `buildRunner()`, so every derived path (venv, pip, python3, pyinstaller) is absolute and immune to `cwd`-relative resolution ambiguity. Reproduced the bug with a minimal standalone repro (`spawn('.../python3', ..., { cwd: '...' })` → ENOENT) before fixing.
- **Files modified:** `meta/buildRunnersOnedir.ts`
- **Verification:** Real build succeeded after the fix; extracted `nile` binary ran and reported `1.1.2 Will A. Zeppeli`.
- **Committed in:** `253b7de3d`
