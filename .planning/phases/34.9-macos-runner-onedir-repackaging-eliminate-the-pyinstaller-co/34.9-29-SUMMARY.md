# Phase 34.9 Plan 29: meta/runTs.cjs compile-to-private-tmpdir wrapper (closes C3-01) Summary

**Cross-platform `meta/runTs.cjs` wrapper compiles every esbuild-then-run `package.json` script into a private `mkdtempSync` directory instead of a shared `node_modules/.cache/<name>.cjs` path, eliminating the concurrent-invocation race the cycle-3 reviewer measured at 100% cross-contamination; 15 scripts converted (one more than the plan's census, discovered live), plus two real bugs found and fixed during execution (a `process.exit`/`finally` ordering bug and a broken `require.resolve()` walk-up once the compile target moved outside the project tree).**

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] `process.exit()` does not run pending `finally` blocks; cleanup was silently skipped**
- **Found during:** Task 1, while authoring `meta/runTs.cjs`
- **Issue:** The plan's action text prescribed wrapping the compile/run logic in `try { ... process.exit(...) ... } finally { fs.rmSync(tmpDir, ...) }`. Empirically verified (`node -e "try { process.exit(3) } finally { console.log('finally ran') }"` prints nothing and exits 3) that Node terminates the process before the stack unwinds far enough to run a pending `finally` -- so the temp directory would never have been cleaned up on either exit path.
- **Fix:** Replaced the `finally`-based cleanup with an explicit `cleanupAndExit(code)` helper called immediately before every `process.exit()` call (compile-failure path, run-completion path, and the `catch` block for unexpected throws).
- **Files modified:** `meta/runTs.cjs`
- **Verification:** Manually confirmed a `gamelib-runts-*` directory count of 0 under `$TMPDIR` both before and after a healthy wrapper run.
- **Committed in:** `6c5902f9b` (Task 1 commit)

**2. [Rule 1 - Bug] esbuild's `bin/esbuild` is a native binary, not a JS file -- `spawnSync(process.execPath, [esbuildBin, ...])` fails**
- **Found during:** Task 1, first live run of the wrapper
- **Issue:** `require.resolve('esbuild/bin/esbuild')` resolves to a real Mach-O/ELF/PE executable (esbuild's own `install.js` overwrites the JS shim with the platform binary on install), not a `node`-runnable script. Running `node <that path>` produced `SyntaxError: Invalid or unexpected token` from Node trying to parse the binary as JavaScript.
- **Fix:** Spawn the resolved esbuild binary directly (`spawnSync(esbuildBin, [...flags], {stdio:'inherit'})`) instead of via `process.execPath`.
- **Files modified:** `meta/runTs.cjs`
- **Verification:** `node meta/runTs.cjs --bundle --platform=node --target=node21 <entry.ts>` now compiles and runs correctly; full wrapper-contract check (healthy + syntax-broken + unresolvable-import shapes) all pass.
- **Committed in:** `6c5902f9b` (Task 1 commit)

**3. [Rule 1 - Bug] Compiling into `os.tmpdir()` broke `require.resolve()` in 2 of the 15 converted scripts**
- **Found during:** Task 2, live-testing `pnpm build:sidecar-sea` and `pnpm verify:updater-key` after conversion
- **Issue:** `meta/updaterSigningKey.ts:95` (bundled into `verify:updater-key`) and `meta/buildSidecarSea.ts:145,156` (the `build:sidecar-sea` entry itself) each call runtime `require.resolve('<pkg>/<subpath>')` to locate a CLI tool's real on-disk path so it can be spawned as a separate process (not `require()`d for its exports). esbuild leaves these as genuine runtime `require.resolve` calls rather than statically bundling them. Node's CJS resolution algorithm walks up parent directories from the CALLING FILE's own location looking for `node_modules`; the pre-C3-01 `node_modules/.cache/<name>.cjs` idiom satisfied that walk by construction (one level up from `.cache/` is `node_modules/`). Compiling into `os.tmpdir()` (fully outside the project tree) breaks it: `pnpm verify:updater-key` failed with `PREFLIGHT GATE FAILED: cannot resolve @tauri-apps/cli/tauri.js`.
- **Census performed:** `grep -rln "require\.resolve(" meta/*.ts` (excluding `__tests__`) across the whole `meta/` tree (including `meta/sdk/`) found exactly these two source files; no other of the 15 converted scripts is affected. Also checked `__dirname` usage across `meta/` for the same failure class -- `genI18nGateScope.ts` and `cleanDistMac.ts` already have their own comments explicitly avoiding `__dirname` for this reason (predating this plan); `preserveRunnerSymlinks.ts`'s `__dirname` usage is in a Vite plugin never compiled by any of the 15 wrapped scripts (used directly by `electron.vite.config.ts`), out of scope.
- **Fix:** `meta/runTs.cjs` now creates `fs.symlinkSync(<repo>/node_modules, <tmpDir>/node_modules, 'junction')` immediately after `mkdtempSync`. Read-only from the compiled script's perspective; points at the same immutable project tree every invocation already shares (concurrent reads were never the C3-01 hazard, only the shared write target was), so this does not reintroduce anything C3-01 closed. `fs.rmSync` does not follow the symlink on cleanup (unlinks the entry, standard `rm -rf` semantics), so the real `node_modules` is never touched.
- **Files modified:** `meta/runTs.cjs`
- **Verification:** `pnpm build:sidecar-sea` now completes end-to-end (real SEA sidecar binary produced at `src-tauri/binaries/gamelib-sidecar-aarch64-apple-darwin`). `pnpm verify:updater-key` now reaches its own business logic (fails only on the expected missing `TAURI_SIGNING_PRIVATE_KEY` env var in this dev environment, not on CLI resolution). Full suite: 250/250 test suites, 4862/4863 tests (1 pre-existing skip), zero regressions -- up from 249/250 suites (1 failing) before the fix.
- **Committed in:** `e50c28e99`
