# Phase 34.9 — Packaging Limitations

This document exists so the honest state of "does the packaged app actually work" is on the
record as a durable artifact, not left implied or inferred from a config diff. It states what
Phase 34.9 proves, what it explicitly does NOT prove, who owns the gap, and the two open signing
risks that stay open regardless.

## What this phase proves

Two build modes are exercised by plan 34.9-11's live gate:

1. **The Electron PACKAGED build** (`pnpm dist:mac`, produced by `electron-builder --mac`) — this
   is the shipping artifact today, until Phase 35 removes Electron entirely. `electron-builder.yml`'s
   `mac.files` now carries every file inside the nested legendary/gogdl/nile onedir trees
   (`build/bin/${arch}/darwin/**/*`), and this is provable: the built `.app` bundle can be
   inspected directly.
2. **The Tauri DEV build** (`pnpm tauri:dev`) — under dev mode, `publicDir`
   (`src/backend/constants/paths.ts:73-76`) resolves to the source `public/` tree, which already
   contains the onedir binaries `pnpm download-helper-binaries` places there. This path works and is
   provable today.

## What this phase does NOT prove: Tauri-PACKAGED runner resolution

Staging the runner tree into the Tauri bundle (this plan's `bundle.resources` addition to
`src-tauri/tauri.conf.json`) is **necessary but not sufficient** for a packaged Tauri build to
actually find and run legendary/gogdl/nile.

The mechanism: `electronStub.app.isPackaged` is hardcoded `false` under the sidecar
(`src-tauri/src/main.rs`'s `resolve_packaged_app_root`, and `src/backend/sidecar/electronStub.ts`).
`publicDir` therefore **unconditionally** appends `'public'` to the app root:

```
export const publicDir = resolve(
  app.getAppPath(),
  app.isPackaged || process.env.CI === 'e2e' ? 'build' : 'public'
)
```

regardless of whether the running process is a dev sidecar or a packaged `.app`. A packaged Tauri
app's resource directory (`app.path().resource_dir()`) has no `public/` child — nothing stages one
there. So even with this plan's `bundle.resources` entry staging `build/bin/` into the packaged
resource root, **nothing will look for it at that staged path**: `publicDir` will still compute a
`public/`-suffixed path that does not exist in a packaged Tauri bundle, and every runner lookup
(`archSpecificBinary()` and its callers) will fail.

This is not a hypothetical. It is the same failure shape `34.5-LIVE-GATE.md` already diagnosed once
for Epic/GOG/Amazon spawn ENOENT under a dev-mode root-resolution bug; the packaged-mode case has
simply never been exercised.

## The two signing risks that stay open

1. **electron-builder issue #3940** — "Executables within `app.asar.unpacked` are not being signed
   correctly in OSX 10.14.5". Nested directory trees (a PyInstaller onedir output has ~100 files,
   including non-executable data files alongside dylibs) are exactly the shape that has historically
   triggered silent skips or false-positive signing attempts. Disposition: **mitigate (partial)** —
   this plan does not trust "no build error" as proof; `pnpm verify:runner-bundle` (plan 34.9-08)
   inspects the BUILT artifact and reports every nested Mach-O's signature state, and plan 34.9-11's
   gate runs it. Residual risk stays open until a real signed build is inspected.
2. **tauri-apps/tauri#11992** — open, untriaged upstream bug: Tauri v2 notarization fails with "the
   signature of the binary is invalid" when `externalBin` (sidecar) binaries are present. GameLib's
   Tauri config already ships `externalBin: ["binaries/gamelib-sidecar"]`, and Phase 34.9
   substantially increases the total signable-file count on top of it (~100 files x 3 runners x 2
   arches). Disposition: **transfer + record** — this is not closable inside Phase 34.9. It is
   recorded here as a known upstream risk to surface to the developer BEFORE real Apple signing
   secrets are enrolled. This plan's Task 3 pins `bundle.externalBin` unchanged
   (`["binaries/gamelib-sidecar"]`) so Phase 34.9 does not widen this risk's blast radius.

**Real-certificate signing has never been exercised in this repo.** Every real macOS CI run to date
has shipped unsigned — D-03/D-04 deliberately defer paid Apple Developer Program enrollment. This
means both risks above are currently untested against reality here; they are risks surfaced from
the general electron-builder/Tauri issue trackers, not confirmed failures in this repo. No task in
this phase claims "signing works" or "notarization works" as a checked-off outcome. The honest proxy
available to this phase is `codesign --verify` against an adhoc-signed bundle plus a per-file
signature-state report (plan 34.9-08's `verify:runner-bundle`). Real notarization proof
(`notarytool submit` against a build signed with real certificates) remains deferred until Apple
Developer credentials are enrolled.
