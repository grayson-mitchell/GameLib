<objective>
Port the Humble Next.js server-action adapter to Rust — session status, the library page and action-id discovery over
`Http`, and the paged library action with React Flight parsing and the redeem action over a new action-transport seam —
pinned on the wire to the TS and to the one real capture.

Purpose: every sync and reveal goes through this adapter. Cloudflare blocks every non-browser Next-Action POST (debug
humble-library-cloudflare-403), so the two server actions are posted from the app's own webview through
`HumbleActionTransport`, and only the GETs stay on reqwest. Only the live checks (94-29's dev smoke, D-09 items 1 and 2)
can finish the proof.
Output: action.rs and action/replay.rs, adapter/{session,action_ids,library_action,flight,redeem}.rs, http_replay.rs,
golden/adapter/deltas.json.
</objective>

<assumption_delta_decision>
Signal: the debug record splits one transport into two (the `pluralization` family: "the HTTP client" was the single
carrier of every Humble request; now a second carrier exists).
- Primary noun: the request kind (a GET of a page, chunk or session status, versus a Next.js server-action POST), not
  "the HTTP client".
- Decision: promote. Each request kind has exactly one seam: `Http` carries GETs (and the Steam store search),
  `HumbleActionTransport` carries server actions. Neither seam falls back to the other and no request kind has a second
  route; the old assumption "one HTTP client carries every Humble request" is demoted to "`Http` carries the GETs".
- Invariant test (accepted, in http_replay.rs): across every replayed case, no request carrying `next-action` reaches
  `Http`, and no GET reaches the action transport.
</assumption_delta_decision>
