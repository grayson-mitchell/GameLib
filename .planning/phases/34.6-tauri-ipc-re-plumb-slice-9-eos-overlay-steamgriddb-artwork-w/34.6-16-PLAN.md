<why_the_obvious_diagnostic_fails>

The todo's prescribed next step is *"instrument `tauriTransport.ts:118`'s `send()` and observe
whether it is entered at all for this channel."* Correct — but the naive implementation cannot
answer the question, and would produce a confident null result.

`send()` currently surfaces rejections through `window.api.logError`. **`logError` is itself a
send-kind channel** — the file's own recursion-guard comment says so. So the failure chain for a
rejected `winetricksInstall` send is:

1. `tauriInvoke(SIDECAR_SEND, {channel:'winetricksInstall', args})` rejects
2. `.catch` calls `window.api.logError(...)` — a NEW `send()` with `channel === 'logError'`
3. if that also fails, the top-level guard falls back to renderer `console.error`
4. renderer `console.error` does not reach `gamelib.log`

**That chain reproduces the observed symptom exactly: zero bytes written to `gamelib.log`.** It is
the surviving narrow form of the todo's candidate 3, and it is consistent with every measurement
taken so far — including `gamelib.log`'s mtime staying stale for 14 minutes after the click.

Therefore: **any diagnostic added to `send()` that travels over `send()` is unfalsifiable.** The
instrument must reach a sink that is not send-kind. Invoke-kind demonstrably works in this instance
(`winetricksAvailable` and `winetricksInstalled` both resolved with real data on the same panel, in
the same app instance, moments before the failing click).

</why_the_obvious_diagnostic_fails>
