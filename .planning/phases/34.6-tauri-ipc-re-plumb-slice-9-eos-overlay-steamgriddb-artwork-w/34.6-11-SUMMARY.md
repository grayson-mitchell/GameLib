This plan (34.6-11) is the dedicated, separately-committed hardening half.

## Per-Channel Enforced Properties

### `moveInstall` (`installFlowRegistration.ts`)
- **Property:** a renderer-supplied `path` that escapes the app's own configured `defaultInstallPath` (via `GlobalConfig.get().getSettings().defaultInstallPath`) is rejected before any move runs.
- **Enforced by:** `assertContainedPath(root, path, 'moveInstall')` as the first statement of the handler body.
- **Proven by:**
  - `'moveInstall rejects a path escaping the configured install root, and SteamGame.moveInstall is never reached (T-34.5-C6-49-03)'`
  - `'a rejected moveInstall still emits the terminal gameStatusUpdate "done" (never wedges in "moving")'`
  - `'a rejected moveInstall never logs the rejected path itself'`
  - `'moveInstall forwards a legitimate apostrophe-and-space-containing path (inside the configured root) to SteamGame.moveInstall() unchanged'`

### `importGame` (`installFlowRegistration.ts`)
- **Property:** same containment contract as `moveInstall`, applied to `path` only — `winePrefix`/`wineVersion`/`wineCrossoverBottle` are explicitly out of scope (see Residuals).
- **Enforced by:** `assertContainedPath(root, path, 'importGame')` as the first statement of the handler body.
- **Proven by:**
  - `'importGame rejects a path escaping the configured install root, and SteamGame.importGame is never reached (T-34.5-C6-49-03)'`
  - `'importGame forwards every field of its argument object through unchanged (path/platform to SteamGame.importGame(), winePrefix/wineVersion/wineCrossoverBottle to writeConfig())'`

### `runWineCommandForGame` (`wineToolsFlowRegistration.ts`)
- **Property:** a malformed `commandParts` (non-array, empty, or containing a non-string element) is rejected before it can reach `spawnAsync`/`runWineCommandOnGame`. On the Windows branch, the argv array is passed directly to `spawnAsync` (non-shell `child_process.spawn`) instead of being flattened into a shell string via `execAsync(commandParts.join(' '))`.
- **Enforced by:** `assertCommandParts(commandParts)` as the first statement of the handler body; `spawnAsync(command, commandArgs)` replacing the old shell call.
- **Proven by:**
  - `'REJECT: a non-array commandParts is rejected by assertCommandParts, and runWineCommandOnGame is never reached'`
  - `'ALLOW: a legitimate apostrophe-and-space-containing commandParts array reaches runWineCommandOnGame UNCHANGED (non-Windows branch, proves this is a shape check, not a content check)'`
  - `'the Windows branch calls spawnAsync with an argv ARRAY, never a shell-joined string'` (isolated-module sandbox forcing `isWindows: true`)

## RED-Proofs (channel-level, not merely the guard's own unit tests)

All four RED-proofs were performed by temporarily editing the real registration files (backed up via `cp` beforehand, restored via `cp` afterward — never `git checkout --`, which fires this repo's `post-checkout` hook), re-running the affected test file, confirming the exact expected test(s) failed, then restoring and reconfirming green.

1. **`installFlowRegistration.ts` containment removal** (both `moveInstall` and `importGame` calls wrapped in `if (false) assertContainedPath(...)`): the two REJECT tests and the no-wedge test failed exactly as expected (`expected 0 calls, received 1`; status sequence became `['moving', 'done']` instead of `['done']`). The path-not-logged test stayed green (no rejection occurred, so no log was emitted either way — expected, not a false negative, since that test only asserts absence).
2. **`wineToolsFlowRegistration.ts` shape-guard removal** (`assertCommandParts` call wrapped in `if (false) ...`): the shape REJECT test failed (`Received promise resolved instead of rejected`).
3. **`wineToolsFlowRegistration.ts` shell restoration** (Windows branch temporarily reverted to `spawnAsync('sh', ['-c', commandParts.join(' ')])`): the argv-array proof test failed (`Expected: "C:\Program Files\Sid Meier's Civilization V\game.exe"`, `Received: "sh"`).

Each file was `diff`-confirmed byte-identical to its pre-neutering state after restoration.

## Residuals (recorded honestly, not smoothed over)

**(a) Windows-branch unverified on real hardware.** `runWineCommandForGame`'s Windows branch (`spawnAsync` argv call) is proven only via a `jest.isolateModules()` sandbox forcing `isWindows: true` — every live gate this project runs is macOS-only. This mirrors the accepted residual already declared in the plan's own threat model as `T-34.6-34`.

**(b) The containment root is reconfigurable by the user.** `assertContainedPath`'s root is `GlobalConfig`'s own `defaultInstallPath` setting. A user who deliberately reconfigures that setting widens the containment boundary by design — this is intentional (the root must be the app's real configured install location, not a hardcoded path), but it means containment is only as strong as that setting's own trust, not an independent boundary.

**(c) `importGame`'s `winePrefix`/`wineVersion`/`wineCrossoverBottle` are NOT contained by this plan.** These are renderer-supplied (destructured directly from `ImportGameArgs`) and flow unchecked into `writeConfig(...)`, from where they are later read back as a Wine prefix directory and Wine binary paths when the imported game is launched. This is a real gap, not a false alarm — filed as `.planning/todos/pending/2026-08-24-importgame-wineprefix-wineversion-not-contained-by-34-6-11.md` with `resolves_phase: 34.6` / `planned_as: 34.6-14`, since Plan 34.6-14 (this phase's closing-artefacts plan) is the one that reads `34.6-11-SUMMARY.md`'s residuals and disposes of the phase's todos.

## This Discharge Is Source-Level, Not a Live Observation

Every proof above is a unit/integration test run against mocked collaborators (`SteamGame`, `libraryManagerMap`, `runWineCommandOnGame`, `spawnAsync`). It does **not** prove the hardened path still works end-to-end against a real Steam/Epic/GOG install or a real Wine process. Only `34.5-LIVE-GATE.md`'s step 5 (which exercises `moveInstall`/`importGame`/`runWineCommandForGame` on a real fixture) can say that. `T-34.5-C6-49-03` is NOT marked closed anywhere in this SUMMARY beyond describing what was built — the ledger disposition (`34.5-SECURITY-EVIDENCE-C6.md` and equivalents) belongs to Plan 34.6-14.

## Decisions Made

- The guard is used purely as a validation gate: its return value is discarded, and the original renderer-supplied path (not a resolved variant) flows downstream, so a legitimate input reaches `libraryManagerMap[...].getGame(...).moveInstall()`/`.importGame()` byte-for-byte unchanged.
- `spawnAsync` (already exported from `backend/utils.ts`, non-shell `child_process.spawn`) was reused for the Windows branch rather than introducing a new helper — this also matches this codebase's own established Wine-execution idiom (`launcher.ts`'s `runWineCommand`), which is more consistent than the old `execAsync`-based approach it replaces.
