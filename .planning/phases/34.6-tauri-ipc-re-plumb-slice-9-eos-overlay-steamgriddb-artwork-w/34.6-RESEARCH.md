## Summary

Phase 34.6 has two independent halves that share one blocking live gate. Half A ports 24 IPC channels from Electron's `main.ts`/module-local `ipc_handler.ts` files onto the Tauri sidecar's `*FlowRegistration.ts` registration layer: 16 previously-deferred channels (EOS overlay 8, SteamGridDB artwork 5, winetricks 3) plus 8 "late-discovered" channels found by the Phase 34.5 preload-surface audit (`frontendReady`, `getAchievements`, `getDefaultSavePath`, `getGogDiscounts`, `getPlaytimeFromRunner`, `importGame`, `moveInstall`, `runWineCommandForGame`). Half B runs live verification legs that were never exercised before under Tauri, re-homed from the parked Phase 34.7: Epic login, `egsSync`, legendary save sync, and Epic logout's `clearEpicCookies`.

This research independently re-verified every citation in 34.6-CONTEXT.md against source and found **three material citation errors** the planner must account for (detailed in Common Pitfalls): D-04's winetricks guard citation points at unrelated DXVK/VKD3D functions (the real `Winetricks` object has no `!isLinux` guard at all — it has genuine macOS support via a `macEnvs` branch); D-05's EOS dialog citation is off by 3 lines AND names the wrong function (the `enable()` dialog only fires when the overlay is NOT installed, so it will never fire during the install→enable→disable→remove round-trip — it's `remove()`'s unconditional dialog, the last step, that actually surfaces). This research also surfaced a security hazard `34.6-CONTEXT.md`'s D-02 section does not mention at all: `steamgrid/secureKey.ts` has an existing, already-written header comment stating that the moment `steamgrid/ipc_handler.ts` is wired into a sidecar registration module (exactly what D-06 requires), the SteamGridDB API key will be persisted in **plaintext** because `safeStorage` is a dead stub under the sidecar — and this hazard is independently confirmed by `keyring_account()`'s own doc comment in `src-tauri/src/main.rs`, which explicitly says SteamGridDB has "deliberately NO slot" in the allowlist today.

**Primary recommendation:** Port all 24 channels via the existing `*FlowRegistration.ts` pattern (2 files: `enrichmentFlowRegistration.ts` for SteamGridDB, `wineToolsFlowRegistration.ts` for winetricks, plus new/extended registration for EOS and the 8 late-discovered channels); harden the SteamGridDB API key onto a `SidecarKeyringSlotStore`-shaped seam (mirroring the `HumbleSecretStore` precedent from Phase 34.4.1 plans 12/13) as a same-phase prerequisite to D-06, not an afterthought; correct D-04's live-gate framing to "winetricks is data-dependent, not platform-gated" before writing the gate script; and re-derive (not hand-edit) Describe 7's `DROPPED_OR_DEFERRED` arithmetic when the 16 deferred channels flip from absence- to presence-assertion.

### The Two Send-Kind Channels — Total-Method Convention (D-11)

`frontendReady` and `winetricksInstall` are the ONLY two of the 24 in-scope channels that are send-kind (verified by checking all 24 — every EOS channel, all 5 SteamGridDB, `winetricksAvailable`/`winetricksInstalled`, and all 7 remaining late-discovered channels are `addHandler`/invoke-kind). Send-kind channels have no return value, so a caller cannot detect failure the way `callOrDeclare` detects an invoke-kind rejection. D-11 requires a NEW sidecar-handler-side observable (e.g., a log line proving the handler body actually ran) rather than changing these channels' fire-and-forget semantics.

**Precedent for the observable's shape:** `SidecarHumbleSecretStore`'s `installSidecarHumbleSecretStore()` function (`src/backend/sidecar/humbleSecretStore.ts`) is the established pattern for "prove an install/registration actually happened, don't assume it" — it emits exactly one `logInfo` line naming what was installed, which a live-gate re-run then greps `gamelib.log` for. Follow this same shape for the two send-kind observables: one `logInfo`/`logDebug` line per handler invocation, distinct enough to grep unambiguously.

```typescript

export const EOS_OVERLAY_CHANNELS = [ /* 8 */ ] as const
export const STEAMGRIDDB_CHANNELS = [ /* 5 short names */ ] as const

export async function callOrDeclare<T>(spec: CallOrDeclareSpec<T>): Promise<DeclaredResult<T>> {
  try {
    const value = await spec.call()
    return { ok: true, value }
  } catch (error) {
    // logs ONE line via window.api.logError, deduped per channel per session (declaredOnce Set)
    // NEVER throws, NEVER rejects — a decline must never become a second failure
    return { ok: false, channel: spec.channel, reason: errorMessage(error) }
  }
}
```

## Common Pitfalls

### Pitfall 1: D-04's Winetricks Guard Citation Is Wrong — And So Is Its Premise
**What goes wrong:** CONTEXT.md's D-04 cites `tools/index.ts:807` and `:843` as `!isLinux` early-return guards inside the `Winetricks` object, framing the macOS live-gate bar as "prove the guard fired, not the feature" (i.e., expect winetricks to decline on macOS).
**Why it happens:** Those exact lines belong to `getDxvkUrl()` (guard at line 807) and `getVkd3dUrl()` (guard at line 843) — two unrelated DXVK/VKD3D URL-selection functions that happen to sit near the `Winetricks` object in the same file. This research read the ACTUAL `Winetricks` object (starting at `tools/index.ts:528`) in full and found **no `!isLinux` guard anywhere in it** — instead it has a dedicated `macEnvs` branch (lines 616-642) providing genuine CrossOver/homebrew-based macOS support, selected via `isMac ? macEnvs : linuxEnvs` (line 642).
**How to avoid:** Do not write a live-gate check that asserts "winetricks declines with a guard message on macOS" — it won't, because there's no such guard. `winetricksInstalled`'s `listInstalled()` (lines 755-765) returns `[]` only when `winetricks.log` doesn't exist at the configured Wine prefix — this is DATA-dependent (no prefix configured for the target game), not platform-gated. Reframe the live-gate bar as: prove the channel resolves with real data (possibly an empty list, if no prefix exists for the fixture game), not that it returns `UNPORTED_CHANNEL_MARKER`.
**Warning signs:** If a plan or gate script contains a comment referencing "the `!isLinux` guard in Winetricks" or expects a specific decline message, it is citing the wrong functions.

### Pitfall 2: D-05's EOS Dialog Fires From the Wrong Step
**What goes wrong:** CONTEXT.md's D-05 cites `eos_overlay.ts:194` `dialog.showMessageBox` as the dialog the round-trip live gate must handle, implying it's part of `enable()`'s normal path.
**Why it happens:** The actual `dialog.showMessageBox` call inside `enable()` is at line 197 (a 3-line citation drift), but more importantly it is gated `if (!isInstalled())` — it ONLY fires when the overlay is not yet installed. Given the D-05 round-trip order (install → enable → disable → remove), by the time `enable()` executes the overlay IS already installed (the immediately-preceding step installed it), so **this dialog will not fire during the round-trip at all**. The dialog that DOES fire is `remove()`'s (line 162), which is called UNCONDITIONALLY every time `remove()` runs — and `remove()` is the LAST step of the round-trip, not `enable()`.
**How to avoid:** Write the live-gate script/checklist expecting a confirmation dialog at the REMOVE step, not the enable step. If the gate script or human-verify checklist references "the enable() confirmation dialog," it will produce a false "gate never fired" observation because it's watching the wrong step.
**Warning signs:** A live-gate run reporting "expected dialog during enable, none appeared" — this is the expected, correct outcome given `isInstalled()` is true at that point; it does not indicate a defect.

### Pitfall 3: SteamGridDB Plaintext-Key Hazard — Undocumented in D-02, Confirmed in Two Independent Files
**What goes wrong:** `steamgrid/secureKey.ts` imports `safeStorage` from `'electron'` directly (line 25). Under the sidecar, this resolves to `electronStub.ts`'s hardcoded-dead stub (`isEncryptionAvailable()` always throws, caught to `false` by `encryptionAvailable()` at lines 30-36). `encryptApiKey()` (lines 42-53) then unconditionally takes its plaintext branch — `if (!encryptionAvailable()) { logWarning(...); return plain }` — and this plaintext value is persisted via `GlobalConfig.setSetting('steamGridDbApiKey', stored)`.
**Why it happens:** `secureKey.ts`'s OWN header comment (already written, from Phase 34.4.1's "F-1b" seam-parity sweep) states this module was found unreachable from the sidecar's curated import graph as of that sweep, and DELIBERATELY left dormant rather than migrated — with an explicit trigger condition: "the moment any future plan wires `steamgrid/ipc_handler.ts`... into a sidecar registration module reachable from `handlers.ts`'s `register*Flows` chain, this becomes a LIVE plaintext exposure." **This phase's own D-06 requires exactly that wiring.** Independently, `keyring_account()`'s doc comment in `src-tauri/src/main.rs` confirms the same fact from the Rust side: "`steamgrid/secureKey.ts` (F-1b, `34.4.1-SEAM-PARITY-SWEEP.md` S-11) deliberately has NO slot here... it stays dormant, not live. A future plan adds its slot only once it is actually wired into a sidecar registration module." Two independent, already-existing project documents agree on this exact hazard and its exact trigger — yet CONTEXT.md's D-02 section (which enumerates security-flagged channels) does not mention it, naming only `importGame`/`moveInstall`/`runWineCommandForGame` under `T-34.5-C6-49-03`.
**How to avoid:** Treat SteamGridDB API key hardening as a co-requisite of D-06, not an afterthought — add a `steamgrid-api-key` slot to `keyring_account()` in `src-tauri/src/main.rs`, and create a `SidecarSteamGridDbSecretStore`-shaped implementation (mirroring `SidecarHumbleSecretStore` exactly: swappable via a `setSteamGridDbSecretStore()`-style seam, total-method contract, one-time plaintext-to-keyring migration, install-time `logInfo` observability) BEFORE porting `steamgriddb.setApiKey`/`steamgriddb.hasApiKey` onto the sidecar. Porting the channel without this hardening will silently persist the user's real API key in plaintext during the D-06 live-gate step itself.
**Warning signs:** Any plan that ports `steamgrid/ipc_handler.ts` without a corresponding keyring-allowlist change in `src-tauri/src/main.rs` is shipping this hazard live.

### Pitfall 4: Two Canonical Documents (34.6-CONTEXT.md and IPC-PORT-INVENTORY.md) Disagree on `frontendReady`'s Caller Line
**What goes wrong:** `IPC-PORT-INVENTORY.md`'s "Late-discovered" section cites `GlobalState.tsx:1586` as `frontendReady`'s caller; 34.6-CONTEXT.md already corrects this to `:1609`.

### Pitfall 5: A Repeat of Phase 34.4.1's "Arithmetically Forced, Not Passing" Cookie-Count Defect
**What goes wrong:** A cookie-census-based pass condition that can be satisfied by doing nothing (e.g., "N non-Humble/non-Epic cookies survive" when the pre-test state already had zero non-target cookies to begin with) is not a real gate.
**Why it happens:** This exact failure occurred once already in this codebase: Phase 34.4.1's live-gate run 3 recorded `survivingNonHumble=0` as a PASS, but the precondition state showed `before total=34` equalled `matched=34` — meaning there was no non-Humble cookie in existence to survive in the first place. The pass was arithmetically forced by an empty starting condition, not earned by correct clear-scoping behavior. The fix (documented in `34.4.1-35-PLAN.md`'s Precondition 6) was to REQUIRE planting a known-name, known-domain foreign cookie before the clear step, and assert BOTH that Humble-domain cookies are all cleared AND that the planted foreign cookie survives BY NAME.
**How to avoid:** D-13 already locks this exact fix for Epic logout ("assert the survivor's IDENTITY... not a count"). When writing the live-gate contract/checklist for step 8, follow the Precondition-6 shape precisely: (a) plant a known foreign cookie with a known name/domain BEFORE the logout step, (b) record the precondition state (`before total`, `matched`) in the result so a future reader can tell a real pass from an arithmetically forced one, and (c) require the item to specify an action a human/gate can actually take to fail it (anti-vacuity, also stated explicitly in `34.4.1-35-PLAN.md`'s own Task 1).
**Warning signs:** A gate contract item whose PASS condition is satisfiable by an empty/no-op starting state.

### Known Threat Patterns for this Stack

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|-----------------------|
| Secret persisted in plaintext because a dependency silently degrades (SteamGridDB API key via dead `safeStorage` stub) | Information Disclosure | Migrate onto `SidecarKeyringSlotStore` + Rust keyring allowlist BEFORE porting the channel that would trigger the exposure (this phase's central finding — see Common Pitfalls Pitfall 3) |
| Log line accidentally including a secret or PII (e.g., an app name/argument) | Information Disclosure | `callOrDeclare`'s own contract explicitly excludes `args` from its log message specifically because this is a public fork whose developers paste log output (`declaredUnavailable.ts`'s own doc comment cites `enableEosOverlay('')`/`disableEosOverlay('')` app-name arguments as the reason) — follow the same discipline for any new observability line added for D-11 |
| Path/command injection via `importGame`/`moveInstall`/`runWineCommandForGame` (already flagged, T-34.5-C6-49-03) | Tampering | D-02 requires porting these as-is then hardening in a dedicated same-phase plan — this research did not re-derive the specific hardening technique (out of this session's evidence budget); planner should check `REQUIREMENTS.md` for a `resolveContainedPath`-style precedent (REQ-37-06, referenced in CONTEXT.md's discretion notes but not independently verified in this research session — flagged as an open item for the planner to confirm) |
