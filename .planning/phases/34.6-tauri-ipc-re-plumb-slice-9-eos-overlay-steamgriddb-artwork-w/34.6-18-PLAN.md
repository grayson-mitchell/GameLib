<objective>
Close the single blocking gap in `34.6-VERIFICATION.md`: REQ-34.6-05's `T-34.5-C6-49-03`
hardening (plan 34.6-11) gates `moveInstall`/`importGame` against
`GlobalConfig.get().getSettings().defaultInstallPath`, and both features exist SPECIFICALLY to
reference a location outside that root. The guard therefore throws `PathContainmentError` on
exactly the input each feature is for.

**The fix direction is DECIDED (not deferred).** Containment against `defaultInstallPath` is
dropped for these two channels and replaced with a shape/plausibility validator. Rationale, and
the alternatives rejected, are recorded in `<decision>` below.

Purpose: make cross-drive move and out-of-tree import work again WITHOUT reverting to an
unvalidated renderer path argument.
Output: one new validator in the existing guard module, two corrected handlers, two corrected
header comments, and regression tests proven RED before the source change.
</objective>

<decision>
## DECIDED: drop `defaultInstallPath` containment for `moveInstall`/`importGame`; validate SHAPE only

**Adopted.** `assertContainedPath(defaultInstallPath, path, ...)` is removed from both handlers
and replaced by a new `assertPlausibleAbsolutePath(path, context)` in the same module:
absolute (after backslash normalisation), no `..` segment, no NUL byte, non-empty after trim,
and a string.

**Why this and not something stricter — two independent reasons, both checkable:**

1. **The containment control is CIRCULAR against its own named adversary.** The threat
   T-34.5-C6-49-03 names is a compromised/tampered RENDERER supplying a hostile `path`. But the
   containment root, `defaultInstallPath`, is written by that same renderer:
   `src/frontend/screens/Settings/components/DefaultInstallPath.tsx` sets it through
   `useSetting('defaultInstallPath', ...)`, which reaches the renderer-callable send-kind
   channel `setSetting` (`src/backend/sidecar/settingsFlowRegistration.ts:160`;
   `src/backend/main.ts:1022` on the Electron leg). A renderer that can call `moveInstall` can
   first call `setSetting` with `defaultInstallPath` set to the filesystem root and then move
   anywhere. The control asserts a property the adversary can grant itself — it reads as a
   boundary and is not one.
2. **The real trust boundary for these two channels is the OS-native directory picker.**
   `moveInstall`'s path comes from `window.api.openDialog({ properties: ['openDirectory'], ... })`
   (`GameSubMenu/index.tsx` `onMoveInstallYesClick`); `importGame`'s comes from
   `PathSelectionBox` in `InstallModal/ImportDialog/index.tsx`. `openDialogCallback`
   (`src/backend/utils/openDialog.ts`) applies zero root enforcement by design —
   `defaultPath` is the dialog's STARTING directory only.

**Rejected alternative A — widen the root to "anywhere the picker can reach."** That is
containment-in-name-only: a guard that asserts nothing while reading as if it asserts
something. This project already carries a recorded pattern of gates that measure the wrong
property; adding another is a worse outcome than removing the check honestly.

**Rejected alternative B — gate on "the path was returned by a real `openDialog()` this
session."** Requires new session-token plumbing across the preload seam for a threat the picker
already bounds, and invents cross-process state that can desync (a picker result that outlives
its token, or a token that survives a reload, both produce a false rejection of a legitimate
move). Disproportionate to a local desktop launcher at ASVS L1.

**What is NOT changed.** `assertContainedPath` / `PathContainmentError` stay exported and
byte-identical, and `rendererPathGuard.test.ts`'s existing assertions stay untouched and green.
Note for the record — and correcting a premise carried into this gap cycle:
`runWineCommandForGame` does NOT use `assertContainedPath`; it uses `assertCommandParts`
(`wineToolsFlowRegistration.ts:70,371`). After this plan `assertContainedPath` therefore has
ZERO production call sites. It is retained deliberately, not by omission, and Task 1 records
that fact and its named future consumer in the module header rather than leaving a dead export
whose prose still claims two live callers. (`ts-prune` will not newly report it — the test file
still imports it — but the prose would have been the lie, not the linter.)
</decision>
