## Implementation Decisions

### Port scope

- **D-01:** Phase 34.6 owns all 24 unported channels — the 16 from 34.5's D-03 deferral **plus** the
  8 late-discovered ones `IPC-PORT-INVENTORY.md` § "Late-discovered — owner Phase 34.6" already
  assigns to this phase. Phase 35's gate is "the IPC re-plumb must be COMPLETE"; leaving 8 unported
  means Phase 35 either absorbs them or ships them broken. **ROADMAP ACTION:** the Phase 34.6 goal
  text says "the 16 channels" and must be amended to 24. Rejected: 16-only with a new 34.6.1 (34.5's
  own history shows an untracked deferral is how UAT debt accumulates); 16 + `frontendReady` only
  (splits the 8 on a criterion the inventory does not use).
- **D-02:** The three security-flagged channels are ported AS-IS, then hardened in a DEDICATED plan in
  this same phase. `importGame`, `moveInstall` and `runWineCommandForGame` carry
  `T-34.5-C6-49-03` — renderer-supplied filesystem paths, and a command string reaching a Wine
  process, with no sidecar handler. Porting byte-equivalently preserves the additive/reversible
  invariant; a separately-committed hardening plan then discharges the finding. Rejected: hardening
  inline at the port (a live-gate FAIL could not be bisected to "port broke it" vs "validation
  rejected it"); forwarding to Phase 35 (the cutover is where it stops being reversible, and this
  project's record — `D-29-08` sat unowned for weeks — is that forwarded findings go unowned).
- **D-03:** 34.6 re-runs `preload-surface-gate.py` at close, and ABSORBS what it finds — up to ~10
  channels. Beyond ~10 the finding becomes a blocking halt and a new phase is inserted before
  Phase 35, in the shape 34.5's gap cycle 6 used. Rationale: "the re-plumb is COMPLETE" can only be
  asserted by a re-derive that runs AFTER this phase's ports land, and the inventory was
  non-exhaustive **twice** (`getInstallInfo`, then 11 more). ~10 is roughly one wave at this
  project's measured 3–4-channels-per-plan rate. Rejected: no ceiling (unbounded — the failure mode
  34.5 D-06's "coupling forces splits, not volume" was written against); record-and-hand-to-35
  (hands the riskiest phase an unbounded list — 34.5 D-05's explicitly rejected alternative);
  don't re-run (eight phases of source changes have landed since the 2026-08-12 audit).

### The honest-decline machinery

- **D-08:** KEEP `callOrDeclare()` and unwind nothing. All 10 wrapped call sites
  (`AdvancedSettings`, `SteamGridDBPicker`, `EditGameDialog`, `SideloadDialog`) stay wrapped after
  the port. Its contract — never throws, never returns a rejected promise — is a genuine safety
  property regardless of porting, and it is the **only** renderer→`gamelib.log` path in the app
  (`frontend/index.tsx:41` bridges `window.error` only, never `unhandledrejection`). A future
  regression therefore still produces a durable log line instead of an invisible `console.warn`.
  Rejected: ripping the wrappers out (re-creates the exact defect 34.5-48 diagnosed — 8 EOS
  rejections in one UAT session with ZERO log lines); keeping them only where a platform can't run
  the feature (two idioms for one channel class, re-judged every time a platform guard moves).
- **D-09:** `runnerSliceRegistration.test.ts` Describe 7 is SPLIT, not deleted. Today it asserts all
  19 dropped-or-deferred names are absent from `handlerRegistry`; 16 of them become registered.
  Split it so **the Zoom 3 stay an ABSENCE assertion** (D-02's drop is a product decision nothing
  else in the repo guards) **and the 16 flip to a PRESENCE assertion**. Both directions must be
  RED-proven, per this project's standing "prove a grep/absence assertion against known-bad input"
  rule. The file's `expect(DROPPED_OR_DEFERRED.length).toBe(19)` arithmetic must be **re-derived**,
  not merely edited. Rejected: deleting Describe 7 (silently drops the only assertion keeping Zoom

- **D-10:** `U-34.5-32` SPLITS — it does not retire wholesale. The SteamGridDB half **retires by
  port**: once ported on macOS there is no decline left to observe, and D-06's gate observes the
  working feature instead. The winetricks half is **discharged live**: ⚠ **REASONING FALSIFIED,
  OUTCOME PRESERVED — see A-01. Winetricks does NOT decline on macOS.** ~~winetricks still declines on
  macOS, so~~ the gate captures `DECLARED_UNAVAILABLE_MARKER` in a real `gamelib.log` — **the first
  live observation of that literal in this project's history** — but it must be captured **BEFORE

- **D-11:** the SEND-kind channels stay send-kind, with a new observable at the sidecar handler.

  `addListener`/send-kind (`tools/ipc_handler.ts`), so `callOrDeclare` cannot wrap it and sidecar

  diverging Electron and Tauri immediately before the cutover); carrying 34.5-55's exemption
  forward unchanged (leaves the winetricks cluster with no observable at all, contradicting D-04).

### The inherited verification leg

- **D-12:** ONE blocking live gate, explicitly SEQUENCED — the Epic login leg runs FIRST, logout runs
  LAST. The Epic session the login leg establishes is a precondition for `egsSync`, save sync,
  `getAchievements` and `getPlaytimeFromRunner`; `clearEpicCookies` destroys that session, so it must
  run last. One document, one verdict, under 34.5 D-08's no-partial-pass rule. Rejected: two gates
  (a second gate document is where items go missing from `audit-uat` here); a separate logout re-run
  (a third artifact, and re-runs multiply — 34.4.2 took nine attempts).
- **D-13:** Epic logout asserts the SURVIVOR's IDENTITY against a PLANTED foreign cookie. The
  ROADMAP's inherited wording is "a `clearEpicCookies` count cross-checked against an independent
  re-read of the jar" — but a **count can be arithmetically forced**, which is exactly why 34.4.1's
  precondition 6 is UNSTRUCK (`survivingNonHumble=0` when `before total=34` equalled `matched=34`).
  So: run the logout against a jar holding a **named non-Epic cookie**, then assert **that exact
  cookie survives by name**. This inherits the correction rather than repeating the defect.
  ⚠ **This decision AMENDS the ROADMAP's stated discharge bar** — the count alone is not sufficient.
  Rejected: the count cross-check as literally worded; both (a count mismatch alongside a correct
  identity result is ambiguous to adjudicate).
- **D-14:** Legendary save sync round-trips a MUTATED save on a small owned Epic game with cloud
  saves. Mutate a save locally → sync up → alter/delete locally → sync down → assert the mutation
  came back. Proves **both directions** through the sidecar. **Wave-ordering constraint this
  creates: `getDefaultSavePath` — one of the 8 late-discovered — must be ported BEFORE this leg, or
  path resolution fails.** Rejected: download-only (the upload half is the one that can DESTROY a
  save); command-exit proof (this project's own lesson — "the function is CALLED" proves wiring, not
  behaviour; a sync that silently syncs nothing would pass).
- **D-15:** SIDLogin does NOT satisfy UAT item 11. Epic has two wired tiles since 2026-08-22
  (primary = embedded login, alternative = SIDLogin device-auth). Item 11 means the **embedded
  login specifically** — it is the primary path and nothing has ever gated it live. Accepting
  SIDLogin as a substitute would let the primary path ship unobserved while the document reads
  "Epic login PASSED" — a pass covering a surface that was never reached, which has happened here
  before. Accepted cost: a 403 recurrence blocks the phase on something outside the project's
  control. Rejected: either-path-establishes-the-session; a pre-authorized downgraded verdict (D-08
  has no partial-pass mode).

### Amendments (2026-08-23, post-research — operator-approved during `/gsd-plan-phase 34.6`)

`34.6-RESEARCH.md` independently re-verified every source citation in this document and falsified
the premise of two locked decisions. Both corrections were confirmed a second time by the
orchestrator reading source directly before amending. **These amendments are binding on the
planner; where they conflict with the original D-text above, the amendment governs.**

- **A-01:** D-04's guard does not exist, and D-10's winetricks reasoning falls with it.
  `tools/index.ts:807` sits inside `getDxvkUrl()` and `:843` inside `getVkd3dUrl()` — unrelated
  DXVK/VKD3D URL-selection functions. The real `Winetricks` object begins at `tools/index.ts:528`
  and contains **no `!isLinux` guard anywhere**; it has a dedicated `macEnvs` branch (`:628`)
  selected by `isMac ? macEnvs : linuxEnvs` (`:642`). **Winetricks has genuine macOS support.**
  `winetricksInstalled`'s `listInstalled()` (`:755-765`) returns `[]` only when `winetricks.log`
  is absent at the configured Wine prefix — that is **data-dependent, not platform-gated**.
  **Corrected bar (replaces D-04's):** the gate asserts the ported channel **resolves with real
  data through the sidecar** — an empty list is an acceptable *result*, not a decline — and that
  the **sidecar handler was reached**, proven by the D-11 observable. The property being measured
  is "handler reached and returned a real result", not "a guard fired".
  **Corrected D-10 winetricks disposition:** the `DECLARED_UNAVAILABLE_MARKER` live observation is
  still owed and still achievable, but **only before the winetricks port lands** — it is the
  *unported* channel that produces the marker, not a platform guard. The gate therefore opens with
  a pre-port marker-capture step on a build without the winetricks registration, and proves the
  working channel after. **No plan may write a gate step expecting a decline message from a ported
  winetricks channel on macOS** — it will not appear, and a "gate never fired" reading would be a
  false negative.
  *Rejected: reframe-only with the marker retiring by port (leaves the literal with zero live
  observations ever, which is what D-10 was written to prevent); deferring winetricks live proof to
  Phase 38 (leaves 3 of 24 channels unobserved across the Phase 35 cutover).*

- **A-02:** D-05's dialog fires at `remove()`, not `enable()`. The `dialog.showMessageBox` inside
  `enable()` is at `eos_overlay.ts:197` (not `:194`) **and is gated `if (!isInstalled())`**, so in
  the D-05 round-trip order (install → enable → disable → remove) it **cannot fire** — the
  preceding install step already made `isInstalled()` true. The dialog that *does* fire is
  `remove()`'s at `:162`, called **unconditionally**, at the round-trip's **last** step. D-05's
  decision is unchanged — the round-trip still traverses the 34.5 D-15 crash hazard — but every
  gate step, checklist item and restore instruction must place the dialog at **remove**. A gate
  reporting "expected a dialog at enable, none appeared" is the **correct** outcome, not a defect.

- **A-03 (NEW DECISION):** SteamGridDB API-key hardening is a CO-REQUISITE of D-06 and lands
  BEFORE the SteamGridDB port. Porting `steamgriddb.setApiKey`/`hasApiKey` onto the sidecar makes
  `secureKey.ts:25`'s `import { safeStorage } from 'electron'` resolve to `electronStub.ts`'s
  deliberately-dead stub (`electronStub.ts:27-29` — "intentionally left dead here (throws on
  use)"), so `encryptApiKey()` takes its plaintext branch and `GlobalConfig.setSetting` persists
  the key in the clear. **D-06 requires entering a REAL key live, so the gate step itself would be
  the moment of exposure.** This hazard is absent from D-02 but was pre-committed to in **three**
  places already in the repo: `steamgrid/secureKey.ts:17-24` states the TRIGGER CONDITION naming
  this phase's exact wiring and instructs that the keyring slot land "**BEFORE** porting the
  channel -- not after"; `keyring_account()` in `src-tauri/src/main.rs` carries no `steamgrid` arm
  and a doc comment saying one is added "only once it is actually wired"; `electronStub.ts:27-29`
  confirms the stub is dead by design.
  **Shape (do not invent a new one):** mirror the shipped `HumbleSecretStore` /
  `SidecarKeyringSlotStore` precedent from Phase 34.4.1 plans 12/13 exactly — a
  `"steamgrid-api-key"` arm added to `keyring_account()`, a `SidecarSteamGridDbSecretStore` behind
  a swappable setter seam, a total-method contract (never throws, never rejects), a one-time
  plaintext→keyring migration, and a single install-time `logInfo` line the live gate can grep.
  **This is a narrow, explicit exception to D-02's port-byte-equivalently-then-harden rule**, taken
  because D-02's rule exists to keep a live-gate FAIL bisectable, and that benefit is worth less
  than not writing the operator's real credential to disk in plaintext during the gate itself.
  D-02's rule is **unchanged** for its own three channels (`importGame`, `moveInstall`,
  `runWineCommandForGame`), which still port as-is and harden in a separately-committed plan.
  *Rejected: port-first-harden-later with a throwaway key at the gate (preserves D-02's invariant,
  but leaves a live plaintext window and contradicts the repo's own written instruction); port
  first with the real key (requires a manual key rotation afterwards).*

- **A-04:** `IPC-PORT-INVENTORY.md` is stale on `frontendReady`'s caller line. It cites
  `GlobalState.tsx:1586`; the measured truth is `:1609`, as this document already recorded and
  research re-confirmed by direct read. The plan that touches the inventory for D-03/D-10 must fix
  this citation in the same pass rather than appending rows around it.
