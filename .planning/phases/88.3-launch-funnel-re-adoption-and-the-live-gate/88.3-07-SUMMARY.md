# Phase 88.3 Plan 07: The launch record, the funnel session, the quit-kill and the lost-sidecar exit watch Summary

**Every funnel launch now leaves a 0600 `<appFolder>/launches/<runner>-<app>.json` with the game leader's pid, start stamp and group, a live member snapshot and the after-script it owes; the quit's kill records play time at the kill and leaves the record `quitKilled` with the after script unrun; a launch whose sidecar dies while the game runs waits for the game and finishes instead of failing.**

## What was built

- `game/record.rs`: `LaunchRecord` (camelCase, `deny_unknown_fields`, `version: 1`), `write_atomic` (folder 0700 if missing, `create_new` 0600 temp sibling, sync, rename; refuses a symlink at the file or the folder and a record over 64 KiB), `read_record` (symlink-metadata first, `O_NOFOLLOW`, regular file on the opened handle, owner is the current uid and no group/other bits, at most 64 KiB, version read before the strict decode), `remove_record` (a regular file only), and `record_game_spawn`, the one function that builds a record for a spawn. A write failure is one fixed `gamelib.log` line; a record too large to hold the after script is rewritten without it (and says so).
- `funnel/session.rs`: `LaunchSessions` on `LaunchCtx.sessions`. `begin` right before the `launch` hook with the after script's `ScriptRunArgs`, the times and a quit hook; `for_run(runner, key)` is how a spawn finds it; the guard drops at the end of `lead`; `finish()` deletes the record, but not for a quit-killed session and not for a guard dropped by the shutdown token.
- Both game arms (`call_runner::execute_game`, `wine_command::run_game`) call `record_game_spawn` after `register_game` and pass a leader-gone observer to `end::wait_end_observed`, which rewrites the member list (`snapshot_members`) only when it changed.
- `registry.rs`: `KillCause { QuitAll, Filtered, Stream, Abort }` and a kill observer. `LaunchCtx::new` installs one that, for `QuitAll` only, marks the session quit-killed and runs its quit hook: `lastPlayed`/`totalPlayed` from `startPlayingDate` to the kill, the runs-for-me record from the launch time, and the record rewritten `quitKilled` with `killedAtMs`.
- `run_launch`: the quit-killed tail (above); the Pitfall 1 branch (a `launch` hook that fails with `sidecar` while the session's game is still registered waits for that entry to leave the registry at the group poll period, then runs the normal tail with `clear_presence`, the GOG playtime post and the saves upload skipped); `run_launch_script` split into a pure `launch_script_args` (so the record can carry the after script's arguments) and the runner; `recent_add` pulled out.
- `ScriptRunArgs`, `ScriptStage`, `LogHandOff` and `gamelib_log::frame::FrameTarget` gained `Serialize` (the record holds the after script's arguments).

## Deviations from Plan

### Judgement calls

**1. Task 3's production code landed in Task 1's commit.** `run_launch`, `registry.rs` and `ctx.rs` carry the record, the session, the quit hook and the exit watch in the same functions, so one buildable commit holds them (88.3-06 did the same). Task 2's commit holds the Wine arm, the test seam and `readopt.rs`. The three Task 3 stub arms are in `stub_game.rs`, in Task 1's commit.

**2. `set_kill_observer`'s callback is `Fn(KillCause, &RunIds)`, not `Fn(KillCause, &RunIds, u64)`.** The registry has no clock; the context's own clock is read by the quit hook, so the kill time and the stored `lastPlayed` agree exactly (the test asserts `lastPlayed == iso_string(killedAtMs)`).

**3. The observer runs under the killed game's own handle lock, not "no lock".** The plan's review criterion says no *registry* lock is held, and that holds (the registry's `inner` lock is not taken). Holding the game's handle lock until the observer has finished is deliberate: the run cannot reap the leader meanwhile, so the funnel's tail cannot read the quit flag before it is set. Called only when the kill ended the tree (`Killed`), not for `Gone`/`NotOurs`.

**4. `libc` added to `gamelib-launch` (`cfg(unix)`).** `read_record` needs `geteuid()` and `O_NOFOLLOW`. libc 0.2.186 is already resolved for `gamelib-proc` and `gamelib-steampoll`; the only lockfile change is one dependency line. No new crate enters the tree (T-88.3-SC holds), but `Cargo.toml` and `Cargo.lock` are outside the plan's `files_modified`.

**5. `Serialize` on `gamelib_log::frame::FrameTarget`** (outside `files_modified`): the record carries `ScriptRunArgs`, whose `LogHandOff` holds a `FrameTarget`. A derive only.

**6. The after script's `log_target` is not recorded** (`None`): the hand-off's rotation flag means nothing to a later start. 88.3-09 should fill it from the game's log writer when it runs the owed script.

**7. The quit-killed tail also skips `clear_presence`** (a hook to the sidecar that is on its way out, so unbounded at quit), and keeps `recent_add` and the display-sleep and engine releases (bounded, local). The plan names the after script, saves upload, GOG post and second play-time write; `clear_presence` is the one addition.

**8. `after-script` assertions use `RecordingSteps` calls, not a marker file.** The funnel runs the script through the `FunnelSteps` seam, so the tests assert on `StepCall::RunScript` (a real script run is covered by `script_real.rs`).

**9. `StubGameHooks` tracks its game under the app name** (as the five real sites do), instead of `funnel-launch-N`, so the session is found; two existing arms still pass unchanged.

**10. `run_prepared_game_for_test` (feature `testing`)** drives the Wine game arm over an already-prepared command, because preparing one needs a real Wine; the wine-site proof is therefore that arm's own registration, not the TS site.
