# Phase 88.3 Plan 11: Sidecar-led single flights Summary

**A leader outside the Rust funnel (the TS Steam dispatch, until 88.3-18 moves it and 90.2 retires it) can now lead, join and end a flight in the one Rust single-flight table through three channels, and every flight it leads is released when the sidecar goes away.**

## What was built

- **`flights.rs`**: `begin_owned(runner, app) -> Begin { Lead(FlightId), Join }` decides under the table's one lock (it is `enter` plus a side-table insert) and keeps the guard under a minted `FlightId`; `wait(runner, app, &shutdown)` is the joiner half for a key led by anyone; `end(&FlightId, value) -> bool` settles and releases only the id's own entry (an unknown, stale or released id returns false and touches nothing); `release_owned_by_sidecar() -> usize` drops every side-table guard outside the lock, so each key is free and each joiner answers `abandoned`. `FlightId::parse` accepts only the minted shape (32 lowercase hex).
- **`lib.rs`**: `launch_flight_begin`, `launch_flight_end`, `launch_flight_wait` in `OPS` (sorted) and `route`, strict `deny_unknown_fields` decode, names held to the kill ops' `run_id` check, fixed `<op>:bad-args`. They run under `guarded`, so a wait ends on the shutdown token with `launch_flight_wait:shutdown`.
- **Shell**: constants, zod schemas (`result` is `x-rust-value`, opaque to the generated decode), generated `ipc_contract.rs` arms, `rust_dispatch` arms and `rpc_launch_flight_*` in `launch_dispatch.rs` (generated decode and arity check first, then the crate; `<op>:not-ready` before install). `release_sidecar_flights` logs one fixed line with the count (never an id or a key) and is called in `sidecar.rs` straight after `drain_pending_invokes` fails the pending invokes and before the slow EOF teardown.
- **TS**: `RUST_LAUNCH_FLIGHT_WAIT` is the twenty-eighth `UNBOUNDED_RUST_CHANNELS` entry (commented, pinned in `dialogOptionForwarding.test.ts`); begin and end stay inside the 60 s bound. `rustInvokeSchemas.test.ts` counts 222 channels and has accept and reject vectors for the three schemas.

### Judgement calls

- **Shutdown is a rejection, abandoned is a value.** The plan says wait answers "the fixed words `abandoned` or `shutdown`". `guarded` already answers `<op>:shutdown` as an `Err` for every launch op when the token fires, so the wait arm maps the table's `shutdown` word to that same `Err(launch_flight_wait:shutdown)` and answers `abandoned` as the string value. A settled boolean can never collide with either.
- **A wait on a key nobody leads answers `abandoned`.** The plan does not say. A joiner told `{ join: true }` whose leader ends before its `wait` arrives gets `abandoned` (the leader's value is gone), not a hang. This is a narrow race a TS caller should treat as "the leader finished, outcome unknown"; 88.3-18's glue should read it that way.
- **`release_sidecar_flights` logs only when it released something.** The plan says "logs one fixed line with the count"; a `0` line on every normal quit would be noise on the exit path, so the line is written only for a non-zero count.
- **`begin`/`wait` take `runner` as a plain string** (`z.string()` in the schema, the kill ops' `run_id` check in the crate), not the five-name enum, because the key `steam:<appId>` must be representable and the table's key space is open by design.
- **No cap on the side table.** The only peer is the sidecar the shell spawned; a runaway leader is bounded by the release at EOF. Noted rather than added.
