# Phase 88.3 Plan 12: Re-adoption wired into the running app Summary

**The shell now runs `readopt::start_with_host` once per boot on a `launch-readopt` thread right after `launch_dispatch::install`, and the sidecar's `frontendReady` handler calls a new `launch_readopted_announce` op on every delivery, so a reopened GameLib shows a game that outlived a crash as Playing once the renderer listens, counts it for the quit dialog, and ends it through its proof at quit.**

## What was built

- **Crate** (`gamelib-launch/src/lib.rs`): op `launch_readopted_announce`, arguments `[]`, answers the count `readopt::announce` returned (it also marks the context frontend-ready). `OPS` is 27, sorted; the every-op bad-args sweep treats it as a zero-argument op like `launch_games_running`.
- **Shell** (`launch_dispatch.rs`, `main.rs`, `rust_dispatch.rs`):
  - `start_readoption()` spawns the std thread `launch-readopt`, which builds a `RunnerHost` from `runner_host()` and calls `readopt_over`, which runs `start_with_host` and writes one fixed `gamelib.log` line: `launch re-adoption: N adopted, N removed, N owed scripts, N skipped`. Counts only; no app name, path or pid. A no-op when the context is absent; a failed thread spawn logs one fixed line. `run_setup` calls it once, straight after `launch_dispatch::install`, inside the same `log_paths` branch (the store host is open and the context exists).
  - `rpc_launch_readopted_announce` / `readopted_announce_over`: the generated decode and an arity check first (fixed `launch_readopted_announce:bad-args`, the same before and after the install), `launch_readopted_announce:not-ready` before the install, then the crate.
- **Contract**: `RUST_LAUNCH_READOPTED_ANNOUNCE` in `sidecarTransport.ts` (in `RUST_INVOKE_CHANNELS`, bounded, not in the unbounded list), strict `[]` schema (`empty`), `pnpm gen:ipc-contract` regenerated `ipc_contract.rs` (+13 lines, nothing else), `check:ipc-contract` up to date.
- **Sidecar**: `announceReadoptedGames(deps)` in `launchrust/funnel.ts` (one returned typed call with `[]`). The `frontendReady` handler calls it right after `markFrontendReady()`, outside the one-shot `claimFrontendReadyBootWork` guard, in its own try/catch; a rejection logs one fixed `console.warn` (`[appShellFlowRegistration] frontendReady -> announceReadoptedGames failed`, the rejection text never logged). No timer, handle or unbounded wait.
- **Schedule**: row `announceReadoptedGames` (shim, `RUST_LAUNCH_READOPTED_ANNOUNCE`, `deletedBy: 98`). Both `launchRun` and `announceReadoptedGames` now take `FUNNEL_SHIM_IMPORTERS` (`launcher.ts` and `appShellFlowRegistration.ts`), because the schedule's `callers` is every importer of the file.

### Judgement calls

- **`start_with_host`, not `start`.** The plan says `readopt::start`; 88.3-09's summary asks for `start_with_host` over the shell's `RunnerHost`. The boot call builds the host from `runner_host()` (falling back to an empty host if the value ever failed to decode, which it cannot today).
- **The counts line is written on every boot**, including all zeros (88.3-11 wrote its line only for a non-zero count). The plan says "one fixed line reports the counts"; a zero line is the live gate's evidence that the scan ran, and costs one line per boot.
- **The schedule's `launchRun` row changed too** (`callers` now include `appShellFlowRegistration.ts`), a consequence of the per-file importer check, not a new fact about `launchRun`.
- **`ctx_built` gained a sibling `ctx_built_with(home, log, emitter)`** in the shell's test module, so the test's context can carry a recording emitter. `ctx_built` is a thin call to it.
- **No mutation run on the tracer.** The shell test passed on first run, and its assertions are exact (a zero-argument announce answering 1, the exact `playing` payload, the `quitKilled` record). 88.3-09's three mutations already prove the crate half; this plan's glue is the call and the op. I did not mutate the glue.
- **Requirement SVC-03 not marked complete here.** It is phase-level (88.3-09 left it unmarked; 88.3-11 listed it); the verifier closes it after 88.3-22.
- **STATE.md, state.json and ROADMAP.md** are written by the closing commit through the gsd-tools verbs, as the operator allowed.
