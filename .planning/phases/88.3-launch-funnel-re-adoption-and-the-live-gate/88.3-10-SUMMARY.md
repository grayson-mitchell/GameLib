# Phase 88.3 Plan 10: The launchRun shim and the Play cutover Summary

**A Play of a non-Steam game now goes from the Launcher's `launchEventCallback` through one typed `RUST_LAUNCH_RUN` request into the Rust funnel and settles on the `{ status }` Rust answers; the TS funnel no longer runs in production.**

## What was built

- `launchrust/funnel.ts`: `launchRun(deps, params)`, one returned `deps.requestRustInvoke(RUST_LAUNCH_RUN, [params])`; `LaunchRunRequest` is the zod input type of the schema's one argument.
- `launchBuilderReply.ts`: `settleLaunchStatus(reply)`, accepting an object whose `status` is one of the three words and throwing `launchRun: the reply was not a launch status` for anything else.
- `launcher.ts`: the `launchEventCallback` member is `async (params) => settleLaunchStatus(await launchRun(deps, toLaunchRunRequest(params)))`. `toLaunchRunRequest` copies the chosen launch option into a plain object (an interface is not assignable to the schema's record type) and leaves an absent one out of the frame. The TS body (single-flight wrapper over `runLaunchEventCallback`, with its own `PowerState`) is behind the exported `createTsLaunchFunnel(deps)`, documented as test-facing and deleted with the file in 88.3-17.
- Tests: `funnel.shims.test.ts` (19 tests) pins the exact frame `[RUST_LAUNCH_RUN, [params]]`, that the arguments pass the sidecar's zod schema, the narrowing and its by-name throw, and the tracer: a Play through `createLauncher(...).launchEventCallback` sends one request and touches no per-game log writer, no wake lock and no library manager; a rejection fails the Play with Rust's word and no TS fallback. The three TS-funnel files (`launcher_launchSingleFlight`, `launcher.engineStep`, `runnerCallSites`) build `createTsLaunchFunnel` instead of the Launcher with no other change. `engineWineShimSchedule.test.ts` gains the `launchRun` row (`deletedBy: 98`, caller `launcher.ts`, a comment naming both entry points and the phases that move them) and keeps `RUST_LAUNCH_` in `CHANNEL_PREFIXES`.

## Deviations from Plan

### Judgement calls

**1. [Rule 3 - Blocking] `settleLaunchStatus` is in `launchBuilderReply.ts`, not `launchrust/funnel.ts`.** The plan's artifact list names it under `funnel.ts`. The schedule's discovery turned every exported value under `launchrust/` into a survivor needing a row (the first run failed with `unscheduled: funnel.ts#settleLaunchStatus`). The other settle helpers (`settleEnvMap`, `settleVerifyPrefixReply`) already live in `launchBuilderReply.ts`, outside the discovery scope, so the helper went there. The plan's `launchRun` row and the shim shape are as written.

**2. [Rule 3 - Blocking] A copy helper between `LaunchParams` and the shim.** `LaunchParams.launchArguments` is a `LaunchOption` interface union, which the type system will not assign to the schema's `Record<string, unknown>`. The plan wrote `launchRun(deps, params: LaunchParams)`. To keep the shim body one returned typed call with no cast, `launchRun` takes `LaunchRunRequest` and the Launcher member builds it through the module-private `toLaunchRunRequest` (a shallow copy; an absent option stays absent). Tested with `toStrictEqual`.

**3. Two commits cover tasks that were developed together** (see Task Commits).
