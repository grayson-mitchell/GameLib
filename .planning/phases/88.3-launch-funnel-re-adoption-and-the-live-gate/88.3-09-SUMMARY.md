# Phase 88.3 Plan 09: Re-adoption of a game that survived a GameLib crash Summary

**`game::readopt::start` reads the launch records at boot inside a 2 s and 64-record bound, proves each running game with `adopt::identify`, registers it as an adopted entry the quit dialog and Stop reach (ended only through `kill_adopted_tree`), appends one fixed re-adopted line to its log, and watches it to the end, where it records play time, runs the after-script, sends `done` and removes the record; a quit-killed record's owed after-script runs at the next boot.**

## What was built

- `game/readopt.rs`
  - `start(ctx)`, `start_with_host(ctx, &RunnerHost)` (the environment an owed or exit after-script inherits) and `start_bounded(ctx, host, cap, bound)` (the tests prove the bounds without 64 records or two seconds). The scan reads the `.json` names of `<appFolder>/launches/` (the folder must be a real directory; at most 1024 entries looked at, sorted), at most 64 of them and until the deadline, and leaves the rest with one fixed line (`Launch re-adoption left N launch records for the next start`).
  - A `running` record is proved with `identify` over its pid, stamp and recorded members. `Leader`, `Member` and `Job` adopt; `Gone` and `NotOurs` remove the record, signal nothing and record no play time. A `quitKilled` record runs its owed after-script in a spawned task holding a `readopt-owed-script` registrant, then removes the record (unless the shutdown token stopped the script, in which case it stays owed). A record that cannot be read is removed only when `is_ours_regular_file` (a regular file, never through a symlink, owned by the current user); a symlink, a folder, a newer-version record or an I/O error is left and counted `skipped` with one fixed line. A record whose runner is unknown, whose pid is 0 or 1, or that sits under a name other than the one its runner and app name compute, is removed as unreadable. A game this context already tracks is not touched.
  - Adoption: a session through `begin_session` (so the quit's kill reaches it exactly as it reaches a live launch), the record kept in the session, `register_adopted`, one `RE_ADOPTED_LINE` appended through `LaunchLog::open_appending` (no rotation), a `playing` status at once when the context is already frontend-ready, and an exit watch.
  - The exit watch holds a `readopt-watch` registrant from adoption to the end of its tail, polls `identify` at the group poll period, and on the shutdown token ends with nothing signalled and the record kept. When the game is over it takes the entry's gate (so a kill in progress finishes its bookkeeping first), then: if the quit's kill ended it, it logs that the script is owed, closes the log, sends `done` and keeps the `quitKilled` record; otherwise it records play time, runs the after-script (bounded by `READOPT_SCRIPT_LIMIT` and the shutdown token), closes the log, sends `done` and removes the record. The adopted entry is unregistered on every exit.
  - `announce(ctx)` marks the context frontend-ready, then sends `gameStatusUpdate { appName, runner, status: 'playing' }` for every adopted entry and answers the count.
- `game/registry.rs`: `AdoptedEntry { id, ids, proof, started_at }` (plus a private gate and `ended` flag), counted by `games_running`, `len`, `contains` and `games`, and reached by every kill selector. `AdoptedEntry::kill` holds the gate for the kill and the observer, calls `kill_adopted_tree` and tells the observer only when the tree was ended by this call.
- `funnel/playtime.rs`: `record_session_playtime`, now the one body of the quit-kill hook and the re-adopted exit. `funnel/run.rs`: `begin_session` is `pub(crate)` and its hook calls the shared function (behaviour unchanged). `funnel/log.rs`: `LaunchLog::open_appending`. `game/record.rs`: `is_ours_regular_file`. `ctx.rs`: `frontend_ready`. `lib.rs`: `task_handle()` (the caller's runtime when inside one, otherwise the crate's own, so the shell's `launch-readopt` thread can call `start` from a plain thread).
- Stand-in shell `shell --user-data <dir> --funnel <params> --game <stub args> [--after-script <path>]`: `run_launch` over in-binary `ManagerHooks` (a native sideload game with install folder `<dir>/install`, the script as its after-script, and a game-class `call_runner` of the stub with the funnel's own log hand-off) and recording steps.
- Tests: `tests/readopt.rs` 12 -> 20 (the eight named in the plan); `tests/stub_game.rs` gained both Force Quit arms on every OS (no `cfg` gate on the arms; the marker script has a `.sh` and a `.bat` form).
- The D-29 todo, with `severity: minor`, `platform: any`, `ready: code` in that order; `pnpm planning-gates` passes (12/12).

## Deviations from Plan

### Judgement calls

**1. The source of Task 2 is in Task 1's commit.** The refusals, the owed script, the cap and `announce` live in the same functions as the tracer's adoption (`process_record`, `start_bounded`, the registry kills), so one buildable commit holds all of `readopt.rs`; Task 2's commit holds its tests and the Wine-shaped arm (the same call 88.3-06 and 88.3-07 made).

**2. `start_with_host` and `start_bounded` exist beside `start(ctx)`.** `start(ctx)` is the plan's signature and gives an owed or exit after-script an empty environment (the crate reads no environment, and `run_script_for_game` replaces the environment with `host.env`). A real script that needs `HOME` or `PATH` wants the shell's own `RunnerHost`. **88.3-12 should call `start_with_host` with the host the shell already builds for launch scripts**; its plan says `readopt::start`, which still works but runs scripts with only the `HEROIC_GAME_*` block.

**3. Play time follows the quit-kill, not a literal reading of "from `startPlayingAtMs`".** `totalPlayed` is the session from the launch's own start (`launchStartedAtMs`, as the funnel's tail and the quit hook do) and the runs-for-me record uses `startPlayingAtMs`. One shared function (`record_session_playtime`) serves both, so the two ways a session can end outside the funnel's tail cannot drift. `run.rs` is outside `files_modified`; its change is `begin_session` becoming `pub(crate)` and its hook calling that function (the golden funnel replay is unchanged: 59/59).

**4. Files outside `files_modified`:** `ctx.rs` (the frontend-ready mark the plan names, "the context's mark"), `lib.rs` (`task_handle`), `funnel/run.rs` (above). `game/mod.rs` and `record.rs` are in the list.

**5. The re-adopted line is forced** (written even when the game's logs are disabled) and the log is closed with the end marker when the session ends, as the funnel's own launch-note warnings are. Nothing rotates (`rotate_owed` is false from `open_appending`); the stub arm asserts the batch carried no rotation.

**6. The exit watch does not refresh the member list.** The proof is the record's members as of the crash; the live funnel's `refresh_members` keeps them current, a re-adopted game's watch does not. A re-adopted Wine game is over for GameLib when every recorded member has exited, even if a newer process of the group still lives. Cheap to add later (the watch would re-snapshot while `identify` answers `Member`); not done because the plan's proof is the record's and the kill must prove the tree it acts on.

**7. A shutdown during a re-adopted game's after-script rewrites the record as `quitKilled`.** Play time is already recorded at that point, so what is owed is only the script, which is exactly the D-31 shape; without it the next boot would find the game gone and drop the record, losing the script.

**8. A newer-version record, an I/O error, a symlink or a folder is left and counted `skipped`**, not removed (not ours to judge or delete); a `Decode`, `TooLarge` or `Insecure` file is removed only when it is a regular file of the current user.

**9. `--after-script <path>` was added to the stand-in's funnel mode** (the plan lists `--funnel` and `--game` only); the script's path has to reach the in-binary `launch_facts`.

## Known limits (for 88.3-12, 88.3-21)

- **Single flight and a re-adopted game.** The funnel's single-flight table does not know an adopted game, so a Play pressed for it would start a second copy. The renderer shows it as Playing (no Play button), so this is not reachable from the UI; a check in `run_launch` against `registry.contains` is the guard if it ever is.
- **Windows:** not run here (cross-clippy on `x86_64-pc-windows-gnu` is clean, host and `--all-targets`). The Game Job's name goes with its last handle (88.3-03), so after a crash only a still-living leader re-adopts on Windows; the first Windows run is windows-latest in 88.3-21. The marker script is a `.bat` that gets `SystemRoot`, `ComSpec` and `PATH` from the test.
- **Live gate:** 88-HUMAN-UAT item 3 (the game alive after `kill -9`, Playing once the renderer listens, the re-adopted line, no further output, play time and the after-script on exit) needs the shell wiring of 88.3-12 first.
- Flagged assumption (spec-less edge probe): SVC-03's edge-coverage row is `unclassified` and unresolved; re-adoption is outside the golden oracle (D-10). `requirements:` SVC-03 was not marked complete: it is phase-level.
