# Phase 34.13 — UI Design Contract

> Visual and interaction contract for the Steam install-time quick-install split button and its
> "Install with options…" wine/bottle dialog.
>
> **⚠ AMENDED 2026-08-15.** D-21..D-28 (`34.13-CONTEXT.md` §"Amendments — quick-install model")
> retired the auto-open trigger model this contract originally described (D-13's always-show
> setting is CUT; the three invisible open-triggers are gone). The install control is now a
> **split button** — primary click = instant quick install, caret/context-menu = "Install with
> options…", which opens the SAME dialog this contract already specced, now reached by explicit
> user request instead of by a hidden predicate. Sections below carry inline markers:
> **SUPERSEDED by D-NN** for content this amendment replaces, unchanged text for content D-21..D-28
> does not touch. The phase no longer targets "GOG parity" — per D-28 it overshoots it (Steam gets
> a one-click default GOG does not have); the directory slug is left unchanged deliberately (see
> ROADMAP.md's own note on why renaming it would desync phase lookup).
>
> **This is still a composition phase, not a fresh-design phase.** Every visual primitive this
> phase needs already exists in the codebase (`Dialog`, `SelectField`, `TextInputField`,
> `WineSelector`, `InfoIcon`, `.infoBox`, the `buttonWithIcon`/`fa-spin` busy idiom, `Dropdown`,
> `ContextMenu`/`Item`, the `faChevronDown` caret-rotation idiom already shipped in
> `FilterFacetGroup`). This contract's job is to say **which existing pieces compose into which
> states**, not to invent new tokens. Do not introduce parallel spacing/color/type values — that
> would violate GameLib's own multi-theme survival rule (theme-aware CSS custom properties only,
> never hardcoded hex).

## Section-Gating Matrix

**⚠ REWORKED by D-22/D-26 — the OLD matrix's indexing is dead, the section-render logic survives.**
The old matrix was indexed by *(Host OS, Game kind, Native install setting, Always-show, Library
count)* and answered "does the form open, and if so what renders?" via the predicate
`opens = bottleRequired OR (nativeInstallOn AND libraryCount > 1) OR alwaysShowOn`. **All three
auto-open triggers retire under D-22** ("the auto-open triggers RETIRE. The user is the trigger"),
and `alwaysShowOn` no longer exists as an input at all (D-26 cuts the setting; D-13 is RETIRED).

**Read the table below as: given the dialog is ALREADY OPEN — because the user clicked "Install
with options…" — which of the four regions render?** There is no more "Form opens?" column: every
row below is reached only by an explicit click, never by an invisible trigger. Regions: **Platform
row**, **Library dropdown**, **Wine section** (engine + read-only bottle name + D-14 notice),
**Free-space line**. This is D-11's "sections render only when relevant" model — D-22 confirms it
"survives in substance," reached by user intent instead of by a setting.

The two remaining inputs that still decide section content — `bottleRequired` (macOS-only,
structurally false for Windows/Linux and for a mac-native game with macOS still selected) and
`nativeInstallOn`/`libraryCount` (still governing whether the library dropdown and free-space line
are WORTH showing, via the same pre-existing `listSteamLibraryTargets()` gate) — are unchanged
facts about the backend, not new decisions. `nativeInstallOn` OFF and `nativeInstallOn` ON-with-
≤1-library render **identically** (the IPC gate returns `[]` either way, RESEARCH.md's Open
Question section) and are merged into one row below, exactly as the prior draft already did for
its always-show-ON wildcard rows — this revision applies that same merge to every row, not just the
always-show ones, since there is no longer an always-show axis to make it conditional on.

| # | Host OS | Case | Native install / library count | Platform row | Library dropdown | Wine section | Free-space line |
|---|---------|------|-------------------------------|---------------|-------------------|---------------|-------------------|
| 1 | macOS | Bottle-required (non-native / 32-bit game) | any | read-only "Windows" (D-03; no macOS option exists for this game at all) | **NO** — destination is the bottle's `steamapps`, never a host library (D-02 qualification) | **YES** — engine picker + read-only `GameLibSteam` name (D-05) + D-14 notice, always visible | **NO** — D-06/D-08 forbid it inside the wine/bottle path |
| 2 | macOS | Mac-native, **macOS selected** (default on open) | OFF, or ON with ≤1 library | **SELECTABLE** — macOS (default) vs. Windows-via-bottle, Windows offered only if the game has a Windows depot (D-17; signal TBD by planning) | **NO** | **NO** | **NO** |
| 3 | macOS | Mac-native, **macOS selected** (default on open) | ON, **>1** library | **SELECTABLE** (same as row 2) | **YES** — chosen host library | **NO** | **YES** |
| 4 | macOS | Mac-native, **Windows selected** (forced via bottle) | any | **SELECTABLE**, Windows now shown as the chosen value | **NO** — destination flips to the bottle the instant Windows is selected | **YES** — appears the instant Windows is selected | **NO** |
| 5 | Windows (host) | any Steam game | OFF, or ON with ≤1 library | read-only "Windows" (D-19 — only one option, ever) | **NO** | **NO** — bottle never applies off-mac | **NO** |
| 6 | Windows (host) | any Steam game | ON, **>1** library | read-only "Windows" (D-19) | **YES** | **NO** | **YES** |
| 7 | Linux (host) | any Steam game | OFF, or ON with ≤1 library | **does not render at all** (D-18, always) | **NO** | **NO** | **NO** |
| 8 | Linux (host) | any Steam game | ON, **>1** library | **does not render at all** (D-18) | **YES** | **NO** | **YES** |

**Rows 5 and 7 are the content-light case D-20 accepts as-is (Q6):** one read-only platform row +
Install button on Windows; literally only a header + Install button on Linux (whose platform row
never renders at all, D-18). **Do not build an empty state** — this IS the correct render. The
expectation-setting line that used to live in the always-show setting's tooltip now lives in the
Copywriting Contract's Q6 `contentLightNotice`, shown only for rows 5 and 7 (see that row above).

**The old "Row 4 discretion call" is resolved by construction, not by a fresh decision.** The prior
draft had to decide what the platform row shows when the `>1`-library trigger fired on macOS
*without* the always-show setting also being on — an edge case where the dialog opened but the
platform row's own selectability rule (D-17) hadn't separately been "earned." **That edge case no
longer exists.** Every row in this table is now reached only via an explicit "Install with
options…" click, and D-17 makes the macOS platform row selectable unconditionally for a mac-native
game (D-17: "On macOS the platform row is SELECTABLE… D-17 stands unchanged," D-26's own text).
There is no longer a path where the dialog opens for a mac-native game on macOS and the platform
row is anything other than row 2's or row 3's SELECTABLE state — the read-only-"Windows"-by-default
question the old note wrestled with cannot arise anymore.

**Zero-friction preservation, restated for the new model:** every row above describes the state of
the **options** dialog once it is open. **None of these rows can be reached by the quick-install
half of the split button** — D-23 (quick install always targets primary) and D-25 (quick install
needs no eligibility probe at all) guarantee the quick path never opens this dialog. The prior
draft's nine-row "must never auto-open" enumeration is retired by construction, not merely
satisfied: with the auto-open triggers gone (D-22), there is no longer any state this table
describes that could be *reached* without the user's explicit click in the first place.

## Interaction Contract: D-17 Platform-Switch (macOS, Rows 2/3 → Row 4)

**This is still the single most important interaction in this phase — unaffected by D-21..D-28
except for its row numbers (renumbered above) and the fact it is now reachable via the caret
instead of the always-show setting.** When the options dialog is open for a mac-native game and
the user flips the platform `SelectField` from "macOS" to "Windows":

1. **Trigger:** `onChange` of the existing `platformSelection()` `SelectField` (already wired to
   `setPlatformToInstall` in `InstallModal/index.tsx:142-144`) — no new event plumbing, reuse the
   existing handler verbatim; only the *availability/read-only* condition around it is new.
2. **What appears, in this order, top-to-bottom in the existing `DialogContent` flow (children
   position unchanged from every other sibling — platform row, then wine section, then footer):**
   - The wine engine `SelectField` (`WineSelector`'s CrossOver-filtered list, D-16) — **appears**
     directly below the platform row.
   - The read-only bottle-name field (D-05), pre-filled `GameLibSteam` — appears directly below
     the engine picker (matches `WineSelector`'s own existing internal order — see
     `WineSelector/index.tsx:150-179` — do not reorder that internal sequence, only mount/unmount
     the whole `<WineSelector>` block).
   - The D-14 shared-bottle notice (`.infoBox`, `faWarning`, default color) — appears immediately
     after the bottle-name field, inside the same mounted block.
   - Simultaneously, if a library dropdown was showing (native install ON, >1 library, macOS still
     selected a moment ago — row 3), it **disappears** — the destination is no longer a host
     library.
3. **Animation vs. snap:** **snap, no animation.** `WineSelector` already renders as a plain
   conditional mount (`{hasWine ? <WineSelector .../> : null}` — `InstallModal/index.tsx:186-199`,
   unchanged pattern for every existing sibling). This phase must not introduce a height-transition
   `.12s–.22s ease` for this mount/unmount — that CSS pattern is reserved (per
   `sketch-findings-gamelib`) for panel-width transitions in the nav redesign, a different surface
   entirely. A sudden reveal is the existing, consistent behavior of this exact mechanism elsewhere
   in `InstallModal`. **Note:** the split-button caret's own rotation DOES use a `.12s ease`
   transform transition (see Split-Button Control Contract below) — that is a *different*, much
   smaller affordance (an icon rotating in place), not a height/layout transition, so it does not
   contradict this "no animation for section mount/unmount" rule.
4. **Dialog height change:** the `Dialog` shell already handles this — `.InstallModal__dialog` is
   `max-height: 90vh` with internal scroll (inherited unchanged). No new height-management code is
   needed.
5. **Flipping back (Windows → macOS):** the wine section unmounts, the D-14 notice unmounts with
   it, and — if the >1-library condition still holds (row 3) — the library dropdown reappears.
   **Any wine-engine/bottle-name selection the user made while on Windows is discarded, not
   preserved**, matching the existing `hasWine` unmount behavior for every other sibling dialog.
6. **Windows availability gating (D-17's own open item):** the Windows option in the platform
   `SelectField` must not render at all if the game has no Windows depot. The `MenuItem` for
   Windows is simply absent from the list (not present-but-disabled) when unavailable — same
   pattern `platforms.filter((p) => p.available)` already uses in `InstallModal/index.tsx:92-94`.
   Do not render a disabled/greyed Windows option with an explanatory tooltip.

**Manual-only:** per `34.13-VALIDATION.md`, this entire transition is structurally unprovable by
Jest (no jsdom). The manual UAT gate must click through steps 1→5 above on a real mac-native Steam
game, reached via the caret/context-menu "Install with options…" path (not an always-show setting,
which no longer exists), on BOTH Electron and Tauri (`pnpm tauri:dev`, never `tauri dev`).

## Split-Button Control Contract (D-21, D-27) — NEW SURFACE

**This section did not exist in the prior draft — D-21's split button has no visual/interaction
contract until now.** The install control becomes a split button: primary click = quick install
(D-23/D-25, no dialog), caret/menu = "Install with options…" (opens the dialog specced above).
**Per-surface shapes genuinely differ (D-27) — do not homogenize them into one component.**

**This contract specs the composition assuming plan 34.13-08 successfully wires each surface to
the split behavior. It does not itself spec routing/call-site wiring** — that is plan 08's job.
Flag explicitly: RESEARCH.md's Q4 found `MainButton`'s Steam Install button and several other
named call sites **do not currently reach `openInstallGameModal` at all** under current HEAD
(Steam bypasses it via a separate hardcoded call in `GamePage/index.tsx:677-688`). This contract
describes the TARGET composition, not something already working today.

### MainButton (`GamePage/components/MainButton.tsx`) — TRUE split button

**Composition — reuse `Dropdown` for the caret half exactly as `FilterFacetGroup` already does,
plus the existing unchanged Install button for the primary half:**

- **Primary half:** the existing `<button className="button is-primary/is-secondary/… mainBtn">`
  Install control (`MainButton.tsx:279-309`) — **zero visual change**. Same classes, same "Install"
  copy (`getButtonLabel()`, unchanged), same disabled/status branching. Only its `onClick` handler
  changes (routing concern, out of this contract's scope).
- **Caret half — NEW, composed from `Dropdown` (`frontend/components/UI/Dropdown/index.tsx`)
  exactly as `FilterFacetGroup/index.tsx:69-83` already composes it:**
  ```tsx
  <Dropdown
    className="SteamInstallCaret"       // new, scoped wrapper class — naming discretionary
    buttonClass="button mainBtn outline" // reuse the SAME visual weight the (Steam-hidden) Import
                                          // button used to have — MainButton.tsx:314's retiring class
    title={
      <span aria-label={t('gamelib:steam.install.withOptionsLabel', 'Install with options…')}>
        <FontAwesomeIcon icon={faChevronDown} className="SteamInstallCaret__icon" />
      </span>
    }
  >
    <button onClick={/* opens the options dialog */}>
      {t('gamelib:steam.install.withOptionsLabel', 'Install with options…')}
    </button>
  </Dropdown>
  ```
  **Why the `<span aria-label>` wrapper:** `Dropdown`'s own `Props` type
  (`Dropdown/index.tsx:4-9`) has no `aria-label` prop, only `title: ReactNode`. Per the standard
  accessible-name-from-content algorithm, an `aria-label` on a *descendant* of the `<button>`
  overrides that descendant's contribution to the button's computed name — this is the same
  mechanism, applied to an icon-only case, that `FilterFacetGroup` avoids needing (it has a
  visible text label beside its chevron, so it never hits this gap). **Do not add a new prop to
  `Dropdown` for this** — the wrapper span is a zero-new-API solution that keeps `Dropdown`'s
  existing 8-test disclosure suite (`Dropdown/__tests__/dropdownDisclosure.test.tsx`) passing

## D-24 Degrade-into-Options Contract — NEW SURFACE

**D-24: if the quick-install target library is missing or full at click time, quick install
degrades into the options dialog "with the problem surfaced," rather than erroring out.** No
contract for this existed in the prior draft; this section is the visual/copy contract for it.

- **When this applies:** only when native install is ON. Quick install's local validity check
  (`window.api.checkDiskSpace(targetSteamappsDir)` — RESEARCH.md Q3, no new IPC) is only meaningful
  when GameLib actually controls a host-library write target. With native install OFF, quick
  install is the unchanged delegated `steam://install` path (D-06/D-08's established rationale) —
  there is no local path for GameLib to check, so D-24 structurally cannot fire there. This is a
  fact about D-24's own scope, not a new gating decision this contract is inventing.
- **What triggers the degrade:** `checkDiskSpace`'s `validPath === false` (library missing/
  unreachable) → `libraryMissingNotice`; OR free space below a Claude's-Discretion sanity floor
  (no existing threshold constant found this session, per RESEARCH.md Q3) → `libraryFullNotice`.
- **Visual result:** the options dialog opens (same dialog the Section-Gating Matrix describes),
  with the appropriate D-24 notice (Copywriting Contract, above) rendered at the TOP of
  `DialogContent`, above the platform row — the first thing the user sees, distinguishing this
  open from a deliberate "Install with options…" click (which shows no notice at all). Same
  `.infoBox` shape as the D-14 notice, but in `--status-danger` (see Color section) since this is
  a genuine local failure, not a fact-stating aside.
- **Everything below the notice renders per the Section-Gating Matrix as normal** — the notice is
  an ADDITION at the top, not a replacement for the platform row / library dropdown / wine section
  / free-space line, whichever combination the game's actual state calls for.
- **⚠ Flag to planning — a genuine functional gap this UI-SPEC cannot resolve alone:** D-24 fires
  only when `nativeInstallOn` is true, and the Section-Gating Matrix's library-dropdown gating
  (rows 3/6/8) only shows a dropdown when `libraryCount > 1`. **If the failing library is the
  user's ONLY library** (`libraryCount ≤ 1`), the degraded dialog still opens per D-24, but there
  is no second library to offer in a dropdown that (per the matrix) would not render at all. The
  honest visual response in that specific corner is to show the D-24 notice plus whatever install
  affordance the matrix's other rows already produce (rows 5/7's content-light shape) — **not to
  fabricate a picker with nothing in it.** This is a real, unaddressed functional question (what
  IS the Install button supposed to do if the one library it would target is the one that just
  failed?) that this contract flags rather than silently resolves — it is a backend/routing
  question, not a visual one.

## D-25 Busy State Contract — SUPERSEDES the prior "D-12 Busy State Contract" (EXACTLY INVERTED)

**⚠ The prior draft's "D-12 Busy State Contract" section is SUPERSEDED by D-25 and its core claim
is EXACTLY INVERTED.** It opened: "**Where it renders: NOT inside the new dialog.**" D-25 says the
opposite: *"The options dialog opens INSTANTLY; the wine section carries the eligibility loading
state; the dialog's own Install button stays disabled until it resolves."* Its premise (the
eligibility check has to resolve BEFORE the decision to open the dialog is made) was correct only
under the retired auto-open model, where the click itself didn't yet know if a dialog should
appear at all. Under D-21..D-28, the user has already asked for the dialog by clicking "Install
with options…" — withholding it for up to 15 seconds is now a dead click, not a safety measure.

- **Scope — macOS only.** `isSteamBottleEligible`'s backend predicate is
  `if (!isMac) return false` (RESEARCH.md Pattern 3, `games.ts:1328`) — a Windows or Linux host
  knows `bottleRequired` is `false` synchronously, with zero network/metadata dependency. **The
  loading state described below applies ONLY when `hostPlatform === macOS`.** On Windows/Linux,
  the dialog opens fully-resolved every time — the Section-Gating Matrix's rows 5-8 render
  immediately, no loading affordance needed, and the dialog's own Install button is never disabled
  by this mechanism.
- **On macOS, what the loading state looks like:** the same, already-existing `buttonWithIcon` +
  `faSyncAlt.fa-spin` idiom the prior draft specced for the origin button — **relocated, not
  redesigned** — now rendered in the physical DOM position `<WineSelector>` would otherwise mount
  (i.e., where row 1's wine section, or row 3/4's absence-of-one, would appear once resolved):
  ```tsx
  // Same shape as MainButton.tsx:182-186 / GameCard/index.tsx:252-258, relocated into the dialog
  <span className="buttonWithIcon">
    <FontAwesomeIcon icon={faSyncAlt} className="fa-spin" />
    {t('gamelib:status.checkingSteamInstallOptions', 'Checking install options…')}
  </span>
  ```
  This key is REUSED verbatim, not renamed — only its render location changes.
- **Resolution:** once the `isSteamBottleEligible` verdict returns, the loading row is replaced —
  **snap, no animation**, consistent with the existing "no transition for this mount/unmount
  mechanic" rule already established for the D-17 platform-switch section above — by either the
  full wine section (row 1, or row 4 if the user has meanwhile switched to Windows) if
  `bottleRequired` resolves true, or by nothing at all (rows 2/3) if the game is confirmed
  mac-native. The library dropdown / free-space line are NOT gated by this loading state — those
  depend only on `nativeInstallOn`/`libraryCount`, both known synchronously at open time; they can
  render immediately alongside the loading row.
- **Dialog's own Install button:** `disabled={true}` for the duration of the macOS-only loading
  window — this is the ONE piece of the prior draft's busy-state contract that is preserved,
  relocated from the origin control to the dialog's own footer button.
- **"No half-rendered modal" rule — REVERSED, not merely relocated.** The prior draft's rule was
  "the dialog must not mount until the verdict is known — there is no partial state to design."
  Under D-25, the dialog mounts INSTANTLY and the wine-section area IS the partial state — this
  contract's job was to design exactly that partial state, which is what the loading row above is.
- **The quick-install path needs NO eligibility probe at all** (D-25's own text: "the backend
  already resolves it inside `install()`"). This removes the entire 15-second dead-click risk from
  the DEFAULT path — the busy state above only ever appears inside the deliberately-opened options
  dialog, never blocking the primary split-button click.
- **Worst case: still 15 seconds** (`METADATA_FETCH_TIMEOUT_MS`, `state.ts:30`) — but now it is
  time-with-a-disabled-dialog-Install-button on a cold metadata cache, not time-on-a-spinning-
  origin-button. This number should appear verbatim in the plan's busy-state task and the manual
  UAT script, same as before, just re-scoped to the new location.
