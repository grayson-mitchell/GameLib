# Phase 34.13 — UI Design Contract

> Visual and interaction contract for the Steam install-time wine/bottle form (GOG parity).
> Generated by gsd-ui-researcher, verified by gsd-ui-checker.
>
> **This is a composition phase, not a fresh-design phase.** Every visual primitive this dialog
> needs already exists in the codebase (`Dialog`, `SelectField`, `TextInputField`, `ToggleSwitch`,
> `WineSelector`, `InfoIcon`, `.infoBox`, `.toggleRow`, the `buttonWithIcon`/`fa-spin` busy idiom).
> This contract's job is to say **which existing pieces compose into which states**, not to invent
> new tokens. Sections below that would normally declare new values instead point at the exact
> existing token/class to reuse. Do not introduce parallel spacing/color/type values for this
> dialog — that would violate GameLib's own multi-theme survival rule (theme-aware CSS custom
> properties only, never hardcoded hex).

## Interaction Contract: D-17 Platform-Switch (macOS, Row 5)

**This is the single most important interaction in this phase.** When the always-show form is open
for a mac-native game and the user flips the platform `SelectField` from "macOS" to "Windows":

1. **Trigger:** `onChange` of the existing `platformSelection()` `SelectField` (already wired to
   `setPlatformToInstall` in `InstallModal/index.tsx:142-144`) — no new event plumbing, reuse the
   existing handler verbatim; only the *availability/read-only* condition around it is new.
2. **What appears, in this order, top-to-bottom in the existing `DialogContent` flow (children
   position unchanged from every other sibling — platform row, then wine section, then footer):**
   - The wine engine `SelectField` (`WineSelector`'s CrossOver-filtered list, D-16) — **appears**
     directly below the platform row.
   - The read-only bottle-name field (D-05), pre-filled `GameLibSteam` — appears directly below
     the engine picker (matches `WineSelector`'s own existing internal order: bottle name is
     already rendered above the engine `SelectField` inside `<details>` — see
     `WineSelector/index.tsx:150-179` — do not reorder that internal sequence, only mount/unmount
     the whole `<WineSelector>` block).
   - The D-14 shared-bottle notice (`.infoBox`, `faWarning`, default color) — appears immediately
     after the bottle-name field, inside the same mounted block (it is part of the wine section,
     not a separate region).
   - Simultaneously, if a library dropdown was showing (native install ON, >1 library, macOS still
     selected a moment ago), it **disappears** — the destination is no longer a host library.
3. **Animation vs. snap:** **snap, no animation.** `WineSelector` already renders as a plain
   conditional mount (`{hasWine ? <WineSelector .../> : null}` — `InstallModal/index.tsx:186-199`,
   unchanged pattern for every existing sibling). This phase must not introduce a height-transition
   `.12s–.22s ease` for this mount/unmount — that CSS pattern is reserved (per
   `sketch-findings-gamelib`) for panel-width transitions in the nav redesign, a different surface
   entirely. A sudden reveal is the existing, consistent behavior of this exact mechanism elsewhere
   in `InstallModal` (e.g. `hasWine` toggling for every other runner) — keep it consistent, don't
   special-case Steam into motion no sibling dialog has.
4. **Dialog height change:** the `Dialog` shell already handles this — `.InstallModal__dialog` is
   `max-height: 90vh` with internal scroll (inherited unchanged from the shared `Dialog` component;
   confirmed every existing sibling with a variable-height `WineSelector` mount already relies on
   this, e.g. `ImportDialog`/`DownloadDialog`). No new height-management code is needed; this is a
   reuse guarantee, not a new requirement.
5. **Flipping back (Windows → macOS):** the wine section unmounts, the D-14 notice unmounts with
   it, and — if the >1-library condition still holds — the library dropdown reappears in its prior
   state. **Any wine-engine/bottle-name selection the user made while on Windows is discarded, not
   preserved**, matching the existing `hasWine` unmount behavior for every other sibling dialog
   (there is no existing precedent in this codebase for preserving a hidden section's form state
   across a platform toggle — inventing one here would be new, untested surface area outside
   CONTEXT.md's scope).
6. **Windows availability gating (D-17's own open item):** the Windows option in the platform
   `SelectField` must not render at all if the game has no Windows depot — CONTEXT.md leaves the
   depot-availability signal to planning. Whatever signal is chosen, the VISUAL contract is: the
   `MenuItem` for Windows is simply absent from the list (not present-but-disabled) when unavailable
   — same pattern `platforms.filter((p) => p.available)` already uses in
   `InstallModal/index.tsx:92-94` for every other platform. Do not render a disabled/greyed Windows
   option with an explanatory tooltip — that is a new pattern this codebase doesn't use anywhere
   else in this selector and CONTEXT.md doesn't ask for it.

**Manual-only:** per `34.13-VALIDATION.md`, this entire transition is structurally unprovable by
Jest (no jsdom). The manual UAT gate must click through steps 1→5 above on a real mac-native Steam
game with always-show ON, on BOTH Electron and Tauri (`pnpm tauri:dev`, never `tauri dev`).

## D-12 Busy State Contract

**Where it renders: NOT inside the new dialog.** The eligibility check (`isSteamBottleEligible`,
up to `METADATA_FETCH_TIMEOUT_MS` = 15s on a cold cache) runs **before** the decision to open the
dialog is even made (RESEARCH.md's sequence diagram: `startSteamInstall()` calls the IPC first,
*then* decides zero-friction vs. dialog-open). So the busy state belongs on the **originating**
Install control — whichever of `GameCard`'s install button or `MainButton`'s install button the
user actually clicked — not on a footer button inside a dialog that may not even open yet.

**Visual contract — reuse the existing "transient Steam status" idiom exactly, do not invent a new
one:**

```tsx
// Matches MainButton.tsx:182-186 and GameCard/index.tsx:252-258 verbatim shape
<span className="buttonWithIcon">
  <FontAwesomeIcon icon={faSyncAlt} className="fa-spin" />
  {t('gamelib:status.checkingSteamInstallOptions', 'Checking install options…')}
</span>
```

- Button itself: `disabled={true}` for the duration of the check — matches every other
  `is.installing`/`is.settingUpBottle` branch in `MainButton.tsx` that already disables + spins in
  place rather than swapping to a separate loading control.
- Both call sites need this state (`GameCard` AND `MainButton` AND `GameSubMenu`'s install entry,
  since D-10's trigger logic lives in the single `startSteamInstall()` chokepoint all of them share
  — RESEARCH.md confirms 7 call sites funnel through one function). Implementation only needs to
  gate on a single new transient state value (e.g. `is.checkingSteamInstallOptions`, naming left to
  planning) read the same way `is.installing`/`is.settingUpBottle` already are today — this is a
  state-plumbing task, not a new visual pattern per surface.
- **No half-rendered modal:** the dialog component itself must not mount until the eligibility
  verdict is known — i.e., `useInstallGameModal.setState({isOpen: true, ...})` only fires AFTER the
  IPC resolves, never before. There is no partial/skeleton state of the dialog to design — it either
  doesn't exist yet (busy state showing on the origin button) or exists fully-formed (all gating in
  the Section-Gating Matrix already resolved for that game).
- **Worst case:** 15 seconds of a spinning, disabled Install button on a cold metadata cache. This
  number should appear verbatim in the plan's busy-state task and the manual UAT script (per
  RESEARCH.md Pattern 3 / VALIDATION.md's Manual-Only table).
