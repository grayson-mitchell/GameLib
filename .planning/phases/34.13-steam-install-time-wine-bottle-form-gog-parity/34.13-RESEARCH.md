receives the identical prop set:

The fifth Steam branch takes the SAME shape (`SteamDialog` in the structure above). Add a
`isSteamManagedApp` boolean computed in `InstallModal/index.tsx` (parallel to the existing

checks (Steam games already skip `showDownloadDialog` entirely today via the `InstallGameModal.ts`

**D-03's exact guard:** `platformSelection()` (`InstallModal/index.tsx:129-158`) returns `null`

loosening `showPlatformSelection` to also render when `runner === 'steam' && availablePlatforms.length === 1`

CONTEXT.md.

**ThirdPartyDialog is the closer model, not DownloadDialog.** `DownloadDialog` (803 lines) owns

**Note (2026-08-15):** `ThirdPartyDialog` also carries an existing `.noticeIcon`/`.noticeInfo`

### Pattern 3: The isSteamBottleEligible IPC Channel

**NEEDS UPDATE.** The IPC design/placement guidance is STILL VALID. The "Cost bound (D-12)"
paragraph is **SUPERSEDED by D-25**: the busy state this cost bound justifies no longer gates the
click that opens the dialog — it now lives inside the already-open dialog's wine section (see Q5).
`METADATA_FETCH_TIMEOUT_MS` is still the correct number to cite, just for a different consumer
(plan 34.13-11's rewrite, not an origin-control busy state).

**Confirmed private, exactly as CONTEXT.md states:**
```typescript
// src/backend/storeManagers/steam/games.ts:1328
private isBottleEligible(): boolean {
  if (!isMac) return false
  const meta = steamMetadataStore.get(this.appId)
  if (meta?.mac_arch === '32') return true
  return meta?.platformsCaptured === true && meta?.is_mac_native === false
}
```
and `ensurePlatformsCaptured()` is also private (`games.ts:1383`).

**Recommended seam:** add ONE new public method to `SteamGame`, e.g.:
```typescript
// New — games.ts, alongside isNative()/isBottleEligible()
async checkBottleEligibility(): Promise<boolean> {
  await this.ensurePlatformsCaptured()
  return this.isBottleEligible()
}
```
This avoids widening the two private methods' visibility (which would let callers skip
`ensurePlatformsCaptured()` by accident) and avoids a third re-derivation of the predicate — the
exact anti-pattern D-09 rules out. The IPC handler then does:
```typescript
addHandler('isSteamBottleEligible', async (_e, appName: string) =>
  new SteamGame(appName).checkBottleEligibility()
)
```
`SteamLibraryManager.getGame(id)` (`library.ts:535-536`) already does exactly `new SteamGame(id)` —
confirms this instantiation is the established pattern, not a workaround.

**Cost bound (D-12):** `METADATA_FETCH_TIMEOUT_MS = 15000` (`src/backend/storeManagers/steam/state.ts:30`).
`ensurePlatformsCaptured()`'s bounded poll (`games.ts:1399-1408`) waits up to this value in 100ms
increments before giving up — so the Install button's busy state (D-12) has a real worst-case of
15 seconds on a cold cache. This is the number the plan's busy-state task and any UAT script should
cite explicitly.

**CONTRADICTION with CONTEXT.md's sidecar file:** CONTEXT.md's canonical_refs section says the new
channel "must land on both Electron `main.ts` and the Tauri sidecar's `installFlowRegistration.ts`."
Verified: `installFlowRegistration.ts` (`src/backend/sidecar/installFlowRegistration.ts`) is real and
does host `listSteamLibraryTargets` (line 189-190), but its own doc-comment (lines 1-77) scopes it
explicitly to "install/uninstall/update-check" — five handlers, none bottle-related. The actual
sibling cluster — `steamBottleProvision`, `isSteamBottleProvisioned`, `steamBottleStatus` — is
registered in **`steamAuthFlowRegistration.ts`**, whose own doc-comment (lines 42-53) names this
exact group "macOS CrossOver bottle trio." `isSteamBottleEligible` is conceptually a fourth member
of that trio (eligibility precedes provisioning/status), so it belongs beside them in
`steamAuthFlowRegistration.ts`, matching `main.ts:927-936`'s own physical grouping. Recommend the
planner register it there, not in `installFlowRegistration.ts` — but this is a placement call, not

## Common Pitfalls

**STILL VALID** — Pitfalls 1-3 are unaffected by D-21..D-28.

### Pitfall 1: Treating D-14's store write as sufficient for D-15's handoff
**What goes wrong:** A plan that only adds the `persistBottleWineVersion()` call on the form's
confirm handler will pass every test that checks the store value, while `SteamBottleSetup.tsx`
silently continues to re-derive its own default and never reads the stored value — the user answers
the wine-engine question twice, exactly what D-15 says must not happen.
**Why it happens:** `getSteamBottleSettings()`/`persistBottleWineVersion()` genuinely are the
correct backend seam (confirmed, Pattern 4 above) — it's easy to assume "the backend already reads
this everywhere" without checking the ONE frontend surface (`SteamBottleSetup.tsx`) that also needs
it.
**How to avoid:** Make the `SteamBottleSetup.tsx` wiring change (Pattern 4, item 2) its own
explicit plan task with its own acceptance check — not a bullet inside the D-14 store-write task.
**Warning signs:** A plan that lists D-14 and D-15 as a single task, or that never modifies
`SteamBottleSetup.tsx`.

### Pitfall 2: Registering the new IPC channel on only one runtime path
**What goes wrong:** Adding `addHandler('isSteamBottleEligible', ...)` to `main.ts` only. Under
Tauri, `window.api.isSteamBottleEligible` would then silently reject via the
`UNPORTED_CHANNEL_MARKER` mechanism (per this repo's own documented SEAM.md Invariant B) — the form
would appear to hang forever in the D-12 busy state on the Tauri build specifically, while working
fine under Electron. This is exactly the class of defect the standing IPC-PORT-INVENTORY.md
discipline exists to catch, but a NEW channel invented in this phase won't be caught by it
automatically — the planner must add the registration to both files as one atomic change.
**How to avoid:** One task, two file edits (`main.ts` + `steamAuthFlowRegistration.ts`, not
`installFlowRegistration.ts` per the corrected placement above), verified by a test that asserts
the preload surface exposes the channel and (ideally) that both registration files declare it.
**Warning signs:** A plan task that touches only `src/backend/main.ts` for this channel.

### Pitfall 3: Filtering the wine-engine list in the wrong layer
**What goes wrong:** Filtering `wineVersionList` down to CrossOver-only inside the new Steam
dialog (or inside `InstallModal/index.tsx`'s shared `useEffect`) rather than inside `WineSelector`
itself. This works for the new dialog but leaves `SteamBottleSetup.tsx`'s independent
`getAlternativeWine()` call unfiltered, so the folded-todo's frontend half (D-16) is only half-closed
— GPTK/plain-Wine engines remain selectable from the guided-setup dialog even after this phase.
**How to avoid:** Filter inside `WineSelector` gated on its existing `runner` prop (Pattern 2
above) so both callers that already pass `runner="steam"` benefit automatically.
**Warning signs:** A diff that touches `InstallModal/index.tsx` or a new dialog file but not
`WineSelector/index.tsx` for the D-16 task.

### Pitfall 4: Assuming the empty-library-list case needs new gating code
**⚠ NEEDS UPDATE.** The core principle (trust the existing gate, don't duplicate it) is STILL
VALID. Its premise references the always-show setting's "just in case" suppression, which no

**What goes wrong:** Writing a new `isSteamNativeInstallEnabled` frontend check to suppress the

### Q1 — D-23: What does "Steam's primary library" actually resolve to?

**Verdict: "primary" is index 0 of `listSteamLibraryTargets()`'s array, which is NOT read from any
Steam-native "default library" designation in `libraryfolders.vdf` — it is the first surviving
entry of a hardcoded-string-then-vdf-derived, existence-filtered array, and Phase 21's own D-09
code already treats it as ground truth today.**

Evidence chain, all direct reads this session:

1. `listSteamLibraryTargets()` (`src/backend/storeManagers/steam/installLocation.ts:61-68`) maps
   `getSteamLibraries()`'s returned array to `SteamLibraryTarget[]` and sets `isPrimary: index === 0`
   — literally "first element of the array," nothing more:
   ```typescript
   export async function listSteamLibraryTargets(): Promise<SteamLibraryTarget[]> {
     const libraries = await getSteamLibraries()
     return libraries.map((path, index) => ({
       path,
       steamappsDir: join(path, 'steamapps'),
       isPrimary: index === 0
     }))
   }
   ```

2. `getSteamLibraries()` (`src/backend/utils.ts:669-690`) builds that array as: a **hardcoded
   `'/usr/share/steam'` string, unconditionally first** (`utils.ts:673`), followed by every path
   found in `defaultSteamPath/steamapps/libraryfolders.vdf`'s `libraryfolders` object
   (`utils.ts:676-681`, parsed via `@node-steam/vdf`'s `parse()`), then the WHOLE array is filtered
   by `existsSync` (`utils.ts:681-683`):
   ```typescript
   export async function getSteamLibraries(): Promise<string[]> {
     const { defaultSteamPath } = GlobalConfig.get().getSettings()
     const path = defaultSteamPath.replaceAll("'", '')
     const vdfFile = join(path, 'steamapps', 'libraryfolders.vdf')
     const libraries = ['/usr/share/steam']
     if (existsSync(vdfFile)) {
       const json = parse(readFileSync(vdfFile, 'utf-8'))
       if (!json.libraryfolders) { return libraries }
       const folders: { path: string }[] = Object.values(json.libraryfolders)
       return [...libraries, ...folders.map((folder) => folder.path)].filter(
         (path) => existsSync(path)
       )
     }
     return libraries
   }
   ```

3. This hardcode is a KNOWN, already-documented quirk in this codebase — `clientSetup.ts:54-63`'s
   own doc comment on a different function (`hasLibraryFoldersVdf()`) explicitly warns about it:
   *"getSteamLibraries() ALWAYS includes a hardcoded '/usr/share/steam' fallback entry regardless of
   whether the vdf exists, so its array length/emptiness can never reliably signal 'vdf absent'."*
   This confirms the hardcode is deliberate (a Wine-lookup-path convention borrowed from
   `WineVersionSelector.tsx:221`'s own "where GameLib looks for Wine/Proton binaries" list — see
   `WineVersionSelector.tsx:205-222`) rather than an oversight, but it was written for a DIFFERENT
   purpose (locating Wine binaries) and was not audited for its effect on "which library is
   primary" when reused by `getSteamLibraries()`.

4. **Practical effect by host, traced through `existsSync` filtering:**
   - **Windows/macOS:** `defaultSteamPath` is a platform-correct path
     (`src/backend/config.ts:39-65`: `%PROGRAMFILES(X86)%\Steam` on Windows,
     `~/Library/Application Support/Steam` on macOS). `/usr/share/steam` does not exist on either
     platform, so it is filtered out by `existsSync` at `utils.ts:682`, and index 0 becomes the
     VDF's own first folder entry. `Object.values(json.libraryfolders)` at `utils.ts:680` iterates
     the parsed VDF object's own numeric-string keys (`"0"`, `"1"`, ...) — per the ECMAScript
     spec, integer-index-like string keys are always enumerated in ascending numeric order
     regardless of insertion order **[ASSUMED — this is a JS-engine ordering guarantee from
     training knowledge, not independently verified by running code against a real
     `libraryfolders.vdf` in this session]** — so VDF key `"0"` (conventionally the folder
     containing the Steam client's own install, per Steam's own libraryfolders.vdf format) lands
     at array index 0 on these two platforms. This is a reasonable, conventional "primary."
   - **Linux:** `defaultSteamPath` resolves to a Flatpak or native `.steam/steam` path
     (`config.ts:44-64`). IF a literal directory named `/usr/share/steam` exists on the user's
     machine (some Debian/Ubuntu-family `steam` packages install shared assets there — **[ASSUMED
     — not independently verified in this session; I did not have access to inspect a real Linux
     Steam install's filesystem, and no code in this repo checks for a `steamapps` subdirectory
     inside `/usr/share/steam` before accepting it]**), it survives the `existsSync` filter and
     claims index 0 / `isPrimary: true` **ahead of** the user's actual default library — even
     though nothing in `getSteamLibraries()` verifies `/usr/share/steam` is a real Steam game
     library (no `steamapps` subdirectory check at this layer; `listSteamLibraryTargets()` blindly
     appends `/steamapps` to whatever survived).

5. **Phase 21's own code already treats index-0/`isPrimary` as the definition of "primary" and
   already builds on it** — `resolveOverride()` (`installLocation.ts:201-219`) does
   `libraries.find((lib) => lib.isPrimary) ?? libraries[0]` when no override path is supplied
   (`installLocation.ts:205`), and this is the EXACT function `resolveSteamInstallTarget()` (the
   function that actually resolves an install's target directory) calls. `SteamInstallLocationPicker.tsx:28`
   uses the identical `libraries.find((lib) => lib.isPrimary) ?? libraries[0]` pattern on the
   frontend. **This means D-23 ("quick install targets Steam's primary library, always... preserves
   Phase 21's D-09 default exactly") is accurate as a description of EXISTING behavior — quick
   install calling `installSteamGame(appName, gameInfo)` with no `path` override already resolves
   to exactly this same index-0 definition of primary, because that is what `resolveOverride()`
   has always done.** D-23 introduces no new ambiguity; it inherits Phase 21's existing definition
   unchanged, quirks included.

**What this means for planning:** Planning does **not** need to write new code to answer "what
does primary mean" — the answer is "whatever `resolveOverride()`'s existing fallback already
resolves to when `installSteamGame()` is called with no path argument," which is unchanged by this
phase. Planning SHOULD, however, record the `/usr/share/steam` hardcode as a known, pre-existing,
**out-of-scope-to-fix** quirk (not introduced by D-23, not something this phase should touch) that
theoretically could put a non-game directory at "primary" on some Linux configurations. **D-24's
local validity check (Q3 below) is the practical safety net**: if `/usr/share/steam/steamapps`
does not exist as a writable directory, `checkDiskSpace()`'s `validPath` check will very likely
return `false` for it, causing quick install to degrade into the options dialog rather than firing
an install that silently fails — this is a fortunate synergy between D-23 and D-24 worth noting in

**COULD NOT VERIFY beyond this session's file reads:** whether a real `/usr/share/steam` directory
actually exists on any target Linux distribution GameLib ships to, and whether it would ever

### Q2 — D-21: Is `src/frontend/components/UI/Dropdown/` the right split-button primitive?

adjacent, independently-clickable primary `<button>` — that primary button is new code this


### Q3 — D-24: What does a "cheap LOCAL validity check" look like here?

**Verdict: the existing `window.api.checkDiskSpace(folder)` IPC is exactly the primitive D-24
