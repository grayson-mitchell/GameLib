# Phase 34.13: Steam install-time wine/bottle form (GOG parity) - Research

**Researched:** 2026-08-14
**Domain:** React/TypeScript frontend dialog composition + dual-runtime (Electron/Tauri sidecar) IPC, inside GameLib's existing Steam bottle-install machinery
**Confidence:** HIGH — every claim below was checked against the actual source at the cited `file:line`, not against CONTEXT.md's transcription of it. Two of CONTEXT.md's own citations are corrected below (marked CONTRADICTION).

## Summary

CONTEXT.md's 16 decisions are complete and internally consistent; this research does not
re-litigate any of them. Its job was to close the one question CONTEXT.md explicitly deferred
(the native-install gate's effect on D-10's multi-library trigger) and to nail down the exact
`file:line` seams D-01 through D-16 touch, since a planner working from CONTEXT.md's line numbers
alone will hit two real drift points.

The highest-value finding: `listSteamLibraryTargets()` (`installLocation.ts:61`) is **not itself**
gated on `isSteamNativeInstallEnabled()` — the gate lives in the two IPC handler wrappers
(`main.ts:913-914`, `installFlowRegistration.ts:189-190`), which return `[]` when the setting is
OFF. This is exactly what CONTEXT.md's code_context section said, and it resolves the open
question cleanly: D-10's ">1 library" trigger is *already* correctly scoped by the existing gate
with **zero new code** — it can only ever fire when native install is ON, mirroring Phase 21's own
rationale (a delegated `steam://install` ignores the path argument, so offering a choice would be
a lie). The only genuinely new decision this creates is a UX one for D-13's always-show setting:
with native install OFF, opening the always-show form on Windows/Linux yields a **platform-row-only
confirm dialog** (no library section — the list is empty, no wine section — not a bottle game).
Options and consequences are laid out below; this is Claude's Discretion territory CONTEXT.md
already flagged for copy, but the *degenerate-empty-state* shape itself was not previously named.

The second-highest-value finding is a genuine gap CONTEXT.md's D-15 assumed away:
`SteamBottleSetup.tsx` (the guided post-install surface) **does not read `getSteamBottleSettings()`
or `persistBottleWineVersion()`'s output today.** It derives its own default via
`resolveSteamBottleEngine(globalConfig.wineVersion, wineVersionList)` and always seeds
`crossoverBottle` to the hardcoded `DEFAULT_STEAM_BOTTLE_NAME` — it has no code path that reads the
store this phase's form writes to. D-15's "opens already carrying that wine version instead of
re-asking" is **not free** — it requires (a) exposing the persisted `wineVersion` to the frontend
(no existing IPC returns it: `steamBottleStatus` only returns `{provisioned, bottleName}`), and (b)
wiring `SteamBottleSetup.tsx` to prefer that value over its own `resolveSteamBottleEngine` default
when present. This must be an explicit task in the plan.

Third: CONTEXT.md's canonical_refs section states the new `isSteamBottleEligible` channel "must land
on both Electron `main.ts` and the Tauri sidecar's `installFlowRegistration.ts`." That sidecar file
is real and does host `listSteamLibraryTargets`, but the actual sibling cluster this new channel
belongs with — `steamBottleProvision`, `isSteamBottleProvisioned`, `steamBottleStatus` — is
registered in **`steamAuthFlowRegistration.ts`** (main.ts:927-936 ↔ `steamAuthFlowRegistration.ts`,
which documents exactly this "macOS CrossOver bottle trio" at its own doc-comment lines 42-53). This
is a CONTRADICTION of CONTEXT.md's stated sidecar file and should be corrected before planning
assigns the task.

**Primary recommendation:** build the fifth sibling dialog closely mirroring `ThirdPartyDialog`'s
shape (lean, no size/DLC/branch machinery) rather than `DownloadDialog`'s; add one public wrapper
method on `SteamGame` for the eligibility IPC rather than exposing the two private methods directly;
register the new channel beside the existing bottle trio in `steamAuthFlowRegistration.ts` (and
`main.ts`); and treat the SteamBottleSetup handoff wiring as its own explicit task, not a side effect
of D-14's store write.

### Pattern 1: The InstallModal Sibling-Dialog Contract

**What:** `InstallModal/index.tsx` (`src/frontend/screens/Library/components/InstallModal/index.tsx`)
owns ALL shared state (`winePrefix`, `wineVersion`, `wineVersionList`, `crossoverBottle`,
`platformToInstall`) and branches to exactly one of four sibling dialogs based on
`isThirdPartyManagedApp` / `isImportMode` / `showDownloadDialog` (lines 173-281). Every sibling
receives the identical prop set:

```typescript
// Source: src/frontend/screens/Library/components/InstallModal/ThirdPartyDialog/index.tsx:24-35
interface Props {
  backdropClick: () => void
  appName: string
  runner: Runner
  platformToInstall: InstallPlatform
  availablePlatforms: AvailablePlatforms
  winePrefix: string
  crossoverBottle: string
  wineVersion: WineInstallation | undefined
  children: React.ReactNode        // this is where {platformSelection()}{hasWine && <WineSelector .../>} land
  gameInfo: GameInfo
}
```

The fifth Steam branch takes the SAME shape (`SteamDialog` in the structure above). Add a
`isSteamManagedApp` boolean computed in `InstallModal/index.tsx` (parallel to the existing
`isThirdPartyManagedApp` at line 161) and branch on it before the `ImportDialog`/`DownloadDialog`
checks (Steam games already skip `showDownloadDialog` entirely today via the `InstallGameModal.ts`
chokepoint, so ordering only matters for the `isImportMode` case — Steam games do not support
import mode, so no conflict).

**D-03's exact guard:** `platformSelection()` (`InstallModal/index.tsx:129-158`) returns `null`
unless `availablePlatforms.length > 1` (line 130). For any bottle-eligible macOS game, `platforms`
(lines 65-90) only marks `Windows.available: true` unconditionally — `macOS.available` requires
`isMacNative` which is false by construction for a bottle-eligible game — so
`availablePlatforms.length === 1` and the row renders nothing today. D-03 requires either (a)
loosening `showPlatformSelection` to also render when `runner === 'steam' && availablePlatforms.length === 1`
(a new one-line branch condition), or (b) the Steam dialog rendering its own static read-only row
instead of calling `platformSelection()` at all — this is explicitly Claude's Discretion per
CONTEXT.md.

**ThirdPartyDialog is the closer model, not DownloadDialog.** `DownloadDialog` (803 lines) owns
`getInstallInfo` polling, DLC/SDL/branch/build selectors, a disk-space-with-projection block, and
`writeConfig` (`DownloadDialog/index.tsx:34,273-283`) — none of which apply per D-06/D-07/D-08/D-14.
`ThirdPartyDialog` (146 lines) is the closest existing shape: header + notice/content + `{children}`
(where `platformSelection()`/`WineSelector` land) + a footer with one Install button. The Steam
dialog additionally needs the D-02 library dropdown and D-08 free-space row, neither of which exist
in `ThirdPartyDialog`, but both are small, self-contained additions (a `<select>` matching
`SteamInstallLocationPicker.tsx:59-72`'s exact shape, and a single `window.api.checkDiskSpace(path)`
call reusing `DiskSpaceData.free` — `common/types.ts:710-716`).

### Pattern 2: WineSelector's Real Prop Surface

**What:** Full prop list, `src/frontend/screens/Library/components/InstallModal/WineSelector/index.tsx:19-47`:

```typescript
type Props = {
  setWineVersion: (newVersion: WineInstallation) => void
  setWinePrefix: (newPrefix: string) => void
  setCrossoverBottle: React.Dispatch<React.SetStateAction<string>>
  winePrefix: string
  crossoverBottle: string
  wineVersionList: WineInstallation[]
  wineVersion: WineInstallation | undefined
  title?: string
  appName: string
  runner?: Runner                  // already present, used today for isKnownNotToWork gating
  initiallyOpen?: boolean
  sharedPrefixNote?: string
  hideSharedPrefixToggle?: boolean
}
```

- **`showBottle`** (line 116) is `wineVersion?.type === 'crossover'` — purely derived from the
  selected engine's `.type`, not a prop. This already correctly hides the bottle-name field when a
  non-CrossOver engine is selected.
- **Engine list source:** `wineVersionList` is populated by the PARENT (`InstallModal/index.tsx`'s
  `useEffect` at lines 109-127, calling `window.api.getAlternativeWine()`) or, for the guided
  setup, by `SteamBottleSetup.tsx`'s own identical call (`SteamBottleSetup.tsx:68`). WineSelector
  itself does zero filtering of this list today.
- **D-16 (CrossOver-only filter) — concrete implementation seam:** the cleanest change is a
  `crossoverOnly?: boolean` prop (or an internal `runner === 'steam'` branch, since the component
  already receives `runner`) that computes `const engineOptions = crossoverOnly ? wineVersionList.filter(w => w.type === 'crossover') : wineVersionList` and uses `engineOptions` in place of
  `wineVersionList` at both the `<MenuItem>` map (line 173) and the `disabled={... || wineVersionList.length === 0}` check (line 164). Filtering **inside WineSelector**, gated on the existing `runner`
  prop, means `SteamBottleSetup.tsx` (which already passes `runner="steam"`) picks up the filter
  automatically too — that surface currently has NO engine filter at all (it relies solely on
  `resolveSteamBottleEngine`'s *default-selection* preference for CrossOver, not a *restriction*
  against picking GPTK/plain Wine from the dropdown). This closes part of the folded GPTK todo more
  completely than D-16's stated scope ("this phase's new dialog") — flag this side effect to the
  planner as a bonus-but-in-scope consequence of the natural implementation, not a scope expansion
  to seek separately.
- **D-05 (read-only bottle name) — confirmed no existing prop covers this.** The bottle-name
  `TextInputField` (lines 150-158) is `disabled={useSharedPrefix}` only. On the Steam guided-setup
  path (`hideSharedPrefixToggle` set), `useSharedPrefix` stays permanently `false`
  (`SteamBottleSetup.tsx:185` comment confirms this), so the field is NOT disabled there either —
  meaning today's `SteamBottleSetup.tsx` bottle name is actually EDITABLE even though the whole
  point of the dedicated bottle is a fixed name. **CONTEXT.md's claim that this "needs a new prop"
  is confirmed correct.** Add e.g. `bottleNameReadOnly?: boolean` and OR it into the `disabled`
  expression at line 156. Recommend applying this to `SteamBottleSetup.tsx` too for consistency
  (same latent editability gap exists there), though that surface is explicitly out of this phase's
  scope per CONTEXT.md's `<domain>` boundary — flag, do not silently fix.

### Pattern 3: The isSteamBottleEligible IPC Channel

**Confirmed private, exactly as CONTEXT.md states:**
```typescript
// src/backend/storeManagers/steam/games.ts:1328
private isBottleEligible(): boolean {
  if (!isMac) return false
  const meta = steamMetadataStore.get(this.appId)
  if (meta?.mac_arch === '32') return true
  return meta?.platformsCaptured === true && meta?.is_mac_native === false
}
```
and `ensurePlatformsCaptured()` is also private (`games.ts:1383`).

**Recommended seam:** add ONE new public method to `SteamGame`, e.g.:
```typescript
// New — games.ts, alongside isNative()/isBottleEligible()
async checkBottleEligibility(): Promise<boolean> {
  await this.ensurePlatformsCaptured()
  return this.isBottleEligible()
}
```
This avoids widening the two private methods' visibility (which would let callers skip
`ensurePlatformsCaptured()` by accident) and avoids a third re-derivation of the predicate — the
exact anti-pattern D-09 rules out. The IPC handler then does:
```typescript
addHandler('isSteamBottleEligible', async (_e, appName: string) =>
  new SteamGame(appName).checkBottleEligibility()
)
```
`SteamLibraryManager.getGame(id)` (`library.ts:535-536`) already does exactly `new SteamGame(id)` —
confirms this instantiation is the established pattern, not a workaround.

**Cost bound (D-12):** `METADATA_FETCH_TIMEOUT_MS = 15000` (`src/backend/storeManagers/steam/state.ts:30`).
`ensurePlatformsCaptured()`'s bounded poll (`games.ts:1399-1408`) waits up to this value in 100ms
increments before giving up — so the Install button's busy state (D-12) has a real worst-case of
15 seconds on a cold cache. This is the number the plan's busy-state task and any UAT script should
cite explicitly.

**CONTRADICTION with CONTEXT.md's sidecar file:** CONTEXT.md's canonical_refs section says the new
channel "must land on both Electron `main.ts` and the Tauri sidecar's `installFlowRegistration.ts`."
Verified: `installFlowRegistration.ts` (`src/backend/sidecar/installFlowRegistration.ts`) is real and
does host `listSteamLibraryTargets` (line 189-190), but its own doc-comment (lines 1-77) scopes it
explicitly to "install/uninstall/update-check" — five handlers, none bottle-related. The actual
sibling cluster — `steamBottleProvision`, `isSteamBottleProvisioned`, `steamBottleStatus` — is
registered in **`steamAuthFlowRegistration.ts`**, whose own doc-comment (lines 42-53) names this
exact group "macOS CrossOver bottle trio." `isSteamBottleEligible` is conceptually a fourth member
of that trio (eligibility precedes provisioning/status), so it belongs beside them in
`steamAuthFlowRegistration.ts`, matching `main.ts:927-936`'s own physical grouping. Recommend the
planner register it there, not in `installFlowRegistration.ts` — but this is a placement call, not
a hard blocker either way (both files are legitimate curated-registration modules with the same
`ipcMain.handle` mechanics); flag the correction and let planning make the final call.

### Pattern 4: The persistBottleWineVersion → SteamBottleSetup Handoff (the gap D-15 assumes away)

**Confirmed, `src/backend/storeManagers/steam/bottle.ts:276-309`:**
```typescript
export function getSteamBottleSettings(): GameSettings {
  const globalSettings = GlobalConfig.get().getSettings()
  const storedWineVersion = steamBottleConfigStore.get_nodefault('wineVersion')
  const storedBottleName = steamBottleConfigStore.get_nodefault('wineCrossoverBottle')
  return {
    ...globalSettings,
    wineCrossoverBottle: storedBottleName ?? DEFAULT_STEAM_BOTTLE_NAME,
    wineVersion: storedWineVersion ?? globalSettings.wineVersion
  }
}

export function persistBottleWineVersion(wineVersion: WineInstallation): void {
  steamBottleConfigStore.set('wineVersion', wineVersion)
}
```
`persistBottleWineVersion` writes `wineVersion` ONLY — it never writes `wineCrossoverBottle` (matches
D-05's read-only-name decision; there is nothing new to write for the name since it's always
`DEFAULT_STEAM_BOTTLE_NAME`). This half is exactly as CONTEXT.md describes.

**What CONTEXT.md's D-15 gets wrong (or leaves unstated): `SteamBottleSetup.tsx` never reads
either of these.** Its wine-version default comes entirely from `steamBottleDefaults.ts`:
```typescript
// SteamBottleSetup.tsx:78-92
useEffect(() => {
  if (!globalConfig || wineVersion || !enginesFetched) return
  setWineVersion(resolveSteamBottleEngine(globalConfig.wineVersion, wineVersionList))
  setWinePrefix(globalConfig.defaultWinePrefixDir)
  setCrossoverBottle(DEFAULT_STEAM_BOTTLE_NAME)   // always the constant, never a stored value
}, [globalConfig, wineVersion, enginesFetched, wineVersionList])
```
`globalConfig` here is `window.api.requestAppSettings()` — the GENERIC app-wide settings, not
`getSteamBottleSettings()`. No IPC handler currently exposes `getSteamBottleSettings()`'s result to
the frontend at all: `steamBottleStatus` (`main.ts:929-936`) returns only `{provisioned, bottleName}`
— no `wineVersion` field.

**This means D-15's "opens already carrying that wine version instead of re-asking" requires TWO
new pieces of work, not zero:**
1. Expose the persisted `wineVersion` to the frontend — either extend `steamBottleStatus`'s return
   shape with a `wineVersion` field, or add it as part of the new `isSteamBottleEligible` verdict
   object (if the planner chooses the "small verdict object" option CONTEXT.md leaves to discretion)
   — a `getSteamBottleSettings()`-shaped read exposed to the renderer is the concrete requirement
   either way.
2. Change `SteamBottleSetup.tsx`'s seeding effect (lines 78-92) to prefer that persisted value over
   `resolveSteamBottleEngine`'s derivation when one exists, and prefer the pre-filled form's choice
   over its own consent-step re-ask.

This must be an explicit plan task — without it, D-15 is unfulfilled even though D-14's store write
happens correctly; the guided setup will keep silently ignoring the form's choice and re-deriving
its own default exactly as it does today.

### Anti-Patterns to Avoid

- **Re-deriving `isBottleEligible()` on the frontend** from `GameInfo.is_mac_native`/`mac_arch`/
  `steamPlatformsCaptured` — possible (the fields exist, `common/types.ts:221/227/234`) but
  explicitly rejected by D-09 for the cold-cache race reason; don't let a plan task quietly
  reintroduce this as a "quick check before the IPC round-trip."
- **Widening `isBottleEligible()`/`ensurePlatformsCaptured()` to `public`** instead of adding a
  wrapper method — this lets a future caller skip the platform-capture step by accident (the exact
  historical bug `steam-bottle-guided-setup-never-fires.md` documents), reintroducing risk this
  phase should be closing, not reopening.
- **Filtering `wineVersionList` in the parent `InstallModal/index.tsx`** instead of inside
  `WineSelector` — would silently NOT apply to `SteamBottleSetup.tsx`'s independent
  `getAlternativeWine()` call, leaving the GPTK-selectable gap open there even though the fix was
  one prop-check away.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Steam library enumeration | A new frontend fetch of `libraryfolders.vdf` | `window.api.listSteamLibraryTargets()` (already ported both paths) | Already IPC-exposed, already dual-registered, already gated correctly on native-install |
| Free disk space | A new disk-space IPC channel | `window.api.checkDiskSpace(path)` (`main.ts:668`, ported via `shellFilesFlowRegistration.ts`, Phase 34.3) | Already dual-ported; returns `{free, diskSize, message, validPath, validFlatpakPath}` — D-08 only needs `.free` |
| Wine engine list | A Steam-specific engine scanner | `window.api.getAlternativeWine()` | Already used by both `InstallModal` and `SteamBottleSetup` |
| Bottle-eligibility predicate | Any frontend heuristic on `GameInfo` fields | New `isSteamBottleEligible` IPC → `SteamGame.checkBottleEligibility()` | D-09; single source of truth, avoids the cold-cache race class of bug |
| The always-show setting | A bespoke settings component | Copy `EnableSteamNativeInstall.tsx` + `nativeInstallSetting.ts` verbatim shape | D-13; proven `isDefault`-gated / single-read-seam pattern already in the codebase |

**Key insight:** every backend primitive this phase needs (library list, disk space, engine list,
bottle store read/write, guided-setup push) already exists and is already dual-ported. The ONLY new
backend surface is the eligibility IPC (one method + one handler pair) and, if the planner takes the
D-15 handoff seriously, one field added to an existing response shape. This is a thin phase by

## Integration Points

### The Open Question: Native-Install Gate vs. D-10 (the priority-1 research target)

**Verified exactly as CONTEXT.md states:** `listSteamLibraryTargets()` itself
(`installLocation.ts:61-68`) has NO gate — it unconditionally calls `getSteamLibraries()`. The gate
is applied by BOTH IPC handler wrappers:
```typescript
// main.ts:913-914

  isSteamNativeInstallEnabled() ? listSteamLibraryTargets() : []
)
// installFlowRegistration.ts:189-190 — byte-identical shape
ipcMain.handle('listSteamLibraryTargets', async () =>
  isSteamNativeInstallEnabled() ? listSteamLibraryTargets() : []
)
```
`main.ts:906-912`'s own comment explains why: gating here rather than inside the function means "a
legacy `steam://install` (opt-in OFF) ignores `path` entirely, so surfacing a picker in that case
would be misleading busywork."

**Resolution:** D-10's ">1 Steam library" trigger is automatically, correctly scoped to
native-install-ON by this EXISTING gate — the planner does not need to write a new condition for it.
Calling the same already-ported IPC gives the new form the identical behavior
`SteamInstallLocationPicker` has today (empty list when OFF → dropdown section simply doesn't
render, matching D-11's "sections gate independently" model already locked). **No new decision
needed for D-10's row 2.**

**The genuinely open question is narrower than CONTEXT.md's framing: it's about D-13's always-show
setting, not D-10's triggers.** With native install OFF and always-show ON, on Windows/Linux, the
form has:
- Platform row: renders (read-only "Windows", D-11) — content.
- Library dropdown: does NOT render (`listSteamLibraryTargets()` returns `[]`, `.length > 1` is
  false) — no content.
- Wine section: does NOT render (not a bottle-eligible platform) — no content.

Net result: a confirm-only dialog with a single read-only platform row and an Install button. Three
options, with consequences:

1. **Accept the content-light confirm dialog as-is (recommended).** No special-casing — the
   existing "sections gate independently, render only when relevant" model (D-11) already produces
   this correctly with zero extra code. Consequence: a Windows/Linux user who enables always-show
   with native-install OFF sees a dialog that mostly just confirms "you're about to install a
   Windows-platform Steam game" — thin, but honest (nothing it could show would be actionable,
   since the delegated `steam://install` path ignores both path and platform choice anyway). This
   matches the precedent D-02's own qualification already sets for bottle-eligible games (never
   show a control that would be a lie about where the game goes).
2. **Ungate `listSteamLibraryTargets()` for display purposes only** (e.g. a `forDisplay` param that
   skips the native-install check). Rejected: this reintroduces exactly the "lying UI" problem D-02's
   own qualification exists to prevent — the dropdown would offer a choice `installSteamGame()`
   would then silently discard, since the underlying `steam://install` call never consults `path`
   when native install is OFF. Would also require touching Phase 21's own D-08/D-09 design, which is
   explicitly out of scope.
3. **Suppress the entire library section explicitly via a frontend `isSteamNativeInstallEnabled`
   read**, rather than relying on the empty-array side effect. Functionally identical outcome to
   option 1, but requires exposing `isSteamNativeInstallEnabled()` to the frontend (no existing IPC
   does this today — it is a backend-only accessor, `nativeInstallSetting.ts:14`) purely so the UI
   can pre-emptively hide a section instead of rendering it empty. More defensive against a future
   change to the gate's location, at the cost of a second copy of the condition. Not recommended
   given option 1 already produces the correct behavior for free.

**Recommendation: option 1.** Flag the resulting UX (a content-light confirm dialog in this specific
combination) explicitly in the plan's copy-review task so the always-show setting's tooltip/wording
(already Claude's Discretion per CONTEXT.md) can set expectations correctly — this is a wording
concern, not an architecture one.

## Common Pitfalls

### Pitfall 1: Treating D-14's store write as sufficient for D-15's handoff
**What goes wrong:** A plan that only adds the `persistBottleWineVersion()` call on the form's
confirm handler will pass every test that checks the store value, while `SteamBottleSetup.tsx`
silently continues to re-derive its own default and never reads the stored value — the user answers
the wine-engine question twice, exactly what D-15 says must not happen.
**Why it happens:** `getSteamBottleSettings()`/`persistBottleWineVersion()` genuinely are the
correct backend seam (confirmed, Pattern 4 above) — it's easy to assume "the backend already reads
this everywhere" without checking the ONE frontend surface (`SteamBottleSetup.tsx`) that also needs
it.
**How to avoid:** Make the `SteamBottleSetup.tsx` wiring change (Pattern 4, item 2) its own
explicit plan task with its own acceptance check — not a bullet inside the D-14 store-write task.
**Warning signs:** A plan that lists D-14 and D-15 as a single task, or that never modifies
`SteamBottleSetup.tsx`.

### Pitfall 2: Registering the new IPC channel on only one runtime path
**What goes wrong:** Adding `addHandler('isSteamBottleEligible', ...)` to `main.ts` only. Under
Tauri, `window.api.isSteamBottleEligible` would then silently reject via the
`UNPORTED_CHANNEL_MARKER` mechanism (per this repo's own documented SEAM.md Invariant B) — the form
would appear to hang forever in the D-12 busy state on the Tauri build specifically, while working
fine under Electron. This is exactly the class of defect the standing IPC-PORT-INVENTORY.md
discipline exists to catch, but a NEW channel invented in this phase won't be caught by it
automatically — the planner must add the registration to both files as one atomic change.
**How to avoid:** One task, two file edits (`main.ts` + `steamAuthFlowRegistration.ts`, not
`installFlowRegistration.ts` per the corrected placement above), verified by a test that asserts
the preload surface exposes the channel and (ideally) that both registration files declare it.
**Warning signs:** A plan task that touches only `src/backend/main.ts` for this channel.

### Pitfall 3: Filtering the wine-engine list in the wrong layer
**What goes wrong:** Filtering `wineVersionList` down to CrossOver-only inside the new Steam
dialog (or inside `InstallModal/index.tsx`'s shared `useEffect`) rather than inside `WineSelector`
itself. This works for the new dialog but leaves `SteamBottleSetup.tsx`'s independent
`getAlternativeWine()` call unfiltered, so the folded-todo's frontend half (D-16) is only half-closed
— GPTK/plain-Wine engines remain selectable from the guided-setup dialog even after this phase.
**How to avoid:** Filter inside `WineSelector` gated on its existing `runner` prop (Pattern 2
above) so both callers that already pass `runner="steam"` benefit automatically.
**Warning signs:** A diff that touches `InstallModal/index.tsx` or a new dialog file but not
`WineSelector/index.tsx` for the D-16 task.

### Pitfall 4: Assuming the empty-library-list case needs new gating code
**What goes wrong:** Writing a new `isSteamNativeInstallEnabled` frontend check to suppress the
library dropdown "just in case," duplicating logic the existing IPC gate already provides for free
via an empty array — extra surface area with no behavior change, and a second place that can drift
from the backend's actual gate condition.
**How to avoid:** Trust `listSteamLibraryTargets()`'s existing `.length > 1` semantics (see the
Open Question section above) unless a concrete reason to duplicate the gate emerges during
implementation.
