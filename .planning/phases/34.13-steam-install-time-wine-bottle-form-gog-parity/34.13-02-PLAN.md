<objective>
Deliver the Steam **backend read-side** this phase's frontend depends on: the D-17 Windows-depot
availability signal, and the D-09 backend-authoritative bottle-eligibility seam.

Purpose:
- **D-17** — Plan 34.13-12 gates a *selectable* Windows `MenuItem` on macOS for a mac-native Steam
  game. That gate needs a Windows-depot-availability signal. Today no such signal exists anywhere —
  but it is free: `games.ts:544` already reads `data.platforms?.mac` and `data.platforms?.linux`
  from an appdetails response that also carries `data.platforms.windows`. This plan captures the
  third field from the same response.
- **D-09** — Plans 34.13-07/08 need a bottle verdict over IPC. `isBottleEligible()` is `private`
  (`games.ts:1328`) and `ensurePlatformsCaptured()` is `private` (`games.ts:1383`). This plan adds
  the single public wrapper that composes them, so neither is widened and no third frontend copy of
  the predicate is ever created.
- **D-07** — `getInstallInfo()` stays a stub; its doc comment records that the new Steam dialog
  deliberately never consults it.

Output: `is_windows_native` captured + persisted + hydrated; `checkBottleEligibility()` public on
`SteamGame`; a `getInstallInfo()` doc comment; four new/extended Jest specs in two backend suites.

**No new network call. No PICS. No `buildDepotPlan`. No behavior change to `install()`.**
</objective>
