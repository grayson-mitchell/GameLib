<design_decisions>
<!-- Resolved here so no task re-litigates them, and so a reviewer reads the intent, not just the diff. -->

**1. The legacy guard is REPLACED for Steam and PRESERVED for the other four dialogs — and that is
not "supplementation".** `platformSelection()` is shared by all five siblings. Deleting
`availablePlatforms.length > 1` outright would silently change GOG / Epic / Amazon / sideload
behaviour, which is out of scope and would be a real regression. The replacement is structural:

- `platformSelection()`'s body loses every reference to `availablePlatforms` — its render decision
  becomes the single closure-scoped value `platformRowMode`.
- `platformRowMode` is `isSteamManagedApp ? steamGating.platformRow : legacyPlatformRowMode`.
- `legacyPlatformRowMode` is the ONLY surviving occurrence of the old expression, named `legacy`
  so its scope is unmistakable, and structurally unreachable from the Steam path.

Task 3 pins this mechanically: zero `availablePlatforms.length` inside `platformSelection`'s body,
exactly one `availablePlatforms.length > 1` in the file, on the `legacyPlatformRowMode` line.

**2. Read-only rows reuse `platformSelection()` with a disabled `SelectField`.** CONTEXT.md
"Claude's Discretion" leaves this open ("reuses `platformSelection()` with a disabled `SelectField`
or renders a simpler static row"). Reuse wins: identical chrome, no new copy, no new CSS, no new
grid layout — and therefore no exposure to the WKWebView 1px-border-on-a-`1fr`-track failure at all.

**Disabling the FIELD (D-19 / Row 4) and OMITTING a `MenuItem` (D-17) are two different mechanisms
and must not be conflated by a reviewer.** A read-only row is a `SelectField` with `disabled` and
exactly one `MenuItem`. A no-depot game has no Windows `MenuItem` in the list at all. The UI-SPEC's
prohibition ("not present-but-disabled") is about the `MenuItem`, and Task 3 gates on
`MenuItem … disabled` specifically, not on the word `disabled`.

**3. `selectSteamPlatformOptions` reads the UNFILTERED `platforms` array, not `availablePlatforms`.**
Two reasons, both load-bearing. First, `platforms`' `Windows` entry is `available: true`
unconditionally (L80) — that flag is precisely the thing D-17 must not trust, and reusing it would
make the depot gate decorative. Second, `availablePlatforms` can lack the `Mac` entry for a
non-mac-native game, so a `'readonly-macos'` verdict resolved against it could yield an empty option
list with a pinned `value` MUI cannot match. Reading the unfiltered list makes every mode's option
set total. The verdict has already decided which values are legitimate for the row; the module's
only additional gate is `hasWindowsDepot`.

**4. The Steam `<WineSelector>` mount is gated on `steamGating.wineSection`, never on `hasWine`.**
`hasWine` is `platformToInstall === 'Windows' && !isWin`. On a **Linux** host `platformToInstall`
defaults to `'Windows'` and `isWin` is false, so `hasWine` is TRUE — mounting a wine section for
matrix rows 11 and 12, violating D-11 and D-18. This is a live defect the naive wiring would ship.
A single derived value, `showWineSelector = isSteamManagedApp ? steamGating.wineSection : hasWine`,
drives the mount in all five arms AND the `getAlternativeWine()` effect. For every non-Steam runner
it equals `hasWine` exactly, so those four arms are byte-identical in behaviour.

**5. `crossoverOnly` is deliberately NOT passed.** 34.13-03's `resolveCrossoverOnly(runner,
crossoverOnly) => crossoverOnly ?? runner === 'steam'` uses `??` specifically so an omitted prop on a
`runner="steam"` caller still filters. Passing `crossoverOnly={true}` would work but would prove
nothing; omitting it exercises the same default path `SteamBottleSetup.tsx` inherits without being
edited (RESEARCH.md Pitfall 3). Task 3 gates that `crossoverOnly` appears nowhere in this file.

**6. Flipping the platform back (macOS ← Windows) clears nothing, deliberately.** UI-SPEC §5 says a
wine selection made while on Windows is "discarded, not preserved", and immediately qualifies that as
"matching the existing `hasWine` unmount behavior for every other sibling dialog". `wineVersion` /
`crossoverBottle` are parent state and survive an unmount today for every runner. **Do not add
state-clearing logic** — inventing it would be new, untested surface outside CONTEXT.md's scope, and
it is unnecessary: 34.13-10's confirm handler only calls `persistBottleWineVersion` when
`gating.wineSection` is true, so a stale engine cannot leak into a library-only install.

**7. Missing `steamInstallContext` fails CLOSED into `SteamDialog`, not through to `DownloadDialog`.**
After 34.13-08, `runner === 'steam' && action === 'install'` always arrives with the payload. If it
somehow does not, falling through the ternary reaches `DownloadDialog`, whose size flow calls
`getInstallInfo` — the stub D-07 records "would loop forever on 'Geting download size…'". So the
branch is taken regardless and the verdict is resolved from an explicitly-named fail-closed input
(no bottle, no libraries, native install off, no depot, `alwaysShowOn: true` purely because the modal
is already mounted so `opens` must be true). The result is D-20's accepted content-light form. A
`window.api.logError` call records the anomaly.

**8. The Steam arm goes FIRST in the ternary chain**, before `isThirdPartyManagedApp`. Steam's
library manager never sets `thirdPartyManagedApp` (that is a legendary concept — `ThirdPartyDialog`
carries `disabled={runner !== 'legendary'}`), so ordering is safe; Task 2 verifies this by grep and
records it. `isSteamManagedApp` requires `action === 'install'`, so a Steam **import** still falls
through to `ImportDialog` unchanged.

**9. The `availablePlatforms` prop passed to `SteamDialog` stays the existing filtered list.** It
feeds only `DialogHeader`'s platform icons, identically to all four existing siblings. Header icon
selection is not a D-17 surface and is out of scope; do not substitute the option list there.
</design_decisions>
