## Final Source, As Shipped (verbatim)

### The writer pair (`games.ts`)

```ts
export function markForcedWindowsViaBottle(appId: string): void {
  const existing = steamMetadataStore.get(appId)
  steamMetadataStore.set(appId, {
    ...(existing ?? { art_cover: '', art_square: '', extra: { reqs: [] } }),
    forcedWindowsViaBottle: true
  })
  logInfo(
    `SteamGame: appId ${appId} — persisted forced Windows-via-bottle verdict after a committed install`,
    LogPrefix.Steam
  )
}

export function clearForcedWindowsViaBottle(appId: string): void {
  const existing = steamMetadataStore.get(appId)
  if (!existing) return
  const wasForced = existing.forcedWindowsViaBottle === true
  steamMetadataStore.set(appId, {
    ...existing,
    forcedWindowsViaBottle: false
  })
  if (wasForced) {
    logInfo(
      `SteamGame: appId ${appId} — cleared forced Windows-via-bottle verdict (bottle ACF confirmed absent)`,
      LogPrefix.Steam
    )
  }
}
```

### The predicate seam (`games.ts`)

```ts
private isForcedWindowsViaBottle(): boolean {
  return (
    isMac && steamMetadataStore.get(this.appId)?.forcedWindowsViaBottle === true
  )
}

private isBottleEligible(): boolean {
  return this.isBottleEligibleFromPlatforms() || this.isForcedWindowsViaBottle()
}
```

`isBridgeEligible()` composes `this.isBottleEligibleFromPlatforms() &&` (unchanged base predicate) — the widened wrapper is deliberately absent from it.

34.13-06's own escalation named four consumers as unaware of the install-time-only forced verdict, plus one detection surface it declined to inspect further:

1. **`getSettings()`** — now resolves the bottle's `GameSettings` for a forced game (D1), because it already called the now-widened `isBottleEligible()` unchanged.
2. **`isNative()`** — now returns `false` for a forced game (D2), same mechanism.
3. **`launch()`** — now dispatches to the bottled Steam client, never `steam://rungameid` (D3), same mechanism.
4. **`uninstall()`** — now dispatches to the bottled Steam client + bottle-scoped polling, never `steam://uninstall` (D4), same mechanism.
5. **Install-state detection** — 34.13-06's escalation table listed this as a fifth surface to check. This plan (via `<verified_findings>` 3, confirmed by direct source read at execution start) found `library.ts` never called `isBottleEligible()` at all — it holds its own duplicate predicate, `isBridgeAuthoritativeForInstallState()`, which already returns `false` for a forced mac-native game (it requires `is_mac_native === false` or `mac_arch === '32'`, neither true for a forced game). The native→bottle→bridge precedence chain in `refreshInstallState()`/`refresh()` therefore **already** reconciled a forced-but-bottle-installed game as installed with `install.platform: 'Windows'`, with zero code changes needed. This plan did not "fix" that surface — it **pinned** it (S1/S2), turning an already-correct-but-unverified behavior into a regression-guarded one.

All five surfaces are now provably consistent — four by construction (one shared seam), the fifth by an existing, now-pinned, correct behavior.

## In-Place Re-Install Limitation (restated for 34.13-13)

⚠ **Known limitation, deliberately not closed by this plan:** re-installing a forced game **without** uninstalling first re-routes to the bottle even if the user picks macOS in the install form. `install()`'s `routeThroughBottle` composes `isBottleEligible()`, which is now `true` for a flagged game (the persisted verdict), so an in-place re-install is treated as a repair/update of the existing bottle install — correct for the bits actually on disk, but it means the form's platform row cannot express a revert in place. **The revert path is uninstall → re-install** (uninstall clears the verdict via `pollUninstallOnce`'s bottle-scoped confirmed-absent branch; a subsequent fresh install with no override then routes natively). 34.13-13's `G-HANDOFF-REINSTALL` gate exercises exactly this path and should record the in-place behavior if observed, but must **not** mark it FAIL — it is specified here, not a defect.
