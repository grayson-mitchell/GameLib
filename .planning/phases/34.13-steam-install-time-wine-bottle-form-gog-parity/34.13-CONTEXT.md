# Phase 34.13: Steam install-time wine/bottle form (GOG parity) - Context

**Gathered:** 2026-08-14
**Status:** Ready for planning

<domain>
## Phase Boundary

A Steam game that needs a CrossOver bottle opens GameLib's install modal — platform row plus
wine/bottle choice — the same way a GOG game does, instead of installing silently with hardcoded
settings. Plus a global opt-in setting to always show the form for every Steam install.

**In scope:** a new Steam-specific dialog inside the existing `InstallModal`; the trigger logic that
decides when it opens; a backend-authoritative bottle-eligibility IPC; persistence of the chosen
wine version; retirement of `SteamInstallLocationPicker` into the new form; the CrossOver-only
engine filter for Steam's `WineSelector`.

**Out of scope:** per-game bottles or an editable bottle name (Phase 22); implementing
`getInstallInfo()` or any download-size computation; changing how `SteamGame.install()` routes
between its four branches; the guided `SteamBottleSetup` surface itself (D-07, Phase 17) beyond
feeding it the form's chosen wine version.

</domain>

<decisions>
## Implementation Decisions

### Form content & shape

- **D-01: Steam gets a NEW lean sibling dialog inside `InstallModal`** — a fifth alongside
  `DownloadDialog` / `ImportDialog` / `SideloadDialog` / `ThirdPartyDialog`, reusing `WineSelector`,
  `platformSelection()` and the shared `Dialog` chrome. Do **NOT** add Steam branches to
  `DownloadDialog`; it is already dense with Epic/GOG-specific DLC, SDL, branch, build and language
  machinery that Steam has none of.

- **D-02: The Steam library location folds INTO the form** as a dropdown fed by
  `listSteamLibraryTargets()`, defaulting to the primary library.
  **QUALIFIED by the D-10 finding:** the dropdown renders **only when the destination is a host
  Steam library** — never for bottle-eligible games, because `installBottleNative()`
  (`games.ts:827`) overrides the write target to `getBottleSteamappsDir(...)`. A host-library
  dropdown on a bottled install would be a lie about where the game goes.

- **D-03: The platform row renders for Steam even when only one platform is available**, as a
  read-only "Windows", so the user can see *why* a bottle is being requested.
  Today `InstallModal/index.tsx:130` hides the selector unless `availablePlatforms.length > 1`, and
  a bottle-eligible macOS game has `is_mac_native === false` by definition — so Windows is the only
  entry and **the platform selector renders nothing for exactly the games this phase targets**.
  Without this decision, the "platform selection" half of the phase goal is a no-op.

- **D-04: `SteamInstallLocationPicker` RETIRES.** The form becomes the single Steam install surface.
  D-09's (Phase 21) 0/1-library zero-friction case is unchanged — nothing opens.

- **D-05: The CrossOver bottle name field is shown prefilled and READ-ONLY** (the dedicated
  `GameLibSteam` bottle). `WineSelector` renders it as free text today; for Steam it must not be
  editable. A name this phase cannot provision is a broken promise, and multi-bottle is explicitly
  Phase 22 scope.

### Download-size blocker

- **D-06: NO download/install size row for Steam.** The form opens instantly and the Install button
  is **never** gated on `diskSize`. Rationale, both halves independently sufficient: (a) with
  `enableSteamNativeInstall` OFF (the default) the install is delegated to `steam://install` or the
  bottled Steam client, so GameLib never computes a size and there is nothing to show, ever;
  (b) `buildDepotPlan` (`depot.ts:628`) requires an authenticated Steam CM connection and then does
  3× `getProductInfo` plus `getDepotDecryptionKey` + `getRawManifest` **per owned depot** — it
  already carries temporary timing instrumentation from the `steam-install-slow-start` debug session.

- **D-07: `SteamLibraryManager.getInstallInfo()` (`library.ts:771`) stays a stub.** The new Steam
  dialog never calls the frontend `getInstallInfo` helper, so the stub can never hang it. Its
  existing comment — which correctly explains that the modal would loop forever on "Geting download
  size…" — is **updated** to record that the Steam dialog deliberately does not consult it, rather
  than left implying the short-circuit is the only defense.

- **D-08: Disk info is FREE SPACE ONLY** on the selected Steam library drive. No "after install"
  projection, no not-enough-space blocking, no force-install label. Free space is still the useful
  number when choosing between two libraries, which is the decision D-02's dropdown asks for.

### When the form appears

- **D-09: New backend-authoritative IPC `isSteamBottleEligible(appName)`**, which internally awaits
  `ensurePlatformsCaptured()` and then returns the real verdict.
  **Do NOT create a third frontend copy of the eligibility predicate.** It already exists twice —
  `games.ts:1328` (`isBottleEligible`) and `library.ts:145`
  (`isBridgeAuthoritativeForInstallState`). `GameInfo` does carry `is_mac_native`, `mac_arch` and
  `steamPlatformsCaptured` (`types.ts:221/227/234`) so a frontend derivation is *possible*, but it
  would drift from the backend and a cold metadata cache reads as "not eligible" — which is the
  precise shape of `.planning/debug/steam-bottle-guided-setup-never-fires.md`.

- **D-10: The form opens on EITHER trigger** — bottle required, **OR** >1 Steam library — plus the
  always-show setting. Sections gate independently and are almost disjoint:

  | Trigger | Platform | Form shows | Destination |
  |---|---|---|---|
  | Bottle required | macOS only | wine version + read-only bottle name | the bottle's `steamapps` |
  | >1 Steam library | any | library dropdown | chosen host library |

  This is what keeps Phase 21's D-09 multi-library override alive after `SteamInstallLocationPicker`
  retires. A bottle-only trigger plus a retired picker would silently drop the multi-library case
  on every platform — that combination was considered and rejected as a D-09 regression.

- **D-11: On Windows/Linux the always-show setting renders the library dropdown + read-only platform
  row, and no wine section.** Same component, sections gated by relevance — the model D-10 already
  commits to.

- **D-12: Busy/disabled state on the Install button** while `isSteamBottleEligible` resolves. A cold
  cache can wait up to `METADATA_FETCH_TIMEOUT_MS`. No half-rendered modal that does not yet know
  whether it should show a wine section; and no silent multi-second dead click either.

- **D-13: The always-show setting is GLOBAL ONLY.** Follow `EnableSteamNativeInstall.tsx` /
  `nativeInstallSetting.ts` exactly — `isDefault`-gated UI, one `GlobalConfig` key, one backend read
  seam that is the only place reading it. No per-game override; the bottle-required and
  multi-library triggers already cover the per-game cases that matter.

### Where the choice lands

- **D-14: The chosen wine version is written via `persistBottleWineVersion()` into
  `steamBottleConfigStore`** — the store `getSteamBottleSettings()` (`bottle.ts:276`) actually
  reads. This is **shared across every bottled Steam game**, and that consequence must be stated
  plainly in the form's own copy.
  The GOG mechanism (write per-game `GameConfig`, then call install) **does not work here**:
  `SteamGame.getSettings()` returns `getSteamBottleSettings()` for bottle-eligible games and ignores
  `GameConfig` entirely. `bottle.ts:291-306` documents a real bug already caused by exactly that gap
  — a per-game `setSetting('wineVersion')` self-heal silently dropped. Note also that `InstallArgs`
  (`types.ts:402`) carries **no wine fields at all**, so nothing travels through the install call
  today.

- **D-15: The form feeds the guided setup; it does not replace it.** When the bottle is not
  provisioned, the form persists the wine choice, `install()` still fires `steamBottleSetupRequired`
  exactly as today, and `SteamBottleSetup` opens **already carrying that wine version instead of
  re-asking**. D-07 (Phase 17) stays intact and the user answers once.
  Inline provisioning from the form was considered and rejected: unlike the bridge path's fast
  `cxbottle --create` (`games.ts:installBridgeGame`, which provisions inline precisely because it
  needs no consent), `provisionBottle` downloads and launches `SteamSetup.exe` and needs the user to
  click through a real multi-GB installer — which is why the dedicated consent surface exists.

- **D-16: Steam's `WineSelector` is filtered to CrossOver-type engines only** when
  `runner === 'steam'`. Bottle creation is hardcoded to `cxbottle`, so any other engine silently
  yields a broken bottle. **Frontend filter only this phase** — the backend `provisionBottle`
  rejection and the `resolveSteamBottleEngine` silent-override half were considered and left on the
  todo (see Deferred).

### Claude's Discretion

- Component naming and file placement for the new sibling dialog (`SteamDownloadDialog` or
  otherwise), and how much of `DownloadDialog`'s layout/SCSS is genuinely shared vs. duplicated.
- Exact wording of the always-show setting, its info tooltip, and the shared-bottle warning copy —
  subject to the standing localisation requirement (new keys under the `gamelib:` namespace).
- Whether the read-only platform row reuses `platformSelection()` with a disabled `SelectField` or
  renders a simpler static row.
- How the busy state in D-12 is rendered (existing per-game status vs. a local spinner).
- Whether the bottle-eligibility IPC returns a bare boolean or a small verdict object.

### Folded Todos

- **`.planning/todos/pending/steam-bottle-gptk-engine-produces-broken-bottle.md`** (2026-07-17,
  area: steam) — "Steam bottle setup offers GPTK/Wine engines that produce a broken bottle."
  Bottle *creation* is hardcoded to CrossOver's `cxbottle`, but the run-path in `launcher.ts:434-442`
  treats engines as mutually exclusive prefix-vs-bottle models, so a `toolkit` (GPTK) Steam bottle
  drops the bottle binding, runs against a prefix with no Steam client, and `isBottleReady()` never
  passes — silently broken, no error surfaced.
  **Fits this phase because this phase creates a second surface that re-exposes the same affordance.**
  **PARTIALLY folded — D-16 takes the frontend-filter half only.** The todo is **re-scoped, not
  closed**: its `provisionBottle` rejection half and its `resolveSteamBottleEngine` silent-override
  half remain open and must survive this phase.

### Reusable Assets
- `src/frontend/screens/Library/components/InstallModal/WineSelector/index.tsx` — **already carries

  `provisionBottle`, `getSteamBottleSettings`, `persistBottleWineVersion`, `bottleWineArch`,
  `isBottleProvisioned`, `isBottleReady`, `getBottleSteamappsDir`, `sanitizeBottleName`.
- `src/frontend/screens/Settings/components/EnableSteamNativeInstall.tsx` +
  `src/backend/storeManagers/steam/nativeInstallSetting.ts` — the exact two-file pattern D-13's new
  setting copies (`isDefault` gate, `useSetting`, `InfoIcon`, single backend read seam).
- `src/frontend/screens/Game/GamePage/components/SteamInstallLocationPicker.tsx` +
  `src/frontend/state/SteamInstallLocation.ts` — the library-selection UI and state being folded
  into the form by D-02/D-04.
- `listSteamLibraryTargets()` — already wired through `main.ts:914` and
  `installFlowRegistration.ts:190`, both gated on `isSteamNativeInstallEnabled()`. **Note that gate:
  the list is empty when native install is OFF**, which directly affects D-02's dropdown and D-10's
  multi-library trigger. Planning must decide what the multi-library trigger means in that state.

### Established Patterns
- `InstallModal/index.tsx` already branches to four sibling dialogs and passes `platformSelection()`
  plus a conditional `<WineSelector>` into each as children. D-01's fifth sibling is that pattern,
  not a new one.
- Defense-in-depth guards in `provisionBottle` (unsafe-name rejection T-17-01, shared-bottle scope
  guard CR-01) are the shape the deferred backend engine-rejection would follow.
- `SteamGame.install()` (`games.ts:679`) has four branches under `isBottleEligible()`:
  bridge-eligible → `installBridgeGame`; bottle-not-ready → `steamBottleSetupRequired` +
  `deferredToSetup`; native-install ON → `installBottleNative`; else → `tellBottledSteamToInstall`.
  **This phase does not restructure that tree** — D-15 preserves the deferral branch exactly.

### Integration Points
- `src/frontend/state/InstallGameModal.ts:71` — the unconditional
  `runner === 'steam' && action === 'install'` short-circuit that is the root cause. This is the
  single chokepoint for every install entry point (library grid/list, game submenu, game page), so
  changing it changes all of them at once. `installSteamGame()` (line 33) hardcodes
  `platformToInstall: 'Windows'`, `installLanguage: 'en-US'`, and empty DLC/SDL lists.
- `InstallArgs` (`src/common/types.ts:402`) has **no wine fields** — no `wineVersion`, `winePrefix`,
  or `crossoverBottle`. GOG delivers its choice by writing per-game config *before* calling install
  (`DownloadDialog` imports `writeConfig`), which is why D-14 has to use the bottle store instead.
- `SteamGame.getSettings()` (`games.ts:~420`) returns `getSteamBottleSettings()` whenever
  `isBottleEligible()` — the reason per-game config never reaches a bottled Steam game.
- New IPC surface: `isSteamBottleEligible` must be registered in **both** Electron `main.ts` and
  the Tauri sidecar's `installFlowRegistration.ts`, and typed through the preload seam.

<specifics>
## Specific Ideas

- **"the same way a GOG game does"** is a parity target for the *user-facing experience* (a modal
  appears, you choose wine/bottle, you confirm), not for the *mechanism*. Three GOG mechanisms are
  explicitly not copied: the size-gated Install button (D-06), the free-directory path picker
  (D-02), and the per-game-config wine write (D-14). Planning should not treat divergence from
  `DownloadDialog` as a defect.
- The user caught a genuine inconsistency mid-discussion — retiring the picker while triggering only
  on "bottle required" would silently drop the multi-library case. The corrected model (D-10) is
  load-bearing; a planner that narrows the triggers back to bottle-only reintroduces the regression.

</specifics>
