<objective>
Create the fifth `InstallModal` sibling: `SteamDialog`. It is the surface the whole phase exists to
deliver — the dialog a Steam game opens when it needs a bottle or when there is a library to choose,
"the same way a GOG game does" from the user's point of view, without any of GOG's mechanism.

Purpose:
- **D-01** — Steam gets its own lean sibling instead of Steam branches inside `DownloadDialog`.
  `ThirdPartyDialog` (146 lines) is the size and shape reference; `DownloadDialog` (803 lines of
  DLC / SDL / branch / build / language machinery Steam has none of) is explicitly not.
- **D-02** — the retiring `SteamInstallLocationPicker`'s library choice folds into this form, as a
  `SelectField` matching every other dropdown in this dialog rather than the picker's raw `<select>`.
- **D-06 / D-08** — the form opens instantly. No size row, no size gate, free space only.
- **D-14** — the wine choice lands in `steamBottleConfigStore` through 34.13-07's IPC, and the form
  says plainly that the choice is shared across every bottled Steam game.

Output: four NEW files under `InstallModal/SteamDialog/`. **This plan creates the component; it does
not mount it.** `InstallModal/index.tsx`'s fifth branch is added once, by 34.13-12 in Wave 6 — the
multi-plan file table assigns that file to 34.13-12 alone. Nothing this plan writes is reachable at
runtime until that branch lands, and that is deliberate: it keeps Wave 5 free of a collision on the
one file three plans would otherwise want.

## What this plan does NOT do

- It does not edit `InstallModal/index.tsx`, `WineSelector/index.tsx`, `state/InstallGameModal.ts`,
  `public/locales/en/gamelib.json`, or any backend file. Every one of those is owned by another plan.
- It does not render the platform row or the `<WineSelector>` — both arrive through `{children}`
  from the parent, exactly as they do for all four existing siblings.
- It does not implement the D-12 busy state. Per the UI-SPEC's "D-12 Busy State Contract", the
  eligibility check runs *before* the dialog opens, so the spinner belongs on the origin control
  (34.13-11), never on this footer button. This dialog's Install button is never disabled.
- It does not claim to unit-test the rendered dialog. See `<testing_reality>` below.
</objective>

<!-- The one structural question this plan has to answer, resolved here so no task re-litigates it. -->

The parent passes the platform row and the `<WineSelector>` block down as a single opaque
`{children}` node (`InstallModal/index.tsx:184-199` is the shape). `SteamDialog` therefore cannot
interleave its own regions between them — and it does not need to, because of an invariant that
falls straight out of 34.13-05's step 9:

**`libraryDropdown` is `!wineSection && nativeInstallOn && libraryCount > 1`, so `libraryDropdown`
and `wineSection` are mutually exclusive in all 16 matrix rows.** The two regions can never both
render, so their relative order is unobservable.

`DialogContent` therefore renders, in source order:
1. `{children}` — the platform row, then the wine section when the parent mounts it.
2. The D-14 shared-bottle notice, gated on `gating.wineSection`.
3. The D-02 library dropdown (with the D-08 free-space line in its `afterSelect` slot), gated on
   `gating.libraryDropdown` / `gating.freeSpaceLine`.

Observed result matches the UI-SPEC's Interaction Contract §2 exactly: platform row → wine section →
shared-bottle notice, **or** platform row → library dropdown → free-space line. Never both.

**Placement note to record in the SUMMARY:** UI-SPEC §2 describes the D-14 notice as appearing
"inside the same mounted block" as the wine section. It cannot literally live inside `WineSelector`
here — that file belongs to 34.13-03 and this plan must not edit it — so it renders immediately
after `{children}` instead, which is the same visual position. This is a file-ownership consequence,
not a design change.
</layout_contract>
