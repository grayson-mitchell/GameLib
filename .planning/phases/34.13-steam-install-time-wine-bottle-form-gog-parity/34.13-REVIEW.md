## Critical Issues

### A-01 (BLOCKER): `InstallArgs.steamForceWindowsViaBottle` never reaches `SteamGame.install()` — the whole D-17 forced-Windows-via-bottle feature is dead in production

**File:** `src/backend/downloadmanager/utils.ts:41-51,143-152`
(with `src/frontend/state/InstallGameModal.ts:108-125`,
`src/backend/downloadmanager/ipc_handler.ts:13-22`,
`src/backend/sidecar/installFlowRegistration.ts:120-143`,
`src/backend/storeManagers/steam/games.ts:786`)

**Issue:**

The full chain, traced end to end on both runtimes:

1. `InstallGameModal.ts:114-124` — `installSteamGame()` marshals
   `steamForceWindowsViaBottle: forceWindowsViaBottle` into
   `window.api.install({...})`. This is the sole write site, per its own doc.
2. Electron: `downloadmanager/ipc_handler.ts:13` — `addHandler('install', ...)`
   puts `args` verbatim into `DMQueueElement.params`. Tauri:
   `installFlowRegistration.ts:123` — same, `(args[0] ?? {}) as InstallParams`.
   The field is intact here.
3. `downloadqueue.ts:160-161` — `installQueueElement(element.params)`.
4. **`downloadmanager/utils.ts:41-51`** destructures a *fixed* field list:
   ```ts
   const { appName, path, installDlcs, sdlList = [], runner,
           installLanguage, platformToInstall, build, branch } = params
   ```
   `steamForceWindowsViaBottle` is not among them.
5. **`downloadmanager/utils.ts:144-152`** rebuilds the `InstallArgs` object from
   that list only:
   ```ts
   libraryManagerMap[runner].getGame(appName).install({
     path: path.replaceAll("'", ''),
     installDlcs, sdlList: ..., platformToInstall, installLanguage, build, branch
   })
   ```

So `args.steamForceWindowsViaBottle` at `games.ts:786` is **always `undefined`**,
`overrideRequested` is always `false`, and therefore:

- `forceWindowsViaBottle` is always `false` — a mac-native game the user
  explicitly asked to install as Windows-via-bottle routes to the legacy
  `native-protocol`/`steam://` path instead. This is a **silently dropped user
  choice**, the exact defect class `games.ts:790-795`'s own comment says is
  recurring in this repo.
- The WR-07 rejection log is unreachable — it is guarded by
  `if (overrideRequested && !forceWindowsViaBottle)`, and `overrideRequested`
  can never be true. The iteration-1 fix improved a line that cannot execute.
- `markForcedWindowsViaBottle()` can never be called, so
  `SteamMetadataCacheEntry.forcedWindowsViaBottle` is never written,
  `isForcedWindowsViaBottle()` always returns `false`, the
  `fetchMetadataIfNeeded` carry-forward at `games.ts:663-665` carries nothing,
  and `clearForcedWindowsViaBottle()` clears nothing. 34.13-14's entire
  durability contract is inert.
- `tsc` cannot catch this: `InstallArgs` declares `steamForceWindowsViaBottle`
  optional, so the 7-field literal at `utils.ts:145-152` type-checks.

**Why the test suite is green.** Every D-17 spec calls the method directly:
`games.test.ts:2832,2857,2876,2895,2917,2937,2958,2969,2986,3011,3349,3379,3406,3428,3455`
all do `await game.install(argsWith({ steamForceWindowsViaBottle: true }))`.
`PRODUCTION_ARGS` (`games.test.ts:2594-2603`) is documented as "transcribed
field-for-field from `installSteamGame()`'s `window.api.install` literal — the
production call shape for EVERY Steam install". That claim is false at exactly
the point where the drop occurs: it is typed `InstallParams` and carries
`appName`/`runner`/`gameInfo`, none of which `SteamGame.install()` ever receives
in production, because `installQueueElement` reshapes the object in between. The
fixture is a replica of the *frontend's* call shape, passed to the *backend's*
entry point, skipping the one function that mutates it.

I searched the phase's planning artifacts for `installQueueElement`,
`downloadmanager/utils` and `addToQueue`: zero hits. This is not a known,
deferred gap. The 34.13-UAT.md items that would have caught it live
(`G-HANDOFF-D17` and the ROW-4 flip items) are all `pending`.

**Fix:**

```ts
// src/backend/downloadmanager/utils.ts
const {
  appName, path, installDlcs, sdlList = [], runner,
  installLanguage, platformToInstall, build, branch,
  // D-17 (34.13-06): the Steam Windows-via-bottle override. Must be
  // forwarded explicitly — this object literal is the ONLY thing
  // SteamGame.install() ever sees, and an omitted optional field is
  // invisible to tsc.
  steamForceWindowsViaBottle
} = params
...
libraryManagerMap[runner].getGame(appName).install({
  path: path.replaceAll("'", ''),
  installDlcs,
  sdlList: sdlList.filter((el) => el !== ''),
  platformToInstall,
  installLanguage,
  build,
  branch,
  steamForceWindowsViaBottle
})
```

Add a gate that exercises the real chain rather than the method — e.g. a spec
that drives `installQueueElement(PRODUCTION_ARGS_WITH_OVERRIDE)` with
`libraryManagerMap` mocked and asserts the object handed to `.install()` still
carries `steamForceWindowsViaBottle: true`. A source gate on
`utils.ts` alone (asserting the identifier appears in both the destructure and
the literal) would also have caught this and is cheap.

### A-04 (WARNING): `persistInstallFormWineVersion` validates the payload's *shape* but not its *provenance* — an arbitrary `bin`/`wineserver` path is persisted and later spawned

**File:** `src/backend/storeManagers/steam/installFormIpc.ts:119-191`
(with `src/backend/storeManagers/steam/bottle.ts:307-309`,
`src/backend/launcher.ts:1496,1512,1578`, `src/backend/launcher.ts:1352-1382`)

**Issue:** The seam's docstring frames itself as a trust boundary ("validates an
untrusted renderer payload", "the value crosses a trust boundary, and its
compile-time type is not something the renderer can be held to at runtime"). The
validation checks `typeof bin === 'string' && bin.length > 0` and
`typeof wineserver === 'string'` — nothing else. It then persists the value into
`steamBottleConfigStore`, from which `getSteamBottleSettings()` feeds
`runWineCommand({ gameSettings })` for every bottled Steam install, launch and
uninstall (`bottle.ts:793,908`).

`launcher.ts:1512` does `const wineBin = wineVersion.bin.replaceAll("'", '')`
and spawns it. The only other check is `validWine()` (`launcher.ts:1352-1382`),
which is purely `existsSync(bin)` — it verifies the file is *there*, never that
it is a wine engine GameLib itself discovered. `wineVersion.wineserver` is
spawned directly at `launcher.ts:1578` with no existence check on the
non-`type: 'wine'` paths.

So a renderer payload of
`{ bin: '/Users/x/Downloads/anything', name: 'X', type: 'crossover' }` is
accepted, persisted durably, and executed on the next bottled Steam operation.
Every legitimate value on this path originates from `getAlternativeWine()`'s
detected-installations list; the seam never checks membership in it. The
deliberate non-rejection of `'toolkit'` documented at lines 110-114 is a
different decision (engine *type*) and does not cover this.

**Fix:** Cross-check the submitted engine against the detected list at the seam,
which is one lookup and does not touch the deferred type-rejection question:

```ts
const known = await GlobalConfig.get().getAlternativeWine()
if (!known.some((w) => w.bin === bin && w.type === type)) {
  logWarning(
    'persistInstallFormWineVersion: rejected an engine that is not in the ' +
      'detected wine-installation list (T-34.13-07-02)',
    LogPrefix.Steam
  )
  return { status: 'error', error: 'unknown-engine' }
}
```

(Never log `bin` — the file's existing no-value-logging discipline is correct and
should be preserved.)

### B-CR-01: A rejected `persistBottleWineVersion` permanently wedges the Install button and silently aborts the install

**File:** `src/frontend/screens/Library/components/InstallModal/SteamDialog/index.tsx:198-260` (specifically `210`, `217`)

**Issue:**
`handleInstall` sets the WR-13 latch and then awaits an IPC round trip that has **no rejection handler**:

```ts
setSubmitting(true)                                   // 210 — never reset
if (gating.wineSection && wineVersion) {
  const result = await window.api.persistBottleWineVersion(wineVersion)   // 217
  if (result.status === 'error') { /* logged, continues */ }
}
...
backdropClick()                                       // 237
installSteamGame(...)                                 // 241
```

The code handles a *resolved* `{ status: 'error' }` but not a **rejection**. `persistBottleWineVersion` is `makeHandlerInvoker('persistBottleWineVersion')` (`src/preload/api/steam.ts:28`), which is `ipcRenderer.invoke` under Electron and `tauriInvoke(SIDECAR_INVOKE, …)` under Tauri (`src/preload/ipc.ts:38-46`, `src/preload/tauriTransport.ts:92-99`). Both reject on a dead channel, a throwing handler, or a sidecar RPC failure — the exact class of failure this repo has ledgered repeatedly under the Tauri sidecar.

On rejection:
1. The `await` throws, so `backdropClick()` and `installSteamGame(...)` **never run** — the user's install silently does not happen.
2. There is no `try/finally`, so `submitting` stays `true` forever. `disabled={eligibilityPending || submitting}` (line 379) leaves the Install button **permanently dead** while the dialog is still open.
3. `handleInstall` is `async` and passed straight to `onClick` (line 378), so React discards the returned promise — this is an **unhandled promise rejection**, precisely what WR-03 (`e9930a1fe`) was created to eliminate on three sibling round trips.

The inline WR-13 comment asserts the latch is safe because *"`handleInstall` ends by closing the dialog, so the component unmounts; leaving it latched is what makes the double-click impossible"* (lines 140-143). That reasoning holds only on the success path. On the rejection path the component does **not** unmount, and the latch becomes a wedge instead of a guard. The fix therefore closed the double-click route while opening a dead-UI route.

The user's only escape is the header close button; there is no error surfaced anywhere, and the persisted-engine store is left in whatever state the failure produced while `installSteamGame` is skipped entirely.

**Fix:** Wrap the persist in its own rejection handler (matching the D-14 "a failed persist degrades to today's behaviour rather than blocking the install" rule already stated in the comment at lines 220-224) and release the latch on every non-success terminal path:

```ts
const handleInstall = useCallback(async () => {
  if (submitting) return
  setSubmitting(true)

  if (gating.wineSection && wineVersion) {
    // A REJECTION is the same class of outcome as `{ status: 'error' }`:
    // the guided bottle setup still derives an engine when nothing was
    // persisted (D-15), so neither may block the install.
    const result = await window.api
      .persistBottleWineVersion(wineVersion)
      .catch(() => ({ status: 'error' as const }))
    if (result.status === 'error') {
      window.api.logError(
        `34.13-10 SteamDialog: persistBottleWineVersion failed with status "${result.status}"`
      )
    }
  }

  const destination = resolveSteamInstallPath(
    selectedPath,
    steamLibraries,
    gating.libraryDropdown
  )
  backdropClick()
  installSteamGame(appName, gameInfo, destination, gating.forceWindowsViaBottle)
}, [...])
```

If you prefer to keep the latch as the sole double-click control, add a `try { … } catch { setSubmitting(false); return }` around the persist so the button can never be left dead. Add a spec driving a **rejecting** `persistBottleWineVersion` mock and asserting that `installSteamGame` is still called — the current `steamDialogSource.test.ts` is source-text only and cannot observe this at all.

### C-01: `SteamBridgeSetup` awaits a non-Promise — the fallback install's error path is now unreachable and `close()` fires before anything is dispatched

**File:** `src/frontend/screens/Game/GamePage/components/SteamBridgeSetup.tsx:87`
(with `src/frontend/state/InstallGameModal.ts:110-124`)

**Issue:**

```tsx
if (!gameInfo.is_installed) {
  await installSteamGame(appName, gameInfo)   // <- returns void
} else {
  await window.api.launch({ appName, runner: 'steam', args: [] })
}
close()
```

`installSteamGame` is declared `(appName, gameInfo, path = '', forceWindowsViaBottle = false) => { void window.api.install({...}) }` — it returns `undefined`, and it swallows the install promise internally with `void`. Consequences, all provable from source:

1. `await undefined` is a no-op. ESLint reports it as a hard error:
   `87:9  error  Unexpected 'await' of a non-Promise (non-"Thenable") value  @typescript-eslint/await-thenable`.
2. The enclosing `try/catch` can no longer catch an install rejection. The
   `catch` block's only remaining reachable trigger on this branch is
   `getGameInfo()` throwing. `bridge.setup.fallbackError` — "Falling back to
   bottled Steam failed: {{error}}" — is now dead copy for the not-installed
   path.
3. `close()` and `finally { setFallingBack(false) }` both run immediately, so
   the "Falling back..." button state is instantaneous and the dialog dismisses
   before the install IPC has even been answered. On a failed fallback the user
   sees the failure surface vanish and nothing happen.

This is a **regression**, not a pre-existing condition. `git show
77eb4b4b6^:src/frontend/screens/Game/GamePage/components/SteamBridgeSetup.tsx`
shows the pre-phase form was `await window.api.install({ ... })` — a real
promise whose rejection *was* caught and surfaced. The 34.13-08 commit comment
asserts "The outcome is byte-identical to the literal this replaces:
`installSteamGame`'s hardcoded fields are the same eight." The *fields* are
identical; the *return contract* is not, and that is the whole difference.

This is a failure-recovery surface. Silently swallowing the recovery's own
failure is the worst possible place for this defect.

**Fix:** Give `installSteamGame` a real return value rather than papering over
the call site — the same defect exists at every other `installSteamGame` caller
that wants to know whether the install started.

```ts
// src/frontend/state/InstallGameModal.ts
export const installSteamGame = (
  appName: string,
  gameInfo: GameInfo,
  path = '',
  forceWindowsViaBottle = false
): Promise<unknown> =>
  window.api.install({ /* …unchanged eight fields… */ })
```

Then the existing `await` in `SteamBridgeSetup` becomes correct as written, and
every fire-and-forget caller (`startSteamQuickInstall`, `InstallOverlay`)
explicitly opts out with `void installSteamGame(...)`. Add a regression test
asserting `handleFallback` sets `fallbackError` when `window.api.install`
rejects — there is currently no test covering this branch at all.

### C-02: `SteamBottleSetup.handleConfirm` has no rejection handling — a rejected provision IPC leaves an unhandled rejection and wedges the wizard in `provisioning` forever

**File:** `src/frontend/screens/Game/GamePage/components/SteamBottleSetup.tsx:215-226`
(with `src/preload/ipc.ts:37-46`)

**Issue:**

```tsx
const handleConfirm = async () => {
  setPhase('provisioning')
  setProvisionError(undefined)
  const result = await window.api.steamBottleProvision({
    bottleName: crossoverBottle || undefined,
    wineVersion
  })
  if (result.status === 'error') {
    setProvisionError(result.error)
    setPhase('error')
  }
}
```

`window.api.steamBottleProvision` is `makeHandlerInvoker('steamBottleProvision')`,
which returns `ipcRenderer.invoke(...)` under Electron and `tauriInvoke(...)`
under Tauri. Both **reject** on a backend throw, a dead sidecar, or a transport
timeout. `handleConfirm` has no `try/catch` and no `.catch`, and it is wired
directly as `onClick={handleConfirm}` (line 276), so nothing downstream handles
it either.

On rejection:
- an unhandled promise rejection is raised (under the Tauri sidecar this is the
  ledgered "sidecar send channels fail silently" failure mode);
- `setPhase('error')` never runs, so `phase` stays `'provisioning'`;
- the banner renders "Setting up Steam — this can take a while on first run."
  **permanently**, with no error, no retry affordance (the "Try again" button
  only exists in the `error` phase), and the 3-second poll armed;
- the only way out is the "Done" button, which closes the surface and leaves
  the poll running (see C-05).

WR-03's issue text in `34.13-REVIEW.iter1.md` named this exact symptom: "the
poll never surfaces the failure, so the banner sits on 'Setting up Steam…'
forever." Commit `e9930a1fe` added a `.catch` to the **poll**, which addresses
the unhandled-rejection-every-3s half but does nothing about the wedge, because
the wedge originates in a different, unguarded promise in the same file that
the fix did not enumerate. Three IPC round trips were audited; this fourth one
was not.

**Fix:**

```tsx
const handleConfirm = async () => {
  setPhase('provisioning')
  setProvisionError(undefined)
  try {
    const result = await window.api.steamBottleProvision({
      bottleName: crossoverBottle || undefined,
      wineVersion
    })
    if (result.status === 'error') {
      setProvisionError(result.error)
      setPhase('error')
    }
  } catch (error) {
    // A rejected provision IPC is a FAILED provision, unlike a rejected
    // status READ (the poll's .catch below) which is merely unknown.
    setProvisionError(error instanceof Error ? error.message : String(error))
    setPhase('error')
  }
}
```

and `onClick={() => void handleConfirm()}` so no promise floats off the JSX
attribute. Additionally, consider bounding the `provisioning` phase with a
timeout that flips to `error` — the surface currently has no terminal state
other than `provisioned === true`.

### C-05: The provisioning poll survives `close()` and runs every 3 seconds for the remaining life of the app

**File:** `src/frontend/screens/Game/GamePage/components/SteamBottleSetup.tsx:63-77,173-205`
(with `src/frontend/App.tsx:138`)

**Issue:** `<SteamBottleSetup />` is mounted permanently in `App.tsx`; `isOpen`
false only makes it `return null` (line 207), it never unmounts. The poll effect
is keyed on `[phase]` alone:

```tsx
useEffect(() => {
  if (phase !== 'provisioning') { if (pollRef.current) clearInterval(pollRef.current); return }
  …
  pollRef.current = setInterval(poll, STATUS_POLL_INTERVAL_MS)
  return () => { if (pollRef.current) clearInterval(pollRef.current) }
}, [phase])
```

`phase` is only reset by the session effect at line 63, which begins
`if (!isOpen) return` — so it resets on **open**, never on **close**. Clicking
"Done" (`handleDone` → `close()`) sets `isOpen` false and leaves `phase ===
'provisioning'`. The effect does not re-run, the cleanup does not fire, and
`window.api.steamBottleStatus()` keeps being invoked every 3 000 ms until the
user opens a *new* guided-setup session (which finally sets `phase = 'consent'`)
or restarts the app.

The interval only self-clears when `status.provisioned` becomes `true`. It never
does if the user cancels the Steam installer, if provisioning failed silently,
or if the channel is erroring — and the WR-03 `.catch` explicitly keeps polling
in that last case ("keep polling (the interval is still armed) and let the next
tick answer"), so a permanently-erroring channel is an unbounded, silent retry
loop.

**Fix:** Key the effect on the surface's liveness as well as its phase, and null
the ref:

```tsx
useEffect(() => {
  if (!isOpen || phase !== 'provisioning') {
    if (pollRef.current) { clearInterval(pollRef.current); pollRef.current = undefined }
    return
  }
  …
  return () => {
    if (pollRef.current) { clearInterval(pollRef.current); pollRef.current = undefined }
  }
}, [isOpen, phase])
```

Optionally also reset `phase` in `handleDone`. Consider a bounded retry count so
a permanently-erroring channel terminates into the `error` phase instead of
looping.

### C-06: The session reset clears four pieces of wizard state but not `enginesFetched` / `wineVersionList`, defeating the seed guard it exists to restore on a second session

**File:** `src/frontend/screens/Game/GamePage/components/SteamBottleSetup.tsx:63-94,134-166`

**Issue:** The reset effect's comment states its purpose precisely — the seeding
effect "latches on the first non-undefined engine it sets … without this reset, a
SECOND guided-setup session in the same app run would keep the FIRST session's
engine forever." It resets `phase`, `provisionError`, `provisioned`,
`wineVersion`, `persistedWineVersion` and `persistedLookupSettled`. It does
**not** reset `enginesFetched` or `wineVersionList`.

`enginesFetched` is the seed effect's guard against "seeding before the engine
list is known" (line 79-82: "otherwise a CrossOver engine that loads after
globalConfig would be missed"). On session 2 it is already `true` from session 1,
so the guard is inert: the seed effect can fire the instant
`persistedLookupSettled` flips, using session 1's **stale** `wineVersionList`,
before the re-issued `getAlternativeWine()` resolves. If the user installed
CrossOver between the two sessions, the derived default is computed against a
list that does not contain it — exactly the failure the guard was written for.

The window is narrow (both are IPC round trips racing), but it is real and the
fix is one line. Note `steamBottleSetupSeeding.test.ts` asserts only
`setWineVersion(undefined)` is present; nothing pins the completeness of the
reset set.

**Fix:**

```tsx
setEnginesFetched(false)
setWineVersionList([])
```
in the reset effect, and extend the seeding source gate to pin the full reset
set rather than a single setter.
