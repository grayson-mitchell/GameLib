## Critical Issues

### A-10 (BLOCKER): a `downloading` bottle manifest makes uninstall delete nothing, emit a terminal-less `uninstalling` status, and start no poll — the game is un-uninstallable and the UI is stuck

**File:** `src/backend/storeManagers/steam/games.ts:2126-2134`
(with `src/backend/storeManagers/steam/library.ts` `pollUninstallOnce` 'downloading' branch,
and `src/backend/storeManagers/steam/__tests__/games.test.ts:4315-4329`)

**Issue:**

```ts
const acfState = await readAcfState(this.appId, 'bottle')
if (acfState.state !== 'installed' || !acfState.installPath) {
  logWarning(`… found no installed bottle manifest … nothing to remove`, …)
  await pollUninstallOnce(this.appId, 'bottle')
  return { stdout: '', stderr: '' }
}
```

`readAcfState` returns exactly three states. `'downloading'` (StateFlags bit 4 unset —
a partial install, an interrupted depot download, or a StateFlags-1026 handoff manifest)
falls into this branch. What then happens:

1. **Nothing is deleted.** The partial install and its manifest stay on disk.
2. `pollUninstallOnce(appId, 'bottle')` re-reads the same ACF, takes its
   `uninstalling` branch (`result.state === 'downloading'` → `uninstalling = true`)
   and emits `gameStatusUpdate { status: 'uninstalling' }`.
3. **No poll is registered.** `539bc979c` removed the bottle path's
   `startUninstallPolling(this.appId, { source: 'bottle' })` entirely — the new spec
   at `games.test.ts:4249` asserts `expect(startUninstallPollingSpy).not.toHaveBeenCalled()`.
   `activeUninstallPolls` is empty, so no later tick and no `stopUninstallPolling`
   will ever run.
4. The method returns `{ stdout: '', stderr: '' }` — a success.

Net effect: the user clicks Uninstall, the tile flips to "Uninstalling", and it stays
there for the rest of the session with the files still on disk and no error surfaced.
That is the same permanently-stuck-UI class as B-CR-01/C-02, and it is strictly worse
than the pre-commit behaviour, which at least ran the poller's `GRACE_TICKS` fallback
that reverted the badge.

**Why the suite is green.** The only spec covering this branch is named
`'no installed manifest found (already absent/downloading) — syncs state via
pollUninstallOnce instead of deleting'` — its name claims `downloading`, but its body
is `readAcfStateSpy.mockResolvedValue({ state: 'absent' })`, and `pollUninstallOnce`
is mocked to `undefined`, so neither the missing deletion nor the emitted status can
be observed. This is the phase's recurring "a test name describes a different property
than the assertion measures" defect, sitting directly on top of the bug.

**Fix:** treat `'downloading'` as its own case — refuse with a real error rather than
reporting success, and never emit a status nothing will clear:

```ts
const acfState = await readAcfState(this.appId, 'bottle')

if (acfState.state === 'downloading') {
  // A partial/handoff manifest is not something this function can safely
  // delete (a depot download may still be writing into it) and it must NOT
  // reach pollUninstallOnce, whose 'downloading' branch emits an
  // `uninstalling` status that nothing on this path will ever terminate.
  logWarning(
    `SteamGame: refusing to direct-delete appId ${this.appId} — the bottle manifest is mid-download`,
    LogPrefix.Steam
  )
  sendFrontendMessage('gameStatusUpdate', {
    appName: this.appId, runner: 'steam', status: 'done'
  })
  return { stdout: '', stderr: 'Cancel the in-progress install before uninstalling' }
}

if (acfState.state !== 'installed' || !acfState.installPath) { … }
```

Add a spec that actually drives `{ state: 'downloading' }` with the REAL
`pollUninstallOnce` (or with `sendFrontendMessage` spied) and asserts no
`status: 'uninstalling'` frame is emitted, and rename the existing spec so it stops
advertising coverage it does not have.

### A-11 (BLOCKER): a bottle-eligible title installed on a NATIVE Steam library is reported as successfully uninstalled — badge flipped, "Game Uninstalled" toast fired — with nothing deleted

**File:** `src/backend/storeManagers/steam/games.ts:1940-1968, 2126-2134`
(with `games.ts` `isBottleEligibleFromPlatforms()` and `library.ts` `pollUninstallOnce`
'absent' branch)

**Issue:** `uninstall()` routes on **title attributes**, never on where the game is
actually installed:

```ts
if (this.isBottleEligible()) { … return this.uninstallBottleGameDirectly() }
```

`isBottleEligibleFromPlatforms()` returns true when `meta?.mac_arch === '32'` — a
verdict whose own comment says it "only ever fires from Plan 18-03's **post-install**
Mach-O ground-truth check". That check runs against a game that is already installed,
including one installed into a **native** Steam library. The moment that verdict is
cached, `uninstall()` sends that game down the bottle path:

1. `readAcfState(appId, 'bottle')` scans only the CrossOver bottle's `steamapps/` and
   returns `{ state: 'absent' }` — correctly, the game is not in the bottle.
2. The early-return branch fires `pollUninstallOnce(appId, 'bottle')`.
3. That takes the `'absent'` branch, which is written on the premise that absence means
   *confirmed removal*: it clears the D-17 flags, sets `is_installed: false`, persists
   the mutated Map to `steamLibraryStore`, pushes `pushGameToLibrary`, and fires
   `notify({ body: 'Game Uninstalled' })`.
4. `uninstallBottleGameDirectly` returns `{ stdout: '', stderr: '' }` — success.

The native install is untouched on disk, GameLib's persisted library says the game is
not installed, and the user was told it was uninstalled. Re-launch will then fail or
re-download. `uninstallBottleGameDirectly`'s own JSDoc asserts the opposite premise —
*"the manifest is now confirmed absent, exactly the condition that branch already
handles"* — which is true only on the path where the deletion actually ran, not on the
early return that shares the same call.

The pre-commit code reached a similar false-positive through the poller, but
`539bc979c` makes it **immediate, unconditional and the only path**, and removes the
grace-window fallback that previously blunted it.

**Fix:** route on the install location, not on title attributes. Resolve the library
entry's own `install.install_path` against the known roots (bottle common/ vs every
native library's common/) with the same `resolve()`+`relative()` idiom, and refuse
rather than guessing when it matches neither:

```ts
const root = await resolveInstallRoot(library.get(this.appId)?.install?.install_path)
if (root !== 'bottle') {
  // not a bottle install — fall through to the native steam:// path (or refuse)
}
```

Separately, `pollUninstallOnce`'s `'absent'` branch must not be reused as a
"synchronise state" primitive by a caller that never removed anything: split the
completion pipeline from the reconciliation read, or pass an explicit
`{ removed: boolean }` so the toast and the badge flip only fire on a real removal.

> Note: uncommitted work in the tree (`library.ts` `resolveInstallRoot` +
> a cross-root survivor check in `pollUninstallOnce`) appears aimed at exactly this.
> It is **not** in the reviewed commit and is not yet green (see A-CTX-01).

### A-12 (WARNING): the manifest deletion target is built from an unvalidated `appId` and is never containment-checked, unlike the install root beside it

**File:** `src/backend/storeManagers/steam/games.ts:2166, 2170`

**Issue:** The function containment-checks `installRoot` with the full
`resolve()`+`relative()`+`isAbsolute()` idiom, then deletes a **second** path that gets
none of it:

```ts
const manifestPath = join(steamappsDir, `appmanifest_${this.appId}.acf`)
…
rmSync(manifestPath, { force: true })
```

`this.appId` is renderer-supplied (`getGame(appName)` off the `uninstall` IPC channel)
and is validated nowhere on this path — the sibling native branch 20 lines above
validates it via `buildSteamProtocolUrl` before use, and `getSteamBottleEligibilityVerdict`
carries `NUMERIC_APP_ID` for exactly this reason. `join` is not containment (Phase 18):
an appId containing `../` moves the delete target out of `steamapps/`. Reachability is
low today (an attacker would also need a matching `steamMetadataStore` entry to pass
`isBottleEligible()`), which is why this is a WARNING and not a BLOCKER — but the
method's JSDoc claims deletion is "scoped to make [over-deleting] structurally
impossible rather than runtime-checked", and that claim is false for this half.

**Fix:** apply the file's own existing guard at the top of the method, so both delete
targets are covered by one check:

```ts
if (!/^\d+$/.test(this.appId)) {
  logWarning(
    `SteamGame: uninstallBottleGameDirectly rejected a non-numeric appId`,
    LogPrefix.Steam
  )
  return { stdout: '', stderr: 'Refused to uninstall: invalid appId' }
}
```

### A-13 (WARNING): the "SharedDepots handled by construction / structurally impossible" claim overreaches — two appIds sharing one `installdir` still cross-delete

**File:** `src/backend/storeManagers/steam/games.ts:2077-2092, 2158-2166`

**Issue:** The JSDoc argues the deletion is safe because a shared depot's files "live
under the OWNING app's own installdir (a **sibling** directory under common/)". That
holds for the SharedDepots case the real-filesystem regression test proves — and that
test is genuinely good. It does **not** hold for the case the argument silently assumes
away: two installed appIds whose ACFs declare the **same** `installdir`. Steam does
this routinely (a game and its dedicated-server/tool app, regional SKU variants,
demo/base pairs). In that shape:

- `installRoot` resolves to the shared directory,
- `rmSync(installRoot, { recursive: true })` deletes the co-installed app's files,
- only `appmanifest_<thisAppId>.acf` is removed, so the other app's manifest survives
  pointing at a now-empty path — Steam and GameLib both still believe it is installed.

There is no cross-manifest check anywhere in the function, and no test covers it. The
finding is that the *claim* ("structurally impossible", "handled by construction") is
stronger than the code supports, which is the more dangerous half — a later reader will
trust it.

**Fix:** either narrow the claim in the JSDoc to the case it actually covers, or add
the one cheap check that makes it true — scan the bottle `steamapps/` for any other
`appmanifest_*.acf` whose `installdir` matches, and refuse (or delete the manifest only)
when one exists:

```ts
const conflicting = await findOtherManifestsWithInstalldir(steamappsDir, installdirSegment, this.appId)
if (conflicting.length > 0) {
  logWarning(`… installdir "${installdirSegment}" is shared with appId(s) ${conflicting.join(',')} — removing manifest only`, LogPrefix.Steam)
  rmSync(manifestPath, { force: true })
  await pollUninstallOnce(this.appId, 'bottle')
  return { stdout: '', stderr: '' }
}
```

### A-20 (WARNING): `getSteamBottleSettings()` now dereferences `wineVersion` unconditionally on a path that only needs the bottle name

**File:** `src/backend/storeManagers/steam/bottle.ts:295-315`
(with `src/backend/storeManagers/steam/library.ts:80-81`)

**Issue:** The pre-`539bc979c` body was `wineVersion: storedWineVersion ?? globalSettings.wineVersion`
— tolerant of both being absent. It is now:

```ts

const wineVersion =
  candidateWineVersion.type === 'crossover'          // ← unguarded dereference
    ? candidateWineVersion
    : (resolveCrossoverWine('…') ?? candidateWineVersion)
```

`library.ts:80` calls this getter **solely** for `wineCrossoverBottle`:

```ts
function getBottleSteamappsRoot(): string {
  return getBottleSteamappsDir(getSteamBottleSettings().wineCrossoverBottle)
}
```

and that function is on `readAcfState('bottle')`'s hot path — every install poll tick,
every uninstall poll tick, `buildBottleInstalledMap`, `refreshInstallState`. A
`GlobalConfig.getSettings()` result without a `wineVersion` (the sidecar's config layer
is a different code path from Electron's, and the ledger records several hollow sidecar
stubs) now turns pure path resolution into a `TypeError` that propagates through the ACF

```ts
  candidateWineVersion?.type === 'crossover'
    ? candidateWineVersion
    : (resolveCrossoverWine('CrossOver (Steam bottle runtime)') ?? candidateWineVersion)
```

and add a spec for `getSettings()` returning no `wineVersion`.

### A-21 (WARNING): the GPTK root cause is masked at the read site, not fixed at the write site — the store still hands the broken engine to the 34.13 install form

**File:** `src/backend/storeManagers/steam/bottle.ts:295-315, 333-334`

**Issue:** `539bc979c`'s commit message names defect #2 as *"getSteamBottleSettings()

**Fix:** put the CrossOver check on the write side as well, where the D-08 CrossOver-only
