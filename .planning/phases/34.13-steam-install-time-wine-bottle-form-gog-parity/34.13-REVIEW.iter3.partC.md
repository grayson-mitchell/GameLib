## Critical Issues

### C-17: `SteamClientSetup`'s readiness poll outlives `close()` and later dispatches an install the user dismissed

**File:** `src/frontend/screens/Game/GamePage/components/SteamClientSetup.tsx:70-98`
(with `src/frontend/App.tsx:139`, `src/frontend/state/SteamClientSetup.ts` `close`)

**Issue:**

This is C-05, verbatim, in the sibling component — plus a side effect C-05 did
not have. The fix pass edited this exact file (commit `fc7ce74a1`, the
`logSteamInstallDispatchFailure` change at lines 84-86) and did not carry the
C-05 lesson across.

```tsx
useEffect(() => {
  if (phase !== 'waiting' || !appName) {      // <- no `isOpen` term
    if (pollRef.current) clearInterval(pollRef.current)
    return
  }
  const poll = () => {
    void window.api.steamClientSetupRecheck(appName).then((result) => {
      if (result.status === 'ready') {
        if (pollRef.current) clearInterval(pollRef.current)
        if (gameInfoRef.current) {
          installSteamGame(appName, gameInfoRef.current).catch(...)   // <- side effect
        }
        close()
      }
    })
  }
  poll()
  pollRef.current = setInterval(poll, RECHECK_POLL_INTERVAL_MS)
  return () => { if (pollRef.current) clearInterval(pollRef.current) }
}, [phase, appName, close])
```

Every precondition for the C-05 failure holds here and I checked each:

1. `<SteamClientSetup />` is mounted **permanently** in `App.tsx:139`; `isOpen`
   false only makes it `return null` at line 100 — it never unmounts, so the
   cleanup is never run by React.
2. `close()` is `set({ isOpen: false })` — it touches **neither** `phase`
   **nor** `appName` (`state/SteamClientSetup.ts`).
3. `close` is a zustand initializer-scope arrow, so its identity is stable
   across renders (verified: `create((set) => ({ …, close: () => set(...) }))`
   runs once).

So the dep array `[phase, appName, close]` does not change when the user
dismisses the banner, the effect does not re-run, its cleanup does not fire,
and `window.api.steamClientSetupRecheck(appName)` keeps being invoked every
3000 ms for the remaining life of the app.

**The consequence is not a wasted timer.** The `'ready'` branch calls
`installSteamGame(appName, gameInfoRef.current)`. Reachable trace:

- Backend pushes `steamClientSetupRequired` with `reason: 'launch-once'` →
  `phase` starts at `'waiting'` immediately (line 61), banner shows "Steam is
  installed but has not been launched yet…".
- User decides not to install this game after all and clicks **Done**
  (`handleCancel` → `close()`), the only dismiss affordance the banner has.
- Poll keeps running. Hours later the user opens Steam for an unrelated
  reason. The next tick returns `'ready'`, and GameLib silently queues a
  multi-gigabyte download for a game the user explicitly walked away from.

There is no component-level test for this file at all (the only
`SteamClientSetup` suite is `state/__tests__/SteamClientSetup.test.ts`, which
covers the store), so nothing would have caught it.

**Fix:** apply the exact shape `SteamBottleSetup.tsx:204-242` now carries, and
close the dismissal race explicitly rather than relying on the interval alone:

```tsx
useEffect(() => {
  if (!isOpen || phase !== 'waiting' || !appName) {
    if (pollRef.current) {
      clearInterval(pollRef.current)
      pollRef.current = undefined
    }
    return
  }
  const poll = () => {
    void window.api
      .steamClientSetupRecheck(appName)
      .then((result) => {
        if (result.status !== 'ready') return
        if (pollRef.current) {
          clearInterval(pollRef.current)
          pollRef.current = undefined
        }
        if (gameInfoRef.current) {
          installSteamGame(appName, gameInfoRef.current).catch(
            logSteamInstallDispatchFailure(appName)
          )
        }
        close()
      })
      .catch(() => {
        // see C-19 — a rejected READ is UNKNOWN, keep polling
      })
  }
  poll()
  pollRef.current = setInterval(poll, RECHECK_POLL_INTERVAL_MS)
  return () => {
    if (pollRef.current) {
      clearInterval(pollRef.current)
      pollRef.current = undefined
    }
  }
}, [isOpen, phase, appName, close])
```

Add a source gate mirroring `steamBottleSetupSeeding.test.ts`'s
`slicePollEffect` specs — the C-05 gate is file-scoped to
`SteamBottleSetup.tsx` and therefore structurally unable to notice this
second instance. A repo-wide census of "permanently-mounted store-driven
surface with a `setInterval` keyed on `phase` but not on `isOpen`" would have
found both.

### C-18: the C-06 fix clears two pieces of state that only an `[isOpen]`-keyed effect can restore — a same-session `appName` change now leaves the wizard permanently engine-less

**File:** `src/frontend/screens/Game/GamePage/components/SteamBottleSetup.tsx:64-90` (reset, deps `[isOpen, appName]`) vs `:96-107` (engine fetch, deps `[isOpen]`)

**Issue:** This is a regression the C-06 fix introduced, and it is invisible to
the gate the same commit added.

The reset effect now ends with:

```tsx
setEnginesFetched(false)
setWineVersionList([])
}, [isOpen, appName])
```

The **only** writer of `enginesFetched(true)` / `setWineVersionList(list)` is:

```tsx
useEffect(() => {
  if (!isOpen) return
  void window.api.getAlternativeWine().then((list) => { … })
}, [isOpen])            // <- appName is NOT a dependency
```

I confirmed both dep arrays mechanically against the real source:
`ENGINE-FETCH EFFECT DEPS: }, [isOpen]` vs
`SESSION-RESET EFFECT DEPS: }, [isOpen, appName]`.

So whenever `appName` changes **without** `isOpen` first going false, the reset
zeroes the engine list and its settle flag and nothing ever refills them. The
seeding effect's guard `if (… || !enginesFetched || …) return` (line 148-154)
then returns forever:

- `wineVersion` stays `undefined` — D-15's persisted engine is never seeded,
  and Phase 17's CrossOver derivation never runs;
- `WineSelector` is handed `wineVersionList={[]}`, so `engineOptions` is empty,
  the engine `SelectField` is disabled, and `showNoCrossoverEngineNotice`
  renders — telling a user who *does* have CrossOver installed that they do
  not;
- `handleConfirm` submits `wineVersion: undefined`.

**Reachable:** `open(appName)` is `set({ isOpen: true, appName })`, so a second
backend `steamBottleSetupRequired` for a **different** game while the surface is
already open changes `appName` with `isOpen` already `true`. The backend emits
that signal from three sites in `storeManagers/steam/games.ts` (lines 902, 1743,
1974), on both `install()` and `launch()`. The window is wide open in the
banner phase, which is deliberately a plain `<div>` toast, not a modal
`Dialog` — nothing blocks the user from clicking Install/Play on a second
bottled game while it is showing. `isSteamBottleSetupActiveFor` is keyed on
`state.appName === appName`, so game B's Install button is **not** disabled by
`is.settingUpBottle` either.

Before the C-06 fix this path was harmless: `enginesFetched` stayed `true` and
the list stayed populated, so the seed still ran (with a possibly stale list —
the narrow race C-06 was filed for). The fix traded a narrow, transient
staleness for a permanent wedge.

The new gate in `steamBottleSetupSeeding.test.ts:206-225` asserts only that the
reset *contains* `setEnginesFetched(false)` / `setWineVersionList([])`. It says
nothing about whether either can be set again, so it is green on exactly the
input that breaks.

**Fix:** make the repopulating effect track the same session key as the reset:

```tsx
useEffect(() => {
  if (!isOpen) return
  let cancelled = false
  void window.api.getAlternativeWine().then((list) => {
    if (cancelled) return
    setWineVersionList(list)
    setEnginesFetched(true)
  })
  return () => { cancelled = true }
}, [isOpen, appName])
```

and add the missing half of the C-06 gate — a spec asserting the engine-fetch
effect's dep array is a **superset** of the reset effect's, driven against a
known-bad derived by deleting `appName` from it.

### C-19: `SteamClientSetup` carries the unfixed C-02 (`await` with no `try/catch`) and WR-03 (poll with no `.catch`) shapes verbatim

**File:** `src/frontend/screens/Game/GamePage/components/SteamClientSetup.tsx:76-91,106-115`

**Issue:** Two more instances the fix pass's enumeration missed in a file it
edited.

**(a) `handleConfirm` — C-02's exact shape.**

```tsx
const handleConfirm = async () => {
  setError(undefined)
  const result = await window.api.steamClientSetupStart()   // no try/catch
  if (result.status === 'error') { setError(result.error); setPhase('error'); return }
  setPhase('waiting')
}
```

`window.api.steamClientSetupStart` is a `makeHandlerInvoker` channel:
`ipcRenderer.invoke` under Electron, the sidecar transport under Tauri. Both
**reject** on a backend throw, a dead sidecar, or a transport timeout — the
argument C-02's own fix comment (`SteamBottleSetup.tsx:272-285`) spells out.
Here that produces an unhandled rejection **and** a silent dead click: `phase`
stays `'consent'`, no error surfaces, the "Install Steam" button just does
nothing. Milder than C-02's forever-wedge only because the consent dialog
happens to remain usable.

**(b) The recheck poll — WR-03's exact shape.**

```tsx
void window.api.steamClientSetupRecheck(appName).then((result) => { … })
```

A bare `void` silences `no-floating-promises` while attaching **no** rejection
handler — the precise wording of the fix already written into
`SteamBottleSetup.tsx:222-231`. Under the ledgered Tauri sidecar failure mode
this is an unhandled rejection every 3000 ms, and (per C-17) for the life of
the app rather than the life of the surface.

**Fix:** copy both remedies from the sibling verbatim, including the asymmetry
comment (a rejected *read* is UNKNOWN, a rejected *start* is FAILED):

```tsx
const handleConfirm = async () => {
  setError(undefined)
  try {
    const result = await window.api.steamClientSetupStart()
    if (result.status === 'error') { setError(result.error); setPhase('error'); return }
    setPhase('waiting')
  } catch (e) {
    setError(e instanceof Error ? e.message : String(e))
    setPhase('error')
  }
}
```

and `.catch(() => { /* UNKNOWN, next tick answers */ })` on the poll. The JSX
attribute is already `onClick={() => void handleConfirm()}` (line 137), so no
change is needed there.

### C-20: the provisioning poll still has no terminal bound, and `phase` is never reset on close — the C-05 fix scoped the poll's lifetime, it did not bound it

**File:** `src/frontend/screens/Game/GamePage/components/SteamBottleSetup.tsx:204-242,291-293`

**Issue:** Commit `ff5ac9e8a`'s subject reads "**bound** the provisioning poll".
What landed is lifetime scoping (`[isOpen, phase]`), which is the correct and
sufficient fix for C-05's stated defect — but there is no bound in the ordinary
sense, and the residual C-05 explicitly recommended ("consider a bounded retry
count so a permanently-erroring channel terminates into the `error` phase
instead of looping") was not implemented. I verified mechanically: the sliced
poll effect contains no `attempt` / `maxPoll` / `retries` / limit term of any
kind.

Answering the review question directly — *what happens at the bound?*

1. **There is no attempt/time bound.** While the surface is open in
   `phase === 'provisioning'`, a `steamBottleStatus` channel that rejects on
   every call polls forever. The WR-03 `.catch` deliberately keeps the interval
   armed, so the banner reads "Setting up Steam — this can take a while on
   first run." indefinitely, with no error, no "Try again" (that button exists
   only in the `error` phase), and no way to distinguish "slow" from "dead
   channel". The only terminal state reachable from `provisioning` is
   `provisioned === true`, or the user pressing Done.
2. **At the lifetime bound (`isOpen` → false) the poll stops silently while
   `phase` is still `'provisioning'`.** `handleDone` is `close()` and nothing
   else; the session effect that resets `phase` begins `if (!isOpen) return`,
   so it resets on *open*, never on *close*. The C-05 fix's own inline comment
   states this as a known fact and works around it rather than correcting it,
   which leaves the invariant "`phase` reflects a live operation" false between
   sessions. It is benign today only because `isOpen` gates every consumer.
3. **Cleanup on unmount is correct** — the effect returns a cleanup that clears
   and nulls `pollRef.current`. It simply never runs, because `App.tsx:138`
   mounts the component permanently.

**Fix:**

```tsx
const MAX_STATUS_POLL_ATTEMPTS = 200   // ~10 min at 3s
const attemptsRef = useRef(0)
…
attemptsRef.current = 0            // on entering the effect
const poll = () => {
  if (++attemptsRef.current > MAX_STATUS_POLL_ATTEMPTS) {
    clearInterval(pollRef.current); pollRef.current = undefined
    setProvisionError(/* i18n: status channel stopped answering */)
    setPhase('error')
    return
  }
  …
}
```

and reset `phase` in `handleDone` (`setPhase('consent')` before `close()`) so
the component's state is never left describing an operation that is no longer
being observed. Either way, the commit subject should be corrected — "bound"
currently describes something the diff does not contain.

### C-24: two of the six reworked source gates measure a proxy narrow enough to miss a realistic drift

**File:** `src/frontend/screens/ConsoleMode/InstallOverlay/__tests__/consoleSteamTarget.test.ts:351-359,81-97`

Both gates are genuinely non-vacuous (I proved each fails on my own derived
known-bad), but I also found inputs that defeat them:

- **B4** matches `/blocked|degrade/` against the destructured parameter. A
  fourth parameter named anything else — I tested `verdict` — passes. The spec
  name is "the parameter object carries no blocked/degrade key", so the name
  and the assertion agree; the residual risk is only that the drift may not be
  spelled `blocked` or `degrade`. Consider asserting the key **set** is exactly
  `{runner, focused}` instead of screening a denylist.
- **D7**'s `assertCopyResolvedThroughTable` forbids the two `reason === '…'`
  equality forms. A `switch (steamBlocked.reason) { case 'library-missing': … }`
  re-branch passes cleanly — the same class of defect the gate exists to stop.

### C-25: the caret's panel item carries `buttonWithIcon` but renders no icon, unlike the sibling it was aligned to

**File:** `src/frontend/screens/Game/GamePage/components/MainButton.tsx:376-386` (with `GameSubMenu/index.tsx:338-349`)

### C-26: the C3 exhaustiveness pin's comment misstates which half catches a deletion

**File:** `src/frontend/screens/ConsoleMode/InstallOverlay/__tests__/consoleSteamTarget.test.ts:400-413`

The comment reads "a member DELETED from `ALL_REASONS` makes
`_BackwardExhaustive` fail". It does not: after a deletion,
`(typeof ALL_REASONS)[number]` is a strict subset of the union and still
`extends` it, so `_BackwardExhaustive` stays `true`. The pin that fails is
`_ForwardExhaustive` (the union no longer extends the shrunken tuple).
`_BackwardExhaustive` catches the opposite drift — a member added to
`ALL_REASONS` that is not in the union. The mechanism is correct and both
directions are covered; only the rationale is wrong, which matters because this
is precisely the kind of comment a future reader will trust instead of
re-deriving.
