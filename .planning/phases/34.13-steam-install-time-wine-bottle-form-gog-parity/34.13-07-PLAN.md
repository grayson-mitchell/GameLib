bottle-eligible, and what wine engine / bottle name is already persisted?" (D-09 + D-15's exposure
half) and a write channel that persists the user's chosen engine into the bottle store (D-14).

- **D-09** — 34.13-08's trigger predicate must ask the backend, not re-derive the answer. The
  backend seam (`SteamGame.checkBottleEligibility()`) landed in 34.13-02; nothing can reach it from
  the renderer until this plan exposes it.

  and `SteamGame.getSettings()` ignores per-game `GameConfig` entirely for a bottle-eligible game,
  so the GOG `writeConfig`-then-install mechanism is structurally unavailable.

  means 34.13-09 needs no second round-trip. **It does not make the guided setup read it.**

of two runtimes, two preload exports, three test files' worth of execution proof, and one
inventory entry.

3. **RESEARCH.md Open Question #1 recommends a verdict "shaped after `getSteamBottleSettings()`'s

   value (`bottle.ts:614-615`), so they agree in practice — but the verdict must use
   `wineCrossoverBottle`, because that is the key the settings object the install actually runs
   against is built from. A prefill sourced from the other key could disagree with the bottle the
   install uses.
