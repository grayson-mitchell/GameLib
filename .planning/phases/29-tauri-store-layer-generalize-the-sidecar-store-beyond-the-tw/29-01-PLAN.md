    (1) D-14 path-keyed shared cell. Add a module-level
    `const cellRegistry = new Map<string, { data: Record<string, unknown> }>()`.
    `FileStore`'s constructor resolves `filePath` as today, then does
    `this.cell = cellRegistry.get(filePath) ?? <create {data: load(filePath)} and set>`.
    Replace every `this.data` read/write in `has`/`get`/`set`/`delete`/`clear`/the
    `store` getter+setter/`[Symbol.iterator]` with `this.cell.data`. Do NOT return a

    object; only the DATA is shared. Export a test-only reset:
    `export function __resetFileStoreRegistry(): void` that clears `cellRegistry`
    (documented as test-only in a comment; production code never calls it).

    (2) D-02b `options.defaults`. If `options.defaults` is a plain object, seed it
    UNDER the loaded data at cell creation time only (loaded on-disk values win over
    defaults; a key present in defaults but absent on disk reads as the default).
    Do not write defaults to disk at construction — document that as an intentional
    deviation from electron-store/`conf` (which persists defaults) with a one-line
    comment naming D-02's "full semantics parity NOT required" bar.

    (3) D-10 atomic persist. `persist()` writes `JSON.stringify(this.cell.data, null, 2)`
    to `${this.filePath}.tmp-${process.pid}` via `writeFileSync`, then `renameSync`s it
    onto `this.filePath`. Import `renameSync` from 'graceful-fs' alongside the existing
    imports. On a `renameSync` failure, fall back to a direct `writeFileSync` to
    `this.filePath` so a persist can never be silently lost, and write a diagnostic to
    `process.stderr` (never include values — token material can live in `data`).

    (4) Documentation block. Extend the existing module docstring with two named,
    greppable notes:
      - `D-14 (in-process same-path sharing)` — why the cell registry exists, naming
        `steamConfigStore`/`steamBottleConfigStore` and `steam_store/config.json`.
      - `D-07 (ACCEPTED cross-process write clobber)` — running the Electron build and
        the Tauri build concurrently against the same userData folder can silently
        erase each other's config writes, because each process caches the whole JSON
        in memory and rewrites it wholesale. Accepted, not engineered around; the
        shipped product is one app. State that the same note is recorded in
        `.planning/phases/27-tauri-shell-walking-skeleton/SEAM.md`.

    Preserve `resolveStorePath()` exactly as-is including its T-27-03 comment — it is
    the path-tampering guard and must not be weakened or moved.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| renderer → sidecar RPC → store construction options | `storeNew` options originate in renderer code; `resolveStorePath()` is the only thing standing between them and an arbitrary filesystem write |
| Electron process ↔ Tauri sidecar process (shared userData dir) | two independent writers of the same JSON files |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-29-01 | Tampering | `resolveStorePath()` in `fileStore.ts` | mitigate | Preserve the T-27-03 guard byte-for-byte: path derives ONLY from `pathShim.getPath('userData')` + `options.cwd`/`options.name`. Acceptance criterion greps for `T-27-03` and `getPath('userData')` still present. The RPC-supplied-options case is closed by plan 29-05's storeNew validation. |
| T-29-02 | Denial of Service | `persist()` temp file | mitigate | Temp file is `${filePath}.tmp-${process.pid}` inside the already-guarded store dir (no attacker-chosen suffix), and a failed `renameSync` falls back to a direct write rather than dropping the persist. |
| T-29-03 | Information Disclosure | `persist()` error diagnostics | mitigate | Diagnostics written to stderr must never include `data` values — token material lives in these stores (mirrors T-28-04). |
| T-29-04 | Tampering | concurrent Electron/Tauri writers | accept | D-07: dev-only situation, shipped product is one app. Documented in `fileStore.ts` (this plan) and SEAM.md (plan 29-07). |
