<objective>
Make the renderer half of the store layer real: tier the snapshot (D-03), give a
not-yet-hydrated synchronous read a safe, DIAGNOSABLE fallback (D-04), apply the
sidecar's per-key change events (D-06), and swap the Tauri path's duplicated
deny-list for the single-sourced allow-list (D-08) — without touching the Electron
branch by a single byte.

Purpose: `index.tsx` awaits `hydrateStoreSnapshot()` behind an 8000ms timeout before
React mounts. Everything not in that payload reads as a default today, silently. D-04
turns that from an invisible correctness hazard into a logged, self-correcting one —
the same class of bug 27-05 was expensive to find precisely because it was silent.

Output: a tiered `tauriTransport.ts`, a comment-only edit to `misc.ts`, and extended
`src/preload/__tests__/tauriTransport.test.ts`.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| renderer script (incl. XSS via themes/custom CSS) → `window.api.storeGet` | any renderer code can name an arbitrary store and key |
| sidecar push (`storeChanged`) → renderer snapshot | inbound data mutates the renderer's authoritative in-memory copy |
| Electron path ↔ Tauri path secret policy | two divergent policies live in adjacent code |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-29-19 | Information Disclosure | `snapshotGet`/`snapshotHas` on a credential field | mitigate | Replace the 2-key deny-list with `isAllowedStoreField` (fail closed). A field not in the allow-list returns `undefined`, not the caller's default — so a blocked read is distinguishable from a miss. Asserted for `csrfToken`, `refreshToken.sub`. |
| T-29-20 | Information Disclosure | `hydrateStore()` pulling an unfiltered store payload into the renderer | transfer | The sidecar's `STORE_FETCH_CHANNEL` handler applies `filterStoreSnapshot` before responding (plan 29-04, T-29-14); the renderer's own `isAllowedStoreField` gate on every read is the second layer. Defense in depth preserved. |
| T-29-21 | Tampering | a `storeChanged` payload naming a store/key the renderer never registered | accept | The push originates only from the sidecar over the Rust-relayed `frontend_message` event — the same trust level as every other backend push (`pushGameToLibrary`). Patching an unregistered store is inert; reads still pass the allow-list gate. |
| T-29-22 | Denial of Service | D-04 warning flooding a hot render loop | mitigate | Warn at most once per `store+key` pair via a Set guard; `hydrateStore` de-dupes concurrent fetches through `inflight`. |
| T-29-23 | Denial of Service | a rejecting lazy hydrate aborting module evaluation and blanking the window | mitigate | All hydrate rejections are caught and logged, never rethrown (SEAM Invariant B; the 27-05 blank-screen failure mode). Asserted by the rejecting-fetch test. |
| T-29-24 | Repudiation | silently-wrong first read that self-corrects | mitigate | D-04's `STORE_LAZY_MISS_MARKER` makes it diagnosable from a log rather than only from a live repro — the explicit accepted-risk mitigation in 29-CONTEXT. |
| T-29-25 | Elevation of Privilege | divergent Electron/Tauri policies misread as a bug and "harmonised" by flipping Electron to fail-closed | mitigate | Explicit D-08 comment at BOTH sites naming Phase 35 as the cutover moment, plus an acceptance criterion pinning the Electron deny-list contents byte-for-byte. |
| T-29-SC | Tampering | npm/pip/cargo installs | mitigate | Not applicable — zero new packages this phase (29-RESEARCH.md § Package Legitimacy Audit). |
