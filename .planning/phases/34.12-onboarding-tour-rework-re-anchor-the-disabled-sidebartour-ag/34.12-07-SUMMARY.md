### Spacing method and numbers (measured, not eyeballed)

This project has twice had "no layout shift" claims proven wrong from eyeballing screenshots,
so spacing was scored in pixels. The window was raised via System Events and captured with
`screencapture -R` inside a single process with a settle delay (VS Code steals focus at the
start of every Bash call); each PNG was decoded in pure python -- there is no PIL or numpy on
this machine -- and reduced to a row profile over panel columns x=40..380, y=200..950 in 2x
Retina pixels, a row counting as GAP when <=2 px differ from the modal panel background.

Default theme, 2x px (halve for CSS px):

| boundary | gap |
|---|---|
| Installed -> Recently played | 46 |
| Recently played -> Favourites | 40 |
| Favourites -> COLLECTIONS (inside `Header__categoriesGroup`) | 88 |
| COLLECTIONS -> STORE (`.Header`'s own gap between the two wrappers) | 75 |
| STORE -> RUNNABILITY (inside `Header__filtersGroup`) | 75 |
| RUNNABILITY -> MORE FILTERS (inside `Header__filtersGroup`) | 75 |

The three facet groups sit at **exactly 75**, the same value as `.Header`'s own inter-wrapper
gap. That is the property 34.12-02 was buying: a wrapper inserted between `.Header` and its
children removes those children from `.Header`'s gap, so a lost wrapper `gap` would read **0**
here. Nothing is collapsed anywhere in the panel.

Across themes the full band tables are **byte-identical** (string-compared, not inspected),
while the modal panel background differs in each -- default `(23,28,30)`, `gruvbox_dark`
`(50,48,47)`, `dracula` `(69,71,88)` -- which proves the theme genuinely changed rather than a
stale capture being re-measured.

## BLOCKING DEFECT -- intro.js tooltip does not render

**Symptom.** Both tours render the dim overlay and the highlight box, but no tooltip: no title,
no body text, no Next/Back/Skip controls.

**Ownership: UNRESOLVED. Do not attribute it to a 34.12 plan on this evidence.** The anchor
work is confirmed correct by Task 2; what is broken is the surface that displays step content.
No phase before this one ever verified a tour *rendering* under Tauri -- 34.10 disabled the
sidebar tour and 34.12 rebuilt it against a jest project with no jsdom -- so this may have been
broken since the shell migration and simply never observed.

**Two hypotheses were tested against the live app and BOTH ARE REFUTED.** Recorded so the
follow-up investigation does not repeat them:

1. **"`introjs.css` never loads, and the dim + highlight come from `Tour.scss` alone."**
   Plausible because `Tour.scss` independently defines `.introjs-helperLayer`'s
   `box-shadow: 0 0 0 1000px rgba(0,0,0,.6)` (the dimming) and `.heroic-tour-highlight` (the
   border). **Refuted:** the vite-transformed module emits
   `import "/node_modules/intro.js/introjs.css"` and the file serves 200.
2. **"`disableInteraction: true` (D-04), or the `position: 'right'` value, suppresses the
   tooltip."** These are the only structural differences between `NavShellTour` and
   `LibraryTour`. Two isolated source probes were run (each diffed against a byte-copy backup
   to prove single-line isolation) and **both are refuted by the same observation**:
   `LibraryTour` was **not modified by either probe**, yet it rendered descriptions during one
   run and none during another. A component nobody touched changed behaviour between runs, so
   the variable was never `disableInteraction` and never `position` -- both probes were reading
   run-to-run variation as a configuration effect.

**The actual signal: the defect is INTERMITTENT and session-stateful, not configuration-driven.**
Run-by-run, in order observed:

| run | observation |
|---|---|
| A (baseline) | nav tour: no descriptions. library tour: "just dims the screen". |
| B (relaunch) | library tour auto-resumed at startup **with** descriptions, walked whole. Then nav tour: none. Then library redo: steps 1-2 element-less by design, game tile onward fine. |
| C (`disableInteraction:false`) | library tour at startup: descriptions through step 3. Then nav tour: step 1 description, then it disappeared. |
| D (`position:'bottom'`) | nav tour: none. library tour: none. |

Candidate pattern, **not established**: the first tour after app start renders tooltips and
later ones in the same session do not. Runs B and C fit; run D is unconfirmed because nobody
checked whether a tour auto-resumed at startup before the nav tour was opened.

**Guidance for the follow-up:** do not repeat the guess-and-relaunch loop. Instrument instead.
The DevTools console **input** is dead in this build; the **output** panel is readable, so the
documented escape hatch is a temporary `console.warn` in `Tour.tsx` reporting whether
`.introjs-tooltipReferenceLayer` / `.introjs-tooltip` exist in the DOM and their
`getBoundingClientRect()`, read from the output panel. Versions in play: `intro.js` 7.2.0,
`intro.js-react` 1.0.0 (peer range `>=2.5.0` satisfied, `intro.js` has no dependencies).
