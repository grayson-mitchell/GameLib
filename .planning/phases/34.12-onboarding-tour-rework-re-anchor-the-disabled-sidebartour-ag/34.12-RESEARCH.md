## Summary

CONTEXT.md's D-01..D-09 are complete and correct against HEAD — every named symbol, file
and line number I re-grepped matches (`SettingsPanel/index.tsx`'s `QuitButton` as last
child, the `Sidebar/` tree containing only `SidebarTour.tsx`, `library-header`'s duplicate

find any drift between CONTEXT.md and HEAD to report as a mismatch under priority 3 — the
twelve target components all still exist with the shapes CONTEXT.md describes.

What CONTEXT.md leaves genuinely open, and where this research concentrates, is:

1. **The positive gate.** `tourDisabled.test.ts` is a pure source-text regex gate over
   whole files (`readStripped(path)` + `.not.toMatch(...)`). Its replacement cannot be
   "grep the twelve strings exist somewhere" — that is explicitly banned and is also, on
   inspection of the sibling test idiom already used throughout `NavShell/__tests__/`,
   unnecessary: this codebase already has a proven, repo-idiomatic way to prove a specific
   prop value lands on a specific named component **without jsdom** — invoke the real
   component function directly (optionally through a hand-rolled hooks harness for
   stateful components) and assert on the returned React-element object graph's `props`,
   keyed by `element.type` identity or by finding the row via its `label`. Three concrete
   sibling tests already do exactly this against these exact twelve components'
   neighbourhood (`SettingsPanel.test.tsx`, `NavTabsComponent.test.tsx`,
   `DownloadsRing.test.tsx`).

2. **A real, previously-undocumented plumbing gap.** `NavItem` — the row primitive that
   renders four of the twelve anchors (Wine Manager, Accessibility, Documentation, Ko-fi)
   — has a **closed prop interface with no `data-*` passthrough**, and its own docstring
   says the tour-anchor prop was **deliberately dropped** when it was ported off the
   retired sidebar ("re-adding it would ship anchors for a tour that does not run" —
   `NavItem/index.tsx:14-18`). This must be un-dropped before four of the twelve anchors
   can exist. CONTEXT.md's Discretion section does not surface this; it is real, scoped
   work, not a rediscovery of D-05's step list.

3. **A confirmed instance of the exact trap D-07 warns about.** The English catalog's
   current text for `tour.sidebar.version` (`public/locales/en/translation.json:1310`)
   already differs from `SidebarTour.tsx`'s own inline fallback string (`SidebarTour.tsx:149`)
   — and the German catalog's version of the same key still says "Heroic-Version", not
   "GameLib" (`public/locales/de/translation.json:1084`, quoted below). This is live
   evidence, not a hypothetical, for why D-07 mints a new key rather than editing the
   fallback.

4. **A new dead `data-tour` occurrence IN-01 did not catalogue:** `data-tour="humble-keys"`
   at `Humble/Keys/index.tsx:130`, referenced by zero tour steps in either `SidebarTour.tsx`
   or `LibraryTour.tsx`.

5. **D-09's two re-anchor targets are architecturally ambiguous at the single-element
   level**, and the naive fix (wrap the relevant siblings in a new container div) risks a
   visible spacing regression because `.Header` is `display:flex; flex-direction:column;
   gap:var(--space-md)` between **direct** children (`Header/index.css:1-9`) — collapsing
   two or three of those children under one new wrapper changes what `gap` applies between.

**Primary recommendation:** Design the positive gate as a *composed two-layer proof* —
(a) each parent component (`SettingsPanel`, `NavTabs`, `DownloadsRing`, `HeroicVersion`,
a new leaf test for `QuitButton`) is invoked directly and asserted to pass the correct
`nav-*` string as a prop to the correct named child/element, and (b) `NavItem` itself is
asserted, once, to forward that prop onto its rendered `<NavLink>`/`<button>` DOM props.
Layer (a) proves wiring-with-identity (not "somewhere in the tree"); layer (b) proves the
primitive doesn't silently eat it. Neither layer alone would catch every failure mode; the
composition does.

### Pattern 1: Direct function invocation + React-element-graph inspection (no jsdom)

**What:** Call a function component directly (`Component(props)`), NOT via
`React.createElement`/render. The return value is a plain nested object
(`{type, props, key}` and so on) — walkable and assertable with zero DOM.

**When to use:** Every jest test in `src/frontend` (`testEnvironment: 'node'`, no jsdom, no
`react-test-renderer` installed — `src/frontend/jest.config.js:4-14`).

**Example — tying a prop to a *specific, identified* child, not "somewhere in the tree"**
(the load-bearing idiom this phase's gate should reuse):
```typescript
// Source: src/frontend/components/UI/NavShell/__tests__/SettingsPanel.test.tsx:50-56, 124-135, 149-170
jest.mock('../components/NavItem', () => ({
  __esModule: true,
  default: (props: Record<string, unknown>) => ({ type: 'mock-navitem', props })
}))
import NavItem from '../components/NavItem'
import SettingsPanel from '../components/SettingsPanel'

function findNavItem(tree: ReactNode, label: string) {
  return collectElements(tree).find(
    (el) => el.type === NavItem && el.props?.label === label
  )
}

const tree = SettingsPanel() as unknown as ReactElement
const wineRow = findNavItem(tree, 'Wine Manager')
expect(wineRow?.props['data-tour']).toBe('nav-wine')   // ties the string to THIS row
```

**Example — a stateful, effect-bearing component (`DownloadsRing`) via the hand-rolled
hooks harness** (established by `StoreSearchScreen.test.tsx`, reused verbatim in
`DownloadsRing.test.tsx:41-`):
```typescript
// Source: src/frontend/components/UI/NavShell/__tests__/DownloadsRing.test.tsx:41-60
// (abbreviated) — mocks 'react' with a real useState/useEffect-cursor-based fake
// dispatcher so DownloadsRing() can be called directly despite using hooks.
jest.mock('react', () => {
  const actualReact = jest.requireActual<typeof import('react')>('react')
  // ... stateSlots/effectDeps cursor machinery ...
  return { ...actualReact, useState: fakeUseState, useEffect: fakeUseEffect }
})
```

### Pattern 2: MUI `Tab`/`Tabs` and React Router `NavLink` both forward `data-*` props to the DOM without any code change

**What:** MUI's `Tab` component forwards unrecognized props to its root element (in this
codebase's usage, `component={NavLink}`, so unrecognized props forward to `NavLink`, which
itself forwards unrecognized props — including `data-*` — to the rendered `<a>`).
[CITED: mui.com/material-ui/api/tab, reactrouter.com/api/components/NavLink] — MEDIUM
confidence (both are well-documented, stable, long-standing library behaviours, but I did
not empirically render the two-hop chain in this exact installed-version combination
(MUI `^5.17.1`, `react-router-dom` `^6.30.0`); recommend the planner prove it once with a
`NavTabsComponent.test.tsx`-style direct-invocation assertion before relying on it).

**When to use:** For anchors 1-4 and 7 (the tier-1 tab strip and each of its four `<Tab>`s)
— add `data-tour="nav-*"` directly as a JSX prop in `NavTabs/index.tsx`. **No component
code change needed**, unlike `NavItem`.

### Pattern 3: Source-scoped regex over a bounded text block, not a whole file

**What:** When a source-text gate is unavoidable, scope the regex to a bounded, named
block (a specific CSS selector's declaration body, a specific function's body) rather than
the whole file — this is what turns "the string exists somewhere" into "the string exists
in the right place."

**Example — brace-counted CSS block scoping** (the strongest existing precedent in this
repo for "tie a check to a specific place, not the whole file"):
```typescript
// Source: src/frontend/screens/Login/__tests__/index.test.tsx:56-71
function cssBlock(source: string, selector: string): string {
  const start = source.indexOf(`${selector} {`)
  if (start === -1) throw new Error(`selector ${selector} not found`)
  let depth = 0
  for (let i = source.indexOf('{', start); i < source.length; i++) {
    if (source[i] === '{') depth++
    if (source[i] === '}') { depth--; if (depth === 0) return source.slice(source.indexOf('{', start) + 1, i) }
  }
  throw new Error(`unterminated block for ${selector}`)
}
```
Not directly reusable for JSX/TSX (no brace-delimited CSS-like block), but the *principle*
— bound the search region to the thing you actually mean — is what makes Pattern 1 (typed
element-graph inspection) strictly better here than any regex over `.tsx` source: the
"bounded region" in Pattern 1 is the component's own returned element tree, which is as
tight a bound as exists short of a real DOM query.

### Anti-Patterns to Avoid

- **"All twelve `nav-*` strings appear somewhere in `src/frontend`"** — explicitly banned
  by CONTEXT.md. It is RED-provable (delete one string, gate fails) but measures the wrong
  property: it would pass just as well if all twelve strings were pasted into a single
  unrelated comment, or attached to the wrong twelve elements entirely (e.g. all twelve on
  one `<div>`). This is the exact "gate can be non-vacuous, RED-proven — and guard NOTHING"
  failure mode this project has hit before (see memory:
  `gate-can-be-nonvacuous-and-measure-wrong-property.md`).
- **A regex per file that only checks "NavShell source references `data-tour`"** (the
  inverse of the current `tourDisabled.test.ts`) — same defect class: proves the string
  exists in the right *file*, not on the right *element*. `SettingsPanel/index.tsx` will
  contain `data-tour` for the Wine Manager row, the Accessibility row, the Documentation
  row and the Ko-fi row — a file-level check cannot distinguish "the right four rows got
  it" from "one row got all four, four times" or "it landed on the wrong four rows".
- **Checking only that `NavItem` was *called* with a `data-tour` prop present, without
  checking its *value*** — this is "function is called ≠ behaviour proven" (memory:
  `verification-can-check-callsite-not-behaviour.md`). Assert the exact string, not just
  presence.

## Common Pitfalls

### Pitfall 1: Assuming `NavItem` forwards arbitrary props

**What goes wrong:** A plan writes `<NavItem ... data-tour="nav-wine" />` in
`SettingsPanel.tsx` expecting it to reach the DOM, the way it would with a plain
`<button>`/`<a>`. `NavItem`'s `NavItemProps` interface (`NavItem/index.tsx:27-37`) has no
index signature and does not spread `...rest` — the prop is silently dropped by
TypeScript's structural typing at the call site (a TS error, actually, since
`data-tour` isn't a declared prop) or, if force-cast, simply never reaches the rendered
`<NavLink>`/`<button>`.
**Why it happens:** `NavItem`'s docstring explicitly documents this as **intentional** —
the tour-anchor prop was dropped on purpose during the 34.10 port (`NavItem/index.tsx:14-18`).
**How to avoid:** Add a `dataTour?: string` (or `'data-tour'?: string`, matching
`AddGameButton`'s and `ActionIcons`' existing convention of a hyphenated prop key) to
`NavItemProps`, destructure it, and pass it through onto **both** JSX branches (the
`<button>` and the `<NavLink>`) — not just one, since `NavItem`'s `elementType` switch
means only one branch renders per instance, but different anchors may use different
branches in the future.
**Warning signs:** A `tsc` error at the four `SettingsPanel` call sites the moment
`data-tour` is added without touching `NavItem` first.

### Pitfall 2: Editing a `t()` call's second argument (fallback) instead of minting a new key

**What goes wrong:** Editing step 12's copy in place —
`t('tour.sidebar.version', 'Check your current GameLib version and access tours from here.')`
— is a silent no-op for every locale whose catalog already has a translation for that key.
**Live proof this already happened once, unnoticed:** the **English catalog itself**
(`public/locales/en/translation.json:1310`) currently reads:
> "Check your current GameLib version, click it to see latest changelog, and access this
> tour from the help icon."

while `SidebarTour.tsx`'s own inline fallback (`SidebarTour.tsx:146-150`) reads:
> "Check your current GameLib version and access tours from here."

These two strings already disagree — the catalog wins at render time (react-i18next
resolves against the loaded catalog before falling back to the inline default), so this
tour, if it were ever re-enabled unchanged, would show the catalog's older text, not the
component's. **The German catalog is worse** — `public/locales/de/translation.json:1084`
still says:
> "Überprüfe deine aktuelle Heroic-Version, um die neuesten Änderungen einzusehen und
> starte diese Tour über das Hilfesymbol."

— literally "Heroic-Version", never rebranded, because `pnpm i18n`
(`i18next-parser.config.js:81`, `locales: ['en']`) only ever regenerates the English
catalog; the other 48 locale directories (`public/locales/*`, confirmed 49 total including
`en`) are untouched by any tooling in this repo and inherit whatever Heroic last wrote.
**How to avoid:** Per D-07, mint a `tour.nav.*` key for any step whose English copy
changes (step 12 definitely qualifies — its content is now factually wrong under D-01).
Leave unchanged-copy steps' existing `tour.sidebar.*` keys alone.
**Warning signs:** `pnpm i18n`'s diff touching `public/locales/de/...` (or any non-`en`
locale) at all — the churn guard (`meta/i18nCatalogChurnGuard.ts`) should already catch
this, but a human reviewing the diff should notice it too.

### Pitfall 3: Wrapping D-09's Views/Collections or facet groups in a new container div without preserving the flex-gap spacing

**What goes wrong:** `Header/index.tsx` currently renders `FilterViewList`,
`FilterCollectionList`, `FilterStoreFacet`, `FilterRunnabilityFacet`, `FilterMoreGroup` as
five **direct** siblings inside `.Header`, which is `display:flex; flex-direction:column;
gap:var(--space-md)` (`Header/index.css:1-9`). `gap` only applies between direct flex
children. If a plan wraps, say, `FilterViewList`+`FilterCollectionList` in a new
`<div data-tour="nav-library-categories">` to give D-09's "categories" step a single
anchor, that wrapper becomes the direct child instead of the two components it now
contains — the `gap` between `FilterViewList` and `FilterCollectionList` (previously
provided by `.Header`'s flex gap) silently disappears unless the new wrapper also declares
`display:flex; flex-direction:column; gap:var(--space-md)`.
**Why it happens:** CSS `gap` is a property of the flex/grid **container**, not the
children — a wrapper inserted between a flex container and two of its children removes
those two from that container's direct-child list.
**How to avoid:** Either (a) give the new wrapper the identical flex/gap declaration, or
(b) anchor the step on one specific existing element instead of wrapping (see Open
Question 1 below — this is a genuinely undecided design point, not resolved by CONTEXT.md).
This project's "multi-theme survival" gate (`gruvbox_dark`, `dracula`, `midnightMirage`)
would be where a silent spacing regression from option (a) done wrong would surface.
**Warning signs:** A visual diff in the Games tier-2 filter panel between this phase and
34.11's baseline, specifically vertical spacing between the Views/Collections block and
the facet groups below it.

### Pitfall 4: Treating `SettingsPanel.test.tsx`'s existing ordering/label assertions as pre-satisfied

**What goes wrong:** Assuming the D-01 launcher row can be added without touching
`SettingsPanel.test.tsx`. Two existing tests will break the moment the row is added:
`'renders all eleven entries in the settled order...'`
(`NavShell/__tests__/SettingsPanel.test.tsx:149-170`) hard-codes the expected `labelsOf`
array (10 `NavItem` labels + the trailing `QuitButton`) and will fail the instant an
eleventh `NavItem` label appears; `'the QuitButton element is the last child of the panel'`
(`:238-245`) will **still pass** as long as the new row is inserted *before* `QuitButton`
in JSX order (which D-01's phrasing — "alongside Documentation, Ko-fi, Accessibility and
Console Mode" — implies), but would fail immediately if a plan appended the row after
`QuitButton`.
**Why it happens:** These are exactly the kind of "coarser than the defect's unit" ordering
assertions this project's tests deliberately hard-code to catch regressions; adding new
content is a real, expected edit to them, not a defect in them.
**How to avoid:** Update the `labelsOf` expectation array in the same task that adds the
row; keep the new `<NavItem>` JSX call site strictly before `<QuitButton />`.
**Warning signs:** `SettingsPanel.test.tsx` red immediately after adding the row — this is
the CORRECT, expected signal that the test file needs a deliberate update, not a bug to
work around.

## THE POSITIVE GATE — full design

### What `tourDisabled.test.ts` currently asserts

Two `describe` blocks (`tourDisabled.test.ts:63-100`):

1. **"NavShell source files never reference the disabled tour"** — walks every `.tsx` file
   under `NavShell/` (excluding `__tests__/`), strips comments
   (`stripSourceComments`), and asserts each file's source does NOT match
   `/SidebarTour/`, `/SIDEBAR_TOUR_ID/`, `/TourButton/`, or `/data-tour/`. This is a
   whole-file regex scan, `it.each`'d over every file individually (so failures name the
   specific offending file, but not the specific offending line/element).
2. **"SidebarTour.tsx has no live importer"** — walks every `.ts`/`.tsx` file under
   `src/frontend` (excluding `SidebarTour.tsx` itself and the whole retired `Sidebar/`
   tree), and asserts none of them import `SidebarTour` via a `from '...SidebarTour'` or
   `require('...SidebarTour')` pattern.

Both are genuinely "file contains/doesn't contain a token" checks — no component
invocation, no element-graph inspection. The docstring (`tourDisabled.test.ts:1-33`)
explains why: this jest project has no jsdom, so a mount-based positive check wasn't an
option even for the ABSENCE gate; the same is about to be true for the presence gate this
phase writes.

### Design A (recommended): Retire the file-scan gate entirely; replace with per-component `data-tour` prop assertions distributed into each anchor's own sibling test file

Rather than one new consolidated file that reinvents seven different components' mocking
setups, extend the seven test files that already invoke these exact components directly
(`SettingsPanel.test.tsx` ×4 anchors, `NavTabsComponent.test.tsx` ×4 anchors,
`DownloadsRing.test.tsx` ×1, plus three new files — `QuitButton.test.tsx`,
`HeroicVersion.test.tsx`, and `NavItem.test.tsx`'s forwarding assertion). Each assertion
reads, e.g.:

```typescript
// In NavShell/__tests__/SettingsPanel.test.tsx, extending the existing findNavItem() helper
it('the Wine Manager row carries the nav-wine tour anchor', () => {
  contextValue = makeContextValue({ platform: 'linux' })
  const tree = SettingsPanel() as unknown as ReactElement
  const wineRow = findNavItem(tree, 'Wine Manager')
  expect(wineRow?.props['data-tour']).toBe('nav-wine')
})
```

**What property this measures:** that `SettingsPanel`'s JSX for the Wine Manager row
literally carries `data-tour="nav-wine"` as a prop value on the `NavItem` instance
identified by its `label`. Combined with a `NavItem.test.tsx` assertion that `NavItem`
forwards its `data-tour` prop onto the rendered `<NavLink>`/`<button>`'s own props, this
closes the loop from "SettingsPanel's source" to "the actual DOM attribute a CSS selector
like `[data-tour="nav-wine"]` would match" — without ever needing jsdom, because DOM
*props* (not DOM *nodes*) are what `React.createElement('a', {..., 'data-tour': 'nav-wine'})`
produces, and that's exactly what direct invocation returns.

**RED-proof plan (per CONTEXT.md's requirement):** delete the `data-tour="nav-wine"` prop
from the `SettingsPanel` JSX call site (or from `NavItem`'s forwarding) — this test goes
red immediately, with a failure message naming "Wine Manager row" specifically, not a
generic file-level diff.

**Retiring the old gate:** delete `tourDisabled.test.ts` outright once every anchor has a
positive assertion — its two `describe` blocks become permanently, structurally false the
moment the first anchor lands (the file docstring already predicts this: "That gate goes
red the moment the first anchor is added"). There is nothing worth keeping from it; a
positive per-component assertion is strictly more informative than its absence-check ever
was.

### Design B (supplementary, not a replacement for A): A twelve-entry manifest census, to close the duplicate-selector defect class

Design A proves each anchor is correct in isolation but does not, by itself, prove
**uniqueness** across the whole tree (the exact defect class step 5's known duplicate
belonged to). Add one small additional test:

```typescript
// New file, e.g. NavShell/__tests__/navTourAnchorCensus.test.ts
// Census, NOT the correctness proof (Design A owns correctness) — this only proves
// no `data-tour="nav-*"` VALUE appears at more than one source location repo-wide.
const NAV_TOUR_IDS = ['nav-menu','nav-library','nav-stores','nav-settings','nav-downloads',
  'nav-wine','nav-manage-accounts','nav-accessibility','nav-docs','nav-community','nav-quit',
  'nav-version']

it.each(NAV_TOUR_IDS)('data-tour="%s" appears at exactly one source location', (id) => {
  const matches = walk(FRONTEND_DIR, ['.tsx']).filter((path) =>
    readStripped(path).includes(`data-tour="${id}"`)
  )
  expect(matches).toHaveLength(1)
})
```

**What property this measures:** uniqueness, not correctness — a weaker, source-text-only
check, deliberately scoped narrow (exact `id` match, not "contains the substring
`data-tour`") so it cannot regress into the banned vacuous form. This is the "prove a grep
assertion in both directions" idiom: it fails against the KNOWN historical bad input
(re-introduce a second `data-tour="nav-downloads"` somewhere and this test goes red) and
passes against the current, correct tree.

**Why Design B alone is insufficient (do not ship it without A):** it cannot detect "the
right *count* (1) landed on the *wrong* element" — e.g. `nav-wine` correctly appearing
exactly once, but on the Accessibility row instead of Wine Manager, would pass Design B
and fail Design A. This is precisely the "audit coarser than the defect's unit" failure
mode.

### Rejected: Design C, "all twelve strings appear somewhere in the tree"

Explicitly banned by CONTEXT.md. Documented here only to record why, for the plan-checker:
it is RED-provable (remove a string, gate fails) but does not tie any string to any
specific element, so it cannot distinguish twelve correctly-placed anchors from twelve
anchors pasted onto one wrong element, or from twelve anchors placed on the WRONG rows
entirely as long as the literal substrings exist in the file. This is the "gate can be
non-vacuous, RED-proven — and guard nothing" failure mode, not a hypothetical for this repo
— it has happened here before (see memory index).

   `<div className="Header__categoriesGroup" data-tour="library-categories">` in
   `Header/index.tsx`, and the three facet components in a second new
   `<div className="Header__filtersGroup" data-tour="library-filters">` — requires adding
   matching `display:flex; flex-direction:column; gap:var(--space-md)` to both new
   wrapper divs to preserve `.Header`'s current spacing (Pitfall 3).
2. **Anchor on one representative element** per step — e.g. `FilterViewList`'s own `<nav>`
   root for "categories" (visually adjacent to `FilterCollectionList` immediately below
   it, so the highlight box would still read as "this general area"), and
   `FilterStoreFacet`'s `FilterFacetGroup` wrapper for "filters" — but `FilterStoreFacet`
   can render `null` when `connectedStores.length === 0`
   (`FilterStoreFacet/index.tsx:39-41`), so the anchor would not exist for a user with no
   connected stores; `FilterRunnabilityFacet`/`FilterMoreGroup` were not confirmed
   null-safe in this pass and should be checked before choosing this as the anchor.

I recommend option 1 (wrap, with matching flex styles) as the safer default — it does not
depend on a filter group's own conditional-render guard, and keeps the tour's
"categories"/"filters" language honestly scoped to what the wrapped group actually
contains — but this is a real open decision for the planner, not something research can
close without a product call.
