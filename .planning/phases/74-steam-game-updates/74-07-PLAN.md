<decisions>
- Shim handover mechanism: `placeShimForGame` already calls `backupOriginalBeforeOverwrite`, which copies the on-disk DLL over `<dll>.gamelib-orig` whenever the on-disk bytes are NOT a GameLib shim (`isGameLibShimBytes`), then places the shim. After an update replaced the shim with the new genuine DLL, that is exactly the handover. When the update did not touch the DLL, the on-disk file is still the shim, so the backup is skipped and placement is a byte-identity no-op: "leave the shim alone" holds by construction. The follow-up therefore always calls placeShimForGame (it is also the rescan); `shimTouched` is reported for logs/tests only. Verify this reading of shimOriginals.ts/shimGenerate.ts in Task 1 before relying on it; if placement refuses because a backup already exists, add a forced refresh of the backup only for the shimTouched case.
- `gamelib_bridge.cfg`: it needs the live helper's OS-assigned port, which only exists at launch; `launchBridgeGameBody` rewrites it on every Play (D-51-01). The follow-up does not write it; report `cfgRewrittenAtLaunch: true`; plan 13's live gate confirms the cfg beside the (possibly new) exe after the first post-update launch.
- Never call `removePerGameBridgeBottle` or `markBridgeFailedThisSession` from this module: the install path removes a just-created bottle when the scan rejects the game, but here the bottle holds an installed game. A changed verdict is persisted and the launch path routes on it.
- Order mirrors installBridgeGameLeased's post-download section: resolveBridgeLaunchExe -> placeShimForGame -> writeBridgeScanVerdict / setBridgeSteamApiPrescreen as the install does -> persistBridgeDrmSignal -> reconcileBridgePrescreen -> resolveInstallEngineSettings + installSteamBridgeSharedRedists({allowLogon: true}) -> prefetchBridgeDrmDownloads. Each step in its own try/catch appending to report.errors.
</decisions>
