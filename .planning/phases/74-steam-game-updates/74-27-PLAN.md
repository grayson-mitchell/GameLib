<objective>
Close two UAT gaps whose fixes sit on the same seam between the download queue and the Steam
update path:

- UAT 18: `[sidecarRpc] IPC_INVALID_ARGS kind=send channel=depotJobEvent paths=0.kind
  codes=invalid_union`. Verified at planning time: the Rust `JobEventBody` (gamelib-depot
  `job.rs`) has a Phase 74 `Stage { stage }` variant, and the TS `RustJobEvent` type
  (`depotRust/types.ts`) has `{ kind: 'stage'; stage: 'delta_planning' | 'delta_committing' }`,
  but the zod `depotJobEvent` discriminated union in `src/common/types/ipc/sidecarInternal.ts` has
  only planned/progress/warning/hostSummary. Each delta sends two stage events per job, so the
  stage text never reaches `progressBridge.ts`.
- UAT 17: the Update button flashes about 2 s before the badge clears after an InstallApp update.
  Mechanism: `updateRegisteredSteamGame` returns `{ status: 'done' }` as soon as it has handed off
  to Steam and started the update poll; `updateQueueElement`'s `finally` then sends 'done', and the
  frontend's done-after-updating drops the badge and starts a checkForUpdates refresh, which
  re-adds the still-stale game while the status is cleared, so the Update button shows until the
  poll's next 'updating' tick and later its completion. The todo's fix direction is "hold the
  Updating state until the update list refresh lands"; the poll already owns the terminal status
  (updatePollOnce `complete()` sends updating then done; the quiet end sends done).

Note for the SUMMARY: UAT 18's missing kind is also a likely cause of the out-of-scope todo
`2026-11-13-bridge-update-hero-planning-label.md` (no "Planning update..." in the Downloads hero).
Record that observation; do not move or edit that todo here.

Purpose: D-10 stage text must reach the UI, and D-11 "Updating..." must persist until Steam
finishes.
Output: schema fix, an explicit hand-off flag the queue honours, terminal-status audit, todos closed.
