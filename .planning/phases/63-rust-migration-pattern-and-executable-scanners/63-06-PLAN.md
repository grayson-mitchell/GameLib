<objective>
Wire the in-process app path (D-03). This plan adds the allow-listed `RUST_SCAN_*` channels, the
shell arms that call `gamelib_scan::dispatch`, and the TS invoke helper with the per-scanner impl
switch. It also creates the path-based async wrapper module for the two peSteamDrm readers that
app callers use.

Purpose: callers in 63-07, 63-08 and 63-09 migrate against a finished boundary.
Output: the channels, the arms, rustScan.ts, peScan.ts and the parity tests.

**Recorded decisions (veto-able):**
- **No timeout exception.** The 60 s `RUST_INVOKE_TIMEOUT_MS` is ample: these are header reads and
  at most 32 followed DLLs. `UNBOUNDED_RUST_CHANNELS` stays human-in-the-loop only.
- **No `spawn_blocking`.** `sidecar.rs` already runs every request on its own `std::thread::spawn`
  worker (~L511); `catch_unwind` inside `dispatch` (63-01) guarantees a reply.
- **Wrapper module for peSteamDrm readers.** The path-based async `detectSteamDrmInPe` and
  `readPeImportedDllNames` live in a NEW `bridge/peScan.ts`, not in `peSteamDrm.ts`. `peSteamDrm.ts`
  stays the pure TS oracle substrate, imported by legacyTsScanners and by the census until 63-10,
  so it cannot take backend imports. Callers switch their import path; `games.test.ts`'s
  `jest.mock('../bridge/peSteamDrm')` moves to `'../bridge/peScan'` in 63-08. Same names and result
  types as D-09 requires. The module path changes, and each wrapper gains a required `caller` tag
  argument used only for the per-caller evidence log.
- **Jest strategy (discretion).** Jest mocks the async boundary (`backend/scanners/rustScan`) and
  never spawns the CLI. The Jest lane has no Rust toolchain.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| sidecar → Rust shell (JSON-lines rustInvoke) | The sidecar is trusted; the allow-list is the gate for any frame (T-28-03) |
| scan result → caller decisions | Results drive shim placement and DRM launch routing |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-63-24 | Elevation of privilege | new channels on the rustInvoke surface | mitigate | Allow-list on both sides plus transportParity and scanChannelParity tests; not registered in `generate_handler!`, so the renderer cannot reach them |
| T-63-25 | Information disclosure | forged frame naming an arbitrary path | accept | Ops return parse facts only (booleans, DLL/symbol names, a real path that the caller already knew lexically); the sidecar could already read these files; containment ops refuse escapes |
| T-63-26 | Denial of service | rustInvoke hang | mitigate | 60 s unref'd timeout retained; catch_unwind guarantees a reply; wrappers map rejection to fail-closed values |
| T-63-27 | Tampering | bytes on the pipe | mitigate | All-string arg types (compile-time `@ts-expect-error` test); no Buffer/fd code in wrapper modules (grep gate) (D-08) |
| T-63-28 | Denial of service | sidecar exit contract | mitigate | No timers/handles/boot work in rustScan.ts/peScan.ts; `pnpm smoke:sidecar` |
</threat_model>
