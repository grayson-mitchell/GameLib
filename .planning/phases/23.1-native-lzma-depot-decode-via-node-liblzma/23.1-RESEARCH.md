# Phase 23.1: Native LZMA depot decode via node-liblzma - Research

**Researched:** 2026-08-17
**Domain:** Node.js native/WASM LZMA decoding, Node SEA (Single Executable Application) native-addon packaging
**Confidence:** MEDIUM-HIGH (the package recommendation was overturned by direct empirical testing this session; SEA-packaging-specific risk remains MEDIUM/unverified in the exact eval'd-worker context this project uses)

## Summary

This research **overturns the package choice in 23.1-CONTEXT.md**. `node-liblzma` — the
candidate CONTEXT.md recommended — was installed and tested directly against a real
`lzma_alone`-format stream (the exact container format Steam's VZ depot chunks use, and the
exact byte layout `decompress.ts`'s `decompressChunk()` already manually reconstructs:
5-byte LZMA1 properties + 8-byte little-endian uncompressed size, no `.xz` container). Its
entire public API surface — `unxz`/`unxzAsync`/`unxzSync`/`createUnxz`, on both the native
binding and the `/wasm`, `/inline` entry points — **rejects this format outright** with
`File format not recognized`. The library only speaks the modern `.xz` container (LZMA2 +
xz stream headers/index/CRC); it exposes no `.lzma`/`lzma_alone`/raw-LZMA1 decoder anywhere
in its documented or importable surface (confirmed by attempting a deep import into
`node-liblzma/wasm/bindings.js`, which the package's own `exports` map blocks). **This
package cannot decode a single Steam depot chunk as things stand.**

The older candidate CONTEXT.md dismissed as "stale, fallback-only" — **`lzma-native`
(addaleax, v8.0.6, last published 2022-01-18)** — was tested the same way and **works
correctly**: `lzma-native.createDecompressor()` and `createStream('aloneDecoder')` both
decoded a real `lzma_alone`-format stream byte-for-byte. A synthetic ~1MB-uncompressed
benchmark (order-of-magnitude matched to this project's own documented ~1MB max
compressed-chunk ceiling) measured **~47x faster decode** than this project's current
pure-JS `lzma` package on this dev machine (332 MB/s vs 7 MB/s) — directionally consistent
with, and higher than, CONTEXT.md's lzbench-derived 15-20x estimate. It also loaded and
decoded correctly inside a real `worker_threads.Worker` spawned from a file path (this
project's dev/Electron worker-spawn mode). All of this is **empirically VERIFIED this
session**, not carried forward from training data or a web search summary.

The staleness concern CONTEXT.md raised about `lzma-native` is real and independently
confirmed (`node-addon-api ^3.1.0`, `engines.node >=10.0.0`, no commits/releases since
2022) — but it did NOT block correct operation on this project's actual target Node
version (v26.2.0) and platform (darwin-arm64) in this session's tests; its N-API binding
loaded and ran without issue, which is expected given N-API's ABI-stability guarantee
across Node major versions.

**Primary technical risk is still Node SEA packaging of a native `.node` addon** — this
part of CONTEXT.md's risk assessment holds and is unaffected by the package swap: whichever
native package is chosen, its `.node` binary cannot be `esbuild`-bundled into the SEA blob
the way the pure-JS `lzma` package or the WASM-with-inline-base64 `zstddec` package already
are. Node's own documented mechanism — embed the `.node` file as a SEA asset, extract it to
a temp file at runtime via `getRawAsset()`, load via `process.dlopen()` — is well-documented
(confirmed via official Node.js docs) but **has never been exercised by this codebase**, and
this exact code area has already produced three separate SEA-packaging defects this debug
arc. A NEW, previously-unconsidered wrinkle this research surfaces: this project's worker
pool spawns its worker script via `new Worker(source, { eval: true })` reading an in-memory
string when running inside a packaged SEA sidecar (not `new Worker(path)`) — `require()`
of a native addon, and `require('node:sea')` itself, inside an **eval'd** worker context is
an untested combination with no directly-applicable precedent in this codebase or in Node's
own SEA native-addon documentation (which only shows the extract-to-tempfile pattern from a
real file-based entrypoint). This is the single highest-priority item for a Wave 1 spike.

**Primary recommendation:** Swap the candidate package from `node-liblzma` to `lzma-native`
(format-compatible, confirmed empirically). Treat this as an INSERTED urgent-work phase with
Wave 1 = a standalone spike proving (a) `lzma-native`'s native `.node` addon can be embedded
as a SEA asset and successfully `process.dlopen()`'d from inside this project's actual
`{ eval: true }` worker-spawn path (not just a normal file-based worker), and (b) real
throughput against an actual captured Steam depot chunk, before committing to full
`DecompressPool`/`decompressWorker.ts`/`buildSidecarSea.ts` integration in later waves.

## Architecture Patterns

### System Architecture Diagram

```
Steam CDN (network)
      │  encrypted chunk bytes (fetchChunk, unchanged)
      ▼
decompressPool.ts :: DecompressPool.decode()
      │  dispatches to an idle pooled worker_threads.Worker
      │  (or falls back inline on main thread if pool never
      │   initialized -- unchanged safety net)
      ▼
decompressWorker.ts (worker_threads isolate)
      │  calls decodeChunk() -> decompress.ts
      ▼
decompress.ts :: decompressChunk()
      │  magic === 'VZ' branch (THIS PHASE'S CHANGE):
      │    - currently: rebuild lzma_alone header, call
      │      pure-JS `lzma.decompress()` (~5-7 MB/s)
      │    - after this phase: same header rebuild, call
      │      `lzma-native`'s `createStream('aloneDecoder')`
      │      or `createDecompressor()` instead (~330+ MB/s,
      │      this session's synthetic benchmark)
      │  magic === 'VS' branch: unchanged (zstddec, WASM)
      │  magic === 'PK' branch: unchanged (node:zlib)
      ▼
sha1/size integrity gate (decodeChunk, unchanged)
      ▼
verified plaintext chunk -> caller (fetchChunk)


Build time (meta/buildSidecarSea.ts):
  esbuild --bundle (fully self-contained, no --packages=external)
      │
      ├─ decompress.ts's `import('lzma')` -- pure JS, bundles fine (unchanged)
      ├─ zstddec's WASM -- base64-inlined JS, bundles fine (unchanged)
      └─ lzma-native's require() of a computed prebuilds/<platform>-<arch>/*.node
         path (via node-gyp-build) -- CANNOT be esbuild-bundled (native binary,
         not JS). Needs: (1) a SEPARATE step embedding the .node file itself as
         a named SEA asset (sea-config.json `assets` field, mirroring the
         existing `decompressWorker.js` asset), (2) a runtime code path using
         `node:sea`'s `getRawAsset()` + `fs.writeFileSync()` to a temp path +
         `process.dlopen()` -- NOT `require()` -- to load it, inside the
         worker that needs it (see Common Pitfalls below for the eval'd-
         worker-context risk).
```

### Recommended integration point
Change is localized to **one function**: `decompressChunk()`'s `magic === 'VZ'` branch in
`src/backend/storeManagers/steam/depot/decompress.ts` (currently lines ~156-183). The
existing header-reconstruction logic (`props(5) + size(8, LE) + payload`) stays
byte-for-byte identical — only the final decode call changes from
`lzma.decompress(stream, callback)` to `lzma-native`'s equivalent. The `LzmaModule`
interface decompress.ts currently declares (`interface LzmaModule { decompress(...) }`)
will need either a second interface for the native module's stream-based API, or an adapter
function inside `decompress.ts` that wraps `lzma-native`'s stream API behind the existing
callback shape so `decodeChunk()`'s signature and every existing call site
(`decompressPool.ts`'s `inlineDecode()`, `decompressWorker.ts`'s `handleDecodeMessage()`,
every existing test in `decompressPool.test.ts`) needs the SMALLEST possible edit.

### Pattern: WASM-as-plain-JS sidesteps SEA native-addon risk entirely (already proven in this codebase)
**What:** `zstddec`'s `.wasm` payload is base64-encoded directly into a `.cjs`/`.js` file at
the package's OWN build time (via `microbundle`), so from `esbuild`'s perspective it is just
a large plain-JS string literal — no separate binary file, no `fetch()`/`fs.readFileSync()`
at runtime in the Node path (`WebAssembly.instantiate(Buffer.from(wasm, 'base64'), ...)`
directly).
**When to use:** This is why `buildSidecarSea.ts` needed ZERO special-case code for
`zstddec` despite it also being a compiled/binary decoder — confirmed by grepping
`buildSidecarSea.ts` and `esbuildWorkerBundleShared.ts` for any `zstddec` reference: there is
none.
**Relevance to this phase:** `node-liblzma` ships an exactly analogous `/inline` entry point
(`lib/lzma.inline.js`, importing a generated `WASM_BASE64` constant) that would have been
similarly zero-risk from a packaging standpoint — **this is why `node-liblzma` looked like
such a strong candidate in CONTEXT.md's original research** (a real, well-designed
SEA-friendly packaging story). The reason it is still rejected in this document is purely
the format-incompatibility finding above, not a packaging concern. If a future maintained
fork/version of `node-liblzma` adds legacy `.lzma`/alone-format support to its public API,
its `/inline` entry point should be re-evaluated as the LOWEST-risk path (no native `.node`
SEA asset/dlopen work needed at all) ahead of `lzma-native`'s native-addon route.

### Pattern: SEA native addon extraction (per official Node.js docs — NOT yet used in this codebase)
```javascript
// Source: https://nodejs.org/api/single-executable-applications.html
const fs = require('node:fs');
const os = require('node:os');
const path = require('node:path');
const { getRawAsset } = require('node:sea');

const addonPath = path.join(os.tmpdir(), 'myaddon.node');
fs.writeFileSync(addonPath, new Uint8Array(getRawAsset('myaddon.node')));
const myaddon = { exports: {} };
process.dlopen(myaddon, addonPath);
console.log(myaddon.exports);
fs.rmSync(addonPath);
```
Introduced in Node v19.7.0 (SEA `assets` field); `getRawAsset()` specifically landed in
v21.7.0/v20.12.0 — both comfortably below this project's `engines.node: >=22` floor, so no
engine bump is needed. `getRawAsset()` returns the RAW backing buffer (not a copy) — the
Node docs explicitly warn against writing to it; this codebase's existing `sea.getAsset()`
usage for `decompressWorker.js` (a text asset, copy-semantics) is a DIFFERENT API and not
directly reusable for this — the native-addon path needs `getRawAsset()`, a new call this
codebase has never made.

### Anti-Patterns to Avoid
- **Assuming `require()` works for a SEA-embedded `.node` file:** SEA's blob is read-only at
  runtime and Node's loader cannot `dlopen()` out of an in-memory buffer — the temp-file
  extraction step above is not optional, it is the only documented mechanism.
- **Reusing `decompressWorker.js`'s `sea.getAsset(key, 'utf8')` call shape for the native
  addon:** that call returns a UTF-8 STRING copy (correct for the existing worker JS-source
  asset); a `.node` binary needs `getRawAsset()` (no copy, returns an `ArrayBuffer`/typed
  array) written to disk as raw bytes, not decoded as text.
- **Testing only the dev/Electron `new Worker(path)` spawn mode and assuming the packaged
  SEA `new Worker(source, { eval: true })` mode behaves identically:** this session's
  worker_threads test (native addon `require()`d successfully inside a worker) used the
  FILE-PATH spawn mode only, matching dev/Electron behavior — it does NOT validate the
  `{ eval: true }` path the packaged SEA sidecar actually uses in production. See Common
  Pitfalls.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| LZMA1/lzma_alone decode | A custom N-API/WASM LZMA1 decoder from scratch | `lzma-native`'s `aloneDecoder`/`autoDecoder` | liblzma is a mature, security-reviewed C library; re-implementing LZMA1 decode correctness + memory safety is exactly the kind of "deceptively complex" problem this project should not take on mid-urgent-fix |
| Native `.node` extraction from a SEA blob | A hand-rolled asset-unpacking scheme | Node's own documented `sea.getRawAsset()` + `process.dlopen()` pattern | Already a first-class, versioned Node API; hand-rolling risks missing the "raw buffer, do not write to it" warning in the docs and the Linux-arm64-docker caveat below |

**Key insight:** The actual hand-rolled logic this codebase already owns and must NOT
duplicate is the `lzma_alone` HEADER RECONSTRUCTION in `decompressChunk()`'s VZ branch
(`props(5) + size(8, LE) + payload`) — that stays exactly as-is; only the function it hands
the resulting stream to changes.

## Common Pitfalls

### Pitfall 1: Package choice silently fails the exact use case (this session's core finding)
**What goes wrong:** Choosing a native LZMA library based on general reputation/npm
popularity/lzbench throughput numbers without confirming it decodes the SPECIFIC container
format the project actually receives.
**Why it happens:** Most modern "LZMA" npm packages have converged on `.xz`
(LZMA2-in-xz-container) as the only supported format, because that's what the `xz` CLI and
virtually all new tooling produces. Steam's own depot chunk format (`VZ`, via SteamKit's
`VZipUtil`) predates and never adopted `.xz` — it is raw legacy LZMA1 (`lzma_alone`), which
is exactly the format `.lzma` files (not `.xz` files) use.
**How to avoid:** ALWAYS test a candidate decoder against a real (or faithfully
reconstructed, as this session did) sample of the project's actual byte format before
committing to it in a plan — this cannot be verified from documentation/marketing copy
alone; `node-liblzma`'s own README and npm description do not mention this limitation.
**Warning signs:** A decoder's docs mention only `.xz`/`xz-utils` compatibility, or only
list `unxz`/`xz` as its function names (as opposed to separately naming `alone`/`legacy`
variants) — this is the naming tell that legacy `.lzma`/LZMA1 support is likely absent.

### Pitfall 2: `worker_threads` + `{ eval: true }` + native addon `require()` is an untested combination
**What goes wrong:** This project's SEA-packaged worker pool spawns its worker via
`new Worker(source, { eval: true })` (source = an in-memory string read from a SEA asset),
NOT `new Worker(path)`. A native addon's `require()`/`process.dlopen()` inside a worker
spawned this way has no confirmed-working precedent in this codebase or in Node's own SEA
native-addon documentation (which demonstrates the pattern from a real main-thread SEA entry
script, not an eval'd worker). This is directly the same CLASS of defect as this debug arc's
prior finding (`dev-mode-decompress-worker-electron-hook`): a worker_threads isolate has its
own module registry and does not automatically inherit assumptions that hold on the main
thread.
**Why it happens:** SEA + worker_threads + native addons is a three-way intersection Node's
own docs do not explicitly cover; each piece is individually documented, their combination
is not.
**How to avoid:** Wave 1's spike MUST test the exact production shape: extract the `.node`
asset (via `getRawAsset()`) and `process.dlopen()` it FROM INSIDE a worker spawned with
`new Worker(source, { eval: true })` inside an actual compiled SEA binary — not from the
main thread, and not from a `new Worker(path)` dev-mode spawn (this session's own
worker_threads test used the latter and is NOT sufficient evidence this pattern works in
production).
**Warning signs:** A spike that only tests native-addon loading on the main thread, or only
in dev mode (`pnpm tauri:dev`, never a real compiled `gamelib-sidecar-<triple>` binary), has
not actually de-risked this phase's primary technical risk.

### Pitfall 3: Linux arm64 Docker build hosts corrupt the injected SEA binary
**What goes wrong:** Per official Node.js docs: if the SEA binary is produced by `postject`
running inside a Linux arm64 Docker container, the resulting ELF binary lacks the correct
hash table for native addons and crashes on `process.dlopen()` — even though the SAME build
succeeds and the resulting binary otherwise runs fine for everything that doesn't
`dlopen()`.
**Why it happens:** A known `postject`/ELF toolchain limitation
(nodejs/postject#105), not something this project's own build script can work around.
**How to avoid:** Confirm the CI matrix's `linux-arm64`-if-any runner (check
`.github/workflows/release-tauri.yml`) is a bare-metal/VM runner, not a containerized one,
before shipping this on Linux ARM. This project's stated target triples in the phase
description are `linux-x64` (not arm64) — flag this as a non-issue for THIS phase's stated
scope, but record it so a future Linux-arm64 target doesn't silently inherit a broken build.
**Warning signs:** A Linux ARM SEA sidecar that starts and runs fine until the first native
decode attempt, which crashes the whole process (not a caught JS error — `dlopen()` failures
of this kind are typically a hard native crash).

### Pitfall 4 (pre-existing, still applies): esbuild cannot bundle a computed native `require()`
**What goes wrong:** `node-gyp-build` (both `lzma-native`'s and `node-liblzma`'s native-load
mechanism) resolves its target `.node` file via a runtime-computed path
(`prebuilds/${platform}-${arch}/${name}.node`) — the exact same class of problem
`buildSidecarSea.ts`'s Rule-1 fix 4 already solved for `steam-user`'s `cdn_compression.js`
and the old `lzma` package's own computed `require()`, via `pnpm patch`
(`patches/steam-user.patch`, `patches/lzma.patch`, wired through
`pnpm-workspace.yaml`'s `patchedDependencies` field — confirmed this session, NOT
`package.json`).
**Why it happens:** esbuild only statically resolves LITERAL string import/require
specifiers; a template-literal/computed path is invisible to its bundler at build time, and
even if it weren't, esbuild cannot "bundle" a native binary file into JS output anyway.
**How to avoid:** This is NOT a "patch the computed require" problem this time (unlike the
prior two fixes) — a native `.node` file must physically exist on disk to be `dlopen()`'d;
there is no way to inline it as JS text the way the two prior patches did. The correct fix
is the SEA-asset-embedding + `process.dlopen()` mechanism (Pattern above), which is a
DIFFERENT mechanism class from the prior two `pnpm patch` fixes — do not attempt to extend
`patches/lzma.patch`'s approach to this package.
**Warning signs:** `ERR_UNKNOWN_BUILTIN_MODULE` or a `Cannot find module '.../prebuilds/...'`
crash at SEA sidecar startup — the exact symptom class `buildSidecarSea.ts`'s file header
already documents for the OLD `lzma`/`steam-user` computed-require bugs; do not assume it's
the same fix.

## Code Examples

### Empirically verified this session — `lzma-native` decodes Steam's chunk format correctly
```javascript
// Source: this session's direct execution (not from any doc) --
// node-liblzma@5.1.1 and lzma-native@8.0.6 installed and tested in a
// scratchpad directory against a real lzma_alone-format stream produced by
// this project's own `lzma@2.3.2` package (byte-identical header shape to
// Steam's VZ chunks: props(5) + uncompressed-size(8, LE), no xz container).
const lzmaNative = require('lzma-native')

const decoder = lzmaNative.createStream('aloneDecoder') // or createDecompressor()
const chunks = []
decoder.on('data', (d) => chunks.push(d))
decoder.on('end', () => {
  const out = Buffer.concat(chunks) // byte-exact match confirmed this session
})
decoder.on('error', (e) => { /* ... */ })
decoder.end(compressedLzmaAloneBuffer)

// node-liblzma, by contrast, on the SAME input:
const nodeLiblzma = require('node-liblzma')
nodeLiblzma.unxz(compressedLzmaAloneBuffer, (err, result) => {
  // err.message === 'File format not recognized' -- confirmed this session
})
```

## Open Questions

1. **Does `process.dlopen()` succeed when called from a worker spawned via `new Worker(source, { eval: true })` inside a real compiled SEA binary?**
   - What we know: The mechanism works from a normal SEA main-thread entry (Node docs) and `lzma-native`'s native addon loads fine inside a normally-file-path-spawned `worker_threads.Worker` (this session's test, dev-mode shape).
   - What's unclear: Whether `require('node:sea')`/`getRawAsset()`/`process.dlopen()` behave identically when the worker's own entry script is itself an eval'd string rather than a file, especially regarding relative-path resolution for the temp file `dlopen()` target.
   - Recommendation: This is Wave 1's spike, not something answerable from documentation — must be tested against a real compiled `gamelib-sidecar-<triple>` SEA binary.

2. **What is `lzma-native`'s actual decode throughput against a REAL captured Steam depot LZMA chunk, on each of the project's real target triples (not just this session's synthetic single-machine test)?**
   - What we know: ~47x speedup on a synthetic payload, darwin-arm64 only.
   - What's unclear: Real depot chunk entropy/structure may behave differently; linux-x64/win32-x64 numbers are completely unmeasured.
   - Recommendation: Also Wave 1's spike scope, per CONTEXT.md's own original recommendation (unchanged by this document).

3. **Is there a maintained alternative to both `node-liblzma` and `lzma-native` that supports legacy `.lzma`/LZMA1 format AND is actively published?**
   - What we know: `node-liblzma` (actively maintained, wrong format) and `lzma-native` (right format, stale since 2022) are the two candidates evaluated this session.
   - What's unclear: Whether a newer WASM-only LZMA1-capable library exists that neither CONTEXT.md's original research nor this session's follow-up surfaced.
   - Recommendation: A 15-minute registry search before Wave 1 begins is cheap insurance; do not block the phase on this if nothing turns up quickly — `lzma-native` is a working, confirmed-correct fallback regardless.

## Security Domain

### Applicable ASVS Categories

| ASVS Category | Applies | Standard Control |
|---------------|---------|-----------------|
| V5 Input Validation | yes | Unchanged — `decodeChunk()`'s existing sha1/size integrity gate (already present, applies identically regardless of which decoder produced the bytes) continues to reject any chunk whose decompressed output doesn't match the manifest-declared hash/size, so a malicious/corrupted chunk from either decoder path is still caught post-decode |
| V6 Cryptography | no | Out of scope — decryption (`steamDecrypt`) happens before this phase's decode step and is unchanged |
| V14 Configuration | yes | Native addon supply-chain: `lzma-native`'s prebuilt binaries are fetched via the standard npm registry install (no separate download step, confirmed no `postinstall` script this session) — no new network-fetch-at-install-time attack surface beyond what `pnpm install` already trusts for every other dependency |

### Known Threat Patterns for this stack

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Malformed/malicious LZMA1 stream causing a native-code memory-safety issue (buffer overflow in liblzma's C implementation, more consequential than a pure-JS decoder's equivalent failure mode) | Denial of Service / Tampering | liblzma is a mature, widely-audited C library (used by every major Linux distro's `.lzma`/`.xz` tooling) — this is an ACCEPTED risk shared with `zstddec`'s existing WASM decoder and the SAME class of risk this project already accepted when it added `zstddec` for VS chunks; the existing sha1/size post-decode gate does not protect against a crash DURING decode, only against WRONG output surviving decode. No new mitigation needed beyond what upstream liblzma already provides — do not attempt to sandbox decode further; this project already trusts pure-JS `lzma`'s decode path identically today. |
| Native `.node` addon supply-chain compromise (a malicious update to `lzma-native` shipping a backdoored prebuilt binary) | Tampering | Pin the exact version (`lzma-native@8.0.6`, not a caret range initially, given the staleness/small-maintainer-surface risk this document already flags) and verify via `pnpm-lock.yaml`'s integrity hash on every install, matching this project's existing dependency-pinning discipline for `steam-user`/`lzma` (both patched via `pnpm.patchedDependencies`) |
