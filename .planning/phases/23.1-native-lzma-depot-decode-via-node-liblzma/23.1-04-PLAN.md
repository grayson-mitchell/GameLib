<objective>
Replace the pure-JS LZMA decode path with `lzma-native` for Steam VZ depot chunks, via
a single loader that both the pooled workers and `DecompressPool`'s inline main-thread
fallback share, and that degrades to the existing pure-JS `lzma` package — loudly —
whenever the native binding cannot be loaded.

Purpose: this is the change the whole phase exists for. CONTEXT.md's live measurement
established that network fetch is flat at ~150-280ms/chunk and decode at ~5-7 MB/s per
thread is the binding constraint; RESEARCH.md measured `lzma-native` at ~332 MB/s on a
synthetic payload and 23.1-01's spike replaced that with a real-chunk multiplier.

Design decision to be explicit about: the planning brief suggested extending
`decompressPool.ts`'s `resolveWorkerSpec()` to resolve the native binary. This plan
deliberately does NOT do that, and the reason belongs in the code comments. A native
addon must be `dlopen()`ed inside the isolate that calls it — a binding loaded on the
sidecar's main thread cannot be transferred to a `worker_threads` isolate, so resolving
it in `resolveWorkerSpec()` (which runs on the main thread and only produces the
worker's source string) would help nothing. The addon is therefore resolved inside each
worker via plan 23.1-03's `--alias:node-gyp-build` shim, and `resolveWorkerSpec()` is
left byte-for-byte untouched. `DecompressPool`'s own main-thread `inlineDecode()` path
gets the native decoder through the same shared loader.

Output: `lzmaLoader.ts`, its ambient type declaration, and three small call-site edits.
`decompressChunk()`'s VZ container parsing is not touched — RESEARCH.md is explicit
that the `props(5) + size(8, LE) + payload` header reconstruction stays byte-for-byte
identical and only the final decode call changes, which the `LzmaModule` adapter shape
makes a zero-line change in that function.

This plan ASSUMES 23.1-01's verdict was `VALIDATED` with go/no-go `proceed`. If not,
STOP and report. Runs in parallel with plan 23.1-03 (disjoint file sets).
</objective>
