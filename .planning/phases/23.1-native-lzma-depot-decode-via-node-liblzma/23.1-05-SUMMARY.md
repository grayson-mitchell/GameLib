# Phase 23.1 Plan 05: Live-Hardware Re-Verification Summary

**Two real, previously-masked defects fixed and byte/log-proven in a cold-built SEA binary (a worker-thread `backend/logger` crash that collapsed the whole pool to inline decode, and a `dir`-based identity guard that rejected the legitimate SEA-bundled `node-gyp-build` call) -- but native LZMA decode ships GATED OFF by default, because verifying those fixes surfaced a third, deeper, still-unresolved defect: a real-sized chunk decode hangs inside a genuinely compiled SEA binary, confirmed CODEC-INDEPENDENT (reproduces via the pure-JS path too, not just native).**

## Performance

- **Duration:** ~5h across three coordinator-directed live-hardware re-verification rounds (this plan's Task 2 checkpoint was reopened twice by new live-hardware findings before reaching this closure)
- **Rounds:** 3 (each found a genuinely different defect, each only reachable after the prior round's fix)
- **Files modified:** 11 production/build files, 5 new/modified test files, 1 new debug investigation file

## Accomplishments

- **Task 1 (unchanged across all three rounds):** confirmed, via a real cold `rm -rf build && pnpm build:sidecar-sea`, that the native `lzma-native` addon's bytes are physically present inside the compiled SEA sidecar binary at a specific, non-zero byte offset (`Buffer.indexOf`, not string-tool inference). Full suite green throughout (288-292/288-292 suites depending on round, modulo the one pre-existing, documented, unrelated `depot.finalize.test.ts` OOM carve-out this whole phase has consistently excluded).
- **Round 1 fix (worker-thread logger crash):** `decompressWorker.ts` now calls `backend/logger`'s `initHeadless(true)` as the first statement inside its own `if (parentPort)` block -- a `worker_threads.Worker` gets a fresh module registry that never runs the sidecar main thread's own `initHeadless()` call, so the FIRST `logInfo`/`logWarning` call inside a live worker (fired by `lzmaLoader.ts`'s one-time decoder log line) previously threw `Cannot read properties of undefined (reading 'logWarning')`, and `DecompressPool.init()`'s catch-all treated the whole worker as failed to spawn -- collapsing the ENTIRE pool to single-threaded inline decode for the whole download run, silently (the install still completed, just slowly). Also found and fixed, while implementing this: a genuine multi-writer log-corruption race (`LogWriter` gained a `skipInitialArchive` constructor param) that the coordinator's own report did not mention -- without it, every one of up to `DECOMPRESS_POOL_MAX_WORKERS` independent `LogWriter` instances would have tried to "rotate" the SAME live, actively-written `gamelib.log` on its own first log write. Proven via a REAL esbuild-compiled worker spawn test (`decompressWorkerRealBuild.test.ts`), RED before the fix / GREEN after, run inside a genuinely separate `child_process` with an explicit `HOME` override (a `worker_threads.Worker`'s own `env` option does NOT redirect the native `os.homedir()` call -- verified empirically -- so a naive test would have written to the developer's real `~/Library/Logs/GameLib/gamelib.log`, the exact class of defect this repo's `jest.setupContainment.ts` already exists to prevent, via a route that mechanism cannot reach).
- **Round 2 fix (identity-guard rejection):** a real packaged SEA install (built via `pnpm exec tauri build --bundles app`, confirmed genuinely running the SEA bundle, not the dev bundle) still failed with `[lzmaNativeBinding] refusing to resolve a native binding for directory "."`. Root cause: `lzmaNativeBinding.ts`'s `dirBelongsToLzmaNative(dir)` guard rejected the legitimate call because `__dirname` collapses to `"."` once esbuild bundles `lzma-native`'s `index.js` into the SEA output (an eval'd worker has no backing file) -- exactly what spike 023's own reference implementation had already predicted. The guard threw BEFORE resolution ever reached the SEA-asset-loading branch Task 1's byte-offset proof had already confirmed the addon shipped correctly for. Fixed by reusing spike 023's own proven mechanism (a build-time-generated data module, `meta/esbuildWorkerBundleShared.ts`'s `writeLzmaNativeResolvedPaths()`) instead of re-deriving identity from the runtime `dir` value, which is structurally incapable of distinguishing callers once genuinely bundled (confirmed empirically: the SEA build collapsed `dir` to `"."`, a real dev-mode build separately collapsed it to a DIFFERENT wrong value, `.../build/main` -- neither meaningful). The T-23.1-03-02 security property is relocated to build time (`assertNodeGypBuildSingleConsumer()`, which scans the real, unbundled dependency tree), covered by a known-bad-input regression test (a synthetic second `node-gyp-build` consumer is correctly detected). Verified in a real cold SEA binary via the `GAMELIB_SIDECAR_SELFTEST=decompress-pool` self-test harness: `nativeWorkers` matched pool size for the first time (previously always 0).
- **Round 3 finding + mitigation (real-chunk decode hang, still open):** verifying round 2's fix in the same real self-test harness surfaced a third, deeper defect: `SELFTEST decode=fail code=decompress_pool_timeout message=decompress task 0 timed out` -- decoding a real-sized (64KB) chunk through the now-correctly-resolved native binding hangs inside a genuinely compiled, postject-injected SEA binary. Extensive isolated reproduction attempts (six independent configurations, all outside a genuinely compiled SEA binary) all succeeded instead of reproducing it -- see the new debug file for the full list. Diagnostic instrumentation showed the worker's own message handler is never entered for the real request at all. At the coordinator/human-operator's explicit direction, **native decode is now gated OFF by default in shipping code** (`NATIVE_LZMA_DECODE_ENABLED = false`, `lzmaLoader.ts`) rather than continuing to debug this live. **While implementing and verifying that gate, a critical correction was found**: the hang is NOT native-specific -- with the gate confirmed active (`nativeWorkers:0`), the exact same real-sized decode still times out via the pure-JS path, reproduced twice independently. This means the gate closes the narrower "native resolves, then hangs" case and proves `lzma-native`'s own binding resolution is now correct (a real, separate, valuable deliverable) -- it does **not** make a packaged SEA install's worker-pool decode path safe end-to-end. Recorded in full in `.planning/debug/sea-native-lzma-real-chunk-decode-hang.md`, including a specific, high-priority open question: whether `DecompressPool` ever gives up and falls back to inline decode after repeated same-task timeouts, or retries indefinitely (not yet determined -- a materially different and more severe risk than "slow but completes").
