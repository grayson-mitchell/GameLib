# Phase 23.1: Native LZMA depot decode via lzma-native - Pattern Map

**Mapped:** 2026-08-17
**Files analyzed:** 6 (3 modified backend files, 1 modified build script, 2 modified test files) + 1 new spike artifact
**Analogs found:** 6 / 6 — every target file already exists and IS its own best analog (this phase modifies existing, well-documented integration points; it does not introduce a new file class)

**Package correction carried forward from RESEARCH.md:** every excerpt below refers to the
LZMA decode call as `lzma-native` (native `.node` addon, `createStream('aloneDecoder')` /
`createDecompressor()`), NOT `node-liblzma` (CONTEXT.md's original, now-rejected pick per
RESEARCH.md's format-incompatibility finding). The `LzmaModule` interface's `.decompress()`
callback shape is what all call sites currently expect — the planner must decide whether to
keep that shape (wrap `lzma-native`'s stream API in an adapter) or thread a second interface
through every call site; RESEARCH.md recommends the adapter as the smallest-diff option.

### `src/backend/storeManagers/steam/depot/decompress.ts` (service, transform)

**Analog:** itself — the `VS` (zstd) branch is the closest sibling pattern for "swap one
container-type's decoder implementation without touching dispatch logic."

**Imports pattern** (lines 10-15):
```typescript
import { createHash } from 'node:crypto'
import { steamDecrypt } from './crypto'
import { HostHealthTracker } from './hostHealth'
import { CdnAuthTokenCache } from './cdnAuth'
import { InflightLimiter } from './inflightLimiter'

```
A new native-addon-facing import (if the adapter needs one) should follow this same flat,
relative/aliased style — no barrel file exists in this directory.

**Current interface this phase's decoder must satisfy or adapt to** (lines 17-23):
```typescript
/** Minimal surface of the `lzma` npm package this module depends on. */
export interface LzmaModule {
  decompress(
    input: Buffer,
    callback: (result: number[] | Buffer | string, error?: Error) => void
  ): void
}
```

**Core VZ branch — exact code to change** (lines 154-182, `decompressChunk()`):
```typescript
export async function decompressChunk(
  buf: Buffer,
  lzma: LzmaModule,
  cbOriginal?: number | string
): Promise<Buffer> {
  const magic = buf.subarray(0, 2).toString('latin1')

  if (magic === 'VZ') {
    if (buf.subarray(-2).toString('latin1') !== 'zv') {
      throw new ChunkDecodeError(
        'bad_footer_magic',
        'VZ chunk: bad footer magic'
      )
    }
    const props = buf.subarray(7, 12)
    const payload = buf.subarray(12, buf.length - 10)
    const outSize = buf.readUInt32LE(buf.length - 6)

    // Rebuild an lzma_alone header: props(5) + uncompressed size(8, LE).
    const size = Buffer.alloc(8)
    size.writeUInt32LE(outSize, 0)
    const stream = Buffer.concat([props, size, payload])

    return await new Promise<Buffer>((resolve, reject) =>
      lzma.decompress(stream, (result, err) =>
        err ? reject(err) : resolve(Buffer.from(result as number[] | Buffer))
      )
    )
  }
  // ... VS (zstd) and PK (zlib) branches unchanged, see below
```
**RESEARCH.md is explicit that the `props(5) + size(8, LE) + payload` header-reconstruction
above stays byte-for-byte identical — only the final `lzma.decompress(stream, callback)` call
changes.** Do not touch anything before that line in the `VZ` branch.

**Sibling pattern for "swap decoder without touching dispatch" — the `VS`/zstd branch**
(lines 184-238, especially the dynamic-import + decode call at 233-237):
```typescript
    const { ZSTDDecoder } =
      (await import('zstddec')) as unknown as ZstdDecoderModule
    const decoder = new ZSTDDecoder()
    await decoder.init()
    return Buffer.from(decoder.decode(compressed, decompressedSize))
```
This is the model for "a WASM/native decoder lazily imported inline, wrapped to return a
`Buffer` synchronously to the caller" — but note RESEARCH.md's finding that `zstddec` needed
**zero** SEA-packaging special-casing because its WASM payload is base64-inlined JS at ITS OWN
build time, unlike `lzma-native`'s real `.node` binary. Do not assume this branch's simplicity
transfers to the native-addon path — it doesn't (see `meta/buildSidecarSea.ts` section below).

**Error handling pattern** (`ChunkDecodeError`, lines 61-88): every decode-stage throw site
tags a stable `.code` (`bad_footer_magic`, `unknown_container`, `sha1_mismatch`,
`size_mismatch`, `decode_failed`) so failures survive the `worker_threads` postMessage
boundary distinguishably. A native-addon load/dlopen failure inside the VZ branch should throw
a `ChunkDecodeError` with a new distinct code (e.g. `native_lzma_load_failed`) rather than a
bare `Error`, to preserve this discipline — consistent with the file's own stated rationale at
lines 32-60.

**Integrity gate downstream (unchanged, do not duplicate):** `decodeChunk()` (line 344) applies
sha1/size verification identically regardless of which decoder produced the bytes — this is
explicitly called out in RESEARCH.md's ASVS V5 analysis as the existing control that already
covers a malicious/corrupted native-addon-decoded chunk.

### `src/backend/storeManagers/steam/depot/decompressWorker.ts` (worker entry point, event-driven)

**Analog:** itself — `getLzma()` is the single function whose body changes; `handleDecodeMessage()` stays untouched.

**Full lazy-load pattern to change** (lines 58-71):
```typescript
let lzmaPromise: Promise<LzmaModule> | undefined

/** Lazily loads the pure-JS `lzma` codec once per worker (module-load-scoped
 *  cache), mirroring downloadDepotFiles' own once-per-install load pattern. */
function getLzma(): Promise<LzmaModule> {
  if (!lzmaPromise) {
    lzmaPromise = import('lzma').then(
      (mod) =>
        ((mod as { default?: LzmaModule }).default ??
          mod) as unknown as LzmaModule
    )
  }
  return lzmaPromise
}
```
If the native addon needs a different load mechanism (`getRawAsset()` + temp-file write +
`process.dlopen()` instead of a plain `import()`), that logic belongs INSIDE this function
(same call-site contract: caller awaits a `Promise<LzmaModule>`-shaped adapter) — this file's
own doc comment (lines 11-30) already documents the general class of "this worker's isolate
does not inherit the main thread's module-loading assumptions" risk that a native-addon
`dlopen()` inside an `{ eval: true }`-spawned worker inherits directly (RESEARCH.md's Pitfall
2 / Open Question 1).

**Call site, unchanged** (lines 79-90, `handleDecodeMessage()`):
```typescript
export async function handleDecodeMessage(
  msg: DecompressWorkerRequest
): Promise<DecompressWorkerResponse> {
  try {
    const lzma = await getLzma()
    const result = await decodeChunk(
      Buffer.from(msg.encrypted),
      Buffer.from(msg.key),
      msg.expectedSha,
      msg.cbOriginal,
      lzma
    )
```
No signature change needed if `getLzma()`'s return type stays `LzmaModule`-shaped.

**Error surfacing pattern to reuse** (lines 99-120): the existing `catch` block already
threads a `.code` field across the `postMessage` boundary — a native-load failure surfaced as
a `ChunkDecodeError` with a new `.code` (see decompress.ts section above) will automatically
flow through this unchanged.

### `src/backend/storeManagers/steam/depot/decompressPool.ts` (worker-pool orchestration, event-driven + fallback)

**Analog:** itself — `resolveWorkerSpec()` and `init()`'s catch-and-fallback block are the
direct architectural precedent for "how does this codebase already solve embedding a
non-JS-literal asset into a SEA binary and safely falling back if it's unavailable."

**`WorkerSpec` type + asset-key constant** (lines 39-46):
```typescript
type WorkerSpec = { kind: 'path'; value: string } | { kind: 'source'; value: string }
const SEA_WORKER_ASSET_KEY = 'decompressWorker.js'
```

**Resolution precedence pattern** (lines 290-322, `resolveWorkerSpec()`) — three-tier
precedence (test override → SEA asset → dev/Electron file path), each guarded, each falling
through safely:
```typescript
  private resolveWorkerSpec(): WorkerSpec {
    if (this.workerSpecCache) return this.workerSpecCache

    if (this.workerPathOverride) {
      this.workerSpecCache = { kind: 'path', value: this.workerPathOverride }
      return this.workerSpecCache
    }

    try {
      // node:sea is a Node builtin; a guarded runtime require (not a
      // relative/alias path) is the deliberate mechanism here, mirroring
      // humbleFlowRegistration.ts's isPackagedSidecar(), not an oversight.
      // eslint-disable-next-line @typescript-eslint/no-require-imports
      const nodeSea = require('node:sea') as {
        isSea: () => boolean
        getAsset: (key: string, encoding: string) => string
      }
      if (nodeSea.isSea()) {
        const source = nodeSea.getAsset(SEA_WORKER_ASSET_KEY, 'utf8')
        this.workerSpecCache = { kind: 'source', value: source }
        return this.workerSpecCache
      }
    } catch {
      // node:sea unavailable (older/dev Node), or getAsset() threw (asset
      // missing from this blob) -- fall through to the path spec below.
    }

    this.workerSpecCache = {
      kind: 'path',
      value: path.join(__dirname, 'decompressWorker.js')
    }
    return this.workerSpecCache
  }
```
**IMPORTANT DIFFERENCE for this phase:** this pattern uses `getAsset(key, 'utf8')` (text-copy
semantics, correct for JS source). RESEARCH.md is explicit that a `.node` binary needs
`getRawAsset()` instead (no-copy, returns a raw buffer, must be written to a temp file before
`process.dlopen()` — NOT `require()`d, NOT `eval`'d). Do not reuse `getAsset()`'s call shape
for the native addon; only the three-tier PRECEDENCE structure (override → SEA → fallback)
transfers directly.

**Fallback-and-log pattern** (`init()`, lines 355-387): every initialization failure sets
`inlineFallback = true`, tears down partially-spawned workers, and logs a structured warning
via `logWarning([...], LogPrefix.Steam)` — never throws out of `init()`. A native-addon
dlopen failure should degrade the SAME way: fall back to the pure-JS `lzma` decode path (which
RESEARCH.md's "Environment Availability" table confirms remains the safety net), not crash the
pool.

**`isPackagedSidecar()` sibling pattern** (`src/backend/sidecar/humbleFlowRegistration.ts`,
lines 159-166) — the SAME guarded `require('node:sea')` shape used elsewhere in this codebase,
confirming `resolveWorkerSpec()`'s approach is the established convention, not a one-off:
```typescript
export function isPackagedSidecar(): boolean {

    // eslint-disable-next-line @typescript-eslint/no-var-requires -- node:sea
    const nodeSea = require('node:sea') as { isSea: () => boolean }
    return nodeSea.isSea()
  } catch {
    ...
```

### `meta/buildSidecarSea.ts` (build tooling, batch asset embedding)

**Analog:** itself — `bundleWorkerForSea()` / `buildSeaConfig()` (the "Rule-1 fix 6" JS-asset
embedding this project already shipped for `decompressWorker.js`) is the direct architectural
precedent, but RESEARCH.md flags a REAL mechanism difference: a `.node` binary cannot be
esbuild-bundled at all (it's not JS), so the "bundle first, then embed the bundle path as an
asset" two-step (`bundleWorkerForSea()` → `buildSeaConfig()`'s `assets` map) only PARTIALLY
transfers — the native `.node` file must be copied/embedded directly (e.g. from
`node_modules/lzma-native/prebuilds/<platform>-<arch>/lzma_native.node`), not produced by an
esbuild step.

**Path constants pattern to extend** (lines 169-177):
```typescript
const SEA_WORKER_BUNDLE_PATH = join(
  'build',
  'main',
  'decompressWorker-sea-bundle.js'
)
/** SEA asset key both this build script and decompressPool.ts's runtime
 *  `sea.getAsset()` call must agree on verbatim -- exported so a test can
 *  assert the two sides never drift apart. */
export const SEA_WORKER_ASSET_KEY = 'decompressWorker.js'
```
A new `LZMA_NATIVE_ASSET_KEY` constant (e.g. `'lzma_native.node'`) exported the same way, plus
a resolved source path (NOT a bundle-output path — the raw prebuilt binary path from
`node_modules/lzma-native/prebuilds/...`), is the direct extension point.

**`buildSeaConfig()` — the asset-map wiring to extend** (lines 515-527):
```typescript
export function buildSeaConfig(): {
  main: string
  output: string
  disableExperimentalSEAWarning: boolean
  assets: Record<string, string>
} {
  return {
    main: SEA_BUNDLE_PATH,
    output: SEA_BLOB_PATH,
    disableExperimentalSEAWarning: true,
    assets: { [SEA_WORKER_ASSET_KEY]: SEA_WORKER_BUNDLE_PATH }

```
Adding a second `assets` entry (`[LZMA_NATIVE_ASSET_KEY]: <resolved .node path>`) is the
minimal-diff extension — `node --experimental-sea-config` embeds ANY file listed in `assets`,
JS or binary, identically; this is confirmed by RESEARCH.md's Architecture Patterns section
("a SEPARATE step embedding the .node file itself as a named SEA asset (sea-config.json
`assets` field, mirroring the existing `decompressWorker.js` asset)").

**Compile-gate discipline to mirror** (`bundleWorkerForSea()`, lines 585-604 — the pattern for
"guard entry-point-missing, guard exit-code!=0, guard exit-0-but-no-output-file", ALL throwing
`COMPILE GATE FAILED (D-06): ...` prefixed errors):
```typescript
async function bundleWorkerForSea(): Promise<void> {
  if (!existsSync(DECOMPRESS_WORKER_ENTRY_PATH)) {
    throw new Error(
      `Missing decompress worker entry point at ${DECOMPRESS_WORKER_ENTRY_PATH}`
    )
  }
  await mkdir(join('build', 'main'), { recursive: true })
  const esbuildArgv = buildWorkerEsbuildArgv()
  const result = await spawnArgv(esbuildArgv.command, esbuildArgv.args)
  if (result.code !== 0) {
    throw new Error(
      `COMPILE GATE FAILED (D-06): esbuild decompress-worker SEA bundle exited ${result.code}:\n${result.stderr}`
    )
  }
  if (!existsSync(SEA_WORKER_BUNDLE_PATH)) {
    throw new Error(
      `COMPILE GATE FAILED (D-06): esbuild exited 0 but no worker bundle was emitted at ${SEA_WORKER_BUNDLE_PATH}`
    )
  }
}
```
A new step verifying the `.node` prebuilt actually EXISTS on disk for the resolved target
triple before `writeSeaConfig()` runs (rather than an esbuild invocation — there's nothing to
compile, just a file-existence + arch/triple match check) should follow this exact
throw-loud-on-any-gap discipline, and be sequenced into `main()` alongside the existing steps
(lines 890-896):
```typescript
  await bundleForSea()
  await bundleWorkerForSea()
  await writeSeaConfig()
  await generateSeaBlob()
  const outputPath = await copyNodeBinary(triple)
  await injectBlob(outputPath, triple)
  await verifyBinaryArch(outputPath, triple)
```

**Prior-art for "a native dependency's computed require() breaks esbuild bundling" — do NOT
reapply this fix, it's the WRONG mechanism class for this phase** (file header, lines 57-71,
and `patches/lzma.patch`): the existing `pnpm.patchedDependencies` fix
(`patches/lzma.patch`, `patches/steam-user.patch`) replaced a runtime-computed `require()`
specifier with a static literal so esbuild could bundle it as JS. RESEARCH.md's Pitfall 4 is
explicit that this does NOT apply to `lzma-native`'s `.node` binary — a native addon must
physically exist on disk to be `dlopen()`'d; there is no way to inline it as JS text. The
correct mechanism is the SEA-asset-embedding pattern above, a DIFFERENT class of fix.

**`--alias`/`--inject` esbuild flags to preserve unmodified** (`meta/esbuildWorkerBundleShared.ts`, `seaEsbuildFlags()`, referenced at `buildSidecarSea.ts` lines 318-353):
```typescript
'--alias:electron=./src/backend/sidecar/electronStub.ts',
'--alias:i18next-fs-backend=i18next-fs-backend/cjs',
'--inject:./meta/sidecarSeaFsShim.ts',
```
These flags are shared verbatim between `buildEsbuildArgv()` (main sidecar bundle) and
`buildWorkerEsbuildArgv()` (worker bundle) via `seaEsbuildFlags()` — any new
`decompressWorker.ts` code path touching `lzma-native` must still pass through this alias set
unchanged, since the worker's import chain (`decompress.ts` → `backend/logger` → ... → the
electron stub) is unaffected by the LZMA package swap.

## Shared Patterns

### `require('node:sea')` guarded-access pattern
**Source:** `src/backend/storeManagers/steam/depot/decompressPool.ts` lines 298-315,
`src/backend/sidecar/humbleFlowRegistration.ts` lines 159-166
**Apply to:** Any new code in `decompressPool.ts`/`decompressWorker.ts` that needs to detect
"am I running inside a compiled SEA binary" before choosing a native-addon load strategy.
```typescript

  // eslint-disable-next-line @typescript-eslint/no-require-imports
  const nodeSea = require('node:sea') as { isSea: () => boolean; ... }
  if (nodeSea.isSea()) { /* SEA path */ }
} catch {
  // node:sea unavailable (older/dev Node) -- fall through to dev-mode path

```

### Inline-fallback-on-init-failure discipline
**Source:** `decompressPool.ts` `init()` (lines 355-387), RESEARCH.md's "Environment
Availability" table
**Apply to:** Any new native-addon load path in `decompressPool.ts`/`decompressWorker.ts`.
Never let a native-addon-load failure crash the pool or the worker — always fall back to the
existing pure-JS `lzma` decode path (already the accepted safety net for worker-pool-spawn
failure) and log via `logWarning([...], LogPrefix.Steam)`, never `console.*` directly.

### `ChunkDecodeError` stable `.code` tagging
**Source:** `decompress.ts` lines 61-88
**Apply to:** Any new throw site in the VZ branch or its adapter layer. Use a distinct,
descriptive `.code` string (not a bare `Error`) so failures remain distinguishable across the
`worker_threads` postMessage boundary — this is load-bearing for future hardware-diagnosis
sessions per this file's own extensive doc-comment history.

### COMPILE GATE FAILED throw-loud discipline
**Source:** `meta/buildSidecarSea.ts` — every `bundle*()`/`generateSeaBlob()`/`injectBlob()`
function (e.g. lines 565-574, 594-603)
**Apply to:** Any new build-time step embedding the `.node` asset. Every failure mode (missing
input file, non-zero exit code, exit-0-but-no-output) must throw a
`COMPILE GATE FAILED (D-06): ...`-prefixed `Error` — never a silent skip or a `console.warn`
that lets the build continue with a missing asset.

### Argv-form-only spawning (never a shell string)
**Source:** `meta/buildSidecarSea.ts` `spawnArgv()` callers throughout (e.g.
`buildPostjectArgv()` lines 255-..., `buildEsbuildArgv()` lines 318-327)
**Apply to:** Any new subprocess invocation this phase introduces (e.g. a step that shells out
to inspect/copy the `.node` prebuilt). T-24-06 discipline: pure exported argv-builder functions
returning `{ command, args }`, tested without invoking the real toolchain, executed via
`spawnArgv()` — never a shell string.
