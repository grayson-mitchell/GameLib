## Summary

Reviewed the widened `SteamBottleEligibilityVerdict` wire type, the single shared IPC handler
that populates it, the new `resolveDepotAvailability`/`hasSteamDepotSignalCaptured` pair in
`steamPlatformRow.ts`, the new `'pending'` member of `SteamPlatformRowMode`, the read-order seam

combinations (seed-captured, seed-uncaptured, probe-landed-present, probe-landed-confirmed-absent,
probe-settled-uncaptured) by hand and cross-checked against the shipped 6-row truth table in
`steamPlatformRow.test.ts` — the arithmetic is correct in every case, including the two D-04
branches (confirmed-absent omits, settled-uncaptured offers). Traced every switch/if-else
consumer of the new `'pending'` `SteamPlatformRowMode` member (`resolveSteamSectionGating`,
`selectSteamPlatformOptions`, `readonlyPlatformValue`, `index.tsx`'s `platformSelection()`) and
found all of them exhaustive — no unhandled `'pending'` branch anywhere. Verified the two
shipped source gates (`steamSectionGating.test.ts` banning `platformsCaptured`/
`steamPlatformsCaptured` in `steamSectionGating.ts`; `steamEligibilityWiring.test.ts`'s Group E
gates in `index.tsx`) against a comment-stripped specimen built with the project's own
`stripSourceComments` and confirmed zero survivors — the JSDoc blocks that legitimately *name*
the banned tokens (to explain why they're banned) are fully removed by the block-comment strip
before the line-filter runs, so the gates are not self-defeating. Confirmed the `=== true`
comparisons in `hasSteamWindowsDepot`/`hasSteamDepotSignalCaptured`/`installFormIpc.ts` are
intact (no loosening to `!== false`). Ran `tsc --noEmit` (zero errors touching any reviewed
file) and the seven touched test suites (225/225 passing).

One Warning: the new `'pending'` mode is functionally exhaustive everywhere, but the "exhaustive
unit coverage" test file for `steamPlatformRow.ts` (`steamPlatformRow.test.ts`) omits `'pending'`
from its `ALL_MODES` fixture and has no dedicated case for `selectSteamPlatformOptions('pending',
...)` or `readonlyPlatformValue('pending')` — a regression in either function's `'pending'` branch
would not be caught at this unit level (it would still likely surface through the higher-level
144-combination `steamSectionGating.test.ts` matrix, but that matrix never calls
`steamPlatformRow.ts`'s own functions, so it can't verify their `'pending'` behavior directly).

Three Info-level observations recorded below (none blocking).

## Warnings

### WR-01: `steamPlatformRow.test.ts` does not exercise the `'pending'` branch of `selectSteamPlatformOptions` or `readonlyPlatformValue`

**File:** `src/frontend/screens/Library/components/InstallModal/__tests__/steamPlatformRow.test.ts:43-48, 72-157, 159-175`

**Issue:** This file's own header comment (lines 12-16) claims "exhaustive unit coverage for the
D-17 depot gate and the omit-not-disable platform-row option list." The `ALL_MODES` fixture used
by the cross-product "every returned entry is a member (by reference)" test (line 43-48) lists
only the pre-34.14 four modes:

```ts
const ALL_MODES: SteamPlatformRowMode[] = [
  'absent',
  'readonly-windows',
  'readonly-macos',
  'selectable'
]
```

`SteamPlatformRowMode` gained a fifth member, `'pending'`, this phase (`steamSectionGating.ts:74`),
and both `selectSteamPlatformOptions` and `readonlyPlatformValue` in `steamPlatformRow.ts` have a
dedicated `case 'pending':` branch (`steamPlatformRow.ts:106-120` and `:140-147` respectively).
Neither branch is exercised by this test file: `readonlyPlatformValue`'s direct test block
(lines 159-175) covers `'readonly-windows'`, `'readonly-macos'`, `'absent'`, `'selectable'` but
not `'pending'`, and `selectSteamPlatformOptions`'s dedicated `describe` block (lines 72-157)
has no `'pending'`-mode case either. I confirmed by grep that no other test file calls
`selectSteamPlatformOptions('pending', ...)` or `readonlyPlatformValue('pending')` directly.

This is not a live bug — I traced both `'pending'` branches by hand and they are correct
(`readonlyPlatformValue('pending')` returns `'Mac'`; `selectSteamPlatformOptions('pending', ...)`
returns the `Mac` entry if present, `[]` otherwise) — but a future regression in either branch
(e.g. accidentally returning the Windows entry, or returning `undefined` instead of `'Mac'`)
would not be caught by this unit suite. The 144-combination matrix in
`steamSectionGating.test.ts` proves `platformRow` resolves to `'pending'` correctly, but that
matrix never imports or calls `steamPlatformRow.ts`'s functions, so it cannot substitute for
direct coverage of them.

**Fix:** Add `'pending'` to `ALL_MODES`, and add two direct assertions mirroring the existing
per-mode style:

```ts
it("'pending' returns exactly the macOS entry", () => {
  const result = selectSteamPlatformOptions('pending', platforms, false)
  expect(result).toEqual([macEntry])
})
```

```ts
it("'pending' -> 'Mac'", () => {
  expect(readonlyPlatformValue('pending')).toBe('Mac')
})
```

## Info

### IN-01: D-03's read-order seam in `resolveSteamSectionGating` is protected by a test, not by structure

**File:** `src/frontend/screens/Library/components/InstallModal/steamSectionGating.ts:215-224`

**Issue:** The `!input.depotSignalResolved` branch is required to run before the
`input.hasWindowsDepot` branch (step 4), and the code comment states this explicitly and at
length ("a future refactor that reorders these two branches must be treated as reintroducing the
34.14 defect"). This is enforced only by comment discipline plus the dedicated
`defensive normalisation` spec at `steamSectionGating.test.ts:856-868` (the excluded
"meaningless pair" `hasWindowsDepot: true, depotSignalResolved: false` case), not by any type-level
or structural guard. I confirmed that reordering the two `else if` branches would only change
behavior for that excluded, currently-unreachable input pair — for the realistic
`(hasWindowsDepot: false, depotSignalResolved: false)` combination the two orderings agree — so
today's production behavior can't actually desync from a reorder, but the *documented* invariant
would silently stop being what the code guarantees. This is exactly what the existing test at
line 856 exists to catch (and does catch, correctly, per the RED-proof convention this file
otherwise follows). Recording as Info because the risk is already covered by a real assertion,
not merely by comment.

**Fix:** No action required; the existing test at `steamSectionGating.test.ts:856-868` already
covers this. Worth keeping in mind if `SteamSectionGatingInput`'s two depot fields are ever
refactored into a single object — at that point the "meaningless pair" would become
unrepresentable at the type level, which would be a strictly stronger guarantee than the current
test.

### IN-02: `installFormIpc.ts`'s rejected-appName early return sets `platformsCaptured: false`, which is easy to misread as a D-04 fail-open trigger

**File:** `src/backend/storeManagers/steam/installFormIpc.ts:91-96`

**Issue:** Already flagged and explained by the plan's own in-code comment (lines 91-95), and I
independently traced this to confirm the note is accurate and the value is correct: a rejected
`appName` short-circuits before `checkBottleEligibility()`/`ensurePlatformsCaptured()` ever runs,
so `platformsCaptured: false` here means "the depot question was never asked" for a different
reason (invalid input) than the D-04 fail-open case (asked, but the answer never landed). Both
produce the same `(false, false)` pair on the wire, and nothing downstream currently
distinguishes them — a rejected `appName` today produces the exact same `windowsDepotOffered:
true` fail-open behavior as a genuine timeout would, because `resolveDepotAvailability` has no
way to see *why* the signal is uncaptured. In practice this path is only reached when the
renderer sends a malformed `appName`, which per the `NUMERIC_APP_ID` guard's own doc comment is a
defensive case, not an expected one — so the fail-open extending to it is low-consequence. Noting
for completeness since the code's own comment flags the ambiguity as worth recording.

**Fix:** No action required — the existing comment already documents this correctly and no
downstream logic currently depends on distinguishing the two "uncaptured" causes.

### IN-03: `resolveDepotAvailability`'s `windowsDepotOffered` and `depotSignalResolved` are computed on every render for every install dialog, including non-Steam runners

**File:** `src/frontend/screens/Library/components/InstallModal/index.tsx:200-208`

**Issue:** `resolveDepotAvailability` is called unconditionally (not gated on `isSteamManagedApp`),
same as the `useSteamBottleEligibility` hook it depends on (which is deliberately unconditional
per the Rules of Hooks, per the file's own comment at lines 105-109). For a GOG/Epic/Amazon
install or a Steam import, `eligibility.pending` resolves to `false` immediately
(`shouldProbeEligibility` returns `false` for those cases), which makes `probeSettled: true` on
the very first render with `probeDepotSignalCaptured: false` — triggering the D-04 fail-open
branch and producing `windowsDepotOffered: true` for a value that is then never consumed (the
JSX only reads `steamGating`/`platformRowOptions` when `isSteamManagedApp` is true). This is
inert dead computation, not a behavioral bug — confirmed no non-Steam code path reads
`windowsDepotOffered` or `depotSignalResolved`. Performance is explicitly out of scope for this
review; noted only because the value briefly *looks* like a fail-open being incorrectly
triggered for a non-Steam game until traced to its (unused) destination.

**Fix:** No action required for correctness. If ever revisited, gating the
`resolveDepotAvailability` call itself on `isSteamManagedApp` (unlike the hook, which cannot be
conditional) would remove the dead computation, but this is a clarity nicety, not a defect.
