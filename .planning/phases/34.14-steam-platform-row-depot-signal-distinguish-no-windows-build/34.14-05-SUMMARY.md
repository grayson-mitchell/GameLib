## Reusable Lesson: Six Procedure Defects in the Gate's Own Contract

Recorded so a future run of a similar forced-network UAT contract does not repeat them:

1. **The dual-host block is over-broad.** Blocking `api.steampowered.com` alongside `store.steampowered.com` kills `steam-user`'s CM login and empties the entire Steam library, making the UAT target unreachable — testing nothing. Block **only** `store.steampowered.com`, the `appdetails` host that carries the depot signal.
2. **`127.0.0.1` is the wrong blackhole address.** It REFUSES in ~1ms, so the 15s `METADATA_FETCH_TIMEOUT_MS` path is never taken and the pending window stays sub-perceptual. Use an unroutable address that silently drops (TEST-NET-3 `203.0.113.1`), verified by `curl` exit `28` (timeout) rather than exit `7` (refused). This single change converted four ledger rows from unobservable to `pass`.
3. **Verify the block by resolution, not by having run the command.** The OS resolver was caught serving a stale `203.0.113.1` after a flush while `/etc/hosts` was already clean — which would silently turn a "blocked" run into an unblocked one and manufacture a false result.
4. **`dig` does not read `/etc/hosts`.** It is the wrong instrument for verifying a hosts-based block; `curl` (which uses the OS resolver) is the right one.
5. **Under Tauri, the observable log is `~/Library/Logs/GameLib/gamelib.log`**, not the `pnpm tauri:dev` stdout capture — the sidecar's stdout IS the RPC pipe, so INFO-level logger lines never appear there.
6. **Network-up runs cannot exercise the pending window** when the target's metadata refetches faster than the operator can open the dialog. If those rows must be arbitrated on a network-up run, the contract needs a latency injection, not a faster operator.

## Findings Filed (none is a 34.14 defect — all pre-existing, surfaced by the gate)

1. `2026-08-16-steam-sync-does-not-capture-platforms-lazy-per-game-only.md` (high) — the Steam library sync captures NO platform data at all; it only reads whatever the metadata cache already holds. Platform flags are populated lazily, one game at a time, by `fetchMetadataIfNeeded` → `appdetails`. Consequence for this phase: "platforms not captured" is a **normal-operation state**, reachable for any never-visited game or slow connection — not an exotic outage-only case — so D-04's fail-open is load-bearing in ordinary use, which strengthens rather than weakens this phase's justification.
2. `2026-08-16-steam-syncing-spinner-has-no-failure-state-blocks-whole-library.md` (high) — the "Syncing your Steam library…" overlay has no failure state and is not scoped to Steam; with Steam unreachable it renders forever and hides other runners' games.
3. `2026-08-16-steam-metadata-cache-lacks-is-windows-native-pre-d17-residue.md` (medium) — 370 of 380 real cache entries carry `platformsCaptured: true` with no `is_windows_native` at all (pre-D-17 residue from an older build); the row concludes "no Windows build" confidently for these, and D-04's fail-open cannot rescue a state that reads as captured. Needs a migration or cache-version bump, out of scope here.
4. `2026-08-16-absent-is-mac-native-treated-as-no-mac-build-mirror-of-34-14.md` (medium) — the mirror image of the defect this phase fixed: absent `is_mac_native` is read as "no Mac build" (`getDefaultplatform()` / the title-icon row), so a cold cache renders a Windows-only heading. Confirmed by direct inversion across Runs 1-4: warm cache showed Apple+Windows with macOS default, cold cache showed Windows-only with Windows default, on the identical game and runtime pairs. This finding independently corroborates that 34.14's fix landed at the correct layer — the symmetric bug was only visible because 34.14 deliberately did NOT extend the same fail-open treatment to the Mac-native signal (out of scope for this phase, per the plan's own D-06 route fence and mac-only-null-set operator constraint).

**2. [Rule 1 - the plan's forcing procedure had a bug] `127.0.0.1` never reaches the 15s timeout path**
- **Found during:** Task 2, Run 2 first attempt
- **Issue:** The plan's literal blocking target (`127.0.0.1`) causes an instant connection refusal (~1ms), so the fetch never reaches `METADATA_FETCH_TIMEOUT_MS` (15,000ms) and the pending row never renders long enough to observe — four ledger rows (`2.1/2.2/2.3/2.6`) were initially `blocked`, not because the code was wrong but because the forcing procedure's blackhole address was wrong for the property being tested.

- **Files modified:** none (procedure-only)
- **Verification:** Second attempt: operator observed the "Checking install options…" row, Install disabled/re-enabled, and Windows offered after settling — corroborated by the app log showing the fetch genuinely ran the full 15,000ms (`AxiosError: timeout of 15000ms exceeded`).
- **Committed in:** `9375d7585`
