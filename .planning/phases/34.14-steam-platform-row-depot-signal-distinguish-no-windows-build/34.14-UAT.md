## Operator finding: the forced states are NOT artificial

Raised by the operator after Run 4 and then confirmed in source. It corrects an assumption this
ledger was originally written under, so it is recorded here rather than only in the todo.

**The assumption:** that "platforms not captured" is an exotic state only reachable by the `sudo`
network forcing, and that on a healthy connection the sync guarantees platform data.

**The reality:** the Steam library sync captures **no platform data whatsoever**. It only reads
whatever the metadata cache already holds (`library.ts:753, 778-780`), and
`Steam: fetched 378 owned games` is `steam-user`'s `getOwnedApps()` — appIds and names only.
Platform flags are populated lazily, one game at a time, by `fetchMetadataIfNeeded` → `appdetails`
(`games.ts:647`, persisted `games.ts:704`).

**Consequences for this gate:**

1. The "not captured" state is a **normal-operation state**, reachable for any never-visited game,
   on a slow connection, or when the fetch loses a race against the user opening the dialog. Runs 1
   and 3 avoided it only because the refetch won that race.
2. D-04's fail-open is therefore **load-bearing in ordinary use**, not merely an outage safety net.
   This strengthens the phase's justification.
3. An earlier framing in this ledger — that the pending path is "sub-perceptual on a healthy
   connection" — is true only for a game whose metadata is already cached or fetches quickly. It
   should not be read as "unreachable in practice". Corrected here rather than silently amended
   above.

Filed as its own todo (sync-time bulk platform capture). Not a 34.14 gap: 34.14 correctly made the
renderer behave safely when the signal is missing; this finding is about the signal being missing
far more often than it needs to be.
