## Summary

This is an unusually rigorous set of test suites, and after a genuinely adversarial pass — hunting
specifically for tautologies, over-complete mocks, logout paths that only clear in-memory state,
error-class conflation, unguarded `expect()`s, un-rearmed mocks, and fake-timer time-proves-nothing
patterns — I found **zero Critical and zero Warning defects** in this scope. One Info-level wording
observation is recorded below. This report also documents, per the coverage-honesty mandate, the
specific adversarial checks I ran and ruled out negative, so a reader can tell "checked and clean"
apart from "not checked."

### The mandate's named hazard shapes, checked explicitly

**(a) Tautology (expected value computed from the same code path under assertion).** Not found.
Every test I checked derives its expected value from either a hardcoded literal (e.g. the distinct
`'SECRET_KEY'`/`SECRETVALUE`/`super-secret-should-never-leave-the-sidecar` markers used across
`steamAuthFlows.test.ts` and `oauthLoginCapture.test.ts`) or an independently-programmed mock
response, never from re-invoking the function under test to produce its own expectation.

**(b) Mocks so complete the assertion only exercises the mock.** Checked `jest.mock('../sidecarRpc', ...)`
(`requestRustInvoke` only) and `jest.mock('backend/logger', ...)` (`logInfo`/`logDebug`/`logError`/
`logWarning`/`LogPrefix`) in `keyringTokenStore.test.ts` and `humbleSecretStore.test.ts` against
the real modules' export surfaces via `grep -n "^export"` — both mocks are exact matches, no drift,
no invented shape. `humbleLoginFlows.test.ts`'s "Describe 2" deliberately does **not** mock
`sidecarRpc` at all — it drives the real `startRpcServer()`/`requestRustInvoke()` transport over a
`PassThrough` pair, so that whole describe block is a transport-level proof, not a mock-only proof
(`humbleLoginFlows.test.ts:186–615`). Keyring failure-mode variety is represented: `'unavailable'`,
`'timeout'`, `keyring:unavailable:PlatformFailure`, `keyring:unavailable:NoStorageAccess` are all
separately programmed and asserted on in `humbleSecretStore.test.ts` (e.g. lines 178–206, 373–402)
and `keyringTokenStore.test.ts`'s dedicated timeout-vs-absent describe block.

**(c) The logout/erase path — both cache and transport, not just in-memory.** `keyringTokenStore.test.ts`'s
cache-invalidation-on-write/delete tests (lines ~740–836, per my earlier full read) prove this the
strong way: after `clearToken()`/`setToken()`, the mocked transport is **re-programmed** with a new
value and a subsequent `getToken()` is shown to hit the transport again and return the new value —
not merely that in-memory state changed. `humbleSecretStore.test.ts`'s equivalent
(`clearSecrets() invalidates BOTH slots' caches`, lines 605–628) is slightly lighter — it proves the
cache was correctly invalidated (a stale `'pre-disconnect-value'` is NOT returned after
`clearSecrets()`) but does not additionally re-arm the transport with a third distinct value to
prove a subsequent read reaches a live transport rather than a "confirmed-empty" cache entry. This
is not a defect: the transport-reaches-delete claim is independently proven in the adjacent,
non-caching test (`clearSecrets() issues a delete for BOTH slots and resolves even if one rejects`,
lines 209–226), and the two tests together cover the same ground `keyringTokenStore.test.ts` covers
in one test. I considered flagging this as a Warning and decided against it — the combined evidence
across the two tests is equivalent, not weaker, and inventing a defect here to satisfy the mandate's
letter over its substance would be exactly the failure mode I was told to avoid.

**(d) Error-class conflation (ENOENT vs EACCES).** Not applicable to this scope in the form named
by the Phase 41 precedent — none of these 5 files' code-under-test does raw filesystem access; the
"failure" surface here is keyring-crate error strings (`PlatformFailure`, `NoStorageAccess`,
`timeout`) and `humbleSecretStore.ts`'s Electron-store-backed plaintext migration (a mocked
in-memory object, not real `fs`). `keyringTokenStore.test.ts`'s own `classifyKeyringFailure()`
coverage (confirmed on my earlier full read) already distinguishes `timeout` from `unavailable` as
two genuinely different reasons, not conflated. I looked for this specific hazard shape and it does
not arise in this scope.

**(e) Assertions on a resolved-promise shape where the rejection path is never exercised.** Not
found as a pattern — every seam method in `humbleLoginFlowRegistration.ts`'s
`createRustLoginWindowSeam()` (`open`, `cookies`, `cookiesForDomain`, `takeEvents`, `close`,
`clearCookies`, `clearStorage`) has an explicit malformed-response-rejects test alongside its
happy-path test in `humbleLoginFlows.test.ts` (e.g. lines 213–228, 274–288, 337–355, 566–583,
585–606) — the "never coerce to 0/false" discipline is proven on both the resolve and reject sides,
for both the pre-existing `cookies()` arm and the newer `cookiesForDomain()` arm, checked
side-by-side per that plan's own stated binding constraint (lines 357–371).

**(f) `expect()` inside a callback that may never run, no `expect.assertions(n)` guard.** Checked
the handler-registry callback-driven tests in `oauthLoginCapture.test.ts` (`handler?.(undefined, {...})`,
lines 831–905) and `steamAuthFlows.test.ts`'s `logoutSteam` rejection-guard test (lines 498–537).
Both use optional chaining (`handler?.(...)`) on a value asserted `toBeDefined()` immediately
before use, and any resulting `undefined` result would fail the subsequent `.toEqual(...)`
assertion rather than silently vacuously pass — no missing-`expect.assertions()` hazard found.

**(g) A mock not re-armed between tests (Phase 34.2 WR-08 precedent).** Checked
`oauthLoginCapture.test.ts`'s three `describe` blocks, each declaring its own
`mockSeamOpen`/`mockSeamTakeEvents`/`mockSeamClose` and re-arming them in `beforeEach` (lines
237–242, 587–595, 725–730) — consistent, no stale-arm risk given the project's `resetMocks: true`
Jest config (which wipes implementations between tests, making the `beforeEach` re-arm mandatory
and, here, present in every block that needs it). `humbleSecretStore.test.ts`'s single top-level
`beforeEach` (lines 102–133) re-arms `mockConfigStore`'s three methods and
`mockRequestRustInvoke`'s implementation every test, and — specifically checked, given this file's
own header doc comment calls it out as load-bearing — calls
`resetSidecarHumbleSecretStoreCachesForTests()` (line 109) before any test body can issue a read,
correctly guarding against the module-level `SLOT_STORES` singleton leaking cache state across
tests in the same file (no `resetModules` in this project's Jest config, per that file's own header
comment, lines 16–24).

**(h) Fake timers with an assertion on real elapsed time.** Not found. Every
`jest.useFakeTimers()` block I checked in `oauthLoginCapture.test.ts` pairs an explicit
`jest.advanceTimersByTime(...)` with an `await flushAsync()` before asserting, and restores real
timers in a `finally` block (e.g. lines 257–291, 330–366, 385–402). No test asserts on wall-clock
time while fake timers are installed.

### Credential-leakage hazard — checked explicitly, none found

Grepped all 5 files for `spawn`, `child_process`, and a literal `env:` object — zero matches in any
of the 5 files. None of them spawns a child process at all, so the "hand-rolled `env` literal
assigning HOME/XDG_*" convention (`CLAUDE.md`'s two-profile rule) does not apply to any file in this
scope by the convention's own stated terms (it targets child-process spawn sites specifically, and
is enforced only there, per `fakeHomeIsolation.test.ts`). `steamAuthFlows.test.ts` isolates its
Electron-store I/O by mocking `os.homedir()` to a disposable per-process tmp dir **in-process**
(`jest.mock('os', () => ({ ...actual, homedir: () => path.join(actual.tmpdir(), \`gamelib-steamauth-test-home-${process.pid}\`) }))`,
near the top of the file) rather than by spawning a child with a modified `env` — this is a
different, and if anything more conservative, isolation mechanism (no env var is ever touched at
all, so there is no risk of a forgotten `HOME` reassignment leaking to a spawned grandchild). I
conclude this is **not** a violation of the convention and **not** a finding — it is a distinct,
legitimate same-process isolation pattern, explicitly outside the scope the convention itself
defines (spawn sites) and outside what `fakeHomeIsolation.test.ts` checks.

Also grepped all 5 files for `toMatchSnapshot`, `writeFileSync`, `appendFileSync` — the only hit is
`keyringTokenStore.test.ts:411–417`, a structural *source-purity* gate asserting the real
`keyringTokenStore.ts` source never references `writeFileSync` (unrelated to test-output leakage).
No test in this scope writes a snapshot file or any other on-disk fixture, so there is no
credential-bearing-snapshot risk to find. All "secret-looking" values used across the 5 files
(`'SECRET_KEY'`, `'super-secret-should-never-leave-the-sidecar'`, `SECRETVALUE`,
`'super-secret-cookie-value-xyz'`, `'super-secret-migration-value-xyz'`, `'QR-SESSION-TEST-TOKEN'`)
are synthetic literals invented by the test file itself, never real Humble/Steam/GOG/Epic session
data, and never persisted anywhere — they exist purely to prove a distinctive marker string does
not leak into a log call, by name, at the exact call sites checked.

### Timer-lifetime / `.unref()` coverage claim — checked explicitly (the pre-confirmed defect's test-side question)

Per the task's specific instruction, I checked whether `oauthLoginCapture.test.ts` (or
`humbleLoginFlows.test.ts`'s windows/pollers) claims coverage of timer lifetime/cleanup relative to
the sidecar's stdin-EOF exit contract that it does not actually deliver.

`humbleLoginFlows.test.ts` has no long-lived timer of its own to test — the poll/deadline state
machine lives entirely in `oauthLoginCapture.ts`, not in the login-window-seam transport this file
covers, so there is nothing to check there.

`oauthLoginCapture.test.ts` never mentions "unref" anywhere in the file (grepped), so it makes no
*explicit* false claim about the sidecar's event-loop-reference contract. Its header docstring's
actual claim is narrower and accurate: `captureOAuthLogin` "never introduces a pending timer after
settling" (lines 11–15) — proven by tests that advance fake timers well past settlement and assert
no further `mockSeamTakeEvents`/`mockSeamClose` calls occur (e.g. lines 320–324, 356–362, 507–538).
That claim is true and is correctly proven; it is a claim about *not double-scheduling after
resolve*, not a claim about `.unref()`.

The finding below (IN-01) is that this suite's *entire* timer coverage runs exclusively under
`jest.useFakeTimers()`, which replaces the real `setInterval`/`setTimeout` with a virtual scheduler
that creates no real libuv timer handle at all — so `.unref()`/`.unref?.()` cannot be exercised,
tested, or proven by this file under any circumstance, regardless of what future changes are made
to the source. I am not re-reporting the pre-confirmed missing-`.unref()` source defect itself
(per instruction); I am reporting that a test-title phrase this close to the project's own
documented invariant, in a suite that is structurally incapable of ever proving that invariant, is
a latent trap for a future reader — worth a wording tweak, not a blocking defect. `CLAUDE.md`'s own
"sidecar's exit contract" section already states plainly that "No test asserts the invariant" and
that a source gate over timer creation was a deliberate, considered rejection — so this is a known,
accepted gap at the project level, not a newly-discovered one, and does not rise above Info.

## Info

### IN-01: `oauthLoginCapture.test.ts`'s "leaves no pending timer" language sits adjacent to an invariant it structurally cannot test

**File:** `src/backend/sidecar/__tests__/oauthLoginCapture.test.ts:11-15, 330, 356-362, 507-538`
**Issue:** The suite's header docstring claims `captureOAuthLogin` "never introduces a pending
timer after settling," and individual test titles echo this ("...and leaves no pending timer",
line 330; "a 'closed' event arriving AFTER the capture already settled ... triggers no second
settle and no extra close call", line 507). Both the claim and its proof are accurate for what they
literally assert — no re-poll or double-close after resolution. But every test in this file runs
under `jest.useFakeTimers()`, which never creates a real Node/libuv timer handle, so this suite is
structurally incapable of ever exercising `.unref()`/`.unref?.()` or proving anything about the
sidecar's documented exit contract ("no handle may hold a reference to the event loop past stdin
EOF," per `CLAUDE.md`). The phrase "leaves no pending timer" is close enough to that invariant's own
language that a future reader skimming test titles (rather than the fake-timers setup) could
reasonably — and wrongly — conclude the exit-contract concern is covered here. It is not, and per
`CLAUDE.md`'s own text this is a known, deliberately-unenforced gap at the project level, not a
regression introduced by this test file.
**Fix:** Consider retitling the affected assertions to something unambiguous about scope, e.g. "no
further poll/close calls occur after settling (fake-timer proof only — does not exercise
`.unref()`)," or add a one-line comment near the top of the file noting that `.unref()` on the real
poll interval / deadline timer is out of this suite's reach by construction (fake timers). This is
a documentation/naming clarity improvement, not a behavioral change, and not blocking.
