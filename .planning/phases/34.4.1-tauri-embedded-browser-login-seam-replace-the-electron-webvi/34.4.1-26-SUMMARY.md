# Phase 34.4.1 Plan 26: F-9 Keychain timeout — bounded classification + redundant-read cache Summary

**A worker-thread-bounded `keyring:timeout` classification for `keyring_get` (8s bound, chosen from two hardware-measured runs showing a present-entry Keychain read can stall 48.9s–291s and fail with `PlatformFailure(-60008)`), plus a process-lifetime read cache + in-flight dedupe in `keyringTokenStore.ts`/`humbleSecretStore.ts` that cuts the 20+ Keychain reads/boot `deferred-items.md` recorded toward the structural floor of 3.**

## Performance

- **Duration:** ~55 min (includes two live timing-harness runs totaling ~340s of wall-clock wait)
- **Completed:** 2026-07-31T06:57:00Z
- **Tasks:** 2
- **Files modified:** 8

## Accomplishments

- **Task 1 (measurement, not a fix):** Added an `#[ignore]`d timing harness (`keyring_read_timing_hypothesis_absent_vs_present_entry`) that times a guaranteed-absent Keychain account read against a real read of the `steam-refresh-token` account, using the `keyring` crate directly (bypassing `keyring_account()`'s allowlist deliberately, per the plan's own accepted threat T-34.4.1-117). Ran it twice on this machine:
  - Run 1: absent-entry `40.04ms` (`NoEntry`); present-entry `48.87s`, ultimately an `Err` (not `Ok`).
  - Run 2: absent-entry `102.23ms` (`NoEntry`); present-entry `291.08s`, `Err(PlatformFailure { code: -60008, message: "Unable to obtain authorization for this operation." })`.
  - **Verdict: REFUTED**, and in the *opposite* direction from the literal hypothesis ("missing entry blocks longer"). The absent entry was consistently fast; the present, allowlisted entry was the one that stalled catastrophically, and both times failed with a Keychain *authorization* error — live, hardware-measured support for `deferred-items.md`'s ad-hoc-code-signature/Keychain-ACL theory (ad-hoc-signed processes cannot durably retain an "Always Allow" grant, so a differently-signed process's request to access an existing protected item can trigger a real, and sometimes extremely long, authorization negotiation).
- **Task 2 (observability, not a root-cause fix):** `keyring_get` now runs its `Entry::new(...).get_password()` call on a worker thread behind a new generic helper, `bounded_keyring_read<F>()`, which reuses `humble_reveal_post`'s existing `mpsc_channel` + `rx.recv_timeout()` shape. On timeout it returns the classified `Err("keyring:timeout")` well before the sidecar's own 60s `RUST_INVOKE_TIMEOUT_MS` RPC budget would otherwise expire and surface as an unattributable generic timeout. `NoEntry` still resolves `Value::Null` (proven by the new `keyring_get_result()` pure-function tests); an unknown slot is still rejected by `keyring_account()`'s existing allowlist *before* any Keychain call is attempted (structurally unchanged — the `?` short-circuit runs before `bounded_keyring_read` is ever called). `keyring_set`/`keyring_delete`/`keyring_available` deliberately keep their original unbounded shape; the reasoning is recorded in-source and in the key-decisions above.
- **User-approved scope widening (both halves required — see `APPROVED_SCOPE_WIDENING` in this plan's prompt):** `SidecarKeyringSlotStore` (`keyringTokenStore.ts`) now caches a successful `getToken()`/`isAvailable()` result per instance, with in-flight promise dedupe so concurrent callers share one real Keychain round trip. `setToken()`/`clearToken()` invalidate the cache *before* issuing their write/delete, and repopulate it with the now-confirmed value only on success. `humbleSecretStore.ts` inherits this for free through its module-level `SLOT_STORES` singleton (one store per secret, shared across every `SidecarHumbleSecretStore` instance for the sidecar's whole lifetime).
- Found and fixed a real regression the scope-widening caching introduced: `migrateOneSecret()`'s one-time plaintext-to-keyring migration write bypasses `SidecarKeyringSlotStore.setToken()` (deliberately, to prove a genuine live readback), so it did not previously trigger cache invalidation. A pre-migration `getSecret()` call's cached `''` would otherwise have kept shadowing the post-migration real value forever. Caught by this plan's own updated `humbleSecretStore.test.ts` round-trip test, fixed by adding an explicit `SLOT_STORES[key].invalidateCache()` call after a successful migration write.

### User-Approved Scope Widening (not a deviation rule — explicit prior authorization)

This plan's prompt included an `APPROVED_SCOPE_WIDENING` block explicitly authorizing both halves of the read-count fix: (1) the timeout handling above, as originally planned, and (2) eliminating redundant Keychain reads by adding caching/in-flight dedupe to **`src/backend/sidecar/keyringTokenStore.ts`** and **`src/backend/sidecar/humbleSecretStore.ts`** — neither file was in this plan's original `files_modified`. Both files (plus their existing test files, which required a cache-isolation fix to keep passing — see below) were modified in the Task 2 commit.

**Threat-model / security tradeoff, stated explicitly per the approval's own instruction:** caching a successfully-decrypted secret in process memory is a security-relevant change. The cache holds the same plaintext value the caller's own `await getToken()` already receives and holds in memory immediately after every (uncached) call — this change does not introduce a NEW class of same-process memory exposure, it extends how long an *already-exposed* value stays resident in this process, from "one `requestRustInvoke` round trip" to "until the next `setToken()`/`clearToken()` on the same slot, or process exit." This phase's own threat register (`T-34.4.1-114`/`T-34.4.1-115`/`T-34.4.1-116` in this plan's own frontmatter) covers the DoS/repudiation/information-disclosure angles of the timeout half; the caching half's information-disclosure angle is covered by the same `T-28-04`/D-08 register `keyringTokenStore.ts`'s pre-existing doc comment already declares (no env-var/plaintext/degraded fallback exists, and none was added) — see the module's updated doc comment for the full statement.

**Correctness constraints from the approval, verified met:**
- Cache does not survive `clearToken()`/`setToken()`/`clearSecrets()`/`setSecret()` — proven by 6 dedicated tests across both test files (including the "failed write/delete still invalidates, never guesses" cases).
- Totality preserved exactly: every method still never rejects/throws; a `null` `keyring_get` result is still the healthy first-run case, still not logged, and is now also cached (a confirmed-absent state is as valid a cache entry as a confirmed-present one).
- Every failure path still logs exactly one warning naming the channel, never the secret value — unchanged; a failed read is explicitly NEVER cached as if it were a value (proven by the "does NOT cache a failed getToken()/isAvailable()" tests).
- No env-var/plaintext/in-memory *fallback* was introduced (D-08/REQ-28-07 unaffected) — the cache is an optimization over an already-total, already-failure-safe read path, not a new failure-recovery mechanism.

**Test-file isolation fix required by the scope widening (documented here rather than as a numbered auto-fix, since it is a direct and expected consequence of the approved widening, not an independent bug):** `humbleSecretStore.ts`'s `SLOT_STORES` is a module-level singleton created once at import time; this project's Jest config has no `resetModules`, so a fresh `new SidecarHumbleSecretStore()` per test does NOT give a fresh cache — the same two slot-store instances (and now their caches) persist for `humbleSecretStore.test.ts`'s entire run. Added `resetSidecarHumbleSecretStoreCachesForTests()` (exported from `humbleSecretStore.ts`, never called from production code) and call it from that file's `beforeEach`, so each test's own scripted `requestRustInvoke` outcome is genuinely exercised rather than shadowed by an earlier test's cached success. `keyringTokenStore.test.ts` needed no equivalent change — every test there already constructs its own fresh `SidecarKeyringSlotStore`/`SidecarKeyringTokenStore` instance.
