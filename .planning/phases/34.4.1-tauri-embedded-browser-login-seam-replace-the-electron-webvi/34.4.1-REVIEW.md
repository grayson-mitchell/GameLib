## Summary

This review covers the Tauri embedded-browser login seam (Rust shell `main.rs`'s
`humble_login_*`/`humble_reveal_post` dispatch arms, the sidecar-side login/OAuth/reveal
registration and capture modules, the preload transport, and the frontend OAuth-login hook and
panel), weighted toward auth token handling, cookie/session lifetime, the preload↔sidecar↔Rust
IPC seam, and tests that might prove less than their names claim.

The engineering quality of the surface actually reviewed is unusually high. The two
highest-risk historical defect classes this codebase names by name — wry's `Webview::cookies_for_url()`
domain-comparison bug (F-34.4.2-19) and the macOS main-thread blocking-cookies deadlock
(F-34.4.2-12) — are both correctly and consistently fixed everywhere they're invoked
(`humble_login_cookies`, `humble_login_cookies_for_domain`, `humble_login_clear_cookies`), and the
macOS-gating of the deadlock fix is pinned by an unusually rigorous, self-aware structural test
(`f_34_4_2_12_wry_blocking_cookies_calls_are_macos_gated`) that explicitly documents its own
limitations rather than overclaiming coverage. The reveal-POST and clear-storage hidden-window
arms close their window on every exit path (success, script failure, timeout). The
preload↔sidecar IPC channel constants (`common/types/sidecarTransport.ts`) carry exhaustive,
historically-grounded doc comments explaining exactly why each direction/argument-order choice
was made, and cross-checking those docs against the Rust arms and the TypeScript call sites found
them accurate (with one stale exception, IN-01 below).

The one substantive finding is a genuine gap, not a stylistic nit: this codebase has a named,
CLAUDE.md-documented, "broken three times in three weeks" sidecar exit contract (every
timer/watcher must be `.unref()`-ed, and the transport layer gets this right in three separate
files), but three business-logic files at the heart of this exact phase's login/OAuth/reveal seam
do not follow it, and the gap is untested. See WR-01.

No critical/BLOCKER-severity issues were found in the code actually reviewed.

## Warnings

### WR-01: Sidecar exit-contract `.unref()` gap in three login/OAuth/reveal business-logic files, untested

**File:** `src/backend/humble/adapter.ts:289` (also `:318`)
**File:** `src/backend/humble/user.ts:569` and `:580` (also `:390-391`, `:579`)
**File:** `src/backend/sidecar/oauthLoginCapture.ts:325` and `:351` (also `:237-238`)

**Issue:** CLAUDE.md documents a load-bearing sidecar invariant: "No handle may hold a reference
to the event loop past stdin EOF" — every `setTimeout`/`setInterval`/watcher must be `.unref()`-ed,
because the sidecar has no explicit shutdown path and exits by event-loop drain when the Rust
shell closes stdin. CLAUDE.md is explicit that this has "broken three times in three weeks," that
the only gate (`pnpm smoke:sidecar`) catches total failure to exit but not slow exit, and that a
miss "leaves an orphan holding an authenticated session" — exactly the risk class this login/OAuth
seam exists to avoid.

The transport/infrastructure layer of this same codebase implements the rule correctly and
consistently:
- `src/backend/sidecar/sidecarRpc.ts:392` — `timer.unref()` on its `requestRustInvoke()` timeout.
- `src/backend/sidecar/installedJsonWatcher.ts:133,153` — `refreshTimeout.unref?.()` and
  `activeWatcher.unref()`, both commented with the exact CLAUDE.md contract language.
- `src/backend/sidecar/appShellFlowRegistration.ts:506` — a 5000ms timer `.unref()`-ed with its own
  reasoning comment.

By contrast, three business-logic files central to this phase's login/OAuth/reveal seam create
timers that are cleared on their own success/failure paths but are never `.unref()`-ed, so each one
can hold the event loop open past stdin EOF for up to its own deadline if the shell's stdin closes
(or the shell's own process quits) while the flow is in flight:

1. `adapter.ts`'s `humblePostRequestViaSeam()` — `timeoutHandle = setTimeout(...)` at line 289,
   `clearTimeout(timeoutHandle)` at line 318 inside a `finally`. Bounded to `REQUEST_TIMEOUT_MS =
   15_000` (15s). This backs the Humble reveal-key POST, i.e. an in-flight request carrying a CSRF
   token and returning a redeemable key.
2. `user.ts`'s `watchForLogin()` — `pollInterval = setInterval(...)` at line 569 (repeats every
   `COOKIE_POLL_INTERVAL_MS` = 1500ms) and `watchDeadline = setTimeout(...)` at line 580
   (re-armable, ultimately bounded by `LOGIN_WATCH_TIMEOUT_MS` = 10 minutes); both cleared at lines
   390-391/579 on completion but never `.unref()`-ed. This is the worst of the three sites: the
   widest exposure window (up to 10 minutes) and the only repeating (`setInterval`) handle among
   them.
3. `oauthLoginCapture.ts`'s `captureOAuthLogin()` — `deadlineTimer = setTimeout(...)` at line 325
   (`DEFAULT_DEADLINE_MS` = 300,000ms = 5 minutes) and `pollInterval = setInterval(...)` at line
   351 (`DEFAULT_POLL_MS` = 500ms), cleared at lines 237-238 but never `.unref()`-ed.

A grep across `src/backend/sidecar/__tests__/*.ts` and `src/backend/humble/__tests__/*.ts` found no
test that exercises `.unref()` on any of these three files' timers — the only `unref` hits in the
whole test tree are a comment in `storeEmbedWireContract.test.ts` referencing `sidecarRpc.ts:392`'s
existing, correct call. So this gap is currently invisible to CI in the same way the prior two
documented breaks were.

This is bounded, not boot-time/unconditional exposure — each site only holds a reference while an
active, user-initiated flow (login watch, OAuth capture, reveal-key POST) is in flight, not at
sidecar idle — and the Rust shell's `shutdown_child()` SIGTERM-then-grace-then-SIGKILL backstop
will still reap the process in the ordinary case. That bound is why this is scored WARNING rather
than BLOCKER. But CLAUDE.md is explicit that the backstop is "not the normal path" and that missing
it "leaves an orphan holding an authenticated session" — and all three of these sites are precisely
the login/auth-token-bearing flows that class of risk is about. Given the contract's own documented
history (three breaks in three weeks, near-zero enforcement, a 30s startup-timeout gate that
doesn't even reliably catch slow exit), this should be treated as a real, prioritized gap rather
than a cosmetic one.

**Fix:** Add `.unref?.()` (the dominant spelling in this codebase, since jest's fake-timer
substitute doesn't implement `unref()`) immediately after each timer is created:

```ts
// adapter.ts
timeoutHandle = setTimeout(() => { ... }, REQUEST_TIMEOUT_MS)
timeoutHandle.unref?.()

// user.ts
pollInterval = setInterval(() => { ... }, COOKIE_POLL_INTERVAL_MS)
pollInterval.unref?.()
watchDeadline = setTimeout(() => { ... }, remaining)
watchDeadline.unref?.()

// oauthLoginCapture.ts
deadlineTimer = setTimeout(() => { ... }, DEFAULT_DEADLINE_MS)
deadlineTimer.unref?.()
pollInterval = setInterval(() => { ... }, DEFAULT_POLL_MS)
pollInterval.unref?.()
```

Given this contract has already broken three times silently, also consider adding at least one
regression test per site (spawn or simulate stdin EOF with one of these flows in flight and assert
the process/handle count drops) rather than relying on comment discipline alone — mirroring the
existing `installedJsonWatcher.ts` precedent's own admission that "nothing enforces this."

## Info

### IN-01: Stale doc comment claims `humble_login_clear_storage` is unwired

**File:** `src/common/types/sidecarTransport.ts:393-395`
**Issue:** The doc comment on `RUST_HUMBLE_LOGIN_CLEAR_STORAGE` states "Not yet called anywhere —
plan 16 wires it into the two disconnect paths." This is no longer accurate: the channel is called
from `src/backend/humble/user.ts:1092` (`seam.clearStorage(...)`), which is implemented in
`src/backend/sidecar/humbleLoginFlowRegistration.ts:312-313` via `requestRustInvoke(RUST_HUMBLE_LOGIN_CLEAR_STORAGE,
...)`. A future reader relying on this comment could mistake a live, load-bearing logout/disconnect
code path for dead code.
**Fix:** Update the comment to reflect that plan 16 has landed and the channel is wired into
`humble/user.ts`'s disconnect flow, or remove the "not yet called" sentence entirely.

### IN-02: Pristine Epic login window's `get_window` fallback is duplicated rather than centralized

**File:** `src-tauri/src/main.rs` (the `humble_login_close`, `humble_login_clear_cookies`, and
`humble_login_cookies_for_domain` arms; the third occurrence is documented in the file itself as
"the third instance of this exact structural bug")
**Issue:** The macOS-only fallback that tries `get_webview_window` and then falls back to
`get_window` for the pristine Epic raw-`WKWebView` window (which isn't a wry `WebviewWindow`) is
repeated across at least three dispatch arms, and the code's own comments acknowledge this is a
repeated structural pattern rather than a one-off. Duplicated fallback logic like this is the
classic setup for the fourth instance being missed when a new arm is added, or for one of the three
existing copies drifting out of sync if the fallback's semantics ever need to change (e.g. a future
platform-specific label rule).
**Fix:** Extract the "try `get_webview_window`, then macOS-only `get_window` for the pristine Epic
case" logic into a single helper function and have all three (and any future) arms call it, so the
structural pattern only has to be corrected in one place.
