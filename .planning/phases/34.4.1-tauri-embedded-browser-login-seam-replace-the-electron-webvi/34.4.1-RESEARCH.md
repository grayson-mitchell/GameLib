## Summary

The spike (013/014a/014b/015, executed 2026-07-27, packaged in
`.claude/skills/spike-findings-gamelib/references/tauri-login-webview-cookies.md`) resolves
every load-bearing unknown this phase's plan needs. **The headline finding: this is NOT the
`navigator.clipboard`-silent-no-op shape.** `Webview::cookies()` on macOS returns `HttpOnly`
+ `Secure` cookies with real values, including `_simpleauth_sess` itself, in 2–4 ms from any
thread. The one genuine landmine — `cookies_for_url()` doing exact string-equality domain
matching, silently dropping `_simpleauth_sess` for `https://www.humblebundle.com` while
returning 4 *other* plausible cookies — is avoidable by construction: use `cookies()` +
a manual suffix-match filter, exactly the fix this research's Code Examples section gives.
Navigation observation for the four OAuth runners is equally sound: `on_page_load`
(Started/Finished, main-frame-only) is the correct `did-navigate` analog; `on_navigation`
is a trap for this specific use (5 of 8 events on the real Humble login page were iframes,
and wiring `notifyLoginNavigated` to it would let a third-party ad frame re-arm the login
watch deadline indefinitely, defeating WR-03's timeout).

**D-02 is resolved: Rust-arms-driven-by-the-sidecar.** This is not a new architectural
choice — it is the SAME pattern already used three times (Phase 28 keyring, Phase 30
`dialog_open`, Phase 34.3 clipboard): a `dispatch_rust_channel()` match arm in
`src-tauri/src/main.rs`, reached via the sidecar's `requestRustInvoke()` /
`RUST_INVOKE_CHANNELS` allowlist, calling a live `AppHandle`-scoped Rust API. The tension
CONTEXT.md names ("`WebviewWindow`'s constructor is a webview-context-only JS API the
headless Node sidecar cannot call") is real for the **JS** `WebviewWindow`
(`@tauri-apps/api/webviewWindow`, `tauriChildWindows.ts`'s renderer-side tool) but does
**not** apply to the **Rust-side** `WebviewWindowBuilder`/`WebviewWindow` API in
`src-tauri`, which is an ordinary Rust type requiring only an `AppHandle` — precisely the
same shape as `app.dialog()`/`app.clipboard()`, both already dispatched from
`dispatch_rust_channel` today. `humbleStartLogin`/`humbleReconnect` already run
`watchForLogin()`'s stateful poll loop in the **backend** (Node sidecar) process; keeping
that orchestration where it already lives and adding new `rustInvoke` arms for
open-window/read-cookies/close-window/delete-cookie is the smallest, most consistent
change. The renderer-owned alternative would require inventing a new
window→renderer→sidecar relay to shuttle cookie values back — genuinely new plumbing this
project has never needed, versus reusing a proven three-times pattern.

**What would falsify this recommendation:** if `WebviewWindowBuilder::build()` (or the
cookie/eval calls) cannot be safely invoked from the sidecar reader thread that
`dispatch_rust_channel` runs on today — e.g. an AppKit main-thread-affinity panic building
an `NSWindow` off-thread. This is flagged as Assumption A4 below (moderate risk, cheap to
confirm early in execution) rather than asserted as proven, since the spike's own harness
constructs windows from `.setup()`/autorun contexts, not from an arbitrary background
thread the way `dispatch_rust_channel` would need to.

**Primary recommendation:** Build the login mechanism as new `dispatch_rust_channel` arms
(window open/close, `on_page_load` navigation relay, cookie read via `cookies()` +
suffix filter, `delete_cookie()` loop for domain-scoped clearing) reached through new
`RUST_INVOKE_CHANNELS` entries from a new `humbleLoginFlowRegistration.ts` sidecar module
that keeps `watchForLogin()`'s existing poll/throttle/revalidate state machine in
`humble/user.ts`, replacing only its `session.fromPartition()` calls with `rustInvoke`
calls. `humbleRevealKey` gets a time-boxed attempt at an in-webview POST from a hidden,
on-demand child window (D-08), using a navigation-intercept exfil pattern proven end-to-end
by spike 014b on the live Humble origin (adapted below to not require a real external
listener) — declare it degraded on a 403, per D-07.

## Channel Registration Kind Verification (Research Question 3)

CONTEXT.md's Discretion section asserted the split below; **verified against source, no
divergence found** — cross-checked three independent sources per channel: `humble/
ipc_handler.ts`'s own `addHandler`/`addListener` call, `common/types/ipc.ts`'s
`AsyncIPCFunctions`/`SyncIPCFunctions` typing, and `preload/api/humble.ts`'s
`makeHandlerInvoker`/`makeListenerCaller` factory choice.

| Channel | `ipc_handler.ts` (actual line) | `common/types/ipc.ts` shape | `preload/api/humble.ts` factory | Kind |
|---------|-------------------------------|------------------------------|-----------------------------------|------|
| `humbleStartLogin` | `addHandler`, L21 | `() => Promise<{status,username?}>` | `makeHandlerInvoker` | **handle** (returns a value) |
| `humbleReconnect` | `addHandler`, L23 | `() => Promise<{status,username?}>` | `makeHandlerInvoker` | **handle** |
| `humbleGetLoginUserAgent` | `addHandler`, L25 | `() => Promise<string>` | `makeHandlerInvoker` | **handle** |
| `humbleRevealKey` | `addHandler`, L102 | `(params) => Promise<RevealOutcome>` | `makeHandlerInvoker` | **handle** |
| `humbleStopLogin` | `addListener`, L126 | `() => void` | `makeListenerCaller` | **send** (fire-and-forget) |
| `humbleLoginNavigated` | `addListener`, L127 | `() => void` | `makeListenerCaller` | **send** |

This exactly matches CONTEXT.md's Discretion-section claim ("`humbleStopLogin` and
`humbleLoginNavigated` are fire-and-forget relays; `humbleStartLogin`, `humbleReconnect`,
`humbleGetLoginUserAgent` and `humbleRevealKey` return values") — **no correction needed
here**, unlike 34.4's research, which found a real mismatch in
`humbleRecordGiftLinkOpened`'s classification. The planner should still cross-check each
new registration's kind against this table by name when writing `humbleLoginFlowRegistration.ts`,
per `sidecar-send-channels-fail-silently`'s standing lesson — a kind mismatch fails 100%
silently and jest structurally cannot catch a `send` registered where a `handle` belongs
(or vice versa) without an assertion written specifically for it.

### Pattern 1: Rust-side dispatch arm reached from the sidecar (D-02's resolved shape)

**What:** A new `dispatch_rust_channel` match arm, gated by a `RUST_INVOKE_CHANNELS`
allowlist entry, called via `requestRustInvoke()` from the Node backend — the SAME shape
as the Phase 28 keyring arms, Phase 30 `dialog_open`, and Phase 34.3 clipboard arms.

**When to use:** Any time the sidecar needs a live `AppHandle`-scoped Rust API result and
is not itself capable of calling it (headless Node process, no window context).

**Example (mirrors the existing clipboard pattern, `src-tauri/src/main.rs`):**
```rust
// Source: pattern read directly from src-tauri/src/main.rs's existing
// "keyring_get"/"dialog_open"/"clipboard_write_text" arms (dispatch_rust_channel, ~L385+)
"humble_login_open" => {
    let url = args.first().and_then(|v| v.as_str())
        .ok_or_else(|| "humble_login_open:bad-args".to_string())?;
    let label = next_child_window_label(); // generated, NEVER derived from `url` (T-34.1-27)
    let win = tauri::WebviewWindowBuilder::new(
        app,
        &label,
        tauri::WebviewUrl::External(url.parse().map_err(|e| format!("bad url: {e}"))?),
    )
    .user_agent(STANDARD_CHROME_UA)
    .visible(false) // D-08: hidden for reveal; the login flow itself sets true
    .on_page_load(move |_w, payload| {
        if matches!(payload.event(), tauri::webview::PageLoadEvent::Finished) {
            // relay to the sidecar as a SidecarNotification, same shape
            // FRONTEND_MESSAGE_EVENT already uses for backend->frontend push
        }
    })
    .build()
    .map_err(|e| format!("humble_login_open failed: {e}"))?;
    Ok(Value::String(label))
}
```

### Pattern 2: Domain-suffix cookie filter (never `cookies_for_url`)

**What:** Read the FULL jar with `cookies()`, filter in Rust with a proper suffix match.
**When to use:** Every cookie read this phase does — login detection AND the D-08
domain-scoped clear.
**Example:**
```rust
// Source: spike 014a's requirement 1, cross-verified against
// wry-0.55.1/src/wkwebview/mod.rs:1184's cookies_for_url() bug
let host = "www.humblebundle.com";
let matching: Vec<_> = webview.cookies()?
    .into_iter()
    .filter(|c| match c.domain() {
        Some(d) => host == d || host.ends_with(&format!(".{d}")),
        None => false,
    })
    .collect();
```

### Pattern 3: Liveness-proven cookie poll (never a bare `count === 0`)

**What:** Classify every cookie read as `SUPPORTED_NONEMPTY` / `SUPPORTED_BUT_EMPTY` /
`UNSUPPORTED_OR_ERROR` / `UNDECIDABLE` (spike 014a's discriminator design), never a bare
empty array treated as "not logged in yet."
**When to use:** `watchForLogin()`'s `checkCookie()` — this is THE fix for the
`navigator-clipboard-noops-under-tauri` failure shape CONTEXT.md's Discretion section
flags as the risk to fear.
**Example:**
```ts
// Source: spike 014a's discriminator design, adapted to the existing
// checkCookie() shape in src/backend/humble/user.ts
async function checkCookie(forceValidation: boolean) {
  // ...
  const all = await requestRustInvoke(RUST_HUMBLE_LOGIN_COOKIES_ALL, [windowLabel])
  if (!everProvedLive && Array.isArray(all) && all.length === 0) {
    // UNDECIDABLE — an unfiltered read on a page that has never set ANYTHING is either a
    // cold app (rare — a login page always sets something, per spike 014a: Humble set 33
    // cookies to an anonymous visitor) or a no-op API. Fail loudly rather than poll.
    logWarning(['Humble login watch: cookie API returned empty on first read — treating as UNDECIDABLE, aborting watch'], LogPrefix.Backend)
    settle({ status: 'error' })
    return
  }
  if (Array.isArray(all) && all.length > 0) everProvedLive = true
  // ... existing filtered _simpleauth_sess lookup, now via the suffix-match rustInvoke arm
}
```

### Pattern 4: `on_page_load`, never `on_navigation`, for the relay

**What:** Wire `humbleLoginNavigated`'s equivalent to `on_page_load` (Started/Finished,
main-frame-only), never `on_navigation` (fires for every iframe/subframe too).
**When to use:** Any navigation-driven relay into `notifyLoginNavigated()`'s
`forceRevalidate()` — the OAuth runners' code-capture point too.
**Why:** Spike 013 measured 8 `on_navigation` events vs. 2 `on_page_load` events for a
single real Humble page load; 5 of the 8 were third-party iframes. Wiring the relay to
`on_navigation` lets an ad iframe re-arm the login watch deadline indefinitely, defeating
WR-03's timeout — a correctness regression the spike caught structurally, not just as a
performance nit.

### Anti-Patterns to Avoid

- **`cookies_for_url()`** — the single most dangerous API surface identified this phase.
  Returns a plausible non-empty result while silently dropping the deciding cookie.
- **`document.cookie` for login detection** — structurally cannot see `_simpleauth_sess`
  (`HttpOnly`), and fails silently (27 other cookie names look healthy).
- **`WebviewWindow::title()` as a return channel** — returns the native NSWindow title,
  never fed by `document.title`. Use `on_document_title_changed` (a builder hook, distinct
  from the `.title()` getter) if a title-based channel is ever wanted — untested by the
  spike, flagged `[ASSUMED]` below.
- **A persistent hidden Humble webview context** — rejected by D-08 (orphan-session risk,
  same reasoning as Phase 34's WR-03 sidecar-orphan concern). Open per-reveal, close after.
- **A url-derived child window label** — T-34.1-27's standing guard; reuse
  `tauriChildWindows.ts`'s `nextExternalWindowLabel()`-style generated-label discipline on

## Common Pitfalls

### Pitfall 1: Treating an empty cookie array as "not logged in yet" without a liveness proof
**What goes wrong:** The poll spins forever, silently, settling `{status:'waiting'}` at the
5-minute deadline with no error, no log, no toast.
**Why it happens:** `watchForLogin()`'s existing `checkCookie()` already has this shape
(`if (cookies.length === 0) return`), which was correct under Electron (where an
unsupported API is not a realistic failure mode) but becomes ambiguous under Tauri, where
`cookies()` returning `Err` on Android (documented) and cookies_for_url's silent domain-miss
prove the "unsupported-but-looks-empty" failure mode is real on this platform family.
**How to avoid:** Pattern 3 above — classify every read, never poll on `UNDECIDABLE`.
**Warning signs:** A login attempt that never resolves either way, with the sidecar log
completely silent about it.

### Pitfall 2: Wiring the OAuth-code-capture relay to `on_navigation`
**What goes wrong:** A third-party ad/analytics iframe's navigation re-arms
`forceRevalidate()`'s deadline, so the login watch never times out even when the user has
abandoned the flow — WR-03's timeout budget silently defeated.
**Why it happens:** `on_navigation` is the more obviously-named analog to
`did-navigate-in-page`, but Electron's `did-navigate`/`did-navigate-in-page` are top-level
document navigations only; `on_navigation` fires for every frame, including iframes.
**How to avoid:** Pattern 4 — use `on_page_load` (main-frame Started/Finished only).
**Warning signs:** A login window that appears to keep "trying" long past the 5-minute
budget, or the sidecar log showing far more navigation events than the user's actual clicks.

### Pitfall 3: Deleting the whole cookie jar on `humbleDisconnect` instead of a domain-scoped clear
**What goes wrong:** Once Phase 34.5 lands and Epic/GOG/Amazon share the same app-wide
platform cookie jar (spike 015: no isolation by default), a blanket
`clear_all_browsing_data()` on Humble disconnect would silently sign the user out of every
other storefront they never touched.
**Why it happens:** `clear_all_browsing_data()` is the obvious, one-line API; the
domain-scoped alternative requires the multi-step `cookies()` + filter + per-cookie
`delete_cookie()` loop from Pattern 2/Code Examples.
**How to avoid:** Never call `clear_all_browsing_data()` for a per-storefront disconnect.
Only use it if a phase ever needs a genuine "wipe everything" action.
**Warning signs:** A code review or test that reaches for the shortest-looking cookie-clear
API.

### Pitfall 4: A url-derived or reused window label
**What goes wrong:** A crafted URL could collide with `main`/`about` and inherit their
capability grants — the exact hazard `capabilities/default.json`'s own description names.
**Why it happens:** It is tempting to label the login window `login-humble` or similar
static string; two concurrent reveal attempts (or a reveal racing a login) would then
collide, or worse, an attacker-influenced input could be used to construct the label.
**How to avoid:** Generate labels (timestamp+counter+entropy), matching
`tauriChildWindows.ts`'s existing WR-04/T-34.1-27 discipline, ported to the Rust side.
**Warning signs:** A hard-coded label string anywhere in the new Rust arms.

### Pitfall 5: `WKWebView.evaluateJavaScript` does NOT auto-await a returned Promise
**What goes wrong:** A single `eval_with_callback("fetch(...).then(r=>r.text())")` call
does not deliver the resolved fetch body — WKWebView's `evaluateJavaScript:completionHandler:`
reports the script's IMMEDIATE completion value; if that value is a `Promise`, the
completion handler receives the Promise object (or a serialization failure), not the
eventually-resolved value. [CITED: Apple/Microsoft documentation of
`WKWebView.evaluateJavaScript(_:completionHandler:)`'s Promise handling, confirmed via
WebSearch — see Sources]
**Why it happens:** It is a very natural (and wrong) assumption that "eval with callback"
means "await the async result."
**How to avoid:** Use a two-step pattern: (1) fire-and-forget eval that runs the fetch and
stashes the result via a side channel (page-global + navigation-intercept exfil, or a
short `eval_with_callback` poll of a page-global variable), never a single call expecting
the resolved value directly.
**Warning signs:** `eval_with_callback`'s callback firing near-instantly with a value that
looks like `"{}"` or a serialization error, even though the network request genuinely
succeeded moments later.

## Code Examples

### `humbleRevealKey`'s in-webview POST — a non-destructive, spike-derived design (D-07/D-08)

Spike 014b proved a NAVIGATION-based exfil channel (Channel C) works end-to-end on the live
Humble origin — the page navigates itself to a URL carrying the payload in the query
string, and the receiving side reads the URL. The spike's own implementation used a real
loopback HTTP listener to catch that navigation. In production there is no such listener,
but a `WebviewWindow`'s `on_navigation` hook receives the target `Url` and can CANCEL the
navigation by returning `false` — meaning the exfil URL never has to actually resolve
anywhere; Rust reads the URL's query string and blocks the navigation from happening at
all. Combined with D-08's hidden, on-demand, short-lived window design, this needs no new
listener and never leaves the reveal page:

```rust
// Source: pattern derived from spike 014b's proven Channel C
// (.planning/spikes/014b-cookie-read-injected-js/README.md) + tauri-2.11.5's
// on_navigation contract (src/webview/mod.rs:528, "returns bool to determine if the URL
// should be allowed to open") — the CANCEL-the-navigation refinement below is NOT itself
// spike-measured; flagged [ASSUMED] in the Assumptions Log, cheap to confirm in a few
// minutes once the window exists (per D-07's own "cheap once the window exists" framing).
let (tx, rx) = std::sync::mpsc::channel::<String>();
let win = tauri::WebviewWindowBuilder::new(app, &label, tauri::WebviewUrl::External(humble_url))
    .user_agent(STANDARD_CHROME_UA)
    .visible(false) // D-08: hidden, on-demand
    .on_navigation(move |url| {
        if url.host_str() == Some("gamelib.invalid") {
            if let Some(payload) = url.query_pairs().find(|(k, _)| k == "data") {
                let _ = tx.send(payload.1.into_owned());
            }
            return false; // cancel — never actually navigate
        }
        true
    })
    .build()?;

win.eval_with_callback(
    r#"
    fetch('https://www.humblebundle.com/humbler/redeemkey', {
      method: 'POST',
      credentials: 'include',
      headers: {
        'Content-Type': 'application/x-www-form-urlencoded',
        'Accept': 'application/json',
        'csrf-prevention-token': '__CSRF_TOKEN__'
      },
      body: '__BODY__'
    }).then(r => r.text())
      .then(t => { location.href = 'https://gamelib.invalid/reveal?data=' + encodeURIComponent(t) })
      .catch(e => { location.href = 'https://gamelib.invalid/reveal?data=' + encodeURIComponent('ERR:' + e) })
    "#,
    |_immediate_value| { /* ignored — the real result arrives via on_navigation above */ }
)?;
```
`__CSRF_TOKEN__`/`__BODY__` are the SAME values `humblePostRequest` already builds in
`adapter.ts` (`csrfToken`, the `URLSearchParams` body — `HUMBLE_REDEEM_PATH =
'/humbler/redeemkey'`) — only the transport changes. If Cloudflare 403s this exactly as it
does axios (D-07's stated expectation is about axios/reqwest/tauri-plugin-http, not about
a genuine WKWebView network stack, which is different in kind — a real browser tab's own
`fetch()`), the same navigation-intercept pattern still receives the 403 body, and the
existing `mapAxiosError`-equivalent classification can run on it in the sidecar.

### Domain-scoped cookie clear for `humbleDisconnect` (D-08)

```rust
// Source: wry-0.55.1/src/wkwebview/mod.rs:1201 (cookies), :1248 (delete_cookie) — both
// [VERIFIED: read from installed crate source]. No single "delete by domain" API exists;
// clear_all_browsing_data() (mod.rs:811) is unscoped and MUST NOT be used for a
// per-storefront disconnect (Pitfall 3).
"humble_login_clear_cookies" => {
    let host = "humblebundle.com";
    let matching: Vec<_> = webview.cookies()?
        .into_iter()
        .filter(|c| matches!(c.domain(), Some(d) if host == d || d.ends_with(".humblebundle.com") || d == "humblebundle.com"))
        .collect();
    for cookie in &matching {
        webview.delete_cookie(cookie)?;
    }
    Ok(Value::Number(matching.len().into()))
}
```

### Known Threat Patterns for this stack

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|----------------------|
| A crafted login-page URL used to derive a window label that collides with `main` and inherits its capability grants | Elevation of Privilege | Generated labels only (timestamp+counter+entropy), never derived from any URL — T-34.1-27's existing guard, ported to the Rust side. |

| A blanket cookie wipe on Humble disconnect silently signing the user out of Epic/GOG/Amazon once they share the same jar (Phase 34.5) | Denial of Service (to the user's own other sessions) | Domain-scoped `cookies()` + suffix-filter + `delete_cookie()` loop — never `clear_all_browsing_data()`, per D-08/Pitfall 3. |

| The exfil-URL navigation-intercept pattern (Code Examples) briefly constructing a URL containing the (possibly sensitive) reveal-key JSON response as a query parameter | Information Disclosure | The URL is never actually navigated to (cancelled in `on_navigation` before any request fires — Open Question 1 flags this as needing a quick confirmation) and is never logged; only the parsed `data` param is passed back over the existing stdio JSON-RPC channel, which already carries the reveal key value today (C4's existing narrow-exposure discipline, unchanged). |
