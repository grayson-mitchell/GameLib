# Plan 34.4.1-33 — D-29-04 and D-29-05: login-window title handling

**Wave 2.** Both items are in `src-tauri/src/main.rs`. They are adjacent but **causally
independent**, and the finding is emphatic about that.

---

## Do not conflate these two

`D-29-04` was proposed as the cause of `D-29-05`'s visible `Tauri app` flash and **explicitly
refuted by ordering**: the flash is one-way and completes before the first title application
(`len=22`), whereas `len=0` fires only *after* the bar already reads `Humble Bundle - Log In`
(`22` → `0` → `42`).

> **Do not write D-29-04 up as the explanation for D-29-05.** It is filed on its own merits as a
> latent smell.

---

## Task 1 — D-29-04: guard the empty title

`humble_login_open`'s `on_document_title_changed` forwards WebKit's reported document title with no
non-empty guard, so `[shell] humble_login_open: title change applied len=0` fires mid-sequence.

Add a non-empty guard. Note that `login_window_title` at `main.rs:1025` already models the intent
(`Some(title) if !title.is_empty() => …`) — the gap is at the **callback**, not the composer.

Assert the observable property: after the guard, an empty title change is a no-op and the previously
applied title survives.

## Task 2 — D-29-05: a provisional title, and the one shape it may take

D-29-05's suggested fix is *"create the window with a provisional title rather than the framework
default."* **Read this next paragraph before writing any code.**

`main.rs:3635` records that the omission is deliberate:

> "Deliberately NO `.title()` call (WR-07 anti-phishing: the loaded document's own title must show,
> never a hard-coded 'GameLib')."

**These reconcile in exactly one direction.** WR-07 prohibits a hard-coded *application* title. It
does not prohibit an **origin-derived** provisional title — and the repo already does precisely that
at `main.rs:2145`, `:4018` and `:4236` via `login_window_title(&origin, None)`.

- **DO:** build with `login_window_title(&origin, None)`, so the window is titled from the origin it
  is about to load, then let the existing title-tracking callback replace it with the document's own
  title.
- **DO NOT:** `.title("GameLib")`, `.title("Signing in…")`, or any static string. That re-opens
  WR-07, which already misdirected two live-gate operators once (`WR-07 CORRECTION`, `main.rs:3656`).

**Scope the change to the `if visible` block.** The same arm builds the hidden reveal/clear windows;
a hidden window has no title bar for a title to matter on, and touching that path is wasted work at
best and a visible flash at worst (`T-34.4.1-82`).

## Task 3 — Write a gate that measures the right property

`main.rs:3656` records the exact trap, and it is a specific instance of a lesson this project has
now learned several times — *a gate can be non-vacuous, RED-proven, and still guard nothing*:

> "A grep gate proving `.title(` is never hard-coded can only establish the **ABSENCE** of the
> prohibited value; it structurally cannot establish the **PRESENCE** of the required one."

So an absence-grep is **not** sufficient here. The gate must assert the provisional title is
origin-derived — e.g. that the builder's title argument is the return of `login_window_title` with
the arm's own origin — and must be red-proven by substituting a static string and observing failure.

State plainly in the plan record which half of WR-07 each assertion covers. If the PRESENCE half
cannot be established statically at all, **say so** and hand it to plan 35's live gate as a named
observation rather than letting an absence-grep stand in for it.

## Acceptance

- An empty document title is a no-op; the previous title survives. Red-proven.
- The visible login window is built with an origin-derived provisional title, never a static string.
- Hidden reveal/clear windows are untouched.
- `cd src-tauri && cargo test` passes. **CI runs no `cargo` step** (`main.rs:1136-1145`), so this
  must be run by hand — a green jest run says nothing about it.
