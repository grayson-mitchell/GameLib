# F-10 diagnosis — Manage Accounts blank on first navigation

> **RESOLVED — read "ROOT CAUSE — `.loginBackground`" below for the conclusion.** F-10 reproduced
> 5 of 6 cold starts. The content renders correctly every time and is centred ~11 000 px below the
> viewport by a decorative background div whose `height: 100%` resolves inside a circular grid
> chain. The two sections below are the diagnostic trail in the order it was walked, including
> two hypotheses (boot proximity, 268 px viewport) that were later falsified and are retained as
> corrections rather than deleted.

**F-10 REPRODUCES: 3 of 4 cold starts** *(round 1; 5 of 6 after round 2)*. Classification
**(C) — the component mounts and takes the `loading=false` branch, and the screen is blank anyway.**

The decisive and unexpected result: **the breadcrumb sequence is identical on a blank navigation
and on a correct one.** Route resolution, mount, loading transition and render count all match.
The defect is therefore **downstream of React's render phase** — it is not a routing failure, not
a mount failure, and not a loading-branch failure. All three were live candidates before this run;
all three are now eliminated.

### The discriminator is time since boot, not navigation count

The one run that rendered correctly is the one where the operator navigated **45 s** after launch.
All three that rendered blank were navigated **5–6 s** after launch. "First navigation" was the
wrong frame: the defect tracks **boot proximity**, and the original gate's "recoverable by
navigating away and back" is consistent with this — the recovery took time as much as it took a
remount.

This reframing is the most actionable output of this run and was not available from the source.

## What is eliminated

- **Routing / chunk loading.** Resolves in 8–21 ms in every run, blank or not.
- **Route rejection.** No rejection breadcrumb ever fired.
- **The `loading` gate.** Reached `false` in every run, blank or not.
- **The Suspense fallback (D).** Fires at boot and on the away-navigation, never on an incoming
  `/login` navigation — which also confirms live that route-level `lazy` does not participate in
  `index.tsx`'s top-level `<Suspense>`, the correction plan 25 made to research assumption A3.
- **The keyring (F-9), now doubly refuted.** Run 1 — the *correct* one — is the only run with a
  `keyring:timeout` (19:50:11, for `humble-session` and `steam-refresh-token`). The three blank
  runs had **no keyring timeout at all**. The stall correlates with success, not failure. This is
  independent of the gate's original refutation by measurement and points the same way.
- **A render-time throw blanking the tree.** Plausible a priori given `errorElement` is absent
  from every route, but three `loading=false` passes complete on the blank runs — the same count
  as the correct run — so render is not being aborted.

## What remains

The defect is **after React's render phase**: the component returns a full `<div className="loginPage">`
tree, and the screen shows nothing. Remaining candidates, none verified:

1. **Layout / paint under WKWebView.** DOM present, zero-size or unpainted. Consistent with a
   boot-proximity race (styles, fonts or a container measured before it settles) and with the
   project's parked uninstall-vanish investigation, which the gate flagged as a possible sibling
   and which is likewise recorded as a frontend render issue with no data loss.
2. **`loginBackground`** — a full-bleed sibling div — covering `loginContentWrapper` when
   something about the container is not yet settled.
3. **A child subtree rendering empty**, rather than throwing, when contexts are unhydrated 5 s
   into boot.

### The one measurement that separates these

Whether the `.loginPage` DOM node **exists and what its bounding box is** at the moment the screen
looks blank. That single fact splits "never made it to the DOM" from "in the DOM, zero-size" from
"in the DOM, correct size, not painted" — and each implies a different fix. It is not answerable
from the current breadcrumbs, all of which sit upstream of layout.

**Task 3 should not fire yet.** *(Round-1 judgement. Superseded by round 2, which established the
cause — Task 3 is now unblocked.)* It is written to "fix the classified cause"; the cause is not
established, and the boot-proximity discriminator is new information that postdates the plan.
Task 3's defensive half — guaranteeing no pending state renders blank, then removing the
breadcrumbs — remains valid regardless.

# Round 2 — layout measurement (2026-07-31, runs 5 and 6)

The Web Inspector console does not accept keyboard input against this WKWebView, so the
`getBoundingClientRect()` measurement was added to the code instead and routed through the same
log path. It resolved the question immediately.

## The measurement

| | Blank render (20:14:13) | Correct render (20:09:58, `.old`) |
|---|---|---|
| `viewport` | **1280x268** | **1280x268** |
| `div.loginPage` | 1030x**23323** | 1030x**770** |
| `main.content` | 1030x**23323** | 1030x**770** |
| `div.App` | 1270x**23323** | 1270x**770** |
| React root div | 1270x**23323** | 1270x**770** |
| `body.marine` | 1280x268 | 1280x268 |
| display / visibility / opacity | `grid` / `visible` / `1` | `grid` / `visible` / `1` |

Everything is present, visible and fully opaque in **both** cases. Nothing is hidden, collapsed or
transparent. The single difference is **height: 23323 px versus 770 px.**

## The blank screen is not blank

`.loginPage` is a grid with two stacked children in the same cell:

- `.loginBackground` — `height:100%`, a full-bleed background image at **`opacity: 0.3`**
- `.loginContentWrapper` — `height:100%`, `display:flex; flex-direction:column; justify-content:center`

The wrapper **vertically centres** its content in `.loginPage`. At 23323 px tall the login tiles
sit at roughly **y=11 660**, while the viewport shows only the **top 268 px**. What remains on
screen is `.loginBackground` alone — a dim background image with nothing on it.

So F-10 is not a render failure at all. **The content renders correctly and is parked ~11 000 px
below the fold.** This is consistent with every earlier negative result: React committed, the
component mounted, three render passes ran, and no error was thrown — because nothing failed.

At `t+1500ms` the blank render additionally shows `top=-198`, i.e. the document had scrolled 198 px
further down on its own, which is why waiting does not help.

## Boot proximity is FALSIFIED

The round-1 hypothesis — blank at 5–6 s after launch, correct at 45 s — does not survive. Run 5
booted at 20:12:44 and navigated at **20:14:13, 89 seconds later**, and was blank. Time since boot
is not the discriminator. Recorded here so it is not re-proposed; the round-1 section above is
left intact rather than rewritten, since its *negative* results still stand.

## Second, independent finding: the viewport is 268 px tall

`viewport`, `body` and `html` are **1280x268 in every sample, blank or correct**. `.App` sets
`min-height: 100vh`, so the entire layout is being computed against a 268 px viewport. Even the
*correct* 770 px render is therefore clipped to its top third inside a scrolling body.

This is a separate defect from the runaway height and does not depend on it. It is almost
certainly why the login screen has "intermittently rendered blank before": a 770 px page in a
268 px window is already showing only its top, and any additional growth pushes the centred
content out of view entirely.

## CORRECTION — the 268 px viewport is NOT part of F-10

Run 6 (20:20:00) reports `viewport=1280x768`, `body`/`html` = 1280x768 — **normal** — and the
operator confirms the window looks normally sized. F-10 reproduced anyway, with the identical
23323 px runaway.

The 268 px viewport seen in runs 3–5 was therefore **transient** (the window still sizing when
those samples were taken) and is **not** a precondition for F-10. The "second, independent finding"
recorded above overstated it: a short-lived mis-sized viewport during boot may still be worth its
own ticket, but it is not this bug and does not explain it. Recorded as a correction rather than
silently removed.

# ROOT CAUSE — `.loginBackground`

The downward probe named it in one run.

```
children .App               -> aside.Sidebar=240x768@0 | main.content=1030x23323@0 | div.controller=1030x0@768
children .loginPage         -> div.loginBackground=1030x23323@0 | div.loginContentWrapper=626x770@11277
children .loginContentWrapper -> div.runnerList=626x701@11277 | button.goToLibrary=196x39@11998
```

| Element | Height | Verdict |
|---------|--------|---------|
| `aside.Sidebar` | 768 | normal |
| `div.controller` | 0 | normal |
| **`div.loginBackground`** | **23323** | **the runaway** |
| `div.loginContentWrapper` | **770** | **correct — it was never broken** |
| `div.runnerList` | 701 | correct |

**`.loginContentWrapper` is correctly sized the whole time.** It is simply positioned at
**`top=11277`**, which is exactly the centre of a 23323 px row:
`23323/2 − 770/2 = 11276.5`. The content is not missing, mis-rendered or unstyled — it is
centred inside a box 30× too tall and therefore ~11 000 px below the viewport.

The runaway is `.loginBackground`: a **decorative, empty** div declared

```css
.loginBackground { height: 100%; width: 100%; grid-column: 1; grid-row: 1; opacity: 0.3; }
```

It sits in the same grid cell as the content and its `height: 100%` resolves against a row whose
height is itself derived from its children — a circular percentage chain that runs
`.App (min-height:100vh, 1fr row)` → `.content (min-height:100%)` → `.loginPage (height:100%)` →
`.loginBackground (height:100%)`. Nothing in that chain has a definite basis. When WebKit resolves
it the intended way the whole stack collapses to the content height (**770 px** — the correct
render). When it resolves the other way `.loginBackground` balloons, sets the grid row, and
centres the content off-screen.

The value is **stable across all three samples** (sync, paint, t+1500 ms), so this is not an
iterating feedback loop — it is one wrong resolution, decided once per layout and then fixed.
That matches the observed behaviour exactly: it never self-corrects, and a remount re-runs the
resolution, which is why navigating away and back "fixes" it.

**A purely decorative background is sizing the layout.** That is the defect.

## Old — which child drives `.App` to 23323 px

The ancestor chain terminates at `html`; it proves `.App` is the runaway but not which of its
three grid children (`offline-message`, `Sidebar`, `content`, `controller`) causes it. Note
`.App .Sidebar` is `max-height: 100vh` + `position: sticky` and `.App .content` is
`min-height: 100%` against a `1fr` row — a percentage-against-indefinite chain of exactly the kind
that can iterate under a layout race. 23323 / 770 ≈ 30, which has the shape of a feedback loop
rather than a single bad value, but that is **unverified**.

A downward one-level probe of `.App`, `.loginPage` and `.loginContentWrapper` has been added to
name the origin instead of inferring it.
