# Phase 34.4.1 Plan 04: Reveal-POST Rust Transport Summary

**`humbleRevealKey` now issues its POST from a hidden Tauri WebviewWindow's own `fetch()` — a real WKWebView network stack — via a JSON-escaped injected script and a cancelled-navigation exfil channel to the RFC 2606 `.invalid` host, closed on every exit path, feeding the unchanged `RevealResponseSchema`.**

## Performance

- **Duration:** ~40 min (not precisely timestamped at start; commits landed within the same session)
- **Completed:** 2026-07-27
- **Tasks:** 2/2
- **Files modified:** 10 (3 in Task 1, 7 in Task 2; `netStub.test.ts` and `tauriShellSource.test.ts` were not in the plan's declared `files_modified` list but required follow-through edits — see Deviations)

## Accomplishments

- Added the `humble_reveal_post` Rust dispatch arm: parses/validates five args, opens a hidden on-demand `WebviewWindow` on the Humble origin, injects a JSON-escaped script that runs the POST via the page's own `fetch()`, and receives the result through an `on_navigation` intercept that cancels before the exfil URL (`https://gamelib.invalid/...`) can resolve anywhere.
- Proved the arm's pure logic (arg validation, script templating/escaping) with 14 new `#[cfg(test)]` cases (37 total in `main.rs`, all green) — including a round-trip proof that a body containing a double quote, single quote, backslash, and `</script>` sequence survives `serde_json::to_string`/`serde_json::from_str` intact, and that a naive `format!("'{}'", value)` interpolation is never produced.
- Wired the TypeScript side: `LoginWindowSeam.revealPost()`, its `rustInvoke`-backed implementation, and `humblePostRequest`'s branch onto it — Electron's `net.request` path is byte-for-byte unchanged; the Tauri path feeds the exact same `RevealResponseSchema`/`HumbleTransportHttpError` contract.
- Retired `electronStub.net.request`'s stale "Phase 34.4.1... See D-06" error message (that seam now exists) while keeping the stub's logged-no-op shape, and updated the one existing test file (`netStub.test.ts`) that pinned the old wording.

## RESEARCH.md Open Question 1 (discharged by this plan, Task 1)

**Question:** does `on_navigation`'s cancellation (`return false`) actually prevent the page's network layer from attempting the request at all, or does it merely stop the WKWebView-level navigation after some earlier request already fired?

**Observed answer this session:** NOT directly observed in-app. Triggering a real reveal requires an authenticated Humble session (`HumbleUser.getCredentials()` gating `HumbleLibrary.revealKey()`), which this automated, non-interactive execution session has no access to — there is no live Humble login available to drive the actual reveal flow end-to-end.

**What WAS run, as a bounded, independent sanity check** (not a substitute for the in-app observation, but supporting evidence for the "worst case is a local resolver miss" claim):
```
$ dscacheutil -q host -a name gamelib.invalid   # exit 0, empty result
$ host gamelib.invalid
Host gamelib.invalid not found: 3(NXDOMAIN)
```
This confirms, independent of the Tauri app, that `gamelib.invalid` genuinely does not resolve on this network — consistent with RFC 2606's `.invalid` TLD reservation. It does NOT observe whether `on_navigation`'s cancellation itself fires before or after any network attempt inside the live app.

**Disposition:** per the plan's own explicit allowance ("If the check cannot be run at this point... hand it to the plan `34.4.1-08` live gate's item 4 — do not silently drop it"), this is handed off to `34.4.1-08`'s live gate item 4. Reproduction commands for that gate: trigger one real `humbleRevealKey` call against an authenticated Humble session under `pnpm tauri:dev`, then run `dscacheutil -q host -a name gamelib.invalid` and `sudo log show --last 2m --predicate 'subsystem == "com.apple.network"' | grep -i invalid` (or a `tcpdump` if inconclusive) immediately after.

RESEARCH.md **Open Question 2** (hidden-window `.visible(false)` cookie/eval parity) is unaffected by this plan and remains dispositioned `DEFERRED-TO-LIVE-GATE` — `34.4.1-08`'s gate item 4 is the code path that judges it; this plan's `humble_reveal_post` arm is exactly the arm under test there.

## Every Return Path Closes the Window (D-08)

Verified by direct read of the `humble_reveal_post` arm (`src-tauri/src/main.rs`):
- **`reveal_post_args` rejects (bad-args):** no window was ever created — nothing to close.
- **`WebviewWindowBuilder::build()` fails:** no window exists — nothing to close.
- **`window.eval(&script)` fails:** `window.close()` called immediately, then the error is returned (close site 1).
- **`rx.recv_timeout(REVEAL_POST_TIMEOUT)` returns `Ok`, a parse failure, OR `Err` (timeout):** a single `window.close()` call runs immediately after the `recv_timeout`, before the `match` that produces any of these three outcomes (close site 2) — covering success, script-parse-failure, and timeout in one place.
