# Phase 34.4.1 Plan 01 — Blocking Live Gate (REQ-34.4.1-12)

This document is a **contract**, written before any live work begins, not a report. Per
D-10 (carrying 34.3's D-13 and 34.4's D-08), this gate is **BLOCKING**: any FAIL in the
4 named items below means the phase does not close and a gap cycle inside 34.4.1 is the
next step — no advisory mode, no pre-authorized override, no deferred UAT entry.

34.4 D-09 had to write into its own gate the standing statement: *"there is no Tauri path
to create a Humble session."* Item 1 below is precisely the thing that statement declared

## Preconditions

**Tick off in order. An unstated precondition is exactly how a gate gets skipped and
becomes UAT debt (Phases 21, 30, 34.2) — 34.4 D-09's lesson.**

1. `pnpm tauri:dev` is running, built from a clean tree (no stale `src-tauri/target`
   artifacts from an in-flight code change).
2. The operator holds real, working Humble Bundle credentials (email + password, and
   access to whatever Humble Guard / email one-time-code channel Humble requires at
   login time).
3. **Start from NO stored Humble credential.** Before doing anything else, inspect
   `~/Library/Application Support/GameLib/humble_store/config.json` (the Humble
   credential store, same family as `steam_store/config.json` referenced in
   `34.4-LIVE-GATE.md`). Confirm it is either absent, or present with `isLoggedIn: false`
   and no `sessionCookie`/credential fields populated. Capture a screenshot or a
   `cat ~/Library/Application\ Support/GameLib/humble_store/config.json` transcript of
   this absent/logged-out state **before** starting item 1 below. If a stale credential
   is found, remove it and re-verify absence before proceeding — a gate that starts from
   an already-authenticated session cannot prove REQ-34.4.1-02/-12's "from scratch" claim.
4. At least one **UNREVEALED** Humble key exists in the connected account's library, so
   item 4 (`humbleRevealKey`) has a real key to attempt against. Confirm this via the
   Humble Keys page (or `humble/adapter.ts`'s gamekeys read) before starting, not
   assumed.
5. Sidecar output for every item below is read from
   `~/Library/Logs/GameLib/gamelib.log`, **NOT** the `pnpm tauri:dev` terminal. Keep
   `tail -f ~/Library/Logs/GameLib/gamelib.log` open in a second window for the whole
   gate run. Electron `app.whenReady()` initializers are **not** auto-run in the sidecar,
   so anything that looks uninitialised there is a real finding, not a test-setup
   problem.
6. A non-Humble cookie of a **known name and domain** has been planted (or is already
   observed present) in the app-wide platform cookie jar before item 3 runs — e.g. visit
   any other `https://` origin in a Tauri child window first, or note an existing
   non-`humblebundle.com` cookie already in the jar from a prior session. This is the
   control that lets item 3 prove the clear was domain-**scoped**, not a blanket wipe: a
   blanket `clear_all_browsing_data()` would also pass a naive "no humblebundle.com
   cookie remains" check while silently destroying every other storefront's session
   (Pitfall 3 / T-34.4.1-03).

### Item 3 — `humbleDisconnect` leaves no `humblebundle.com` cookie; re-login is genuinely fresh (REQ-34.4.1-06, REQ-34.4.1-12)

**What to do:** From the signed-in state (item 1/2), trigger Humble disconnect.

**What to observe:** The stored Humble credential is cleared AND the `humblebundle.com`
cookie(s) are removed from the app-wide platform jar (`humble_login_cookies` against
`humblebundle.com` reports `total` unchanged or reduced appropriately but zero `matched`
entries for the session cookie) — while the precondition-6 planted non-Humble cookie
**still exists** in the jar afterward.

**Evidence required:** BOTH of the following, not just one:
  (a) A `humble_login_cookies` read (or equivalent) confirming no `humblebundle.com`
      cookie remains after disconnect.
  (b) A separate read confirming the precondition-6 non-Humble cookie **survives** the
      disconnect — this is the proof the clear was domain-scoped and not a blanket wipe
      (D-08 / Pitfall 3). A gate that only checks (a) would also pass for a
      `clear_all_browsing_data()` implementation, which is exactly the defect D-08
      forbids.

### Item 4 — `humbleRevealKey`'s real outcome recorded, pass or 403 (REQ-34.4.1-05, REQ-34.4.1-12)

**What to do:** Using the precondition-4 unrevealed key, attempt a real reveal through
the in-webview POST mechanism (D-07/D-08).

**What to observe:** Either the reveal succeeds (the key's redeemable value is returned)
or it fails with a declared, classified outcome (e.g. a Cloudflare 403).

**Evidence required:** The actual HTTP outcome and the classified result the sidecar
surfaces to the UI. **A 403 is a VALID, DECLARABLE result and is NOT a phase failure** —
D-07's own framing already expects Cloudflare Bot Management may block this exactly as it
blocked axios/reqwest in rounds 1–6 of the `humble-reveal-key-fails` investigation.
Reveal is live-testable at all — unlike 34.4 D-08's refused `redeemSteamKey` — because per
Phase 14's D-30 realignment, Humble's `redeemed_key_val` field being populated means the
key was **revealed, not activated**: it is irreversible at Humble's end (the key cannot
be un-revealed) but not destructive to the user's ability to use it, and Mark-as-redeemed
in GameLib remains a local-only, always-undoable overlay regardless of the reveal
outcome.

## What this gate falsifies

Phase 34.4's own live gate (`34.4-LIVE-GATE.md`) recorded, as decision D-09, the standing
statement that **"there is no Tauri path to create a Humble session until 34.4.1 lands."**
That statement was true when written — Phase 34.4 shipped Humble's other 15 IPC channels
but explicitly left the login/cookie mechanism to this phase. Item 1 of this gate is the
direct test of that statement's continued truth: if item 1 PASSes, a real Tauri path to a
Humble session now exists, and 34.4 D-09's statement is FALSE going forward. Per
REQ-34.4.1-10, plan `34.4.1-07` is responsible for striking that statement from the
record (via `34.4.1-PORTED-CHANNELS.md` and/or an explicit dated note against 34.4 D-09)
once — and only once — this gate's item 1 is recorded PASS, rather than leaving a falsified
claim standing silently in an earlier phase's artifact.
