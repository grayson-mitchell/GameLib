#### DEFECT F-1 (BLOCKING) — the Humble session cookie is persisted in PLAINTEXT under Tauri

This item's stated evidence requirement is "the store now holding an **encrypted** `sessionCookie`
with `isLoggedIn:true`." The store holds an **unencrypted** one. Recorded as a defect rather than
rounded into the PASS (T-34.4.1-40).

Log line, emitted twice at the moment of persist:
```
(17:39:40) [WARNING]: [Backend]: safeStorage unavailable — storing Humble session in plaintext (degraded encryption)
```

**Root cause — structural, not environmental.** This is NOT a denied Keychain prompt or a
`PlatformFailure(-128)` (Phase 28's known shape). Traced to source:

1. `src/backend/humble/user.ts:1` — `import { safeStorage, session } from 'electron'`.
2. In the sidecar that import resolves to `src/backend/sidecar/electronStub.ts:489`, where
   `isEncryptionAvailable` is hardcoded **`(): boolean => false`** and `encryptString`/
   `decryptString` **throw**. The stub says so in its own comment: *"Phase 28 graduated this API:
   real Keychain storage now lives in SidecarKeyringTokenStore ... safeStorage itself is
   intentionally left dead in the sidecar — use getTokenStore()"*.
3. Therefore `encryptionAvailable()` (`user.ts:78`, a `try/catch` returning `false` on throw) can
   only ever return `false` under Tauri, and the plaintext branch at `user.ts:88` is the **only
   reachable branch**. `user.ts:99`'s `safeStorage.encryptString(...)` is dead code in the sidecar.

**Corroborating measurement:** the pre-gate Electron-era store (Jul 27, preserved in the recovery
backups) recorded `encryptionDegraded: false` with `sessionCookie` len **314** and `csrfToken` len
**58**. The Tauri-created store records `encryptionDegraded: true` with lengths **208** and **29** —
shorter, consistent with plaintext rather than base64 ciphertext carrying the `HUMBLE_TOKEN_PREFIX`.

**Scope — one confirmed, one same-shape-unverified, one NOT affected.** Enumerated by direct call
site rather than assumed:

| Call site | Secret | Status |
|---|---|---|
| `src/backend/humble/user.ts:1,78,99,117` | Humble session cookie | **CONFIRMED plaintext, live, this gate** |
| `src/backend/steamgrid/secureKey.ts:1,8,27,40` | SteamGridDB API key | Identical direct-import shape; **not exercised by this gate** — same-shape, unverified live |
| `src/backend/storeManagers/steam/tokenStore.ts` | Steam refresh token | **NOT affected.** Phase 28's `TokenStore` interface seam applies: `ElectronTokenStore` is only the Electron impl, and the sidecar installs `SidecarKeyringTokenStore` via `setTokenStore()`. |

**Assessment:** a Tauri-rearchitecture regression — the Electron build encrypted this cookie, the
Tauri build does not. It is invisible to the whole automated suite (3279/3279 green at gate time,
`cargo test` 40/40) because nothing asserts the *live sidecar* resolution of the `electron` import.
This is precisely the class of failure the gate exists to catch, and the second time in this
project a live gate has found what a fully-green suite could not (34.4's unreachable channel being
the first). **Disposition: gap-cycle item inside 34.4.1.** No fix attempted in this plan — plan 08
is run-and-record, and inventing a keyring migration at gate time would ship unproven code.

#### FINDING F-4 (non-blocking, UX) — the login window is under-specified

in-app modal webview instead of a separate OS window was considered and is explicitly **out of
scope for 34.4.1** — that is a design change, not a defect fix.

#### DEFECT F-6 (BLOCKING) — the Tauri disconnect is a strict subset of the Electron disconnect

Root cause is an **objective asymmetry between the two branches of the same function**,
`src/backend/humble/user.ts` `disconnect()`:

| Branch | Wipe steps |
|---|---|
| Electron (`seam === null`, `user.ts:796-804`) | **5** — `clearStorageData()`, `clearCache()`, `clearAuthCache()`, `clearHostResolverCache()`, `clearData()` |
| Tauri (`seam !== null`, `user.ts:806-838`) | **1** — `seam.clearCookies(label, 'humblebundle.com')` |

And the Rust arm that step calls (`src-tauri/src/main.rs:1067-1092`) does exactly one thing:
enumerate `window.cookies()`, filter by `cookie_domain_matches`, and `delete_cookie` each match. It
contains **no storage-clearing capability at all**.

Consequence: under Tauri, `localStorage`, `sessionStorage`, IndexedDB, service workers and HTTP
caches all **survive a disconnect**. Humble's own web application restores a session from what
remains, which is precisely the auto-signed-in page the operator observed. Electron's
`clearStorageData()` covered all of these; nothing replaced it.

**Severity: this is a functional AND privacy regression versus the Electron build — "disconnect"
does not actually disconnect.** A user who disconnects Humble on a shared machine reasonably
believes their session is gone; the next login window signs the next person straight in.

**Confidence:** the code asymmetry is an objective, verifiable fact and it is the leading
explanation for the observation. It is *not* conclusively isolated — no instrumented A/B was run
(e.g. clearing storage by hand and re-testing), because plan 08 is run-and-record and building the
instrument would be implementation. Isolation belongs to the gap cycle.

**This inverts the concern 3(b) was written to guard against.** 3(b) exists to prove the clear was
not *too broad* (a blanket `clear_all_browsing_data()` wiping other storefronts' sessions —
D-08/Pitfall 3). The live answer is the opposite failure: the clear is **too narrow**. Both the
over-broad and under-broad risks are now on the record, and a fix must satisfy both at once —
clear Humble's storage as well as its cookies, while still leaving other origins untouched. That
constraint is the real output of item 3.

**Result — 3(b):** BLOCKED-UNOBSERVABLE (see amendment above; not attempted live) — gap-cycle item.

**Item 3 overall:** cannot be a clean PASS while 3(b) is unobservable.
