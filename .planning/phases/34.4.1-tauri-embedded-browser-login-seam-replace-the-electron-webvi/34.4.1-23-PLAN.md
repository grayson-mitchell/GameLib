<objective>
Close **F-6's Defect B**, the blocking defect: `humble_login_clear_cookies` reports success while
deleting nothing.

Purpose: the live gate measured 25 `delete_cookie()` calls, every one returning `Ok(())`, and the
jar shrank by **one**. All 23 Humble cookies survived, so Humble re-authenticated from them and the
four correctly-built wipe steps bought nothing. Two independent things are wrong in that arm and
both are fixed here:

1. **The reported count is an attempted count.** `let deleted = matching.len()` (`main.rs:1254`) is
   computed BEFORE the delete loop runs. It can never report failure. This is the reporting half of
   the same "resolves without doing the work" shape that `navigator.clipboard` and `queryLocalFonts`
   already exhibit under WKWebView — the third instance in this phase.
2. **`delete_cookie()` does not reliably delete.** wry's implementation
   (`wry-0.55.1/src/wkwebview/mod.rs:1248-1267`) hands `WKHTTPCookieStore.deleteCookie` a
   **freshly reconstructed** `NSHTTPCookie` from `cookie_into_wkwebview()`, and the completion
   handler fires unconditionally — "the operation was processed", not "a cookie was found". The
   identical bug shape (a Cookie↔NSHTTPCookie round trip losing a property and silently breaking
   the store's internal match) is a real, previously-filed WebKit defect,
   [bugs.webkit.org #184938](https://bugs.webkit.org/show_bug.cgi?id=184938).

The fix, on macOS, bypasses the round trip entirely: reach the webview's **live**
`WKWebsiteDataStore` through Tauri's documented `with_webview()` escape hatch and delete via
`fetchDataRecordsOfTypes` + `removeDataOfTypes(for:)`, filtered by `WKWebsiteDataRecord.displayName`.
It never reconstructs a cookie object, so the identity-mismatch class structurally cannot recur, and
it stays domain-scoped, which `clear_all_browsing_data()` — wry's only bulk alternative — is not.
**D-08's "scoped by domain, never a blanket wipe" is non-negotiable and binds this fix**: the jar is
app-wide and will hold Epic/GOG/Amazon cookies once Phase 34.5 lands.

**`Ok(())` is not proof (binding constraint 2).** The arm must return a count derived from a
post-removal **re-read** of the jar, not from any API's return value. Every acceptance criterion in
this plan asserts an observable state change or a source property — never a returned status.

**Adjacent already-present code this plan verifies (binding constraint 1).**
`storeManagers/legendary/user.ts`'s `clearEpicCookies` calls the **exact same** Rust arm — shared
code, not merely similar shape (research Pitfall 4). It has carried this defect since Phase 34.5
plan 06 and nothing has ever verified it. Task 3 gives it the same verified-count logging Humble
has, so the shared fix is observable at BOTH call sites rather than assumed correct at the second by
inheritance. **This is a deliberate cross-phase edit into open Phase 34.5**, declared here in
frontmatter and in the task, exactly as the last cycle's equivalent edit was declared.

Output: a macOS cookie clear that actually clears, an honest measured count, a declared and
unchanged Linux/Windows path, and a second call site that is verified rather than inherited.
</objective>

**The count contract this plan establishes.** The census in `humble/user.ts` evaluates
`deleted == matched-before` where `matched-before` is a **cookie** count. So the arm must keep
returning a cookie count, not a website-data-record count. The honest way to produce one:
read the matching cookie count, remove the matching data records, re-read the matching cookie
count, and return `before_matching - after_matching`. That number is measured after the operation
and cannot report a success that did not happen.

**D-08, verbatim from `34.4.1-CONTEXT.md`:** *"Scoped by domain, never a blanket wipe — the same jar
will hold Epic/GOG/Amazon cookies once 34.5 lands, and clearing those would silently sign the user
out of storefronts they never touched."* `clear_all_browsing_data()`
(`wry-0.55.1/src/lib.rs:2137`) is disqualified and `main.rs`'s own comments already forbid it
appearing anywhere in the file.

**Platform note (D-09 / REQ-34.4.1-13).** wry's `webview2` (`webview2/mod.rs:1681`) and `webkitgtk`
(`webkitgtk/mod.rs:1086`) `delete_cookie` implementations are separate code paths with their own
conversions. This bug's root cause is **not proven to exist there**, and the fix is macOS-specific.
Linux/Windows keep the existing path and must be DECLARED as such, not silently assumed fixed or
silently assumed broken.
