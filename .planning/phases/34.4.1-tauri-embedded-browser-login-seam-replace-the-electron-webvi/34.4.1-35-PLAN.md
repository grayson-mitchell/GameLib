## Task 1 — Write the gate contract BEFORE any live work

Create `34.4.1-LIVE-GATE-RERUN-4.md` with **empty result slots**, following the shape of runs 1–3.
Writing results into a contract authored after the fact is how a run manufactures its own evidence.

### Precondition 6 is UNSTRUCK. This is the whole point of the plan.

Run 3's contract **struck** the planted non-Humble cookie as moot, reasoning that plan 17's census
*"supplies the evidence without it."* That conflated the **measuring apparatus** with the **thing
measured**.

The consequence, measured: `survivingNonHumble=0` was **arithmetically forced, not passing** —
`before total=34` equalled `matched=34`, so no non-Humble cookie existed for the delete to spare.
Item 1's from-scratch reset then guaranteed that single-origin condition. **The contract instructed
the operator not to plant a cookie, then required an outcome only a planted cookie could produce.
No action available during the run could have satisfied it.**

So the contract must now state, explicitly:

- **Plant at least one non-Humble cookie of KNOWN name and KNOWN domain before item 3(b).**
- The planted cookie and the census are **complements, not alternatives**.
- Item 3(b) PASSES only if, after the clear, `matched-after == 0` **and** the planted foreign cookie
  **survives by name**. A `survivingNonHumble` count alone is not sufficient — assert the *identity*
  of the survivor, not just a non-zero tally.
- **Record the precondition state (`before total`, `matched`) in the result, so a future reader can
  tell a real pass from an arithmetically forced one.** That distinction is what run 3 lacked.

### Anti-vacuity, stated in the contract itself

For every item, name the observation that would make it FAIL. An item whose pass condition is
satisfiable by doing nothing is not a gate. Run 3 shipped one such item and it took a cycle to see.

## Task 4 — Write `34.4.1-VERIFICATION.md` — the file this phase has never had

The phase closed 2026-07-31 on a live gate and `/gsd-verify-work` never ran. Its absence is why
34.4.1 contributes **zero** to `gsd-sdk query audit-uat` and why ten findings sat unowned for 23
days. **Creating it is a required deliverable of this cycle, independent of the gate's verdict.**

Three known silent failure modes govern how it is written. All three are measured, not theoretical:

1. **`status` must be `human_needed`, never `gaps_found`.** The tool admits a VERIFICATION.md when
   status is `human_needed` OR `gaps_found`, but only *emits* items when status is `human_needed` —
   so `gaps_found` is admitted and then always yields **zero** items, and the phase vanishes from the
   report entirely.
2. **Resolved items must be MOVED to a separate `human_verification_resolved` key**, never annotated
   in place. The tool counts every entry in `human_verification` regardless of any `result:` field.
3. **An empty `human_verification: []` with `status: human_needed` makes the tool scrape the document
   BODY** and report prose headings as phantom open items. If the array empties, flip `status` too.

Record honestly which items are discharged, which are relocated (and to which phase), and which
remain open. **Relocated is not resolved** — use a distinct key so a future reader cannot mistake one
for the other.
