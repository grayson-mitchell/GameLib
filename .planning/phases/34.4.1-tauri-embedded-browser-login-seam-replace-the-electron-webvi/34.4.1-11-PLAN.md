<objective>
Make the keyring seam multi-slot via a compile-time ALLOWLIST, so a non-Steam secret can be
stored in the OS keyring without clobbering the Steam refresh token.

Purpose: **D-GAP-01, binding.** F-1's obvious fix — pointing `humble/user.ts` at
`getTokenStore()` — is WRONG. `src-tauri/src/main.rs:161-162` hardcodes one
`KEYRING_SERVICE`/`KEYRING_ACCOUNT` pair, all four arms use it, and `keyring_set` takes only the
secret with no key parameter. That is deliberate, per **threat T-28-03**: *"the sidecar must not
be able to address an arbitrary Keychain entry."* Writing the Humble session cookie through the
existing arms would overwrite the Steam refresh token's Keychain entry — a silent Steam sign-out
with no error path, strictly worse than the plaintext F-1 describes.

Output: a slot-aware keyring seam where the sidecar names a slot, Rust validates it against a
fixed compile-time set and maps it to a constant account string, and an unknown slot is a hard
error. T-28-03 is preserved, not reopened: the sidecar still cannot address an arbitrary entry,
only one of a fixed set.

**This plan stores no new secret.** It only makes the seam capable of holding more than one.
Plan 12/13 migrate Humble onto it; plan 14 handles SteamGridDB.

Rejected designs, recorded so they are not revisited (D-GAP-01):
- *Dedicated `keyring_humble_*` channels* — zero regression risk to the Steam arms, but
  duplicates ~60 lines of Rust per secret and does not scale to F-1b.
- *Free-form account argument from `args`* — smallest diff, but explicitly reopens T-28-03; a
  compromised sidecar could read or overwrite any GameLib Keychain entry. Declined.
</objective>
