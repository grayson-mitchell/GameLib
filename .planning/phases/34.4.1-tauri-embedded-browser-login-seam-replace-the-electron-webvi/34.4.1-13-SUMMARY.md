# Phase 34.4.1 Plan 13: Keyring-backed Humble secret store + plaintext migration Summary

**Closes F-1 (BLOCKING) at the code level: the sidecar now installs a keyring-backed Humble secret store over the humble-session/humble-csrf slots, migrates any existing plaintext session cookie into the keyring via a verified write->readback->compare, and clears the keyring on disconnect.**

## Accomplishments

- `SidecarHumbleSecretStore` implements plan 12's `HumbleSecretStore` seam over plan 11's slot-parameterized keyring store, binding `sessionCookie` -> `humble-session` and `csrfToken` -> `humble-csrf`. Every method is total (mirrors `SidecarKeyringSlotStore` exactly): a `null` `keyring_get` result is the healthy first-run case (not logged), a genuine failure logs exactly one warning naming the channel, and no method ever logs a secret value.
- `installSidecarHumbleSecretStore()` installs the store via `setHumbleSecretStore()` and logs an observable confirmation line to `gamelib.log`:
  ```
  [bootstrap] Humble secret store installed: keyring-backed (humble-session/humble-csrf slots)
  ```
  **This exact line is what plan 20's live-gate re-run must grep for** to confirm the keyring path (not the Electron-default plaintext fallback) actually ran.
- One-time plaintext-to-keyring migration, run (fire-and-forget) at install time: for each of `sessionCookie`/`csrfToken` independently, read the `configStore` plaintext -> write it to the keyring -> read it back -> compare -> only on an EXACT match, delete the `configStore` key and set `encryptionDegraded` to `false`. A rejecting write, a rejecting readback, or a mismatched readback all leave the plaintext in place, keep the user signed in, and log exactly one warning naming the failure mode -- never the secret value. A `csrfToken` migration failure cannot strand a successfully-migrated `sessionCookie` (and vice versa).
- `disconnect()` in `humble/user.ts` now calls `getHumbleSecretStore().clearSecrets()` immediately after the existing `configStore.clear()` -- WR-02/T-10-07's "credential wipe first" ordering is unchanged and load-bearing; the new call is guarded so a rejection is logged and swallowed, never able to abort disconnect() or precede the configStore clear.
- 22 new/updated tests in `humbleSecretStore.test.ts` (totality, slot isolation, install observability, and the full migration failure matrix) plus 2 new tests in `user.test.ts` proving disconnect() ordering and rejection-swallowing.

## Decisions Made

- `isAvailable()` checks only the `humble-session` slot's keyring reachability rather than probing both slots -- both live in the same OS Keychain under the same service identity (only the account name differs per `keyring_account()` in `src-tauri/src/main.rs`), so one totalized check is representative and avoids an unnecessary second round-trip on every availability probe.
- Migration's write/readback calls go through `requestRustInvoke` directly rather than the totalized `SidecarKeyringSlotStore.setToken`/`getToken` -- those methods already swallow their own failures into a single warning, which would have made it impossible for migration to distinguish "write rejected" from "readback rejected" from "readback mismatched" without either double-logging or losing the distinction the threat model (T-34.4.1-57) requires.
- `encryptionDegraded` is only ever explicitly set to `false` on a successful migration; a failure path never explicitly sets it `true`. The flag is already `true` on the Tauri-created plaintext shape this migrates (set by the existing `storeHumbleSecret()` code path via `isAvailable()`), so leaving it untouched on failure correctly preserves the existing degraded signal to the UI without introducing a second write site for the same flag.
