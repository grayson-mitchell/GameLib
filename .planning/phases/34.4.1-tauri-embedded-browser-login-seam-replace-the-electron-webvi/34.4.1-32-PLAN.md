# Plan 34.4.1-32 — D-29-02 and D-29-03: the Humble adapter's observability gaps

**Wave 2.** Both items live in `src/backend/humble/adapter.ts`, which is why they share a plan.
They are **not** the same defect — see below.

---

## The discriminator is already settled — do not re-litigate it

`D-29-02` demanded, before either it or D-29-01 was fixed: *determine whether Manage Accounts'
update path is gated on `getAccountIdentity`'s result.*

**Settled by code reading (see `34.4.1-GAP-CYCLE-3-ANALYSIS.md`): it is not.**
`HumbleUser.finishLogin` (`src/backend/humble/user.ts:678`) gates acceptance on **`getGamekeys`** —
*"Only a gamekeys-endpoint 'ok' proves login (D-16)"* — and performs `storeHumbleSecret` +
`configStore.set('isLoggedIn', true)` on that signal alone. `getAccountIdentity` runs afterwards,
best-effort, inside a `try`/`catch`.

**Therefore D-29-01 and D-29-02 are two unrelated defects that coincided in one scrollback.** D-29-01
is independently fixed. This plan does not close it and must not claim to.

---

## Task 1 — D-29-03: instrument the reveal success path

Today the log records `Humble reveal: calling adapter (...)` and then **nothing**. Failure paths are
instrumented; success is silent. The consequence is the reason this is filed rather than shrugged
off: **live gate item 4's central outcome — did the real network call work — was not verifiable
from the log at all**, and rested entirely on the operator's screen. A future automated or
semi-automated gate cannot confirm that item without a human present.

Add **one INFO line on the success path** carrying HTTP status and duration.

**Explicitly no body, no revealed value, no cookie.** The redaction discipline here is proven
correct — the revealed value appears in no log and no document — and must survive this change.

**Test it in both directions.** A test that asserts the line appears is half the job; add one that
asserts the revealed value does **not** appear in any log sink, and red-prove it by temporarily
logging the value and watching the test fail. A redaction test audited through one caller found one
leak on this project four times; assert over the sink, not over one call site.

## Task 2 — D-29-02: establish, or explicitly fail to establish, the 404

```
status=404 contentType=text/html; charset=utf-8 bodyIsString=true looksLikeHtml=true bodyLength=232
```

Two candidate explanations, **neither established** at filing: the endpoint path has moved, or an
interstitial is answering in its place. `looksLikeHtml=true` on a 404 fits both.

Determine which. If it cannot be determined without a live authenticated session, **say so and stop**
— record it as a live-gate observation for plan 35 rather than guessing. This phase's own history is
the argument: *correlation shipped as cause* cost F-10 nine live runs.

Whatever the outcome, the fetch stays **best-effort**: it must never gate login acceptance. If the
endpoint has genuinely moved, correcting it is in scope; making the UI depend on it is not.
