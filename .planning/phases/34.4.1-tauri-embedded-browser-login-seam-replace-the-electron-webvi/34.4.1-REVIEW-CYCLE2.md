### B-CR-01 downgraded: critical → info

Lane B's factual claim is **correct**. `electronReachLedger.test.ts`'s docstring states "Plan
35-16 cleared both," while `BASELINE_ELECTRON_REACHING_MODULES` (:360-373) still contains
`'src/common/types.ts'` and `'src/common/types/ipc.ts'`, with adjacent comments describing the
pre-35-16 state ("35-16 owns this", "35-18 must expect these two until 35-16 clears them"). A
shipped comment contradicts shipped code in the same file.

Its **impact analysis is wrong.** Lane B concluded the growth tripwire would silently accept a
regained `electron` import on those two paths. The baseline array has exactly one consumer —
the growth tripwire at :547-562 — and the *next test in the same file*, sharing the same
`beforeAll` measurement, asserts:

```js
expect(measured.size).toBe(0)   // :578, "anti-degradation"
```

That is strictly stronger than "every measured module is baselined." If either path regained an
`electron` import, the growth tripwire would pass, and the anti-degradation test would fail with
`size = 1`. The regression is caught loudly one test later. Post-cutover, `measured.size === 0`
subsumes the growth tripwire entirely, which makes the stale baseline entries **vestigial, not
dangerous**.

Residual risk, and the reason this stays a recorded finding rather than being dismissed: the
staleness starts mattering again the moment anyone reverts the `size === 0` inversion. The
in-file comment already warns against deletion ("invert-don't-delete"), so that is a live
possibility, not a hypothetical.

**Disposition:** info. Fix is to empty the array and correct the docstring, or to state in the
comment that the array is retained deliberately and is no longer load-bearing.

### E-WR-01 sharpened: the blast radius is larger than reported

Lane E reported `.warning` (App.css:172-175) as resolving neither token "in 10 of ~14 themes."
Measured directly:

- `--text-warning` is defined **once** in the entire frontend, at `themes.scss:223`, inside
  `body.cyberSpaceOasisAlt` (theme root at :155).
- `--warning` is defined **nowhere**. The only repo hit is a class name
  (`.StoreEmbedControls__hostText--warning::selection`), not a custom-property declaration.

So the fallback chain `var(--text-warning, var(--warning))` cannot rescue itself. `.warning`
resolves in **exactly one theme** and yields an invalid declaration (inherited colour) in every
other — **including the default `body` root at :1**. The finding is right; the framing
understated it. This is the shape CLAUDE.md records as "a fallback made 2 typos correct" — here
the fallback does the opposite, because its target does not exist either.

**D-WR-01 — self-vacuating log-hygiene assertion** ·
`src/frontend/screens/WebView/__tests__/useTauriOAuthLogin.test.tsx:1041-1092`

The strongest finding in this cycle. The test named *"every logInfo argument uses only the
permitted key vocabulary — never a code, token, redirect URL, or raw username"* loops:

```js
for (const [line] of mockApi.logInfo.mock.calls) { … }
```

Nothing asserts `mock.calls` is non-empty. The suite seeds a real secret
(`code: 'NILE-SECRET-CODE'`, a matching `redirectUrl`, `'SecretUsername'`) and then proves no
log line contains it — but an empty call list satisfies the test trivially. It is non-vacuous
today only incidentally, because the nile capture path happens to log ≥2 lines. Gate or remove
that logging and this becomes a green check over a credential-leak assertion that tests nothing.

Fix: `expect(mockApi.logInfo.mock.calls.length).toBeGreaterThan(0)` before the loop.
Verified at line 1075 by direct read.

## Observations that are not findings

**`logout()`'s early return is a narrower guarantee than its comment reads.** The comment above
`wipeSteps` says the credential-side cleanup "MUST run unconditionally — even when every
cookie-side step in this block fails or throws." That is true *of the block*. But `logout()`
returns early on `res.error || res.abort` from the `legendary auth --delete` command, before
`wipeSteps` is ever reached, logging an error and leaving `userInfo` and the cache intact. That
is arguably correct — a failed CLI revocation means the session still exists, so retaining
`userInfo` is defensible — but "unconditionally" invites a reader to conclude cleanup always
runs. Not filed as a finding because the behaviour may well be intended; flagged so a future
reader does not have to re-derive it.
