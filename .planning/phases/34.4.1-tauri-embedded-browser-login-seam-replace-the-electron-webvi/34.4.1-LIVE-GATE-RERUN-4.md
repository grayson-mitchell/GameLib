## Why a fourth run exists — read this before anything else

Run 3 passed 4/4 and closed the phase. **Item 3(b) was the exception, and it was not the operator's
fault.**

`survivingNonHumble=0` was recorded. That number was **arithmetically forced, not passing**:

```
before(total=34, matched=34)   →   every cookie in the jar was Humble's
```

With `total == matched`, **no non-Humble cookie existed for the delete to spare**, so a surviving
count of zero was the only value the census could ever have produced. It measured nothing.

The root cause is **the contract**. Run 3's precondition 6 struck the planted non-Humble cookie as
moot, reasoning that plan 17's jar census *"supplies the evidence without it."* That conflates the
**measuring apparatus** with the **thing measured** — a census cannot report `survivingNonHumble > 0`
against a single-origin jar however correct its counting. Item 1's from-scratch reset then
guaranteed the single-origin condition.

**The contract instructed the operator not to plant a cookie, and then required an outcome only a
planted cookie could produce. No action available during that run could have satisfied it.**

The planted cookie and the census are **complements, not alternatives**. That is what run 3 got
wrong, and it is the single thing this run exists to correct.

### Item 2 was MIS-SPECIFIED BY THIS CONTRACT — recorded against the contract, not the operator

Items 2(a)/(b)/(c) ask what the **title bar** shows. On macOS the login window is an AppKit sheet,
and `main.rs:1551` states it outright: *"AppKit sheets structurally render NO title bar UI at all,
so that string is never user-visible on macOS (F-34.5-G6-16)."*

**This is the same defect class as run 3's item 3(b): a contract requiring an observation its own
setup makes impossible.** Written the day after unstriking precondition 6 for exactly that reason.
Scoring 2(a) "PASS — `Tauri app` never appeared" would have been a pass covering a surface that
cannot render at all.

What the operator *did* observe is the **designed replacement**: the login-sheet origin banner
(Phase 34.5 Plan 52, F-34.5-G6-16), an in-page element that exists precisely because sheets have no
title bar. It showed the origin **from the very start** — `origin banner updated len=28`, and
`len("https://www.humblebundle.com") == 28`. The anti-phishing intent WR-07 protects is satisfied,
by a different mechanism than the one this contract named.

**Consequence for D-29-05: it cannot be verified on macOS at all, and plan 33's fix is
unobservable here.** The provisional `.title()` sets an `NSWindow` title macOS never renders. The
fix is still correct for **Windows/Linux**, where a title bar exists — and that is the only place
its live half can ever be closed. D-29-05 stays OPEN, relocated to a platform, not passed.

**D-29-04 is unaffected and PASSES**: its guard operates on the title regardless of visibility, and
`applied len=0` is now 0 where run 3 saw the `22 → 0 → 42` sequence.

### New finding — not a D-29 item, filed as a todo

A newly-synced Humble key cannot be claimed until the user navigates away and back.
`refreshAnnotations()` has three call sites — mount (`[]` deps), claim-wizard close, and undo —
and **none fires on a sync**, so `humble.keys` gains the key while the `annotations` map stays at
its mount-time snapshot and `keyindexResolved ?? false` disables Claim. Backend was correct
throughout (`gamekeys=32 keysCached=32`). **An incomplete fix of a defect already known on this
exact map** (`Waiting/index.tsx:60-73` records fixing it for claim-flow mutations only), and the
same family as D-29-01 on a different surface.
→ `.planning/todos/pending/2026-08-23-humble-keys-annotations-stale-after-sync-claim-disabled.md`
