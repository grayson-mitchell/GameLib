## Critical Issues

### B-CR-01: `electronReachLedger.test.ts`'s own docstring claims the allowlist was cleared to 0; the shipped allowlist array still contains 2 stale entries with the opposite claim in their own comments

**File:** `src/backend/sidecar/__tests__/electronReachLedger.test.ts:41` (docstring claim) and
`:360-373` (the contradicting array)
**Confidence:** High — confirmed by direct read of both regions plus an independent `grep` of the
two named files.

**Issue:** The file's top-level docstring (lines 37-52) states, in the "UPDATE, plan 35-16" note:

> "Plan 35-15 cleared every `src/backend/` entry from `BASELINE_ELECTRON_REACHING_MODULES` (39 ->
> 2) and left the remaining two ... explicitly marked as plan 35-16's. **Plan 35-16 cleared
> both.**"

This is a direct, unambiguous claim that the allowlist array now holds zero entries. It is false.
The actual `BASELINE_ELECTRON_REACHING_MODULES` array (lines 360-373) still contains exactly the
two entries the docstring says were cleared:

```js
const BASELINE_ELECTRON_REACHING_MODULES: string[] = [
  // ...
  'src/common/types.ts', // 35-16 owns this: a Form 2 electron type-import under src/common/
  'src/common/types/ipc.ts' // 35-16: same, and the file D-35-13-02 flags as non-mechanical
  //
  // FOR PLAN 35-18's D-03 GREP GATE: the length is 2, NOT 0. D-03's success test therefore
  // carries a documented asterisk rather than being a clean single grep, and 35-18 must
  // expect these two until 35-16 clears them. Recorded here because 35-18 reads this number.
]
```

The array's own adjacent comments describe a *pre*-35-16 state ("35-16 owns this", "until 35-16
clears them") — directly contradicting the docstring's "Plan 35-16 cleared both" three lines
away in the same file. The two halves of the file disagree with each other about a fact that is
mechanically checkable in the file itself.

I independently confirmed the *underlying reality* the docstring is trying to describe: neither
`src/common/types.ts` nor `src/common/types/ipc.ts` currently imports `electron`
(`grep -n "from 'electron'\|from \"electron\"" src/common/types.ts src/common/types/ipc.ts`
returns no output) — so the docstring's substantive claim (reach is genuinely zero today) is
true. What is false is that the array — the thing that actually gates the test — reflects that.

**Functional consequence:** The growth-tripwire test computes
`measured.filter(mod => !BASELINE_ELECTRON_REACHING_MODULES.includes(mod))` and fails only on
modules *not* in the allowlist. Because these two paths remain in the allowlist, if either file
were to regain an `electron` import in the future, the growth tripwire would treat it as
"already reviewed and accepted" and would not flag it — silently defeating the tripwire's stated
purpose for exactly these two paths. This is currently dormant (measured reach is zero, so no
test is failing today), but it is a live hole in a safety-net array, shipped alongside a comment
that asserts the hole was closed.

**Fix:**
```js
// Remove the two stale entries now that neither file imports electron, and correct the
// docstring to match:
const BASELINE_ELECTRON_REACHING_MODULES: string[] = []
```
And update the "UPDATE, plan 35-16" docstring note to state the array is now empty (`0`, not the
already-claimed-but-unshipped `0`), removing the stale "35-16 owns this" / "until 35-16 clears
them" comments from the array itself so a future reader cannot find two contradictory versions of
the same fact three lines apart in the same file.

## Info

### B-IN-01: the electron-reach BFS's terminal-marker match is exact-string, not prefix-aware — a future `electron/<subpath>` import would not be recognised as electron-reaching

**File:** `src/backend/sidecar/__tests__/electronReachLedger.test.ts` (`collectModuleSpecifiers`
/ `computeElectronReach`, the bare-specifier `'electron'` terminal check)
**Confidence:** High that the gap exists as described; confirmed not currently live.

**Issue:** The BFS treats the bare specifier `'electron'` (exact string equality) as the terminal
"this file reaches electron" marker. A hypothetical future `import { x } from 'electron/main'` (or
any other electron subpath export) would not match and would not be recorded as an electron-reach
edge, silently under-counting the reach set exactly the way the file's own header warns against
doing elsewhere. I confirmed this is not currently exploitable:
`grep -rn "from 'electron/\|require('electron/\|from \"electron/" src/` returns zero hits — no
file in the repo currently imports an electron subpath. This is a latent trap, not a live defect.

**Fix:** Match `specifier === 'electron' || specifier.startsWith('electron/')` at the terminal
check, with a short comment noting why (Electron does not currently ship subpath exports that
matter here, but the pattern is legal and the census should not silently miss it if one is ever
introduced).

### B-IN-02: `testContainment.test.ts`'s per-suite provenance commentary has grown to ~450 lines and is the same shape of drift risk that produced B-CR-01 in a sibling file

**File:** `src/backend/sidecar/__tests__/testContainment.test.ts:443-894` (the prose block
preceding `STRUCTURALLY_CONTAINED_SUITES`)
**Confidence:** High that the volume is as described (confirmed by direct read); this is a
judgment call about maintainability risk, not a bug.

**Issue:** This is the most rigorously self-validating file in the lane — every gate here has an
explicit RED-proof, and the actual test run (`npx jest ... testContainment.test.ts`, 55/55
passing) is clean. The one soft spot is scale: roughly 450 lines of running, self-correcting
historical commentary (readdirSync recounts climbing from 28 through 66 across phases, individual
per-file provenance notes) sit ahead of a ~62-entry array. This is not itself a functional defect
— the array and its accompanying `readdirSync`-derived set-equality tripwire (Block C) are both
independently verified and currently pass — but it is exactly the kind of narrative-heavy,
hand-maintained block where a claim ("X was cleared", "Y now has zero members") can drift out of
sync with the code sitting a few lines below it without any mechanical check catching the
mismatch, which is precisely what happened in `electronReachLedger.test.ts` (B-CR-01). Flagging
this as a latent-risk pattern to watch, not as a present defect in this file.

**Fix:** No code change required. Consider, opportunistically, collapsing the oldest/superseded
per-file provenance entries (those whose phase is long closed and whose recount has not moved in
several subsequent phases) into a single archival note, the way this project's own
`process-lessons-index.md` splits out for size — reduces the surface area for exactly the kind of
silent contradiction found in B-CR-01.
