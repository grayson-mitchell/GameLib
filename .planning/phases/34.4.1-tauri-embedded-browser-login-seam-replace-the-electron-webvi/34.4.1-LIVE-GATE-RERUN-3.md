  **100% of the jar** (33/33), while the (unfixed) census direction matched only 29/33.
- **F-6 Defect B** (plan 23) — on macOS the clear now deletes through the live `WKWebsiteDataStore`
  (`fetchDataRecordsOfTypes_completionHandler` + `removeDataOfTypes_forDataRecords_completionHandler`
  scoped to `WKWebsiteDataTypeCookies`), never wry's `delete_cookie()` (whose `Ok(())` fires
  unconditionally regardless of whether anything was deleted — bugs.webkit.org #184938). Every
  platform now returns a count **measured by re-reading the jar after removal**, never the old
  pre-removal `matching.len()` attempted count. Epic's `clearEpicCookies` — the shared arm's second,
  already-shipped caller, unverified since Phase 34.5 — is now instrumented with the same
  measured-count + zero-count-warning discipline.
- **WR-07** (plan 24) — `humble_login_open`'s visible branch now wires Tauri's documented
  `on_document_title_changed` builder callback, so the OS title bar tracks the loaded document's
  title. The prior FALSE claim that WR-07 was "enforced by the grep gate" was corrected in-source: a
  grep gate can only prove the ABSENCE of a hard-coded title, never the PRESENCE of a tracking one.
- **F-4** (plan 24) — no code change (the platform offers only one-shot focus or a persistent pin),
  but the window's requested presentation is now logged, so this run's observation has a machine
  record to be checked against.
- **F-10** (plan 25) — root cause established by measurement: `.App .content`'s `min-height: 100%`
  resolved against `.App`'s `1fr` grid row, a circular dependency WebKit resolves by iterative
  feedback (converging on a garbage `23323.0625px` row) rather than to `auto`. The login screen was
  rendering fine, ~11,000px below the fold. Fixed by deleting the redundant declaration; hardware
  confirmed (`oversized=0`, `.loginContentWrapper` at `top=0`). A router `errorElement` was also
  added — before this, any route throw unmounted the tree to an empty document, a failure mode
  visually identical to F-10.
- **F-9** (plan 26) — `keyring_get` now runs on a worker thread bounded at `KEYRING_READ_TIMEOUT`
  (8s), rejecting a classified `keyring:timeout` well under the sidecar's 60s RPC budget. A
  hardware timing harness **REFUTED** the original "missing entry is slower" hypothesis: an absent
  Keychain entry read in 40-102ms, while the **present**, allowlisted `steam-refresh-token` entry
  stalled **48.9s then 291s**, both times failing `PlatformFailure(-60008, "Unable to obtain
  authorization for this operation")` — direct hardware evidence for the ad-hoc-code-signature /
  Keychain-ACL theory (an ad-hoc-signed dev build cannot durably retain an "Always Allow" grant, so
  every `pnpm tauri:dev` rebuild re-triggers Keychain authorization negotiation for every allowlisted
  slot). A process-lifetime read cache + in-flight dedupe was also added to
  `keyringTokenStore.ts`/`humbleSecretStore.ts`, cutting the observed 20+ reads/boot toward the
  structural floor of 3 (one per allowlisted slot: `steam-refresh-token`, `humble-session`,
  `humble-csrf`).
- **`REQ-34.4.1-GAP-13`** (plan 27) — `queryLocalFontsSafe()` guards the Chromium-only
  `queryLocalFonts` API from throwing (degrades to CSS-declared default fonts); `CachedImage` no
  longer emits an `imagecache://` URL when `imageCacheSchemeAvailable()` is false, eliminating the
  ~150 guaranteed-failing `unsupported URL` requests per library render under Tauri. **Only the
  unit-provable half is closed** — the live half (zero `unsupported URL` errors observed on a real
  build) is explicitly this gate's job.
- **Tooling** (plan 28) — a new self-tested `wkwebview-silent-noop-sweep.py` sibling script; the
  `seam-parity-sweep.py` S-07/S-10/S-11 staleness (twice logged, twice re-forwarded) is closed.
