## Login mechanism strategy

### Q1 — One unified mechanism, or fork by capture type?

| Option | Description | Selected |
|--------|-------------|----------|
| One child WebviewWindow for all 5 | Dedicated Tauri WebviewWindow per login, extending tauriChildWindows.ts. Navigation watch for the 4 OAuth runners, cookie read for Humble. Closest analogue to Electron's `<webview>`; keeps 34.4 D-01's "one shared seam" premise true; 34.5 inherits one thing. Risk: rests on APIs unverified at 2.11.5. | ✓ |
| Fork: window for Humble, system browser for the 4 | Epic/GOG/Amazon/Zoom to the OS browser with loopback/paste handoff (like shipped SIDLogin); Humble gets the window because it genuinely needs a cookie jar. Only one runner depends on the unverified API; the 4 gain real SSO/password-manager support. Cost: two mechanisms, 34.5 inherits both. | |
| System browser for all 5 | Everything to the OS browser; Humble's cookie pasted or locally captured. Zero dependence on any Tauri webview API, no untrusted remote content in-app. Cost: awkward Humble UX; reveal-key loses its only in-app answer. | |

**User's choice:** One child WebviewWindow for all 5
**Notes:** Scouting had established that `tauriChildWindows.ts` (34.1 D-12) already ships the fail-closed labelling, anti-phishing and capability-isolation work this needs, and that `core:webview:allow-create-webview-window` is already granted — so the option's stated risk is narrower than 34.4 D-07 assumed. → **D-01**

| You decide | Research settles it empirically against Tauri 2.11.5, constrained so the 6 channels keep their signatures. | ✓ |

**Notes:** Deferred to research on evidence. Recorded with non-negotiable constraints: the 6 channels keep their current signatures; the login window matches no capability; no label derives from a caller-supplied URL (T-34.1-27). → **D-02** + Discretion

### Q3 — What if the cookie-jar read doesn't work on macOS?

The consequence is stated explicitly so the bad case reads as a declared outcome, not a review-time discovery. → **D-03**

## Claude's Discretion

- **D-02's ownership shape** — Rust-arms-driven-by-sidecar vs renderer-owned, settled on the spike's evidence, under three fixed constraints (channel signatures, no capability match, no url-derived labels).
- **A stale-`isTauri()`-guard sweep of the login path plus an `npm start` regression check before human gate time** — not a gate item, but 34.4's item 2 and 34.4-10's build regression were each caught only by one of these two cheap checks.
- **Whether to add test-proven safe degradation for Linux/Windows** (D-09's rejected option) — do it if cheap.
- **Whether 34.4 D-06's `electronStub.net.request` hardening is retired or kept** once D-07 changes its only caller — decide deliberately; don't leave a stale "missing seam" message pointing at a seam that now exists.
- **Curated imports** — `humble/ipc_handler.ts` now registers 15 already-ported channels alongside this phase's 6; import `humble/user.ts`, `humble/adapter.ts` and `humble/userAgent.ts` directly.
- **Send-vs-handle discipline** — `humbleStopLogin`/`humbleLoginNavigated` are send-shaped; a mismatch fails 100% silently.
- **`humbleGetLoginUserAgent` is pure** and ports regardless of how D-03 resolves — so the phase must not be mis-scored "0 of 6" in the bad case.
