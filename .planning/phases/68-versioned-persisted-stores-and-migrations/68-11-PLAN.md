<objective>
Close CR-01, the one blocker in 68-VERIFICATION.md. `atomicWritePrivate` (backup.ts:41-54) wraps
the temp write and the rename in one `try`. When the temp write fails (ENOSPC, EDQUOT, EIO), the
`catch` runs `writeFileSync(filePath, ...)`, which opens the LIVE file with O_TRUNC and then fails
the same way. The live file is left truncated. That breaks D-06 ("the pre-migration file is
untouched") for the settings/global v0->v1 migration on every v0 profile and for every future
conf-store chain. It also breaks 68-01 truth 6, which limits the fallback to a rename failure.

Fix: split the `try`. A temp-write failure unlinks the temp file and rethrows, so the live file is
never touched. The direct-write fallback stays for a `renameSync` failure only (Windows
EPERM/EBUSY). A new test suite proves both branches at the `atomicWritePrivate` level, and at the
engine level proves that an ENOSPC temp write during a real migration leaves the live file
byte-identical and the store read-only with reason `'failed'`.

Purpose: one root cause, two failed truths (68-02 truth 5, 68-01 truth 6). One change closes both.
Output: a new test suite (RED first, against the current code) and the fixed `backup.ts` (GREEN).
