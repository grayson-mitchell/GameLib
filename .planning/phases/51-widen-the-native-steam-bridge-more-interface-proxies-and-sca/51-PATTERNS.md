### `src/backend/storeManagers/steam/bridge/helperProcess.ts` (service, event-driven)

**Analog:** itself — the single biggest structural change in the phase (D-51-01 supersedes D-03/D-04's single-shared-helper model).

**Current single-helper state to convert to a registry:**
```typescript
// D-03: the ONE shared, long-lived helper handle.
let helperProcess: ChildProcess | null = null
let unregisterLongLivedChild: (() => void) | null = null
```
Convert to `Map<string /* appId */, { process: ChildProcess; unregister: () => void; port: number }>` — keep every other shape identical: `spawnHelperIfNeeded()`'s no-op-if-live guard (lines 108-111) becomes a per-appId no-op-if-live guard; `probeHealthAndWhoami()` (lines 170-234) and its bounded-poll budget (`POLL_ATTEMPTS`/`POLL_INTERVAL_MS`/`PROBE_TIMEOUT_MS`, lines 60-62) are unchanged per-connection logic, just parameterized by the per-appId port. The `registerLongLivedChild('steam-bridge-helper', shutdownBridgeHelper)` call (lines 150-153) must become `registerLongLivedChild('steam-bridge-helper-' + appId, ...)` so `shutdownLongLivedChildren()` tears down ALL per-game helpers on quit, not just one.

**`steam_appid.txt` identity write** — currently done natively in `bridge_helper.c` (`ensure_steam_appid_file`, see below) using a fixed cwd staged with `480`. D-51-01 requires each spawn's `cwd` to stage the GAME's real AppID instead — `spawnHelperIfNeeded`'s `cwd: dirname(steamBridgeHelperPath)` (line 119) is currently a single shared staging dir; this must become a per-appId staging dir (one per running helper) so two concurrent helpers (D-51-03, no lock) never race on the same `steam_appid.txt`.

**Port allocation (Claude's Discretion item):** `BRIDGE_HELPER_PORT = 54550` (line 55) is currently a single fixed port. A per-appId registry needs either a fixed small pool or ephemeral-port allocation communicated to the shim — follow the existing bounded-constant style (a `const` list or a simple increment-from-base) rather than introducing a new allocation library.

**Readiness status shape** (lines 72-78, 236-312) — `BridgeHelperReadyStatus = 'ready'|'not-inited'|'unreachable'` and the distinct `sendFrontendMessage('steamBridgeSetupRequired', {appName, reason})` calls for each failure are the template for D-51-04's fallback-to-480 path: add a `'fallback-identity'` status/reason so the caller can fire D-51-02's one-time notice distinctly from the existing two failure reasons.

## Shared Patterns

### Numeric AppID guard
**Source:** `importScan.ts:25`, `allowlist.ts:40`, `bottle.ts:826`/`:836`, `helperProcess.ts:50`
**Apply to:** every new function taking an `appId: string` parameter — reuse the literal `const NUMERIC_APP_ID = /^\d+$/` value and name; never redefine a divergent regex. Guard BEFORE any lookup/spawn, return a safe typed failure (never throw) on a bad caller-supplied id — this is T-24-06/T-24-07 lineage and the project's own docblocks repeatedly flag it as a must-preserve convention.

### Fail-loud (bundled config) vs fail-safe (runtime lookup) posture
**Source:** `allowlist.ts` docblock (lines 1-25)
**Apply to:** the widened `bridge-allowlist.json` schema and any new bundled JSON (known-bad list). The bundled asset itself is a trust boundary: `.parse()` not `.safeParse()`, throws at module load on malformation. The consumer-facing `has()`/lookup function is the opposite posture: never throws, numeric-guards and returns a safe default. Keep both postures when widening — do not relax the load-time strictness, do not make the lookup function throw.

### CARRY-FORWARD warning on `steamMetadataStore.set`
**Source:** `electronStores.ts` (`forcedWindowsViaBottle`, `mac_arch_verified`, `platformsSource` doc comments)
**Apply to:** every new field added to `SteamMetadataCacheEntry` and every write site that touches that store. `set()` replaces the WHOLE entry — any writer enumerating its payload (rather than spreading `...existing`) must explicitly carry every prior field forward, new fields included. Audit every existing `steamMetadataStore.set(` call site, not just new ones, when adding fields.

### Observable-failure, never-a-hang pattern
**Source:** `helperProcess.ts` (`ensureBridgeHelperReady`, `POLL_ATTEMPTS`/`POLL_INTERVAL_MS`/`PROBE_TIMEOUT_MS`)
**Apply to:** any new per-game readiness probe (now N helpers instead of 1) and any D-51-16 "Waiting for Steam…" grace-window state — bounded poll budget, distinct typed status values for distinct failure reasons (never one generic timeout), `sendFrontendMessage` fan-out on each distinct failure.

### Argv-form spawn only, never string-concatenated shell
**Source:** `importScan.ts` docblock (lines 10-17), `bottle.ts:836`, `helperProcess.ts` spawn call
**Apply to:** any new spawn site (a Win64 `zig cc` toolchain invocation if D-51-13 greenlights it, a second objdump invocation for the 64-bit heading check, per-appId helper spawns). `createFakeHomeProfile()` per the repo-wide convention for every spawn site from `src/`/`meta/` (per CLAUDE.md).

### In-app vs native dialog choice
**Source:** `dialog.ts` docblock (lines 10-24)
**Apply to:** D-51-08's known-bad dialog (3 buttons → must be in-app) and D-51-10's toggle (checkbox-adjacent → must be in-app). Never rely on native Escape-to-second-button semantics for anything resembling a persisted suppression/preference.
