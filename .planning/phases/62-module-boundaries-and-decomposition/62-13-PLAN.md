Planner decisions (Claude's Discretion, recorded):
- Identity helper: `export type StoreKey = Runner | 'humble'` (humble is a login/key store compared
  in WebView/TauriLoginPanel/signInProbe, not a Runner). `export function isStore(subject: StoreKey | null | undefined | { runner?: StoreKey | null }, store: StoreKey): boolean` — returns false for null/undefined. This is the one sanctioned raw comparison; `src/common/**` is outside the ratchet scope so it needs no disable comment.
- Flag accessor: `export function hasCapability(runner: Runner | string | null | undefined, flag: keyof Omit<StoreCapabilities, 'store'>): boolean` returns false for any value that is not a key of the table. Legacy `runner === 'steam'` is false for undefined/unknown runners; a bare `storeCapabilities[runner].flag` would throw there, so call sites whose runner is not statically `Runner` must use hasCapability.
- `StoreCapabilities` carries `store: Runner` (identity field) plus boolean flags named for behaviour, not store. Research's candidate flags (to confirm or replace from the audit): `installManagedExternally`, `supportsDlcSelection`, `resumableInstall`, `stopRequiresExplicitCall`, `hasStorePage` (delisted handling still reads `GameInfo.is_delisted` per game), `launchTrackedByStore`, `installHandOffToClient`. Prefer one flag per distinct behaviour, not per site.
- Compound behaviour (e.g. `runner === 'steam' && action === 'install'` in InstallModal, GameCard, steamEligibilityProbe.ts, state/InstallGameModal.ts) gets one shared predicate. If its inputs are common/ types, it lives in storeCapabilities.ts; if it needs frontend types, record it in the classification as "predicate to create in src/frontend/helpers/<name>.ts by the first frontend plan that converts it" — 62-17 owns frontend helpers.
- Late flags: the aim is a complete day-one set, but if a conversion plan (62-14..62-19) finds a
  behaviour the audit missed, it adds the flag through recipe step C8 (62-15-PLAN.md): a separate
  commit, before the conversion, that edits storeCapabilities.ts and its test and appends the row to
  62-SITE-CLASSIFICATION.md. That is the only reason those plans list storeCapabilities.ts.
- Counts: classify against the numbers the widened 62-02 selector measured (names ending in
  Runner/Store, e.g. removedRunner, scopedRunner, activeRunner, warnLoginForStore), not the research estimates.
- Rationale comments (D-27, D-28, REQ-37-02, 34.13 C-04 ...) next to a converted site stay with the site; flags in the table get a one-line comment naming the behaviour and the decision that introduced it.
