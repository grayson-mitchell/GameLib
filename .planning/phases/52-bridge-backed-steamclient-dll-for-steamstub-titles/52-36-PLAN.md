<objective>
Close the item-30 conjunct of the amended done-when ("GameLib shows an honest notice ... instead of
failing silently") by making the notice reach the operator through a channel GameLib controls, and
make OS-notification delivery observable in the log. Done unconditionally, before the re-gate
(52-37), rather than only if a GameLib.app re-run fails again. Reasons:

1. **The OS notification alone cannot satisfy "shows".** notify() is fire-and-forget. On the plugin
   backend (every non-`.app` macOS run) `macos_notifications.rs`'s header says macOS 26 drops it
   silently. On the UserNotifications backend, a denied authorization, Focus, or banner style
   "None" each leaves the user with no notice. In none of these cases can GameLib tell the
   notice reached the user.
2. **The repo's own dialog policy already puts this notice in-app.** `src/backend/dialog/dialog.ts`
   rule 1 says: "In-app (showDialogBoxModalAuto): ... any nag or warning". The forwarded SteamStub
   notice is a warning.
3. **52-35 proved that a log line proves the trigger, not the notice** (52-UAT item 30). A logged
   delivery result tells "accepted by UserNotifications" apart from "handed to a plugin that may
   drop it", so the next gate can name the channel instead of guessing it.
4. **No conditional replanning.** If the change were conditional on the re-gate failing, a failure
   would need a new planning round. Done now, one re-gate scores it.

**Scope held small.**
- The in-app dialog is added only to the forwarded notice (the open gap). `maybeNotifySteamStubUnforwarded`
  is not changed.
- Backend selection (`select_notification_backend`) is not changed: the raw debug binary keeps the
  plugin. Its silent drop is now visible in the log as `delivery not confirmable` rather than
  hidden. The in-app dialog covers that run mode for this notice.
- No new i18n strings: the dialog reuses the 52-33 forwardedTitle/forwardedBody keys.
- The notice stays informational and one-way. showDialogBoxModalAuto without an event only
  `sendFrontendMessage`s outward and does not block, so wine still starts right after it (52-34
  boundary: never aborts or reroutes the launch).

Output: games.ts dialog dispatch + tests; Rust backend label + arm return; shim 'show' event;
notify() delivery log + tests.
</objective>
