A zero-warning bar is NOT this phase's target and must not appear as an acceptance criterion.

code. The honest target is **zero errors plus a documented, ratcheted warning count.**

<measurement_hazards_binding_on_every_criterion_you_write>
1. `pnpm codecheck` is `tsc --noEmit`. It says NOTHING about lint. A green codecheck is not evidence
   about any lint finding. It appears in this plan only as a compile guard.
2. Count only `severity === 2` as an error. Never write a combined "problems" figure without the
   error/warning split — conflating them mis-scopes by two orders of magnitude, which is exactly how
   the ROADMAP's figure misled.
3. A lint finding can name the wrong file with the right line numbers. This project has hit it. If a
   task edits at reported lines, read the file first and confirm the violation is actually there.
   (Research spot-checked the top three warning files on 2026-09-02 and found no misattribution, but
   that sample does not generalise to files this phase changed.)
4. `prettier --check` is a DIFFERENT gate and is separately red repo-wide. This phase does not own
   it. If `eslint --fix` runs, diff its changed-file list against `prettier --check`'s to DOCUMENT
   overlap — never to fix it, and never as justification for running `prettier --write`.
</measurement_hazards_binding_on_every_criterion_you_write>

| this phase's lint number -> the next eighteen months | The ratchet's whole value is that it makes drift visible. Set inert, it is worse than nothing, because it looks like a control. |

No new dependency, no network surface, no user input, no auth change.
