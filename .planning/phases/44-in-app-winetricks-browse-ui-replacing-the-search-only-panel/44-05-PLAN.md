## The three open questions this plan closes

**1. `hideProgress`'s replacement (RESEARCH Open Question 3, handed to the planner by CONTEXT.md).**

Current, `Winetricks/index.tsx:232-234` (verified):
`!guiOpen && !installing && !loadingInstalled && !loadingAvailable`.

`loadingInstalled` is one boolean carrying two unrelated facts: "we have never yet loaded the
installed list" and "a background refresh is in flight right now". D-17 requires decoupling them.
Replace it with three named pieces of state:

| New state | Meaning | What it may gate |
|---|---|---|
| `hasInstalledData: boolean` | false until the first `listInstalled()` resolves; **never returns to false** | a first-load placeholder, and `hideProgress` |
| `isRevalidatingInstalled: boolean` | true for the duration of **every** `listInstalled()` call | the thin stale-while-revalidate overlay ONLY — **never a mount** |
| `hasAttemptedInstall: boolean` | sticky, set true the first time `install()` runs in this dialog session | `hideProgress` |

New expression:
`hideProgress={!guiOpen && !installing && !hasAttemptedInstall && hasInstalledData && !loadingAvailable}`

Two deliberate changes beyond the literal decoupling, each with a reason:
- `!loadingInstalled` becomes `hasInstalledData` — the log box shows during first load (as today)
  but a **background revalidation no longer toggles it**. That is the whole point of the split.
- `!hasAttemptedInstall` is added — once any install has been attempted in this dialog session the
  log box stays visible. Without it the box vanishes the instant `installing` flips false and the
  refetch resolves, taking the completion and failure lines with it. The phase adds a per-row
  Errored state whose only diagnostic detail lives in that log; hiding it at exactly the moment a
  user needs it would make the new Retry affordance unexplainable.

**2. Per-verb error attribution must happen at the event, not over the log array.**

`logs` is a flat, ever-accumulating array shared across all installs with no per-line verb. It cannot
be attributed retroactively. `onWinetricksProgress`'s payload is the only place where `messages` and
`installingComponent` arrive **together**, so that handler is the correlation point. Call
`attributeProgressEvent` (plan 44-01) there.

**3. `winetricks.unavailableDetail` must be relocated, not deleted with its host block.**

D-11 retires `installedWrapper` (`:199-221`). That block is NOT inside the `!declined` gate — it is a
sibling, and it hosts the `declined` branch that renders
`tGamelib('winetricks.unavailableDetail', …)` at `:204`. Grep confirms `Winetricks/index.tsx:204` is
its only consumer in `src/`. Retiring the block wholesale without moving that branch would silently
drop the declined state's only explanation, leaving a bare one-line "unavailable" with no reason.
Move it into the existing `declined` block at `:146-154`. This is not in D-11's text; D-11 is about
the "Installed components: a, b, c" summary, and the detail copy is unrelated collateral in the same
JSX block.
