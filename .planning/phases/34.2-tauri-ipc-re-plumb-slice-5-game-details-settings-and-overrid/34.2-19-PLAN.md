CORRECTED 2026-07-26 (during execution — see Deviation Log at the bottom of this plan): the
env-only approach below does NOT work inside a Jest test, despite being true in plain Node.
`node -e "process.env.HOME='/tmp/fake-home-probe'; console.log(require('os').homedir())"`
does print `/tmp/fake-home-probe` — but that probe runs OUTSIDE Jest. Inside `jest-environment
-node`, `jest-util`'s `installCommonGlobals` (`createProcessObject.js`) replaces `global.process`
PER TEST FILE with a deep-cloned synthetic process object whose `.env` is a pure-JS `Proxy` — a
one-time snapshot of the real environment, decoupled from it. Writes to `process.env.HOME`
inside a Jest test mutate only this JS-only clone; they never call the real `setenv()`.
`os.homedir()` is a NATIVE binding (libuv `uv_os_homedir()`) that reads the real OS environ
directly, bypassing Jest's fake `process.env` entirely — so env vars ALONE never redirect it,
and `getBaseLogPath()`'s isMac branch (`join(homedir(), 'Library', 'Logs', 'GameLib')`, which has
no env-var fallback at all) keeps resolving to the developer's real home. Verified live: a full
`sidecar/__tests__` run with the env-only fix installed still changed the real
`~/Library/Logs/GameLib/gamelib.log`/`.log.old` mtimes.

Two non-`jest.mock` alternatives were tried and ruled out during execution: direct
`Object.defineProperty(os, 'homedir', ...)`/`jest.spyOn` throw `TypeError: Cannot redefine
property: homedir` (Node's core-module exports are non-configurable getters under CJS
`require()` on this Node version); a `Module._load` hook (the technique
`installElectronHook.ts` uses successfully for `require('electron')`) does not intercept
`require('os')` under Jest, since Jest's Runtime resolves builtins via its own captured
`require()`, bypassing `Module._load` entirely (verified empirically).

The ACTUAL, WORKING mechanism: `jest.mock('os', () => ({ ...jest.requireActual('os'), homedir:
() => containmentRoot }))`, called ONCE from `jest.setupContainment.ts` (a `setupFiles` module,
registered project-wide, running before any test file's own imports — so this is still
structural and can't be opted out of by omission, the property this plan actually cares about).
Only `homedir` is overridden; every other `os` export stays real via `jest.requireActual`. The
env-var redirection (HOME/USERPROFILE/APPDATA/LOCALAPPDATA/XDG_CONFIG_HOME/XDG_STATE_HOME) is
KEPT as defense-in-depth for the Windows/Linux branches below, which DO correctly read Jest's
per-test-file `process.env` and were never the problem — only `os.homedir()`'s native binding
needed `jest.mock`.

Original (now-corrected) text, preserved for context: "Node semantics that make the env-only
approach work (probed on this host, 2026-07-26): `os.homedir()` returns `process.env.HOME`
verbatim when it is set on POSIX, and `process.env.USERPROFILE` on win32. ... Therefore setting
HOME/USERPROFILE plus the four APPDATA/LOCALAPPDATA/XDG_CONFIG_HOME/XDG_STATE_HOME variables
covers every branch of both resolvers on every platform, with no `jest.mock` and no
module-registry surgery." — this was TRUE for the Windows/Linux env-var branches, but FALSE
for `os.homedir()` itself under Jest, per the correction above.

## Amendment 2026-07-26 (mid-execution, coordinator-approved)

**What was found:** Task 1's originally-specified mechanism (pure `process.env` redirection via
`setupFiles`, explicitly forbidding `jest.mock`) does NOT redirect `os.homedir()` inside a Jest
test on this project's Jest 29 / Node 26 setup, even though the plan's own "probed on this host"
claim (`node -e "process.env.HOME=...; os.homedir()"`) is true in *plain* Node. Root cause:
Jest's `jest-environment-node` + `jest-util`'s `installCommonGlobals`
(`node_modules/jest-util/build/createProcessObject.js`) replace `global.process` PER TEST FILE
with a deep-cloned synthetic process object whose `.env` is a pure-JS `Proxy` — a one-time
snapshot of the real environment, decoupled from it. Writes to `process.env.HOME` inside a Jest
test mutate only this JS-only clone; they never call the real `setenv()`. `os.homedir()` is a
NATIVE binding (libuv `uv_os_homedir()`) reading the real OS environ directly, bypassing Jest's
fake `process.env` entirely. `backend/logger/paths.ts`'s `getBaseLogPath()` isMac branch has NO
env-var fallback at all (`join(homedir(), 'Library', 'Logs', 'GameLib')`), so this is the one
branch env-var redirection could never reach, and it is the exact branch that was destroying real
developer data.

**Live proof of the gap:** ran a full `npx jest --testPathPattern="src/backend/sidecar/__tests__"`
with the (then-committed) env-var-only fix installed, and `stat`'d the real
`~/Library/Logs/GameLib/gamelib.log`/`.log.old` before and after — both mtimes changed
(11:36:51/11:36:22 → 11:42:53/11:42:53), proving the defect was NOT closed by commit `ec800227`.

**Alternatives investigated, ruled out:**
- `Object.defineProperty(os, 'homedir', {...})` / `jest.spyOn(os, 'homedir')` — both throw
  `TypeError: Cannot redefine property: homedir`. Node's core-module exports are non-configurable
  getters under CJS `require()` in this Node version.
- A `Module._load` hook (the technique `src/backend/sidecar/installElectronHook.ts` uses
  successfully for `require('electron')`) — does NOT intercept `require('os')` under Jest. Jest's
  Runtime resolves Node builtins via its own captured `require()`, bypassing `Module._load`
  entirely. Verified empirically with a test-local hook.

**Fix approved by coordinator:** `jest.mock('os', () => ({ ...jest.requireActual('os'), homedir:
() => containmentRoot }))`, called once from `jest.setupContainment.ts` — a module-registry
substitution (new object), not a property mutation, registered once via `setupFiles` before any
test file's own imports run, so containment remains structural (one registration point, no suite
opts in or out). Scope stays narrow: only `homedir` is overridden, every other `os` export is
real via `jest.requireActual`. The original env-var redirection is KEPT as defense-in-depth for
the Windows/Linux branches, which DO correctly observe Jest's per-test-file `process.env` and
were never the problem.

**Sections amended:** the `<interfaces>` "Node semantics" note; Task 1's action text, docstring
instruction, and `jest.mock(` acceptance criterion (now permits exactly one comment-stripped
`jest.mock(` call site in the setup module, and asserts zero in any per-suite test file); Task
2's read_first note, RED-PROOF action text and acceptance criteria (actual observed RED: 5 of 6
tests fail, not "Tests 1-4" — Test 4 stays green independently via the pre-existing default
`electron` Jest automock, unrelated to this fix); the must_haves truth statement; threat rows
T-34.2-61 and T-34.2-62 (substance of both mitigations unchanged, wording corrected).

**Verified working (not just claimed) on this Jest 29 setup:** confirmed empirically that
`jest.mock('os', ...)` called from a `setupFiles` module DOES take effect for that test file's
own subsequent `require('os')` calls (both direct and transitive, via
`backend/logger/paths.ts`), and is NOT defeated by `resetMocks: true` in `jest.config.js` (the
factory returns a plain arrow function, not a `jest.fn()`, so there is nothing for `resetMocks`
to reset). `jest.config.js` has no `resetModules`/`restoreMocks` setting that could interfere.
