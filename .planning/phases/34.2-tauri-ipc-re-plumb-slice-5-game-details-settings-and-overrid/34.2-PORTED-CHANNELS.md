# Phase 34.2 — Declared Ported-Channel List

**Purpose:** The enumerated set the next Tauri phase (34.3+) starts from, and the artifact the
Phase 35 cutover gate reads for this slice, mirroring how this phase itself started from
`34.1-PORTED-CHANNELS.md`. It describes what actually shipped in 34.2-01..34.2-06 — verified row
by row against all six plan SUMMARY.md files, not against this phase's original planned intent.
Reconciliation findings are in section 7; no drift was found between the plan's declared 26-channel
list and what shipped.

---

## 1. Port kinds

This slice introduces **no new kind** to the vocabulary Phases 30–34.1 established. It uses exactly
two of the existing kinds:

- **`sidecar invoke`** (23 channels) — the channel is registered on the sidecar's `ipcMain.handle`
  and answered over the Tauri transport.
- **`sidecar send`** (3 channels) — registered via `ipcMain.on`, fire-and-forget, each body wrapped
  in `try`/`catch` → `logSendFailure` so a throw cannot reach the sidecar's unguarded process
  boundary.

Zero `rustInvoke` rows and zero `renderer-side (Tauri JS)` rows this slice. The Rust-adjacent
changes — adding the string `"getCrossoverIndex"` to the existing `LONG_RUNNING_CHANNELS` array in
`src-tauri/src/main.rs` (plan 34.2-06), then adding `"repair"` and `"readConfig"` to the same array
during gap cycle 1 (plan 34.2-08, closing verification gap #1 / code-review CR-01) — are
**timeout-policy edits**, not a port kind, and add no `dispatch_rust_channel` arm. `LONG_RUNNING_CHANNELS`
now has **eight members** (`install`, `updateGame`, `uninstall`, `checkGameUpdates`,
`refreshLibrary`, `getCrossoverIndex`, `repair`, `readConfig`) — three of which are attributable to
this phase. The `dispatch_rust_channel` arm count stays at 11 (last changed by Phase 34.1's
`tray_set_icon`).

### The two bootstrap wirings (not channels — do not count these in the 26)

These are the load-bearing content of this slice, not the channel table above. Both are fixes to
already-shipped defects, not new features (Phases 30/32 shipped the underlying bugs; this slice is
the first to expose them because its channels are the first to depend on either).

- **i18next initialization (D-02, REQ-34.2-02).** `i18next.use(Backend).init({...})` — previously
  present only inside Electron's `app.whenReady()` in `main.ts` — now also runs at sidecar boot in
  `bootstrap.ts`, mirroring `main.ts:460-472` field-for-field behind an idempotent guard. Before this
  fix, `i18next.t()` returned `undefined` (not a throw, not the inline default) at every backend call
  site reachable from the sidecar, including `repair`'s notify body. **What the tests prove:**
  `i18next.t()` returns a real, non-`undefined` string after `init()`, against the real (unmocked)
  `i18next` singleton (`bootstrapWirings.test.ts`), and `repair`'s own notify body reflects a real
  translated string over the real sidecar RPC loop (`gameDetailsFlows.test.ts`, RED-confirmed by
  temporarily removing the `init()` call). **What the tests do NOT prove:** that a notification
  actually renders in a running Tauri window, or that the packaged build's locale-path resolution
  (the `publicdir-getapppath-chunking` gotcha family) works — jest runs from the repo root, where
  `process.cwd()` happens to resolve correctly. See §6 and `34.2-HUMAN-UAT.md` UAT-34.2-01.
- **`fetchLastestReleases()` + the re-homed `releasesInfoReady` → `downloadAntiCheatData` listener
  (D-07, REQ-34.2-07).** `fetchLastestReleases()` — the sole emitter of `releasesInfoReady` — was
  previously called only from `main.ts`, never in the sidecar bootstrap, so the event never fired
  under Tauri and `getAnticheatInfo` structurally could not return data. Both are now wired into
  `bootstrap.ts`'s `init()`, after `initOnlineMonitor()` per its `runOnceWhenOnline` precondition.
  The listener body is reproduced verbatim from `anticheat/ipc_handler.ts:12-19` (not imported — that
  file's module scope calls `addHandler` from `backend/ipc`, forbidden under `src/backend/sidecar/`).
  **What the tests prove:** the event fires and `downloadAntiCheatData` writes the data file, against
  a tmp home with a mocked axios (`bootstrapWirings.test.ts`); the anticheat riders (see §3 rider 2)
  are asserted, not just documented (`enrichmentFlows.test.ts`). **What the tests do NOT prove:** that
  a real GitHub fetch completes in a live process across a real network after a real connectivity
  transition, or that the file lands under a real `appFolder` in a packaged build. See §6 and
  `34.2-HUMAN-UAT.md` UAT-34.2-02.
  **Gap cycle 1 (plan 34.2-09) — the wiring was crash-unsafe.** This entry was originally declared
  "wired" when it shipped, but the `void downloadAntiCheatData(...)` call inside the
  `releasesInfoReady` listener body was crash-unsafe: a single `EACCES`/`ENOENT`/TOCTOU/is-a-directory
  fault reading or writing `areweanticheatyet.json` would have rejected an unguarded promise and, with
  no process-level `unhandledRejection` handler anywhere in the sidecar, killed the whole sidecar
  process. The surrounding `try`/`catch` covered only the synchronous `backendEvents.on(...)`
  registration call — zero coverage for the listener body, which runs later from the emitter, outside
  that stack frame. Closed by code-review finding CR-02 / verification gap #2: plan 34.2-09 attached a
  `.catch()` directly to the `downloadAntiCheatData(...)` call inside the listener (logging via
  `logWarning`, never rethrowing), and added `sidecar/processGuards.ts`'s log-only, idempotent,
  never-throw/never-exit `installUnhandledRejectionGuard()` as process-wide defence-in-depth,
  installed from `src/sidecar/index.ts` before `init()`. Proven live: `sidecarRejectionGuard.test.ts`
  drives the real, unmocked `bootstrap.init()` with a rejecting `downloadAntiCheatData` and asserts
  zero `unhandledRejection` events fire.

## 3. Declaration riders

Three riders, stated so a reader cannot over-read the table above.

**1. Steam-runner upstream stubs.** For Steam titles, FOUR ported channels are inert **in Electron
already** — porting them faithfully reproduces Electron's own current behavior, not a regression this
phase introduces, and not a gap to open a cycle against:
- `repair` — `storeManagers/steam/games.ts:1610` logs `"SteamGame.repair not implemented until Phase 2"`.
- `changeInstallPath` — `storeManagers/steam/library.ts:790` (`changeGameInstallPath`), an
  underscore-arg no-op. This is the **fourth** Steam stub; CONTEXT.md D-01 named three
  (`repair`/`changeGameVersionPinnedStatus`/`getLaunchOptions`) and this one was found during
  planning.
- `changeGameVersionPinnedStatus` — `storeManagers/steam/library.ts:797`, an underscore-arg no-op.
- `getLaunchOptions` — `storeManagers/steam/library.ts:907`, an underscore-arg no-op.

**2. `getAnticheatInfo` even when primed.** `gameAnticheatInfo` matches on
`info.storeIds.epic?.namespace` and early-returns `null` on `isWindows`, so even with plan 34.2-01's
D-07 wiring and the data file present on disk, it returns `null` for Steam titles on every platform
and `null` for everything on Windows. **"Ported and primed" must not read as "anticheat badges appear
for Steam games."**

**3. Six channels unreachable in a Steam-only workflow.** `readConfig`, `getGameOverride`,
`getGameSdl` (all three Legendary/Epic), `getAvailableCyberpunkMods`, `setCyberpunkModConfig` (both
GOG — and `setCyberpunkModConfig` has **zero** frontend callers at all), and `addNewApp` (sideload).
Ported at parity per D-08 so the Phase 35 cutover gate closes with no residue, not because they are
exercised by GameLib's current Steam-first workflow.

## 4. Declared divergences from the Electron build

**`getGameSettings` and the already-ported `requestGameSettings` now BOTH exist on the sidecar as
near-duplicates.** This is Electron's own duplication (both end at
`getGame(appName).getSettings()`), not introduced here. `requestGameSettings`
(`settingsFlowRegistration.ts:113`, ported Phase 31) carries a `steamLibrary.has(appName)`
bottle-launch fix `getGameSettings` does not have (D-09) — a shipped, hardware-proven fix for a real
bug, and this slice deliberately does not touch it. `getGameSettings` was ported at parity, unmodified,
alongside it. **State plainly: two settings reads must not both survive into the Electron-free build
by accident.** Deduping the two is a recorded Phase 35 cutover cleanup — see §5.

## 6. Sign-off — the honest statement

**State the difference plainly rather than copy 34.1's wording.** 34.1's headline deliverable was
visual and interactive — the frameless toggle, the titlebar buttons, the tray appearing and changing
colour, gamepad navigation, macOS traffic lights vs custom buttons — and jest structurally could not
see any of it, so "wired and unit-proven" was a weak claim there. **This slice is almost entirely
data-in/data-out: 26 channels with assertable return shapes, exercised over the real sidecar RPC
loop, so "wired and unit-proven" is genuinely close to "works" here.** Every row above is backed by a
test that drives the real extracted body (or already-clean module) over the real transport and
asserts a real return value — not a mock's echo.

That stronger claim has **exactly two honest exceptions**, and they are not softened:

- **D-02.** Tests prove `i18next.t()` returns a real string after `init()`, and that `repair`'s notify
  body reflects it over the real sidecar RPC loop. Nobody has booted the Tauri build and seen a
  translated notification render, and the packaged build's locale-path resolution (the
  `publicdir-getapppath-chunking` gotcha family) is unproven by construction — jest runs from the
  repo root, where `process.cwd()` happens to resolve `publicDir` correctly.
- **D-07.** Tests prove the event fires and the anticheat data file is written, under a tmp home with
  a mocked axios. Nobody has booted the Tauri build and confirmed a real GitHub fetch lands
  `areweanticheatyet.json` in the real `appFolder` across a real network after a real connectivity
  transition.

**Do not read "wired and unit-proven" as "seen working" — that is exactly how G-30-02 was declared fixed twice while the live build hung.**

Wherever a row's automated proof covers only wiring and not
observable behavior, that is stated on the row (see §3 riders 1–2, and the two bootstrap-wiring
entries in §2). Read this document together with `34.2-HUMAN-UAT.md` — neither artifact should be
read in isolation, because either one alone could leave a later reader with the wrong impression.
