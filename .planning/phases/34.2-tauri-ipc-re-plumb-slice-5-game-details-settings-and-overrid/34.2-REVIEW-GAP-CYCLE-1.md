### CR-01: The CR-01 renderer fix swallows repair failures with ZERO signal under Tauri — `window.api.logError` is an unported `send` channel

**File:** `src/frontend/screens/Game/GameSubMenu/index.tsx:143-149`
**Also:** `src/backend/sidecar/sidecarRpc.ts:138-150`, `src/backend/logger/ipc_handler.ts:15`,
`src/backend/sidecar/handlers.ts:43-51`

**Issue:**
The gap plan's renderer half converts an unhandled rejection into:

```ts
try {
  await repair(appName, runner)
} catch (error) {
  window.api.logError(`repair failed for ${appName}: ${error}`)
}
```

`logError` is a **`send`**-kind channel (`src/preload/api/misc.ts:127` —
`makeListenerCaller('logError')`). Its ONLY registration in the whole backend is
`src/backend/logger/ipc_handler.ts:15` (`addListener('logError', ...)`), and
`src/backend/sidecar/handlers.ts` does not import `logger/ipc_handler.ts` — verified: no
`'logError'` registration exists anywhere under `src/backend/sidecar/`.

On the Tauri path the frame therefore lands in `dispatchSend`:

```ts
function dispatchSend(request: SidecarRpcRequest): void {
  const listeners = listenerRegistry.get(request.channel) ?? []
  for (const listener of listeners) { ... }   // empty array -> no-op
}
```

An unregistered `send` channel produces **no reject, no timeout, no
`UNPORTED_CHANNEL_MARKER`, no log line** — this repo's own recorded G-30-01 /
`sidecar-send-channels-fail-silently` failure class. The net effect of the "fix" under Tauri:
a `repair` that fails at the transport layer (or a wedged long-running repair that the user
cancels the app out of) is now caught and thrown away silently. The pre-fix behaviour at
least produced a visible renderer-console unhandled rejection.

There is also no user-facing feedback on either build: the catch neither surfaces a dialog
nor a toast, and it does not clear any in-flight UI state — the user sees the repair dialog
close and nothing else happen.

**Fix:** log through a channel that is actually live on the sidecar, and give the user
feedback. Either register `logError` in the sidecar (a one-line `ipcMain.on('logError', ...)`
in a curated registration module, matching `logger/ipc_handler.ts:15`'s body), or use a
channel this slice already ported. Minimum viable:

```ts
async function onRepairYesClick(appName: string) {
  try {
    await repair(appName, runner)
  } catch (error) {
    // console.error is transport-independent and always visible in the webview
    console.error(`repair failed for ${appName}:`, error)
    window.api.logError(`repair failed for ${appName}: ${error}`)
    showDialogModal({
      showDialog: true,
      type: 'ERROR',
      title: t('box.error.title', 'Error'),
      message: t('box.repair.error', 'Repair failed. See the log for details.')
    })
  }
}
```

and, separately, add `logError` to the sidecar's curated registrations (plus a positive
side-effect test — "did not throw" is explicitly not acceptable evidence for a `send` channel
in this slice's own stated standard).

### CR-02: `installUnhandledRejectionGuard` can itself crash the sidecar — `String(reason)` is built OUTSIDE its own `try`

**File:** `src/backend/sidecar/processGuards.ts:48-63`

**Issue:**
The module docstring states the absolute contract: *"This guard must NEVER re-throw, NEVER
terminate the process ... Its own logging is wrapped in a try/catch"*. The message
construction is not inside that `try`:

```ts
target.on('unhandledRejection', (reason: unknown) => {
  const message = `[sidecar] unhandled promise rejection: ${String(reason)}`  // <-- line 49, OUTSIDE the try
  try {
    logWarning(message, LogPrefix.Backend)
  } catch { ... }
})
```

`String(reason)` throws `TypeError: Cannot convert object to primitive value` for any value
with a null prototype or a throwing/absent `toString`/`Symbol.toPrimitive` — e.g.
`Promise.reject(Object.create(null))`, or a `Proxy` whose `get` trap throws. Verified
empirically in this environment:

```
$ node -e "... t.on('unhandledRejection', r => 'x' + String(r)); t.emit('unhandledRejection', Object.create(null))"
listener emit THROWS out of emit(): Cannot convert object to primitive value
```

A throw from a `process` `'unhandledRejection'` listener is not contained: Node converts it
into an `uncaughtException`, and the sidecar installs no `uncaughtException` handler — so the
process dies. That is the precise `sidecar-dialog-reject-crashes` failure mode this module was
written to prevent, reintroduced by the guard itself.

Group 2's test at `sidecarRejectionGuard.test.ts:414-438` covers only the case where
`logWarning` throws; nothing exercises a non-stringifiable `reason`, so the suite stays green.

**Fix:**

```ts
target.on('unhandledRejection', (reason: unknown) => {
  let message = '[sidecar] unhandled promise rejection: <unstringifiable reason>'
  try {
    message = `[sidecar] unhandled promise rejection: ${
      reason instanceof Error ? reason.stack ?? reason.message : String(reason)
    }`
  } catch {
    // keep the fallback message
  }
  try {
    logWarning(message, LogPrefix.Backend)
  } catch {
    try {
      process.stderr.write(`${message}\n`)
    } catch {
      /* swallow */
    }
  }
})
```

and add a Group 2 case: `expect(() => target.emit('unhandledRejection', Object.create(null))).not.toThrow()`.

### CR-03: The gap cycle's own new suite reuses the redirect mechanism CR-03 declared insufficient — real config dir is touched at module load, and the suite is guaranteed red on Windows

**File:** `src/backend/sidecar/__tests__/sidecarRejectionGuard.test.ts:29-76, 280-289`
**Also:** `src/backend/constants/paths.ts:9, 31-42`, `src/backend/sidecar/pathShim.ts:30-39`

**Issue:**
`gameDetailsFlows.test.ts` and `enrichmentFlows.test.ts` were correctly fixed by mocking
`../pathShim`. The suite this cycle **created** was not: it mocks only `os.homedir()` and
relies on a `beforeAll` tripwire. Its docstring justifies that with *"NO FILESYSTEM WRITES ...
this suite never calls any directory-creation, file-write, or file-removal Node fs API
itself."* That justification is wrong on two counts:

1. **It does write.** Every test calls `init()`, which calls `initLogger()`; the resulting
   `LogWriter` creates and rotates a real log file. Proven after running this suite locally:
   ```
   /var/folders/.../T/gamelib-sidecarrejectionguard-test-home-33645/1/.local/state/GameLib/logs/gamelib.log
   ```
2. **The tripwire fires too late, and only on some platforms.** The assertion at line 285-288
   calls `setupIsolatedBootstrapHarness()` *first*, which `require`s
   `backend/constants/paths.ts`. On win32 `pathShim.resolveAppDataDir()` returns
   `env.APPDATA`; on Linux it returns `env.XDG_CONFIG_HOME` when set — neither is affected by
   the `os` mock (`pathShim.ts` reads `platform` from `process`, not from the mocked
   `backend/constants/environment`). `paths.ts` then executes, at module scope:
   ```ts
   const legacyAppFolder = join(configFolder, 'heroic')
   if (existsSync(legacyAppFolder) && !existsSync(appFolder)) {
     renameSync(legacyAppFolder, appFolder)   // real user config folder, renamed
   }
   ```
   That mutation happens **before** the containment `expect(...)` on the next lines can fail.
   Immediately afterwards, the `expect` fails, so on Windows (and on Linux with
   `XDG_CONFIG_HOME` set) this suite is **permanently red** — a new, unconditional CI failure
   on any Windows leg, not a safety net.

This is the same finding CR-03 raised, unclosed for the newest suite, plus a cross-platform
CI regression.

**Fix:** copy the exact `jest.mock('../pathShim', ...)` factory from `gameDetailsFlows.test.ts:136-161`
into this suite (same tmp-root shape, per-suite name), keep the tripwire as a belt-and-braces
check, and delete the "NO FILESYSTEM WRITES" paragraph — replace it with an accurate statement
that `init()` writes a log file inside the redirected tmp root. Also see WR-01 below: the
tripwire must additionally assert the log path.

### WR-01: No containment tripwire covers the log path — `getBaseLogPath()` is env-driven and bypasses BOTH the `os` mock and the `pathShim` mock

**File:** `src/backend/sidecar/__tests__/gameDetailsFlows.test.ts:318-331`;
`src/backend/sidecar/__tests__/enrichmentFlows.test.ts:274-287`;
`src/backend/sidecar/__tests__/sidecarRejectionGuard.test.ts:280-289`
**Root:** `src/backend/logger/paths.ts:12-24`, `src/backend/logger/log_writer.ts:67-75`

**Issue:**
All three tripwires assert containment for `appFolder`, `userDataPath` and `fixesPath` only.
The log directory is computed independently of `pathShim`:

```ts
if (isWindows) return join(process.env.LOCALAPPDATA ?? join(homedir(), 'AppData','Local'), 'GameLib', 'logs')
if (isMac)     return join(homedir(), 'Library', 'Logs', 'GameLib')
const stateHome = process.env.XDG_STATE_HOME ?? join(homedir(), '.local', 'state')
return join(stateHome, 'GameLib', 'logs')
```

Every one of these suites calls `init()` → `initLogger()`, and `LogWriter.#archiveOldLogFile()`
`renameSync`s any existing `gamelib.log` to `gamelib.log.old` on first write — a destructive
rename of a real user file. With `XDG_STATE_HOME` set (these suites pin
`backend/constants/environment` to `isLinux: true`, so the Linux branch is always taken
regardless of host OS), the target is the developer's real state directory, and the tripwire
that exists precisely to make this impossible does not look at it.

**Fix:** add the log path to each tripwire and, better, redirect it. In the guard:

```ts
import { getLogFilePath } from '../../logger/paths'   // or re-derive getBaseLogPath()
for (const candidate of [appFolder, userDataPath, fixesPath, getLogFilePath({})]) { ... }
```

and in each suite's mock block, neutralise the env inputs the way `pathShim` is neutralised —
e.g. `delete process.env.XDG_STATE_HOME; delete process.env.LOCALAPPDATA` in a hoisted block,
or mock `backend/logger/paths`'s `getLogFilePath` to a tmp path.

### WR-02: The Gate 7 / Gate 8 sha256 pins hash raw bytes with no line-ending normalisation — both fail on any Windows checkout

**File:** `src/backend/sidecar/__tests__/gameDetailsImportGate.test.ts:283-300, 354-373`

**Issue:**
Both gates do `createHash('sha256').update(readFileSync(filePath))` — raw bytes. The repo's
`.gitattributes` contains only `pnpm-lock.yaml linguist-generated=true`; there is no
`* text=auto eol=lf`. Git for Windows defaults to `core.autocrlf=true`, so the working-tree
copies of `settingsFlowRegistration.ts` and `electronUntouched.test.ts` are CRLF there and both
digests change. The gate then reports the do-not-touch file as tampered with when nothing was
touched — noise that trains reviewers to update the constant reflexively, which is exactly the
failure mode the pin was introduced to prevent. (`.editorconfig` declares `end_of_line = lf`
but editorconfig does not govern git checkout.)

**Fix:** hash normalised text, and/or normalise at the git layer.

```ts
const normalized = readFileSync(filePath, 'utf-8').replace(/\r\n/g, '\n')
const digest = createHash('sha256').update(normalized, 'utf-8').digest('hex')
```

(and add `* text=auto eol=lf` to `.gitattributes`; the digests as committed are the LF digests,
so they stay valid under this change — verified locally.)

### WR-04: `src/sidecar/index.ts`'s stated ordering property is not what the code achieves, and the Group 3 gate cannot detect the difference

**File:** `src/sidecar/index.ts:20-29`; `src/backend/sidecar/__tests__/sidecarRejectionGuard.test.ts:441-456`

**Issue:**
The docstring claims: *"`installUnhandledRejectionGuard()` must run BEFORE `init()` — the guard
must be live before `bootstrap.ts`'s module scope and `init()` can produce any rejection."*
ES modules evaluate **every static import before any of the importing module's own executable
statements** — the exact rule `bootstrap.ts`'s own docstring (lines 17-22) spells out for the
`Module._load` hook. So the real order is:

1. `backend/sidecar/bootstrap` module scope (which pulls `./installElectronHook`, `./handlers`,
   and the entire backend module graph),
2. `backend/sidecar/processGuards` module scope (no side effects),
3. `installUnhandledRejectionGuard()`,
4. `init()`.

The guard is therefore *not* live during bootstrap's module scope. In practice this is benign
today — Node emits `unhandledRejection` only after the microtask queue drains at the end of the
tick, and steps 1-3 are one synchronous run — but the property the file claims (and the property
a future reader will rely on) does not hold, and Group 3's gate only compares
`indexOf('installUnhandledRejectionGuard(')` against `indexOf('init()')` in the source text: it
would pass unchanged even if the guard genuinely could not cover module scope.

**Fix:** make the install a module-scope side effect of a module imported first, so import
ordering is the ordering:

```ts
// src/sidecar/installGuard.ts
import { installUnhandledRejectionGuard } from 'backend/sidecar/processGuards'
installUnhandledRejectionGuard()

// src/sidecar/index.ts
import './installGuard'                            // MUST be the first import
import { init } from 'backend/sidecar/bootstrap'
init()
```

and change the Group 3 gate to assert that `'./installGuard'` is the first import line, plus
correct the docstring.

### WR-07: `loadMainRsCode()`'s mid-line comment strip corrupts any Rust string literal containing `//`

**File:** `src/backend/__tests__/longRunningChannels.test.ts:54-61`

**Issue:**

```ts
.map((line) => line.replace(/\/\/.*$/, ''))
```

is applied to every surviving line, including code. Any Rust string literal containing `//`
(a URL such as `"steam://rungameid/..."`, `"https://..."`, a path with a doubled separator)
is truncated at that point in the stripped copy. `main.rs` has no such literal on a code line
today, so nothing is currently broken — but this helper's whole job is textual fidelity, and it
already backs the `INVOKE_TIMEOUT` assertion. A future `const SOME_URL: &str = "https://…";`
silently changes what every gate in this file sees.

**Fix:** only strip a trailing `//` comment when it is outside a string literal, or (simpler and
sufficient for this file's purpose) drop the mid-line strip entirely and rely on the
whole-line filter, since `main.rs` puts its comments on their own lines:

```ts
return raw.split('\n').filter((line) => !line.trim().startsWith('//')).join('\n')
```
