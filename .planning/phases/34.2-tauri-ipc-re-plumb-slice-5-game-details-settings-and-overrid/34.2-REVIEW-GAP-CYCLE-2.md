## Critical Issues

### CR-01: The new containment gate declares an 11-suite hole as "deferred debt" — and one of those suites destroys the developer's real log file on every test run (REPRODUCED)

**File:** `src/backend/sidecar/__tests__/testContainment.test.ts:295-307` (the declared hole), realized in `src/backend/sidecar/__tests__/bootstrap.test.ts`

**Issue:**
`testContainment.test.ts` introduces `KNOWN_UNCOVERED_BOOTSTRAP_DRIVING_SUITES` — 11 suites that drive the real `bootstrap.init()` without the containment kit — with the note that they "carry the SAME pre-existing env-bypass risk class (`tests-clobbering-real-steam-store`)" and are "recorded as declared debt."

That is not theoretical debt. I reproduced live data loss twice:

```
(10:48:30) [INFO]: [Steam]: Steam TokenStore implementation set to SidecarKeyringTokenStore
```

Bisected to a single suite:

```

           settingsFlows skeletonFlows steamAuthFlows onlineMonitorWiring ...; do ... done
```

`bootstrap.test.ts` carries exactly one `jest.mock` (`../../online_monitor`, line 35) — no `os` mock, no `pathShim` mock, no `backend/logger/paths` mock — and calls the real `init()` three times (lines 82, 94, 125). `init()` → `initHeadless()` → `new LogWriter(getLogFilePath({}))` → `LogWriter#archiveOldLogFile()` `renameSync`s the real `gamelib.log` to `gamelib.log.old`, **destroying the prior `.old`**. Real user diagnostic data is lost on every `npm test`. (Confirmed the electron-store `*.json` files under `~/Library/Application Support/GameLib` were NOT touched — the token-wipe variant is not currently triggered, but nothing structurally prevents it: the same suite constructs real stores through the same unmocked path.)

The four in-scope suites are only contained on this macOS host because they *also* mock `backend/constants/environment` (`isMac:false`), forcing `getBaseLogPath()`'s Linux branch → `XDG_STATE_HOME ?? homedir()/.local/state` → mocked `homedir()`. `bootstrap.test.ts` mocks neither, so it takes the real darwin branch straight to `~/Library/Logs/GameLib`.

Shipping a gate whose explicit purpose is to prevent this class, while enumerating a live instance of it as acceptable debt, is not closure — it is documentation of an open data-loss defect.

**Fix:** Either (a) apply the same four-element kit to `bootstrap.test.ts` and the other 10 suites, or preferably (b) make containment structural instead of per-suite, so a new suite cannot opt out. A `setupFiles` entry for the backend jest project is the cheaper, drift-proof option:

```ts
// src/backend/jest.setupContainment.ts  (add to jest project `setupFiles`)
import { tmpdir } from 'os'
import { join, resolve, relative, isAbsolute } from 'path'

const TEST_ROOT = join(tmpdir(), `gamelib-jest-${process.pid}`)
process.env.XDG_STATE_HOME = join(TEST_ROOT, 'state')
process.env.XDG_CONFIG_HOME = join(TEST_ROOT, 'config')
process.env.LOCALAPPDATA = join(TEST_ROOT, 'localappdata')
process.env.APPDATA = join(TEST_ROOT, 'appdata')
jest.mock('os', () => ({ ...jest.requireActual('os'), homedir: () => TEST_ROOT }))

// Fail loudly if anything still resolves outside the sandbox.
const guard = (p: string) => {
  const rel = relative(resolve(tmpdir()), resolve(p))
  if (rel.startsWith('..') || isAbsolute(rel)) {
    throw new Error(`REFUSING TO RUN: "${p}" escapes os.tmpdir()`)
  }
}
```

Then `KNOWN_UNCOVERED_BOOTSTRAP_DRIVING_SUITES` can be deleted rather than maintained. At minimum, `bootstrap.test.ts` must be contained before this cycle is accepted — it is a one-file, ~40-line copy of the kit already written four times in this cycle.

## Warnings

### WR-01: The "no longer claims NO FILESYSTEM WRITES" gate is vacuous — it can never fail

**File:** `src/backend/sidecar/__tests__/testContainment.test.ts:368-376`

**Issue:** The assertion runs against **comment-stripped** source:

```ts
const stripped = stripComments(readFileSync(join(__dirname, name), 'utf-8'))
expect(stripped.toUpperCase()).not.toContain('NO FILESYSTEM WRITES')
```

`stripComments` (line 148-153) drops every line matching `^\s*(\/\/|\*|\/\*)`. A "NO FILESYSTEM WRITES" claim only ever lives in a docblock — i.e. on a line beginning with ` * ` — so it is always removed before the assertion runs. Proved empirically by injecting the claim into `loggerFlows.test.ts`'s docblock and re-running the stripper:

```
claim present in raw:          true
claim present after strip:     false
```

The test passes whether or not any of the four suites carries the false claim. This is the exact "vacuous test" failure mode this phase has already been cited for.

**Fix:** Match the false-claim gate against RAW source, and keep only the *pattern-presence* gates on stripped source:

```ts
it.each(IN_SCOPE_SUITES)('%s no longer claims "NO FILESYSTEM WRITES"', (name) => {
  const raw = readFileSync(join(__dirname, name), 'utf-8')
  expect(raw.toUpperCase()).not.toContain('NO FILESYSTEM WRITES')
})
```

The self-satisfaction risk the stripper exists for does not apply here: the whole point is to catch the claim wherever it appears, and this gate file itself is not in `IN_SCOPE_SUITES`.

### WR-02: New `logError` send listener leaks a floating promise — a failed log write becomes an unhandled rejection

**File:** `src/backend/sidecar/loggerFlowRegistration.ts:56-58`

**Issue:**

```ts
ipcMain.on('logError', (_event: unknown, ...args: unknown[]) => {
  logError(args[0] as string, LogPrefix.Frontend)
})
```

`logError` returns `heroicLogWriter.logError(...)` → `LogWriter#logBase()`, which is **`async`** (`log_writer.ts:131`) and performs `fsPromises.appendFile` / `mkdir`. The returned promise is neither awaited nor `.catch()`ed. `dispatchSend`'s `try`/`catch` (`sidecarRpc.ts:137-146`) is synchronous and cannot catch it — an `EACCES`/`ENOSPC`/deleted-log-dir failure produces a process-level `unhandledRejection`.

Today that is absorbed by `processGuards.ts` — but that module's own docstring (lines 10-14) states in bold that it "is explicitly NOT a substitute for call-site `.catch()`/`try`/`catch` handling — every `send`-kind body and every fire-and-forget call the sidecar owns must still guard itself." Brand-new code landed in the same gap cycle violates the invariant its sibling plan wrote. Net effect: a real log-write failure is reported as a generic `[sidecar] unhandled promise rejection` warning that is itself written to the log that just failed.

**Fix:**

```ts
ipcMain.on('logError', (_event: unknown, ...args: unknown[]) => {
  void Promise.resolve(logError(args[0] as string, LogPrefix.Frontend)).catch(
    (error: unknown) => {
      // Never stdout: that stream carries the RPC frame protocol.
      process.stderr.write(
        `[sidecar/loggerFlows] logError write failed: ${
          error instanceof Error ? error.message : '<unstringifiable>'
        }\n`
      )
    }
  )
})
```

### WR-03: `reportRepairFailure` re-introduces the CR-02 `${unknown}` interpolation class, and its "three independent signals" are actually sequential and unguarded

**File:** `src/frontend/screens/Game/GameSubMenu/repairFailure.ts:43-52`

**Issue:** The module docstring claims three signals "each with a different failure mode, so a single broken layer ... can never reproduce the zero-signal state." They are three bare statements in sequence with no guard between them:

```ts
console.error(`repair failed for ${appName}:`, error)          // 1 — safe (error is an arg)
window.api.logError(`repair failed for ${appName}: ${error}`)  // 2 — CAN THROW
showDialogModal({ ... })                                       // 3 — never runs if 2 throws
```

Line 45 interpolates `error: unknown` directly. For a null-prototype reason, or one whose `toString`/`Symbol.toPrimitive` throws, this throws `TypeError: Cannot convert object to primitive value` — the *identical* failure that plan 34.2-15 spent a whole task removing from `processGuards.ts` (see that file's lines 22-28). The consequence here is the user-visible signal (the ERROR dialog, signal 3) never renders, and the throw escapes `onRepairYesClick`'s `catch` (`index.tsx:147-149`) into the dialog button's un-awaited `async () => onRepairYesClick(appName)` (`index.tsx:158`) as an unhandled renderer rejection.

ESLint already flags exactly this line: `45:56 warning Invalid type "unknown" of template literal expression @typescript-eslint/restrict-template-expressions`.

The new test file's fourth case (`repairFailure.test.ts:105-117`) advertises itself as covering "the kind of 'hostile reason' this gap cycle's sibling plans (34.2-15) have specifically hardened against elsewhere" but only passes `'a plain string rejection'` — which never exercises the throw path. A `Object.create(null)` case would fail today.

**Fix:** stringify defensively and show the user-visible signal first (or independently):

```ts
export function reportRepairFailure({ appName, error, showDialogModal, t }: ReportRepairFailureOptions): void {
  let errorText = '<unstringifiable error>'
  try {
    errorText = error instanceof Error ? (error.stack ?? error.message) : String(error)
  } catch {
    // keep the fallback
  }

  console.error(`repair failed for ${appName}:`, error)
  window.api.logError(`repair failed for ${appName}: ${errorText}`)
  showDialogModal({ showDialog: true, type: 'ERROR', title: t('box.error.title', 'Error'), message: t('box.repair.error', 'Repair failed. See the log for details.') })
}
```

and add the missing regression case to `repairFailure.test.ts`:

```ts
it('never throws, and still shows the dialog, for an unstringifiable error', () => {
  expect(() => reportRepairFailure({ appName: 'G', error: Object.create(null), showDialogModal: showDialogModalMock, t })).not.toThrow()
  expect(showDialogModalMock).toHaveBeenCalledTimes(1)
})
```

### WR-04: `testContainment.test.ts` mislabels a load-bearing mock as "parity only", inviting a change that makes RED-PROOF-2 vacuous

**File:** `src/backend/sidecar/__tests__/testContainment.test.ts:122-133` (and the RED-PROOF-2 note at 263-268)

**Issue:** The comment above `jest.mock('backend/constants/environment', ...)` states it is "kept even though `pathShim.ts`/`logger/paths.ts` read `process.platform`/`process.env` directly rather than this module — included for parity."

That is factually wrong for `logger/paths.ts`. `getBaseLogPath()` (`src/backend/logger/paths.ts:12-24`) branches on `isWindows`/`isMac` imported **from `../constants/environment`** — it never reads `process.platform`. Only `pathShim.ts:31` reads `process.platform`.

Consequence: Block A's `Object.defineProperty(process, 'platform', 'linux')` does nothing for the log path; the Linux branch is reached solely because of the `isMac:false` mock this comment describes as decorative. If a future reader trusts the comment and removes that mock, on macOS `getBaseLogPath()` takes the darwin branch → `homedir()` → contained by the `os` mock regardless — and RED-PROOF-2 ("commenting out the `backend/logger/paths` mock makes the `getLogFilePath({})` test fail") silently becomes false. The gate would then pass while proving nothing.

**Fix:** correct the comment and mark the mock load-bearing:

```ts
// ── backend/constants/environment — LOAD-BEARING, not parity: `logger/paths.ts`'s
// getBaseLogPath() branches on isWindows/isMac imported from THIS module (it never
// reads process.platform). Pinning isMac:false forces the XDG_STATE_HOME branch, which
// is what makes RED-PROOF 2 below non-vacuous on a darwin host. Do not remove.
```

### WR-05: The containment tmp-root string is duplicated three times per suite, inconsistently — one edit silently desynchronizes the mocks while every tripwire still passes

**File:** `src/backend/sidecar/__tests__/loggerFlows.test.ts:84, 105, 139`; `testContainment.test.ts:44, 66, 97`; `sidecarRejectionGuard.test.ts:83, 108, 145`; `gameDetailsFlows.test.ts:123, 141, 180`; `enrichmentFlows.test.ts:82, 100, 139`

**Issue:** Each suite hardcodes its tmp root three times — once per mock factory — and `loggerFlows.test.ts`/`testContainment.test.ts` make it worse by extracting a `TMP_ROOT_NAME` const for the `os` factory only, leaving the other two as inline literals. Nothing asserts the three roots agree. Change one and the `os` mock, the `pathShim` mock and the `backend/logger/paths` mock point at three different directories — while the `beforeAll` tripwire still passes, because all three are still under `os.tmpdir()`. The tripwire cannot detect the desync it most needs to detect.

**Fix:** hoist to a single `mock`-prefixed module-scope constant (the `mock` prefix is what makes it legal inside a hoisted factory) and use it in all three factories:

```ts
const mockTmpRootName = `gamelib-loggerflows-test-home-${process.pid}`
// ...then reference `mockTmpRootName` in the os, pathShim and logger/paths factories.
```

### WR-06: Hoisted `jest.mock` factories reference an out-of-scope `const` — survives only by accident of call ordering

**File:** `src/backend/sidecar/__tests__/loggerFlows.test.ts:88-95` (uses `TMP_ROOT_NAME` declared at :84); `testContainment.test.ts:48-55` (uses `TMP_ROOT_NAME` declared at :44)

**Issue:** ts-jest hoists `jest.mock(...)` above the `const TMP_ROOT_NAME` declaration and above all `import`-generated `require`s. The reference survives today only because it sits inside the lazily-evaluated `homedir: () => ...` arrow and nothing calls `os.homedir()` during module evaluation (both `pathShim` and `backend/logger/paths` are mocked away). Any future import chain that calls `homedir()` at module scope yields `ReferenceError: Cannot access 'TMP_ROOT_NAME' before initialization` — a confusing failure with no relation to its cause. Under `babel-jest` (which `babel-plugin-jest-hoist` enforces) the file would be rejected outright: "The module factory of `jest.mock()` is not allowed to reference any out-of-scope variables."

**Fix:** rename to a `mock`-prefixed identifier (`mockTmpRootName`) — the convention this repo already uses for `mockTestHomeSuffix` in `sidecarRejectionGuard.test.ts:73` — which is both hoist-legal and TDZ-documented. Combine with the WR-05 fix.

### WR-07: Block A mutates `process.platform` and four env vars process-wide, restored only in `afterAll` — the exact pattern the file itself declares unsafe

**File:** `src/backend/sidecar/__tests__/testContainment.test.ts:167-206`

**Issue:** `beforeAll` overwrites `APPDATA`, `XDG_CONFIG_HOME`, `XDG_STATE_HOME`, `LOCALAPPDATA` with non-existent absolute sentinels and redefines `process.platform` to `'linux'`; `afterAll` restores. The suite's own docstrings (and `loggerFlows.test.ts:235-237`, and the repo's `tests-clobbering-real-steam-store` lesson at commit `92c29a5e`) state that "an `afterAll` restore is not a safety net under jest worker force-exit." Jest reuses a worker process across test files, so a force-exit or a `process.exit` in this suite leaks a fake `linux` platform and four bogus path roots into every subsequent file in that worker.

**Fix:** move the mutation into `beforeEach`/`afterEach` scoped to the three tests that need it, and add a `try`/`finally` inside the tests themselves rather than relying on hook ordering. Alternatively use `jest.replaceProperty(process, 'platform', 'linux')` (jest ≥29.4), which is unwound by `restoreAllMocks` and by jest's own teardown.

### WR-08: The Block B gate is a fixed 4-entry declared list — a new uncontained suite is invisible to it

**File:** `src/backend/sidecar/__tests__/testContainment.test.ts:279-284, 310-316`

**Issue:** `IN_SCOPE_SUITES` is hardcoded to four names with an anti-vacuity `toHaveLength(4)` pin. The declared-not-derived rationale is sound for preventing the list from *shrinking*, but it also means the gate cannot *grow*: a suite added tomorrow that drives `bootstrap.init()` without the kit passes every gate in this file silently. Given CR-01 above (an existing suite already doing exactly that), this is the failure mode most likely to recur.

**Fix:** keep the declared list as the floor, and add a derived tripwire that fails on any *unclassified* suite:

```ts
it('every sidecar suite is either in the contained list or the declared-uncovered list', () => {
  const all = readdirSync(__dirname).filter((f) => f.endsWith('.test.ts') && f !== 'testContainment.test.ts')
  const classified = new Set([...IN_SCOPE_SUITES, ...KNOWN_UNCOVERED_BOOTSTRAP_DRIVING_SUITES])
  expect(all.filter((f) => !classified.has(f))).toEqual([])
})
```

### IN-05: Unchecked `args[0] as string` cast in the send listener

**Fix:** drop the cast and pass `args[0]` through as `unknown`, matching both the contract and `LogWriter`'s signature.
