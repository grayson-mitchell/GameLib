### Auto-fixed Issues

**1. [Rule 1 - Bug] `settingsFlows.test.ts`'s Invariant B guard asserted a now-false premise**
- **Found during:** Task 2 verification sweep (cross-plan regression check)
- **Issue:** `settingsFlows.test.ts` had a combined "Invariant B guard" test asserting BOTH `getUserInfo` and `readConfig` stayed unported (rejecting with `UNPORTED_CHANNEL_MARKER`). This plan's Task 1 makes `readConfig` a real registration (`main.ts:977`, owned by `gameDetailsFlowRegistration.ts`), so the `readConfig` half of that assertion became false and the test failed with a real dispatch error instead of the expected marker.
- **Fix:** Narrowed the test to `getUserInfo` only (still genuinely unported this phase) and added a comment pointing future readers at `gameDetailsFlows.test.ts` for `readConfig`'s real-dispatch coverage. `settingsFlowRegistration.ts` itself (the D-09 do-not-touch target) was NOT modified — only its test file.
- **Files modified:** `src/backend/sidecar/__tests__/settingsFlows.test.ts`
- **Verification:** `settingsFlows.test.ts` 17/17 green after the fix; `settingsFlowRegistration.ts` confirmed byte-identical to HEAD via `git diff --stat` and Task 3's own Gate 7.
- **Committed in:** `45ecaf6c` (Task 2 commit)

**2. [Rule 1 - Bug] `repair`'s D-02 proof test was initially vacuous — project-wide i18next automock**
- **Found during:** Task 2, during the mandated RED spot-check for the i18next-init removal
- **Issue:** `src/backend/__mocks__/i18next.ts` is a project-wide Jest manual mock, silently substituted for the real `i18next` npm package in EVERY backend test file with no explicit `jest.mock('i18next', ...)` call anywhere (the same trap 34.2-01's `bootstrapWirings.test.ts` discovered a level further back). The first RED spot-check attempt (temporarily removing `bootstrap.ts`'s `i18next.init()` call) still PASSED, because the notify body was the automock's `t(key) => key` echo (`"notify.finished.reparing"`, a non-empty string) rather than the real uninitialized package's `undefined` — the assertion would have passed identically whether or not the D-02 fix existed.
- **Fix:** Added `jest.unmock('i18next')` at the top of `gameDetailsFlows.test.ts` (mirrors `gameDetailsModules.test.ts`'s own precedent from plan 34.2-02), with a module-docstring comment recording the discovery. Re-ran the RED spot-check: now correctly fails with `Expected: "string", Received: "undefined"`.
- **Files modified:** `src/backend/sidecar/__tests__/gameDetailsFlows.test.ts`
- **Verification:** RED spot-check now genuinely fails without D-02's fix; GREEN with it restored. Full 22-test suite passes.
- **Committed in:** `45ecaf6c` (Task 2 commit)

**3. [Rule 1 - Bug] `repair`'s `isOnline()` gate silently defaulted to `undefined` under `resetMocks: true`**
- **Found during:** Task 2, initial suite run (before any RED spot-checks)
- **Issue:** The project's shared `jest.config.js` sets `resetMocks: true`, which runs `jest.resetAllMocks()` before EVERY test — including the very first one, BEFORE any `beforeEach` re-arms anything. This strips even a `jest.mock` FACTORY's own inline default implementation (`isOnline: jest.fn(() => true)`), not just call history. Without re-arming, `isOnline()` returned `undefined` for every test in the file, so `repair`'s `if (!isOnline())` guard silently took its early-return branch and neither `notify()` nor `sendGameStatusUpdate()` were ever called — both `repair` tests failed with "0 calls".
- **Fix:** Added `mockedIsOnline.mockReset().mockReturnValue(true)` to the suite's `beforeEach`, with a comment documenting the gotcha for future suites in this codebase.
- **Files modified:** `src/backend/sidecar/__tests__/gameDetailsFlows.test.ts`
- **Verification:** Both `repair` tests pass; full 22-test suite green.
- **Committed in:** `45ecaf6c` (Task 2 commit)
