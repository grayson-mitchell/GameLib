## Critical Issues

### CR-01: The WR-02 call-site rejection guard is inert — `logError()` returns `undefined`, so `.catch` can never fire

**File:** `src/backend/sidecar/loggerFlowRegistration.ts:114-134`
**Also:** `src/backend/sidecar/__tests__/loggerFlows.test.ts:453-616` (the tests
that "prove" the fix)

**Issue:**

The fix is:

```ts
void Promise.resolve(logError(args[0], LogPrefix.Frontend)).catch((error) => { ... })
```

and the accompanying docstring asserts (lines 65-69):

> `logError(...)`'s return value is normalised via `Promise.resolve(...)` before
> `.catch` is attached: the declared TypeScript return type is `void` ... **but
> the runtime value is a promise today** via `LogWriter#logError` -> `#logBase`.

That last clause is false. `backend/logger/index.ts:25-27` is:

```ts
const logError = (...params: Parameters<LogWriter['logError']>) => {
  heroicLogWriter.logError(...params)   // <-- block body, NO return
}
```

The arrow function has a **block body with no `return`**, so the promise produced
by `LogWriter#logError` -> `#logBase` is dropped inside `backend/logger` and
`logError()` evaluates to `undefined`. (This is also *why* the declared TS return
type is `void` — the docstring cites that fact as if it were merely a stale
annotation, when it is the type checker correctly reporting the runtime shape.)

Empirically confirmed against the real module during this review:

```
RETURN VALUE typeof= undefined  isPromise= false  hasThen= false
```

Consequences:

1. `Promise.resolve(undefined).catch(...)` resolves immediately; the handler is
   **unreachable in production**. A real `EACCES`/`ENOSPC`/deleted-log-dir
   failure still surfaces as a process-level `unhandledRejection` absorbed by
   `processGuards.ts` — exactly the state WR-02 claims to have ended. The
   documented `processGuards.ts` invariant the fix says it restores is still
   violated.
2. The four new WR-02 tests (`loggerFlows.test.ts` Tests A-D) pass only because
   each one does
   `jest.spyOn(logger, 'logError').mockImplementation(() => Promise.reject(...))`
   — replacing the export with a **promise-returning** shape that never occurs at
   runtime. Test A's load-bearing assertions
   (`expect(callSiteDiagnostic).toBeDefined()`,
   `expect(line).not.toContain('unhandled promise rejection')`) are therefore
   green against a fabricated contract. The suite would pass identically if the
   `.catch` were deleted from production code and the spy alone kept.
3. A **synchronous** throw from `logError` (e.g. `heroicLogWriter` still
   `undefined` before `initHeadless()` — reproduced in this review as
   `TypeError: Cannot read properties of undefined (reading 'logError')`) also
   escapes the guard, because it happens during argument evaluation, before
   `Promise.resolve` is ever called. It lands in `dispatchSend`'s catch, not the
   new handler. This is the recorded `heroicLogWriter unset until bootstrap init`
   gotcha.

**Fix:**

Propagate the promise at the source, then re-prove the guard *without* a spy on
`logger.logError`.

```ts
// src/backend/logger/index.ts:25-27 — expression body returns the promise
const logError = (...params: Parameters<LogWriter['logError']>) =>
  heroicLogWriter.logError(...params)
```

(Do the same for `logDebug`/`logInfo`/`logWarning` or leave them; note this
changes the inferred type to `Promise<void>` and will surface floating promises
at other call sites — audit with `@typescript-eslint/no-floating-promises`.)

Then also guard the synchronous throw path at the call site:

```ts
ipcMain.on('logError', (_event: unknown, ...args: unknown[]) => {
  let settled: Promise<unknown>
  try {
    settled = Promise.resolve(logError(args[0], LogPrefix.Frontend))
  } catch (error: unknown) {
    settled = Promise.reject(error)
  }
  void settled.catch((error: unknown) => { /* existing diagnostic body */ })
})
```

And replace the spy-based proof with one that exercises the real module — e.g.
point `getLogFilePath` at an unwritable path via the existing
`jest.mock('backend/logger/paths', ...)` kit and assert the
`[loggerFlowRegistration]` prefix appears. A test that must stub the function
under test to observe the behaviour under test is not evidence.

### CR-02: Structural containment is specifier-dependent — `jest.mock('os')` does not cover `require('node:os')`, and no gate detects the hole

**File:** `src/backend/jest.setupContainment.ts:161-178` (and its claim at lines
41-51, 163-166)
**Also:** `src/backend/sidecar/__tests__/structuralContainment.test.ts:31`,
`src/backend/sidecar/__tests__/testContainment.test.ts:706-742`

**Issue:**

The module states its guarantee as universal:

> so every module in the backend graph that does `require('os')` /
> `import { homedir } from 'os'` for the rest of this test file's lifetime gets
> THIS factory's object ... a twelfth suite added tomorrow with zero containment
> code of its own is contained by construction

Measured inside a real backend test file with this `setupFiles` entry active:

```
os.homedir()      = /var/folders/.../T/gamelib-jest-home-42126   <- contained
node:os.homedir() = /Users/graysonmitchell                        <- REAL HOME
sameObject        = false
```

Jest's registry keys the `node:`-prefixed builtin separately, so `jest.mock('os')`
leaves `node:os` fully un-redirected. The `node:` import style is already
established in this codebase — `src/backend/storeManagers/steam/depot/decompressPool.ts:18`
does `import * as os from 'node:os'`, and eight backend test files import
`tmpdir` from `'node:os'`. A single future `import { homedir } from 'node:os'` in
`logger/paths.ts`, `pathShim.ts`, `constants/paths.ts`, `steam/constants.ts` or
`utils/compatibility_layers.ts` silently re-opens the exact
`renameSync`-over-`~/Library/Logs/GameLib/gamelib.log` data-loss path — and:

- `structuralContainment.test.ts` stays green, because it imports `homedir` from
  `'os'` (line 31), not `'node:os'`;
- `testContainment.test.ts` Block D stays green, because it only regex-matches
  `process.env.<KEY> =` assignments (lines 706-742) and never checks the `os`
  mock at all (see WR-02 below);
- `bootstrap.test.ts`'s own tripwire stays green for the same reason.

The same gap exists for `os.userInfo().homedir`, which is not redirected at all —
`structuralContainment.test.ts:132` deliberately relies on that fact for its
anti-vacuity check, which is precisely what makes it an uncontained read.

A secondary instance of the same "by construction" over-claim: `jest.config.js`
lines 18-21 assert the destruction path "is reachable only from `src/backend`, so
the frontend/common/preload/meta jest projects are deliberately untouched." That
is true today (`meta/__tests__/buildSidecarSea.test.ts` only reads source text),
but it is a hand-maintained, unenforced assumption of exactly the kind plan
34.2-19 exists to eliminate — nothing fails if a `meta` or `preload` suite starts
importing `backend/logger` tomorrow.

**Fix:**

1. Register both specifiers in `jest.setupContainment.ts`:

```ts
const osFactory = () => ({
  ...jest.requireActual<typeof import('os')>('os'),
  homedir: () => containmentRoot,
  userInfo: (...args: Parameters<typeof import('os').userInfo>) => ({
    ...jest.requireActual<typeof import('os')>('os').userInfo(...args),
    homedir: containmentRoot
  })
})
jest.mock('os', osFactory)
jest.mock('node:os', osFactory)
```

(If `userInfo` is redirected, `structuralContainment.test.ts` Test 6 needs a
different independent reference — read `/etc/passwd` or capture the real value in
`setupFiles` before the mock and export it.)

2. Add an executable gate that would have caught this, e.g. in
   `structuralContainment.test.ts`:

```ts
it('node: specifier is redirected identically to the bare specifier', () => {
  const bare = require('os') as typeof import('os')
  const prefixed = require('node:os') as typeof import('os')
  expect(prefixed.homedir()).toBe(bare.homedir())
  assertContained(tmpdir(), prefixed.homedir())
})
```

3. Add a source gate forbidding `homedir`/`userInfo` imports from `'node:os'`
   anywhere under `src/backend` (comment-stripped), so the hole cannot be
   reopened by a future import.

### WR-07: Predictable, never-cleaned, default-permission containment root with a TOCTOU window

**File:** `src/backend/jest.setupContainment.ts:141-159`
**Issue:**

```ts
const containmentRoot = join(realTmpRoot, `gamelib-jest-home-${process.pid}`)
if (!existsSync(containmentRoot)) {
  mkdirSync(containmentRoot, { recursive: true })
}
```

The path is fully predictable from `TMPDIR` + pid, `existsSync`-then-`mkdirSync`
is a check-then-act race, no mode is specified, and the module states it
deliberately never cleans up. On macOS `tmpdir()` is per-user and private, so the
risk is low there; on Linux CI/dev boxes `/tmp` is world-writable, and a
pre-created symlink at `/tmp/gamelib-jest-home-<pid>` captures or redirects
everything the suite writes into it — which includes real `electron-store` JSON
(`fileStore.ts`) that some fixtures populate with token-shaped values, and the
full contents of `gamelib.log`. The no-cleanup decision also means every jest run
leaves a fresh directory tree behind indefinitely.
**Fix:** use the atomic, mode-0700, unpredictable-suffix primitive:

```ts
const containmentRoot = realFs.mkdtempSync(join(realTmpRoot, 'gamelib-jest-home-'))
realFs.chmodSync(containmentRoot, 0o700)
```

`mkdtemp` is atomic (no TOCTOU), creates with mode 0700, and removes the pid
collision concern entirely. If a stable path is genuinely needed for the
proof-suite assertions, export it (see WR-09) rather than deriving it.

### WR-08: `loadMainRsCode()` strips `//` to end-of-line unconditionally and will corrupt Rust string literals

**File:** `src/backend/__tests__/longRunningChannels.test.ts:54-61`
**Issue:** `.map((line) => line.replace(/\/\/.*$/, ''))` has no string-literal
awareness. `main.rs` is safe today (every `steam://` / `https://` occurrence is

```ts
expect(codeQuotes % 2).toBe(0) // no literal was cut in half
```

or scope the trailing-comment strip to lines with balanced quotes.

### WR-11: `structuralContainment.test.ts` Test 6's anti-vacuity assertion is macOS-specific and can hard-fail in containerised CI

**File:** `src/backend/sidecar/__tests__/structuralContainment.test.ts:127-152`
**Issue:** Three portability problems in the suite's only anti-vacuity check:

1. `join(realHome, 'Library', 'Logs', 'GameLib', 'gamelib.log')` is the macOS
   layout. On Linux/Windows the resolved log path can never equal that string, so
   `expect(logPath).not.toBe(realGamelibLog)` is trivially true and the assertion
   contributes nothing — the anti-vacuity check is itself vacuous off-macOS.
2. `assertNotContained(realHome, tmpdir())` fails spuriously wherever `TMPDIR` is
   set under `$HOME` (a common per-user dev/CI convention).
3. `os.userInfo()` throws `SystemError: uv_os_get_passwd` when the running uid has
   no `/etc/passwd` entry — routine in containerised CI (`--user $(id -u)` on a
   Docker image). That would take the whole suite red for an unrelated reason.

**Fix:** derive the expected real path from the same platform branch
`getBaseLogPath()` uses (import `isMac`/`isWindows` from
`backend/constants/environment`), guard `userInfo()` in a `try`/`catch` with an
explicit `it.skip`-style bail, and replace assertion 2 with a direct check that
`tmpdir()` is not a prefix of the *redirected* home rather than the real one.

### WR-12: `XDG_DATA_HOME`/`XDG_CACHE_HOME` are described as unread by first-party code, but `constants/paths.ts` reads `XDG_DATA_HOME`

**File:** `src/backend/jest.setupContainment.ts:208-213`
**Issue:** The comment states:

`src/backend/constants/paths.ts:21` is first-party code that reads it:

future change to the `.replace('/data','')` logic would silently alter behaviour
