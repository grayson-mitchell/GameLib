<objective>
Close gap-cycle-3 WARNING WR-03. `src/frontend/screens/Game/GameSubMenu/repairFailure.ts:45`
interpolates `${error}` where `error: unknown`, with no `try`/`catch`. This is the identical
defect class plan 34.2-15 was created specifically to remove from `processGuards.ts` — now
reintroduced in a new location within the same gap cycle.

For a null-prototype reason, or one whose `toString` / `Symbol.toPrimitive` throws, line 45
throws `TypeError: Cannot convert object to primitive value` BEFORE reaching the
`showDialogModal` call two lines below. Consequences: the user-visible ERROR dialog — the exact
signal REQ-34.2-12 exists to guarantee — never renders, and the throw escapes
`onRepairYesClick`'s catch (`index.tsx:147-149`) into the dialog button's un-awaited
`async () => onRepairYesClick(appName)` (`index.tsx:158`) as an unhandled renderer rejection.
The module's own docstring claims the three signals have "a different failure mode, so a single
broken layer can never reproduce the zero-signal state" — three bare sequential statements with
no guard do not deliver that property.

The existing suite's fourth test (`repairFailure.test.ts:105-117`) advertises itself as covering
"the kind of 'hostile reason' this gap cycle's sibling plans (34.2-15) have specifically
hardened against elsewhere" but passes only `'a plain string rejection'`, which never exercises
the throw path. It passes vacuously.

Purpose: make the user-visible signal unconditional and prove it with cases that actually fail
against today's code.
Output: a defensively-stringified `reportRepairFailure` and regression tests using
`Object.create(null)` and a throwing-`toString` object.
</objective>
