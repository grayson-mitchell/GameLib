<objective>
Close **verification gap #1 (REQ-34.2-12) / code-review finding CR-01**: the Phase 34.2 slice
ported `repair` onto the sidecar's 60s-bounded `invoke` path without auditing it against
`LONG_RUNNING_CHANNELS`, and did the same for `readConfig`.

`repair` is a full re-verify/re-download of an installed game (`legendary repair` / `gogdl repair`)
and routinely exceeds 60s on a multi-GB title. Today the Rust shell drops the pending entry at 60s,
returns `sidecar invoke timed out`, and later logs the real response as
`response for unknown/timed-out id=... (dropped)` — while the repair keeps running in the sidecar.
The renderer call site has no `.catch()`, so that spurious timeout also becomes an unhandled
promise rejection. This is verbatim the failure class the exemption list was created for
(Phase 30 CR-03).

`readConfig('library')` has the identical shape: it calls `libraryManagerMap['legendary'].refresh()`,
the exact operation `refreshLibrary` is already exempted for.

Purpose: convert a slow, silent, wrong-answer failure on real (non-Steam) game repairs back into the
honest failure mode the exemption list exists to provide.
Output: an eight-member exemption list, a pin that reflects it, and a renderer call site that cannot
produce an unhandled rejection.
</objective>

| Rust shell -> Node sidecar (stdio frames) | The pending-request map is keyed by id; a dropped entry and a late response are both attacker-irrelevant but availability-relevant |
