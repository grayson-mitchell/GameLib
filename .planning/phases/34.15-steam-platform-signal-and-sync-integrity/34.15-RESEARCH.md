**Researched:** 2026-08-16
**Domain:** Steam PICS bulk metadata capture (Node `steam-user` sidecar), Electron/Tauri dual-runtime IPC push events, React source-shape testing under a jsdom-less jest project
**Confidence:** HIGH (all file:line claims re-verified at HEAD 2026-08-16; the one genuinely external unknown — PICS `common.oslist`'s wire shape — is MEDIUM, backed by three independent third-party appinfo dumps, not the installed `steam-user` package itself, which ships no type definitions and does not document this field)

## Summary

CONTEXT.md's 16 decisions are locked and well-scouted. This research does not re-litigate any
of them. Its job was to answer the two things a planner cannot get from CONTEXT.md alone: (1)
the exact wire shape of PICS `appinfo.common.oslist` — the one fact D-02's "absent/empty writes
nothing" rule cannot be implemented correctly without — and (2) re-verify every canonical
file:line citation at HEAD, since CONTEXT.md was gathered same-day but several citations had
already drifted by the time this research ran.

**Primary recommendation:** Implement item 1's capture as a narrow local type (mirroring the
already-shipped `AppCommonName` pattern in `depot.ts:178`), never widening `select.ts`'s shared
`SteamAppInfo` interface. `common.oslist` is a top-level, comma-separated, lowercase string
(`"windows,macos,linux"`, tokens `windows`/`macos`/`linux` — never `osx`) — identical vocabulary
to the depot-level `config.oslist` the codebase already parses at `depot/select.ts:186-189`.
Absence is real but appears concentrated in old/non-game (Tool-type) PICS entries; every explicit
game appinfo example found in this research populated `common.oslist`, including Windows-only
titles. D-02's "write nothing" branch is therefore a genuine safety net for a minority case, not
a rule that silently defeats item 1's purpose for most of the library.

Two significant additions beyond CONTEXT.md's own citations: (a) `refresh()` has **three**
explicit `return` exit paths, but **Steps 2–4 of its body (lines 705–847) are wrapped in no
try/catch at all** — an exception thrown there is a fourth, uncaught failure mode that
CONTEXT.md's D-07 text does not name, and it is reachable on the exact unscoped mount-time path
(`runOnceWhenOnline(() => this.refresh())`, `library.ts:607`) that D-07 says is where the bug
reproduces; a plan that only adds emits at the two documented return sites will still leave this
path spinning forever on a hydration-loop exception. (b) the "three shipped saboteur gates" named
in D-12 (`treatsAbsentAsAvailable`/`includesWindowsRegardless`/`readonlyRowLeaksDepot`,
`steamPlatformRow.test.ts:194-249`) target `hasSteamWindowsDepot` and `selectSteamPlatformOptions`
— **not** `resolveDepotAvailability`, the function D-12 actually widens. The function D-12 widens
has its **own**, separate 8-test block (`steamPlatformRow.test.ts:281-416`, six truth-table rows +
`failsClosedOnUnknown` + one D-03 leak-guard) that will need reconciling at the TypeScript level
because `ResolveDepotAvailabilityInput`/`Output` currently have zero optional fields. This is a
reconciliation-cost correction, not a challenge to D-12's substance.

## Findings by Research Focus Area

### A. PICS `oslist` — the shape question

**Location in the codebase of the bulk-PICS precedent (re-verified at HEAD, all citations match
CONTEXT.md within 0-1 lines — negligible drift):**
- `depot.ts:420-434` — `getOwnedSets()`: `client.getProductInfo([], packageIds, true)` wrapped in
  `withTimeout(..., STEAM_PICS_BULK_TIMEOUT_MS, 'getOwnedSets getProductInfo')`. Sends the **full**
  package-id list in ONE call — **no chunking at all**.
- `depot.ts:447-464` — `fetchAppInfo()`: single-app fetch, `STEAM_PICS_TIMEOUT_MS` (25s).
- `depot.ts:466-484` — `fetchDlcInfos()`: `client.getProductInfo(dlcIds, [], true)`, full DLC-id
  list in one call, `STEAM_PICS_BULK_TIMEOUT_MS`.
- `withTimeout.ts:34` — `STEAM_PICS_TIMEOUT_MS = 25000` (single-app bound).
- `withTimeout.ts:47` — `STEAM_PICS_BULK_TIMEOUT_MS = 90000` (bulk/many-appid bound, sized
  specifically because node-steam-user #144 flags large-library PICS as legitimately slow; NOT
  multiplied by retries since WR-02 made a timeout non-retryable single-attempt).

**Precedent implies for item 1's chunk-size discretion (MEDIUM confidence — inferred from
precedent, not stated as a rule anywhere):** the existing bulk-PICS callers do **zero chunking** —
they pass the entire id list (however large) to one `getProductInfo` call and rely solely on
`STEAM_PICS_BULK_TIMEOUT_MS` as the safety net. A ~378-app owned-library scoped by D-04 to
uncaptured entries is well within the same order of magnitude as `getOwnedSets`' full
package-license list. Recommendation: mirror this precedent exactly — no batching, one
`client.getProductInfo(scopedAppIds, [], true)` call, bound by `STEAM_PICS_BULK_TIMEOUT_MS`
(reused, not a new constant, satisfying the Discretion constraint). If a future measured UAT run
(D-16) shows this genuinely times out on a large real library, that is empirical evidence to
revisit — not something knowable from source alone.

**The `common.oslist` shape (MEDIUM confidence — steam-user 5.3.0 ships NO type definitions
(`node_modules/steam-user/index.js`, no `.d.ts`; no `@types/steam-user` present in
`node_modules/@types/` despite being listed in the Standard Stack doc — verify this at plan time
if type coverage matters) and does not document `common.oslist` anywhere in its 133KB README. The
codebase's own type, `SteamAppInfo` in `depot/select.ts:75-78`, does not model `common` at all —
only `depots`/`extended.listofdlc`. This finding is therefore sourced from three independent
third-party PICS dumps, not from an authoritative Steam/steam-user source):**

- `common.oslist` is a **top-level field under `appinfo.common`**, a comma-separated STRING
  (never an array), using the SAME lowercase token vocabulary the codebase already parses at the
  DEPOT level (`depot/select.ts:186-189`, `cfg.oslist.split(',').includes(os)`): `windows`,
  `macos`, `linux`. **Never `osx`** — confirmed across all three sample dumps.
- Example (VEIN dedicated server, appid 2131400): `common.oslist: "windows,linux"`.
- Example (appid 538480, a title with a native macOS depot): `common.oslist: "windows,linux"` at
  the app-common level, with `depots.1005.config.oslist: "macos"` for the mac-specific depot —
  i.e. `common.oslist` reflects the UNION of what the title supports app-wide, matching
  `depot/select.ts`'s existing per-depot filtering semantics.
- Absence example (appid 4270, "RACE 07 Demo Dedicated Server", PICS `type: "Tool"`): NO
  `oslist` key anywhere under `common` at all. This is the only absence case found in this
  research, and it is a non-game Tool-type entry, not a Windows-only game.
- Sources: `github.com/WindowsGSM/SteamAppInfo` (community-maintained, auto-updated dedicated-
  server appinfo JSON dumps — the closest available proxy for real PICS wire shape since
  SteamDB's own browsable UI (steamdb.info) returned HTTP 403 to automated fetch during this
  research session) and `github.com/natbro/kaon` (macOS Steam-client internals research, which
  independently confirms `common { ... oslist "windows" ... }` is populated even for a plain
  Windows-only game, and documents the Steam CLIENT's own dual-check: "when `macos` is in the
  `oslist`... AND there is a valid macOS launch option" vs. "when `oslist` contains just
  `windows`").

**Practical implication for D-02's "absent/empty writes nothing" rule:** the absence case in this
research's sample set correlates with non-game Tool/legacy entries, not with the common
"ordinary Windows-only game" case — every actual GAME example found (including Windows-only
titles) populated `common.oslist` explicitly. This is reassuring evidence that D-02's safety-net
branch will be a genuine minority case for a real Steam library, not a rule that silently defeats
item 1's bulk-capture goal for most owned titles. This is not a challenge to D-02 — it is evidence
the rule is correctly conservative without being self-defeating. Flagged `[ASSUMED — MEDIUM]`
because it rests on third-party dumps rather than the installed `steam-user` package or an
authoritative Valve source; the D-16 UAT gate against a real ~378-game library is what will
actually confirm this at scale (worth an explicit note in the UAT script: "spot-check how many of
the repaired 370 residue entries actually got an `is_windows_native` value vs. stayed
`undefined`").

**Parser edge cases the Discretion-scoped `oslist` parser must handle (beyond D-02's literal
"absent/empty" text), inferred from `depot.ts:fetchAppInfo`'s existing single-app handling
(`depot.ts:456-460`, which currently THROWS when `apps?.[numericAppId]` is missing — a shape that
must NOT be copied into the new fail-soft bulk path):**
1. The whole bulk `getProductInfo` call throws/times out → D-03's fail-soft applies at the
   `refresh()` call-site level (log + continue), not per-app.
2. An individual `appId` is entirely absent from a SUCCESSFUL bulk response's `apps` map (e.g. a
   delisted or token-gated entry) → treat identically to "oslist absent": write nothing for that
   app. Do NOT throw (unlike `fetchAppInfo`'s single-app precedent).
3. `entry.appinfo.common` itself is absent (not just `.oslist`) → same, write nothing.
4. `entry.appinfo.common.oslist` present but an empty string `""` → write nothing (explicit in
   D-02's text).

**Recommended type pattern (mirrors an ALREADY-SHIPPED precedent exactly — `depot.ts:175-180`'s
`AppCommonName`):**
```typescript
// Source: depot.ts:175-180 pattern, mirrored
/** Narrow, ADDITIONAL view of PICS appinfo's `common.oslist` field — not part
 *  of select.ts's own SteamAppInfo (which only needs depots/extended). */
interface AppCommonOslist {
  common?: { oslist?: string }
}
```
Do NOT widen `SteamAppInfo` in `depot/select.ts` — that interface is shared with the download
orchestrator and widening it risks unrelated blast radius. This narrow-cast pattern is already the
house convention (used identically for `common.name` and for the depot `branches.public.buildid`
special key at `depot.ts:664-671`).

**PICS `oslist` vs. `appdetails.platforms` divergence:** not measurable from source alone (no
existing code path compares them). D-01 already accepts this as an intended, un-reconciled
divergence (later `appdetails` fetches legitimately overwrite PICS-sourced values) — this
research found no evidence to add beyond what CONTEXT.md already states, and reconciling them is
explicitly Deferred.

### C. The sync failure propagation seam

**`refresh()` exit-path census (re-verified at HEAD — `library.ts:670-853`):**

| # | Location | Trigger | Current behaviour |
|---|---|---|---|
| 1 | `library.ts:677-680` | `SteamUser.ensureConnected()` fails / no client / no `steamID` | `logWarning('Steam client not ready...')`, `return null` |
| 2 | `library.ts:699-703` | `client.getUserOwnedApps()` throws | `logError(...)`, serves cached library via `pushGameToLibrary`, `return { stdout: '', stderr: String(err) }` |
| 3 | `library.ts:846-852` | Success | persists library + syncedAt, `return { stdout: ..., stderr: '' }` |
| **4 (UNDOCUMENTED in CONTEXT.md)** | **`library.ts:705-847` (Steps 2-4: `buildInstalledMap`, `buildBottleInstalledMap`, `buildBridgeInstalledMap`, `buildIncompleteInstallSet`, the per-game hydration loop, `steamLibraryStore.set`)** | **Any exception in this ~140-line span** | **NOT wrapped in any try/catch — propagates as an UNCAUGHT REJECTED PROMISE.** |

Exit path 4 matters because of where `refresh()` is actually called:
- `library.ts:607`, `init()`'s background sync: `runOnceWhenOnline(() => this.refresh())`.
  `runOnceWhenOnline` (`online_monitor.ts:136-142`) calls `callback()` and discards its return
  value — no `.then`/`.catch` anywhere in the chain. A Step 2-4 exception here becomes a genuine
  unhandled promise rejection in the main/sidecar process, with **zero UI signal**, on the exact
  "mount-time refresh is unscoped" path CONTEXT.md's own D-06 rationale names as "where the bug
  actually reproduces."
- `main.ts:1049`, the `refreshLibrary` IPC handler: `await libraryManagerMap[library].refresh()`.
  Here a throw DOES propagate to the `await`, so this specific call path is not silent — but it is
  a different failure shape than exit paths 1/2/3 (an IPC rejection vs. a controlled return), and
  a plan that only wraps emits around the two documented `return` statements will still miss this
  path entirely on both call sites.

**Implication for D-07's "emit on every exit path" requirement:** the plan must wrap the ENTIRE
body of `refresh()` (or at minimum Steps 2-4) in a try/catch/finally that emits
`steamSyncStatus: 'failed'` before re-throwing or returning an error result — not just add two
emit calls next to the existing `return` statements. This is an extension of D-07's scope
consistent with its own text ("every exit path"), not a contradiction of it — CONTEXT.md's
citations for D-07 (`library.ts:670`, `:699-703`) simply didn't enumerate this fourth, unguarded
path.

**Clarification on the "silent failure on the sidecar" risk, verified from `src/preload/ipc.ts`
and `src/backend/sidecar/electronStub.ts`:** the ledgered `sidecar-send-channels-fail-silently`
memory is about a DIFFERENT direction (renderer→backend `send` calls like `logoutSteam`) — it is
not a literal description of this channel. For a BACKEND→RENDERER push like `steamMetadataSyncing`
(and the new `steamSyncStatus`), the mechanism is: `sendFrontendMessage()` (`backend/ipc.ts:68-83`)
→ under Tauri, `electronStub.ts`'s `pushFrontendMessage: (channel: string, ...args) => void` — a
**channel-agnostic forwarder** (accepts any string, no allowlist array to update on the emit side)
→ delivered as a `SidecarNotification` to the Rust webview. The actual silent-failure risk for a
NEW channel is entirely on the CONSUMER side: if `preload/api/steam.ts` doesn't export a
`frontendListenerSlot('steamSyncStatus')` registration AND `GlobalState.tsx` doesn't call it, the
backend emits fine, Rust forwards fine, and the renderer simply has nobody listening — no error
anywhere. `common/types/ipc.ts`'s `FrontendMessages` type will catch a missing TYPE declaration at
compile time, but will NOT catch a missing preload export or a missing `GlobalState.tsx`
subscription — those two are the genuinely silent gaps. This refines, rather than contradicts,
D-07's "obligation 1" text.

## Common Pitfalls

### Pitfall 1: Trusting `refresh()`'s two documented exit points as exhaustive
**What goes wrong:** D-07's emit wiring only covers `library.ts:680` and `:699-703`; Steps 2-4
(`:705-847`) throw uncaught on a hydration-loop exception (e.g. a corrupt ACF file), and the
mount-time caller (`runOnceWhenOnline`, `library.ts:607`) has no `.catch` at all.
**Why it happens:** the two `return` statements are the only OBVIOUS exit points; the absence of
a try/catch around the bulk of the function body is easy to read as "nothing can fail here"
rather than "nothing catches failure here."
**How to avoid:** wrap the whole `refresh()` body (or at minimum Steps 2-4) in try/catch/finally;
emit `steamSyncStatus: 'failed'` in the catch before re-throwing or returning an error shape.
**Warning signs:** a UAT forcing procedure that only tests the `client not ready` and
`getUserOwnedApps throws` branches and never forces a hydration-loop exception will pass green
while this gap remains.

### Pitfall 2: Reconciling the wrong tests for D-12
**What goes wrong:** a plan that "fixes" the three named `treatsAbsentAsAvailable`/
`includesWindowsRegardless`/`readonlyRowLeaksDepot` saboteurs (because D-12's text says "three
shipped saboteur gates pin" the widened function) wastes effort on tests that don't touch
`resolveDepotAvailability` at all, while the 8-test block that DOES will fail to compile
unnoticed if the plan doesn't also update it.
**Why it happens:** CONTEXT.md's phrasing groups "three saboteur gates" with "the function D-12
widens" in the same sentence; the actual test-to-function mapping requires reading the test file.
**How to avoid:** state explicitly in the plan (per Item E above) which block needs which change.
**Warning signs:** `npx jest steamPlatformRow.test.ts` reporting TypeScript compile errors on the
`resolveDepotAvailability` describe block's fixture objects.

### Pitfall 3: Assuming `is_mac_native` is three-valued at the point `InstallModal/index.tsx` reads it
**What goes wrong:** a mac-triple implementation that gates on `gameInfo.is_mac_native === undefined`
never fires, because `library.ts:785` already collapsed `undefined -> false` one layer upstream.
**Why it happens:** the Windows field (`is_windows_native`) is deliberately NOT collapsed at the
same boundary, and it is easy to assume the mac field follows the same rule by analogy.
**How to avoid:** gate mac-signal-unresolved on `steamPlatformsCaptured` (via
`hasSteamDepotSignalCaptured`), exactly mirroring how the Windows side already separates
"available" from "captured" into two distinct reads.
**Warning signs:** a unit test asserting `resolveDepotAvailability`'s mac branch behaves
differently for `is_mac_native: undefined` vs `is_mac_native: false` inputs would immediately
reveal this is moot if the seed is always pre-collapsed to `false`.
