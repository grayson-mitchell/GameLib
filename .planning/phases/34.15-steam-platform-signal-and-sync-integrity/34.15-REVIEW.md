# Phase 34.15: Code Review Report

**Reviewed:** 2026-08-16T04:46:38Z
**Depth:** standard
**Files Reviewed:** 30 (plus 4 read for cross-file tracing: `games.ts`, `online_monitor.ts`, and two locked-decision documents)
**Status:** issues_found

## Summary

This phase's three goals (bulk PICS platform capture, a real terminal `steamSyncStatus` signal, and mac-side
absent-is-not-negative parity) are each individually well-implemented and unusually thoroughly tested — the
`refresh()` exit-path census, the `steamSyncStatus` five-touchpoint wiring gate, and the `resolveDepotAvailability`
asymmetry table are all genuinely non-vacuous and RED-proven against real, source-derived specimens.

The review found one BLOCKER and four WARNINGs, all clustered around the same root cause: **the phase's own D-12/D-13
work widened `resolveDepotAvailability` and gated the header glyph row on `depotSignalResolved`, but never addressed
the fact that a *resolved* signal can still disagree with the seed `GameInfo` the frontend already has in memory** —
because two independent backend writers (`games.ts`'s `appdetails`-sourced per-game fetch and this phase's
`platformCapture.ts`'s PICS-`oslist`-sourced bulk fetch) write the same `is_mac_native`/`is_windows_native` fields
from two different Steam data sources with no reconciliation rule. The scrutiny brief's exact question — "a game
whose probe resolves `macDepotOffered: true` but whose seed `gameInfo.is_mac_native` is still stale — is that state
reachable?" — is answered **yes**, and it is not a rare corner case: it is the ordinary shape of "the eligibility
probe's live per-game fetch learned something the last bulk sync didn't."

The `refresh()` exit-path work (D-06/D-07) is real and the 4-path census is accurate for the code as written, but one
of the four properties this phase's own summary claims ("all four exit paths now emit `steamSyncStatus`") is **not
actually invariant** — it depends on an unenforced cross-module "never throws" contract on `captureOwnedAppPlatforms`,
which the test suite itself explicitly documents as accepted risk rather than closing.

## Critical Issues

### CR-01: The SteamDialog header glyph row can show a confirmed-wrong platform badge set once the depot signal resolves, because it reads a stale seed rather than the freshly-resolved answer

**File:** `src/frontend/screens/Library/components/InstallModal/index.tsx:165-166,224-249` and
`src/frontend/screens/Library/components/InstallModal/SteamDialog/index.tsx:404-413`

**Issue:**

`SteamDialog`'s header renders platform glyphs from `availablePlatforms`, gated only on `depotSignalResolved`
(34.15 D-13):

```tsx
{depotSignalResolved &&
  availablePlatforms.map((p) => (
    <FontAwesomeIcon className="InstallModal__platformIcon" icon={p.icon} key={p.value} />
  ))}
```

`availablePlatforms` is `platforms.filter(p => p.available)`, and `platforms`' macOS entry is computed from:

```ts
const isMacNative = Boolean(gameInfo?.is_mac_native)   // index.tsx:166 — the SEED, captured once at modal open
...
{ name: 'macOS', available: isMac && (isSideload || isMacNative), value: 'Mac', icon: faApple }
```

`isMacNative` is derived from the `gameInfo` prop handed down when the modal opened — it is **never** re-derived from
the live `resolveDepotAvailability` output (`macDepotOffered`/`hasMacDepot`) that this same file computes two lines
above it and that the *default platform* (`getDefaultplatform`) and the *select dropdown's option list*
(`selectSteamPlatformOptions`, fed the **unfiltered** `platforms` array) both correctly consult. D-13 only suppresses
the header row while `depotSignalResolved` is `false`; once it flips `true`, the row renders from whatever
`availablePlatforms` happened to compute from the stale seed.

This is concretely reachable, not hypothetical: `is_mac_native`/`is_windows_native` are written by **two
independent backend paths from two different Steam data sources**:

- `games.ts:648-656` (per-game, on `checkBottleEligibility()` → `ensurePlatformsCaptured()`, which is exactly what
  the install-form eligibility probe drives): `is_mac_native = !!data.platforms?.mac` — sourced from the public
  **`appdetails` store API**.
- `platformCapture.ts` (this phase's new bulk sync writer, D-01/D-02): sourced from the **PICS `appinfo.common.oslist`**
  field, explicitly documented in that file as "MEDIUM confidence... sourced from third-party PICS dumps."

Both write into the same `steamMetadataStore` entry's `is_mac_native`/`is_windows_native`/`platformsCaptured` fields
with no precedence rule — whichever ran most recently wins, and the two sources are not guaranteed to agree for a
given app. So the state the scrutiny brief asked about — `macDepotOffered: true` from the live per-game probe while
the seed `gameInfo.is_mac_native` (populated by the last bulk PICS sync, or never captured at all) is still `false`
— is an ordinary consequence of this design, reachable any time:

1. the last full library sync's bulk PICS capture skipped, failed, or disagreed with `appdetails` for this specific
   app, or
2. the modal is opened for a game added to the library after the last full sync, or
3. the modal is opened while a background `refresh()` is still in flight.

**What the user sees:** the SELECT dropdown correctly defaults to and offers "macOS" (via `getDefaultplatform`'s
re-derivation effect and `selectSteamPlatformOptions`'s unfiltered read), but the dialog's own header — sitting right
above it — shows no Apple glyph at all, and (because `platforms`' Windows entry is `available: true`
*unconditionally*, with no `hasWindowsDepot` gate) may simultaneously show a Windows glyph even for a game whose
Windows depot is confirmed absent (`platformRow === 'readonly-macos'`). This is precisely the "confident but wrong
platform assertion" defect class D-12/D-13/D-14 exist to close, reappearing in the omission direction the moment the
signal resolves via the live probe instead of the seed.

No existing test catches this: `steamDialogSource.test.ts`'s D-13 block (`Block 6`) only proves the row is *gated* on
`depotSignalResolved`; it asserts nothing about what `availablePlatforms` actually contains once that gate opens.

**Fix:** Feed the header glyph row (or `availablePlatforms` itself, for the Steam path only — the comment on
`SteamDialog/index.tsx:129-133` already notes the array must stay unfiltered for the other four dialogs) from the
same `windowsDepotOffered`/`macDepotOffered` values `resolveDepotAvailability` already computes, e.g. by deriving a
Steam-specific glyph list in `index.tsx` alongside `platformRowOptions`:

```ts
const steamHeaderPlatforms = isSteamManagedApp
  ? platforms.filter((p) =>
      p.value === 'Mac' ? macDepotOffered
      : p.value === 'Windows' ? windowsDepotOffered
      : p.available
    )
  : availablePlatforms
```

and pass `steamHeaderPlatforms` into `SteamDialog` instead of `availablePlatforms`.

**Resolution (2026-08-16, gap-closure round, commit `77f094bfd`):** Fixed as suggested, with one refinement — the
projection (`resolveSteamHeaderPlatforms`) was extracted into `steamPlatformRow.ts` as a standalone, unit-testable
pure function rather than inlined in `index.tsx`, so its CONTENT could be RED-proven against a filled specimen in
`steamPlatformRow.test.ts` (jest has no jsdom for `index.tsx`/`SteamDialog/index.tsx`). `SteamDialog`'s prop was
renamed `availablePlatforms` → `headerPlatforms` to make the content source explicit at the call site.
`availablePlatforms` itself is untouched and still feeds `DownloadDialog`/`ImportDialog`/`ThirdPartyDialog`/
`SideloadDialog` unchanged — proven by a source-gate census (`steamEligibilityWiring.test.ts` Group G) counting
exactly 4 occurrences of `availablePlatforms={availablePlatforms}`, none inside the `<SteamDialog>` arm. New tests
cover both reachable states named in this finding (stale-seed-omits-Mac, and the `readonly-macos` mirror where the
unconditional Windows entry must not leak through).

## Warnings

### WR-01: `selectSteamPlatformOptions`'s `'selectable'` branch always offers "macOS" regardless of `macDepotOffered`, undermining this phase's own mac-depot conservatism

**File:** `src/frontend/screens/Library/components/InstallModal/steamPlatformRow.ts:117-137` (pre-existing 34.13
code, not touched by this phase's diff, but directly relevant to this phase's D-12/D-14 charter)

**Issue:** `resolveDepotAvailability`'s `macDepotOffered` (34.15 D-12) is deliberately conservative — per its own doc
comment it is `true` "ONLY when the signal was genuinely captured AND said yes" and must never fail open. That
conservatism protects the *default* selection (`getDefaultplatform`), but it is never consulted by
`selectSteamPlatformOptions`'s `'selectable'` case:

```ts
case 'selectable': {
  const macEntry = platforms.find((p) => p.value === 'Mac')   // unconditional — no macDepotOffered check
  const windowsEntry = hasWindowsDepot ? platforms.find((p) => p.value === 'Windows') : undefined
  return [macEntry, windowsEntry].filter((p): p is T => Boolean(p))
}
```

`resolveSteamSectionGating` enters `'selectable'` whenever `isMac(host) && !effectiveBottleRequired &&
depotSignalResolved && hasWindowsDepot` — none of those four conditions requires the game to actually be confirmed
mac-native. `effectiveBottleRequired` (the one condition that *would* route a genuinely Windows-only game to
`'readonly-windows'` instead) is derived from `isBottleEligible()`, which requires `platformsCaptured === true`
before it can assert `bottleRequired = true`. If the eligibility probe **times out or fails** (a state D-04
explicitly anticipates and fails open for on the Windows side), `platformsCaptured` stays `false`,
`effectiveBottleRequired` stays `false` (fails closed), and `hasWindowsDepot`/`windowsDepotOffered` fails **open** to
`true` per D-04. The net result: `platformRow = 'selectable'`, and the dropdown will present "macOS" as a selectable
option for a game whose mac depot was never confirmed — and may not exist at all — purely because its eligibility
probe failed to resolve.

`steamPlatformRow.test.ts:140-143` pins this exact shape as intentional ("`'selectable'` with `hasWindowsDepot`
true returns `['Mac', 'Windows']`"), so this is a known, tested, 34.13-era design choice — but it directly
contradicts this phase's D-14 rationale ("macDepotOffered... must never be loosened... an uncaptured or unresolved
signal yields `false`, full stop") for the option *list*, even though D-14 is honored for the option *default*.

**Fix:** Either gate the `'selectable'` case's `macEntry` inclusion on a `hasMacDepot`/`macDepotOffered` parameter
(mirroring the existing `hasWindowsDepot` gate on `windowsEntry`), or — if this is judged out of this phase's scope —
record it explicitly as a known gap in `34.15-CONTEXT.md`'s Deferred Ideas so a future reviewer does not have to
re-derive it from scratch.

**Resolution (2026-08-16, gap-closure round, commit `dabd1ccc4`):** Fixed as suggested — `selectSteamPlatformOptions`
gained a required `hasMacDepot` parameter, applied only to the `'selectable'` branch (the one this finding named;
`'readonly-macos'`/`'pending'` are unaffected, confirmed by new invariance tests). The pinned test at
`steamPlatformRow.test.ts:140-143` was confirmed NOT to be one of Phase 34.14's DO-NOT-TOUCH gates (those are
specifically `hasSteamWindowsDepot` and its three saboteurs — `treatsAbsentAsAvailable`, `includesWindowsRegardless`,
`readonlyRowLeaksDepot` — none of which pins the `'selectable'` unconditional-mac shape), so it was safe to update; it
was replaced with a full 2×2 (`hasWindowsDepot` × `hasMacDepot`) truth table. A new `macIncludedRegardless` saboteur,
reproducing the exact pre-fix production shape, RED-proves the fix against the reachable state this finding named
(`windowsDepotOffered` true via D-04 fail-open, `macDepotOffered` false because never confirmed).

### WR-02: Two independent Steam platform-signal writers can silently disagree for the same app, with no precedence rule

**File:** `src/backend/storeManagers/steam/platformCapture.ts:149-173` (`mergePlatformCapture`) vs.
`src/backend/storeManagers/steam/games.ts:648-731`

**Issue:** `platformCapture.ts`'s bulk writer (this phase) and `games.ts`'s per-game writer (pre-existing) both
perform a read-modify-write merge into the same `steamMetadataStore` entry, writing `is_windows_native`,
`is_mac_native`, `is_linux_native`, and `platformsCaptured` — but from two structurally different Steam APIs (PICS
`appinfo.common.oslist` vs. the public `appdetails` store API's `platforms` object). Neither writer checks whether
the other has already written a value, and neither records provenance (which source produced the currently-stored
answer). Whichever writer runs most recently for a given appId wins outright, with no signal to any consumer that
the previously-displayed answer changed. `platformCapture.ts`'s own doc comment acknowledges the store's `mac_arch`
field must never be inferred by this writer specifically to avoid clobbering the Mach-O ground truth, but applies no
equivalent reasoning to `is_mac_native`/`is_windows_native` themselves, which both writers freely overwrite.

This is the underlying mechanism that makes CR-01 reachable in ordinary use, not merely as a network-failure corner
case.

**Fix:** At minimum, document the precedence relationship (e.g., "PICS oslist wins because it reflects actual depot
manifests, not the store page") in both writers' headers so a future reader does not assume the two are
interchangeable. Consider skipping the bulk writer's overwrite of `is_mac_native`/`is_windows_native` when the
existing entry already has `platformsCaptured === true` from a per-game `appdetails` fetch, or vice versa, whichever
direction the team decides is more authoritative.

### WR-03: `refresh()`'s "all four exit paths emit `steamSyncStatus`" guarantee depends on an unenforced cross-module contract, and the gap is explicitly pinned rather than closed

**File:** `src/backend/storeManagers/steam/library.ts:757-766` (the `captureOwnedAppPlatforms` call site, Step 1.5)

**Issue:** The Steps-2-4 `try` this phase added (D-07 exit path 4) starts *after* the `captureOwnedAppPlatforms`
call, not before it. `captureOwnedAppPlatforms` is contracted to "never throw," and its own test suite is unusually
thorough about proving that (including the case where the internal filter step itself throws) — but that contract is
enforced only by convention and tests, not by the type system. `library.test.ts:876-897` explicitly documents and
accepts the resulting gap:

> "pins current behaviour when `captureOwnedAppPlatforms` itself rejects (contract violation, defence in depth): the
> call sits OUTSIDE the Step 2-4 try, so the rejection propagates un-emitted, not as exit path 4"

Because `refresh()` is invoked from `init()`'s unscoped `runOnceWhenOnline(() => this.refresh())`
(`backend/online_monitor.ts:136-142`), which calls the callback with **no** `.then`/`.catch` at all and discards the
returned promise entirely, a future edit to `platformCapture.ts` that reintroduces a throw outside its own try (or a
new Node/V8-level exception type the current tests don't happen to cover) would silently regress into exactly the
unhandled-rejection hole D-07 was chartered to close — with no UI signal, and, depending on the Node runtime's
`--unhandled-rejections` mode, a possible sidecar process crash.

This is not a bug in the code as it stands today (the contract genuinely holds, and is well-tested), but the phase's
own framing ("emitted on EVERY exit path of `SteamLibraryManager.refresh()` (all four)") overstates what is actually
structurally guaranteed versus what is merely true-by-current-implementation.

**Fix:** Either widen the D-07 `try` to start before the `captureOwnedAppPlatforms` call (removing the reliance on
the cross-module contract entirely, at the cost of one extra `steamSyncStatus` emit call already available), or add
a defensive `.catch` at the `runOnceWhenOnline(() => this.refresh())` call site in `init()` so a future contract
violation degrades to a logged warning instead of a silent/crashing rejection.

### WR-04: A Steam-sync retry against a library with cached games gives no visible feedback while the retry is in flight

**File:** `src/frontend/screens/Library/librarySyncIndicator.ts:70-77` and
`src/frontend/screens/Library/components/SteamSyncNotice/index.tsx:80-93`

**Issue:** `resolveSteamSyncIndicator`'s `'syncing'` branch only fires when `steamLibraryCount === 0`. `refresh()`'s
own exit path 2 comment establishes that a `'failed'` status is typically reached *with* cached games already pushed
to the frontend (`library.ts:717-727`: "cached games are pushed BEFORE the failure emit... so the notice must render
above a populated grid"). So the common shape when a user sees the failed notice and clicks "Retry Steam sync" is:
`steamLibraryCount > 0`. The instant the retry's `refresh()` call emits `{ status: 'syncing' }`, `resolveSteamSyncIndicator`
falls through both the `'failed'` branch (no longer applicable — status is now `'syncing'`) and the `'syncing'`
branch (blocked by `steamLibraryCount > 0`), landing on `'hidden'`. The failure notice — including its retry button —
disappears immediately on click, and nothing replaces it until the retry either succeeds (notice stays hidden,
silently correct) or fails again (notice reappears). The module's own comment justifies the `steamLibraryCount === 0`
gate by pointing to `steamMetadataSyncing` as covering the populated-library case, but `steamMetadataSyncing` is an
unrelated per-game background metadata/art throttled-fetch signal, not driven by `refresh()`'s own lifecycle — so
that justification does not actually hold for the retry-with-cached-games case this button exists to serve.

**Fix:** Either let `SteamSyncNotice` render a brief "retrying…" state locally between click and the next terminal
`steamSyncStatus` emission (e.g. local `useState` flipped on click, cleared on the next `steamSyncStatus` change), or
widen `resolveSteamSyncIndicator`'s `'syncing'` branch to also show while `steamSyncStatus === 'syncing'` immediately
following a `'failed'` state, regardless of `steamLibraryCount`.
