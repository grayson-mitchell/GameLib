### Two real bugs found and fixed
1. **Closed a synchronous-throw gap in `captureOwnedAppPlatforms`** (orchestrator finding #2). The `depotSignalCaptured(steamMetadataStore.get(...))` filter step ran OUTSIDE the function's own try/catch. The function's doc comment states it "MUST NOT throw under any input" (D-03's fail-soft contract), and `library.ts`'s `refresh()` call site (`:758-761`) carries NO try/catch of its own precisely because it trusts that contract -- on the unscoped mount-time path (`init()`'s `runOnceWhenOnline(() => this.refresh())`, no `.catch` anywhere in the chain), a throw here would have been a silent unhandled rejection, exactly the hole D-07 exists to close. Moved the `try` to wrap the filter step too; tracks `scopedCount` via a mutable outer binding for the catch (since `scoped` itself may never be computed if the filter is what throws); added a regression test proving the filter-throw path fails soft without ever reaching `getProductInfo`.
2. **Fixed the one failing suite** (`genI18nGateScope.test.ts`'s A-17 anti-rot check). Plans 06 and 08 added two new fork-touched frontend files (`librarySyncIndicator.ts`, `SteamSyncNotice/index.tsx`) that were never folded into `meta/i18nGateScope.json` or regenerated into `meta/i18nForkTouchedFiles.json`. ### Orchestrator VERIFY items -- resolved with recorded evidence

**Finding #2 (library.ts:758, capture call outside every try/catch) -- was a real, narrow gap; now fixed.** See "Two real bugs found and fixed" #1 above. Before the fix, the specific scenario (`steamMetadataStore.get()` throwing synchronously during the D-04 scoping filter) was exceedingly unlikely in practice -- electron-store's `.get()` reads an already-loaded in-memory object, not per-call disk I/O -- but it was a genuine, if narrow, violation of the function's own documented contract, and D-07's whole purpose is closing exactly this class of silent-death path. Fixed rather than merely documented as acceptable, per Rule 1 (the function's own doc comment states a correctness contract the code did not fully satisfy).

**Finding #3 (InstallModal/index.tsx:233, residual unknown->false collapse in the selector option list) -- investigated in full; UNREACHABLE, with the reasoning recorded here so a future reader does not have to re-derive it.**

Traced the complete path from `isMacNative`/`macDepotOffered` to the rendered `<SelectField>`:

1. `platforms`' unfiltered `Mac` entry's `available` flag (from the stale seed `isMacNative`) is **never read** by `selectSteamPlatformOptions`'s `'selectable'` branch -- it does `platforms.find(p => p.value === 'Mac')`, which finds the entry structurally by `value`, ignoring `available` entirely. So whenever `platformRowMode === 'selectable'`, Mac is **unconditionally** one of the offered options, regardless of `isMacNative`/`macDepotOffered`.
2. `platformRowMode` itself (`steamGating.platformRow`, from `resolveSteamSectionGating` -- untouched by this phase, confirmed by the D-13 scope-fence diff above) can only reach `'selectable'` when `bottleRequired` is `false` (checked BEFORE `depotSignalResolved`/`hasWindowsDepot`) -- i.e. only when the backend's independent bottle-eligibility check has already decided a native Mac install is viable. `macDepotOffered` (from `resolveDepotAvailability`, D-12's addition) is a **separate**, fail-CLOSED signal that never feeds `resolveSteamSectionGating` at all (`SteamSectionGatingInput` has no mac field).
3. For every NON-`'selectable'` row (`'readonly-windows'`, `'readonly-macos'`, `'pending'`, `'absent'`), the `<SelectField>`'s displayed `value` is **forced** by `readonlyPlatformValue(platformRowMode)` (`InstallModal/index.tsx:530`: `value={readonlyPlatformValue(platformRowMode) ?? platformToInstall}`), which returns a defined literal for every one of those modes -- so `platformToInstall`'s internal state (including whatever `getDefaultplatform(macDepotOffered)` set it to) is **never read** for the displayed value on a read-only row. An internal mismatch there is inert.
4. The actual install submission (`SteamDialog/index.tsx:363-368`) dispatches `installSteamGame(..., gating.forceWindowsViaBottle)` -- the verdict's own field, never `platformToInstall` read raw -- and `forceWindowsViaBottle` is computed from `effectivePlatform`, which for non-`'selectable'` rows is hardcoded per row (never `selectedPlatform`) in `resolveSteamSectionGating` step 5.

Conclusion: `getDefaultplatform`'s choice of `'Mac'` vs `'Windows'` can only ever matter within `'selectable'` mode, and within that mode Mac is always a valid, already-offered option. The hypothesized state (default points to Mac, but the option list does not offer it) cannot occur, because the two computations (`macDepotOffered`-driven default; `platformRowMode`-driven option list) are read through completely different, non-interacting code paths for every row where the distinction could matter. No code change made -- `steamSectionGating.ts` remains untouched (confirmed by the D-13 diff check above) and this analysis stays entirely within already-shipped, already-tested 34.13/34.14 architecture.
