## Findings (record ANY observation that contradicts a plan assumption)

- RESEARCH.md assumption A2 (`oslist` presence rate correlates with Tool-type entries, not

### F-1 (minor, real) -- the capture summary is logged TWICE on every call

Two independent statements log the same summary, differing only by the `failed=` suffix:
`platformCapture.ts:300` (`scoped=N captured=N skipped=N`) and `library.ts:763`
(`... failed=<bool>`). Every run in the developer's logs shows the pair, sometimes in reverse order
(17:34:03 logged the `failed=` variant FIRST). Harmless to behaviour, but it doubles the line count
in any log census and invites a reader to believe two captures ran. Recommend deleting the
`platformCapture.ts:300` log and keeping the caller's, which carries strictly more information.

### F-2 (worth fixing) -- a single mount fires TWO concurrent refreshes, each doing a full bulk PICS call

Observed live in the cold run. One `[refreshLibrary] runner=all origin=mount` at 17:24:41 produced:
- **two** `Steam: fetched 378 owned games` lines, both at 17:24:42
- **two** full bulk captures -- `(17:24:47) scoped=378 captured=363 skipped=15` and
  `(17:24:51) scoped=378 captured=363 skipped=15`

The second call re-scoped **all 378** rather than the ~15 the first had left, which proves the two
`refresh()` invocations were **in flight simultaneously** -- both computed their `scoped` filter
before either had flushed its writes. Consequences:
1. Every cold start pays for **two** 378-app PICS round trips (~5s + ~4s) instead of one.
2. This is exactly the **lost-update hazard on `mergePlatformCapture`'s read-modify-write** that the
   phase's code review raised as a question (see `34.15-REVIEW.md`) -- now observed in the wild. It
   was benign here ONLY because both writers computed identical values from the same PICS response.
   Two writers that disagreed (which WR-02 documents as possible, since `games.ts`/`appdetails` and
   `platformCapture.ts`/PICS have no precedence rule) would silently lose one side's write.

This is a pre-existing double-refresh in the mount path, not something 34.15 introduced -- but 34.15
is what made it expensive and what made the race observable.

**F-2 REFINEMENT (from the Tauri legs) -- the double-refresh is ELECTRON-ONLY.** Counting refreshes
per single `origin=mount` across all four developer runs:

| Run | Runtime | Refreshes from one mount |
|---|---|---|
| 17:24 cold | Electron | **2** fetches, **2** full 378-app PICS calls |
| 17:44 Branch C | Electron | **2** `Steam client not ready` |
| 18:01 cold | Tauri | **1** fetch, **1** PICS call |
| 18:04 Branch C | Tauri | **1** `Steam client not ready` |

Tauri fires exactly one. This also plausibly explains the latency gap (Electron ~5s vs Tauri ~2s for
the identical 378/363/15 result) -- Electron was issuing two concurrent PICS calls.

**Consequence for prioritisation:** F-2 lives in the Electron runtime, which **Phase 35
(electron-cutover-remove-the-electron-build) deletes outright**. It does not need its own fix; it
needs to not be reintroduced. The underlying lost-update hazard on `mergePlatformCapture`'s
read-modify-write remains theoretically real and is still tracked as WR-02 in `34.15-REVIEW.md`
(two writers, no precedence rule) -- that one is runtime-independent and outlives Electron.
