## Bulk platform-capture source + timing

### Q1 — Where should bulk platform data come from?

| Option | Description | Selected |
|--------|-------------|----------|
| PICS `getProductInfo` (`common.oslist`) | Authenticated CM; proven bulk path already in repo at `depot.ts:430`/`:476` bounded by `STEAM_PICS_BULK_TIMEOUT_MS`. No HTTP rate limit to measure. Cost: different source than `appdetails.platforms`, and a PICS write carries only OS data so it must merge, never wholesale `set()`. | ✓ |
| Batched `appdetails` (the ROADMAP's assumption) | Same source as today's per-game path, full payload. Risk: multi-appid mode reportedly returns reduced payloads unless `filters=` is set — if `platforms` is stripped, dead end. | |
| Research decides — measure both | Let the researcher verify empirically. Cost: the largest item stays unresolved through planning. | |

**User's choice:** PICS `getProductInfo`
**Notes:** This overrides the ROADMAP's stated direction. Recorded in CONTEXT.md as landmine #1 so a planner reading only the ROADMAP does not plan the wrong mechanism.

### Q2 — How should a PICS write interact with the `platformsCaptured` / `depotSignalCaptured` contract?

| Option | Description | Selected |
|--------|-------------|----------|
| First-class capture, merge-write, empty `oslist` writes nothing | Merges the three OS flags + `platformsCaptured: true`; `depotSignalCaptured()` stays byte-identical; read-modify-write so carry-forward fields survive; absent `oslist` writes nothing. | ✓ |
| Second-class — flags only, `platformsCaptured` stays appdetails-owned | New provenance field records PICS origin. Cost: `depotSignalCaptured()` must be widened — the exact boundary quick task `260816-hdg` just pinned. | |
| You decide | Leave the shape to planning under three constraints. | |

**User's choice:** First-class capture, merge-write, empty `oslist` writes nothing
**Notes:** Designed specifically so `depotSignalCaptured()` needs no edit. A plan that finds itself editing it is wrong.

### Q3 — When should the bulk PICS capture run?

| Option | Description | Selected |
|--------|-------------|----------|
| Inline in `refresh()`, awaited before the GameInfo hydration loop | Between Step 1 and Step 3; CM already connected, ID list already in hand. Every GameInfo correct on first push — no re-push, no second event, no convergence window. Must fail soft. | ✓ |
| Post-sync background backfill | First sync not slowed. Cost: real convergence window, resumability state, plus a re-push or second event to reach the rendered library. | |
| You decide | Planning picks based on measured PICS latency, constrained to fail-soft. | |

**User's choice:** Inline in `refresh()`, awaited before the GameInfo hydration loop
**Notes:** Fail-soft is a hard requirement — aborting the sync would trade incomplete metadata for no library, which is defect 2's shape.

### Q4 — Which owned apps should the bulk capture cover on each sync?

| Option | Description | Selected |
|--------|-------------|----------|
| Only apps where `depotSignalCaptured()` is `false` | Self-limiting and converging; first sync repairs the ~370 residue entries; reuses the same predicate 34.14's gating reads. Accepts staleness for already-captured games. | ✓ |
| Every owned app, every sync | Always fresh. Cost: a full ~378-app request forever, never gets cheaper. | |
| Every app, gated on PICS changenumbers | Freshest and cheapest in steady state. Cost: a changenumber store, its persistence contract, and a new class of staleness bug for a rarely-changing signal. | |

**User's choice:** Only apps where `depotSignalCaptured()` is `false`

### Follow-up raised by the user (mid-area, out of turn)

> *"If you can see a Steam game in your library, will you certainly have the platforms supported?"*

Answered **no**, with four durable paths verified at HEAD: PICS fail-soft; per-app absent `oslist`; the cached-library early returns (`library.ts:670`, `:701-702`); and `init()` pushing the persisted list independently of `refresh()` (`library.ts:510-521`). A fifth, milder second chance is the dialog-open eligibility probe, which is a race with a 15s deadline, not a guarantee.

This became **D-05** in CONTEXT.md — the governing non-consequence of item 1. It is the reason none of 34.14's safety layers may be weakened after this phase lands, and it is what made the frozen-default question in Q3 of the mac area material rather than theoretical.

## Steam sync failure — terminal state and what the user sees

### Q1 — What replaces `refreshingInTheBackground` as the spinner's driver?

| Option | Description | Selected |
|--------|-------------|----------|
| A real Steam sync state machine (`'idle' \| 'syncing' \| 'failed'`) | Explicit tri-state owned by `GlobalState`; spinner renders only on `'syncing'`. Makes the terminal state structural. | ✓ |
| Reuse `refreshingByRunner.steam` | Already exists, already clears on failure, already source-tested. Cost: boolean (cannot distinguish failed from succeeded-and-empty), and the mount-time refresh is unscoped, so it would never be set on the path where the bug reproduces. | |
| You decide | Constrained to: reachable terminal state, and the flag must actually mean "refresh in flight". | |

**User's choice:** A real Steam sync state machine
**Notes:** Scouting found the guard is worse than the todo describes — `refreshingInTheBackground` is reset to `true` after every unscoped refresh (`GlobalState.tsx:1066`), so the guard reduces to "Steam logged in AND library empty", permanently.

### Q2 — How should the backend failure propagate?

| Option | Description | Selected |
|--------|-------------|----------|
| A `steamSyncStatus` frontend event mirroring `steamMetadataSyncing` | Copies a complete shipping pattern (emit site, `ipc.ts` declaration, preload allowlist, `GlobalState` consumer). Works on both runtimes. Obligations: allowlist the channel (silent failure otherwise), emit on every exit path including `library.ts:670`. | ✓ |
| Typed failure return read at the call site | Widen `refresh()`'s return and surface it through the IPC response. Cost: the mount-time call is unscoped, so a per-runner outcome has nowhere to live — and that path is where the bug reproduces. | |
| You decide | Constrained to: identical on Electron and sidecar, must fire on the `:670` early return. | |

**User's choice:** A `steamSyncStatus` frontend event

### Q3 — What does the user see on failure?

| Option | Description | Selected |
|--------|-------------|----------|
| Inline, non-blocking Steam notice with a Steam-scoped retry | Compact row in the library flow, retry calls `refreshLibrary({ library: 'steam' })`. Other runners stay visible. Cost: new user-facing strings → localisation gate BLOCKING. | ✓ |
| Silent clear — spinner just disappears | Zero new strings, gate stays a no-op. Cost: contradicts the todo's own instruction ("surface the actual error"); silently incomplete library with no explanation. | |
| Inline notice, but reuse existing strings only | Keeps the gate a no-op. Cost: copy cannot name Steam or the reason, so the honesty gain is partial. | |

**User's choice:** Inline, non-blocking Steam notice with a Steam-scoped retry
**Notes:** `ErrorComponent` exists with a wired retry but is a full-screen replacement — using it here would recreate defect 2b. The BLOCKING localisation gate was accepted knowingly.

### Q4 — How is the failure path proven?

| Option | Description | Selected |
|--------|-------------|----------|
| Extract a pure resolver + exhaustive unit tests + a RED-proven source gate | The house pattern used three times already for the no-jsdom constraint. Source gate must be demonstrated to fail against the known-bad expression. | ✓ |
| Source-shape grep test only | Mirrors `GlobalStateScopedRefresh.test.ts`. Cost: proves the code was written a certain way, not that the state machine is correct. | |
| Live UAT only | Cost: nothing guards the regression afterwards — and this defect is the sibling of one already fixed once. | |

**User's choice:** Extract a pure resolver + exhaustive unit tests + a RED-proven source gate

## Mac signal — icon-row suppression and default platform

### Q1 — What shape does the mac side take?

| Option | Description | Selected |
|--------|-------------|----------|
| Extend the SAME `resolveDepotAvailability` to return a mac triple | One function keeps owning "what do we know about this game's platforms". Cost: widens a function three shipped saboteur gates pin — must be reconciled explicitly. | ✓ |
| A separate sibling function for mac | Smaller blast radius on existing gates. Cost: two readers of the same fact is the drift `steamPlatformRow.ts`'s header warns against. | |
| You decide | Constrained to: "unknown" representable, no `!== false`, saboteurs stay valid and green. | |

**User's choice:** Extend the SAME function to return a mac triple

### Q2 — What should the glyph row render while unresolved?

| Option | Description | Selected |
|--------|-------------|----------|
| Suppress the whole row — no glyphs at all | The row is an assertion the app cannot make. Also drops the unconditional Windows glyph, correctly. Scope: SteamDialog header only. | ✓ |
| Suppress only the mac glyph, keep Windows | Narrowest change. Cost: leaves the row asserting Windows from a hardcoded `available: true` that reads no signal — and says "Windows-only" by omission, the exact false reading observed. | |
| Render the glyphs with a visual hedge | Keep the row but mark it provisional. Cost: new visual vocabulary in a phase with no UI-SPEC, and a dimmed Windows glyph still asserts Windows. | |

**User's choice:** Suppress the whole row
**Notes:** Confirmed at HEAD that `SteamDialog/index.tsx:380-391` renders from `availablePlatforms` and the Windows entry is `available: true` unconditionally, producing exactly one Windows glyph on an unresolved signal — reproducing the operator's observation precisely.

### Q3 — What is `getDefaultplatform`'s uncaptured-case behaviour?

*Asked, then paused by the user to ask the "will you certainly have the platforms" question above; re-asked verbatim afterwards and answered the same way.*

| Option | Description | Selected |
|--------|-------------|----------|
| Windows on unknown, commented, AND re-derive on resolve | Windows-via-bottle always works and most Steam titles are Windows-only. Freezing the guess is the observed defect, so the default re-derives when the signal resolves. Safe because Install is disabled for the whole pending window. | ✓ |

**User's choice:** Windows on unknown, commented, AND re-derive on resolve
**Notes:** The operator-locked constraint says **mac-ONLY** games are a null set — which does not imply most games have a Mac build. Recorded in CONTEXT.md so the constraint is not misread as an argument for defaulting to Mac.
