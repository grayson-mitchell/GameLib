<objective>
Close WR-04 (59-REVIEW): a per-game write that fails both attempts (ENOSPC, EACCES, read-only
volume) leaves three copies disagreeing. `createSettingSetter` updates React state before the
fire-and-forget send; `GameConfigV0.setSetting` assigns `this.config[key]` before `flush()`;
the file keeps the old value; and the launch path reads the file
(`readStoredEngineOverride`). The user believes the engine override changed while the launch
uses the old engine.

Fix per the reviewer: roll the in-memory value back when the flush throws, and tell the renderer
so it re-reads the truth. No new user-facing string: the control snapping back to the stored
value is the visible signal, and the log line already exists.

Output: rollback, a typed push channel, renderer re-fetch, tests.
</objective>

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-59-123 | Tampering | in-memory GameConfig after a failed write | mitigate | rollback restores the prior value or removes the key, so a later flush cannot persist a value the user never saw saved |
| T-59-124 | Information disclosure | gameSettingWriteFailed payload | accept | carries only appName and key (no value, no error text, no path) |
| T-59-125 | Denial of service | renderer re-fetch loop | mitigate | re-fetch only for the matching appName, one push per failed write (after two attempts), and the push is never sent on success |
