<planning_findings>
1. **`validStoredUrl`'s current test is a substring match on the whole URL.** Measured at plan time,
   the surviving implementation reads `url.includes('gog.com')` for GOG and the same shape for the
   other four stores. `https://evil-gog.com.attacker.net/` passes. So does
   `https://attacker.net/?redirect=gog.com`. The stored value is only narrowly
   attacker-influenceable — it is written from a URL the embed already loaded — but it feeds a native
   webview's INITIAL navigation on the next app start, which is exactly the position where a weak
   check is worth the small cost of fixing (D-31).

2. **The correct check is host-based, not URL-based**: parse the URL and compare the HOSTNAME either
   exactly to the apex or as a dot-prefixed suffix of it. `hostname === 'gog.com' ||
   hostname.endsWith('.gog.com')`. Never `includes` on the full URL, and never `endsWith('gog.com')`
   on the hostname alone — that still matches `evilgog.com`. The leading dot is the whole point, and
   this project has already shipped one production defect (F-34.4.2-19) from omitting exactly that
   kind of boundary.

3. **D-30's re-derivation has a smaller job than the original.** Plan `40-08`'s `hide()`-on-leave
   keeps the embed and its page state alive across route changes within a session. So the
   session-storage restore now earns its keep ONLY across app restarts. Note that the existing code
   uses `sessionStorage`, which does not survive a process restart — so a restore keyed to
   `sessionStorage` cannot deliver the one property it now exists for. Determine the correct storage
   by measurement and record the finding; do not port the storage choice along with the logic.

4. **D-32's caveat is likely INVERTED, and the correction matters.** CONTEXT.md worries that the
   adtraction detection targets a blocked third-party SUBRESOURCE. Reading the retired code: the
   handler fired on a load-failure event whose failed URL matched the tracker domain, then extracted
   a redirect target from that URL's own query string and navigated to it. That is a MAIN-FRAME
   redirect hop — the store link goes through the tracker in the main frame — not a subresource.
   **However**, measured against vendored source at plan time: wry 0.55.1's macOS backend implements
   NO navigation-failure callback at all. There is no `didFailProvisionalNavigation` or
   `didFailNavigation` handling, and no failure handler field on the attributes struct. Confirm this
   against `40-EMBED-API-VERIFICATION.md` Q3, which is the authority.
   So the shape of the problem is: the event is main-frame (good) but no failure signal exists (hard).
   Task 3 branches on Q3's recorded verdict and must produce an honest outcome either way.

5. **The deep-link URL is genuinely third-party.** It arrives from deal data that returns
   storefronts beyond the five embedded ones. D-34's rule: parse it, embed it if the origin matches a
   configured store, otherwise open it externally. This keeps unvetted third-party input out of a
   native webview without making the Discounts surface worse. Note the Rust scheme policy from plan
   `40-04` is a second, independent control — but it is a scheme policy, not an origin policy, so it
   would happily load an arbitrary https origin. This origin check is the control for that.

6. **D-35 falls out of the origin check and adds no new concept.** A deep link that resolves to a
   configured store IS that store's embed pointed at a different starting URL: same user agent, same
   restore key, same history stack. Do not introduce a sixth store identity for deep links.

7. **The five store keys and their apexes, measured from the surviving route map**: epic
   (`epicgames.com`), gog (`gog.com`), amazon (`gaming.amazon.com`), zoom (`zoom-platform.com`),
   steam (`store.steampowered.com`). Note GOG's start URL is an affiliate host (`af.gog.com`) which
   is a subdomain of the `gog.com` apex, so the suffix rule covers it — verify that rather than
   assuming. Epic remains OUT of scope for embedding (D-05) but keeps its entry in the table, because
   the table also answers "is this a known store origin" for the deep-link decision.
</planning_findings>
