<objective>
Mount the embed: a slot div that is the single geometry oracle, a host hook that syncs its bounds and
owns the route lifecycle, and a WebView screen that renders the chrome above the slot with the
placeholder behind it.

Purpose: this is where Model B becomes visible. The layout inversion is the whole difficulty — under
the retired model the element was IN the document and CSS laid it out; under `add_child` it is a
native subview and the DOM can no longer contain it, only describe where it should be. Spike 017's
two rules follow directly: one layout oracle, and overlays hide it rather than paint over it.

Output: a host hook, a rebuilt store/wiki render path, and the styles that make the slot measurable.
</objective>

<planning_findings>
1. **The proven bounds-sync shape is in the spike reference and is already the answer, not a hint.**
   A `ResizeObserver` on the slot div, debounced around 40 ms, reading `getBoundingClientRect()` and
   sending `x`, `y`, `width`, `height` in logical px. Measured: JS viewport coordinates map 1:1 to
   child logical coordinates with NO titlebar offset at scale factor 1.0, integer px round-trip
   exactly, and fractional CSS px round to the nearest whole logical px with no cumulative drift.
   Copy that shape rather than deriving one.

2. **A second geometry writer wins silently with zero errors.** The spike's own interactive panel
   overrode its scripted run's bounds and produced no signal at all. So the control cannot be a
   runtime check — it must be structural: exactly one call site in the whole renderer sends bounds,
   and the slot's rect is the only input to it. Never compute a rect from window size, from a CSS
   variable, or from a parent's dimensions as a "fallback"; a fallback rect is a second writer.

3. **The WKWebView layout pathologies recorded for this project do NOT apply to the embed itself** —
   this is native-frame geometry, not CSS layout. But they DO apply to the SLOT, which is an ordinary
   DOM element. Two are directly relevant: a percentage height behaves differently from a `1fr` grid
   row, and a 1px border on a fractional grid-track boundary never rasterises. Give the slot a
   deterministic size through the grid rather than a percentage, so its measured rect is stable.

4. **Route-change lifecycle (D-21):** `hide()` on leaving a store route, `close()` only at app
   teardown. Both hide and show were proven to return Ok with the webview and the cookie jar
   surviving. That is what makes returning to the store tab instant with page state and scroll intact
   — most of what makes the tab feel native rather than like launching a browser. Do NOT close on
   route change; re-creating on every visit throws that away.

5. **The webview handle dies with the webview.** Any poller must be anchored to a survivor. In this
   plan that means the host hook must not hold a stale label reference across a close, and the
   navigation-state read must tolerate the embed being absent (hidden or closed) by returning a
   quiescent state rather than throwing into the render path.

6. **The chrome and the placeholder are already built** by plans `40-07` and `40-06`. This plan
   composes them; it does not restyle them and does not modify NavShell.

7. **What survives in `WebView/index.tsx` from plan `40-01`:** the route-to-URL map, the `startUrl`
   resolution, `validStoredUrl` and the session-storage restore, the store-page query-param branch,
   the `showLoginWarningFor` state and effect, the adtraction warning state, the Humble early return,
   and the login-path arm returning the Tauri login panel. This plan adds the store/wiki render path
   in place of the unconditional unavailable-panel return — and leaves the panel reachable for
   non-macOS, which plan `40-10` then rewords. Plan `40-09` owns the restore and origin-parsing
   rework; do not do it here or the two plans collide on the same file.
</planning_findings>

  <action>
Create `useStoreEmbedHost.ts`, a hook taking a slot ref and a start URL and owning four
responsibilities: opening the embed, syncing its bounds, running the route lifecycle, and reflecting
suppression.

BOUNDS SYNC — the single-writer rule is structural. Attach a `ResizeObserver` to the slot element,
debounce at roughly 40 ms (the spike's measured interval; make it a named constant with a comment so
it is tunable and not a magic number), read `getBoundingClientRect()` and send `x`, `y`, `width`,
`height` straight through. This hook contains the ONLY `setBounds` call in the entire renderer.
Never compute a rect from the window size, a CSS variable, or a parent's dimensions — not even as a
fallback when the ref is null. If the slot ref is null, send nothing and log; a fallback rect is a
second writer in disguise, and spike 017 proved the second writer wins silently with no error.
Also fire the sync on window resize and on the slot's own scroll-position changes if the slot can
move without resizing, since `getBoundingClientRect` is viewport-relative and a scroll that moves the
slot changes its rect without changing its size — a resize-only observer would leave the embed
stranded. Determine whether that is possible for this layout by reading the styles, and record the
answer either way.

LIFECYCLE — open on mount with the start URL; on a start-URL change for the same store, navigate
rather than re-opening; on leaving a store route, call `hide()`; call `close()` only on app teardown,
never on route change (D-21). Returning to the store tab must be instant with page state and scroll
intact — that is most of what makes the tab feel native. Anchor nothing to the webview handle across a
close, and make the navigation-state read tolerate an absent embed by returning a quiescent state
rather than throwing into the render path.

SUPPRESSION — subscribe to the suppression read hook. When it becomes true, call `hide()`; when it
becomes false AND the route is still a store route, call `show()`. Guard the transition so a
suppression released after the user has already navigated away does not resurrect the embed on a
non-store screen.

NAVIGATION STATE — expose the current URL, host and back/forward availability plus the four
navigation callbacks, so the screen can hand them to the chrome as props. Availability is pushed
state, never a synchronous query.

Write `__tests__/useStoreEmbedHost.test.tsx` proving seven properties, each individually able to
fail: (1) mounting opens with the start URL; (2) a slot resize sends bounds equal field-for-field to
the observed rect; (3) two rapid resizes inside the debounce window produce ONE send; (4) a null slot
ref sends nothing and logs — asserting specifically that no rect was sent, not merely that no error
was thrown; (5) suppression true calls hide, false calls show; (6) leaving the route calls hide and
NOT close; (7) unmounting the app teardown path calls close. Record the mutation that turned each red.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| DOM layout → native subview geometry | The renderer describes where a native view should sit. A wrong rect places third-party content over app chrome — including over the chrome's own host display, which is the user's origin signal. |
| route state → embed URL | The start URL comes from the route map and, on the deep-link route, from third-party deal data. Plan `40-09` owns the origin check; this plan must not open the deep-link path early. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-40-08-01 | Spoofing | embed rect covering app chrome | mitigate | The slot is rendered BELOW the chrome (D-24) so the measured rect structurally cannot include it, and there is exactly one bounds call site fed only by that slot's rect. A fallback rect is forbidden by an acceptance criterion, because a wrong rect could place a third-party page over the host display the user reads to identify the origin. |
| T-40-08-02 | Spoofing | app UI drawn over the embed and invisible-but-clickable | mitigate | Plan `40-06`'s suppression is subscribed here: suppression held means hide plus placeholder. Test 5 asserts both transitions. |
| T-40-08-03 | Tampering | a second geometry writer | mitigate | Structural, not a runtime check — spike 017 proved a second writer wins with zero errors, so no runtime check could detect it. One call site, asserted by a repo-wide grep criterion; no numeric coordinate literals; no window-size or CSS-variable fallback. |
| T-40-08-04 | Information Disclosure | an authenticated store page left live off-route | accept | D-21 keeps the embed alive and hidden across route changes so returning is instant with state intact. The page stays authenticated in the shared jar either way (D-14), so hiding rather than closing adds no exposure the jar does not already carry. Close happens at app teardown. |
| T-40-08-05 | Denial of Service | a throwing navigation-state read taking down the store screen | mitigate | The read tolerates an absent embed by returning a quiescent state rather than throwing into the render path; the handle dies with the webview, so absence is a normal condition, not an error. |
| T-40-08-06 | Denial of Service | embed stranded by a slot that moves without resizing | mitigate | `getBoundingClientRect` is viewport-relative, so a scroll that moves the slot changes its rect without changing its size. Task 1 requires determining whether that is possible in this layout and recording the answer either way, rather than assuming a resize observer is sufficient. |
| T-40-08-SC | Tampering | npm/pip/cargo installs | mitigate | This plan adds no package. If either lockfile changes, stop for a blocking package-legitimacy checkpoint. |
</threat_model>
