<objective>
Close **CR-01** (BLOCKER): `meta/buildSidecarSea.ts` derives the sidecar's output triple from
`process.arch` of the CI runner, so both `macos-latest` matrix legs (which are Apple-Silicon-native)
produce `gamelib-sidecar-aarch64-apple-darwin`, and `copyNodeBinary()` copies the arm64
`process.execPath` regardless. The `--target x86_64-apple-darwin` leg therefore either fails to
resolve its `externalBin` or ships arm64 bytes inside an x86_64 app bundle.

Per user decision **GAP-D-02**, fix this properly and keep Intel Mac support:
1. add a `GAMELIB_SIDECAR_TARGET_TRIPLE` override consumed by this script, falling back to
   `hostTriple()` when unset, and
2. stop copying `process.execPath` when cross-building — obtain the **official nodejs.org Node
   binary for the target triple**, verify it against `SHASUMS256.txt`, and use it as the SEA base,
3. and **prove** the produced binary's real architecture with `lipo -archs` as a build-time gate.

Dropping the x86_64 matrix leg and using Rosetta were both explicitly rejected — neither is an
acceptable outcome here.

Purpose: the x86_64 macOS leg must ship a genuinely x64 sidecar so Intel Mac users get a working
app, and so the leg stops silently mislabeling its output.
Output: a target-aware `meta/buildSidecarSea.ts` plus regression tests in the existing Wave-0
`meta/__tests__/buildSidecarSea.test.ts` suite (the review explicitly calls out that `hostTriple()`
is untested).
</objective>

| nodejs.org -> build machine | A remote archive is downloaded and becomes the base bytes of a shipped executable |
