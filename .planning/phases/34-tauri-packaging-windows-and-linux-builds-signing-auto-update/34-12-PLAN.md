<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| GitHub Actions runner -> GitHub Releases API | `gh release download crossover-index` pulls a network artifact into the build tree that is then bundled into shipped installers |
| Job-level `env:` -> individual steps | The job exports `APPLE_*`, `WINDOWS_*`, `TAURI_SIGNING_*` to every step, including the three new build steps |
| Renderer build -> shipped installer | `build/` contents become the app's webview payload on every platform |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-34-16 | Tampering | `gh release download crossover-index` step | mitigate | Fetch is scoped to the SAME repository via `${{ github.token }}` (no cross-repo source, no third-party URL), restricted to a single asset by `--pattern crossover-index.json.gz`, and non-fatal via `|| echo` so a missing/partial index degrades to "ship without a snapshot" rather than to a half-written file. Identical trust posture to the already-shipping `draft-release-mac.yml` step. |
| T-34-17 | Information disclosure | Job-level signing secrets visible to the new build steps | accept | Pre-existing job-level `env:` scoping, not introduced here. Residual risk is bounded: all three new steps run BEFORE the `Import Windows signing certificate` step, so no cert material exists on the runner filesystem while they execute. Narrowing job-level `env:` to step-level is out of scope for this gap cycle. |
| T-34-18 | Tampering | `pnpm exec electron-vite build` output bundled into installers | accept | The renderer is built from the checked-out, reviewed source tree by the repo's own committed build config; adding the step does not widen the input set relative to the Electron pipeline that already ships this exact output. |
| T-34-SC | Tampering | npm/pip/cargo installs | n/a — accept | This plan adds NO package-manager install task and makes NO `package.json`/lockfile change. The Package Legitimacy Gate is not triggered; `pnpm install` continues to run only inside the pre-existing `install-deps` composite action. |
</threat_model>
