  <what-built>
    Plan 34-17 added `pnpm verify:updater-key`, which signs a throwaway probe file with a
    candidate key/password pair using the real Tauri signer and then compares the resulting
    signature's minisign key id against the `plugins.updater.pubkey` committed in
    `src-tauri/tauri.conf.json`. It exits 0 only when the password decrypts the key AND the key
    is the one the shipped app will trust.
  </what-built>
  <how-to-verify>
    Run every command from the repo root. Do NOT paste the password into a command line that
    lands in shell history — use a variable read with `read -rs` or your password manager's CLI.

    BRANCH A — the password is recoverable (expected: the key file's public half already matches
    the committed pubkey, so only the password secret is likely wrong):
    1. Recover the candidate password from your password manager.
    2. Prove the pair locally:
       `read -rs PW; TAURI_SIGNING_PRIVATE_KEY="$(cat ~/.tauri/gamelib-updater.key)" TAURI_SIGNING_PRIVATE_KEY_PASSWORD="$PW" pnpm verify:updater-key`
       It must print the OK line naming key id `ecc69c7849aa1aa7` (the little-endian hex form of
       the `ECC69C7849AA1AA7` in the pubkey comment). If it reports a password mismatch, try the
       next candidate. If it reports a PUBKEY mismatch, the local key file is not the one the
       repo trusts — go to Branch B.
    3. Enroll BOTH secrets in one sitting, from stdin (never as an argv value):
       `gh -R grayson-mitchell/GameLib secret set TAURI_SIGNING_PRIVATE_KEY < ~/.tauri/gamelib-updater.key`
       `printf '%s' "$PW" | gh -R grayson-mitchell/GameLib secret set TAURI_SIGNING_PRIVATE_KEY_PASSWORD`
       Re-enroll the KEY too even if you believe it is fine — the whole defect is that the two
       secrets were set 55 minutes apart from different sources. Setting them together removes
       the ambiguity.
    4. Confirm both `Updated ...` timestamps are seconds apart:
       `gh -R grayson-mitchell/GameLib secret list`
    5. `unset PW`.

    BRANCH B — the password is unrecoverable, or the local key does not match the committed
    pubkey. This regenerates the updater trust anchor. It is SAFE right now and only right now:
    no GameLib release has ever shipped a Tauri updater artifact, so there is no installed client
    holding the old public key. Once a real release ships, this becomes a breaking change.
    1. `pnpm exec tauri signer generate -w ~/.tauri/gamelib-updater-v2.key`
       (34-03 recorded that `-- -w` is rejected; pass `-w` directly.) Store the new password in
       your password manager BEFORE proceeding.
    2. Prove it: `TAURI_SIGNING_PRIVATE_KEY="$(cat ~/.tauri/gamelib-updater-v2.key)" TAURI_SIGNING_PRIVATE_KEY_PASSWORD="$PW" pnpm verify:updater-key`
       It MUST report a pubkey mismatch at this point — that is correct and expected, because the
       repo still commits the old public key. Record both key ids it prints.
    3. Enroll both secrets from stdin exactly as in Branch A steps 3-4, using the new key file.
    4. Copy the full contents of `~/.tauri/gamelib-updater-v2.key.pub` (a single base64 line) —
       Task 2 pastes it into `src-tauri/tauri.conf.json`.
    5. `git status` must show no `*.key`/`*.pub` file anywhere under the repo tree.

    In BOTH branches, never paste the private key or password into the chat, a commit, a summary,
    or a log line. Key IDs are public and safe to record.
  </how-to-verify>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Developer machine -> GitHub Actions secrets store | The updater trust anchor's private half crosses here |
| Committed pubkey -> every installed GameLib client | The public half is the root of update trust for all users |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-34-40 | Information disclosure | Private key / password during re-enrolment | mitigate | Secrets are piped from a file or stdin, never passed as an argv value or echoed; the password is read with `read -rs` and unset afterwards; neither value may appear in the summary, a commit, or the chat. |
| T-34-41 | Spoofing | Regenerated keypair without updating the committed pubkey | mitigate | Task 2 is mandatory on Branch B, and 34-17's preflight fails the CI run outright if the enrolled key and the committed pubkey disagree — the mismatch cannot ship silently. |
| T-34-42 | Repudiation | Unclear which key is authoritative after regeneration | accept | Only key IDs (public values) are recorded in the summary; the old key is superseded and no release ever shipped it, so no revocation path is needed. |
| T-34-SC | Tampering | npm/pip/cargo installs | mitigate | No installs — `@tauri-apps/cli` is already a devDependency. |
</threat_model>
