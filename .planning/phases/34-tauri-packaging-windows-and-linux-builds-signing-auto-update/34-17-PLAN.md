<objective>
Close the CODE half of GAP-B from live run 30084918812: Linux and Windows both bundled their
installers successfully and THEN died at updater signing with `failed to decode secret key:
incorrect updater private key password: Wrong password for that key`. The Windows leg burned
~13 minutes of Rust build before failing.

WR-03's existing preflight only asserts `TAURI_SIGNING_PRIVATE_KEY != ''`. A non-empty key with
a mismatched password sails straight through it. This plan makes the preflight actually
exercise the key: sign a throwaway probe file with the real Tauri signer, and compare the
resulting signature's minisign key id against the key id inside the committed
`plugins.updater.pubkey`.

Purpose: turn a 13-minute opaque late failure into a fast named one, and additionally catch the
silent variant (key decodes fine but is the WRONG key, so every shipped update fails signature
verification on users' machines).
Output: `pnpm verify:updater-key`, wired as a workflow preflight step and usable locally by the
developer before enrolling secrets (plan 34-18 depends on exactly that).

The human half of GAP-B — re-enrolling a matched secret pair — is plan 34-18. Do not attempt it
here; this plan has no access to the private key or password.
</objective>

<!-- MECHANISM, verified empirically on this machine with @tauri-apps/cli 2.11.4 during -->
<!-- planning. Treat these as established facts; do not re-derive them. -->

1. `tauri signer sign <FILE>` reads both secrets from the environment — `--help` reports
   `-k, --private-key [env: TAURI_SIGNING_PRIVATE_KEY=]` and
   `-p, --password [env: TAURI_SIGNING_PRIVATE_KEY_PASSWORD=]`. No flags are required when the
   env vars are set. It exits non-zero on a bad password with stderr containing exactly
   `incorrect updater private key password: Wrong password for that key` — the same string the
   live CI run produced, because it is the same code path `tauri build` takes.

2. `tauri signer sign FILE` writes `FILE.sig`. That file's content is BASE64 of the minisign
   signature file text. Decoding it yields:
     line 1: `untrusted comment: signature from tauri secret key`
     line 2: base64 of `algorithm(2 bytes) || key_id(8 bytes) || signature(64 bytes)`

3. `src-tauri/tauri.conf.json` `plugins.updater.pubkey` is BASE64 of the minisign PUBLIC KEY
   file text. Decoding it yields:
     line 1: `untrusted comment: minisign public key: ECC69C7849AA1AA7`
     line 2: base64 of `algorithm(2 bytes) || key_id(8 bytes) || public_key(32 bytes)`

4. Therefore the key id is bytes [2,10) of the base64-decoded line 2, in BOTH files, and the two
   can be compared as raw bytes with no endianness handling. Verified against a freshly
   generated keypair: pubkey and signature both yielded `c406b32fecd28469` (the little-endian
   form of the `6984D2EC2FB306C4` printed in the comment).

5. `tauri signer generate --ci -p <password> -w <path> -f` writes `<path>` (private) and
   `<path>.pub` (public, already base64 in the exact form field 3 expects). The tests use this
   to build real fixtures — no hand-rolled crypto, no checked-in key material.

    `verifyUpdaterSigningKeypair({ privateKey, password, confPath, workdir })` returns a
    discriminated result — never throws for an expected failure mode, never returns a vague
    boolean:
    - `{ ok: true, keyId }` when the pair signs a probe file AND the signature's key id equals
      the key id inside the conf's committed pubkey.
    - `{ ok: false, kind: 'missing-key' }` when privateKey is empty/whitespace.
    - `{ ok: false, kind: 'password-mismatch', detail }` when the signer exits non-zero with
      stderr matching /incorrect updater private key password|Wrong password for that key/.
    - `{ ok: false, kind: 'sign-failed', detail }` for any other non-zero signer exit (detail =
      trimmed stderr, which contains no secret material).
    - `{ ok: false, kind: 'pubkey-mismatch', signatureKeyId, pubkeyKeyId }` when signing works
      but the key ids differ.
    - `{ ok: false, kind: 'bad-pubkey', detail }` when the conf pubkey is absent or not
      decodable into the two-line minisign form.

    Tests (meta/__tests__/updaterSigningKey.test.ts) generate REAL keypairs in `beforeAll` with
    the Tauri CLI — keypair A (password `pw-alpha`) and keypair B (password `pw-beta`) — and
    write two fixture conf files (one carrying pubkey A, one carrying pubkey B):
    - matched key A + `pw-alpha` + conf-with-pubkey-A -> `ok: true`, keyId is 16 lowercase hex chars.
    - key A + `pw-beta` -> `kind: 'password-mismatch'` (THE live failure).
    - key A + `pw-alpha` + conf-with-pubkey-B -> `kind: 'pubkey-mismatch'` with two different ids.
    - empty privateKey -> `kind: 'missing-key'` and the Tauri CLI is never spawned.
    - conf whose `plugins.updater.pubkey` is `"not-base64-minisign"` -> `kind: 'bad-pubkey'`.
    - `keyIdFromMinisignFile` returns the same id for keypair A's `.pub` file content and for a
      signature produced by keypair A (the core invariant, asserted directly).
    - end-to-end entry: running the real `pnpm verify:updater-key` with the wrong password exits
      non-zero and emits a line starting `::error::`; with the matched pair it exits 0. Guard
      this one with the `process.platform === 'win32' ? describe.skip : describe` pattern used
      elsewhere in the repo, and give these tests an explicit longer timeout — each spawns the
