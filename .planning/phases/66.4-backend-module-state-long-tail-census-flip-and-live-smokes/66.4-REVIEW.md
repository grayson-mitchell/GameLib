# Phase 66.4: Code Review Report

**Reviewed:** 2026-11-14
**Depth:** standard
**Files Reviewed:** 123
**Status:** issues_found

## Summary

Phase 66.4's runtime conversion is, on the whole, sound. I read the boot step list in `bootstrap.ts`, every `createXRuntime()` factory, the sidecar transport, the stdin-EOF release, the outbound HTTP tracker, the `app-folder` step, the shortcut writer and icon resolver, and the census script. I checked the following and found them correct:

- Every runtime factory allocates only maps, closures and counters. Timers go through the unref'd injected clock.
- `derivePaths` and `resolveAppDataDir` match the deleted `constants/paths.ts` and `pathShim.ts` value for value. I diffed them against `d872dea92^`.
- win32 `knownFolder('desktop'|'documents')` still throws, and its only callers go through `readWindowsShellFolder`, so the OneDrive-redirect behaviour is preserved.
- The quoted `.lnk` argument escaping in `buildShortcutEnv` is correct.
- `createRealRunner()` applies `pinnedEnv` after the `replaceEnv` merge, so the win32 shortcut tests stay fake-HOME isolated even though `buildShortcutEnv` spreads `process.env`.

The headline problem is that the phase's own zero-tolerance gates are red at HEAD. The census gate is also weaker than its "zero-tolerance" label implies: it has three blind spots I could prove with a script. The orphan checker's `eof` arm leaks the fake profile it creates.

## Critical Issues

### CR-01: The module-state census test fails on main; the zero-tolerance gate is red

**File:** `src/backend/__tests__/moduleStateCensus.test.ts:77-80` (data from `src/backend/humble/adapter.ts:295`, `src/backend/humble/adapter.ts:794`, `src/backend/storeManagers/steam/authTrigger.ts:123`)

**Issue:** Running `listModuleStateSites()` against the current tree returns six sites. The test sanctions only three: logger x2 and bootstrap x1. The extra three sites are:

- `humble/adapter.ts:295` `let libraryActionCache` (commit 31a4f11df, 2026-11-13)
- `humble/adapter.ts:794` `let redeemActionCache` (commit a58e3e3e8, 2026-11-14)
- `storeManagers/steam/authTrigger.ts:123` `const INFERRED_REFRESH_ORIGINS = new Set([...])` (commit abd2bc538, 2026-11-14)

So `violations()` reports "not a sanctioned file" for both files, and the `has no site outside SANCTIONED` test throws. All three landed after 66.4 closed. The first two re-introduce exactly the per-process mutable state this phase removed: a cache shared across boots.

The `authTrigger` site is a false positive of the census definition. The census counts every `const x = new X()` whatever it is used for, and this set is never mutated.

**Fix:**
```ts
// humble/adapter.ts: move both caches into the boot-owned Humble services (createHumbleServices),
// and read them through the injected slice instead of module `let`s.

// authTrigger.ts: avoid a `new Set` const that the census cannot tell from state
const isInferredRefreshOrigin = (origin: string): boolean =>
  origin === 'steam-store-exit'
```
Then re-run `node meta/backendDiCeilings.cjs`, and run the census test to confirm that only the three sanctioned sites remain.

## Warnings

### WR-01: `pnpm backend-di-ceilings` fails with 21 errors at HEAD

**File:** `meta/backendDiCeilings/sidecar.json` (and the sibling shards), checked by `meta/backendDiCeilings.cjs:704-735`

**Issue:** `node meta/backendDiCeilings.cjs` exits 1. One failure is `grew: src/backend/storeManagers/steam/__tests__/games.test.ts 48 > baseline 47 (jestMock)`. The other 20 read "new violation: ... has N (jestMock) and no baseline entry". The files named there include `updateBridge.test.ts`, `updateDetection*.test.ts`, `updateDispatch.test.ts`, `updateNative.test.ts`, `bridgeUpdateFollowUps.test.ts`, `checkGameUpdates.test.ts`, and several frontend tests. They are the work of phases 74 and 75 and the quick tasks. This script is the gate that defines the jest.mock ratchet this phase flipped. As things stand it either does not run in CI, or it runs and nobody acts on it.

**Fix:** Either remove the `jest.mock` calls from those suites by injecting deps, which is the stated D-16 policy, or add baseline entries in the commit that introduced them. Then wire `pnpm backend-di-ceilings` into the CI step that runs `planning-gates` so it cannot silently drift again.

### WR-02: The "zero-tolerance" census has three provable blind spots

**File:** `meta/backendDiCeilings.cjs:210-262` (`moduleStateSites`) and `meta/backendDiCeilings.cjs:166-204` (`mutatedIds`)

**Issue:** I ran `countModuleState` on fixtures and got 0 for each of the following:

1. `export const reg: string[] = []` in file A, with `reg.push()` called from file B. Mutation is tracked only within the declaring file, and B has no declaration.
2. `const x = Object.create(null); x.a = 1`. This is a dictionary object that no rule counts.
3. `const cache = {}; export function put(o = cache) { o.k = 1 }`. The mutation goes through an alias, and `mutatedIds` follows only the root identifier.

`export default []` and `export default {}` are also uncounted. `containerCallResidual()` covers only call-expression names matching a regex, so none of the above reaches it. A regression of the kind the phase removed would therefore keep the gate green.

**Fix:**
- Treat any top-level `const` bound to an empty `{}` or `[]` literal that is exported as a site, whether or not it is mutated locally.
- Add `Object.create(` to the counted initialisers.
- Count `export default <object or array literal>`.

Alternatively, document these limits in the test header next to "Zero module state" so the gate is not read as covering them.

### WR-03: `sidecarExitCheck --mode eof` leaks the fake profile and any hung child

**File:** `meta/sidecarExitCheck.ts:214-229`, `meta/sidecarExitCheck.ts:307-362`

**Issue:** `runEof` does `try { ... return invalid(...) / return finish(...) } finally { profile.dispose() }`. Both `finish()` and `invalid()` end in `process.exit(...)`, which terminates the process synchronously, so the `finally` never runs. The fake-HOME profile is therefore never disposed. It holds the sidecar's logs and config, which the conventions say belong to the harness to clean up (`260913-901` left 103 MB of unredacted captures for this reason). The `invalid('eof', 'sidecar never wrote the READY sentinel')` path also leaves the child running. That is the very hang this tool exists to detect. It then keeps writing into the profile directory that was never deleted.

**Fix:**
```ts
// Make the drivers return a verdict, and exit only after cleanup.
async function runEof(): Promise<Report> { /* ... return {...} instead of finish()/invalid() ... */ }

job.then((report) => finish(report)) // finish() runs after runEof's finally
// and on the INVALID paths: child.kill('SIGKILL') before returning (the child is this script's own).
```
Alternatively, call `profile.dispose()` and `child.kill()` explicitly before `finish()`/`invalid()`.

## Info

### IN-01: `ShortcutDetails` declares four fields the writer silently ignores

**File:** `src/backend/shortcuts/shortcuts/windowsShortcut.ts:23-32`, `windowsShortcut.ts:129-149`

**Issue:** `cwd`, `description`, `appUserModelId` and `toastActivatorClsid` are accepted but never reach `buildShortcutEnv` or the C# `Writer.Write`, which handles only path, target, args and icon. The shape is inherited from Electron's `writeShortcutLink`. Today's callers pass only a URL target, but a future caller that sets `cwd` for an `.exe` target would get a `.lnk` with no working directory and no error.

**Fix:** Drop the four unused fields from the interface, or wire `SetWorkingDirectory` and `SetDescription` through env vars.

### IN-02: A relative `storeExecutable` with no `installPath` is resolved against the sidecar's cwd

**File:** `src/backend/shortcuts/shortcuts/windowsShortcutIcon.ts:169-175`

**Issue:** `path = installPath && !isAbsolute(storeExecutable) ? join(installPath, storeExecutable) : storeExecutable`. When `installPath` is undefined and `storeExecutable` is relative, `stat(path)` resolves it against `process.cwd()`. Any `.exe` or `.dll` at that relative path in the app directory is accepted. The resulting relative `IconLocation` is then written into the `.lnk`.

**Fix:** Require `isAbsolute(path)` before `isUsableIconFile`, or skip the store-executable arm when it cannot be anchored.

### IN-03: `prebuilt.paths` is a dead seam, and the boot reads paths from two sources

**File:** `src/backend/sidecar/bootstrap.ts:1681`, `bootstrap.ts:1693`, `bootstrap.ts:1695`

**Issue:** The 'config' step reads `prebuilt.paths ?? ctx.paths` and publishes it as `state.services.paths`. Every other path consumer reads `ctx.paths` directly: 'stores', 'steam-bottle', 'engine-runtime', 'app-runtime', 'secret-vault', 'rosetta' and others. No test supplies `prebuilt.paths`; `bootstrap.test.ts` overrides `context.paths` instead. If a test ever did supply it, the config and managers would use one root and the runtimes another.

**Fix:** Remove `prebuilt.paths` and use `ctx.paths` throughout, or take every consumer from `state.services.paths`.

### IN-04: `images_cache.ts` is unreferenced and carries two latent defects

**File:** `src/backend/images_cache.ts:21-63`

**Issue:** The file's own comment says nothing imports it, so the cache has no consumer. If it is ever wired up, two problems arise. The `axios(...).then(pipe).finally(...)` chain is neither returned nor caught, so a network error becomes an unhandled rejection. A stream that dies partway leaves a truncated file at `cachePath`, and `existsSync(cachePath)` then serves it forever.

**Fix:** Delete the module and its `createImageFetches` slot in `appRuntime.ts`, or add a `.catch`, write to a temp name and `rename` on completion.

### IN-05: Duplicated sanctioned-count literal and a stale header in the census test

**File:** `src/backend/__tests__/moduleStateCensus.test.ts:2-4`, `moduleStateCensus.test.ts:77-80`

**Issue:** The expected counts appear twice, in `SANCTIONED` and in the final `toEqual({...})`, so a legitimate edit has to be made twice. The header says "Zero jest.mock", but nothing in this file asserts that. That check lives in `meta/backendDiCeilings.cjs`, which is red per WR-01.

**Fix:** Derive the `toEqual` object from `SANCTIONED` filtered to counts above 0, and fix the header sentence.
