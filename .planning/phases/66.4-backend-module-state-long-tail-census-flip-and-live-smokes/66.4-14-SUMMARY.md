# Phase 66.4 Plan 14: Tools state and tools/wine/anticheat paths Summary

The tools long tail (5 census sites in tools/index.ts and tools/winetricksEnvironment.ts) is now closure state of one boot-owned `createToolsState()`, and five tools, wine and anticheat files read toolsPath, runtimePath, userHome and appFolder from a paths slice instead of `backend/constants/paths`.

## Commits
Two code commits; the tree typechecks between the tasks.
- `d22d62acf` Task 1: ToolsState owner, winetricks environment factory, 'tools-state' step, shard deletions.
- `3075de895` Task 2: path cascade and test fixes.

## ToolsState and boot step
`'tools-state'` allocates a Map and closures only: no I/O, timer or handle. Every Tools built from the boot (`toolsFrom`, the Wine-tools and runner-misc registrations, the launcher's engine source) receives the same instance through `deps.toolsState`, so the catalog and script-metadata caches and the single-flight slot still cache (T-66.4-43). The winetricks queue reads `toolsState.installing.get()` for `busy`, from the same instance Winetricks.install writes (T-66.4-44), and the single-flight logic is unchanged. Tests: `toolsState.test.ts` (per-instance state, listener replacement, copies), plus shared-state and isolated-state cases in `winetricksListAvailable.test.ts` (a second Tools on the same state reuses the catalog without a new wine call and the script metadata without a re-read).

## Paths
`tools/index` (installer, DXVK, winetricks) reads `deps.paths.toolsPath` / `userHome`; `tools/dxmt` carries `paths` on its listener deps and helper args; `wine/manager/utils` getInstallDir and installWineVersion take `paths`; `wine/runtimes/runtimes` download and isInstalled take `paths`; `anticheat/utils` takes `paths` (appFolder). Callers pass the boot paths (launcher, handlers, bootstrap, enrichment and runner-misc registrations). `census-clean --no-paths-import` passes for all five files; `toolsPath`/`runtimePath` still come from the parity-pinned `derivePaths` (T-66.4-45).
