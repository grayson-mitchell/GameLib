# Phase 50 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Scope note:** this phase's dominant surface is a native, Rust-owned `WKWebView` subview that
renders Epic's own unmodified page (L-1: zero page-side injection, zero DOM styling). This
contract therefore does **not** specify anything about Epic's page — it covers only the
GameLib-owned chrome *around* that surface: the existing `StoreEmbedControls` bar (unchanged,
reused as-is), the existing `StoreEmbedPlaceholder` (now shown *through* a transparent subview per
D-06, not only while hidden), the new D-07 timeout banner, the new `'epic-challenged'`
`WebviewUnavailablePanel` reason (D-10), and the new D-14 blocked-scheme toast. Every value below
is either lifted from the project's existing, shipped token set and component CSS (never
invented), or flagged explicitly as an assumption where CONTEXT.md left the visual shape open.

## Design System

| Property | Value |
|----------|-------|
| Tool | none |
| Preset | not applicable |
| Component library | none — hand-rolled `div`/`button` elements styled via per-component CSS files against the project's CSS custom-property token set (`src/frontend/styles/_colors.scss`, `_spacing.scss`, `_typography.scss`, `src/frontend/themes.scss`). No shadcn, no Radix, no Base UI. |

screen, every one of the 8 shipped themes) is built on the hand-rolled token system above, not a
component library. Introducing shadcn for this phase's handful of small chrome additions would
fragment the design system rather than serve it, and this phase touches no new screen — it extends
three already-shipped, already-styled components. **Assumption (see below): Tool stays `none`.**

## Spacing Scale

This is the project's own existing scale (`src/frontend/styles/_spacing.scss`), pre-populated —
**not** a generic 8-point grid; it is `em`-relative to the 16px root (`--text-md`), so values
below are the resolved px at the default root size for reference only. **Do not introduce a
parallel px-literal scale for this phase's new UI** — use these tokens.

| Token | Value (em) | ≈px @ 16px root | Usage in this phase |
|-------|-----------|------------------|----------------------|
| `--space-3xs` | 0.25em | 4px | Icon-to-text gap on the new banner/toast (`StoreEmbedControls__icon` margin precedent); border-inline-start width on the warning accent bar |
| `--space-2xs` | 0.375em | 6px | Banner/toast border-radius (`HumbleExpiryToast` precedent) |
| `--space-xs` | 0.5em | 8px | — |
| `--space-sm` | 0.75em | 12px | Gap between icon/message/action inside the new banner and toast (`HumbleExpiryToast` precedent); action button horizontal padding |
| `--space-md` | 1em | 16px | Banner/toast padding (all sides); `WebviewUnavailablePanel` spacing is unchanged — already uses this token for its spinner margin |

## Color

Every value is a CSS custom property — **never a literal hex** — per the project's multi-theme
survival rule (8 shipped themes override these tokens independently; `gruvbox_dark` and `dracula`
are the two the project's own conventions call out as the ones that break naive hard-coded color).

| Role | Token | Usage |
|------|-------|-------|
| Dominant (60%) | `var(--body-background)` | The page background behind everything; also the color the Epic subview's host window shows at its very edges. Unchanged by this phase. |
| Secondary (30%) | `var(--background-darker)` (StoreEmbedControls bar, the new banner/toast surface) and `var(--background-secondary)` (StoreEmbedPlaceholder's dim fill, now also visible *through* the transparent subview per D-06 until Epic paints) | Chrome surfaces around the embed |
| Accent (10%) | `var(--accent)` | Reserved for: `StoreEmbedControls__icon`'s `:active`/`:focus-visible` states and its `border-bottom` divider under the bar. **Not** used by the new banner, toast, or challenged panel — those are informational/caution surfaces, not active/brand-accent surfaces (see Second semantic color below). Do not extend `--accent` onto the new elements. |
| Second semantic color | `var(--status-warning)` | Reserved for: the D-07 timeout banner (border-inline-start accent bar, icon color, "Reload" action text/border — `HumbleExpiryToast`'s own established pattern) and the D-14 blocked-scheme toast (same pattern, caution not failure). |
| Destructive / error | `var(--danger)` / `var(--text-danger)` | Already reserved by `StoreEmbedControls__hostText--warning` (the insecure-`http://`-host indicator) — unchanged by this phase. The new `'epic-challenged'` panel does **not** use this token; a Cloudflare challenge is a transient, retryable state (D-11: no stickiness), not a destructive/error state, so it inherits the plain `WebviewUnavailablePanel` look (no color override at all — see next row). |
| Panel (challenged / all existing reasons) | *(none — unstyled)* | `WebviewUnavailablePanel` has no dedicated background/surface rule beyond the global `h1`–`h3` → `var(--text-default)` color and the spinner's `var(--accent)` ring. The new `'epic-challenged'` reason must not introduce a colored surface that the `'platform'`/`'epic'` reasons don't already have — keep it visually identical to the existing two reasons, text-only plus buttons. |

## Assumptions made in lieu of user answers

Per the unattended/`yolo` workflow mode, the following were decided by picking the option most
consistent with the existing embed host, the existing `WebviewUnavailablePanel`/`StoreEmbedControls`
code, and the sketch findings' multi-theme survival rule — rather than blocking on a question:

1. **A1 — shadcn gate skipped, `Tool: none`.** `components.json` is absent and the entire app is
   built on the hand-rolled CSS-custom-property token system. Initializing shadcn for this phase's
   small chrome additions would contradict the rest of the app's design system. Risk if wrong:
   low — nothing in this phase's scope needs a component library (no new dialogs, forms, or data
   display — just a banner, a toast, and a panel reason variant, all extensions of existing
   unstyled-by-design components).

2. **A2 — D-10 challenged-panel heading text.** CONTEXT.md D-10 gives only the body sentence
   ("Epic asked for a security check this view can't complete."). A heading was drafted
   ("Epic needs a security check this view can't pass") to parallel the existing two reasons'
   heading/body split, since `WebviewUnavailablePanel`'s structure (`heading` + `body` + optional
   `nextStep`) is being reused, not replaced. Risk if wrong: low — pure copy, trivially
   correctable in `gamelib.json` without touching layout, color, or component structure. **This is
   the one row the checker/user should explicitly confirm or override.**

3. **A3 — D-14 toast's visual shape.** CONTEXT.md's own Discretion section does not name a toast
   mechanism, and the project has **no toast/snackbar library** (`HumbleExpiryToast`'s own doc
   comment states this explicitly). Assumed: the D-14 toast follows `HumbleExpiryToast`'s
   established "minimal from-scratch banner" shape (fixed position, icon + message, `--status-warning`
   accent, auto-dismissing since D-14 names no dismiss control and the notice is transient/one-shot
   per navigation attempt) rather than inventing a new toast primitive or a dialog. Risk if wrong:
   medium — if the planner instead wants a persistent/dismissible toast (matching
   `HumbleExpiryToast`'s dismiss button) rather than auto-dismiss, the copy and color token are
   unaffected, only the interaction/timeout behavior changes.

4. **A4 — banner/toast icon library.** Assumed `@fortawesome/free-solid-svg-icons`'
   `faTriangleExclamation` (matching `HumbleExpiryToast`'s established warning-banner convention)
   rather than an MUI icon (which `StoreEmbedControls` uses for its *controls*, not for status
   messaging). Risk if wrong: trivial — a one-line icon-import swap, no layout/color impact.

5. **A5 — banner row height/placement mechanics.** D-07 says "the planner decides how" the
   placeholder/banner stack under `StoreEmbedControls`; this spec records the 40px row-height
   parity with `StoreEmbedControls` itself as the visual target but leaves the actual CSS-grid
   mechanics (new named grid row vs. absolute overlay) to the planner, per CONTEXT.md's own
   deferral.
