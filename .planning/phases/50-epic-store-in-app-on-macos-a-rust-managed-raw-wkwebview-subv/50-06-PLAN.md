**Ordering constraints — this is Test 5's output and it is the part most likely to be skipped.**
The unit of review is the requirement PAIR: does satisfying A destroy B's evidence? Three pairs on
this gate do, and the document must state the ordering as a hard constraint with its reason:

1. **Cold jar BEFORE warm signed-in jar, and the cold arm is run ONCE.** Satisfying the warm arm

   botched, record it as botched and re-derive the ordering for a later session; do not clear the
   jar to retry.
2. **Every online arm BEFORE the timeout arm.** Forcing a stall by going offline destroys the
   warm-jar arm's and the Steam positive control's preconditions in the same session. Prefer a
   host-level block over a full network disconnect so the Steam control survives, and state which
   mechanism was used.
3. **The Steam positive control in the SAME session as every Epic arm.** An Epic arm with no Steam
   render alongside it proves nothing — it cannot distinguish "Epic did not render" from "this
   launch was a dead harness" (spike 024's own method note).

Add a fourth, environment-level constraint that has already eaten a fixture on this repo: **a live
`tauri dev` relaunches the app on every commit**, and one such relaunch consumed an as-found
profile fixture twenty minutes before a gate. The contract must instruct the operator to quit any
running `tauri dev` BEFORE the gate build, and to back up any fixture profile the gate depends on.
