<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Console (renderer) → OS via `steam://` protocol handoff | Activating a Steam game triggers `steam://rungameid/{appId}` (launch) or `steam://install/{appId}` (install), which the OS routes to the Steam client. The appId originates from GameLib's own library data, but the URL crosses into OS-level protocol handling. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-08-03 | Tampering / Elevation | `steam://` URL construction for launch + install | mitigate | The frontend constructs NO raw `steam://` URLs. Both LaunchOverlay and InstallOverlay call the EXISTING runner-agnostic `launch()` / `install()` helpers, which route to the validated backend `steam/games.ts` where `buildSteamProtocolUrl` validates the appId before building the protocol URL. Verified by the `! grep "steam://"` gate in Task 3. |
| T-08-04 | Denial of Service | Fire-and-forget overlays (Launch + Install) | accept | Steam never reports running/exit, so overlays cannot depend on a completion signal. Both use a bounded 1500ms `setTimeout` auto-dismiss with a cleanup guard (`clearTimeout` / `cancelled` flag), so no overlay can hang or leak a timer. The managed indefinite "Launching…" state is deliberately NOT reused for Steam (D-04). |
| T-08-SC | Tampering (supply chain) | npm/pip/cargo installs | accept | Zero new packages introduced in this plan (confirmed by RESEARCH and UI-SPEC Registry Safety). No install tasks — only edits to existing frontend/i18n files. |
</threat_model>
