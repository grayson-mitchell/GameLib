<objective>
Close CR-04 (D-01/D-17): Sideload `handleRunExe` passes `{ ...gameSettings, ...engineConfig }` to
`window.api.runWineCommand`. `engineConfig` holds only `engineOverride` and
`wineCrossoverBottle`; `wineVersion`/`winePrefix` keep the stored defaults. The sidecar's
`runWineCommand` handler (`wineToolsFlowRegistration.ts:136-141`) is pass-through by design and
never calls `resolveToolSettings`, and the per-game bottle does not exist yet. The installer runs
in the wrong prefix or against a non-existent bottle, so the game's registry entries and
redistributables land where the launch never looks.

Trace done at planning time (the executor re-confirms in Task 1's RED tests):
- The review's suggested route, `runWineCommandForGame` -> `runWineCommandOnGame`
  (`tools/index.ts:1506`), cannot serve the normal case. Run installer is clicked before the
  sideload game is added, so `libraryManagerMap.sideload.getGame(appName).getGameInfo()` returns
  `{}` (`sideload/games.ts:38-45`) and `SideloadGame.isNative()` destructures `install.platform`
  from undefined and throws (`sideload/games.ts:149-152`). It also hard-codes `wait: false`.
- `resolveToolSettings` (`engine/toolSettings.ts:100`) needs a `Game` only for
  `engineKeyIfEligible` and `getGameInfo().runner/app_name`.
- `tools/ipc_handler.ts` is not imported by any live entry point (only named in sidecar comments);
  the live handler is `wineToolsFlowRegistration.ts`.

Design (planner): extract a Game-free `resolveToolSettingsForId`, add
`runWineCommandForPendingInstall` that resolves the game's bottle from the config the dialog just
wrote (with `ensureBottle: true`), and reach it through the existing `runWineCommandForGame`
channel with two optional args (`wait`, `pendingInstall`). No new IPC channel, so no census or
inventory row changes.

Output: Game-free resolver, pending-install runner, extended channel args, fixed dialog, tests.
</objective>
