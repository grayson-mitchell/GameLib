<objective>
The per-game bottle (D-01, D-03) and the single rule that says which prefix a game runs in
(D-02, D-04, D-05).

Decisions recorded here:
- **Name scheme (CONTEXT discretion, D-01):** `GameLib-<runner>-<encoded appName>`. Encoding
  keeps `[A-Za-z0-9-]` and writes every other byte of the UTF-8 appName as `_xx` (lower-case
  hex, `_` itself becomes `_5f`), which is injective; the runner in the name makes it
  collision-free across stores. When the result exceeds the cap measured by spike 068
  (`verdict.json` `bottleName.maxLengthAccepted`, and never more than 64), it is cut and
  suffixed `-<first 10 hex of sha256(runner + ':' + appName)>`. If spike 068 showed dots are
  accepted, `.` may be kept literally except where it would form `..` (record which in the
  SUMMARY). Every produced name must satisfy `sanitizeBottleName(name) === name`.
- **CrossOver create (D-19 note):** D-19 limits extraction from `bottle.ts` to six primitives,
  and Steam's CrossOver-create arm lives inside `provisionBridgeBottle`. So this plan writes a
  small `createCrossoverBottle` in the engine (argv-form `cxbottle --create --bottle <name>
  --template win10_64`, `CX_CREATE_CAP_MS` cap, kill + remove-on-failure) built only from the
  extracted primitives, and leaves Steam's arm untouched. Phase 65 should fold the Steam arm onto
  it. The no-CrossOver path reuses `createFallbackBottle` (D-03), no second path.
- **Prefix rule (`resolveGamePrefix`):** see Task 2.

Output: `perGameBottle.ts`, `gamePrefix.ts`, `pinnedEngineProgress.ts`, tests.
</objective>
