<objective>
Implement the engine key and the read-time migration (D-05..D-09) as one backend module,
`src/backend/engine/engineConfig.ts`, plus the backend write guard and the new-game default.

Decisions recorded here (CONTEXT "Claude's Discretion: name and storage of the engine key"):
- New key `GameSettings.engineOverride?: string` for every store, same closed grammar as
  `parseEngineOverride`. Steam keeps reading its old `steamEngineOverride` as a fallback (users
  have it on disk); the Engine control only ever writes `engineOverride`.
- Legacy is never a stored value. It is a derived variant `{ kind: 'legacy', label }` produced
  only when no key exists and the stored Wine is outside the option list. A stored
  `legacy:anything` parses to `automatic` by the closed grammar and is rejected at write time.

Purpose: one implementation of the migration, so the UI and the launch can never disagree, and
no data migration (D-08: derived at read, written only on user save; not the
`src/backend/migration/` runner).
Output: `engineConfig.ts` + tests, `engineOverride` type, write guard, first-write default.
</objective>
