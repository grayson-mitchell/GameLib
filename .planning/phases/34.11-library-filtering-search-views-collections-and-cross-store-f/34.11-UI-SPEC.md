## New Finding: a third theme-survival defect in the same class as CR-01/CR-02

Scouting `src/frontend/themes.scss` for CR-01 turned up a **second, unlogged instance of the
exact defect class** `34.10-REVIEW.md` already named once (the "no-fallback custom property"
collapse): `.NavShell__tier2`'s own `border-inline-end: 1px solid var(--divider)`
(`NavShell/index.scss:149`) uses `--divider`, which is defined in only **2 of 11** theme blocks
(`midnightMirage` at `themes.scss:97`, `classic`/`cyberSpaceOasis*` at `themes.scss:145`) —
**`gruvbox_dark` and `dracula` do not define it.** Per the CSS custom-properties spec, an
undefined property with no fallback is invalid at computed-value time, which drops the entire
`border-inline-end` shorthand — the filter panel's own right-edge divider silently disappears in
both of this phase's two mandatory stress-test themes, not just one.

This exact mechanism was already found and fixed **once** in 34.10 (the navbar's bottom-border
seam, `NavShell/index.scss:116`, fixed to `var(--body-background)`) — the comment at that fix site
explicitly flags this second occurrence as "KNOWN, OUT-OF-SCOPE, RECORDED SEPARATELY... left
unchanged here" because it draws the tier-2 column's border, not the navbar/content seam that
34.10 task owned. This phase **is** the tier-2 column's content — fix it here.

**Fix:** change `NavShell/index.scss:149`'s `border-inline-end: 1px solid var(--divider);` to
`border-inline-end: 1px solid var(--body-background);` — the exact same token substitution proven
safe app-wide in 34.10 (verified present, and distinct from `--navbar-background`, in all 11
theme blocks). Verify visually in `gruvbox_dark` and `dracula` alongside the CR-01/CR-02 checks
this phase already owes.

### Facet row control — checkbox, not `ToggleSwitch`

`CategoryFilter` and `LibraryFilters` (both retired by this phase) use `ToggleSwitch` — a pill
switch appropriate for a single boolean setting inside a dropdown. The sketch's facet rows are a
**scannable list of options with counts**, which is a checkbox-list pattern, not a settings-toggle
pattern — reusing `ToggleSwitch` for 4-6 stacked facet options per group would misrepresent them as
independent settings rather than a set of alternatives with counts attached. **Build new facet-row
markup per the sketch's `.item`/`.chk` CSS pattern** (adapted to real tokens below), not a
`ToggleSwitch` reuse. Views and Collections rows are a different control again — see next section.

### Views/Collections row control — a `NavItem` gap to flag

`components/UI/NavShell/components/NavItem/index.tsx` is the exact row primitive already driving
Stores/Settings tier-2 nav lists, and its CSS (`NavItem/index.scss`) is already scoped under
`.NavShell__tier2 .NavItem`, so it would apply for free to anything rendered inside this portal.
**However, `NavItem`'s `elementType="button"` branch does not support the `active` class or a
`className` prop** — `case 'button': return <button className="NavItem" onClick={onClick}>...` —
only the default `NavLink` branch applies `active`/`className` via `classNames()`. Views and
Collections are **not** routes (they're local `LibraryContext` state, not URLs), so they must use
the button branch, which today cannot render a selected state at all.

**This phase must extend `NavItem`'s button branch to accept `className` and an `active`/`isActive`
boolean** (mirroring what the `NavLink` branch already does), rather than forking a parallel
component — the CSS custom properties (`--navitem-active-color`, `--navitem-active-background`)
are already theme-correct and exactly what Views/Collections rows need. Flag this as a required
task, not an optional cleanup: without it, "selected view" and "selected collection" have no way
to render distinctly from the rest of the row.

## Spacing Scale

Reuse 34.10's already-declared em-relative tokens (`src/frontend/styles/_spacing.scss`). No new
spacing tokens are introduced by this phase.

| Token (existing) | px @ 16px root | Usage in this phase |
|---|---|---|
| `--space-3xs` | 4px | Checkbox-to-label gap inside a facet row (sketch: `gap: 9px` — nearest real token is `--space-2xs` at 6px, see Exceptions) |
| `--space-2xs` | 6px | Facet-row vertical padding (sketch: `padding: 6px var(--space-3)` — 6px maps exactly) |
| `--space-xs` | 8px | Chip vertical padding (sketch: `padding: 3px 8px` — the 8px half maps exactly, see Exceptions for the 3px half); row vertical padding, matching `NavItem`'s own `padding: var(--space-xs) var(--tier2-row-padding-inline)` |
| `--space-sm` | 12px | Gap between panel sections (Search / Views / Collections / facet groups) |
| `--space-md` | 16px | Row horizontal padding (`--tier2-row-padding-inline`), chip-to-chip gap in the chip row |
| `--space-lg` | 24px | Panel top/bottom padding, matching `Header`'s existing `padding: var(--space-lg) var(--space-sm)` (`Header/index.css:6`) — **reuse this rule as-is**, do not redeclare |

Exceptions (dictated by the sketch's own small-scale UI, not aesthetic choice — same rationale
34.10 used for its own literal exceptions):

- **Checkbox size 14×14px** — the `.chk` box. No spacing-scale token is a checkbox-size token;
  this is a fixed control dimension, not rhythm.
- **9px checkbox-label gap → round to `--space-2xs` (6px)**, not a new literal. The sketch's own
  values are not multiples-of-4 in several places (`gap: 9px`, `padding: 6px var(--space-3)`,
  `font-size: 10px` for counts) because it is unstyled-prototype CSS; this contract rounds each to
  the nearest real token rather than importing the sketch's raw numbers verbatim, matching how
  34.10 treated the same reference file's non-8pt values.
- **Chip padding `3px 8px` → `var(--space-2xs) var(--space-xs)`** (6px 8px) — nearest tokens,
  chips are a small enough control that exact-sketch-px is not load-bearing.
- **Count column font-size 10px → `var(--text-xs)`** (11.11px at 16px root) — the codebase has no
  10px type-scale rung; `--text-xs` is the smallest that exists and is close enough that inventing
  a ninth scale rung for one label is not justified.

**CR-01 fix — `--navbar-active` in `gruvbox_dark`:** `themes.scss:192-231` (`body.gruvbox_dark`)
never sets `--navbar-active`. Recommended value: **`--navbar-active: var(--navbar-accent);`** —
`gruvbox_dark` already defines `--navbar-accent: #f9f5d7` (a warm cream already used for that
theme's own accent role, `themes.scss:195`), giving a theme-appropriate bright value rather than
falling through to the grey base `--text-secondary: #b1b1b1` (`themes.scss:3`, the only other
thing `var(--navbar-active)` could resolve to with no theme override). Confirm this value reads
clearly against `--navbar-active-background: #282828` (`themes.scss:201`) during live theme
verification — this is a recommendation, not an already-measured value, precisely because the
theme-survival rule requires it be checked live, not assumed from hex math.

**CR-02 fix — `-webkit-app-region: drag`:** neither `.NavShell__navbar` nor any of its FontAwesome
tab/icon children (`NavTabs`, `DownloadsRing`) currently declare any `app-region` at all — the only
existing `no-drag` declarations in the codebase are on `WindowControls` (`WindowControls/index.scss:6`)
and `HeroicVersion` (`HeroicVersion/index.scss:35`), neither of which is inside the navbar. Add
`-webkit-app-region: drag;` to `.NavShell__navbar` (`NavShell/index.scss:37-...`), then add
`-webkit-app-region: no-drag;` to every clickable child inside it that isn't already covered:
`.NavTabs` (the tab strip) and `.NavShell__navRight`'s interactive children (`DownloadsRing`'s
click target at minimum). `WindowControls` needs no change — it already has `no-drag`.

**Accessibility — gamepad focus-scroll (Deferred Idea, explicitly measure this time):** the
Deferred Ideas section of `34.11-CONTEXT.md` flags gamepad focus-scroll in the tier-2 panel as
**never measured** across any of 34.10's four gate runs, and notes this panel becomes "considerably
taller and scrollable" — this phase is the first real opportunity to measure it. Not a design
contract requirement, but the executor/verifier should not let it go unmeasured a second time.

**Accessibility — facet checkboxes:** use real `role="checkbox"` / `aria-checked` semantics (or a
native `<input type="checkbox">` visually replaced), not a `<button>` with only a CSS `.on` class —
the sketch's own markup is prototype-grade and does not specify ARIA; this contract requires real
checkbox semantics so screen readers announce facet state correctly, matching the accessibility bar
34.10 already set for tab/nav roles.

**Accessibility — chip removal control:** the chip `×` is icon-only, so its visible glyph is not an
accessible name. It **must** carry an explicit one: mint
`t('gamelib:library.filterPanel.removeFilter', 'Remove {{filterLabel}} filter')` and apply it as
`aria-label` on the `×` control, interpolating that chip's own label (`Installed`, `GOG`,
`"witcher"`, …). A bare `aria-label="Remove"` is **not acceptable** — with 4 chips active it
announces four identical controls. The `Clear all` chip needs no extra label; its text is its name.
Both are real focusable controls (`<button>`), not click handlers on a `<span>`.

## Open Questions

Recorded per instruction — genuinely unresolved by CONTEXT.md, the skill, or the codebase.
Recommended defaults given; not locked contract.

1. **Windows-host runnability facet has almost no discriminating signal today.** The codebase has
   `is_mac_native`, `mac_arch`, `crossoverRatings` (macOS) and `isLinuxNative` (Linux) — there is no
   equivalent "is this a native Windows build" boolean, and on a Windows host nearly every
   library-listed game is Windows-runnable by construction. **Recommended default:** render only a
   single, unlabelled-as-a-choice "Runs natively" row on Windows hosts (D-12's "hide what you can't
   compute," taken to its logical single-row conclusion), or consider omitting the Runnability
   facet group entirely on Windows if a one-option facet is judged not worth its header row. This
   is a genuine product decision, not purely visual — flag for `/gsd-plan-phase 34.11` rather than
   deciding unilaterally here.
2. **Should the "Manage collections" panel row also appear when zero collections exist**, mirroring
   `CategoryFilter`'s existing empty-state message ("No custom categories. Add categories using
   each game menu.", `CategoryFilter/index.tsx:79-89`)? **Recommended default:** yes, reuse that
   exact empty-collections message (already-translated key `header.no_categories`) inside the new
   Collections section when `customCategories.listCategories()` is empty, rather than hiding the
   section outright — consistent with D-17's "zero migration, same data" framing.
3. **Exact icon (if any) for view rows.** The sketch's views are text-only; `NavItem` supports an
   optional `icon` prop but Stores/Settings tier-2 rows all use one today. **Recommended default:**
   no icons on Views/Collections/facet rows in this panel — the sketch ships icon-free and adding
   icons for four views plus N collections plus store/runnability rows is a content-inventory
   decision (which icon means "Recently played"?) with no clear existing FontAwesome precedent to
   draw from; treat as text-only unless a strong icon set is proposed at plan time.
