## Accomplishments
- `FilterFacetGroup`/`FilterFacetRow` is a pure, React-context-free presentation primitive: real `role="checkbox"`/`aria-checked` rows (not `ToggleSwitch`, not a styled button), a count slot that renders `0` correctly (`count !== undefined`, never a truthiness test), and a caret whose rotation is driven purely by `Dropdown`'s own `aria-expanded` with no mirrored local state. Its SCSS is the single declaration site for facet row/group styling, scoped under `.NavShell__tier2Portal`, with the mandatory `font-variant-numeric: tabular-nums` count column (D-29).
- `FilterStoreFacet` renders exactly one row per `connectedStores` entry, in that array's own order, and returns `null` when it is empty -- it holds no account-connectivity logic of its own (no `ContextProvider`, no `.username` reads), so it structurally cannot render a row for a store the user hasn't connected (D-04).
- `FilterRunnabilityFacet` returns `null` entirely when `runnabilityRows` is empty (the Windows host, D-12 extension) -- no group header, no empty section, and explicitly not a degenerate all-pass "Runs natively" row. Proven by a `toBeNull()` assertion, not a children-length check. No tier derivation, medal identifier, or per-game field (`is_mac_native`, `mac_arch`, `GameInfo`) is duplicated here -- confirmed by a source gate observed FAILING against the file's own prose before a wording fix, then passing.
- `FilterMoreGroup` holds both `off`/`show`/`only` tri-states (Hidden, non-Available -- cycle ported verbatim from `LibraryFilters/index.tsx:50-68`) and the three remaining booleans inside exactly ONE collapsed group, with no counts on any row (D-06/D-07/D-28).
- All four components registered in `meta/i18nGateScope.json` via an additive, re-read-then-write edit (header untouched, array sorted and deduplicated) that preserved plan 06's `FilterViewList`/`FilterCollectionList` entries, landed in the same wave. `pnpm lint-translations:gamelib` exits 0; all 7 minted `gamelib:library.filterPanel.*` keys are present in `public/locales/en/gamelib.json` with correct (non-empty) default English text.
- Genre-drop source gate (D-13/D-14/D-15) added to `FilterMoreGroup.test.tsx`, scanning all seven panel component sources (this plan's four, plan 04's `facetLabels.ts`, and plan 06's `FilterViewList`/`FilterCollectionList`, already landed) for any mention of `genre`, `ExtraInfo`, or `extra?.genres` -- proven non-vacuous against a known-bad literal.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] FilterRunnabilityFacet's spread call is invisible to the i18n extractor; a literal-key/non-literal-default hybrid produces an empty catalog value**
- **Found during:** Task 2/3 self-verification (running `pnpm i18n` explicitly, per the plan's instruction not to assume a green jest run implies a passing gate)
- **Issue:** The plan's primary design (`tGamelib(...RUNNABILITY_LABELS[tier])`, a spread over a runtime lookup) is invisible to `i18next-parser`'s `JavascriptLexer`, matching 34.11-06's finding for a fully-variable call. Attempting the plan's suggested remedy with a literal KEY but a non-literal `defaultValue` (`tGamelib('gamelib:library.filterPanel.runsNatively', RUNNABILITY_LABELS.native[1])`) DID extract the key, but the generated `public/locales/en/gamelib.json` got an EMPTY string for that key's default text -- and because i18next renders whatever value exists in the resource bundle once a key is present (never falling back to the call-site `defaultValue` argument in that case), all four runnability rows would have rendered as blank text in the running app.
- **Fix:** Made both the key and the default text literal at each of the four `tGamelib()` call sites inside `runnabilityLabel`'s switch. Added a `process.env.NODE_ENV !== 'production'` dev-only check that echoes each call site's own `defaultValue` argument back out (via a stand-in function, not a duplicated literal-text object) and throws if it ever diverges from `facetLabels.ts`'s `RUNNABILITY_LABELS` tuples, so the two copies cannot silently drift.
- **Files modified:** `src/frontend/components/UI/NavShell/components/FilterRunnabilityFacet/index.tsx`
- **Verification:** `pnpm i18n` re-run -- `gamelib: Added keys: 7` with correct (non-empty) default text for all four runnability keys, confirmed via `git diff public/locales/en/gamelib.json`; `pnpm lint-translations:gamelib` exits 0; `npx tsc --noEmit` clean; `pnpm jest src/frontend/components/UI/NavShell` green.
- **Committed in:** `680e1a1d4` (Task 3 commit -- caught and fixed before that commit)

**2. [Rule 1 - Bug] The dev-only drift guard's own literal-text object tripped the hardcoded-string gate**
- **Found during:** The plan's overall `pnpm test:ci` verification step (not caught by the scoped `pnpm jest src/frontend/components/UI/NavShell` run from Task 3, since `meta/__tests__/hardcodedStringGate.test.ts` lives outside that scope)
- **Issue:** The first version of the dev-only drift guard (added for Deviation 1) declared a plain `Record<RunnabilityTier, string>` object literal duplicating the four English strings, so it could compare them against `RUNNABILITY_LABELS`. Once `FilterRunnabilityFacet/index.tsx` entered `meta/i18nGateScope.json`'s scan scope (via this same plan's Task 3), `meta/hardcodedStringGate.ts` correctly flagged those four object-property string values as untranslated literals -- `meta/__tests__/hardcodedStringGate.test.ts` failed with `Received length: 4`.
- **Fix:** Replaced the duplicated literal-text object with an `echoDefaultValue` stand-in function that is passed into `runnabilityLabel` in place of the real `tGamelib`, so the dev-only check reads each call site's own literal `defaultValue` argument straight out of the switch instead of re-declaring the text a second time anywhere in the file.
- **Files modified:** `src/frontend/components/UI/NavShell/components/FilterRunnabilityFacet/index.tsx`
- **Verification:** `pnpm jest meta/__tests__/hardcodedStringGate.test.ts --silent` -- 124/124 pass; full `pnpm test:ci` -- 229/229 suites, 4384/4384 tests pass.
- **Committed in:** `643ea0959` (follow-up fix commit, after Task 3's own commit -- the full-suite run that caught it happens after all three tasks are committed, per the plan's own verification block)
