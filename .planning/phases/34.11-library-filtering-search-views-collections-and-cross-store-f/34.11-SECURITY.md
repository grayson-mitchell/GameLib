# Phase 34.11 — Security

> Per-phase security contract: threat register, accepted risks, and audit trail.

**Register origin:** authored at plan time. All 9 of this phase's PLAN.md files carry a
`<threat_model>` block, so this audit ran in **verify-mitigations** mode — it confirms the
registered controls exist in the implementation, and did **not** retroactively scan for
unregistered threats.

`-15/-16/-18/-19/-20/-21/-22` in 2 each.

## Audit Notes

### 1. T-34.11-02 — OPEN: the boundary half of a two-part mitigation is absent at HEAD

The mitigation reads: *"the engine never reads `localStorage` itself; `nonAvailableAppNames` is
passed in as an already-parsed array by the caller, so a malformed `nonAvailableGames` value is
handled once at the boundary."*

The engine half is **true and verified**. The boundary half is **not**: at HEAD,
`engineWiring.ts`'s `buildEngineDeps` parses with a bare `JSON.parse(inputs.nonAvailableGamesRaw || '[]')`
and no `try/catch`. A malformed value throws out of `buildEngineDeps`, out of the `engineDeps`
`useMemo`, and takes the whole Library screen down — for a `localStorage` string the app rewrites
on its own. The pre-fix code said so in a comment, deferring to review finding **WR-02**.

**A fix exists but is uncommitted.** The working tree adds `parseNonAvailableAppNames()`, which
degrades to `[]` on absent, malformed, and non-array input, and rejects a parsed non-array value
(`"5"`, `{}`) that would otherwise reach `filterEngine` without `.includes`. That is the correct
control. It is not in any commit, so this audit cannot record it as shipped.

⚠ **Cross-phase attribution risk:** the new comment attributes the change to *"08.1 review WR-04"*,
not to 34.11's WR-02 or to `T-34.11-02`. When it lands, this threat's closure will be recorded
under a different phase's finding ID and the link back here will not exist. Add the 34.11 WR-02 /
`T-34.11-02` reference to that comment before committing.

**CLOSED 2026-08-25, commit `598f71aac`.** The fix landed with the cross-reference added at both
comment sites (`08.1 review WR-04 = 34.11 review WR-02 = threat T-34.11-02's boundary half`), so
the link back to this register survives the phase boundary.

One correction landed with it. The new test's docblock claimed *"every case below throws or returns
a non-array against the previous implementation"*. Measured against
`JSON.parse(raw || '[]')` rather than assumed, **six of its seven cases go red; `''` does not** —
`'' || '[]'` short-circuits to `'[]'`, so the old expression already returned `[]` for it. The case
is kept as a behavioural pin and is now explicitly **not** counted as a red-proof. Overstating a
gate's power is the failure mode `T-34.11-26` and `F-34.10-08` both exist to prevent, so shipping
the claim as written would have contradicted this phase's own register.

### 2. T-34.11-12 — OPEN: the mitigation asserts a parity the code does not have

The mitigation reads: *"Derived from the same `gog.username` / `epic.username` /
`amazon.username` / `steam?.username` gates `makeLibrary()` already uses, so the panel cannot
advertise a store the user is not signed into."*

`connectedStores` (`Library/index.tsx:295-307`) gates Amazon on **`amazon.username`**.
`makeLibrary` (`:633`) gates it on **`amazon.user_id`**. The claimed parity does not hold for
Amazon, and the in-code comment asserting it is wrong.

Consequence, in the threat's own terms: when `amazon.username` is truthy and `amazon.user_id` is
not, the Store group renders an Amazon row while the grid contains no Amazon games — a
**permanently-`0` row**, which is precisely the outcome `T-34.11-12` and `T-34.11-19` were both
written to prevent. Independently raised as review finding **WR-03** on 2026-08-10 and confirmed
still present in `34.11-VERIFICATION.md`'s own warning table.

This is a *declared control that was never implemented*, not a newly discovered threat — the same
class as Phase 34.4's secure-phase run, where two declared mitigations did not exist.

**To close:** align the two gates on one field (or document why they must differ), then re-run.
Choosing which field is correct is a behavioural decision and deliberately not made here.

### 3. Out of register, recorded not closed — three unguarded legacy parses survive

`T-34.11-01`'s rationale states *"No input path throws, so a corrupted key cannot crash the
Library screen."* That is true of the two `migrate*` helpers it names. It is **not** true of the
screen: `Library/index.tsx:134`, `:161` and `:190` still parse `storesFilters`,
`platformsFilters` and `crossoverRatingFilters` with bare `JSON.parse`.

The exposure is narrow but real: the `facetOptInMigrated` effect removes those keys, but it runs
**after** the initialisers on the first mount following upgrade, so one corrupt legacy value can
throw on that render. The whole block is dead code that review finding **WR-04** says should have
been deleted when plan 09 landed — its own comment reads *"deletable once plan 09 lands"*, and
plan 09 has landed.

Not counted in `threats_open` (no register ID covers it, and this audit runs in verify-mitigations
mode, not retroactive-STRIDE). Recorded so it is not rediscovered as novel.
