# Phase 34.11 Plan 04: Filter State Model Summary

**Added the full opt-in facet state model (view/store/runnability/collection) to `Library` and exposed it through `LibraryContext` -- including the active filter DESCRIPTOR LIST plan 08 needs and a detectable outside-the-provider sentinel -- with zero change to what the grid currently shows.**

## Performance

- **Duration:** ~20 min
- **Tasks:** 3 completed
- **Files modified:** 4 (1 created, 3 modified)

## Accomplishments
- `LibraryContextType` now carries the complete opt-in facet surface (`libraryView`, `storeFacet`, `runnabilityFacet`, `currentCollection`, `clearAllFilters`, `activeFilterDescriptors`, `activeFilterCount`, `runnabilityRows`, `connectedStores`, `countForStore`, `countForRunnability`) alongside every legacy field, which stays untouched until plan 09.
- `initialContext` supplies a default for every new field plus `__isDefaultLibraryContext: true` -- the sentinel that lets a consumer distinguish "mounted, nothing selected" from "rendered outside the provider," the exact ambiguity that let 34.10 ship a relocated `<Header>` whose filters looked alive and did nothing.
- `facetLabels.ts` is now the one declaration site for `RunnerToStore` and `RUNNABILITY_LABELS`, so plan 07's facet rows and plan 08's chip row can never disagree on label text. It deliberately is not registered in `meta/i18nGateScope.json`.
- `Library/index.tsx` declares four new persisted filter states following the shipped read-once-initialiser + write-through-wrapper pattern, with `storeFacet`/`runnabilityFacet` initialising through plan 01's D-02 migration helpers (which discard, never translate, a legacy opt-out shape).
- A one-shot, sentinel-guarded effect discards the legacy `storesFilters`/`platformsFilters`/`crossoverRatingFilters` keys exactly once, resolving RESEARCH assumption A1 in favour of active removal without racing `LibraryFilters` (still mounted and still writing those keys until plan 09).
- `FilterEngineState`/`FilterEngineDeps` are assembled once per render in two `useMemo`s and reused by both the exclude-your-own-facet counts (`countForStore`/`countForRunnability`, built on `filterEngine.countFor`) and the single `describeActiveFilters` call that produces both `activeFilterDescriptors` and `activeFilterCount` (`.length` of the same array -- never a second independent computation).
- `clearAllFilters` resets and persists every filter to its default (D-25) -- `filterText` is the sole session-only exception, with no `localStorage` key.
- Behaviour is unchanged: `gamesForAlphabetFilter` still drives the grid through the legacy pipeline. `tsc --noEmit`, the Library jest suite, and the full `pnpm test:ci` (222/222 suites, 4317/4317 tests) all pass.

## Decisions Made
- Switched `filterEngine.ts` imports to a namespace import (`import * as filterEngine from './filterEngine'`) so every helper call site is the identifier's only appearance in the file -- several of this plan's own acceptance criteria assert an exact grep count of 1 for a bare function name (no trailing paren), which a named import would fail by also matching the import line.
- `engineState.searchMatchedKeys` is `null` this plan rather than wired to the existing Fuse results -- the plan is explicit that no task here touches the grid pipeline, and computing a parallel fuzzy-match set would have duplicated `Fuse` logic that plan 05 owns.
- `countForStore`/`countForRunnability` compute against `gamesForAlphabetFilter` (the existing combined, legacy-filtered library) rather than a freshly-derived raw library array, since assembling an unfiltered cross-runner library is explicitly plan 05's rewiring responsibility.
