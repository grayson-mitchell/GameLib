# Phase 34.11: Library filtering — search, views, collections and cross-store facets - Context

**Gathered:** 2026-08-09
**Status:** Ready for planning

<domain>
## Phase Boundary

Build the Games tier-2 panel for real, as sketch `004` **variant C (hybrid)**.

The tier-2 slot already exists and is already filled: `Library/index.tsx:819` portals
`<Header />` into `GamesPanel`'s registered DOM node via `Tier2PortalContext`. This phase
**replaces the contents of that portalled header** with the real filter panel, and adds the parts
that do not exist yet — a collections section, facet counts that exclude their own facet, and
removable filter chips above the grid.

**In scope:**
- Panel structure: search → views (single-select) → collections (single-select) → collapsed
  multi-select facets → collapsed "More" group.
- Inversion of store/platform facet semantics from opt-out to opt-in, with a one-time migration.
- A **runnability** facet replacing the literal platform facet, absorbing the Phase 19 CrossOver
  medal filter.
- Facet counts computed with the exclude-your-own-facet rule.
- Removable filter chips above the grid + `Clear all`.
- Zero-result state with an inline recovery action.
- Retirement of `components/UI/CategoryFilter` and `components/UI/LibraryFilters`.
- Two Critical findings carried forward from Phase 34.10 (CR-01, CR-02) — see D-31/D-32.

**Out of scope:**
- The genre facet (D-14 — dropped this phase, backlogged behind a metadata backfill).
- Rule-based / smart collections (D-19 — deferred).
- Any change to sort, layout, or the alphabet filter beyond leaving them where they are.
- Metadata pipeline work of any kind.

</domain>

<decisions>
## Implementation Decisions

### Filter semantics

- **D-01:** Store and runnability facets are **opt-in**, matching the sketch engine: an empty
  selection means no constraint; ticking `GOG` shows only GOG. This inverts today's shipped
  `storesFilters` / `platformsFilters`, which are opt-out masks defaulting to all-`true`.
- **D-02:** Migrate legacy `localStorage` values with a **one-time reset to empty**. Detect the
  legacy shape, discard it, start with no filters active. Mirrors the existing
  `migrateFilterMode()` helper in `Library/index.tsx:184` that handled the tri-state migration.
  Do **not** attempt to translate old values into an equivalent opt-in selection.
- **D-03:** Combination semantics are **AND across facet kinds, OR within a kind** —
  `(GOG OR Steam) AND (Runs natively)`. This confirms the sketch's convention, which it flagged as
  never validated with a user.
- **D-04:** A store facet row for an **unconnected account is hidden entirely**. Today
  `Library/index.tsx:478-493` gates each store on `gog.username`, `epic.username` etc.; that gate
  now decides whether the row renders at all, so no row ever sits at a permanent `0`.

### Panel structure and the existing filter inventory

- **D-05:** Views are **single-select**: `All games` · `Installed` · `Recently played` ·
  `Favourites`. Today `showInstalledOnly` and `showFavourites` are independent booleans that can
  combine; that combination becomes unexpressible and this is accepted. Combining is what the
  facets are for, and the fast-path/power-path split is what won variant C.
- **D-06:** The tri-state `showHidden` and `showNonAvailable` filters (Phase 08.1, LIB-09) keep
  their `off` / `show` / `only` semantics and move into **their own collapsed group** below the
  facets. Do not collapse them to booleans — that would regress shipped, verified behaviour.
- **D-07:** `showSupportOfflineOnly`, `showThirdPartyManagedOnly` and `showUpdatesOnly` join the
  same collapsed group as the tri-states.
- **D-08:** The alphabet filter, sort (`sortDescending` / `sortInstalled`) and grid-vs-list
  `layout` are **not filters** and stay out of the panel, in the grid header near the chip row.
  The panel answers "which games"; those answer "how shown". Sketch 004 has no sort or layout
  control in the panel.

### Platform → runnability

- **D-09:** The platform facet becomes a **runnability** facet — "will this run on my machine",
  not "is this a native build". Derived from `is_mac_native`, `mac_arch` and the CrossOver rating.
  This is the sketch's explicit recommendation and the reason it matters on this fork: GameLib
  runs Windows games on macOS through Wine/CrossOver bottles.
- **D-10:** The shipped macOS CrossOver-rating filter (`crossoverRatingFilters`, Phase 19 D-17,
  gold/silver/bronze/wontRun/unrated) is **absorbed into the runnability facet**. The medal tiers
  become the evidence behind the facet rows rather than a user-facing control. The per-game
  `CrossoverBadge` on the game card is unaffected and stays.
- **D-11:** A macOS build that is 32-bit only (`mac_arch: '32'`, which GPTK aborts and Phase 18
  routes to a CrossOver/Wine bottle) counts as **playable via bottle** — grouped with the
  bottle-run row, not with "won't run".
- **D-12:** On Windows and Linux hosts there is no CrossOver index (Phase 19 is macOS-only). The
  facet falls back to **native-vs-not** using whatever signal exists per host
  (`is_linux_native`, etc.) and **hides rows it cannot compute**. Do not render a row whose
  predicate has no data behind it.

  > **Extended 2026-08-09 at `/gsd-plan-phase` — Windows resolved.** Research confirmed by full
  > read of `src/common/types.ts` that `GameInfo` carries `is_mac_native`, `mac_arch` and
  > `is_linux_native` but **no Windows-native equivalent of any kind**. Every runnability row is
  > therefore uncomputable on a Windows host, so applying D-12's own rule to all rows means the
  > **entire Runnability group does not render on Windows** — no group header, no empty section,
  > and explicitly *not* a degenerate all-pass row (operator decision). The group renders on macOS
  > and Linux only. Extending the data model with a Windows-native signal was considered and ruled
  > out of scope for this phase.

### Genre

- **D-13:** Measured coverage, from the store managers — **GOG** (`gog/library.ts:1107`) and
  **Amazon** (`nile/library.ts:72,109`) populate genres at library sync; **Steam**
  (`steam/games.ts:536`) populates them only via the lazy per-game `appdetails` fetch (LIB-04);
  **Epic** populates none at all; **ZOOM** hardcodes `[]` (`zoom/library.ts:160`). Genres also
  live on `GameInfo.extra?.genres` (`ExtraInfo`), not on `GameInfo` directly, so they are not in
  the array the grid filters over.
- **D-14:** **The genre facet is dropped from this phase.** This applies the sketch's own rule:
  "dropping the genre facet is an acceptable outcome; shipping it half-populated is not."
- **D-15:** Genre is recorded as a **backlog item whose prerequisite is explicit** — per-store
  genre coverage must be real before the facet ships. Not dropped permanently, not promoted to
  its own phase now.
- **D-16:** **Nothing replaces genre's slot.** The panel ships with two facets (Store,
  Runnability) plus the collapsed "More" group. Do not invent a third facet to fill space.

### Collections

- **D-17:** **Reuse `customCategories` as-is** — same `configStore` key (`games.customCategories`),
  same add/remove/rename/removeCategory functions in `GlobalState.tsx:477-547`, same data.
  Existing user categories appear as panel collections on day one with zero migration.
- **D-18:** No rename pass. The user-facing terminology stays as it currently ships. **The panel's
  section header wording is Claude's discretion** (see below), but under a hard constraint: do
  **not** churn the existing `CategoriesManager` strings. Phase 34.8's localisation gate is
  blocking and a rename would touch every one of them.
- **D-19:** **Manual collections only** this phase. Rule-based / smart collections are recorded as
  a deferred idea. Sketch 004 explicitly left this out of scope, and a saved-filter feature should
  be designed as one rather than smuggled into a filter panel.
- **D-20:** `+ New collection` lives **in the panel**; rename, delete and bulk membership stay in
  the existing `CategoriesManager` dialog. Do not rebuild management UI inline.
- **D-21:** Collections are **single-select**, and the panel's collections list **replaces**
  `components/UI/CategoryFilter`. That component is retired, not left running alongside.

### Persistence and reset

- **D-22:** Search text is **session-only and cleared on tab switch**. A stale search box is the
  most confusing possible startup state. This preserves today's behaviour — `filterText` is
  `useState`-only at `Library/index.tsx:182`.
- **D-23:** All other filters **survive tab switches** within a session. Since 34.10 made Games a
  tab, leaving and returning is routine; a trip to Settings must not discard a filter setup.
- **D-24:** Filter state stays in **`localStorage`**, keeping existing keys wherever semantics are
  unchanged. Only the store and platform keys change, per D-02. Do not move to `configStore` —
  that adds an IPC round-trip per toggle for no current benefit.
- **D-25:** **`Clear all` clears and persists the cleared state.** Whatever the chip row shows is
  what comes back next launch. Persisted filters are not a preset that `Clear all` temporarily
  suspends.

### Chips, counts, empty state

- **D-26:** Chips render for **everything non-default, including views**. `All games` is the
  default and shows no chip; `Installed` does. Facet values, the collection, the search term and
  the "More" group filters all get one. This is what makes the chip row answer "why am I looking
  at 6 games instead of 214".
- **D-27:** A tri-state filter's chip uses a **plain-language label** ("Hidden only", "Including
  hidden"), and its `×` **returns the filter to `off`** rather than stepping down the cycle. A
  chip's `×` always means "remove this constraint", never "cycle it".
- **D-28:** **Counts render on facet options only** — not on views or collections. Counts guide
  the next click *within* a facet, which is what the exclude-your-own-facet rule serves. A view is
  a jump, not a refinement.
- **D-29:** Counts **recompute live** from whatever is currently loaded. They will move while a
  Steam library refresh runs, which is honest because the grid is moving too. Use
  `font-variant-numeric: tabular-nums` (already in the sketch CSS) so the count column does not
  jitter as digits change.
- **D-30:** The zero-result state carries an inline **`Clear all filters`** action **and names the
  filters responsible** — e.g. `No games match Installed + GOG + "witcher"`.

### Carried forward from Phase 34.10

- **D-31:** **CR-01** — `--navbar-active` is undefined in the scored `gruvbox_dark` theme. Fixed in
  this phase. It was deferred at 34.10 close only to keep HEAD matching the gated bundle; that
  reason has expired, and this phase must theme-test `gruvbox_dark` regardless.
- **D-32:** **CR-02** — `-webkit-app-region: drag` was never ported to the new navbar, breaking
  frameless window drag. Fixed in this phase.

### Search

- **D-33:** Search matches **title only** — do **not** extend to developer or publisher: publisher
  coverage across the four stores is inconsistent enough to reproduce the same half-populated
  problem that killed the genre facet. The title-only scope is IN SCOPE for this phase.

  > **Amended 2026-08-09 during `/gsd-plan-phase` — premise falsified.** This decision originally
  > read "substring, case-insensitive — the sketch's validated behaviour **and today's shipped
  > behaviour**." Phase research falsified the second half: `Library/index.tsx:601-616` runs
  > `Fuse.js` fuzzy matching at `threshold: 0.4`. Substring is *not* what ships today. The
  > substring/fuzzy half of this decision is **deferred** by operator decision (see Deferred
  > Ideas); only the title-only scope remains in scope here.
- **D-34:** Search **stays where it is — at the top of the panel.** `Header` (which contains
  `LibrarySearchBar`) is already portalled into the tier-2 slot by `Library/index.tsx:819`, so
  "where it is" and "what sketch 004 specifies" are the same place. This is **not** a deviation
  from the sketch. (Amended during discussion: an earlier option was worded as though the header
  sat above the grid; it does not.)
- **D-35 [informational — DEFERRED 2026-08-09]:** Do **not** use fuzzy matching. GameLib's existing
  85% fuzzy matcher for Humble/Steam dedup needed a user-override escape hatch for its false
  positives — evidence that fuzzy in this codebase brings its own problems.

  > **Deferred by operator decision at `/gsd-plan-phase 34.11`.** Research found `Fuse.js` fuzzy
  > search live in `Library/index.tsx:601-616` (`threshold: 0.4`) — removing it was ruled out of
  > scope for this phase. No plan implements this decision; it is tagged informational so the
  > decision-coverage gate does not block. Search ships this phase with its **existing fuzzy
  > behaviour unchanged**. See Deferred Ideas.

### Claude's Discretion

- The panel's collections section header wording, subject to D-18's no-rename constraint.
- Exact row labels for the runnability facet ("Runs natively" / "Runs via bottle" / "Won't run" is
  indicative, not binding).
- Whether the "More" group has one header or is split into two collapsed groups.
- Panel scroll bounding — the sketch's `max-height: 620px` is explicitly called out as a sketch
  artifact ("real app: bound to viewport, not a magic number").

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets

- **`Tier2PortalContext` + `GamesPanel`** — the tier-2 slot is already built and already filled.
  `GamesPanel` renders `<div className="NavShell__tier2Portal" ref={setTarget} />` and nothing
  else; `Library` portals `<Header />` into it and calls `setFilled(true)` on mount
  (`index.tsx:761`). This phase changes *what* is portalled, not the portal.
- **`customCategories`** (`GlobalState.tsx:133,304,477-547`) — manual collections, already
  persisted to `configStore` at `games.customCategories`, with add/remove/rename/removeCategory
  and a working `CategoriesManager` dialog. D-17 reuses this wholesale.
- **`crossoverRatings: Record<string, number | null>`** (`GlobalStateV2.ts:46,93`) — the Phase 19
  CrossOver Compatibility Index in frontend state. The data behind D-09's runnability facet.
- **`migrateFilterMode()`** (`Library/index.tsx:184`) — an existing, shipped precedent for a
  one-time `localStorage` shape migration. D-02 should follow its shape.
- **The sketch's filter engine and CSS** — `library-filtering.md` carries the whole `filtered()`
  function with the `skip` parameter, plus panel/facet-row/chip/collapsible CSS with real token
  names. It is copy-adaptable, not just illustrative.

### Established Patterns

- **Filter state is renderer-local and `localStorage`-persisted**, read once into `useState`
  initialisers and written through a `handleX` wrapper that does `storage.setItem` then
  `setState`. Nine filters follow this exactly. D-24 keeps it.
- **Multi-select filters use spread-and-flip** (`{ ...filters, [key]: !current }`), tri-states use
  an explicit cycle function. `LibraryFilters/index.tsx` shows both, and D-17 of Phase 19 records
  that a rating filter deliberately took the multi-select shape rather than the tri-state one.
- **Store gating pairs the filter flag with a login check** — `storesFilters['gog'] && gog.username`.
  D-04 turns that pairing into a render decision.
- **Localisation is a blocking gate** (Phase 34.8). Every new user-facing string needs a key; the
  `gamelib:` namespace prefix breaks the tuple idiom — see `LibraryFilters/index.tsx`'s
  `tGamelib` usage for the shipped pattern. A green jest run does not mean the gate is satisfied.

### Integration Points

- **`components/UI/Header/index.tsx`** — currently `LibrarySearchBar` + `CategoryFilter` +
  `LibraryFilters`. This is the component the new panel replaces. `CategoryFilter` and
  `LibraryFilters` are retired (D-21); `LibrarySearchBar` stays (D-34).
- **`LibraryContext`** — the panel reads and writes every filter through this context. Adding
  opt-in facet state and removing `crossoverRatingFilters` as a user-facing control both land here
  and in `frontend/types.ts`.
- **The chip row** is new surface above the grid, between the grid header (sort/layout/alphabet
  per D-08) and the cards.
- **`GamesList/index.tsx`** — carries a `document.body.scrollTo()` that 34.10's scroll-container
  relocation already made a silent no-op. Anything touching grid scroll should check it.

<specifics>
## Specific Ideas

- The chip row is called out in the sketch as **"the most portable idea in the sketch"** — it is
  what makes the filter state legible without re-reading the panel. Treat it as load-bearing, not
  decoration.
- `font-variant-numeric: tabular-nums` on the count column, explicitly, so numbers do not jitter
  during a live refresh (D-29).
- Chip hover previews **removal** in the danger colour; `Clear all` is dashed to read as a
  different kind of action. Both are in the sketch CSS.
- `.item.zero { opacity: .38 }` exists in the sketch for zero-count-and-unselected rows — still
  useful for facet values that genuinely reach 0 under other active filters, even though D-04
  removes the unconnected-store case.
- **Do not let the grid container omit `min-width: 0`** — a flex child with grid content overflows
  the panel without it. Called out explicitly in the sketch's "What to Avoid".

</specifics>

<deferred>
## Deferred Ideas

- **Genre facet** — deferred with an explicit prerequisite: real per-store genre coverage. Today
  Epic contributes none and Steam only contributes for games the user has already opened. Would
  require a background metadata backfill, which is a metadata-pipeline feature, not a UI one.
  (D-14, D-15)
- **Rule-based / smart collections** — saved facet states like "all GOG games", or membership
  rules that evaluate continuously. Should be designed as its own feature rather than folded into
  a filter panel. (D-19)
- **An "Install state" facet** (Installed / Not installed / Update available / Downloading) —
  raised as a candidate to fill the slot genre vacated, and rejected for this phase per D-16. All
  the data exists on `GameInfo.install`, so it remains a cheap future addition.
- **Combining views** — e.g. "installed favourites". Made unexpressible by D-05's single-select
  views. If it turns out to be a real need, the fix is promoting Favourites to a facet, not making
  views multi-select.
- **Gamepad focus-scroll in the tier-2 panel** — Phase 34.10's verification records this sub-check
  as never measured across any of its four gate runs. The panel becomes considerably taller and
  scrollable in this phase, so it is worth measuring here.
- **Replacing `Fuse.js` fuzzy search with plain substring matching** — deferred by operator
  decision at `/gsd-plan-phase 34.11` (2026-08-09). Research found fuzzy matching live in
  `Library/index.tsx:601-616` at `threshold: 0.4`, contradicting D-33/D-35. Ripping it out was
  ruled out of scope for this phase; **search ships with its existing fuzzy behaviour unchanged**.
  Two consequences the executor and verifier must not treat as defects: (a) search results will
  include near-misses that a substring matcher would exclude, and (b) **facet counts are computed
  over the fuzzy-matched set**, so a count can include a title the user would not consider a match.
  Re-opening this means removing the `Fuse.js` call site and its `threshold` config — the decision
  text is already written in D-33/D-35, so no re-litigation is needed. (D-33, D-35)
