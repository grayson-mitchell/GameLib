<objective>
Build the two grid-area surfaces that answer "why am I looking at 6 games instead of 214": the
`FilterChipRow` above the grid, and the zero-result empty state that names the filters responsible.

Purpose: waves 1-3 make the panel able to *set* filters. Nothing yet makes an active filter
**visible or removable from the grid**, and today a fully-filtered-out library falls through to
`EmptyLibraryMessage`, which is written for "you own no games" and says nothing about filters. Both
gaps are user-facing dead ends. This plan closes them, and is the only place in the phase where D-08
(sort/layout/alphabet are not filters) and D-30 (the empty state names names) are decided.

Output: a pure label resolver shared by both surfaces, the chip row, the zero-result state, their
mount points in `Library/index.tsx`, and the Wave 0 test file `34.11-VALIDATION.md` requires.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| `configStore` (`games.customCategories`) → i18n interpolation → rendered copy | Collection names are user-authored free text. This plan is the first place in the phase where such a name is fed into a translated **sentence** as an interpolation value (`{{filters}}`, `{{filterLabel}}`) rather than rendered as its own isolated label. |
| Search input → i18n interpolation → rendered copy | The raw `filterText` the user typed is quoted into the same two interpolation slots. Same class of value as above, arriving from a keystroke rather than from persisted state. |
| `localStorage` → plan 04 state → descriptors → this plan's render | A locally-tampered filter key can produce a descriptor with an unexpected `value`. This plan renders descriptors without re-validating them. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-34.11-18 | Tampering | `{{filters}}` / `{{filterLabel}}` interpolation of user-controlled strings | mitigate | Be precise about what i18next does and does not protect. react-i18next runs with `interpolation.escapeValue: false` (React escapes text children itself), so **i18next is not the control here — React is**. Both interpolated results are rendered as plain React text children of a `<p>` and as an `aria-label` string attribute. Neither goes through `Trans`, markup parsing, or `dangerouslySetInnerHTML`, which is what the Task 3 source gate pins. Under those two conditions a hostile name is inert markup-wise. |
| T-34.11-19 | Tampering | i18next **nesting** (`$t(...)`) reaching the interpolation slot | mitigate | i18next resolves `$t(...)` nesting against the **template**, not against interpolated values, and `interpolation.skipOnVariables` defaults to `true` in the version in this tree — so a collection named `Backlog $t(header.uncategorized)` should render literally rather than resolving another key. That is a claim, not a guarantee, and it depends on config this plan does not own, so it is pinned by a behavioural test rather than by prose: two hostile-name cases (`$t(...)` and a literal `{{filters}}` token inside a collection name) assert the run survives verbatim. If either fails, the fix is to set `skipOnVariables: true` explicitly in the i18n init and re-run — not to sanitise the name, which would corrupt a legitimate collection title. |
| T-34.11-20 | Information disclosure | the zero-result sentence and the chip labels | accept | Everything named is data the app persisted for this same local user, or text they just typed, displayed back to them in their own window. There is no cross-user, cross-account, log or network sink in this plan. Naming the filters is the explicit product requirement (D-30); withholding them would be the defect. |
| T-34.11-21 | Denial of service | a pathologically long collection name or search term | accept | The chip row is `flex-wrap: wrap` and the empty-state body has `line-height: 1.4` precisely because it wraps, so a long value degrades to more rows rather than to overflow. The value is self-inflicted — the user typed it or named the collection — and no truncation is specified by the UI-SPEC. Inventing an ellipsis rule here would add an unreviewed visual contract, and truncating the filter list would directly undercut D-30's "name the filters responsible". |
| T-34.11-22 | Tampering | a tampered `localStorage` filter value producing an unmapped descriptor | mitigate | `chipLabelSpec` returns `null` — never a fabricated or raw-value label — for any kind/value pair this phase does not define, and the chip row drops `null` specs without throwing. A tampered value therefore renders no chip instead of rendering attacker-chosen text into the UI. Validation of the value itself stays at plan 04's initialisers, the one place that owns it. |
| T-34.11-SC | Tampering | npm/pnpm/cargo installs | mitigate | **No packages are installed by this plan.** Every import already exists in the tree (`react`, `react-i18next`). If an install appears necessary, STOP — it is out of scope and requires a blocking human legitimacy checkpoint against `RESEARCH.md`'s package audit. |
