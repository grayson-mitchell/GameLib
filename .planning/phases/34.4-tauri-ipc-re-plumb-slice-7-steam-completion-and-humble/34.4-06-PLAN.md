<objective>
Harden `electronStub.net.request` so it fails fast and legibly instead of being a silent dead end
(D-06).

Purpose, stated precisely because an earlier reading of this got it wrong: `net.request()` today
(`electronStub.ts:592`) returns `{ on, end, write, setHeader }` where `on()` is a total no-op — a
listener registered against it never fires. Its only backend caller is `humblePostRequest`
(`humble/adapter.ts:264-336`), which backs the deferred `humbleRevealKey` channel. That call does
**not** hang forever: `humblePostRequest` arms its own `REQUEST_TIMEOUT_MS` timer (L277-287) and
rejects after it. The actual defect is the **cause it reports** — `"Humble reveal request timed
out"` — which reads as a Humble outage rather than a missing seam, and would send Phase 34.4.1's
owner straight back into the Cloudflare investigation that six rounds of the
`humble-reveal-key-fails` debug session already falsified.

The fix is one function, and its shape is constrained by a real past incident. It must **not** throw
or reject synchronously inside `request()` — that would fire before the caller has had a chance to
register `request.on('error', ...)`, and `sidecar-dialog-reject-crashes` records what an unguarded
fire-and-forget rejection does to this sidecar. Instead, emit an asynchronous `'error'` event naming
the missing seam. `humblePostRequest` already has `request.on('error', ...)` wired and ready
(`adapter.ts:~328`, which clears the timeout and rejects) — it has simply never fired.

This is `electronStub.session`'s own stated rationale ("fails loudly with a clear log line instead of
an opaque TypeError") applied to its immediate neighbour in the same file.

Output: a legible stub, and a test that proves the error reaches `humblePostRequest`'s handler — not
merely that the stub emits something.
</objective>

   a rejecting promise. `sidecar-dialog-reject-crashes` is the recorded incident:
   an unguarded fire-and-forget `await` of a rejecting stub hard-crashes the sidecar.
3. **Optional invocation.** A caller that registers no `'error'` handler must be unaffected — the
   scheduled callback must not throw on a missing handler.
