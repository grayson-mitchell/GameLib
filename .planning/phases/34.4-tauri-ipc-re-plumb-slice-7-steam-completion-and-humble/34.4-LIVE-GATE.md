### Deviation: broken bare `preload/tauriTransport` import in `WebView/index.tsx`, found and fixed in Task 1 (Rule 1 — commit `9f9f0402c`)

The **first** `npm start` run surfaced a real build-time error in the Electron renderer's Vite
dev server:

```
11:52:51 AM [vite] Internal server error: Failed to resolve import "preload/tauriTransport"
from "src/frontend/screens/WebView/index.tsx". Does the file exist?
```

**Root cause (confirmed, not guessed):** plan 34.4-07 (D-04) added
`import { isTauri } from 'preload/tauriTransport'` to `WebView/index.tsx`. This is a **bare**
module specifier. `electron.vite.config.ts`'s renderer `resolve.alias` (`srcAliases`) only maps
`backend`, `frontend` and `common` to their `src/*` directories — there is **no** `preload`
alias — so Vite's bundler could not resolve it. Every other frontend caller of
`tauriTransport` (`src/frontend/index.tsx`, `src/frontend/state/GlobalState.tsx`) uses a
**relative** import instead (`'../preload/tauriTransport'`, `'../../preload/tauriTransport'`).

**Why `tsc --noEmit` did not catch this:** `tsconfig.json` sets `baseUrl: "./src/"`, which lets
TypeScript's own module resolution treat `preload/tauriTransport` as `src/preload/tauriTransport`
structurally — a resolution rule Vite's `resolve.alias` config does not share. `tsc` and Vite
diverged on the exact same bare specifier; `tsc --noEmit` passing clean on this branch (before
and after the fix) was never sufficient evidence the Electron build worked, which is exactly why
this task's own REQ-34.4-15 `npm start` behavioral check exists as a separate row rather than
being inferred from `tsc`.

**Fix applied:** changed the import to `'../../../preload/tauriTransport'` (the correct relative
depth from `src/frontend/screens/WebView/index.tsx`, matching the pattern every sibling caller
already uses), rather than adding a new Vite alias mid-slice — the smaller, most parity-safe fix.

**Verification after the fix:** `tsc --noEmit` clean; `WebView`-scoped frontend jest 13/13; full
frontend jest 27/27 (213/213 tests); `prettier --check` on the changed file clean; a second
`npm start` run shows the import-resolution error gone entirely, with the library still
rendering identically (377 Steam games, Humble 26/26 keys, Download Queue started). Only the
pre-existing, unrelated `getCrossoverIndex` startup-race error remained.

**File modified:** `src/frontend/screens/WebView/index.tsx` (1 line). **Commit:** `9f9f0402c`.

This is exactly the class of defect this phase's own live-gate discipline exists to catch before
spending human gate time: a real Tauri/Electron-parity-relevant regression in the one file D-04
added, invisible to `tsc` and to every jest suite (none of which run a real bundler), caught only
by actually launching the app.

## Why there is no packaged-build item (D-10)

**Deliberate, not an oversight.** Unlike Phase 34.3's D-12 — which required a packaged-build gate
item because `main.rs` spawns a *different* sidecar binary in dev vs. packaged mode, and
`app.restart()` re-execs a different binary in each mode, making "which child process gets
killed" a build-mode-dependent question — **nothing in this slice's five gate items depends on
the dev-vs-packaged sidecar spawn path.** All five items are login, sign-out, data reads and a
status check:

1. Credential + SteamGuard login reaching a populated library.
2. `logoutSteam` actually signing out.
3. `getSteamUserInfo`/`getSteamSyncedAt` returning real data.
4. `humbleSync`/`humbleGetKeys` returning a real key list.
5. `steamBottleStatus`/`isSteamBottleProvisioned` reporting truthfully.

None of these five behaviors differ structurally between a dev sidecar process and a packaged
one — the sidecar binary identity, not its content or behavior, is what 34.3's D-12 item existed
to prove. The one part of this slice's surface that genuinely *does* behave differently when the
app is code-signed — the Phase 28 keyring seam the credential-login path writes the refresh
token through — is **already exercised** by the previously-ported QR login flow (34.3's live
gate did not need to re-prove it either, for the same reason). A full package-and-sign cycle
per gate re-run (`electron-vite build && pnpm build:sidecar-sea && npx tauri build`, ~5+ minutes
per 34.3's own record) is expensive and would buy nothing here.

Since 34.3's D-12 and the `publicdir-getapppath-chunking` family of gotchas have made a packaged
item the *default* expectation for this project's live gates, this rationale is recorded
explicitly here (D-10) so the omission reads as a scoped decision, not a gap.

### Incidental finding: the surviving `refreshToken` is correct, and retires a standing risk

`steam_store/config.json` still holds a 677-char `refreshToken` after sign-out. This is **not** a
leaked credential:

- It is `steam:v1:`-prefixed, i.e. **encrypted via `safeStorage`** (`tokenStore.ts`'s `encryptToken`),
  not plaintext.
- It belongs to the **Electron** build's store. `ElectronTokenStore` is the only code permitted to
  touch `configStore[TOKEN_STORE_KEY]`; under Tauri the active store is the keyring-backed
  implementation from plan 28-04, whose contract (`tokenStore.ts` interface notes (b), REQ-28-03 /
  D-02, "no migration bridge") states it **MUST NEVER** import `configStore` or `TOKEN_STORE_KEY`.
  So `logout()`'s `await getTokenStore().clearToken()` (`user.ts:276`) cleared the **Keychain** entry
  and correctly left Electron's separate store untouched.

**This retires a latent risk recorded in the v0.8 partial audit.** That audit flagged
`tokenStore.ts`'s module-level default `activeTokenStore = new ElectronTokenStore()` as guarded only
by sidecar bootstrap call ordering. Had that risk fired — the Electron store still active inside the
sidecar — `clearToken()` would have deleted `refreshToken` from this file. It did not. The keyring
store was therefore correctly installed by the sidecar bootstrap before any token access.

Consequence worth noting for future testers: signing out under Tauri does **not** sign you out under
Electron. Two builds, two credential stores, deliberately unbridged.

## Item 5 — bottle status reports truthfully on macOS (REQ-34.4-03)

**Build:** `tauri:dev`
**Result:** **PASS (port fidelity)** — with a pre-existing Electron defect found and logged below.
**Evidence:** Both invokes driven from the `tauri:dev` web inspector:

```js
await window.api.steamBottleStatus()
// → { bottleName: "GameLibSteam", provisioned: false }

await window.api.isSteamBottleProvisioned()
// → true
```

**The two channels contradict each other.** On-disk ground truth, checked directly:
`~/Library/Application Support/CrossOver/Bottles/GameLibSteam/cxbottle.conf` **exists** — and that
exact file is what `isBottleProvisioned()` tests (`bottle.ts:199`,
`existsSync(join(getBottleDir(name), 'cxbottle.conf'))`).

- `isSteamBottleProvisioned() → true` — **matches reality.**
- `steamBottleStatus().provisioned → false` — **does not.** It never consults the filesystem; it
  reads `steamBottleConfigStore.get_nodefault('provisioned') ?? false`, and that flag is unset.
  `provisioned` is only ever written by `provisionBottle()`'s own paths (`bottle.ts:264`, `:671`,
  `:823`), so a bottle that exists on disk while the flag is absent/false is reachable — e.g. via
  `:671`'s `set('provisioned', false)` on a failure or teardown path.
- `bottleName: "GameLibSteam"` — matches the real bottle directory name.

### Why this is a PASS for this gate, not a port failure

The sidecar handler (`steamAuthFlowRegistration.ts:234-241`) is a byte-faithful reproduction of
`main.ts:948-953` — same store, same key, same `?? false` fallback, same `bottleName` fallback
chain. Plan 34.4-02 deliberately reproduced the store read rather than re-deriving it from
`isBottleProvisioned()`, on the explicit grounds that diverging would be a behavior change rather
than a port. That call was correct — and it faithfully carried an **inherited Electron defect**
across the seam. The port did its job; the underlying logic is what disagrees with itself.

This gate item asks whether the ported channels report what Electron reports. They do. Fixing the
store-vs-filesystem split is Electron-side work outside this slice's scope.

### Carried defect (new, pre-existing, not introduced here)

`steamBottleStatus.provisioned` and `isSteamBottleProvisioned()` answer the same question from two
different sources of truth — a persisted store flag vs. a live filesystem check — and can disagree
indefinitely, as they do on this machine today. Any UI branching on `steamBottleStatus.provisioned`
will believe an unprovisioned bottle exists where one is actually present. Candidate for the same
follow-up phase as the other carried items (`electronStub` `request.abort()`, the six deferred
Humble channels).

_Advisory, unrelated: GPTK/Wine engine selection producing a broken bottle remains a known
Electron-side defect, out of scope here and not observed during this gate._

**Observed at:** 2026-07-27
**Outstanding:** Electron parity spot-check — run the same two calls under `npm start` to confirm
Electron returns the identical contradictory pair. The implementations are byte-identical, so this
is confirmatory rather than exploratory.
