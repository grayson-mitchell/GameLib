### Deviation: broken bare `preload/tauriTransport` import in `WebView/index.tsx`, found and fixed in Task 1 (Rule 1 — commit `9f9f0402c`)

The **first** `npm start` run surfaced a real build-time error in the Electron renderer's Vite
dev server:

```
11:52:51 AM [vite] Internal server error: Failed to resolve import "preload/tauriTransport"
from "src/frontend/screens/WebView/index.tsx". Does the file exist?
```

**Root cause (confirmed, not guessed):** plan 34.4-07 (D-04) added
`import { isTauri } from 'preload/tauriTransport'` to `WebView/index.tsx`. This is a **bare**
module specifier. `electron.vite.config.ts`'s renderer `resolve.alias` (`srcAliases`) only maps
`backend`, `frontend` and `common` to their `src/*` directories — there is **no** `preload`
alias — so Vite's bundler could not resolve it. Every other frontend caller of
`tauriTransport` (`src/frontend/index.tsx`, `src/frontend/state/GlobalState.tsx`) uses a
**relative** import instead (`'../preload/tauriTransport'`, `'../../preload/tauriTransport'`).

**Why `tsc --noEmit` did not catch this:** `tsconfig.json` sets `baseUrl: "./src/"`, which lets
TypeScript's own module resolution treat `preload/tauriTransport` as `src/preload/tauriTransport`
structurally — a resolution rule Vite's `resolve.alias` config does not share. `tsc` and Vite
diverged on the exact same bare specifier; `tsc --noEmit` passing clean on this branch (before
and after the fix) was never sufficient evidence the Electron build worked, which is exactly why
this task's own REQ-34.4-15 `npm start` behavioral check exists as a separate row rather than
being inferred from `tsc`.

**Fix applied:** changed the import to `'../../../preload/tauriTransport'` (the correct relative
depth from `src/frontend/screens/WebView/index.tsx`, matching the pattern every sibling caller
already uses), rather than adding a new Vite alias mid-slice — the smaller, most parity-safe fix.

**Verification after the fix:** `tsc --noEmit` clean; `WebView`-scoped frontend jest 13/13; full
frontend jest 27/27 (213/213 tests); `prettier --check` on the changed file clean; a second
`npm start` run shows the import-resolution error gone entirely, with the library still
rendering identically (377 Steam games, Humble 26/26 keys, Download Queue started). Only the
pre-existing, unrelated `getCrossoverIndex` startup-race error remained.

**File modified:** `src/frontend/screens/WebView/index.tsx` (1 line). **Commit:** `9f9f0402c`.

This is exactly the class of defect this phase's own live-gate discipline exists to catch before
spending human gate time: a real Tauri/Electron-parity-relevant regression in the one file D-04
added, invisible to `tsc` and to every jest suite (none of which run a real bundler), caught only
by actually launching the app.

## Why there is no packaged-build item (D-10)

**Deliberate, not an oversight.** Unlike Phase 34.3's D-12 — which required a packaged-build gate
item because `main.rs` spawns a *different* sidecar binary in dev vs. packaged mode, and
`app.restart()` re-execs a different binary in each mode, making "which child process gets
killed" a build-mode-dependent question — **nothing in this slice's five gate items depends on
the dev-vs-packaged sidecar spawn path.** All five items are login, sign-out, data reads and a
status check:

1. Credential + SteamGuard login reaching a populated library.
2. `logoutSteam` actually signing out.
3. `getSteamUserInfo`/`getSteamSyncedAt` returning real data.
4. `humbleSync`/`humbleGetKeys` returning a real key list.
5. `steamBottleStatus`/`isSteamBottleProvisioned` reporting truthfully.

None of these five behaviors differ structurally between a dev sidecar process and a packaged
one — the sidecar binary identity, not its content or behavior, is what 34.3's D-12 item existed
to prove. The one part of this slice's surface that genuinely *does* behave differently when the
app is code-signed — the Phase 28 keyring seam the credential-login path writes the refresh
token through — is **already exercised** by the previously-ported QR login flow (34.3's live
gate did not need to re-prove it either, for the same reason). A full package-and-sign cycle
per gate re-run (`electron-vite build && pnpm build:sidecar-sea && npx tauri build`, ~5+ minutes
per 34.3's own record) is expensive and would buy nothing here.

Since 34.3's D-12 and the `publicdir-getapppath-chunking` family of gotchas have made a packaged
item the *default* expectation for this project's live gates, this rationale is recorded
explicitly here (D-10) so the omission reads as a scoped decision, not a gap.

## Item 2 — `logoutSteam` actually signs out (REQ-34.4-02) — the item this gate exists for

### Attempt 1 — FAIL (stale frontend guard), fixed in-phase

**Build:** `tauri:dev`
**Result:** **FAIL**
**Evidence:** Sign-out produced the dialog "Steam sign-out isn't available in this build yet.
You'll remain signed in." — no attempt was made to reach the seam at all. Root cause:
`src/frontend/state/GlobalState.tsx`'s `steamLogout` still carried the Phase 30 **G-30-01**
mitigation, an `if (isTauri()) { ...dialog...; return }` early-return placed *before*
`window.api.logoutSteam()`. That guard's own comment asserted its premise outright — "no
listener is registered for it on the sidecar under Tauri (`steamAuthFlowRegistration.ts`
deliberately excludes it, per its own docstring)" — and plan 34.4-01 falsified that premise by
registering `ipcMain.on('logoutSteam', ...)` at `steamAuthFlowRegistration.ts:183`. No plan in
this phase touched `GlobalState.tsx`, so the backend channel shipped reachable-in-principle and
unreachable-in-practice. `34.4-PORTED-CHANNELS.md` had already declared the row "unit + LIVE
(item 2)".

This is precisely the class of defect the automated suite cannot catch: `logoutSteam` is a
`send`, so there is no rejection, no timeout and no console line to assert on — only a human
driving the real UI could observe it.

**Resolution (in-phase deviation, authorized by the user rather than routed to a gap cycle):**
commits `1cf42d43b` (fix) and `52dfcfb66` (test). The stale guard and its now-false comment were
removed, and the underlying fire-and-forget race was closed rather than merely unblocked —
deleting the guard alone would have turned a deterministic no-op into an intermittent one,
because `window.location.reload()` can beat `SteamUser.logout()`'s credential clear, letting
`steamConfigStore.userData` rehydrate the same identity. New `src/frontend/state/SteamSignOut.ts`
fires the send, then polls the already-ported `getSteamUserInfo` invoke (20 × 150ms, ~3s bound)
until it confirms the signed-out state before clearing local state and reloading; the timeout
path surfaces an honest failure dialog instead of a silent revert or a false success. The
signed-out signal was verified, not assumed: `SteamUser.logout()` (`steam/user.ts:249`) deletes
the `userData` key that `getUserDetails()` (`steam/user.ts:284`) reads, and both builds call the
identical function. `logoutSteam`'s `send` kind is unchanged; `main.ts` and `src-tauri/` remain
byte-unchanged for the whole phase.
