# Phase 34.4 — Declared Ported-Channel List

**Purpose:** The enumerated set the next Tauri phase (34.4.1, then 34.5) starts from, and the
artifact the Phase 35 cutover gate reads for this slice, mirroring how this phase itself started
from `34.3-PORTED-CHANNELS.md`. It describes what actually shipped in 34.4-01..34.4-08, verified
row by row against all eight prior plan SUMMARY.md files, not against this phase's original
planned intent.

**This slice got SMALLER during discussion, deliberately — read the scope surgery first.** The
inventory's slice-7 list started at 38 channels and ended at 31:

- **`isLoggedIn` moved to Phase 34.5** (D-03). It is `LegendaryUser.isLoggedIn()` — Epic auth,
  filed under this slice's `main.ts` grouping only because the inventory groups channels by file,
  not by runner. Phase 34.5 owns `login`/`logoutLegendary`/`getUserInfo`, which are what give
  `isLoggedIn` meaning.
- **6 Humble browser-auth channels moved to the newly-inserted Phase 34.4.1** (D-01/D-02):
  `humbleStartLogin`, `humbleReconnect`, `humbleStopLogin`, `humbleLoginNavigated`,
  `humbleGetLoginUserAgent`, `humbleRevealKey`. The `<webview>`/`session.fromPartition` seam they
  need is shared with Phase 34.5's Epic/GOG/Amazon logins and does not belong inside a
  Steam-and-Humble store-completion slice. Phase 34.4.1 runs BEFORE Phase 34.5 because 34.5's
  three logins depend on the identical seam.

**Ported in 34.4: 31 channels — 15 Steam + 16 Humble.** All 31 are enumerated below, each with its
port kind, its real backing code, and an HONEST proof level. No reader should take "wired and
unit-proven" for "seen working" for a single row in this table.

## Framing corrections this document owes

This phase corrected four claims made by its own upstream planning documents. Declaring
corrections rather than silently absorbing them is this project's discipline — a future reader
who trusts a stale planning-time claim over what actually shipped is exactly the failure class
this document exists to prevent.

**1. `humbleRecordGiftLinkOpened` is a `handle`, not a `send`.** `34.4-CONTEXT.md`'s Discretion
section claimed it was a `send` channel alongside `logoutSteam` and `humbleDisconnect`. It is not.
Confirmed by three independent source citations: `src/backend/humble/ipc_handler.ts:72`'s
`addHandler` call, `src/common/types/ipc.ts:350`'s `Promise<void>` return signature, and
`src/preload/api/humble.ts:31`'s `makeHandlerInvoker` wrapper. Plan 34.4-05 registered it as
`ipcMain.handle` and pinned the kind with a dedicated test.

**2. `getPrivateBranchPassword`/`setPrivateBranchPassword` are GOG, not Steam.** The inventory
filed both under this slice's Steam list because it groups by source file (`main.ts:1510-1515`),
not by actual runner. Both delegate to `libraryManagerMap['gog'].getGame(appName)`. Plan 34.4-03
registered them in `settingsFlowRegistration.ts`, never in `steamAuthFlowRegistration.ts`.

**3. The electron-reach ledger gained FOUR new baseline entries, not the two `34.4-CONTEXT.md`
and `34.4-RESEARCH.md` predicted, nor the three this very plan's own `<interfaces>` section
anticipated.** Plan 34.4-08 measured the real traversal at execution time (never transcribed from
planning-time prose) and found: `src/backend/humble/user.ts` and `src/backend/humble/adapter.ts`
(the two originally-predicted direct `import ... from 'electron'` edges), `src/backend/humble/
expirationAlerts.ts` (the predicted third, a two-hop transitive edge via `humble/library.ts:22`),
and **`src/backend/humble/userAgent.ts`** — an unpredicted fourth module, reached independently
two-hop via `humbleFlowRegistration.ts -> humble/user.ts:16 -> ./userAgent` and three-hop via
`humbleFlowRegistration.ts -> humble/library.ts:12 -> ./adapter -> ./userAgent`. Neither
`34.4-RESEARCH.md`'s canonical_refs nor `34.4-CONTEXT.md`'s D-10 section named `userAgent.ts`.
`BASELINE_ELECTRON_REACHING_MODULES` grew 30 → 34 modules (measured, not assumed). This is
recorded as a finding, not a defect — per the plan's own stated rule, "if the measurement
disagrees with the prediction, the measurement wins."

**4. `settingsFlowRegistration.ts` and `steamAuthFlowRegistration.ts` were NOT already
`electronReachLedger.test.ts` entry points**, contrary to `34.4-RESEARCH.md`'s claim. Plan 34.4-08
added all three of this slice's registration modules (`humbleFlowRegistration.ts`,
`steamAuthFlowRegistration.ts`, `settingsFlowRegistration.ts`) to `ENTRY_POINTS`, extending it from
7 to 10 entries — `humbleFlowRegistration.ts`'s addition was itself deferred here by plans 34.4-04
and 34.4-05, which explicitly left that edit to plan 34.4-08.

## The Humble Claim Wizard's real Tauri state

REQ-34.4-14 explicitly requires this be stated plainly, not left for a reader to infer. The
Humble Claim Wizard's Copy button (`HumbleClaimWizard/index.tsx:120,366`) **now works under
Tauri**, thanks to Phase 34.3's clipboard seam (`clipboardWriteText`, real Rust-backed) — **but
only for an already-revealed key**. `humbleRevealKey` itself is deferred to Phase 34.4.1 (D-02),
since revealing a key requires the Chromium fingerprint `humblePostRequest` routes through the
`persist:humble` partition specifically to survive Cloudflare Bot Management. A Tauri user who has
never revealed a key under Electron first has no way to reveal one yet; a Tauri user who reveals a
key under Electron and then switches builds can copy it cleanly under Tauri. Stating this
prevents a reader concluding the claim flow is end-to-end functional under Tauri today — it is
not, and reveal itself is deferred until 34.4.1 lands.

## D-06 and D-04 — not channels, but this phase's other deliverables

**D-06 — `electronStub.net.request` hardening.** `net.request()` previously returned a silent
dead end (`on()` never fired). It now records handlers by event name and asynchronously
(`setImmediate`) invokes a registered `'error'` handler with an `Error` naming the stub, Phase
34.4.1, and D-06 — never a synchronous throw, never a rejecting promise a fire-and-forget caller
could crash on (`sidecar-dialog-reject-crashes` discipline). `humblePostRequest`'s own
already-wired `request.on('error', ...)` handler is proven reachable through the REAL, unmocked
stub via `revealKey()`. Two dormant gaps were found and deliberately left unfixed, owed to Phase
34.4.1: `electronStub.ts`'s `app` has no `userAgentFallback` (read by
`standardBrowserUserAgent()`, currently unreachable in production), and the stub's `request`
return value has no `abort()` method (`humblePostRequest`'s timeout branch calls it
unconditionally — meaning the real pre-D-06 timeout failure mode was a masking `TypeError`, not
the misleading-but-clean rejection message originally assumed).

**D-04 — the honest "not available on this build" login panel.** `WebView/index.tsx`'s
`!webviewPreloadPath` branch previously returned a silently-blank `<></>` under Tauri (34.1
D-12's declared-empty `getWebviewPreloadPath` return made this branch reachable there for the
first time). It now diverges on `isTauri()`: Tauri renders `WebviewUnavailablePanel` (naming the
build limitation, the attempted store when known, and the Electron-build workaround) and logs via
`window.api.logInfo`; Electron's `<></>` arm is byte-unchanged and proven structurally
unreachable-and-distinct by a self-tested source gate (not merely asserted in prose) — hand
RED-proofed by merging the two arms and confirming the gate fails for the exact expected reason.

## Automated vs live proof boundary

**What the jest suites prove:** that each channel dispatches with the right arguments and kind
(`invoke` vs `send`, cross-checked against `main.ts`/`humble/ipc_handler.ts`'s own registration
for every ported channel — the corrected `humbleRecordGiftLinkOpened` kind chief among them);
that trust-boundary guards (redeem's WR-03, the ownership-override non-fuzzy re-validation) reject
BEFORE the mutating delegation, not merely return the right shape; that `humbleDisconnect`'s real
`disconnect()` genuinely clears the three stores independent of the partition-wipe no-op; and that
`humbleRunValidation`'s packaged-signal guard resolves correctly across all three branches.

**What only the live gate (34.4-10, not yet run as of this document) proves:** that credential
login genuinely reaches a signed-in, populated library (item 1); that `logoutSteam` — the one
channel jest structurally cannot prove — actually signs a real session out (item 2); that
`getSteamUserInfo`/`getSteamSyncedAt` return real, non-placeholder data after that login (item 3);
that `humbleSync`/`humbleGetKeys` run against a real Humble session and return the real key list
(item 4); and that `steamBottleStatus`/`isSteamBottleProvisioned` report the TRUTH about a real
macOS bottle, not a mocked filesystem's opinion of one (item 5).

**No reader may take "wired and unit-proven" for "seen working"** — this is exactly how G-30-02
was declared fixed twice while the live build hung. That conflation is the one thing this document
exists to prevent, row by row.
