## Implementation Decisions

### Scope — the slice splits

- **D-01 — SPLIT the embedded-browser login seam into a NEW Phase 34.4.1, inserted BEFORE
  Phase 34.5.** The seam is not Humble-specific: `WebView/index.tsx:467` renders one
  Electron-only `<webview partition="persist:…">` for **Humble, Epic, GOG and Amazon alike**,
  and `session.fromPartition()` is how all of them capture their cookie. Building it inside a
  Steam/Humble slice would put a cross-cutting platform seam in the wrong place and leave
  34.5 to hit the identical wall and defer again. Placement **before** 34.5 is load-bearing:
  34.5's three logins depend on the same seam, so 34.4.1 must exist first. Same reasoning
  34.1 **D-14** used to move `callTool` out of slice 4. Rejected: building it here (makes
  this the largest platform-work slice yet — 34.2 needed four gap cycles for less);
  porting all 38 at parity with login declared degraded (ships structurally dead channels,
  which 32 **D-01**, 34.1 **D-11** and 34.3 **D-01** each explicitly refused).

- **D-02 — The split line: `humbleDisconnect` STAYS, `humbleRevealKey` MOVES.** All 21
  `ipc_handler.ts` channels were classified by whether they actually touch Chromium:
  - **Clean (14 + `humbleRunValidation`)** — store reads, or axios GETs through
    `humbleRequest` (`adapter.ts:126`), which sets an explicit `Cookie: _simpleauth_sess=…`
    header from the *stored* value. These port with no seam at all.
  - **Chromium-bound, deferred (5)** — `humbleStartLogin`, `humbleReconnect`,
    `humbleStopLogin`, `humbleLoginNavigated`, `humbleGetLoginUserAgent`. The first four
    drive `watchForLogin()`'s partition-cookie poll; the fifth is a pure function whose only
    consumer is the deferred `<webview>`'s `useragent` attribute, so it travels with it.
  - **`humbleRevealKey` — deferred (6th).** A *different* Chromium dependency from login:
    the network fingerprint, not the webview. Its Cloudflare problem is only solvable once a
    real browser context exists, so it belongs with 34.4.1.
  Rejected: moving `humbleDisconnect` too (cleaner boundary to state, but its real job —
  deleting the stored cookie — works perfectly in the sidecar, so deferring it means a Tauri
  user cannot sign out of Humble at all); keeping `humbleRevealKey` here (drags the hardest
  network problem into a slice we just decided to keep narrow, and it cannot be live-tested
  without a working login).

- **D-03 — `isLoggedIn` is REASSIGNED to Phase 34.5.** `main.ts:875` is
  `addHandler('isLoggedIn', () => LegendaryUser.isLoggedIn())` — Epic auth. Phase 34.5 owns
  `login`, `logoutLegendary` and `getUserInfo`, which are what give it meaning. Follows 34.1
  **D-14** exactly. **Requires an `IPC-PORT-INVENTORY.md` edit:** slice 7 38→31 (with the
  six 34.4.1 channels listed under a new heading), slice 8 56→57. Rejected: keeping it (a
  one-line delegation that costs nothing to port, but it lands an Epic channel in the Steam
  slice's declared list).

### The login surface — what 34.4 owes the user before 34.4.1 lands

- **D-04 — Replace the silently-blank login screen with an honest "not available on this
  build" panel.** 34.1 **D-12** already made `getWebviewPreloadPath` return a declared-empty
  `''` on the sidecar, and `WebView/index.tsx:445` returns `<></>` when there is no preload
  path — so a Tauri user who opens Humble login today gets a **blank screen with no error,
  no log line and no explanation**. Add a short explanatory panel on the
  `isTauri() && !webviewPreloadPath` branch. This is the project's own "logged, never
  silent" discipline (31 **D-03/D-04**, 34.1 **D-13**) applied at the one place a user
  actually sees the gap. **Rider: it must not change Electron's behavior at all** — Electron
  always has a preload path, so the branch is structurally unreachable there; prove that in
  the test rather than asserting it. Rejected: leaving the blank screen and declaring it (the
  exact failure shape 34.3 **D-01** called out for clipboard, and Tauri is not yet the
  shipped build so nobody would catch it); hiding the login entry point under Tauri (hides a
  shipped feature behind a build check Phase 35 must unwind, and makes the gap invisible
  during 34.4.1's own testing).

- **D-05 — Port `humbleDisconnect` and DECLARE its partial precisely.** `user.ts:591` calls
  `session.fromPartition(HUMBLE_LOGIN_PARTITION)` and clears storage; under Tauri that
  resolves to `electronStub.session`'s logged no-op (Phase 29 **D-09**). But **the stored
  encrypted cookie IS deleted** — that is the real sign-out and the actual security
  boundary. Only the Chromium partition wipe no-ops, and under Tauri that partition never
  held anything. Declare per-row in `34.4-PORTED-CHANNELS.md` that "ported" means the
  app-side session is cleared, and add the note that **once 34.4.1 creates a real browser
  context, `humbleDisconnect` must be revisited to clear it too** — otherwise 34.4.1 silently
  inherits a half-finished sign-out. Rejected: surfacing a warning that a browser session may
  survive (under Tauri today there is none, so the warning would be *false* — and 34.3
  **D-01**'s rider explicitly warned against inflating a precautionary no-op into a shipped
  defect); deferring it to 34.4.1.

### The network seam

- **D-06 — Harden `electronStub.net.request` to fail fast and legibly.** `electronStub.ts:592`
  returns `{ on, end, write, setHeader }` where `on()` never fires — a silent dead end added
  in Phase 33 purely so `net.isOnline` could exist. **Accurate failure mode, corrected during
  discussion:** `humblePostRequest` arms its own `REQUEST_TIMEOUT_MS` timer
  (`adapter.ts:277-287`), so this **rejects after the timeout — it does not hang forever**.
  But it rejects with `"Humble reveal request timed out"`, which reads as a Humble outage
  rather than a missing seam, and would send 34.4.1's owner straight back into Cloudflare
  territory. Fix: emit an `'error'` event asynchronously naming the missing seam —
  `humblePostRequest` already attaches `request.on('error')` and clears its timeout there, so
  it rejects immediately with an accurate cause. This is `electronStub.session`'s own stated
  rationale ("fails loudly with a clear log line instead of an opaque TypeError") applied to
  its neighbour. Rejected: leaving it and only declaring the trap (zero risk, but it leaves a
  booby trap in a file this slice already edits); deleting `net.request` entirely (an
  unguarded TypeError in fire-and-forget code is how `sidecar-dialog-reject-crashes`
  happened).

- **D-07 — Seed 34.4.1 with candidates and landmines; pre-commit NO mechanism.** Record in
  34.4.1's phase entry (and in `<deferred>` below) everything this scout paid for:
  - **Three candidate login mechanisms** — a dedicated Tauri `WebviewWindow` on
    humblebundle.com whose cookies are read through Tauri's own webview cookie API; the
    system browser with a loopback or paste handoff; an iframe inside the main webview.
  - **Landmine 1:** Humble's CSP / `X-Frame-Options` almost certainly kills the iframe.
  - **Landmine 2:** 34.3 **D-02** established that `"windows": ["main"]` shares capability
    grants with untrusted remote content — a login window rendering humblebundle.com must not
    inherit the main window's grants.
  - **Landmine 3 (unverified):** nothing in this repo has confirmed that Tauri's webview
    cookie API exists at our version or reaches the platform cookie jar. 34.3 **D-05** is the
    live reminder of what happens when an API inference is treated as fact — **34.4.1's
    research must verify empirically before anything is planned on it.**
  - **The reveal-POST constraint:** rounds 1–6 of the `humble-reveal-key-fails` debug session
    **FALSIFIED** cookie/header fidelity as sufficient. Round 6 got a live 403 with
    `fullCookieJarPresent=true` and every header fix in place; the root cause was axios's
    **TLS/HTTP transport fingerprint**. So any Node- or Rust-side transport (axios, reqwest,
    `tauri-plugin-http`) is expected to fail the same way. Do not let 34.4.1 re-run rounds 1–5.
  - **The per-platform engine risk nobody has faced yet:** Tauri's webview is **WKWebView on
    macOS, WebKitGTK on Linux, and only WebView2/Chromium on Windows**. So "route it through
    the webview" is *three different fingerprints*, and **macOS — the primary dev platform —
    is the one furthest from the Chromium stack that currently works.** Name this up front;
    it is the most likely way 34.4.1 gets surprised late.
  Rejected: pre-committing to the second-window approach (fastest, closest structural
  analogue to Electron — but rests on an unverified API); recording nothing (throws away
  scouting already paid for, and a bare pointer to debug artifacts is how 34.2's repo-wide
  comment-stripper defect went four cycles before anyone counted instances).

### Sign-off

- **D-08 — A BLOCKING 5-item live gate, scoped to REVERSIBLE items.** Carries 34.3
  **D-11/D-13** rather than reverting to the 34.1 **D-15** / 34.2 **D-11** unit-only
  precedent. The deciding evidence is `logoutSteam`: it is the **G-30-01** channel, a `send`
  whose failure mode (`sidecar-send-channels-fail-silently`) produces no reject, no timeout
  and no console line — structurally invisible to assertions, and already a known past
  defect. The five items:
  1. Credential + SteamGuard login (`steamStartCredentials` → `steamSubmitGuard` →
     `steamPollCredential`) reaches a signed-in, populated library.
  2. `logoutSteam` actually signs out — the send-kind check jest cannot make.
  3. `getSteamUserInfo` / `getSteamSyncedAt` return real data after that login.
  4. `humbleSync` + `humbleGetKeys` run against a real session and return the real key list
     (see **D-09**'s precondition).
  5. `steamBottleStatus` / `isSteamBottleProvisioned` report truthfully on macOS.
  **`redeemSteamKey` and `steamBottleProvision` stay unit-proven and declared** — the first
  burns a key irreversibly and cannot be re-run on failure, the second downloads a bottle.
  **Failure is blocking**: findings become a gap cycle inside 34.4, per 34.3 **D-13**.
  Rejected: adding a live key redemption to close Phase 26's deferred UAT (retires real debt,
  but mixes a v0.6 UAT backlog item into a port slice's gate and is unrepeatable); unit-only
  (cheapest, and these channels genuinely do have assertable return shapes unlike 34.3's OS
  side effects — but it leaves `logoutSteam`'s known silent-send failure mode unproven).

- **D-09 — The Humble gate items require an Electron-captured session; state it as a
  numbered setup step.** Until 34.4.1 lands there is **no Tauri path to create a Humble
  session**. Both builds share the same `appFolder` and the same encrypted `configStore`
  entry, so the cookie carries across. The gate step must read: *"log in to Humble under
  `npm start` FIRST, then relaunch under `pnpm tauri:dev` and verify sync/keys."* Write it
  into the gate as an explicit numbered precondition — **an unstated precondition is exactly
  how a gate gets skipped and becomes UAT debt** (Phases 21/30/34.2). Rejected: dropping the
  Humble items from the gate (the whole Humble port would ship with zero live evidence, and
  34.4.1 would then have to verify both the new seam and this slice's work at once);
  hand-seeding an encrypted cookie into the store (tests the store read, not the end-to-end
  path, and means reimplementing the `safeStorage` write the app owns).

- **D-10 — `tauri:dev` for ALL five gate items; no packaged-build item.** Unlike 34.3
  **D-12**, nothing here depends on the dev-vs-packaged sidecar spawn path — these are login,
  sign-out, data reads and a status check, all build-independent. **Record WHY explicitly in
  the gate document, so the omission reads as a decision rather than an oversight**, since
  34.3 D-12 and the `publicdir-getapppath-chunking` family make a packaged item the default
  expectation now. Rejected: adding one packaged credential-login item (Phase 28's keyring
  seam does behave differently when signed — but a full package cycle per gate re-run is
  expensive, and the keyring path is already exercised by the already-ported QR login).

### Claude's Discretion

- **The extraction shape for the 15 `main.ts` Steam registrations.** 34.1 **D-07/D-08**,
  34.2 **D-03** and 34.3's discretion note established extract-the-body / keep-the-
  registration. **This slice needs almost none of it:** all 15 are one-line delegations to
  functions already exported cleanly (`SteamUser.*`, `provisionBottle`, `isBottleProvisioned`,
  `startGuidedClientInstall`, `ensureSteamClientReady`). Whether to register directly against
  those exports or create a `steamAccount/`-style module family for symmetry is a planner
  call, provided registrations stay in `main.ts`, the curated-import rule holds, and nothing
  is re-implemented twice. `steamBottleStatus`'s inline object literal (`main.ts:948-953`) is
  the one genuinely inline body.
- **The curated-import rule, inherited unchanged** (30 **D-08** → 34.1 **D-09** → 34.2
  **D-04** → 34.3 **D-14**): import the UNDERLYING module, never a feature module's
  `ipc_handler.ts`. **`humble/ipc_handler.ts` is especially dangerous here** — it registers
  the 5 deferred login channels alongside the 15 being ported, so side-effect-importing it
  would register channels 34.4.1 owns *and* drag `backend/ipc` in. Import `humble/user.ts`,
  `humble/library.ts` and `humble/validation.ts` directly.
- **`logoutSteam`, `humbleDisconnect` and `humbleRecordGiftLinkOpened` are `send` channels**
  (`addListener`), the rest are `handle`. A mismatch **fails 100% silently** (Phase 31
  Pitfall 2, `sidecar-send-channels-fail-silently`). Cross-check every registration against
  `main.ts` / `humble/ipc_handler.ts`'s own `addHandler`/`addListener` call for that exact
  channel name.
- **Whether `steamStartCredentials`/`steamSubmitGuard`/`steamPollCredential` extend
  `steamAuthFlowRegistration.ts` or get their own module.** That file's docstring currently
  says it "deliberately does NOT register" those five channels per Phase 30 **D-02** — that
  docstring **must be updated either way**, not left contradicting the code.
- **How the D-04 frontend panel is worded and where it lives** — a small component or an
  inline branch is a planner call.
- **Expect ZERO new Rust arms this slice.** If planning discovers a need for one, stop and
  ask why (34.2's standing rider). The bottle/client-setup channels are Node `child_process`
  work; the Steam login path is `steam-session` running headless, already proven by the
  ported QR flow.
