## Warnings

### WR-01: `waitForSteamSignedOut` doesn't guard against `getSteamUserInfo()` rejecting — violates its own documented "never neither" contract

**File:** `src/frontend/state/SteamSignOut.ts:74-92` (loop), consumed by `performSteamLogout` at `:112-128`

**Issue:** `performSteamLogout`'s own docstring (`:104-111`) states it "calls exactly one of
`onSignedOut` / `onSignOutFailed` — never both, never neither." `waitForSteamSignedOut`'s loop
calls `await getSteamUserInfo()` with no `try/catch`. `getSteamUserInfo` is a real `invoke`
channel (can reject on a transport error, an unhandled exception inside
`SteamUser.getUserDetails()`, or a timeout) — if it rejects on any attempt, the `for` loop
throws, `waitForSteamSignedOut`'s promise rejects, `performSteamLogout`'s `await` re-throws,
and **neither** `onSignedOut` nor `onSignOutFailed` is ever called — directly contradicting
the documented invariant. In `GlobalState.tsx`, this means local Steam state is left
unchanged and no failure dialog is shown to the user. The only reason this doesn't crash the
app is that the sole current call site (`Login/components/Runner/index.tsx:28-44`) wraps
`props.logoutAction()` in its own `try/catch`, logs to `console.error`, and resets
`isLoggingOut` in `finally` — but that's a coincidental safety net at a different layer, not
a property of this module, and it still produces a silent-to-the-user failure (button just
stops spinning, `console.error` only, no dialog). Confirmed untested: neither
`SteamSignOut.test.ts` nor `GlobalStateSteamLogout.test.ts` exercises a rejecting
`getSteamUserInfo`.

**Fix:**
```ts
export async function waitForSteamSignedOut(
  getSteamUserInfo: () => Promise<SteamUserData | undefined>,
  { maxAttempts = STEAM_SIGN_OUT_DEFAULT_MAX_ATTEMPTS,
    intervalMs = STEAM_SIGN_OUT_DEFAULT_INTERVAL_MS,
    delay = defaultDelay }: WaitForSteamSignedOutOptions = {}
): Promise<boolean> {
  for (let attempt = 0; attempt < maxAttempts; attempt++) {
    try {
      const userInfo = await getSteamUserInfo()
      if (!userInfo) return true
    } catch (error) {
      console.warn('[SteamSignOut] getSteamUserInfo poll attempt failed:', error)
      // treat as "still signed in" for this attempt, keep polling/retrying
    }
    if (attempt < maxAttempts - 1) await delay(intervalMs)
  }
  return false
}
```
This preserves the "exactly one of onSignedOut/onSignOutFailed, never neither" contract even
when a poll attempt transport-errors.

### WR-02: `WebviewUnavailablePanel` leaks internal runner codenames instead of using the project's established display-name helper

**File:** `src/frontend/screens/WebView/components/WebviewUnavailablePanel.tsx:38-40`

**Issue:**
```ts
const runnerLabel = runner
  ? runner.charAt(0).toUpperCase() + runner.slice(1)
  : undefined
```
This naively capitalizes the raw `runner` param instead of using the project's existing
`getStoreName(runner, other)` helper (`src/frontend/helpers/index.ts:140-153`), which every
other user-facing surface in the codebase uses for this exact purpose
(`DownloadManagerItem/index.tsx:303`, `GameCard/index.tsx:578`, etc.). Concretely: for
`runner === 'legendary'` (Epic Games' internal runner id in this codebase) the panel would
show **"Legendary"** instead of "Epic Games" — leaking an internal implementation codename to
the end user in a user-facing error panel. For `runner === 'gog'` it shows **"Gog"** instead
of "GOG". This is user-visible text (`webview.unavailable.store-suffix`), reachable any time a
Tauri user clicks "Log in to Epic/GOG/Amazon" (per `WebView/index.tsx`'s `isTauri()` branch),
not a hypothetical.

**Fix:**
```ts
import { getStoreName } from 'frontend/helpers'
// ...
const runnerLabel = runner ? getStoreName(runner as Runner, runner) : undefined
```
(`getStoreName` has no `'humble'` case today — falls to its `other` fallback param, so passing
`runner` itself as `other` preserves today's "Humble" output for that one runner while fixing
the Epic/GOG/Amazon mislabeling.)

### WR-03: `WebviewUnavailablePanel`'s i18next calls bake dynamic values into the "default" string instead of using `{{placeholder}}` interpolation

**File:** `src/frontend/screens/WebView/components/WebviewUnavailablePanel.tsx:51-57`

**Issue:**
```ts
const bodyStoreSuffix = runnerLabel
  ? ' ' + t('webview.unavailable.store-suffix', `Signing in to ${runnerLabel} is unavailable here.`)
  : ''
```
The runtime value (`runnerLabel`) is interpolated directly into the JS template literal passed
as `t()`'s *default value* argument, rather than using i18next's own interpolation mechanism
(`t('key', 'default {{runner}}', { runner: runnerLabel })`) — the pattern already established
elsewhere in this codebase, e.g. `steam/library.ts:497-501`
(`i18next.t('steam.resumeAvailable.notify', '...{{game}}', { game: existing?.title ?? '' })`).
As written, once a real (non-English) translation is added for the
`webview.unavailable.store-suffix`/`webview.unavailable.body` keys, i18next will return the
*translated* string (looked up purely by key) and **ignore** the dynamically-built default
entirely — so the runner name will silently disappear from every translated locale, while
continuing to work only in the untranslated (English) fallback path this repo currently ships.
Confirmed untested: `WebviewUnavailablePanel.test.tsx` mocks `useTranslation`'s `t` to always
return the raw `defaultValue` verbatim (`t: (_key, defaultValue) => defaultValue`), so this
test suite cannot and does not catch the divergence between the translated-key path and the
default-value path.

**Fix:**
```ts
const bodyStoreSuffix = runnerLabel
  ? ' ' + t('webview.unavailable.store-suffix',
      'Signing in to {{runner}} is unavailable here.',
      { runner: runnerLabel })
  : ''
```

### IN-01: `handlers.ts` doc comment undercounts `registerHumbleFlows()`'s registered channels

**File:** `src/backend/sidecar/handlers.ts:29-36` (block comment) vs. `humbleFlowRegistration.ts:178-353` (actual registrations)

**Issue:** The module docstring in `handlers.ts` describes `registerHumbleFlows()` as
registering "the curated Humble library/sync + key-state channels ... humbleGetUserInfo/
humbleCheckHealth/humbleSync/humbleGetKeys/humbleGetSyncState/humbleGetGiftedAt/
humbleMarkRedeemed/humbleUndoRedeemed/humbleGetRevealedKeyValue/humbleGetClaimAnnotations" —
10 channels by name — and the inline comment directly above the `registerHumbleFlows()` call
(`:157-165`) repeats the same "10 library/sync + key-state" framing. The function actually

extra channels ARE correctly registered and correctly documented in
`humbleFlowRegistration.ts` itself), but a future reader skimming only `handlers.ts` would
undercount this module's surface.

**Fix:** Update the `handlers.ts` doc block and inline comment to either list all 16 channel
names or say "16 channels (see humbleFlowRegistration.ts for the full breakdown)" rather than
repeating a stale 10-channel enumeration.

### IN-02: `electronStub.ts`'s `net.request()` stub supports only one listener per event name

**File:** `src/backend/sidecar/electronStub.ts:622-640`

**Issue:** `handlers[event] = cb` overwrites any previously-registered handler for the same
event name, unlike a real Node `EventEmitter`-backed request object (which supports multiple
listeners per event via `addListener`). Not currently a problem — `humblePostRequest`
(`backend/humble/adapter.ts`), the sole caller, registers each event name at most once — but
it's a latent surprise for a future caller that assumes real `http.ClientRequest` semantics
and registers a second handler for the same event (e.g. instrumentation/logging middleware
added later).

**Fix:** Low priority given the single current caller; if this stub gains more callers,
switch `handlers` to `Record<string, Array<(arg?: unknown) => void>>` and invoke all
registered handlers for an event.
