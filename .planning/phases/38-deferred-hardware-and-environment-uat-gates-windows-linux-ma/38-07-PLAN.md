<objective>
Discharge Phase 38's last four items - the Windows window-chrome trio and the off-macOS Epic logout -
closing the phase's observation set.

Purpose: three of these are correct fixes on surfaces this project's hardware structurally cannot
render. `WindowControls` sits behind an unconditional `!isMac` gate. The tray dark/light swap is
vestigial on macOS by design, because AppKit tints template images itself. The login window is
presented as an AppKit SHEET on macOS, and sheets render no title bar UI at all, so the
origin-derived `.title()` sets a string this hardware never displays. Each has strong static
evidence and zero live observation. The fourth, 38-W06, is different in kind: its outcome off macOS
is GENUINELY UNKNOWN, and since commit `bea07cd17` an unreadable cookie jar THROWS rather than
failing open - so if the census reads reject off macOS, every Epic logout on Windows ends in a
visible error dialog.

Output: four discharged items, each with a log-line artifact and an operator verdict.

**NO SOURCE FILE IS MODIFIED.** A FAIL is recorded and filed as a todo; Phase 38 does not repair
what it observes.

<w03_both_halves>
38-W03 has TWO failure modes and only one of them is obvious.

The obvious one: the bar reads the framework default "Tauri app". That is the original defect.

The non-obvious one: the bar shows the origin and NEVER gives way to the document title. That is a
WR-07 REGRESSION INTRODUCED BY THE FIX ITSELF, not a pass. Watch the bar continuously from the
instant the window appears through page load, and record the sequence of strings it displayed with
rough timings. A single glance after load cannot distinguish the two outcomes.

Source can prove the title ARGUMENT is origin-derived; `main.rs`'s own WR-07 CORRECTION records that
a grep gate can establish the ABSENCE of a prohibited hard-coded title but structurally CANNOT
establish the PRESENCE of the required one. Only a human watching the bar can.
</w03_both_halves>

<w02_prior_state>
38-W02 was blocked on ARTWORK, not hardware, until 2026-08-22 - which is why it correctly did NOT
move to this phase with the first six items. `icon-dark.png` and `icon-light.png` were byte-identical
for the project's entire history (verified by md5 at all three scales), so `darkTrayIcon` was a
switch wired to nothing and the item would have FAILED on a Windows machine too. That is now fixed:
`meta/trayIconVariants.ts` generates `icon-tray-{dark,light}{,@2x,@3x}.png` from the same
hue-segmented mask as the macOS template, differing only in fill, and REFUSES to write an identical
pair at any scale. Both that gate and the asset tests are RED-proven against known-bad input.

So the item is genuinely runnable now, which was NOT true of it before. The asset-level property is
already gated without hardware by `trayIconAssets.test.ts`; what cannot be automated is whether the
swap is VISIBLE and LEGIBLE at real tray size against a real taskbar. Score legibility, not file
difference.
</w02_prior_state>
