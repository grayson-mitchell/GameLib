## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Plan contradiction] the bottle dialog is not `show_engine_dialog`**
- **Found during:** Task 2
- **Issue:** the plan names `gamelib_engine::launch::dialogs::show_engine_dialog` for the missing CrossOver bottle, but that function sends a system notification, always shows type `MESSAGE`, mints an acknowledgement id and logs an `[engine-notice]` line. The golden (`mac-crossover-010`, `named-crossover-bottle-missing`) holds one `raiseMainWindowForInAppDialog` and one `showDialog` of type `ERROR` with no ack id, and no notification.
- **Fix:** `ui.raise_main_window()` then `ui.show_dialog(title, message, "ERROR", "")`, with the title and message from the i18n catalogue (`box.error.cx-bottle-not-found.*`, `bottle_name` interpolated). The empty ack id is what `gamelib-wine`'s tool-install error dialog already sends. The key link `show_engine_dialog` in the plan's artifacts therefore does not exist; the replay compares the raise and the dialog through a recording `EngineUi`.
- **Commit:** 5feeddb05

**2. [Rule 3 - Blocking] the jest pins and the generated contract**
- **Issue:** `tauriShellSource.test.ts` and `rustInvokeSchemas.test.ts` pin the arm and channel counts (213 to 214) and name each proven arm, and `ipc_contract.rs` is generated; none is in the plan's file list (as in 88.1-07, 88.1-08 and 88.1-11).
- **Fix:** both pins updated, contract regenerated with `pnpm gen:ipc-contract`.
- **Commit:** aced77013

**3. [Rule 3 - Blocking] `sha2` as a dev-dependency of gamelib-launch**
- **Issue:** the tree comparison needs each file's sha256, which the plan's file list does not cover (`Cargo.toml`, `Cargo.lock`).
- **Fix:** `sha2 = "0.10"` under `[dev-dependencies]`; already locked by gamelib-engine, gamelib-wine and gamelib-knownfix, so no new package enters the lock file (T-88.1-SC). The lock change is one line.
- **Commit:** aced77013

### Design points the plan left open (judgement calls, not golden diffs)

- **Replay differences (test level, `deltas.json` stays `{}`).** Five, each required to be used by a case or the replay fails: `in-process-wine-valid` (the TS asked the `wine_valid` channel again from inside `verifyWinePrefix` and the wine command, once or twice per prefix check; both run in process now), `eos-overlay-slot` (the `isOverlayEnabled` hook call and its `EOS Overlay:` line are the reply's slot), `adapter-writes-prefix-line` (`Created/Updated Wineprefix at <prefix>` names a path, so it stays the adapter's line; the replay proves it is there exactly when `prefixUpdated` is true, from `settings.winePrefix`), `wine-spawn-failure-line` (as in 88.1-11) and `dialog-without-ack-id`.
- **Rig facts, not differences.** The TS oracle put `<HOME>/bin/umu-run` on the PATH through its executable seam and left `PATH` pinned, while Rust finds umu on the host `PATH`: the replay prepends `<HOME>/bin` for a umu case and strips it from the recorded spawn's `PATH` before comparing. The runtime path is `<TOOLS>/runtimes` (`<APPFOLDER>/tools/runtimes`), which is where the goldens' `PROTON_EAC_RUNTIME` points; `Profile` now maps `<TOOLS>` both ways.
- **Tree comparison.** The golden tree is the whole run's; the finish half's GOG dummy (`drive_c/ProgramData/...`, and the `drive_c` folder it made under a Proton prefix that had none) is left out, and the fake wines the replay lays out are subtracted from the Rust tree, since the TS oracle scripted validity and left no wine on disk.
- **Spawn class** is taken from `golden/classes.json` for the call site, as in 88.1-11; the Rust spawns are all Helper by the wine core's own contract.
- **Mutation checks.** A trailing newline in `installed_games` (297 cases red), a skipped bottle check (61 red) and an inverted offline-warning rule (60 red) each turn the replay red, so the green is not an empty loop.
