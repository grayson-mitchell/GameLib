## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Plan contradiction] the finish step needs the game's stored settings as well as the launch settings**
- **Found during:** Task 2 (the replay's engine-overlay cases)
- **Issue:** the plan's args list names only "settings from begin", but the TS resolved a `runInPrefix` program's tool settings (`engine_resolve_tool_settings`, `stored`) from the game's own stored settings, and the golden holds both (the launch settings say `Engine Wine`, the resolver's `stored` says `Game Wine`) on the engine-overlay cells of every OS.
- **Fix:** `storedSettings` is a required object in `PrepareWineFinishArgs` and the zod schema; `install_fixes` starts the resolver from it. The winetricks verbs, the registry, the overlay and the wine env keep the launch settings.
- **Commit:** 04bef7459 (the argument), dab75bcae (its use)

**2. [Rule 3 - Blocking] the finish op's host is the tool host, and the plan's file list is short of three files**
- **Issue:** the GOG dummy copies from the bundled public directory and the runtime downloads read the online answer, neither of which the wine host carries and neither of which may come from the sidecar.
- **Fix:** the arm appends `wine_dispatch::tools_host_value()` (the wine host, `publicDir`, `online`), which was private, so `wine_dispatch.rs` makes it `pub(crate)`; `gamelib-launch` decodes it as `ToolsHost`. `wine_dispatch.rs` is not in the plan's file list.
- **Commit:** 04bef7459

**3. [Rule 3 - Blocking] `BaseValues` is `Sync` (gamelib-knownfix)**
- **Issue:** `profile_overlay_env`'s future holds a `&dyn BaseValues`, which was not `Sync`, so it could not be boxed into the `Send` future the `PrepareDeps` seam returns. `gamelib-knownfix/src/overlay/env.rs` is not in the plan's file list.
- **Fix:** `pub trait BaseValues: Sync` and the closure impl `F: Fn(&str) -> Option<String> + Sync`. Every existing implementor (the string map and the closures over borrowed maps) already is; `cargo test -p gamelib-knownfix` is green.
- **Commit:** 04bef7459

**4. [Rule 3 - Blocking] the jest pins and the generated contract**
- **Issue:** `tauriShellSource.test.ts` and `rustInvokeSchemas.test.ts` pin the arm and channel counts (214 to 215) and name each proven arm, and `ipc_contract.rs` is generated; none is in the plan's file list (as in 88.1-07, -08, -11 and -12).
- **Fix:** both pins updated, contract regenerated with `pnpm gen:ipc-contract`.
- **Commit:** 04bef7459

### Design points the plan left open (judgement calls, not golden diffs)

- **`resolve_tool_settings` is a `PrepareDeps` method of its own.** The plan lists `run_wine_command_for_game` only. The TS made two requests per program (the resolver, then the command); recording both in the scripted deps keeps the golden's calls comparing one to one with no extra delta.
- **Replay differences (test level, `deltas.json` stays `{}`).** Six new ones, each required to be used by a case or the replay fails: `game-status-bus-emit` (the TS also emitted each status on an in-process bus nothing listens to; the replay requires each emit to follow its renderer push and compares the pushes), `online-monitor-observation` (how often the TS asked the monitor), `winepath-error-line-fixed-text` (`Couldn't get wine path for <path>.\n<stderr>` is the fixed `Couldn't get wine path`), `dummy-failure-line-fixed-text` (the `: Error: ENOENT ...` tail names paths), `settle-warning-fixed-text` (the registry, overlay and deadline warnings carried the rejection's `Error: ...` text) and `tier1-env-line-key-order` (the TS listed the tier-1 variables in the fix file's order; the reader's maps are ordered by key, so Rust lists them sorted. The line is a log; the env is a map and is compared whole. The replay compares the two lines with their tier-1 items sorted).
- **Rig facts, not differences.** The oracle's scripted `winepath` left an already-installed dummy behind (`dummy: present`), so the wrapper runner writes it on the first `winepath` spawn of such a case; the tree comparison is now the whole `tree.json`. The finish half runs in the same rig as the begin half, so the prefix, the scripted runner's queues and the logs are the run's.
- **Store-setup hook.** The golden finish half starts with the adapter's `prepareLaunch` hook call; the replay only requires it to appear at most once and only when the begin step said `prefixUpdated`, which is the cue the adapter (88.1-15) uses.
- **The tracer's scope is by trace, not by OS.** The plan said "Linux wine cases"; the predicate is "no installFixes, GOG dummy, tool or runtime step in the golden trace", which also admits proton, CrossOver and toolkit cells (122 cases).
- **Hardening beyond the TS.** A `winetricks` or `runInPrefix` value in a fix file that is not a list of strings runs nothing (the TS would have iterated whatever it was and rejected); an empty winepath answer never reaches `copy`.
- **Mutation checks.** Skipping the vkd3d install (76 cases red), removing the comet-off guard (19 red), ignoring `mergesTier1Env` (7 red), dropping the online check on the runtimes (31 red) and turning off `wait` on the `runInPrefix` command (19 red) each turn the replay red, so the green is not an empty loop.
