| repo -> build | deleted builder, system-information and channel TS must not come back as a fallback | 88.1-17 |

### Observations (not register threats)

1. **IN-01 against T-88.1-19.** The plan says every probe is a Helper `ProcSpec` with the TS timeout. That holds for every probe the TS spawned (`run_probe_bounded`, `sysinfo/mod.rs:86-111`). The four macOS host facts the TS read in process through `os.cpus()`, `os.release()` and `os.totalmem()` are read in Rust by synchronous `Command::new("/usr/sbin/sysctl").output()` with no timeout (`gamelib-info/src/sysinfo/host.rs:169-199`). `88.1-REVIEW-DISPOSITION.md` records this as IN-01, accepted (rule 1 of the Rust shutdown contract permits short synchronous probes). Medium, below the high threshold, not counted in `threats_open`; see AR-88.1-09.
2. **WR-04 against T-88.1-41 and the "shutdown ends it" claim.** `ShellDialogs::ask` (`launch_dispatch.rs:57-70`) parks the worker thread in `rpc_dialog_message` until the user answers, so a quit with the wine-change dialog open does not cancel the op: the `launch` registrant is held through the 3.5 s drain. Deferred to `.planning/todos/pending/2026-11-26-wine-change-dialog-holds-the-launch-registrant-through-shutdown.md` (severity medium). T-88.1-41 is `accept` (low), and its recorded rationale is restated accurately in AR-88.1-07. It does not weaken T-88.1-34 (a failed dialog is still never read as Yes).
3. **WR-03 against T-88.1-19.** The declared bound (5 s per pci.ids lookup) is present; there is no overall deadline across the serial per-name lookups, so a black-holed resolver can hold a launch about 15 s per GPU. Deferred to `.planning/todos/pending/2026-11-26-launch-waits-on-pci-ids-dns-lookups-with-no-overall-deadline.md` (medium). Not a failure of the declared mitigation.
4. **Unregistered flag (88.1-11 Threat Flags): `prepare_host` reads `/app/manifest.json`.** Maps informationally to T-88.1-26 (the shell builds host facts itself). Verified: fixed path (`launch_dispatch.rs:789-796`), read only when `FLATPAK_ID` is set, only the `runtime-version` string is extracted, the value appears only in a fixed failure sentence, nothing comes from the sidecar. No action.
5. **Where the plans' "deny_unknown_fields" strictness actually lives.** The generated decode in `src-tauri/src/ipc_contract.rs` contains no `deny_unknown_fields` (0 occurrences). The strictness T-88.1-13, -26, -32 and -39 name is delivered by the strict zod schemas on the TS side (`rustInvoke.ts`) and by the crate structs behind each arm (`WrapperEnvArgs`, `PrepareLaunchArgs`, `PrepareHost`, `PrepareWineBeginArgs`, `PrepareWineFinishArgs`, `CheckWineArgs`). The positional settings objects are deliberately lenient views (`GameSettingsView`, `SetupEnvView`, `WineInstallation`) because the TS owns settings until 98 (T-88.1-32, T-88.1-50). Intent met; the plan wording "generated serde decode with `deny_unknown_fields` in the arm" is imprecise.
