  <decision>How gamelib-info performs the `<ids>.pci.id.ucw.cz` TXT lookup that names GPUs on Linux and Windows (Node used `dns.resolveTxt`; Cargo.lock holds no DNS crate)</decision>
  <context>The TS drops a GPU whose device or vendor name lookup fails, so a lookup that cannot run is a visible regression in Settings and in every launch log's System Info. macOS never probes GPUs. RESEARCH committed to "no new third-party crate enters the lockfile". Reversibility: option B is costly (new lockfile names and a supply-chain review); A and C are reversible.</context>
  <options>
    <option id="a">
      <name>A (recommended): in-repo TXT query over std UDP to the system resolvers</name>
      <pros>No new crate; resolvers read as the OS lists them (unix `/etc/resolv.conf` nameservers, Windows `GetAdaptersAddresses` via windows-sys features of the locked version); query is one fixed shape</pros>
      <cons>About 200 lines of own code including a bounds-checked answer parser (an untrusted-input surface, covered by unit vectors with truncated and malicious packets); no TCP fallback for truncated answers (pci.ids TXT answers are short)</cons>
    </option>
    <option id="b">
      <name>B: add `hickory-resolver` (system config, TXT lookup)</name>
      <pros>A maintained resolver; least own code</pros>
      <cons>New crate names in Cargo.lock and `EXPECTED_LOCKFILE_CRATE_NAMES`; requires a blocking human package-legitimacy check on crates.io before any install (no RESEARCH audit row exists); this plan stops for a re-plan of Task 3 with that checkpoint</cons>
    </option>
    <option id="c">
      <name>C: spawn the OS lookup tool (`nslookup -type=TXT`) as a Helper probe</name>
      <pros>No new crate, no parser of raw DNS packets</pros>
      <cons>`nslookup` is absent on many Linux desktops, so GPU names (and the GPUs) disappear there; output format differs by platform</cons>
