## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 - Blocking] a second context seam, `WineManagerFacts`, and three more files**
- **Issue:** the plan names only `dialogs` on `LaunchCtx`. The in-process install needs the shell's install settings (`downloadProtonToSteam`, `defaultSteamPath`, read from `config.json`) and the cancel registry the renderer's `abort(version)` reaches, and discovery needs the shell's `DiscoveryHost` (roots, the Steam libraries). None can be built inside the Tauri-free crate. Without them a download started by a launch would ignore the Proton-to-Steam setting and could not be cancelled, which the TS path (`rpc_wine_manager_install`) could.
- **Fix:** `WineManagerFacts` in `deps.rs`, `LaunchCtx.manager` with `with_manager`, `ShellWineManager` in `launch_dispatch.rs`. `wine_dispatch.rs` (not in the plan's file list) makes `discovery_host`, `read_install_settings`, `register_install` and `InstallGuard` `pub(crate)`. The facts are read lazily, only when discovery or an install runs.
- **Commits:** adef40a73 (dialogs), 62449fd2f (manager)

**2. [Rule 3 - Blocking] the generated contract, `ipcSchemaSnapshot.json` and the two jest pins**
- **Issue:** `ipc_contract.rs` is generated, and `tauriShellSource.test.ts` and `rustInvokeSchemas.test.ts` pin the arm and channel counts (215 to 216) and name each proven arm; none is in the plan's file list (as in 88.1-07 to 88.1-13).
- **Fix:** both pins updated, contract regenerated with `pnpm gen:ipc-contract` (the snapshot came out unchanged).
- **Commit:** adef40a73

### Design points the plan left open (judgement calls, not golden diffs)

- **Replay-level difference (test level, `deltas.json` stays `[]`).** One: `discovery-rejection-fixed-reason` (the TS let a rejected discovery escape `checkWineBeforeLaunch` with its text; Rust answers the fixed reason `failed`). It is required to be used by a case. The backend log lines are compared by level and text; the `Backend` prefix is the shell log's, not the crate's.
- **Interleaving is compared.** The replay merges the golden's requests, dialogs and backend log lines by `seq` and compares them against one recorded timeline, so a dialog asked before a download, or a log line written between two calls, is checked, not just each stream.
- **A list read that fails.** `wine_manager_list` answering an error is treated as no list (the log line `Could not find default wine version`, answer `None`); the TS would have rejected the launch. Not in the goldens; a launch that cannot find a wine stops in both.
- **An out-of-range dialog answer** is a dismissal in the shell (`filter(index < buttons.len())`), not a button.
- **Mutation checks.** Swapping the two macOS release types, ignoring the install result, dropping the global write, and reading anything but the first button as Yes each turn the replay red, so the green is not an empty loop.
- **A deleted test.** A lib test that drove the op over a fake Linux home reached the real release feeds and a real install (57 s). It was removed before any commit; the op's decode is covered by `the_check_wine_op_decodes_strictly_and_never_echoes_what_it_was_sent`, and the behaviour by the scripted replay.
