# Phase 88.1: Code Review Report

**Reviewed:** 2026-11-26
**Depth:** standard
**Files Reviewed:** 52 (production files read in full or by hunk; golden and test files read only where they decided a production question)
**Status:** issues_found

## Summary

The Rust ports are, on the whole, faithful: the npm shlex port matches `node_modules/shlex` line for line (including the `quote` run grouping), the env/wine-env builders, the gamescope command, the prepare-launch log lines and the settings filter match the pre-port TypeScript (`git show 6a9669b06~1:src/backend/launcher.ts`), and the zod schemas in `rustInvoke.ts` agree field-for-field with the `deny_unknown_fields` structs of the crate. `dns.rs` is carefully bounded: every length is checked against the packet, no compression pointer is followed, the answer walk is capped, the id and question are echoed-checked, and the whole lookup is bounded at 5 s under a shutdown registrant. No process is spawned outside `gamelib-proc` except the one `Command::output()` in `host.rs` (permitted by the convention for short synchronous probes, but see IN-01).

The one serious defect is a platform-gating bug at the TS/Rust seam: `launch_setup_env_vars` decodes the whole settings object into a struct that requires `wineVersion`, and Windows game settings never carry one, so legendary and sideload launches on Windows are rejected. I reproduced the rejection against `target/debug/gamelib-launch-cli`.

Deliberate behaviour changes listed in the brief were not flagged.

## Critical Issues

### CR-01: `setupEnvVars` is rejected on Windows because `GameSettingsView` requires `wineVersion`

**File:** `src-tauri/crates/gamelib-wine/src/wine_cmd/env.rs:103-104` (decode), `src-tauri/crates/gamelib-launch/src/lib.rs:295-311` (`settings_arg`); callers `src/backend/storeManagers/legendary/games.ts:1006` and `src/backend/storeManagers/storeManagerCommon/games.ts:157`
**Issue:** `GameSettingsView.wine_version: WineInstallation` has no `#[serde(default)]`, and `WineInstallation` requires `bin`, `name` and `type`. `settings_arg` (used by both `launch_setup_env_vars` and `launch_setup_wine_env_vars`) runs `serde_json::from_value::<GameSettingsView>`, so any settings object without a complete `wineVersion` is answered `launch_setup_env_vars:bad-args`.

On Windows the per-game settings have no `wineVersion`: `game_config.ts:238-240` only sets `defaultSettings.wineVersion` under `if (!isWindows)`, and the factory default for the global one on Windows is `{}` (`config.ts:249-251`). The old TS `setupEnvVars` never read the wine, so it worked. Legendary (`legendary/games.ts:1006`) and the sideload path (`storeManagerCommon/games.ts:157`) call `setupEnvVars` unconditionally, unlike GOG and Nile which guard with `isWindows ? {} : ...`. The result is that every Epic and sideloaded game launch on Windows now fails at env build time.

Reproduced with the built CLI:

```
op launch_setup_env_vars '[{"nvidiaPrime":false,"winePrefix":""},null,null]'   -> launch_setup_env_vars:bad-args (exit 2)
op launch_setup_env_vars '[{"wineVersion":{}},null,null]'                        -> launch_setup_env_vars:bad-args
op launch_setup_env_vars '[{...,"wineVersion":{"bin":"/x","name":"w","type":"wine"}},null,null]' -> {"LD_PRELOAD":""}
```

No golden case covers `setupEnvVars` on `platform: windows` (the only `"windows"` platform cases in `golden/builders/cases.json` are `sonoma`), which is why the replay is green.

**Fix:** `setup_env_vars` reads no wine field at all (nvidiaPrime, showFps, environment options, install path), so give it its own view, or make the wine optional in the shared one:

```rust
// gamelib-wine/src/wine_cmd/env.rs
#[serde(rename = "wineVersion", default)]
pub wine_version: Option<WineInstallation>,
```
and let `build_wine_env_vars` return an empty env (or an error) when it is `None`; or, smaller, add a `SetupEnvView { nvidia_prime, show_fps, enviroment_options }` for `launch_setup_env_vars` only and keep `GameSettingsView` for the wine ops. Add a `platform: "windows"` case with no `wineVersion` to the builders golden, and a `lib.rs` test that `launch_setup_env_vars` answers `{"LD_PRELOAD":""}` for `{}` settings.

## Warnings

### WR-01: A legacy key in a stored `wineVersion` breaks the settings decode and the global default wine, though `wine_valid` and `check_wine` are written to tolerate it

**File:** `src-tauri/crates/gamelib-wine/src/wine_cmd/mod.rs:37-38` (`#[serde(deny_unknown_fields)]` on `WineInstallation`), `src-tauri/crates/gamelib-launch/src/prepare/deps.rs:311-314` (`global_default_wine`), `src-tauri/crates/gamelib-launch/src/prepare/wine_begin.rs:157`
**Issue:** `wine_dispatch::persisted_wine` and `check_wine::wine_of` both exist because "a stored wine may carry a legacy key": they keep only the six declared keys before decoding. Three other decode sites do not. `GameSettingsView` (every builder op and `launch_prepare_wine_begin`/`finish`) and `CtxPrepareDeps::global_default_wine` decode `WineInstallation` strictly, so one extra key in a game's or the global `wineVersion` turns the launch into `bad-args` (settings) or silently reads as "no default wine" (`global_default_wine` returns `None`, so `check_wine_before_launch` falls through to discovery/download instead of offering the user's default). Reproduced: `"wineVersion":{"bin":"/x","name":"w","type":"wine","legacy":1}` gives `launch_setup_env_vars:bad-args`.
**Fix:** drop `deny_unknown_fields` from `WineInstallation` (the strictness is already enforced at the shell boundary for the ops that need it), or run `wine_of` over the value in `global_default_wine` and in a custom `Deserialize` for `GameSettingsView.wine_version`.

### WR-02: A non-string value in the gamescope settings fails the whole `launch_prepare` instead of that one flag

**File:** `src-tauri/crates/gamelib-launch/src/prepare/launch.rs:370-373`, `src-tauri/crates/gamelib-launch/src/builders/gamescope.rs:19-46`
**Issue:** `GamescopeSettings` declares `game_width`, `fps_limiter`, etc. as `String` with `#[serde(default)]`; `default` only covers an absent key. A value that is a number or `null` (a hand-edited `GamesConfig/<app>.json`, e.g. `"gameWidth": 1920`) makes `serde_json::from_value` fail and the step returns `Err("the gamescope settings have an unexpected shape")`, so `launch_prepare` rejects and the adapter throws. The TS pushed the value into the argv as it was. The error also aborts the launch for an unrelated reason: the user only asked for a frame limiter.
**Fix:** decode leniently per field, e.g. a `#[serde(deserialize_with = ...)]` that accepts string, number or null and yields a `String` (empty for null), or read the group as `Value` and take `as_str().map(str::to_string).or_else(|| number.to_string())`. Add a vector with a numeric `gameWidth` to the builders golden.

### WR-03: A launch waits on the pci.ids DNS lookups, with no bound beyond five seconds per name

**File:** `src-tauri/crates/gamelib-info/src/sysinfo/dns.rs:325-340,371-395`, `src-tauri/crates/gamelib-info/src/sysinfo/pci_ids.rs:136-168`, `src-tauri/crates/gamelib-launch/src/prepare/deps.rs:246-251`
**Issue:** `prepare_launch` awaits `system_info_text()` before it returns, and that read runs one lookup per name serially: with sub-ids a GPU costs a sub-key lookup, a plain-key lookup and a vendor lookup. Each is bounded at `LOOKUP_TIMEOUT` (5 s) and a black-holed resolver (a firewall dropping UDP/53, a captive network) reaches the bound every time, so one GPU can hold the launch for 15 s and two GPUs for 30 s. The per-server 2 s plus three servers is 6 s, so the third server never gets its slot (`left.min(PER_SERVER_TIMEOUT)` shortens it to 1 s). `ServerFailed` results are not remembered, so every fresh process repeats this. After the read the GPU list is cached in memory for the life of the process (cache.rs: no time limit), so a first read with no network leaves the GPU list empty and `steamDeckInfo` at `isDeck:false` (the Deck check needs `gpus.first()`) until restart. The TS shared the cache lifetime, but its overall exposure was never on the launch path's critical section.
**Fix:** put one deadline over the whole GPU naming step (for example 5 s total in `populate_device_and_vendor_name`, falling back to the names already cached), and do not cache a `SystemInformation` whose GPU list was emptied by a resolver failure (return it, but skip `cached = Some(...)` so the next read retries).

### WR-04: The "use another wine?" dialog blocks the worker thread and cannot be cancelled by shutdown

**File:** `src-tauri/src/launch_dispatch.rs:46-63`, `src-tauri/crates/gamelib-launch/src/prepare/dialogs.rs:23-29`, `src-tauri/crates/gamelib-launch/src/lib.rs:316-332`
**Issue:** `LaunchDialogs::ask` is a synchronous trait method called from inside `async fn check_wine_before_launch`. `ShellDialogs::ask` blocks in `rpc_dialog_message` (`rx.recv()`) until the user answers. While the thread is parked, the `tokio::select!` in `guarded` that races `token.cancelled()` never gets polled, so the `launch` registrant stays held until the user clicks, and shutdown's drain times out (3.5 s) instead of cancelling the op. This is the shape the Rust shutdown contract warns about (a registrant held on in-flight work that does not watch the token).
**Fix:** make `ask` return a future (or run it through `tokio::task::spawn_blocking` and `select!` the join handle against the shutdown token, treating cancellation as a dismissal `None`). A dismissal already means "No", so a shutdown mid-dialog degrades correctly.

## Info

### IN-01: macOS host facts run four blocking `sysctl` children on the async executor, with no timeout

**File:** `src-tauri/crates/gamelib-info/src/sysinfo/host.rs:167-206`
**Issue:** `cpu_models()` (two calls), `release()` and `total_mem()` each run `Command::new("/usr/sbin/sysctl")....output()` synchronously, and `probe_parts` calls them from an async fn, so they run on a tokio worker thread (the launch crate's runtime has only two). CLAUDE.md allows short synchronous probes on `Command::output()`, so this is not a convention breach, but a wedged `sysctl` (rare) would hold the worker indefinitely, and `memory.rs` already runs `sysctl -n vm.pagesize` through `gamelib-proc` with a 30 s bound, so the same binary is spawned two different ways.
**Fix:** read the four values once through `run_probe` (or in a `spawn_blocking`), or use `libc::sysctlbyname` for `machdep.cpu.brand_string`, `hw.logicalcpu`, `kern.osrelease`, `hw.memsize`, which needs no child at all.

### IN-02: Zone-scoped IPv6 nameservers are skipped, and when they are the only ones the lookup silently goes to 127.0.0.1

**File:** `src-tauri/crates/gamelib-info/src/sysinfo/dns.rs:227-238,378-387`
**Issue:** `parse_resolv_conf` drops `fe80::1%en0`-style addresses (they fail `IpAddr::parse`), and `SystemTxtResolver::lookup` then substitutes `127.0.0.1:53` when the list is empty. A machine whose only listed resolver is a scoped link-local address is thus sent to a loopback port nothing listens on, so every name fails with a connection-refused `ServerFailed` and the GPU list comes out empty. Node's c-ares handled the scope.
**Fix:** parse the zone (`SocketAddrV6::new(ip, 53, 0, scope_id)` with `if_nametoindex`), or distinguish "no `nameserver` lines" (fall back to loopback) from "lines present but all skipped" (return `None` without querying).

### IN-03: `install_galaxy_dummy` does blocking filesystem work inside an async fn

**File:** `src-tauri/crates/gamelib-launch/src/prepare/wine_finish.rs:163-181`
**Issue:** `destination.exists()`, `std::fs::create_dir_all` and `std::fs::copy` (the bundled `GalaxyCommunication.exe`) run directly on the executor. The copy is small, so this is not a correctness issue, but it is the one place in the crate that does synchronous I/O in the async path while the rest (`installed_games::update`, the settings reads) uses the same pattern, so it is cheap to normalise with `tokio::fs` or `spawn_blocking` the next time the file is touched.
**Fix:** `tokio::fs::copy(&source, destination).await.map_err(|_| ())?` (the `fs` feature is already enabled in `gamelib-launch/Cargo.toml`).
