### IN-04: `SetupEnvView` still rejects `null` and wrongly-typed values the TS tolerated

**File:** `src-tauri/crates/gamelib-wine/src/wine_cmd/env.rs:113-121`
**Issue:** The doc comment says the view mirrors the three fields the pre-port TS read, and the CR-01 fix is meant to make `setupEnvVars` as tolerant as the TS. It is tolerant of a missing or unknown key, but not of a present value of the wrong type. Reproduced against the built CLI, each of these answers `launch_setup_env_vars:bad-args` (exit 2): `{"nvidiaPrime":null}`, `{"enviromentOptions":null}`, `{"enviromentOptions":[{"key":"A"}]}` and `{"showFps":"true"}`. The TS read each with a plain truthiness test (`if (gameSettings.nvidiaPrime)`, `if (gameSettings.enviromentOptions)`), so a `null` was treated as absent and the launch went on; now a bad-args reject aborts the launch. I cannot show the app writing such a value (the defaults are `false` and `[]`, and `JSON.stringify` omits `undefined`), so this is a hand-edited `GamesConfig/<app>.json` case, the same class as the deferred WR-02 (gamescope strings), which is why it is Info.
**Fix:** If the TS leniency is the goal, decode the three fields with a small helper that maps `null` to the default, for example `#[serde(default, deserialize_with = "null_as_default")]` for `nvidia_prime`, `show_fps` and `environment_options` (`Option::<T>::deserialize(d).map(Option::unwrap_or_default)`). If the strictness is deliberate, say so in the `SetupEnvView` doc comment so it is not mistaken for the TS behaviour. The `Default` derive on the struct has no user and can go in the same edit.

### IN-05: `check_wine`'s `wine_of` tolerates a stored wine with no `name`, but every later decode requires one

**File:** `src-tauri/crates/gamelib-launch/src/prepare/check_wine.rs:129-150` against `src-tauri/crates/gamelib-wine/src/wine_cmd/mod.rs:44-46`
**Issue:** `wine_of` keeps the six declared keys and supplies an empty `name` when it is absent ("`name` as text (empty when absent)"), so a stored wine without a `name` passes the Wine check. `WineInstallation.name` is still a required `String`, so the next step, `launch_prepare_wine_begin` (`prepare/wine_begin.rs:157`, a `GameSettingsView` decode), and `launch_setup_wine_env_vars` answer `bad-args` for the same wine. Reproduced: `launch_setup_wine_env_vars` with `"wineVersion":{"bin":"/x","type":"wine"}` gives `bad-args`. WR-01 closed the unknown-key half of this tolerance gap; the missing-field half is still open. TS `WineInstallation.name` is required and discovery always sets it, so I cannot show a real stored wine without one, hence Info.
**Fix:** Give the field the same default `wine_of` already applies: `#[serde(default)] pub name: String`. Then the stored-value tolerance is one rule across `wine_of`, `persisted_wine` and the serde decode, and a `name`-less wine reaches the wine check's own fallback instead of a bad-args rejection mid-launch.
