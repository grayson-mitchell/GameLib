## Fixed Issues

### IN-04: `SetupEnvView` still rejects `null` and wrongly-typed values the TS tolerated

**Files modified:** `src-tauri/crates/gamelib-wine/src/wine_cmd/env.rs`
**Commit:** 371cc3051
**Applied fix:** Added a `null_as_default` serde helper (`Option::<T>::deserialize(d).map(Option::unwrap_or_default)`) and applied it with `deserialize_with` to `nvidia_prime`, `show_fps` and `environment_options` of `SetupEnvView`, so a present `null` reads as the field default, as the TS truthiness tests did. A wrongly typed value (`"showFps":"true"`, an `enviromentOptions` entry missing `value`) is still refused; the `SetupEnvView` doc comment now says so. Removed the unused `Default` derive on the struct (the review noted it had no user). Added two unit tests next to the type: null fields decode as absent, and set values are kept while wrong types are refused.

### IN-05: `check_wine`'s `wine_of` tolerates a stored wine with no `name`, but every later decode requires one

**Files modified:** `src-tauri/crates/gamelib-wine/src/wine_cmd/mod.rs`
**Commit:** 1eac18313
**Applied fix:** `WineInstallation.name` now carries `#[serde(default)]`, matching the empty-name fallback `wine_of` already applies, so a name-less stored wine that passes the Wine check also decodes in `prepare_wine_begin` and `setup_wine_env_vars` instead of answering bad-args mid-launch. Updated the type's doc comment and added `a_wine_installation_without_a_name_decodes_with_an_empty_one`. Serialisation is unchanged (`name` is still always written), and the renderer-facing `parse_wine_installation` allowlist is untouched.
