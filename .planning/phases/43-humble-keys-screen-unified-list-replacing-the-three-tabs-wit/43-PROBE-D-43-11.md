## VERDICT and mapping used

**VERDICT:** CANDIDATE A REJECTED

Mapping used (per this plan's Task 3 table): the captured line matches
`reveal rejected by server success=false keyPresent=... errorMsgLength=N` exactly →
`SELECTED BRANCH: candidate B` (Phase 40 embedded browser), per D-43-11's stated fallback
order.

**The single most important finding:** `43-CONTEXT.md`'s stated unknown for candidate A was
that `RevealResponseSchema` "expects a key value and may not parse a keyless response." That
predicted failure mode did **not** occur. The response body parsed cleanly —
`success=false`, `keyPresent=false`, and `errorMsgLength=32` are all fields read off a
successfully-parsed body, not a `describeSchemaFailure` diagnostic. Candidate A fails on a
Humble **server policy decision** (a definitive denial), not on client-side schema
incompatibility. The predicted failure mode was wrong; the actual one is different in kind.

**SELECTED BRANCH:** candidate B

Rationale: candidate A is measured-dead for `gog_keyless` (a real, live entitlement with all
documented preconditions satisfied was definitively denied by the server). Candidate B (Phase
40 embedded store browser) keeps the operator in-app, which is what they explicitly asked for
before accepting a path that leaves the app, and `tauri-embedded-store-browser.md` confirms the
embed inherits the process-wide cookie jar, so the Humble session established by the login
webview carries over without a second auth step.

### Rejected branches, with reasons

- **Candidate A (reuse the reveal endpoint):** rejected by direct measurement, 2026-09-10. A
  real `gog_keyless` entitlement whose preconditions (`UNREVEALED`, no ownership badge, no
  prior reveal annotation) were all independently verified was sent through the exact,
  already-shipped `revealKey()` path and the server returned a definitive denial
  (`success=false`). Not a schema failure — the body parsed. Implementation consequence: none
  required, since candidate A is not being built; no change to `revealKey`'s
  `schema_error`/`rejected_by_server` classification is needed for this outcome (contrast with
  the plan's other branch, which would have required changing that classification).
- **External-browser fallback:** rejected as the primary path because it is the exact outcome
  D-43-11 was raised to avoid — the operator explicitly asked for an in-app path before
  accepting one that leaves the app. Candidate B is available, and the Phase 40 spike findings
  already prove the embed's cookie-jar inheritance. Retained as the documented last-resort
  fallback in `43-UI-SPEC.md`'s CONDITIONAL table if candidate B hits the `hide()`-before-modal
  compositing problem in practice during plan 43-09's implementation.

## Observed defect (recorded here; not fixed by this plan — no source file is touched)

server denying the request and no game being granted:

- Cache state moved `UNREVEALED` → `REVEALED` after the post-attempt sync.
- `humble_revealed.json` gained an entry `racine_gog` → `{"revealedAt":1788999862004}`, written

- Consequence: because `doRevealKey` (`library.ts:1213-1250`) refuses any key whose state is

  attempt 1's credential-guard abort) does not hold for attempt 2's server-denial path.
- Scope note: this defect is out of scope for this plan (`43-03`'s only file is this probe

## Residual unknowns

1. **Humble's actual error message is redacted by design (C5) and is the single most
   diagnostic datum we don't have.** We know `errorMsgLength=32` and nothing else. Whether the
   server said "already redeemed," "not eligible," "link your GOG account first," or something
   else entirely is unmeasured. The C5 wall working correctly — never logging `error_msg`
   verbatim because it may echo a key value — is what cost us this datum. This is the
   redaction discipline functioning as designed, not a bug in it.
2. **n=1.** One entitlement, one account, one successful network attempt. Whether all
   `gog_keyless` entitlements behave this way, or whether this one denial was specific to some
   property of this account or order, is unproven. The sample is now unrepeatable: the
   `humble_revealed.json` annotation moved it out of `UNREVEALED`, so it cannot be re-attempted
   through GameLib even if local state is restored to look "clean" — see Observed defect above.
3. **Behaviour when the GOG↔Humble account link is ABSENT stays unmeasured** — there is no
   second, unlinked test account available. This is unmeasurable with the resources at hand,
   not an oversight. It also remains a live alternative explanation for the denial: whether the
   operator's Humble account has a GOG account linked on Humble's side was never independently
   confirmed as the *cause* of the rejection (unknown 1, above, subsumes this — we cannot read
   the server's stated reason either way).
4. The sample is consumed by this probe. Any future question about `gog_keyless` behaviour
   needs a newly-acquired entitlement; none remains for re-testing a different question.
