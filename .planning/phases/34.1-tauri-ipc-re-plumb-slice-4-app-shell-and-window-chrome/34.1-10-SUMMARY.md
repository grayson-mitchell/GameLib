## Reconciled Mechanism (for plan 34.1-14's reference)

- `tauri.conf.json`'s `titleBarStyle` declares ONLY the creation-time state (before any JS has run) — value is `"Visible"`, matching `framelessWindow`'s default of `false`, so the default user's pre-paint apply is a true no-op.
- `setTitleBarStyle` (via `applyFramelessDecorations`) owns every state after creation: the pre-paint apply from `tauriAttach.ts`, the post-hydration re-apply from `index.tsx` (CR-02), and every user toggle.
- On macOS: `framelessWindow: true` -> `setTitleBarStyle('overlay')`; `framelessWindow: false` -> `setTitleBarStyle('visible')`. Native traffic lights are present in BOTH states — that is the whole point of this reversal. `setDecorations` is never called on macOS.
- On Windows/Linux: unchanged — `setDecorations(!resolved)` remains the only mechanism.
- The only user who experiences a post-creation transition is one who had `framelessWindow` ON from a prior session (created `visible`, then driven to `overlay`). This is the SAME timing shape the current code already has, and UAT test 3 measured that shape as flip-free on this hardware — a strong empirical prior, **not a measurement of the new call**. It is not claimed as observed here.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 - Blocking issue] `framelessRuntime.test.ts`'s pre-existing (un-retuned) assertions crashed the test process under Task 2 alone, on this specific host**
- **Found during:** Task 2 verification (`npx jest src/preload --silent`)
- **Issue:** This Jest environment's Node runtime (v26.2.0) exposes a real, built-in `navigator.platform` reflecting the actual host OS — on this macOS dev machine it reports `"MacIntel"`. Before Task 3's retune, the pre-existing `applyFramelessDecorations` tests had no platform stub at all, so once Task 2 landed the macOS branch, those tests silently started exercising the macOS branch on this host. One test in particular (`a setDecorations rejection is caught and warned...`) creates a pre-rejected `Promise.reject(new Error('denied'))` for `mockWindow.setDecorations`, expecting `applyFramelessDecorations()` to call and `.catch()` it — but on macOS the function now returns early via the `setTitleBarStyle` branch without ever calling `setDecorations`, leaving that promise's rejection permanently unhandled and crashing the Jest worker process (`Error: denied`, uncaught, Node process exit).
- **Fix:** Implemented Task 3 (the plan's own designated fix for exactly this class of problem) immediately, in the same session, before running Task 2's own `npx jest src/preload --silent` verification to completion — so the working tree was never left in a state with a crashing test suite between commits. Task 2 and Task 3 remain two separate atomic commits (`1ff87f938`, `5651e4f4e`) per the plan's file-scoped task boundaries; only the *sequencing within this execution session* was reordered (Task 3's test-file edits were authored before Task 2's own final verification run) to avoid ever leaving a broken intermediate state in the repository.
- **Files modified:** `src/preload/__tests__/framelessRuntime.test.ts` (Task 3's designated file — no files outside Task 3's plan scope were touched for this fix)
- **Verification:** `npx jest src/preload --silent` — 126/126 passed after Task 3 landed; confirmed the identical crash reproduces against the ORIGINAL (pre-Task-2) file when Task 2's mac branch alone is present, via a temporary `git checkout -- src/preload/api/tauriWindowChrome.ts` sanity check (test passed against unmodified original code, confirming the crash was newly introduced by Task 2's mac branch interacting with the unstubbed test, not a pre-existing flake)
- **Committed in:** `5651e4f4e` (Task 3's own commit — this was Task 3's designated work, not scope creep; only the *within-session ordering* is the deviation, not the file scope)
