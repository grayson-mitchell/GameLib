## Tests

1. **Window buttons** — `pnpm tauri:dev`. With `framelessWindow` on, click minimize, then
   maximize, then unmaximize, then close in GameLib's own custom titlebar.
   Expected: each click causes the real OS window to minimize / maximize / restore / close,
   exactly as the equivalent native title-bar button would.
   result: pass — verified live 2026-07-25. Confirms the CR-03 fix (restore button was
   unreachable before it: nothing emitted maximize state under Tauri, so the button
   re-maximized instead of restoring).

2. **Frameless toggle** — toggle `framelessWindow` on in Settings.
   Expected: the window chrome changes (native decorations disappear, GameLib's own titlebar
   appears) without requiring a restart. On a fresh profile with no settings yet written, the
   window starts DECORATED — the Electron default — not frameless.
   result: pass — verified live 2026-07-25. The on-toggle re-apply (a deliberate superset of
   Electron parity, whose own toggle says "requires restart") works without a restart.

3. **No startup flip** — with `framelessWindow` already on from a prior session, restart the app
   (`pnpm tauri:dev`).
   Expected: the window does not visibly flip from decorated to undecorated partway through
   load — decorations are applied pre-paint, not after the first frame.
   result: pass — verified live 2026-07-25. Confirms the CR-02 fix. Before it, the pre-paint
   read always saw an empty store snapshot (static import ran before `hydrateStoreSnapshot()`'s
   top-level await), so a frameless user got the native titlebar AND the overlay controls.

4. **Frameless drag — highest-risk unobserved item.** With `framelessWindow` on, drag the
   sidebar to move the window; double-click the sidebar to toggle maximize/restore.
   Expected: dragging the sidebar moves the real OS window; double-clicking it maximizes or
   restores it, mirroring native titlebar drag/double-click behavior.
   **This is explicitly flagged as the highest-risk unobserved item in the whole slice.**
   Whether this works at all depends on whether the platform webview exposes
   `-webkit-app-region` in computed styles — plan 34.1-03 implements a `.Sidebar`-selector
   fallback for webviews that don't expose it, but **neither the primary path nor the fallback
   has ever been run against a real webview.** This is the single most likely item in this
   document to fail outright.
   result: pass — verified live 2026-07-25. **The highest-risk item in the slice passed.**
   Both sidebar drag and double-click-to-maximize work against a real webview, so the
   `-webkit-app-region` path (or its `.Sidebar` fallback) does function under WKWebView.
   This item is no longer unobserved.

5. **Zoom** — change the zoom slider while the app is running, including on a
   sub-1200px-wide display where the DPI compensation branch applies.
   **Location correction (found during this UAT):** the zoom control is NOT in Settings — it is
   on the **Accessibility** screen, a slider labelled "Zoom (N%)", range 60–200 step 10.
   `GlobalState.setZoomPercent` debounces 500ms before calling `setZoomFactor(percent/100)`.
   The original wording of this item sent the tester to the wrong screen.
   Expected: the UI visibly scales to match the new zoom level, including on the narrow display
   where the level→scale-factor conversion (`Math.pow(1.2, level)`) must also account for the
   DPI compensation branch.
   result: pass — verified live 2026-07-25 across 200% / 60% / 100%.

6. **Tray** — start the app and observe the system tray/menu bar. Click the tray icon. Use each
   of the two menu items (Show GameLib, Quit). Toggle the dark-tray-icon setting.
   Expected: a tray icon appears at startup. Clicking it shows/focuses the main window. "Show
   GameLib" shows/focuses the window; "Quit" exits the app. Toggling the dark-tray-icon setting
   swaps the tray image within roughly 500ms (the collapsing settle-timer window
   `changeTrayColor` uses).
   result: issue — verified live 2026-07-25. Sub-items 1–3 PASS: the tray icon appears at
   startup, clicking it shows/focuses the main window, and both menu items (Show GameLib,
   Quit) work. Sub-item 4 FAILS.
   reported: "1-3 yes, dark tray icon does nothing"
   severity: major
   note: This is the slice's ONLY new Rust arm (`tray_set_icon`). The tray itself is proven
   working, so the failure is isolated to the icon-swap path — not tray creation.

7. **Gamepad** — connect a game controller. Navigate the `/console` routes using: d-pad and left
   stick (all four directions), Tab/Shift+Tab, the B/back button, the right stick (scroll), and
   the stick clicks (activate).
   Expected: d-pad and left-stick moves focus in the expected direction with no wrap. Tab/
   Shift+Tab traverse focusable elements forward/backward. B/back navigates back. The right
   stick scrolls the page — **explicitly the sign convention most likely to be inverted**, check
   the scroll direction matches the stick direction, not the reverse. Stick clicks (left/right
   click equivalents) activate the element currently under focus/cursor.
   result: skipped
   reason: No controller available at the time of the 2026-07-25 session.
   note: STILL UNVERIFIED. `gamepadAction` (D-10) is the one channel in this slice whose entire
   implementation is a from-scratch rewrite — Electron injected synthetic input via
   `webContents.sendInputEvent`, which has no Tauri equivalent, so all twelve action cases plus
   a hand-written geometric nearest-in-direction focus algorithm were reimplemented as pure DOM
   dispatch. It is the largest untested surface left in the phase. Two specific risks to check
   when a controller is available: (a) the right-stick scroll sign convention, most likely to be
   inverted; (b) Up/Left directional focus from a cold start with nothing focused, which was
   broken as WR-02/WR-03 and fixed unit-only during code review.

8. **Child windows** — click a ProtonDB, AppleWiki, or AreWeAntiCheatYet link from a game's
   detail page. Open the About window (from wherever it's triggered in the UI).
   Expected: clicking an external-content link opens a real, separate OS window showing that
   page. Opening About shows a window with the REAL app version string (e.g. matching
   `package.json`), never `unknown` or `0.0.0`.
   result: skipped
   reason: Not attempted in the 2026-07-25 session.
   note: STILL UNVERIFIED, and this one carries a security-relevant claim. `createNewWindow`
   loads renderer-supplied REMOTE content into a child `WebviewWindow`, and Tauri has no
   `<webview>` isolation boundary. The design intent is that child windows (labelled `about`
   and `external-<n>`) match NO capability and therefore get ZERO Tauri command access, because
   the capability stays scoped `"windows": ["main"]`. The code reviewer verified this holds
   statically (labels are a monotonic counter, never url-derived; `main` cannot be re-created),
   but it has never been confirmed against a running window. Also unconfirmed: the About
   version string, which would read `0.0.0` in packaged builds before the 34.1-04 fix.

9. **macOS traffic lights vs custom buttons** — on macOS, with `framelessWindow` on, look at the
   titlebar.
   Expected: this is a deferred aesthetic call (D-06/D-15), not a pass/fail check — decide
   whether GameLib's own custom buttons (used on every platform under Tauri, per D-06's declared
   divergence from Electron's native macOS traffic lights) look acceptable, or whether this
   needs revisiting.
   result: pass — accepted as-is 2026-07-25. D-06's divergence stands; the aesthetic question
   is CLOSED. No further polish on frameless chrome.
   decision: **Stop investing in the frameless option.** Raised by the user during this session:
   the feature's value is thin relative to its cost. It defaults to `false`, is a standalone
   opt-in Settings toggle, and is NOT wired to ConsoleMode (checked — no TV/controller-mode
   dependency). Against that, three of the code review's eleven findings are frameless-only
   (CR-02 pre-paint decorations, CR-03 restore button — which exists only because a custom
   titlebar must track maximize state the OS otherwise tracks for you, WR-01 drag-region
   selector), and test 4 — the highest-risk item in the whole slice — is frameless-only. The
   drag region is bespoke machinery (`-webkit-app-region` is Chromium-only, so WKWebView needed
   document-level mousedown/dblclick handlers plus a `.Sidebar` fallback) re-implementing what
   the OS provides free. On macOS it additionally costs the traffic lights.
   Resolution: NOT removed now — it works, the risky part passed UAT, and removal would mean
   new churn across `main_window.ts`, `UseFramelessWindow.tsx`, `tauriAttach.ts` and the
   frameless suites on an already-large branch. Instead: no further investment. If frameless
   causes friction in a later slice (34.2–34.5), drop the feature at that point rather than
   paying to polish it. Candidate for removal, not a committed removal.

10. **Electron parity** — `npm start` (the Electron build, not Tauri). Exercise the themes,
    language, About, releases, and changelog surfaces.
    Expected: all of these surfaces behave exactly as they did before this phase — confirming
    the D-07 `main.ts` extraction (moving six handler bodies into `src/backend/appshell/*.ts`)
    changed no observable Electron behavior.
    result: pass — verified live 2026-07-25. **This closes the phase's single largest evidence
    gap.** 34.1 is the first slice to modify `src/backend/main.ts`, which made the
    additive/reversible invariant BEHAVIORAL rather than textual; until this run, no one had
    launched the Electron build since the extraction. Themes, language, About, releases and
    changelog all behave as before.
    incident (not a phase defect): the first `npm start` attempt failed with
    `dyld: Library not loaded: @rpath/Electron Framework.framework/Electron Framework` —
    `node_modules/electron/dist/Electron.app/Contents/Frameworks/` was empty. This is the
    project's known recurring broken-Electron-install issue, unrelated to 34.1. Repaired by
    overwrite-extracting the already-cached
    `~/Library/Caches/electron/electron-v41.1.1-darwin-arm64.zip` into
    `node_modules/electron/dist/` (no re-download); binary then reported `v41.1.1` and the
    retry passed.

## The unavoidable gap, restated

Every automated test in this phase proves **wiring**: that the right Tauri API was called with
the right arguments. **None proves the window on screen actually did the thing.** Nobody has run
this build and looked at it. The frameless toggle applying, the titlebar buttons moving the
window, the tray appearing and changing colour, gamepad navigation working, and how macOS traffic
lights versus custom buttons look are all **unobserved**. `cargo check` proves the tray code
compiles; it proves nothing about a tray existing. Do not read "wired and unit-proven" as "seen
working" — that is exactly how G-30-02 was declared fixed twice while the live build hung. Read
this document together with `34.1-PORTED-CHANNELS.md` §6 — neither artifact should be read in
isolation, because either one alone could leave a later reader with the wrong impression.
