  - the `tray-icon` Cargo feature (currently `features = []`)
  - a `TrayIcon` built at setup with a tooltip, the dark/light icon variants embedded at

    registration reading `darkTrayIcon` from `GlobalConfig`, plus one initial sync

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| sidecar → Rust `tray_set_icon` | The sidecar can ask the shell to swap the tray image. The payload is a single boolean derived from local config, not from the renderer. |
| renderer → sidecar `changeTrayColor` | Any script in `main` can trigger a tray icon refresh. It carries no attacker-controlled data — the icon source is compile-time embedded. |
| compile-time icon bytes | The tray images are `include_bytes!`-embedded, so no runtime path is resolved and no file can be substituted post-build. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-34.1-21 | Tampering | An attacker substituting the tray icon file at runtime to spoof a different app in the OS tray | mitigate | Icons are `include_bytes!`-embedded at compile time; no runtime path resolution exists. This also sidesteps this repo's recurring publicDir/`getAppPath` path-resolution failures. |
| T-34.1-22 | Denial of Service | A tray build failure or a bad icon decode panicking out of `.setup()` and killing the whole shell | mitigate | Task 1 forbids `unwrap()`/`expect(` in the tray block and requires `tray_image` to fall back to the light variant on decode failure; Task 3 asserts the absence of `unwrap`/`expect` by source gate. |
| T-34.1-23 | Denial of Service | Unbounded `setTimeout` accumulation from a renderer spamming `changeTrayColor` | mitigate | Task 2 requires a single module-level timer handle that is cleared and rescheduled; Task 3 asserts repeated sends within the window collapse to one invoke. |
| T-34.1-24 | Elevation of Privilege | Granting `core:tray:*` to the renderer, exposing tray creation/removal to remote content in `main` | mitigate | No tray capability is granted at all — the tray is Rust-side only, and Task 1's acceptance criteria assert `capabilities/default.json` is untouched by this plan. Consistent with Phase 33 WR-03's minimal-exposure stance. |
| T-34.1-25 | Repudiation | The tray "feature not port" scope silently expanding into the full Electron menu | mitigate | Task 3's negative-bound source gate fails on `recent`/`dock`/`Reload`/`Debug`/`openDevTools` appearing in `main.rs`. |
| T-34.1-SC | Tampering | npm/pip/cargo installs | mitigate | No new crate and no new npm package. The only manifest change is enabling an already-vendored optional feature (`tray-icon`) on the existing `tauri` dependency, whose source is already in `Cargo.lock` at 2.11.5. No registry fetch of an unaudited package occurs. |
</threat_model>
