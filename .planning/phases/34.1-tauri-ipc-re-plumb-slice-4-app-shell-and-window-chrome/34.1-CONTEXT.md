# Phase 34.1: Tauri IPC re-plumb slice 4 — app shell and window chrome - Context

**Gathered:** 2026-07-25
**Status:** Ready for planning

<domain>
## Phase Boundary

Port the **app shell and window chrome** IPC cluster onto the Tauri build, following
SEAM.md's Incremental-Port Checklist. This is the fourth re-plumb slice, and the
**first one whose source has no importable module**: 28 of the 34 channels are
registered directly inside `src/backend/main.ts` (L302–L1541), the Electron entry
module the sidecar can never import (it calls `app.whenReady()`, constructs
`BrowserWindow`, and wires `app.on(...)` at module scope). Every prior slice ported a
cluster module (`downloadqueue.ts`, `config.ts`); this one must first **extract**.

It is also the first slice where the honest answer to "where does this channel run?"
is sometimes **not the sidecar**. Window chrome is a renderer-owned concern under
Tauri, and this phase establishes that as a declared third port kind.

**Inventory note:** the slice is **33 channels, not 34** — `callTool` is reassigned to
Phase 34.5 (**D-14**). `.planning/IPC-PORT-INVENTORY.md` must be updated in both lists
so the Phase 35 completion gate stays honest.

**In scope:**
- **Window chrome renderer-side** (**D-01**): `minimizeWindow`, `maximizeWindow`,
  `unmaximizeWindow`, `closeWindow`, `isMaximized`, `isMinimized`, `isFullscreen`,
  `setFullscreen`, `isFrameless`, `setZoomFactor` implemented in the Tauri preload
  factory against Tauri's JS window API — no sidecar hop, no new Rust arms.
- **Runtime `framelessWindow` support** (**D-04/D-05**): read the setting at startup
  and on change, apply via `setDecorations()`; GameLib's own titlebar buttons on all
  three platforms when on; default stays **decorated**, matching Electron.
- **Handler-body extraction** (**D-07/D-08**): pull the 28 `main.ts` handler bodies
  into shared, Electron-free modules; `main.ts` keeps its `addHandler`/`addListener`
  lines as one-line delegations; a new curated sidecar module registers the same
  functions on `electronStub`'s `ipcMain`.
- **Sidecar-ported remainder**: themes (`getCustomThemes`/`getThemeCSS`/`getCustomCSS`),
  app metadata (`getHeroicVersion`/`getCurrentChangelog`/`getLatestReleases`),
  `isIntelMac`, `abort`, `set-connectivity-online`, `changeLanguage`, `notify`,
  `quit`, `openReleases`, `openCustomThemesWiki`, `openWebviewPage`.
- **`gamepadAction` re-implemented renderer-side** (**D-10**) — synthetic DOM
  events/focus moves replacing `webContents.sendInputEvent`.
- **A real Tauri tray** (**D-11**) so `changeTrayColor` acts on something.
- **`createNewWindow` + `showAboutWindow` as genuine Tauri WebviewWindows** (**D-12**).
- `34.1-PORTED-CHANNELS.md` declared list + SEAM.md §3→§1 move + the
  `IPC-PORT-INVENTORY.md` correction for `callTool`.

**Explicitly OUT of scope:**
- The **`<webview>` login story** — navigation interception, OAuth redirect capture,
  session/cookie access. Owned by **Phase 34.4** (Humble), which has a real flow to
  test against; Phase 33 **D-09** already recorded `session` as an accepted gap
  (**D-12**). `getWebviewPreloadPath` returns a declared-empty value here.
- **`callTool`** — reassigned to Phase 34.5 (**D-14**).
- **`lock`/`unlock`** real behavior — `powerSaveBlocker`, already accepted as a logged
  no-op by Phase 33 **D-08**; carried forward unchanged (**D-13**).
- **`setTitleBarOverlay`** real behavior — no native overlay survives D-05's
  own-buttons-everywhere choice; declared logged no-op (**D-13**).
- **Any live/hardware gate as a phase-closing condition** — unit-proven, live UAT
  deferred (**D-15**).
- Any change to the Electron build's *behavior*. `npm start` and `pnpm tauri:dev` must
  both work. Note this slice **does touch Electron files** (the D-07 extraction) — the
  invariant is behavioral, not textual, and that is a first for this series.

<decisions>
## Implementation Decisions

### Window-control transport (the architectural headline)

- **D-01 — Window chrome executes RENDERER-SIDE via Tauri's JS window API.** The Tauri
  preload factory (`src/preload/tauriAttach.ts` → `./api`) implements
  minimize/maximize/unmaximize/close/isMaximized/isMinimized/isFullscreen/
  setFullscreen/isFrameless/setZoomFactor directly against `getCurrentWindow()` —
  **no sidecar hop, no new `dispatch_rust_channel` arms.** `withGlobalTauri: true` is
  already set. Rationale: this is where Tauri intends window control to live, it is the
  lowest-latency path for a button click, and it needs zero Rust work.
  Rejected: sidecar → new Rust channels (consistent with `dialog_message`/
  `notification_show`/`app_exit` and with Phase 29 D-01's "Rust is the platform seam",
  but pays a cross-process round-trip for a titlebar click and adds ~8 Rust arms);
  hybrid reads-local/actions-via-Rust. **Accepted cost:** `window.api` now has two
  genuinely different implementations across builds for these channels — acceptable
  because Phase 35 deletes the Electron half.

- **D-02 — Renderer-side implementation COUNTS AS PORTED for the Phase 35 gate.**
  `34.1-PORTED-CHANNELS.md` declares these with a **third kind** —
  `renderer-side (Tauri JS)` — alongside the existing `sidecar invoke/send` and
  `rustInvoke` kinds. The gate reads "the channel has real behavior under Tauri," not
  "the sidecar owns it." The sidecar registers nothing for them; the
  `UNPORTED_CHANNEL_MARKER` path is simply never reached because `window.api`
  short-circuits first. Rejected: adding sidecar logged-no-op guards (a stray call is
  not a real risk while the preload short-circuit is the only caller path); rewriting
  the inventory's gate definition mid-flight.

- **D-03 — The renderer-side principle is scoped STRICTLY to window chrome.**
  Everything else in the slice — `notify`, `quit`, `openReleases`,
  `openCustomThemesWiki`, `openWebviewPage`, themes, version/changelog, `abort`,
  `changeLanguage`, `set-connectivity-online` — keeps the sidecar seam. Rationale:
  Phase 33's **WR-03 minimal-exposure** stance is binding — `notification:default` was
  deliberately NOT granted so the renderer holds no notification surface, and reversing
  that here for convenience would undo a considered security decision. Rejected:
  "any Tauri-owned primitive goes renderer-side" (widens renderer capability grants and
  reverses Phase 33); the same, plus routing quit/open* to existing Rust arms (that
  part is right and is captured under Claude's Discretion below, but it is an
  implementation detail, not a scope principle).

- **D-04 — Capabilities: explicit per-command allow-list, composition verified first.**
  Grant exactly the commands used (`core:window:allow-minimize`, `allow-maximize`/
  `allow-toggle-maximize`, `allow-unmaximize`, `allow-close`, `allow-start-dragging`,
  `allow-set-fullscreen`, `allow-is-fullscreen`, `allow-is-maximized`,
  `allow-is-minimized`, `allow-set-decorations`, plus
  `core:webview:allow-set-webview-zoom`) — nothing broader — and extend the identifier
  `description` in `src-tauri/capabilities/default.json` to explain each, matching how
  `notification:allow-is-permission-granted` and the scoped `shell:allow-execute` are
  already documented there.
  **Load-bearing rationale:** capabilities are scoped `"windows": ["main"]`, and
  GameLib renders untrusted remote surfaces (store search now; Humble login in 34.4).
  Under Tauri there is no `<webview>` boundary, so remote content in the `main` window
  inherits whatever that capability grants — the same hazard the file's existing
  description already names when explaining why `dialog:allow-open` was refused.
  **MANDATORY planner instruction:** before finalizing the list, verify what
  `core:window:default` *actually* contains in the installed Tauri version and record
  it in the plan. It is believed to be the read-only getter set (in which case the
  explicit mutation grants are required regardless), but that was not verified during
  discussion and must not be taken on the discussing agent's recollection. Rejected:
  `core:window:default` wholesale; `default` + explicit mutations.

### Window chrome shape

- **D-05 — Honor `framelessWindow` at RUNTIME; default stays decorated.**
  **Correction established during discussion, load-bearing:** framelessness in Electron
  is **not** a platform property — it is an off-by-default user setting,
  `settings.framelessWindow`, read at window-creation time (`main_window.ts:43-53`),
  and `isFrameless()` reads persisted `window-props` (`main_window.ts:15`). So "match
  Electron" means **make the setting work**, with **decorated as the default** — it
  does NOT mean "ship frameless." Implementation: read the setting at startup and call
  `window.setDecorations()` to match, re-applying when the user toggles it. Rejected:
  decorated-only with the setting as a logged no-op (the Settings toggle would do
  nothing); static `decorations:false` in `tauri.conf.json` (ships a different default
  than Electron and makes the toggle lie). **Planner note:** apply decorations before
  first paint or the window visibly flips on startup.

- **D-06 — When frameless is ON: GameLib's own buttons on ALL platforms, one code
  path.** `decorations: false` everywhere; the frontend's existing custom titlebar
  renders unmodified. **Why this falls out of the platform, not preference:** under
  Tauri, `navigator.windowControlsOverlay` is undefined (WKWebView/WebView2 don't
  expose it — Phase 33 gate gap-fix #3 guarded exactly that read at
  `frontend/index.tsx:213`), so
  `showOverlayControls = isFrameless && !hasNativeOverlayControls` (`App.tsx:43`)
  evaluates **true on every platform** with no frontend change at all. Electron does
  the opposite on macOS/Windows (native overlay, own buttons hidden) — that divergence
  is **declared, not discovered**. Consequence: `setTitleBarOverlay` has no native
  overlay left to restyle and becomes a logged no-op (**D-13**).
  **The macOS traffic-lights-vs-custom-buttons aesthetic call is a deferred live-UAT
  item** (**D-15**), not a config-schema decision. Rejected: macOS `titleBarStyle:
  Overlay` with native traffic lights (needs a new frontend signal to suppress the
  custom buttons, since `navigator.windowControlsOverlay` can't carry it under Tauri,
  plus a per-platform branch in an otherwise platform-neutral slice).

### Handler home — where the ported code lives

- **D-07 — EXTRACT handler bodies from `main.ts` into shared modules.** Not
  re-implementation. One source of truth for behavior, no silent drift between the two
  builds. Precedent: Phase 29 **D-15** extracted `downloadManager`'s store declaration
  specifically to enable Phase 32's port — extraction-to-enable-a-port is an
  established move in this project. Rejected: re-implementing in a curated
  `appShellFlowRegistration.ts` with `main.ts` untouched (zero Electron risk and
  matches every prior slice's shape, but ships two implementations of 28 handlers that
  can drift); hybrid-by-portability (two patterns in one slice, a judgment call per
  channel). **This is the first slice to modify the Electron entry point — the
  additive/reversible invariant is BEHAVIORAL here, not textual.**

- **D-08 — Extraction shape: BODIES only; registration stays in `main.ts`.** Export
  handler bodies as plain functions from the new modules; `main.ts`'s
  `addHandler('getCustomThemes', …)` lines become one-line delegations; the sidecar's
  curated module registers the same functions on `electronStub`'s `ipcMain`. Benefits:
  `main.ts`'s diff is mechanical and reviewable, its registration site stays auditable
  in one place, and the extracted modules import **no electron** so the sidecar can
  pull them safely. Rejected: moving registration into the modules with `main.ts`
  side-effect-importing them (more idiomatic — it's what `tools/ipc_handler.ts` and
  `utils/ipc_handler.ts` already do — but registration side-effects would land in
  modules the sidecar also imports, risking `backend/ipc` being dragged into the
  sidecar graph, which the curated-import discipline exists to prevent);
  bodies-only-where-it-pays.

- **D-09 — Curated-module discipline carries forward unchanged.** The new sidecar
  registration module follows Phase 30 **D-08**: curated imports only, and **no file
  under `src/backend/sidecar/` imports the real `electron` module**. Note `abort` and
  `isIntelMac` currently live in `utils/ipc_handler.ts`, which also registers slice-6
  and slice-8 channels (`getLegendaryVersion`, `getSystemInfo`, `hasExecutable`, …) —
  **do not side-effect-import that file**; re-register only the two channels this slice
  owns.

### Hard-gap scope shape

- **D-10 — `gamepadAction`: re-implement RENDERER-SIDE.** Electron injects synthetic
  input via `webContents.sendInputEvent` (`main.ts:1377`, switch at L1381+); Tauri has
  no equivalent. The frontend already reads the Gamepad API and asks the backend to
  inject — under Tauri the renderer dispatches its own synthetic DOM events / focus
  moves instead of round-tripping. This is the only approach that keeps gamepad
  navigation **working**, and GameLib has real consumers (`isSteamDeckGameMode`, the
  `/console` routes). Consistent with D-01's renderer-owns-chrome direction. Rejected:
  logged no-op (silently removes a feature from a launcher whose audience includes
  Steam Deck and couch users); minimal-action-subset. **Cost accepted:** rewriting the
  action→input translation against DOM semantics rather than Electron input events.

- **D-11 — `changeTrayColor`: BUILD THE REAL TAURI TRAY.** Not a no-op. A colour-change
  channel is structurally hollow without a tray — the same "don't ship channels that
  act on nothing" argument Phase 32 **D-01** used to justify re-routing install through
  the queue. Uses Tauri's `TrayIcon` API / `core:tray`. Rejected: logged no-op deferred
  to Phase 35 (Phase 33 already deferred tray once to "Phase 34/35" and Phase 34 didn't
  take it — deferring again just moves it). **Cost accepted and flagged: this is a
  FEATURE, not a port** — it pulls in icon assets, per-platform colour variants, a tray
  menu, and the `nativeImage` work Phase 33 also deferred. **Planner note:** this is the
  single largest scope risk in the slice; bound it explicitly and consider its own wave.

- **D-12 — `createNewWindow` + `showAboutWindow` as genuine Tauri WebviewWindows; the
  login-webview story is 34.4's.** Build the **window primitive** here — that is
  literally this slice's domain (app shell and window chrome) — establishing
  multi-window capability, per-window-label capability scoping, and window lifecycle
  that 34.4/34.5 build on. `openWebviewPage` routes to the existing `open_external`
  rustInvoke arm (Electron already just calls `openUrlOrFile`, `main.ts:719`).
  `getWebviewPreloadPath` returns a **declared-empty** value.
  **Why the split:** real Tauri windows ARE the end state — Epic/GOG/Amazon/Humble
  logins render remote pages in-app via Electron's `<webview>` tag (`webviewTag: true`
  in `main_window.ts`), Tauri has no `<webview>`, and an iframe can't substitute
  (`X-Frame-Options`). It hasn't bitten yet only because Steam auth is QR/credentials
  and headless. But opening a window is the easy half — **navigation interception and
  session/cookie access is the hard half**, and that is exactly Phase 33 **D-09**'s
  accepted gap ("non-Steam login-webview cookies deferred to the cutover"). Designing
  that API here, against no real consumer, builds the wrong abstraction; 34.4's
  `humbleStartLogin`/`humbleLoginNavigated` is a real flow to design against. Rejected:
  full multi-window including login plumbing now; external-browser-only with all
  windows deferred to 34.4 (ships `showAboutWindow`/`createNewWindow` visibly degraded
  and dumps a whole capability on a 38-channel phase).

- **D-13 — Carried-forward logged no-ops (declared, never silent).** `lock`/`unlock`
  are `powerSaveBlocker` (`main.ts:610`/`625`) — Phase 33 **D-08** already accepted this
  as a logged no-op; unchanged here, re-declared in `34.1-PORTED-CHANNELS.md` for
  completeness. `setTitleBarOverlay` (`main.ts:1541`) is a Windows/macOS-Electron API
  with no native overlay left to target under D-06 — logged no-op.

- **D-14 — `callTool` reassigned to Phase 34.5.** `tools/ipc_handler.ts:25` is
  Winetricks/winecfg/runExe — Wine tooling, which is 34.5's entire domain. It is in
  slice 4 only because the inventory grouped channels by file. Porting it here would
  expand this slice's import graph into `runWineCommandOnGame` + `Winetricks` for a
  channel unrelated to app shell or window chrome. **Update
  `.planning/IPC-PORT-INVENTORY.md` in BOTH lists** (34.1: 34→33 channels; 34.5:
  55→56) so the Phase 35 completion gate stays reconcilable.

### Sign-off

- **D-15 — Unit-proven; ALL live UAT deferred.** The standard slice-1/2/3 pattern
  applies to all 33 channels: assert wiring and behavior in jest, log the visual/window
  checks as deferred UAT items. Rejected: a Phase 33 D-13-style live gate scoped to
  window chrome; a full live gate on everything.
  **Honest tension, to be recorded in the phase's own artifacts and NOT glossed:** this
  slice's headline deliverable is *visual and interactive* — "the frameless toggle
  applies," "the buttons actually move the window," "the tray appears and its colour
  changes," "gamepad navigation still works," "macOS traffic lights vs custom buttons
  looks right" — and jest structurally cannot prove any of it. **The phase will close
  without anyone having looked at it.** This is the same class of claim that let
  G-30-02 be declared fixed twice while the live build hung (Phase 33 D-13's stated
  rationale). The deferred-UAT item must say so plainly, and no downstream reader may
  read "wired and unit-proven" as "the window chrome was seen working."

### Claude's Discretion

- **Reuse existing rustInvoke arms rather than writing new behavior** for the
  sidecar-routed natives: `quit` → the `app_exit` arm (Phase 33), `openReleases` /
  `openCustomThemesWiki` / `openWebviewPage` → the `open_external` arm (Phase 30/33),
  `notify` → the `notification_show` arm (Phase 33). These four become thin
  re-wirings of proven transport; **expect zero new Rust arms for them.** If any needs
  new Rust work, stop and ask why (the Phase 29 `storeChanged` precedent).
- The exact module decomposition under D-07/D-08 (how many shared modules, and their
  paths) is a planner call, provided the modules are Electron-free, `main.ts` keeps its
  registration lines, and D-09's curated-import discipline holds.
- Whether the D-11 tray gets its own wave/plan is a planner call — but it must be
  bounded explicitly, since it is a feature rather than a port.
- `isFullscreen` returns `isSteamDeckGameMode || isCLIFullscreen` (`main.ts:747`) —
  an env/CLI signal, **not** actual window state. Port the semantics as-is; do not
  "improve" it into a real window query.
- The precise renderer-side action set for D-10 follows from what the `/console` routes
  and existing gamepad handling actually need — trace during research.

</decisions>
