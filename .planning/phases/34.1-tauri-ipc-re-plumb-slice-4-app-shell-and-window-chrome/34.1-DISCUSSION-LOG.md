## Window-control transport

### Q1 — Where do minimize/maximize/unmaximize/close/setFullscreen/setZoomFactor execute?

| Option | Description | Selected |
|--------|-------------|----------|
| Sidecar → new Rust channels | `window.api` → `sidecar_invoke/send` → new `dispatch_rust_channel` arms calling `WebviewWindow`. Consistent with `dialog_message`/`notification_show`/`app_exit`; honors Phase 29 D-01 ("Rust is the platform seam"); one shared `window.api` implementation. Costs a Rust round-trip per button click and ~8 new arms. | |
| Renderer-side Tauri JS API | Preload factory implements these via `getCurrentWindow().minimize()` etc. No sidecar hop, no Rust changes, lowest latency, where Tauri intends window control to live. Costs `window.api` divergence between builds + capability grants. | ✓ |
| Hybrid: reads local, actions via Rust | State reads answered renderer-side; mutations through the sidecar→Rust seam. | |

**User's choice:** Renderer-side Tauri JS API
**Notes:** → CONTEXT D-01. Accepted cost: two genuinely different `window.api` implementations for these channels, acceptable because Phase 35 deletes the Electron half.

### Q2 — Renderer-side channels never reach the sidecar, but the inventory counts them as unported and Phase 35 can't run while any channel is unported. How is that resolved?

| Option | Description | Selected |
|--------|-------------|----------|
| Renderer-side counts as ported | Declared in `34.1-PORTED-CHANNELS.md` as a third kind, `renderer-side (Tauri JS)`. The gate reads "has real behavior under Tauri," not "the sidecar owns it." | ✓ |
| Renderer-side + sidecar guard | Same, plus a logged no-op registered in the sidecar so a stray call fails loudly if the preload short-circuit ever regresses. | |
| Split the inventory instead | Move renderer-owned channels into a separate section; the gate reads "zero unported *sidecar* channels." | |

**User's choice:** Renderer-side counts as ported
**Notes:** → CONTEXT D-02.

### Q3 — How far does the renderer-side principle extend beyond window chrome?

| Option | Description | Selected |
|--------|-------------|----------|
| Window chrome only | Strictly the window-state/control set; everything else keeps the sidecar seam. Narrowest new renderer surface; consistent with Phase 33 WR-03 minimal-exposure. | ✓ |
| Any Tauri-owned primitive | Window controls AND `notify` AND `quit` AND the three `open*` channels via renderer-reachable plugins. Fewer hops; widens renderer grants and reverses Phase 33's notification decision. | |
| Window chrome + reuse existing arms | Window chrome renderer-side; `quit`/`open*` routed to the `app_exit`/`open_external` arms already built. | |

**User's choice:** Window chrome only
**Notes:** → CONTEXT D-03. The third option's substance (reuse existing arms) was retained as an implementation detail under Claude's Discretion — it is how the sidecar-routed natives should be wired, but it is not a scope principle.

### Q4 — How wide should the capability grant be? *(first framing rejected by user; reformulated)*

The user declined the initial two-option framing and asked which option was closest to the app's end state. Answer given: the explicit per-command allow-list, on two grounds — (1) capabilities are scoped `"windows": ["main"]` and GameLib renders untrusted remote surfaces (store search now, Humble login in 34.4); with no `<webview>` boundary under Tauri, remote content inherits the main window's grants, the same hazard the capability file already cites when explaining why `dialog:allow-open` was refused; (2) the command set is small and stable, so the maintenance argument for `default` doesn't pay off. A correction was also volunteered: `core:window:default` in Tauri v2 is believed to be the read-only getter set, which would make the original option B non-viable standalone — flagged as unverified.

| Option (reformulated) | Description | Selected |
|--------|-------------|----------|
| Explicit list, mutations + getters | Enumerate every command used; extend the identifier description to explain each, matching the existing notification/shell entries. | |
| `core:window:default` + explicit mutations | Take the default getter set, add mutations explicitly. Fewer lines; grants unused read access to window/monitor state. | |
| Explicit list + research composition first | Same as option 1, but a hard planner instruction to verify what `core:window:default` actually contains in the installed version before finalizing. | ✓ (recommended, user delegated) |

**User's choice:** "what do you recommend" → recommendation given and locked: explicit list + verify composition first
**Notes:** → CONTEXT D-04. Rationale for recommending option 3 over option 1: identical end state, but the one input the discussing agent was least sure of gets checked rather than assumed. Stated explicitly that a permission boundary should not be set from an agent's recollection of a version-specific default set.

## Frameless vs native chrome

### Q1 — Which chrome does the Tauri build ship? *(answer superseded by a mid-discussion correction)*

| Option | Description | Selected |
|--------|-------------|----------|
| Frameless — match Electron | `decorations:false`, `isFrameless` true, custom titlebar live. | ✓ (then reframed) |
| Native decorations — defer frameless | OS chrome, `isFrameless` false, control channels real but uncalled. | |
| Frameless on macOS only | Mirror Electron's per-platform result. | |

**User's choice:** Frameless — match Electron
**Notes:** Scouting then established that framelessness in Electron is **not** a platform property but an off-by-default user setting (`settings.framelessWindow`, `main_window.ts:43-53`), and `isFrameless()` reads persisted `window-props` (`main_window.ts:15`). So "match Electron" precisely means *make the setting work*, with decorated as the default — not *ship frameless*. This was surfaced to the user and the question re-asked.

### Q1b — Given `framelessWindow` is an off-by-default user setting, what should Tauri do?

| Option | Description | Selected |
|--------|-------------|----------|
| Honor the setting at runtime | Read at startup, apply via `setDecorations()`, re-apply on toggle. True parity: default decorated, toggle works. Costs a startup-ordering concern and a `set-decorations` grant. | ✓ |
| Decorated only, defer the setting | Native chrome always; the setting becomes a declared logged no-op. Lowest risk; the Settings toggle would do nothing. | |
| Static frameless via `tauri.conf.json` | `decorations:false` at build time, setting ignored. Makes controls load-bearing immediately but ships a different default than Electron and makes the toggle lie. | |

**User's choice:** Honor the setting at runtime
**Notes:** → CONTEXT D-05.

### Q2 — When frameless is on, which chrome does each platform get?

Context given: under Tauri `navigator.windowControlsOverlay` is undefined (Phase 33 gate gap-fix #3 guarded exactly that read), so `showOverlayControls = isFrameless && !hasNativeOverlayControls` evaluates true on every platform — GameLib's own buttons render everywhere with no frontend change. Electron does the opposite on macOS/Windows.

| Option | Description | Selected |
|--------|-------------|----------|
| Own buttons everywhere | `decorations:false` on all three; one code path; `setTitleBarOverlay` becomes a logged no-op. Diverges from Electron on macOS/Windows — declared, not discovered. | |
| macOS native, own buttons elsewhere | macOS gets Tauri `titleBarStyle: Overlay` with real traffic lights; needs a new frontend signal to suppress custom buttons plus a per-platform branch. | |
| Own buttons everywhere, revisit macOS live | Ship the single code path; flag macOS traffic-lights-vs-custom-buttons as a live-UAT item rather than deciding from the config schema. | ✓ |

**User's choice:** Own buttons everywhere, revisit macOS live
**Notes:** → CONTEXT D-06, D-13 (`setTitleBarOverlay`), D-15 (the deferred macOS look).

## Handler home: extract vs re-implement

### Q1 — Where do the ported handlers live, given 28 channels sit inside `main.ts`?

| Option | Description | Selected |
|--------|-------------|----------|
| Extract to shared modules | Pull handler bodies into importable Electron-free modules both builds use. One source of truth. Precedent: Phase 29 D-15. Costs the first refactor of the Electron entry point. | ✓ |
| Re-implement in sidecar module | New curated `appShellFlowRegistration.ts`, `main.ts` untouched. Zero Electron risk, matches every prior slice; two implementations that can drift. | |
| Hybrid by portability | Extract the Electron-free bodies, re-implement the `BrowserWindow`/`app`-coupled ones. Minimizes both duplication and churn; two patterns in one slice. | |

**User's choice:** Extract to shared modules
**Notes:** → CONTEXT D-07. First slice where the additive/reversible invariant is behavioral rather than textual.

### Q2 — What shape should the extraction take?

| Option | Description | Selected |
|--------|-------------|----------|
| Bodies only; registration stays put | Export bodies as plain functions; `main.ts`'s `addHandler` lines become one-line delegations; the sidecar module registers the same functions. Mechanical diff, auditable registration site, extracted modules import no electron. | ✓ |
| Move registration too | Modules own their `addHandler` calls, `main.ts` side-effect-imports them (the `tools/ipc_handler.ts` pattern). More idiomatic; risks dragging `backend/ipc` into the sidecar graph. | |
| Bodies only, and only where it pays | Extract only channels with real logic; re-implement one-liners in the sidecar module. | |

**User's choice:** Bodies only; registration stays put
**Notes:** → CONTEXT D-08.

### Q3 — Multi-window / webview group *(first framing declined; user asked which option is closest to the ideal end state)*

Answer given: real Tauri windows **are** the end state, because Epic/GOG/Amazon/Humble logins render remote pages in-app via Electron's `<webview>` tag, Tauri has no `<webview>`, and an iframe can't substitute (`X-Frame-Options`). It hasn't bitten yet only because Steam auth is QR/credentials and headless. But opening a window is the easy half — navigation interception and session/cookie access is the hard half, and that is Phase 33 D-09's accepted gap. Designing it here against no real consumer builds the wrong abstraction. Options were re-split accordingly.

| Option (reformulated) | Description | Selected |
|--------|-------------|----------|
| Window primitive here, login story later | `createNewWindow`/`showAboutWindow` as genuine Tauri WebviewWindows (this slice's actual domain); `openWebviewPage` → existing `open_external`; `getWebviewPreloadPath` declared-empty; the `<webview>`-login problem explicitly owned by 34.4. | ✓ |
| Full multi-window incl. login plumbing | Build the interception/session surface too, so 34.4/34.5 inherit a finished primitive. Costs designing against no real consumer. | |
| External browser now, windows in 34.4 | Cheapest; ships `showAboutWindow`/`createNewWindow` visibly degraded and dumps a whole capability on a 38-channel phase. | |

**User's choice:** Window primitive here, login story later
**Notes:** → CONTEXT D-12.

## Claude's Discretion

- Reuse the existing rustInvoke arms for the sidecar-routed natives — `quit` → `app_exit`, `openReleases`/`openCustomThemesWiki`/`openWebviewPage` → `open_external`, `notify` → `notification_show`. Expect zero new Rust arms; if any needs new Rust work, stop and ask why (Phase 29 `storeChanged` precedent).
- Exact module decomposition under D-07/D-08 (count and paths), provided modules stay Electron-free, `main.ts` keeps its registration lines, and curated-import discipline holds.
- Whether the D-11 tray earns its own wave/plan.
- `isFullscreen` semantics ported as-is (`isSteamDeckGameMode || isCLIFullscreen` — an env/CLI signal, not window state); explicitly not to be "improved."
- The precise renderer-side action set for D-10, traced from what the `/console` routes actually need.
