<objective>
D-12: build the window primitive. `createNewWindow` and `showAboutWindow` become genuine
Tauri `WebviewWindow`s, establishing multi-window capability, per-window-label capability
scoping, and window lifecycle that Phases 34.4 and 34.5 build on.

**Resolving 34.1-RESEARCH.md Open Question 1, explicitly:** these two channels are
implemented **renderer-side (Tauri JS)**, the same third kind D-02 establishes for window
chrome — not sidecar-routed. The reason is structural, not preference: `WebviewWindow`'s
constructor is a webview-context-only JS API that the headless Node sidecar cannot call at
all, and the only sidecar-side alternative is a new Rust arm, which the Claude's-Discretion
"expect zero new Rust arms" framing does not pre-approve for this pair. D-03's enumerated
sidecar-seam list does not name `createNewWindow` or `showAboutWindow`, so this does not
contradict it. Record this resolution in the plan summary and in
`34.1-PORTED-CHANNELS.md`.

**Explicitly NOT in scope — Phase 34.4 owns it:** the `<webview>` login story. Navigation
interception, OAuth redirect capture, and session/cookie access are the hard half, and
Phase 33 D-09 already recorded `session` as an accepted gap. Designing that API here,
against no real consumer, builds the wrong abstraction; 34.4's
`humbleStartLogin`/`humbleLoginNavigated` is a real flow to design against.

Output: a `tauriChildWindows.ts` module, two `isTauri()` branches in `helpers.ts`, a static
`about.html`, one capability grant, and a fail-closed child-window boundary proven by test.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| renderer-supplied URL → a new `WebviewWindow` | `createNewWindow(url)` loads arbitrary remote content in-process. Callers today are hardcoded reference sites, but the channel takes any string and is reachable from anything running in `main`. |
| child window → Tauri command surface | Capabilities resolve per window LABEL. `default.json` names only `main`, so `about` and `external-<n>` match nothing. |
| `about.html` → the app's own origin | The about page is served from `frontendDist`, same origin as the app shell. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-34.1-26 | Elevation of Privilege | A child window inheriting or being granted `main`'s capability set, giving remote content direct access to `sidecar_invoke`, `open_external`, `shell:allow-execute` and the window commands | mitigate | `windows` stays `["main"]`; child labels are never added; Task 1 asserts the array's exact value AND that exactly one capability file exists. Task 2/3 forbid any child window claiming the `main` label and assert per-call unique labels. |
| T-34.1-27 | Spoofing | A URL-derived or attacker-influenced label colliding with `main` (which WOULD inherit the full grant set) | mitigate | Labels come from a monotonic module-level counter, never from the URL. Asserted by the "same url yields different labels" and "label is never `main`" tests. |
| T-34.1-28 | Elevation of Privilege | Granting the broader `core:webview:allow-create-webview` (create a webview INSIDE an existing window) instead of / in addition to `-window` | mitigate | Task 1 asserts the bare identifier is absent. Creating a webview inside `main` would place remote content in a window that DOES hold the full grant set. |
| T-34.1-29 | Information Disclosure | The about page leaking app state or reaching the network | mitigate | `about.html` is fully static, carries its own restrictive CSP meta (the shell's global `security.csp` is `null` — Phase 34 WR-04 accepted debt), and is asserted to contain no `fetch`/`XMLHttpRequest`/`__TAURI__`/`<a >`. The only dynamic value is the version string, passed via query param and rendered as text. |
| T-34.1-30 | Denial of Service | Unbounded window creation from repeated `createNewWindow` calls | accept | Same as Electron today (`new BrowserWindow(...)` per call, no cap). The About window is deduplicated by label, which is the case a user can actually hit repeatedly. A global cap would be a behavior change smuggled into a port. |
| T-34.1-31 | Tampering | The `<webview>` login story (navigation interception, cookie access) being partially built here against no real consumer, producing an abstraction 34.4 then has to fight | mitigate | Explicitly out of scope and stated in the objective, the module comment, and `34.1-PORTED-CHANNELS.md`. `getWebviewPreloadPath` returns declared-empty (plan 34.1-04). |
| T-34.1-SC | Tampering | npm/pip/cargo installs | mitigate | Not applicable — this plan installs zero packages. `@tauri-apps/api` 2.11.1 is a pre-existing dependency; `webviewWindow` ships inside it. |
</threat_model>
