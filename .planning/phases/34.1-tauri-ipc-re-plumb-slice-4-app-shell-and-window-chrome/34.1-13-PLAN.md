<declared_deviation_from_the_gap_text>
The gap's `missing:` list says "Regenerate icon-dark.png/@2x/@3x as a genuinely distinct dark
treatment." **The measurement above says the file to regenerate is `icon-light.png`, not
`icon-dark.png`** — and this deviation is declared here rather than applied silently.

Reasoning: `getIcon()` (`tray_icon.ts:91`) returns `darkTrayIcon ? iconDark : iconLight`, so
`icon-light.png` is the DEFAULT asset. A tray glyph for a DARK menu bar needs LIGHT ink; a glyph
for a LIGHT menu bar needs DARK ink. The shared artwork measures 94.6 mean opaque luminance — dark
ink. So the artwork currently in both slots is already the correct `icon-dark` content, and it is
`icon-light.png` that holds the wrong variant.

The observable outcome the gap demands is identical either way: the two assets differ, and toggling
the setting changes the tray image. The human checkpoint in Task 2 confirms the mapping visually
against both a light and a dark menu bar before anything is considered done. If the operator
disagrees at that checkpoint, swap the two file sets and re-run — Task 3's gates are symmetric
about naming and will follow.

<tooling_constraint>
