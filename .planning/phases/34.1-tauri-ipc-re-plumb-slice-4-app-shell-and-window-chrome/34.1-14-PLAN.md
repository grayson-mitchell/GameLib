  <name>Task 2: How should the frameless toggle present itself on macOS?</name>
  <files>.planning/phases/34.1-tauri-ipc-re-plumb-slice-4-app-shell-and-window-chrome/34.1-14-SUMMARY.md</files>
  <decision>
    Given that `settings.framelessWindow` is now decoration-inert on macOS, how should the Settings
    toggle present itself to a macOS user?
  </decision>
  <context>
    This question is a FORCED CONSEQUENCE of the D-06 reversal, not a new proposal. `titleBarStyle`
    is a static window-creation config key and Tauri v2 exposes NO runtime setter for it — there is
    no `setTitleBarStyle` in `@tauri-apps/api/window`, and the macOS Rust extension is not surfaced
    to the webview. So overlay mode plus native traffic lights is now macOS's PERMANENT appearance,
    and `applyFramelessDecorations` had to become a macOS no-op, because the only alternative
    mechanism (`setDecorations(false)`) is exactly what stripped the traffic lights in the first
    place.

    What the setting still does on macOS: persists, applies the `.frameless` class (which drives
    some layout rules), and is honoured normally on Windows and Linux.
    What it no longer does on macOS: change window decorations. You just observed this in Task 1
    step A6 — the traffic lights stayed through both toggle directions.

    Relevant prior context: the 2026-07-25 session resolved "stop investing in frameless — candidate
    for removal, not a committed removal." The D-06 reversal supersedes that stance ON MACOS
    specifically, because overlay mode moves work toward the OS providing the controls rather than
    GameLib re-implementing them. The "candidate for removal" note still stands for Windows/Linux,
    where custom buttons remain the only option.
  </context>
  <options>
    <option id="hide-on-macos">
      <name>Hide the toggle entirely on macOS</name>
      <pros>A control that changes nothing visible is worse than no control. The component already
        has an early-return precedent (`window.isSteamDeckGameMode`), so this is a small, local
        change. No copy to maintain.</pros>
      <cons>The setting still has a non-decoration effect on macOS (the `.frameless` class), so
        hiding it removes the user's access to that. Divergent Settings surfaces per platform.</cons>
    </option>
    <option id="keep-with-macos-copy">
      <name>Keep it, with a macOS-specific description</name>
      <pros>Honest: the setting exists and does something, and the copy says what. Consistent
        Settings surface across platforms. Directly continues gap G2's principle — the label must
        describe what the control actually does.</pros>
      <cons>A second string in the `gamelib` namespace plus a platform branch in a component that
        plan 34.1-12 just simplified. Explaining "this no longer controls decorations on macOS" to
        a user is awkward.</cons>
    </option>
    <option id="leave-as-is">
      <name>Leave it exactly as plan 34.1-12 left it</name>
      <pros>Zero further churn on an already-large branch. The copy "Use frameless window" is not
        FALSE on macOS — the window genuinely is frameless-looking in overlay mode, permanently.</pros>
      <cons>The toggle appears to do nothing when a macOS user flips it, which is the same class of
        confusion the dark-tray-icon no-op produced. Ships a known dead-feeling control.</cons>
    </option>
  </options>
