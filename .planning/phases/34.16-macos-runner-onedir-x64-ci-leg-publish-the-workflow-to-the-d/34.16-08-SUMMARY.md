# Phase 34.16 Plan 08: Two-Layer Tripwire for Pinned Runner Build Invocations Summary

**Added an offline jest tripwire (`meta/runnerBuildInvocations.ts` + its test suite) that goes RED the moment `RELEASE_TAGS` is bumped without re-capturing a runner's upstream PyInstaller invocation, plus an on-demand networked checker (`meta/checkRunnerInvocations.ts`, `pnpm check:runner-invocations`) that re-derives from live GitHub and catches the one thing the offline layer structurally cannot: an already-pinned tag being force-moved upstream.**

## Both Layers' Stated Latency (for 34.16-11)

- **Layer 1 (`meta/runnerBuildInvocations.ts` + its test suite):** fires at the very commit that edits `meta/releaseTags.ts`, at that commit's own `pnpm jest --selectProjects Meta` run -- automatic, but only catches a record that was never re-captured for a new tag. Cannot see a tag being force-moved after the fact (never touches the network).
- **Layer 2 (`meta/checkRunnerInvocations.ts`):** only fires when explicitly invoked (`pnpm check:runner-invocations`) -- not wired into any workflow. Catches upstream force-moving an already-pinned tag, which Layer 1 structurally cannot. A tripwire nobody runs detects nothing; wiring Layer 2 into a scheduled or release workflow is a **routed follow-up**, currently **blocked** by `34.16-LIVE-GATE.md` §12 criterion 5 (asserts `build-base.yml`, `.github/actions/install-deps/action.yml`, `build-main.yml`, `build-prs.yml` unchanged for this phase) and Precondition 6 (`build-runners-onedir-macos.yml`'s sha256 pinned) -- adding a step to any of those files would fail a scored live-gate item. Record for 34.16-11: wire Layer 2 into CI only after the live-gate run this phase is building toward has closed.

## Decisions Made

- Layer 2 reuses `extractUpstreamPyinstallerCommand` from `meta/buildRunnersOnedir.ts` verbatim rather than re-implementing YAML parsing, so Layer 1, Layer 2, and the real `build-runners-onedir-macos.yml` build all share exactly one extraction contract -- a divergence between two independently-written parsers would be a worse failure mode than the one this plan closes.
- Layer 2's `main()` reports all three runners before deciding pass/fail (never stops at the first mismatch), matching the plan's requirement and Layer 1's own `it.each` shape (all cases run, not fail-fast).
- Layer 2 sets `process.exitCode = 1` rather than calling `process.exit(1)` directly inside `main()`, so all pending `console.log` output flushes before the process exits with a non-zero code; the top-level `.catch()` still calls `process.exit(1)` for genuinely unhandled rejections (e.g. a network failure reaching `main()` itself, which should not happen since `checkRunner` catches per-runner).
