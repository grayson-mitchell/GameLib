<decisions>
## Implementation Decisions

### Landing the workflow on the default branch

- **D-01:** **Workflow-only commit to `gamelib/main`.** One commit adding just
  `.github/workflows/build-runners-onedir-macos.yml`. Not a merge of the feature branch (3830
  commits — a whole-fork ship decision far larger than this phase), and not a default-branch
  repoint. The file's presence on `main` satisfies GitHub's registration rule; the dispatch then
  targets `--ref fix/steam-native-install-stability` and **that ref's** version of the workflow is
  what actually runs.
- **D-02:** **The copy on `main` is byte-identical to the branch copy, plus a ref guard.** A first
  step that hard-fails when `github.ref` is the default branch, naming the correct `--ref` in the
  error. The guard goes into **both** copies so they stay byte-identical and drift is visible in a
  plain `diff`. Rationale: `main` has no `meta/buildRunnersOnedir.ts` and no `build-runners-onedir`
  script, so a mis-targeted dispatch would otherwise burn ~2 min of macOS runner time before dying
  on a confusing "script not found".
- **D-03:** **The phase prepares; the developer pushes.** Plans produce the exact file content, the
  no-checkout commit recipe, and a copy-paste command block (push → `gh workflow run` → the run URL
  to watch). Execution stops at a **HUMAN GATE**. This matches the 34.9 ledger's own position that
  pushing to `main` is outside any plan's authorization.
- **D-04:** **Retire the ROADMAP's "do not plan before the default-branch push".** Code-side work
  (guard widening, digest-pinning tooling, the `release:mac` decision) is authorable and testable on
  the feature branch today. Plan it now; isolate everything requiring a real dispatch into a
  LIVE-GATE document, the pattern 34.9 used and passed on rerun. The blanket instruction predates
  knowing how small the required push is.

### Guard arch coverage (items 12 and 13)

- **D-05:** **Two sequential invocations**, not an arch list and not tree-derived:
  `… && pnpm verify:runner-bundle build --arch=arm64 && pnpm verify:runner-bundle build --arch=x64 && electron-builder …`
  in both `dist:mac` and `release:mac`. Zero change to `meta/verifyRunnerBundle.ts` (it already
  parses `--arch=x64`), fail-closed by construction, and each failure names its own arch. The
  tree-derived variant was rejected explicitly: it passes vacuously the moment the layout changes or
  the tree is empty.
- **D-06:** **The guard stays npm-script-level.** No new explicit step in `build-base.yml`. Once
  `install-deps` stops throwing on the sentinels, the macOS leg reaches the build step and the guard
  runs — item 13 closes with no new wiring, and the guard cannot drift away from the build it
  protects.
- **D-07:** **Evidence bar — local RED on x64 + CI GREEN.** Inject a broken symlink into a *real
  downloaded* x64 onedir tree on the dev machine and prove the guard goes red naming `arch=x64`;
  take the CI run as evidence of execution only. Reuses `34.9-GUARD-PROOF.md`'s contract **under
  AMENDMENT v2**, costs no extra macOS CI minutes, and proves the gate in both directions rather
  than only that it ran.

### `release:mac` auto-publish exposure (item 18)

- **D-08:** **Close it by the guard widening alone; `-p always` stays.** D-05's second invocation
  lands in `release:mac`, so an unverified x64 build can no longer reach the `electron-updater`
  feed. This is item 18's own named precondition. `--publish=never` was considered and rejected:
  it rewrites the release ritual for a script Phase 35's Electron cutover deletes, and the
  replacement ritual is not this phase's to design.
- **D-09:** **No new publish-safety pin.** Stated consequence, deliberately accepted: the existing
  pin at `meta/__tests__/verifyRunnerBundle.test.ts:605-622` asserts only
  `indexOf('pnpm verify:runner-bundle') < indexOf('electron-builder')`, so it stays **green if a
  future edit deletes the x64 invocation**. Item 18's closure is correct at the moment it lands but
  is unprotected against regression. Do not describe this closure as "pinned".

### Digest pinning and rolling-release drift (items 2 and 3)

- **D-10:** **A pin script**, not hand-transcription and not a bot PR. `pnpm pin:runner-digests`
  fetches `SHA256SUMS-x64` and `SHA256SUMS-arm64` from the `runners-onedir-macos` rolling release and
  rewrites `meta/runnersOnedirDigests.json`, recording the source run id from
  `BUILD-MANIFEST-{arch}.json`. Repeatable after every re-dispatch; no six-hex-string transcription
  risk; provenance captured rather than remembered.
- **D-11:** **Let the mismatch throw, but name the run.** `--clobber` means every re-dispatch
  invalidates all six pins. Keep the digest mismatch as the drift detector — it is loud and
  fail-closed, and already refuses to write anything under `public/bin`
  (`downloadHelperBinaries.ts:188`). Add the pinned run id to `meta/runnersOnedirDigests.json` and
  quote it in the mismatch error, so the failure says *which run to re-pin from*. Run-scoped asset
  filenames were considered and rejected (unbounded release growth; digest keys would have to carry
  a version).
- **D-12:** **Proof bar for items 2 and 3 — green fetch + RED digest + x64 actually executes.**
  (a) A clean-tree `pnpm download-helper-binaries` fetching all six archives, transcript captured;
  (b) a deliberate one-character digest corruption proving it throws and writes nothing under
  `public/bin`; (c) running the extracted x64 `legendary`/`gogdl`/`nile` under Rosetta to prove the
  x64 archives are not merely well-hashed but actually work. A green fetch alone is near-tautological,
  since the pin script read those digests from the same publication.

### Claude's Discretion

- **The no-checkout commit mechanics.** `git commit-tree` plumbing against `gamelib/main`, or a
  throwaway clone under the scratchpad — planner's choice, subject to the hard constraint in
  `<constraints>` that no checkout may occur in this worktree.
- **Contingency if the real x64 onedir tree FAILS the guard's framework-structure checks.** This
  direction is explicitly **unproven** (see constraint 3). The plan must branch on the observed
  result — guard bug (checks are arm64-shaped) vs. build bug (`meta/buildRunnersOnedir.ts` emits a
  malformed x64 tree) — and must not be authored assuming a PASS.
- Whether `pin:runner-digests` should refuse to pin from a run whose `BUILD-MANIFEST` records
  `RELEASE_TAGS` differing from the repo's pinned versions.
- Exact wording and placement of the LIVE-GATE document, following 34.9's precedent.

<constraints>
## Known constraints — do NOT rediscover these

1. **`.husky/post-checkout` runs `pnpm i && pnpm download-helper-binaries`.** Any checkout of a
   branch based on `gamelib/main` fires it against a 3830-commit-old tree, and checking *back* to the
   feature branch fires `download-helper-binaries` against the six sentinels, which throws by design.
   **The `main` commit must be built without a checkout in this worktree.**
2. **`origin` is Heroic upstream; `gamelib` is the fork.** The push target is `gamelib main`, never
   `origin main`.
3. **Whether a real x64 onedir tree passes the guard's framework-structure checks has never been
   observed.** Ledger item 12 refuses to assert either direction, and this phase must preserve that.
   What *is* known is why the current x64 tree fails: `build/bin/x64/darwin` holds **onefile**
   binaries today, which have no `_internal` and no `Python.framework`, so they miss the
   `FILE_COUNT_FLOOR = 20` for a reason unrelated to symlink integrity.
4. **Item 12's blocker dissolves the moment the digests are real.** `downloadOnedirAsset()` already
   fetches *both* arches (`downloadHelperBinaries.ts:307/308`, `330/331`, `346/347`), writing real
   onedir trees to `public/bin/x64/darwin/{runner}/{runner}`. Consequence: the prose at
   **`electron-builder.yml:71-79`** ("Coverage is ARM64 ONLY … `build/bin/x64/darwin` holds onefile
   binaries and would fail the file-count floor") becomes **stale-by-behaviour on the same commit
   that pins the digests** and must be rewritten in that change.
5. **PyInstaller cannot cross-compile** (34.9-CONTEXT.md constraint 1). x64 and arm64 each build on
   their own runner; the x64 leg is CI-only and cannot be locally proven before the dispatch.
6. **`RELEASE_TAGS` must not drift.** This is a packaging phase, not a runner upgrade — no plan may
   change `meta/releaseTags.ts`.
   **[CORRECTED 2026-08-24 during plan-phase — the literals originally recorded here were stale at
   the moment this CONTEXT.md was written.]** This constraint originally read "legendary `0.20.43`,
   gogdl `v1.2.1`, nile `v1.1.2`, comet `v0.2.0`". Those values were superseded two days earlier by
   commit `0034ad265` (2026-08-22, `feat(runners): bump legendary 0.21.0, gogdl 1.3.0, nile 1.2.0`),
   confirmed an ancestor of HEAD. Live values are legendary `0.21.0`, gogdl `v1.3.0`, nile `v1.2.0`,
   comet `v0.2.0`, `epic-integration` `v0.4`. That bump deliberately left the macOS onedir digest
   path untouched (its own message: "The macOS onedir digests stay PENDING-CI-PUBLISH"), so it
   corroborates this constraint's intent rather than contradicting it.
   **Binding form for plans:** do NOT hardcode any `RELEASE_TAGS` literal in plan text or in a
   verification step. Assert instead that `meta/releaseTags.ts` is byte-unchanged across this
   phase's commits, reading its current values fresh at execution time.
7. **`gsd-sdk query state.*` verbs corrupt STATE.md** — a known recurring defect on this repo. Snapshot,
   run, diff; or hand-apply.
8. **Since plan 01 landed (`adc648eb6`, 2026-08-25), `pnpm dist:mac` and `pnpm release:mac` ABORT on
   every machine** — do not plan a step that runs either until real x64 digests are pinned. Both
   scripts now `&&`-chain `pnpm verify:runner-bundle build --arch=x64`, and that guard fails against
   today's tree. Measured 2026-08-25 against the working tree, both directions:
   `pnpm verify:runner-bundle build --arch=arm64` → **PASS**;
   `pnpm verify:runner-bundle build --arch=x64` → **FAIL**, all three runners reported missing,
   because `build/bin/x64/darwin` still holds onefile binaries (constraint 3). Three consequences:
   - **`build-base.yml:48`'s macos-15 leg goes red on the first PR or push to `main`.** Nothing is
     red today only because `build-prs.yml` triggers on `pull_request` to `main`/`stable` and
     `build-main.yml` on pushes to the same — neither sees this feature branch. The workflow-publish
     commit this phase exists to make is exactly such a push.
   - **`pnpm dist:mac --arm64 --publish=never` is invalidated as a re-run recipe.** The guard steps
     are hardcoded per-arch (D-05), and pnpm appends CLI args to the END of the resolved script
     string, so `--arm64` lands on `electron-builder` and never suppresses the x64 guard step. That
     command is the one that discharged **34.9 ledger item 16** and it is named normatively by
     **`34.9-GUARD-PROOF.md` §2.5 AMENDMENT v2 §A3** (cite, never paraphrase) — so that contract
     cannot be re-run as written until the digests are real. Do not "fix" it by dropping the x64
     step; that would reopen item 18 / C2-05.
   - This is **fail-closed by design, not a defect**: an unverified x64 leg can no longer reach
     `electron-builder`, which is the whole point of D-05/D-08. It is recorded here because no plan
     01 artifact stated it, and plans 34.16-03..06 would otherwise discover it mid-run.
   **This constraint expires on the commit that pins real digests** (plan 34.16-05) — the same
   commit that retires the `[REMOVE WHEN DIGESTS ARE PINNED]` marker in `electron-builder.yml`.
