# Phase 34.16 Plan 04: runId provenance + D-11 mismatch-error provenance Summary

**`meta/runnersOnedirDigests.json` now carries an explicit-null `runId` sibling, the sha256-mismatch throw in `meta/downloadHelperBinaries.ts` names the pinned run (or explains its absence) per D-11, and `darwinLayoutMarker()`'s blindness to the new sibling key is proven behaviourally through the function itself, with a recorded RED-proof and a vacuity guard.**

## Performance

- **Duration:** ~35 min
- **Tasks:** 2 completed

## Accomplishments

- Added a top-level `"runId": null` field to `meta/runnersOnedirDigests.json`, sibling to `layout` and `digests`, and extended the file's `_comment` to record that `runId` is written by `pnpm pin:runner-digests`, names the workflow run the digests were pinned from, and is deliberately invisible to `computeLayoutMarker()` (positional-args signature, structurally blind to any sibling key). All six `PENDING-CI-PUBLISH` sentinels and the `onedir-v1` `layout` value are byte-unchanged -- confirmed by `git diff` showing only the `runId` line and the `_comment` extension added.
- Widened the shape cast on the imported digests module in `meta/downloadHelperBinaries.ts` (`runId?: string | null`) -- no behavioural change in Task 1.
- Extended the single sha256-mismatch throw (D-11) with a provenance clause: when `runnersOnedirDigests.runId` is non-null, the message gains `-- re-pin from run <id> if this is a rolling-release update (gh release upload --clobber invalidates all six pins at once)`; when null, it gains `-- no source run is pinned in meta/runnersOnedirDigests.json; run pnpm pin:runner-digests to fill it in`. The message prefix through `refusing to write anything under public/bin` is byte-identical to before. The sentinel-gate throw (`DIGEST_SENTINEL`) and the traversal-gate throw are untouched -- confirmed by `git diff` scoping.
- Added 5 new tests total, all inside existing `describe` blocks per the plan's constraint (no new top-level describe):
  - **Task 1** (3 tests, in `describe('computeLayoutMarker (darwinLayoutMarker sensitivity, mutation-proof)')`):
    1. Precondition guard -- the real committed `meta/runnersOnedirDigests.json` has a top-level `runId` key (without this, the load-bearing test below would be vacuous).
    2. **Load-bearing:** `darwinLayoutMarker()` equals `computeLayoutMarker('onedir-v1', mockOnedirDigests)`, even though the mocked digests module (which `darwinLayoutMarker()` reads internally) also carries a `runId` sibling. Routed through `darwinLayoutMarker()` itself, not a synthetic `computeLayoutMarker()`-vs-`computeLayoutMarker()` comparison, per the plan's explicit rejection of that shorter (vacuous) form.
    3. Vacuity guard -- `computeLayoutMarker('onedir-v1', {...mockOnedirDigests, extra: 'x'})` does NOT equal `darwinLayoutMarker()`, proving the load-bearing assertion reads the data rather than comparing a constant to itself.
  - **Task 2** (2 tests, in `describe('digest gate')`): one per D-11 branch (runId present / runId null), each re-asserting `mockedWriteFile`/`mockedSpawn` were never called, and the null-branch test asserting the literal strings "re-pin from run null" and "re-pin from run undefined" never appear.
- **RED-proof performed and recorded** (Task 1, load-bearing test): temporarily rewrote `darwinLayoutMarker()`'s body to `createHash('sha256').update(JSON.stringify(runnersOnedirDigests)).digest('hex')` (hashing the whole parent object, including `runId`). Test run: `darwinLayoutMarker() is blind to the runId sibling: ...` (load-bearing) went **RED** -- `Expected: "b243dbfc..."`, `Received: "d79c19fd..."` -- while the vacuity guard and the rest of the 47 other tests in the file stayed green. Restored the original 3-line `computeLayoutMarker(layout, digests)` body via direct edit (not `git checkout --`, per the repo hazard rule), verified via `git diff meta/downloadHelperBinaries.ts` showing only the intended `runId?: string | null` cast widening survived (no trace of the mutation), then re-ran the suite: all 48 tests green.

## Decisions Made

- Extracted the mocked digests object into a named `mockOnedirDigests` constant (prefixed `mock` for babel-plugin-jest-hoist) shared between the `jest.mock(...)` factory and the load-bearing marker test, instead of hand-retyping the six-entry digest map a second time inside the test -- eliminates a drift risk the plan's own action text warned about implicitly (two independently-maintained copies of the same fixture going out of sync).
- Drove the null-`runId` branch (Task 2) by importing the same mocked JSON module the source file reads (ES module singleton under Jest's mock) and mutating `.runId` in place inside a `try/finally`, rather than `jest.isolateModules`/`jest.resetModules` + re-require. Simpler and does not disturb the shared `mockOnedirDigests` object other tests in the file depend on for their `layout`/`digests` values.
- Removed two `eslint-disable-next-line @typescript-eslint/no-explicit-any` comments that were flagged as unused directives once the mutable import was given a proper `{ runId?: string | null }` cast instead of `any` -- `pnpm tsc --noEmit` and `eslint` both confirmed clean (0 new warnings, 0 errors) after the fix.
