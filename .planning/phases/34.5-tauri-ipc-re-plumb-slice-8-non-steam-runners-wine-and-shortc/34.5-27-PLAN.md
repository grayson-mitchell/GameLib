are entering credentials into) and F-34.5-G6-05 (black-on-black text in Amazon's verification-code

not tell whether a pasted verification code had landed.

Key facts this task depends on:
- The OS title currently tracks the loaded DOCUMENT's title — a value the remote page fully controls. A page can title itself anything, so the current title is NOT an origin indicator and must never be treated as one.
- `.on_navigation(|url| …)` is the builder callback already used twice in this file (the `humble_reveal_post` and `humble_login_clear_storage` arms, lines ~1687 and ~1754) to observe navigations. That is the existing, proven idiom for reacting to a URL change in this codebase — follow it rather than inventing a new mechanism.
- `login_window_url_arg(args)` already validates the URL is parseable and https-only; it returns a `tauri::Url`, so an `origin`/`host_str` is available without re-parsing.
- Every `eprintln!("[shell] …")` in this file goes to the SHELL process's stderr — the `pnpm tauri:dev` terminal — NOT to `~/Library/Logs/GameLib/gamelib.log`. The standing `sidecar-console-and-logger-are-invisible` finding means gate evidence must not depend on these lines.
- `.on_document_title_changed`'s existing comment explicitly forbids logging the title STRING (remote page content must never reach an uploadable log); it logs the length only. The same rule binds anything this plan logs.

    - A pure helper composes the window title from an origin and an optional document title, with the ORIGIN first, so a truncated title bar still shows the origin rather than the page's chosen text.
    - Given a page title containing characters that could impersonate a URL prefix, the helper still places the real origin first and does not let the page's text precede it.
    - Given no document title, the helper returns a title containing the origin alone.
    - The helper is `AppHandle`-free and unit-testable, mirroring the existing `clipboard_text_arg` / `login_window_url_arg` pattern in this file.
  </behavior>
  <action>
    Add an `AppHandle`-free pure helper — name it `login_window_title` — that takes the current
    origin (as a `&str` derived from a `tauri::Url`) and an optional document title, and returns the
    string to set as the OS window title, with the ORIGIN FIRST. Give it `#[cfg(test)]` coverage in
    the same style as `clipboard_text_arg`/`login_window_url_arg`, which REQ-34.5-01 already
    established as this file's convention for testable pure helpers.

    Wire it into the `"humble_login_open"` arm in the `if visible` block:

    - Seed the title from the URL the arm was ALREADY given and validated by `login_window_url_arg`,
      so the origin is visible from the moment the window appears rather than only after the first
      title event.
    - Add `.on_navigation(…)` following the existing idiom in this file, and on each main-frame
      navigation recompute the title from the NEW url's origin so the displayed origin tracks where
      the window actually is. A login flow legitimately crosses hosts (Amazon's sign-in redirects,
      GOG's `auth.gog.com` → `embed.gog.com`), so a title fixed at open time would be actively
      misleading — worse than none.
    - Keep the existing `.on_document_title_changed` behaviour, but route it through the same helper
      so the page's own title can only ever appear AFTER the origin, never before it and never
      instead of it.

    **The origin must come from the URL the shell resolved, never from page content.** The document
    title is fully attacker-controlled; that is exactly why it cannot serve as the origin indicator
    and why this helper exists. Say so in the helper's doc comment.

    Keep the existing logging discipline: log the length of anything remote-influenced, never the
    string. Do not add a log line carrying a full URL. And note in the SUMMARY that
    `eprintln!("[shell] …")` reaches only the `tauri:dev` terminal, so the live gate must verify this
    by LOOKING AT THE WINDOW, not by grepping `gamelib.log`.

    Do NOT attempt to build an in-window address bar or any HTML chrome. The window loads a remote
    origin directly; injecting UI into it would mean injecting script into a third-party credential
    page, which is a strictly worse security posture than using the OS title bar the window already
    has.
  </action>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| remote login page → OS window title | The document title is fully controlled by the loaded page and is currently the ONLY thing shown to the user |
| remote login page ← injected script | Anything the shell injects runs inside a live credential-entry context |
| shell-resolved URL → user's trust decision | The user decides which stored credential to enter based on what the window tells them |
