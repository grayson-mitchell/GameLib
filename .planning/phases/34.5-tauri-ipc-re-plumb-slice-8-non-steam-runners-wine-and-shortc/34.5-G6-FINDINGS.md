# F-34.5-G6-02 — root-cause diagnosis

**Verdict in one sentence:** F-34.5-G6-02 is shape **(c)** — the consume path (`useTauriOAuthLogin.ts`
calling `login`/`authGOG`/`authAmazon` after a `status=captured` outcome) EXISTS and is written
correctly, but the captured outcome never reaches it, because `oauthCaptureLogin` is a
`sidecar_invoke`-routed channel bound by `src-tauri/src/main.rs:104`'s 60-second `INVOKE_TIMEOUT`
(it is absent from `LONG_RUNNING_CHANNELS`, `src-tauri/src/main.rs:134-145`) while its own internal
deadline is `DEFAULT_DEADLINE_MS = 300_000` (`src/backend/sidecar/oauthLoginCapture.ts:62`) — every
real-world login takes longer than 60 s to complete, so the Rust shell's `sidecar_invoke` command
rejects the renderer's promise at the 60 s mark, roughly 3-4 minutes before the backend actually
settles `status=captured` or `status=timeout`. That rejection lands on an `await` at
`useTauriOAuthLogin.ts:99` which is NOT inside a `try`/`catch` (the enclosing `try` block ends at
line 97), so it becomes a silently-swallowed unhandled promise rejection — the hook's own
`window.api.logInfo` calls (which fire on every terminal outcome) never execute, matching the
observed **zero** `useTauriOAuthLogin` log lines despite **six** real backend terminal outcomes this
session.

## (a) / (b) / (c) — decided from source

This is **NOT (a) missing**: `useTauriOAuthLogin.ts:133-172` calls `window.api.login`/`authGOG`/
`authAmazon`/`authZoom` on `outcome.status === 'captured'`, exactly as REQ-34.4.1-08 shipped it.

This is **NOT (b) present-but-still-stubbed**: `login`/`authGOG`/`authAmazon` are real,
Phase-34.5-ported `ipcMain.handle` channels now (`src/backend/sidecar/runnerAuthFlowRegistration.ts:136,157,195`)
— they are no longer the `UNPORTED_CHANNEL_MARKER` stub Phase 34.4.1 shipped. The `catch` block at
`useTauriOAuthLogin.ts:158-172` that turns that marker into `phase: 'blocked'` is legacy defensive
code from 34.4.1, not evidence of a live stub — REQ-34.5-04 already ported these three channels.

This **IS (c) exists-but-never-reached**: decided from `src-tauri/src/main.rs:288-326`
(`SidecarState::invoke`) — `timeout_for("oauthCaptureLogin")` returns `Some(INVOKE_TIMEOUT)` (60 s)
because `"oauthCaptureLogin"` is not a member of `LONG_RUNNING_CHANNELS` (`main.rs:134-145`, quoted
verbatim in evidence item 4 below), so `rx.recv_timeout(bound)` fires at 60 s and the command returns
`Err("sidecar invoke timed out".into())` — a REAL settle (a `#[tauri::command]` async fn that has
returned cannot leave the underlying Tauri IPC message unsent; see the R-A/R-B discrimination below).
That rejection reaches `tauriInvoke()` in `src/preload/tauriTransport.ts:92-97` and propagates to the
bare `await` at `useTauriOAuthLogin.ts:99`, which is structurally outside the `try` block that ends at
line 97 (evidence item 5).

## R-A vs R-B — which reading the evidence selects

Two readings both fit the symptom "UI stuck on Signing in…":

- **R-A** — the transport rejected at its bound (60 s) and the rejection was swallowed as an
  unhandled promise rejection.
- **R-B** — the promise simply never settled at all (a true hang).

**The evidence selects R-A**, not merely by absence of renderer log lines (both readings predict zero
renderer log lines — that alone does not discriminate) but by a **source-level structural fact**:
`sidecar_invoke` (`main.rs:332-343`) is a `#[tauri::command] async fn` that has already `return`ed a
value — `Err("sidecar invoke timed out".into())` — by the time `rx.recv_timeout(bound)` expires
(`main.rs:307-314`). Tauri's own command-invocation contract requires that a command function which
has returned MUST have its result value serialized and sent back over the IPC boundary; there is no
code path in `SidecarState::invoke` where the 60 s branch returns a value without that value reaching
the calling `tauriInvoke()` promise. A hang (R-B) would require the Rust-side future to never resolve
at all — but `rx.recv_timeout` is precisely a bounded, self-resolving primitive; it structurally
cannot leave `sidecar_invoke`'s `async fn` pending forever. **R-A is therefore not merely the nicer
reading — it is the one the source code makes possible; R-B is foreclosed by `sidecar_invoke`'s own
contract.**

**Falsifying observation for R-A** (what would overturn it): a future live run in which
`gamelib.log`'s `[Frontend]:`-prefixed lines contain a `sidecar invoke timed out` string reaching a
generic top-level unhandled-rejection logger (there is none currently wired for the renderer — see
"Implied fix" below), OR a run in which a `captured`/`timeout` outcome settles in UNDER 60 s and the
hook STILL never logs — either would mean the 60 s bound is not the actual blocking mechanism. Neither
was observed this session; all six outcomes exceeded 60 s and all six produced zero renderer log
output, which is exactly what R-A predicts and what R-B cannot be ruled in or out by (R-B is
foreclosed at the source level regardless).

## Is F-34.5-G6-01 (Epic "greyed out" form) the same defect, or separate?

**Recorded as a SEPARATE defect**, upstream of F-34.5-G6-02, with the following evidence (not
assumed):

1. Item 1's own evidence (34.5-LIVE-GATE-RERUN.md) is **0 of 3 `status=captured`** for `legendary` —
   `matchOAuthRedirect('legendary', ...)` was never even called with a matching URL, because no
   redirect was ever produced. F-34.5-G6-02's mechanism (the 60 s invoke bound swallowing an
   eventually-`captured`/`timeout` outcome) only matters for a promise that WOULD have settled with
   useful information past 60 s — Epic's promise did eventually settle (`status=timeout` at 300 s,
   per the backend log), so if F-34.5-G6-02 were the ONLY thing wrong, Epic should show the identical
   downstream shape items 2/3 show (a captured/timeout outcome silently lost). Instead, Epic's own
   defect (a non-interactive page) prevented the precondition for ANY capture (a real user-driven
   redirect) from ever existing in the first place — a defect in the embedded window's own content
   rendering/interactivity, not in the invoke-timeout plumbing this finding diagnoses.
2. `activeSeam.open(loginUrl, ...)` (`oauthLoginCapture.ts:230-248`) resolved fast enough to log its
   `label=` line within the same second as each attempt's start (`11:01:44`, `11:02:41`, `11:10:27`)
   — the window-opening call itself is not blocked by anything resembling the 60 s bound, so the
   "greyed out" rendering defect cannot be explained by `oauthCaptureLogin`'s own timeout mechanics.
3. F-34.5-G6-02's mechanism operates strictly AFTER a redirect is captured (or after the backend's
   own 300 s deadline fires) — it cannot explain a symptom (page rendered but non-interactive) that
   manifests immediately on window open, before any redirect exists to be captured or lost.

**Caveat, stated explicitly per the plan's own instruction not to pick the nicer reading:** this
conclusion is inferential (structural non-overlap of the two mechanisms), not directly falsified
against a counter-hypothesis by a dedicated live test. If a future gap cycle instruments the embedded
window's own `on_page_load`/interactivity signal and finds it, too, is gated by a sidecar-invoke
round-trip subject to the same 60 s bound, this conclusion would need revisiting. No such live
instrumentation was performed this plan (NO CODE CHANGES).

Per the standing lesson (count before scoping), every `ipcMain.handle(...)` channel across
`src/backend/sidecar/*FlowRegistration.ts` was checked for an internally-awaited deadline/wait
constant longer than `INVOKE_TIMEOUT` (60 000 ms), starting from `oauthCaptureLogin`'s own
`DEFAULT_DEADLINE_MS = 300_000`:

| # | Channel | Registration | Internal deadline | In `LONG_RUNNING_CHANNELS`? |
|---|---|---|---|---|
| 1 | `oauthCaptureLogin` | `oauthLoginFlowRegistration.ts:68` (`ipcMain.handle`) | `DEFAULT_DEADLINE_MS = 300_000` ms (`oauthLoginCapture.ts:62`) | **NO** — this finding's root cause |
| 2 | `humbleStartLogin` | `humbleLoginFlowRegistration.ts:326` (`ipcMain.handle`) | `LOGIN_WATCH_TIMEOUT_MS = 10 * 60_000 = 600_000` ms (`humble/user.ts:71`), via `HumbleUser.startLogin()` → `HumbleUser.watchForLogin()` (`humble/user.ts:222-223`) | **NO** |
| 3 | `humbleReconnect` | `humbleLoginFlowRegistration.ts:338` (`ipcMain.handle`) | same `watchForLogin()` path (`humble/user.ts:228-229`) | **NO** |

**Count: 3 channels share this defect shape**, not 1. `oauthCaptureLogin` is the one this session's
live gate happened to exercise long enough to observe (Epic/GOG/Amazon logins routinely take over a
minute for a human to complete); `humbleStartLogin`/`humbleReconnect` carry an even larger 10-minute
internal deadline and were NOT exercised by this session's live gate (Humble was not one of items
1-5), so their exposure to this exact defect is inferred from source, not live-observed this session.
Per the standing "a shared bound's defect hits every caller" lesson, a fix scoped to
`oauthCaptureLogin` alone would leave 2 of 3 known instances open.

**Scope note, deliberately narrow:** this count covers channels with an identifiable, named
deadline/poll CONSTANT exceeding 60 s (the same shape as `oauthCaptureLogin` — a bounded wait for an
external, human-paced event). It does NOT include channels whose duration is merely
network/hardware-variable with no named ceiling (e.g. `installWineVersion`,
`wineToolsFlowRegistration.ts:107`, which awaits a real download of unbounded size) — those are a
different risk shape (already-known-unbounded work, arguably belonging in `LONG_RUNNING_CHANNELS` by
the same CR-03 rationale that put `install`/`repair` there) and are named here for completeness but
deliberately excluded from the "3" count above, which is scoped to the exact deadline-vs-bound
mismatch this finding diagnoses.
