## How this register was built, and why the unit matters

**362 audit units across 281 distinct threat IDs.** The register is keyed by
**`(plan, threat_id)`**, never by threat ID alone and never by range.

Two census errors were caught while building it, both of which would have produced a
falsely-clean result:

1. **Namespace blindness.** A first pass grepping `T-34\.5-[0-9]+` found **67** IDs. The real
   register is **281**, because the gap cycles use namespaced IDs (`T-34.5-G6-*`, `-C4-*`,
   `-C5-*`, `-C6-*`, `-C7-*`) that the pattern cannot match. Auditing on 67 would have skipped
   **214 IDs — 76% of the phase.**
2. **Range-shaped coverage claims.** The SUMMARY files assert coverage as ranges
   (*"T-34.5-18 through T-34.5-22, all mitigate"*). A range is not per-ID evidence; it is the
   exact shape that lets an uncovered ID hide inside a passing statement. Every range was
   expanded and every ID scored on its own named mitigation.

30 threat IDs recur across plans with **different mitigation text each time** (`T-34.5-SC`
alone appears in 21 plans), which is why the ID alone is the wrong key.

**Also noted:** 41 of 61 SUMMARY files have no `## Threat Flags` section at all. Absence of a
flag was treated as *not* evidence of closure.

## Open Threats — 8 rows, 5 root causes

### R1 — Login-origin transcription never discharged (3 rows, Spoofing / anti-phishing)

| Threat ID | Plan |
|---|---|
| `T-34.5-C5-13` | 34.5-41 |
| `T-34.5-C6-36` | 34.5-50 |
| `T-34.5-C6-49` | 34.5-51 |

One root cause counted three times because three plans each restated the obligation.

The declared control is that the login window's title-bar origin is **transcribable by the
operator** — the anti-phishing surface a user relies on to tell a real Epic/GOG/Amazon login
from a spoofed page. `U-34.5-05`'s bar demands a live transcription. It has never been
obtained: `src-tauri/src/main.rs:3659` sets `initial_visible = false` unconditionally on the
macOS sheet path, and gate 4 (`34.5-LIVE-GATE-RERUN-3.md`, item 1 clause (i)) scored this
**FAIL** as `F-34.5-G6-16`.

Plan 34.5-52 shipped an in-page origin banner as the fix. It was **not live-transcribed
within any shard's evidence**, and `U-34.5-05` / `U-34.5-31` both remain OPEN. Gate 5 struck
the second-transcription clause as *unperformable* rather than passing it.

**Do not mark mitigated until the banner is live-transcribed on macOS.**

### R2 — A promised `grep` assertion that does not exist (2 rows, Elevation of Privilege)

| Threat ID | Plan |
|---|---|
| `T-34.5-17` | 34.5-05 |
| `T-34.5-32` | 34.5-09 |

The register states: *"`grep` asserts no `process.platform`/`isMac`/`isLinux` branch was
introduced outside comments"* in `src/backend/sidecar/wineToolsFlowRegistration.ts`.

The invariant is **true today** — a comment-stripped scan finds zero live occurrences (only
comment references at lines 207, 218, 222). **The assertion does not exist.** Searched
`wineToolsFlows.test.ts`, `runnerSliceRegistration.test.ts`, `testContainment.test.ts`,
`sidecarRejectionGuard.test.ts`. The `stripSourceComments` + `not.toMatch(/process\.platform/)`
pattern exists only in `humbleLoginFlows.test.ts`, guarding a **different module**
(`humble/loginWindowSeam.ts`) for a **different requirement** (REQ-34.4.1-13).

A future edit reintroducing a platform branch ships with zero CI signal. Classified OPEN on the
rule that *a grep assertion must be able to fail against a known-bad input* — here there is no
assertion to fail. "True today by inspection" is a coincidence, not a control.

### R3 — Keyring cache resurrects a signed-out session (1 row, Elevation of Privilege)

`T-34.5-G6-14` — plan 34.5-25. **The only open row that is a live code defect.**
Independently re-verified during this audit, not taken on the auditor's word.

Declared mitigation: *"setToken/clearToken invalidate the success cache, the failure memo
**AND the in-flight promise**."*

Implementation does the first two only. `keyringTokenStore.ts:435-440` clears `cachedToken`,
`cachedAvailable`, `failedTokenAt`, `failedTokenReason`; its own doc comment states it
*"Does NOT touch an in-flight `pendingToken`/`pendingAvailable` promise."*

The consequence is at `keyringTokenStore.ts:347`:

```ts
const value = typeof result === 'string' ? result : ''
this.cachedToken = { value }        // unconditional — no generation/epoch check
```

A read in flight when `clearToken()` fires resolves afterwards and writes its **pre-signout**
value back into `cachedToken`. Tests at `keyringTokenStore.test.ts:599,733` exercise
invalidation **sequentially only**; nothing drives a concurrent in-flight `getToken()`.

Two facts make this practical rather than theoretical: the race window is bounded by
`KEYRING_READ_TIMEOUT` = **45 seconds**, and `34.5-KEYRING-ARM-SESSION.md` recorded keyring
reads racing Keychain approval at roughly **9:1**. "Sign out while a Keychain prompt is still
pending" is a plausible sequence.

The code's rationale — mirroring `bounded_keyring_read`'s *"abandoned, not cancelled"* on the
Rust side — is defensible; you cannot un-send the request. **But it was never adopted as this
row's disposition, and the register still claims the in-flight promise is invalidated.**
Resolve by adding a generation counter so a stale resolve cannot write, or by amending the
register and logging an accepted risk. Do not leave the two disagreeing.

### R4 — A `transfer` whose target retired without its own observation (1 row, DoS)

`T-34.5-C6-06` — plan 34.5-43, disposition **`transfer`** → ledger row `U-34.5-16`.

A transfer is only closed if the target still carries the threat. `U-34.5-16`'s stated
retirement bar is a **live details-page open with no `sidecar invoke timed out` line for
`getInstallInfo`**. It is marked RETIRED in `34.5-UNTESTED-ITEMS.md` on **structural proof
only** — `LONG_RUNNING_CHANNELS` membership plus `cargo test`/`jest`. No live `getInstallInfo`
observation appears in `34.5-LIVE-GATE-RERUN-3.md` or `-RERUN-4.md`.

This is a transferred threat closed against a bar it did not meet. Either run the live
observation `U-34.5-16` demands, or amend the row to state that structural proof was accepted
as sufficient — but do not leave it claiming an unmet live observation.

### R5 — A credential precondition that did not fire (1 row, Information Disclosure)

`T-34.5-C4-50` — plan 34.5-37.

The control: a precondition forbidding real credentials during the Epic discriminator
experiment (`34.5-G6-EPIC-DISCRIMINATOR-2.md:140-145`), plus acceptance criteria requiring the
developer to confirm none was entered.

**Arm E completed a full real Epic login** — `legendary auth --code <redacted>` →
`Game list updated, got 15 games & DLCs`, logged out ~12s later. The plan contradicts itself:
`34.5-37-PLAN.md:308` asserts *"both arms were run on real hardware without a real Epic
credential"*, which the same plan's Result section disproves.

Mitigating: **self-disclosed**, not concealed (`34.5-37-SUMMARY.md:31-32,48-49`), and **no
secret value reached the repo** — the one-time code is redacted, verified separately by
`T-34.5-C4-51` (closed). The exposure is a real-account credential entered on a dev machine
during an experiment that forbade it, not a leak into version control.

### A1 — Plan 34.5-61: HIGH severity, zero threat model, undisposed residual

`34.5-61` is the **only plan in the phase with no `<threat_model>` block**, and its own
frontmatter carries `security_severity: high`. It fixed **three** credential-logging leaks in
`getRunnerCallWithoutCredentials` (`launcher.ts:1877+`), all verified present at HEAD:

| Finding | Leak |
|---|---|
| `F-34.5-G6-22` | nile PKCE `code_verifier` via `callRunner()` — a **different call site** than the two plan 34.5-53's mitigation covered |
| `F-34.5-G6-24` | GOG private-branch `--password` — user-chosen, reused secret, never previously redacted |
| `F-34.5-G6-25` | A PowerShell `-ArgumentList` regex that never matched the real backtick-quoted shape, so redaction **silently no-op'd on Windows** for `--code`/`--token` too |

Fix verified: `sensitiveArg` now covers `['--code','--token','--code-verifier','--password','--serial','--client-id']`; `launcher_callRunner.test.ts` 10/10.

**The residual has no disposition anywhere** — no `accept`, no `transfer`, no accepted-risk
entry. It exists only as `U-34.5-33`, OPEN: the GOG private-branch-password fix and the
PowerShell branch have never run on hardware (every gate in this phase ran on macOS; the
PowerShell branch is Windows-only and unit-probed only).

`F-34.5-G6-22` also vindicates the per-`(plan, ID)` keying: plan 53's mitigation for
`T-34.5-C7-09` was correctly implemented and **still missed the sibling call site**.

### A3 — Steam account id in a published commit message (no action; decision already binding)

The C5 shard flagged a real Steam account id (`userdata/35601368`) in the message of commit
`d48b4d964`. Publication state was checked rather than assumed:

```
d48b4d964  2026-08-03  docs(34.5-42): close gap cycle 5 ...
  contained in: remotes/gamelib/fix/steam-native-install-stability   ← PUBLISHED
```

The binding developer decision of 2026-08-02 is **redact-forward only**: published files and

commit messages to future credential sweeps — a pattern improvement, not a remediation.
