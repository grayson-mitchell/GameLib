<objective>
Close Routing item 4: on some attempts a GOG login reaches `status=captured` → `Login Successful` →
`Saved username to config file` and produces NO `useTauriOAuthLogin` log line at all, dumping the
developer back to Manage Accounts; on the next attempt, the identical flow propagates correctly. Same
code path, two outcomes — a race.

Purpose: the checkpoint recorded attempt 2 (19:21:10) failing this way and attempt 3 (19:22:49)
succeeding. `useTauriOAuthLogin.ts`'s effect sets `cancelled = true` in its cleanup and then returns
early — with NO log output — at two points that sit AFTER irreversible work has already happened: the
guard immediately after the capture outcome resolves, and the guard immediately after the runner's
auth channel has returned. A teardown landing in either window silently throws away a captured
single-use OAuth code, or a completed, already-persisted authentication. That is exactly the observed
signature: backend side effects present in the log, hook side effects entirely absent.

Output: cancellation semantics that can only suppress a React state update, never a completed login;
plus instrumentation that names which cancellation window fired.

**This plan does not claim to know what triggers the teardown.** `onLoginSuccess` is
`GlobalState.tsx`'s `completeOAuthLogin`, a class-instance property assigned once and therefore
referentially stable, so a dependency-identity change is unlikely and unmount is the leading
candidate — but that is a source-level inference, not an observation. Task 1 instruments the question
instead of answering it; Task 2's fix is deliberately shaped so it is correct whichever side of the
race wins, so it does not depend on Task 1's answer.

**Live observable that would prove this — nothing else counts.** A live session in which a
`runner=gog status=captured` line is followed by a `[useTauriOAuthLogin]` line for that same runner in
every attempt, including any attempt where a `phase=cancelled-midflight` line also appears. A passing
test suite proves the guard logic, not the live race.
</objective>

  <behavior>
    - A capture resolving `status: 'captured'` after teardown still hands its code to the runner's auth channel.
    - An auth channel returning `status: 'done'` after teardown still invokes `onLoginSuccess` exactly once.
    - After teardown, `setState` is never called by this effect.
    - `onLoginSuccess` is invoked at most once per run, whether or not teardown occurred.
    - Non-`captured` terminal outcomes (cancelled, timeout, unsupported, error) still return early after teardown, since they carry nothing to propagate.
  </behavior>
  <action>
    Adopt one rule and apply it uniformly: `cancelled` gates React state updates ONLY. It must never
    abandon a side effect that is irreversible (a credential already written to disk) or perishable (a
    single-use OAuth code that expires and cannot be re-obtained without a fresh user login). Record
    that rule in the module docstring in one sentence, naming this plan, so a future reader does not
    "restore" the old guards as a memory-leak cleanup.

    Concretely, make three changes.

    First, at the guard immediately after the capture outcome resolves: when
    `outcome.status === 'captured'`, do NOT return — continue to the auth exchange. Discarding the
    code guarantees the login fails; exchanging it can at worst fail the same way, and at best
    completes the login the user already performed. Keep the early return for every non-`captured`
    status, which carries nothing to propagate. Task 1's `at=capture` line is still emitted either
    way.

    Second, at the guard immediately after the auth channel resolves: remove the unconditional early
    return. When the resolved `status` is `done`, always emit the existing
    `phase=idle (login completed, library refresh triggered)` line and always invoke
    `onLoginSuccess`. This is safe because `onLoginSuccess` is `GlobalState.tsx`'s
    `completeOAuthLogin`, bound to the GlobalState instance rather than to this hook's component — it
    remains mounted when the WebView screen unmounts, and its own work is `setState` on GlobalState
    plus `handleSuccessfulLogin`, neither of which touches the torn-down component.

    Third, route every `setState` call in `run()` through a single local helper that no-ops when
    `cancelled` is true, and use that helper everywhere instead of the raw setter. One gate in one
    place is checkable; four scattered guards are how the current defect exists. Add a guard against
    double-invocation of `onLoginSuccess` using the same terminal-state boolean Task 1 introduced, so
    an effect that re-runs cannot complete the same login twice.

    Do NOT change the effect's dependency array, do NOT memoise `onLoginSuccess` at the call site in
    `screens/WebView/index.tsx`, and do NOT edit `GlobalState.tsx` in this plan. Those would be
    attempts to win the race rather than to be correct regardless of it, and they would also pull
    files outside this plan's declared `files_modified`.
  </action>

|----------|-------------|
| capture outcome → auth channel | A single-use OAuth code crosses from the capture window into a credential exchange |
| hook → renderer log file | Login-flow diagnostics are written to a log that is pasted into public-fork documents |
| torn-down component → live callback | A callback is invoked after the component that registered it has unmounted |

| Threat ID | Category | Component | Disposition | Mitigation Plan |

| T-34.5-C4-20 | Repudiation | a completed authentication discarded with no log line | mitigate | Task 1 emits `phase=cancelled-midflight at=auth authStatus=done` at exactly that site; Task 2 removes the discard entirely |
| T-34.5-C4-21 | Information disclosure | the new cancellation lines leaking a code, token or username | mitigate | Task 1 fixes the permitted key vocabulary to `runner|phase|at|authStatus|inflight` and adds a test that scans every logged argument against it (T-34.5-G6-02 evidence-handling rule) |
