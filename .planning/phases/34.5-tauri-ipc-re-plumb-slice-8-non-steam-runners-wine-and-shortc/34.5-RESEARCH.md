# Phase 34.5: Tauri IPC re-plumb slice 8 — non-Steam runners, Wine and shortcuts - Research

**Researched:** 2026-07-29
**Domain:** Electron→Tauri sidecar IPC port (Node sidecar behind a Rust shell), non-Steam storefront auth (Epic/GOG/Amazon), Wine tooling, Steam-shortcut/VDF writes
**Confidence:** MEDIUM-HIGH (wave-1 seam mechanisms verified against source; one wave-1 item — nile's true redirect host — is verified only against upstream `nile` source, not this project's live traffic)

## Summary

This phase ports 38 of 57 inventoried channels (11 auth+sign-out, 9 Wine, 7 shortcuts, 4 runner-CLI
versions, 3 other, 2 saves-sync, 2 runtime) plus three wave-1 seams that gate all of them: extending
`pathShim` with `desktop`/`exe`/`documents`, host-anchoring nile's OAuth redirect capture, and
standing up `runWineCommand`'s execution path. All three wave-1 claims in CONTEXT.md were verified
against source and hold structurally, but this research found **one factual correction** (D-15's
dialog-call-site citation is wrong — see `## Corrections to CONTEXT.md`), **one precision gap**
CONTEXT.md left as Discretion now resolved (`documents` belongs to the Saves-sync cluster, not
shortcuts), **one previously-uncited second `exe` call site** (`shortcuts.ts:227`, macOS `.app`
shortcut launch command — D-10 named only `nonesteamgame.ts:258`), and **one concrete mechanism
recommendation** for D-10's open question (how the Tauri shell hands its own executable path to the
sidecar).

**Primary recommendation:** Extend `pathShim.getPath()` with three new cases (`desktop`, `exe`,
`documents`) as wave-1 work before any of the 38 channels are ported. Resolve `exe` via a new
`GAMELIB_SHELL_EXE` environment variable set by `main.rs` at sidecar-spawn time (both dev and
packaged paths) — not a new `rustInvoke` round-trip — because `getPath()` is a synchronous function
called from inside async IPC handlers that have no reason to await a Rust round-trip for a value the
shell already knows before the child process exists. Host-anchor nile's redirect matcher on
`www.amazon.com` (verified against `imLinguin/nile`'s own `openid.return_to` parameter, MEDIUM
confidence — confirm empirically during the wave-1 plan). Land `runWineCommand`'s seam as a thin
pass-through (it already works transitively for Steam and is pure Node `child_process` plumbing with
zero Electron dependency) and prove it live only for a non-Steam runner, since that combination has
never actually run under the sidecar (install/launch are ported, but no non-Steam game has ever
reached them without a working login).

## Corrections to CONTEXT.md

**Correction 1 (loud) — D-15's dialog citation is wrong; the real dialog is elsewhere and IS in
scope.**

D-15 states: *"the macOS missing-deps path (`tools/index.ts:794`) shows a dialog. Under the sidecar a
dialog rejection crashes the app."*

Reading `tools/index.ts:776-799` (`Winetricks.checkDependencies`) directly: the `if
(missingDeps.length > 0 && isMac)` block at line 794 calls **only** `appendMessage(message)` (a
progress-stream callback) and `logWarning(...)`. **There is no `showDialogBoxModalAuto` call, no
`dialog.*` call, and no `rustInvoke` of any kind on this path.** `Winetricks.checkDependencies`'s
only caller is `Winetricks.runWithArgs` (`tools/index.ts:665`), and `Winetricks` itself is the
winetricks cluster, which D-03 **defers to Phase 34.6** — it is not reachable from any of 34.5's 38
channels at all.

The dialog D-15 is trying to describe DOES exist, but at a different, in-scope location:
`installOrUpdateTool` (`tools/index.ts:72-143`) calls `showDialogBoxModalAuto` at **line 137** on a
DXVK/VKD3D/DXMT download failure. This function IS reachable from 34.5's Wine cluster:
`toggleDXVK`/`toggleDXVKNVAPI`/`toggleVKD3D` (`main.ts:999-1019`) → `DXVK.installRemove` →
(if the tool isn't cached) `DXVK.getLatest()` → `Promise.all(tools.map(installOrUpdateTool))`.

**Practical consequence, and why this correction matters:** `showDialogBoxModalAuto`'s primary path
is `sendFrontendMessage('showDialog', ...)` — a fire-and-forget push to the renderer, not a blocking
native dialog. It only falls through to `dialog.showErrorBox`/`showMessageBox` in a `catch` block if
the push itself throws. Both of those `electronStub.dialog` members are already wired to
`RUST_DIALOG_MESSAGE` and are already non-throwing by design (`electronStub.ts:320-382`, verified —
see `## Common Pitfalls` Pitfall 3). **The D-15 "dialog reject crashes the app" landmine does not
apply to this call site as written** — it is already safe. The correction is about *citation
accuracy* (wrong line, wrong cluster, wrong scope), not about an unmitigated risk.

**Correction 2 (precision) — D-12 misnames nile's real CLI-credential directory.**

D-12 lists nile's CLI-owned config dir as `nile_store`. Reading `nile/library.ts:478-486` and
`nile/constants.ts:4`: the nile CLI's real credential/config directory is set via
`options.env.NILE_CONFIG_PATH = dirname(nileConfigPath)`, where `nileConfigPath = join(appFolder,
'nile_config', 'nile')` — **`nile_config`, not `nile_store`**. `nile_store`
(`nile/electronStores.ts:13`) is a *different* directory: the `cwd` for the `configStore`
electron-store instance that holds nile's **profile** data (`userData`), the OTHER half of D-12's own
distinction ("Epic/GOG/Amazon persist profile data via `configStore`... while their real auth tokens
are held by the runner CLIs in their own config dirs"). D-12 accidentally lists the profile-store
directory a second time where it meant to list the CLI-credential directory. **This does not change
D-12's structural conclusion** — both `nile_config` and `nile_store` are `join(appFolder, ...)`
derivatives, and `appFolder` resolves through `pathShim`'s already-implemented `userData` case
(`appFolder = join(configFolder, 'GameLib')`, `configFolder = app.getPath('appData')`), so both
already line up under the sidecar. Fix the label when this research is folded into planning/
requirements; no code or scope consequence.

**Correction 3 (gap, not an error) — D-10 names only one of two `getPath('exe')` call sites.**

D-10 names `nonesteamgame.ts:258` as the `exe` call site. A second, independent call site exists at
`shortcuts/shortcuts/shortcuts.ts:227` (`generateMacOsApp`, inside `run.sh`'s launch command for the
macOS `.app` shortcut wrapper: `` `${app.getPath('exe')} --no-gui gamelib://launch?...` ``). Same
semantic requirement (must resolve to the Tauri shell binary, not node), same consequence class if
wrong (a macOS `.app` shortcut that launches the wrong executable). Not a factual error — D-10's
mechanism note and rejection of `process.execPath` apply identically to both sites — but the plan
must not scope its `exe`-path work, or its live-gate proof, to `nonesteamgame.ts` alone.

### Alternatives Considered

| Instead of | Could Use | Tradeoff |
|------------|-----------|----------|
| Env-var handoff for `exe` path (`GAMELIB_SHELL_EXE`) | A new `rustInvoke` round-trip (e.g. `shell_get_exe_path`) | Rejected: adds async-round-trip latency and a new Rust arm for a value that never changes after process start and is trivially knowable at spawn time; also `getPath()` is a synchronous function (`pathShim.ts:45`) called from many non-async call sites in principle — an env var preserves that synchronous contract exactly, a rustInvoke would not without a structural change to `getPath()`'s signature. |
| Host-anchor nile on `www.amazon.com` | Host-anchor on a broader `*.amazon.com` suffix | The verified `openid.return_to` value from `nile`'s own source is the literal string `https://www.amazon.com` — an exact-host check is tighter and matches what the client itself requests; a suffix match is a reasonable fallback if live testing shows a country-TLD variant (e.g. `amazon.co.uk`) in practice, but should not be adopted without that evidence. |

### Pattern 1: `exe`-path handoff via spawn-time environment variable (resolves D-10's open mechanism question)

**What:** `main.rs` already knows its own executable path before it ever spawns the sidecar
(`std::env::current_exe()`, a standard-library call with no new dependency). Both existing spawn
functions (`spawn_sidecar_dev` at `main.rs:1193` and `spawn_sidecar_packaged` at `main.rs:1223`)
build a `std::process::Command` and currently set no environment variables on it. Add one:
`.env("GAMELIB_SHELL_EXE", shell_exe_path)` on both.

**Why this mechanism, not a `rustInvoke` round-trip:** `pathShim.getPath()` is a plain **synchronous**
function (`pathShim.ts:45: export function getPath(name: string): string`), matching Electron's own
synchronous `app.getPath()` contract that 20+ call sites already depend on without `await`. A
`rustInvoke` (`requestRustInvoke`) is inherently async — using it here would force every `getPath('exe')`
call site to become async, a wider blast-radius change than adding an env var the shell already has
at spawn time and the value never changes for the life of the process.

**Implementation sketch:**

```rust
// src-tauri/src/main.rs, both spawn_sidecar_dev() and spawn_sidecar_packaged()
let shell_exe = std::env::current_exe()
    .map(|p| p.display().to_string())
    .unwrap_or_else(|_| String::new()); // empty string, never panic — see fallback note below
// ... existing Command::new(...) / std_command builder ...
    .env("GAMELIB_SHELL_EXE", &shell_exe)
    .stdin(Stdio::piped())
    // ... unchanged ...
```

```typescript
// src/backend/sidecar/pathShim.ts
import { env, platform } from 'process'
// ... inside getPath(name) switch ...
case 'exe': {
  const shellExe = env.GAMELIB_SHELL_EXE
  if (!shellExe) {
    throw new Error(
      `[sidecar/pathShim] getPath('exe') is unavailable — GAMELIB_SHELL_EXE was not set by the ` +
      `Tauri shell at spawn time`
    )
  }
  return shellExe
}
```

**Testability:** Fully unit-testable — set/unset `process.env.GAMELIB_SHELL_EXE` in a jest test and
assert `getPath('exe')` returns it or throws the named error, exactly the same pattern the existing 4
cases don't need (they derive from `os`/`process.platform`, not an injected env var) but that
`electronStub.app.getVersion()`'s `pkgJson` import (`electronStub.ts:38`) already establishes as
precedent for "value baked in / handed in at a known point, read synchronously." The **live** half —
that the value the shell actually sets is a real, executable path, and that a VDF/`.app` shortcut
built from it actually launches GameLib — is the wave-1 live-gate item this phase must add (see
`## Validation Architecture`).

**Fallback if `current_exe()` fails:** `std::env::current_exe()` returns `io::Result`; on the (rare,
mostly-theoretical on desktop OSes) failure path, set the env var to an empty string rather than
omitting it or panicking — `pathShim`'s `case 'exe'` should treat an empty string the same as unset
(throw loudly), never silently write an empty path into a VDF/plist.

- **Side-effect-importing `*/ipc_handler.ts` files directly.** Every prior slice's curated-import
  rule (30 D-08 → 34.1 D-09 → 34.2 D-04 → 34.3 D-14 → 34.4 D-02) applies here too:
  `shortcuts/ipc_handler.ts`, `tools/ipc_handler.ts`, `wine/runtimes/ipc_handler.ts`, and
  `wine/manager/ipc_handler.ts` each import `backend/ipc`'s `addHandler`/`addListener`, which drags in
  more than this phase wants registered in one shot (e.g. `tools/ipc_handler.ts` also registers
  `runWineCommandForGame`, `winetricksInstall`, `winetricksAvailable`, `winetricksInstalled` — the
  last three belong to the DEFERRED winetricks cluster). Import the underlying modules
  (`shortcuts/shortcuts/shortcuts.ts`, `shortcuts/nonesteamgame/nonesteamgame.ts`, `tools/index.ts`,
  `wine/runtimes/runtimes.ts`) directly and register only the 38 channels this phase owns.
- **Treating `runWineCommand`'s wave-1 seam as greenfield.** It is not — `child_process.spawn` is a
  Node built-in already exercised by the already-ported `install`/`launch` channels for Steam. The
  actual wave-1 risk is narrower: this exact function has never been exercised for a non-Steam runner
  under the sidecar, because no non-Steam login has ever worked there. Scope wave-1 work to closing
  that specific gap (a live proof against one non-Steam runner), not to re-architecting execution.
- **Writing an empty/unset `exe` path into a VDF or `.app` plist.** Both `nonesteamgame.ts:258` and
  `shortcuts.ts:227` interpolate the value directly into a launch command with no existence check
  today (Electron's `app.getPath('exe')` cannot meaningfully fail, so none was ever needed) — the
  sidecar's version CAN fail (unset env var) and must throw loudly per `pathShim`'s own convention,
  never silently interpolate `''` or `undefined`.

## Common Pitfalls

### Pitfall 1: `documents` belongs to Saves-sync, not Shortcuts (resolves CONTEXT.md's open Discretion question)

**What goes wrong:** Assuming `documents` is a third missing name inside the shortcuts cluster (as
D-09's prose groups it) and gating it behind the same shortcuts-specific plan.
**Why it happens:** D-09 lists all three missing names (`desktop`, `exe`, `documents`) together under
one "shortcuts cluster throws" framing, and explicitly says "cluster not yet confirmed" for
`documents`.
**How to avoid:** `getPath('documents')` is called exactly once, at `save_sync.ts:146`, inside
`getDefaultGogSavePaths` — GOG-specific save-path resolution, consumed by `syncGOGSaves`
(`main.ts:1255-1257` → `libraryManagerMap['gog'].getGame(appName).syncSaves(...)`). It has **no
relationship to the shortcuts cluster at all**. Gate `documents` behind the Saves-sync plan, not
Shortcuts — and note `syncGOGSaves` therefore ALSO has a wave-1 `pathShim` precondition, the same
class of dependency D-09 named for shortcuts, just on a different cluster.
**Warning signs:** A plan that ports `syncGOGSaves` without first (or simultaneously) extending
`pathShim` will throw at runtime on any native-platform GOG save-sync call — the same throw-loudly
failure mode D-09 already described for shortcuts, just unnoticed because it wasn't in that cluster's
list.

### Pitfall 2: `runWineCommand`'s wave-1 seam is "already wired, never live-exercised for non-Steam" — not "not built"

**What goes wrong:** Scoping wave-1 Wine-seam work as if `child_process.spawn`-based Wine execution
needs to be invented for the sidecar.
**Why it happens:** D-14 frames `runWineCommand` as a wave-1 seam, which is correct, but could be
misread as "doesn't work yet."
**How to avoid:** `install` and `launch` were ported before Phase 34.1 even started (the pre-slice-4
"Already ported (28)" set, `IPC-PORT-INVENTORY.md:34`), and both are runner-agnostic — they already
route through `runWineCommand` for GOG (`gog/games.ts:690,952,1082`) and the shared
`storeManagerCommon/games.ts:254` helper legendary/nile both use. The plumbing is real and already
proven for Steam. **The actual gap:** no non-Steam game has ever been installable or launchable under
the sidecar, because `login`/`authGOG`/`authAmazon` still reject `UNPORTED_CHANNEL_MARKER` — so this
exact code path (Wine execution for a non-Steam game) has literally never run under the sidecar. Wave
1's job is to prove it works for at least one non-Steam runner once auth exists, not to build new
execution machinery.
**Warning signs:** A plan that adds new spawn/env-construction code for Wine (duplicating
`tools/index.ts:642`'s `isMac ? macEnvs : linuxEnvs`) instead of just proving the existing path live.

### Pitfall 3: The D-15 dialog landmine is real in general, but does not apply to `showDialogBoxModalAuto`'s primary path

**What goes wrong:** Treating every `showDialogBoxModalAuto`/`dialog.*` call reachable from this
phase as a live-blocking-dialog risk requiring a "resolve a safe-decline sentinel, never reject" fix.
**Why it happens:** The general sidecar gotcha (`sidecar-dialog-reject-crashes`) is real and documented
project-wide, and D-15 invokes it.
**How to avoid:** `showDialogBoxModalAuto`'s primary path is `sendFrontendMessage('showDialog', ...)`
— fire-and-forget, cannot reject, resolves synchronously. Its fallback `catch` branch calls
`electronStub.dialog.showErrorBox`/`showMessageBox` (`electronStub.ts:320-382`), and BOTH are already
implemented as non-throwing async functions wired to `RUST_DIALOG_MESSAGE` with their own internal
`.catch()` defaulting to a safe response — verified by direct read, not assumed. **No new fix is
needed here.** The only genuinely new dialog-adjacent risk this phase introduces is the ONE reachable
call site at `installOrUpdateTool` (`tools/index.ts:137`, see `## Corrections to CONTEXT.md`
Correction 1) — and it goes through the exact same already-safe `showDialogBoxModalAuto` path.
**Warning signs:** A plan task that "fixes" `showDialogBoxModalAuto` or adds a new
`dialog_open`-style Rust round-trip for this phase's dialog — unnecessary; the existing wiring already
satisfies D-15's underlying safety concern.

### Pitfall 4: Winetricks is a live dependency of one in-scope channel even though its own 3 channels are deferred

**What goes wrong:** Assuming `callTool` (in-scope, "Other" cluster) is fully independent of the
deferred winetricks cluster.
**Why it happens:** D-03 defers `winetricksAvailable`/`winetricksInstall`/`winetricksInstalled` to
Phase 34.6, which reads as "winetricks is out of this phase."
**How to avoid:** `callTool`'s `tool === 'winetricks'` case (`tools/ipc_handler.ts:31-33`) calls
`Winetricks.run(runner, appName)` directly — the same underlying `tools/index.ts` `Winetricks` object,
just not through its own dedicated IPC channels. This already works with zero extra wiring (the
function exists, is pure Node, has no Electron dependency) — it is not blocked on Phase 34.6. Flag it
explicitly in the plan/PORTED-CHANNELS doc so a reader doesn't assume `callTool`'s winetricks branch
is broken or deferred.
**Warning signs:** A plan that guards `callTool`'s winetricks case behind a "wait for 34.6" comment —
unnecessary; nothing about it depends on the deferred IPC channels.

### Known Threat Patterns for this stack

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Unanchored OAuth redirect param match (nile, pre-fix) | Spoofing | Host-anchor the matcher (Pattern 2) before `authAmazon` mints a credential from a captured value |
| Wrong `exe` value written into a Steam shortcut VDF / macOS `.app` launch command | Tampering | Never interpolate an empty/unset `GAMELIB_SHELL_EXE`; throw loudly (pathShim's existing convention) rather than writing a bad launch command silently |
| `runWineCommand`/`callTool`'s `runExe`/`winecfg` cases construct a command from caller-supplied `commandParts`/`exe` | Tampering (command construction) | Unchanged from Electron — these are existing, already-accepted trust boundaries (the caller is this app's own frontend, not untrusted remote input); this phase does not widen that boundary, it only relocates the same code onto the sidecar transport |
| Shared app-wide cookie jar (T-34.4.1-47, inherited) | Information Disclosure | Already accepted in 34.4.1; 34.5's login windows use the SAME `LoginWindowSeam`/`humble_login_open` arm, landing Epic/GOG/Amazon cookies in the same jar Humble uses — any future per-runner "disconnect" must be domain-scoped exactly as `humbleDisconnect`'s already-shipped fix is, never a blanket clear |
| Send-kind sign-out channel (`logoutGOG`) failing silently | Repudiation (a failed sign-out that looks successful) | Registration-kind cross-check test (Code Examples above) plus, if the live gate finds it actually fails, escalate to a gap cycle per this project's blocking-live-gate precedent — do not ship a silently-broken sign-out |
