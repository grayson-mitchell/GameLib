## Open finding 1

### Row 6 — T-34.5-C6-06 (34.5-43), Denial of service — OPEN

**Declared mitigation (transfer):** "Cannot be closed here... Task 3 transfers it to the record as new
ledger row `U-34.5-16`, **retiring only on a live observation**."

**What the code shows:** the underlying code-level DoS mechanism IS fixed. `src-tauri/src/main.rs:208-219`
adds `"getInstallInfo"` to `LONG_RUNNING_CHANNELS`, and `timeout_for()` (verified by an array-iterating
`cargo test` case) returns `None` for every member — `getInstallInfo` can no longer be hard-killed at 60s
with its late response silently dropped. This is real, verified, working code (row 10 above, CLOSED).

**What the ledger shows:** `34.5-UNTESTED-ITEMS.md` row `U-34.5-16`'s own "Retirement Proof Needed" cell
names: *"A live details-page open on a real GOG title that renders its size/version fields, with no
`sidecar invoke timed out` line for `getInstallInfo` anywhere in the preserved `gamelib.log`."* That is a
**live observation**, matching the transfer disposition's own "only on a live observation" language.

The row's RESULT cell nonetheless reads **"RETIRED 2026-08-11 by plan 34.5-44 Task 4"**, and states its
own justification explicitly: *"`getInstallInfo` now [is] a `LONG_RUNNING_CHANNELS` member... [proven by]
array-iterating `cargo test`... `longRunningChannels.test.ts`."* Every one of those is a structural/unit
proof, not the live-session proof the row's own cell names. Searching every live-gate document produced
since (`34.5-LIVE-GATE-RERUN-3.md`, `34.5-LIVE-GATE-RERUN-4.md`) for `getInstallInfo` finds only structural
confirmations (channel-registration greps, `LONG_RUNNING_CHANNELS` membership greps) — never a details-page
open, and never a `gamelib.log` grep for the absence of a timeout line.

This is a ledger-integrity violation of the project's own Ledger Rule 1 ("a row retires only by the
observation named in its own cell"), applied inconsistently: `U-34.5-14` (row 28's neighbour) retires
correctly because its own cell names a *completed diff* as sufficient, and that diff exists. `U-34.5-05`
(the sibling spoofing row, see Open finding 2) was left correctly OPEN despite a code fix landing, with an
explicit note that a live transcription is still required. `U-34.5-16` is the one row in this cycle where a
structural fix was substituted for the live proof its own text demands, and the row was closed anyway.

**Verdict for this audit:** the acute DoS mechanism is genuinely closed in code (do not re-open row 10).
The **transfer's own declared closure condition** — required by both the original threat-model text and the
ledger row it created — was not met, and the row was marked RETIRED regardless. Per the audit brief's own
standing lesson ("a transfer whose target quietly closed without discharging the threat is exactly that
failure"), this row is reported OPEN.

**Recommendation:** either re-open `U-34.5-16` pending an actual live-gate observation (a `getInstallInfo`
details-page open with no timeout line in `gamelib.log`), or explicitly amend the row's retirement
condition with a stated developer decision that the structural proof is accepted as sufficient — but do
not leave the row silently claiming a live observation that never happened.

## Open finding 2

### Rows 37 and 51 — T-34.5-C6-36 (34.5-50) / T-34.5-C6-49 (34.5-51), Spoofing — OPEN

**Declared mitigation:** "Item 1 requires the login window's own title-bar origin to be transcribed
(`U-34.5-05`), which is the anti-phishing surface plan 34.5-27 landed."

**What the live gate itself found (this very cycle's own work, `34.5-LIVE-GATE-RERUN-3.md` item 1 clause
(i), finding `F-34.5-G6-16`):** the anti-phishing origin title is **never visible on macOS**. The login
window is unconditionally presented as a native AppKit sheet
(`src-tauri/src/main.rs:3659` — `let initial_visible = false;`, confirmed still present at current HEAD),
and AppKit sheets structurally render no title-bar UI at all. `on_document_title_changed`'s composed
`{origin} — {document title}` string is still set on the underlying `NSWindow`, but that call has no
visible effect for a sheet-presented window. Operator report, live session B: *"there is no url in the
titlebar... just the page."* Item 1's clause (i) was scored **FAIL** by explicit developer decision — "the
observation is complete and positive (the feature does not exist on macOS as built), not merely unproven."

This means a macOS user has **no way to verify the origin of the page they are entering GOG/Amazon/etc.
credentials into** in the embedded login window — precisely the spoofing threat T-34.5-C6-36/49 were
written to close. The code that composes the origin string exists, but it does not fire observably; this
is exactly the class of defect the audit method requires catching ("verify the mitigation FIRES, not
merely that the code EXISTS").

**Disposition of the underlying finding:** this was **not** silently accepted. `34.5-CYCLE7-ROUTING.md`
correctly carries it forward as work item 1, and plan `34.5-52` shipped a code-level fix (an in-page origin
banner, since AppKit sheets cannot render a title bar) — but `34.5-52-SUMMARY.md` itself states plainly:
*"Nothing in this plan or this SUMMARY claims `F-34.5-G6-16` is closed... it closes only when the banner is
live-transcribed... never merely when this code lands."* `U-34.5-05` was re-targeted, not retired, and
`U-34.5-31` was opened for the banner's own residual spoofability. As of this shard's own two plans
(34.5-50, 34.5-51), the mitigation these two threat-model rows point to is confirmed non-functional on
macOS and was still open at the time this shard's work concluded.

**Verdict for this audit:** OPEN. The gap is real, was honestly self-discovered and self-reported by the
project's own process (not found by this audit), and a fix is in flight (34.5-52) but not yet
live-verified as of this shard. This is consistent with the prior gap-cycle-5 audit's finding at
`SECURITY-C5.md` row 20 (`T-34.5-C5-13`), which flagged the same underlying macOS title-bar defect as OPEN
before this cycle's own live gate (re-)discovered and root-caused it as `F-34.5-G6-16`.

**Recommendation:** treat `F-34.5-G6-16`/`U-34.5-05`/`U-34.5-31` as a standing BLOCKER on any claim that
T-34.5-C6-36/49 (and their ancestor, `T-34.5-C5-13`) are mitigated, until the wave-5 live gate
(plan 34.5-59, per the project's own routing) live-transcribes the in-page banner and both rows retire on
that observation.
