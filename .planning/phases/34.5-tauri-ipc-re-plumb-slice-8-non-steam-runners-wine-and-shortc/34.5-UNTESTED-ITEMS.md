## Interaction with plan 34.5-35

Plan 34.5-35 raised `KEYRING_READ_TIMEOUT` 8s→45s (`src-tauri/src/main.rs`) and
`KEYRING_FAILURE_MEMO_MS` 15s→120s (`src/backend/sidecar/keyringTokenStore.ts`) to close the
keyring read-timeout/human-approval race (Routing item 3, ledger row `U-34.5-10`). Its own live
proof REQUIRES the KEYRING arm — a session run with the dev-only vault (`U-34.5-01`) enabled
never issues a real `keyring_get`, so it cannot demonstrate the raised timeout/memo bound doing
anything at all, and cannot produce the single-Keychain-prompt observation `U-34.5-10`'s own row
names.

**Binding statement**: a run using the dev-only secret vault CANNOT serve as evidence for plan
34.5-35's item-3 ("only ONE Keychain approval prompt") claim. `U-34.5-01` and `U-34.5-10` therefore
need EITHER two separate live runs, OR one single run with `GAMELIB_DEV_SECRET_VAULT` left unset
(disabled) so both the real keyring path (retiring `U-34.5-01`) and the read-timeout/memo race fix
(retiring `U-34.5-10`) are exercised by the SAME session. A gate operator who enables the vault to
save time on Keychain prompts is implicitly choosing to leave BOTH rows open for that run, not
just `U-34.5-01`.

## Rules

1. A row is retired ONLY by the observation named in its own row, never by a passing test suite and
   never by inference from a neighbouring row.
2. Any plan that creates a new untested hole MUST add its row in the same commit that creates the
   hole.
3. This ledger is read at every gate-authoring decision, and any OPEN row that the gate's own items
   would have covered must be named in the gate contract as a known hole rather than silently
   assumed covered.
