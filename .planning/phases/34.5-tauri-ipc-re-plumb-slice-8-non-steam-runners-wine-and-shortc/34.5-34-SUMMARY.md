# Phase 34.5 Plan 34: OAuth cancellation instrumentation + post-teardown propagation fix Summary

**`useTauriOAuthLogin.ts` now names every cancellation window with a distinct diagnostic log line and can no longer discard a captured OAuth code or a completed GOG/Epic/Amazon/Zoom login when the WebView screen unmounts mid-flight -- proven by 48 unit tests, still OPEN on the standing ledger pending a live session.**

## Accomplishments

- Task 1: instrumented all four of the plan's named cancellation sites (`login-url`, `capture-transport`, `capture`, `auth`) with a `phase=cancelled-midflight at=<site>` log line, plus `authStatus=<status>` at the `auth` site -- the unambiguous signature of a completed authentication being discarded. Added a `phase=teardown inflight=<bool>` line from the cleanup, tracked via a new `reachedTerminal` local set at every terminal path of `run()`.
- Task 2: removed the unconditional early return at the `capture` and `auth` sites. A `captured` outcome now continues to the auth exchange even after teardown (a single-use code is perishable and must not be discarded); a `status: 'done'` auth response now always invokes `onLoginSuccess` and logs, whether or not teardown landed first. Every `setState` call in `run()` now routes through one `safeSetState` helper that no-ops when `cancelled`, replacing four scattered raw calls. `onLoginSuccess` is guarded against double-invocation via `reachedTerminal`.
- Module docstring records the rule by name ("cancellation suppresses state updates only... Plan 34.5-34"), so a future "leak cleanup" cannot silently restore the removed guards.
- `npm run test:ci`: 3528/3528 passed. `npx tsc --noEmit`: clean.
- Added ledger row U-34.5-09 (Task-2-created hole): this fix is unit/structural proof only; the live observable that retires it is named explicitly.

## Decisions Made

- **Conformed to the plan's fixed four-site vocabulary despite a fifth `if (cancelled) return` existing in the code.** The plan's action text explicitly enumerates `capture`, `auth`, `login-url`, `capture-transport` as a closed set, and its acceptance criteria requires `grep -c "phase=cancelled-midflight"` to equal exactly 4. The pre-existing code has a fifth guard (the catch block wrapping the entire auth-exchange try, catching a REJECTED auth-channel call) that the plan's prose never mentions. Left it un-instrumented, matching its own "harmless, nothing irreversible" rationale already applied to the login-url/capture-transport sites — a rejected auth call has no persisted credential or single-use code to lose.
- **`onLoginSuccess` guarded by `reachedTerminal`, not by `cancelled`.** The plan is explicit that `onLoginSuccess` must fire regardless of cancellation (it targets GlobalState, not this hook's component), so the only protection needed is against a hypothetical double-call within a single `run()` closure — which the existing linear control flow already makes structurally impossible, but the guard is added defensively per the plan's own instruction.
- **Non-`captured` cancelled outcomes still return early** (cancelled/timeout/unsupported/error) since none of them hold anything perishable or irreversible to propagate — matches the plan's explicit behavior spec.
- **Added ledger row U-34.5-09** for the same reason plan 33 added U-34.5-07/08: the critical_constraint governing this execution states the standing ledger rule plainly ("a passing test suite NEVER retires a row"), and this plan's fix is proven only against a hand-rolled effect harness in unit tests, never a live session.
