# JSON-transport `undefined`→`null` hazard — sweep (fix/34.5-33 follow-up)

Written after fixing the live-proven `steamFlowRegistration.ts` `refreshLibrary` regression
(2026-08-01 `pnpm tauri:dev` session, `gamelib.log` lines 14-16: `refreshLibrary failed
runner=null: unknown runner`). Not a new plan — a scoped follow-up fix. This document records the
required sweep for the same defect class across every sidecar registration module, per this
follow-up's own scope item 3: a gotcha documented at one call site with no sibling sweep has
already recurred four times in this project (`publicdir-getapppath-chunking`); this one does not
get a fifth.

## The defect class

Under Electron, `ipcRenderer.invoke(channel, ...args)` uses the structured-clone algorithm, which
preserves `undefined` exactly. Under the Tauri sidecar (`preload/tauriTransport.ts` →
`requestRustInvoke` → the Rust shell → the sidecar's stdin RPC frame), request arguments are
JSON-encoded. `JSON.stringify([undefined])` produces `"[null]"` — an explicitly-passed `undefined`
argument (an array ELEMENT that IS `undefined`, as opposed to an OMITTED argument, which simply
shortens the args array and never reaches this hazard at all) arrives at the sidecar handler as
`null`, never `undefined`.

**The defect fires when a handler compares a JSON-transport-delivered argument against `undefined`
with a strict `!==`/`===` operator whose FALSE branch is presumed unreachable for the "no value
supplied" case, and that false branch's behaviour differs from the true branch's** — e.g. gating
entry into a "the caller supplied a specific value" branch that throws on an unrecognized value,
when "no value supplied" was meant to route elsewhere. Optional chaining (`?.`), truthy/falsy
checks (`if (x)`), and default parameters combined with falsy checks are NOT vulnerable to this
class, because `null` and `undefined` are both falsy and both short-circuit `?.` identically —
only a *strict* equality/inequality check against `undefined` specifically (not `null`, not a
truthy check) creates the hazard.

## Method

Swept every `src/backend/sidecar/*FlowRegistration.ts` module plus `storeRegistration.ts` for
`!== undefined`, `=== undefined`, and `typeof x === 'undefined'` applied to a value derived from a
handler's `...args: unknown[]` (or a named RPC parameter). `hasOwnProperty`/`typeof x === 'string'`
type-guard patterns were also checked, since a defect could hide behind a widened type guard too.

```
grep -n "undefined" src/backend/sidecar/*FlowRegistration.ts src/backend/sidecar/storeRegistration.ts
grep -n "hasOwnProperty\|typeof .* ===\|typeof .* !==" src/backend/sidecar/*FlowRegistration.ts src/backend/sidecar/storeRegistration.ts
```

## Verdict

**One defect found and fixed** (#1). Two sites in the codebase (`runnerAuthFlowRegistration.ts`
`authAmazon`, `humbleLoginFlowRegistration.ts` `revealPost`) had already independently
identified and correctly handled this exact hazard before this sweep — cited above as positive
precedent, proof the pattern is knowable in advance, not just in hindsight. One latent,
currently-unreachable caveat noted (#8) for the record, not fixed, since no live caller exercises
it and "fix everything that could theoretically matter" is out of this follow-up's scope (the
task's own scope item 3 asks for a sweep and a fix of same-defect hits, not a preemptive rewrite
of every optional-argument site in the sidecar).

### Offline arms run

1. **Frame-level RPC test** (`shortcutsFlows.test.ts`, describe block `F-34.5-G6-08
   discriminator`): a real `{id, kind:'invoke', channel:'addToSteam', args:[...]}` frame was
   written into the REAL `startRpcServer` loop (`sidecarRpc.ts`), against the REAL, unmocked
   `addNonSteamGame`/`shortcutsFlowRegistration.ts` handler chain (only `backend/wiki_game_info`
   is mocked, per this file's own standing convention, to keep the chain network-free) and a
   disposable `tmp` Steam-root fixture. The emitted stdout frame was parsed and asserted:
   `frame.ok === true`; `Object.prototype.hasOwnProperty.call(frame, 'result') === true` (the
   H2/H3 discriminator — an OWN-key assertion, not merely a value assertion); `frame.result ===
   true`. **Result: PASS.** This directly excludes H2 (the handler DOES return a value on this
   path, as source already proved) and H3 (the envelope carries an own `result` key with the
   correct value under offline/fast conditions) — the sidecar's JSON-RPC transport is proven
   sound for the ordinary, non-timed-out case.
2. **Source-text pin for interfaces fact 2** (same describe block): reads `src-tauri/src/main.rs`
   off disk and asserts it still contains the literal `unwrap_or(Value::Null)` in the response
   branch. **Proven RED**: with that literal temporarily changed to `.unwrap()` in a scratch
   edit of the real file, the assertion FAILED with:
   ```
   expect(source).toContain('unwrap_or(Value::Null)')
   ```
   (Jest's own diff output, `shortcutsFlows.test.ts:830`, `1 failed, 27 skipped`). The file was
   restored (`diff` against the pre-edit backup confirmed byte-identical) and the assertion PASSED
   again (`27 skipped, 1 passed`). This pins the fact that the Rust leg's floor is `Value::Null`,
   never `undefined` — the single most decisive discriminator between H1/H5 (a genuine
   `undefined`, reachable only above this leg) and H3/H4 (a genuine `null`, reachable only at or
   below it).

### H5 exposure — observation, not conclusion

At execution time, `addToSteam` is **absent** from `LONG_RUNNING_CHANNELS`
(`src-tauri/src/main.rs:134-168`), so `timeout_for("addToSteam")` returns `Some(INVOKE_TIMEOUT)` =
60s. `addNonSteamGame` (`nonesteamgame.ts`) does two networked things before its VDF write at
`:318-321`: `getWikiGameInfo(game)` at `:209` (PCGamingWiki + gamesdb — gate 3's own session
recorded PCGamingWiki 403s) and `await prepareImagesForSteam(...)` at `:281` (SteamGridDB/CDN
artwork downloads). Either can plausibly exceed 60s on a slow network or a rate-limited/blocked
request. **This can only be confirmed or excluded by a live log** — a unit test cannot make a real
PCGamingWiki request time out, and the fingerprint this mechanism leaves
(`[shell] response for unknown/timed-out id=<id> (dropped)`, `main.rs:5177`) only appears against
real wall-clock time on a real network.

### H1 exposure — observation, not conclusion

Gate 3's evidence was captured through a WKWebView/Safari Web Inspector session under Tauri, not
Chrome DevTools. A bare `await window.api.addToSteam(...)` typed at a WebKit inspector prompt is a
plausible candidate for reporting a wrapper/microtask completion marker rather than the promise's
own resolved value — this is a known WebKit inspector quirk, not something this project's own
prior findings have pinned for THIS call shape. Like H5, this can only be confirmed or excluded
live: the discriminating observable is whether an explicit `.then((v) => console.log('[G6-08]',
typeof v, JSON.stringify(v)))` readout differs from the bare `await` prompt's own display, in the
SAME live session.

### Verdict

VERDICT: NOT REPRODUCED. No offline arm reproduced the drop. The offline frame-level test proves the transport is sound
under ordinary (fast, non-timed-out) conditions — excluding H2 (source-proven; handler always
returns) and H3 (frame-level proof; the envelope carries `result:true` with its own key) as the
GENERAL-CASE mechanism. H4 is excluded by interfaces fact 2 (source-pinned, RED-proven): the
Rust leg's floor is `Value::Null`, never `undefined`, so a genuine `undefined` observation (as
gate 3 recorded) cannot originate there. The two surviving candidates — **H1** (a WKWebView
DevTools artifact) and **H5** (the 60s bound racing two networked awaits) — are BOTH live-only:
neither can be reproduced nor excluded by any unit test, because H1 requires a real WKWebView
inspector session and H5 requires real wall-clock network timing. Per this section's own
"H1/H5 exposure" notes above, the discriminating observable for each is named for the next live
session to capture.
