## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| sidecar → OS Keychain | Every read crosses into the platform secure store and may raise a user-facing approval dialog |
| in-memory secret cache → process lifetime | A decrypted secret held in memory outlives the Keychain interaction that authorised it |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-34.5-G6-14 | Elevation of privilege | failure memo resurrecting a signed-out session | mitigate | The binding correctness floor is extended, not weakened: `setToken`/`clearToken` invalidate the success cache, the failure memo AND the in-flight promise before issuing their underlying call. A dedicated test proves a post-`clearToken` read hits the transport |
| T-34.5-G6-15 | Denial of service | a permanent negative cache locking a user out of their own secret | mitigate | The memo is time-bounded, justified against `KEYRING_READ_TIMEOUT`'s 8 s, and a test proves a read after expiry reaches the transport |
| T-34.5-G6-16 | Repudiation | a user believing they approved a prompt that was already abandoned | accept | `bounded_keyring_read` abandons rather than cancels the worker thread; that is pre-existing shell behaviour this plan does not change. Recorded so it is not later mistaken for something this fix introduced |
| T-34.5-G6-17 | Information disclosure | secret held in memory for the memo window | accept | Pre-existing and already documented in `keyringTokenStore.ts`'s own header as an accepted consequence of the read cache; this plan adds no new secret to memory — a memoized FAILURE holds no secret at all |
| T-34.5-G6-SC | Tampering | npm/cargo installs | mitigate | This plan installs no packages. Any install requires `slopcheck` plus a blocking human checkpoint first |
