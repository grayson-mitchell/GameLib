<discrepancy_resolution>
The outline flagged one load-bearing discrepancy and instructed the planner to build the
discriminator rather than assume it away: **why did `getInstallInfo` log its
`[GAMELIB_UNPORTED_CHANNEL]` rejection 16 times while the 8 EOS channels logged zero, when both are
exposed identically via `makeHandlerInvoker`?**

**This was settled at planning time against the preserved UAT log and the live tree. Do not re-open
it; verify the two anchors below and move on.**

The two candidate mechanisms were (a) the EOS calls never fire at all, guarded by an earlier
platform/runner/render condition, versus (b) they fire and reject silently without logging. **(b) is
correct**, and the reason is a missing bridge, not a missing call:

1. **The sidecar never logs an unported rejection for ANY channel.**
   `src/backend/sidecar/sidecarRpc.ts:113-120` writes `UNPORTED_CHANNEL_MARKER` into the *response
   frame* and returns. There is no `logWarning`/`logError` on that path. So the marker's presence in
   `gamelib.log` is never evidence that the sidecar saw the call, and its absence is never evidence
   that it did not.

2. **The only renderer -> `gamelib.log` bridge is `window.api.logError`, and it must be called
   explicitly.** Discriminator, run against the preserved UAT log
   `~/Library/Logs/GameLib/gamelib.log.34.5-uat-20260803`: all 16 marker lines carry the
   `[ERROR]: [Frontend]:` prefix, i.e. they came through `window.api.logError`, not from the
   sidecar. Their source is `src/frontend/screens/Game/GamePage/index.tsx:275-279`, an explicit
   `.catch` that calls `window.api.logError`. `src/frontend/helpers/index.ts:88`'s `getInstallInfo`
   itself has no catch -- the logging lives entirely at that one call site.

3. **The EOS call sites have no catch, so their rejections become *unhandled* -- and unhandled
   rejections are not bridged.** `src/frontend/index.tsx:41` bridges only
   `window.addEventListener('error')` to `window.api.logError`. There is **no**
   `unhandledrejection -> logError` bridge anywhere. An unhandled EOS rejection is instead caught by
   `src/frontend/bootErrorSurface.ts:49`, which recognises `UNPORTED_CHANNEL_MARKER`, emits a
   `console.warn` and returns. `console.warn` lands in the Web Inspector console only. **Hence zero
   lines in a log that structurally could never have contained them.**

**Consequence for the fix, and it is the whole point:** the calls DID fire and DID reject. Candidate
(a) is FALSIFIED for the three reachable paths -- `getEosOverlayStatus` (index.tsx:69,
unconditional `useEffect`), `getLatestEosOverlayVersion` (index.tsx:78, unconditional `useEffect`)
and `installEosOverlay` (index.tsx:126, the Install `onClick`). Candidate (a) is TRUE for exactly
one channel, `isEosOverlayEnabled` (index.tsx:96-98), which is `isWindows`-gated and genuinely never
fires on macOS -- so unavailability must be derived from the two unconditional probes, never from
that one.

**The defect is therefore not "the call is missing" but "the rejection has nowhere to go".** The fix
is a catch at every EOS call site that (i) routes to `window.api.logError` so the decline becomes
durable evidence, and (ii) flips the panel into a visible declined state so the UI stops asserting
backend facts it never learned.
</discrepancy_resolution>
