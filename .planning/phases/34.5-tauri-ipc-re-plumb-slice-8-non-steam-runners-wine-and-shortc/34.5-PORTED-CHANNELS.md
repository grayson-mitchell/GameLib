# Phase 34.5 — Declared Ported-Channel List

**Purpose:** The enumerated set plan 34.5-15's blocking live gate and Phase 35 both start from,
mirroring how `34.4.1-PORTED-CHANNELS.md` served the same role for the prior slice. It describes
what actually shipped in plans 34.5-01 through 34.5-13, verified row by row against every prior
plan's own `SUMMARY.md`, never against planning-time intent. **If the measurement disagrees with
the prediction, the measurement wins** — the same discipline `34.4.1-PORTED-CHANNELS.md` stated
and this document inherits.

**This document was originally written BEFORE plan 34.5-15's live gate ran.** That FIRST live gate
ran 2026-08-01 (developer-driven on real macOS hardware) and FAILED: 0 of 5 items PASS, 4 FAIL
(items 1, 2, 3, 5), 1 NOT ATTEMPTED (item 4) — all three OAuth runner binaries failed to spawn under
the sidecar (`spawn ./{legendary,gogdl,nile} ENOENT`), because `publicDir` resolved to a nonexistent
`src-tauri/public`. See `34.5-LIVE-GATE.md` for that FAILED first run's full evidence; it is
byte-unchanged and remains the record of that run — never cite it as evidence of a PASS.

Gap-cycle plans 34.5-16/17/18 fixed that root cause (G-1) at the code level, and plan 34.5-19
authored a RE-RUN contract, executed by plan 34.5-20 on 2026-08-01: **`34.5-LIVE-GATE-RERUN.md`**.
The re-run also FAILED, 0 of 5 items PASS (3 FAIL — items 1, 2, 3 — and 2 NOT ATTEMPTED — items 4,
5) — but the G-1 fix IS proven closed (items 2 and 3 both reached `status=captured` at the backend
for the first time ever; the first run never got past the `ENOENT` spawn failure). The re-run
surfaced a NEW, downstream defect: Epic's login form never becomes interactive (0/3 captures), and
GOG/Amazon's successful backend captures are never consumed into a completed, UI-visible,
library-populated login. Every `LIVE (item N)` cell below now reflects the RE-RUN's recorded
result — FAIL for items 1/2/3's cells, PENDING for items 4 and 5's cells (both genuinely NOT
ATTEMPTED this run, each Riders cell says why). **No `LIVE (item N)` cell here may be read as "seen
working"; a FAIL cell means the opposite was observed, and a PENDING cell means not attempted, not
proven either way.** See `34.5-LIVE-GATE-RERUN.md` for full evidence and the new downstream-defect
diagnosis. Phase 34.5 does NOT close on this result — another gap cycle is required (D-08's
no-partial-pass rule, unchanged).

## What shipped

**38 of 57 inventoried channels are ported**, registered across four new sidecar registration
modules: `runnerAuthFlowRegistration.ts` (11), `wineToolsFlowRegistration.ts` (9),
`shortcutsFlowRegistration.ts` (7), `runnerMiscFlowRegistration.ts` (11) — 11+9+7+11 = 38, measured
by plan 34.5-13's completeness test (`runnerSliceRegistration.test.ts` Describe 6), not merely
predicted by this phase's own CONTEXT.md.

**3 channels are DROPPED permanently** (D-02): `authZoom`, `getZoomUserInfo`, `logoutZoom`. Zoom
sign-in dies at the Phase 35 cutover — accepted, because Zoom is absent from GameLib's stated core
value ("Epic, GOG, Amazon, and Steam") and is purely inherited from Heroic.

**16 channels are DEFERRED to the newly-inserted Phase 34.6** (D-03/D-05): EOS overlay (8:
`disableEosOverlay`, `enableEosOverlay`, `getEosOverlayStatus`, `getLatestEosOverlayVersion`,
`installEosOverlay`, `isEosOverlayEnabled`, `removeEosOverlay`, `updateEosOverlayInfo`), SteamGridDB

`steamgriddb.searchGame`, `steamgriddb.setApiKey`), and winetricks (3: `winetricksAvailable`,
`winetricksInstall`, `winetricksInstalled`).

**The dropped and deferred channels required NO new code.** The `UNPORTED_CHANNEL_MARKER` machinery
(`src/common/types/sidecarTransport.ts`) already catches and declares them at boot — dropping or
deferring means *let it reject and declare it honestly*, not *build a new degradation path*. Plan
34.5-13's SEAM Invariant B test (`runnerSliceRegistration.test.ts` Describe 7) directly asserts all
19 names are absent from both `handlerRegistry` and `listenerRegistry`, so they still reject with
`UNPORTED_CHANNEL_MARKER` — measured, not assumed.

**38 + 3 + 16 = 57**, reconciling exactly against `IPC-PORT-INVENTORY.md`'s "Phase 34.5" section
(the authoritative work-list, counted at 57 during `34.5-CONTEXT.md`'s own discussion).

**None of the 38 has passed a live gate.** Every one is proven registered by automated test
(bidirectional registration-kind, curated-import discipline, argument-forwarding, or a real-filesystem
loud-throw pin, depending on the channel). Plan 34.5-15's blocking 5-item live gate ran on 2026-08-01
and FAILED — 0 of 5 items PASS. Its own precondition 1 (Phase 34.4.1's own gate recording PASS on

### Two corrections this declaration must not paper over

1. **`getDefaultSavePath` is genuinely unported, and GOG saves-sync does not work end-to-end under
   the sidecar until Phase 34.6 ports it.** CONTEXT.md's D-09 and `34.5-RESEARCH.md`'s Pitfall 1
   both claim `syncGOGSaves` reaches `save_sync.ts:146`'s `getPath('documents')` (via
   `getDefaultGogSavePaths`). Plan 34.5-12 verified this is wrong: `syncGOGSaves`'s own handler
   chain (`libraryManagerMap['gog'].getGame(appName).syncSaves(arg, '', gogSaves)`) only iterates
   the already-resolved `gogSaves` array it is handed — it never calls `getDefaultGogSavePaths`. The
   real and only caller of `getDefaultGogSavePaths` is the separate `getDefaultSavePath` channel,
   invoked by the frontend (`SyncSaves/gog.tsx`'s `getLocations()`) *before* `syncGOGSaves`, in its
   own round trip. `getDefaultSavePath` is **not one of this slice's 38 channels** — confirmed
   absent from every sidecar registration module (`grep -rn getDefaultSavePath src/backend/sidecar/`
   returns nothing) — and remains genuinely unported after this phase. The Discretion question
   research resolved (`documents` belongs to the saves-sync domain, not shortcuts) still holds; only
   the specific claim about which channel's *runtime call path* reaches the line is corrected.
   Practical consequence, stated plainly: **the frontend's GOG saves-sync settings panel does not
   resolve its default location under the sidecar today** — `syncGOGSaves` itself works standalone
   once a caller supplies a `gogSaves` array by some other means, but the panel's own
   location-resolution round trip fails. Logged as deferred item 4 in `deferred-items.md`, flagged
   for Phase 34.6.
2. **`save_sync.ts` is NOT a new electron-reach entry point.** Plan 34.5-13's own prediction (echoed
   from CONTEXT.md/RESEARCH.md) that adding this slice's four registration modules as
   `electronReachLedger.test.ts` entry points would newly confirm `save_sync.ts` as
   electron-reaching did not hold — measured directly, the electron-importing module count stayed
   at 34 (unchanged from the pre-34.5 baseline). `save_sync.ts` is imported by exactly one
   first-party file in the whole repo: `src/backend/main.ts`, which has never been one of the
   ledger's entry points and is not reached transitively by any of this slice's four new modules.
   Recorded here so this document's own channel-count claims are never read as implying a
   reach-ledger change that did not actually happen.

## Accepted residuals

- **`processShortcut`'s `ctrl+r` and `ctrl+shift+i` are DEGRADED under Tauri (T-34.5-27).** They
  reach `electronStub.ts`'s `fakeWindow.reload()` and `fakeWebContents.openDevTools()` — logged
  no-ops added by plan 34.5-08, not a functioning renderer reload or devtools toggle. This is an
  accepted gap, not a hidden one: a shell-level reload/devtools-open has no sidecar/WebView
  equivalent, and inventing one would be new work, not a port. `processShortcut`'s other four cases
  (documented in `shortcutsFlows.test.ts`'s six-case switch coverage) are unaffected.
- **Amazon and GOG cookies persist in the shared app-wide cookie jar after sign-out — the inherited,
  accepted `T-34.4.1-47` residual (T-34.5-37).** Spike 015 (Phase 34.4.1) found no per-window cookie
  isolation by default; Electron's own `NileUser.logout()`/`GOGUser.logout()` never cleared these
  cookies either, so this phase adding a clear would be a behaviour CHANGE, not a faithful port.
  Epic's sign-out (plan 34.5-06) IS domain-scoped (`epicgames.com` apex, mirroring `humble/user.ts`'s
  own convention) because Epic's cleanup previously aborted mid-wipe under the sidecar's session
  stub — a real defect this phase fixed, unrelated to the Amazon/GOG residual. Any future
  Amazon/GOG cookie clear MUST be domain-scoped the same way, never a blanket wipe.
- **The `www.amazon.com` anchor's mechanism is CONFIRMED, but the broader research uncertainty this
  entry tracks stays OPEN (research Assumption A1).** The FIRST run FAILED before it could confirm
  or falsify the anchor at all (`nile` `ENOENT` before any Amazon login attempt). The RE-RUN
  (`34.5-LIVE-GATE-RERUN.md` item 3) reached `status=captured` at the backend with a zero-count
  `origin-mismatch` grep across the full session — CONFIRMED structurally from `matchOAuthRedirect`'s
  own code, since a `nile` `captured` outcome is only reachable via an exact `www.amazon.com`
  hostname match. **This does not retire Assumption A1 as a standing claim**: the claim's own
  eligibility rule requires a PASS of item 3 as a whole (matched redirect AND populated library), and
  item 3 FAILED on the library half (no follow-up `nile auth --login` CLI invocation, no frontend
  `captured-blocked` transition). The narrow host-anchor mechanism is confirmed; the broader
  end-to-end claim stays open pending an item-3 PASS in the next gap cycle.
- **`std::env::current_exe()`'s macOS bundle behaviour remains unproven — still OPEN (research
  Assumption A2).** Item 4 was NOT ATTEMPTED in EITHER the first run (developer elected to skip it)
  or the RE-RUN (`34.5-LIVE-GATE-RERUN.md` item 4 — the developer's session was spent driving items
  1-3, none of which reached a confirmed populated/authenticated state, and item 4's own groundwork
  target, GOG's *Alan Wake*, depends on a working in-session GOG login item 2 did not deliver; the
  devtools console steps were never reached).
  `GAMELIB_SHELL_EXE` (plan 34.5-01) is unit-proven to be present and non-empty at spawn time on
  both Rust spawn paths, and both `exe` consumers (`nonesteamgame.ts:258` via `addToSteam`,
  `shortcuts.ts:227` via `addShortcut`) are unit-proven to throw loudly rather than write a garbage
  value when it is absent. Whether the *value itself* actually resolves to the packaged Tauri shell
  binary (rather than some other path) inside a real macOS `.app` bundle is still unproven — item 4
  must run both call sites in a future gate re-run before this assumption can be retired. Even a dev
  PASS would never retire the packaged branch — see the `R-34.5-G1-PKG` entry below, which covers
  the same dev/packaged split for the asset root.
- **Research Pitfall 2's non-Steam Wine claim remains STANDING, unretired by either run.** "No
  non-Steam runner has ever executed a Wine command under the sidecar" is eligible to be struck only
  on a PASS of item 5. The first run FAILED BY BLOCKAGE (items 1-3 failed upstream at the
  runner-binary spawn defect, so item 5 was never reached). The RE-RUN (`34.5-LIVE-GATE-RERUN.md`
  item 5) recorded NOT ATTEMPTED instead — genuinely different from a blockage FAIL: the developer
  confirmed explicitly that item 5 was not attempted, because none of items 1-3 delivered an
  authenticated, library-populated non-Steam runner to drive it against. Neither run exercised or
  falsified anything about `runWineCommand`'s own code; the claim stays open pending an item-5 PASS.
- **`R-34.5-G1-PKG` — the packaged Tauri build's asset root is still unresolved (2026-08-01,
  `34.5-APP-ROOT-SWEEP.md` § 3).** The G-1 fix this gap cycle landed (`GAMELIB_APP_ROOT` handoff,
  plan 34.5-16) is proven correct for a **dev** build only: `electronStub.app.isPackaged` stays
  `false` under the sidecar, so `publicDir` always appends `'public'`, which exists at the repo root
  in dev. In a packaged build the handed-down root is Tauri's `resource_dir()`, which has no
  `public/` child — appending `'public'` there would resolve to a path that does not exist, the same
  shape of defect this cycle just closed for dev. Plan 34.5-18's boot self-check makes this loud
  (a `[bootstrap] SIDECAR ASSET ROOT DEFECT` line) rather than a silent `ENOENT` six layers
  downstream, but does not resolve it. The RE-RUN's own precondition 4 and item 4 were both dev-only
  (`pnpm tauri:dev`) and neither covers this residual — it stays open regardless of this run's
  outcome, and its future home is the packaging work (building and self-checking a real `.app`
  bundle's resource layout), not Phase 34.6's channel port, since no additional IPC channel is
  involved.
