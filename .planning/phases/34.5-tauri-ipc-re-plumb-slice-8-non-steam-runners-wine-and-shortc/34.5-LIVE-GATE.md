   - `GAMELIB_SHELL_EXE` is emitted at exactly one place in the tree — `eprintln!` at
     `src-tauri/src/main.rs:1231`, on the **shell process's stderr**, i.e. the `pnpm tauri:dev`
     terminal.
   - **Nothing in the sidecar ever writes it to `gamelib.log`.** Verified by sweep: the only other
     references are `pathShim.ts:78` (reads `env.GAMELIB_SHELL_EXE`), `pathShim.ts:81` (the
     unset/empty throw message), doc comments in `shortcutsFlowRegistration.ts`, and two test
     files.
   - So precondition 5 ("read back from `gamelib.log`") and precondition 2 ("sidecar output is read
     from that log file and NOT from the `pnpm tauri:dev` terminal") **cannot both be satisfied**.
     The value above was necessarily taken from the terminal.

   This is a **gate-contract defect, not a code defect** — the handoff itself works. Two ways to
   close it, both out of scope for plan 03's contract-authoring:

   1. *(preferred)* Have the sidecar log the value it actually **received** at boot. That is
      strictly stronger evidence than the current `eprintln!`: it proves what the child got, not
      what the parent claims it sent. `main.rs:1231` cannot distinguish "set on the child env" from
      "actually visible to `pathShim`".
   2. Reword precondition 5 to name the shell terminal as the legitimate source for this one value,
      with an explicit note that it is the parent's claim rather than the child's observation.

   **Dev-vs-packaged caveat, material to what item 4 retires.** This value comes from a **dev**
   build, where `current_exe()` resolves to `src-tauri/target/debug/gamelib-shell`. A packaged
   build resolves to a path inside the `.app` bundle — a different value from a different branch
   (`spawn_sidecar_packaged`, `main.rs:1268`). **Item 4 passing in dev does not transfer to the
