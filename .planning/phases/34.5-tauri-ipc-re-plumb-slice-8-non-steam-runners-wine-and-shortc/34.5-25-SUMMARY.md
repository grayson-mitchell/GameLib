# Phase 34.5 Plan 25: Bound the shared keyring failure memo (F-34.5-G6-06) Summary

**Diagnosed the "double Keychain prompt on GOG sign-out" as a mislabeled shared-arm defect — GOG owns none of the keyring slots involved — then added a 15-second bounded negative-result memo to `SidecarKeyringSlotStore.getToken()` so a failed read isn't retried (and re-prompted) on every subsequent runner sign-out's page reload.**

## Accomplishments

- Diagnosed F-34.5-G6-06 to its actual mechanism using the preserved gate log
  (`gamelib.log.34.5-g6-gate2`) and source citations, appended as a new
  `## F-34.5-G6-06` section to the shared `34.5-G6-FINDINGS.md` (Task 1, no code
  touched).
- Named the shared arm precisely: `SidecarKeyringSlotStore` (3 instances — Steam's
  refresh token, Humble's session cookie, Humble's csrf token), not a GOG-owned
  slot. The causal path is `gogLogout()` → `window.location.reload()` → `GlobalState`
  remount → its mount-time effect (`GlobalState.tsx:1233-1234`) →
  `HumbleUser.checkHealthAndFlagExpiry()` → `getCredentials()`/`getCsrfToken()` — a
  path shared identically by Epic, Amazon, Zoom, and Steam sign-out (all five call
  `window.location.reload()` for their own unrelated reasons).
- Counted the session-wide blast radius: 7 `keyring_get failed` lines (3
  `keyring:unavailable`, 4 `keyring:timeout`) across 3 different slots and at least 7
  distinct call sites — not the single GOG-sign-out event originally reported.
- Selected K1 (failure-not-cached + 8s-timeout interaction) over K2 (two prompts are
  an unavoidable cost) using the pre-existing success cache's own behavior as the
  discriminator: a slot that succeeds once never prompts again for the rest of the
  process, which K2 cannot explain but K1 predicts exactly.
- Implemented the bounded negative-result memo (`KEYRING_FAILURE_MEMO_MS = 15_000`)
  on `SidecarKeyringSlotStore.getToken()`, layered alongside — not replacing — the
  pre-existing `pendingToken` in-flight dedupe (commit `2d1abe64a`). Extended the
  binding correctness floor (`invalidateCache()`, called by `setToken()`/
  `clearToken()` before their underlying call) to also clear the memo, so a
  sign-out can never be blocked by (or resurrect) a stale memoized failure.
- `isAvailable()` was deliberately left untouched (per the plan's own behavior
  spec) — it retains its existing "cache only successful probes" contract.

## Deviations from Plan

None — plan executed exactly as written. Task 1 touched no source files (verified by its own automated gate); Task 2 implemented exactly what Task 1's K1 finding justified, did not touch `src-tauri/src/main.rs` (`KEYRING_READ_TIMEOUT` untouched, confirmed by `git diff --name-only` showing zero `src-tauri/` paths), and did not add a second in-flight dedupe field (`grep -c "pendingToken"` unchanged at 6 before and after — two incidental prose mentions in a new doc comment were reworded to keep the count identical, since the acceptance criterion is literal).

One test (`clearToken() invalidates a memoized failure...`) needed correcting mid-implementation: its first draft used a *successful* `clearToken()`, which (correctly, per pre-existing behavior) repopulates the success cache with a confirmed-empty value and therefore never even reaches the failure-memo check — not a bug, just the wrong scenario to prove the point. Rewrote it against a *failed* `clearToken()` (mirroring the suite's existing "a FAILED clearToken() still invalidates the cache" pattern), which correctly exercises the memo-invalidation floor. This was caught by the test itself failing on first run and fixed before commit — not a Rule 1-3 deviation, just normal TDD iteration.

## What Is Proven vs. What the Live Gate (34.5-31) Still Must Confirm

**Proven by this plan's unit tests (mocked `requestRustInvoke`, no real Keychain):**
- The memo returns a memoized failure without a second transport call inside the window (62/62 tests green, including 4 new memo-specific tests).
- The memo expires and lets a fresh read through after the window.
- `clearToken()`/`setToken()` invalidate the memo, not just the value cache — a sign-out cannot be blocked by (or resurrect through) a stale memoized failure.
- The pre-existing concurrent-dedupe (`pendingToken`) is untouched and still green.
- `npx tsc --noEmit` clean; `npm run test:ci` 3485/3485 passing (up from 3482 baseline before this plan, +3 net new tests), 179/179 suites.

**NOT proven by unit tests, and requiring the live gate (34.5-31) to confirm:**
- Whether a real macOS Keychain prompt actually disappears on the second sign-out-triggered reload — the mocked transport can prove the memo suppresses a *second RPC call*, but per this phase's own standing lesson ("never accept a mutating call's own report as proof of effect"), only a human watching the actual OS dialog count on a real GOG/Epic/Amazon/Zoom/Steam sign-out can confirm the prompt count itself dropped from two to one.
- Whether the 15s window is well-calibrated in practice — it is justified against `KEYRING_READ_TIMEOUT`'s 8s arithmetically, but a real developer's actual approve-time under real dark-wake/network conditions is the only way to confirm it neither reprompts too eagerly nor locks out a legitimate retry for too long.
- Whether the blast-radius finding (5 sign-out flows sharing the mechanism) generalizes correctly across all 5 in a live run — this plan's diagnosis is a source-level trace confirmed against one preserved log (GOG), not independently reproduced against Epic/Amazon/Zoom/Steam sign-out in a fresh live capture.
