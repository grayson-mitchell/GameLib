# F-34.5-G6-01 — Electron-vs-Tauri discriminating experiment (second contract)

**This document is a CONTRACT, written before any experiment runs, exactly as
`34.5-G6-EPIC-DISCRIMINATOR.md` was written before its own live run.** It exists because the
first contract returned `verdict: R1-FALSIFIED` (both arms non-interactive; the UA override did
not fix the symptom) with R2 (a Chromium-only web API throwing under WKWebView) left merely
SURVIVING, not confirmed — the first contract's own instruction was that eliminating R1 is not
evidence for R2, and shipping R2 as a fix on the strength of elimination alone is exactly the
mistake this project's own F-10 lesson warns against. The first contract's own `## Result`
section, under "Context for the next cycle," named the concrete next discriminator: run the same
`EPIC_LOGIN_URL` under Electron (`npm start`) as well as under Tauri (`pnpm tauri:dev`), to
separate "broken by the Tauri port" from "broken by an Epic server-side change unrelated to this
project's port at all." This document pre-registers that exact experiment. Plan 34.5-37 Task 1
authors the contract only, with `verdict: null`. The same plan's Task 2 is a human checkpoint that
runs both arms on real hardware. Task 3 fills the Result section and the frontmatter `verdict` from
whichever of the four pre-registered outcome combinations was observed.

## Interfaces (re-confirmed by direct source read for this contract)

- `EPIC_LOGIN_URL` — `src/frontend/screens/WebView/loginRoutes.ts:45`, value
  `https://www.epicgames.com/id/login?responseType=code`. No `client_id`, no `redirectUrl`.
- `src/frontend/screens/WebView/index.tsx` — the Electron `<webview>` path, which is what
  `npm start` exercises. It sets its own user agent inside a `useLayoutEffect` `loadstop` handler
  (currently lines ~242-260): for any runner other than `humble`, it computes
  `userAgent = startUrl === epicLoginUrl ? 'Mozilla/5.0 (Windows NT 10.0; Win64; x64)
  EpicGamesLauncher' : 'Mozilla/5.0 (Windows NT 10.0; Win64; x64) Chrome/200.0'` and calls
  `webview.setUserAgent(userAgent)` only if it differs from the webview's current agent. That
  Chromium `<webview>` supplies its own product tokens underneath whatever string is set — this is
  where `USER_AGENTS.legendary`'s token-less string in the Tauri sidecar was copied from.
- `src/backend/sidecar/oauthLoginCapture.ts` — the Tauri path. `resolveUserAgent()` is called only
  at line 284, inline inside `.open(loginUrl, { visible: true, userAgent: resolveUserAgent(runner)
  })`, so the `user-agent-override len=` receipt line structurally cannot be emitted before the
  login window opens (recorded in the first contract's Result, and re-confirmed here by direct
  source read).
- `nav host=` logging was added by plan 34.5-24 Task 1 and is available on the Tauri arm only. The
  Electron arm has no equivalent; its evidence is the visible page and the title bar.

## The two readings

- **E1 — broken by the Tauri port.** Something about the Tauri/WKWebView login-window seam
  prevents Epic's login page from becoming interactive. R2 from the first contract (a
  Chromium-only web API throwing under WKWebView) is one mechanism of this shape; the standing
  project record already has a confirmed instance in `queryLocalFonts` throwing under WKWebView
  (`.claude/skills/spike-findings-gamelib/references/tauri-chromium-only-web-apis.md`). This
  reading does not commit to a specific API — it commits only to the shell (Tauri/WKWebView) being
  the differentiator.
- **E2 — broken independently of this project.** Epic's login page no longer works when loaded at
  `EPIC_LOGIN_URL` as written, regardless of shell — for example because the flow now requires a
  `client_id` the inherited URL literal does not carry. This reading is supported, not established,
  by Arm B's literal `Parameter "client_id" is required` error message and by the URL literal
  predating the Tauri port (`git show c76875e83^`).

Both readings are consistent with everything observed so far in the first contract, which is
exactly why an Electron arm — a completely different embedded-browser shell loading the identical
URL literal — is the cheapest experiment that can separate them.

## How to run each arm

**Precondition, unconditional:** Epic signed out before starting. Re-verify; do not assume — the
first contract's own precondition made the same demand and this one carries it forward.

**The single measured variable:** whether Epic's login form accepts keyboard and mouse input
(interactive) or stays non-interactive ("greyed out" or an error page that accepts no input). The
title bar text and any visible error text must be transcribed verbatim on both arms regardless of
the interactivity answer.

1. **Arm E — Electron.**
   1. Run `npm start`.
   2. Open Manage Accounts and click Epic.
   3. Wait for the login page to render, allowing at least 60 seconds — the 2026-08-01 session
      recorded a GOG form taking over 30 seconds to appear, so a slow render is not itself a blank
      page.
   4. Record: does the form accept keyboard and mouse input, yes or no? Transcribe the window
      title bar exactly. Transcribe any visible error text exactly.
   5. Do not enter a real Epic credential (see precondition below) — clicking into a field to test
      focus and typing a single throwaway character is the whole interactivity test.
   6. Quit the app.
2. **Arm T — Tauri.**
   1. Run `pnpm tauri:dev` with `GAMELIB_OAUTH_UA_LEGENDARY` UNSET (the stock agent, matching the
      gate's original configuration and the first contract's own Arm A).
   2. Open Manage Accounts and click Epic.
   3. Apply steps 3-5 from the Electron arm identically (wait at least 60s; record interactivity,
      title bar, error text; no real credential).
   4. After the attempt settles, read back `~/Library/Logs/GameLib/gamelib.log` (or
      `gamelib.log.old` if the session rotated) with `grep -n "runner=legendary" gamelib.log` and
      copy every `label=`, `nav host=` and `status=` line for that attempt, in order. The Electron
      arm has no equivalent line; its evidence is the visible page and the title bar only.

Supply all of the above verbatim. Redact in place per the evidence-handling rule below if any line
carries a token, cookie, session id or Steam `userdata` account id — redact, never omit the line.

## Precondition — no real Epic credentials on either arm

The measured variable is whether the form is interactive, not whether a login completes. A
completed login is neither required nor wanted for this experiment: entering a real credential
into a page whose behaviour is actively under investigation is unnecessary credential-handling
risk, and a single throwaway character typed into a field is sufficient to establish whether the
field accepts input at all. Do not enter a real Epic credential on either arm.

## Decision rule (filled in BEFORE the experiment runs)

All four outcome combinations, decided in advance:

- **Electron interactive AND Tauri non-interactive → E1 SELECTED.** The shell is the whole
  difference that flips the form from interactive to non-interactive; the same URL literal working
  under one embedded browser and not another implicates the Tauri/WKWebView seam specifically.
  Routes to instrumenting the embedded window's own console/script-error signal — the additional
  observation the first contract already named as the one that would confirm R2 — not to shipping
  a guess. `USER_AGENTS`, `EPIC_LOGIN_URL`, and `matchOAuthRedirect` remain unchanged by this
  route; instrumentation is diagnosis, not a fix.
- **Both non-interactive → E2 SELECTED.** The same URL literal fails identically under two
  unrelated embedded-browser shells, which implicates something about the URL/flow itself rather
  than the Tauri port. Routes to a further contract comparing `EPIC_LOGIN_URL` against upstream
  Heroic's current value and against legendary's own documented auth flow. **E2 being selected
  does NOT authorise editing `EPIC_LOGIN_URL` inline in this or any other plan** — a URL change is
  a new hypothesis and gets its own pre-registered contract, exactly as E1 and E2 did here, and
  exactly as R1 and R2 did in the first contract.
- **Both interactive → NOT-REPRODUCED.** Record the result as NOT REPRODUCED (frontmatter verdict
  value `NOT-REPRODUCED`) and route to re-running the Tauri arm before concluding anything — a
  defect that vanishes without an identified change is unexplained, not fixed. Do not close
  F-34.5-G6-01 on a single both-interactive observation.
- **Electron non-interactive AND Tauri interactive → NEITHER-READING-FITS.** STOP and escalate to
  a further diagnosis cycle, recording NEITHER READING FITS (frontmatter verdict value
  `NEITHER-READING-FITS`). Do not invent a third reading inline to rescue the experiment in this
  document — a third reading, if warranted, gets its own pre-registered contract the same way E1
  and E2 did here.
