<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Rust shell → Node sidecar (process spawn) | The only channel by which the sidecar learns the shell's own binary path; a value crossing here ends up inside an executable launch command |
| sidecar → on-disk launch artifacts (Steam VDF, macOS `.app` `run.sh`) | A string written here is later executed by Steam or by Finder, outside this app's control |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-34.5-01 | Tampering | `pathShim.getPath('exe')` return value | mitigate | Unset/empty `GAMELIB_SHELL_EXE` throws a named error; two dedicated test cases assert the throw. An empty string is never returned and therefore never interpolated into `nonesteamgame.ts:258`'s `Exe` or `shortcuts.ts:227`'s `run.sh`. |
| T-34.5-02 | Tampering | node interpreter written as the launch command | mitigate | `process.execPath` is grep-asserted absent from `pathShim.ts`; the value comes only from the shell's own `current_exe()` (D-10's explicit rejection). |
| T-34.5-03 | Denial of Service | `current_exe()` failure at spawn | accept | Returns `""` rather than panicking; the shell still starts and every other channel still works. Only `exe`-dependent channels degrade, and they degrade loudly. |
| T-34.5-04 | Information Disclosure | logging the resolved shell path | accept | A local filesystem path in a local log file; no secret, no user data. Logged on the dev path only, deliberately, so the live gate can read it back. |
| T-34.5-SC | Tampering | npm/cargo installs | accept | Zero new packages in either ecosystem (research § "Package Legitimacy Audit": nothing to check). |
</threat_model>
