<objective>
Close Routing item 3: `KEYRING_READ_TIMEOUT` is 8 seconds, which is shorter than the time a human
takes to notice, read and approve a macOS Keychain dialog. The read therefore times out, the failure
is not cached long enough, and the next caller prompts again — two approval prompts for the same
`steam-refresh-token` slot in one session (19:22:57 and 19:24:38), which is the exact outcome plan
34.5-25's own decision rule defines as FALSIFIED.

Purpose: plan 34.5-25 added a 15-second failure memo (`KEYRING_FAILURE_MEMO_MS`) on the reasoning that
it is roughly twice the 8-second read bound. The two live prompts were **101 seconds apart** — the
memo had long expired, and the underlying 8-second bound meant the first read could never have
succeeded at human speed in the first place. Both constants are wrong against live human timing;
neither is wrong against the other.

Output: a read bound a human can win, a failure memo that outlasts the observed re-read interval, and
a cross-language invariant test pinning the read bound strictly inside the sidecar's own
`rustInvoke` bound.

**Root cause is contested, and this plan does not settle it.** The live-confirmed defect is the
8-second bound versus human approval time. The ad-hoc-code-signing / Keychain-ACL-non-persistence
theory recorded in `deferred-items.md` is a likely SEVERITY MODIFIER for dev builds, not something
this plan establishes or fixes. **This plan does not drop, disable, or make optional the Keychain path
in production** — a dev-build artifact is not grounds for removing a production security control.

**Live observable that would prove this — nothing else counts.** A live session in which
`~/Library/Logs/GameLib/gamelib.log` contains at most ONE `keyring_get failed: keyring:timeout` line
per slot, and in which a human approving a Keychain dialog at ordinary speed produces no
`keyring:timeout` line for that slot at all. A passing test proves the constants and their ordering,
not the human timing.
</objective>

<interfaces>
The three constants this plan reasons about, and the invariant between them:
- `KEYRING_READ_TIMEOUT: Duration = Duration::from_secs(8)` in `src-tauri/src/main.rs` — the bound on
  the worker-thread Keychain read before `keyring_get` classifies the call `keyring:timeout`. Its own
  doc comment records the measured basis: an absent-entry read completes in 40-102 ms; a
  present-entry read against the real `steam-refresh-token` account took 48.9 s on one run and 291 s
  on another. A timed-out worker thread is ABANDONED, not cancelled — `SecItemCopyMatching` has no
  interrupt API — so this bound protects the RPC round trip, not the underlying OS call.
- `RUST_INVOKE_TIMEOUT_MS = 60_000` in `src/backend/sidecar/sidecarRpc.ts` — the sidecar-side bound on
  a `rustInvoke` round trip. `KEYRING_READ_TIMEOUT` must stay strictly under this with round-trip
  headroom, or a keyring read stops being reported as `keyring:timeout` and starts being reported as
  an opaque transport timeout by the outer layer instead.
- `KEYRING_FAILURE_MEMO_MS = 15_000` in `src/backend/sidecar/keyringTokenStore.ts` — how long a
  FAILED read is memoized so a second caller does not issue a second `keyring_get` (and therefore a
  second Keychain prompt). It holds a timestamp only, never a value.

The caching layers already present in `SidecarKeyringSlotStore` and deliberately NOT in scope here:
- `cachedToken` — the success cache; once a slot reads successfully it short-circuits for the life of
  the process, no further prompt ever.
- `pendingToken` — the in-flight dedupe; collapses concurrent same-tick callers to one request.
Both are working as designed and were explicitly ruled out as the gap by `34.5-G6-FINDINGS.md` § 3.
The gap is the interaction of the read bound with human approval time, plus a memo window shorter
than the interval between sequential callers.

Blast radius established by `34.5-G6-FINDINGS.md` § 4 — the defect is not slot-specific or
runner-specific. Three slots (`steam-refresh-token`, `humble-session`, `humble-csrf`) reachable from
at least seven call sites, including all five runners' sign-out flows, which each call
`window.location.reload()` and land on the same `GlobalState.tsx` mount-time `humbleCheckHealth()`.
A fix scoped to one slot or one flow would miss all of this.
</interfaces>
