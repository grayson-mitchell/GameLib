**The seam this depends on — already fully wired, do not touch:**

- `TextInputField/index.tsx:6-9` (`TextInputFieldProps extends Omit<React.InputHTMLAttributes<HTMLInputElement>, 'onChange'>`) inherits `onKeyDown` as a standard HTML attribute, and it reaches the real DOM node via the prop spread at `TextInputField/index.tsx:65` (`{...inputProps}` inside the `<input ... />` at lines 60-69).

**Enter-key precedent survey — house style is NOT uniform; two distinct idioms exist, pick deliberately:**

| Site | Line | Idiom | Element role | Purpose |
|---|---|---|---|---|
| `SteamGridDBPicker/index.tsx` | 169 | `if (e.key === 'Enter')` (Enter only) | text `<input>` (via `TextInputWithIconField`) | commit/submit a typed value |
| `StoreSearch/components/StoreSearchBreakdown/index.tsx` | 78 | `if (event.key === 'Enter' || event.key === ' ')` | `<div role="button" tabIndex={0}>` | keyboard-activate a clickable, non-native-button element |
| `ConsoleMode/index.tsx` | 376 | `else if (e.key === 'Enter' || e.key === ' ')` | grid-navigation key handler | activate the focused game tile |
| `ConsoleMode/InstallOverlay/index.tsx` | 304 | `if (e.key === 'Enter' || e.key === ' ')` | overlay focus-navigation handler | activate the focused install/cancel control |
| `ConsoleMode/components/ConfirmDialog/index.tsx` | 88 | `if (e.key === 'Enter' || e.key === ' ')` | dialog button-group handler | activate the focused dialog button |

**These are two different problems, not competing conventions for the same problem.** The four
`'Enter' || ' '` sites are all **button/tile activation** on non-native-`<button>` elements (ARIA
`role="button"` keyboard-accessibility idiom — Space is included because native buttons activate
on both Enter and Space). `SteamGridDBPicker` is the only precedent for **text-input commit**,
where Space must NOT trigger a commit (a user typing a space inside the path/query string would
wrongly fire the action). **`SteamGridDBPicker`'s bare `e.key === 'Enter'` is the correct analog
for `PathSelectionBox`** — matching data flow (text input → commit callback), not matching element
role (button vs. field). Recency does not disambiguate here (SteamGridDBPicker: 2026-08-14;
ConsoleMode files: 2026-08-21/22, i.e. more recent) — the two idioms remain live and correct for
their respective element types; a planner should not "average" them or add `|| e.key === ' '` to
`PathSelectionBox`.

**Anti-patterns already ruled out in RESEARCH.md (do not re-litigate):**
- Do not widen `TextInputWithIconField`'s or `TextInputField`'s prop interface — both already carry `onKeyDown` end-to-end.
- Do not wrap the field in `<form onSubmit>` — zero `<form>` elements exist across any of the 13 call sites today; this is why Enter currently does nothing rather than something harmful.
- Do not call `e.currentTarget.blur()` after a programmatic commit — changes focus/tab-order unnecessarily; `onBlur` already independently double-covers the commit.

   jest.mock('react', () => {
     const actualReact = jest.requireActual<typeof import('react')>('react')
     let slots: unknown[] = []
     let effectDeps: (unknown[] | undefined)[] = []
     let cursor = 0
     let effectCursor = 0

     const depsChanged = (
       prev: unknown[] | undefined,
       next: unknown[] | undefined
     ): boolean => {
       if (!prev || !next) return true
       if (prev.length !== next.length) return true
       return prev.some((d, i) => !Object.is(d, next[i]))
     }

     return {
       ...actualReact,
       useState: (initial: unknown) => {
         const idx = cursor++
         if (idx >= slots.length) {
           slots[idx] =
             typeof initial === 'function' ? (initial as () => unknown)() : initial
         }
         const setState = (updater: unknown) => {
           slots[idx] =
             typeof updater === 'function'
               ? (updater as (prev: unknown) => unknown)(slots[idx])
               : updater
         }
         return [slots[idx], setState]
       },
       useEffect: (effect: () => void | (() => void), deps?: unknown[]) => {
         const idx = effectCursor++
         if (depsChanged(effectDeps[idx], deps)) {
           effectDeps[idx] = deps
           effect()
         }
       },
       __beginRender: () => { cursor = 0; effectCursor = 0 },
       __resetMount: () => {
         slots = []; effectDeps = []; cursor = 0; effectCursor = 0
       }
     }
   })
   ```

   function collectElements(
     node: ReactNode,
     out: ReactElement<PropsWithChildren>[] = []
   ): ReactElement<PropsWithChildren>[] {
     if (node === null || node === undefined || typeof node === 'boolean') return out
     if (Array.isArray(node)) {
       node.forEach((child) => collectElements(child as ReactNode, out))
       return out
     }
     if (typeof node === 'object' && 'type' in node) {
       const element = node as ReactElement<PropsWithChildren>
       out.push(element)
       if (element.props?.children !== undefined) {
         collectElements(element.props.children, out)
       }
       return out
     }
     return out
   }

   function findByType(tree: ReactNode, type: unknown) {
     return collectElements(tree).find((el) => el.type === type)
   }
   ```

## Shared Patterns

### The double-commit guard (`useSetting`'s no-op mechanism)

**Source:** `src/frontend/hooks/useSettingsContext.ts:78-88` (the real implementation backing
`useSetting`'s `setSettingF` — `useSetting.ts` itself, lines 5-19, is a thin `getSetting`/`setSetting`
pass-through with no guard of its own; the guard lives one layer up, in the context provider):
```ts
const contextValues: SettingsContextType = {
  getSetting: (key, fallback) => currentConfig[key] ?? fallback,
  setSetting: (key, value) => {
    const currentValue = currentConfig[key]
    if (currentValue !== undefined || currentValue !== null) {
      const noChange = JSON.stringify(value) === JSON.stringify(currentValue)
      if (noChange) return
    }
    setCurrentConfig({ ...currentConfig, [key]: value })
    window.api.setSetting({ appName, key, value })
  },
  // ...
}
```
**Apply to:** cites this exact mechanism as the reason 12 of 13 `PathSelectionBox` call sites
(everything except `EgsSettings.tsx`'s macOS/Linux branch) are already idempotent on a double-commit
— the planner can point at these specific lines instead of asserting idempotence abstractly. Note
for the planner's own awareness (not a defect to fix in this phase): the guard's outer condition
`currentValue !== undefined || currentValue !== null` is a tautology (always true, since a value
cannot simultaneously be both `undefined` and `null`) — in practice this means the `JSON.stringify`
comparison always runs, which is the behavior everyone already relies on; it is not a live bug
blocking this phase, just an odd-looking line worth not being confused by.

## The Affordance Question — What Actually Exists (REQ-34.17-03)

Surveyed every confirmation/feedback primitive this frontend genuinely uses. **Verdict: no
established "field committed" affordance pattern exists in this codebase.** Below is every
adjacent primitive found, with the honest gap named for each:

| Primitive | Path | Real usage | Fit for "value committed" |
|---|---|---|---|
| `warning` prop on `TextInputField` | `TextInputField/index.tsx:16,27,70` (`{value && warning}`) | `WrappersTable.tsx:63-68` — persistent, always-shown static warning text about arg quoting, not a transient success confirmation | **Mismatch.** It's a permanent explanatory hint tied to `value` truthiness, not a one-shot "this just saved" pulse. Reusing it for a commit confirmation would mean it never goes away once a value exists. |
| `role="status"` banner (no dedicated component; ad hoc per-feature) | `HumbleExpiryToast/index.tsx:60` (`<div className="humbleExpiryToast" role="status">`) | A dismissible reconnect-prompt banner reacting to a global context value (`humble.expired`), explicitly built because **"No toast/snackbar library exists in this codebase"** (comment at `HumbleExpiryToast/index.tsx:14-20`, independently re-stated verbatim at `SteamBottleSetup.tsx:17`: *"No toast/snackbar library exists in this codebase, so this is a minimal from-scratch banner"*) | **Mismatch by scale, but the closest architectural precedent.** It's a full standalone component with its own CSS, icon, dismiss button, and global-state wiring — built for a persistent multi-second alert, not a per-keystroke micro-confirmation. Two independent comments in this codebase (two days apart, two different features) both had to explain from scratch that no shared toast primitive exists — this is a confirmed, repeated gap, not a one-off oversight. |
| `aria-live` regions | `ConsoleMode/InstallOverlay/index.tsx:345`, `ConsoleMode/components/LaunchOverlay/index.tsx:169`, `ConsoleMode/components/ConfirmDialog/index.tsx:129` | All three are scoped to **ConsoleMode** (the gamepad/10-foot UI), on `role="dialog"`/`role="status"` container `<div>`s wrapping entire overlay screens, not on any Settings-screen or `PathSelectionBox`-adjacent element | **Mismatch in surface.** `PathSelectionBox` renders inside Settings/InstallModal (desktop mouse+keyboard screens), never inside ConsoleMode. Copying an `aria-live` pattern here would be introducing it to a screen family that has never used it, not applying an existing local convention. |
| CSS class-based transient state (e.g. a `.committed`/`.dirty` modifier class) | — | **None found.** No grep hit for any existing "just-saved"/flash/pulse CSS class pattern anywhere under `src/frontend/components/UI` or `src/frontend/screens/Settings`. | **Does not exist.** This would be a genuinely new pattern, not a reuse of an existing one. |

**Honest summary for the planner:** there is no reusable "field committed" affordance in this
codebase today. The nearest analog by *architecture* (a lightweight, non-blocking, self-contained
visual signal reacting to local state) is `HumbleExpiryToast`'s from-scratch banner shape, but it is
the wrong *scale* — it is a persistent multi-second alert component, not a one-shot micro-confirmation,
and instantiating a full sibling component for a single-field pulse would be disproportionate. The
nearest analog by *location* (already lives inside `TextInputField`'s own render tree) is the
`warning` prop slot, but its semantics (persistent hint) don't fit either. **This phase's REQ-34.17-03
is asking the planner to design something genuinely new**, not apply an existing pattern — RESEARCH.md's
own recommendation (a transient CSS state added directly to `PathSelectionBox`'s own
`textInputFieldWrapper`-adjacent markup, kept intentionally minimal) is consistent with this survey's
finding and is the right scope: smaller than a new component, novel in the sense that no existing CSS
class or component can simply be reused, but architecturally consistent with the "no toast library,
build the smallest thing locally" precedent both `HumbleExpiryToast` and `SteamBottleSetup` already
establish.

Per VALIDATION.md and this agent's constraints: **whatever affordance is chosen cannot be covered by
a jest test** (no DOM, no paint timing) — it is a manual-only requirement (screenshot/recording),
already reflected in `34.17-VALIDATION.md`'s Manual-Only Verifications table. Do not plan an
automated test asserting a CSS class name appears in a mock tree — this project has already shipped
exactly that false-pass shape once (`stylesheet-can-be-wholly-dead-against-its-component.md`).
