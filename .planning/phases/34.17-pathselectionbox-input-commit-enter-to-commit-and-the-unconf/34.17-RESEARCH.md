# Phase 34.17: `PathSelectionBox` input commit — Research

**Researched:** 2026-08-25
**Domain:** React controlled-input commit semantics (Half A) + Tauri/WKWebView native clipboard-paste behavior (Half B)
**Confidence:** HIGH (Half A — every claim re-verified against HEAD source) / LOW-MEDIUM (Half B — no live host access this session; findings are source-level plausibility analysis only, not a reproduction)

## Summary

This phase closes phase-34.9 deferred item 8, which carries **two unrelated defects** that must be
planned, implemented, and gated separately.

**Half A (Enter-to-commit)** is fully understood and provable from source alone. `PathSelectionBox`
commits only via `onBlur`; `TextInputWithIconField` already declares and forwards an `onKeyDown`
prop all the way to the native `<input>` element via `TextInputField`'s prop spread — the seam is
real and unbroken at HEAD. A near-identical house pattern already exists in this codebase
(`SteamGridDBPicker`'s search field), so the fix is not a novel pattern, it is applying an existing
one. There are **13 call sites** of `PathSelectionBox` across the app; 9 write through `useSetting`
(idempotent by construction — the setter no-ops on unchanged value), 3-4 write to local `useState`
(cheap, idempotent), and exactly **one** (`EgsSettings.tsx`, macOS/Linux branch) fires a real,
non-idempotent side effect (`window.api.egsSync`) on every commit — this is the one call site where
an Enter-then-blur double-fire is a genuine risk, not a theoretical one.

**Half B (paste)** cannot be resolved by more source reading — it requires a live Tauri host run,
which this research session did not have access to. What source analysis *can* establish: the
ledger's suspected cause (`navigator.clipboard` silently no-opping under WKWebView) is **mechanically
implausible** for this specific symptom. That standing project note is about `navigator.clipboard`
*write* failing silently (confirmed, well-documented, fixed elsewhere in this codebase via
`window.api.clipboardWriteText`/`clipboardReadText`) — it says nothing about native ⌘V *paste* into
a plain, uncontrolled `<input>`, which never invokes the Clipboard API at all; it is handled by the
OS/webview's native text-editing responder chain. No `onPaste` handler exists anywhere in the
`PathSelectionBox` chain, and no code intercepts `Cmd+V`. A **different**, real, already-documented
class of bug exists in this codebase — a tao/wry `Cmd+V` key-equivalent delivery gap — but it was
found and fixed only for a bespoke, manually-created secondary WKWebView (the Humble/Epic login
child window), not the primary Tauri-managed window `PathSelectionBox` renders in. Whether that
mechanism (or something else entirely) explains the 2026-08-11 observation is **unproven** and must
be settled by live reproduction, per the ROADMAP's explicit instruction.

**Primary recommendation:** Plan Half A as a small, source-verified fix + a house-pattern-matched
affordance, gated by an in-repo (non-DOM) jest test. Plan Half B as a **reproduction task**, not a
fix task — its only deliverable this phase is a recorded artifact that either reproduces the glyph
(after which the *fix* becomes its own follow-up item, per the scope fence) or falsifies it, closing
it VERIFIED-ABSENT.

## Architecture Patterns

### Current commit chain (verified at HEAD, 2026-08-25)

```
User types in <input>
        │
        ▼
TextInputField's raw DOM `input` event listener (NOT React onChange —
deliberately, "so it works with the virtual keyboard")
        │  element.addEventListener('input', handler); handler calls onChange(element.value)
        ▼
TextInputWithIconField.onChange (pass-through)
        │
        ▼
PathSelectionBox: onChange={(newVal) => setTmpPath(newVal)}   ← LOCAL state only
        │
        │   (nothing commits here — value only visible in the field itself)
        │
        ▼
User action that TODAY triggers a commit:
   ┌─────────────────────────────┬───────────────────────────────────┐
   │ blur (tab away / click out) │ Folder/Backspace icon click        │
   │ onBlur={(e) =>              │ handleIconClick() → onPathChange(  │
   │   onPathChange(e.target.    │   selectedPath | '')               │
   │   value)}                   │                                     │
   └─────────────────────────────┴───────────────────────────────────┘
        │
        ▼
onPathChange(path) — passed in by the CALLER (13 distinct implementations,
see census table below)
        │
        ▼
Either: useSetting's setSettingF → SettingsContext.setSetting →
        (no-op if unchanged) → window.api.setSetting({appName,key,value})
   Or:   plain React useState setter (ImportDialog/SideloadDialog/
        DownloadDialog/WineSelector)
   Or:   EgsSettings.handleSync → window.api.egsSync(path) — REAL SIDE EFFECT
```

**Pressing Enter today:** falls through to nothing. No `onKeyDown` is passed anywhere in this chain,
so the native `<input>`'s default Enter behavior applies — which, since no `<form>` wraps any of the
13 call sites (verified — zero `<form>` elements found across every file that renders
`PathSelectionBox`, its own file, and both Settings/InstallModal container components), is **truly
nothing**: no implicit submit, no navigation, no reload. This confirms the ledger's framing exactly:
"Enter does nothing," not "Enter does something harmful you can't see."

### The seam that already exists (why this is a small fix)

`TextInputWithIconFieldProps` (`TextInputWithIconField/index.tsx:5-18`) already declares:
```ts
onKeyDown?: (event: React.KeyboardEvent<HTMLInputElement>) => void
```
and `TextInputWithIconField` spreads `...props` (which includes `onKeyDown` if passed) straight into
`TextInputField`. `TextInputField`'s own props type
(`TextInputFieldProps extends Omit<React.InputHTMLAttributes<HTMLInputElement>, 'onChange'>`)
already includes `onKeyDown` as a standard HTML attribute, and it reaches the real DOM node via:
```tsx
<input type="text" id={htmlId} value={value} ref={input} {...inputProps} onChange={() => {}} />
```
(`TextInputField/index.tsx:60-69`). **`onKeyDown` is NOT declared-but-dropped — it is declared and
fully forwarded.** `PathSelectionBox` is the only link in the chain that never passes one. The fix is
adding one prop to `PathSelectionBox`'s own `<TextInputWithIconField>` call
(`PathSelectionBox/index.tsx:80-93`) — it does **not** require touching
`TextInputWithIconField` or `TextInputField` at all.

### Anti-Patterns to Avoid

- **Do not widen `PathSelectionBox`'s or `TextInputWithIconField`'s prop interface.** The seam
  already exists top-to-bottom; the only change needed is passing a value through it from
  `PathSelectionBox`.
- **Do not wrap Enter-commit in a `<form onSubmit>`.** None of the 13 render trees use `<form>`
  today; introducing one risks resurrecting the exact implicit-submit/reload class of bug the
  ROADMAP's framing was careful to rule out as *not* the current behavior.
- **Do not call `e.currentTarget.blur()` after an Enter-commit** as a way to "finish" the
  interaction unless you have confirmed it's wanted — it changes focus behavior mid-form (tab order,
  screen-reader focus loss) and is unnecessary: `onBlur` already independently double-covers the
  commit and (per the census table) is safe to double-fire everywhere except site 11.

## Common Pitfalls

### Pitfall 1: Double-commit at `EgsSettings.tsx`'s real side effect

**What goes wrong:** if Enter calls `onPathChange` and is immediately followed by the user tabbing
away (triggering `onBlur`, which also calls `onPathChange` with the same now-current value), every
other of the 13 call sites either no-ops (the `useSetting` guard) or costs nothing (local state).
`EgsSettings.tsx`'s macOS/Linux branch is the exception: `onPathChange={handleSync}`, and `handleSync`
calls `window.api.egsSync(newPath)` — a real Epic Games Store sync action — every single time it is
invoked, with no internal debounce.
**Why it happens:** `handleSync` sets `isSyncing(true)` synchronously in the function body, but React
state updates are asynchronous/batched — an Enter keypress followed by an immediate Tab in the same
event-loop tick can fire `handleSync` twice before `isSyncing` becomes `true` and the field's
`disabled={!canEditPath || disabled}` (fed by `canEditPath={!isSyncing}`) has a chance to block a
second edit.
**How to avoid:** either (a) suppress the following `onBlur` commit when the value has already been
committed by Enter (e.g. track a small "just committed via Enter, skip the next blur if value
unchanged" flag inside `PathSelectionBox`), or (b) have `PathSelectionBox`'s Enter handler compare
`tmpPath` against the already-committed `path` prop and no-op if unchanged (mirrors the
`useSetting`/`SettingsContext` guard other sites already get for free) — option (b) is simpler,
requires no new state, and generalizes the existing no-op discipline down into the shared component
instead of relying on 13 different callers to each implement it correctly.
**Warning signs:** if a plan implements Enter-commit as a bare, unconditional
`onKeyDown={(e) => e.key === 'Enter' && onPathChange(e.currentTarget.value)}` with no
already-committed check, it will regress `EgsSettings.tsx` specifically — this is the one call site
a plan/verification pass must exercise (or explicitly reason about) before calling Half A done.

### Pitfall 2: Treating "no `<form>` today" as permanent

**What goes wrong:** a future refactor could wrap one of these fields in a `<form>` (e.g. to get
native validation UX) without realizing that would change Enter's default behavior from "does
nothing" to "submits" — a regression this phase's own fix is not responsible for preventing, but the
verification for Half A should assert *why* Enter currently does nothing (no form present) so a
later regression is legible against this phase's own findings.
**Why it happens:** form-wrapping is an easy, common pattern for "press Enter to submit" that
developers reach for by default; it is the wrong tool here because the desired behavior is "commit
this one field," not "submit a set of fields."
**How to avoid:** implement Enter-commit via the `onKeyDown` seam directly (as researched above), not
via a `<form onSubmit>`.

### Pitfall 3: Conflating Half A and Half B in one task/commit

**What goes wrong:** because both defects live in the same three files, it is tempting to fix them
together. The ROADMAP is explicit that they must not be — Half A is provable today; Half B requires
a live host run and must not be "fixed" ahead of reproduction (fixing an unreproduced cause is named
as this project's own recurring failure mode: gates that measure the wrong property).
**How to avoid:** two separate plan tasks (or two separate plans), each independently gateable; Half
B's task produces a reproduction artifact as its sole deliverable this phase, not a code change,
unless reproduction succeeds and the cause is confirmed in-scope (`PathSelectionBox`-local, not a
host-level clipboard shim — see Scope Fence).

### Pitfall 4: Assuming a green jest suite proves the paste half

**What goes wrong:** a jsdom-based (or even a jsdom-less, handler-invoked) unit test that simulates a
`paste` event and asserts the input value updates would prove nothing about this defect, because (a)
this project's frontend jest project has no DOM at all, and (b) even with a DOM, a *simulated*
`ClipboardEvent` bypasses the exact mechanism under suspicion — native OS-level key-equivalent
delivery through the WKWebView responder chain. See `## Validation Architecture` for the explicit
foreclosure of this false-pass shape.
**How to avoid:** do not write a jest test claiming to cover Half B's reproduction. Its verification
is a live-host, human-executed protocol only (see below).

### What each layer can and cannot prove (read before writing plan verification steps)

**Provable by jest (no DOM, handler-invocation pattern):**
- That `PathSelectionBox` passes an `onKeyDown` prop through to `TextInputWithIconField` that,
  when invoked with `{ key: 'Enter' }`, calls the `onPathChange` prop with the field's current
  value. This directly tests REQ-34.17-01's wiring.
- That the same handler, invoked twice in a row with an unchanged value (simulating Enter then
  blur), calls `onPathChange` at most once with a changed value — proving REQ-34.17-02's
  double-commit guard exists and works, **as a unit claim about the component's own logic**.

**A FALSE PASS this test design forecloses:** a test that only asserts "`onKeyDown` prop exists on
the rendered tree" (checking the call site, not behavior — this project's own named failure mode)
would pass even if the handler body were empty or wired to the wrong prop (e.g. `onChange` instead
of `onPathChange`). The test must invoke the actual function and assert on the **mock call
arguments**, not merely its presence, and must include at least one call with `key !== 'Enter'`
(e.g. `'a'`) that asserts `onPathChange` was **NOT** called — proving the handler discriminates on
the key rather than committing on every keystroke.

**CANNOT be proven by jest, and a green jest run must never be cited as covering these:**
- **REQ-34.17-03 (the affordance).** Whatever visual/DOM feedback a plan chooses (border flash,
  icon change, transient text) is a rendering/paint-timing claim. This project's frontend jest
  project has no DOM at all — there is nothing to paint, and even with a DOM added, CSS
  transitions/paint timing are not meaningfully assertable in jsdom. **A FALSE PASS this forecloses:**
  a test asserting a CSS class name string appears in a mock render tree would pass even if that
  class had no visible effect (dead stylesheet — this project has hit exactly this failure mode
  before, per `stylesheet-can-be-wholly-dead-against-its-component.md`). The only valid check is a
  human looking at the running app.
- **REQ-34.17-04 (Half B reproduction).** A simulated `ClipboardEvent`/`paste` DOM event — even if
  jsdom were added — tests React's event handling, not the actual mechanism under suspicion (OS-level
  key-equivalent delivery through WKWebView's native responder chain into an uncontrolled DOM node).
  **A FALSE PASS this forecloses:** "we wrote a jest test that pastes text and the input updates, so
  paste works" is exactly the shape of false confidence this project's own standing lessons warn
  against (`a-test-can-pin-the-defect-it-should-catch.md`,
  `gate-can-be-nonvacuous-and-measure-wrong-property.md`) — a passing simulated-paste test would be
  measuring React's synthetic event system, a property that was never in question, while leaving the
  actual suspected defect (native delivery) completely unexercised. **No plan should write this
  test.** The only valid check is the live reproduction protocol below.

### Reproduction Protocol for Half B (concrete, cheap, evidence-producing)

**Precondition:** a real Tauri build running on macOS. Use `pnpm tauri:dev` — **not** `tauri dev`
directly (project memory: `tauri dev` serves a stale static bundle). Also note: if an instance is
already running, `pnpm tauri:dev` **exits 0 without replacing it** (project memory:
`tauri-dev-noops-against-a-running-instance.md`) — confirm via `pgrep -fl gamelib-shell` (not
`pgrep GameLib`) that a fresh process is actually running before starting the protocol, or fully
quit the app first.

**Surface to open:** Settings → any of the path fields backed by `useSetting` is sufficient and
lowest-risk (e.g. "Default Install Path" or "Alt Legendary Bin" — `DefaultInstallPath.tsx` /
`AltLegendaryBin.tsx`). Avoid `EgsSettings.tsx`'s path field for this protocol specifically, since a
successful paste there will fire a real `egsSync` side effect (Pitfall 1) — not needed to observe
the paste symptom itself.

**Steps:**
1. Copy a short, distinctive, easily-verified string to the system clipboard from *outside* the app
   — e.g. open Terminal and run `echo -n "/tmp/gamelib-paste-probe-12345" | pbcopy`. Using a
   synthetic, unlikely-to-collide string makes it trivial to tell "my paste" apart from "residual
   clipboard content from a previous test."
2. In the running GameLib window, open Settings, focus the target `PathSelectionBox` field's
   `<input>` (single click, do not use the folder-picker icon).
3. Paste via the real key equivalent: press **Cmd+V** (not Edit ▸ Paste from the menu bar — the
   ledger's own report was a keyboard paste, and this project has separately found that key-equivalent
   delivery and menu-driven paste can behave *differently* in this codebase for a sibling window
   class — testing the keyboard path specifically is the one that matches the original report).
4. **Capture evidence — this step is mandatory, not optional:**
   - Take a screenshot of the field's rendered content immediately after the paste attempt.
   - Separately, verify what the DOM node's `.value` actually contains — open the app's DevTools
     (note: this project's own memory records the Tauri DevTools **console cannot be pasted
     into**, so do not attempt to type/paste a verification snippet directly into the console input;
     instead, right-click the field → Inspect Element, and read the `value` attribute/property directly
     from the Elements/DOM inspector panel, or add a temporary `console.log(element.value)` in the
     `input` event listener at `TextInputField/index.tsx:41-43` before the run and read it from the
     already-open DevTools console output pane, which — unlike the console *input* — is readable).
   - Also paste the same clipboard content (repeat step 1's clipboard, no need to re-copy) into
     GameLib's own library search bar (`document.getElementById('search')`, reachable via Cmd+F per
     `shortcuts.ts:5`) in the same running instance. This is the control that answers Open Question 2:
     if the search bar also garbles the paste, the cause is host/shell-level (out of scope, mint
     separately); if only `PathSelectionBox` fields are affected, the cause is local to this chain
     (in scope, may be fixed in a follow-up within this phase's own scope fence).
5. Record the result in the phase's UAT/verification artifact: the exact string that appeared (or
   the exact "repeating unrenderable glyph" if reproduced — copy/screenshot the actual character(s),
   do not paraphrase "garbled text"), whether the control (search bar) also failed, and the recorded
   evidence (screenshot + DOM inspector reading, or console log line).

**Outcome A — reproduces, control (search bar) is also affected:** cause is host/shell-level. Close
Half B in this phase as **REPRODUCED, ROOT CAUSE HOST-LEVEL, OUT OF SCOPE** per the ROADMAP's own
scope fence — mint a new item, do not fix it here.

**Outcome B — reproduces, control (search bar) is unaffected:** cause is local to
`PathSelectionBox`/`TextInputField`'s custom hand-wired `input`-event-listener architecture. This
becomes a legitimate in-scope fix for this phase — file it as its own task once the mechanism is
understood from the live evidence (do not guess at a fix before this point).

**Outcome C — does not reproduce at all:** close as **VERIFIED-ABSENT**, per the ROADMAP's explicit
instruction. Record the protocol steps taken and their (negative) result as the closing evidence —
"we ran the protocol and could not reproduce it" is a complete, honest closure, not a gap.

## Candidate Requirements

The planner should mint these (or a close variant) as `REQ-34.17-*`. Half A's two requirements are
fix obligations; Half B's is deliberately a **reproduction-or-falsification obligation**, not a fix
obligation, per the ROADMAP's explicit instruction not to fix an unreproduced cause.

- **REQ-34.17-01** (Half A, fix): Pressing Enter while focused in any `PathSelectionBox` field
  commits the currently-typed value via the same `onPathChange` contract `onBlur` already uses,
  without requiring the field to lose focus. Wire via `TextInputWithIconField`'s already-declared
  `onKeyDown` prop (no interface widening needed); match the existing `SteamGridDBPicker` house
  pattern for the `e.key === 'Enter'` check.
- **REQ-34.17-02** (Half A, fix): An Enter-commit immediately followed by a blur-commit of the same,
  unchanged value does not double-fire a non-idempotent side effect. Concretely: `EgsSettings.tsx`'s
  macOS/Linux `PathSelectionBox` (the one call site of 13 whose `onPathChange` is not
  guard-idempotent) must not call `window.api.egsSync` twice for one user edit. Recommended
  implementation: compare against the already-committed `path` prop inside `PathSelectionBox` itself
  (generalizes the guard to all 13 call sites at once, rather than requiring each caller to implement
  it).
- **REQ-34.17-03** (Half A, fix, the affordance clause): after an Enter-commit (and ideally also
  after a blur-commit, for consistency), the user receives some visible, non-blocking confirmation
  that their edit was saved. No exact existing pattern for "field committed" exists in this codebase
  today (nearest precedents — the `warning` prop slot on `TextInputField`, `HumbleExpiryToast`, and
  `aria-live` regions used only in `ConsoleMode` — are all semantically or architecturally mismatched;
  see Architecture Patterns). The planner/design pass should choose the smallest viable option (a
  transient CSS state on the field itself is the lowest-risk fit given the existing `textInputFieldWrapper`
  structure) and, if any new user-facing string is needed, add it to `gamelib.json` (never
  `translation.json`, per project rule) and keep `pnpm lint-translations:gamelib` green.
- **REQ-34.17-04** (Half B, **reproduction-or-falsification, not a fix**): run the Reproduction
  Protocol above on a real Tauri host and record one of the three outcomes (A/B/C) with the specified
  evidence artifacts. This requirement is satisfied by a recorded, evidenced outcome — **not** by a
  code change. If Outcome B occurs, a follow-up in-scope fix task may be added to this same phase
  (the mechanism will be known by then); if Outcome A occurs, a new ROADMAP item must be minted and
  this requirement closes as "reproduced, routed out of scope"; if Outcome C occurs, this requirement
  closes as VERIFIED-ABSENT.
