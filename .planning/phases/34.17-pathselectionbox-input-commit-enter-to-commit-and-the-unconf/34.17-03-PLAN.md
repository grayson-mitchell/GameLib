**The ledger's own suspected cause is mechanically implausible — carry this into the record, do not
silently drop it.** The ledger names `navigator.clipboard` silently no-opping under Tauri/WKWebView
as the likely root cause. That standing project note concerns PROGRAMMATIC `writeText()`/`readText()`
calls. Phase 34.3 (commit `44232d3e`) migrated every such call site onto
`window.api.clipboardWriteText` / `clipboardReadText`, and ZERO `navigator.clipboard` call sites
remain in the codebase. A native Cmd+V into a plain `<input>` never touches that API on any code
path. This candidate is not merely unproven — there is no mechanism connecting it to the symptom.

**A more plausible but still unconfirmed candidate, already fixed ONCE in this repo for a different
window.** `src-tauri/src/main.rs`, inside `open_pristine_epic_login_window` (function begins at
line 2210), carries a "Key-equivalent delivery fix (live-confirmed 2026-08-03)" at lines 2363-2454.
Its own comment states the mechanism precisely: choosing Edit ▸ Paste from the menu bar pastes
correctly — proving the webview IS first responder and DOES handle `paste:` — but pressing Cmd+V
does nothing, because tao's `NSWindow` subclass consumes the raw Cmd+V `NSEvent` before AppKit's
`performKeyEquivalent:` main-menu traversal sees it. The installed fix is an `NSEvent` local
monitor that re-dispatches five Edit-menu selectors, and the comment states it deliberately lets
"every other event -- including these same shortcuts in every OTHER window -- fall through
completely unchanged." **The primary Tauri window, where `PathSelectionBox` renders, is therefore
NOT covered by that fix.**

**Evidence pulling the other way, which is why this is genuinely open.** `Skill("spike-findings-gamelib")`
records for login-window UX (spikes 019-022) that the two working Keychain channels are
right-click ▸ AutoFill ▸ Passwords and **Cmd+V paste from the Passwords app** — i.e. Cmd+V was
observed working in a WKWebView surface in this app. That does not settle the primary window, but
it does mean "Cmd+V is broken everywhere under wry" is not a safe prior.

**The protocol must not encode either candidate as the cause.** Its job is to discriminate. Note
also that the tao candidate predicts Cmd+V does NOTHING, while the ledger reports a repeating
unrenderable GLYPH — those are different symptoms, and which one actually occurs is itself a
finding.

**Discriminating surfaces, all reachable on one screen (Settings → Advanced):**
- Target: `#setting-alt-legendary` — Alternative Legendary Binary, a `PathSelectionBox` whose
  `onPathChange` is `useSetting('altLegendaryBin')`, idempotent and safe to write.
- Control C1 (host-level discriminator): the library search bar, `#search`, focusable with Cmd+F
  (`src/frontend/helpers/shortcuts.ts:3-6`). Its `<input>` is **fully uncontrolled** — no `value`
  prop, no React `onChange`, just a `ref` (`SearchBar/index.tsx:77-85`). If paste garbles HERE, no
  React-controlled-input theory can explain it and the cause is host/shell-level.
- Control C2 (component-layer discriminator): `#steamgriddb-api-key` — SteamGridDB API Key, a
  plain `<TextInputField>` on the same Settings → Advanced screen
  (`SteamGridDbApiKey.tsx:69-74`). It shares `TextInputField`'s hand-wired
  `element.value = value` + `addEventListener('input', ...)` architecture
  (`TextInputField/index.tsx:37-50`) but is NOT a `PathSelectionBox`. C1 clean + C2 garbled means
  the cause is in `TextInputField`; C1 clean + C2 clean + target garbled means it is in
  `PathSelectionBox` itself.

**The field to avoid.** Do NOT use `EgsSettings.tsx`'s path field as the target. Its
`onPathChange` is `handleSync`, which fires a real `window.api.egsSync` IPC and maps any falsy
value to `'unlink'`, spawning `legendary egl-sync -y --unlink`. A pending todo
(`.planning/todos/pending/2026-08-24-pathselectionbox-onblur-silently-unlinks-egs-sync.md`)
records a live operator hitting exactly that. Nothing in this protocol requires it.
