# 34.17 Half B — Paste Reproduction Gate

## 1. What is being tested, and what is NOT

This gate settles one question only: **does pasting into `PathSelectionBox` reproduce the
2026-08-11 ledger report of a repeating unrenderable glyph replacing the clipboard text?** It does
not settle *why*, and it does not fix anything. Both a clean reproduction attempt (`VERIFIED-ABSENT`)
and an actual reproduction (`REPRODUCED-HOST-LEVEL` / `REPRODUCED-LOCAL`) are complete, passing
outcomes of this gate. Nothing in this document can be satisfied only by the defect existing.

The **Enter-to-commit half is separate work**, owned by `34.17-01` (already landed) and `34.17-02`.
Nothing observed by this gate may be used to score the Enter half, and nothing recorded here makes
any claim about it.

## 2. Candidate causes — ranked, unconfirmed hypotheses, not conclusions

Every candidate below is an unconfirmed hypothesis. None of them is asserted as a conclusion by
this document. The protocol's job is to discriminate between them, not to pick a winner in advance.

**Candidate A — `navigator.clipboard` silently no-opping under Tauri/WKWebView (the ledger's own
suspected cause).** This candidate is mechanically implausible for a native Cmd+V into a plain
`<input>`. Phase 34.3 (commit `44232d3e`) migrated every programmatic clipboard call site in this
codebase onto `window.api.clipboardWriteText` / `clipboardReadText`; zero `navigator.clipboard`
call sites remain anywhere in the tree. A native OS-level keyboard paste into a DOM `<input>` never
touches that API on any code path that exists today. **Falsifier:** none needed to rule this in —
it is already ruled out by absence of a connecting mechanism. It is recorded here only so a later
reader cannot resurrect it as the explanation without re-deriving this absence for themselves.

**Candidate B — the tao/wry Cmd+V key-equivalent delivery gap, already fixed once, but only for the
Epic login child window.** `src-tauri/src/main.rs` (function `open_pristine_epic_login_window`,
beginning at line 2210) carries a live-confirmed fix at lines 2363-2454. Its own comment records
the diagnostic: choosing Edit ▸ Paste from the macOS menu bar pastes correctly (proving the webview
is first responder and does handle `paste:`), but pressing Cmd+V does nothing, because tao's
`NSWindow` subclass consumes the raw Cmd+V `NSEvent` before AppKit's `performKeyEquivalent:`
main-menu traversal ever sees it. The installed fix is an `NSEvent` local monitor scoped, by its
own explicit comment, to that one window only — "every other event -- including these same
shortcuts in every OTHER window -- fall[s] through completely unchanged." The primary Tauri window,
where `PathSelectionBox` renders, is NOT covered by that fix. **Falsifier:** if Cmd+V does nothing
at all in the target field (no glyph, no text, field unchanged) AND Edit ▸ Paste from the menu bar
succeeds, that symptom shape matches Candidate B exactly. **This candidate predicts silence, not a
glyph** — the 2026-08-11 report describes a repeating unrenderable glyph, a different symptom
shape, which is itself evidence against a clean match to Candidate B.

**Candidate C — no defect, or a transient one-off from the original gate run.** Evidence pulling
this direction already exists: `Skill("spike-findings-gamelib")` records, for the Epic/Humble
login-window UX spikes (019-022), that Cmd+V paste from the Passwords app is one of the two working
Keychain-autofill channels observed in a WKWebView surface in this app. That does not settle the
primary window, but it does mean "Cmd+V is broken everywhere under wry" is not a safe prior.
**Falsifier:** the probe string appears correctly, character for character, in the target field
after Cmd+V.
