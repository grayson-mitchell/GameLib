**Load-bearing framing:** this phase has two halves with *different* validation regimes.
Half A (Enter-to-commit) is unit-provable. Half B (the paste glyph) is **not provable by
any test in this repo** and must not be given one. A plan that writes a jest paste test
has manufactured false confidence, not coverage.

**⚠ Case-sensitivity trap — load-bearing here, not a footnote.**
`--selectProjects frontend` (lowercase) matches **nothing and exits 0**. The real
`displayName` is `Frontend`. Any plan or verification step using `--selectProjects` must
use the exact capitalised name, or it will silently skip every test and still report
success. This is a failure that fails *open*.

**⚠ There is no DOM.** The frontend jest project runs `testEnvironment: 'node'`. Tests
invoke components as plain functions and walk the returned element tree. Do not plan a
test that assumes `render()`, `screen`, `userEvent`, or any jsdom global.

## What each layer can and cannot prove

### Provable by jest (no DOM, handler-invocation pattern)

- **REQ-34.17-01** — `PathSelectionBox` passes an `onKeyDown` to `TextInputWithIconField`
  which, when invoked with `{ key: 'Enter' }`, calls `onPathChange` with the field's
  current value.
- **REQ-34.17-02** — the same handler invoked twice in a row with an unchanged value
  (Enter, then blur) calls `onPathChange` at most once for a changed value.

**False pass this must foreclose:** a test that only asserts *"an `onKeyDown` prop exists
on the rendered tree."* That checks the **call site, not the behaviour** — this project's
own named failure mode — and would pass with an empty handler body.

**Foreclosure requirement (mandatory on the plan):** the test must (a) **invoke** the
handler, not merely assert its presence, and (b) assert that a **non-Enter key does not
commit**. Without the negative case, a handler that commits on *every* keystroke also
passes, and that handler is a worse defect than the one being fixed.

### NOT provable by jest — do not plan a test for these

- **REQ-34.17-03 (the affordance).** Any visual/paint/transition claim. The frontend jest
  project has no DOM at all, and even with jsdom, paint timing is not meaningfully
  assertable.
  **False pass:** asserting a CSS class-name string appears in the mock render tree. That
  passes even when the class has **no visible effect** — this project has already shipped
  exactly that failure (a stylesheet wholly dead against its component). The only valid
  check is a human looking at the running app.

- **REQ-34.17-04 (Half B, the paste glyph).** A simulated `ClipboardEvent` / `paste` DOM
  event — even if jsdom were added — exercises React's synthetic event system, which was
  never in question. The mechanism under suspicion is **OS-level key-equivalent delivery
  through WKWebView's native responder chain** into an uncontrolled DOM node.
  **False pass:** *"we wrote a jest test, it pastes text, the input updates, therefore
  paste works."* That is precisely the shape of false confidence this project's standing
  lessons warn against — a green gate measuring a property that was never broken while
  leaving the suspected defect entirely unexercised.
  **No plan may write this test.** The only valid check is the live reproduction protocol.

### Half B Reproduction Protocol (evidence-producing, macOS)

**Preconditions.** `pnpm tauri:dev` is the correct dev command (not `tauri dev`), and it
**exits 0 without replacing an already-running instance**. Confirm a fresh process is
actually running via `pgrep -fl gamelib-shell` (**not** `pgrep GameLib`, which misses it),
or fully quit the app first.

**Surface.** Settings → any path field backed by `useSetting` (e.g. "Default Install Path"
or "Alt Legendary Bin"). **Avoid `EgsSettings.tsx`'s path field for this protocol** — a
successful paste there fires the real `egsSync` IPC side effect, and it is not needed to
observe the paste symptom.

1. Copy a short, distinctive, collision-proof string to the clipboard from **outside** the
   app: `echo -n "/tmp/gamelib-paste-probe-12345" | pbcopy`. A synthetic string makes it
   trivial to tell "my paste" apart from residual clipboard content.
2. In the running GameLib window, open Settings and focus the target `PathSelectionBox`
   `<input>` by single click. Do **not** use the folder-picker icon.
3. Paste via the real key equivalent: **Cmd+V**. Do not use the Edit ▸ Paste menu — the
   original report was of a keyboard paste, and this project has separately found that
   key-equivalent delivery and menu-driven paste can behave differently in a sibling
   window class. Testing the keyboard path is what matches the original report.
4. **Capture evidence — mandatory, not optional:**
   - Screenshot the field's rendered content immediately after the paste attempt.
   - Separately verify what the DOM node's `.value` actually contains. **The Tauri DevTools
     console cannot be pasted into**, so do not plan to paste a verification snippet into
     it — instead right-click the field → Inspect Element and read the `value` property
     directly in the Elements panel.
   - **Control test (answers the scope question):** paste the same string into GameLib's
     own library search bar (reachable via Cmd+F) in the same running instance. If the
     search bar **also** garbles the paste, the cause is host/shell-level — **out of this
     phase's scope fence**, and must be minted as its own item. If **only**
     `PathSelectionBox` fields are affected, the cause is local to this chain and in scope.
5. Record in the phase's UAT/verification artifact: the exact string that appeared — or the
   exact glyph if the defect reproduced (**copy or screenshot the actual character(s); do
   not paraphrase as "garbled text"**) — whether the control also failed, and the captured
   evidence (screenshot + DOM inspector reading).

**Both outcomes are valid deliverables.** If the defect does not reproduce, the correct
result is to close Half B as **VERIFIED-ABSENT** with the evidence attached — not to fix
it by assumption.
