# Phase 79 Plan 31: refresh() as a thin caller of the Rust Refresh

On `cm=rust`, `refresh()` keeps its grant, deferral and lease code byte-identical, then makes one `steamcm_refresh` call and does only the TS-owned persistence: snapshot-checked metadata writes under `withPlatformCaptureLock`, in-memory `libraryState`, `pushGameToLibrary`, `steamLibraryStore 'games'`, `steamSyncStore 'syncedAt'` and `steamSyncStatus`. `cm=ts` runs today's `syncOwnedLibrary` unchanged; install/uninstall/update polling files are untouched (D-17).

## Behavior
- Inputs: metadata (deep-cloned snapshot), previousGames, native/bottle/bridge/incomplete install maps (restart holds applied, sizes via `getFileSize`; bottle and bridge only under today's isMac gates), bridge allowlist, known-fix mac32 ids, isMac.
- Stale-skip: a metadata update is written only when the store entry still deep-equals the sent snapshot entry; otherwise it is kept and counted (T-79-127).
- Games pass `stripToSchema` + `invalidPaths` before state or store (T-79-93).
- `{ok:false}` (and a rejected invoke) -> `restoreLocalSteamLibrary(pushAll)` + failed `owned-apps-failed`, lease released (T-79-94). Input-build or apply throw -> failed `sync-failed`, re-thrown.
- Bridge launch-target backfill stays in TS, runs after the op on the same lease, fail-soft.
- Log lines: capture (original wording plus anon/held), enrichment, metadata written/staleSkipped; counts only.

## Deviations from Plan
1. **[Rule 3] `leaseIdOf` lives in `cm/RustCmClient.ts`, not user.ts.** 79-18 did not add it. It reads a symbol-keyed non-enumerable property set by `createRustCmClient`. A first version used a module-level WeakMap and failed `moduleStateCensus`, so it was changed to a client property.
2. **[Rule 3] `bridgeAllowlist.seedIds()` added to `bridge/allowlist.ts`.** The allowlist had no enumerator and the op needs the ids as data. Not in the plan's files_modified.
3. **Jest-fixture parity (deferred from 79-27) not executable.** The existing `library.refresh.test.ts` fixtures feed TS `getUserOwnedApps` mocks and assert TS-built games; there is no real Rust in Jest, so the same fixtures cannot yield a games array through the Rust path. `library.refresh.rust.test.ts` instead replays a hand-built `RefreshResult` through the full TS persistence path, and Rust-side assembly parity rests on 79-27's hand-built fixtures mirroring those cases. A live comparison belongs to UAT / 79-33.
4. **No steamcm_refresh entry added to `rust-results.json`.** That file is regenerated by the Rust golden test (`GAMELIB_WRITE_STEAMCM_RUST=1`), so a hand edit would be flagged stale; the Jest test uses an inline recorded-shape result instead.
5. A client that is not a Rust lease under cm=rust is a client-not-ready failure with cached restore (defensive; unreachable in normal wiring).
