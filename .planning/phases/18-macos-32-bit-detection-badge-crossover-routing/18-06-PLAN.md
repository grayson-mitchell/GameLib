<objective>
Close the single Phase-18-scoped gap from 18-UAT.md test 5 (MAC32-03 recovery robustness): `SteamGame.forceUninstall()` (src/backend/storeManagers/steam/games.ts:850-858) calls `library.delete(this.appId)`, which FULLY REMOVES the owned game from the in-memory library Map. Live consequences confirmed via GameLib logs + the persisted store:

1. The "32" badge (and the whole game entry) blinks out during i386 recovery — the game vanishes from the frontend-visible library until a later refresh() re-adds it from ownedApps.
2. If the subsequent bottle reinstall does not complete (the common case — it hands off to the CrossOver Steam dialog and can time out at the 60s grace window), the game is left orphaned: absent from the persisted `steam_library.json` games[] entirely (Age of Wonders III was confirmed absent post-recovery, while its metadata cache still held mac_arch:'32').
3. forceUninstall() also never persists the mutated Map to steamLibraryStore (unlike every other Map-mutating site in this codebase), so the divergence is written out on the next persist (code-review WR-01 class).

The fix: make forceUninstall() mirror the canonical keep-entry uninstall pattern already used by `pollUninstallOnce()`'s 'absent' branch (library.ts ~1131-1144). An owned game that is uninstalled must REMAIN in the library marked is_installed:false — preserving mac_arch and every other field — rather than being removed. This is correct for BOTH callers of forceUninstall(): library.ts:746 (promptI386Recovery) and utils.ts:295 (general uninstall path).

Purpose: an i386-recovery (or any) forceUninstall leaves the owned game in the library marked not-installed with its 32-bit badge data intact, and never orphans it.
Output: the keep-entry fix in games.ts + updated/added regression tests in games.test.ts that lock the badge-preserving behavior so this cannot silently regress.

Scope fence (do NOT touch): library.ts's promptI386Recovery, the bottle install poller, the MacArchBadge component. Do NOT address the bottle-reinstall-feedback or dual-dialog UAT notes — those are Phase 17/3-rooted and tracked as separate todos.
</objective>
