<objective>
Port the five DownloadManager queue-management channels onto the Tauri sidecar as a new
curated flow module, and prove the two push channels (`progressUpdate`,
`changedDMQueueInformation`) ride the existing generic `frontend_message` relay with zero
Rust changes. Suppress boot-time auto-resume (D-05) while preserving pre-`initQueue`
cancelability.

Purpose: This is the pull-side + push-proof half of the queue re-plumb. The install re-route
(Plan 32-02) enqueues into the queue these channels act on; docs (Plan 32-03) declare the
result. The single highest-risk detail is the send-kind vs invoke-kind transport split — a
mis-registered `send` channel fails completely silently (Phase 31 Pitfall 2 / `setSetting`).

Output: `downloadQueueFlowRegistration.ts` (new), the `handlers.ts` wiring, and
`downloadQueueFlows.test.ts` (new harness) covering REQ-32-02/03/04/05/08.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| renderer → sidecar (RPC frame) | Queue-channel args (`appName`, `removeDownloaded`) arrive as `unknown[]` from the JSON-RPC stream and are cast at the registration boundary |
| sidecar → frontend (push relay) | `progressUpdate` / `changedDMQueueInformation` frames written to stdout, re-emitted by the generic Rust `frontend_message` relay |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-32-01 | Tampering | `removeFromDMQueue`/`cancelDownload` args (`unknown[]`) | mitigate | Cast `args[0] as string`/`as boolean` at the `ipcMain.on` boundary; downstream `removeFromQueue`/`cancelCurrentDownload` look appName up via `libraryManagerMap` (unmodified, no shell/path interpolation at this layer — path containment is depot.ts's shipped `resolveContainedPath`) |
| T-32-02 | Repudiation | send-kind queue channels (silent-failure class) | mitigate | Register with `ipcMain.on` not `.handle`; every test asserts the underlying real fn was CALLED — a mis-registered send channel is otherwise completely silent (Pitfall 1). D-05 disablement is logged, never silent |
| T-32-03 | Denial of Service | oversized/malformed queue `send` frame | accept | Already covered project-wide by `sidecarRpc.ts` `MAX_LINE_LENGTH` (10 MiB) frame cap + per-listener `dispatchSend` try/catch (T-27-04, inherited) — no new mitigation this phase |
| T-32-SC | Tampering | npm/pip/cargo installs | accept | No package installs this phase (pure in-repo re-plumb) — Package Legitimacy Gate not applicable |
</threat_model>
