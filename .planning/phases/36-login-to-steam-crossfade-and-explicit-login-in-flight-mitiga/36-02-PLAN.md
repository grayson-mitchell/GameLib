THE QUESTION: both artifacts cite `showSidLogin` as an existing conditionally-mounted overlay that
leaves all six tiles mounted. But `loginInFlightUiReachability.test.tsx` documents unmount-on-navigate
as THE mechanism making a second store's sign-in control unreachable. Both cannot be fully true.

THE ANSWER IS (a), WITH A QUALIFIER THAT MATTERS: SIDLogin IS an existing hole in that mitigation,
and the current gate ALREADY KNOWS IT AND SAYS SO. The existing test file's header comment, lines
29-33, reads verbatim:

    "`Runner.handleLogin()` (`Runner/index.tsx`), for every tile with no `primaryLoginAction` (the
     GOG/Amazon/Steam/Zoom/Humble shape -- Epic under Tauri is the sole exception via
     `primaryLoginAction`, out of scope here per this phase's own Epic-deferred boundary), calls
     `navigate(props.loginUrl)`"

So the existing gate never claimed "no overlay exists." It claimed, precisely, "for the five tiles
with no `primaryLoginAction`, the unmount is the mechanism" — with Epic-under-Tauri explicitly carved
out and named as out of scope. There is no contradiction to resolve, only an exception to carry
forward correctly.

WHAT IS ACTUALLY TRUE OF SIDLogin, verified from source:
  - `Login/index.tsx:156-158` — Epic's tile passes
    `primaryLoginAction={isTauri() ? () => setShowSidLogin(true) : undefined}`. Under Tauri, clicking
    Epic mounts an overlay and does NOT navigate. All six tiles stay mounted.
  - `SIDLogin/index.css:1-14` — `.SIDLoginModal` is `position: absolute; inset: 0; z-index: 8`,
    containing a `.backdrop` span at `inset: 0; z-index: 6`. `.loginContentWrapper` is `z-index: 1`
    (`Login/index.scss:49`) and `.loginPage` is `position: relative` (`Login/index.scss:8`). The
    backdrop therefore paints over the tiles and swallows mouse clicks aimed at them, dismissing
    SIDLogin rather than starting a second login.
  - That backdrop is an INCIDENTAL, pointer-only guard. `SIDLogin` is a hand-rolled `<div>`, not a
    MUI `Modal`: no focus trap, no `inert`, no `disabled` wiring back to the tiles.

WHAT THIS PLAN DOES ABOUT IT: NOTHING, DELIBERATELY. Epic is a standing project deferral and is named
OUT in this phase's scope fence. Wiring SIDLogin into `loginInFlight` would be scope creep into the
Epic flow. It is recorded as a separate named finding (F-36-01 in the threat model below) and carried
forward verbatim into the rewritten gate's exception clause.

WHAT THE REWRITTEN GATE MUST THEREFORE NOT DO: it must NOT assert any universal such as "every
overlay-opening action sets `loginInFlight`" or "`primaryLoginAction` appears exactly once."
SIDLogin violates both TODAY, so such an assertion would be wrong on day one. Scope every universal
to the Steam flow and reuse the existing header's own carve-out language for Epic.
</resolved_sidlogin_precedent>

<verified_guard_layer_analysis>
<!-- VERIFIED BY DIRECT SOURCE READ 2026-08-20. This determines what each layer actually buys.
     Do NOT restate these as "three redundant layers" — they are not equivalent. -->

1. `disabled` is NOT a DOM attribute here. `Runner` renders its clickable element as
   `<div className="runnerLogin" onClick={() => handleLogin()}>` (`Runner/index.tsx:112-118`). The
   `disabled` prop is a React prop consumed by `handleLogin()`'s early return
   (`Runner/index.tsx:59-61`) and by a `disabled` class on `.runnerWrapper`. PRIMARY, universally
   supported, load-bearing.

2. `.runnerWrapper.disabled` sets ONLY `cursor: not-allowed` (`Runner/index.css:19-22`). There is no
   `pointer-events: none` anywhere in `Runner/index.css`. That layer must be added — this plan adds
   it on `.loginContentWrapper` (screen level), not in `Runner/index.css`, so one class stays the
   single source of truth.

3. THE TILES ARE NOT FOCUSABLE TODAY. `.runnerLogin` is a bare `<div>` with an `onClick`, no
   `tabIndex`, no `role`, not a `<button>` or `<a>`. It is already absent from the tab order and
   exposes no interactive role to assistive technology. Consequence: `inert`'s focus-order and
   a11y-tree removal buys very little FOR THE TILES — which materially downgrades 36-RESEARCH.md
   Pitfall 2's macOS 12.0–12.3 residual from "a real gap" to "near-zero impact for the tiles." Keep
   `inert` regardless: it is the correct declarative statement of intent and future-proofs the day
   someone correctly converts these divs to `<button>`s.

4. `.loginContentWrapper` DOES contain two genuinely focusable controls that are not tiles: the
   `LanguageSelector` and `<button className="goToLibrary">` (`Login/index.tsx:235-247`). On
   Safari >= 15.5 `inert` covers them. On the macOS 12.0–12.3 slice it does not — there the layer
   that holds is MUI's `Modal` focus trap, active for `SteamLogin` because `Dialog.tsx` overrides
   none of `disableAutoFocus` / `disableEnforceFocus` / `disableRestoreFocus` (verified: none of the
   three appears anywhere in `Dialog.tsx`). Name this honestly; do not claim `inert` covers it.

5. MUI portals the Dialog to `document.body` — `Dialog.tsx` sets no `disablePortal` (verified by full
   read). The Steam dialog is NOT a descendant of `.loginContentWrapper`, so inerting the wrapper
   cannot inert the dialog. This is why 36-01 renders `<SteamLogin>` as a sibling of
   `.loginContentWrapper` rather than inside it.
</verified_guard_layer_analysis>

<react_18_inert_form>
This project pins `react@^18.3.1` and `react-dom@^18.3.1` (verified, `package.json` lines 116-117).
Boolean `inert` landed in React 19 (facebook/react PR #24730). On React 18 the boolean form silently
renders `inert="true"`, and `inert={false}` emits a "Received `false` for a non-boolean attribute"
console warning.

REQUIRED FORM:  inert={loginInFlight ? '' : undefined}

`36-PATTERNS.md` line 253 recommends the boolean form and claims "React 19/18 both support it
natively." That claim is WRONG for this project's pinned version; RESEARCH.md's correction is the one
to follow. Operator-locked — do not revisit.
</react_18_inert_form>
