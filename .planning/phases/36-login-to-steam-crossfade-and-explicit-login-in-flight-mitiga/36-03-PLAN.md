<locked_decisions>
- View Transitions API is OUT. WebKit shipped it in Safari 18 (macOS 15+); this app's `oldMac` floor
  is macOS 12 (`Login/index.tsx:79-89`). `document.startViewTransition` is simply undefined there.
  Use plain CSS `transform`/`opacity` transitions on a state-toggled class, per the
  `ConsoleMode.launching` precedent. Operator-locked — do not revisit.
- The motion MUST be expressed as a CSS `transition` (or `animation`) property. A raw JS style
  mutation with no CSS transition property is structurally invisible to `App.css:116`'s global
  override and would silently break the in-app "disable animations" accessibility toggle. This is an
  implementation constraint, not a preference.
- Do NOT add a `@media (prefers-reduced-motion: reduce)` rule. 36-RESEARCH.md floats it as optional
  and discretionary. Declining it: the codebase honours zero such queries today, so a single scoped
  one would imply partial support that does not exist, and the `disableAnimations` toggle already
  covers this transition completely. Recorded as a deliberate non-goal, not an oversight.
</locked_decisions>
</context>

  <action>
Add a `transition` declaration to the existing `.loginContentWrapper` rule (currently lines 40-51)
covering `transform` and `opacity` at `500ms`. Use the literal `500ms`, matching `Dialog.tsx`'s
`transitionDuration={500}` — this codebase has no motion token system and the closest sibling literal
is the correct precedent to follow. Task 2 adds a gate that fails if the two drift apart.

Use `cubic-bezier(0, 0, 0.2, 1)` as the easing. This is MUI's own `easeOut` curve, which is what the
Dialog's `Slide` entrance uses by default — matching it is what makes the two halves read as one
motion rather than two animations that happen to overlap.

Extend the `.loginPage.steamFlowOpen` block that plan 36-02 created (it currently sets only
`pointer-events: none` on `.loginContentWrapper`) so the same selector also sets
`transform: translateY(-100%)` and `opacity: 0`. `-100%` is exact rather than approximate here
because `.loginContentWrapper` is `height: 100%` of `.loginPage` — verified above.

Do NOT modify the `.loginBackground` rule (lines 32-38). It is out of flow at `inset: 0` and stays
painted automatically; its comment block records that a prior edit to this exact rule caused defect
F-10, where the login screen rendered ~11000px below the fold. Leave it alone.

Do NOT add `overflow: hidden` to `.loginPage`. Translating a child upward does not extend the
scrollable overflow region in a top-to-bottom writing mode, so no scrollbar should appear — but this
is a rendering-level claim that no source gate in this repo can verify, so it is listed as an explicit
observation in the plan 36-05 human gate instead of being pre-emptively "fixed." If the human gate
observes a scrollbar or clipping, that is the moment to add it, with the evidence in hand.

Do NOT add keyframes. A state-toggled `transition` is sufficient and reverses for free on dismiss,
which is what makes the closing motion work without a second rule.
