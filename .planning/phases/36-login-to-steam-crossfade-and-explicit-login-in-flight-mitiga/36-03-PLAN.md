<expected_behaviour_notes>
Two behaviours below are DELIBERATE OUTCOMES OF THIS PHASE'S DESIGN, not defects. They are named here
so the operator does not report them as regressions.

1. THE DIALOG'S EXIT TRANSITION MAY PLAY FOR THE FIRST TIME. `Dialog.tsx`'s `close()` runs
   `setOpen(false)` and `onClose()` in the same tick, so before this phase the tree unmounted before
   MUI's Slide exit could get a frame. Plan 36-01's deferred unmount gives it that frame on the
   close-button, backdrop, and Escape paths. Any newly-visible closing animation there is in scope
   and expected.

2. THE FOUR POST-SUCCESS PATHS BEHAVE DIFFERENTLY FROM THE CLOSE BUTTON, BY DESIGN. Those paths call
   the dismiss handler directly and never route through `Dialog`'s internal `close()`, so the Dialog's
   own `open` state stays true and its exit Slide does not play. What the operator should see is the
   "completing sign-in" confirmation UI holding for roughly half a second while the login panel slides
   back down, then clearing. This was a considered trade: the alternative was adding a controlled
   `open` prop to the shared `Dialog` primitive, which is named OUT in this phase's scope fence and
   would change behaviour for all 25 Dialog consumers. Item 6 below scores this specifically. If the
   operator judges it visually wrong, that is a legitimate FAIL and a future phase can revisit the
   primitive — but it is not a bug report against this implementation.
</expected_behaviour_notes>
