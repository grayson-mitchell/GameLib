<objective>
Land the real command runner behind the `commandRunner` service: `callRunner`, `runWineCommand`, `getWinePath` and
`runScriptForGame` re-implemented on `ProcessRunner.run`, pinned by a mock-free Layer-2 port of plan 02's
characterization cases. Consumers already holding the `commandRunner` slice (none yet; plans 07-22 convert them) get the
runner-based version without further edits.

Purpose: MH-4 and D-11 (`callRunner`/`runWineCommand` become thin runner callers). This is the first production caller
of the runner; plan 01 already fixed C-02.
Output: `src/backend/commandRunner.ts`, its suite, boot wiring, depcruise rule. Ceilings: none in this plan (the legacy
`launcher.ts` spawn and its 3 moduleState entries fall in plan 24, `_root` shard).

Decisions recorded here:
- **Injection over imports for hermetic tests:** commandRunner.ts takes logging, log-writer lookup, abort-controller
  registry, `searchForExecutableOnPath`, `commandToArgsArray` and the wine env/validation helpers as deps. D-07 lets modules
  keep the logger import; injecting here is what lets the Layer-2 suite run with zero `jest.mock` (D-12, D-16). Production
  passes the real functions.
- **A4:** pass `windowsHide: false` everywhere in this module: the legacy spawns passed nothing (false); a refactor must
  not change console visibility on Windows.
- **A5:** keep the legacy accumulation (per-chunk `trim()`, last-50-chunk memory logs) in `onStdout`/`onStderr` and
  build the result from it; ignore the runner's 8 MiB capture for the result.
- **wineserver --wait:** 30-minute finite timeout. On timeout log a warning naming the prefix and resolve the first
  child's result (the caller already has it); today a hung wineserver hangs the caller forever.
</objective>
