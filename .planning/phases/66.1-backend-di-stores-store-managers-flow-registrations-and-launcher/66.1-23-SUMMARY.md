## Cancel/stop trace (item 6)
- Cause: since 66.1-05 `commandRunner.callRunner` reports a signal-exited child as `.error` unless the abort controller was signalled. The legacy runner read a `child.kill()`-ed child as success (`child.killed`).
- Paths: `kill` (dispatch.kill) and the download queue's `stopCurrentDownload`/`downloadmanager/utils` all call `callAbortController(appName)` first, so legendary/nile/gog runs with `abortId` = game id already classify as `.abort` (gog launch maps `abort` to success; legendary/nile `!error`). The gap was a kill with no matching abort controller: sideload native launch (random abortId, `trackKey` = appName) killed through `killTracked`, and any `killAllTracked` at quit. Steam stop/cancel goes through its own abort/bridge-bottle paths (`SteamGame.stop`), never `callRunner`, so it was already clean and is unchanged.
- Fix: the tracked registry records children it killed (`wasKilled`, WeakSet); the runner puts `killedByUs: true` on the RunResult; `callRunner` classifies it as `.abort` (no error log, no error text, no `error` field), before the signal/exit-code checks, so a graceful non-zero exit after our SIGTERM is also a cancel. Not guessed from the signal: an unmarked SIGTERM still surfaces as an error (test).
- Tests: runner.test (real node child killed via killTracked is `killedByUs`, a sibling and a self-SIGKILL are not), commandRunner.test (marked signal exit and marked non-zero exit are abort; unmarked signal exit is still an error), createStoreManagers.test (a real child run through the real runner + commandRunner, stopped via `library.nile.getGame(id).stop(false)` with an unrelated abort id, resolves `{ abort: true }` with no error).
