## Phase Boundary

D-15 step 2 of Phase 66 (ROADMAP "### Phase 66.1"). Nothing is constructed at import time.

- A stores factory replaces the 16 `*/stores.ts` modules and `key_value_stores.ts`.
- `createStoreManagers` builds the library and game manager classes (gog, legendary, nile, steam, sideload) with constructor deps at boot (D-02); the 46 non-test consumers of `libraryManagerMap` / `gameManagerMap` / `storeLaunchHooks` receive them.
- The 25 `sidecar/*FlowRegistration.ts` files take narrow slices (D-01).
- `launcher.ts`: `callRunner`, `runWineCommand`, the gamescope probe and script spawns become runner callers, pinned by characterization tests first.
- `utils.ts` `spawnAsync` becomes a thin runner caller; `handleExit` calls the runner's teardown.
- `trackedChildren.ts` and `longLivedChildren.ts` are deleted; comet and the bridge `helperSpawn` move to `spawnLongLived` (D-10, D-11).
- Ceilings in `meta/backendDiCeilings/` drop in the same commits (D-16).

**Out of scope (66.2 / 66.3):** routing every remaining backend spawn through the runner and the `child_process` lint ban (66.2); driving module state to zero and the live macOS smoke (66.3, D-17).

### Carry-overs from Phase 66 execution (new for 66.1)
- **C-01: Build on what 66 shipped.** `src/backend/process/` (`createClock`, runner `run`/`spawnLongLived`/`runSync`/`openDetached`, tracked + long-lived registries, `createAppContext`), `src/backend/testUtils/` (`scriptedRunner`, `realRunner`, `fakeClock`, `captureLog`, `createTestContext`), and `bootstrap.ts` as 27 named steps via `bootSidecar(ctx)`. New boot-built objects (stores, managers) are added as boot steps / context fields, not module-level singletons. Sidecar tests boot through `bootFresh()` (with `reuseRegistry` for suites that configure mocks pre-boot — see 66-06-SUMMARY).
- **C-02: Fix runner review findings before callers depend on them.** 66.1 is the first phase where production code calls the runner, so `66-REVIEW.md` WR-01 (`run()` can hang forever after a timeout kill when a grandchild holds the pipes), WR-02 (truncation can splice discontinuous output) and WR-03 (win32 `killPid` always reports success; `runSync` has no `maxBuffer`) must be fixed — with tests — before or in the plan that first migrates a production caller (`spawnAsync` / launcher).
- **C-03: WR-07 belongs here.** The `removeLegacyZoomData` boot step reads `platformApi.app.getPath('userData')` instead of `ctx.paths.userData`. Fix as part of moving boot consumers onto the context.
- **C-04: The deferred late-log leak.** `registerDownloadQueueFlows()` schedules a bare `setImmediate` auto-resume notice at import of `./handlers`, which outlives per-case boots ("Cannot log after tests are done", see 66 `deferred-items.md`). 66.1 converts flow registrations to `createX(deps)`/boot-time registration, so make that notice part of a bounded boot step (or the injected clock) and remove the leak; do not silence the console.
- **C-05: Ratchet hardening is optional here.** WR-04 (shard edits can raise the ratchet; no compare against `origin/main`), WR-05/WR-06 (child_process / jest.mock counting bypasses) and IN-02 (loose census floors) are gate-hardening items. Plan them only if cheap; otherwise leave them for 66.2, which owns the `child_process` ban.
