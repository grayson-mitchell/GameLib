## Summary

Phase 66 shipped the leaf (`process/`), the fakes, the ratchet (`pnpm backend-di-ceilings`, 44 shards) and an ordered 27-step boot. 66.1 is the first phase that spends it. Measured now: **16 store modules (950 lines)** with 34 importers for steam alone; **39 code consumers of `libraryManagerMap`** plus 7 files that only mention it in comments (the roadmap's 46 is a grep count; **there is no `gameManagerMap`** in the tree, game objects come from `libraryManagerMap[runner].getGame(id)`); **25 `*Registration.ts`** (22 flow files = 7,429 lines, plus `depotHostRegistration`, `devEpicCookieSweepRegistration`, `storeRegistration`); **5 spawn sites in `launcher.ts`** and 31 `spawnAsync` call sites in 14 files. Phase 73 is complete and its TS depot files are already gone, so **no 66.1 file sits on a D-14 exemption list** and the ceilings carry zero `rust-overlap` entries.

Three findings change the plan. (1) **The runner is not yet a drop-in for the launcher.** WR-01 is real and I reproduced the Node semantics (`exit` at 205 ms, `close` at 4,008 ms while a grandchild held the pipes); the same fix also gives `runWineCommand`'s `resolveOnExit` its drain-grace behaviour, so one mechanism serves both. WR-02 as written **cannot occur in the current code** (`outBytes` is incremented even for a dropped chunk, so no later chunk can fit); pin it with a regression test and a one-line clarity fix instead of a behaviour change. The runner also lacks things the launcher needs: an explicit no-timeout opt-out (installs, game launches and GOG installers run for hours; D-10's `spawnLongLived` does not fit because it registers teardown by *id* and returns no captured output), `ChildHandle` exit-state accessors (`knownFixesRegistry.ts:496` reads `child.exitCode`/`signalCode`), and scripted-runner support for `onSpawn`/abort/hold. (2) **`libraryManagerMap` consumers sit in a 194-file import cycle** with `launcher.ts`, `utils.ts`, `logger`, `config`; the existing code breaks it with six dynamic `await import('backend/storeManagers')` sites. The safe cutover is expand/contract (identity facades first, convert consumers once, flip construction last), not family-at-a-time. (3) **The ratchet forbids new test files that call `jest.mock`** ("new violation ... no baseline entry"), so characterization tests for the not-yet-injectable launcher must extend existing mock-bearing files or use real children, never add mocks.

**Primary recommendation:** 18 plans in 5 waves: runner/characterization/boot-handlers first (3 disjoint plans), identity facades on `AppContext` second, consumers converted once each (registrations, non-manager consumers, launcher factories, per-store managers, `spawnAsync`/`handleExit`) third and fourth, then contract plans that flip store and manager construction and delete `trackedChildren`/`longLivedChildren`, ending in a human-verify live-launch checkpoint.

### Pattern A: expand/contract cutover (recommended; A3)
**What:** D-15 says "no module touched twice", but the research for 66 already conceded it is hard here, and a big-bang flip of the 39 consumers cannot stay green. Ratchet rules also forbid a transitional module-level `let` binding (a new violation fails the gate).
1. **Expand (one plan):** add `ctx.stores` and `ctx.managers` as boot-built *identity facades*: `createStores(deps)` returns the existing module singletons grouped by family; `createStoreManagers(deps)` returns the existing `libraryManagerMap`/`storeLaunchHooks`. No consumer changes, ratchet-neutral (a `const` whose literal contains `new` is not counted), no `let`.
2. **Convert consumers once each**, in groups, each file receiving stores + managers + runner + command-runner slices in a single touch (tests stop mocking `backend/storeManagers` and `*/stores`, lowering `jestMock`).
3. **Contract (two small plans):** turn each `stores.ts` into a real `createXStores(deps)` and delete the singletons; move `new XLibraryManager(deps)` into `createStoreManagers` and delete the `libraryManagerMap`/`storeLaunchHooks` exports. At that point no consumer imports them, so contract plans touch only the owning files + shard.
Moduleshard lowering happens in the contract plans (48 stores sites + `typed_store.ts` registry); `jestMock` lowers in the consumer plans.

### Pattern B: late-bound map for the manager cycle
Managers need siblings (`libraryManagerMap['legendary']` is used inside `gog/library.ts:1691`, `utils.ts`, etc.). `createStoreManagers` allocates the `Record<Runner, LibraryManager>` object first, passes that object by reference as `deps.libraryManagers` to each constructor, then fills it. Constructors must not dereference siblings, only methods at call time. Mirrors the existing "only dereferenced inside functions" safe-cycle comments (`launcher.ts:46`).

### Pattern C: split launcher.ts along the dependency line
`callRunner`/`runWineCommand`/`getWinePath`/`runScriptForGame` need only `runner` (plus `libraryManagerMap['legendary'].commandToArgsArray` at `launcher.ts:2042`, one logging helper: pass a `commandToArgsArray` function). `launchEventCallback`/`prepareLaunch`/`prepareWineLaunch`/`launchCleanup` need managers and `storeLaunchHooks` (7+7 refs). Managers import the first half (no cycle); registrations and `protocol.ts` import the second half.

### Anti-patterns to avoid
- **New test files that call `jest.mock`:** the gate fails with "new violation: <file> has N (jestMock) and no baseline entry". Also do not dodge with `jest.doMock` (WR-06 hole, not counted); that hides, not removes, the coupling.
- **A transitional `let`/settable binding** to bridge `libraryManagerMap`: ratchet-visible violation.
- **`getContext()` or whole-`AppContext` parameters:** D-01.
- **Two construction paths for managers** (import-time and boot) alive at once after the contract plan.
- **Importing `backend/utils`/`config`/`logger` into `process/`:** `runner-is-a-leaf` fails.

## Runner findings (C-02) `[VERIFIED: source read + real-process experiment]`

Current `process/runner.ts` (302 lines) facts the plans depend on:
- `run()` tracks every child (`track ?? {runner:'runner', key: cmd}`), unrefs child + stdio, SIGKILLs from an unref'd clock timer, settles on `close` (or on `exit` too if `resolveOn:'exit'`), rejects only on spawn `error` (ENOENT), treats `AbortError` as `aborted: true`.
- `positiveFinite(timeoutMs)` rejects `Infinity`: there is **no way to run without a timeout**.
- `ChildHandle` is `{pid, kill}` only. `common/types.ts` still types `CallRunnerOptions.onOutput(output, child: ChildProcess)` and `WineCommandArgs.onSpawn(child: ChildProcess)`; `knownFixesRegistry.ts:432,496-500` reads `child.exitCode`/`child.signalCode` and calls `child.kill('SIGKILL')`; `sharedRedistInstall.ts:358` passes `onSpawn: unrefWineChild` (redundant once the runner unrefs; delete). Other `onOutput` consumers read only the chunk.
- `windowsHide` defaults to `true` (launcher spawns pass nothing, i.e. false): a benign Windows difference (no console flash); note it in the launcher plan.

### WR-01 (real) — reproduce and fix
Experiment: `spawn('sh',['-c','sleep 4 & wait'])`, `kill('SIGKILL')` at 200 ms -> `exit` at 205 ms, **`close` at 4,008 ms**. With a daemonized grandchild `close` never comes and `run()` never resolves, defeating D-10. Fix design (one mechanism, two users):
1. After `exit` (when `resolveOn === 'exit'`, or `timedOut`, or `aborted`), arm a `DRAIN_GRACE_MS` (250, matching `runWineCommand`'s grace) clock timer; if `close` has not fired, `stdout.destroy()`/`stderr.destroy()` and `finish(code, signal)`; clear the timer on `close`. Use `deps.clock` (unref'd).
2. Result carries the exit code even when the drain was cut short; output after the grace is dropped (exactly `launcher_runWineCommandResolveOnExit`'s pinned WR-01 behaviour), which proves `runWineCommand` can become a thin caller.
3. Tracked registry untracks on `close`/`error`; for the cut-short path also untrack on `exit` (otherwise `killTracked` can SIGTERM a recycled PID).
**How to test under fake HOME:** use `createRealRunner()` (pinned `createFakeHomeProfile()` env; no real-profile arm needed, the defect does not depend on a populated profile). Child: `process.execPath -e` that spawns a grandchild `process.execPath -e "setTimeout(()=>{},5000)"` with `stdio:'inherit'` and itself idles. Assert `run(..., {timeoutMs: 200})` resolves `timedOut: true` in well under 2,000 ms (measured elapsed with `Date.now()`; real clock). A second case: `resolveOn:'exit'` with a grandchild resolves after ~grace, not after 5 s. The grandchild exits on its own after 5 s so nothing leaks (it is spawned by the test child, not the jest process). Add a scripted-runner twin only for the option plumbing, not the timing.

### WR-02 (as written, not reproducible in current code)
`capture()` increments `outBytes`/`errBytes` even for a dropped chunk, so once any chunk is dropped `outBytes + bytes <= maxBytes` can never be true again; the "splice" in the review cannot happen. Experiment: `cap('aaaa'); cap('B'x20); cap('c')` with max 10 -> `"aaaa"`, `truncated: true`. Plan: add the regression test (chunks 4 B, 20 B, 1 B with `maxBufferBytes: 10` against the real runner via `node -e`, assert stdout is exactly the first chunk and `truncated === true`) and a small readability change (explicit `stopped` flag per stream); do not change behaviour. Record in the plan that the review item was verified and found not reproducible, so nobody "fixes" it into a different truncation rule.

### WR-03 (real, partly testable on macOS)
- `killPid` on `win32` discards the `taskkill` result and returns `true`; make it `return r.code === 0 && !r.error`-equivalent. Test on any host: build a runner with `platform: 'win32'` and the real `runSync`; `taskkill` does not exist on macOS/Linux so `code` is `null`/ENOENT, so `killTracked` must now return 0 and log the warning. - `runSync` has Node's 1 MiB default `maxBuffer`: `spawnSync(node,['-e','process.stdout.write("x".repeat(2e6))'])` reports ENOBUFS. Pass `maxBuffer: DEFAULT_MAX_BUFFER_BYTES` and report `truncated`/error clearly. Test with that 2 MB case through `createRealRunner().runner.runSync`.

## Common Pitfalls

### Pitfall 1: new `jest.mock` in a new test file fails the gate
**What goes wrong:** `node meta/backendDiCeilings.cjs` -> "new violation: ... (jestMock) and no baseline entry". **Avoid:** new tests take injected fakes (`createTestManagers`, `createTestStores`, scripted/real runner); extend existing files for pre-injection characterization. **Related:** a plan that removes a mock must lower that file's entry *in the shard that holds it* (`grep -l '<path>' meta/backendDiCeilings/*.json`) in the same commit; deleting a test file removes its entry (stale entries fail).

### Pitfall 2: manager cycle at construction
Managers reference siblings inside methods; a constructor that dereferences the map during `createStoreManagers` sees an unfilled object. Use Pattern B and add a unit test that constructs managers and asserts no constructor read the map.

### Pitfall 3: duplicate store registration across factory calls
`typed_store.ts` keeps the first instance and writes to stderr on duplicates. The registry must be per-boot (see Inventory 1); add a test that two `createStores()` calls yield independent registries and no stderr write.

### Pitfall 4: `launcher.ts` is on the Rollup/`Module._load` path
`utils.ts:106` documents that a bare `require('./storeManagers')` breaks the packaged bundle. Use static imports or injected deps only; verify with `pnpm build:sidecar && pnpm smoke:sidecar` (jest cannot catch bundle breakage).

### Pitfall 5: `handlers.ts` moves from import time to a step
Anything that relied on "registered before step 1" (tests importing `./handlers` directly, `storeLayer.test.ts`; `skipInitialTraySync` guard; the Module._load comments) changes. The step must precede `rpc-server`. Cover with the bootstrap wirings/source-shape tests and a "channels registered before the first frame is served" case.

### Pitfall 6: unbounded runner use changes the exit contract
The runner unrefs every child and pipe. `callRunner` children used to be ref'd (they could, in principle, delay sidecar exit); now they cannot. That is the intended D-11 semantics, but the sidecar must still honour stdin-EOF teardown (`teardownAll`, `killAllTracked`) before exit; the human-verify plan checks no orphaned `legendary`/`gogdl`/`nile`/`wine` after quit.

### Pitfall 7: `ChildProcess` retyping fan-out
`common/types.ts` (`CallRunnerOptions`, `WineCommandArgs`), `knownFixesRegistry.ts`, `bridgeKnownFixes.ts`, `sharedRedistInstall.ts` and `signInProbe` all touch the child type; do the retype in the same plan as the runner capability change that makes it possible, and keep `common/types.ts`'s `ChildProcess` type import only if something still needs it.

### Pitfall 8: knip baseline vanish-fail
Deleting `trackedChildren.ts`, `longLivedChildren.ts`, `getGame`, `execAsync` re-exports or old `stores.ts` exports can make baseline findings vanish; `meta/knipRatchet.cjs` fails on a vanished finding, so lower `meta/knip-baseline.txt` in the same commit. Exports consumed only by `require()` in tests need `@public` (66-08 lesson).

### Pitfall 9: `steam/library/*` and Phase 75
Seven files in the Phase-75-deleted local scan import `steam/stores` (`library/{index,installPollOnce,installRoot,macArch,refresh,resumeBreadcrumbs,uninstallPolling}.ts`); files reading VDF/ACF/shortcuts there are `acfState`, `installedMap`, `installRoot`, `resumeBreadcrumbs`, `manifestFlags`, `runningPoll`. They cannot keep importing a deleted `steam/stores.ts`, so apply the **minimal** change (receive the steam stores slice through `SteamLibraryManager` deps / a parameter) and do not add `rust-overlap` sanctioned entries (they have no module state beyond `pollState`/`restartHold`, 66.3's; 66-RESEARCH open question 1 was resolved by the user: convert `runningPoll` and poll-state files).
