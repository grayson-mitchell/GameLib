<objective>
Give Tauri a real tray, and delete every tray affordance it cannot honour.

Purpose: `src/backend/tray_icon/tray_icon.ts` is a whole subsystem — tray menu, recent-game
quick-launch entries, show/hide, dock menu, icon-colour and language rebuilds — that is entirely
dead under Tauri. `src/frontend/screens/Settings/components/TraySettings.tsx` is a live settings
panel the user can toggle that changes nothing. That is the sharpest example of the rule this phase
establishes: **nothing ships an affordance it cannot honour.**

The scope correction that shapes this plan: CONTEXT.md says "implement it", but a bounded tray
already exists in Rust and its own comment states exactly what it excludes. This is a delta, not a
greenfield subsystem.

Output: an extended Rust tray, a reachable About window, and a `TraySettings` panel that either
works or is gone.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| tray menu item id -> launch dispatch | a `recent:<appName>` string crosses from a menu id into a game-launch call |
| Rust shell -> Node sidecar | the launch intent and the About signal cross the IPC boundary |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-35-20 | Tampering | An `appName` parsed out of a `recent:` menu id and passed to a launch path without validation. Menu ids are constructed by this code, but the recent-games titles/appNames come from library data, so the id string is not wholly trusted input | mitigate | The `recent:` id parser is a named function with a `#[cfg(test)]` test including a malformed-id rejection case. It must reject anything that is not a plain appName, mirroring the validation discipline `protocol_url_arg()` established for the deep-link surface |
| T-35-21 | Elevation of Privilege | Routing an internal tray click through `gamelib://` and the OS-level deep-link registration would widen the trust boundary — any process able to emit a `gamelib://` URL would reach the same dispatch | mitigate | Explicitly rejected in the constraints and asserted by an acceptance criterion (`gamelib://` count unchanged in `main.rs`). The click stays in-process |
| T-35-22 | Denial of Service | A tray build failure taking down `.setup()` and making the app unlaunchable | mitigate | T-34.1-22's non-fatal discipline is preserved and re-asserted: an `unwrap()`-count acceptance criterion measured before and after, plus a live forced-failure check in Task 3 step 6 |
| T-35-23 | Information Disclosure | Recent-game titles rendered in an OS-level tray menu are visible to anyone at the screen | accept | Equivalent to the Electron build's existing behaviour and to Steam's own tray. No credential or account identifier is exposed; the user controls what is in their library |
| T-35-24 | Repudiation | A `TraySettings` toggle left in the UI that the tray does not honour — the user believes a setting took effect and it did not | mitigate | D-05's rule applied mechanically from Task 1's explicit HONOURED / NOT HONOURED list, all three registration sites removed together, and re-checked live in Task 3 step 5 |
| T-35-SC | Tampering | npm/cargo installs | mitigate | This plan adds NO dependency — the `tray-icon` Cargo feature is already enabled.
