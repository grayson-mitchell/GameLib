<objective>
On Windows, Play on a Steam game drops back to "Play" a moment after the click, and Playing only
appears once the a9g launch watch has found the game. After this plan the button holds
"Launching…" from the click until the watch detects the game running, when Playing and Stop
appear. If the game never starts within the watch's 90 s window, the watch sends `done` and the
button returns to Play.

This extends the a9g win32 install-folder watch rather than adding a second mechanism. The changes
are confined to `steamLaunchWatch.ts` and its tests: two sends, one flag, and a widened type.

Purpose: one launcher that shows the truth about what it launched, from the click onward.
Output: the extended watch, the updated a9g wire tests, and new unit and end-to-end cases.
</objective>

<decisions>
**Locked by the user (from the orchestrator brief and the re-plan request).**
- **L-01** On win32, for native Steam launches, keep `launching` from the click until the game is detected running (then `playing`, and Stop shows). Send `done` if it never starts within a bounded window. A failed hand-off is unchanged.
- **L-02** A `done` must never overwrite a `playing` that has already arrived.
- **L-03** Hold Launching only: no poller interval change, and no new fast-poll mode.
- **L-04** Timers come only from the injected clock and are unref'd. One wait per appId. A second Play must not stack timers.
- **L-05** Prefer extending a9g's win32 watch over a parallel mechanism, if that fits (P-02).
- **L-06** No frontend change unless it is needed (P-08).
- **L-07** Every `<verify>` runs `npx prettier --check` over exactly the paths the task writes. Jest runs only the touched suites, compared against a baseline.

**Planner decisions.**
- **P-01 Nothing is sent between the click and the watch's `playing`, and this corrects a9g's prose.**
  - Steam never reaches `launcher.ts`'s `launchEventCallback`. The sidecar `launch` handler and the
    `gamelib://` deep link both go through `dispatchSteamLaunch`
    (`sidecar/steamFlowRegistration.ts:336-365`, `protocol.ts:256-272`), and `launcher.ts:285-287`
    says so in a comment.
  - `launchDispatch.ts` sends no status. `handleLaunch` returns `{ status }` as the IPC *result*,
    not as a `gameStatusUpdate`.
  - a9g's PLAN (truths at lines 31-32) and SUMMARY ("Exact wire sequences") describe a "launcher
    `launching`, launcher hand-off `done` (unchanged since 9mj)". **No such frames exist.**
  - a9g's tests do not pin them either: C3, C4, C6 and C7 model only watch, poller and stop
    frames, which matches reality.
  - So today Launching shows only through the frontend's click latch, which is released in a
    `finally` when the IPC resolves (`GamePage/index.tsx:715-727`, `GameCard/index.tsx:772-786`).
    That is right after `openExternal`.
  - Record this correction in the SUMMARY. a9g's own artifacts are not edited.
- **P-02 Extend a9g's win32 watch. The earlier `steamLaunchHold.ts` design is withdrawn.** On
  win32 the a9g watch already has everything the hold needed:
  - It starts on every native hand-off, right after `openExternal` resolves. a9g removed both
    `isWindows` guards (`gameLaunch.ts:249` and `:284`), and G1/G2 pin this.
  - It takes the poller claim synchronously at start (`steamLaunchWatch.ts:143`), so the poller
    sends nothing for the appId while the watch lives. That removes the poller-versus-hold race
    the old design had to argue around.
  - It already owns the bounded start window (90 s, `startWindowMs`), one registry entry per appId,
    a relaunch path that arms no new timer (`noteRelaunch`), and the entry that Stop cancels.
  A separate hold that waited for poller reports would wait on a poller the claim keeps silent.
  As a result `gameLaunch.ts`, `steamLaunchedDeps.ts`, `runningPoll.ts` and `games.ts` all stay
  unchanged. The `sendStatus` closure in `steamLaunchedDeps.ts:56-57` already forwards any status
  to `sendGameStatusUpdate`, so only the interface type widens.
- **P-03 The start send (win32 only, new watch only).** Right after `deps.registry.set(appId, entry)`
  and `const releasePoller = win ? deps.pollerHold(appId) : undefined`, in the same synchronous
  block:
  - If `win` and `!deps.pollerReports(appId)`, set a local `launchingSent = true`, set
    `entry.shown = true`, and call `deps.sendStatus(appId, 'launching')` inside try/catch. On a
    throw, log a warning and carry on, so a failed send can never leave a registered watch without
    its loop and its claim release.
  - **Already running.** If `deps.pollerReports(appId)` is true, the poller has already shown
    `playing` for a game that was running before this Play. Send nothing (L-02). The search will
    re-send `playing` when it finds the game.
  - **The `already-watching` path is untouched**, so a second Play sends no second `launching`.
  - **Why `shown = true`.** On win32, `shown` now means "this watch owns a non-terminal status on
    screen". `SteamGame.stop()` (`games.ts:598-618`) sends its one `done` exactly when
    `cancelSteamLaunchWatch` reports `shown`, so a Stop during Launching ends cleanly. MainButton
    disables Play/Stop while launching (`MainButton.tsx:43-49`), so in practice this is reached
    only through a programmatic kill. It must still never leave the status stranded.
- **P-04 The terminal `done` when a watch shown Launching ends without reaching Playing.**
  - Add a local `playingSent`, set where the win32 search loop sends `playing`
    (`steamLaunchWatch.ts:239`).
  - In the `.finally` (lines 314-318), keep `releasePoller?.(doneSent || cancelled)` exactly where
    it is.
  - Directly after it, if all of these hold, call `deps.sendStatus(appId, 'done')` and log
    `appId <id>: not detected running; ending Launching`:
    - `win`
    - `launchingSent`
    - `!playingSent`
    - `!doneSent`
    - `!cancelled`
    - `!deps.pollerReports(appId)`
  - **Order matters.** release(false) runs first. If the poller already reads the appId, it sends
    `playing` itself (`runningPoll.ts:267-274`), and the `pollerReports` check in the same
    synchronous turn then suppresses the `done`.
  - The `done` must not touch `doneSent` or the release argument. The claim was released with
    `false`, so the poller resumes normally and sends `playing` later if the game starts after all.
  - **Exits this covers:**
    - the start window running out (90 s from the latest Play, which is the bound in L-01);
    - the 5-empty-scan bail when the poller has not read the appId yet;
    - no install folder;
    - an unexpected error in `run()`.
- **P-05 Relaunch during Launching.** a9g's `noteRelaunch` resets `origin` and arms no timer.
  Because `shown` is now true during Launching, it also sets `reassert`. Reset `reassert = false`
  where the search loop sends `playing`, so the tracking loop does not send a duplicate `playing`.
  The re-assert after a relaunch while the game is running (`shown` true in tracking) is
  unchanged.
- **P-06 Why the order is safe (L-02).**
  - From the synchronous claim until release, the poller sends nothing for the appId.
  - All of the watch's frames come from one sequential async flow, so `launching` comes before
    `playing`, which comes before `done`, by construction.
  - The only `playing` that can predate the watch is the already-running case, handled in P-03.
  - After release, either release(false) sends the poller's `playing`, and P-04 suppresses the
    fallback, or release(true) drains, as a9g built it.
- **P-07 Scope fences.**
  - **macOS/Linux.** `runPosix` and every posix send are untouched. The same drop-back exists on
    macOS/Linux rungameid launches, but it is outside this Windows task.
  - **No new timer, probe or interval.** The 2000 ms reg-gated search, the 500 ms liveness check
    and the 90 s window are a9g's.
  - **Files that stay byte-identical:** `runningPoll.ts`, `gameLaunch.ts` (995 lines against the
    1000 ceiling), `steamLaunchedDeps.ts`, `games.ts`, `stopSteamLaunchedGame.ts` and every
    frontend file.
- **P-08 No frontend change (L-06).** Every part of the frontend already handles a backend `launching`:
  - `releasesPlayClicked` releases the latch on `launching` (`GamePage/playClickedLatch.ts:10-12`).
  - GamePage renders `launching: isLaunching || playClicked` (`GamePage/index.tsx:184`, `:433`).
  - GameCard derives Launching from the status (`GameCard/constants.ts:33`).
  - `libraryState` keeps `launching` until `done` or `error` (`state/libraryState.ts:285-308`).
  - No frontend timer reverts it. ConsoleMode's `STEAM_SAFETY_MS` only dismisses its overlay.
- **P-09 Known limit, kept bounded.** For a game whose install folder cannot be resolved (the ACF
  or library list is unreadable), the watch ends at once. The wire is then `launching`
  immediately followed by `done`, which matches today's drop back to Play, and the poller reports
  the game later because the claim is released with `false`. Holding Launching there would need a
  reg-only wait loop, which this plan does not add.
</decisions>
