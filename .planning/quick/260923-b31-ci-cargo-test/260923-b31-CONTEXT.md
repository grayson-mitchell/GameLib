# Quick Task 260923-b31: Add a CI job that runs `cargo test` for the Tauri shell - Context

**Gathered:** 2026-09-23
**Status:** Ready for planning

<domain>
## Task Boundary

Action `.planning/todos/pending/2026-09-22-windows-rust-tests-not-run-in-ci.md`: no workflow in
`.github/workflows/` runs `cargo test` or `cargo check` on any OS, so a real compile break in
`src-tauri/src/main.rs`'s `#[cfg(test)] mod tests` sat on `main` unnoticed until Phase 46 research
ran the harness by hand on Windows.

Add a `cargo test --bin gamelib-shell` job to CI. In scope: the workflow file, and moving the todo
to `completed/`. Out of scope: changing any Rust source, and flipping the GitHub branch-protection
"required check" toggle (repo-admin setting, not a file in this repo).

</domain>

<decisions>
## Implementation Decisions

### OS matrix
- `windows-latest` and `macos-latest`. These are the two legs with zero coverage today: the
  `#[cfg(windows)]` named-mutex/named-pipe single-instance FFI, and the
  `#[cfg(target_os = "macos")]` `store_embed_*` / objc2 / WKWebView surface.
- Ubuntu is deliberately excluded. `src-tauri` needs `libwebkit2gtk-4.1-dev`, `libappindicator3-dev`,
  `librsvg2-dev` to build (see `release-tauri.yml:93-97`), and the only Linux-specific Rust code is
  the `cfg(unix)` `libc::kill` arm, which the macOS leg already compiles.

### Renderer prerequisite
- Run the real `pnpm exec vite build`, reusing `.github/actions/install-deps`, exactly as
  `release-tauri.yml:166-168` does.
- Required, not optional: `src-tauri/src/main.rs:9813` calls `tauri::generate_context!()`, which
  embeds `frontendDist` (`../build/renderer`, per `tauri.conf.json`) at compile time. Without that
  directory the crate does not compile at all, tests included.
- A stub `build/renderer/index.html` was considered and rejected: it is a fake input, so a real
  asset/codegen break would pass the gate and only surface at release time — the
  green-check-proving-nothing pattern this project keeps stamping out.

### Claude's Discretion
- **Placement**: a new `.github/workflows/rust-test.yml` rather than a job inside `test.yml`.
  `test.yml` is a single ubuntu-only Node job; grafting a two-OS matrix that needs a Rust toolchain
  and a vite build onto it would make both harder to read, and a separate file lets the Rust gate
  carry its own `paths` filter and its own name in the checks list.
- **Trigger shape**: mirror the other workflows (`push` to `main`/`stable`, `pull_request`,
  `workflow_dispatch`, plus the `concurrency` cancel-in-progress group), so the new gate behaves
  like every existing one.
- **Toolchain/cache actions**: `dtolnay/rust-toolchain@stable` and `swatinem/rust-cache@v2` with
  `workspaces: './src-tauri -> target'`, matching `release-tauri.yml:170-177` verbatim rather than
  introducing a second convention.

</decisions>

<specifics>
## Specific Ideas

Measured before planning, on this Windows machine, 2026-09-23:

- `cd src-tauri && cargo test --bin gamelib-shell` → `234 passed; 0 failed; 2 ignored`. The
  `store_embed_wire_contract_*` break the todo describes is already fixed, so the new job lands
  green rather than red on day one.
- `gamelib-shell` is the crate's only target (binary, no lib), so `cargo test --bin gamelib-shell`
  and a bare `cargo test` select the same set. The explicit `--bin` is kept because it is the exact
  command the todo names and it fails loudly if a lib target is ever added without thought.

</specifics>
