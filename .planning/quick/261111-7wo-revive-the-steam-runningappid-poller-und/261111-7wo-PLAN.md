<objective>
Revive the global Steam RunningAppID poller under Tauri. It is built at boot (`createSteamProcesses`)
but started only from `SteamLibraryManager.init()`, which nothing calls since the Tauri move, so
Windows Steam launches (the `steam://launch` verb, which `steamLaunchWatch` does not cover) never
reach Playing. Start it from a dedicated sidecar boot step and stop it at stdin EOF. Pin how it
coexists with `steamLaunchWatch` in exact-frame jest tests, and record the runner/DI decision.

Purpose: Windows Steam titles launched from GameLib show Playing, and return to Play when the game
quits. macOS/Linux keep the per-launch watch, and the poller and the watch never fight. Windows
Stop is out of scope and gets captured as a todo only.

Output: a boot step plus EOF stop (code), a tracer boot test, coexistence and EOF unit tests, and
corrected comments. The source todo gets a status note and stays pending for the live gate, and a
new pending todo records the Windows Stop gap.

Not closed by this plan: the live gate is operator-run. On Windows, launch a Steam title from
GameLib: the card shows Playing, then returns to Play after quitting from inside the game. On the
Mac, WazHack 264160 still gets exactly one Playing and one Done. The source todo stays
`ready: live-gate` until that passes.
</objective>

<decisions>
Planner decisions (quick task, no CONTEXT.md). Every task cites these IDs.

- **P-01 Runner/DI: no move needed; the todo's premise is stale.** `readRunningAppId()` already
  probes through the injected `ProcessRunner.run` (`deps.runner.run`). `steamProcesses.ts` wires it
  as `readRunningAppId({ runner }, platform)`, and Phase 66.2 plan 06 rebuilt its tests on a
  scripted runner. `runningPoll.ts` imports no `child_process` and has no `spawnSync` or
  `execFileSync`. The only sync I/O left is the `graceful-fs` read of `registry.vdf` on
  macOS/Linux, which is a file read and not a spawn, so no ceiling counts it. Smallest change:
  touch nothing in `runningPoll.ts`. The ceilings stay green because this plan adds no
  `child_process` site, no counted module-level state and no `jest.mock` call. Baseline measured at
  planning time: `backend-di-ceilings: PASS moduleState=233 (116 files) childProcess=1 (1 files)
  jestMock=2363 (447 files) sanctioned=3`.
- **P-02 Start owner: a dedicated boot step, `'steam-running-poll'`.** Place it directly after
  `'installed-json-watcher'` and before `'playtime-lock-clear'`. That is after `'rpc-server'` and
  `'transport'`, so a frame always has a bound transport, and before READY. `start()` is
  registration only, and the first tick lands 5 s later. It is an idempotent `start()` with the
  default 5000 ms, wrapped in try/catch with `logWarning`, so the poller can never fail boot.
  - No `JEST_WORKER_ID` guard, unlike `'installed-json-watcher'`: the timer comes from `ctx.clock`,
    which is a fake clock in every test boot, so nothing real is armed. A guard would also make the
    step untestable.
  - The dead `start()` call in `SteamLibraryManager.init()` is removed, so the boot step is the
    single owner.
- **P-03 Stop: at stdin EOF, through a new required dep of `releaseOnStdinEof`
  (`stopRunningGamePoll`).** It gets its own try/catch and runs before
  `SteamUser.releaseForShutdown()`.
  - The poller is NOT a loop-holder: its timer is unref'd. The stop exists so a post-EOF tick
    neither spawns reg.exe/ps nor writes a gameStatusUpdate frame to a stdout whose peer is gone.
    Document it that way, not as a fourth holder.
  - Quit needs no `quitHandler` change. The routed quit ends in `exit()`, then `shutdown_child()`'s
    process-group SIGTERM, and the shell closing stdin; the unref'd timer holds nothing.
  - Do NOT change the existing `'[sidecar] stdin closed: releasing Steam CM session, ...'` log text.
    It is quoted by `.planning/debug/resolved/sidecar-survives-force-quit.md`, `73-UAT.md` and the
    261110-9w2 plan.
- **P-04 Coexistence: pin exact frames, and add no cross-sender dedupe.**
  - The duplicate: where both senders can report (Linux reaper scan, or a Mac Steam that ever writes
    RunningAppID), the watch shows `playing` at its first 2 s scan. The poller's first 5 s tick then
    sends a second `playing`, the watch sees `pollerReports` and ends quietly with no `done`, and
    the poller sends the single `done`.
  - The frontend already drops the duplicate: `libraryState.handleGameStatus` returns early when
    status, context and managedBySteam are unchanged.
  - Why not dedupe: a shared "last status sent" across the poller and the watch would suppress a
    legitimate `playing` after a `done` sent by another route (Stop, `bottleProcessMonitor`, the
    launcher). That trades a harmless wire duplicate for a new defect class.
  - Per platform, the wire carries exactly one `playing` and one `done` on Windows (the watch
    returns `unsupported-platform`) and on today's macOS (the poller reads 0, so the watch is the
    sole sender).
- **P-05 Test double:** `createTestSteamProcesses().runningPoll` becomes inert by default, reusing
  `createInertSteamProcesses().runningPoll`. This mirrors the existing `macSteamOffline` precedent
  ("Inert, not unscripted: every boot pays the owed goonline through this instance"), because every
  boot now calls `start()` and every EOF calls `stop()`. The unscripted proxy would otherwise throw
  inside "a boot with every service prebuilt never reports missing services". No test relies on the
  unscripted throw (grep for `steam running poll` finds only the definition).
- **P-06 Scope:** Windows Stop is out of scope. `SteamGame.stop()` (`games.ts:527`) is a no-op for
  these launches because `findPidsRunningFromFolder` returns `[]` and `runningFromFolder` returns
  false on win32. It is noted only, as a new pending todo, with no code. The live gate is
  operator-run, and the source todo is not closed by this plan.
</decisions>
