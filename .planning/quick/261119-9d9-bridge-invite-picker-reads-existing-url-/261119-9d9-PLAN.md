<objective>
Stop the bridge invite picker from asking its own webview for its URL. When the `bridge-invite` window already exists, `rpc_bridge_invite_picker_open` (`src-tauri/src/login_window/invite_picker.rs:127-139`) currently reads the window's live URL and joins the new path onto it. On macOS, wry 0.55.1 `url_from_webview` unwraps `WKWebView.URL` on the main thread. That URL is nil when the window's first navigation failed (for example the Vite dev server was down), so the shell panics. The panic happens inside wry's event-loop handler, so our `.and_then`/`.map_err` chain cannot catch it. This is the same class of crash as G-47-9 (`.planning/debug/offline-stores-tab-crash.md`, fixed for the store embed by plan 47-14). That debug session found this site, and plan 47-14 left it unfixed.

Fix: build the reuse URL the same way the create path's `WebviewUrl::App(path)` is resolved, by recomputing the base from the same app config (the todo's "recomputed from the same config" option). Never read it from the webview.

Purpose: close todo `2026-11-18-invite-picker-url-read-panics-on-failed-first-load.md` (severity minor, platform macos, ready code).
Output: two pure helpers in `invite_picker.rs`, the reuse branch rewired to them, three regression tests (a base-resolution matrix, a create-path parity check, and a source gate proving the live getter is gone), and the todo moved to `completed/`.
</objective>

<design_decisions>
Claude's discretion (quick task, no CONTEXT.md). Recorded so the executor does not re-decide them.

1. **The base is recomputed from config, not stashed at open time.** A stash would still need the resolved base, and that cannot be obtained without either asking the webview (the bug) or computing it (this fix). So compute it, in one pure function that mirrors tauri-2.11.5 exactly. `AppManager::get_app_url` (`~/.cargo/registry/src/index.crates.io-1949cf8c6b5b557f/tauri-2.11.5/src/manager/mod.rs:339-368`) returns `build.dev_url` under `cfg(dev)`. Otherwise it returns `build.frontend_dist` when that is a `FrontendDist::Url`, and otherwise `tauri_protocol_url(https)`: `http(s)://tauri.localhost` on Windows/Android, `tauri://localhost` elsewhere. The `WebviewUrl::App` arm (`src/manager/webview.rs:444-459`) then joins the path onto that base, unless the path is exactly `index.html`, which ours never is. `cfg(dev)` inside tauri is `!custom-protocol` (`tauri-2.11.5/build.rs:255-258`). That is the same signal as the public `tauri::is_dev()` (`src/lib.rs:308-310`), so `tauri::is_dev()` is the exact input. `https` is false because the invite builder never calls `use_https_scheme` (no call anywhere in `src-tauri/src`). Mobile `PROXY_DEV_SERVER` is irrelevant (desktop only).
2. **The create path stays `WebviewUrl::App(path.into())`.** It works today and lets tauri resolve the URL itself. Switching it to `WebviewUrl::External` would change a proven path for no gain. Instead, parity between the two paths is pinned by a test that asserts the literal URLs tauri's App arm produces.
3. **How the regression proof works, and how it differs from 47-14.** 47-14's read was *conditional*: it was allowed once a page had finished loading. There, a call-counting injected reader was the right tool. Here the read is removed *entirely*, so the matching proof has two parts. (a) The reuse core `bridge_invite_reuse_url` receives its URL source as a parameter (the config-derived base) and is never handed a window, so it cannot ask one. The tests drive it with injected bases. (b) A source gate asserts that the file's production region contains no live URL getter call at all. That catches a reintroduction anywhere in the file, including outside the core, which a counter could not. The mutation check (put the live read back, watch the gate go red, revert) is the guard-sensitivity evidence, the same way 47-14 recorded its RED.
4. **No `unwrap`/`expect` in production code of this module.** The constant protocol URLs are parsed with the error mapped to `bridge_invite_picker_open:build-failed:{e}`, the error prefix the reuse branch already uses.
</design_decisions>
