## Decisions made at planning time (with reasons)

- **POST from the renderer (Tauri webview), not the Node sidecar.** Web3Forms API reference
  (docs.web3forms.com/getting-started/api-reference, fetched 2026-10-31) says: "Server side
  usage requires paid plan + server IP whitelisting", and recommends browser/client-side use.
  A sidecar POST is server-side, so it would fail on the free plan. Also, the sidecar would add
  an IPC channel for no gain.
- **Access key = one exported constant** `WEB3FORMS_ACCESS_KEY` in
  `src/frontend/helpers/reportProblem.ts`, committed as `''`. The repo has no renderer
  `import.meta.env` usage anywhere (grepped; vite's `envPrefix` is configured but unused), and
  the frontend jest/ts-jest setup has never been exercised against `import.meta`. A plain
  constant is testable and fits. Web3Forms access keys are public by design (they ship in
  public HTML forms), so committing one later is acceptable. Do NOT invent a key.
  `isReportingConfigured()` returns true only if the trimmed key matches a UUID regex.
- **Reuse existing diagnostics surfaces; no new collector or IPC:**
  `window.api.systemInfo.get(true)` (returns `SystemInformation`: OS, versions; the source the
  Settings -> System Information "Copy to clipboard" button uses),
  `window.api.getHeroicVersion()` (app version), `window.api.getLogContent({})` (GameLib app
  log), `window.api.getLogContent({ appName, runner })` (game log, the same call LogSettings
  makes), `window.api.isNative({ appName, runner })`, and for Steam games
  `window.api.getSteamBridgeRoute(appId)` (returns `SteamBridgeRouteVerdict.route`:
  `'bridge' | 'bottle' | 'not-eligible'`).
  Do NOT reuse the inherited `uploadLogFile` flow. It uploads logs publicly and unredacted.
- **Launch route mapping:** steam + isNative -> `native`; steam otherwise -> `bridge` /
  `bottled` / `not-eligible` from the verdict; non-steam + isNative -> `native`; non-steam
  otherwise -> `compatibility layer`. Any thrown error -> `unknown`. Collecting diagnostics
  must never block sending.
- **Log size bound:** keep the last `REPORT_LOG_MAX_LINES = 300` whole lines, redact, then cap
  to `REPORT_LOG_MAX_BYTES = 24 * 1024` at a line boundary (keep the tail). There are at most 2
  logs, so diagnostics stay under ~50 KB. Reasons: the failure is almost always at the tail.
  The report arrives as an email the operator has to read. Web3Forms does not document a
  request size limit, so keep requests small. Cutting by whole lines BEFORE redaction means a
  token is never split at the cut, so a half-token cannot slip past the patterns. Capping
  AFTER redaction means placeholder length changes cannot push the payload over the limit.
- **The user's free text is sent as typed (not redacted).** Those are their own words, and
  redacting would mangle game names and their email. The "What will be sent" preview shows
  the diagnostics exactly.
- **Placement:** a NavItem in the Settings panel next to Log / System Information, routed as
  `/settings/report` through the existing `Settings` `type` param. This needs no new route or
  dialog plumbing.
- **CSP is live only in a bundled build** (see the doc comment in `tauriConf.test.ts`:
  `tauri dev` serves through devUrl, so no policy applies). The live gate must therefore run
  `pnpm tauri:dev:packaged`, not `tauri dev`.
