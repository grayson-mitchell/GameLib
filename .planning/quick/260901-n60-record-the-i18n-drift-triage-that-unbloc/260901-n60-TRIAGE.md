## Root causes

**Bucket T — the parser's input glob includes test files.**
`i18next-parser.config.js` sets `input: ['src/**/*.{ts,tsx}']`, which matches 343
`__tests__` files. Test-local i18n keys are therefore extracted into shipped catalogs:

- `translation:bottle.setup.done = "INLINE-DEFAULT-SENTINEL"` —
  `src/frontend/screens/Game/GamePage/components/__tests__/labelSuiteI18nCensus.test.ts:118`.
  Note the production call site at `SteamBottleSetup.tsx:499` uses the same key with the
  real default `'Done'`; the test's sentinel default wins because the test file sorts later.
- `translation:no.such.key.anywhere = "fallback"` — same test file, line 123, a deliberately
  nonexistent key asserting `t()`'s fallback behaviour.
- `gamelib:__wr16spec.plural`, `gamelib:__wr16spec.typo` —
  `src/frontend/screens/Library/components/FilterChipRow/__tests__/chipLabels.realI18next.test.ts`.

Fix shape: exclude `**/__tests__/**` (and `*.test.ts{,x}`) from the parser `input` glob.

**Bucket P — `{{count}}` triggers plural-suffix generation.**
The parser sees `{{count}}` and emits `_one`/`_other` variants. The base keys already exist
in `en/translation.json`. This is the same reserved-interpolation behaviour that has bitten
this project before: with `{{count}}` present, i18next resolves the suffixed key, so the
base key alone is not sufficient at runtime. These six are arguably a real bug being
surfaced, not noise.

**Bucket E — one key with an unresolvable default.**
`translation:box.repair.error` is a genuine production call site
(`src/frontend/screens/Game/GameSubMenu/repairFailure.ts:138`) but is invoked as
`t('box.repair.error', message)` where `message` is a runtime variable. The lexer cannot
resolve the default, so it emits `""`.

**Bucket R — 67 real fork-authored strings never added to a catalog.**
These are live UI strings (`webview.login.*`, `redeemSteamKey.*`, `steam.download.error.*`,
`box.steam.mac32Detected.*`, `login.steam_logout_failed_*`, `winetricks.unavailable*`,
`queue.label.failed`/`retry`, `edit-game.sgdb.unavailable`, `login:button.paste`, …) whose
`t()` call sites shipped without the catalog entry landing. They currently render via their
inline English default, so there is no user-visible breakage in English — but they are
invisible to `meta/lintTranslations.ts`, which compares a translation's *own* keys against
English and is structurally blind to a key absent from English too.

## Why the drift cannot simply be committed

The two gates that guard `public/locales/` are in direct contradiction on this drift:

- `pnpm i18n --fail-on-update` (leg 4 of `.husky/pre-push`) demands zero pending updates —
  i.e. that all 71 keys be written into `en/translation.json`, `en/gamepage.json` and
  `en/login.json`.
- D-05's `meta/i18nCatalogChurnGuard.ts` forbids `pnpm i18n` from changing **any** catalog
  except `gamelib.json` / `gamelib.mt.json`, on the grounds that such a change means a
  `t()` call is missing its `gamelib:` namespace prefix.

The churn guard is right about the cause. The only resolution that satisfies both gates is
to **fix the call sites** — route the fork-authored bucket-R strings through `gamelib:` and
move their text into `gamelib.json` — then exclude test files so bucket T stops leaking.
Committing the parser's output as-is would satisfy the pre-push gate and violate D-05.

`pnpm i18n --fail-on-update` **writes nothing** — verified twice, exits 1 with
`public/locales/` byte-clean. Only bare `pnpm i18n` writes. The backup-first precaution
applies to the bare form only.

`meta/lintTranslations.ts` sets `printExtraTransations = false`, so keys present in a
translated catalog but absent from English are ignored by design. This matters for the
upstream pull: refreshed non-English catalogs may legitimately carry keys `en/` lacks.

- The drift is 4 files, all under `public/locales/en/`.
- Upstream `c39d40174` + `270353382` touch **73 files across 45 locales — none under `en/`**
