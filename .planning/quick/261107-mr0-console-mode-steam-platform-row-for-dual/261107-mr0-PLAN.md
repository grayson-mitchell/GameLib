<design_calls>
These are decided. Executors implement them as written.

DC-1 Dual-build detection reuses the desktop pipeline, no re-derivation. `isConsoleSteamDualBuild` feeds the `useSteamBottleEligibility` hook result (same IPC `isSteamBottleEligible`, same fail-closed behaviour) plus the `gameInfo` seeds (`hasSteamWindowsDepot`, `hasSteamMacDepot`, `hasSteamDepotSignalCaptured`) through `resolveDepotAvailability`, then `resolveSteamSectionGating` (which carries the bottle-required to readonly-windows rule, covering 32-bit `mac_arch` because the backend folds that into `bottleRequired`), then `selectSteamPlatformOptions`. Dual-build means `platformRow === 'selectable'` and the option list has both 'Mac' and 'Windows'. Console's `gameInfo` alone is not enough (no `bottleRequired`), so the hook is called, as the desktop dialog does. The resolver's library inputs are fixed to `nativeInstallOn: false, libraryCount: 0` (Console has no library dropdown; neither input affects `platformRow`).

DC-2 Pending is not dual-build. `isConsoleSteamDualBuild` returns false while `eligibility.pending` is true, because `bottleRequired` is fail-closed false while pending: a 32-bit Mac title with a Windows depot would otherwise flash 'selectable'. It also returns false unless `hostPlatform === 'darwin'` (explicit, though the resolver already never yields 'selectable' off-mac).

DC-3 Windows is offered only on a native-bridge verdict. When dual-build is true, the overlay fetches `window.api.getSteamBridgeRoute(game.app_name, true)` once. `resolveConsoleSteamPlatformOffer` returns `{ offered: true, options: ['Mac', 'Windows'] }` only when dual-build AND `verdict.route === 'bridge'`; otherwise `{ offered: false, options: [] }`. The backend already folds `userRoute: 'bottle'` into route 'bottle' (bridgeRoute.ts line 243), so the frontend reads `route` only, like the desktop reads it through `resolveBridgeRouteLine`. A rejected fetch sets the verdict undefined (fail-closed, silent, same as SteamDialog).

DC-4 Pending UX (least jarring for a controller): the row is hidden until both the eligibility probe and the bridge verdict resolve; it then appears above the Install-to row while focus stays where it is (default `install`), so nothing jumps under the controller. Install keeps today's gate (`steamReady`) and, while the row is hidden, installs the macOS default. That is a resolved choice: Windows cannot be selected until the row exists, and `consoleSteamWindowsChosen` requires `offer.offered`, so Install can never fire with an unresolved Windows choice. Blocking Install on the eligibility probe was rejected: it can take up to 15s (METADATA_FETCH_TIMEOUT_MS) and would slow the common Mac-only path.

DC-5 No dead single-value row. When not offered, `availablePlatforms` for Steam is empty and `showPlatform` is false. Option order is Mac then Windows, so the initial `platformIndex` 0 is macOS once the options appear.

DC-6 Install to label. With Windows chosen, the Install-to row shows the new en-only key `gamelib:consoleMode.steamInstallTargetBridgeBottle` with default 'Its own Windows bottle' (the bridge bottle path is backend-owned and not known to the renderer; showing the Steam library path would be wrong). macOS keeps today's `steamTargetPath ?? steamInstallTargetDefault`.

DC-7 Library probe stays a gate for both platforms. `probeSteamQuickInstallTarget`'s free-space check measures the Steam library drive, not the bridge bottle's location, so for a Windows/bridge install it is only an approximation. Its blocked verdict still blocks a Windows install: the blocked card replaces the whole form, so the Platform row is unreachable, and a library-missing or client-setup cause applies to the bridge too (the bridge talks to the Mac Steam client). This is the conservative, existing behaviour; no new verdict or card is added. Record this call in the SUMMARY.

DC-8 Dispatch shape. The Steam branch calls `installSteamGame(game.app_name, game, undefined, steamWindowsChosen)`: `undefined` keeps the "no path argument" rule of D-23 (the default '' applies), and the fourth argument is the only route by which Windows reaches the backend. The overlay never names `forceWindowsViaBottle`.

DC-9 Census update. `steamEligibilityWiring.test.ts` A4 pins `steamEligibilityProbe` to one importer. Console becomes the second legitimate consumer of the hook, so A4's matcher is widened to any import path ending in `steamEligibilityProbe'` and its expected list becomes exactly the two files; A3's `isSteamBottleEligible` census is untouched (the overlay never names that token).
</design_calls>
