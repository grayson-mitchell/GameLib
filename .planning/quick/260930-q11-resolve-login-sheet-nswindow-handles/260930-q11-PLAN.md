### SUBSTRATE FINDING A — the handle is AUTORELEASED, so the hazard is unconditional

`~/.cargo/registry/src/index.crates.io-*/tauri-2.11.5/src/window/mod.rs:1642`, read directly and
re-verified during planning:

```rust
Ok(objc2::rc::Retained::autorelease_ptr(ns_window).cast())
```

The address `ns_window()` hands back is **autoreleased**. Its guaranteed validity is bounded by the
autorelease pool of the thread that resolved it — **not** by the login window's lifetime. Carrying it
across a GCD deferral into a later run-loop turn is therefore outside the API's contract
**independent of whether the user closes the window**.

**This is the strongest justification for the change and it appears in NEITHER the todo NOR WR-02.**
Carry it into the SUMMARY and into the replacement doc/SAFETY comments.

### SUBSTRATE FINDING B — the AppKit accessor and the autorelease both run on the WORKER thread

Same file, the full body of `ns_window()`:

```rust
self.window.dispatcher.window_handle()      // <- crosses to the main thread via window_getter!
  .map_err(Into::into)
  .and_then(|handle| {                      // <- this closure runs on the CALLING thread
    let view: &objc2_app_kit::NSView = unsafe { h.ns_view.cast().as_ref() };
    let ns_window = view.window().expect("view to be installed in window");   // AppKit, caller's thread
    Ok(objc2::rc::Retained::autorelease_ptr(ns_window).cast())                // autorelease, caller's pool
  })
```

`window_handle()` is the dispatcher getter (`tauri-runtime-wry-2.11.4/src/lib.rs:2144` ->
`get_raw_window_handle`, a `window_getter!`), but the `and_then` closure runs on the **caller's**
thread. So at HEAD both `view.window()` (an AppKit accessor) and the autorelease registration execute
on a worker thread, whose pool is not the main thread's. Moving resolution into the main-thread
closure fixes this too. Record it; it is a second, independent gain.

### SUBSTRATE FINDING C — resolving from the main thread cannot deadlock and cannot double-borrow

Both confirmed by direct read of the vendored crates during planning:

- `tauri-runtime-wry-2.11.4/src/lib.rs:239-248` — `send_user_message` short-circuits to
  `handle_user_message` **inline** when `current_thread().id() == context.main_thread_id`, returning
  `Ok(())` without ever reaching `rx.recv()`. The `getter!` macro (`:197-203`) is an unbounded
  `$rx.recv()` with no timeout parameter — but on the main thread the reply is already delivered
  before `recv()` runs. Resolving from the main thread therefore cannot self-deadlock.
- `tauri-runtime-wry-2.11.4/src/lib.rs:3335` — `Message::Task(task) => task()` sits at the **top
  level** of `handle_user_message`'s match, outside any `windows.0.borrow()` scope, so a nested
  resolution from inside a `run_on_main_thread` closure cannot panic on a `RefCell` double-borrow.
- Independently: the deferred GCD closure runs in a **fresh** run-loop turn, not nested inside
  `handle_user_message` at all, so the present path is clear on both counts twice over.

### SUBSTRATE FINDING D — `objc2` API available for the replacement

`src-tauri/Cargo.toml:132` declares `objc2 = "0.6.4"` as a direct dependency, and `main.rs` already
uses `objc2::rc::Retained<...>` (e.g. `:4547`, `:8103`).

`~/.cargo/registry/src/index.crates.io-*/objc2-0.6.4/src/rc/retained.rs`:

- `:428` `pub unsafe fn retain(ptr: *mut T) -> Option<Retained<T>>` — plain `objc_retain`, null-safe.
- `:457` `pub unsafe fn retain_autoreleased(...)` — **do not use this one.** Its
  `objc_retainAutoreleasedReturnValue` optimization requires the call be immediately adjacent to the
  returning message send, which it is not here. Plain `retain` is correct and always valid on a live
  object.
