# Quick task 260930-q11: resolve login-sheet NSWindow handles inside the main-thread closure

Both login-sheet paths now resolve their `NSWindow` handles inside the main-thread closure that
dereferences them, through a new retaining helper — deleting two Send-pointer shims and all four
raw-address-to-`&NSWindow` reconstructions, and leaving exactly one `unsafe` block on the path.

**Tasks 1 and 2 are complete. Task 3 — the operator's live gate — is NOT satisfied and was not
attempted.** No hardware result appears anywhere in this plan's artifacts. The todo stays in
`.planning/todos/pending/` with `ready: live-gate` intact; WR-02 reads **desk-complete, live gate
pending**, never "resolved".

## What changed

### Task 1 — `src-tauri/src/main.rs` (commit `bb567faf3`)

- **New `login_window_ns_window_retained(app, label) -> Option<Retained<NSWindow>>`**, placed
  immediately after `login_window_ns_window`, `#[cfg(target_os = "macos")]`. It delegates to
  `login_window_ns_window` for the address — so the file keeps exactly ONE resolver, not a second
  competing one — and turns it into an owned handle via `objc2::rc::Retained::retain`. Deliberately
  not `retain_autoreleased`, whose `objc_retainAutoreleasedReturnValue` optimization requires
  adjacency to the returning message send; `retain` is plain `objc_retain` and is null-safe by
  contract, so no null check is hand-rolled. This is the **only remaining `unsafe` block** on either
  login-sheet path — four raw casts collapsed into one documented site with a real stated invariant.
- **`present_login_window_as_sheet`**: both resolutions moved to the top of the **deferred GCD
  closure** — the innermost one, the one that calls `beginSheet:completionHandler:` — not the outer
  `run_on_main_thread` closure, which still runs 250ms too early. An `AppHandle` clone and an owned
  `String` label are carried in; both are `Send`, so nothing but `Send` values cross the boundary.
  Each unresolvable-window arm WARNs and then **`tx.send(false)`**, never a bare `return`.
- **`dismiss_login_window_sheet`**: the same restructure inside its `run_on_main_thread` closure.
- **Deleted**: both `struct SendPtr` + `unsafe impl Send` pairs, both Rust-2021 disjoint-capture
  rebinding pairs *and the comments explaining them* (they described a wrapper that no longer exists),
  all four reconstruction lines, and both "resolved moments ago" SAFETY comments — that timing
  assumption was the thing this task existed to delete.
- **Unchanged, deliberately**: `SHEET_PRESENT_WKWEBVIEW_WARMUP_DELAY` is still `250ms`, still
  unconditional, still armed via `dispatch2::DispatchQueue::main().after()`. This task makes the
  deferral safe; it does not revert it.
- The standalone `both NSWindow addresses resolved` live-evidence line lost its pre-dispatch home, so
  an equivalent (`both NSWindow handles resolved on the main thread … deferred_elapsed=…`) now sits
  inside the deferred closure after resolution succeeds, keeping a future gate able to localize a
  stall to the resolution leg. `[shell]` prefix discipline preserved: labels and elapsed durations
  only, never a URL, origin, or title.

### The single most important line

The present path's unresolvable-window arms **send `false` down the existing channel** rather than
bare-returning. The old code could `return false` from the function body because resolution ran
before the channel mattered; the new code is inside a closure, and a bare `return` there drops out of
the closure leaving the worker blocked on `rx.recv_timeout(10s)` for the full ten seconds before
`humble_login_open`'s `attached == false` visible-fallback arm could run. The user would stare at
nothing for ten seconds instead of seeing the window shown normally straight away. Pinned by a test.

### A dismiss-path detail that D-06 forced

The dismiss closure signals on `tx` from **every** arm, including the two that never touch AppKit.
This is not tidiness. The channel answers *"did the main-thread hop run"*, and only a hop that did
**not** run may re-register the label (WR-01). A silent early `return` would drop the sender,
`recv_timeout` would report `Disconnected`, `.is_err()` would be true, and the healthy "window is
already gone" path would wrongly re-register a window that no longer exists — stranding its label in
`PRESENTED_LOGIN_SHEETS` for the process lifetime, which is the exact failure WR-01's re-registration
exists to prevent. The reasoning is recorded on both the function's doc comment and in the closure.

## Findings A and B — the strongest justification, absent from both the todo and WR-02

Both were measured during planning by direct read of the vendored crate and are re-stated here, in
the replacement code comments, in the todo, and in WR-02's new status block.

**A — the handle is AUTORELEASED, so the hazard was unconditional.**
`~/.cargo/registry/src/index.crates.io-*/tauri-2.11.5/src/window/mod.rs:1642`:

```rust
Ok(objc2::rc::Retained::autorelease_ptr(ns_window).cast())
```

The address `ns_window()` hands back is autoreleased. Its guaranteed validity is bounded by the
autorelease pool of the thread that **resolved** it, not by the login window's lifetime. Carrying it
across a GCD deferral into a later run-loop turn was therefore outside the API's contract
**independent of whether the user closes the window**. Both the todo and WR-02 framed the defect
purely as a race against a window close (Cmd+W, `captureOAuthLogin` settling, `humble_login_close`),
which understates it — and it is what removed the basis for treating the dismiss path as merely
"narrower" because its callers are already on the main thread. The pool, not the thread, is the
bound; so both paths were fixed.

**B — the AppKit accessor and the autorelease both ran on the WORKER thread.** In `ns_window()`,
only the inner `window_handle()` getter crosses to the main thread (tauri-runtime-wry's
`window_getter!`); the `.and_then` closure that follows runs on the **caller's** thread. So at HEAD
both `view.window()` — a plain AppKit accessor — and the autorelease registration executed on a
worker thread, onto a pool that is not the main thread's. Moving resolution into the main-thread
closure fixes this too: a second, independent gain, also absent from the todo and from WR-02.

Resolving from the main thread is safe on both counts, also confirmed by direct read:
`send_user_message` (tauri-runtime-wry-2.11.4/src/lib.rs:239-248) short-circuits to
`handle_user_message` **inline** when the caller is already on the main thread, so `getter!`'s
unbounded `rx.recv()` is never reached and this cannot self-deadlock; and `Message::Task(task) =>
task()` sits at the top level of that match (`:3335`), outside any `windows.0.borrow()` scope, so a
nested resolution cannot panic on a `RefCell` double-borrow.

## Verdict on `LOGIN_SHEET_PRESENT_WATCHDOG_TIMEOUT` — KEPT

Its old doc comment justified the constant by the two `.ns_window()` calls running at the top of
`present_login_window_as_sheet`, **before** the inner bound started, on `getter!`'s unbounded
`rx.recv()`. **Both halves are now false**: those resolutions happen inside the deferred GCD closure,
which sits inside the inner `rx.recv_timeout(10s)` window, and they run on the main thread where
`send_user_message` short-circuits inline so `recv()` finds the reply already delivered. The inner
10s bound now covers the whole critical path — both resolutions, the 250ms deferral, `beginSheet:`,
and the CR-02 read-back.

The constant is nevertheless **kept**, and the comment now says why on the evidence:

1. What the inner bound still does not cover, between function entry and `recv_timeout` being armed:
   the entry `eprintln!` on a stderr a stalled consumer can block; `app.run_on_main_thread`'s own
   cross-thread send into tao's event proxy, which nothing in this file bounds;
   `register_presented_login_sheet`'s `PRESENTED_LOGIN_SHEETS` mutex acquisition, which runs *after*
   the inner bound has returned; and whatever a future edit inserts on either side of that bound.
2. `PENDING_VISIBLE_LOGIN_WINDOW_TTL` is **derived from** this constant, and the Rust test
   `pending_login_window_ttl_is_derived_from_the_watchdog_timeout_with_a_margin` asserts the TTL is
   strictly greater than it — so deleting the constant would be a change to `humble_login_open` and
   to that test, not a comment edit.

`SHEET_PRESENT_WKWEBVIEW_WARMUP_DELAY`'s own doc comment was re-read: its citation of
`send_user_message`'s inline short-circuit (why a nested `run_on_main_thread` would not yield a
run-loop turn) is still correct, still load-bearing, and now doubly relevant — it is the same
mechanism that makes main-thread resolution non-deadlocking. Left as written. One in-body comment was
updated from "the actual `beginSheet:` call and its read-back are deferred" to name the two
resolutions as deferred too, so no two comments disagree.

## What only hardware can tell us

Whether AppKit still actually attaches the sheet. The eight desk gates prove the shape is right and
that it compiles; **they cannot prove `beginSheet:` still works.** This is `unsafe` Objective-C
interop on a path with a nine-attempt live-gate history (FAIL 0/6 → FAIL → FAIL 5/6 → FAIL 5/6 →
FAIL 1/6 → FAIL 0/5 → PASS 5/5); every defect in this area has only ever been caught on hardware.

No timing test was written, deliberately (D-05): one would pass on the defective code most of the
time, which is precisely the property that let this shape survive nine live-gate attempts.
