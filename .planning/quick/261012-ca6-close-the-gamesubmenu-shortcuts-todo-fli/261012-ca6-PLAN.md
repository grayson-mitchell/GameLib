Close the todo `.planning/todos/pending/2026-10-12-gamesubmenu-shows-remove-shortcuts-before-the-write-is-known.md`.
Today, GameSubMenu flips `hasShortcuts` as soon as it fires the send-kind `addShortcut`/`removeShortcut`,
before anyone knows whether the write worked. After this plan it flips only from the outcome.

**Fix chosen (the todo gave three options and decided none).** Both channels become invoke-kind. Each resolves
the `shortcutsExists` predicate, evaluated in the sidecar AFTER the work has settled. This is the todo's
option 1 combined with option 2, with the re-query moved to the one place where settlement is actually known.
Reasons, from the code read at planning time:

- **Option 2 alone (re-query from the renderer) is impossible with a send-kind channel.** `tauriTransport.send`
  (`src/preload/tauriTransport.ts:104`) resolves once the Rust shell has accepted the frame. `sidecarRpc.ts:216`
  runs listeners fire-and-forget, and the sidecar listener is a `void (async () => {...})()` IIFE
  (`shortcutsFlowRegistration.ts:219-261`). Nothing in the renderer can observe when the write finished, so a
  bare `shortcutsExists` call races it.
- **Option 3 (a pushed outcome event) costs more than it buys.** It needs a new `FrontendMessages` channel,
  filtering by appName and runner, and a subscribe/unsubscribe lifecycle in a component that already has more
  than twelve hooks. All of that is to rebuild a reply that invoke already provides.
- **Option 1 copies a pattern already in the same three files.** `shortcutsExists`, `addToSteam`,
  `removeFromSteam` and `isAddedToSteam` are invoke-kind in `shortcutsFlowRegistration.ts:138-209` and
  `src/preload/api/menu.ts:11-14`. `handleAddToSteam` (`index.tsx:327-356`) already sets its state from the
  resolved value.
- **The return value is "do shortcuts exist now", not "did the call succeed".** This gives one source of truth,
  shared with the remount path (`index.tsx:368-370`). A partial add (one of the two files written, so
  `addShortcuts` rejects) correctly shows "Remove shortcuts", because a removable shortcut exists. An add that
  resolves without writing anything (the DLC early return, or no shortcut paths at `shortcuts.ts:36,50-52`)
  does not flip.
- **The remove outcome is only knowable once `removeShortcuts` awaits its deletions.** Today it calls the
  callback-style `unlink(path, cb)` and `rm(path, opts, cb)` (`shortcuts.ts:153-176`) and returns before
  either finishes. Its callbacks log "removed" even when they receive an error. Task 2 fixes this.

Purpose: a failed write never leaves the menu claiming shortcuts that do not exist, and a second click never runs
the remove path against shortcuts that were never written.
Output: invoke-kind shortcut channels, a tested `toggleShortcuts` renderer helper, a `removeShortcuts` that awaits
its deletions, and the todo closed.
</objective>
