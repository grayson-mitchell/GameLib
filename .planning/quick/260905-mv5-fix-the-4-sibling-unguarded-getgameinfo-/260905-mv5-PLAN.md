# Quick Task 260905-mv5

## Objective

Close the four unguarded `getGameInfo()` title consumers that 260905-luf's own
consumer census recorded as out-of-scope: the force-uninstall confirmation
dialog, the uninstall-error notification, and the two `shortcutsExists`
handlers (Electron + Tauri sidecar).

**Purpose:** luf fixed the install-failure surfaces and left a documented
residue. Two of the four remaining sites are *destructive-confirmation* and
*IPC-throwing* surfaces, not merely cosmetic ones.

**Output:** one relocated fallback chain that is importable without closing an
import cycle, four fixed call sites, and a RED-proven regression test per site.

## D-01 is settled — do NOT relitigate

From 260905-luf (`.planning/quick/260905-luf-.../260905-luf-PLAN.md`, section
D-01, confirmed not overturned by that task's SUMMARY):

- Do **NOT** populate `{} as GameInfo` with a stub. It breaks `dispatch.ts:82-89`
  (the `{}`→`null` frontend contract), `appShellFlowRegistration.ts:536` (tray
  runner resolution), and `library.ts:1257` (the library manager's own fallback).
- Do **NOT** make `getGameInfo()` async. ~40 sync call sites across ~20 files.
- Do **NOT** make it throw. Memory record
  `null-to-throw-accessor-swap-drops-guaranteed-cleanup`.
- Do **NOT** touch `SteamGame.getGameInfo()` at all. Its once-per-appId warning
  (luf, `games.ts`) already covers observability, and `games.test.ts`'s
  `expect(result).toEqual({})` pin must stay untouched.

## Evidence measured at plan time (HEAD `cba66f3bd`) — do not re-derive, but DO falsify

Everything below was executed, not inferred. **Two premises handed to the
planner were measured FALSE; they are corrected here.**

1. **Site 1** — `src/backend/utils.ts:329-330`, `askForceUninstall(game: Game)`:
   `const { title } = game.getGameInfo()` feeds `dialog.showMessageBox({ type:
   'question', title, message: 'Game folder appears to be deleted...', cancelId: 0 })`
   (line 331). A nameless destructive-confirmation dialog.

2. **Site 1's two callers both have `appName` in scope.**
   - `launcher.ts:110-128`: `appName` destructured from `LaunchParams`. Note this
     caller reads `gameInfo.install.install_path` at :124 **before** calling
     `askForceUninstall`, so on a `{}` GameInfo it throws at `.install` first —
     this path is effectively unreachable with an empty GameInfo.
   - `utils.ts:372-373`: `if (error.includes(deletedFolderMsg) && appName)
     { await askForceUninstall(getGame(appName, runner)) }`. `appName` is
     **provably non-empty** here (the `&& appName` guard). **This is site 1's
     real exposure**: `getGameInfo()` is read fresh inside `askForceUninstall`.
   - The `Game` interface (`src/common/types/game_manager.ts:48+`) carries **no
     `appName` property** — verified. So the fallback must be passed in.

3. **Site 2** — `src/backend/utils/uninstaller.ts:107-108`:
   `const game = libraryManagerMap[runner].getGame(appName); const { title } =
   game.getGameInfo()` feeds `notify({ title, body: t('notify.uninstalled.error',
   'Error uninstalling') })` in the catch branch. `appName` **and** `runner` are
   both in scope. This is the easiest of the four.

4. **⚠ FALSE PREMISE #1 — corrected.** The briefing stated that
   `shortcutFiles`' other two callers "call it as `shortcutFiles(gameInfo.title)`
   where `gameInfo` is a full GameInfo passed in as a parameter — NOT re-read
   from `getGameInfo()`." **This is wrong.** Measured:
   - `shortcuts.ts:33-34` `async function addShortcuts(game: Game, fromMenu?)`
     → `const gameInfo = game.getGameInfo()`
   - `shortcuts.ts:123-124` `async function removeShortcuts(game: Game)`
     → `const gameInfo = game.getGameInfo()`

   Both take a **`Game` instance** and re-read `getGameInfo()` themselves. They
   are subject to the identical `{}` sentinel.

5. **⚠ FALSE PREMISE #2 — corrected, and it is the decisive one.** The briefing
   speculated that "`shortcutFiles` returning `[undefined, undefined]` for a
   falsy title may already be part of the answer." It does not. Measured by
   executing the real module in jest (`sanitize-filename` 1.6.3, confirmed
   installed):

   | input | actual result |
   |---|---|
   | `shortcutFiles(undefined)` | **THROWS** `Input must be string` (from `sanitize()` at `shortcuts.ts:152`) |
   | `shortcutFiles('')` | **RETURNS a real path pair** — on darwin, `~/Applications/.app` for both entries |
   | `addShortcuts({} as GameInfo)` | **THROWS** `Cannot read properties of undefined (reading 'is_dlc')` at `shortcuts.ts:35`, *before* reaching `shortcutFiles` |

   Consequences, in order:
   - **Sites 3 and 4 do not return a wrong answer today — they THROW.**
     `shortcutsExists` is an `invoke` channel, so the throw rejects to the
     renderer at `GameSubMenu/index.tsx:308`
     (`window.api.shortcutsExists(appName, runner).then(...)` — a `.then` with
     no `.catch`, i.e. an unhandled rejection). That is a materially different
     defect than the "nameless string" the other two sites have.
   - **`addShortcuts` and `removeShortcuts` can never have written a
     title-derived path when the title is unresolvable** — they throw at
     `is_dlc` first. So every shortcut that exists on disk was written from a
     **real, non-empty** title.
   - Therefore a `|| appName` fallback at sites 3/4 would probe
     `~/Applications/<appName>.app` — a path `addShortcuts` **provably never
     writes**. Guaranteed-wrong: false-negative normally, false-**positive** if
     anything unrelated occupies it.
   - And a `|| ''` fallback is worse: it resolves to the **shared** path
     `~/Applications/.app` for *every* untitled game — one stray file there
     would report "shortcut exists" for all of them.

6. **HAZARD B confirmed.** `src/backend/downloadmanager/utils.ts:2-6` imports
   `{ downloadFile, isEpicServiceOffline, sendGameStatusUpdate } from '../utils'`
   → `src/backend/utils.ts`. Site 1 lives in `src/backend/utils.ts`, so
   importing `resolveGameTitle` back from `downloadmanager/utils.ts` closes a

7. **Relocation target is safe.** `src/backend/utils/` already exists as a

   introduces no new cycle.

## D-02 — where the fallback chain lives (resolves HAZARD B)

**CHOSEN: relocate the chain to a new zero-runtime-import module
`src/backend/utils/gameTitle.ts`; re-export `resolveGameTitle` from
`downloadmanager/utils.ts` under its existing name.**

- One private `pickTitle(live, appName, fallback?)` holding the **only** `||`
  chain in the backend. Both public wrappers delegate to it — luf's
  "exactly ONE chain" invariant is preserved by construction, not by convention.
- Two public wrappers, because site 1's signature genuinely differs:
  - `resolveGameTitle(libraryManagerMap, runner, appName, fallback?)` — moved
    verbatim from `downloadmanager/utils.ts:86-94`, same behaviour.
  - `resolveTitleForGame(game: Game, appName: string)` — for callers holding a
    `Game` instance rather than `(map, runner, appName)`.
- The module imports **types only** (`GameInfo`, `Runner`, `Game`, and the
  `LibraryManagerMap` alias `typeof import('backend/storeManagers').libraryManagerMap`).
  All erased at compile time → it can be imported from anywhere, including
  `backend/utils.ts`, without any cycle.

Rejected: adding the helper as a new export **of `backend/utils.ts`**. Sixteen
test files factory-mock `backend/utils` with explicit member lists
(`shortcutsFlows.test.ts:54`, `installFlows.test.ts:110`, `games.test.ts:201`,
`library.test.ts:100`, ...); a new export there is exactly the luf Rule-1
regression, multiplied by sixteen.

Rejected: duplicating `live || appName` inline at each site. luf's whole point
was one chain, and its own doc comment says so.

## D-03 — what sites 3 and 4 do when the title is unresolvable (resolves HAZARD A)

**CHOSEN: return `false` and log a warning. Do NOT fabricate a path.**

Grounded entirely in evidence item 5, which is measured, not argued:

- `addShortcuts`/`removeShortcuts` throw on `{}` **before** `shortcutFiles`, so
  every shortcut on disk came from a real non-empty title.
- An `appName`-derived probe therefore targets a path the writer provably never
  wrote — it can only be wrong, and can be wrong in the **false-positive**
  direction.
- An `''`-derived probe targets a single shared path (`~/Applications/.app`)
  common to every untitled game — strictly worse.
- `false` is the honest answer to "can I confirm a shortcut exists?" when the
  identity of the shortcut cannot be established. The UI
  (`GameSubMenu/index.tsx:308`) then offers "Add shortcut"; clicking it reaches
  `addShortcuts`, which throws loudly on the same `{}` — the failure stays
  visible rather than being laundered into a silent wrong answer.
- It also **removes an unhandled promise rejection** at the renderer, since
  `.then(...)` at `GameSubMenu/index.tsx:308` has no `.catch`.

Rejected: routing sites 3/4 through `resolveTitleForGame` like sites 1/2. The
fallback there is a *display* string; `shortcutFiles` consumes it as a
*filesystem path component*. Same value, incompatible contracts. This is the
one place in this task where the shared chain is deliberately **not** used, and
the code comment must say why.

**No new i18n key is needed anywhere in this task.** Sites 1/2 fall back to an
existing `appName`; sites 3/4 emit a **log**, not user copy. If the executor
concludes otherwise, the key goes in `public/locales/en/gamelib.json` and
**never** `translation.json`.
