## Planner findings (measured at `46dfc9612`; all paths repo-root-relative)

**Grid rule.** `src/frontend/screens/Library/index.css:1-8`: `.gameList` is `display: grid; grid-template-columns:
repeat(auto-fill, minmax(156px, 1fr)); grid-gap: 1.5rem`. The `1fr` maximum is why tiles grow with the window.
`.listing` (`:82-86`) is the scrolling column that holds both the grid and the focus-row strip; it is their
nearest common ancestor. `GameCard` is `width: 100%` with `aspect-ratio: 173/275`, so a fixed-width track
yields a fixed-size card. The list layout (`.gameListLayout`) does not use the column rule. No JS reads
`grid-template-columns` (grep: only `blankRenderProbe.ts` logs it).

**How Accessibility "size" reaches tiles today.** The Accessibility screen has one size control,
`Zoom` (`src/frontend/screens/Accessibility/index.tsx:115-140`, range 60-200 step 10). The chain is:
1. `setZoomPercent` (`src/frontend/state/GlobalState.tsx:609-618`) persists `zoomPercent`.
2. After a 500ms debounce it calls `window.api.setZoomFactor(percent / 100)`.
3. That reaches `tauriSetZoomFactor` (`src/preload/api/tauriWindowChrome.ts:126-135`).
4. `tauriSetZoomFactor` computes `factor = 1.2 ** ((f*k - 1) / 0.2)`, with `k = availWidth/1200` below a
   1200px screen and 1 otherwise, then calls `getCurrentWebview().setZoom(factor)`.

That is **whole-webview page zoom**: every CSS px, including the 156px track, is scaled by `factor`. No CSS
variable or root font-size is involved. So:
- The only way to make tile size zoom-invariant is to divide the tile's CSS width by the factor *actually
  applied*.
- `zoomPercent / 100` is wrong for two reasons: the `k` term, and the second point below.

Two more facts:
- **The persisted zoom is never re-applied at startup.** The only caller of `setZoomFactor` is
  `setZoomPercent`, and its only caller is the Accessibility slider's `onChange` (`index.tsx:84`). Nothing in
  `src-tauri/src`, `src/preload` or GlobalState's boot path applies it. So the webview runs at factor 1 after
  every launch until the slider is touched. This is desk-derived and is filed as a follow-up todo in Task 3;
  it is not fixed here.
- Tauri exposes no zoom getter, so the factor has to be published at apply time (Task 3).

overflow-y: auto`). The panel's floor is `.Header__footer` (`Header/index.tsx:303-400`; CSS

**Existing range input.** Accessibility's stylesheet (`src/frontend/screens/Accessibility/index.css:1-23`)
styles `input[type='range']` **globally and unscoped**:

`<label>`, native range) but not those styles. Every target engine (WKWebView, WebView2, WebKitGTK) honours the
`-webkit-` range pseudo-elements.

**The focus-row strip derives its card width from the old grid arithmetic. That machinery becomes dead.**
`FocusRowStrip/focusRowOverflow.ts:131-366`:

  "match the grid".
- `FocusRowStrip/index.tsx:81-130` and `:132-166` wire it, together with a `gridShown` prop

With fixed columns, a grid tile is always exactly the tile width, so "match the grid" holds by construction if
the strip reads the same variable. If the sync kept running, it would overwrite the strip with the old `1fr`
share and break the ruling. So it is retired, not adapted.

**Why the range is 140-320, step 4, default 156.** These are discretion choices, each bound to a gate:
- **Floor 140.** The controller-mode art-fit gate needs `w * (275/173 - 4/3) >= 35` (the badge bar), so
  `w >= 136.6px`. 140 is the first step-aligned value above that, with a 0.88px margin, and it stays green.
  Today's 156 has a 4.98px margin.
- **Ceiling 320.** The strip-end clearance gate needs the ring reach `0.025w + 5.25 <= 15px` (the list's
  inline padding). That holds to 390px. 320 sits inside the 336px supremum the gate was already proven at,
  so no strip CSS geometry changes. Reach at 320 is 13.25px horizontal and 17.97px vertical, against
  `margin-block` `0.04w + 6.5 = 19.3`.
- **Default 156.** It equals today's floor and every existing `var(--focus-row-card-width, 156px)` fallback,
  so a fresh profile looks like today's narrowest tiling.
- **Step 4.** `(156 - 140)` and `(320 - 140)` are both multiples of 4.

## Discretion choices (recorded so the executor does not re-decide them)

- **Where the variable lives.** `--library-tile-width` (the slider value in px) goes on
  `document.documentElement`. The Library writes it in a `useLayoutEffect` on mount, before paint; the slider
  writes it on change. `.listing` derives `--library-tile-css-width` from it, which keeps the zoom division in
  one declaration. There is no React state in `Library/index.tsx`, so dragging the slider re-renders only the
  slider, not the 1,200-line Library tree.
- **Leftover width.** `justify-content: start` on `.gameList`, so leftover width collects at the inline end.
  Strip cards are left-packed with the same 1.5rem gap, so the strip and grid columns stay x-aligned
  (focusRowStripSource Test G's premise).
- **The 1.5rem gap stays as is.** It is not tile size, and it still zooms.
- **List layout.** The slider stays visible in list layout, because the focus-row strip above the list still
  renders cards at the tile width.
- **Slider colours** come only from the panel's established pair: `color: var(--text-secondary)` on
  `--navbar-background`, which is what every panel label already uses. The track and the thumb both paint
  `currentColor`, and the thumb is told apart by shape (a 14px disc on a 4px track). Hover lifts `color` to
  `var(--text-default)`. Focus copies the Header's inset ring recipe (`Header/index.css:56-66`), because the
  control sits inside the scroll-clipped tier-2 column. Nothing new needs a contrast gate.
- **Out of scope:**
  - Re-applying the saved zoom at startup is filed as a todo.
  - Scaling the strip's 15px inline padding for effective zoom below 1 is a recorded residual.
  - No Accessibility-screen copy changes.
  - `librarySyncNoticeSource.test.ts`'s prose that still mentions the `gridShown` prop is left as is. Its count
    assertion stays 3.
