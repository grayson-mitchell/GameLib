# Quick Task 261015-n5k: live-gate the embed container's zero-floor column in the running app

## Why this is orchestrator-run, inline

A live gate drives a real window with CGEvent clicks, keystrokes into the Web Inspector console,
`screencapture -l<CGWindowID>` and `CGWindowListCopyWindowInfo` reads. Prior gates in this repo
(50-UAT Items 3/16, 34.4.2 RERUN-7) ran the rig from the orchestrating session; a planner/executor
round-trip adds nothing a live gate needs and costs the 35-minute first-write latency recorded in
`execute-phase-sequential-orchestration-signals`. This plan is therefore written by the session
that ran it, before the record is closed, so the arms and pass bars are stated ahead of the
verdict.

## Locked decisions (from the todo's own evidence and the repo's precedent)

- **Pass bar is UI-SPEC E3's row as written** (50-UI-SPEC.md:152): at 900px the single 40px row
  shows message + Reload + Open in browser; the message may ellipsise, the actions may not clip.
  No new bar is invented for below-900 — there the deliverable is "degrades as the harness
  predicts", scored against `261015-dlu`'s evidence table.
- **Raise the banner through the renderer's own drain**, by wrapping `window.api.storeEmbedTakeNavEvents`
  from the console, rather than a `/etc/hosts` blackhole (needs sudo and 45 s per arm) or a
  hand-inserted copy of the banner markup (would not exercise the React path).
- **Reach sub-900 viewports by docking the Web Inspector right** (a true layout-viewport shrink),
  not by a CSS override on `.App`; a CSS override is the fallback only if the dock cannot be
  driven.
- **Include a pre-fix control arm** at the sub-floor widths — a live "not clipped" without a live
  "clipped" proves nothing about the mechanism (`gates-that-prove-nothing` family).
