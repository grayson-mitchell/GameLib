<objective>
`checkNintendo` states a premise in its own header comment -- "Chromium reports these with the
'standard' mapping by physical position" -- and never checks it. On the operator's PowerA
Advantage Wired Controller for Nintendo Switch 2, Chromium reports a NON-standard mapping and
passes raw HID through untouched. Result, measured live on 2026-09-23: all four face buttons
dispatch the wrong action (and every glyph in the hint bar contradicts what the button does --
the exact defect this layout exists to fix, reintroduced for a device class it does not handle),
and the d-pad is completely dead because `buttons[12-15]` is not where a non-standard pad puts it.

Purpose: make the layout read the mapping BEFORE applying any position-based assumption, and fix
BOTH subsystems that hard-code standard-mapping indices -- global spatial navigation
(`checkNintendo`) and Console Mode's overlays (`getActionButtonIndex`/`getBackButtonIndex`) -- in
one change, through ONE shared table, so they cannot disagree.

Output: a mapping-aware Nintendo layout, mapping-aware Console Mode index helpers, behavioural
tests covering both mappings, a permanent one-line HID diagnostic in `gamelib.log`, and a retired
todo. Unblocks the controller leg of Phase 38: `38-C01`'s d-pad half and `38-C08` become
scoreable outright. `38-C03`/`38-C04` become scoreable ONLY IF Task 1's A4 measurement shows
the shoulder and stick-click indices are NOT shifted -- the todo's "shifted" claim is a
DEDUCTION, not a measurement, and this plan expects it to be wrong (raw HID Switch order puts
L/R/ZL/ZR at 4/5/6/7 and L3/R3 at 10/11, the same as standard). If A4 shows a real shift, a
NEW todo is filed and those two items stay blocked. Stated conditionally on purpose, to match
`<decision_record>` and `<honesty_about_reach>` rather than overclaiming up front.
</objective>

<decision_record>
## The fix shape: one shared face-index table, consumed by both subsystems. ADOPTED.

`nintendo.ts` gains an exported table function -- `nintendoFaceIndices(mapping)` -- returning
`action`, `back`, `alt`, `menu`. Two constant rows feed it:

- STANDARD (`mapping === 'standard'`): action 1 (right cap), back 0 (bottom cap), alt 2 (left cap
  = printed Y), menu 3 (top cap = printed X). **This row reproduces exactly what ships today** --
  it is a refactor of the existing constants, not a change to them.
- RAW HID (everything else): derived from the classic SNES/Nintendo button order Y, B, A, X,
  giving action 2 (A), back 1 (B), alt 0 (Y), menu 3 (X). This row is CONFIRMED against the
  operator's pad in Task 1 before Task 3 commits to it.

`checkNintendo` takes the mapping as a fifth parameter and resolves its four face indices through
that table. `getActionButtonIndex`/`getBackButtonIndex` take the mapping as a second parameter and
resolve through the SAME table.

**Why this shape rather than any other.** `nintendo.ts:52-62` calls itself THE SINGLE SOURCE OF
TRUTH precisely so the glyph and the acting button can never disagree, and `controller.ts:27-36`
carries the warning that stacking two swaps cancels them out. Any fix that edits the two
subsystems separately -- however carefully -- restores exactly the split those comments exist to
prevent, and leaves the next change one edit away from re-breaking it. Routing both through one
table makes agreement structural: there is one place that can be wrong, and it is wrong for both
halves simultaneously or for neither, which is a condition a single test can pin (case (p) below).

## The mapping branch lives INSIDE `checkNintendo`, not in `gamepad.ts`'s dispatch. ADOPTED.

`gamepad.ts:570-586` is an `id.match()` chain, and `nintendoLayout.test.ts`'s header names routing
as "the easiest thing to get wrong here". Adding a second, nested branch there would add a new
routing failure mode and would change the meaning of every existing routing assertion in that
suite. Instead `gamepad.ts` changes by exactly ONE argument -- `controller.mapping` is passed
through -- and the ONE function that owns Nintendo pads owns the whole decision.

**REJECTED alternative: a separate `checkNintendoNonStandard` export.** More readable in isolation,
but it creates a second dispatch site in the chain those tests were written to protect, for no
behavioural gain. Recorded so the next reader does not re-propose it as an obvious cleanup.

## Threading to Console Mode: a SECOND REQUIRED PARAMETER, not a descriptor object. ADOPTED.

`useGamepadInfo()` (`hooks.ts:81-103`) already resolves the first connected pad; it gains `mapping`
alongside `layout` in its return. The call sites become `getActionButtonIndex(layout, mapping)` /
`getBackButtonIndex(layout, mapping)`.

**REJECTED: a `ControllerProfile { layout, mapping }` descriptor passed everywhere.** It would drag
the LABEL helpers (`getActionButtonLabel`/`getBackButtonLabel`) into taking a mapping too, which is
actively WRONG: the printed cap is a property of the plastic, not of the HID report, and a
signature implying otherwise invites someone to make the glyph mapping-dependent. Two parameters
make the type system say the true thing -- labels depend on layout alone; indices depend on layout
AND mapping.

**The parameter is REQUIRED, with no default.** An optional `mapping = 'standard'` would compile at
every existing call site unchanged and let a future call site silently re-acquire this exact
defect. Making it required means `pnpm codecheck` forces every call site to be looked at. The
one-time cost of five edits buys a compile-time guarantee; take it.

## D-pad on a non-standard pad: hat axis, CARDINALS ONLY. ADOPTED.

Follow the SHAPE of `checkN64Clone1` (`nintendo.ts:124-177`) -- read one axis, `Math.round(v * 10)`,
compare against an integer table -- but **do NOT inherit its constants**. That function's comment
and code disagree with each other (the comment says down is 0.14286, the code tests
`dPadVal === -1`; the code tests padRight against 4, which the comment labels down-left), and hat
values are device-specific regardless. The constants for THIS pad come from Task 1's live
observation, with the Chromium/W3C generic-hat convention as the PRIOR: up -10, up-right -7,
right -4, down-right -1, down 1, down-left 4, left 7, up-left 10, neutral 13 (1.28571).

**Diagonals dispatch NOTHING.** A diagonal that fired both of its components would move spatial
navigation twice in one frame -- surprising in a grid, and not what a user pressing up-right on a
card grid means. `checkN64Clone1` already sets this precedent. A test asserts the diagonal silence
so the choice is visible rather than accidental.

**`checkN64Clone1` is NOT fixed here.** Different device, no hardware to test it, explicitly out of
scope per the brief. Its comment/code disagreement stays recorded in this plan and nowhere else
changes.

## Instrumentation: one line KEPT, the dump REMOVED. Both justified.

KEPT permanently: the `Gamepad added:` line at `gamepad.ts:626` is converted from `console.log` to
`window.api.logInfo` and widened to carry `mapping`, `buttons.length` and `axes.length`.
Justification: `console.log` never reaches `gamelib.log`, and the ABSENCE of exactly these four
facts is why this defect had to be diagnosed by falsifiable prediction rather than by reading a
log. One line per controller connect is cheap -- the same reasoning `blankRenderProbe.ts:58-61`
records for `probeMark` ("cheap enough to leave on"). Guard it as `window.api?.logInfo?.(...)`
inside try/catch, because three jest harnesses stub `window.api` with three different partial
shapes and an unguarded call throws inside the `gamepadconnected` listener.

REMOVED before the final commit: the per-frame newly-pressed-button / changed-axis dump. It is
per-rAF-frame noise, it exists only to answer Task 1's questions once, and leaving it would write
to `gamelib.log` on every input for the life of the app.

## Multiple simultaneous pads: RECORDED, not fixed.

`useGamepadInfo` reads the FIRST connected pad while `useGamepadButtonPress` applies the resulting
index to EVERY pad. With a standard Xbox pad and a non-standard Nintendo pad both connected, one of
them gets the other's indices. This is PRE-EXISTING -- already true of `layout` today -- and
widening it to a per-pad resolution is a different, larger change touching every hook. Record it in
a comment at `useGamepadInfo` and in SUMMARY.md. Do not fix it here.
