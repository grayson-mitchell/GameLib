**1. The todo's premise is wrong for Steam today.** The todo says a joined bridge Play runs
`createGameLogWriter`, `checkWineBeforeLaunch`, `persistBottleWineVersion`, the before/after
launch scripts and the launching/done status updates. All of those live in
`launcher.ts`'s `launchEventCallback`, and **Steam never reaches it**:
- the sidecar IPC `launch` handler (`src/backend/sidecar/steamFlowRegistration.ts` `handleLaunch`, registered at L399) sends `runner === 'steam'` to `dispatchSteamLaunch` (L361-364); and
- the `gamelib://launch` deep link (`src/backend/protocol.ts` L213-217) does the same.
They are the only two callers of `launchEventCallback`. Its `runner === 'steam'` /
`persistBottleWineVersion` block (launcher.ts ~L232-236) is dead code for Steam. For a joined
Steam Play, the work that actually runs twice is `SteamGame.launch()`'s pre-routing:
`noteSteamAuthTrigger('user-play')`, `clearStaleBridgeVerdict()`, `ensurePlatformsCaptured()`,
the bottle-monitor phase lookup and `findBridgeInstallBottle`. That is followed by a second
`addRecentGame` in `dispatchSteamLaunch`. So the Steam launch IPC entry is
**`dispatchSteamLaunch`** (`src/backend/storeManagers/steam/launchDispatch.ts`), the one funnel
both Steam entry points share.

**2. The second entry point.** The UAT 38 double launch did not come from one Play button. Four
other surfaces call `window.api.launch` for the same app without sharing any "launching" state:
- **The library grid card's right-click/context-menu "Play"** (`src/frontend/screens/Library/components/GameCard/index.tsx` ~L403-407). It is shown when `isInstalled && !isPlaying && !isUpdating && !isQueued` and is **not** gated on the card-local `isLaunching` or on the `launching`/`drm-setup`/`engine-download`/`steam-starting` statuses. The grid card's own Play button (~L306-323) is gated on both. A context-menu Play clicked during bridge pre-flight is therefore a direct second launch. This is the most likely UAT 38 source.
- **Grid card plus GamePage.** Each component keeps its own `isLaunching` React state (GameCard L113; the GamePage MainButton reads backend status). A Play on the card followed by navigating to the game page and pressing Play there produces two IPC calls, unless a backend status has already arrived. Steam bridge pre-flight sends no `launching` status of its own early on.
- **The `gamelib://launch` deep link** (`protocol.ts` `handleLaunch`, L76), for example a desktop shortcut double-clicked.
- **The SteamBridgeSetup fallback** (`src/frontend/screens/Game/GamePage/components/SteamBridgeSetup.tsx` L106). It calls `window.api.launch` directly.
All four reach `dispatchSteamLaunch` (Steam) or `launchEventCallback` (other runners). **A guard at those two funnels covers every entry point.** No frontend change is needed, and gating the context menu would only be cosmetic once the backend joins.

**3. G26 is kept and is not provably redundant.** On the IPC path the new guard and G26 cover
the same span. `dispatchSteamLaunch` settles exactly when `launchBridgeGame` settles, so on that
path G26 never sees a joiner. But `SteamGame.launch()` is a public `Game` interface method. Any
direct caller (tests, `launchEventCallback` if handed `runner: 'steam'`, future code) bypasses
`dispatchSteamLaunch`. G26 stays as the inner bottle-level defence, and its tests stay as they
are. The quick/261024-gvu bottle-monitor guard (SteamGame.launch ~L3881-3892) also stays. It
covers Plays after the launch has started, which is outside both single-flight spans.

<design>
Guard placement and semantics. These are binding for the executor.

- **One shared map** in the new `src/backend/launchSingleFlight.ts`: `Map<string, Promise<unknown>>`, keyed `` `${runner}:${appName}` ``. It has no imports beyond types, so neither launcher.ts nor launchDispatch.ts gains a new import cycle.
- `singleFlightLaunch<T>(runner: string, appName: string, onJoin: () => void | Promise<void>, run: () => Promise<T>): Promise<T>`. The check-and-set is **synchronous at call entry**, with no `await` before it. If an entry exists: call `onJoin()`, catch and drop a rejection from it (`Promise.resolve().then(onJoin).catch(() => undefined)` style, so a throwing notifier cannot reject the joiner), and **return the existing promise** (cast to `Promise<T>`). Otherwise: `const p = run()`, set the entry, then attach `p.finally(() => { if (map.get(key) === p) map.delete(key) }).catch(() => undefined)` and return `p`. This mirrors the G26 code in games.ts L4870-4898 exactly. The joiner awaits the same promise: it gets the owner's value and rejects if the owner rejects. This matches G26, whose tests assert both callers resolve to the body's value and both reject on a body rejection.
- `resetLaunchSingleFlightForTests()` clears the map.
- **Steam** (`dispatchSteamLaunch`): move the current body into an inner `async function runDispatch(appName)` and make `dispatchSteamLaunch` a non-async function returning `singleFlightLaunch('steam', appName, onJoin, () => runDispatch(appName))`. `onJoin` is async. It logs `dispatchSteamLaunch: appId ${appName} launch already in progress; joining it (WR-03)` via `logInfo` with `LogPrefix.Steam`, then lazily imports `backend/storeManagers` for the title. It calls `notify({ title, body: i18next.t('gamelib:steam.bridge.alreadyLaunching', 'This game is already starting. Wait for its window to open.') })`, reusing the existing catalog key so no locale or i18n-baseline change is needed. Copy the `// eslint-disable-next-line import-x/no-named-as-default-member` comment from games.ts L4877-4878, and wrap the body in try/catch that sends errors to `logWarning`. The joiner never reaches `SteamGame.launch()`, so G26's own notify is not fired and the user sees exactly one notification.
- **Non-Steam** (`launchEventCallback` in launcher.ts L115): rename the existing arrow to `runLaunchEventCallback`, unchanged. Add `const launchEventCallback: (args: LaunchParams) => StatusPromise = (params) => singleFlightLaunch(params.runner, params.appName, onJoin, () => runLaunchEventCallback(params))`. It is a plain non-async arrow so the check runs before `runLaunchEventCallback`'s `await import('backend/storeManagers')`. `onJoin` here only calls `logInfo(\`Launch of ${appName} (${runner}) already in progress; joining it (WR-03)\`, LogPrefix.Backend)`. It does **no notify**: for these runners the in-flight span covers the whole play session (`await command` resolves at game exit), so "already starting" copy would be wrong mid-session, and the frontend already shows launching/playing status. The export list at L2221 keeps the name `launchEventCallback` and now exports the guarded wrapper. Update the stale launcher.ts comment above the `runner === 'steam'` block (~L219-231) with one line noting that Steam does not reach this callback today (sidecar and protocol both use `dispatchSteamLaunch`), and leave the code in place.
- **Effect on non-bridge runners.** Native-Steam (`steam://` hand-off) and bottled-Steam launches go through `dispatchSteamLaunch` too. A second Play during the short hand-off window joins and gets one notification instead of a second `openExternal`/`-applaunch`. For legendary, gog, nile and sideload, a second concurrent launch from the context menu, game page or deep link now joins the running `launchEventCallback` and returns its status at game exit, instead of starting a second process and running the before/after scripts twice. A deep link for an already-running non-Steam game no longer starts a second instance. The guard is released when the launch settles (exit, kill via `sendKill`, error or abort), so relaunch after exit is unchanged. No change to `game.launch` implementations, status updates, play-session recording or CLI `app.exit`, all of which run once, in the owner.
</design>
