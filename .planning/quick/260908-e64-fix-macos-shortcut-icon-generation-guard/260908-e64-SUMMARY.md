# Quick Task 260908-e64: Fix macOS Shortcut/Icon Generation Guard Summary

**Guarded and awaited `getIcon` (async, `Promise<string | undefined>`) closes both the `install_path!` non-null-assertion throw and the fire-and-forget download race that produced `ENOENT`, with all 4 real call sites degrading to an iconless shortcut instead of deleting the `.app`.**

## Performance

- **Duration:** ~50 min
- **Tasks:** 3
- **Files modified:** 4 source files + 1 new test file + 1 todo file (rename + edit)

## Accomplishments

- Fixed DEFECT 1: `getIcon`'s gog branch no longer dereferences `gameInfo.install.install_path!`; an absent `install_path` now falls through to the `getProductApi` lookup instead of throwing `TypeError [ERR_INVALID_ARG_TYPE]`.
- Fixed DEFECT 2: `downloadImage` is now `async` and awaits `downloadFile`; `getIcon` awaits `downloadImage` and re-verifies `existsSync(icon)` before returning a path, eliminating the race that produced `ENOENT` on a correct install.
- Propagated the resulting `Promise<string | undefined>` through all 4 real call sites (linux `.desktop` generation, `convertPngToICNS`, `generateMacOsApp`, `addNonSteamGame`'s `newEntry.icon` assignment) with `logWarning` at each no-icon branch.
- Removed the destructive behavior in `generateMacOsApp` where a failed icon conversion deleted the just-created `.app` bundle (D-04) — the `.app`/`Info.plist`/`run.sh` are now written unconditionally; only the `CFBundleIconFile` plist key is conditional.
- Added `src/backend/shortcuts/__tests__/getIcon.test.ts` with 4 tests against the real `getIcon`/`downloadImage`, RED-proven for the 3 defect cases at base commit `eedf46e64` and GREEN against the fix.
- Closed the 2026-09-07 todo: moved to `.planning/todos/completed/`, `status: RESOLVED`, corrected `files:` list, recorded per-defect resolution mapping.

## Decisions Made

- Made both `getIcon` and `downloadImage` `async`/awaited end-to-end (per plan D-01/D-02) rather than adding a synchronous poll, since the plan required propagating the nullable return through all call sites rather than papering over the race.
- Kept `convertPngToICNS`'s existing `catch`'s `logError` byte-unchanged (D-05) — genuine failures still log at error level; only the new expected no-icon branches use `logWarning`.
- Serialized `prepareImagesForSteam`'s per-image downloads (D-07) as an unavoidable consequence of awaiting `downloadImage` at `steamhelper.ts:116`; this makes the previously-dead `if (error) errors.push(error)` branch reachable for the first time. At most 4 images per game, each abort-signalled — accepted per threat model T-e64-04.
- `generateMacOsApp` restructured (D-04) so `.app`/`Info.plist`/`run.sh` are written unconditionally; only the `CFBundleIconFile` plist key pair is conditional on `convertPngToICNS` succeeding.

## Deviations from Plan

None — plan executed exactly as written. All decisions (D-01 through D-07) and both tasks' `<action>`/`<done>` criteria were followed as specified.

One implementation-level discovery during Task 3 (not a deviation from the plan, since it did not change any planned behavior or file): this project's jest config sets `resetMocks: true`, which strips even a `jest.fn(impl)` constructor-supplied implementation before EVERY test (not just tests after the first). The test file's `jest.mock('backend/utils/aborthandler/aborthandler', () => ({ createAbortController: jest.fn(() => new AbortController()) }))` factory's inline arrow was therefore wiped before each test ran, causing the real (unmocked) `downloadImage`'s `createAbortController(imageURL).signal` to throw on `undefined`. This was caught by `downloadImage`'s own `try/catch` and silently reported as a download failure — masking the exact behavior test (b) exists to prove. Fixed within Task 3 (before committing) by adding a `beforeEach(() => { mockedCreateAbortController.mockReturnValue(new AbortController()) })`. No plan file or done-criteria was affected; this is test-harness plumbing, not a source-code change.
