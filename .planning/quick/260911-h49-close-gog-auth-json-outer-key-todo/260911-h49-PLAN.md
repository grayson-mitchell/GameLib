**F1 — The outer key is gogdl's OAuth `client_id`.** From gogdl's vendored source,
`.build-tools/runners-onedir/src/gogdl/gogdl/auth.py`:
- L1-2 docstring: `# Manages authorization` / `# with ability to have multiple tokens (will come in handy in the future)`
- L11: `CLIENT_ID = "46899977096215655"` — exactly the value the todo flagged as an unknown identifier
- L130 (`handle_cli`, `--code` exchange): `self.credentials_data.update({CLIENT_ID: data})`
- L114 (`refresh_credentials`): `self.credentials_data.update({client_id: data})`
- L39-63 `get_credentials(self, client_id=None, client_secret=None)`, L51:
  `credentials = self.credentials_data.get(client_id)` — reads BY client_id, defaulting to `CLIENT_ID`

The file is a dict keyed by client_id by design. The outer key is never meant to equal `user_id`.

**F2 — This repo already ships that value as a client_id.**
`src/frontend/screens/WebView/loginRoutes.ts:48` builds the GOG OAuth URL with
`client_id=46899977096215655`. The "unknown identifier" is our own constant.

**F3 — gogdl puts both ids in ONE URL, proving distinct spaces.**
`.build-tools/runners-onedir/src/gogdl/gogdl/saves.py`:
- L202: `self.credentials = self.auth_manager.get_credentials(self.client_id, self.client_secret)`
- L212: `f"{constants.GOG_CLOUDSTORAGE}/v1/{self.credentials['user_id']}/{self.client_id}"`

`user_id` and `client_id` are two separate path segments of the same URL. This is the
"multiple tokens" case from the L1-2 docstring: per-game cloud-save client credentials
(`get_auth_ids()`, L112/L193) for the SAME account.

**F4 — Nothing in this repo writes `auth.json`.**
- `src/backend/storeManagers/gog/constants.ts:7` defines `gogdlAuthConfig`
- `src/backend/storeManagers/gog/library.ts:1521-1532` passes `--auth-config-path` to the gogdl binary
- `src/backend/storeManagers/gog/user.ts:360-361` — the only other use: `unlinkSync(gogdlAuthConfig)` on logout
- `src/backend/storeManagers/gog/user.ts:245` reads `resolved.user_id`

No code anywhere reads the outer key. This answers the todo's own Fix-sketch question
("trace the write path ... determine what the outer key is supposed to represent")
definitively: gogdl writes it, keyed by OAuth client_id.

**F5 — The live file was re-confirmed this session.** Outer key `46899977096215655`,
nested `user_id` `54283569140944678`. Both observed values in the todo are CORRECT. The
observation was right; the interpretation ("mismatch", "oddity") was wrong.

**F6 — The todo's forward-looking risk is INVERTED, and the real hazard is worth recording.**
The todo warns that multi-account support would make "this mismatch silently resolve to
the wrong account". Backwards: multiple outer keys are multiple CLIENT SCOPES for the SAME
account, never multiple accounts. The genuine hazard is the opposite shape — every GOG
account collides on the SAME key `46899977096215655`, so signing into a second account
OVERWRITES the first account's token in place. `refresh_credentials` (auth.py:97)
hardcodes `self.credentials_data.get(CLIENT_ID)` to source the refresh token, so there is
exactly one slot for the primary session. Multi-account support needs a different keying
scheme entirely — not a reconciliation of key vs field.
