## What was found

The todo observed correctly and interpreted wrongly. `auth.json`'s outer object key
(`46899977096215655`) is gogdl's OAuth `client_id` namespace, not a user id, and was never
meant to equal the nested `user_id` field (`54283569140944678`). Traced in
`.build-tools/runners-onedir/src/gogdl/gogdl/auth.py`: `CLIENT_ID = "46899977096215655"`
(`:11`), a dict keyed by client_id by design (`:39-63`, `:114`, `:130`), per the module's
own docstring ("ability to have multiple tokens"). This repo already ships that same value
as a `client_id` at `src/frontend/screens/WebView/loginRoutes.ts:48`, and gogdl's own
`saves.py:202`/`:212` puts `user_id` and `client_id` side by side as two segments of one
cloud-save URL — proof they are distinct identifier spaces that legitimately coexist.
Nothing in this repo writes or reads the outer key (`user.ts:245` reads `resolved.user_id`;
`user.ts:360-361`'s only touch is `unlinkSync` on logout), so there was never a fix
available here — gogdl owns the shape entirely.

## (b) Multi-account keying hazard recorded as prose, not filed as a todo

The todo's forward-looking risk was inverted: it warned that multi-account support would
make "this mismatch silently resolve to the wrong account," but multiple outer keys mean
multiple *client scopes* for the *same* account, never multiple accounts. The real hazard —
every GOG account collides on the single key `46899977096215655`, so a second account's
login overwrites the first account's token in place, because `refresh_credentials`
(`auth.py:97`) hardcodes `CLIENT_ID` as the one refresh slot — is recorded only as design-note
prose inside the Resolution section. Per the plan's `<out_of_scope>`, no new todo was filed:
it describes a feature (multi-account support) that does not exist yet.
