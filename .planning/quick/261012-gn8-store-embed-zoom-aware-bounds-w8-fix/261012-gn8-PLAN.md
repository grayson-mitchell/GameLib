## Diagnosis (verified by the planner by reading the code at 4c3e745b9; the executor re-confirms by reading these exact lines, never by assumption)

1. **Unit mismatch, all three platforms.** `useStoreEmbedHost.ts` `flush()` (around lines
   258-276) sends `slot.getBoundingClientRect()` verbatim as `{x, y, w, h}` to
   `storeEmbedOpen`/`storeEmbedSetBounds`. Those values are CSS px. Rust consumes them as
   logical px:
   - macOS/Windows: `src-tauri/src/main.rs` `store_embed_open` calls
     `window.add_child(..., LogicalPosition::new(x, y), LogicalSize::new(w, h))` (around line
     6624), and `store_embed_set_bounds` calls `set_position(LogicalPosition)` /
     `set_size(LogicalSize)` (around lines 6841-6846).
   - Linux: `store_embed_linux_gtk_rect` rounds the same logical rect into the `i32`
     `gtk::Fixed` coordinates used by `linux_store_embed_layout::mount` / `apply_bounds`. GTK
     logical units are logical px too.

   App zoom is a WEBVIEW zoom. `tauriSetZoomFactor` calls `getCurrentWebview().setZoom(factor)`
   (WebView2 ZoomFactor, WKWebView pageZoom, WebKitGTK zoom level), which shrinks the CSS
   viewport by f. Under zoom f the embed is therefore drawn at 1/f scale and shifted toward the
   window origin, on every backend.

2. **The existing-embed open drops the rect on macOS/Windows.** This is the half that makes W8
   fail even with scaling. `store_embed_open`'s `if let Some(existing)` branch (around lines
   6479-6501) re-applies the rect only under `#[cfg(target_os = "linux")]`. On macOS and Windows
   it calls `show()` and then `navigate()`, and the open rect is discarded.

   The hook unmounts on every route leave and remounts on return. Its single initial
   ResizeObserver observation is consumed by that `storeEmbedOpen`, so nothing else re-sends
   bounds.

   Zoom is changed on a separate screen. `src/frontend/screens/Accessibility/index.tsx` calls
   `GlobalState.setZoomPercent`, which starts a 500 ms timer before calling
   `window.api.setZoomFactor`. So on a return to Stores at 120% the embed keeps its 100%
   geometry while the chrome around the slot has grown. That matches "overlaps the increased
   size".

   The same reasoning predicts a latent, unmeasured sibling: a window resized while away from
   the store route leaves the embed stale on return.

   Fixing this on the Rust side would add a second `set_position`/`set_size` call site, which
   D-18/T-40-02-03 forbids. It would also rebuild the running dev instance. Instead the renderer
   follows every successful open with its own throttled `setBounds`, through the already-guarded
   `store_embed_set_bounds`, whose zero-area guard drops a 0x0 rect on macOS/Windows.

3. **Ordering.** `publishWebviewZoom` writes `--webview-zoom` only AFTER `setZoom` resolves. A
   resize or RO tick caused by the zoom change can run first and read the stale factor, so the
   re-flush has to be keyed on the property write itself. A MutationObserver on
   `document.documentElement` (attribute `style`) does that without touching the preload. The
   factor is read from the root's INLINE style (`document.documentElement.style.getPropertyValue`):
   that is exactly where the preload writes it, and an inline read forces no style recalc during
   a 25 Hz drag. `src/frontend/screens/Library/index.css` already treats this property as the
   source of truth (`var(--webview-zoom, 1)`).

## Interfaces (to create)

- `readWebviewZoomFactor(): number`. Returns 1 when `typeof document === 'undefined'` or there is
  no `documentElement`. Otherwise reads `document.documentElement.style.getPropertyValue('--webview-zoom')`,
  trims it and converts with `Number(...)`. A result that is non-finite or <= 0 returns 1;
  otherwise the number. Never throws.
- `scaleRectForZoom(rect: { x: number; y: number; width: number; height: number }, factor: number): StoreEmbedBounds`.
  Normalises the factor first: non-finite or <= 0 becomes 1. Returns
  `{ x: rect.x * f, y: rect.y * f, w: rect.width * f, h: rect.height * f }`. No rounding: macOS
  takes f64 verbatim, and Linux rounds in Rust (`store_embed_linux_gtk_rect`).
- Derive `StoreEmbedBounds` from the real IPC type,
  `Parameters<typeof window.api.storeEmbedSetBounds>[0]`, the same derive-don't-redeclare pattern
  the hook uses for its nav types. `src/backend/store/storeEmbedSeam.ts` has a same-named
  interface, but the frontend does not import from backend.
- Export only these two functions. Keep the property-name literal module-private, because
  `pnpm find-deadcode` (ts-prune) flags exports used only within their own module.
