## Minimal two-value swap, NOT reuse of `nintendoHatDirection`

The brief required this be decided, not assumed. Both options were evaluated against the actual
helper (`nintendo.ts:199-218`).

**Reuse is behaviourally equivalent, so this is not a correctness question.**
`nintendoHatDirection` switches on `Math.round(hatValue * 10)` with cases `-10 -> 'up'`,
`1 -> 'down'`, `7 -> 'left'`, `-4 -> 'right'` and `default -> null`. That is the same transform,
the same four cardinals, and the same everything-else-is-null treatment that the corrected
`checkN64Clone1` needs. Routed through it, the N64 clone would produce identical output. The
choice is therefore about PROVENANCE and OWNERSHIP, not about which one works.

**Chosen: the minimal swap, because this file has a written, repeated rule against exactly the
coupling reuse would create -- and the helper itself is one of the places that states it.**

1. `nintendoHatDirection`'s own comment (`:196-198`) says: *"`checkN64Clone1` below uses DIFFERENT
   constants for a DIFFERENT device, and its own comment and code already disagree with each other
   -- do not copy that row here, and this function does not change it."* The instruction is
   bidirectional in spirit and explicit in one direction.
2. `RAW_HID_STICK_AXES`'s comment (`:154-158`) states the same rule for a second pair of
   functions: *"`checkGamecube` at :27-30 uses axes[3]/axes[4] for a DIFFERENT device in this same
   file, and axes[3] was live-FALSIFIED as this pad's right-stick axis. Do not copy that row here
   ... Same rule this file already applies to `checkN64Clone1`'s hat table: derive from
   observation and say so."* That rule was not abstract -- borrowing `checkGamecube`'s axis row
   was measured WRONG for the PowerA pad on 2026-09-25.
3. `nintendoHatDirection`'s comment body is a MEASUREMENT RECORD for one specific device (PowerA,
   Vendor 20d6 Product a720, measured 2026-09-23 21:04-21:12) and records a divergence from the
   generic convention: its measured NEUTRAL is `3.28571` where the convention predicts `1.28571`.
   A device whose cardinals match the convention can still have a rest value that does not.
   Making that measurement record the shared contract for a second, entirely unmeasured device
   class is the precise failure the two comments above exist to prevent. If a future N64-clone
   measurement diverges the way the PowerA's neutral did, a shared helper has to be split back
   apart -- churn bought with nothing.
4. The scope fence excludes changing `checkNintendo`/`nintendoHatDirection` behaviour. Reuse
   would not change behaviour, but it would change the helper's contract from
   "one measured device's table" to "two device classes, one measured" and force its comment to
   be rewritten device-generically -- deleting measurement provenance to serve a two-token fix.

**Cost of the choice, stated honestly:** the comparison logic now exists twice in this file,
spelled differently (a `switch` returning a direction in one place, four `===` comparisons in the
other). That duplication is deliberate and is the point -- two devices, two independently-sourced
tables. Task 2 writes that rationale in-situ so the next reader does not re-litigate it.
</implementation_decision>
