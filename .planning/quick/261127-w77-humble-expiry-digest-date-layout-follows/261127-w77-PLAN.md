regional-locale plumb from the shell. `en`, and any language without a pattern, stays on `M/D/YYYY`, so the existing
`golden/alerts` cases keep replaying. The calendar day is still read in the host zone, and only the layout changes.
Each non-en layout gets at least one unit case. The todo is closed as the last step. The related todo
`2026-11-24-humble-digest-text-is-html-escaped` is left alone.

Decisions this plan takes (Claude's discretion, each recorded in the todo's Resolution):

- **The TypeScript gets no change.** `src/backend/humble/expirationAlerts.ts` is live today. The sidecar's `humbleSync`
  channel (`src/backend/sidecar/humbleFlowRegistration.ts`) runs `library.ts`'s sync, which calls
  `detectAndNotifyExpirationTransitions` at `src/backend/humble/library.ts:1236`. The Rust digest has no caller until
  94-25 wires it. After the Rust cutover the TS is not live, because 94-30 deletes `src/backend/humble/` entirely. So
  the Rust digest is the only one that exists when this policy reaches users. Changing the TS now would mean re-pinning
  its jest test (`src/backend/humble/__tests__/expirationAlerts.test.ts:405`) and the oracle's en-US date spy
  (`src/backend/humble/__tests__/oracle/secretsAlerts.oracle.test.ts:887-903`), for code with one phase left to live.
  Until 94-25 and 94-30 land, users keep the TS's host-locale date, and the UI-language layout arrives with the cutover.
- **No golden re-record.** The date is a recorded param (`i18nCalls[1][2].date`). Every `golden/alerts` case was
  recorded at `locale: 'en'` with the en-US date pin, and `en` keeps `M/D/YYYY`, so all 11 cases replay byte for
  byte. A non-en golden cannot be recorded from the TS oracle: the TS stays on the host locale and the oracle pins
  en-US. Each non-en layout is therefore pinned by a Rust unit case whose expected strings are the Intl measurement in
  `<interfaces>`. That measurement, not the layout code, is the source of the expected values.
- **Every shipped language gets a layout**, not a hand-picked subset. Without one, a `de` user would get the
  `M/D/YYYY` layout, which is the defect this todo describes. The test fails if a language is added to
  `SHIPPED_LANGUAGES` without a measured row, so the next language forces a decision.
- **`fa` is the one exception to the Intl rule.** Its default renders the Solar Hijri calendar in Persian digits
  (`۱۴۰۵/۱۰/۱۲`). A layout over the Gregorian civil day cannot express that, so `fa` takes CLDR's Gregorian Latin-digit
  layout (`fa-u-ca-gregory-nu-latn`: `2027/1/2`). Year-first is unambiguous, and the `M/D/YYYY` fallback is not.
- **`ar` keeps CLDR's U+200F RIGHT-TO-LEFT MARK after the day and after the month**, which is what Intl renders.

Observation, not a blocker: only `public/locales/en/translation.json` translates `humble.notification.*`. Every other
language falls back to the English sentence, so a `de` user sees the English sentence with a `2.1.2027` date. That
matches the UI language the user chose. When the keys are translated, the sentence and the date will agree.

Purpose: after the Humble cutover, a non-English user sees the date in their own language's layout, not a US-order
date.
Output: `Catalog::language()`, `digest_date` with a per-language layout table, a measured unit case for every shipped
language, and the todo closed.
