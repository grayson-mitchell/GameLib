# Quick 260911-j88: Flip the frontmatter gate's controls, add a divergence-shape check, and repair two misfiled records Summary

## What was built

`planning-frontmatter-gate.py`'s own self-test used to ACCEPT, as its positive control, a document
with both narrative fields written as `|-` block scalars — exactly the shape that empties those
fields for every GSD tool that isn't the gate itself, because the SDK's hand-rolled
`parseFrontmatterYamlLines` has no block-scalar support and returns the literal two-character
string `"|-"`, and `phase-lifecycle.js:1122`'s regex rewrite then orphans everything beneath it.
The gate's positive control was the bug. Four tasks, one atomic commit each:

1. **Flipped the gate's controls and added a shape-based divergence check.** `VALID_STATE_DOCUMENT`
   is now single-line single-quoted (the shape `STATE.md` ships today), with a raw `"` and a
   doubled apostrophe (`''`) both present in `stopped_at`. Added `mutate()` so every mutation of
   that base document fails loudly on a missed string anchor instead of silently handing a REJECT
   case an unmutated, still-valid document (proven by a negative control: a corrupted copy of the
   gate genuinely fails its own self-test). Added `check_divergence_shapes()` — a pure regex-based
   check, not a second parser — that rejects a bare block-scalar indicator (`|`, `|-`, `|+`, `>`,
   `>-`, `>+`) and a double-quoted scalar containing a backslash-escaped `\"`, on both required and
   optional targets, while deliberately accepting the one divergence this repo already lives with
   (`''`). Five new self-test cases added (18 total); rewrote the docstring and the self-test
   summary prose, since both used to assert the now-false claim that `|-` is correctly accepted.
2. **Deleted a duplicate `finding:` key** in `.planning/debug/resolved/epic-login-non-interactive.md`
   (identical value on both lines; js-yaml was throwing `duplicated mapping key`).
3. **Relocated five misfiled fields** in `34.1-VERIFICATION.md`: `moved_as: "38-W01"`, `moved_on`,
   a `platform_gate` naming `App.tsx:79`, `was_uat_item: "1a"`, and a `note` naming plan `34.1-09`
   were sitting inside the *Tray* item's mapping (after a stray blank line, duplicating that item's
   own `moved_on`/`platform_gate` keys) but actually describe the *Window buttons* item. Moved via
   line-slice, never retyped; a multiset diff proved no line was altered or invented.
4. **Re-scoped the block-scalar todo** to the corrected population: the original 53 js-yaml
   failures were cosmetic (all read correctly by the SDK; 51 contain an apostrophe, so fixing them
   for js-yaml would have injected `''` into 51 perfect reads). The real defect is 64 files / 92
   block-scalar fields, 56 of which (53,081 characters) read as the literal `"|-"`/`">-"` through
   every SDK consumer. Ran the bounded severity check the plan required and found it disagreed with
   the plan's own background claim — documented below.

## Deviations from Plan

### Auto-fixed / adapted issues (not Rule 1-3 bugs — verify-script adaptations, per plan's explicit "expected deviations")

**1. [Expected deviation, Task 1 verify step 3] The `for pat in ...` loop's redundant discarded
grep.** Ran the intent directly instead: for each pattern (`|-`, `>-`, `escap`, `optional`),
`grep -i "$pat" <<<"$OUT" | grep -c "correctly rejected"`. All four returned non-zero (4, 1, 1, 1).

**2. [Not listed in "expected deviations", found during Task 3] `String(Date)` date-format
assertion in the plan's own verify script.** `34.1-VERIFICATION.md`'s Window-buttons item carries
`moved_on: 2026-08-22` UNQUOTED (per the plan's own instruction to preserve it exactly, not
normalize it to match the Tray item's quoted `"2026-08-22"`). js-yaml auto-casts an unquoted
`YYYY-MM-DD` scalar to a native JS `Date` object, so `String(win.moved_on).slice(0,10)` yields
something like `"Sat Aug 22"` (a `Date.toString()` prefix), not `"2026-08-22"` — the plan's
`.replace(/-/g,"").length!==8` check threw `"moved_on missing"` on a field that was, in fact,
present and correctly valued. Confirmed live: `moved_on instanceof Date === true`,
`moved_on.toISOString() === "2026-08-22T00:00:00.000Z"`. Adapted the assertion to check
`win.moved_on instanceof Date && win.moved_on.toISOString().slice(0,10) === "2026-08-22"` instead
— same intent (prove the field exists and carries the right date), correct for the actual js-yaml
type. This is a verify-script artifact, not a defect in the relocation: the multiset diff (Task 3
verify step 1) independently proved every field value byte-preserved.

**3. [Expected deviation, Task 4 verify step 6] Corpus total rose from 2448 to 2449.** Expected —
this task's own PLAN/SUMMARY/todo edits add frontmatter-bearing files to the corpus. The number
that matters, the FAILURE count, landed exactly on the required **51** (down from 53 via Tasks 2+3).

**4. [Found during Task 4's required bounded severity check — a genuine correction, not a bug fix]
The plan's action block asserted "`audit-open.js` genuinely reads `description`."** The task
instructed running a bounded check to decide `severity: medium` vs. `major` before writing the
todo. Checked both currently-resolved copies of that tool
(`~/.claude/get-shit-done/bin/lib/audit.cjs` and the npx-cached `get-shit-done-cc@1.42.3`'s
`sdk/{src,dist}/query/audit-open.{ts,js}`): neither reads `description`, `notes`,
`disposition_note`, `evidence`, `rationale`, `resolution`, or any `gap_*` field from frontmatter.
`scanQuickTasks`' `description` variable is a hardcoded empty string in both copies, never
assigned from `extractFrontmatter()`'s result. The fields actually read across `audit-open`'s scan
functions are `status`, `updated`, `date`, `priority`, `area`, `title`, and `open_questions`. Per
the plan's own instruction ("if the check is inconclusive... keep medium... do not assert
contamination you did not verify"), this is a conclusive negative result, not an inconclusive one
— so `severity` stayed at `medium`, and the todo documents the discrepancy explicitly with the
files/line evidence, rather than silently carrying forward a claim this task's own required check
did not support. Files/paths that back this: both tool copies listed above; no line numbers cited
because the search was for absence, not presence.
