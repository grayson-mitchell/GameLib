<dedupe_design>
**Chosen: shim-side dedupe against what WebKit actually reports (options b and c combined), with
explicit identity fields in the native payload. Option (a) is rejected.**

- Native payload carries `name` (gilrs `os_name()`), `vendorId` and `productId` (numbers or null)
  alongside the Chromium-shaped `id`, so the shim never has to parse its own id.
- On every `getGamepads()` call the shim computes, for each native pad, whether any non-null
  browser pad is the same device. The rules, in order:
  1. exact `id` equality (the prototype's rule);
  2. the browser id matches the WebKit HID format `^([0-9a-f]+)-([0-9a-f]+)-`, and the parsed
     vendor and product equal the native vendorId and productId;
  3. the browser id matches the WebKit GameController format `^(.*?) (Extended )?Gamepad$`, and
     the captured vendorName equals the native `name` after normalising both sides (lowercase,
     trimmed, internal whitespace collapsed).
  A suppressed native pad's slot is left null, so `gamepad.ts`'s `updateStatus` skips it while
  the browser copy drives. Exactly one copy acts at any moment.
- Gesture-gate timing: WebKit exposes a pad only after a press, so the native copy may be
  announced first. The shim adds a `gamepadconnected` listener on window that ignores events it
  dispatched itself (mark them, e.g. with a module-level WeakSet). When a real browser pad
  connects, the shim re-evaluates and dispatches `gamepaddisconnected` for any native pad that is
  now suppressed, and logs `[NATIVE-GAMEPAD] suppressed slot=N id=... matched=...` through
  `window.api?.logInfo?.` so live check L4 can be read from gamelib.log. A native pad that is
  suppressed when it first connects is never announced at all. A native pad is announced only
  while unsuppressed.
- Why not (a), skipping GameController-claimed pads natively: `[GCController supportsHIDDevice:]`
  is the exact predicate WebKit uses to drop a device from its HID path. The spike shows the
  PowerA pad is missing from BOTH WebKit paths, and offline we cannot rule out that
  GameController claims the pad yet never produces a GCController for it. If that is the case,
  (a) would hide the very pad this task lands. It also needs IOHIDManager and GameController FFI
  that cannot be tested offline. Dedupe against the pads WebKit really returns is
  self-correcting: it suppresses only when a browser copy exists right now. Rules 1-3 are pure
  string logic, fully unit-testable.
- Residual risk: rule 3 assumes GameController's vendorName equals the HID product string. If it
  does not, a GameController-claimed pad (Xbox, DualSense) would double-drive after the first
  press. L4 checks this live. If L4 fails, record the observed browser id in the SUMMARY and open
  a follow-up rather than widening the match blindly.
</dedupe_design>
