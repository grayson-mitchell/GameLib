**1. Bare `graphify` DOES resolve in the environment hooks actually run in. Measured, not assumed.**

Every live `claude` CLI process (pids 7092, 8048, 73894, 90481, 93253) carries
`/Users/graysonmitchell/.local/bin` at position 3 of its `PATH`. The hooks docs state a hook process
*"inherits the parent environment"* apart from `OTEL_*` and the `CLAUDE_CODE_SUBPROCESS_ENV_SCRUB`
set. So hooks get that PATH without sourcing any profile.

Confirmed by direct execution, profile-free:

    env -i PATH="/Users/graysonmitchell/.local/bin:/usr/bin:/bin" HOME="$HOME" \
      sh -c 'graphify hook-guard read'   # -> valid hookSpecificOutput JSON, EXIT=0

`graphify` is a pipx shim for the `graphifyy` package. Its shebang points at the venv interpreter and
its body does `sys.argv[0].removesuffix('.exe')` — i.e. the package already expects a Windows `.exe`
launcher, so pipx on Windows will produce a PATH-resolvable `graphify.exe`.

**2. Use shell form with a bare command. Do NOT switch to exec form.**

Exec form (`"command": "graphify", "args": [...]`) would also resolve from PATH, but it adds an
`args` key — outside this task's scope — and the docs warn exec form on Windows *"requires a real
executable"*. Shell form is what is already there: `sh -c` on macOS/Linux, Git Bash on Windows, or
PowerShell when Git Bash is absent. All three resolve a bare command from PATH.

**3. Fail loudly. Do NOT add a `command -v` guard. Three reasons.**

The tradeoff the task asked to weigh, resolved:

- A missing binary exits **127**, and the docs are explicit that for `PreToolUse` *only exit 2
  blocks*. 127 lands in the "plain text or empty stdout" bucket: non-blocking error, tool call
  proceeds, transcript shows `Failed with non-blocking status code: ...`. So an absent graphify on
  Windows can never wedge the session — it nags visibly and work continues. That visible nag is the
  correct signal to run `pipx install graphifyy` on the Windows box.
- A guard (`command -v graphify >/dev/null && graphify hook-guard search`) exits 0 when the binary is
  missing, producing exactly the failure the docs warn about — *"a mistyped path in settings.json
  leaves the gate silently disabled"* — against a workflow CLAUDE.md calls mandatory.
- `&&` is not portable to the PowerShell 5.1 that Claude Code falls back to on Windows without Git
  Bash. The guard would be shell-dialect-dependent; a bare command is not.

**4. Two premises in the task brief are FALSE. Do not act on them.**

- *"The file is currently minified onto one line"* — it is **24 lines**, 2-space indented, and
  `diff <(npx prettier .claude/settings.json) .claude/settings.json` is empty: already
  prettier-canonical. Preserve the existing layout; reformatting is not part of this task.
- *"prettier-sensitive, will redden the push gate"* — `.claude` is listed in `.prettierignore`
  (line 30, under "Tooling/agent state and planning artifacts, not shipped source"), so
  `pnpm prettier` never walks this file at all. There is no push-gate exposure here. Verify anyway
  (cheap), but do not restructure the file in the name of prettier.

**5. A live in-session hook fire CANNOT verify this change. Use the reproduction gate instead.**

The docs say a file watcher normally picks up hook edits mid-session — but whether it did or not, the
`additionalContext` text emitted is *identical* for the old and new command strings. Observing the
hook fire after the edit therefore cannot discriminate between "new command works" and "old command
still loaded". Task 2's gate exists because of this: it extracts the command strings *from the edited
file* and executes them out-of-band, with a negative control to prove the gate can go red.
</findings>
