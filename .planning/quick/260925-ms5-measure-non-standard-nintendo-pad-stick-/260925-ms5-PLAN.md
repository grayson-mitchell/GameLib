<parity_gate>
**The parity question, and the honest state of it BEFORE the sitting.**

The concern is real and correctly raised: Chromium uses a different gamepad backend per OS (IOKit
HID on macOS, XInput/raw-HID on Windows), so the same physical pad can enumerate with a different
`mapping`, a different button count, and different indices. Measuring `buttons[10]`/`[11]` on one
OS and writing it into a table derived from a capture on another would fuse two device/OS profiles
into one.

**Two pieces of first-hand evidence found while planning, both of which bear on it:**

1. `ROADMAP.md:4648` records: **"SITTING 1 WAS HELD 2026-09-23 on the operator's Windows 11
   machine"** — that is the sitting that produced A1–A7. `STATE.md:1101` independently says the same
   ("Found LIVE during the Phase 38 controller sitting on the Windows machine"). So the original
   capture was Windows, not macOS. The CLAUDE.md platform-vocabulary inference ("`windows` = not the
   operator's primary OS" ⇒ primary is a Mac) is about which machine is PRIMARY, and does not
   establish where any given sitting ran.
2. `%LOCALAPPDATA%\GameLib\logs\gamelib.log` on THIS machine currently carries ten `[GAMEPAD]`
   connect lines, the most recent at **16:07 today (2026-09-25)**, every one of them reading:

   ```
   [GAMEPAD] id="PowerA Advantage Wired Controller for Nintendo Switch 2 (Vendor: 20d6 Product: a720)" mapping="" buttons=17 axes=10
   ```

   Byte-identical to the recorded triple. The 9de sitting earlier today also logged all ten axes
   with the hat at index 9 resting at `3.28571`, reproducing qe5's measured neutral exactly.

**So the gate is expected to MATCH, and this is now a strong prior rather than an open question.**
It is still not a substitute for the reading, for a reason that is not ceremonial: a USB re-plug into
a different port, a pad firmware change, a Chromium version bump behind a Tauri update, or a second
pad connecting first can all change what the NEXT connect line says. The line is free — it fires on
connect with no extra instrumentation. Read it.

**Three outcomes, all planned for:**

- **MATCH** (`mapping=""`, `buttons=17`, `axes=10`, same `id`) → the capture legitimately extends the
  same profile. Proceed to the presses. Record the line verbatim anyway.
- **ANY DIVERGENCE** in any of the four fields → **STOP. Do not press buttons as though the numbers
  are comparable.** A per-OS or per-connection enumeration difference is a MORE IMPORTANT fact than
  the original question, and it changes what `nintendo.ts` and `ConsoleMode` must do. Record the
  divergence verbatim as the finding, hand back, and take no source action beyond removing the
  instrumentation (Task 4) until the divergence has been discussed. Branch **P2** below.
- **NO `[GAMEPAD]` LINE AT ALL** → almost certainly NOT a defect. Chromium's Gamepad API withholds
  `gamepadconnected` until the page sees pad activity, so a freshly reloaded app reports no gamepads
  until a button is pressed. The procedure says so explicitly, in the operator's steps, so
  "nothing happened" is not misread as a fault. If a button HAS been pressed and still no line
  appears, that IS a finding — branch **P3**.
