<objective>
Fix the ir1 regression on Manor Lords (1363080). The Shipping exe imports steam_api64.dll only through
the PE Delay Import Directory, so the scan saw no importer and placed the shim anyway. The shim then
crashed the game, which had run offline before ir1.

This plan does three things:
- (A) Teaches the scan to read delay imports.
- (B) Adds a guard: when importer evidence names gaps the shim cannot serve, the shim is not placed (or is
  withdrawn) and the launch goes direct with the game's own steam_api.
- (C) Keeps a `.gamelib-orig` backup of every game-original dll the shim overwrites, and restores it when
  the guard trips.

Out of scope: implementing the missing interface versions (a separate todo the orchestrator writes);
teaching meta/bridgeCensus.ts about delay imports; and restoring Manor Lords' on-disk dll (the orchestrator
does that by hand).

Output: three test-then-fix commit pairs, in the same pattern as i94 and ir1.
</objective>

<decisions>
A. Delay-import reader. Use a zero-spawn, fd-ranged TS reader (`readPeSteamApiDelayImports`) in
   peSteamDrm.ts, not a second objdump spawn. Reasons:
   - The live evidence shows `objdump --private-headers` does not list delay imports. A different objdump
     flag would be a guess about Apple LLVM's output with no fixture to pin it.
   - peSteamDrm.ts already holds the bounded PE reader (readExact, caps, never throws) and the census's
     zero-import discipline.
   - The importer walk already spawns up to 512 objdumps per tree. A reader that never spawns adds
     ranged reads only.
   scanSteamApiImports merges the two sources and keeps the objdump argv form unchanged.

B. Which coverage outputs count as a gap. The guard trips only on importer evidence (the exe-imports
   branch, or a runtime-loaded dll with at least one same-arch importer), and only on these two gaps:
   - (1) A missing symbol that a PE delay-imports. The loader accepts it and the first call faults, so
     the game crashes at runtime instead of failing loudly at load.
   - (2) An unservable interface version: a required version not in the arch's served map that is
     either answered with NULL, or answered with the null object while the shim serves a different
     version of the same family (version skew, e.g. SteamFriends017 when 015 and 018 are served).
   These do not count, and oq7 behaviour is kept for each:
   - A static-import missing symbol. Windows fails it at load with an entry-point dialog. oq7 records
     this as "expected by design" and uses the miss to drive widening.
   - versionProblems (`@unknown-version`, `@ambiguous`).
   - Served-stub families (mode 'stub', the intentional 51-14 behaviour).
   - The x64 null object for a family with no served version at all. This is the designed D-51-13 answer
     ELEX relies on: SteamHTTP, SteamUGC and so on.
   - The '@runtime-loaded' marker with no importer evidence (Unity) keeps oq7's "placed-miss, place
     anyway". It is a different hazard: no static or delay import table names the symbols, and the
     game resolves them itself at call time.
   This is also the only rule that leaves every existing pinned test green. Withholding on static
   misses too would reverse oq7's user decision ("Place shim anyway") and flip the tests at
   shimGenerate.test.ts L338, 373, 391, 418, 494, 835, 996, 1161 and 1318. That is surfaced to the
   orchestrator and not done here.

B'. Status and the games.ts change. Add a new status, `'withheld'`, carrying
   `{ verdict: SteamBridgeScanVerdict; restored: string[] }`. Reusing 'no-steam-api' would need no
   games.ts diff, but it would lie about the evidence. It would also let reconcileBridgePrescreen write
   prescreen 'none' over 'unknown' for a title that does import steam_api. The games.ts diff is one
   condition plus one log line in launchBridgeGame. Install needs no change: the verdict is persisted
   generically, the status is not an error, and reconcile is a no-op for an unknown status.

C. Backup and restore.
   - The backup is `<target>.gamelib-orig` (suffix constant `ORIGINAL_BACKUP_SUFFIX`), contained in the
     bottle. It is written only from bytes that isGameLibShimBytes says are not a shim, so it is
     refreshed when a game update ships a new original and never overwritten by a shim.
   - If the backup cannot be written, placement returns 'error' and the target is left untouched. An
     original is never overwritten without a backup.
   - The dll walk matches names exactly and the importer walk needs a `.exe`/`.dll` extension, so the
     backup is excluded by construction. Tests pin both.
   - Restore runs only when the guard trips, and only over a target that is a GameLib shim. The backup is
     kept after a restore.

Known limit, reported and not fixed: Manor Lords today has a current shim on disk and no backup, so it
takes the pinned no-walk 'already-placed' path before any guard can run. It needs the orchestrator's
hand restore first. After that, the next launch evaluates, withholds and leaves the restored original
alone.
</decisions>
