**Why the same-module rows need code moved, not a cleverer mock.** Jest is `ts-jest` (CJS). A
cross-module call compiles to `gameX_1.fn(...)`, a property read at call time, so
`jest.spyOn(moduleNamespace, 'fn')` intercepts it. Existing proof: `jest.spyOn(gameMetadata,
'fetchMetadataIfNeeded')` and `jest.spyOn(gamesModule, 'isNativeInstallInFlight')`. A call inside
the same module compiles to a direct local reference, which no spy can reach.
`jest.mock(path, () => ({ ...jest.requireActual(path), fn: jest.fn() }))` does not help either:
it swaps the export, but the caller's local reference still points at the real function. The fix
is to move the callee into a sibling module so the call crosses a boundary:
- installNative and installBottleNative move to `gameInstallDepot.ts`. It already holds
  `installDepotDownload`, the only thing both of them call, and it does not import `gameInstall.ts`.
- `launchBridgeGame` and `runBridgeLaunch` (the ~45-line in-flight dedupe wrapper,
  gameBridgeLaunch.ts:62-105) move to a new `gameBridgeLaunchGate.ts`. That way `launchBridgeGameBody` (the
  large body) stays put and the wrapper reaches it across a module boundary.

**Import cycles (decision made here, flag in SUMMARY).** Two of the stubs are documented as
existing to avoid an import cycle (`prefetchBridgeDrmDownloads`, `fireBridgeWineLaunch`). Removing
all stubs makes these cycles real: gameInstall <-> gameInstallBridge, gameLaunch <->
gameBridgeWineLaunch, and gameLaunch -> gameBridgeLaunchGate -> gameBridgeLaunch -> gameLaunch.
Under both ts-jest CJS and the esbuild `--format=cjs` sidecar bundle, a cycle is harmless as long
as every cross-cycle import is only read inside a function body at call time, never at module top
level. Task 3 checks this. Plain static imports are the chosen fix. Do not add a lazy
`await import()` just for these calls: it adds microtask hops that can upset the deferred-promise
dedupe tests. If Task 3 finds a top-level read of a cycle partner's export, stop and report it.
Do not paper over it.
