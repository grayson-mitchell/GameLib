<findings>
Settled at planning time by reading the code and measuring. The executor relies on these and does not re-derive them.

F1 Timing (why a plain allowlist row is not enough).
- The helper pumps Steam's manual-dispatch queue ONLY inside DRAIN (slot 6), the WHOAMI warm-up `pump_callbacks()`, and, after this task, slot 9. Nothing pumps on a timer. A 1101 posted at helper init therefore waits in Steam's pipe until the first pump, then in `g_cbq` (8 slots, drop-oldest, never cleared on accept/close, bound to the launch secret).
- The shim drains only from `SteamAPI_RunCallbacks` and only while `gl_cb_relay_count > 0`, i.e. after the game registered a CCallback for a RELAYED id. It drains destructively (at most 4 per call, 30 ms apart) and drops a message whose id has no live non-gameserver target (`gl_cb_no_target`, 55 WR-05).
- In the ELEX run (gamelib.log, 01:27:36 helper init, 01:27:38 first HELLO, 01:27:45 RequestCurrentStats) there is not one CBQ line. That is expected and proves nothing about 1101: the pump logs only allowlisted ids, and with 168 as the only relayed id and ELEX registering no 168 listener, the shim never sent a DRAIN.
- Consequences built into the design: (a) the helper must pump when the game asks (slot 9), not wait for a drain; (b) a cached 1101 must be re-offered on request, because the init-time one may already have been forwarded and consumed or dropped; (c) the shim must hold a 1101 that arrives before its listener (possible when a 168 listener keeps the drain running), or a modern-SDK game that never calls RequestCurrentStats could lose its only 1101.

F2 Is 1101 received in the helper, and how to force it.
- Unverified from evidence (see F1: the pump never ran with 1101 visible). Modern Steam auto-requests stats at init, so a broadcast 1101 is likely but not proven.
- The Mac `libsteam_api.dylib` (nm, 2026-10-27) exports `SteamAPI_ISteamUserStats_RequestUserStats`, `SteamAPI_ManualDispatch_GetAPICallResult`, `SteamAPI_SteamUserStats_v013`, `SteamAPI_ISteamUser_GetSteamID`, and has NO RequestCurrentStats export. RequestUserStats returns a SteamAPICall_t whose result is a UserStatsReceived_t. Under manual dispatch a call result arrives as a `SteamAPICallCompleted_t` (k_iCallback 703; Mac pack(4): u64 m_hAsyncCall@0, i32 m_iCallback@8, u32 m_cubParam@12, size 16) and its payload is fetched with `bool SteamAPI_ManualDispatch_GetAPICallResult(HSteamPipe, SteamAPICall_t, void *pCallback, int cubCallback, int iCallbackExpected, bool *pbFailed)`, called BEFORE FreeLastCallback. Steam may also post a broadcast 1101 for the same fetch; whichever arrives first satisfies the pending request and the other only refreshes the cache.
- The helper already resolves `g_bd_self_steamuserstats_interface_version013`, `g_bd_self_steamuser023` and `g_bd_flat_SteamUser023_GetSteamID` (static in the included bridge_dispatch.h; WHOAMI uses the last two) and has `g_bd_identity_only`.

F3 Layout, measured with the repo-pinned zig (`.build-tools/zig/zig clang -cc1 -fdump-record-layouts-simple`) against an SDK-faithful declaration (uint64 m_nGameID; EResult m_eResult; CSteamID m_steamIDUser, where CSteamID is the SDK class wrapping a union of the bitfield struct and uint64 m_unAll64Bits; Windows under pack(push, 8), Mac/Linux under pack(push, 4) as in steam_api_common.h):
- x86_64-pc-windows-msvc: `Size:192 FieldOffsets: [0, 64, 128]` -> 24 bytes, 0/8/16.
- i686-pc-windows-msvc: `Size:192 FieldOffsets: [0, 64, 128]` -> 24 bytes, 0/8/16.
- arm64-apple-macosx (pack 4): `Size:160 FieldOffsets: [0, 64, 96]` -> 20 bytes, 0/8/12.
Both Windows arches agree, so the helper repacks once into the 24-byte wire form and the shim relay row is `{1101, 24}` for both DLLs. CGameID for a plain app is the appid as a full uint64 (type 0, mod 0), so the own-app check is `m_nGameID == strtoull(g_appid)`.
