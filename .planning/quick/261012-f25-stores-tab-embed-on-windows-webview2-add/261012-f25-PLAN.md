<objective>
Implement the in-app Stores tab embed on Windows (WebView2 `add_child`). This discharges the code
half of `.planning/todos/pending/2026-10-11-stores-tab-embed-not-implemented-on-windows.md`. The
shape mirrors quick `260930-blh` (the Linux arm), but Windows needs far less than Linux did.

**The positioning decision is settled by evidence, so no new Windows code path is needed.**
- Spike 027 read wry's WebView2 backend (`.planning/spikes/027-windows-add-child-crosscheck/README.md`,
  investigation step 5). Windows child webviews are real `WS_CHILD` HWNDs, and `set_bounds` is an
  unconditional `SetWindowPos`. That puts Windows in macOS's "real absolutely-positioned child"
  family, not Linux's GtkBox-packing family.
- Its live sitting-13 run on this machine's OS, at scale 1.25, drove the embed with exactly the
  macOS calls, `set_position(LogicalPosition)` + `set_size(LogicalSize)`
  (`app/src/main.rs:300-320`). Placement error was 0 px across three rects, and drag-resize
  passed (187 updates, gap median 43 ms).
- So Windows takes the macOS branch everywhere:
  - `add_child` with the renderer's logical rect;
  - `set_position`/`set_size` in `store_embed_set_bounds`;
  - the zero-area-rect guard (wry would `SetWindowPos` a 0x0 rect verbatim, which is the exact
    hazard quick 261001-svm measured on macOS);
  - the shared show-before-navigate existing-embed path.
- Nothing from `linux_store_embed_layout` compiles on Windows.

**Threading stays as it is.** Spike 027 found that `add_child` called from a SYNC Tauri command on
the main thread never returned on WebView2. GameLib's `store_embed_*` arms are reached only through
the sidecar RPC dispatch, and `dispatch_rust_channel` always runs on a `thread::spawn` worker
(`src-tauri/src/main.rs` ~7772). This plan adds no Tauri command and no new dispatch arm.
`tauriShellSource.test.ts`'s `newArms` must stay `['tray_set_icon']`.

**The `:unsupported-platform` branches.** Windows stops compiling them. The ten strings stay in
source, behind `not(any(macos, linux, windows))`. That keeps the crate compiling, with a legible
error, on any target where Cargo.toml does not union `unstable`. It is also the section's own
documented "legible error, never compiled out silently" rule. No shipped target reaches them.

**The `platform` panel reason is kept, not retired.** Two paths still reach it:
- `src/preload/tauriAttach.ts:77` only ever assigns `'darwin' | 'win32' | 'linux'` to
  `window.platform`. So once the gate admits win32, the gate's own branch is reached only by
  ContextProvider's `'unknown'` default. It becomes a defensive fallback.
- The D-34 deep-link escape hatch (`index.tsx` ~502) renders `<WebviewUnavailablePanel>` with no
  `reason`, so it shows the platform copy on EVERY OS.

The body copy therefore becomes OS-neutral, and true for both paths. The repo's
key-presence-only invalidation convention then applies to the 48 machine translations of the old
body. That is D-09, with quick `260925-88h` and `261004-bz3` as precedent: delete the stale key
from every non-English `gamelib.json` and `gamelib.mt.json`, write no translation by hand or by
model, and re-record the presence baseline with the lint's own writer.

**The todo is triaged, not closed.** `ready: code` becomes `ready: live-gate`, a dated addendum is
added, and the file stays in `pending/`. That is 260930-blh's convention. The live Windows UAT
(Steam/GOG render, navigation, resize, route return, Epic round trip) is operator-only. It is
recorded as pending human verification and never blocks this plan.

Purpose: Windows users get the in-app store/wiki embed macOS and Linux already have.

Output: a Windows-compiling embed, a three-OS renderer gate, OS-neutral panel copy with stale MT
invalidated, desk evidence, and the todo at `ready: live-gate`.
