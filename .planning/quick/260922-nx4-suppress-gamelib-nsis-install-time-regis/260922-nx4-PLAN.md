<objective>
Stop the first Windows Tauri NSIS installer from registering `gamelib://` (HKCU/HKLM `Software\Classes\gamelib`) while Windows still has no single-instance guard. The runtime code already declines to register on Windows (`register_all()` is `#[cfg(target_os = "linux")]`), but the Tauri CLI reads `plugins.deep-link.desktop` into bundle settings and its NSIS (and WiX) template writes the protocol keys at install time — the exact D-05 hazard (every external URL starts a second app + second sidecar). Fix: an explicit `"schemes": []` override in `tauri.windows.conf.json`.

Purpose: make the D-05 / option-c decision true at install time, not just at runtime.
Output: config override, a jest regression test, empirical installer.nsi evidence (or an honestly recorded fallback), corrected comments, updated todo.
</objective>

- `tauri.windows.conf.json` currently holds ONLY `$schema` + `bundle.resources` (3 entries: `../build/bin/x64/win32/`, `../build/bin/arm64/win32/`, `../build/bin/legendary.LICENSE`). Preserve them byte-for-byte in meaning.
- Base `src-tauri/tauri.conf.json` line ~50: `"deep-link": { "desktop": { "schemes": ["gamelib"] } }`. `tauri.macos.conf.json` and `tauri.linux.conf.json` contain no `deep` key at all.
- `tauri_utils::config::DeepLinkProtocol` (tauri-utils 2.9.3, config.rs:1483) is `deny_unknown_fields`, with `schemes: Vec<String>` and `domains: Vec<String>` both `#[serde(default)]` (empty Vec), `name: Option<String>`, `role` default. So `{"schemes": []}` deserialises to a valid protocol with zero schemes and zero domains — no http/https fallback. The `default_schemes() -> ["https","http"]` in tauri-plugin-deep-link 2.4.9 config.rs belongs to `AssociatedDomain.scheme` (the mobile/appLink struct), NOT `DeepLinkProtocol`. Still: never delete the key — an explicit `[]` is the only form whose meaning does not depend on defaults.
- Plugin runtime on Windows: tauri-plugin-deep-link 2.4.9 lib.rs:72-81 — on `#[cfg(desktop)]` the plugin's init calls `deep_link.handle_cli_arguments(std::env::args())`, which on Windows/Linux fires `on_open_url` only for URLs whose scheme `config.desktop.contains_scheme(...)`. With `[]` on Windows this path matches nothing. This IS a runtime difference on Windows (not "no change" as the brief assumed): a `gamelib://` argv no longer reaches main.rs's `on_open_url` handler (~9054) on Windows. It is harmless/desirable because (a) nothing on Windows registers the scheme, so the OS never launches the exe with one, and (b) argv URLs are ALSO forwarded by GameLib's own `sidecar_forward_args` -> `protocol_url_arg(args)` (main.rs ~8065-8073), so the plugin path was a duplicate delivery. Executor must confirm (b) by reading main.rs ~8060-8075 and its call site(s) and checking they are not `#[cfg(unix)]`-gated; record the conclusion in SUMMARY.
- `register_all()` (plugin lib.rs:235-244) iterates `config.desktop.schemes()` — with `[]` it is a no-op, and main.rs only calls it on Linux anyway.
- Tests in this repo run under JEST (`"test": "jest"` in package.json), not vitest. Style: `readFileSync` + `JSON.parse`, paths via `join(__dirname, '..','..','..','src-tauri', ...)` as in packagingConfig.test.ts.
- tauri CLI 2.11.4 has no config-dump command (`tauri inspect` only offers `wix-upgrade-code`). `tauri build` supports `--debug`, `--bundles nsis`, and `-c/--config <JSON>` (merged after the default config, later wins) — usable for the control run without editing files.
