## How the gate was run

The todo prescribed `pnpm tauri:dev` + `graphify update .` and watching for an
FSWatcher EBUSY. That arm was **not** run, by operator decision. Two reasons:

1. A live dev server (PID 14020, `node .../vite/bin/vite.js`, started
   2026-09-25 18:41:49) was already up with the GameLib Tauri window attached
   (PID 8876, `msedgewebview2` for `gamelib-shell.exe` 0.7.0, started 18:41:53).
   `strictPort: true` means a second `pnpm exec vite` cannot bind 5173 anyway.
2. `graphify update .` rewrites `graphify-out/` — which **that** server also
   watches — so the destructive arm endangers the operator's session no matter
   which vite process is nominally under test. There is no safe variant of it.

Instead the gate asked the watcher directly, read-only, via vite's Node API:
`createServer({ configFile: 'vite.config.ts' })` → `server.listen()` →
`server.watcher.getWatched()`. Probe script:
`<scratchpad>/watcherProbe.mjs` (session-local, not committed).

## Why this is RED and not merely suggestive

`src-tauri/target = 0` is the **control**, and it is what makes the
`graphify-out = 3485` row load-bearing. It proves, in the same process and the
same snapshot, that (a) the ignore mechanism works, and (b) the probe can tell
a covered subtree from an uncovered one. So `graphify-out` at 3485 watched
entries is not a null result being over-read.

The todo's open question was never whether a write to a watched `graph.json`
throws EBUSY — the captured stack already shows it doing exactly that, at
`_addToNodeFs` on `graphify-out/2026-09-23/graph.json`. The open question was
whether the **post-`c9775edac`** config still watches that path. It does. And
the pre/post-fix delta only ever concerned `src-tauri/target`, which is
orthogonal to this subtree.

## What this does and does not establish

**Does:** vite's dev-server watcher, on the current config, holds watches on
3485 entries under `graphify-out/`, a gitignored 340 MB regenerable directory
that `CLAUDE.md` actively instructs contributors to rewrite.

**Does NOT:** re-observe the EBUSY crash itself on the post-fix config. No
FSWatcher error was produced during this gate. A reader must not cite this file
as "the crash was reproduced on the fixed config" — it was not, and the todo was
emphatic that the 2026-09-24 22:38 crash ran on a **pre-fix** server (started
18:24; `c9775edac` landed 22:35:21).

**Unsettled:** if `graphify update` wrote atomically (temp file + rename), EBUSY
would not fire at all. The original stack firing directly on `graph.json` is
evidence of in-place rewriting, but this gate did not verify graphify's write
strategy independently.

## `build/` decision — DECLINE, with the measurement recorded

`build/` is measurably watched (169 dirs), and it is **not** auto-ignored:
`resolveChokidarOptions()` only appends the outDir when `emptyOutDir` is true,
and this config sets `emptyOutDir: false`. `pnpm build:sidecar` writes there and
can be run while a dev server is up.

Declined anyway. Every entry in `server.watch.ignored` is currently a *measured
failure*; adding one on reasoning alone dilutes that property, which is the same
instinct that kept `src-tauri/**` narrow. `public/bin` is watched for the same
reason and has the same shape (downloaded `.exe`s, written by
`download-helper-binaries`).

Not lost: filed as a separate pending todo so the measurement survives without
being smuggled into this fix.
