## Design decisions (planner's, recorded so the executor does not re-litigate them)

1. **The CI runner OS is NOT Linux.** The `cargo-test` matrix is `os: [windows-latest,
   macos-latest]`, and the existing caveat (a) states there is no Linux leg. `macos-latest` is
   arm64, the same triple as this Mac (`aarch64-apple-darwin`). That makes the macOS leg the
   one place where a local measurement predicts CI exactly. cfg-gated code differs per OS, so the
   ceilings are **keyed by `process.platform`**. Only `darwin` is measured and committed, and the
   clippy steps run only on the macOS leg (`if: runner.os == 'macOS'`). Windows is NOT
   cross-measured from this Mac. A cross-target clippy run (`--target x86_64-pc-windows-msvc`)
   would need the target installed. tauri-build's Windows resource step and any `cc` build
   scripts are likely to fail without MSVC tools, and even a successful cross run is not proven to
   match a native Windows run. Guessing a Windows ceiling would put a red leg on `main` at the
   first push, because an equality ceiling fails in both directions. The Windows gap is stated in
   the workflow caveats and filed as a follow-up todo (Task 3). That is honest non-coverage, not a
   scope cut. The todo's spec measures on this Mac, which only predicts the macOS leg.
2. **Pin the clippy toolchain.** The job's existing `dtolnay/rust-toolchain@stable` moves, and
   caveat (c) already records that. New clippy releases add and re-tune lints, and with an
   equality ceiling that turns `main` red on a Rust release with no repo change, in either
   direction. The clippy step therefore installs `1.99.1` with the `clippy` component and runs
   `cargo +1.99.1 clippy`. The `stable` toolchain used by `cargo test` stays untouched, so test
   behaviour does not change. Clippy builds in check mode, so its dependency artifacts are a
   separate unit set from the test build whichever toolchain it uses. The pin adds a toolchain
   download but no avoidable rebuild. Bumping the pin is a deliberate act: change the version in
   the workflow and in `CLIPPY_TOOLCHAIN`, then re-measure the ceilings in the same commit.
   **Order matters.** `dtolnay/rust-toolchain` makes the toolchain it installs the default, so the
   pinned install step must come AFTER the `cargo test` step, or it would silently re-pin the
   tests too.
3. **The script reads a file. It does not spawn cargo.** `meta/clippyRatchet.cjs` takes the path
   to a saved `--message-format=json` stream as argv. That keeps it pure and testable, and it
   keeps it out of the fake-HOME spawn convention. A fake HOME would hide `~/.cargo` and
   `~/.rustup`, so cargo could not run under one anyway. The jest test DOES spawn
   `node meta/clippyRatchet.cjs`, so the test must use `createFakeHomeProfile()` as the Phase 62
   precedent test did.
4. **A crash cannot look like a pass.** The stream must contain a `{"reason":"build-finished",
   "success":true}` line. It must also contain at least one `compiler-artifact` whose `target.name`
   is `gamelib-shell`, which is the scope-collapse floor in the spirit of 62-02's `minFiles`.
   Otherwise the script fails, naming which precondition is missing.
5. **Count per lint and deduplicate across targets.** Each `compiler-message` with
   `message.level === "warning"` is keyed by `message.code.code`, or the literal `"(uncoded)"`
   when `code` is null. It is deduplicated on (code, primary span `file_name`/`line_start`/
   `column_start`, `message.message`). Messages with no primary span and no code, such as the
   "N warnings emitted" summaries, are skipped. Equality applies per lint: a lint above its
   ceiling, or a lint absent from the map, fails as "new warning(s)". A lint below its ceiling
   fails as "lower `<lint>` to N in this commit". This makes it shrink-only per lint, so fixing
   one warning while adding a different one cannot net to green.
