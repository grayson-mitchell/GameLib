<objective>
Stop the game page from showing "Launching" after a bottled-Steam game has started and exited.

Verified root cause (the todo's working hypothesis is WRONG on the backend half — do not re-add backend emits):
- The backend DID clear the status. `bottleProcessMonitor.ts` has emitted `gameStatusUpdate {status:'done'}` on the "matched process(es) gone" branch since quick/261016-t3e (pre-gvu source line 359), and the todo's own `[refreshLibrary] runner=steam origin=game-status` line is the FRONTEND's `handleGameStatus` done-branch (`GlobalState.tsx` ~1564/1577) — proof the renderer received `done` and removed the libraryStatus entry.
- The stuck "Launching" is GamePage's local `playClicked` latch (`index.tsx` ~163/336/405/681-690). `is.launching = isLaunching || playClicked`, and `MainButton.getPlayLabel()` checks `is.launching` BEFORE `is.playing`, so the latch outranks every backend status. The latch is released only by (a) the derived status becoming `'launching'` or (b) `await launch(...)` resolving.
- On 2026-10-23 (before quick/261024-gvu, which landed 2026-10-24 12:16) nothing emitted `launching` for Steam, so (a) never fired; the status sequence was installed -> playing -> installed. (b) did not fire either: `dispatchToBottledSteam('launch')` awaits `runWineCommand({wait:false})`, which in `launcher.ts` (~1532-1598) still resolves only on the child's `'close'` event (`wait:false` only skips `wineserver --wait`). When the bottled Steam is cold, the spawned wine process IS steam.exe, so the launch IPC stays pending for the Steam session and the latch never drops.
- quick/261024-gvu now pushes `launching` from the monitor, which releases the latch on the main path, so the defect is largely masked today. The latch rule is still brittle: any path that reaches `playing` without a preceding `launching` render (or a launch() that throws) re-arms the bug. This plan hardens the latch at its only source and pins it.

Stop button: post-gvu `SteamGame.stop()` already ends a pending monitor and emits `done` (games.ts ~3645-3680); the 10-23 `no-op` / `Could not find a matching abort controller` lines are the pre-gvu behaviour. A monitor that never matches holds `launching` with no deadline by design (LD-4), with "Stop waiting" as the escape hatch — not changed here.

Output: one pure helper + its test, a two-site GamePage edit, and the todo moved to completed/ with a closure section.
</objective>
