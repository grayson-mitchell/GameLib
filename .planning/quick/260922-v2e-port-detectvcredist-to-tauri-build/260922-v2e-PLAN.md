<design_decisions>
Read these before touching code -- they are the plan's reasoning, and the SUMMARY must restate them.

D1 -- WHERE the call goes: inside the `frontendReady` handler in
`src/backend/sidecar/appShellFlowRegistration.ts`, NOT in `bootstrap.ts`'s `init()`.
- The old Electron call site used NATIVE `dialog.showMessageBox(mainWindow)`, which works before the
  renderer exists. Quick 260919-sch moved detectVCRedist to in-app `showDialogBoxModalAuto` ->
  `sendFrontendMessage('showDialog')`, which is one-way and is dropped if no renderer listener exists
  (`src/preload/tauriTransport.ts:122` `listen()` has no buffer/replay). A call in `init()` (Block F
  style) would run the probe before the webview has even loaded and the dialog would vanish.
- `dialog.ts`'s own policy comment (260919-sch) routes nags/warnings to the in-app path, and the Snap
  warning -- the other boot-time in-app dialog 260919-sch moved -- is fired from exactly this
  `frontendReady` handler. That is the existing renderer-ready mechanism; no new channel is invented.
- `bootstrap.ts` still reaches it: `init()` -> `./handlers` -> `registerAppShellFlows()` registers the
  listener. The wiring test therefore drives the registered `frontendReady` listener.

D2 -- placement INSIDE the handler: after the `if (isCLINoGui) return` (no GUI, no dialog), inside the
existing one-shot `if (!frontendReadyBootWorkDone)` block, AFTER the `setTimeout(... initQueue(true) ...)
.unref()` is scheduled, wrapped in its OWN try/catch that logs via `logSendFailure('frontendReady ->
detectVCRedist', error)`. Ordering matters: a synchronous throw from spawn must never skip the download
queue auto-resume. One-shot matches the old semantics (createWindow ran once per process) and stops a
renderer reload from re-spawning powershell. Update the module docstring's frontendReady bullet (the
"deliberate subset of main.ts:560-601" paragraph) and `frontendReadyBootWorkDone`'s doc comment to
name the new member of the boot half. `detectVCRedist` is added to the EXISTING `import { handleExit,
openUrlOrFile } from '../utils'` line -- no new module edge.

D3 -- exit contract, HALF 2 applies (bounded in-flight work), half 1 does not. A running powershell
child is referenced work: its process handle and its stdout/stderr pipes each hold the loop. `unref()`
is the wrong tool (it would have to cover the child AND all three stdio pipes, and would silently drop
the result on a quick quit). The bound is `spawn(..., { timeout: VC_REDIST_PROBE_TIMEOUT_MS,
windowsHide: true })`: Node kills the child at the bound, the pipes close, the loop drains. Worst case a
user quitting during the first seconds keeps the sidecar alive at most VC_REDIST_PROBE_TIMEOUT_MS past
stdin EOF (the Rust `shutdown_child()` backstop is unchanged). The probe also no longer runs at boot at
all -- it runs only after a renderer says frontendReady -- so `pnpm smoke:sidecar` (no renderer, never
sends frontendReady) behaves identically on every OS: the probe never starts there.

D4 -- timeout value: default `VC_REDIST_PROBE_TIMEOUT_MS = 15_000`, exported from `utils.ts` with a
comment citing the Task 3 measurement. Rule: it must be >= 3x the worst of the measured probe wall
times on this box (cold + warm) AND <= 30_000. If the measurement breaks the rule, adjust the constant
(then re-run Task 1/2 tests) and record why.

D5 -- close handler must become signal-safe. Today it is `child.on('close', (code) => { if (code) {...}
})`. A timeout kill closes with `code === null` and a signal, `null` is falsy, and the function would
fall through to "fewer than 4 lines -> show the dialog" -- a false nag caused purely by the bound. Change
to `(code: number | null, signal: NodeJS.Signals | null)`, and treat `code !== 0` as failure: if
`signal` is set, `logWarning` a line naming the timeout and the signal and return; any other non-zero
code keeps the existing `logError` (with its `log-secret-gate-exempt` comment preserved verbatim) and
returns. No dialog on either.

D6 -- spawn argv hardening (Claude's discretion, justified by D3's bound): prepend `-NoProfile` and
`-NonInteractive` to the powershell argv. A user profile script can add seconds to every probe or
print to stdout; `-NonInteractive` stops a prompting profile from hanging until the timeout. The
Get-ItemProperty / Select-Object / Format-Table tail stays byte-identical. The live measurement in
Task 3 uses this exact final argv.

D7 -- observability: the existing `logInfo('VCRuntime is installed', LogPrefix.Backend)` becomes
`VCRuntime is installed (<n> matching entries, probe <ms> ms)` (count and elapsed only -- no
DisplayNames, no stderr). Add ONE `logInfo('VCRuntime check skipped (skipVcRuntime is set)', ...)` on
the skipVcRuntime early return, so a live run can prove the check ran whichever non-dialog branch the
operator's profile takes. The dialog branch needs no new log (the dialog is the observable).
</design_decisions>
