<objective>
Fix D-UAT-11. After a Steam "Delete Files" cancel, the next install of the same app showed the
cancelled run's percentage (Darkest Dungeon 262060 reopened at 6%). Clear the stale per-app
progress at its source, inside the cancel-delete path, once the partial install is gone.

Purpose: progress must reflect what is on disk. Once the files are deleted, that is 0.
Output: one backend emit in `cancelDelete.ts`, a regression test, a store guard test, the todo
moved to completed, and the fix recorded in the UAT finding.
</objective>

<root_cause>
Located during planning. Nothing needs to be rediscovered.

1. **The holder is the frontend zustand store** `useInstallProgressRaw` in
   `src/frontend/state/InstallProgress.ts`, keyed `${appName}_${runner}` (here `262060_steam`).
   The only writer is the module-level `window.api.onProgressUpdate` listener, which overwrites
   the key with the last `progress`. Nothing ever deletes or resets a key: not cancel, not
   cancel-delete, not uninstall.
2. **Every mounted `hasProgress(appName, runner)` hook mirrors it** (`src/frontend/hooks/hasProgress.ts`).
   Its `useEffect` copies `installationProgress` into local `currentProgress` whenever the percent
   differs. The hook is used by GamePage, GameCard, DownloadManagerItem, DownloadHero, ConsoleCard,
   InstallOverlay and DLC. A freshly mounted card therefore reads the stale 6% straight from the
   store. A page that stayed mounted keeps its own 6% copy. Both cases persist until the new run's
   first emit. A native Steam run spends seconds in logon/plan-build before that first emit, so the
   stale 6% is plainly visible. The `useEffect` only acts when the store value is truthy, so
   *deleting* the key would not reset an already-mounted page. The reset has to be a
   **zero-percent progress value**.
3. **This is not the localStorage holder.** `handleStopInstallation`'s Delete Files `onClick`
   (`src/frontend/helpers/library.ts` ~L130-136) already calls `storage.removeItem(appName)`.
   Stop & Keep Files (`storage.setItem(appName, {...progress, folder})`) and `UninstallModal`
   (`storage.removeItem(appName)`) only touch localStorage too. The `${appName}_${runner}_progress`
   key that `hasProgress` reads has no writer anywhere in `src/`.
4. **The backend is not the holder.** `depot.ts` seeds `doneBytes` from the reconciler's
   `reconciledSkippedBytes`. Those are sha1-verified files actually on disk, and after
   `deleteCancelledSteamInstall` removes `common/<installdir>` there are none.

**Why the fix goes in the backend cancel-delete path, not the dialog's onClick.**
`cancelCurrentDownload` is synchronous and does not wait for the abort. A late throttled or forced
`emitProgress` from the dying depot run could land *after* a frontend-side reset and re-seed 6%.
`deleteCancelledSteamInstall` deletes only after `isNativeInstallInFlight(appId)` goes false. At
that point `runNativeDepotDownload`'s `finally` has run and no further depot emit is possible. So
an emit placed right after a successful delete is the last word, and it is placed exactly where
the partial install is removed.

**Consistency with the other paths:**
- *Stop & Keep Files* intentionally keeps the store value, because the files are still on disk and
  a resume legitimately restarts near that percent. It stays untouched.
- *Refused* cancel-delete keeps the files, so it must not reset either.
- *Normal uninstall* has the same never-cleared store entry, but it only becomes visible after a
  completed install. It is outside D-UAT-11's scope and is NOT changed here. Mention it in the
  SUMMARY as an observation. Do not create a new todo.
</root_cause>
