<planner_findings>
Two facts were established empirically during planning. Both are load-bearing — do not re-derive,
but do not contradict them either.

**F1 — the raw string is the ONLY one in main.rs, and it is multi-line.**
`grep -n 'r#"\|"#;\|r##' src-tauri/src/main.rs` → opener at line 559, closer at line 890, plus one
doc-comment mention at 1175. There are no `r##"` literals and no zero-hash `r"..."` literals in the
file today. The literal's body contains 44 lines starting with `//` (it is a JS init script) and
zero `"#` sequences.

**F2 — a naive raw-string regex would DESTROY real code. The boundary guard is mandatory.**
```
grep -c 'r"'                src-tauri/src/main.rs  → 14
grep -c '[^A-Za-z0-9_]r"'   src-tauri/src/main.rs  →  0
```
All 14 hits are ORDINARY string literals whose final character happens to be `r`:
`    "repair",` · `const KEYRING_SERVICE: &str = "com.gamelib.launcher";` ·
`"shell_show_item_in_folder" =>` · `.unwrap_or("sidecar error")` · `assert_eq!(timeout_for("repair"), None);`

A pattern of `/r(#*)"[\s\S]*?"\1/g` matches the `r"` inside `"repair"` and then deletes everything up
to the next quote — silently eating real source, including `LONG_RUNNING_CHANNELS` members. The `r`
MUST be required to sit at start-of-string or after a non-identifier character. Task 2 pins this
with a dedicated self-test.

**F3 — running the raw-string pass AFTER `loadMainRsCode()` is safe.**
`loadMainRsCode()`'s comment stripping can only DELETE text (whole `//` lines, or a trailing
comment suffix). It can therefore never manufacture a spurious `"#` (the two characters would have
to become adjacent, but a whole-line drop leaves the `\n` join intact and a suffix cut removes the
`#` along with everything after it), and it never harms the delimiters themselves: `"#;` does not
start with `//`, and `stripTrailingLineComment` enters in-string state at the leading `"` and
returns the line whole. So the guards may keep calling `loadMainRsCode()` first. Keeping the new
pass at the two guard sites (rather than inside `loadMainRsCode()`) also contains the blast radius
away from `extractLongRunningChannels()` / `extractInvokeTimeoutMs()`, which is the safer choice
given F2.

**F4 — out-of-scope observation, record only, do NOT act on it.**
`src-tauri/src/main.rs` ~line 1171 carries a doc comment on `reveal_post_script` explaining that its
JS template is assembled from `concat!` single-line pieces *specifically because* this WR-08 guard
rejects multi-line raw strings. This fix lifts that constraint. Do not edit main.rs — it holds an
uncommitted Epic fix being committed separately. Mention this in the SUMMARY as a follow-up note only.
</planner_findings>

  <action>
Add `function stripRustRawStrings(source: string): string` as a direct sibling of
`stripRustCharLiterals` (immediately after it, around line 160), then wire it into the two WR-08
guards.

REQUIRED SEMANTICS of the normalizer:
1. Remove Rust raw string literals with MATCHED hash counts — `r"..."`, `r#"..."#`, `r##"..."##`,
   and so on for N hashes. The closing delimiter must match the opening hash count EXACTLY: a `"#`
   appearing inside an `r##"..."##` body must NOT terminate it.
2. Handle the multi-line case — the real literal spans 332 source lines.
3. The `r` MUST be at start-of-string or preceded by a non-identifier character (`[^A-Za-z0-9_]`).
   This is mandatory, not defensive: see planner finding F2. Re-emit that boundary character; do not
   swallow it.
4. PRESERVE LINE COUNT. Replace the matched literal with a string carrying the same number of
   newlines it spanned (i.e. strip every non-newline character from the match), NOT with the empty
   string. The per-line guard reports `index` values for diagnosis, and collapsing 332 lines would
   shift every subsequent index and destroy the diagnosability the guard's own comment calls out.
   With this rule the opener becomes `const DEV_LOGIN_DIAGNOSTIC_INIT_SCRIPT: &str = ` and the
   closer becomes `;` — both balanced.

Reference implementation (verify it against Task 2's self-tests rather than trusting it blind):

  source.replace(
    /(^|[^A-Za-z0-9_])(r(#*)"[\s\S]*?"\3)/g,
    (_match, boundary: string, literal: string) => boundary + literal.replace(/[^\n]/g, '')
  )

Note on the groups: 1 = boundary character, 2 = the whole literal, 3 = the hashes, so the
backreference is `\3`. `#*` is greedy on purpose (it must claim both hashes of an `r##"` opener
before the `"` is required); the body is lazy so the FIRST correctly-hashed closer wins.

DOC COMMENT — write it in the same voice as `stripRustCharLiterals`'s existing one (explain WHY, not
just what). It must state:
  - what property the WR-08 guards actually measure: an ordinary string literal cut in half by the
    comment stripper;
  - why a raw string's delimiter lines read as false positives: the literal legitimately spans many
    lines, so `r#"` and `"#;` each carry one bare `"` with nothing truncated;
  - why the non-identifier boundary before `r` is required, citing the concrete counter-examples
    `"repair",` and `"com.gamelib.launcher"` — 14 lines in main.rs end a string with `r`, and
    without the boundary the pass would eat real code up to the next quote;
  - why line count is preserved (per-line index diagnosability);
  - the accepted limitation, in the same register as `parseMsConstantFromSource`'s existing caveat:
    this is a narrow normalizer for trusted first-party source, not a Rust lexer — an `r#"` sequence
    appearing INSIDE an ordinary string literal would be mis-detected. That failure mode is loud (it
    unbalances quotes and the guard goes red), not silent.

WIRING — apply to the FULL source before any splitting, in both guards:

  a) whole-file guard (~line 342-343): change to
     `const stripped = stripRustCharLiterals(stripRustRawStrings(loadMainRsCode()))`
     Raw strings first, then char literals.

  b) per-line guard (~line 352-353): change to
     `const strippedLines = stripRustRawStrings(loadMainRsCode()).split('\n')`
     Leave the per-line `stripRustCharLiterals(line)` call inside the `.map()` unchanged.

CRITICAL ORDERING CONSTRAINT — and it must be documented, not just obeyed. Add a short inline
comment above (b) stating that a per-line pass cannot see a multi-line construct, so raw strings are
stripped from the FULL source BEFORE `.split('\n')`, and that reordering these two calls silently
reverts this fix. That comment is what protects the ordering from a future refactor.

Do not modify `loadMainRsCode()`, `stripRustLineComments()`, `stripRustCharLiterals()`, or any
assertion's expected value.
