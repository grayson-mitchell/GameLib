Findings from planning (settled by reading code — do not re-derive):

- **Shared seam.** `recordFirstMatch(appId, entry, matches)` in `bottleProcessMonitor.ts` (~L232)
  runs exactly once per monitor on first match, for BOTH callers: `SteamGame.fireBridgeWineLaunch`
  (`steam/games.ts` ~L2948, `kind: 'bridge'`) and `tellBottledSteamToLaunch` (`bottle.ts` ~L1073,
  default `kind: 'bottled-steam'`). It is called from both the poll loop and `launcherExited()`.
  `matches` is `Array<{ pid: string; command: string }>`, `pid` is digits-only (parsed by
  `parsePsLine`'s `\d+` regex), `command` begins with the Windows path, e.g.
  `C:\Program Files (x86)\Steam\steamapps\common\Avernum 6\Avernum 6.exe ...`.
- **Sideloaded Wine** does not use the monitor. `launchGame` in
  `src/backend/storeManagers/storeManagerCommon/games.ts` (~L279-296) logs
  `launching non-native sideloaded` then `await runWineCommand({ ..., wait: true })`. There is no
  pid there; the process name is `basename(executable)`. GOG/Epic/Amazon Wine launches go through
  their own `games.ts` launch paths and are OUT of scope for this task (not a shared seam).
- **Mechanism already shipped:** `osascript` + System Events `set frontmost of p to true`, via
  `spawnAsync('osascript', [...])`, used by `raiseBottledGameWindow`/`raiseInstallerWindow` and
  described in-code as "already-working". It uses the same Automation (System Events) consent the
  bottled path already requires — no new permission class, no new binary. There is no existing
  `NSRunningApplication` helper in `src/`, `src-tauri/` or `native/`. Do NOT add a Swift/ObjC
  helper or a Rust command for this task. (`NSRunningApplication.activate` from a background
  child is subject to macOS cooperative activation and is the less reliable choice here.)
- **Wine pid vs window owner:** under CrossOver the process System Events lists for a Windows
  exe is named after the exe (e.g. `Avernum 6.exe`). The matched `ps` pid is expected to be that
  same process, but if it is a helper/child the pid lookup misses — hence the name fallback.
- **Minimise-on-launch fallback (note only, do not change):** `launcher.ts` ~L150/L185 reads
  `minimizeOnLaunch` and calls `getMainWindow()?.hide()`; default `false` in `config.ts` ~L368.
  Whether it works under the Tauri shell is unverified. Mention it in the SUMMARY as the fallback
  if the live check shows GameLib re-taking focus; do not wire or modify it.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| `ps` output / sideload executable path -> osascript | process names and paths are attacker-influenceable strings (a game or user can name an exe anything) reaching an AppleScript interpreter |
| sidecar -> System Events | GameLib asks macOS to change the frontmost app |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-g3m-01 | Tampering / Elevation | wineWindowRaise osascript script | mitigate | Script text is a constant `on run argv` handler; pids and names travel only as argv, never interpolated; pids additionally filtered to `/^\d+$/`. Unit test asserts a quote-bearing name and a non-numeric pid cannot alter the script. |
| T-g3m-02 | Denial of Service | raise loop in the sidecar | mitigate | Bounded to 12 attempts + 1 settle re-raise; timers `unref?.()`'d so stdin-EOF drain exit is unaffected; never awaited by launch paths. |
| T-g3m-03 | Spoofing | raising the wrong process | accept | Targets are the pid(s) the monitor already attributed to this game's own install dir, then that exe's name; worst case a same-named visible process comes forward — cosmetic, no data exposure. |
| T-g3m-04 | Information Disclosure | logs | accept | Logs contain pid + exe name, already logged by the existing first-match line. |
