<objective>
Give the Steam sign-in surface the same windowed presentation the other stores' sign-in
surfaces have: a floating panel centred over the app with a dimmed backdrop, a titled header,
and a close control — instead of today's bare `.steamLoginPanel` box that renders flush in the
content area.

Purpose: the user's report is that Steam's login does not present like Humble's. Humble (and
every other runner) opens a real sign-in WINDOW over the app; Steam renders an unadorned page.
This closes the presentation gap using the app's own shared modal primitive.
Output: `SteamLogin` renders inside `frontend/components/UI/Dialog`, plus a source gate pinning
that shape, plus a human visual confirmation.
</objective>

**1. Steam has NO native login window, and cannot have one.**
`grep -n "steam" src/frontend/screens/WebView/useTauriOAuthLogin.ts src/frontend/screens/WebView/loginRoutes.ts`
returns nothing, and `src/backend/sidecar/steamAuthFlowRegistration.ts` registers no window arm.
Steam authenticates entirely in-process via `steam-session` behind `window.api.steamStartQR` /
`steamStartCredentials` / `steamSubmitGuard` / `steamPollCredential` — there is no URL to load
into a webview.

Routing Steam through Humble's native mechanism (`"humble_login_open"` arm,
`src-tauri/src/main.rs:3534`) is STRUCTURALLY BLOCKED, not merely inconvenient: login windows
are deliberately excluded from the Tauri capability scope. See `src-tauri/src/main.rs:967`
("never join `capabilities/default.json`'s `windows: ["main"]` array") and `:5624`. A login
window therefore has NO `window.api` / `invoke` access at all, so the Steam form could not make
a single one of its five backend calls from inside one. Widening that scope to accommodate a
presentation change would be a security regression and is explicitly out of scope here.

This plan therefore delivers the in-app equivalent — the shared modal window primitive — which
is the closest achievable presentation parity.

**2. Do NOT convert the Steam tile into an overlay on the Login screen.**
`src/frontend/screens/Login/__tests__/loginInFlightUiReachability.test.tsx` is a threat-pinned
source gate (T-34.4.2-39 / T-34.4.2-41, mutation-proven) whose documented mechanism is: clicking
a login tile NAVIGATES AWAY from the Login screen, unmounting all six tiles at once. Giving the
Steam tile a `primaryLoginAction` that opens an in-place overlay would falsify that gate's own
prose and weaken the pin. Keep the existing `loginUrl={steamLoginPath}` navigation exactly as it
is. `src/frontend/screens/Login/index.tsx`, `Runner/index.tsx` and `App.tsx` are NOT touched by
this plan.

Because the `/loginweb/steam` route renders inside `Root`'s `<Outlet/>` while the app shell
(nav/titlebar) stays mounted, and because MUI's `Dialog` portals to `document.body`, the dialog
floats over the entire app with a full-viewport backdrop — visually a sign-in window over the
app, which is the requested outcome.

**3. Dialog primitive contract (read, not assumed).**
`src/frontend/components/UI/Dialog/components/Dialog.tsx` exports
`Dialog({ className?, children, showCloseButton, onClose })`. It renders a MUI `Dialog`
(portal + backdrop + Escape + focus trap), an absolutely-positioned close `IconButton` gated by
`showCloseButton`, and wraps `children` in MUI's own `DialogContent`. `DialogHeader({ children })`
renders a MUI `DialogTitle`. Backdrop-click close is already honoured unless
`disableDialogBackdropClose` is set in `ContextProvider`.

Import shape used by existing callers (`WineManager/components/WineManagerSettingsModal.tsx:3-6`,
`WebView/index.tsx:34-37`):
`import { Dialog, DialogHeader } from 'frontend/components/UI/Dialog'`

`Dialog` holds its own `open` state initialised to `true` and mounts with a 500ms entrance
transition plus a `window.api.gamepadAction({ action: 'tab' })` focus hack. It must therefore be
mounted ONCE and kept mounted — see Task 1's single-return requirement.

**4. SteamLogin's three top-level render branches (line numbers at HEAD).**
- `:272` `if (step === 'not-installed')` -> returns `<div className="steamLoginPanel">`
- `:321` `if (step === 'checking')` -> returns `<div className="steamLoginPanel">`
- `:575` main tabs view -> returns `<div className="steamLoginPanel">`
`renderQRContent` (`:330`) and `renderCredentialsContent` (`:407`) are inner helpers, not
top-level returns. All five `navigate('/login')` call sites are at `:94`, `:140`, `:226`, `:253`,
`:310`, `:581`.

**5. Timer teardown already exists.** The mount effect with `[]` deps owns interval/timer
cleanup on unmount (stated in the comment at `:196-205`), and `navigate('/login')` unmounts the
route component. A new dismissal route (Escape / backdrop / header close) therefore needs NO
extra teardown beyond navigating — do not add speculative clears.

**6. Test environment has NO DOM.** `src/frontend/jest.config.js` is `testEnvironment: 'node'`;
jsdom and react-test-renderer are not installed. The established convention in this area is a
comment-stripped SOURCE GATE via `stripSourceComments` from `backend/testUtils/stripSourceComments`
(see `loginInFlightUiReachability.test.tsx`). A render test is not available — which is why
Task 3 is a human visual gate, not a substitute assertion.

**7. Localisation.** `SteamLogin/index.tsx` contains NO `t()` calls at all today; every string is
a raw English literal. This plan MOVES the existing `Sign in to Steam` literal from the `<h1>` at
`:582-593` into the dialog header. It introduces ZERO new user-facing strings and therefore adds
no new i18n keys. Do not opportunistically localise this file here — that is its own task.

**8. Pre-existing, out of scope.** `.tabsWrapper` (`SteamLogin/index.tsx:600`) has no matching
CSS rule reachable from this component (`.tabsWrapper` is styled only inside
`src/frontend/screens/WineManager/index.css:57`). That is already true at HEAD. Do not fix it
here; just confirm in Task 3 that the tabs remain legible inside the dialog.

|----------|-------------|
| user -> Steam sign-in form | Steam username, password and Steam Guard code are typed into this surface |
| renderer -> sidecar (`window.api.steam*`) | Credentials cross into the Node sidecar and on to Steam's CM network |

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-KQ0-01 | Spoofing | `SteamLogin` window presentation | mitigate | The window is rendered by the app's OWN `Dialog` primitive inside the main webview — it is NOT a separate OS window and cannot be confused with one from another origin. The plan explicitly refuses to widen `capabilities/default.json`'s `windows: ["main"]` scope (finding 1), so no new IPC-capable surface is created. |
| T-KQ0-02 | Information disclosure | password / Steam Guard inputs | accept | `type="password"` and the existing input handling are untouched; no field is moved into a new process or a new logging path. No `window.api.logInfo` call is added to this component by this plan. |

Task 2 re-runs `loginInFlightUiReachability.test.tsx` as a regression gate. |
| T-KQ0-SC | Tampering | npm/pip/cargo installs | mitigate | No new dependency is introduced — `@mui/material` and `frontend/components/UI/Dialog` are already in the tree and already used by this screen's sibling components.
