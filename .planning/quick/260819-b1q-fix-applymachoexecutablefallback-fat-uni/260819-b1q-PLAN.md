Source of truth for this defect (already verified during planning — do NOT re-derive):

`applyMachOExecutableFallback` (depot.ts ~1575) reads `MACHO_PROBE_BYTES = 4096` from the head of

<design_decision>
Read this before writing code. The shape is settled; implement it, do not re-litigate it.

**Rejected: raising `MACHO_PROBE_BYTES`.** A slice offset is arbitrary, file-dependent data. Any
fixed buffer is a guess that silently fails again for the first binary whose slice sits beyond it —
reproducing this exact bug with a larger number — and it multiplies the per-file read cost across
~18.5k files on both the download and the resume path.

**Chosen: a two-stage probe. Stage 1 stays a pure `Buffer` classifier; stage 2 is a second, small,
positional read performed where the `FileHandle` already lives.**

Rationale for putting stage 2 in `applyMachOExecutableFallback` rather than making
`isExecutableMachO` async/reader-based:
- The `FileHandle` is already open there and is already the thing responsible for closing it. An
  async reader-based classifier would have to either take the handle (leaking I/O into the parser)
  or take a callback (an indirection with no second caller).
- Header parsing stays synchronous, pure, and unit-testable against plain `Buffer`s — which is the
  property the existing tests and constraints both depend on.
- It keeps the T-21-02 "never RAM-buffer a whole file" discipline literally intact: two bounded
  reads, 4096 + 32 bytes, never the file.

Concretely:

```
type MachOProbeVerdict =
  | { kind: 'executable' }
  | { kind: 'declined' }
  | { kind: 'slice'; offset: number }
```

- `isThinMachOExecutable(buf, offset)` — pure. `detectMachOEndianness` → `readMachOFiletype` →
  `filetype === MH_EXECUTE || filetype === MH_DYLIB`. This is the existing logic, extracted.
- `classifyMachOProbe(buf)` — pure. Replaces `isExecutableMachO`.
  - Thin magic at 0 → `isThinMachOExecutable(buf, 0)` → `executable` / `declined`.
  - `FAT_MAGIC` at 0 → structural validation (below), then:
    - if the slice header is ALREADY fully inside `buf` (`buf.length >= sliceOffset + 16`) →
      classify inline and return `executable`/`declined`, **no second read**. This preserves the
      existing offset-64 fat tests byte-for-byte and costs nothing for small fat files.
    - else → `{ kind: 'slice', offset: sliceOffset }`.
  - anything else → `declined`.
- `applyMachOExecutableFallback` keeps its own `try { ... } finally { await handle.close() }`, but
  the classification now happens INSIDE that block so stage 2 can reuse the handle. On
  `kind: 'slice'` it does one `handle.read(sliceBuf, 0, MACHO_HEADER_BYTES, offset)` and feeds the
  result to `isThinMachOExecutable(sliceBuf, 0)` — **non-recursively**, so a fat magic nested inside
  a slice is declined rather than looping.

**Bounding the attacker-influenced offset** (it is uint32 data read from file content):
- Structural, in the pure classifier: reject `nfatArch < 1`; reject `nfatArch > MACHO_MAX_FAT_ARCH`
  (32); reject `sliceOffset < 8 + nfatArch * 20`, i.e. a slice that would overlap its own
  `fat_header`/`fat_arch` table.
- I/O-side, in the probe: reject `sliceOffset > MACHO_MAX_SLICE_OFFSET` (64 MiB — no real first
  slice is remotely that deep); reject `sliceOffset + MACHO_HEADER_BYTES > fileSize` using
  `await handle.stat()` on the handle already open; treat a short read (`bytesRead < 16`) as
  `declined`.
- Free bonus worth a comment: `0xcafebabe` is ALSO the Java `.class` magic. There, `readUInt32BE(4)`
  is `minor<<16 | major`, which for every real class file is > 32, so the `nfatArch` bound declines
  Java class files structurally instead of chasing a garbage offset into the file.

**Explicit non-goal, document it in a comment, do not implement:** `FAT_MAGIC_64` (0xcafebabf,
64-bit slice offsets) is not handled. It only appears when a slice exceeds 4 GiB, which no shipped
game binary does, and adding it would widen this plan past atomic.
</design_decision>
