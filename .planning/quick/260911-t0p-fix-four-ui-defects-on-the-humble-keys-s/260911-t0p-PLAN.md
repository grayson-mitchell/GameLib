# Fix four UI defects on the Humble Keys screen

Four independent defects on `screens/Humble/Keys`, all reported off the REQ-43-19 live
gate era. Three are CSS-only and land in one file. The fourth is a behaviour change that
**reverses a recorded Phase 43 decision**, so it carries a records-correction obligation
that is a first-class task here, not a footnote.

## What is wrong, verified at HEAD

| # | Symptom | Cause (all line numbers verified at HEAD) |
|---|---|---|
| 1 | `Humble Keys` h4 wraps to two lines | `index.css:21-26` makes `.humbleKeysHeaderTop` a flex row; the middle child `SearchBar` sets `width: 100%` (`components/UI/SearchBar/index.scss:3`). The h4 is a flex item at default `flex-shrink: 1`, so SearchBar's 100% basis squeezes it to min-content. `.humbleKeysTitle` (`index.css:28-30`) declares only `margin: 0`. |
| 2 | The `Sort` label sits **above** the picker | `SelectField` always renders `<label>` as a sibling of `<Select>`, and `.selectFieldWrapper` (`SelectField/index.css:1-4`) is `display: grid; grid-template-areas: 'label' 'select'` — stacked by design. The shipped inline variants are `.small`/`.smaller` (`:79-83`) and `.rightButtons` (`:99-103`); none is passed here. |
| 3 | `Redeemable keys only` still shows REVEALED keys | `index.tsx:513` filters on `WAITING_STATES.has(key.state)`, and `viewFilters.ts:16-20` defines that set as `{UNPICKED, UNREVEALED, REVEALED}`. |
| 4 | `Likely owned on Steam` unreadable on light themes | `index.css:479` is `color: var(--status-success)` = `#0ce396` (`styles/_colors.scss:26`) on `body.nord-light`'s `#eceff4` (`themes.scss:324`). Measured **1.46:1**. |

## The two constraints that shape this plan

**`WAITING_STATES` MUST NOT CHANGE.** Its other consumer is `selectKeysWaiting`
(`viewFilters.ts:65-75`), which feeds the StoreSearch and Discounts backend surfaces, and
`index.tsx:414`'s `hasClaimEligibleState` per-row claim gate. Editing the shared set would
silently move all three. Defect 3 gets a **new, separately named constant**.

**Defect 3 reverses a recorded decision, deliberately.**
`43-DISCUSSION-LOG.md:205-209` records the user picking "REDEEMED + UNREDEEMABLE" with the
label reworded to "Redeemable keys only", and states the predicate "lands ... exactly on
the shipped, unit-tested `WAITING_STATES` constant (`viewFilters.ts:20`) — no new predicate
needed." `43-DISCUSSION-LOG.md:215` records "In — reuse `WAITING_STATES`" as selected. The
user has now overridden that: REVEALED comes out. Four records assert the old behaviour and
must be corrected **additively** — this is a supersession, not a rewrite of history.

## Why `viewFilters.ts` is the home for the new constant

That file's own header (`viewFilters.ts:4-10`) states its role: "Pure view-membership +
sort helpers ... Kept in `common/` (no React, no i18n, no I/O) so it is unit-testable from
the backend jest project". `43-RESEARCH.md:43` reaffirms the tier for exactly this class of
predicate. A screen-local constant would be unreachable from the backend jest project,
which is where the only assertions that can actually adjudicate defect 3 live. Put it next
to `WAITING_STATES` so the contrast between the two sets is legible at the point of
definition.

## What CANNOT be proven by any test in this repo

`src/frontend/jest.config.js` sets `testEnvironment: 'node'` — no jsdom, no CSS engine.
Nothing in the frontend project can compute inheritance, resolve `currentColor`, or
evaluate `color-mix`. **Defects 1, 2 and 4 are visual and cannot be adjudicated by any test
written here.** The source-text gate this plan extends proves only that the source *says*
the right thing. Defect 3 is pure set membership and **is** genuinely unit-testable.
Consequence: task 3 files one `ready: live-gate` todo carrying the three unverified visual
claims to the next live run.

## Task 1 — the three CSS fixes, all in `Keys/index.css`, plus their source pins

**Files:**
- `src/frontend/screens/Humble/Keys/index.css`
- `src/frontend/screens/Humble/Keys/__tests__/humbleKeysStylesheet.test.ts`

### 1a. Stop the title wrapping (defect 1)

Extend `.humbleKeysTitle` (`index.css:28-30`) so the h4 stops yielding to `SearchBar`'s
`width: 100%` flex basis. Both parts are needed: `flex-shrink: 0` stops the flex algorithm
shrinking it below its content, and `white-space: nowrap` stops it wrapping if some future
sibling still wins the space fight. Keep `margin: 0`. Do **not** touch
`.humbleKeysHeaderTop` — its `gap: var(--space-sm)` is pinned by a 43-UI-SPEC "Screen
Layout Contract" item documented in the comment at `index.css:15-20`.

### 1b. Put the `Sort` label inline with the picker (defect 2)

Add a **new, bare** `.humbleKeysSortPicker { ... }` rule to `Keys/index.css`, placed
immediately **before** the two existing descendant rules at `index.css:671-684`, under the
existing "Sort Picker Contract" comment block. Reasons this belongs here and not in
`SelectField/index.css`: the call site already passes
`extraClass="humbleKeysSortPicker"` (`index.tsx:605`) and this file already owns the
MUI overrides for that class, so the whole picker's presentation stays in one place.

The rule must override `grid-template-areas` to `'select label'` and declare
`grid-template-columns`. The column track is **load-bearing, not cosmetic**:
`.selectFieldWrapper .MuiOutlinedInput-root` (`SelectField/index.css:7-11`) sets
`width: 100%` and `min-width: 100px`, so the select has no intrinsic width to size a
`min-content`/`auto` track from — it will collapse toward `min-width` unless the track is
explicit. Give the select column a fixed width wide enough for the longer of the two
shipped options (`Expiring soonest`, `Alphabetical`) and the label column `max-content`.
`.selectFieldWrapper label` (`SelectField/index.css:60-64`) already carries
`grid-area: label` and `align-self: center`, so no label rule is needed; add a
`column-gap` if the two sit flush. Add a short comment stating *why* the explicit track
exists (the `width: 100%` interaction above) so a later reader does not "simplify" it away.

**Do not restructure the existing `.humbleKeysSortPicker .MuiOutlinedInput-notchedOutline`
rule.** Its `var(--divider, color-mix(...))` fallback is one of exactly three occurrences
the gate counts, and prettier has wrapped it across four lines (`index.css:676-679`) — a
naive grep for `var(--divider` finds only two of the three.

### 1c. Fix the owned-badge contrast (defect 4)

`index.css:479`: `color: var(--status-success)` → `color: var(--success)`. One site only.

Why this is safe in every theme: `themes.scss:100` declares `--success: var(--status-success)`
inside the **base `body {}` block**, so unlike `--divider`, `--success` is defined in every
theme and needs no fallback. `body.nord-light` overrides it at `themes.scss:363` to
`#3e532d` → measured **7.35:1** on `#eceff4`. Dark themes are unchanged or improved
(classic `#0ce396` on `#13172a` = 10.51:1; old-school overrides to `#0bd48c` = 8.53:1 on
its own `#1d1f1f`).

**Out of scope — do not touch:** the four `background: var(--status-success)` uses
(`Keys/index.css:465`, `StoreSearch/index.css:183`, `DiscountCard/index.css:96`,
`GameCard/index.css:259`). Those are fills sitting behind fixed-contrast text, not
foreground text. Only `Keys/index.css:479` is a text colour.

### 1d. Extend the source gate

Add three `describe` blocks to `humbleKeysStylesheet.test.ts`, each with the **SANITY
counterpart** that file's existing blocks all carry (assert the matcher rejects a
known-bad input, proving the pin is not vacuously true). Follow the file's established
shape exactly: read through `stripSourceComments`, use block-scoped
`/\.SELECTOR\s*\{([^}]*)\}/` anchors.

1. `.humbleKeysTitle` block declares both `flex-shrink: 0` and `white-space: nowrap`.
2. `.humbleKeysSortPicker` block declares `grid-template-areas: 'select label'` and a
   `grid-template-columns`. Note the anchor `/\.humbleKeysSortPicker\s*\{/` cannot match
   the descendant rules (`.humbleKeysSortPicker .MuiSelect-select,` — `\s*` may eat the
   space but the next char is `.`, not `{`), so placing the bare rule first makes the
   first-match unambiguous.
3. `.humbleKeyOwnedBadge` block declares `color: var(--success)` and does **not** contain
   `var(--status-success)`. Because a block-scoped negative leaves a widening blind spot
   outside the block, pair it with two file-wide counts: `var(--status-success)` occurs
   exactly **1** time (down from 2 — the survivor is the `.humbleKeyStateBadge--REDEEMED`
   fill at `:465`) and `var(--success)` — matched with the closing paren so it cannot
   also catch `var(--success-hover)` — occurs exactly **1** time.

**Do not add or remove any `var(--divider, ...)` occurrence.** The existing test
"declares the currentColor color-mix fallback at exactly the three known sites" must still
pass unchanged.

**Verify:**
```

grep -c 'var(--status-success)' src/frontend/screens/Humble/Keys/index.css   # expect 1
```
(`--selectProjects` is case-sensitive; `Frontend` is the `displayName` at

**Done:** all three CSS edits landed in `Keys/index.css`; the stylesheet test passes
including its pre-existing divider-count-3 and `.gogIcon` scoping assertions; each new pin
has a SANITY sibling that demonstrably fails against a known-bad input.
