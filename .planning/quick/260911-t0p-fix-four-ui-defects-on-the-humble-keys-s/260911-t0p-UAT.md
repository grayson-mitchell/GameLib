## Results

Measured from `shot0.png`, a `screencapture -x -R116,65,1280,800` of the live window
(captured 2560×1600 — the display is 2× retina, so all CSS figures below are measured
pixels ÷ 2). Decoded with a pure-Python PNG reader; **neither PIL nor ImageMagick is
installed on this machine**, which is why no image library appears here.

Active theme confirmed **nord-light** by sampling the page background: `#eceff4`, matching
`themes.scss:325`'s `--body-background`. This was not assumed from the app looking pale.

### Item 1 — title on one line → **PASS**

Row-luma profile over the title's own column range (`x` 430–735, excluding the SearchBar
pill which starts at `x` 742):

- **exactly one** dark-text band: `y` 143–184 → **21.0 CSS px tall**, `x` 444–714 → 135 CSS px wide.
- A wrapped title would produce **two** bands at that glyph height. It produces one.

*Trap avoided:* a first scan over `y` 110–270 found **two** bands and would have read as a
FAIL. The second band (`y` 215–236) is **11.0 CSS px** tall — half the title's glyph height —
i.e. the `Last synced 1 hour ago` sync indicator in `--text-xs`, a different element. Scoring
band-count without checking glyph height would have failed correct code.

### Item 2 — `Sort` beside the picker, picker not collapsed → **PASS as measured, but the measured layout is SUPERSEDED**

> **⚠ Read this before citing the numbers below.** They were taken from `shot0.png`, which is
> the `260911-t0p` build. **Two later changes moved this exact control, so the geometry below is
> no longer what ships:**
>
> - `260911-ue4` (`a2c670f2a`) **flipped the order** — the label now renders to the **LEFT** of
>   the select (`grid-template-areas: 'label select'`). The table below says the label is to the
>   *right*; that was true when measured and is false now. The operator asked for the flip after
>   seeing this result, so this PASS is what *prompted* the change, not a description of HEAD.
> - `260911-umj` (`e368075c3`) **shrank the select 40px → 34px** app-wide, which moves the
>   vertical centring this item scores.
>
> The horizontal sub-claims (label beside rather than above; select not collapsed to its 100px
> floor) survive both changes — neither touched the `12rem` track or the areas' side-by-side-ness.
> **The vertical-centring sub-claim needs a re-measure against the 34px select** and is carried
> forward in the `ready: live-gate` todo rather than being assumed to have survived.

Measured on the t0p build (superseded — see the warning above):

Horizontal scan at `y` 358 (mid-control-row), classifying runs against the page background:

| measurement | value |
|---|---|
| select box | `x` 217.5 → **414.0** CSS |
| select **width** | **197.0 CSS px** |
| `min-width` floor it must clear | 100 px |
| `Sort` label ink begins | **427.0 CSS** |
| gap select→label | 13.0 CSS px (≈ `--space-sm` 12px + antialiasing) |

- **Beside, not above:** label left edge (427.0) is right of the select's right edge (414.0). Unambiguous.
- **Not collapsed:** 197.0 CSS px ≈ the declared `12rem` (192px) + borders, nearly 2× the 100px floor.
- **Vertical centring — scored by containment, not baseline.** The label's ink band
  (173.0–184.5 CSS) lies **entirely within** the select box's vertical extent (158.5–205.0 CSS);
  ink-centre offset 3.0 CSS px. An attempt to compare glyph baselines directly was
  **contaminated by the focus ring** around the focused select and is NOT reported as evidence.
  The 3 px offset is the expected artifact of `Sort` having no descenders (ink-centre sits above
  text-box centre); it is not a measured misalignment.

**Complementary direction — now VERIFIED by the operator.** Unticking the checkbox yields

`click at {610,244}` was attempted first and **did not land** — `shot1.png` came back
identical to `shot0.png` with the box still ticked (no `cliclick`, no `pyobjc` on this
machine). That was recorded as **unverified rather than passed**, since an unchanged
screenshot is not evidence a toggle works, and the count was then supplied by the operator
driving the real control.
