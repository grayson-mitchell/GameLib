**RETRACTED (r1 claim, refuted 2026-09-01). `zig cc` is NOT deterministic across rebuilds.**
r1 of this plan asserted that two same-path compiles produced a byte-identical `.dll`. That was
wrong: those two runs landed inside the same wall-clock second. Re-measured with a >1s gap
between runs, three consecutive compiles at the identical output path produced three different
sha256 values, and the PE COFF `TimeDateStamp` at offset `e_lfanew+8` advanced with the clock
each time (`2026-09-01T03:19:24Z`, `:25Z`, `:27Z`). The shipped baseline's stamp decodes to
`1788201505` = `2026-08-31T18:38:25Z`. **A rebuild can never reproduce the shipped bytes.**

**The rebuild-comparison acceptance bar was the wrong test, independently of the flake.**
`.github/workflows/release-tauri.yml:158` runs `pnpm build-steam-bridge` on every CI release, so
the shipped DLL already carries a fresh timestamp on every release — production has never had
byte-identity here and does not need it. `src-tauri/tauri.conf.json:8` sets
`beforeBuildCommand: ""` and no local script chains the bridge build, so locally nothing
rebuilds it either. "Does a rebuild reproduce the DLL?" is a question about compiler
determinism. The question this change actually raises is **"can the unlink alter the DLL?"** —
and that is answerable exactly, four ways:

- **P1 — structural (primary).** The unlink runs strictly after `zig cc` has returned and after
  both gate throws, and `rmSync`s two paths that are not the DLL. It cannot alter
  `steam_api.dll` by construction. Provable by inspection; independent of determinism.
- **P2 — same-build hash, either side of the prune.** Hash the DLL, run the prune, hash again,
  assert equal. No recompile between the two hashes, so compiler non-determinism is excluded
  by construction. Realised twice: as a permanent unit test (B7) and as an end-to-end scratch
  check (Task 2, E1).
- **P3 — do not rebuild the real tree.** To clear the two existing byproducts from
  `public/bin/arm64/darwin/`, plain `rm` them. Do NOT run `pnpm build-steam-bridge` against the
  real tree at any point in this task. The local and shipped DLL then remain `2da072ba…` and
  criterion 1 is trivially true instead of unachievable. All exercise of the changed script
  happens on a SCRATCH copy, where DLL churn is irrelevant.
- **P4 — masked rebuild comparison (measured cheap and non-vacuous, so it is REQUIRED, not
  optional).** `zig cc`'s volatile set is exactly four spans / 32 bytes: COFF `TimeDateStamp`
  `(128,4)`, OptionalHeader `CheckSum` `(208,4)`, debug-directory entry `TimeDateStamp`
  `(729092,4)`, and the RSDS GUID+Age `(729120,20)`. Zero those and **two fresh scratch builds
  AND the 2026-08-31 shipped baseline all hash to `cc3e8b4a1fba55b9ab9cb69927b9c76d…`** — which
  also accounts for r1's "output-path dependence" finding: that variance was the RSDS GUID,
  which the mask removes.
  **PRECONDITION — the compared files must share the same `-o` basename.** The RSDS record
  continues past the masked GUID+Age with a NUL-terminated PDB name string (`steam_api.pdb`, at
  729140), and it is deliberately left UNMASKED. Two builds emitted as `steam_api.dll` versus
  `DIFFERENT_NAME.dll` therefore mask to `cc3e8b4a…` and `5607d2f8…` and the tool reports a
  mismatch — correct behaviour, since the name is real content. It is safe here only because
  `shimOutputPath()` always emits the fixed name `steam_api.dll`. So the accurate statement is
  "deterministic modulo four spans, GIVEN a fixed output basename", NOT "filename-agnostic".
  Record the precondition in MEASUREMENTS.md alongside the result; on a false RED check the
  `-o` basename first and never widen the mask to cover the name string.
  The mask is **non-vacuous**: a one-line addition to the shim source (identical 805,888 B
  output) masks to `d8a979b6…`, so it does not hide real code changes.
  Tool, validated during planning and committed with this plan:
