# Quick Task 260905-l8g

## Why this beats what shipped in jx3/kd0

`0fdbdac36` made the prompt visible and `260905-kd0` made the gate able to see it. Both are
mitigations. `keyring_available` still calls `entry.get_password()` on a REAL, protected Keychain
item, so it still raises a real macOS authorization dialog. This removes the channel.

## The mechanism is already hardware-measured IN THIS REPO

`main.rs:11559-11594`'s `keyring_read_timing_hypothesis_absent_vs_present_entry` harness, run twice
on this machine on 2026-07-31:

| Read | Elapsed | Outcome |
|---|---|---|
| **absent** account (never written) | **40.04 ms**, then **102.23 ms** | `NoEntry` |
| **present** account (`steam-refresh-token`) | **48.87 s**, then **291.08 s** | Keychain **authorization** error (`-60008` "Unable to obtain authorization for this operation") |

A lookup for an item that does not exist returns `errSecItemNotFound` (`-25300` → `NoEntry`)
immediately: there is no item, therefore no ACL, therefore no authorization step and no dialog. A
lookup for an item that DOES exist is what triggers the negotiation. The probe rides the fast path
by construction, and this is measurement rather than inference.

## Why no metadata-only API is used instead

Checked keyring 3.6.3 (`apple-native`), the actual vendored source:

- `get_attributes()` has **no** macOS override. `credential.rs:74-79`'s default calls
  `self.get_secret()?` "for effect" — i.e. it prompts exactly like `get_password()`.
- `macos.rs` routes `get_password`, `get_secret` and `get_credential` all through
  `find_generic_password` (`SecKeychainFindGenericPassword`), which returns the secret data and so
  performs the ACL check.

There is no non-prompting metadata call available through this crate. The absent-account probe is
the portable way to ask "does the backend answer" using only the public API.

## Design

- New `KEYRING_REACHABILITY_PROBE_ACCOUNT`, **stable, not randomly suffixed** — deterministic
  behaviour and a reproducible live gate are worth more than per-call unguessability, and absence
  is guarded by tests rather than by randomness. Deliberately outside `keyring_account()`'s
  allowlist so it can never collide with a real slot.
- Outcome mapping: `NoEntry` → `true` (the healthy, expected answer); `Ok(_)` → `true` **plus a
  warning**, because a value there means something wrote to a reserved account; `NoStorageAccess` /
  `PlatformFailure` / `Entry::new` failure → `false`.
- The slot argument is still parsed and still validated through `keyring_account()`, so
  `keyring:unknown-slot` remains the contract for a bad slot — but it no longer selects the item
  looked up.

## The semantic change, stated rather than buried

`isAvailable()` currently conflates two questions: "is the Keychain backend reachable" and "can we
read THIS item". After this change it answers only the first — which is what its own source comment
("Backend works, whether or not a token is currently stored") and `SidecarHumbleSecretStore`'s
("a Keychain that is reachable for one slot is reachable for the other") have always claimed it
asks.

Concretely: a user who **denies** the authorization dialog for a real item used to drive
`isAvailable()` to `false`; now it stays `true`. One caller is affected —
`humble/user.ts:116`'s `configStore.set('encryptionDegraded', !(await store.isAvailable()))`.
That is judged correct: denying access to one item does not make the backend unavailable, and the
write path's own `setSecret()` failure handling is what reports a failed write. Accepted
deliberately, not overlooked.
