## D-01 — the selection rule: prefer the run-level record, else index 0

`selectPrimaryDepotFailure(failures)` returns `failures.find((f) => f.scope === 'run') ?? failures[0]`.

Determinism is the defect, and either deterministic choice fixes it — but the CHOICE
matters. The stall is normally the right headline: the run gave up, and a single upstream
file failure is usually a symptom of that rather than the thing a user should be told to
retry against. `classifyDepotError` reaches `isStallError` (`depotErrors.ts:283`) and
returns the real localised `steam.download.error.stalled` copy with `action: 'retry'`,
which is the actionable diagnosis; the file-level alternative under ordering A can be a
`sha1 mismatch` classified `verifyFailed` with `action: 'none'` — an affordance-free
message about a symptom.

This changes ordering B and ordering C not at all (both already read the run-level
record). It changes ordering A's outcome, which is a genuine user-facing change for an
ordering that occurs today, and is why this needed its own task rather than riding along
with `260927-tpm`.

## D-02 — tier 1 (prefer a non-retryable file-level cause) is DROPPED, on a measurement

The three-tier rule was gated on a factual question, now answered in the census above: no
file-level `DepotDownloadFailure` can carry a `.cause` for which
`isNonRetryableDepotError` returns true. The only two sites in `src/` that stamp a numeric
`.eresult` property both live inside `buildDepotPlan`, whose throws are classified
directly by the orchestrator's outer catch and never enter `failures`. The two file-level
producers cannot reach either site.

So the shipped rule is two-tier. No tier-1 mechanism is written and no tier-1 test is
written, because this repo has a standing lesson against hand-maintained sets that only
list cases someone imagined.

**The residual, named honestly and NOT gated.** The measurement is a snapshot of today's
call graph. If a future change stamps a numeric `.eresult` on something thrown out of
`downloadSingleFile` or `healReconciledFileModes`, a permanent cause could be masked by
retryable-looking stalled copy — telling a user to retry something that can never
succeed. Nothing detects that. The invalidating condition is written into the helper's own
doc comment (where the next reader of this code will see it) and into the todo resolution
note. A source gate over `.eresult` assignment sites was considered and declined: it would
be broad, fragile, and would look like it covered more than it does.

## D-03 — ONE shared helper, not two copies of the same precedence

The two consumers read the same record today, so they cannot diverge from each other.
Preserving that is a requirement, and a shared function call is the only shape that
preserves it structurally. Two independent implementations of the same precedence would
satisfy every behavioural arm in this plan and still be free to drift on the next edit.
The source-shape arm (T3 in Task 2) is what pins the single-call shape rather than merely
the current behaviour.

## D-04 — `first: file="(run)"` is the correct display, and no new sentinel is invented

When the run-level record is selected, the `first:` fragment names `(run)`. This satisfies
specialist finding I-1, whose rule is that the fragment must not name a file that never
ran: `(run)` names no file at all. `260927-tpm`'s D-A already established `(run)` as the
display placeholder with `scope` as the discriminant. `file` stays a required `string`.

## D-05 — the helper keeps today's non-empty precondition; it is not made total

`const first = failures[0]` already throws on an empty array at the `first.file` read, and
its only production caller is guarded by the entry gate at `depot.ts:3498`. The helper
returns `DepotDownloadFailure` (not `| undefined`) so no call site has to grow a narrowing
branch. Widening the contract would be scope creep into the entry gate, which is
explicitly out of scope.
