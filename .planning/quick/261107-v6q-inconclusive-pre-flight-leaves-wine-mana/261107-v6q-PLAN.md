<objective>
Close the residual hole in 61-26's WR-01 fix, which 61-REVIEW calls the new WR-01 and 61-HUMAN-UAT lists as item 4. The user decided FIX on 2026-11-07. Under an inconclusive CrossOver pre-flight, a bottle whose marker is not a known pin is coerced today to `d.pins.current`. That covers a `wine-manager` marker (pinId null) and a retired or unknown pin id. `prepareBottleForEngine` then performs a real switch: it kills the wineserver, rewrites the marker and changes DXVK. After this plan such a bottle keeps its recorded engine. When the recorded engine cannot be resolved, the bottle takes the CrossOver branch. It is never moved to pins.current. The reason stays cx-inconclusive, with no toast, notice or badge.

Purpose: an inconclusive probe proves nothing (59 D-09). A launch must not rewrite the engine of a bottle the user or a past launch put on Wine Manager or an older pin.
Output: code and tests in src/backend/engine, and UAT item 4 recorded as pass.

## Design decision (planner's choice, justified)

The task offered two options. The first keeps the recorded engine through a no-op "keep current engine" selection, if one can be expressed. The second takes the CrossOver branch. Reading `prepareBottleForEngineBody` (engineSwitch.ts ~488-611) shows the second option is not a no-op for these markers. `identityOf(prev)` is `wine-manager:<v>` or `pinned:<retired>`, and a crossover selection's identity is `crossover`. A mismatch means a real switch: `busyRefusal`, `killPrevious` (wineserver kill), a DXVK restore and a marker rewrite to crossover. The CrossOver branch only leaves a bottle untouched when the marker is crossover or missing, which is why 61-26 used it for those cases. The no-op therefore has to come from a selection whose identity equals the marker's identity. That selection can be expressed:

- **wine-manager marker:** the `EngineSelection` wine-manager arm already exists. `resolveWineManagerStaging(markerId, d)` yields wineBin and wineserverBin from the installed build. `markerForBase` gives identity `wine-manager:<managerVersion>`, which equals the marker's identity, so prepare returns `{ok:true, changed:false}`. The only type change is widening that arm's `reason` from `'override'` to `'override' | 'cx-inconclusive'`. Every fallback-toast and notice gate already excludes `cx-inconclusive` by reason, not by kind: launchEngine.ts ~436-442, steam/gameLaunch.ts ~709-713 and engineState.ts ~365-370.
- **retired pin marker:** the pinned arm, with `pinId` set to the marker id, has identity `pinned:<id>` and is a no-op for prepare. The engine paths come from the marker's own `wineserverBin`. The summary accessor only exposes it when the path is inside `pinnedEngineRoot()` and its basename is `wineserver`. The decision only uses it when both `wineserver` and its sibling `wine` exist (`d.fileExists`).
- **unresolvable recorded engine:** this covers an uninstalled or -DXMT Wine Manager build, and a retired pin whose directory `pruneUnpinnedEngines` already deleted. No engine exists that keeps the bottle as it is, so a switch cannot be avoided. These cases take the existing CrossOver branch with reason cx-inconclusive. That is 59 D-09's inconclusive default and Automatic's own engine. pins.current would be an engine nobody chose, and returning `unavailable` would make a persistent residual invalid-bottle a permanent launch refusal. D-16 still holds here: prepare's `busyRefusal()` refuses the switch while another game runs in the bottle, so a busy-bottle timeout cannot kill a neighbour.
</objective>
