<design_decision>
## Newer-build marker: refuse to switch, never infer over it

How a null marker is used today (engineSwitch.ts `prepareBottleForEngineBody`): `readMarker` null
falls through to `inferMarker`, which guesses `prev` from `cxbottle.conf` (Timestamp => crossover,
else the CURRENT pin with no `dxvk`). Then (a) same identity => `if (!marker) writeMarker(nextMarker)`
overwrites the file; (b) a switch to CrossOver decides `restoreNeeded` from `current_dxvk-macOS` or
`prev.dxvk` and takes its DLL list from the inferred pin rather than the recorded dir; and the final
`writeMarker(bottleDir, nextMarker)` replaces the only record of what was installed. So "treat a
newer marker as absent" would both act on a guess and destroy the newer build's record. Even when a
newer marker still passes v1's strict field validation, a newer build may track DXVK in a field v1
does not know, so a v1 switch could leave DLLs behind and then downgrade the record.

Rule (applies whenever `isEngineMarkerReadOnly(markerPath)` is true — reason `newer`, or `failed`
from an unexpected engine error):
1. `readMarker` still does its strict best-effort parse, so the read-only accessors
   (`readBottleEngineMarkerKind`, `readBottleEngineMarkerSummary`, `restoreNeedsAbsentPin`) keep
   working for a newer marker whose v1 fields still validate, and return null otherwise (their
   documented "never infers or writes" contract; null there is display/decision input, not a write).
2. `prepareBottleForEngineBody`: if the parsed marker exists, its identity equals `next`, and this is
   NOT the `dxvk === 'failed'` retry => return `{ ok: true, changed: false }` with no write (same
   engine, nothing on disk needs to change, launch proceeds). Every other case — marker unparseable
   (null), a real engine change, or the failed-DXVK retry — returns
   `{ ok: false, reason: 'marker-newer', detail }` before `busyRefusal`, `onSwitching`, any kill, any
   `ensurePinEngine`/restore-source download and any DXVK step. `inferMarker` is never consulted.
3. `writeMarker` refuses (one `logWarning`, no file touched) when the marker is read-only — a
   belt-and-braces guard; rule 2 already prevents every write path from being reached.

Why refusing is the right trade: the cost is that a user who downgraded after running a newer build
cannot switch that one bottle's engine on the older build (same-engine launches still work); the
alternative is stale DXVK DLLs under CrossOver or a lost restore record, which is the exact defect the
todo exists to prevent. The engine also records the file in the read-only notice (area `app-data`).
</design_decision>
