<objective>
Stop the OAuth login overlay from rendering a Dialog for the post-window token exchange, and give
the Accounts-screen tile its own busy spinner so the feedback for that wait moves from a modal
onto the tile.

Purpose: a modal that slides in over 500ms and straight back out is worse than nothing when the
wait behind it is a second or two. The operator has now measured that wait on this machine. But
the reasoning that made silencing it safe — "there is already a spinner on the button" — was
false, so the silencing has to be paired with actually building that spinner, or the screen looks
completely idle during the exchange.

Output: one new optional `Runner` prop with a CSS ring spinner, five tiles wired to it, a
four-member Dialog-phase set in `OAuthLogin`, two existing gates re-aimed at their real intent
rather than weakened, new element-tree assertions in the `Runner` suite (which, unlike the Login
source gates, is a real harness), and a twelve-question macOS live gate carried as a
`<human-check>`.

NOT in scope, and deliberately so: `src/frontend/screens/WebView/components/TauriLoginPanel.tsx`
and the `isLoginPathname(pathname)` branch of `src/frontend/screens/WebView/index.tsx` are NOT
touched. Those routes have two further entry points —
`src/frontend/screens/Humble/Keys/index.tsx` (~L113-117) and
`src/frontend/screens/Login/components/LoginWarning/index.tsx` (~L38-56) — and the panel's own
post-window branch (`TauriLoginPanel.tsx:195-216`) is still reached from there. `preparing` is NOT
touched either (D-1).
</objective>

261003-s04 the orchestrating session argued this phase must render, citing "5-27 s of dead UI"
from `src/frontend/screens/WebView/useTauriOAuthLogin.ts:40`. Re-measured at planning time: that

modal spends most of its life sliding. That is the amendment's whole basis.

`preparing` is NOT affected and stays in the Dialog set: it IS explicitly measured (~12.8s) and
Amazon-only, per quick task 260806-teb, whose own existence is the record that the old copy lied
about a window having opened during that wait.

**D-2 — FIVE tiles get the spinner, not six. This CORRECTS the brief, on a type fact.**

The brief says "apply `busy` to all six tiles". Zoom cannot take it. Derived at planning time:
`OAuthRunner = 'legendary' | 'gog' | 'nile' | 'zoom'` (`src/common/types/oauthLogin.ts:15`),
`OAuthOverlayRunner = Exclude<OAuthRunner, 'zoom'>` (`OAuthLogin/index.tsx:21`, D-7 of 261003-s04),
and `LoginOverlay = 'steam' | 'humble' | OAuthOverlayRunner` (`Login/index.tsx:57`) — so
`openOverlay`'s type is `'steam' | 'humble' | 'legendary' | 'gog' | 'nile' | null`, which has no
overlap with the Zoom id. `pnpm codecheck` is expected to reject the comparison outright (TS2367,
"no overlap"); that run is the live proof of this paragraph.

The conclusion holds either way, which is why it is safe to decide here: even if TypeScript
accepted the comparison it would be permanently false, because the Zoom tile passes no
`primaryLoginAction`, so clicking it runs `navigate(props.loginUrl)` and unmounts the whole
`runnerGroup` — there is no tile left on screen to spin.

Therefore the new prop is OPTIONAL (`busy?: boolean`) and the Zoom tile simply omits it, leaving
Zoom byte-identical to today. The brief's "all six" is satisfied in substance: every tile that can
be in flight shows that it is.

**D-3 — `busy` is derived PER TILE from `openOverlay`, never from the screen-wide flag.**
`loginInFlight` is `openOverlay !== null` (`Login/index.tsx:105`) and is screen-wide by
construction, so feeding it to the tiles would spin all of them at once. Each tile compares
`openOverlay` against its OWN overlay id. A source gate pins the screen-wide form out (Task 2).

The window this covers is verified, not assumed: `openLoginOverlay` sets `openOverlay`
(`index.tsx:233`), `dismissLoginOverlay` clears it synchronously and immediately
(`index.tsx:240`, with the T-34.4.2-41 comment recording why), and `OAuthLogin` calls `dismiss`
only from its success and cancel handlers (`OAuthLogin/index.tsx:104-111`), both of which fire
AFTER the exchange. So the spinner covers `preparing` -> `awaiting` -> the now-silent exchange and
clears on success — exactly the window D-1 opens up.

`busy` is ADDITIVE. It must not replace, narrow or fold into `disabled`. See T-U48-03.

**D-4 — the spinner is a CSS ring copied from a measured-working in-repo precedent, NOT
FontAwesome.**

The dominant in-repo idiom for a small inline spinner is
`<FontAwesomeIcon className="fa-spin-pulse" icon={faSpinner} />` — six call sites
(`StoreSearchBreakdown`, `ImportDialog`, `DownloadDialog`, `SearchBar`, `DLCList/DLC`,
`Winetricks/WinetricksBrowse/Row`), plus `icon={faSpinner} spin` in `SideloadDialog` and
`SteamGridDBPicker`. It was considered and NOT taken, on a measurement: a grep for
`fontawesome-svg-core`, `autoAddCss` and any FontAwesome stylesheet import across
`src/**/*.{ts,tsx,css,scss}` returns ZERO hits, so `fa-spin-pulse`'s animation depends entirely on
FontAwesome's own auto-injected CSS. Whether that injection lands under this app's Tauri/WKWebView
surface cannot be established from the desk, and a spinner that renders as a static ring is
precisely the silent half-fix this task exists to avoid.

Use instead the pattern at `src/frontend/screens/WebView/index.css:40-57` —
`.WebView__unavailablePanel-spinner` plus `@keyframes gamelibFinalizingSpin` — scaled down for a
60px-tall tile. That spinner is measured-working in this app: it is the one the operator watched
for 1-2s/4-5s while taking the measurement D-1 rests on.
