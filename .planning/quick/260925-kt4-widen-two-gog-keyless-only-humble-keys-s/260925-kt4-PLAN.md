## The todo names TWO sites. There are FOUR, and the extra two are created by fixing site 1.

This was measured during planning, not assumed. Record it in the closing todo.

| # | Site | Current gate | In the todo? |
|---|------|--------------|--------------|
| 1 | Claim destination fork — `Keys/index.tsx:468` | `key.platform === 'gog_keyless'` | yes |
| 2 | Gift affordance — `viewFilters.ts:160` (`isGiftable`) | `key.platform !== 'gog_keyless'` | yes |
| 3 | `login-and-claim` exclusion — `HumbleKeyRow/index.tsx:273` | `humbleKey.platform !== 'gog_keyless'` | **no** |
| 4 | Claim-button label — `HumbleKeyRow/index.tsx:571` | `isGogKeyless` (local, `:364`) | **no** |

**Sites 3 and 4 are not optional extras — leaving them would ship two new lies the moment site 1
lands.** Both are consequences of re-pointing the click:

- **Site 3.** `GAMELIB_LOGIN_STORES` (`keyTypePresentation.ts:207-216`) maps `epic_keyless -> 'epic'`.
  So an `epic_keyless` row with `storeLoginConnected === false` resolves to `'login-and-claim'`
  and renders "Log into Epic and claim" — while its claim click, after site 1, opens Humble's
  embed. That is verbatim the failure the existing comment at `HumbleKeyRow/index.tsx:266-269`
  says the `gog_keyless` exclusion exists to prevent ("would send the user to connect a store the
  click never reaches"). `origin_keyless` is absent from that table (`-> null`) and is immune, so
  this is an `epic_keyless`-only exposure.
- **Site 4.** The label branch reads `isSteam ? 'Activate' : isGogKeyless ? 'Claim on Humble' :
  'Claim on {{store}}'`. After site 1, an `epic_keyless` button would say **"Claim on Epic Games"**
  and open Humble. `origin_keyless` would say "Claim on Origin" and open Humble. The
  D-43-12/D-43-11 honesty standard recorded at `:559-563` is that this label names the destination
  the click actually reaches.

Both are one-token swaps against the `isKeyless` local that **already exists** at
`HumbleKeyRow/index.tsx:371`, and `humbleKeys.claimOnHumble` is an existing key already filled in
all 49 locales. So sites 3 and 4 cost no new string and no new predicate.
</scope_finding>

<decisions>
**D1 — site 1 routes ALL keyless types to the Humble-keys embed.** The live D-43-11 probe measured
the embed destination for `gog_keyless` **only**, and no second probe is being bought. The
generalisation to `epic_keyless`/`origin_keyless` rests on a *structural* fact, not on a second
measurement: `classify.ts:174-181` gives all three the same no-key-code shape, and
`humbleKeysEmbedPath()` targets Humble's own platform-agnostic keys page — not a store-specific
redemption endpoint — so nothing store-specific is being guessed. The alternative (leave them
pointed at the reveal wizard) is a known dead end for a code that does not exist. **Write this
limit into the code comment at the fork; do not let a later reader believe all three were
measured.**

**D2 — site 2 changes `isGiftable` ONLY. `isGiftableSpare` is NOT touched.** `isGiftableSpare`
(`viewFilters.ts:116-120`) reads only `ownedElsewhere` and `state`; it has no platform parameter
and excludes no key type at all. Widening it would mean changing its `Pick<>` signature and its
meaning, which the 260911-nyq comment at `HumbleKeyRow/index.tsx:251-256` explicitly forbids —
"the SPARE classification is still what selects scenario 3; the gift AFFORDANCE is a wider
question, answered by `isGiftable` at the caller". Widening `isGiftable` alone closes the
affordance everywhere, and that chain is measured: `Keys/index.tsx:493` builds `giftAction` from
`isGiftable(key)`; `HumbleKeyRow/index.tsx:387` derives `hasGiftAction: giftAction !== undefined`;
the `gift-only` branch at `:257` requires `hasGiftAction`. Task 1 **pins that chain with a test**
rather than leaving it as an argument on paper.

**D3 — closed set only, never `endsWith`.** All four sites call the existing `isKeylessKeyType`
(`keyTypePresentation.ts:200-202`). Do not add a predicate. Do not convert it to a suffix match: a
suffix match would admit an unrecognised, possibly hostile `key_type` into branches that
*suppress* an affordance. Every task below carries a `foo_keyless` assertion — that is the single
assertion that tells a closed literal set apart from a suffix test, and it is the reason this plan
has three of them.

**D4 — no new strings, confirmed by measurement, with one consequence stated honestly.**
Site 1 re-points an existing route; site 4 reuses the existing `humbleKeys.claimOnHumble`; sites 2
and 3 withhold existing elements. **The one thing to notice and NOT panic about:** an
`ownedElsewhere` + `UNREVEALED` + non-fuzzy keyless row loses its full-width `gift-only` button
and its KEY cell goes empty. That is not a new state and not a regression introduced here —
`isGiftable` already excludes `gog_keyless` today, so that exact empty cell already ships for
`gog_keyless`. Site 2 only extends an already-accepted behaviour to the other two types. It is
therefore **not** the j58 "a suppressed button must still leave the cell saying something true"
case, where the suppressed element was the cell's only occupant and no prior art existed. Do not
invent a string for it.
</decisions>
