<objective>
Implement Verify for Steam games on both install routes, replacing today's bridge-DLL-only `repair()` in
`src/backend/storeManagers/steam/gameMaintenance.ts` (~35). Spec: the Verify section of
`.planning/todos/pending/2026-11-07-implement-steam-verify-and-move-install.md`. Its Move section is
OUT of scope here and is split into a new todo (Task 3). `moveInstall` stays exactly as it is.

1. **Steam-registered (Mac-native) games:** ask Mac Steam to validate through the bridge helper's
   IClientAppManager attach (`StartValidatingApp`, slot 27 on the measured build, `(appId) -> bool`,
   proven silent in spike 069). Resolve the slot at runtime, as InstallApp/UninstallApp do. Fall back to
   `steam://validate/<appId>`. Hold `repairing` until Steam's app state says it has finished.
2. **Bridge games** (bottle `steamapps`, which Mac Steam never sees): run a Rust depot job over the ACF's
   InstalledDepots GIDs. It fetches only chunks that fail SHA-1 and never touches files the manifests
   don't own. After it, re-place the `steam_api` shim and re-check the shared-redist ledger. Show
   `repairing` with progress, and refuse while the game is running.

Purpose: Verify is one of the two Steam library actions GameLib can't start today. Bridge games have no
other verifier at all.
Output: the helper subcommand, two route modules, chunk-level repair in the depot crate, honest
notifications, and the todo split.

**Three measured facts that override the task description. Read them before starting:**

- **`verify_only` fetches nothing.** `src-tauri/crates/gamelib-depot/src/download.rs` ~1111: "No chunk is
  fetched: the reconcile walk is the whole job", and test `verify_only_fetches_nothing` in
  `tests/job_modes.rs` proves it. A repair therefore uses an **`install`-mode** job: reconcile first, then
  fetch only what's queued. Today `install` mode re-downloads every chunk of a bad file, because
  `write_file` opens it with `truncate(true)` (~562). Task 2 makes it reuse SHA-1-verified chunks, so only
  bad or missing chunks are fetched. Record this deviation from the "verify_only" wording in the SUMMARY.
- **A Steam validate does not move the ACF.** Spike 069 `watch.jsonl` at 09:23:32–33: StateFlags stayed
  `4` throughout and only TargetBuildID flipped to `0`. Over IPC the same seconds read
  `installState: 268` and `downloadingAppId: 333300`, then `4` / `0` once it was done. The Rust steampoll
  update arm only completes on a build change (its `update.rs` header, D-11), and a validate never
  changes the build. So the existing ACF/steampoll pollers cannot see a validate finish. The completion
  signal is IPC app state, read by the helper itself (Task 1). `dispatch.repair` already sends
  `repairing` before awaiting `game.repair()` and `done` after, so a `repair()` that resolves only when
  Steam finishes holds `repairing` without adding a poll loop in TS or Rust.
- **`buildDepotRefs` returns the branch's CURRENT manifests and buildid**
  (`src/backend/storeManagers/steam/depot/plan.ts` ~453–560). A verify run on those would silently
  become an update. Pin every ref's `gid` to the ACF's InstalledDepots manifest, and finalize with the
  ACF's installed buildid.
</objective>

**Helper, C (`gamelib_installapp.h` + `bridge_helper.c`).** Add a `--steam-validateapp <appId> [--wait] [--dry-run]` subcommand, modelled on the uninstall subcommand.

New defines, from the interfaces block:
- GL_IA_FN_STARTVALIDATING 0x5078u
- GL_IA_FN_CANCELVALIDATION 0x9949u
- GL_IA_FN_INSTALLSTATE 0xeaf2u
- GL_IA_FN_DOWNLOADINGAPP 0xae86u
- GL_IA_VALIDATE_WAIT_CAP_S 21600 (6 h)
- GL_IA_VALIDATE_START_GRACE_S 20
- an active-state mask of 0x8 | 0x100 | 0x400 | 0x20000

Add `gl_ia_run_validate(app_id, wait, dry_run)`. It uses the same attach order as `gl_ia_run_uninstall`: getter-slot scan, then the app manager, then its vtable.
- **Slot guard.** Resolve the StartValidatingApp slot by unique high half. Require that CancelValidation resolves to exactly that slot + 1 (the same neighbour guard UninstallApp uses). If either check fails, report `gl_ia_unavailable("method-unverified:StartValidatingApp")`. Never call a hard-coded slot.
- **Dry run.** `--dry-run` prints `{"result":"ok","dryRun":true,...slots}` and calls nothing.
- **The call.** Call the slot with the probe's call shape. A zero low byte prints `{"result":"refused"}` and exits GL_IA_EXIT_ERROR.
- **Without `--wait`.** Print `{"result":"ok","tracked":false}`.
- **With `--wait`, resolve the state slots.** Resolve GetAppInstallState and GetDownloadingAppID by unique high half. If either is unresolved, print `{"result":"ok","tracked":false,"reason":"method-unverified:<name>"}` and exit 0.
- **With `--wait`, the poll.** Sample both once a second (usleep). The app is active when GetDownloadingAppID equals appId or installState intersects the active mask.
- **With `--wait`, stopping.** Finish when the app was seen active and then reads inactive on 2 consecutive samples, or when it was never seen active within the start grace. If the UpdatePaused bit (0x200) is set, stop with `"finished":false,"reason":"paused"`. At the wait cap, stop with `"finished":false,"reason":"wait-cap"`.
- **Output.** stdout carries exactly ONE final line: `{"result":"ok","tracked":true,"finished":<bool>,"installState":<last value>[,"reason":...]}`. Log state transitions only, to stderr, so the 64 KiB runner buffers never fill.
