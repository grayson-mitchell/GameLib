<objective>
Run a measured experiment on the Linux store embed's stale-size defect. Keep a code change only if
the measurements earn it.

Live evidence (orchestrator, this machine, 2026-11-05, `pnpm tauri:dev`, one run each): R1, R3, R4
and R5 were fine. R2, R6 and R7 failed. In each failure the settled line had the requested position
but a stale size:

- R2: requested `307,98,973x702`, embed `1024x718`.
- R6: requested `213,68,787x632`, embed `744x618`.
- R7: requested `213,68,937x652`, embed `744x618`.

There were no zero-area, linux-not-mounted or dispatch-timeout lines, so `apply_bounds` returned Ok.

Planner's source reading. This is a hypothesis, not a measurement. GTK 3.24.33 is this host's
version (`pkg-config --modversion gtk+-3.0`). Source: https://gitlab.gnome.org/GNOME/gtk/-/raw/3.24.33/gtk/
- `gtkwidget.c` `gtk_widget_set_usize_internal`: `set_size_request` updates the request but calls
  `gtk_widget_queue_resize` ONLY when the widget is visible and the value changed. On a hidden
  widget the size-request cache is left holding the old size.
- `gtk_widget_show` queues a resize on the PARENT only.
- `gtkfixed.c` `gtk_fixed_size_allocate` allocates each child at `child->x/y` (`Fixed::move_`
  updates those even while the child is hidden) with `gtk_widget_get_preferred_size`. That size
  comes from the child's cache: `gtksizerequest.c` calls `gtk_widget_ensure_resize`, which clears
  the cache only when `resize_needed` is set.
- Result: a rect applied while the embed is hidden lands at the NEW position with the OLD size. D-21
  hides the embed on route leave, and `store_embed_open`'s existing-embed branch applies the rect
  before `show()`. That matches all three failures exactly.
- The renderer's follow-up `scheduleFlush` re-sends the identical rect. `changed` is then false, so
  it is a no-op and the stale size persists.
- An explicit `queue_resize()` on the embed sets `resize_needed`, so the next measure re-reads the
  request.
- The morning's single R5 pass is NOT explained by this reading. Something else, such as a WebKit
  internal resize during navigation, can invalidate the cache, which would make the defect
  intermittent. This is why both arms are repeated.

Experiment design:
- Arm A adds `embed_w.queue_resize()` alone. That is one variable, and it is the call the source
  reading targets.
- Arm B is a bounded contingency, used only if Arm A has any failing line. It also adds
  `fixed.queue_resize()`, the orchestrator's second candidate. The source reading says this call is
  redundant, because `show()` and `Fixed::move_` already queue the Fixed.
- No reordering relative to `show()` is attempted. `resize_needed` persists until the next measure,
  so ordering should not matter. If both arms fail, the reading is refuted and that becomes the
  finding.

REAL-PROFILE ARM, declared under the CLAUDE.md two-profile rule:
- Both live arms deliberately inherit the operator's real HOME. The defect was measured under the
  signed-in profile, and the Stores route's state is part of the measured condition, so a fake
  profile would be a different experiment.
- Consequences: no raw log line other than `store_embed(linux)` geometry ever leaves the scratchpad.
  Screenshots are never committed. Raw captures are deleted at teardown. The zoom and window size
  the run changes are restored.

Purpose: answer, with a same-session before/after contrast, whether a queued resize makes Linux R2,
R6 and R7 pass. Close item 2 of the store-embed follow-ups todo, and the Linux half of item 3, only
if it does.

Output: baseline and experiment evidence (geometry lines only), `score.py` with a self-test, a
mechanically computed verdict, the code change kept or reverted to match, and a dated todo section.
