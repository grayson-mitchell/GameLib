### Why the character total is a floor

twice; characters are counted on the dedented raw extent, which is not the string a YAML parser
emits (chomping `|- |+ >- >+` and folded `>` line-joining change the final length); and trailing
blank lines are trimmed.

## The finding the todo did not anticipate: `expected: |` SUPPRESSES, it does not truncate

`parseUatItems`' `testPattern` (`uat.js:150`) needs `expected:` to carry inline text **and**
`result:` to be the very next line. A block scalar puts the body in between, so the pattern never
matches and **every item in the file disappears from `audit-uat`**.

Proved by control: `34.5-UAT.md` has 22 `### N.` items, 23 `expected: |` blocks, 3 `result: blocked`.
Phase 34.5 is **absent** from `audit-uat`. Flattening the **single** `expected: |` of item 18 in a
scratch copy made phase 34.5 **appear**, with exactly one item. Nothing else changed.

This is strictly worse than the defect the todo describes: truncation shows an operator an
obviously-wrong `"|"`; suppression shows them a clean, complete-looking audit with three `blocked`
items silently missing. This is what drove the severity change.

## Reader asymmetry — confirmed, and it bounds any future remedy

Same file, same syntax, opposite outcomes, both from tool output:
`uat render-checkpoint --file .../34.5-UAT.md` returns test 5 with its `expected: |` block (L104)
**fully dedented and intact** (829-char checkpoint), while `audit-uat` omits phase 34.5 **entirely**
because of that same syntax. **Flattening body `expected: |` would regress `render-checkpoint`,
which is correct today, to repair `audit-uat`.** All 4 `reaches-correctly` fields reach via
`render-checkpoint`.
