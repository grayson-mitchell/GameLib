<critical_finding>
THE FILED FIX AS WORDED IS INSUFFICIENT. Read this before writing any code.

The task brief says "add a call to `applyMachOExecutableFallback` after
`applyEDepotFileModes`". That alone changes NOTHING for HUMANKIND, because of the guard
on **depot.ts:1650**:

    if (jobFiles.has(file) || !file.flags) continue

HUMANKIND's manifest carries `flagBearing=140` out of 18,949 entries, and those 140 are
exactly the 140 Directory(64) entries (`distinctFlagValues=[64]`, per 23-TRACE.md's H2
verdict). Every real game file — including `Contents/MacOS/Humankind` — has
`file.flags === undefined`, so `!file.flags` is TRUE and the loop `continue`s **before**
reaching `applyEDepotFileModes` at all. Appending a second call after line 1653 would
sit in a branch that flagless files never enter.

The fix therefore requires **restructuring the guard**, not appending a call:
`!file.flags` must stop being an early-continue and become a condition on the
`applyEDepotFileModes` call only. This mirrors the fresh-download call site exactly,
which already has this shape (depot.ts:1388-1401): `if (file.flags) { applyEDepotFileModes… }`
then an **unconditional** `await applyMachOExecutableFallback(dest, file.filename, file.flags)`.
</critical_finding>
