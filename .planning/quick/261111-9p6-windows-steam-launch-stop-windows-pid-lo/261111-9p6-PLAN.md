<objective>
Make GameLib's Stop button end Steam-launched games on Windows. Since quick 261111-7wo these
games reach Playing on Windows, but Stop does nothing for them. Source:
`.planning/todos/pending/2026-11-11-windows-steam-launch-stop-is-a-no-op.md`. Today
`findPidsRunningFromFolder` returns `[]` on win32 and `stopSteamLaunchedGame` returns
`unsupported-platform`, so `SteamGame.stop()` logs its no-op warning and the operator has to quit
from inside the game.

Purpose: one launcher that stops what it launched, on Windows as on macOS/Linux.
Output: a win32 PID lookup by executable path under the install folder, run through the injected
runner, and a win32 stop path (close request, then bounded grace, then force-end survivors), with
unit tests for both. A win32-only real-PowerShell test runs on the operator's box (CI is
ubuntu-only).
</objective>

<decisions>
The todo leaves the design open. These choices are the planner's discretion, grounded in what the
repo already does and in measurements taken on this Windows 11 26200 box on 2026-11-11.

- **P-01 Lister: PowerShell 5.1 CIM, absolute path, constant script.** The lister runs
  `windowsSystem32Path('WindowsPowerShell', 'v1.0', 'powershell.exe')` with
  `-NoProfile -NonInteractive -Command <WINDOWS_PROCESS_LIST_SCRIPT>`. Why not the alternatives:
  `wmic` is absent here (`where wmic` finds nothing), and `tasklist` prints no paths. The repo
  already uses `Get-CimInstance` (`src/backend/utils/filesystem/windows.ts`,
  `src/backend/utils/systeminfo/gpu/windows.ts`), and `steamClientProcess.ts`
  (`readSteamProcessStartTokens`) already runs an absolute System32 PowerShell through the runner.
  The script does four things: it sets `$ErrorActionPreference = "Stop"` (a failed CIM query then
  exits non-zero instead of looking like an empty list), sets `[Console]::OutputEncoding` to
  `New-Object System.Text.UTF8Encoding $false`, runs
  `Get-CimInstance -ClassName Win32_Process -Property ProcessId,ExecutablePath`, filters
  `Where-Object { $_.ExecutablePath }`, and emits one `"$($_.ProcessId) $($_.ExecutablePath)"`
  line per process. Measured: about 1.2 s warm, CRLF line endings, no BOM. Without the encoding
  line, a path under `Gämé Ünï` came back in OEM cp437 (byte 0x84 for `ä`). The default timeout is
  15 000 ms, the same as `START_TOKEN_TIMEOUT_MS` ("cold PowerShell start is much slower").
  **No `env` is passed.** This follows the two-profile rule: the child reads only the process
  table, `-NoProfile` keeps the user's PowerShell profile from running, and both the sibling posix
  arm and `steamClientProcess.ts` pass no env either. There is no real-profile arm.
- **P-02 Matching is on ExecutablePath, path.win32, case-insensitive.** The match uses
  `path.win32` explicitly, never the native `path`, so ubuntu CI and Windows behave the same.
  The folder is normalized with `win32.isAbsolute` and then `win32.resolve`, and it is rejected
  when it is empty, relative, drive-relative (`C:Game`), or a root (`C:\`, `C:/`,
  `\\server\share`, `\\server\share\`). Measured: `win32.resolve('\\\\server\\share')` returns
  `\\server\share\`, and its `parse().root` is itself. The exe path has `/` normalized to `\` and
  a leading `\\?\` before a drive letter stripped. The match is
  `exe.toLowerCase().startsWith(folder.toLowerCase() + '\\')`, and the trailing separator is the
  `Game` vs `Game2` guard. The existing `STEAM_HELPER` deny list and `excludePids` (selfPids)
  apply as on posix.
- **P-03 The close step on win32 is `taskkill.exe /PID <pid>`, with no force flag and no tree
  flag.** It goes through the runner at `windowsSystem32Path('taskkill.exe')`, with
  `timeoutMs: 5000`, `windowsHide: true` and `stdin: ''`. This is the WM_CLOSE analog of SIGTERM.
  The posix SIGTERM cannot simply be reused: Node's `process.kill(pid, 'SIGTERM')` on Windows is
  an unconditional TerminateProcess, with no chance for the game to save. Exit codes, measured:
  a pid that does not exist exits **128**, which is treated as gone and skipped (the ESRCH
  analog). A windowless console process exits **1** ("can only be terminated forcefully"). Exit 1,
  access denied, a timeout or a spawn error all still go into `termed`, so the force step reaches
  them after the grace.
- **P-04 The force step is unchanged.** It stays `deps.signal(pid, 'SIGKILL')`, which is
  `process.kill`, which is TerminateProcess of that one pid. It runs only for pids still present
  in a fresh rescan (the existing PID-reuse guard). Liveness stays `deps.signal(pid, 0)`, which
  Node supports on Windows. There is no tree kill: as on posix, only processes whose executable
  is inside the folder are ever ended.
- **P-05 Scope fences.** None of the following changes:
  - `isProcessRunningFromFolder` (the delete route) keeps returning false on win32.
  - `startSteamLaunchWatch` keeps `unsupported-platform` on win32, because the RunningAppID poller
    is the Playing signal there.
  - `steamLaunchedDeps.ts` is not touched.
  - The `unsupported-platform` member of `StopSteamLaunchedOutcome` stays: `games.test.ts`
    parametrises over it. It simply has no producer any more.
- **P-06 A duplicate `done` is accepted.** After a stop with outcome `stopped`, `games.ts` sends
  `done`, then the poller sees RunningAppID drop and sends a second `done`.
  `libraryState.handleGameStatus` drops the repeat; quick 261111-7wo P-04 documents and accepts
  this. No dedupe is added.
</decisions>
