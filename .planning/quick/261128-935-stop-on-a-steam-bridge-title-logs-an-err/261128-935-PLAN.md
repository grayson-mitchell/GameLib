## Root cause (found at plan time, with evidence)

- The ERROR comes from `logNotFound` in `src/backend/utils/aborthandler/aborthandler.ts`. The todo's
  `files:` path (`src/backend/aborthandler/aborthandler.ts`) is wrong: the module lives under `utils/`.
- The call that misses is **`dispatch.kill`**, not anything in the launch code. In
  `src/backend/gamedetails/dispatch.ts:190-216`, `kill` runs `deps.aborts.call(appName)` for every
  runner and then `getGame(appName).stop()`. The one exception is a delegated Steam install
  (quick 261106-pvk). The frontend sends `kill` when a game is playing or updating:
  `GamePage/index.tsx:779`, `GameCard/index.tsx:775`, ConsoleMode, and the "Stop waiting" button in
  `GameStatus.tsx:386`.
- Nothing is keyed by a running Steam game's appId, on either side of the registry:
  - **TS map.** Steam registers bare-appId controllers only for download and maintenance jobs:
    `gameInstallDepot.ts:175`, `gameInstallBridge.ts:183`, `moveNative.ts:220`, `updateBridge.ts:155`,
    `validateNative.ts:58` and `verifyBridge.ts:107`. The bridge launch has no controller by design,
    as `gameBridgeLaunch.ts:300` and `gameBridgeWineLaunch.ts:273` say.
  - **Rust table (`forwardAbort` -> `launch_runner_abort`, 88.2-16).**
    - Every wine run's abort id is `wine-<serial>` (`src-tauri/crates/gamelib-launch/src/runner/wine_command.rs:313`
      and `:541`), and the `launch_wine_command` schema has no `abortId` field (`src/common/types/ipc/rustInvoke.ts:1401`).
    - Steam runner calls get no app name from their command parts (`call_runner.rs:204`). Steam's
      explicit abort ids are all prefixed (`drm-runner-clone:`, `overlay-runner-clone:`, `overlay-attach:`).
    - No Steam spawn is game-class (there is no `spawnClass` under `src/backend/storeManagers/steam/`),
      so no launch record is written and nothing is re-adopted under the appId (`game/record.rs:298`,
      `game/readopt.rs:377`).
  - So for a running Steam game the forward always answers `false`, and `logNotFound` fires on every Stop.
- What really stops a bridge title is `SteamGame.stop()`'s bridge route. Quick 261024-urq added it:
  `wineserver -k` in the game's own per-game bottle, then the helper stops and the monitor ends
  (`src/backend/storeManagers/steam/games.ts:653-669`). That is why Stop "worked" in the 87-59 live gate.

## Decision (and the rejected alternatives)

- **Rejected: register an abort controller for the bridge launch.** Stop already has a real
  mechanism for the bridge. A controller would either be a dummy nobody listens to, or a second kill
  path that duplicates `stopPerGameBridgeBottle`. A bare-appId key would also share the key space of
  the six download and maintenance controllers above: `create` overwrites, `delete` from one job
  would unregister another, and `downloadqueue`'s `has`/`getSignal` would read a launch as a download.
  The wine schema cannot carry an abort id to Rust either.
- **Rejected: gate `kill`'s abort on `deps.aborts.has(appName)` for Steam.** It is correct today,
  because the TS map holds every Steam appId abortable. But it skips the Rust forward. When the Steam
  launch moves into Rust (`funnel/flights.rs:16-17`: "the TS Steam dispatch until 90.2") and Steam
  runs become game-class with an appId abort id, it would silently drop a needed abort. It would also
  leave the identical false ERROR on sideload Stop (see below).
- **Chosen: keep the abort and the forward, and choose the log level at the call site.** `call(id, opts?)`
  takes `ifMissing: 'error' | 'info'`, default `'error'`. `kill` passes `'info'`, because its abort is
  best-effort for every runner: each store's `stop()` is what ends a running game. For Steam that is
  the route-based teardown. Legendary (`games.ts:1225`), GOG, Nile and sideload end it by a tracked kill.
- **Callers that keep the ERROR (checked one by one).** Each of these expects a registration, so a
  miss is a real defect:
  - `SteamGame.stop()` in-flight depot branch, `games.ts:619`. Its `nativeInstallsInFlight` entry says a controller must exist.
  - `stopCurrentDownload`, `downloadqueue.ts:542`. A current download registers one.
  - The `abort` IPC, `appShellFlowRegistration.ts:499`. EosOverlay and WineItem cancel an operation the user saw start.
  - `signInProbe/pass.ts:273`, the probe's own abortId at its bound.
  - `eos_overlay.ts:132` and `:292`, inside the run's own `onOutput`.
  - `installStallWatchdog.ts:106` and `downloadmanager/utils.ts:393`. Both already ask `has` first.
  - `abortAll` uses `abortLocal` and never logs.
- **Sideload has the same false ERROR. Observed in code, not live.** Its launches pass only `trackKey`
  (`storeManagerCommon/games.ts:186`, `:228`), sideload gets no app name in Rust (`call_runner.rs:204`),
  and its wine runs are `wine-<serial>`. The `kill`-site option covers it with no extra change. Record
  this in the SUMMARY; do not add sideload-specific code.
