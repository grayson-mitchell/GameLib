<objective>
When a store embed's first load fails while the app is ONLINE (one host's DNS or TLS fails, a captive portal, a blocked host), tell the user. Today the Tauri store embed stays blank and nothing says why.

Purpose: wry 0.55.1's macOS navigation delegate has no load-failure callback (Started is didCommitNavigation and Finished is didFinishNavigation, nothing else), so a failed first navigation sends neither event. That makes "no Finished within a bound" the only signal there is. This plan derives it in Rust, carries it over the existing nav-event wire as `loadTimedOut` (already defined for Epic), and shows it in the existing `StoreEmbedTimeoutBanner` row, whose timed-out variant and Rust-side monitor the macOS Epic surface already has.

Output: the Rust load clock and drain raise with 9 unit tests; the coerceNavState extension with tests; the banner's non-Epic variant, Reload route and drain-merge fix with tests; the new string in all 49 catalogues; and the todo closed.

Source item: `.planning/todos/pending/2026-11-18-store-embed-online-first-load-failure-surface.md` (filed by plan 47-14, gap G-47-9; see also `.planning/debug/offline-stores-tab-crash.md`). There is no CONTEXT.md, so there are no D-XX decisions. The choices made here at Claude's discretion are listed below, and each task's action names the ones it applies.

Discretion decisions (each reversible):
- DD-1: evaluate the timeout in the existing drain (`take_nav_events_with`), not in a new thread. This copies the Epic monitor's SHAPE: a bound constant, a pure inclusive boundary fn, a one-shot flag on the state, the flag merged onto every nav state, and Finished clears it. The evaluation site differs because the renderer already polls this drain every 250 ms, under the same lock, whenever the row could be visible. That means no thread lifecycle, no main-thread marshalling, and no new handle at all.
- DD-2: the bound is 20 s. Nielsen's 10 s attention limit, doubled for slow store pages, and shorter than Epic's 45 s because the failure case here is a blank pane. A false positive on a slow page costs one row above a still-visible page, and the row clears on Finished.
- DD-3: the clock is armed by store_embed_open (cold and warm), navigate, back and forward. NOT by reload, because a WKWebView reload of a never-committed page produces no event at all. Started does NOT stop the clock: on Linux Started fires before commit, so only Finished is a cross-platform end-of-load signal. Linux (WebKitGTK) and Windows (WebView2) deliver Finished even for a failed load and paint their own error page, so in practice the raise only fires where a failed load is silent.
- DD-4: copy is "This page hasn't finished loading", which is true for both a hung load and a failed one. The Reload label reuses the existing translated `webview.epicEmbed.timeout.reload`.
</objective>
