# Quick task 260823-tq7 — two record defects in Phase 38's own source of truth

Found while confirming 38-C05 is audit-visible after quick task `260823-tct` closed WR-01. Neither
blocks anything today; both are the silent-rot shape this phase was created to prevent.

## Defect 1 — the `score:` line undercounts by two

```
score: N/A — collection phase, no must-haves. 6 relocated items, 0 discharged.
```

The `human_verification` array holds **8**: `38-W02`, `38-W01`, `38-W03`, `38-C01`..`38-C05`.
ROADMAP.md already says "Items: 8 as of 2026-08-23 … Was 7 as of 2026-08-22. Seeded with 6." So
the array and ROADMAP agree; the `score:` field is the one that drifted, twice, as W02 and then
W03 joined.

The load-bearing count is the array — `audit-uat` counts entries, not this string, so nothing is
mis-audited today. This is `summary-can-be-wrong-while-the-record-is-right`: the restatement rots
while the record stays true, and the restatement is what a human reads first.

**Fix:** `8 relocated items, 0 discharged`. Do not add a "was 6" history note here — ROADMAP.md
already carries the arrival sequence, and duplicating it creates a second thing to keep in sync.

## Defect 2 — `id:` does not survive into the audit output, and position ≠ id

`gsd-sdk query audit-uat` emits each item with a positional `test:` integer and the `test:` prose
as `name`. **The `id:` field is dropped entirely.** Measured 2026-08-23:

| audit position | actual id | prose |
|---|---|---|
| 1 | **38-W02** | Tray — Windows/Linux dark/light tray icon swap |
| 2 | **38-W01** | Window buttons — Windows/Linux |
| 3 | 38-W03 | Login window provisional title |
| 4-8 | 38-C01..C05 | the five gamepad items |

Position 1 is **W02, not W01**, because the array is in arrival order rather than id order. Anyone
reconciling "audit item 3" against "38-W03" gets it right by luck and is wrong one row either side.

This is the failure mode this project has hit five times under
`threat-register-ranges-hide-uncovered-ids` — an audit keyed at a different unit than the record it
audits. Here it is one step worse than usual: the id is not merely unused, it is **absent from the
tool's output**, so there is no key to join on at all except the prose.

**Fix:** append a paragraph to `audit_tool_note` stating that `id:` is dropped, that positions are
arrival-ordered and do not track ids, that position 1 is W02 (the concrete counter-example, so the
note is falsifiable rather than a vague caution), and that cross-referencing must go through the
`test:` prose. Also state the consequence for relocation receipts: an origin phase's
`human_verification_relocated` receipt names an **id**, so a reader who then counts positions in
the audit output will land on the wrong item.
