The Steam library cache ALREADY EXISTS and is ALREADY WRITTEN. The defect is that
the renderer has no way to READ it at boot.

1. Backend cache exists and is populated.
   `src/backend/storeManagers/steam/electronStores.ts:20`
   `const steamLibraryStore = new CacheStore<GameInfo[], 'games'>('steam_library', null)`
   — byte-for-byte the same construction shape as GOG's
   `new CacheStore<GameInfo[], 'games'>('gog_library', null)`
   (`src/backend/storeManagers/gog/electronStores.ts`). `SteamLibraryManager.refresh()`
   writes it (`library.ts:954`), and `refresh()` IS reachable under Tauri via
   `steamFlowRegistration.ts`'s `refreshLibrary` handler. So the file on disk is real.

2. How GOG/Epic/Amazon/Zoom appear at startup — the pattern to copy.
   Each has a RENDERER-side twin CacheStore at the SAME filename, read
   SYNCHRONOUSLY in `GlobalState`'s class-field initialisers:
   `src/frontend/helpers/electronStores.ts:124/137/149/172` declare
   `libraryStore('legendary_library')`, `gogLibraryStore('gog_library')`,
   `zoomLibraryStore('zoom_library')`, `nileLibraryStore('nile_library')`;
   `GlobalState.tsx:256-271` seeds each slice via
   `loadLegendaryLibrary()` / `loadGOGLibrary()` / `loadAmazonLibrary()` /
   `loadZoomLibrary()`. Those reads work at construction time because
   `hydrateStoreSnapshot()` (`src/preload/tauriTransport.ts`) is awaited before
   React mounts and eagerly serves `BOOT_SET_STORES`.

3. Steam is missing from EVERY link in that chain — the root cause.
   - `src/common/types/storePolicy.ts:181` `BOOT_SET_CACHE_STORE_NAMES` is
     literally `['legendary_library', 'gog_library', 'nile_library', 'zoom_library']`.
     `steam_library` is ABSENT, so it is not in `BOOT_SET_STORES`, so the eager boot
     snapshot never carries it, AND it is not in `RECOGNIZED_CACHE_STORE_NAMES`
     (derived at line 197), so `storeNew('steam_library')` from the renderer would be
     refused by `storeWriteHandlers.ts`'s gate.
   - `src/frontend/helpers/electronStores.ts` has `steamConfigStore` but NO
     `steamLibraryStore`.
   - `src/frontend/state/GlobalState.tsx:273-276` hardcodes `steam: { library: [] }`.
   Steam's ONLY path into React state is the async `pushGameToLibrary` event stream
   (`componentDidMount`, line ~1494), which starts empty on every launch.

4. Why the backend's own comment claiming otherwise is WRONG — do not trust it.
   `src/backend/storeManagers/steam/library.ts:784-786` asserts "`init()` pushing the
   persisted list to the frontend independently of `refresh()`, so the library is on
   screen from the first frame of every cold start". `SteamLibraryManager.init()`
   (library.ts:522) does read the cache and push it — but `init()` is only ever
   invoked by `initStoreManagers()` (`src/backend/storeManagers/index.ts:64`), whose
   SOLE call site is `src/backend/main.ts:422`, inside Electron's `whenReady()`.
   `main.ts` is imported by NOTHING in the sidecar chain (`bootstrap.ts` imports
   `./handlers`, never `../main`). This is the same class of defect as the known
   `MigrationSystem` trap: Electron-only startup code that is dead under Tauri.
   Even if it did run, a sidecar push racing the renderer's `componentDidMount`
   listener attachment would be lost.

OUT OF SCOPE, deliberately (record in the SUMMARY, do not fix here): the dead
`initStoreManagers()` under Tauri also disables `startRunningPoll()` and the
interrupted-install resume SURFACING for Steam. Reviving it would start
resume-surfacing machinery at boot for the first time under Tauri — a known
prior root cause of a silent whole-app crash. It is a separate defect with a much
larger blast radius and it is NOT required for the user's ask, which this plan
fully delivers via the renderer-side seed.
</diagnosis>
