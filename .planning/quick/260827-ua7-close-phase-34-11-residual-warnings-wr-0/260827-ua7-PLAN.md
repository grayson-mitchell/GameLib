<design_decision id="WR-08">
**Chosen: option (b) — give `+ New collection` a distinct entry point.**
The spec was checked FIRST, as instructed, and is *not* silent — but it does not resolve
the finding either. `34.11-UI-SPEC.md:281` names `+ New collection` the panel's Primary-CTA
analogue that "opens the existing `CategoriesManager` flow (D-20 — panel only launches it,
does not rebuild it inline)". `:283` mints `manageCollections` as the row that opens the
same dialog. So the spec **mandates that both rows exist and both launch the same dialog**,
and is silent only on how they differ once open.

That mandate kills option (a): deleting either row deletes a spec'd element and orphans a
shipped `gamelib.json` key. It also weakens option (c): re-labelling changes nothing about
behaviour, and on this project a rename attempted through the `t()` default argument is a
silent no-op (the key already exists), so (c) would need catalog surgery to buy zero
behavioural change.

Option (b) is viable because **the create flow already exists**: `CategoriesManager`
renders a `TextInputField htmlId="new-category-name"` with an `Add` button
(`CategoriesManager/index.tsx:201-219`). `TextInputField` spreads `...inputProps` onto its
`<input>` and its props extend `React.InputHTMLAttributes<HTMLInputElement>`
(`TextInputField/index.tsx:6-9`, `:65`), so `autoFocus` passes straight through with **no
change to `TextInputField` itself**. And because `CategoriesManager` is mounted only while
`showCategories` is true (`Library/index.tsx:1153`), `autoFocus` fires on each open.

Option (b) also needs **no new i18n string**, which sidesteps the `gamelib.json`-vs-
`translation.json` rule and the inert-`t()`-default trap entirely. D-20 survives verbatim:
neither row adds, renames nor deletes a category — both still only launch the dialog.
</design_decision>
