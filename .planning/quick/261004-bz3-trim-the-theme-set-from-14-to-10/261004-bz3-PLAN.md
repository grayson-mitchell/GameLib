## D-1 — DECIDED: leave each surviving base theme's `--navbar-accent` exactly as it is

The three `-classic`/`Alt` pairs differ by exactly one token, `--navbar-accent`,
granted to the variant by one shared group rule near the end of `themes.scss`
(re-verified live at lines 710-716). The brief offered two ways to make the collapse
"lossless". Both are rejected in favour of changing nothing:

- **Rejected: add `--navbar-inactive: #eae8e5` to the three surviving bases.** This
  inverts the migration. It makes `marine`, `zombie` and `cyberSpaceOasis` adopt the
  *deleted* variant's near-white nav labels, so every user already on a surviving
  base theme sees a change. A trim must not alter a theme that survives.
- **Rejected: add `--navbar-inactive` to the base `body {}` block.** Measured: this
  would override `gruvbox_dark`'s cream `#f9f5d7`, `sweet`'s mauve `#d4c2d6`,
  `nord-dark`'s `#afc4eb`, and would *lower* `high-contrast` from 18.73:1 to a
  single grey. That is a four-theme regression.
- **Accepted: delete the variants, touch no token.** The residual difference is
  borne only by a user migrating off a theme that no longer exists — which is what
  a migration is. Measured contrast of each survivor's own `--navbar-accent` against
  its own `--navbar-background`: `cyberSpaceOasis` 7.77:1, `marine` 4.87:1,
  `zombie` 5.82:1 — all at or above AA for normal text, so there is no
  accessibility argument for forcing the near-white either.

**Consequence: `FilterFacetGroup/index.scss` is NOT modified.** Its two bare
`color: var(--navbar-accent)` reads stay bare. The header comment at lines 9-18 (read
live) records *why* the bare read was deliberate: `--navbar-inactive` is undefined in
most themes and an undefined custom property with no fallback drops the entire
declaration at computed-value time, whereas `--navbar-accent` resolves in every theme
block. That reason is still true after the trim. Only the stale parenthetical at
line 28 (`dracula-classic, nord-light), 7`) is corrected — see Task 2.

## D-2 — Migration is mandatory, and lives in `themeLabels.ts`

Re-verified live: `window.setTheme` (`src/frontend/index.tsx:223`) treats any key not
in `defaultThemes` as a *custom theme filename* (`:227-228`) and sends it to
`window.api.getThemeCSS` (`:230`) before assigning `document.body.className`
(`:240`). A user left on `old-school` would therefore get `''` back from a file that
does not exist and land on a `body.old-school` class with no CSS — a blank app, not
a fallback.

The map and the pure migration function go in
`src/frontend/components/UI/ThemeSelector/themeLabels.ts`, not inline in
`index.tsx`: that module is already the single home of `defaultThemes`, is already
imported by `index.tsx`, and is deliberately SCSS-free so this project's jsdom-less
jest config can test it (its own header comment states this). `index.tsx` gets a
call site and a `configStore.set`, nothing more.

## D-3 — No new gate

Rejected adding a source gate over theme counts. CLAUDE.md is explicit that a gate
appearing to cover more than it does is the green-check-proving-nothing pattern. The
set is already pinned from four independent directions that this plan updates rather
than replaces: `defaultThemes` key-set equality plus an exact-length assertion
(`ThemeSelector/__tests__/index.test.tsx`), a hand-maintained selector list whose
`cssBlock()` throws on a vanished block (`themeTokens.test.ts`), a
`REAL_THEME_BLOCK_PATTERNS` regex list (`appShellLayout.test.ts`), and — discovered
live, see D-4 — a catalogue/manifest staleness check. Four pins is enough.
