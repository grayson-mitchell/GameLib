<objective>
Put the per-bottle shared-redist ledger (`<bottle>/gamelib-shared-redists.json`) on the Phase 68
store-versioning engine, so a future shape change migrates it (with a backup) instead of tripping
`readLedger`'s "unreadable, starting empty" fallback and dropping a pending display-driver restore
(`displayDriver.prior`) or the `done` record — neither can be recomputed.

Purpose: closes `.planning/todos/pending/2026-11-08-version-shared-redists-ledger.md` and the
`needs versioning later` row in 68-INVENTORY.md.
Output: a ledger codec module (mirroring `settingsFiles.ts`), the ledger reader/writer wired to it,
tests, inventory row updated, todo moved to completed.

**Analog (cite and copy its shape):** `src/backend/storeVersioning/settingsFiles.ts`. Settings
files are the only engine adopters that keep a **top-level** version field (`version: 'vN'`) via a
custom `VersionCodec` (`settingsVersionCodec`) and call `prepareStoreFile(path, chainKey,
{ kind: 'user-state' }, codec)` per file path, then gate writes with
`isReadOnlyPath`/`noteRefusedWrite`. The ledger does the same with a numeric top-level `version`.
The conf-store codec (`storeVersionCodec`, `__internal__.gamelib.schemaVersion`) is NOT used: it
would put a second stamp beside the existing `version: 1`, which the todo forbids.

**Design decisions (planner discretion, recorded here so the executor does not re-decide):**
- The engine stamp *replaces* the hand-rolled field by *being* it: the codec reads/writes the
  existing top-level `version` number. So every on-disk `version: 1` file is already at the
  engine's baseline v1 (`currentVersionOf` defaults to 1) — adoption is a no-op with zero byte
  changes and zero data loss. Older GameLib builds keep reading these files exactly as before.
- Chain key: `steam_bridge/shared-redists` (fixed string; `storeKeyOf` would derive a per-bottle
  key from the bottle directory name, which must not be a chain key). Engine STATE is keyed by
  resolved path, so one chain key serves every bottle. Register it in `STORE_MIGRATIONS` with an
  empty chain and a comment "baseline v1 = the pre-engine hand-rolled `version: 1`".
- Engine contract for a newer version: `runFileMigration` marks the file read-only ('newer'), never
  writes it. The ledger honours that by skipping the whole redist pass for this launch (warning
  logged, no wine calls, no writes). Rationale: a newer build's shape cannot be trusted, and the
  newer build will perform its own pending restore; leaving the file untouched is what
  "refuse to clobber" means here. Same handling for 'failed' (migration step threw).
- Engine contract for corrupt/unparseable files: the engine has no opinion (returns `ok`, leaves
  the file alone — "conf keeps its own clearInvalidConfig behaviour"); each store owns it. For the
  ledger, before starting empty, preserve the unreadable bytes with the engine's own
  `writePreMigrationBackup(path, fromVersion, bytes)` (0o600, dedupes identical bytes, prunes to 3)
  where `fromVersion` is the codec-read version when the file parsed to a plain object, else 0. If
  that backup throws, skip the pass this launch and do not write (no clobber of the only copy).
- `failedView` is irrelevant (the ledger reads the file itself, not through `viewOf`). The
  read-only notice area falls back to `app-data` via `areaForStoreKey`'s default; do NOT add a new
  `ReadOnlyArea` (out of scope).
- Sidecar exit contract: everything added is synchronous graceful-fs or the existing async fs
  calls inside the user-initiated launch path; no timer, watcher or handle; nothing at boot.
</objective>
