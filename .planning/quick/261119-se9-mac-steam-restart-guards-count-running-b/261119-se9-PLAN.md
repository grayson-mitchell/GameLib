<objective>
Make the Mac Steam restart guards refuse while a bridged (bottled) game GameLib launched is running. The guards are restart-on-Play and "Restart Steam now", both of which go through `restartSteamForAdoption`. This resolves the todo `.planning/todos/pending/2026-11-18-mac-steam-restart-ignores-running-bottled-game.md`.

Purpose: quick 261118-uma gave macOS a running-game signal from a process scan by executable path under `<library>/steamapps/common/<installdir>/`. A bridged game, e.g. Avernum 5 / 206040 in bottle `GameLibSteamBridge-206040`, runs as wine processes whose executable is the wine binary, so the scan reads "no game running". GameLib can then quit Mac Steam mid-session, which breaks the bridge's connection to the running Mac Steam.

Output: one session-state read, `runningBridgedAppId`. The restart deps consult it before the Rust read, and both callers wire it in. The plan also adds unit tests for the signal and for the guard refusals, and moves the todo to completed with the operator's live check pending.

Decisions made in planning (a quick task has no CONTEXT.md; these are the planner's calls, with reasons):

1. **The signal is GameLib's own launch bookkeeping: `gameSession.bridgeLaunchBottles` together with `gameSession.bridgeLaunchesInFlight`** (`src/backend/storeManagers/steam/gameSessionState.ts`). Between them they cover the whole bridged session, as follows:
   - `launchBridgeGame` (`gameBridgeLaunchGate.ts`) puts the appId in `bridgeLaunchesInFlight` from Play through pre-flight. Pre-flight covers the engine switch, redists, shim placement and the helper check, and lasts until the wine spawn settles.
   - `launchBridgeGameBody` (`gameBridgeWineLaunch.ts`, around line 573) records `bridgeLaunchBottles` before it spawns wine. `clearLaunchRecord` clears it when the process monitor's `onStopped` fires, which is the same event that tears down the bridge helper. With no monitor, it is cleared when the `winewrapper.exe --run` launcher settles; that launcher lives as long as the game. It is also cleared on launch failure and by `SteamGame.stop()`.

   It covers DRM-mode and overlay launches too, since they take the same path. It is bridge-only and carries the bottle name.

   Rejected alternatives:
   - A Rust process scan for wine processes. Their executable is the CrossOver/wine binary. Mapping one to an appId would need another process's WINEPREFIX (KERN_PROCARGS2) and the bottle naming. A bottle's wineserver can outlive the game, and the shared bridge bottle hosts several games.
   - The bridge-helper registry. Not every bridged session spawns a helper: the no-steam-api route spawns none (`gameBridgeWineLaunch.ts` line ~201).
   - A HELLO/session marker. It arrives only after the game initialises Steam, but a restart during pre-flight or before HELLO already breaks the launch. A helper failure there marks the app bridge-failed for the session.
   - The engine ledger (`markGameRunning`). It is marked only when an install root resolves.
   - The bottle-process-monitor phase (as `updateBridge.ts` `isRunning` uses it). It also covers bottled-Steam games (`bottledSteam.ts`), which a Mac Steam restart does not touch, and no monitor starts when the install root is unresolved.
2. **Wire it into `createRestartDeps.readRunningAppId`, not into `runningPoll.ts`.** That read feeds only the two restart guards, and `steam://exit` is fired from `restartSteamForAdoption` and from nowhere else in `src/`. The uninstall and update guards (`readRunningAppIdOrThrow` / `readRunningAppId`) are not extended. They compare the answer with their own native appId, and a bridged appId is a bottle install on another route that cannot equal a native target. The 5 s RunningPoll and the steampoll Rust op are untouched.
3. **Bridged first, then Rust.** The bookkeeping is a synchronous in-memory read that cannot fail, so consulting it first means a failed or slow Rust read can never hide a known bridged session. When a bridged session is active the Rust IPC is skipped.
4. **`gameSession` is a required dep** of `createRestartDeps`, typed `Pick<SteamGameSessionState, 'bridgeLaunchBottles' | 'bridgeLaunchesInFlight'>`, so neither caller can forget to wire it. Both callers already hold `steamGame.deps.steamSession.gameSession`.
5. **Several bridged sessions:** the lowest numeric appId (not lexicographic) is returned, so the answer is deterministic. The guards refuse on any non-zero value.
6. **Known limit:** the bookkeeping lives for one boot (one `createSteamGameSessionState` per boot), so a bridged session left over from a previous GameLib process is not counted. A false positive fails safe (a refused restart). The user's remedy, as before, is to quit the game.
7. **Platforms:** no platform branch is added. The bridge maps are only filled on macOS, so the read is 0 elsewhere and Windows/Linux keep their behaviour.
</objective>
