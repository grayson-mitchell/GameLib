## Discovered, Filed, NOT Fixed (out of scope)

**i18next cannot resolve plural forms for `nb_NO`/`pt_BR`/`zh_Hans`/`zh_Hant`.** While writing the CLDR cross-check test for Task 1, measured that `i18next`'s `PluralResolver.getRule()` calls `new Intl.PluralRules(code, ...)` with the RAW `lng` code it is given, and never converts an underscore-separated code to the dash form `Intl.PluralRules` requires — these four locale DIRECTORIES are named with underscores, and `loadPath: 'locales/{{lng}}/{{ns}}.json'` feeds the directory name straight through as `lng`. `new Intl.PluralRules('nb_NO')` throws today; `i18next` catches it and `getSuffix` returns `''` for every count. This is PRE-EXISTING (proven live via `translation.json`'s 4 existing English `_one`/`_other` pairs, unrelated to this task) but newly consequential, since Task 2 ships the FIRST plural keys in the fork-owned `gamelib` namespace and these four locales will hit this defect for all of them. Filed as
`.planning/todos/pending/2026-09-25-i18next-cannot-resolve-plurals-for-underscore-locale-codes.md`
(`severity: major`, `ready: code`) rather than fixed — the fix is architectural (a custom `languageUtils`/`pluralResolver` override or a locale-directory rename with a backward-compat migration for already-stored user preferences), out of a quick task's scope, and not something the plan asked for.
