# Quick Task 260924-f9y — the macOS updater artifact is never built

## Goal

`src-tauri/tauri.conf.json` sets `createUpdaterArtifacts: true` and gives the bundler no
updater-enabled macOS target, so `GameLib.app.tar.gz(.sig)` is never produced and `latest.json`
can never gain a `darwin-*` entry. Add the missing target, move the D-11 tripwire that pins the
target array, and close the todo on an honest record.

## Substrate verification (the todo's requirement 1 — done BEFORE planning, not asserted from memory)

The todo forbids naming the target from memory: the bundler's own warning in run `35841476015`
ended at the colon and never printed its list. That list exists verbatim in the INSTALLED CLI
binary (`@tauri-apps/cli` 2.11.4, confirmed via its own `package.json`):

```
$ strings -a node_modules/@tauri-apps/cli-darwin-arm64/cli.darwin-arm64.node | grep 'updater-enabled targets'
The bundler was configured to create updater artifacts but no updater-enabled targets were built.
Please enable one of these targets: app, appimage, msi, nsis
```

Two facts follow, both MEASURED against the installed version rather than recalled:

1. **`app` is the updater-enabled macOS target.** It is also a valid `BundleType` in that same
   package's `config.schema.json` (`enum: ["app"]`, described "The macOS application bundle
   (.app)"), so the config stays schema-valid.
2. **The todo's requirement 2 — is `nsis` likewise the updater-enabled Windows target?**
   `nsis` IS in that enumeration, so YES as a matter of the bundler's own list. That is the whole
   of what is established here: the Windows leg has still never produced an artifact (it dies at
   step 5 `install-deps`, tracked by `2026-09-22-windows-packaged-build-breaks-on-darwin-runner-symlinks.md`),
   so nothing about Windows updater artifacts is measured END TO END and must not be written as if
   it were.

## Ordering choice, stated because it is deliberate

`app` is inserted BEFORE `dmg`, giving `["nsis", "appimage", "app", "dmg"]`. The dmg bundler
consumes the `.app`; tauri-bundler is believed to sort package types by priority so this would not
matter, but that sort was NOT verified here, and declaring the producer before the consumer is
correct under either behaviour. The macOS pair also reads adjacently.

Adding `app` is a no-op on the Linux and Windows legs. That is not an assumption: run
`35841476015` carried `["nsis", "appimage", "dmg"]` on every leg and the macOS leg built only the
dmg while the Linux leg built only the AppImage — the bundler already intersects `bundle.targets`
with the target platform's own set.

## Tasks

### Task 1 — add `app` to `bundle.targets`

- files: `src-tauri/tauri.conf.json`
- action: change `"targets":["nsis","appimage","dmg"]` to `"targets":["nsis","appimage","app","dmg"]`.
  Nothing else in the file changes; `createUpdaterArtifacts` was already `true`.
- verify:
  - `node -e` reads the file and asserts the array deep-equals `['nsis','appimage','app','dmg']`
  - `npx prettier --check src-tauri/tauri.conf.json`
- done: the config declares an updater-enabled macOS target.

### Task 2 — move the D-11 tripwire and pin the reason

- files: `meta/__tests__/artifactTargets.test.ts`, `src/backend/__tests__/tauriConf.test.ts`
- action: `artifactTargets.test.ts` deep-equals `EXPECTED_TARGETS = ['nsis','appimage','dmg']`. Its
  own header calls itself "a tripwire, not a prohibition" and requires that a deliberate target
  change also update this file — so update `EXPECTED_TARGETS` and record WHY `app` joined, so the
  next reader does not read it as target-set creep. Its `exactly one Linux target` assertion is
  untouched (`app` is not in that filter list) and its over-reach control still holds.
  Add one focused assertion to `tauriConf.test.ts` naming `app` as the updater-enabled macOS
  target, so removing it fails a test that says what broke rather than a generic array mismatch.
- verify:
  - `npx jest --config src/backend/jest.config.js -t 'tauri.conf'` (or the project's meta jest
    project) green for both files
  - `npx prettier --check meta/__tests__/artifactTargets.test.ts src/backend/__tests__/tauriConf.test.ts`
- done: both gates pass and the new target is pinned in the direction of removal.

### Task 3 — close the todo honestly

- files: the pending todo → `.planning/todos/completed/`
- action: append a `## RESOLUTION` section recording the measured enumeration, the Windows answer
  and its bound, and — load-bearing — that the PROOF is NOT discharged: the todo's own
  "Readiness split" says confirming `latest.json` gains a `darwin-aarch64` entry needs a macOS
  release run. This closes the FIX, not the observation. The residual live gate must survive the
  close, so it is handed to a live-gate todo rather than evaporating with this one.
- verify: `pnpm planning-gates`; `git status` shows the file moved, not copied.
  NOTE: `npx prettier --check` over a `.planning/` path is VACUOUS — `.prettierignore` carries a
  bare `.planning` — so it is deliberately not claimed as a gate here.
- done: the pending todo is closed and the un-discharged live proof has a home.

## Deviation from the /gsd-quick default path (stated up front)

The workflow spawns gsd-planner + gsd-executor. Both were skipped and this ran inline. Reason: the
substrate verification above was already complete in the orchestrator's context before planning,
and it is the one part of this task that can be got wrong (the repo has repeatedly recorded
prescribed fixes that were wrong about the substrate). Re-deriving it inside a subagent would have
risked a weaker answer than the one already measured. `workflow.use_worktrees` is `false` in this
project, so no isolation was given up by doing so.
