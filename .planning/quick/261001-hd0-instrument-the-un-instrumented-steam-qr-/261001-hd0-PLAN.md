## Planner's discretion, exercised and recorded

1. **A named constant for the timeout.** The challenge-issued line must state the timeout value
   (operator's suggested site). Interpolating a second hand-typed `120000` would let the logged
   number drift silently from the number actually set. Task 1 therefore extracts
   `QR_LOGIN_TIMEOUT_MS = 120000` and has both the assignment and the log line reference it, which
   makes drift a type/compile concern rather than a reading concern. Three non-comment occurrences
   is the gate.
2. **Where the tracker is reset.** `qrSessionState` is reset at exactly two sites: `startQRLogin`
   (`:508`) and `logout` (`:302`). The new `qrLastLoggedStatus` is reset at BOTH, so the two fields
   cannot drift into an incoherent pair. `logout()`'s reset is QR session state, not the credential
   flow, so this stays inside D-04's scope. The `startQRLogin` site is the load-bearing one — it is
   what lets a second attempt log its own first observation.
3. **The transition line logs the PREVIOUS status too.** `none -> waiting` on first observation,
   then e.g. `waiting -> error`. A line naming only the new status cannot distinguish "first poll of
   a fresh attempt" from "status changed", which is exactly the ambiguity the sibling dev-vault todo
   was filed about.

</decisions>
