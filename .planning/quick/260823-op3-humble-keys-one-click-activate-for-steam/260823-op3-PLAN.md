# Quick Task 260823-op3 — Humble Keys one-click Activate + row column reorder

## Why

The Steam redeem path (`window.api.redeemSteamKey` → `SteamUser.redeemKey`) is
live and verified working by the operator (2026-08-23). With a working
redemption API, the Phase 14 claim wizard's manual choreography — warning →
reveal → copy key → open the Steam `registerkey` page → "Mark as redeemed" — is
four steps of hand-work for something the app can do itself.

## Scope

### 1. One-click Activate (Steam keys)

`HumbleClaimWizard` gains an `activating` → `activated` fast path for
`humbleKey.platform === 'steam'`:

1. reveal (`humbleRevealKey`) — or, in `finish` mode, read the already-revealed
   value via `humbleGetRevealedKeyValue`
2. auto-copy the key to the clipboard (D-73 retained — the reveal is
   irreversible, the clipboard is the free safety net)
3. `window.api.redeemSteamKey({ store: 'steam', key })`
4. on `success` / `already-owned` → `humbleMarkRedeemed`, then a terminal
   result panel using the existing `redeemOutcomeCopy()` from
   `RedeemSteamKeyDialog/copy.ts`, plus a Steam library refresh
5. on `invalid` / `rate-limited` / `error` → fall through to the EXISTING
   `keyShown` step (key value + Copy + Open Steam + Mark as redeemed) with the
   outcome copy rendered as a banner above it

**Retained unchanged:** every reveal-failure branch — `owned_blocked` (C2),
`ambiguous`, `rejected_by_server`, `cooldown`, `failed`, and the WR-05
IPC-rejection → `ambiguous` posture.

**Removed for Steam claim entry only:** the D-65 `warning` step. Non-Steam keys
keep warning-first + reveal + show-key, because no auto-activation API exists
for them (D-68's generic help URL is still the only destination).

**Amends T-14-08.** `humbleRevealKey` now has a mount-effect call site. The
previous guarantee against a stray reveal was the warning step; the replacement
guarantee is (a) the wizard only ever mounts from an explicit Activate click and
(b) a `useRef` single-fire latch, so a StrictMode/remount double-invoke cannot
fire the irreversible POST twice.

### 2. Row column order

`HumbleKeyRow` DOM order becomes: **Activate → Gift on Humble → Status badge
(+ urgency) → Title/info → Expiration.**

Action cells keep their existing per-tab gating (`claimAction` = Keys-waiting
only, `giftAction` = Giftable Spares only, D-60/D-67) — a tab that does not
supply an action renders no cell rather than an empty one. Within a tab every
row has the same shape, so a fixed-basis action cell aligns the column.

### 3. i18n

New user-facing strings get NEW keys with `t('key', 'Default')` defaults AND
matching `public/locales/en/translation.json` entries — `humbleKeys.claim` is
already `'Claim'` in en, so relabelling via the default argument alone would be
a silent no-op.
