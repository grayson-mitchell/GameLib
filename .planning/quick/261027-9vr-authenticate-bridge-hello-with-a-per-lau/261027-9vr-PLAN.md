## Locked operator decisions (2026-10-27) -- implement exactly, referenced below as OD-1..OD-6

- OD-1 Harden now. Threat model: other OS users and processes that cannot read the user's files.
  A same-user attacker is explicitly out of reach (can read the cfg and the stored Steam refresh
  token). State this in code comments; do not try to solve it.
- OD-2 Secret channel: backend generates a per-launch random secret (node:crypto randomBytes(32),
  hex). Shim learns it from a `secret=` line in `gamelib_bridge.cfg` (written by writeBridgeConfig,
  tmp-then-rename, result mode 0600; parsed in the generated shim's cfg loader). Helper receives it
  via env at spawn -- NEVER argv. Production inherits ambient env, so the secret is merged onto
  process.env (or onto bridgeHelperSpawnEnvOverride in tests).
- OD-3 HELLO (CONTROL slot 2) carries the secret in its arg blob. Helper marks the connection
  authenticated only on a constant-time match. Unauthenticated: refuse every CONTROL slot except
  HEALTH and HELLO, refuse all interface dispatch; DRAIN (slot 6) never sees the ring. Matching
  reconnect keeps the ring. Never clear the ring on accept/close.
- OD-4 Backend paths that send auth-only CONTROL slots must send HELLO-with-secret first.
  Audit result (done at planning time): the ONLY backend wire client is
  `probeHealthAndWhoami()` in helperProcess.ts, which sends HEALTH then WHOAMI. WHOAMI becomes
  auth-only, so the probe becomes HEALTH -> HELLO(secret) -> WHOAMI. Nothing in src/ sends
  CREATE_INTERFACE / REPORT_* / DRAIN (shim only). Executor re-confirms with
  `grep -rn "encodeControl\|encodeRequest\|CONTROL_SLOT" src --include='*.ts' | grep -v __tests__`.
- OD-5 One secret per helper spawn, stored on the BridgeHelperEntry. A reused helper keeps its
  secret; the identity-only (480) fallback is a new spawn and gets its own. The cfg must carry the
  secret of the entry whose port it carries.
- OD-6 Helper without the env secret fails closed: refuses authenticated slots.

## Planner decisions (Claude's discretion, documented)

- D-A (OD-5 delivery): `ensureBridgeHelperReady()` returns `secret` alongside `port` on every
  ready outcome ('ready', 'fallback-identity'), taken from the SAME entry that was probed. games.ts
  passes `secret: helperReady.secret` into `writeBridgeConfig`. Rejected: a separate
  `getBridgeHelperSecret(appId)` getter -- it could read a different (respawned) entry than the
  one whose port was returned.
- D-B Wire format: HELLO arg blob = exactly 64 ASCII lowercase-hex secret bytes, optionally
  followed by ONE role byte. Role 0x01 (`HELLO_ROLE_PROBE`) = backend readiness probe: it
  authenticates the connection but suppresses the helper's `HELLO shim attached appid=...` log
  line, because that line is the "shim attached" half of the strict bridge-verified criterion
  (memory: bridge-verified-criterion-is-strict) and must not be manufactured by the launcher's own
  probe. Any other length, or a role byte other than 0x01, is a non-matching HELLO.
- D-C Env var name `GAMELIB_BRIDGE_SECRET`. Helper validates it is exactly 64 chars of [0-9a-f],
  copies it to a static buffer, then `unsetenv()`s it (so nothing the Steam dylib spawns inherits
  it). Missing/invalid -> fail closed (OD-6) with one `AUTH` stderr line.
- D-D HELLO semantics on the helper: matching HELLO -> authenticated=1, STATUS_OK. Non-matching
  HELLO -> authenticated=0 (fail closed, even if previously authenticated on that socket) and
  STATUS_ERR. HEALTH stays unconditional. Refusals answer STATUS_ERR with an empty ret blob and keep
  the connection open (same shape as today's unknown-slot refusal). Refusal logging is capped
  (at most 16 `AUTH refused` lines per process, mirroring the NOVER cap) so a hostile client cannot
  flood stderr.
- D-E Shim authenticates in `bridge_ensure_connected()` on every freshly connected socket, before
  publishing it as `g_bridge_sock` -- this is what makes idle/WR-02 reconnects keep working. If the
  cfg had no valid `secret=` line, the shim refuses to connect at all (fail closed, same posture as
  `g_bridge_port == 0`). The two existing explicit HELLO senders (`gamelib_bridge_hello()` and
  `GameLibBridge_CreateInterface`'s `s_hello_sent` block) send the secret blob too (otherwise D-D
  would de-authenticate the socket).
- D-F Todo closure follows the quick-261026-u1a / 261026-uhi precedent: the executor does NOT move
  the todo; the orchestrator moves it to `.planning/todos/completed/` in its docs commit, and the
  live gate below is recorded as a pending human-verify item in the SUMMARY.
