<objective>
Make GameLib write `gamelib_bridge.cfg` into the directory of every GameLib-placed shim DLL for the
launching appId, not only beside the launch exe.

Purpose: The shim reads its cfg beside ITS OWN module (`load_bridge_port_once`, GetModuleHandleExA
FROM_ADDRESS + GetModuleFileNameA), and that self-relative resolution is a deliberate threat-model
choice (no caller-supplied path), so the shim side stays as it is. For runtime-loaded Unity titles
(measured live 2026-10-23, Vampire's Fall: Origins 1167950), the shim sits in
`<install>/<Game>_Data/Plugins/x86_64/` while the cfg went to `<install>/`. So port=0,
SteamAPI_Init returned 0, and gamelib.log had no `HELLO shim attached` line.

Output: backend writes N cfg copies (exe dir plus each distinct shim dir) on every bridge launch.
</objective>

<design_notes>
Stale-port risk with multiple copies (answer, nothing further to build): the risk is no worse than
with one copy, because every copy is rewritten on every launch. `placeShimForGame` runs on every
bridge launch, and once Task 2 lands it reports every current shim path on 'already-placed' as well
as on 'placed'/'placed-miss'. `writeBridgeConfig` runs on every launch after the helper's fresh
port is known, and before `fireBridgeWineLaunch`. Each copy is replaced atomically
(tmp-then-rename). One case remains: a directory that USED to hold a shim but no longer does (for
example, a game update restored the original DLL) can keep an old cfg. This is harmless. Only the
shim reads the file, and the next launch puts the shim back and rewrites the cfg in that same
launch, before wine starts. No cleanup or sweep is added.

Failure semantics: validate ALL target paths (exe and every shim path) before writing anything. Any
path outside the bottle rejects the whole call, and no file is written. Writes happen in a fixed
order: the exe dir first, then the shim dirs in input order, deduplicated by resolved directory.
The first write failure stops the loop, cleans up its own .tmp, logs with logError naming the
failing path, and returns `{ status: 'error' }`. games.ts then fails the launch through the existing
`bridge-config-write-failed` path, so a failure is surfaced exactly as the single write's failure is
today. Copies already written before the failure hold the current port, which is harmless.
</design_notes>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| backend -> bridge bottle filesystem | GameLib writes the cfg into directories derived from a filesystem walk of the game install tree, which is game-controlled content |
| bridge bottle -> shim | The shim trusts a cfg found beside its own module to name the loopback port |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-ue0-01 | Tampering | writeBridgeConfig shimPaths | mitigate | Every shimPath goes through resolve() + isContainedWithin(bottleDir) before ANY write. One escape rejects the whole call with zero files written (tested). |
| T-ue0-02 | Tampering | cfg write mechanics | accept | Same tmp-then-rename and default mode as the existing single write. There is no symlink guard today, and adding one is outside this fix. Directories come from the bounded walk that placeShimForGame already trusts for copyFileSync. |
| T-ue0-03 | Information disclosure | multiple cfg copies | accept | The content is a loopback ephemeral port plus a public appId, so there is nothing secret in it. Copies are rewritten every launch. |
| T-ue0-04 | Spoofing | shim cfg resolution | mitigate | The shim side is unchanged: it still resolves only beside its own module, and there is no caller-supplied path. |
</threat_model>
