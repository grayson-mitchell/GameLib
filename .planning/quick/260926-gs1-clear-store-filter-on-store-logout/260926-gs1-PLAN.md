  <action>
Export a new pure helper from `src/frontend/screens/Library/filterEngine.ts`,
placed alongside the existing `migrate*` helpers at the end of the module:

`pruneDisconnectedStores(selection: StoreFacetValue[], previousConnected: StoreFacetValue[] | null, currentConnected: StoreFacetValue[]): StoreFacetValue[]`

Rule, in this order:

1. If `previousConnected` is `null` there is no baseline -- return `selection`
   unchanged (same reference). **This is the single biggest hazard in the whole
   task and the reason the signature takes a baseline at all.** `epic` / `gog` /
   `amazon` arrive from `ContextProvider` asynchronously, so a mount-time
   `selection` intersect `currentConnected` would silently wipe a legitimately
   persisted selection during the account-load window. Prune on TRANSITION only.
2. Compute the set that was connected in `previousConnected` and is absent from
   `currentConnected` -- that, and only that, is a logout.
3. If no member of that set appears in `selection`, return `selection` unchanged
   (same reference). The identity return is load-bearing: the caller uses
   reference inequality as its "something actually changed" signal, so a fresh
   array here would make the effect rewrite state and localStorage on every
   render.
4. Otherwise return a filtered copy with those stores removed.

Write a docstring in the house style of the neighbouring helpers that states
(a) the D-08a precedent this implements -- when the control governing a filter
is hidden, the filter is cleared -- and (b) the transition-only rule with the
async-account-load reason, so nobody later "simplifies" it to an intersection.

WHY THIS IS A SEPARATE PURE MODULE AND NOT INLINE IN `index.tsx` -- mandatory,
not stylistic: `Library/index.tsx` has NO jsdom coverage, and
