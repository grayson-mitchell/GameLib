**How `roadmap.analyze` actually resolves (read from
`get-shit-done-cc/sdk/src/query/roadmap.ts`) — the merge must satisfy this or the fix
does not land:**

- `extractCurrentMilestone()` reads `milestone:` from STATE.md frontmatter (`v0.7`), then
  finds the **first heading** matching `^#{1,3}\s+.*v0\.7(?![\d.])[^\n]*` and slices from
  there to the next version-bearing `##` milestone heading. Only that slice is parsed.
- Phases inside the slice are matched by `#{2,4}\s*Phase\s+(\d+…)\s*:\s*(name)`.
- Per-phase `disk_status`: `summaryCount >= planCount && planCount > 0` → `complete`;
  else `summaryCount > 0` → `partial`; else `planCount > 0` → `planned`; else
  `no_directory` / `empty`. A `- [x] **Phase N:` checkbox **inside the slice** upgrades a
  phase to `complete`, but nothing can downgrade `planned`.
- `current_phase` = **first** phase in document order whose status is `planned` or `partial`.
- `next_phase` = first phase whose status is `empty` / `no_directory` / `discussed` / `researched`.

Consequences that constrain the merge:
- Phase 23 (5/10 = `partial`) must be the **first** planned-or-partial phase in the v0.7 slice.
- Phase 22 (8 plans / 0 summaries = `planned`) appears **before** 23 in numeric order and
  would hijack `current_phase`. It must therefore live **outside** the v0.7 slice — see Task 1.
