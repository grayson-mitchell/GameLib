<objective>
Unhide Winecfg, Run EXE and the Winetricks tab for macOS Steam bridge titles that run in their own per-game bottle, and make the backend target exactly that bottle. Legacy shared-bottle bridge installs and bottled-Steam titles stay blocked.

Purpose: quick 261110-v08 restored the tools for non-Steam CrossOver games but deliberately kept Mac Steam titles hidden, because `runWineCommandOnGame` refuses Steam store-wide (`storeCapabilities.steam.winePrefixToolsAvailable === false`, Pitfall 5, Phase 17: Steam titles used to share one bottle, so prefix tools would change every Steam title and Steam itself). Bridge titles now get their own bottle `GameLibSteamBridge-<appId>`, where per-game tools are safe.

Facts established during planning (verified in the code, do not redo):
- `findBridgeInstallBottle(appId)` (steam/bridgeBottle.ts:130) returns the per-game bottle only when it is ready (`isBridgeBottleReady`) AND holds `appmanifest_<appId>.acf`; otherwise the legacy shared `GameLibSteamBridge` if ready and holding the manifest; otherwise null. Use THIS, not `resolveBridgeBottleName`: step 3 of the latter returns the per-game name even for a game that was never installed, so it cannot tell "own bottle" from "nothing installed". Launch routes to the bridge on the same `findBridgeInstallBottle(appId) !== null` test (steam/gameLaunch.ts:143). A bottled-Steam-only title has no bridge manifest, so it resolves to null.
- `bridgeBottleNameFor(appId)` returns null for a non-numeric appId (`DEFAULT_BRIDGE_BOTTLE_NAME = 'GameLibSteamBridge'`, steam/bottle.ts:69).
- Engine of a bridge bottle: during a launch `getBridgeBottleSettings(appId)` (bridgeBottle.ts:440) returns the DRM/overlay clone runner or the registered non-CrossOver selection; outside a launch it returns stock CrossOver (`stockBridgeBottleSettings`), whose `wineVersion` silently falls back to the global one when CrossOver is absent. A bottle switched to the built-in engine carries a non-CrossOver marker (`readBottleEngineMarkerKind`, engine/engineSwitch.ts:163). `resolveToolSettingsForId` (engine/toolSettings.ts) already answers this for non-Steam bottles: marker non-crossover or a `pinned:`/`wine-manager:` engine id -> `nonCrossoverEngine(engineId)` + `buildFallbackGameSettings`; otherwise CrossOver. A tool never flips the marker.
- Steam's engine id: `parseEngineOverride(readSteamEngineOverride(appId))` (steamEngineDeps.ts). Engine key for Steam is the appId (`engineKeyFor`).
- Today Steam never reaches a bottle through Winetricks only because the frontend hides it: `resolveToolSettings` returns `{ kind: 'stored' }` for Steam (`engineKeyIfEligible` is null for `usesBottleRuntime`), i.e. `SteamGame.getSettings()` = the shared bottled-Steam bottle. This plan closes that hole too.
- Engine state already reaches the renderer for Steam titles: `getEngineState` IPC -> `getSteamEngineState` (steamEngineDeps.ts) -> `getEngineState` (engine/engineState.ts), and `EngineOverride` on the Wine tab fetches it into `useEngineState`. Steam state is null when `findBridgeInstallBottle` is null. Pushes go through `compute(...)` at a second site (engineState.ts ~line 405).
- GameSubMenu's `isSteam` (`!winePrefixToolsAvailable`) gates only Update/Move/Change-location/Add-to-Steam; it exposes no Winecfg/Run EXE/Winetricks entry. Do not touch it. `storeCapabilities.steam.winePrefixToolsAvailable` stays `false` (store-wide default; eligibility is now per game).

Output: a Steam-side eligibility predicate and tool-settings resolver, the tools layer routed through it, an `EngineState.wineToolsEligible` field, and the Settings gate driven by it.
</objective>
