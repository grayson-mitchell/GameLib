# Summary

## What shipped

`font: var(--font-secondary-bold);` at `SearchBar/index.scss:97`, `InfoBox/index.css:39` and
`FormControl/index.css:12` became:

```css
font-family: var(--secondary-font-family);
font-weight: var(--medium);
```

`grep -rn "font-secondary-bold" src` now returns nothing.

## The finding that picked the fix

The todo offered two directions — declare the missing token, or replace the call sites with
longhands — and could not choose between them. `git log -S "--font-secondary-bold:"` decides it:
the token was not absent, it was **deleted**, with its whole `--font-{primary,secondary}-*`
family, by upstream Heroic `b6f3da757` ("[Tech/Refactor] Frontend/design system", #1851,
Oct 2022). That refactor introduced `styles/_typography.scss` as the replacement and migrated
most call sites; these three are stragglers it missed. Direction 1 would have resurrected a
vocabulary retired on purpose.

Two traps in the value mapping, both of which would have produced a plausible-looking wrong fix:

- **500, not 700.** `--font-secondary-bold` meant weight 500 → `var(--medium)`. `var(--bold)` is
  700. "Bold" in the old names was a slot label, not a weight.
- **Its own family token is dead too.** The old value referenced `--content-font-family`, which
  is also declared nowhere. `GlobalState.tsx:528-542` sets `--primary-font-family` /
  `--secondary-font-family` at runtime from the Accessibility font pickers; the `--content-` /
  `--actions-` names are never declared.

## Correction to the todo's premise

The todo's shorthand mechanism is right but implies the styling once applied and was later lost.
It never applied. `var(--content-font-family) normal 500` is not a legal `font` shorthand either
— no `font-size`, and the family must come last — so these declarations were invalid at
computed-value time both before and after `b6f3da757`. The intended rendering has not been seen
in this repo or upstream since at least 2022.

## Rendering delta

Weight 400 → 500 on `.searchBarInput`, `.FormControl__{button,select,input}` and
`.infoBox > strong`. Family is a no-op for the InfoBox rule (already inherited from `body`) but
newly reaches the two form controls, which UA stylesheets give the system font — so the
Accessibility "Content Font Family" picker now reaches them, which it did not before. No
`font-size` or `line-height` added: the dead shorthand never validly set either, and
`260911-umj` ratified these controls at 34px the previous day.

## NOT done — stated, not buried

**The todo's "re-verify the rendered font against the intended design" instruction was not
discharged.** No live app run was taken. The change is font-weight plus font-family, neither of
which can shift the ratified 34px control height, and the todo carried `ready: code`. Recorded
as unmeasured rather than claimed measured.

## Scope found to be far larger than the todo, and filed

Generalising the todo's check — every `--x:` declaration in `src/**`/`public/**` (plus the two
names set via `setProperty`) subtracted from every `var(--x)` in `.css`/`.scss` — the todo had
named **3 of 42**. After this fix, **39 references to 23 custom properties declared nowhere**
remain. 13 are more retired-vocabulary stragglers; three are outright typos, one of them
`--input-backgroundd` at `SearchBar/index.scss:25` — sixteen lines above the line this task
edited, and missed by `260911-umj` too. None of it was touched here. Filed as
`.planning/todos/pending/2026-09-12-39-references-to-23-css-custom-properties-declared-nowhere.md`.

No gate in the repo can see this class: `pnpm lint` is eslint on `.ts`/`.tsx` and there is no
stylelint.
