<objective>
Move the per-game Steam Engine override from the Advanced tab to the Wine tab of a game's
Settings. While doing so, stop showing the Wine tab's Wine Version / Wine Prefix / CrossOver Bottle
controls for macOS Steam titles, because the investigation below shows they do nothing for those
titles and would sit next to the Engine control as a second, competing "which Wine" choice.

Purpose: the engine choice is a Wine setting, and users look for it on the Wine tab. Today that tab
shows an inert Wine Version selector instead, and the real control is hidden under Advanced.
Output: the edited GamesSettings, a placement test, and updated copy pointing to "Wine settings".

**Deviation from 59-CONTEXT D-14 (record this in the SUMMARY):** D-14 put the override "under
Advanced, collapsed". This plan changes only the tab. The control stays collapsed (`<details>`,
summary "Engine (advanced)" kept as-is, so there are no i18n changes for that key), keeps the
unsupported warning, keeps its backend eligibility gate (WR-04) and keeps the same render gate
`!isDefault && isMac && gameInfo?.runner === 'steam'`. D-08 still holds: the select remains the
only route to the previous pinned build.
</objective>

<investigation>
Evidence collected during planning. The executor does not need to re-derive it.

1. **The Wine tab is visible for bridged Steam titles on macOS.** `shouldShowSettings('wine')`
   (GamesSettings/index.tsx:92-97) hides it only for `isWin || isNative || isBrowserGame`. A
   Windows-only Steam title on a Mac is not native, so the tab is shown, and `getStartingTab`
   (index.tsx:60-76) even opens on it.
2. **What the Wine tab reads for these titles.** Steam `getSettings()` (steam/games.ts:1271-1303)
   returns `getSteamBottleSettings()` for every bottle-eligible title (games.ts:3678-3682, which
   means Windows-only on a Mac). That getter (steam/bottle.ts:~339-362) returns the shared
   Phase-17 Steam bottle's `wineVersion` (CrossOver) and its `wineCrossoverBottle`. The tab
   therefore shows CrossOver plus the shared Steam bottle's name, not the game's real per-game
   bridge bottle `GameLibSteamBridge-<appId>`. That is misleading as well as inert.
3. **What it writes, and whether launch reads it.** Writes go to the title's GameConfig
   (sidecar/gameSettingWrite.ts:23). Only `TITLE_AUTHORITATIVE_KEYS` (steam/titleSettings.ts:50-62)
   are merged back, and they deliberately exclude `wineVersion`, `wineCrossoverBottle` and
   `winePrefix` (LD-2 comment, titleSettings.ts:41-48). The bridge launch resolves its Wine from
   `getBridgeBottleSettings(appId)` (bottle.ts:1782-1797, used at games.ts:5098). That function
   picks one of: the DRM runner; `buildFallbackGameSettings` with the engine-decision selection
   (bottle.ts:1730-1747, `...globalSettings` plus the selected engine's wine binary); or
   `stockBridgeBottleSettings` (bottle.ts:1471-1486, `resolveCrossoverWine(...) ??
   globalSettings.wineVersion`). None of them reads the title's `wineVersion`. The bottled-Steam
   path uses `steamBottleConfigStore`, also not the title's value.
4. **How the Engine override fits in.** `decideLaunchEngine` (steam/engine/engineDecision.ts:397+)
   reads `steamEngineOverride` from the title file via `readStoredEngineOverride`
   (engineDecision.ts:394-396). engineDecision.ts never references `wineVersion`. So for these
   titles the Engine override is the only per-game Wine choice that launch honours. The per-game
   Wine Version, Wine Prefix and CrossOver Bottle settings are inert.
5. **Eligibility.** `SteamEngineOverride` renders only when the backend reports
   `overrideEligible` (engineState.ts:254-255: the title has its own bridge bottle and is not a
   DRM-mode title). Any other macOS Steam title (no bridge install yet, a legacy shared bottle, or
   DRM mode) would get an empty "which Wine" area. To avoid an empty or confusing tab, show a
   one-line hint above the control.

**Decision:** for `isMacSteamTitle`, the Wine tab shows a hint ("GameLib chooses the Wine engine and
bottle for Steam games.") followed by `<SteamEngineOverride />`, in place of WineVersionSelector,
WinePrefix and CrossoverBottle. The three controls hidden here have no launch effect for these
titles (points 3-4). Nothing with a real effect is hidden.

**Deliberately left unchanged (for the user to decide later; not part of this task):** the Wine
tab's `!isCrossover` block (DXVK/esync/msync/... toggles plus Tools) only appears when the shared
bottle's wineVersion is not CrossOver, which happens when CrossOver is absent. The toggles are
inert for bridged titles by the same evidence. Tools (winecfg/winetricks run buttons) does act on
the shared Steam bottle. Keep the block as it is.
</investigation>
