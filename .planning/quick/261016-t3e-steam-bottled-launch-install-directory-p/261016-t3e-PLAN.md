<objective>
Give a bottle-installed Steam game real started/stopped feedback on macOS by adopting Playnite's SteamPlayController pattern: after the `-applaunch` hand-off, poll `ps` for any process whose executable path lives under that game's own bottle install directory. First match = `playing`. Matched set empties = `done` + logged session duration.

Purpose: `dispatchToBottledSteam('launch', …)` returns `{status:'done'}` the instant `runWineCommand({wait:false})` is handed off, and the only process detection in the file (`raiseBottledGameWindow` → `raiseFrontmostBottledProcess`, bottle.ts L454-598) raises a window and then gives up after ~18s. The native running-game poller (`library.ts pollRunningOnce`, L3350-3378) reads the native Mac Steam `registry.vdf`, which a bottled WINDOWS Steam never writes. So no `playing` and no `done` has ever fired for a bottled game — Play looks dead, and there is no session duration either.

Output: one new module, one new test file, a three-line wiring change in bottle.ts's `'launch'` branch, one assertion in bottle.test.ts, and a dated update to the pending todo.

Scope locks from the task spec (non-negotiable):
- LD-1 NO changes to `raiseBottledGameWindow`, `raiseFrontmostBottledProcess`, or the native running poller in `library.ts`. Keep every non-`launch` verb byte-identical.
- LD-2 NO new runtime dependency. `ps` is spawned in argv form through the already-imported `spawnAsync`; never a shell string.
- LD-3 NO changes under `src/frontend`.
- LD-4 NO fixed deadline on the FIRST match. The whole point of the change is that a 6-minute Steam block still resolves correctly. Do not add a give-up timer to the pre-match phase.
- LD-5 macOS-only. Return without side effects on any other platform.
- LD-6 The monitor can never block or fail a launch. Every failure path logs and returns.
