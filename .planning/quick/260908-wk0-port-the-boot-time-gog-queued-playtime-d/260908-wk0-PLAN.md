<design_decisions>
Settle these as written. Each is a decision, with its reason, not a suggestion.

**D1 — Exported helper `syncQueuedPlaytimeWhenOnline()`, not an inline block.** Matches Block D
(`clearStrandedPlaytimeSyncLock`) and Block E (`reconcileStoreUsersWhenOnline`) exactly. Blocks
A/B are inline because their bodies are two lines; this body has a setting gate, two arms, a
deferred callback and a floated promise, and it must be unit-testable WITHOUT going through
`init()` — which matters more here than anywhere else in this file, because the once-guard means
only ONE `init()` call per test file can do anything (see D7).

**D2 — Placement: Block G, appended after Block F's `checkRosettaWhenMac()` guard, still before
`output.write(READY_SENTINEL)`.** Four constraints, and one of them is load-bearing:

  - **AFTER Block D — THE LOAD-BEARING ONE.** Block D clears a lock stranded by process death.
    `syncQueuedPlaytime()`'s first statement is `if (playtimeSyncQueue.has('lock')) return`
    (established fact 6). Sequencing Block G before Block D would let a stale lock silently
    no-op the very drain this task adds — restoring the call site while leaving the bug
    unfixed for exactly the users whose previous sync died mid-flight, i.e. the ones with a
    non-empty queue. This is the single most important sentence in this plan. Put it in the
    Block G comment, in these terms.
  - AFTER `initLogger()` — the helper logs, and `heroicLogWriter` is unset before that (the
    standing `sidecar-console-and-logger-are-invisible` finding).
  - AFTER `initOnlineMonitor()` — it calls `runOnceWhenOnline`, the same requirement Block B's
    and Block E's comments already record.
  - BEFORE `READY_SENTINEL` — so the drain is at least *queued* before the frontend can drive
    any RPC. It deliberately does NOT delay READY.

Appending after Block F satisfies all four while leaving the existing A→B→C→D→E→F sequence
byte-identical, so the diff cannot perturb any ordering another gate depends on.

**D3 — Guard flag `playtimeQueueDrainInitialized`, declared alongside
`playtimeLockClearInitialized` / `storeUserReconcileInitialized` / `rosettaCheckInitialized`,
with its own declaration comment in their idiom.** Without it, every repeated `init()` in
`bootstrap.test.ts` / `*Flows.test.ts` would register another `runOnceWhenOnline(...)` — either
re-invoking the drain immediately (if online) or stacking another `'online'` listener on
`connectivityEmitter`. The flag lives at the CALL SITE, not inside the helper, matching Blocks
A/B/E/F, so the new suite can call the helper directly without owning a guard it cannot reset.

**D4 — TWO try/catch layers, plus an explicit `.catch` on the floated promise. Three guards, not
one.** Per established fact 7, when offline `runOnceWhenOnline` defers the callback to a later
turn, so an outer `try { runOnceWhenOnline(cb) } catch {}` covers only the REGISTRATION, never
the deferred body. And per established fact 5 the floated `syncQueuedPlaytime()` promise can
reject while `runOnceWhenOnline` discards its return value, so without an explicit `.catch` the
rejection would surface only via `processGuards`' process-wide net — which is exactly what
`deliverStartupProtocolUrl` and the migrations block in this same file already refuse to rely on.
Comment the inner guard with this reasoning so a future reader does not "simplify" it away.

Use a DIRECT `.catch(...)` on the call, not `Promise.resolve(...).catch(...)`.
`syncQueuedPlaytime` is `async` and therefore always returns a promise (unlike `handleProtocol`,
which is why `deliverStartupProtocolUrl` needs the wrap). Do not design the production shape
around what a test mock might return.

**D5 — Read the setting OUTSIDE the callback, at helper entry.** `GlobalConfig.get().getSettings()`
runs before `runOnceWhenOnline`, and the `disablePlaytimeSync` branch returns early. Two reasons:
fidelity (the deleted `main.ts` read `settings` at `whenReady()` time, not at online time), and
determinism (a user toggling the setting between boot and coming online should not change what a
boot-time decision already made). The whole synchronous body sits inside the outer try, so a
throwing `getSettings()` cannot fail boot.

**D6 — The ported `logDebug` line stays VERBATIM and UNPREFIXED, including its
`{ prefix: LogPrefix.Backend }` options-object form.** Justification, since the brief asks for
one explicitly:

  1. Block E established the house rule at this exact site: a PORTED log literal keeps its
     original form; NEW diagnostic lines added by the port take the local `[bootstrap] ` prefix.
     A rule beats a case-by-case judgment, and this is the second application of it.
  2. Honesty about what it is NOT: unlike Block E's `'User Not Found, removing it from Store'`,
     this string is NOT the todo's own bundle-level evidence — this todo's evidence is the
     *count of `syncQueuedPlaytime()` call sites in `build/main/sidecar.js`* (it recorded exactly
     one, at `sidecar.js:23753`). So the verbatim decision here rests on the rule and on port
     fidelity, not on protecting a named grep. Say this in the doc comment rather than borrowing
     Block E's stronger claim, which does not apply.
  3. It is nonetheless a clean, independent receipt for the DISABLED arm specifically — that
     string appears zero times in `src/` today (established fact 1).

Your two new catch-arm diagnostics DO take the `[bootstrap] ` prefix and name the helper, in the
shape of `reconcileStoreUsersWhenOnline`'s catch arms.

**D7 — The wiring proof and the ordering proof are FUSED into a single `init()`-driven test, and
that is forced, not preferred.** The module-scope once-guard means exactly ONE `init()` call per
test file does any work (established fact 16). Two separate `init()`-driven tests are therefore
impossible in one file, and a second file for one assertion is disproportionate. So the first
test seeds a stranded `lock`, calls `init()` once, and carries three assertions at once. Name the
test so both duties are visible. Record this constraint in the test's own comment — a future
reader must not "split it up for clarity" and silently create a test that measures a consumed
guard.

**D8 — The ordering proof is honest by construction: record the lock state AT CALL TIME.** The
naive version ("seed a lock, call `init()`, assert the drain still happened") is VACUOUS — the
spy replaces the real `has('lock')` early-return, so a mocked `syncQueuedPlaytime` is called
whether or not the lock is present, and the assertion passes for the wrong reason. Instead, give
the spy an implementation that pushes `playtimeSyncQueue.has('lock')` onto an array at the moment
it is invoked, and assert that array is `[false]`. Reorder Block G above Block D and the array
becomes `[true]` — which is precisely the mutation the plan requires you to run (Task 2,
mutation 2).

State the limit of the claim in a comment: this proves the PRECONDITION holds at call time (the
lock is already cleared when the drain fires), not that the real function drained a real queue.
That is the correct thing to assert at this seam, and over-reading it would be the defect this
decision exists to prevent.

**D9 — The mock must prove the callback RAN, and the proof is structural.** The standing project
finding is that a mocked `runOnceWhenOnline` which never invokes its callback makes every
downstream assertion vacuous. Mock it as `jest.fn((cb: () => unknown) => cb())` — invoke inline —
and re-arm that implementation in `beforeEach` (established fact 15). The proof that the callback
ran is that **every assertion in this suite is on an EFFECT that only occurs inside the callback**
(the `syncQueuedPlaytime` spy's call count, and the lock-state array it populates). No test
asserts `expect(runOnceWhenOnline).toHaveBeenCalled()` — that assertion would be exactly the
vacuous shape the finding warns about, and it is banned in this file. If the mock silently stopped
invoking, the spy would have zero calls and every test would go RED. Write that sentence in the
suite docstring.

**D10 — One test re-mocks `runOnceWhenOnline` to DEFER, to prove the INNER guard is load-bearing.**
With the inline-invoke mock, a throw inside the callback propagates back out through the mock into
the OUTER try — so an inline-invoke test cannot distinguish inner from outer, and would pass with
the inner guard deleted. The deferred-arm test captures the callback instead of invoking it
(`mockImplementation((cb) => { captured = cb })`), calls the helper (registration only), then
invokes `captured()` from the test's own frame — outside anything the helper wraps — and asserts
it does not throw. That is the only shape that proves the inner guard exists.

**D11 — Dedicated test file `src/backend/sidecar/__tests__/playtimeQueueBootDrain.test.ts`**, per
established fact 16, modelled on `playtimeLockBootClear.test.ts`'s structure and docstring
discipline and `bootstrapUserReconcile.test.ts`'s `online_monitor` preamble.

**D12 — Register the new suite in `STRUCTURALLY_CONTAINED_SUITES`**, per established fact 13.

**D13 — OUT OF SCOPE, explicitly: `runOnceWhenOnline(gogPresence.setPresence)`.** It sat on the
very next line of the deleted `main.ts` (line 477, verified) and is a SEPARATE, still-open todo
(`.planning/todos/pending/2026-09-06-gog-presence-never-set-at-startup-and-its-keepalive-never-arms.md`).
Do not port it, do not touch that todo, do not import `gogPresence`. Note the adjacency in your
SUMMARY so the next reader knows it was seen and deliberately left.
