<diagnosis>
This was measured during planning, not guessed.

**1. Idle keep-alive sockets do NOT hold the loop. In-flight and unconsumed responses DO.**
Measured on this machine under Node v22.23.4, which is the node `tauri dev` spawns the sidecar
with (`/opt/homebrew/bin/node`, from gamelib-shell.log). The probe used a local server on
`http.Agent({keepAlive:true})`:
- request completed and body consumed: the process exits in 8 ms.
- response body still streaming (server never ends it): still alive at 5 s.
- response received but body never read: still alive at 5 s.

So lsof's 6 ESTABLISHED sockets are a mix. Idle sockets on axiosClient's private
`https.Agent({ keepAlive: true })` (`src/backend/utils.ts:1823-1827`, no agent `timeout`) stay
ESTABLISHED indefinitely but are unref'd, so they are harmless. Node 22's `https.globalAgent`
uses `keepAlive: true, timeout: 5000`, so its idle sockets close within 5 s. A global-agent socket
still ESTABLISHED after minutes is therefore in flight, and it holds the loop.

**2. Nothing at EOF touches raw outbound HTTP.** `releaseOnStdinEof()`
(`src/backend/sidecar/stdinEofRelease.ts`) does four things: pause the queue,
`callAllAbortControllers()`, stop the nettop monitors, and `SteamUser.releaseForShutdown()`
(the authenticated CM plus `releaseAnonymousForShutdown()`). Only requests whose caller
registered a controller via `createAbortController` stop. These sites carry no such controller:
- Bare `axios` on `https.globalAgent` with NO timeout: `storeManagers/steam/gameRequirements.ts:221`
  (store.steampowered.com, akamai), `storeManagers/legendary/games.ts:140/184/243`, and
  `utils/inet/downloader/index.ts:69` (`downloadFile`, arraybuffer, used by `tools/index.ts:837`
  for GitHub-hosted tool assets, which matches the 185.199.111.133 socket).
- axiosClient (`utils.ts:1823`). Its `timeout: 10000` is axios' node-adapter `req.setTimeout`, a
  socket IDLE timeout and not a total deadline, so a trickling body is never bounded. It is used
  by the wiki/extra-info fetchers (`wiki_game_info/pcgamingwiki`, `applegamingwiki`, `protondb`,
  `steamdeck`), `utils/releases.ts`, `wine/runtimes`, `crossover_index/fetcher.ts` and
  `anticheat/utils.ts`. gamelib-shell.log shows `invoke abandoned (sidecar exited) ...
  channel=getExtraInfo` at a quit on 2026-11-09 (epoch 1794214529), so extra-info HTTP is
  routinely in flight when the shell goes away.
- EasyDl (`utils.ts:1611`, `downloadFile`): 5 parallel connections on the global agent, with
  retries (`maxRetry: 3`). `storeManagers/steam/setupDownloads.ts:32` passes no `abortSignal`.
- steam-user's webapi `HttpClient` (`node_modules/steam-user/components/06-webapi.js:32`)
  builds a PRIVATE `https.Agent({keepAlive:true})`
  (`@doctormckay/stdlib/lib/http/client/HttpClient.js:52`), so its requests are invisible to any
  fix that only touches the global agents.

**3. Why the fix is agent-agnostic.** Destroying only `https.globalAgent` plus axiosClient's agent
misses the private agents (steam-user, EasyDl internals). It also misses a request that a
chained caller issues AFTER the destroy: HLTB search followed by a page fetch, or a
pcgamingwiki-to-HLTB fallback. `node:diagnostics_channel` `http.client.request.start` sees every
`http.ClientRequest`, whatever its agent. A probe in the planning scratchpad confirmed this on
Node 22. Tracking `{request}` on start and dropping it on the request's `'close'`, then calling
`request.destroy(err)` on each live entry at EOF, let a process with a hanging response on
EITHER the global agent or a private keepAlive agent exit 7 ms after the destroy. A request
created after the flag was set was destroyed synchronously inside the start publish
(`late req: shutting down`).

**Not covered, deliberately:**
- `fetch` (undici): its only call site is `logger/uploader.ts:15`, a user-triggered log upload.
- WebSocket upgrades already open: steam-user's CM. `releaseForShutdown()` logs those off.

**Residual uncertainty:** no `--report-on-signal` report was taken from the orphan, so the planner
cannot prove HTTP was the ONLY holder. Task 2 therefore adds an unref'd post-EOF diagnostic. It
fires only if something still holds the loop, and it logs `process.getActiveResourcesInfo()`, so
a failed live gate names the remaining holder instead of leaving it a mystery.

**No `process.exit()` hammer.** The exit contract (gamelib-conventions) forbids it as the
mechanism, and `releaseOnStdinEof`'s own doc says "never calls process.exit". No precedent in
`src/backend/sidecar/` justifies a timed exit on the EOF path. The shell's `shutdown_child()` is
the backstop for Ctrl-C/Cmd-Q, and the diagnostic covers the Force Quit case. Do not add one.
</diagnosis>
