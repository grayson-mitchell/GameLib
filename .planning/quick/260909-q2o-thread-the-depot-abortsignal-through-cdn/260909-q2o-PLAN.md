<design_decisions>
These are decided. Implement them; do not re-derive them.

**D1 — Abort resolves to `''`; `getToken` still NEVER throws.**
The module's contract (doc comment L136-141) is that `getToken` always degrades to `''` and
lets the caller's own retry/host-rotation decide the outcome. An abort is a third reason to
return `''`, alongside cooldown and fetch failure. It must NOT become a new throw site — the
sole caller (`fetchChunk`) has its own `if (signal?.aborted) throw new ChunkFetchAbortedError()`
checkpoints immediately before and immediately after this await, and those are the checkpoints
the 2026-09-08 live gate proved bound the loop. cdnAuth's only job here is to stop *blocking*
them.

**D2 — An abort must NOT write to `negativeCache`.**
A cancel is not evidence the token endpoint failed. Poisoning a depot+host key for 60s because
the user pressed Cancel would be recording the wrong fact. This mirrors two decisions already
in the file: `invalidate()`'s doc comment ("deliberately does NOT touch the failure cooldown —
a 401/403 is a completely different signal from 'the fetch failed'") and
`ChunkFetchAbortedError`'s ("a user cancel is not evidence a content-server host is
unhealthy"). Structurally this falls out for free: the fast path returns before any cache is
consulted, and the mid-flight race returns without disturbing the shared fetch promise, whose
own catch is the only writer of `negativeCache`.

**D3 — The shared in-flight fetch is NEVER cancelled, only stopped being waited on.**
Concurrent callers coalesce onto one promise in `pending`, and they may carry different signals
or none. Aborting the shared promise would break a caller that never asked to be cancelled. So
the aborting caller races locally and walks away; the underlying fetch runs to settlement,
still populates `cache`/`negativeCache`, and is still removed from `pending`. This costs at most
one already-bounded 3s round-trip whose result is discarded — the exact same trade
`callGetCDNAuthToken`'s doc comment already accepts for its own timeout ("steam-user itself has
no way to 'cancel' an in-flight ServiceMethodCallFromClient, so the discarded closure is the
only cost").

**D4 — Move `pending.delete(key)` off the awaiting caller and onto the fetch's own settlement.**
Today the *creating* caller deletes the key in its `finally` after `await`. Under D3 that
caller can now return early, which would delete a `pending` entry whose fetch is still in
flight — and the next non-aborted caller for that key would start a SECOND redundant CM
round-trip, silently regressing the single-flight guarantee the module exists to provide.
Fix: attach the deletion to the fetch promise itself (`void fetchPromise.finally(() =>
this.pending.delete(key))`) so the entry's lifetime tracks the fetch, not the caller. Safe
because `fetch()` never rejects, so the derived promise cannot produce an unhandled rejection.

**D5 — `callGetCDNAuthToken` internals are deliberately NOT made abort-aware.**
Its round-trip is already hard-bounded at 3s, and rejecting it on abort would route into
`fetch()`'s catch — which sets a 60s cooldown, violating D2. All abort awareness lives at
`getToken`, the only surface a caller ever blocks on. State this in the code comment so a
future reader does not "complete" the threading and reintroduce the D2 violation.

**D6 — Listener hygiene is load-bearing, not tidiness.**
The download-run signal is long-lived and `getToken` is reachable once per chunk attempt across
tens of thousands of chunks in one install. Register the abort listener ONLY on the mid-flight
path (never on the fast path, where there is nothing to wait for) and ALWAYS remove it in a
`finally`. Without this we manufacture a `MaxListenersExceededWarning` and a retained-closure
leak on the very signal we are honouring. Mirror `fetchChunk`'s own
`signal?.removeEventListener('abort', onExternalAbort)` in its `finally` (decompress.ts:1207).

**D7 — Optional and additive.**
`signal?: AbortSignal` is appended as the THIRD parameter of `getToken`. Every existing caller
and test that passes two arguments must be untouched and unchanged in behaviour — the same
discipline `cdnAuth?: CdnAuthTokenCache` itself was threaded with (depot.ts:1287, 1482).
</design_decisions>
