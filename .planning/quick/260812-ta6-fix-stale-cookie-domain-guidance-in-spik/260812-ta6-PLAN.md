<context>
**The falsified claim** (lines 46-47):

> Humble stores `_simpleauth_sess` with `domain='humblebundle.com'` (WebKit normalises away the
> leading dot)

The real, live-measured domain is **`.humblebundle.com`** — leading dot present. Measured via a
read-only OS-level WKWebView cookie-jar parse during the F-34.4.2-19 debug session
(`.planning/debug/resolved/humble-isloggedin-never-set.md`). The "WebKit normalises away the
leading dot" parenthetical is the specific inference that was wrong.

**The harmful prescription** (lines 63-72), under "Do this instead:":

```rust
Some(d) => host == d || host.ends_with(&format!(".{d}")),   // proper suffix match
```

`format!(".{d}")` on an already-dotted `d` (`.humblebundle.com`) yields `"..humblebundle.com"` —
an impossible suffix no real hostname can satisfy. The comparator is therefore categorically blind
to **any** leading-dot cookie domain, for any host. This shipped as `cookie_domain_matches` and
silently broke Humble login: the poll ran forever, `_simpleauth_sess` never entered the `matched`
array, `total` stayed healthy every tick, `classifyCookieRead` always returned
`SUPPORTED_NONEMPTY`, and nothing was ever logged.

**The shipped fix** — `src-tauri/src/main.rs:975-994`, commit `0dfd08044`:

```rust
Some(d) => {
    let d = d.strip_prefix('.').unwrap_or(d);
    host == d || host.ends_with(&format!(".{d}"))
}
```

RFC 6265 defines a `.example.com` cookie as applying to `example.com` itself, not only to its
subdomains, so stripping the leading dot is the spec-correct fix, not a special case.
