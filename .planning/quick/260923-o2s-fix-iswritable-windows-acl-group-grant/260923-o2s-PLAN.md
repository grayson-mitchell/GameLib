<objective>
`isWritable_windows` asks an ACL whether an ACE names the individual user. Windows grants write
access through GROUPS, so it answers FALSE for effectively every path outside `C:\Users\<name>` --
including `D:\SteamLibrary`, which Steam demonstrably writes into. Two user-visible symptoms on
ALL Windows installs: the Steam dialog's free-space line never renders (the direct cause of
`38-S08` row 4), and the generic install dialog shows a permanent, false
"Warning: path might not be writable."

Purpose: make the predicate answer the question its one consumer actually asks -- "can this
process write here" -- correctly in BOTH directions, and delete the second, independent
false-`false` path (single-entry ACL -> `ConvertTo-Json` emits an object -> array parse throws ->
`catch { return false }`) rather than leaving it dormant.

Output: a rewritten `isWritable_windows`, the first tests it has ever had, and a retired todo.
</objective>

<decision_record>
## Fix direction: a real write probe. Adopted.

Create a uniquely-named zero-byte file in the target directory with `flag: 'wx'`, delete it, clean
up in a `finally`. This is the only option that is correct in both directions, and it removes a
`powershell` spawn from every disk-space probe.

## `fs.access(path, W_OK)`: REJECTED, explicitly.

On Windows, `access` with `W_OK` reflects only the read-only **file attribute** -- it does not
consult ACLs at all. Node documents this ("the Windows access() function does not check ACLs").
It would therefore report `C:\Program Files` and other ACL-restricted trees as WRITABLE. That
trades a false-negative for a false-positive, which is strictly worse here: the false-negative
shows a visible (if wrong) warning, while the false-positive is silent and the install fails
later, after the user has committed to a path.

## Resolving Windows group membership in JS: REJECTED.

Nested groups, deny ACEs, and ACE ordering make an identity-based answer a reimplementation of
Windows authorization. The probe sidesteps the whole question by letting the kernel answer it.

## `isWritable_unix`: NOT CHANGED. Scope held.

`isWritable_unix` is `access(path)` with NO mode argument (`unix.ts:34-39`) -- that is `F_OK`, an
EXISTENCE check, not a writability check. `findFirstExistingPath` (`unix.ts:26-32`) DEPENDS on
that: it climbs `while (!(await isWritable_unix(p))) p = join(p, '..')` until the path exists.
Turning the Unix side into a real writability check would silently break `getDiskInfo_unix`'s
`df` target selection and falsify `findFirstExistingPath`'s own name. Fixing that properly means
splitting existence from writability across both call sites -- a different, wider task with its
own Unix/macOS live gate. This task leaves Unix alone and RECORDS WHY in a comment at the
asymmetry. The two platforms knowingly answer different questions today; the comment is what
stops the next reader "harmonising" them by accident.

## `getDiskInfo`'s "path does not have to exist" contract: PRESERVED.

A nonexistent path returns FALSE on both platforms today. The new implementation `stat`s first and
returns `false` on ENOENT before probing, so that is unchanged.
</decision_record>
