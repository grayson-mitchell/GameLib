<objective>
Make a successful Keychain operation readable. Route all nine emission sites in the four keyring RPC dispatch arms through `shell_diag()` so they persist to `gamelib-shell.log` instead of vanishing into discarded stderr, and add a one-line-per-operation success emission carrying a closed-set `outcome=` token.

Purpose: today a credential-persistence success and a credential-persistence failure are indistinguishable from either GameLib log file. During the 2026-10-01 `debug/steam-token-survives-keychain` investigation the macOS unified log (`/usr/bin/log`) was the only instrument that could observe a Keychain write at all — the absence of a GameLib log line proved nothing. Measured here at HEAD `f90ed6f73`: `~/Library/Logs/GameLib/gamelib-shell.log` is 2470 lines / 206,484 bytes and contains **zero** lines matching `keyring`. That is the gap, measured directly rather than inferred.

Output: a closed-set outcome enum plus a pure formatter in `main.rs`, fourteen `shell_diag()` emission sites across the four arms, cargo tests on the pure formatter (including a runtime leak assertion), a CI-visible jest source gate over comment-stripped `main.rs`, and the todo closed into `completed/`.

<decision>
## Both halves of the todo's open direction, as locked by the operator

The todo (`## Direction, not decision`) left two choices open. **Both are taken.**

(a) **Conversion.** All nine emission sites in the four arms move from bare stderr to `shell_diag()`. Because `shell_diag()` already prepends `[shell] `, the `[shell] ` prefix is dropped from each message's own text — so the rendered **stderr output for the existing error lines is byte-identical to today**, while the same text now also lands in `gamelib-shell.log`.

(b) **Success emission.** One new line per successful operation, carrying `outcome=<token>`. Tokens: `found`/`absent` for `keyring_get`, `stored` for `keyring_set`, `deleted`/`absent` for `keyring_delete` (both of whose `Ok(())` and `Err(NoEntry)` are success).

**One line per operation, never two per branch.** Each dispatch of each arm emits exactly one `shell_diag()` line: the error branches keep their single existing failure line, the success branches gain a single new outcome line. Never both. This follows the sibling dev-vault fix `afb0fe744` (`[dev-secret-vault] write key=<slot> op=store|wipe`), whose whole point was keeping the established grep prefix byte-stable while appending a disambiguating token — so a reader's existing habit keeps returning the same set of lines instead of silently dropping the new ones.

## Scope extension, named deliberately: `keyring_available`

The todo names three arms. A fourth, `keyring_available`, lives in the same `match` and has **three** bare-stderr sites of its own. It gets **half (a) only — conversion, no success emission.**

Why extend: leaving one arm of the same `match` emitting to stderr only would re-create the exact blind spot being closed, one arm over. Why not the other half: `keyring_available`'s healthy answer is `Err(keyring::Error::NoEntry)` from a deliberately-never-written probe account — a capability probe, not a credential operation, with no slot-scoped outcome worth a token. Its `Ok(_)` branch already emits a loud WARNING, which is the one event there worth reading.

This extension is stated here, in the task action, and **in the commit message**, so it cannot read as a silent widening.

**Correction to the briefing, measured.** The briefing states `keyring_available` has two bare-stderr sites. Measured at HEAD over lines 6471-6576: it has **three** — the reserved-probe-account `Ok(_)` WARNING, the inner `Err(e)`, and the outer `Entry::new` `Err(e)`. Total across the four arms is **nine**, not eight. The briefing also states twenty existing `shell_diag(` call sites; measured, the token occurs twenty times of which one is the `fn shell_diag(` definition, so there are **nineteen** call sites. Both corrections are small and change no decision; they are recorded because the gate numbers below are derived from them.

## The account string is safe to log — verified, not assumed

Locked decision 2 requires this be checked rather than assumed. Read at `src-tauri/src/main.rs:1358`: `keyring_account(slot: &str) -> Result<&'static str, String>` is a four-arm compile-time allowlist (`steam-refresh-token`, `humble-session`, `humble-csrf`, `steamgrid-api-key`) with **no wildcard arm** — an unrecognised slot is `keyring:unknown-slot`, always. So:

- What reaches the log is one of **four compile-time string constants**, never caller-supplied text. T-28-03's existing boundary is what makes this true, and it is unchanged.
- The `?` on `keyring_account(...)` runs **before** any emission in every arm, so an unknown slot returns `Err` without ever reaching a log line.
- The raw `keyring_slot_arg(args, 0)` return is **not** safe to log — that one *is* caller-supplied arbitrary text — and is therefore never passed to the formatter. Log the validated account; never the raw slot argument.

## Two type-level barriers instead of a review convention

`keyring_set`'s existing comment ("Never log the secret itself (threat T-28-04) — channel + error only") is a convention a future edit can quietly break. This change replaces it with construction:

1. **`outcome` is a closed enum**, not a free `&str`. Mirrors `afb0fe744`'s own stated reasoning for making `WriteDirection` a two-member union rather than a string. A secret cannot be smuggled in as an outcome token.
2. **`account` is typed `&'static str`.** Any secret is a runtime-derived `String`; a `String` does not coerce to `&'static str`. The compiler, not a reviewer, is what forbids it.

The formatter therefore has no parameter capable of carrying a secret. This is the `format_panic_record` pattern (`main.rs:11209`) — a pure function split out specifically so a test can assert what the line carries without writing to the operator's real log file — and the `invoke_abandoned_message` pattern at the `shell_diag` call sites `main.rs:1576`/`:1588`.
</decision>
