<objective>
Replace the counter-intuitive "Stop Installation / Do you wish to KEEP downloaded files? / [Keep Installing] [Yes] [No]"
dialog with a standard verb-button dialog, add an opt-in `variant` to the shared MessageBoxModal buttons (no
change for any existing dialog), make the Steam variant truthful about what its backend actually does, and align the
console-mode cancel dialog's button labels.

Purpose: Yes/No against a "KEEP?" question is easy to misread and one answer deletes data. Verb buttons name the
outcome; the destructive one is visually distinct and set apart.
Output: updated types, MessageBoxModal, handleStopInstallation + its three call sites, ConsoleMode labels, en gamelib
strings, two jest suites, one triaged todo.
</objective>

<steam_resume_finding>
Determined from code (2026-10-26), not assumed:

- KEEP FILES DOES RESUME for Steam. `cancelCurrentDownload({removeDownloaded:false})`
  (src/backend/downloadmanager/downloadqueue.ts:335) calls `stopCurrentDownload()` -> `callAbortController(appName)`.
  The native depot download returns `{status:'cancelled'}` and `runNativeDepotDownload`
  (src/backend/storeManagers/steam/games.ts ~L2237-2245) calls `markSteamInstallIncomplete(appId)`, setting
  `steamResumePending`. The next Install click runs `resumeInterruptedSteamInstall` (games.ts ~L1126) and every
  `downloadDepotFiles` run calls `reconcilePartialState` first (depot.ts ~L2924-2946): "a present, sha1-verified file
  is never re-downloaded". Resume granularity is per-file (a half-written file is re-fetched), which is fine.
  Steam-client handoff routes (steam://install, bottled Steam) leave the files to Steam, which resumes natively.
- DELETE FILES IS A NO-OP for Steam. The `removeDownloaded` branch of `cancelCurrentDownload` only deletes when
  `libraryManagerMap[runner].getGame(appName).getGameInfo().folder_name` is truthy, and no file under
  src/backend/storeManagers/steam/ ever sets `folder_name` (grep: zero hits). DownloadManagerItem/index.tsx ~L111-115
  already documents this ("Steam GameInfo never populates folder_name ... the backend removeDownloaded path keeps its
  own `if (folder_name)` guard"). So today Steam "No" (delete) silently keeps every file and still leaves
  `steamResumePending` set.

Consequence for this plan: the orchestrator's pre-approved fallback (drop the keep button if Steam can't resume) does
not apply — the inverse is true. To avoid a button that lies, for `runner === 'steam'` the dialog shows only
[Keep Downloading] [Stop & Keep Files] with a Steam-specific message. Wiring a real Steam delete (steamapps
common/<installdir>, the downloading/ staging tree, the appmanifest ACF and the resume flag) is backend work outside
this UI task; Task 3 files it as a triaged todo rather than shipping it here. The caller should surface this deviation
from the approved button list to the user.
</steam_resume_finding>
