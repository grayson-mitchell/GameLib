<objective>
Give the bottled-route 1026 handoff a way forward. Today `pollInstallOnce` (library.ts:2476) sees
StateFlags exactly 1026 on an `isNativeHandoff` poll and emits `context:
'steam-waiting-for-restart'` (library.ts:2523-2525, 2557-2564). `MainButton.tsx` renders that as
"Restart Steam to finish" (`getButtonLabel`, :171-190), and the button is disabled by
`disabledInstallButtons`' `(gameInfo.runner === 'steam' && is.installing)` term (:60-61). The
disabled state is passive by design: it waits for the user to restart Steam themselves so Steam
adopts GameLib's manifest on its next start (library.ts:2503-2507, "Never launch/focus/drive
Steam (T-21-16-02)"; constants.ts:32-33 "GameLib never auto-drives Steam"). That works natively.
On the bottled route nothing ever starts the bottled Windows Steam client, and the user has no
way to start it, so the state never ends.

Chosen behavior: an explicit button, not auto-start. The code states "never auto-drive Steam" as
a rule in three places, and starting a Wine Steam client can self-update or ask for a login.
That should follow a user click, not a poll tick. One code path covers both cases, running and
not running. `steam.exe steam://install/<appId>` either starts bottled Steam with the URI (what
the operator ran by hand) or hands the URI to the already-running instance. So no process
detection is needed. `dispatchToBottledSteam('install')` (bottle.ts:1018) already raises the
Steam window (`raiseInstallerWindow`).

Scope: only the existing bottle-source handoff state is made actionable. Nothing is rerouted to
bottled Steam. The backend refuses the call unless the poll is that exact state. Per the user's
memory, bottled Steam is a narrow fallback. Do NOT touch the cross-depot collision root cause
(`2026-10-22-unresolved-cross-depot-file-collisions-leave-install-stuck-at-1026.md`).

Output: backend contexts + guarded IPC, frontend button/status copy, locale keys, closed todo.
