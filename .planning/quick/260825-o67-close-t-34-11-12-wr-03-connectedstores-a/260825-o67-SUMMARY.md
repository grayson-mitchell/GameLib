# 260825-o67 — the parity WAS the control, so the parity got a test

## What was wrong

`T-34.11-12`'s registered mitigation said `connectedStores` is *"derived from the same
`gog.username` / `epic.username` / `amazon.username` / `steam?.username` gates `makeLibrary()`
already uses, so the panel cannot advertise a store the user is not signed into."*

Four of the five stores matched. Amazon did not: `connectedStores` read `amazon.username`,
`makeLibrary` read `amazon.user_id`. A username-without-user_id account got an Amazon row over a
grid with no Amazon games — the **permanently-`0` row** that `T-34.11-12` and `T-34.11-19` were
both written to prevent.

This was not a newly discovered threat. It was raised as review finding **WR-03** on 2026-08-10
and sat open for 15 days, because nobody had connected the review's warning list to the threat
register — see [[threat-mitigation-text-can-assert-false-parity]].

## Decision

**`user_id`, chosen by the operator on 2026-08-25** — the panel follows the library, not the
reverse. The `useMemo` dependency moved with the body; leaving it keyed on `amazon.username` would
have been a quieter version of the same defect.

## Why a source gate, and why it is not the weak kind

Every jest project in this repo is `testEnvironment: 'node'` — no jsdom, no
`@testing-library/react`. The memo cannot be rendered, so the invariant can only be read out of the
source text. `connectedStoresParity.test.ts` parses both regions, normalises away `!!` and
whitespace (the only differences that carry no meaning), and compares all five gated stores.

Three things keep it from being the kind of gate this project has been bitten by before:

1. **Proven against known-bad input**, not assumed — `T-34.11-26` registers exactly this, and
   `F-34.10-08` recorded a `^`-anchored pattern that could never match, returning `0` even for a
   file that *did* carry the defect. A specimen with the pre-fix expression is convicted with
   exactly one mismatch, `nile: amazon.username !== amazon.user_id`, naming both sides.
2. **Non-vacuity asserted separately.** Deleting `connectedStores` outright would make
   `[].filter(...)` green, so the suite first asserts the parser finds exactly the five expected
   stores in each region.
3. **Discrimination proven.** The pre-fix specimen must yield *one* mismatch, not "some" — a
   checker that always fails is as useless as one that never does.

`sideload` is excluded **by name**: it is pushed unconditionally and has no `makeLibrary` login
gate, so a future store that loses its gate cannot inherit the exemption by accident.

## The commit had to be carved out of someone else's in-flight work

`Library/index.tsx` also carried two uncommitted **08.1 review** changes (`migrateFilterMode`
extraction, the `favouriteGamesList` IN-02 fix) that call `filterEngine` exports which are *also*
still uncommitted. Committing the file wholesale would have produced a commit that does not
compile.

`git stash` and `git reset` are both banned here ([[executor-git-stash-strands-concurrent-session]]),
so instead: back up the file byte-exact, reconstruct `HEAD + my region only` by swapping the
`connectedStores` region out of the real working file (never retyping it — a first attempt through
an **unquoted heredoc let the shell command-substitute the backticks** out of the comment, caught
by an assertion), commit with `--only`, then restore from backup and verify by SHA-256.

Restore verified: `58c31503…` before and after, identical. The 08.1 work is untouched and still
dirty, as are `filterEngine.ts`, `filterEngine.test.ts`, `GameCard/index.css`,
`RecentlyPlayed/index.tsx` and `steam/games.ts`. The concurrent session's staged todo rename
survived all commits.
