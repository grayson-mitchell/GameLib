# 260825-o67 — close T-34.11-12: one field, and a test that keeps it that way

## Decision (operator, 2026-08-25)

**`connectedStores` moves to `amazon.user_id`.** Asked which of the two fields is correct, the
operator chose `user_id` — i.e. the panel follows the library, not the other way round.

## Why

`34.11-SECURITY.md` records `T-34.11-12` (Spoofing, `connectedStores`) as the one remaining open
threat. Its registered mitigation reads *"derived from the same `gog.username` / `epic.username` /
`amazon.username` / `steam?.username` gates `makeLibrary()` already uses, so the panel cannot
advertise a store the user is not signed into"* — and for Amazon that parity does not hold:

| Site | Line | Expression |
|---|---|---|
| `connectedStores` | `Library/index.tsx:299` | `if (amazon.username)` |
| `makeLibrary` | `Library/index.tsx:633` | `const showAmazon = !!amazon.user_id` |

When `amazon.username` is truthy and `amazon.user_id` is not, the Store group renders an Amazon
row while the grid holds no Amazon games — a **permanently-`0` row**, the exact outcome
`T-34.11-12` and `T-34.11-19` were both written to prevent. Independently raised as review finding
**WR-03** on 2026-08-10 and still listed open in `34.11-VERIFICATION.md`'s warning table.

The other four stores already agree and must not change:

| Store | `connectedStores` | `makeLibrary` |
|---|---|---|
| gog | `gog.username` | `!!gog.username` |
| legendary | `epic.username` | `!!epic.username` |
| zoom | `zoom.enabled && zoom.username` | `zoom.enabled && !!zoom.username` |
| steam | `steam?.username` | `!!steam?.username` |

`sideload` is unconditional in `connectedStores` and has no `makeLibrary` login gate — it is
excluded from the parity check by name, not by accident.

## Tasks

### Task 1 — Move the gate

**Files:** `src/frontend/screens/Library/index.tsx`

**Action:** At `:299`, `if (amazon.username)` → `if (amazon.user_id)`. Update the `useMemo`
dependency at `:306` from `amazon.username` to `amazon.user_id` — leaving it stale would keep the
memo keyed on a field the body no longer reads, which is a second, quieter version of the same
defect. The existing D-04 comment already claims parity with `makeLibrary`; after this it is true,
so extend it to name the threat rather than rewrite it.

**Verify:** no `amazon.username` remains in the file; `react-hooks/exhaustive-deps` reports no new
warning for this memo.

**Done:** both sites read `amazon.user_id`.

### Task 2 — Pin the parity so it cannot drift back

**Files:** `src/frontend/screens/Library/__tests__/connectedStoresParity.test.ts` (new)

**Action:** A **source gate** — every jest project here is `testEnvironment: 'node'` with no jsdom
and no `@testing-library/react`, so the memo cannot be rendered and the invariant has to be read
out of the source text. Parse both regions of `Library/index.tsx`, normalise each gate expression
(strip `!!` and whitespace), and assert the two maps agree for all five gated stores.

**The gate must be proven to fail against known-bad input** (`T-34.11-26`, and `F-34.10-08` which
recorded a `^`-anchored pattern that could never match). Include a specimen carrying the pre-fix
`if (amazon.username)` and assert the checker convicts it, plus a non-vacuity assertion that the
parser actually found five stores rather than zero — an empty-vs-empty comparison passes for free.

**Verify:** suite green against the fixed source; the known-bad specimen produces a mismatch naming
`nile`; the parser reports 5 stores.

**Done:** a drift in either direction fails CI instead of shipping.
