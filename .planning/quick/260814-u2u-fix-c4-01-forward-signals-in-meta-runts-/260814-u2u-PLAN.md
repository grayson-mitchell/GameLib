<design_decisions_already_made_implement_these_exactly>
These are decided. Implement them; do not re-open them mid-task.

**D1 — BOTH steps move to async `spawn`, not just the run step.**
esbuild is short-lived but not instant, and a SIGTERM landing during compile hits the exact same
blocked-loop problem and leaks the exact same tmpdir. Two spawn mechanisms in one file would also
mean two different signal stories. One mechanism, one story.

**D2 — Forward `SIGTERM`, `SIGINT`, `SIGHUP`.** SIGTERM and SIGINT are the two the reviewer measured;
SIGHUP is the terminal-closed case that produces the same orphan+leak. Nothing else is forwarded.

**D3 — Escalate to `SIGKILL` 5000ms after forwarding, if the child is still alive.**
Chosen over waiting indefinitely because unbounded waiting reproduces C4-01's failure mode in a new
shape: an ignoring child keeps the destructive work running and the tmpdir alive for that child's
whole lifetime, and the wrapper hangs instead of aborting. A bounded escalation guarantees
termination and cleanup. 5s is far above any current `meta/*.ts` entry's teardown (none installs a
signal handler at all today, so every one of them dies on the first forwarded signal — the timer is
insurance against a future entry that does), and short enough that row 11's procedure terminates
deterministically. The timer is cleared on the child's `close`; it is NOT `unref`'d.

**D4 — Repeat signals during termination are IGNORED.** One escalation mechanism (D3's timer), one
thing to test. Do not add double-Ctrl-C force-kill behaviour.

**D5 — Exit codes.**
- Wrapper was signalled (`terminatingSignal` set): exit `128 + signum(terminatingSignal)` — the
  signal the CALLER sent, regardless of how the child actually died. A SIGTERM'd wrapper answers
  `143` even if the child had to be SIGKILL'd, because the wrapper is a transparent shim and 143 is
  the conventional answer to "I was terminated by TERM". This also makes the proof deterministic.
- Wrapper NOT signalled, child died by signal (C4-04's case — external `kill -9 <child_pid>` while
  the wrapper survives): exit `128 + signum(child signal)`, e.g. `137`. Never a flat `1`.
- Child exited normally: its own code.
- Child failed to launch (`error` event): print the error, exit `1`.

**D6 — `process.on('exit', cleanup)` YES; `uncaughtException` NO.**
Node emits `'exit'` on normal return, on explicit `process.exit()`, AND after an uncaught exception
(it prints the stack trace first, then emits `'exit'`), so a sync `fs.rmSync` in an `'exit'` listener
covers every non-SIGKILL path without suppressing Node's own diagnostic output — which an
`uncaughtException` handler would. **Verify this empirically in Task 1 rather than trusting it**
(Task 2's C4-02 test is the proof). C4-02 is ALSO fixed structurally by moving `symlinkSync` inside
the `try` — belt and braces, because the reviewer named the `try/catch` specifically.

**D7 — C4-03 falls out and is in scope.** Async `spawn`'s `'error'` event MUST be listened for
(an unhandled `'error'` on a ChildProcess throws), so logging it is mandatory for correctness, not
scope creep. Log `compile`/`run` launch errors to stderr before exiting.
</design_decisions_already_made_implement_these_exactly>
