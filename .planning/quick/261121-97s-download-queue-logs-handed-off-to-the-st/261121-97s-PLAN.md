<objective>
Close todo `.planning/todos/pending/2026-11-19-download-queue-finished-installation-at-steam-handoff.md`. When a Steam install is delegated to the Steam client, the download queue logs `[DownloadManager]: Finished Installation of <appId>` in the same second as the hand-off, while Steam is still downloading. That line misled the Phase 81 live gate. The queue must log that the install was handed off to the Steam client instead.

**Which field marks the hand-off (read from the code, not guessed).** The todo names `managedBySteam` / `installManagedExternally`. Neither is usable here:
- `installManagedExternally` is a per-runner store capability (`src/common/storeCapabilities.ts`), true for EVERY Steam install. That includes GameLib's own depot installs (`installNative`, `installBottleNative`, `installBridgeGame`), which really have finished when they return `done`. Keying on it would mislabel them.
- `managedBySteam` is a `GameStatus` badge field (`src/common/types.ts:402`), not an install-result field.

The install result already has the right field: `InstallResult.handedOffToSteam?: boolean` (`src/common/types/game_manager.ts:43`). Today only the Steam update path sets it (`updateNative.ts`), and `updateQueueElement` reads it (`downloadmanager/utils.ts:516-519`). The two install hand-off returns in `src/backend/storeManagers/steam/gameInstall.ts` return a bare `{ status: 'done' }`:
- line ~442: the macOS experimental InstallApp `outcome.kind === 'ok'` branch, after `startInstallPolling(..., { delegatedToSteamClient: true })`
- line ~478: the final steam://install `openExternal` branch, after the same poll.

This plan sets the flag on those two returns, forwards it through `installQueueElement`, and makes `processNotification` log the hand-off line for it.

**Claude's discretion (documented):** the same defect fires for a Steam update hand-off: "Finished Update of X" is logged while Steam updates. `updateQueueElement` already computes `handedOffToSteam` but drops it from its return. `processNotification` is shared by both element types, so Task 2 forwards the flag on the update path too. That costs one return line and one test, and stops the queue call site from having to special-case updates.

**Out of scope:** the toast (already suppressed for Steam by `installManagedExternally`), the finished-list record (`addToFinished` still records the hand-off), the badge flow in `installQueueElement`'s `finally` block, and any frontend change.

Purpose: a log reader (or a live gate grepping the log) can tell a Steam-client hand-off from a GameLib-completed install.
Output: the flagged hand-off returns, the forwarded flag, the new log branch, unit tests in `downloadqueue.test.ts` and `utils.test.ts`, updated hand-off assertions in `games.test.ts`, and the todo moved to completed.
</objective>
