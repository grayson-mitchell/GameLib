# Quick 260908-gx3: make `totalPairs` self-consistency-checked, and de-stale the 794-pair prose

## Problem

Two sibling todos, both landing in the same writer block of `meta/lintTranslations.ts`:

1. `2026-09-07-presence-baseline-totalpairs-is-unenforced-prose` — `comparePresenceBaseline()`
   derives everything from `baseline.missing` and never reads `baseline.totalPairs`. That design
   is correct and must not change. The risk is that `totalPairs` *looks* enforced: a future
   maintainer reading `totalPairs: 0` can conclude the gate asserts zero missing pairs. Nothing
   catches the field silently desyncing from `missing` under a hand-edit.
2. `2026-09-07-linttranslations-header-comment-cites-794-pairs-now-zero` — the header comment and
   the baseline's own embedded `reason` string both describe a 794-pair gap that quick task
   `260906-u8i` filled the same day. The `reason` string is the worse of the two: it is written
   *into* the generated JSON, so the stale claim ships in the artifact and is re-emitted verbatim
   by every future `LINT_TRANSLATIONS_WRITE_BASELINE=1` run.

## Disposition

Todo 1 offers three dispositions in order of preference. Take **option 1** (derive at write time,
assert at read time as a self-consistency check only). It is the only one that adds a gate, and
the coupling it introduces is *within one file* — `totalPairs` vs `missing` in the same JSON
object — never between the artifact and the live catalogs. That is categorically different from
the artifact/pin coupling this repo has already paid for
(`regenerating-an-artifact-breaks-the-pins-that-guard-it`), where a committed count had to track a
separately-evolving tree.

### Deviation from the todo's wording, stated explicitly

The todo says the result should be "reported as a finding about the *file* rather than about the
catalogs". Two readings: (a) the *subject* of the message is the file, (b) the *channel* is
`result.findings`. This plan takes (a) and routes the message to `result.hardFailures`.

Rationale: `findings` do not contribute to the exit code. A check whose only effect is a line in
CI output nobody reads is a gate gesture, which is the failure class this repo has recorded a
dozen times over. Routing to `hardFailures` is safe here because the predicate is a pure function
of a single committed file that the writer *always* emits consistently — the only way to make it
fire is a hand-edit, i.e. exactly the failure the todo describes. It cannot be tripped by
translation state, locale drift, or a fixture tree.

## Tasks

### Task 1 — Add the self-consistency check and wire it into the gate

**Files:** `meta/lintTranslations.ts`

**Action:**
- Add `export function checkPresenceBaselineSelfConsistency(baselinePath: string): string[]`,
  returning hard-failure messages (empty array = consistent). It reads via the existing
  `readPresenceBaseline()` and asserts two things about the FILE:
  - `totalPairs` is a finite number (absent / non-numeric is a failure — an inert field that is
    also missing gives a reader nothing to check against);
  - `totalPairs === sum(missing[*].length)`.
  Messages name `baselinePath` and both numbers, and must read as being about the artifact, never
  about a locale or a key.
- Call it in `lintTranslations()` immediately after the `existsSync(baselinePath)` guard and
  before `comparePresenceBaseline()`, pushing results into `result.hardFailures`. Placement is
  deliberate: a desynced file is a fact about the file, so it is reported even when the
  comparison that follows is clean.
- Do NOT touch `comparePresenceBaseline()`'s body. The comparison stays over `missing` alone.

**Verify:** `pnpm exec tsc --noEmit -p .` (or the repo's existing typecheck entry point) is clean.

**Done:** `checkPresenceBaselineSelfConsistency` exists, is exported, and is reached from
`lintTranslations()` on the hard-failure path.

### Task 2 — Prove it RED, four ways

**Files:** `meta/__tests__/lintTranslations.test.ts`

**Action:** Add an `R15` describe block covering:
1. **Desynced fixture → RED.** Copy the committed baseline into a scratch dir, hand-edit
   `totalPairs` so it disagrees with `missing`, assert a non-empty message set naming the file.
   This is the arm the todo demands; without it the whole task is theatre.
2. **Absent `totalPairs` → RED.** A baseline object with `missing` but no `totalPairs` at all.
3. **Committed baseline → GREEN.** The real `meta/i18nCatalogPresenceBaseline.json` returns `[]`.
   This is what makes the check safe to leave on the hard-failure path.
4. **Wiring → RED through `lintTranslations()`.** Drive the real entry point with the canonical
   `public/locales` (so the canonical-path guard is satisfied) and `baselinePath` pointed at the
   desynced fixture; assert the message lands in `hardFailures`, not `findings`.

Arm 4 is the one that proves the check is actually mounted — arms 1-3 alone would pass against a
helper nothing calls (`a-pass-can-cover-an-unreachable-surface`).

**Verify:** The new suite passes. Then temporarily neutralise the check in `lintTranslations.ts`
and confirm arms 1, 2 and 4 all go RED — a check that cannot be made to fail has not been proven.
Restore afterwards.

**Done:** All four arms pass; the negative control confirms three of them are load-bearing.
