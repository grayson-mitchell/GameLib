Decisions made at planning time (the executor implements these, it does not revisit them):
- Save-location source: the stored `gogSaves` from the game's settings (resolved absolute paths,
  may be user-edited) PLUS the GOG templates cached on the library entry
  (`getGameInfo().gog_save_location`), using only those that start with `<?INSTALL?>` and carry no
  other `<?NAME?>` variable, with `<?INSTALL?>` resolved to the install path.
  `library.gog.getSaveSyncLocation()` is NOT called: it fetches remote-config.gog.com over axios,
  so it is slow or fails offline at uninstall time. The library refresh already caches the same
  templates on `gog_save_location` for installed non-Linux games (library.ts ~635 and ~908). Every
  other variable (Saved Games, AppData, Documents, Application Support) resolves outside the
  install folder, so it cannot change what is kept.
- Platform scope: every platform where uninstall deletes the folder, not only win32. The delete
  runs on all platforms. `<?INSTALL?>` resolves to the host install path everywhere. Stored
  `gogSaves` are host paths (Wine games go through getWinePath in save_sync.ts). A path that is
  not absolute on the host is ignored. Nothing in the code makes this unsafe on Linux or macOS,
  because the change only ever deletes LESS than today.
- Safety check: sub-path targets use the existing `SafetyRequest` shape: `kind: 'game-install'`,
  `trustRoot` = the canonical install folder, the same `selfKey`, `knownInstalls` and
  `protectedRoots`. The crate accepts them on its own rules. `check_known` skips the `selfKey`
  entry (remove.rs:144), so a path inside the game's own install is not `inside-known-install`.
  `check_trust_root` admits only paths strictly inside the trust root. `remove_tree` re-checks
  every target at delete time. No Rust change, no bypass.
</objective>
