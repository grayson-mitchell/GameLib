<findings_that_override_the_todo>
The plan follows the code, not the todo, on two points.

**F-1. Launch target: `gamelib://launch?appName={appId}&runner=steam`, not a raw `steam://rungameid/{appId}`.**
The todo asks for a launcher that runs `steam://rungameid/{appId}`. The shared module already
builds every shortcut around `gamelib://launch?appName=…&runner=…`. Where that URL ends up:

- macOS: `run.sh` runs `"<GAMELIB_SHELL_EXE>" --no-gui '<url>'`, with both query values passed
  through encodeURIComponent.
- Linux: `Exec=xdg-open <url>`.
- Windows: the `.lnk` target.

`src/backend/protocol.ts` accepts `runner=steam`. `RUNNERS` includes `'steam'` (D-35-19-05), and
lines 205-218 route a Steam title to `dispatchSteamLaunch(appName)` in
`storeManagers/steam/launchDispatch.ts`. That calls `SteamGame.launch()`, the same code the Play
button runs.

`SteamGame.launch()` does not just open `steam://rungameid`. On macOS it first picks a route: the
bridge-bottle launch, single-flight against a live bottle monitor, the guided bottle-setup prompt,
or `tellBottledSteamToLaunch`. It falls back to `shell.openExternal('steam://rungameid/…', { activate: false })`
only for native titles. It also records the game in recent games.

A shortcut that opened `steam://rungameid` directly would skip all of that. It would send a bridge
or bottle-routed title to native Steam, which is exactly the misroute the project's bottled-Steam
and bridge rules exist to prevent. Using the shared module unchanged keeps one launch path, and a
native title still ends at `steam://rungameid` through `launch()`. So no Steam-only writer and no
URL-target seam are needed. The unit tests pin `runner=steam` and the appId in each OS's target.

**F-2. No non-menu caller reaches the Steam stub.**
The callers of `game.addShortcuts(...)` are:

- the `addShortcut` channel: `sidecar/shortcutsFlowRegistration.ts:203`, plus the Electron-era
  `shortcuts/ipc_handler.ts:45`;
- post-install calls in `gog/games.ts`, `legendary/games.ts`, `nile/games.ts` and
  `sideload/library.ts`.

`SteamGame.install()` never calls `addShortcuts`, and neither does anything under
`storeManagers/steam/`. So no post-install `addShortcuts(false)` reaches the stub, and there is no
other caller to align. This plan does not add post-install shortcut creation for Steam: the todo
asks for it only where a caller already reaches the stub. The executor records this in the closing
note. It also records that a Steam uninstall, which goes through Steam's own dialog, does not remove
the shortcut. A leftover shortcut then routes to `launch()`, so Steam prompts to install.

**F-3. The shared `addShortcuts` would register a Steam game as a non-Steam game.**
`shortcuts.ts:43-45` calls `addNonSteamGame(game)` whenever the global `addSteamShortcuts` setting
is on, and `nonesteamgame.ts` has no runner guard. Once SteamGame delegates to the shared module,
that would write a Steam game into `shortcuts.vdf` as a non-Steam shortcut. The menu already hides
"Add to Steam" for Steam games (`GameSubMenu/index.tsx` around line 625), so add the matching guard
`runner !== 'steam'` in the shared module.

**Icons.** `getIcon(appName, gameInfo)` in `shortcuts/utils.ts` uses `gameInfo.art_square`. For
Steam that is the same `…/library_600x900.jpg` URL the tile shows (`steam/games.ts` around line 820).
It downloads once to `<iconsFolder>/<appId>.jpg` and reuses the file after that.

If there is no art, the module already falls back cleanly. macOS gets an `.app` with no
`CFBundleIconFile` (D-04), and Linux gets a `.desktop` with no `Icon=`.

On Windows the `.lnk` icon comes from `gameInfo.install.executable`, which Steam does not fill in,
so Steam `.lnk` files get the default shell icon. That is acceptable; no change.
</findings_that_override_the_todo>
