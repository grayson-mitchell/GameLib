### Two corrections to the source todo, both load-bearing

1. **The todo's attributed call site is wrong.** It names
   `src/backend/utils/inet/downloader/index.ts:70` (a bare unbounded `axios.get`).
   That call site NEVER FIRES at boot — it is the winetricks path. Anyone editing it
   would change nothing. This is the second time this todo's prescribed remedy has
   pointed at the wrong object; `260913-m9c` already caught the first.
2. **Option 1 in the todo rests on a false premise.** It proposes "do not block
   `init()` on boot-time downloads". `init()` already does not: `READY_SENTINEL` is
   written as the last statement of `init()`, and this download begins later via
   `runOnceWhenOnline` -> event -> listener. Measured `ready=YES` while exiting at 27s.
   The coupling is **exit-time only**.

## Why THIS remedy and not the one originally proposed

The obvious fix — an `'end'` handler on `startRpcServer()` calling
`callAllAbortControllers()` — is **explicitly fenced** and must not be built:

- `.planning/todos/completed/2026-09-13-sidecar-stdin-owned-exit-contract-....md`,
  "Not in scope": *"Do not 'fix' this by adding an `'end'`/`'close'` handler to
  `startRpcServer()` ... The first misunderstands the design."*
- `260913-ty4-PLAN.md` "Out of scope" repeats it.
- `CLAUDE.md`: *"`startRpcServer()` therefore has no `'end'`/`'close'` handler by
  design ... adding one misunderstands the mechanism rather than hardening it."*

`CLAUDE.md` names exactly two admissible remedies for the in-flight class:
**bounded, or not issued at boot.** This plan is the second, and it touches the exit
contract not at all.

### The boot fetch is waste on a cold profile — the download precedes the check that needs it

`tools/dxmt.ts:148-171` today:

```js
if (releasesInfo['dxmt'].tag === currentDXMTVersion) return
await DXMT.getLatest()                                   // <- downloads the tarball
const availableWines = wineDownloaderInfoStore.get('wine-releases', [])
const installedWineStagingVersions = availableWines.filter(
  (wine) => wine.type === 'Wine-Staging-macOS' && wine.isInstalled
)
installedWineStagingVersions.forEach(...)                // <- EMPTY on a fresh profile
```

On a cold profile no Wine-Staging-macOS exists, so the tarball is fetched and copied
into **zero** wine installs.

**This cannot starve a new wine install.** `dxmt.ts:134-139` already fetches DXMT on
demand when a Wine-Staging-macOS version is installed (`wineVersionInstalled` ->
`DXMT.getLatest()` -> `copyWineAndConfigure`). The `releasesInfoReady` listener's job
is only to *update* DXMT inside wines that already exist — its own header comment says
so: "Update DXMT version in `*-DXMT` wines if new version available".

**Nothing else consumes the downloaded files.** `copyLatestDXMTFiles` has exactly two
callers: `copyWineAndConfigure` (which fetches first itself) and this listener's
`forEach`. Every other `DXMT` reference in the repo tests a wine *name* suffix
(`-DXMT`), not the tool files.
