## Task 5 (round 3 fix): Make the QR box fixed-size instead of computing a reservation

Restructured `renderQRContent()` in `index.tsx` so the `isQRLoading` branch and the `step === 'qr-active' && challengeUrl` branch merge into ONE shape: the same top `<p>` ("Open Steam on your phone and scan this code.", now always rendered, not gated on `challengeUrl`), the same `.steamQrContainer` > `.steamQrBox` nesting, and the same bottom `<p>` slot -- swapping only the box's child (`FontAwesomeIcon` spinner vs `<QRCode>`) and the bottom caption's text ("Generating QR code..." vs "QR code refreshes automatically."). Both `<p>`s now set `lineHeight: 1.4` explicitly instead of relying on the browser default, removing the font-metric guess entirely rather than tuning it. `.steamQrBox` (new CSS class in `index.scss`) is a fixed `216px x 216px` box (200px `<QRCode>` + 8px padding per side) regardless of which child it holds, so the two states are equal-height **by construction**, not by a computed reservation.

Deleted the old `.steamLoginBody #tabpanel-qr > div { min-height: 310px }` rule and its full arithmetic comment entirely -- not left behind alongside the new fix, since it is no longer needed: with both states rendering the identical DOM shape, there is nothing left for a reservation to reserve against. Kept `.steamQrContainer svg { display: block; }` (still load-bearing -- it keeps the QR-holding box the same height as the spinner-holding box, since `react-qr-code` emits a bare inline `<svg>` that would otherwise add an unpredictable baseline gap).

**No residual min-height literal was added.** Per the coordinator's instruction to either equalise the text block or add an honestly-labelled residual, the choice made here was full equalisation (identical DOM shape, identical font-size/line-height for both states' captions) rather than tuning a number -- this is the more robust of the two options because it removes the font-metric dependency instead of estimating around it. Since I have no way to visually confirm zero delta myself (no live browser access in this environment), **I am not claiming the resize is gone** -- only that the previous font-metric-dependent guess has been replaced with a construction that removes that specific class of error. If the operator still observes any delta after this change, it points to a different cause (a genuine subpixel/rendering artifact, not the assumption this fix removes) and should be reported with a measured px estimate so any further reservation is added as an empirically-confirmed value, not another guess.

No user-visible string was changed -- all three existing captions reused verbatim (moved markup, not copied text). Verified via `sass` compile (clean), `tsc --noEmit` (clean), the window-chrome suite (23/23), and the two i18n meta suites (154 passed/1 skipped/0 failed, matching the pre-existing baseline -- `expectedCount: 26` for this file unmoved). ## Task 7 (followup 1 fix): Centre `.steamLoginBody` inside Paper

**What changed:** added `margin-inline: auto;` to `.steamLoginBody` in `index.scss`, with a comment
documenting the investigation. Added one mutation-proven source-gate PRESENCE assertion to
`steamLoginWindowChrome.test.ts` ("the fixed-width .steamLoginBody centres itself instead of relying
on Paper to have zero slack").

**Mechanism investigation (analytical only -- no live browser available this session):**
- `Dialog.tsx`'s `MuiDialog` has `maxWidth="md"` but no `fullWidth` prop -- confirmed via source read.
  Without `fullWidth`, MUI's Paper shrink-wraps to content width rather than always filling
  `maxWidth`.
- `DialogContent` in that file is MUI's own stock component (imported directly from `@mui/material`),
  not this repo's local `DialogContent.tsx` (`components/UI/Dialog/components/DialogContent.tsx`,
  confirmed unrelated and unused in this render path) -- it has symmetric default padding.
- No `.steamLoginDialog`-scoped CSS currently overrides width or padding; a prior rule targeting that
  class was removed in quick task `260820-kq0`'s round 3.
- Under a bare shrink-to-fit computation, `.steamLoginBody` (fixed `width: min(480px, 95%)`) is itself
  the widest child driving Paper's width, so there should be no slack for it to sit off-centre in.
- **Leading, UNCONFIRMED hypothesis for the actual slack:** this `Dialog` passes `scroll="paper"`,
  under which MUI applies `overflow-y: auto` directly to Paper (not to DialogContent). When Paper's
  content is tall enough to need a vertical scrollbar, that scrollbar consumes width on one side of
  the content box, shifting a flush-left, non-auto-margin block off-centre relative to Paper's outer
  edge. This is plausible and consistent with the direction reported ("too far to the left" -- a
  right-side scrollbar would shift left-aligned content left), but it was NOT measured live this
  session -- no browser/DevTools access was available to confirm a scrollbar is actually present at
  the size this dialog renders at.
- **What was confirmed, not guessed: this is OUR regression, not pre-existing.** `git log --oneline
  --all -- .../SteamLogin/index.scss` shows `.steamLoginBody` (and its `width: min(480px, 95%)`,
  carried over unchanged from its predecessor `.steamLoginPanel`) was introduced by `fdc362444`
  (`quick-260820-kq0`). That same commit is the FIRST to wire SteamLogin's root into MUI's
  `Dialog`/`Paper`/`DialogContent` structure at all -- `git show fdc362444^:.../index.tsx` confirms
  the predecessor rendered `.steamLoginPanel` as a plain top-level `<div>`, with no MUI dialog/paper
  centering context to be off-centre within. The centring gap did not exist before that commit and
  was never given a centring rule when the dialog wrapping was added.

**Why `margin-inline: auto` rather than a computed offset:** this fix self-corrects to whatever free
space actually exists on either side of `.steamLoginBody`, regardless of the exact mechanism that
produces it (confirmed scrollbar or otherwise) and regardless of the exact px amount -- it is a no-op
if there turns out to be no slack at all. This avoids repeating the exact class of mistake the
original `310px` min-height guess made (assuming a specific numeric cause instead of measuring or
self-correcting).

## Followup 2 -- credentials tab equal-height: DEFERRED to its own task

**The request (verbatim):** "username and password change the size of the form, would look a lot
better if username password used the same form size and adjusted elements in the form to fit."

**Investigation.** `renderCredentialsContent()`'s step-1 form (username input + password input, each
in a `marginBottom: var(--space-md)` block, plus an optional error line, plus a full-width submit
button with `marginTop: var(--space-lg)`) and step-2 (`credentials-2`, the SteamGuard code form) are
each visibly shorter than the QR tab's content (`renderQRContent()`'s top caption + the now-fixed
216x216px `.steamQrBox` + bottom caption + surrounding padding) -- consistent with the operator's
report that switching tabs visibly resizes the dialog.

The shared `TabPanel` component (`components/UI/TabPanel/index.tsx`) always renders its OUTER
`<div role="tabpanel">` wrapper for every tab, but only mounts the INNER `<div>{children}</div>`
when `value === index` -- inactive tab content is fully unmounted, not merely hidden. Making the two
panels equal-height "by construction" (the same principle Task 5 used for the QR states, per this
task's own standing instruction not to use a computed literal that can drift) requires the panel
CONTENT to exist simultaneously so CSS can size a shared box to the taller of the two -- e.g. a CSS
Grid stack (`grid-area: 1 / 1` on both panels, `visibility: hidden` + `aria-hidden` + `tabIndex={-1}`
+ `pointer-events: none` on the inactive one) -- which is not possible under `TabPanel`'s current
unmount-on-inactive behaviour without either modifying `TabPanel` itself or building a parallel,
non-shared mechanism just for this screen.

**`TabPanel` is not exclusively SteamLogin's.** `grep -rln "components/UI/TabPanel"` (excluding
`__tests__`) shows three consumers: `SteamLogin/index.tsx`, `Settings/sections/GamesSettings/index.tsx`,
and `Game/GamePage/index.tsx`. Changing `TabPanel`'s mount behaviour to always-mount (needed for a
Grid-stack approach) would affect those two unrelated screens too, and neither of them has been
exercised or audited as part of this task -- their own state-reset-on-unmount behaviour, if any,
could silently change, and any of their own interactive elements newly kept mounted-but-hidden would
need the same `tabIndex`/`aria-hidden`/`pointer-events` treatment this task would only think to apply
to SteamLogin's two panels.

A second option -- token-budget height-matching (sizing the credentials form's spacing to sum to the
QR panel's height using the same `--space-*` vocabulary) -- was considered and rejected: it
reintroduces exactly the unverifiable font-metric/box-model-guessing risk that produced the original,
now-fixed `310px` min-height mistake (Task 2, later replaced in Task 5), and there is no live
browser/DOM access in this session to confirm any specific computed height actually matches.

**Decision: DEFER to its own quick task, per this plan's own stated permission** ("If this turns out
to need more than a contained layout change, STOP and say so rather than half-doing it. It can become
its own task"). This is not a "contained layout change" -- it either touches a three-consumer shared
primitive (`TabPanel`) with real accessibility work that needs its own verification across all three
screens, or requires inventing a new, currently-nonexistent local pattern in this codebase, in both
cases without any way to confirm the visual result in this session. Implementing it now, without live
verification, risks repeating the exact "confident guess that turned out wrong" pattern that produced
two of this plan's three prior gate FAILs.

**Not implemented. No code change was made for followup 2.** `index.tsx`'s
`renderCredentialsContent()` and `TabPanel/index.tsx` remain byte-identical to their Task 6 state.
The `expectedCount: 26` i18n allowlist pin for `SteamLogin/index.tsx` is unaffected because this file
was not touched for this item.
