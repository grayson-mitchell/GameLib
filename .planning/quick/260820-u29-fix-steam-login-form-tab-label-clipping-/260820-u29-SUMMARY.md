**Deviation from the WineManager/index.css convention this was pointed at as canonical:** that file's `&.Mui-selected`/`:hover` rules use `var(--text-primary)`, but a repo-wide `grep -rn -- "--text-primary:" src/frontend` returns **zero results** -- the token is used in several places (`App.tsx:101`, `WineManager/index.css:33,84,89`, `WineManager/components/WineItem/index.css:58`, `PopoverComponent/index.scss:5`) but defined nowhere. ## Task 5 (round 3 fix): Make the QR box fixed-size instead of computing a reservation

Restructured `renderQRContent()` in `index.tsx` so the `isQRLoading` branch and the `step === 'qr-active' && challengeUrl` branch merge into ONE shape: the same top `<p>` ("Open Steam on your phone and scan this code.", now always rendered, not gated on `challengeUrl`), the same `.steamQrContainer` > `.steamQrBox` nesting, and the same bottom `<p>` slot -- swapping only the box's child (`FontAwesomeIcon` spinner vs `<QRCode>`) and the bottom caption's text ("Generating QR code..." vs "QR code refreshes automatically."). Both `<p>`s now set `lineHeight: 1.4` explicitly instead of relying on the browser default, removing the font-metric guess entirely rather than tuning it. `.steamQrBox` (new CSS class in `index.scss`) is a fixed `216px x 216px` box (200px `<QRCode>` + 8px padding per side) regardless of which child it holds, so the two states are equal-height **by construction**, not by a computed reservation.

Deleted the old `.steamLoginBody #tabpanel-qr > div { min-height: 310px }` rule and its full arithmetic comment entirely -- not left behind alongside the new fix, since it is no longer needed: with both states rendering the identical DOM shape, there is nothing left for a reservation to reserve against. Kept `.steamQrContainer svg { display: block; }` (still load-bearing -- it keeps the QR-holding box the same height as the spinner-holding box, since `react-qr-code` emits a bare inline `<svg>` that would otherwise add an unpredictable baseline gap).

**No residual min-height literal was added.** Per the coordinator's instruction to either equalise the text block or add an honestly-labelled residual, the choice made here was full equalisation (identical DOM shape, identical font-size/line-height for both states' captions) rather than tuning a number -- this is the more robust of the two options because it removes the font-metric dependency instead of estimating around it. Since I have no way to visually confirm zero delta myself (no live browser access in this environment), **I am not claiming the resize is gone** -- only that the previous font-metric-dependent guess has been replaced with a construction that removes that specific class of error. If the operator still observes any delta after this change, it points to a different cause (a genuine subpixel/rendering artifact, not the assumption this fix removes) and should be reported with a measured px estimate so any further reservation is added as an empirically-confirmed value, not another guess.

No user-visible string was changed -- all three existing captions reused verbatim (moved markup, not copied text). Verified via `sass` compile (clean), `tsc --noEmit` (clean), the window-chrome suite (23/23), and the two i18n meta suites (154 passed/1 skipped/0 failed, matching the pre-existing baseline -- `expectedCount: 26` for this file unmoved). Committed at `6823765ee`.
