# Quick Task 260910-et3 — flip the `tauri:dev` default to the dev secret vault

## Problem

`260909-su5` added `tauri:dev:vault` as an **opt-in** sibling and deliberately left `tauri:dev` on
the keyring arm. That decision has now been overruled by the operator, with live evidence: at
planning time a `pnpm tauri:dev` session started without the flag had been running 2h31m, its log
read `[bootstrap] secret stores: keyring`, and it carried `keyring_get` reads of **6640ms** and
**8519ms** — the latency signature of a macOS Keychain approval dialog blocking on a human.

The failure mode is not the prompt itself, it is that the prompt is the **default** and the bypass
is the thing you have to remember. Every prior incident in this repo's ledger is the same shape: a
session started without the flag, took the keyring arm, and the first real operation died
(`260909-nzb`: `refresh token read failed (timeout)`, zero bytes, a BLOCKED run that measured
nothing, then a ~120 s failure memo that made the retry read as a second independent failure).

Making the safe arm the default inverts the memory burden: you now have to remember only when you
specifically *want* the keyring.

## Approach

Four scripts, one build chain.

| Script | Value | Role |
|---|---|---|
| `tauri:dev:run` | `pnpm build:sidecar && pnpm build:decompress-worker-dev && tauri dev` | Internal base. **The only place the build chain is written.** |
| `tauri:dev` | `cross-env GAMELIB_DEV_SECRET_VAULT=1 pnpm tauri:dev:run` | The new default — dev-vault arm. |
| `tauri:dev:keyring` | `pnpm tauri:dev:run` | Explicit keyring arm, for gates that exercise the shipped Keychain path. |
| `tauri:dev:vault` | `pnpm tauri:dev` | Back-compat alias; `STATE.md:5819` and operator notes name it. |

**Why the base script exists:** duplicating `pnpm build:sidecar && pnpm build:decompress-worker-dev
&& tauri dev` across two arms is a drift hazard — a future change to the build chain would land in
one copy. Task 1's verify includes a structural gate asserting the chain string is owned by exactly
one script.

**Why `tauri:dev:keyring` delegates to the base and not to `tauri:dev`:** `cross-env VAR=0` on an
outer script cannot unset what an inner script sets. The keyring arm must never route through the
flagged script.

### Decided: `tauri:dev:keyring` omits the flag rather than forcing `=0`

`cross-env GAMELIB_DEV_SECRET_VAULT=0 pnpm tauri:dev:run` was considered and **rejected**, despite
being strictly more robust against an inherited exported `GAMELIB_DEV_SECRET_VAULT=1`.

`devSecretVault.ts`'s guard is an exact `=== '1'` match and its own docblock names `'0'` as a
value that returns `false` silently — so `=0` would correctly select the keyring arm. But two live
gate contracts require the variable to be **UNSET**, not merely non-`'1'`:

- `.planning/quick/260817-d61-defer-the-steam-keyring-read-from-startu/260817-d61-LIVE-GATE.md:41`
  — "**`GAMELIB_DEV_SECRET_VAULT` MUST be unset.**"
- `.planning/quick/260907-ov3-live-gate-the-keyring-get-bounded-classi/260907-ov3-LIVE-GATE.md:234`
  — F7, "must be unset in the launching shell".

A script that positively sets `0` satisfies the arm and violates the letter of both contracts, and
a future operator scoring condition (1) mechanically would have to adjudicate. Not worth it. The
inheritance hazard is instead **documented, not engineered away**: those contracts already require
the operator to confirm the shell variable, and the `[bootstrap] secret stores:` receipt is the
real proof of arm either way.

### Consequence this change introduces, and where it is closed

Those same contracts score "`GAMELIB_DEV_SECRET_VAULT` unset in the launching shell" as evidence of
the keyring arm. **After this change that inference is no longer sound** — `pnpm tauri:dev` sets the
flag inside the child regardless of the shell. The contracts do not become fail-open (conditions
(2)/(3), the `[bootstrap] secret stores:` receipt and a zero `[dev-secret-vault]` line count, still
catch a mis-armed run), but condition (1) alone stops being sufficient. Those two files are
**discharged historical records and must not be edited**. The forward-looking correction lands in
Task 3, in the auto-loaded memory doc that future sessions actually read.
