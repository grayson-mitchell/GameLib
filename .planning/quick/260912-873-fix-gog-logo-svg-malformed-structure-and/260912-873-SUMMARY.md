# Summary

## What shipped

`src/frontend/assets/gog-logo.svg` — 1271 bytes / 8 lines, tab-indented — became a flat
1120-byte, 3-line `<svg><path/>`:

```xml
<svg class="gogIcon" viewBox="0 0 34 31" xmlns="http://www.w3.org/2000/svg">
	<path class="cls-1" d="…1008 chars, byte-identical…"/>
</svg>
```

Dropped: the `<use>`/`<symbol>` self-nesting (a `<use>` referencing a `<symbol>` id defined as
its own descendant), the JSX-ism `className="cls-1"` → `class="cls-1"`, and
`preserveAspectRatio="xMidYMax meet"` (bottom-alignment — the actual rendering defect). Root
`viewBox` changed from the outer `0 0 32 32` (which only *looked* square) to `0 0 34 31` (the
path's true bounds), with `class="gogIcon"` preserved on the root.

`src/frontend/screens/Game/GamePage/index.css` lost the 4-line `&.gogIcon { padding: 0px
var(--space-3xs) var(--space-3xs); }` block at lines 618–621 that existed solely to hand-correct
the old bottom-flush render. GOG now inherits the base `padding: var(--space-2xs)` shared by
Epic, Steam, and Amazon on the GamePage.

## Byte-identity gate on the `d` attribute

The plan's headline fidelity requirement: never retype or hand-copy the 1008-character `d`
value. Extracted programmatically via regex from the original file, sha256'd
(`87bff842488bf74f6c65aba2597434f3246d03bd56bffa92e69cf15e78d790e1`), copied the original to the
session scratchpad, wrote the new file by string interpolation, then re-extracted `d` from the
new file and re-hashed. Hashes matched. Length checked at 1008 both before and after.

## The todo's headline remedy was rejected on measurement, not applied

The source todo asked to square the `<symbol>`'s `viewBox` so GOG renders 19.0 × 19.0 like Steam.
**This was not done.** The gog.com wordmark's own `<path>` spans `0..34` × `0..31` user units —
34:31 is the brand's actual aspect, not a defect. A square viewBox with `meet` is a no-op (ink
stays 34:31, letterboxed, re-measuring 19.0 × 17.5 again); forcing true square needs
`preserveAspectRatio="… none"`, a ~9.7% vertical stretch that turns the rounded corners of the
wordmark's background rectangle into ellipses. `steam-logo.svg` (`0 0 496 512`) and
`amazon-logo.svg` (`0 0 448 512`) are also non-square — square was never this repo's convention
for store logos. Full reasoning recorded in the closed todo's new `## Resolution` section so a
future reader can't re-file "make it square" without first reading why it was rejected.

The same measurement exposed the real defect instead: `xMidYMax` bottom-aligned the glyph,
dumping all letterbox slack above it and none below — GOG sitting visibly lower than the
vertically-centred Steam mark beside it. That's what this task fixed.

## Geometry re-measurement, and a tooling quirk worth flagging

Rendered both the pre-edit and post-edit SVGs with `rsvg-convert -w 192 -h 192 -b white` and
decoded the resulting PNGs in pure Python (`zlib` + `struct`, manual per-scanline unfilter for
PNG filter types 0–4; `rsvg-convert` emitted 24-bit RGB, colortype 2, not RGBA — the decoder was
written to handle both). Ink = any pixel not pure white.

**Discrepancy from the plan's literal command, reported rather than silently worked around:**
`rsvg-convert -w 192 -h 192` on the *pre-edit* file letterboxes correctly, because its outer
`viewBox="0 0 32 32"` is square (trivial 1:1 map to a square raster) and the inner
`<symbol>`'s own `preserveAspectRatio` is resolved by librsvg's internal SVG-viewport nesting
regardless of the raster call. The *post-edit* flat file has a non-square root viewBox
(`0 0 34 31`) with no `width`/`height` attributes — and `rsvg-convert -w 192 -h 192` on that
shape **stretches to fill the full square rather than letterboxing** (confirmed: ink filled
192×192 edge-to-edge, no gaps). Adding `-a`/`--keep-aspect-ratio` doesn't reproduce a padded
square canvas either — it shrinks the *output raster itself* to 192×176, so there's no gap to
measure inside a fixed box. Neither is what a browser does: a browser placing this `<svg>` in a
CSS-sized square box (which is exactly how the app embeds it — `width:100%;height:100%` inside a
sized container) always honors `preserveAspectRatio` (default `xMidYMid meet`) and letterboxes.
To get an apples-to-apples desk measurement of that real behavior, built a temporary harness
(scratchpad only, never shipped) that wraps the extracted `d` in the same square-viewBox +
`<use>`-of-symbol structure the *original* file used — reproducing the real embedding pattern
rather than rsvg-convert's bare CLI stretch:

| | before (`xMidYMax`) | after (`xMidYMid`, via harness) |
|---|---|---|
| ink width | 192 | 192 |
| ink height | 176 | 176 |
| top gap | 16 | 8 |
| bottom gap | 0 | 8 |

Plan's predicted numbers were height 175 / gaps ≈8/≈8; the 176-vs-175 and 16-vs-17 deltas are
inclusive-pixel-row counting at this raster size, not a defect. Height holding at 176 in both
renders is the proof 34:31 was preserved (not stretched); gaps equalising from 16/0 to 8/8 is the
proof the centring fix landed.
