<objective>
`pnpm smoke:sidecar` is RED and blocks every PR to `main`/`stable`. The gate builds
`build/main/sidecar.js` and runs it with no stdin, expecting exit 0 within 30s.

The governing todo's root cause is STALE and must not be inherited. What is measured today:

| env | outcome |
| --- | --- |
| real HOME (the gate's own env) | never exits; no exit at 120s, reproduced twice |
| real HOME + `CI=e2e` | exit 0 in 0.5s |
| cold empty fake HOME, first run | exit 0 in 27.7s |
| same fake HOME, second run | exit 0 in 1.0s |

At 40s under the real HOME the process holds exactly two handles, both stdio pipes
(`fd 1`, 713 bytes written; `fd 2`, 0 bytes), and `process._getActiveRequests()` returns 0.
No TLS sockets, no timers, no child processes. The same run logged
`connectivity-changed {status: "online"}`, so the pings SUCCEEDED. This is not the offline
`retry()` timer chain and not a network outage.

A Node process with no ref'd handles and no pending requests should exit. It does not.
**That contradiction is the finding, and Task 1 exists to resolve it before anything is changed.**

There is no explicit exit path to look for: `src/sidecar/index.ts` calls `init()`, `init()` ends
at `deliverStartupProtocolUrl()`, and `startRpcServer()` (sidecarRpc.ts:296) only attaches an
`input.on('data')` listener. The sidecar exits solely because the event loop drains. So "it does
not exit" means, necessarily, that something is still holding the loop — and the JS-visible
introspection says nothing is. The instruments in Task 1 are chosen to see what
`_getActiveHandles()` structurally cannot: native-addon libuv work, threadpool requests, and
blocked native threads.

Purpose: unblock CI by FIXING the defect, not by hiding it.
Output: a named holder with evidence, a narrow fix (or an argued, recorded decision), a green
gate, a proven-still-effective negative control, and a corrected todo.
</objective>
