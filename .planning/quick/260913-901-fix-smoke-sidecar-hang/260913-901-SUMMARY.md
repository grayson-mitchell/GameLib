# quick-260913-901: Fix the `pnpm smoke:sidecar` hang — Summary

Named the sidecar's boot hang as an un-`unref()`'d 5-minute GOG-presence `setInterval`, fixed it at
its creation site, and discovered in the process that the gate's own negative control no longer
works.

## Outcome

`pnpm smoke:sidecar` went from **`rc=1` at 30.7s** (ETIMEDOUT arm; the raw bundle ran 60s under the
real HOME without exiting and had to be SIGKILLed) to **`rc=0` in 1.9s**.

## The finding

The plan's objective recorded a paradox: at t=40s the process held only two stdio pipes, zero
pending requests, and still would not exit. That was an **instrument artefact**.
`process._getActiveHandles()` only reports libuv handles that have a JS wrapper; Node multiplexes
every JS timer onto one internal `uv_timer_t` that has none, so a ref'd `setInterval` is invisible
to it by construction.

Two instruments named the holder:

1. A Node diagnostic report (SIGUSR2 at t=40s) showed **exactly one referenced+active libuv handle:
   a `timer`**, at an address inside Node's internal per-`Environment` handle block. Both `tcp`
   handles and the `installed.json` `fs_event` were `is_referenced: false`.
2. An `async_hooks` probe (its own dump timer `unref()`'d, so it could not be the artefact the plan
   warned about) resolved it: `REFD_TIMER_COUNT=1`, `_repeat=300000`, stack terminating in
   `setPresence` — stable at t=10/20/30/40s. `beforeExit` never fired.

`setPresence()` arms the keep-alive only when a GOG account is logged in, which is exactly why it
reproduced under the real HOME and never under an empty fake HOME.

**Fix (Branch A):** `interval.unref?.()` at `src/backend/storeManagers/gog/presence.ts:39` with an
in-situ comment. `unref()` does not stop the keep-alive — stdin holds the loop for the whole of the
sidecar's real life, so the 5-minute POST still fires. This also removes a real user-facing hazard,
not just a red gate: a sidecar that cannot exit on stdin EOF is the same orphan mechanism as the
standing `tauri-dev-shell-does-not-reap-its-node-sidecar` finding.

## Falsified hypotheses

- **stdout backpressure — FALSIFIED with measurement.** Three real-HOME runs with fd 1 on an
  undrained pipe, a file, and `/dev/null` all hung identically; output was 713 bytes against a
  ~64KB buffer. Resolved, not left open.
- **The todo's "five live TLSSockets" — FALSIFIED.** That was a t=3s snapshot of the boot transient.
  At the timeout moment no socket was referenced and the pings had already succeeded.
- **`installed.json` FSWatcher regression — FALSIFIED** (`fs_event` is unreferenced).
- **A blocked native Keychain/keyring thread (the plan's leading Step 1.3 hypothesis) —
  FALSIFIED.** The process serviced its own probe interval at t=10/20/30/40s, so it was not blocked
  in native code. `sample` was therefore unnecessary. No native keyring/keytar/fsevents addon ships
  in this project.

## BLOCKING FINDING — the gate's negative control failed

**`pnpm smoke:sidecar` can no longer detect the regression class it was built for.** A
`throw new Error(...)` at `bootstrap.ts` module scope — verified present in the built bundle —
still produced `[sidecar-smoke] PASS`, `rc=0`.

Mechanism, proven by direct run rather than argued: `src/sidecar/index.ts`'s first import installs
`installUncaughtExceptionGuard()`, whose own doc comment states it "suppresses Node's default
behaviour of printing the stack and exiting non-zero". The throw was caught
(`[sidecar] uncaught exception: Error: NEGATIVE CONTROL 260913-901` at `Module._compile`), the
sidecar died without ever emitting `__GAMELIB_SIDECAR_READY__` (0 occurrences in stdout), and it
exited **0**. The gate's only success signal is that exit code.

The guard is correct and must not be removed. The gate's **ETIMEDOUT arm is still sound** — it is
what caught this task's hang — so the presence fix remains trustworthy, having been verified by
direct measurement of the bundle rather than by the exit code. Per the plan this was **reported,
not worked around**, and filed as its own todo with the one-line remedy (assert the READY sentinel,
which the script already captures and never inspects).

The source tree was restored byte-for-byte: shasum matches
`64cbc468979817a64ef2635fa4d4763166c5e47014d87cbc28bd821f6af5add7`, `git diff --stat -- src/` empty,
gate green afterwards. Restored with `cp`, never `git checkout --`.

## Second defect found and filed (not fixed)

A cold boot sits REFERENCED on ~25 pooled keep-alive TLS sockets for ~26s (all born in the first
1.75s, then idle in the agent's free-socket pool) against the gate's 30s budget — a 2.3s margin on
an always-cold CI runner. Different resource and creation site from the hang, so per the plan it was
filed rather than folded into the fix.

## Deviations from plan

1. **Step 1.3 (`sample` the hung process) was not run.** The diagnostic report had already named a
   referenced libuv timer, which fully explains non-exit, and the process was demonstrably
   responsive throughout — so there was no blocked native thread to sample. Recorded in FINDING.md
   as falsified-with-reason rather than skipped silently.
2. **Task 1's verify needed the HOLDER line to not be a Markdown heading.** The verify pipes through
   `grep -v '^#'`, so a `## HOLDER:` heading would have been stripped and counted 0. Written as a
   bold line instead.
3. **Task 3's commit used `git commit --only`.** A concurrent session staged its own work
   (`STATE.md`, a `260913-9qk` summary, an unrelated todo rename) into the shared index mid-task; a
   plain `git commit` would have swept it in (threat T-901-04). `--only` scoped the commit to three
   explicit paths and left the neighbour's entries untouched.
4. **The neighbour's commit `f9712e8af` absorbed my staged `git mv`** of the todo into `completed/`
   (visible there as `R100`) before I could commit it. The on-disk result is correct — the todo is
   in `completed/` and my content rewrite landed in `f0b9825cd` — but the rename is attributed to
   their commit. Disclosed rather than rewritten.
5. **Step 1.1 could not observe CI hitting this.** All ten recent `test.yml` runs are `success` on
   unrelated branches; none exercises this branch. Recorded and moved on, as the plan allowed.
