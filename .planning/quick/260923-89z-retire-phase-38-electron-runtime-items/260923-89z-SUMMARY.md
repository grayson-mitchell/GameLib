## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 — blocking issue] Edit tool clobbered direct-disk Python edits when interleaved**
- **Found during:** Task 1, first attempt at editing `38-VERIFICATION.md`
- **Issue:** The plan's YAML surgery (moving 9 large multi-line frontmatter entries) is too
  large and unicode-sensitive to hand-retype reliably, so it was done with a Python script
  writing directly to disk. Three subsequent Edit-tool calls (score line, `38-S16` pair_note,
  `38-C08` scope_note) each appeared to succeed individually, but after all three, the file had
  reverted to its pre-script (390-line) state for the entries-move while somehow retaining the
  Edit-tool changes -- i.e. the Edit tool was operating on a stale in-memory snapshot captured
  at the conversation's initial `Read` (before the Python script ran), overwriting the disk
  script's array-move on its first write.
- **Fix:** Re-derived the current on-disk state fresh, then performed ALL remaining edits
  (entries-move, score line, `38-S16` pair_note, `38-C08` scope_note) via Python scripts that
  read fresh from disk immediately before writing, verified exclusively via `Bash`/`grep`
  afterward, and avoided the `Edit` tool entirely for `38-VERIFICATION.md` and `34.13-UAT.md`
  for the remainder of the task. `ROADMAP.md` and `38-HUMAN-UAT.md` used `Edit` safely because
  each was edited exactly once, immediately after a fresh `Read`, with no intervening direct-disk
  write.
- **Files modified:** `.planning/phases/38-deferred-hardware-and-environment-uat-gates-windows-linux-ma/38-VERIFICATION.md`
- **Verification:** Re-ran the plan's Task 1 automated verify command after the fix; it passed.
  Confirmed via `gsd-sdk query audit-uat` that the final on-disk state produces the expected
  34→25 / 59→50 delta.
- **Committed in:** `d75429d15`
