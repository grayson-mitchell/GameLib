# Quick Task 260808-gl6 — Closing the Humble sign-in window must not surface an error

## Problem

Signing in to Humble Bundle and then closing the native sign-in window renders the generic
failure panel:

> Something went wrong while signing in: the Humble sign-in window closed or could not be reached

Deliberately closing the window is a **cancel**, not a failure. It should return to the standard
Manage Accounts page (`/login`) with no error surface.

## Root cause

`src/backend/humble/user.ts` `watchForLogin()` consumes the Rust `WindowEvent::Destroyed`-sourced
`{ event: 'closed' }` nav event and settles `{ status: 'error' }` (added by the F-34.4.2-19 fix).
That lumps a deliberate user close in with genuine failures — the UNDECIDABLE and
UNSUPPORTED_OR_ERROR cookie-read verdicts, which settle the same status. `LoginResult` has no
status that means "the user backed out", so the frontend
(`src/frontend/screens/WebView/index.tsx` `runHumbleLoginWatch`) can only render the error panel.

## Approach

Give the user-close outcome its own status rather than widening the meaning of `'error'` — the
genuine-failure surface (Retry button, error copy) must stay reachable for the two cookie-read
verdicts that still settle `'error'`.

## Tasks

### T1 — Backend: distinct `'cancelled'` status for a user-closed window

**Files:** `src/backend/humble/user.ts`, `src/common/types/ipc.ts`

- Add `'cancelled'` to `LoginResult['status']` (user.ts) and to the `humbleStartLogin` /
  `humbleReconnect` return types (ipc.ts).
- The `'closed'` nav-event branch settles `{ status: 'cancelled' }` instead of `{ status: 'error' }`.
- Downgrade its `logWarning` to `logInfo` — a user closing a window is not a warning condition.
- `settle()` needs no change: its one-shot guard + floated `seam.close()` already run identically
  on every exit path, so the self-triggered `'closed'` event stays a no-op as before.
- `humbleLoginFlowRegistration.ts`'s handlers pass the result through untouched — no change.

**Verify:** `LoginResult` and both ipc signatures carry `'cancelled'`; the `'closed'` branch
settles `'cancelled'`; both `settle({ status: 'error' })` calls for the UNDECIDABLE and
UNSUPPORTED_OR_ERROR verdicts are unchanged.

### T2 — Frontend: navigate back to Manage Accounts silently

**File:** `src/frontend/screens/WebView/index.tsx`

- Add a `result.status === 'cancelled'` branch to `runHumbleLoginWatch()` that logs the outcome and
  calls `navigate('/login')` without touching `humbleLoginState` — so no error/timeout panel ever
  renders for a deliberate close.
- Order it before the `'error'` branch. The `'error'` and `'waiting'` branches stay as-is.
- `TauriLoginPanel.tsx` needs no change — the `'cancelled'` outcome never reaches it (the route
  navigates away), and its generic error/timeout branches stay reachable for real failures.
- No new i18n keys (nothing new is rendered), so the blocking localisation gate is unaffected.

**Verify:** the watch's `'cancelled'` branch calls `navigate('/login')` and sets no error state.

### T3 — Tests

**Files:** `src/backend/humble/__tests__/user.test.ts`,
`src/frontend/screens/WebView/__tests__/HumbleLoginWatchErrorHandling.test.ts`

- Update the `{ event: 'closed' }` test to expect `{ status: 'cancelled' }` and the `logInfo`
  liveness line, keeping its two existing structural assertions (no cookie read was needed; the
  watch is fully torn down).
- Add a source-text gate asserting `runHumbleLoginWatch` handles `'cancelled'` by navigating to
  `/login` and never by setting `phase: 'error'`, with an anti-vacuity self-test matching the
  file's existing convention.
- `TauriLoginPanel.test.tsx` needs no change — the error/timeout render contract is untouched.

**Verify:** `pnpm jest src/backend/humble/__tests__/user.test.ts src/frontend/screens/WebView`
passes; full `test:ci` shows no new failures.

## must_haves

- Closing the Humble sign-in window returns to `/login` with no error panel.
- A genuine watch failure (UNDECIDABLE / UNSUPPORTED_OR_ERROR cookie read) still renders the
  error panel with its Retry button.
- The WR-03 ten-minute deadline still renders the timeout panel.
