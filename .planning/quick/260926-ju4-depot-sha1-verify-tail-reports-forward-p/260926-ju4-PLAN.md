<objective>
Close `.planning/todos/pending/2026-09-26-depot-stall-bound-can-over-fire-on-a-long-sha1-verify-tail.md`.

`StallTracker`'s 180s no-progress clock is reset at exactly two sites today: `downloadFileChunks`'
`await fd.write(...)` (`depot.ts:1423`) and the worker loop's successful `downloadSingleFile` return
(`depot.ts:2718`). `downloadSingleFile`'s post-chunk verify tail — a whole-file `sha1File(dest)`
re-read, then `applyEDepotFileModes`, then `applyMachOExecutableFallback` (`:1653-1690`) — sits
between those two and reports nothing. Thirty-two concurrent whole-file SHA1 re-reads of multi-GB
paks on a slow external disk can exceed the 180s window, and since `62f916e58` made `hasStalled()`
terminal at the worker-loop top, a healthy run can be killed by it.

Fix: give `sha1File` an optional progress callback and have the depot call site feed it into
`stallTracker.recordProgress()`, so the verify read counts as the work it is.
Output: one new optional parameter, one call site, two regression tests, todo closed.
</objective>

<measured_findings>
Measured on the unmodified tree at plan time. These shape the test and are not restated from the
todo — two of them CORRECT it.

**1. The whole Backend jest project is green at baseline.** `npx jest --selectProjects Backend` —
221 suites, 5065 passed, 3 skipped, 0 failed.

**2. `reconcile.ts`'s `sha1File` call is OUT OF SCOPE by construction, not by choice.**
`reconcilePartialState` runs at `depot.ts:2187`; the `StallTracker` is constructed at `:2280`. The
reconciler's whole-file SHA1 pass therefore completes before the clock exists, so it cannot arm this
defect and needs no progress reporting. `reconcile.ts:144` keeps calling `sha1File(dest)` with one
argument — which is why the new parameter must be OPTIONAL, not required.

**3. The todo's framing of the trigger is imprecise, and the imprecision changes what a test can
honestly assert.** The todo says "if every worker is simultaneously inside one file's post-chunk
verify tail for longer than `STALL_TIMEOUT_MS`, the run is still misread as stalled and killed."
Traced against the code, the worker loop is:

```
while (queue.length) { hasStalled()? → job → downloadSingleFile(...) → recordProgress() }
```

The success-path `recordProgress()` at `:2718` is the last statement before the loop returns to its
own `hasStalled()` consult, with no await in between. So a worker that SUCCEEDS can never read a
stale clock left by its own tail, and no other worker is at the loop top during that window without
having just recorded progress itself. **On an all-success run the residual is unreachable at the
worker-loop consult.** It is reachable at exactly two consults:

  - `depot.ts:2610` reached via the per-file **catch** — `downloadSingleFile` threw (the sha1
    mismatch at `:1660`, or a mode failure at `:1682`), so no `recordProgress()` ran, and the
    clock is stale by the whole length of the tail that preceded the throw. Consequence: one
    genuine per-file failure is escalated into a **run-level stall that abandons the rest of the
    queue**.
  - `depot.ts:1462`, `downloadFileChunks`' per-chunk catch, consulted by a DIFFERENT worker while
    this one is mid-tail. Consequence: one transient chunk error fails a whole file — precisely
    what `StallTracker` was introduced to prevent.

Both are closed by the same fix. Task 2 pins the first, because it is deterministic within a single
worker; the second needs a cross-worker interleaving that would be a racy test.

**4. `jest.spyOn(fs, 'createReadStream')` does NOT work here — `jest.mock('node:fs', …)` does.**
Probed both. `spyOn` throws `TypeError: Cannot redefine property: createReadStream` (Node's `fs`
exports are non-configurable). A partial module mock —
`{ ...jest.requireActual('node:fs'), createReadStream: jest.fn() }` — intercepts `depot.ts`'s call
successfully; a 300 KB file produced **5** `data` events through the wrapper (64 KB `highWaterMark`),
digest unchanged. This is the injection point the test needs: it is the only way to make virtual
time advance as a function of the verify read itself.

**5. Why the existing W-1 test's clock trick is NOT reusable here.** That test advances a virtual
clock one tick per `hasStalled()` consult. That cannot express this defect: the thing that must
advance time is the tail, and the tail makes no consults. A clock driven by `recordProgress()`
would be circular (it is the signal under test), and one driven by consults alone leaves both arms
identical. Hence finding 4.
</measured_findings>

files complete: no chunk ever landed, so `downloadSingleFile` never reached its post-chunk tail and
`sha1File` never ran. The new progress signal is therefore unreachable on that failure path by
construction. Keep it that way — report progress only from bytes actually read off disk, never from
entering the tail, never from a timer.

It is a separate shape decision about the `failures` array and stays open. In particular, do not
change what is pushed into `failures` or how `failures.length` is read.

**Do NOT add progress reporting to `reconcile.ts`** (finding 2) or to `applyEDepotFileModes` /

steps are bounded per file and adding signals there would be unmeasured scope.

**Do NOT throttle the callback.** Per 64 KB read it is one `Date.now()` and one field assignment,
against a SHA1 of the same 64 KB. A throttle would be untested complexity in the exact path whose
silence caused the defect.
</scope_boundaries>

Two edits in `src/backend/storeManagers/steam/depot.ts`, plus one comment correction.

**1a — `sha1File` (`:1136`).** Add a second, optional parameter `onProgress?: (bytesRead: number) => void`
and call it from the existing `'data'` handler AFTER `hash.update(chunk)`. The digest path must be
byte-for-byte unchanged; the callback is a pure side-channel.

Extend the existing doc comment to say why the parameter exists: the whole-file re-read is the
dominant cost of `downloadSingleFile`'s post-chunk tail, it can run for minutes on a multi-GB pak,
and the caller needs to be able to prove that read is live work rather than a wedged run. Name the
optionality as load-bearing, with the reason: `depot/reconcile.ts:144` calls this with one argument
and runs BEFORE the run's `StallTracker` is constructed (`:2187` vs `:2280`), so it neither needs
nor can use the signal.

**1b — the call site (`:1659`).** Change

```ts
const got = await sha1File(dest)
```

to pass `() => stallTracker?.recordProgress()`.

Comment it with the mechanism and the safety argument, in the register of the surrounding comments:
this is the THIRD forward-progress signal after `downloadFileChunks`' `fd.write` (`:1423`) and the
worker loop's successful return (`:2718`), and it is the one that covers the gap BETWEEN them. State
the non-weakening argument explicitly: reaching this line requires every one of the file's chunks to
have already landed, so on a run where nothing downloads (the 2026-08-27 Californium case the bound
exists for) it is unreachable.

**1c — retire the "residual, named not fixed" paragraph (`:2593-2602`).** That comment currently
ends with "Closing that needs progress reporting from inside sha1File, which is a larger change than
this fix is entitled to make." Rewrite that sentence to record that it IS now closed, by the
`sha1File` progress callback at `:1659`, and keep the surrounding explanation of why the clock has to
be able to see verify work. Do not delete the paragraph — its explanation is what makes the third
signal legible.

Also correct the in-situ claim, in the same edit, that a healthy run could be killed at THIS consult:
per measured finding 3 the success path records progress immediately before the consult, so the
reachable consults are the per-file catch below and `downloadFileChunks`' per-chunk guard at `:1462`.
Say that plainly rather than leaving the stronger, unmeasured claim in place.
