## The rule (both sides, word for word in each doc comment)

Sentence: **an absolute expiry is kept only when its written date is a real calendar date with year, month and day
all present and a four-digit year from 1000 to 9999, and the parser read that same date: the parsed instant is within
one day of the written date's UTC midnight.**

Steps, run on the raw `value` (untrimmed, as the parse gate saw it) and the parsed time value in ms:

1. Walk the maximal ASCII digit runs (global `[0-9]+`) in order. The first run whose next character is `:` starts the
   time of day. That run and everything from its start onward are not read (the "cut"). The runs before it are the
   date numbers, kept as strings.
2. The month word is the LAST maximal ASCII letter run (global `[A-Za-z]+`) that starts before the cut and whose first
   three letters, lower-cased, are one of `jan feb mar apr may jun jul aug sep oct nov dec`. This is V8's month-name
   rule: a longer word matches on its prefix (`February`, `Sept`), and day names, `T`, `Z`, `GMT` and `UTC` never match.
3. `small(run)`: drop leading `0`s. If at most two digits remain, the value is their number (an all-zero run is 0).
   Otherwise there is no value, so it is never a day or a month. A run is day-like when `small(run)` is 1..31.
4. With a month word, at least two date numbers are needed. If the first is day-like, it is the day and the second is
   the year; otherwise the first is the year and the second the day. Without a month word, at least three are needed.
   If the first is day-like they are month, day, year; otherwise year, month, day. Fewer numbers means reject. (This
   mirrors V8's DayComposer: `js_date.rs` `DayComposer::write`.)
5. Keep only when all of these hold:
   - The year run is exactly four characters and does not start with `0`.
   - `small(month)` is 1..12.
   - `small(day)` is 1..days-in-month: 31, except 30 for months 4, 6, 9 and 11, and February is 29 when the year is
     divisible by 4 and (not by 100, or by 400), else 28.
   - `|utcDay(year, month, day) - floor(parsedMs / 86_400_000)| <= 1`, where `utcDay` is the day number of the
     written date's UTC midnight. In TS that is `Date.UTC(year, month - 1, day) / 86_400_000`. In Rust it is
     `local_midnight(year, month - 1, day, LocalZone::UTC)` then `div_euclid(86_400_000)` (a `None` there means
     reject). Use `div_euclid` on the parsed ms and `Math.floor` in TS so pre-1970 instants agree.

Why the fifth step's last check exists: steps 1-4 read the written text, while V8 decides on its own which number is
which. On contrived strings the two readings can differ: a zone offset written before the year (`Feb 28 GMT+2026`, which
V8 reads as 2001), or a month word in a parenthesised comment V8 skips (`Feb 30 2026 (Mar)`, read as Mar 2). The
one-day check rejects those, so a kept value is never far from the date written. Any real zone offset (under 24 h)
plus a time of day moves the UTC date by at most one day, so no legitimate value is lost.

Linear time is part of the rule. Walk the runs with a global regex `exec`/`matchAll` loop (TS) and `find_iter`
(Rust), and test the character after each run. Never search with a pattern like a digit run followed by a colon: in
JavaScript that backtracks across every start of a long digit run and goes quadratic. The 200,000-zero row exists to
catch that.
