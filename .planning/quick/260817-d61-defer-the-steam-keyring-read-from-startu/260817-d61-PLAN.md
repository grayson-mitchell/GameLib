<objective>
Move the Steam refresh-token keyring read off the app-startup path so the macOS Keychain
prompt arrives immediately after a deliberate Steam action instead of unattended during
bootstrap, and annotate every `keyring_get` issue site with what triggered it and how it
ended so the 9:1 read-failure ratio can be re-measured on real hardware.

Purpose: the observed failure ratio (7 timeouts + 2 Deny vs 1 success on the real
`steam-refresh-token` slot) is HYPOTHESISED to be caused by a context-free prompt fired during
bootstrap. Quick task `260814-r2d` made a failed read honest; it deliberately did not change
*when* the read happens. This task changes when — and ships the instrumentation that makes
shipping the fix also a test of the hypothesis.

Output: a single deferral gate module, a trigger-annotated read seam, and structural tests
that prove the startup path issues zero keyring reads while the deliberate path still issues
exactly one.
</objective>

<design>
## The seam (Claude's-discretion decisions, recorded)

**Gate location: the top of `SteamLibraryManager.refresh()`, before the `steamSyncStatus`
emit.** Chosen over a guard in the IPC handler because `init()`'s `runOnceWhenOnline` path
(startup path B above) never goes through an IPC handler at all — a handler-only guard would
leave that path reading the keyring at bootstrap and the fix would be silently half-done.
Chosen over gating inside `ensureConnected()` because install/play/depot already call
`ensureConnected()` directly and MUST keep working; gating there would break them.

**Unlock is sticky and process-scoped.** Once any deliberate Steam action has occurred, later
automatic refreshes proceed normally. A non-sticky gate would permanently disable background
sync, which is a worse bug than the one being fixed.

**Deliberate origins are an ALLOWLIST, never a denylist.** A denylist would silently classify
any newly-added automatic origin as deliberate — reintroducing this defect with no code change.
`'mount'`, `'push'`, absent and unrecognised all map to `'startup'`.

**Trigger threading: an optional `context` argument on the read seam,** not a module-level
global read by `keyringTokenStore.ts`. That module is shared with Humble; importing a Steam
module into it to fetch a trigger would couple two unrelated slots. An optional argument keeps
the store slot-agnostic (Humble's calls simply log `trigger=unspecified`).

**No new IPC channel.** The `refreshLibrary` handler gains an optional SECOND argument. The
existing first argument's shape — including the documented Tauri `undefined -> null`
JSON-transport hazard at steamFlowRegistration.ts:133-148 — is left byte-identical.

## Honest limitation, recorded rather than omitted

Opening a Steam game page unlocks the gate AND fires a fire-and-forget
`SteamUser.ensureConnected()` so the read genuinely happens at page-open (per the locked
decision). That call is bounded by `ensureConnected`'s own existing timeouts and fires ONLY on
the locked->unlocked transition, never on every page open. If it fails, page render is
unaffected — the catch swallows it and the next deliberate action retries.

## What this plan does NOT claim

Nothing here proves the prompt moved, that the prompt is now approved more often, or that the
9:1 ratio improved. `GAMELIB_DEV_SECRET_VAULT=1` bypasses the Keychain, so the defect does not
reproduce in a dev loop, and jest cannot observe a macOS Keychain prompt at all. Every
verification below is STRUCTURAL. The behavioural measurement is a deferred operator session
(Phase 34.5 ledger rows `U-34.5-01` / `U-34.5-10`, plan `34.5-58`) reading the log lines this
plan emits. **A green suite is NOT a behavioural pass and must not be reported as one in the
SUMMARY.**
