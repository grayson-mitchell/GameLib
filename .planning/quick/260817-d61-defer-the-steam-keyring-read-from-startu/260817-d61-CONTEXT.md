# Quick Task 260817-d61: Defer the Steam keyring read from startup to first Steam user action - Context

**Gathered:** 2026-08-17
**Status:** Ready for planning

<domain>
## Task Boundary

Move the Steam refresh-token keyring read off the app-startup path so the macOS Keychain
prompt arrives immediately after a deliberate Steam action instead of unattended during
bootstrap. Add instrumentation so the prompt-timing hypothesis can be re-measured against
its 9:1 baseline.

Source todo: `.planning/todos/pending/keyring-read-lazy-at-point-of-use.md`
(area: auth, severity: minor, needs: design-then-code-fix)

</domain>

<traced_call_chain>
## Confirmed prompt source (traced 2026-08-17, before planning)

```
GlobalState (renderer, mount)
  -> window.api.refreshLibrary(...)
  -> main.ts:1047  addHandler('refreshLibrary')
  -> SteamLibraryManager.refresh()          src/backend/storeManagers/steam/library.ts:674
  -> SteamUser.ensureConnected()            library.ts:685
  -> readTokenOutcome(getTokenStore())      src/backend/storeManagers/steam/user.ts:177
  -> SidecarKeyringSlotStore.getToken()     src/backend/sidecar/keyringTokenStore.ts:231
  -> keyring_get                            (Rust; issues the macOS Keychain prompt)
```

Second read path through the same seam: `SteamUser.getCredentials()` (`user.ts:317`) —
also `readTokenOutcome(getTokenStore())`. Both must keep routing through the one seam;
do NOT reintroduce a divergent read path.

**`SteamLibraryManager.init()` (`library.ts:514`) already hydrates the library from
`steamLibraryStore` cache and pushes each game to the frontend before any network or
keyring work.** This is why deferring the refresh does not leave the Steam library empty
at startup — the cached list still renders. `init()` itself does NOT call
`ensureConnected()`; it must stay that way.

</traced_call_chain>

<decisions>
## Implementation Decisions

### Deferral trigger — LOCKED

Skip the Steam leg of the startup library refresh. The keyring read fires on the first
deliberate Steam user action: opening a Steam game page, Install, Play, or an explicit
Refresh. The Keychain prompt then arrives with obvious in-app context.

Rejected alternatives (do not revisit):
- In-app consent gate at startup — keeps the read on the bootstrap path.
- Defer AND add a dedicated reconnect affordance — larger than one quick task.

### Measurement — LOCKED

Ship the deferral WITH instrumentation. Every `keyring_get` issue site must log what
triggered it and the outcome, so the observed 9:1 failure ratio can be re-measured on real
hardware after this change. The todo is explicit that prompt timing is a **hypothesis, not
a diagnosis** — the instrumentation is what makes shipping the fix also a test of it.

Target log shape (illustrative, not literal):

```
[Steam] keyring_get issued trigger=user-install appId=1091500
[Steam] keyring_get ok present=true len=497 elapsed=1204ms
```

`trigger=` must distinguish at minimum: startup (should become absent/rare), user-initiated
library refresh, game-page open, install, play. Never log token material — length only,
matching the existing `present=/len=` convention at `keyringTokenStore.ts:346`.

### Claude's Discretion

- Exact seam for the skip (a scope/origin parameter on `refresh()`, a guard in the
  `refreshLibrary` handler, or a lazy flag on the manager) — pick whichever is least
  invasive and keeps the single read path intact.
- How `trigger` is threaded to the log site.
- Whether the deferred state needs any frontend signal. Note `refresh()` emits
  `steamSyncStatus` as its first statement (`library.ts:682`); a skipped refresh must not
  strand the UI in `syncing`. Reuse the existing tri-state rather than inventing a status.

</decisions>

<constraints>
## Hard constraints — carried from the todo, all MUST hold

1. **Raising `KEYRING_READ_TIMEOUT` is NOT the fix.** Already raised to 45s
   (`src-tauri/src/main.rs`); 7 of the 9 observed timeouts postdate that change. Do not
   touch it.
2. **The 120s failure memo must keep working.** `KEYRING_FAILURE_MEMO_MS`
   (`keyringTokenStore.ts:59`) must keep suppressing the second Keychain prompt — this is
   `F-34.5-G6-06`. A memo hit must continue to issue **zero** `keyring_get`. New logging
   must not perturb the memo, the success cache, or the in-flight dedupe.
3. **No env-var / in-memory / plaintext fallback** (D-08 / `REQ-28-07`). An unreadable read
   fails closed.
4. **`keyringTokenStore.ts` must keep importing no `configStore` / `TOKEN_STORE_KEY`**
   (`REQ-28-02`).
5. Preserve the three-valued `readTokenOutcome` contract (`present` / `absent` /
   `unreadable`) and quick-260814-r2d's honesty fix: an `unreadable` read must never be
   reported as `absent`, must never clear the session, and must never destroy a token.

</constraints>

<specifics>
## Specific Ideas

- `GAMELIB_DEV_SECRET_VAULT=1` bypasses the Keychain entirely, so this defect does NOT
  reproduce in a normal dev loop. Jest cannot observe the prompt at all. Verification is
  therefore structural (call-graph assertions: startup path issues no `keyring_get`) plus a
  deferred operator session on real hardware — do not claim a behavioural pass from a green
  suite.
- Phase 34.5 ledger rows `U-34.5-01` / `U-34.5-10` and plan `34.5-58` already prescribe the
  operator session that would measure prompt behaviour. This task's instrumentation should
  produce the log lines that session reads.

</specifics>
