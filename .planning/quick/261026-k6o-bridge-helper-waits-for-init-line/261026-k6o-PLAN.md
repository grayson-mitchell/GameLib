<objective>
Fix 51-REVIEW WR-02 (todo `.planning/todos/pending/2026-10-25-bridge-helper-inits-steam-before-accept-loop.md`).
The native bridge helper is single-threaded. It runs write steam_appid.txt, then bind/listen, then logs `LISTEN`, then does dlopen + `SteamAPI_InitFlat`, and only then enters the accept loop. A connection made before `accept()` sits in the kernel backlog with no answer. So when a cold init is slow, the backend's ~3 s HEALTH/WHOAMI budget (POLL_ATTEMPTS 6 × (POLL_INTERVAL_MS 250 + PROBE_TIMEOUT_MS 250)) runs out and the helper is reported `unreachable`.

Fix (locked decision): the backend waits for the helper's terminal init signal on stderr before it starts the HEALTH/WHOAMI poll. No threading, no wire-protocol change, and HEALTH/WHOAMI behave exactly as before.

Planner's choice, which the locked decision allows: the helper emits ONE dedicated marker line, `READY  init=ok|failed|dylib-missing appid=<id>`, immediately before `for (;;) accept`. The backend parses that line instead of the three human-prose `INIT` messages. Reasons:
(a) The prose varies: `InitFlat failed r=... err=...`, `SteamAPI ready (...)`, `dylib-missing -- ...`.
(b) A non-terminal `INIT manual dispatch ready/unavailable` line comes before the success line. A regex over the INIT prose would have to tell the two apart.
(c) The READY line is printed at exactly one source location, and only the accept loop runs after it. It therefore marks the real precondition ("now serving") rather than standing in for it.
The C change is three lines in main().

Output: the helper emits READY, the backend waits for it, the unit tests cover the new wait, the false docs are corrected, and the native helper is rebuilt. The live slow-init gate is left pending for the human.
</objective>

Every FATAL exit in main() happens before LISTEN. load_steam_api() may log `FATAL` (dlopen/dlsym) and return 0. That FATAL is followed by the dylib-missing INIT line, and the process does not exit.
