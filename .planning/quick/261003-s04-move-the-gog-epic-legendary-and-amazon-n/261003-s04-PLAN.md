<decisions>

**D-1 — one component, parameterised by runner; no `renderState` render-prop split.**
`src/frontend/screens/Login/components/HumbleLogin/index.tsx` needs a `renderState` callback
because the component that owns the login watch (`HumbleLoginSurface`) lives in `WebView/` and
is ALSO used by the `/loginweb/humble` route — hoisting its conditional into the host would
remount the surface on every phase change and restart the watch. That constraint does not
exist here: the new `OAuthLogin` owns the hook and the phase conditional in the same component,
so React keeps the hook state across every render regardless of what the component returns.
One component, three runner ids. Do not invent a second file to mirror Humble's split.

**D-2 — the two hook callbacks MUST be identity-stable, and the stabilisation lives in the new
component.** `useTauriOAuthLogin`'s effect dependency array is
`[runner, onLoginSuccess, onCancelled]`. `dismissLoginOverlay` in `src/frontend/screens/Login/index.tsx`
is a plain `function` declaration in the component body, so it gets a fresh identity on every
render of `NewLogin` — and `NewLogin` does re-render while an overlay is open (its tile-state
`useEffect` lists `openOverlay` among its dependencies). Passing `dismiss` straight into the
hook would therefore re-run the capture effect mid-login, which opens a SECOND native sign-in
window and discards a single-use OAuth code. `HumbleLoginSurface` is immune only because its
own effect has an empty dependency array; nothing protects this hook.

Stabilise inside `OAuthLogin` (a ref updated by an effect, read from empty-dependency
`useCallback`s) rather than by converting `dismissLoginOverlay` to `useCallback` in the host.
Two reasons: the protection then travels with the component that actually consumes the hook,
and `src/frontend/screens/Login/index.tsx` is a heavily source-gated file whose diff should
stay minimal.

**D-3 — phase split. The rule is "is a native window on screen?", not "is the phase terminal?".**
OPERATOR-DECIDED, 2026-10-03, superseding this plan's first draft (which rendered nothing for
`preparing` and `finalizing` and carried that as an open live-gate question):

| phase | surface |
|---|---|
| `idle`, `awaiting` | render NOTHING — the native sign-in window is on screen and on top. This is exactly the justification commit `bede817fd` recorded for Humble: an in-app panel behind a native window is noise, it opens *underneath* that window, and it flashes back for `Dialog`'s own 500ms Slide exit on teardown. |
| `preparing`, `finalizing` | render the `Dialog` — NO window is on screen and the wait is long. |
| `blocked`, `error`, `timeout` | render the `Dialog`. |
| `cancelled` | `dismiss` — no branch needed; the hook already invokes `onCancelled`. |

The discriminator is window presence, and it is the whole reason the first draft was wrong:
"terminal vs non-terminal" put `preparing` and `finalizing` in the silent set even though neither
has a window to defer to. `preparing` is nile-only and covers a measured ~12.8s `nile auth`
subprocess spawn BEFORE any window exists — quick task 260806-teb exists precisely because the
old copy claimed a window had opened during that wait. `finalizing` covers a 5-27s token exchange
AFTER the window closed (quick task 260803-eee). `TauriLoginPanel` already owns honest copy and a
spinner for both; this split is what lets that copy reach a user on this surface.

`blocked` earns its place even though all four OAuth channels were ported in Phase 34.5 and the
hook's own module doc calls that branch legacy defensive code: if it ever fires, it means a
capture succeeded against an unported channel, and the user needs told.

CONSEQUENCE TO EXPECT, not a defect: for `nile` the Dialog now mounts, unmounts and mounts again
within one overlay lifetime (`preparing` -> `awaiting` -> `finalizing`). `legendary` and `gog`
never observe `preparing` at all (their login URLs are constants, so they reach `awaiting`
synchronously), so they get exactly one `finalizing` mount. Neither sequence flashes in practice —
both panels are on screen for seconds, far longer than the 500ms slide — but each `Dialog` mount
also fires `window.api.gamepadAction({ action: 'tab' })` twice from its own mount effect (a focus
nudge, `Dialog.tsx`), so a nile sign-in now triggers that nudge twice rather than once. Harmless
while a native window holds focus; named here so it is not discovered as a mystery, and checked
at the live gate (Q5, Q5a).
