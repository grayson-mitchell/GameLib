<objective>
Give every bridge-routed Steam game its own CrossOver bottle, `GameLibSteamBridge-<appId>`, Proton-style, instead of the single shared `GameLibSteamBridge`. This closes `.planning/todos/pending/2026-10-16-bridge-games-should-each-get-their-own-bottle.md`. The operator decision is locked: one bottle per bridge game.

Purpose: the operator expected per-game bottles from Phase 24 onward. No D-number ever recorded the shared bottle; it came from a "share as much as possible" research note. Per-game bottles let CrossOver be tuned for one game without affecting the other. They are cheap: a bridge bottle holds no Windows Steam client, so a new one costs no second login and no Steam self-update.

Output: four new bottle.ts functions and one changed signature. Every caller is routed through a single resolver. The installed-state scan now covers every bridge bottle. Uninstalling a per-game install deletes that bottle. Tests cover the new behaviour in all seven affected suites.

Decisions implemented (orchestrator-locked for this task):
- D-A: the per-game name is `GameLibSteamBridge-<appId>`, built by one pure numeric-guarded helper, `bridgeBottleNameFor(appId)`.
- D-B: legacy compatibility with NO migration. A game resolves to its per-game bottle. If that bottle is not ready AND the legacy `GameLibSteamBridge` bottle holds `steamapps/appmanifest_<appId>.acf`, it resolves to the legacy bottle. New installs always provision a per-game bottle. This rule lives in ONE function, `resolveBridgeBottleName(appId)`, and every call site uses it.
- D-C: `buildBridgeInstalledMap()` scans every ready bridge bottle (the legacy one plus every `GameLibSteamBridge-*` under the CrossOver Bottles dir). It is gated on any of them being ready, not on the legacy one alone.
- D-D: uninstalling a game that lives in a per-game bottle removes that bottle directory. The guard matches only the per-game name for that exact appId: never the legacy shared bottle, never the Phase 17 `GameLibSteam` bottle. Uninstall from the legacy bottle keeps today's behaviour.
- D-E: `getBridgeBottleSettings` takes an appId. Every remaining zero-argument call is routed through the resolver. No allowlisted game can reach the shared bottle by any path except D-B.

Scope locks (non-negotiable):
- LD-1 No migration (D-B). Nothing is moved or copied out of `GameLibSteamBridge`, and the legacy bottle is never deleted.
- LD-2 No change to the native bridge helper (`bridge/helperProcess.ts`, `native/steam-bridge/**`). It is one shared host process on loopback TCP and does not know about bottles. Wine shares the host network namespace, so every bottle reaches it at `127.0.0.1`.
- LD-3 No change under `src/frontend/**` or `src-tauri/**`.
- LD-4 Uninstall from the legacy bottle keeps the exact same behaviour (D-D), including leaving its `appmanifest_<appId>.acf` where it is.
- LD-5 `library.ts` `removeSteamInstallCopy` / `enumerateSteamInstallCopies` and `removeAllCopies.ts` are not edited. They reach the right bottle through `readAcfState(appId, 'bridge')`, which becomes per-app in Task 1.
- LD-6 No new runtime dependency. No new spawn site that carries an `env` literal; the only new spawns go through the existing `killBottleWineServer` and an env-less `spawnAsync(CXBOTTLE_BIN, …)`.
- LD-7 Do NOT write `.planning/STATE.md`, and do not move the todo file. The orchestrator owns both.
