# Quick 260925-bq4: make i18next resolve plurals for the underscore-named locale codes

`Intl.PluralRules('nb_NO')` throws `RangeError: Invalid language tag`. i18next 22.5.1's
`PluralResolver.getRule` passes the code in raw and swallows the throw:

```js
return new Intl.PluralRules(code, { type: ... })   // node_modules/i18next/dist/cjs/i18next.js
} catch (_unused) { return; }
```

(the `_` -> `-` cleaning i18next added as `getCleanedCode` only exists from v23). No rule ->
`getSuffix` returns `''` -> the lookup is the **unsuffixed** key -> that key exists in no catalog,
only `_one`/`_other` do -> `resolve()` walks on to `fallbackLng: 'en'` and recomputes the suffix
*for `en`*, which hits. So this is not a missing-plural bug, it is a **silent English fallback**
for every counted string in `nb_NO`, `pt_BR`, `zh_Hans`, `zh_Hant`.

Measured against real i18next + the real catalogs, `t('humbleKeys.cooldown', { count: 5 })`:

| `lng`     | rule resolves | suffix    | result                                |
| --------- | ------------- | --------- | ------------------------------------- |
| `en`      | yes           | `_other`  | "...retry in 5 minutes"               |
| `nl`      | yes           | `_other`  | "...probeer opnieuw over 5 minuten"   |
| `pt`      | yes           | `_other`  | "...tente novamente em 5 minutos"     |
| `nb_NO`   | **no**        | `""`      | **English**                           |
| `pt_BR`   | **no**        | `""`      | **English**                           |
| `zh_Hans` | **no**        | `""`      | **English**                           |
| `zh_Hant` | **no**        | `""`      | **English**                           |

Arrived with `ddd2b8ed0` (machine-fill emitting CLDR plural forms). 8 plural key families x 4
locales today, and it grows with every new plural key.

## Approach: normalise at the i18next boundary, keep the directory names

The `public/locales/nb_NO` directory names stay. They are the on-disk layout in two trees, they
are the persisted `configStore` `language` value, and they key `languageLabels`/`languageFlags`
in `LanguageSelector`. Renaming them needs a config migration and touches four `meta/` locale
tools (`pruneUnofferedLocales`, `assembleRendererDist`, `lintTranslations`,
`rebrandUpstreamCatalogs`). Instead, convert to BCP-47 **only** where a code crosses into
i18next, and convert back where `i18n.language` flows out.

### Three measured facts the plan rests on

1. **`supportedLngs` must be converted too, or the fix is worse than the bug.** With the
   underscore list still in `supportedLngs` and `lng: 'nb-NO'`, `toResolveHierarchy('nb-NO')`
   returns `["en"]` — the locale is filtered out entirely and *everything* goes English, not just
   plurals.
2. **With the BCP-47 list, `supportedLngs` suppresses the bare language part.**
   `toResolveHierarchy('nb-NO')` -> `["nb-NO", "en"]`. Without `supportedLngs` it would be
   `["nb-NO", "nb", "en"]` and would fetch a `locales/nb/` directory that does not exist. Both
   init sites already pass `supportedLngs` (`src/frontend/index.tsx:172`,
   `src/backend/sidecar/bootstrap.ts:1017`) — that existing option is load-bearing for this fix,
   do not remove it.
3. **The two backends' `loadPath` function signatures differ.** `i18next-http-backend` 2.7.3
   calls `loadPath(languages, namespaces)` with **arrays** (`:89-90`); `i18next-fs-backend` 2.6.0
   calls `loadPath(language, namespace)` with **scalars** (`:52-53`). Writing one shape for both
   silently yields `[object Array]` in a path.

## Tasks

1. **`src/common/languages.ts`** — leave `supportedLanguages` exactly as is (it is the directory
   name list and four `meta/` tools depend on that). Add three exports:
   - `toI18nextCode(lng)` — `_` -> `-`; the form handed to i18next.
   - `toShippedLanguage(code)` — the inverse, via an explicit map built from
     `supportedLanguages`, **not** a blind `-` -> `_` replace, so an unknown code passes through
     untouched instead of being corrupted.
   - `supportedLanguageTags` — `supportedLanguages.map(toI18nextCode)`, for `supportedLngs`.

2. **`src/frontend/index.tsx`** — `lng: toI18nextCode(languageCode)`;
   `supportedLngs: supportedLanguageTags`; `<html lang>` (`:141`) gets the BCP-47 form, since
   `lang="pt_BR"` is not a valid tag; `loadPath` (`:129`) becomes a function using the
   **array** signature, mapping the resolved code back to the directory name. Keep the
   260901-b8z comment above it.

3. **`src/backend/sidecar/bootstrap.ts`** — `lng: toI18nextCode(settings.language)`;
   `supportedLngs: supportedLanguageTags`; `loadPath` becomes a function using the **scalar**
   signature. Delete the `addPath` option (`:1008`): nothing sets `saveMissing` in this init, so
   it is dead, and after this change it would point at a directory that does not exist — exactly
   the "dead option pointing at a plausible-looking path is a trap for the next reader" case that
   quick task 260901-b8z already removed from the renderer's copy. Note the removal in place.

4. **Cover `changeLanguage`, not just init** — a runtime language switch re-breaks plurals
   otherwise:
   - `src/frontend/components/UI/LanguageSelector/index.tsx:132` —
     `i18n.changeLanguage(toI18nextCode(newLanguage))`. Lines `:129-131` and `:133` keep the
     **shipped** form (they persist to `configStore`/`localStorage` and feed `setLanguage`).
   - `src/backend/appshell/language.ts:52` — `i18next.changeLanguage(toI18nextCode(language))`.
     Line `:64` `setSetting('language', language)` keeps the shipped form. Do not normalise the
     function parameter itself; normalise only the i18next argument.

5. **Convert back where `i18n.language` flows out** — `src/frontend/state/GlobalState.tsx:483`
   `language: this.props.i18n.language` is read into app state and reaches
   `LanguageSelector`'s `currentLanguage` (`:126`), which indexes `languageLabels` /
   `languageFlags` (keyed by the underscore form, `:116-117`) and is the `<select>` value. Left
   unconverted it would silently show a raw `nb-NO` label with no option selected. Wrap in
   `toShippedLanguage(...)`.

6. **Regression test** — follow the existing `*.realI18next.test.ts` precedent
   (`src/frontend/screens/Library/components/FilterChipRow/__tests__/chipLabels.realI18next.test.ts`
   and two others). Assert, with real i18next and the real catalogs:
   - every entry in `supportedLanguages` resolves a plural rule with >= 1 category once passed
     through `toI18nextCode`;
   - a known plural key returns **non-English** text for `nb_NO`/`pt_BR`/`zh_Hans`/`zh_Hant` at
     `count: 1` and `count: 5`;
   - `toShippedLanguage(toI18nextCode(l)) === l` for every supported language.

   This is the durable half: `lint-translations` is blind to this class and no gate detects
   English drift, so nothing in the repo sees it today.
