<findings>
These were checked against the code while planning, so the executor does not need to explore again.

**How tabs route today (part 2 does NOT already work, for any tab).** `NavTabs/index.tsx` renders five MUI `<Tab component={NavLink}>`s with hard-coded `to` values: `/login`, `/`, `/store/${defaultStore}`, `/download-manager`, `/settings/general`. The lit tab is derived from the route: `resolveActiveTab(location.pathname)` in `NavShell/navTabs.ts`. `/gamepage/*` always resolves to `'games'`, whichever way you got there. Nothing remembers a per-tab location. There are two partial, unrelated mechanisms. Leave both untouched:
- `resolveDefaultStore` reads `sessionStorage.getItem('last-store')`, but nothing in `src/` writes that key. It is a dead read ported from the old sidebar.
- `WebView/useStoreEmbedHost.ts:389` persists each store embed's in-page URL to localStorage `last-url-${store}`. That is inside a store page, not tab-level.

**Game-page entry points, all found:** Library `GameCard` (`GameCard/index.tsx:442,584`, state `{ gameInfo }`); Downloads `DownloadManagerItem` (`:131`, state `{ fromDM: true, gameInfo }`); `RedeemSteamKeyDialog` "View in library" (`:105`, state `{ gameInfo }`, opened from the Stores tier-2 list); tray/deeplink `handleGoToScreen` in `NavShell/index.tsx` (state `{ fromGameCard: false }`, no `gameInfo`). Store pages do not navigate to game pages. The link goes the other way: `GameSubMenu:648` opens `/store-page?store-url=…`, which lights Stores.

**Ownership rule (the decision for this plan):** a location belongs to the tab that `resolveActiveTab` lights for it. That is the tab the user sees selected while they are there. So every game page belongs to the Games tab, including one opened from Downloads or from the Redeem dialog. No provenance-based ownership. With a provenance rule, the remembered tab could disagree with the tab that was lit, which is the orphan-state problem `navigation-shell.md` §7 rejected. A game page opened from Downloads keeps its `fromDM` state, so after a restore its Back button still goes to `/download-manager`. That is exactly where the user was.

**Crash hazard that shapes the memory format:** `GamePage/index.tsx:107` does `const { gameInfo: locationGameInfo } = location.state`, so it throws if `state` is null. A restored game page must therefore carry the original `location.state`. A game-page location whose state has no `gameInfo` (the tray/deeplink path) must NOT be remembered. Fall back to the root.

**Back button:** GamePage's Back is `<NavLink to={backRoute}>` with `backRoute = '/library'` (or `/download-manager` when `fromDM`). `/library` hits the `*` route and redirects with `replace` to `/`. That remounts `Library`, which is why part 1 needs state that outlives the component. `/library` resolves to a `null` tab, so the memory ignores it.

**Test harness:** jest, project `Frontend` (`src/frontend/jest.config.js`), `testEnvironment: node`. There is no jsdom or React Testing Library. Do NOT add either, because it would be a new dependency. Component tests call the function component directly with `react` / `react-router-dom` mocked and inspect the returned element tree (see `NavTabsComponent.test.tsx`, `NavShell.test.tsx`; the latter mocks `useEffect` to run the effect synchronously). Existing tests mock `useLocation` as `() => ({ pathname })` with no `search`/`state`, so new code must tolerate those being undefined. `NavTabsComponent.test.tsx:191` asserts the five root `to` strings. Keep `to` a plain string so it stays green, and pass state through a separate `state` prop (MUI `Tab` forwards unknown props to `NavLink`).
</findings>
