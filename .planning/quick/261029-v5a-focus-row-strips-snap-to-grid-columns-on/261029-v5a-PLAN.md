<objective>
Bug (user): "when you scroll to the right the tiles do not line up, the first tile is cut in
half... the 'columns' should be maintained with below tiles."

Diagnosis (verified while planning): `.focusRowTrack` is `overflow-x: auto` and has no snapping, so a
free scroll stops wherever the wheel or trackpad momentum ends. Every scripted path already lands on
whole pitches (pitch p = card width w + 1.5rem gap):
- `pageScrollDelta` (focusRowOverflow.ts:57) returns `max(1, floor(...)) * cardPitch`, a whole number of pitches.
- End of travel: the track is n*p - gap + 30 wide and the list is m*p - gap + 30, so max scrollLeft = (m - n)*p. The hero slot plus its gap is exactly 2p, so this still holds.
- `scrollFocusedCardIntoViewHorizontally` (focusRowOverflow.ts:262) aligns a card's start to trackLeft + 15, giving scrollLeft = c*p, or its end to trackRight - 15, giving scrollLeft = (c + 1 - n)*p. Both are whole pitches.

Fix: CSS scroll snapping. Free scrolls then come to rest on the positions the scripted paths already target.

Purpose: strip columns stay locked to the grid columns below at every resting position.
Output: snap declarations in index.css and pins for them in focusRowStripSource.test.ts.
</objective>

GREEN, in index.css:
1. In `.focusRowTrack`, add `scroll-snap-type: inline mandatory;` right after `scroll-padding-inline: 15px;`. Use the logical `inline` axis, not `x`: the file uses logical properties throughout because RTL locales ship, and `scroll-snap-align: start` already resolves against the inline axis. Use `mandatory`, not `proximity`: `proximity` lets a slow drag rest between columns, which is the reported bug.
2. In `.focusRowTrack .gameList > *`, add `scroll-snap-align: start;`. Because of `scroll-padding-inline: 15px`, each snap position puts a card's start 15px inside the track. That is grid column 1, because the viewport bleeds -15px. Do not add `scroll-snap-stop: always`: with `normal`, a fling can cross several columns and still rest on one; `always` would cap every fling at one card.
3. Hero anchor. With only (2), a hero strip has snap positions {0, 2p, 3p, ...} and nothing at 1p. `scrollFocusedCardIntoViewHorizontally` end-aligns the first off-screen card (column c = n) to scrollLeft = (c + 1 - n)*p = 1p. A mandatory snap container then re-snaps that to the nearest snap position. 0 and 2p are an exact tie, and at 0 the focused card stays off-screen. To prevent that, add `position: relative;` to `.focusRowTrack .gameList` and a new rule `.focusRowTrack .gameList::before` with:
   - `content: '';`
   - `position: absolute;`
   - `inset-block-start: 0;`
   - `inset-inline-start: calc(15px + var(--focus-row-card-width, 156px) + 1.5rem);`
   - `inline-size: 1px;`
   - `block-size: 1px;`
   - `pointer-events: none;`
   - `scroll-snap-align: start;`

   An absolutely positioned child of a flex container is not a flex item and takes no `gap`, so it adds no layout. In a non-hero strip, 1p is already card 1's own snap position, so the anchor is a no-op there. Leave it unconditional: `:has()` cannot nest the hero's own `:has()` argument. Before editing, confirm that no other `.gameList::before` rule exists. Planning grep found none in src/frontend. `position: relative` without `z-index` creates no stacking context, so the Test 2 track stacking contract is unchanged.
