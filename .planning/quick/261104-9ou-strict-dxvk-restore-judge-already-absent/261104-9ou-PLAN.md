## Decision: per-override `reg query /v` judged by exit code (not user.reg)

Chosen by the planner (discretion given by the orchestrator):
- `user.reg` is rejected: the docblock on `restoreDxvkStrict` records that the registry is saved
  only when `prepareBottleForEngine` stops the lingering CrossOver wineserver, AFTER the restore
  returns. Reading `user.reg` inside the restore would read the pre-import state. Faithful
  modelling would also need the test to synthesise a registry file the real wineserver has not
  written yet.
- `reg query KEY /v <name>` per override, with the verdict taken from `result.code`, which the
  `exit` event carries regardless of pipe truncation (see `settle(code)` on `exit` in
  `src/backend/launcher.ts` around lines 1692-1703). Wine `programs/reg/query.c`
  (wine-mirror/wine master, read 2026-11-04): key missing -> `STRING_KEY_NONEXIST`, `return 1`;
  value missing -> `STRING_VALUE_NONEXIST`, `return 1`; value present -> `return 0`. Invalid
  syntax also returns 1, but the arguments are fixed by us.
- Exit code 1 is ambiguous only if wine itself failed to start. Guard: trust code 1 as "absent"
  only when the preceding `reg import` exited 0 in the same call, which proves wine and reg.exe run in
  this bottle. If the import failed the restore already fails; skip the verify queries then.
- Cost: one wine process per unique override (DXVK 2.x ships d3d8, d3d9, d3d10core, d3d11, dxgi,
  so 5) instead of one. Each settles at exit + at most 250 ms on a warm wineserver. The import stays
  batched, so this is 1 + 5 processes against G30's original 1 + 1 and the pre-G30 per-DLL deletes'
  N + 1. Record this tradeoff in the docblock.
