# Debug: Epic sign-in never produces a login form on a cold cookie jar

## Current Focus

reasoning_checkpoint:
  hypothesis: "GameLib's cold-jar Epic sign-in hangs because (1) `open_pristine_epic_login_window` shares ONE long-lived, persistent `WKWebsiteDataStore.default()` across the whole `gamelib-shell` process lifetime, AND (2) `humble_login_clear_cookies`/`clearEpicCookies` deliberately scopes its removal to `WKWebsiteDataTypeCookies` ONLY (by design, per Phase 34.4.1 Plan 23), leaving any pre-existing HTTP disk-cache entry for `EPIC_LOGIN_URL`'s origin untouched. When a real successful Epic login has occurred earlier in the same process (writing a disk-cache-reusable entry for the login page), a later cookie-only clear followed by a fresh sign-in attempt causes the pristine window's WKWebView to be served that STALE cached document instead of a fresh anonymous one. That stale document's client-side JS was built for an authenticated session that no longer exists (cookies are gone), so it polls session-dependent subresources that can never resolve — producing the observed continuous retry loop for the full 300s, exactly one `nav host=` line (the load event fires once, for the cached response), a WebContent process/page that stays alive throughout (no teardown), and GameLib's own 300s client timeout firing at the end rather than any WebKit-side termination."
  confirming_evidence:
    - "Real unified-log trace of the actual failing run (PID 73124/pageID=140, re-verified fresh): resourceID=11 (main document, isMainResource=1) shows `retrieveCacheEntry: HTTP (foundCachedEntry=1)` -> `didRetrieveCacheEntry` -> `sendResultForCacheEntry` -> `cleanup: (result=1)` with NO `startNetworkLoad` line anywhere — served entirely from disk cache, zero network round-trips, and this is the FIRST-EVER main-resource load of this page in the whole captured window (so the entry predates this run)."
    - "Source-level read of `src-tauri/src/main.rs:3286-3563` (`open_pristine_epic_login_window`): every call builds a fresh `WKWebViewConfiguration`/`WKWebView` with NO explicit `websiteDataStore` assignment, so it defaults to the shared, process-wide `WKWebsiteDataStore.default()` — the same store persists across every login attempt for the process's entire lifetime."
    - "Source-level confirmation (via `.planning/phases/34.4.1-.../34.4.1-23-SUMMARY.md`) that `humble_login_clear_cookies` fetches `allWebsiteDataTypes` broadly but removes ONLY `WKWebsiteDataTypeCookies` at removal time, by design — shared verbatim by Epic's `clearEpicCookies`."
    - "Real transcript timestamps: successful authenticated login at 10:38 (warm jar, 5 stale cookies including `cf_clearance`), cookie clear at 10:45:50, failing cold-jar attempt at 10:45:52 — ~7 minutes later, in the SAME long-lived process, comfortably inside any reasonable cache-freshness window."

## Recovery Procedure (for any machine poisoned before this fix shipped)

The code fix alone does NOT self-heal a machine that already has a stale disk-cache entry for
Epic's login origin sitting in `WKWebsiteDataStore.default()` from an earlier authenticated
session — that entry is durable and survives a `gamelib-shell` rebuild/restart untouched. Anyone
who logged out of Epic on a pre-fix build needs a one-time eviction in addition to updating the
binary. Two viable mechanisms, in order of preference:

1. **Rebuild, then run the app's own Epic logout flow once**, even if already signed out /
   nothing to log out of. Post-fix, `LegendaryUser.logout()`'s `wipeSteps` (`clearEpicStorage`
   then `clearEpicCookies`) now evict the HTTP disk/memory cache in addition to cookies for the
   Epic origin — this is the shipped, app-level path and requires no custom tooling. (No standalone
   frontend/IPC entry point runs just this eviction outside `logout()` — see the `next_action`
   correction above; do not try to build a bespoke dispatch call for this.)
2. **Direct on-disk eviction** of the WebKit NetworkCache records for `epicgames.com` domains
   under `~/Library/Caches/com.gamelib.shell/WebKit/NetworkCache/Version 17/Records/`, bypassing
   the app entirely — the same class of manual removal already used elsewhere in this session for
   leftover probe artifacts. A post-recovery check in this session still found 10 files under that
   tree matching `epicgames` content; this is NOT necessarily a problem — a successful post-fix
   sign-in legitimately writes fresh, correctly-scoped cache entries for an authenticated session,
   which is different from the stale pre-existing entry the defect exploited.

On the operator's own machine, independent filesystem evidence (a rebuilt binary newer than the
fixed source, a cookie jar sized 18270 bytes, and a freshly-written
`legendaryConfig/legendary/user.json` time-correlated with the cookie jar) supports that recovery
and a real post-fix sign-in did occur on 2026-09-28. The EXACT mechanism used to perform the
one-time eviction on this specific machine (option 1 vs. option 2 above) was NOT independently
confirmed by this session and is not asserted as fact — only the outcome (recovery succeeded) is
evidenced.
