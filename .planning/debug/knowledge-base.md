## email-steamguard-still-invalid — credential guard_required branch missing authenticated listener causes DeviceConfirmation auto-cancel
- **Date:** 2026-06-29
- **Error patterns:** invalid code, Login attempt has been canceled, submitSteamGuardCode, EResult, guard_required, DeviceConfirmation, steam guard, credential login, _pollingCanceled
- **Root cause:** startCredentialLogin returned guard_required without attaching an 'authenticated' listener on the session. For accounts with DeviceConfirmation (type 4) in validActions, steam-session auto-starts polling via setImmediate(_doPoll) inside _processStartSessionResponse. When polling fires 'authenticated' (phone push approval or DeviceConfirmation poll response), steam-session internally calls cancelLoginAttempt() setting _pollingCanceled=true. With no 'authenticated' listener, finishAuth was never called and the user was not logged in. Subsequent submitSteamGuardCode hit _verifyStarted() → _pollingCanceled===true → synchronous throw "Login attempt has been canceled". Confirmed from real-environment [DIAG2] log capture: validActions=[type:3, type:4], no 'error' event during the wait, 34s gap then throw. Two prior fixes were insufficient: (1) casing normalization (01-04, commit 3e4863d) and (2) loginTimeout=180000 — both retained as defense-in-depth but neither addressed the root cause.
- **Fix:** Attach session.once('authenticated'/'error'/'timeout') in the guard_required branch of startCredentialLogin BEFORE returning to the frontend. 'authenticated' handler calls finishAuth and _settleCredSession('done'). 'error' handler logs real EResult and calls _settleCredSession('error'). submitSteamGuardCode uses _waitForCredSession() (shared settle, no duplicate listeners). Added pollCredentialLogin() backend method + frontend 2s credPollInterval for out-of-band DeviceConfirmation phone-approval completion path.
- **Files changed:** src/backend/storeManagers/steam/user.ts, src/backend/main.ts, src/common/types/ipc.ts, src/preload/api/steam.ts, src/frontend/screens/Login/components/SteamLogin/index.tsx, src/backend/storeManagers/steam/__tests__/user.test.ts

## humble-reveal-key-fails — Cloudflare Bot Management blocks Humble reveal POST via axios TLS fingerprint; stale claim-annotations cache after reveal
- **Date:** 2026-07-08
- **Error patterns:** couldn't reveal this key, access_denied, 403, contentType=text/html, looksLikeHtml=true, Cloudflare Bot Management, __cf_bm, axios TLS fingerprint, csrf-prevention-token, csrf_cookie, humbler/redeemkey, Claim button still shown after reveal, stale annotations, keys waiting count
- **Root cause:** (1) The reveal POST to /humbler/redeemkey was blocked by Cloudflare Bot Management's HTML-challenge WAF layer (403, contentType=text/html, ~4.5KB body) based on axios's non-browser TLS/HTTP transport fingerprint — a transport-layer block occurring before Humble's own application code ever inspected the request, independent of header/cookie/CSRF content (all of which were separately confirmed correct across 5 rounds: csrfToken backfill, csrf-prevention-token header, csrf_cookie double-submit, dropped X-Requested-By, full/native cookie attachment). (2) Separately, after the reveal succeeded, the Keys-waiting row kept showing the "Claim" button instead of "Finish activation" because the frontend's per-row claim-annotations map (revealedAt/redeemedAt) was fetched once at mount and never refetched, even though the backend's key-state cache and its live push (humbleKeysUpdated) were already correct.
- **Fix:** (1) Routed the reveal POST through Electron's own `net.request` on the `persist:humble` partition (`credentials: 'include'`, `useSessionCookies: true`, a matching Chrome-shaped User-Agent) instead of axios — a genuine Chromium TLS/HTTP2 fingerprint indistinguishable from a real browser tab. GET paths (read-only Humble endpoints) remain axios, unaffected. (2) Added a `refreshAnnotations()` call in the frontend's Keys-waiting tab, invoked after every claim-wizard close and after undo-redeem resolves, mirroring the existing optimistic-refresh pattern already used by the sibling Giftable-spares tab.
- **Files changed:** src/backend/humble/adapter.ts, src/backend/humble/__tests__/adapter.test.ts, src/backend/humble/user.ts, src/backend/humble/__tests__/user.test.ts, src/backend/humble/userAgent.ts, src/backend/humble/library.ts, src/backend/humble/__tests__/library.test.ts, src/frontend/screens/Humble/Keys/Waiting/index.tsx, src/frontend/screens/Humble/Keys/Waiting/__tests__/index.test.tsx

## steam-startup-resume-crash — unattended startup auto-resume of stale StateFlags=1026 installs kills main process via native fatal
- **Date:** 2026-07-18
- **Error patterns:** window vanishes, no crash dialog, no .ips, silent vanish, StateFlags 1026, scanDownloadingAppIds, starting install polling, Preventing machine to sleep, native fatal, axios 404, unhandled rejection, appmanifest, interrupted install, auto-resume on launch
- **Root cause:** SteamLibraryManager.init() called scanDownloadingAppIds() on every launch and, for every on-disk StateFlags=1026 (interrupted) manifest, unattendedly drove the full locate -> buildDepotPlan -> reconcile -> finalize -> startInstallPolling sequence with no user consent. A leftover Cyberpunk (1091500) manifest triggered this, spinning up the native depot download/decompress machinery immediately after boot; a native fatal in that path (not JS try/catch-able — no dialog, no .ips, no post-crash log) killed the entire Electron main process ~13-16s later, on every single launch. A secondary, non-fatal unhandled axios 404 in the metadata/resume path was present alongside it but eliminated as the cause of death (this runtime only warns on unhandled rejections; app survived past the 404).
- **Fix:** Softened Phase 23 D-04 from auto-resume to user-initiated resume. init() now only DETECTS a leftover interrupted install (sets steamResumePending:true + notifies) — no heavy work runs unattended on boot. The original heavy recovery sequence moved verbatim into resumeInterruptedSteamInstall(appId), which only runs when the user's own Install click triggers it (SteamGame.install() checks steamResumePending first). Both the detection loop and resumeInterruptedSteamInstall() are try/catch hardened per-appId so neither can throw out to the caller or block startup. getGameInfo()'s fire-and-forget fetchMetadataIfNeeded() call site got an explicit .catch() as defense-in-depth against the 404/any metadata error. The native fatal itself in the depot download/decompress path was NOT fixed — deferred as a tracked follow-up for a future user-initiated resume/install (only the unattended-on-launch trigger is closed). Commit 416ff217. Hardware-verified 2026-07-18: restoring both 1026 manifests and launching no longer crashes; app stays up 2+ min, new "surfacing as resumable, NOT auto-resuming" log line fires, old crash-path log signatures absent.

## steam-relogin-no-autorefresh — stuck refreshing flag + single UI-timeout doubling as connect signal wedges library refresh after a cold Steam relogin
- **Date:** 2026-07-21
- **Error patterns:** spinner keeps spinning, library never auto-refreshes, timeout then manual refresh works, refreshLibrary, refreshing stuck true, ensureConnected, connectSteamUserClient, loggedOn, steam-user CM reconnect, rebuild kills session, relaunch relogin
- **Root cause:** Two compounding defects. (1) Frontend GlobalState.refreshLibrary() guards every call with `if (this.state.refreshing) return`, but its catch block never reset `refreshing` back to false on a thrown/rejected refresh — any failed refresh (Steam's own post-login refresh, or any other store's) permanently wedged the flag and silently no-op'd every subsequent refresh attempt, including the manual Refresh button (same method). (2) Backend SteamUser.connectSteamUserClient() used one hardcoded 15s timeout for two purposes at once: a lenient "give up on a display name" UX fallback, and (via ensureConnected()'s `Boolean(client.steamID)` check) the sole functional signal for "is Steam actually connected." A cold CM reconnect immediately following an abrupt process kill (rebuild+relaunch never calls client.logOff()) can legitimately take longer than 15s; when the wrapper timed out first, SteamLibraryManager.refresh() silently returned null (log-only, no user-facing error) with nothing to retry, even though the same client's 'loggedOn' listener was still attached and could fire moments later. connectSteamUserClient's Promise also never rejects (masks genuine CM errors as a fallback-name resolve).
- **Fix:** (1) src/frontend/state/GlobalState.tsx refreshLibrary() now resets `refreshing:false` in the catch block. (2) src/backend/storeManagers/steam/user.ts ensureConnected() now gives an already-connecting client one bounded 20s grace window (listening directly for 'loggedOn'/'error') before giving up, instead of trusting the 15s UI timeout as the sole functional signal. Self-verified: tsc clean, jest (steam suite) 23/23 suites pass with no regressions, eslint clean. Human-verified 2026-07-21 against a real rebuild+force-kill+relaunch+relogin: symptom did not reproduce — BUT the observed relogin reused a persisted refresh token (fast reconnect), so this run directly confirms fix (1) and only defensively (not measurably) exercises fix (2). A genuine server-side CM session collision outliving the 20s grace window remains an open, unconfirmed residual risk if the symptom recurs after a slow/forced fresh credential login.
- **Files changed:** src/frontend/state/GlobalState.tsx, src/backend/storeManagers/steam/user.ts

## steam-logon-button-tauri — Steam Logout silently no-ops under Tauri (unported `send` channel, no error handling), misdiagnosed as broken QR login
- **Date:** 2026-07-23
- **Error patterns:** logon button unresponsive, QR tab never reached, Steam tile Logout, silent reload, no console output, no error, no rejection, fire-and-forget send, makeListenerCaller, logoutSteam, unregistered listener, dispatchSend, sidecar_send, D-02, unported channel, button latch, Logging out forever
- **Root cause:** `logoutSteam` is registered on the frontend/preload side as a fire-and-forget IPC `send` (`makeListenerCaller`, preload/api/steam.ts:17), but Phase 30 D-02 deliberately left it unregistered on the Tauri sidecar side (no `listenerRegistry` entry; `steamAuthFlowRegistration.ts` explicitly excludes it). A `send` has no response protocol at all — unlike an unported `invoke` channel (which rejects with `UNPORTED_CHANNEL_MARKER`), an unregistered `send` silently, "successfully" does nothing: no reject, no hang, no console output. `GlobalState.tsx`'s `steamLogout()` did not distinguish this case — it always optimistically cleared local state and force-reloaded the page, which discarded the one differing console line and caused the reload to rehydrate the same still-authenticated `steamConfigStore.userData`, so the tile silently reverted to Logout with zero visible feedback. `Runner/index.tsx`'s `handleLogout` had no error handling either, so any future genuine rejection would have latched the button in "Logging out..." forever. The bug was originally misfiled as a broken QR-login "logon button" — the tester was actually already signed in and had clicked Logout, not Login; the QR mount-effect code path was never reached and was never implicated.
- **Fix:** (1) `GlobalState.tsx`'s `steamLogout()` now branches on `isTauri()`: if true, shows an honest dialog ("Steam sign-out isn't available in this build yet. You'll remain signed in.") instead of silently no-op'ing + reloading; Electron branch unchanged. (2) `Runner/index.tsx`'s `handleLogout()` now wraps `await props.logoutAction()` in try/catch/finally so the button can never latch on any platform regardless of failure mode. Human-verified live 2026-07-23 on both builds ("yes, both get expected behaviors").
- **Files changed:** src/frontend/state/GlobalState.tsx, src/frontend/screens/Login/components/Runner/index.tsx, .planning/phases/30-tauri-ipc-re-plumb-slice-1-install-uninstall-update-check/30-HUMAN-UAT.md, .planning/debug/resolved/steam-logon-button-tauri.md

## gog-login-ui-never-updates — Phase 29 D-06 store-change push covered only renderer-initiated writes, so sidecar writes left the renderer snapshot frozen
- **Date:** 2026-08-03
- **Error patterns:** No cache found getting data from gog, library never renders after login, games only appear after restart, spinner keeps spinning, backend persists but UI empty, gog_library.json has games but Library is empty, snapshot stale, hydrated, STORE_CHANGED_CHANNEL, storeChanged, snapshotGet, snapshotHas, CacheStore.get returns fallback, zero errors logged, Tauri sidecar store write
- **Root cause:** Under Tauri the renderer keeps a synchronous in-memory store snapshot (`preload/tauriTransport.ts`) because electron-store's read API is sync and Tauri IPC is not. Phase 29 D-06 gave it a `STORE_CHANGED_CHANNEL` listener to stay in sync with disk, but the ONLY emit site was inside `sidecar/storeWriteHandlers.ts`'s `applyStoreWrite()` — the handler for `storeSet`/`storeDelete` frames the RENDERER sends. Every sidecar-initiated write (all backend store managers, e.g. `GOGLibraryManager` → `libraryStore.set('games', …)` → `backend/cache.ts` → electron-store) bypassed it and announced nothing. `hydrated` was append-only (`.add` at two sites, never `.delete`), so once a store was hydrated its snapshot was frozen for the life of the window. Both sync read paths (`snapshotGet`/`snapshotHas`) fail CLOSED and return the caller default with no warning when a store is already marked hydrated — hence a total absence of errors. `storeWriteHandlers.ts`'s own file header had predicted this exact divergence in writing and it was never enforced. Trigger sequence: `gogLogout` ends with `window.location.reload()`, which re-hydrates from a just-emptied disk; the login's sidecar write lands ~48s later and can never reach the snapshot. Live-isolated by restarting with NO login — games appeared immediately, proving disk was fine and only the renderer's copy was stale.
- **Fix:** New dependency-free `src/backend/storeChangeNotifier.ts` seam that `cache.ts`/`electron_store.ts` call on set/delete/clear/commit; the sidecar installs the real implementation in `registerStoreWriteHandlers()`, pointing it at `applyStoreWrite`'s single existing push site (the file's one-push-site invariant is preserved). `CacheStore` announces BOTH the value AND its `__timestamp.<key>` — the renderer's mirror returns its fallback unless both resolve, so a value-only push would have changed nothing observable. `clear()`/`commit()` emit a new `invalidated` payload; the renderer drops the store from `hydrated` and re-fetches (`hydrateStore` REPLACES, WR-07) since a per-key encoding cannot express removals. `pushStoreChanged` gates on `isAllowedStoreField` — the store classes have no write-time allow-list gate, so without it a sidecar write of a Steam refresh token or Humble session cookie would land in the renderer snapshot, defeating `filterStoreSnapshot()` via a side door (verified RED/GREEN). `withStoreChangeSuppressed` prevents a double-push, since `applyStoreWrite` writes THROUGH these same classes then pushes a richer payload itself; rule established: whoever initiates a write owns its notification. No notifier is installed under Electron, so those paths are byte-for-byte unchanged. Live-verified 2026-08-03: 3 `storeChanged` frames received, `loadGOGLibrary store=7`, games render with no restart and no Refresh press. Closes F-34.5-G6-12/F-34.5-G6-03 (gate item 2 clause d). Two traps worth remembering: a "no change" result was twice misleading — once because the running bundle predated the fix (`grep -c storeChangeNotifier build/main/sidecar.js` → 0; `tauri:dev` only rebuilds on launch), once because the library takes ~50s to appear and was checked too early.
- **Files changed:** src/backend/storeChangeNotifier.ts, src/backend/cache.ts, src/backend/electron_store.ts, src/backend/sidecar/storeWriteHandlers.ts, src/common/types/sidecarTransport.ts, src/preload/tauriTransport.ts, src/backend/__tests__/storeChangeNotifier.test.ts, src/backend/sidecar/__tests__/storeLayer.test.ts, src/preload/__tests__/tauriTransport.test.ts

## white-window-not-sheet-cr01 — macOS login sheet never attaches; sheet-candidate window built visible before beginSheet:, and beginSheet: itself wedges the main thread when called synchronously right after WKWebView window creation
- **Date:** 2026-08-04
- **Error patterns:** white window, blank white content, ordinary titled window, not a sheet, not a child, sheet_presented=true, beginSheet_completionHandler, attachedSheet, isSheet, CR-01, CR-02, endless beachball, spinner never cleared, main-thread closure entered, main-thread dispatch timed out, WKWebView modal window deadlock, dispatch2, DispatchQueue::main().after(), NSWindow sheet, tauri login window macOS
- **Root cause:** Three-round arc. (1) CR-01: the login `WebviewWindowBuilder` was built `.visible(visible)` with `.center()`/`.focused(true)` applied synchronously during `.build()`, which runs strictly BEFORE `present_login_window_as_sheet` is called — tao/wry orders the window in and makes it key at build time, so `beginSheet:completionHandler:` silently fails to attach an already-visible/key window as a sheet, leaving an ordinary titled window on screen. (2) CR-02: `present_login_window_as_sheet` returned `true`/logged `sheet_presented=true` on nothing more than "the main-thread dispatch didn't time out," with no `attachedSheet()`/`isSheet()` read-back — CR-01's silent failure was invisible to both logs and the `PRESENTED_LOGIN_SHEETS` registry. (3) TERMINAL: `beginSheet:completionHandler:` invoked synchronously immediately after WKWebView window creation wedges the real OS main thread forever, because WebKit's content-process handshake has not had any run-loop turns yet — a known failure class independently reported for unrelated Rust/Go webview+native-window stacks (Apple Developer Forums "WKWebView in a modal window"; `wailsapp/wails#4226`; `r0x0r/pywebview#138`). Two falsified hypotheses along the way: same-thread `rx.recv` self-deadlock (falsified — `present_login_window_as_sheet` always runs on a spawned worker thread, dispatch_rust_channel's only call site), and an unbounded `login_window_ns_window()`/`.ns_window()` getter stall (falsified live — both NSWindow addresses resolved in 58.5ms, well before the wedge, which live logs isolated to the single `beginSheet_completionHandler` call itself).
- **Fix:** macOS-only (`#[cfg(target_os = "macos")]`), three additive rounds all still live: (1) build the sheet-candidate window `.visible(false)` on macOS, skip pre-emptive `.center()`/`.focused(true)`; (2) `present_login_window_as_sheet` reads back `child.isSheet()` + pointer-compared `parent.attachedSheet()` inside the same main-thread closure right after `beginSheet_completionHandler` returns, only registers/returns success on confirmed attachment, and falls back to `window.show()`/`.set_focus()` if unconfirmed; (3) `humble_login_open` races the entire `present_login_window_as_sheet` call on a background thread against a 15s `LOGIN_SHEET_PRESENT_WATCHDOG_TIMEOUT` so the visible-fallback is never itself gated on an unbounded/wedged call; (4) TERMINAL FIX — defer the actual `beginSheet_completionHandler` call and its CR-02 read-back onto GCD's main queue via `dispatch2::DispatchQueue::main().after()` with a 250ms `SHEET_PRESENT_WKWEBVIEW_WARMUP_DELAY`, giving WebKit's handshake real run-loop turns before the AppKit call (NOT a second `app.run_on_main_thread(...)` call — `tauri-runtime-wry`'s `send_user_message` runs those synchronously inline when already on the main thread, so that would not yield a run-loop turn at all). `dispatch2 = "0.3.1"` added as an explicit direct macOS-target dependency (already resolved transitively via tao/objc2-core-foundation/objc2-core-graphics/rfd — no new crate/version entered the tree). Live-hardware-confirmed round 3: `deferred beginSheet closure entered (deferred_elapsed=260.3ms)` → `beginSheet dispatch call returned` → `read-back attached=true`, `sheet_presented=true`, downstream work proceeded normally. SCOPE: this closes gate item 1 (sheet attachment) only — items 2-6 of the 34.4.2 live gate (close affordance, autofill glyph, Cmd+V, kill switch, hidden-reveal/Epic checks) and un-losability sub-checks remain unmeasured; the phase does not close on this result alone.
- **Files changed:** src-tauri/src/main.rs, src-tauri/Cargo.toml, src-tauri/Cargo.lock, .planning/debug/resolved/white-window-not-sheet-cr01.md

## humble-isloggedin-never-set — cookie_domain_matches categorically blind to leading-dot cookie domains; watch polls forever with zero log output
- **Date:** 2026-08-08
- **Error patterns:** isLoggedIn never set, configStore.set isLoggedIn true never fires, no Logout control rendered, no login form rendered, humble_store/config.json unchanged, WKWebView appears already authenticated, silent watch, zero log output, cookie_domain_matches, leading-dot cookie domain, .humblebundle.com, _simpleauth_sess not found in matched set, SUPPORTED_NONEMPTY, checkCookie if !match return, F-34.4.2-19, humble_login_cookies poll arm, D-G2 branch a falsified

(3) cookie_domain_matches strips a leading '.' from the `domain` argument before comparing (`let d = d.strip_prefix('.').unwrap_or(d)`), RFC 6265-correct (a `.example.com` cookie applies to `example.com` itself too), argument order left untouched at every call site (does not re-litigate the prior Defect-A ordering decision). (4) A new throttled heartbeat (logCandidateNotFoundStatus, mirroring the existing logRejectionStatus shape) now logs total/matchedCount (counts only) when the jar is live but the target cookie is absent from the filtered set, closing the silent-forever gap for good. Residuals (not fixed): Track 1's error/timeout UI remains live-unverified (only the success path was exercised); clearHumbleStorage/logout remains unproven (WKWebView session survives disconnect, auto-relogs); two upstream artifacts (34.4.1-SPIKE-016-FINDINGS.md, the spike-findings-gamelib cookie-domain skill reference) still encode the stale premise and need a future owner.

## steam-bottle-uninstall-reverts — CrossOver renders Steam's confirm dialog off-screen; uninstall routed by title attributes deleted the wrong copy
- **Date:** 2026-08-15
- **Error patterns:** uninstall reverts, badge does not flip, uninstalling then reverts back, no uninstall detected user may have cancelled, grace window 20 ticks, steam://uninstall does nothing, no confirm dialog, deleted files on disk still shows installed, ExecuteSteamURL, CW_USEDEFAULT, 805240832, raiseFrontmostBottledProcess, no matching process within ~18s, app.hide is not a function, Game Porting Toolkit wine64, WINEPREFIX does not exist, dual install, install_path, SharedDepots, GameLibSteamBridge
- **Root cause:** SIX stacked layers, each masking the next. (1) `dispatchToBottledSteam()` raised no window for the `'uninstall'` verb, unlike its `'install'`/`'launch'` siblings. (2) `getSteamBottleSettings()` trusted a persisted `wineVersion` regardless of its `type` — a Game Porting Toolkit engine was persisted for the CrossOver Steam bottle, so `setupWineEnvVars` wired `WINEPREFIX` (at a path that did not exist) instead of `CX_BOTTLE`, and every delegated dispatch ran GPTK's `wine64` against a missing prefix reaching for a `steam.exe` in a different bottle; `steam.exe` exited in ~1s and no bottled Steam process ever existed. Same defect class as Phase 24's `D-UAT-24-06`, never back-ported to this Phase 17 sibling. (3) A dormant bottled Steam spends its first dispatch self-updating (177MB) and drops the `steam://` URI across the bootstrapper's relaunch — a 60s poll grace window can never cover it. (4) **TERMINAL for delegation:** with all the above fixed — CrossOver engine, warm client, CM-connected, logged in, `ExecuteSteamURL` logged three times — Steam still did nothing. Its own `logs/webhelper.txt` shows why: `Uninstall: Created window: size: 648,224 pos: 805240832,805240832`. The confirm dialog IS created, then positioned off-screen from Win32's `CW_USEDEFAULT` sentinel (`-2147483648`) mangled by CrossOver. `steam://uninstall/<id>` is a UI-gated verb, so it can never be confirmed in this bottle — for ANY title, warm or cold, Steam- or GameLib-authored. Proven with Hoard, a genuinely Steam-authored control case, ruling out manifest authorship (an earlier hypothesis) as the variable. (5) `uninstall()`'s routing predicate chose bottle-vs-native by TITLE ATTRIBUTES (`isBottleEligible`/`forcedWindowsViaBottle`/windows-only), never by where the title was actually installed. Pre-existing and harmless while delegation was a silent no-op — the direct-deletion fix for (4) turned it into real data loss: for dual-installed HOARD it deleted the bottle copy while the library entry (and the toast) represented the native one. (6) The dual-install survivor check added for (5) was PAIRWISE (native<->bottle) and excluded the Phase 24 bridge bottle; HOARD was installed on all THREE roots at once, so removing the native copy declared a complete uninstall while 277M survived in `GameLibSteamBridge`.
- **Fix:** (1) reuse `raiseInstallerWindow('uninstall')`. (2) `getSteamBottleSettings()` resolves CrossOver's own wine binary whenever the candidate engine is not already `type: 'crossover'`, mirroring `getBridgeBottleSettings()`; the write-side counterpart landed independently as 34.13's `C-03`. (3)/(4) GameLib owns bottle uninstall outright — `uninstallBottleGameDirectly()` removes the install directory (resolved from the manifest's own `installdir`, never a naming convention) plus `appmanifest_<id>.acf`, containment-checked with the `resolve()`+`relative()` idiom, taking only the FIRST path segment under `common/` so a title declaring `SharedDepots` cannot reach shared depot content living under a sibling installdir. (5) `uninstall()` routes solely on the entry's `install.install_path` (read from `library.get()`, never `getGameInfo()` and its lazy-fetch side effect), resolved against the bottle root and every native root from `libraryfolders.vdf`; resolving inside neither REFUSES and deletes nothing. (6) `pollUninstallOnce()` probes every root except the one uninstalled from, in fixed order, re-resolving `install_path` to a survivor and suppressing the "Game Uninstalled" toast while one remains — each probe individually guarded, because `getBridgeBottleSettings()` returns nothing on an unprovisioned bridge and unguarded that threw out of the poller and broke uninstall completion entirely.
- **Live-verified:** the direct-deletion mechanism and the `install_path` routing, on real data (`source native` in the log for a title that previously routed to the bottle; native 574M copy removed; all sibling bottle titles and `Steamworks Shared` intact). Layer (6) is self-verified only (RED-proven test, suite 1014/1014).
- **Diagnostic technique:** GameLib's own log only proves the dispatch fired. The **bottled Steam client's own logs** are the ground truth — `webhelper.txt` (window creation coordinates), `content_log.txt` (per-AppID state changes; zero entries for the target while busy for other apps is real signal), `bootstrap_log.txt` (self-update cycle), `console_log.txt` (`ExecuteSteamURL`), `connection_log.txt` (logon). Do NOT trust `raiseFrontmostBottledProcess` reporting success — it raised a windowless bootstrapper.

## dev-mode-decompress-worker-electron-hook — dev-mode decompress worker silently falls back to inline decode; worker_threads isolate never inherits the electron Module._load hook
- **Date:** 2026-08-17
- **Error patterns:** Cannot read properties of undefined (reading 'getPath'), worker_threads pool failed to initialize, inlineFallback true, pool inline=true, DecompressPool, decompressWorker.js, workerPath, require('electron') unresolved, externalizeDepsPlugin, Module._load hook, worker isolate module registry, installElectronHook, constants/paths.ts app.getPath appData, Rollup multi-entry chunk hoisting, tauri:dev slow decode, HUMANKIND slow install dev mode
- **Root cause:** TWO independent, compounding gaps. (1) decompressWorker.ts's import chain (./decompress -> backend/logger -> ... -> constants/paths.ts) needs require('electron') resolved to a headless stub because constants/paths.ts calls app.getPath('appData') at MODULE SCOPE — but in dev mode this file was built by electron-vite's shared 'main' Rollup block (alongside main.js) with externalizeDepsPlugin leaving 'electron' external/unresolved, and no runtime Module._load hook (installElectronHook.ts, which correctly serves the main sidecar thread) is ever installed inside a worker_threads.Worker's own isolate — worker isolates get a fresh, independent Node module registry that does not inherit a parent thread's Module._load patch. (2) A first-import-based runtime-hook fix (the natural first attempt) does NOT work for this bundler output shape: Rollup's CJS output for a multi-entry build hoists ALL requires — including a shared chunk containing the offending import chain, extracted because main.js's own graph also reaches it — into a single leading require() statement at the top of the file, executing before any of the importing module's own body code, regardless of static ES-import source order.
- **Fix:** Statically alias electron -> src/backend/sidecar/electronStub.ts at ESBUILD BUILD TIME for a dedicated, standalone dev-mode worker bundle, eliminating the runtime require('electron') entirely so there is nothing left for bundler chunk-hoisting to race against — mirroring the fix already proven for the packaged SEA worker bundle (quick-260817-pkx). New meta/esbuildWorkerBundleShared.ts (side-effect-free shared esbuild flags/paths extracted from meta/buildSidecarSea.ts, which itself runs a full SEA build as an import-time side effect and could not be imported directly); new meta/buildDecompressWorkerDev.ts (standalone compile-gate producing build/main/decompressWorker.js); decompressWorker entry removed from electron.vite.config.ts's Rollup input so electron-vite/Rollup no longer builds this file at all; new package.json script build:decompress-worker-dev wired into tauri:dev's pipeline after build:sidecar.
- **Live-verified:** real HUMANKIND install in the rebuilt dev app showed pool[inline=false] sustained across a full 60s capture (all 10 workers busy, 34-38 queued backlog), ~2x pre-fix throughput (~30 attempts/sec vs ~15-18/s), avgDecodeMs now dominant over avgNetMs (expected healthy shape — the pure-JS LZMA decoder's own speed is the residual bottleneck, a separate already-flagged follow-up, not this bug).
- **Files changed:** src/backend/storeManagers/steam/depot/decompressWorker.ts, electron.vite.config.ts, meta/buildDecompressWorkerDev.ts (new), meta/esbuildWorkerBundleShared.ts (new), meta/buildSidecarSea.ts, package.json

## epic-cookie-clear-read-divergence — Epic logout re-created the cookies it deleted, via a hidden webview it opened at Epic's own live login page purely to obtain a window handle the macOS path never used
- **Date:** 2026-08-31
- **Error patterns:** matched=0, after(total=54, matched=0, verdict=SUPPORTED_NONEMPTY), Epic cookie clear removed 7 cookie(s), cookies still present after logout, EPIC_SESSION_AP, _epicSID, _tald, EPIC_DEVICE, EPIC_LOGIN_ID, __cf_bm, binarycookies, HTTPStorages, gamelib-shell.binarycookies, com.gamelib.shell.binarycookies, post-clear census, jar total does not reconcile, cleared 1 with total unchanged, wry cookie delete lies, clearEpicCookies, clearEpicStorage, EPIC_LOGIN_ORIGIN, seam.open, WKWebsiteDataStore, defaultDataStore, REQ-35-07, D-35-29-02, D-35-19-15
- **Root cause:** The cookies never survived the clear — the logout RE-CREATED them. `clearEpicCookies` called `seam.open(EPIC_LOGIN_ORIGIN, {visible:false})`, a hidden webview pointed at Epic's LIVE login page, solely to obtain a window handle that the macOS code path then never uses: `open_pristine_epic_login_window` never registers the window with Tauri, so `app.get_webview_window(label)` is `None` for ANY label, and both Rust cookie arms take their `WKWebsiteDataStore::defaultDataStore()` fallback precisely BECAUSE of that `None` (main.rs: "deliberately label-independent, taking only the domain to filter on"). The window bought nothing, but building a WKWebView on an https url IS a navigation — real requests that Epic and Cloudflare answer by setting `__cf_bm`, `EPIC_DEVICE`, `EPIC_LOGIN_ID`, `_epicSID`, `_tald`, concurrently with the clear loop and for ~1-2s after its final census. `clearEpicStorage` (which legitimately MUST load Epic's origin, since localStorage/IndexedDB/Cache are origin-scoped) then opened a SECOND live window at the same url and ran AFTER the cookie step, with no sweep behind it. The source comment encoded the false premise verbatim: "no navigation/login flow ever runs against this url" — true of login flows, false of network traffic, and only the second claim would have made the window safe. **The decisive measurement was a timezone conversion:** the binarycookies parser emits UTC while the machine and gamelib.log are UTC+12, and converted, every surviving record's `created` second lands exactly on its own clear (dev clear 19:27:14-15 -> records created 19:27:14/:15/:15/:15/:15/:16; packaged clear 18:15:15 -> 18:15:16/:16/:16/:16/:17). Corroborated independently: both `__cf_bm` records carried an expiry exactly 30 minutes after creation — Cloudflare's bot-management TTL, mintable only by a live HTTPS round trip. **Three prior beliefs falsified:** (1) "two distinct cookie stores" — it is ONE shared store, proven numerically, 56 live records minus exactly 2 expired = the census's own reported `after(total=54)`; (2) "the delete lies" (`wry-cookie-delete-lies-about-deleting`) — the delete deletes, and the jar total falls monotonically 57->54->54->53->52->51 across the sweep; (3) "EPIC_SESSION_AP survived, created nine hours earlier" — a timezone misread of the same kind, `06:17:18Z` = 18:17:18 LOCAL, two minutes AFTER the 18:15:15 clear, minted by a deliberate re-login the log shows at 18:16:34 with `status=captured` at 18:17:19.
- **Fix:** Three changes in `src/backend/storeManagers/legendary/user.ts`. (1) The cookie step no longer opens a window at Epic: on macOS it opens NO window at all, passing `EPIC_COOKIE_CLEAR_NO_WINDOW_LABEL` — a label that cannot resolve, which is exactly the precondition the Rust arms' default-data-store fallback requires, so the identical Rust code runs with only the page load removed; off macOS a real window is still required (the fallback is `#[cfg(target_os = "macos")]`) and is pointed at `https://gamelib.invalid/`, RFC 2606 reserved, instead of Epic. (2) `clearEpicStorage` now runs BEFORE `clearEpicCookies` — the storage step has no choice but to load Epic's origin, so whatever it seeds must be swept afterwards; the previous order meant nothing ever was. (3) A final post-clear verification census over all five Epic hosts, taken after every mutation, decides the reported outcome, and a residual throws (`clearEpicCookies` is `FATAL_WIPE_STEP`) — REQ-35-07's literal "does not report success unless a post-clear read confirms it", which the per-host before/after pair structurally could not satisfy because both members are taken mid-sweep. RED-proven against three separate mutations (removing the verification throw fails 2 tests, restoring the Epic-pointed window fails 6, restoring the step order fails 1); 50/50 green restored. The step ORDER is guarded by a SOURCE gate, deliberately: every behavioural test mocks `seam.clearStorage`, and a mock sets no cookies, so swapping the steps back produces an identically green run — the defect lived in exactly that blind spot. **Live-verified 2026-08-31 21:03** (dev build pid 85098; live jar identified by which mtime MOVED): product reported `post-clear verification — 0 Epic-owned cookie(s) remain across 5 domain(s)` and an independent index-walking parse of the same jar found 0 Epic-owned live records, 0 by domain substring, 0 by cookie-NAME substring, and 0 raw byte occurrences of any Epic cookie name; **0 `__cf_bm` anywhere**, the positive evidence that no page load happens in teardown at all. All four arithmetic reconciliations the pre-fix run FAILED now hold (jar total 59->51 = 8 = reported cleared 8; per-host deltas sum to 8; every per-host delta matches its own census; 51 live records - 0 expired = census `after(total=51)`). Not vacuous — BEFORE census measured `matched=8` versus a pre-fix baseline of 3, and all 8 went. No collateral damage: 0 non-Epic records lost, Humble/GOG/Amazon sessions intact. **Residuals:** D-35-19-15's sibling-domain sub-criterion is still unexercised (all four non-primary hosts reported `before(matched=0)` — because the cookies that used to populate them during a logout were set by the removed window itself, so proving they clear now needs a deliberately seeded fixture); non-macOS is unverified until Phase 38; and an `api.hcaptcha.com`/`hmt_id` cookie PARTITIONED to `https://epicgames.com` correctly survives (not Epic-owned; clearing it is the REQ-34.4.1-06 harm), so the string `epicgames` still appears once in the jar's bytes after a clean logout.
