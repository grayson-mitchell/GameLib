# Debug: Steam native install ~30s pre-download latency (cold CM/PICS) + non-abort-aware cancel

## Symptoms

- **Expected:** Clicking Install on a native Steam depot download starts streaming bytes within ~1-2s, like the real Steam client (which keeps its CM connection + PICS cache always-warm).
- **Actual:** ~30+ seconds elapse between clicking Install and the first download bytes. Reported consistently ("downloads take quite a while to start"), across installs, on the post-rebuild build that includes Phase 23's single-flight guard + progress heartbeat.
- **Coupled symptom (same root latency):** cancelling during that pre-download window removes the item from the DownloadManager queue immediately, but the game's library button stays "Installing" with the spinner for ~30s before clearing — because the cancel/abort can't interrupt the in-flight pre-download seam mid-call.
- **Error messages:** none — this is latency, not a failure.
- **Timeline:** Observed 2026-07-18 during Phase 23 Gate 1 real-hardware UAT (macOS, Apple Silicon). The 3s install-status poller is NOT the cause (30s != 3s).
- **Reproduction:** `enableSteamNativeInstall` opt-in ON; click Install on a native Steam title; time from click to first download bytes (and separately, cancel during that window and time how long the library button stays "Installing").

## Prior/related context (READ FIRST)

- `.planning/debug/steam-cm-drop-planbuild.md` (RESOLVED, 2026-07-17): established that `buildDepotPlan` (`src/backend/storeManagers/steam/depot.ts:485`) calls `SteamUser.ensureConnected()` ONCE up front, then does a long sequence of PICS/manifest network calls (`fetchAppInfo`, `getOwnedSets`, `fetchDlcInfos`, per-depot `fetchDepotPlanEntry` → `getRawManifest` + `getDepotDecryptionKey`), all now wrapped in `withPlanBuildRetry` (`PLAN_BUILD_MAX_ATTEMPTS=3`, `PLAN_BUILD_RETRY_DELAY_MS=500`) which calls `ensureConnected()` + re-resolves `getDepotClient()` on failure. That session was about a CM *drop* causing a hard failure; THIS session is about cold-connect/PICS-warmup *latency* on a healthy connection — distinct symptom, same subsystem.
- Static analysis already done (confirm, don't assume): `ensureSteamClientReady` (`clientSetup.ts:92`) is synchronous/fast (isSteamClientInstalled + hasLibraryFoldersVdf) — NOT the culprit. The latency is downstream in `resolveSteamInstallTarget` (`installLocation.ts:205` → `fetchInstalldir`, PICS appinfo) and `buildDepotPlan`.
- Known upstream issue: node-steam-user #144 — `getOwnedApps()`/PICS cache population is slow for large libraries.

## Suspected root cause (verify with timing, don't assume)

1. **`SteamUser.ensureConnected()` cold-connect cost.** The steam-user CM connection (login via stored refresh token) is likely established cold on the first install of a session (or not kept warm), so the first `ensureConnected()` + PICS warmup pays ~30s. The real Steam client keeps this always-on. PRIORITY hypothesis.
2. **`withPlanBuildRetry` backoff compounding** if early PICS calls fail because the connection isn't ready (but 3×500ms ≈ 1.5s alone can't explain 30s unless each `ensureConnected()` attempt itself blocks ~seconds).
3. **Serial PICS fetches** (`fetchInstalldir` in resolveSteamInstallTarget, then `fetchAppInfo`/`getOwnedSets`/`fetchDlcInfos`/`fetchDepotPlanEntry` in buildDepotPlan) that could be pre-warmed or parallelized.

## Investigation plan

Add lightweight timing instrumentation (log start/end durations) around, in order: `ensureSteamClientReady`; the CM connection / `SteamUser.ensureConnected()` (cold vs warm); `resolveSteamInstallTarget` / `fetchInstalldir`; and each `buildDepotPlan` step (`fetchAppInfo`, `getOwnedSets`, `fetchDlcInfos`, the per-depot `fetchDepotPlanEntry` loop) + each `withPlanBuildRetry` attempt count. Then have the user reproduce ONE native install on real hardware and read the durations from the dev log to attribute the ~30s precisely before choosing a fix. This bug requires runtime timing — it cannot be pinned from static reading alone.

## Fix goals (acceptance)

- Native install begins streaming bytes within a few seconds of the click on a warm session (target: comparable to Steam, not ~30s).
- Likely direction (pick after timing): pre-warm the CM connection + PICS cache (e.g. at app start or Steam-library load) so per-install setup is cheap; and/or reduce/parallelize the pre-download PICS work.
- **Secondary (same root, do after latency understood):** make the pre-download seams abort-aware — thread `controller.signal` into `resolveSteamInstallTarget` and the `buildDepotPlan` phase (or race against the abort) so a cancel during the pre-download window resolves promptly instead of waiting ~30s. Currently `games.ts` `runNativeDepotDownload` only checks `controller.signal.aborted` BETWEEN seams, never during them.
