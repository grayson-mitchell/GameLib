## Problem

On win32, `pathShim.getPath('desktop'|'documents')` is sync and returns `join(homedir(), 'Desktop')`
and `join(homedir(), 'Documents')` (`src/backend/sidecar/pathShim.ts` lines 98-101 and 116-118).
It cannot await the registry. Callers that need the real folder await `readWindowsShellFolder` first
(`'Desktop'`, `'Personal'`) and fall back to the sync path when that lookup fails or times out.

The 2026-11-11 live gate measured the operator's Desktop and Documents as OneDrive-redirected
(`<profile>\OneDrive\Desktop`, `<profile>\OneDrive\Documents`), so on that host the fallback is not
the real folder. Whether `<profile>\Desktop` exists there was not checked. The trap arms only when
the registry lookup fails or times out, and no failure has been observed.

The `src/backend/process/README.md` hand-off (lines 186-189) says 66.3 should retire the fallback.
The 66.3 ROADMAP goal does not name it, so this todo is its only tracked carrier.

source: .planning/todos/completed/2026-11-10-66.2-windows-spawn-paths-live-gate.md

## Done when

Either outcome closes the todo:

- (a) 66.3 retires the sync fallback, and the win32 callers no longer depend on it; or
- (b) a Windows run confirms that the fallback path is usable before the async lookup resolves (the
  closed todo's original follow-up).

## Resolution (code fix, quick 261111-aq4, 2026-11-11)

Outcome (a) is taken: the sync fallback is retired and no win32 caller depends on a guessed folder.

Live evidence on the operator's Windows 11 box on 2026-11-11 rules out outcome (b):

- `Test-Path <profile>\Desktop` returned False and `Test-Path <profile>\Documents` returned True.
- `[Environment]::GetFolderPath` gave `<profile>\OneDrive\Desktop` for `'Desktop'` and
  `<profile>\OneDrive\Documents` for `'MyDocuments'`.

So the Desktop fallback named a folder that does not exist (a shortcut write would fail), and the
Documents fallback named a folder that exists but is the wrong one (GOG native save sync would have
read and written the wrong directory without any error).

What changed:

- `pathShim.ts`: on win32, `getPath('desktop')` and `getPath('documents')` throw a named error that
  points at `readWindowsShellFolder`. The darwin and linux arms are unchanged.
- `shortcuts/shortcuts/shortcuts.ts`: `shortcutFiles` returns no Desktop path on win32 unless the
  registry answered. `addShortcuts` records an unresolved Desktop as a failed Desktop shortcut and
  still writes the Start Menu `.lnk`, so it rejects and the sidecar shows the error toast instead of
  "created on Desktop and Start Menu". If no Desktop shortcut was requested, a failed lookup is not a
  failure. `removeShortcuts` removes the Start Menu `.lnk` and logs a warning, and never rejects.
- `save_sync.ts`: `getDefaultGogSavePaths` no longer falls back to `app.getPath('documents')` on win32.
  A location that needs an unresolved `<?DOCUMENTS?>` is left out with a warning, not blanked,
  because the returned list can reach gogdl `save-sync` verbatim. A location the user already set
  keeps the user's path.

Tests pin it: `pathShim.test.ts` (win32 throws, darwin control), `addShortcutsOutcome.test.ts` (lookup
fails and registry answers, with the `.lnk` paths read from the PowerShell call env),
`removeShortcutsOutcome.test.ts` (win32 warn-and-continue) and
`getDefaultLegendarySavePathRefresh.test.ts` (GOG omission, registry-success control, user-path
survival). The host-platform cases in `shortcutsExistsFallback.test.ts`, `shortcutsFlows.test.ts` and
`runnerMiscFlows.test.ts` are pinned to linux, so CI and a Windows host agree.

Nothing in the registry-success path changed, and the 66.2 live gate (quick 261111-5fw) already
proved that path on this machine.
