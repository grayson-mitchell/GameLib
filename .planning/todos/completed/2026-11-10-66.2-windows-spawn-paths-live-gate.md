## Problem

66.2 moved every backend spawn onto the process runner. The Windows-only argv and exit-code
handling was asserted with scripted runners on macOS but never run on Windows. Run each path
once on a Windows machine and confirm the expected observable result.

## Paths to live-check

- robocopy (`moveOnWindows` in utils.ts): moving an install folder across drives finishes and the
  files arrive. Known quirk kept as-is: "Finished Moving" logs on `code !== 0`, and robocopy codes
  0-7 are success.
- reg.exe (`knownFolders.readWindowsShellFolder`, plus the running-poll lookup): Desktop and
  Documents resolve to the registry shell-folder value (OneDrive-redirected Desktop included), and
  fall back to `app.getPath` when the query fails.
- tasklist and powershell (`steamClientProcess` probes): a running Steam client is detected, a
  stopped one yields none, and a probe timeout reads as unknown, not as "not running".
- powershell `.lnk` write (`windowsShortcut`, script on stdin): add and remove a desktop shortcut;
  the `.lnk` exists, points at the launcher and carries the icon.
- powershell (`detectVCRedist`, filesystem and systeminfo probes): the VC redist dialog appears only
  when the redist is missing; a timeout shows only a warning in the log.
- where.exe semantics, now a PATH scan (`os/path`): a tool on PATH resolves, including a `.exe`
  suffix and `PATHEXT` entries; a missing tool resolves to not found.
- taskkill (runner kill path): cancelling a running long-lived child ends the whole process tree,
  with no orphan left in Task Manager.
- wmic and systeminfo probes (plan 05): the hardware info panel still fills in on a machine with
  and without wmic installed.

## Follow-ups

- The sync-fallback of `knownFolders` and `pathShim` on win32 is documented in the process README
  as a 66.3 hand-off; verify it still returns a usable path before the async lookup resolves.
- The fake-HOME spawn-detector regex was extended to runner calls and stayed green, so there is no
  flagged-site follow-up.

## Resolution (live gate passed 2026-11-11, real Windows, quick 261111-5fw)

Run on 2026-11-11 (local time; UTC 2026-11-10T14:49-14:53Z) on the operator's Windows 11 Home
10.0.26200 machine. Each converted path was driven through the production runner
`createProcessRunner` (`src/backend/process/runner.ts`) with the operator's real environment and
real binaries, using a temporary jest harness that was deleted afterwards and never committed. The
evidence log was kept outside the repo. Result: 7/7 harness items plus 2/2 Steam arms PASS, on final
launches 4-6. Launches 1-3 failed only on harness defects, not product defects: the logger was not
initialised under jest, and a where.exe comparison bug in the harness.

1. robocopy (`moveOnWindows`): a C: scratch folder (one 3 MiB file plus a subdir) moved to D:\.
   Status was done, the files arrived, and the source was removed. robocopy exited 1, so "Finished
   Moving GateGame" was logged. That is the known quirk, kept as-is.
2. reg.exe (`readWindowsShellFolder`): Desktop resolved to `<profile>\OneDrive\Desktop` and Personal
   to `<profile>\OneDrive\Documents`, both equal to `[Environment]::GetFolderPath`, so the
   OneDrive-redirected case is covered. A bogus value name gives undefined. A forced 1 ms timeout
   gives undefined, and the caller falls back to `app.getPath`. The running poll `readRunningAppId`
   (`reg query HKCU\Software\Valve\Steam RunningAppID`) gives 0 with no game running.
3. tasklist (`listSteamClientPids`): stopped gives [], matching Get-Process. Running (Steam started
   with -silent for the gate, then shut down) gives [11540], matching Get-Process. A forced timeout
   gives undefined, meaning unknown rather than "not running".
4. powershell `.lnk` write (`writeWindowsShortcut`, script on stdin): wrote
   `Gäme ゲーム – Test.lnk`, a non-ASCII path, and returned {ok:true}. Read back through WScript on
   an ASCII copy: TargetPath C:\Windows\explorer.exe, Arguments gamelib://launch/steam/220,
   IconLocation C:\Windows\System32\notepad.exe,0. The shortcut was removed cleanly.
5. detectVCRedist: with 6 "Microsoft Visual C++ 2022" entries installed there was no dialog, and
   logInfo "VCRuntime is installed (6 matching entries, probe 983 ms)". On a forced timeout there
   was no dialog, only logWarning "VCRuntime check killed after exceeding VC_REDIST_PROBE_TIMEOUT_MS".
6. PATH scan (`findExecutableOnPath`): `powershell` resolved via PATHEXT to
   ...\WindowsPowerShell\v1.0\powershell.EXE, and `robocopy.exe` to C:\Windows\system32\robocopy.exe.
   Both match where.exe, compared case-insensitively. A `.cmd` tool on PATH resolves via PATHEXT. A
   missing tool gives null.
7. taskkill (runner kill path): `spawnLongLived` ran `cmd.exe /c ping -n 120` with track.
   `killTracked` returned 1. Afterwards cmd and its 2 child processes were all gone (aliveAfter 0):
   no orphan.
8. systeminfo powershell probes (`getGpuInfo_windows`, `osInfo_windows`, Get-CimInstance): 2 GPUs,
   NVIDIA 10de:2f58 with driver 610.74 and AMD 1002:150e. OS "Microsoft Windows 11 Home" 10.0.26200.
   wmic is NOT installed on this host, so the "without wmic" arm is covered.

Not covered: the in-app UI gestures (the Add Shortcut menu, the VC dialog on a host without the
redist, a real game Move, and cancelling a real install), since the paths were driven below the UI.
Also not covered: the missing-redist dialog arm (the redist is installed on this host) and the "with
wmic" arm (the probes no longer call wmic).

Follow-ups: the first follow-up (the win32 `knownFolders`/`pathShim` sync fallback) was NOT checked.
It is carried by the new pending todo `.planning/todos/pending/2026-11-11-66.3-win32-known-folder-sync-fallback.md`,
because the 66.3 ROADMAP goal does not name it. The second follow-up needs no action. The `files:`
entry for knownFolders was corrected to `src/backend/sidecar/knownFolders.ts`; the old
`src/backend/platform/knownFolders.ts` path does not exist.
