## Cross-Phase Integration — Clean

All six audited seams CONFIRMED wired by direct source read:

1. **Token-store seam** — `bootstrap.ts:98` calls `installTokenStore(new SidecarKeyringTokenStore())` synchronously after `startRpcServer()` and before `READY_SENTINEL`. Node's single thread means no frame can dispatch first; the default `ElectronTokenStore` is structurally unreachable in production.
2. **Transport correctness** — `RUST_INVOKE_CHANNELS` (`sidecarTransport.ts:150-155`) matches `dispatch_rust_channel()`'s arms (`main.rs:207-275`) byte-for-byte. No ID collision: Rust uses a decimal `AtomicU64`, the sidecar uses `randomUUID()` — disjoint spaces. Responses correlate in both directions.
3. **SEAM.md is current, not stale** — phase 28 correctly graduated `safeStorage` from stubbed to ported (§1 lines 63-109) and updated the deferred table. A genuine positive finding; phases 29-35 can trust it.
4. **Plaintext stub removed** — the literal passthrough is gone; `electronStub`'s `encryptString`/`decryptString` now throw. (See WARNING below for the residual vector.)
5. **Electron unaffected** — no non-sidecar backend file imports `src/backend/sidecar`; `npm start` unchanged; the one cross-cutting edit (`main.ts:967`, awaiting the now-async `logout()`) matches existing convention.
6. **Snapshot exclusion holds** — `handlers.ts:42-44` still strips `refreshToken` from the renderer snapshot, and it's the same store `tokenStore.ts` resolves to.

## ⚠️ New Finding — Plaintext Fallback Guarded Only by Call Order

`ElectronTokenStore.encryptToken()` (`tokenStore.ts:73-84`) checks
`encryptionAvailable()` and, when false, takes a **plaintext-fallback branch** —
it never reaches the throwing `encryptString`. `fileStore.ts:12-15,43-51` resolves
to the *same on-disk path* real `electron-store` uses.

So if `ElectronTokenStore`'s default instance were ever reached in the sidecar
before `installTokenStore()` runs, it would silently write a **plaintext token
into the file Electron reads** — exactly the corruption trap SEAM.md records as
closed, and exactly the failure mode that made Phase 28 order-critical in the
first place.

It is safe **today**: the ordering in `bootstrap.ts:94-97` is correct and
self-documented as load-bearing (T-28-10). But nothing structurally enforces it —
no assertion, no throw-fast, no build-mode flag. The milestone's central safety
property rests on discipline rather than defense-in-depth. Worth hardening before
phases 29–32 wire more token-touching channels.

Not a blocker. A fragility.
