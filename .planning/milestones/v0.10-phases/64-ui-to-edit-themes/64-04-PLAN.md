<assumption_delta_decision>
Detector fired (pluralization: "fallback", chosen: "custom"). Identity question: the theme key moves from
"one of 10 built-in class names" to "a built-in key OR a custom theme id".
- Primary noun: **ThemeKey** = a built-in key (`midnightMirage`, ...) or `custom:<id>`. It is what
  `settingsState.theme`, `configStore.theme`, `window.setTheme(key)`, the gallery's active marker and
  `data-theme-key` hold.
- Decision: **promote**. One resolver, `resolveThemeKey(key, customs) -> { kind: 'builtin', key } |
  { kind: 'custom', theme } | { kind: 'unknown', key }`, answers "which theme is this" everywhere
  (`applyTheme`, the gallery active marker in Plan 05/06, delete fallback). "Built-in class name" is demoted to
  a derived detail: the body class is computed from the resolution (`key` for built-ins, `theme.base` for
  customs, the default for unknown); no caller compares a theme key against `defaultThemes` directly anymore.
- Companion invariant test (accepted, Task 1): every key the gallery can offer round-trips through
  `resolveThemeKey` and `applyTheme` to exactly one built-in class on body.
</assumption_delta_decision>
