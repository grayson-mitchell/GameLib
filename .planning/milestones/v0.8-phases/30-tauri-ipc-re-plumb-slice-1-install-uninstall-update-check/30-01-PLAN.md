## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| renderer → sidecar RPC | Untrusted invoke frames reach the three new handlers |
| sidecar → OS Keychain (via Rust `rustInvoke`) | The Steam refresh token crosses here on a successful QR poll |
| sidecar → shared `userData` config store | `isLoggedIn` / `userData` writes land in a folder the Electron build also reads |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-30-01 | Information Disclosure | `steamPollQR` result + store snapshot | mitigate | Token is written only through `getTokenStore().setToken()` (SidecarKeyringTokenStore); `STORE_ALLOWLIST` already limits `steamConfigStore` to `['isLoggedIn','userData']`, so `refreshToken` cannot enter a snapshot. Task 2 asserts this as a regression test. |
| T-30-02 | Tampering | shared `configStore` / token seam | mitigate | Phase 28 D-04 is binding: the sidecar must never write `TOKEN_STORE_KEY` into the shared `configStore`. Enforced by construction — `keyringTokenStore.ts` does not import `configStore` or the key constants; Task 1 changes only its docstring. |
| T-30-03 | Denial of Service | login channel on Keychain failure | mitigate | Phase 28 D-06 failure policy governs: `NoEntry` is healthy first run; every other outcome collapses to a clean signed-out state with one logged warning and never a plaintext write. No new failure handling is introduced here. |
| T-30-04 | Elevation of Privilege | newly registered handlers widening reach | accept | The three handlers take no renderer-supplied arguments at all (`() => ...`), so no untrusted input reaches `SteamUser`. Credential/guard/logout channels stay unregistered and keep rejecting. |
| T-30-SC | Tampering | npm/cargo installs | mitigate | This plan installs no packages. The one `[ASSUMED]` package this phase touches (`tauri-plugin-dialog`) is gated by a blocking human checkpoint in plan 30-03. |
</threat_model>
