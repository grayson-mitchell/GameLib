### Discovered, out-of-scope issue (not fixed — logged per SCOPE BOUNDARY)

**Backend test suite 4 failures, not the 3 expected — RESOLVED 2026-08-27 by the orchestrator, and the diagnosis recorded here at execution time was WRONG. Corrected in place rather than left to mislead a later reader.**

At Task 3's execution `npx jest --selectProjects Backend` returned 4 failing tests (later measured as 5, across 3 suites): the 3 pre-existing `decompressPool.test.ts` native-LZMA failures plus `appRootResolution.test.ts` and `enrichmentFlows.test.ts`.

**Recorded cause at the time (WRONG):** "Task 2's live gate replaced the directory's contents ... versus whatever fixture/mock state the tests previously ran against." That inverts the assertion. `appRootResolution.test.ts:256` asserts `expect(existsSync(binaryPath)).toBe(true)` for FOUR binaries — `legendary`, `gogdl`, `nile` and **`comet`**. `existsSync` returns true for a directory, so the three onedir runner trees satisfied it. The failing member was `comet`, which was ABSENT.

**Actual cause:** the orchestrator ran `rm -rf public/bin/arm64/darwin` before §3 criterion 1 to force a genuinely cold `download-helper-binaries` run. That deleted `comet` along with the three runner trees. The re-download did NOT restore it — zero `comet` mentions in the captured log — and `public/bin/arm64/darwin/comet` was the only file missing (every other platform's comet survived; `x64/darwin` still held all four).

**The generalizable trap, worth more than this incident:** `download-helper-binaries` is idempotent by RELEASE TAG, not by file presence. It diffs `public/bin/.release_tags` against `RELEASE_TAGS` and downloads only what differs, so **a binary deleted from disk is never restored** while its tag still matches. The `__darwin_layout` branch that does force re-downloads is deliberately scoped to `DARWIN_LAYOUT_RUNNERS` and its own comment says comet "must never be pulled in from here". A `rm -rf` of a bin directory is therefore NOT undone by re-running the downloader — which also means the §3/1 "cold run" was only partially cold.

**Fix applied:** deleted the `comet` key from `public/bin/.release_tags` (backed up by `cp` first) so the tag comparison would fire, re-ran `pnpm download-helper-binaries` (exit 0, `Downloading: [ 'comet' ]`), restoring `public/bin/arm64/darwin/comet` at 10,667,240 bytes; `.release_tags` healed itself back to the full five-key set. Backend is back to its baseline **4271 tests, 4266 pass / 3 fail / 2 skip**, `decompressPool.test.ts` the only failing suite. Meta 603/1/1, Common 41, Preload 140, Frontend 2059 — all at baseline.

Task 3's own scope judgement was CORRECT: this was Task 2 fallout, outside its two declared files, and refusing to fix it there was right. Only the causal explanation needed correcting.

Meta suite matched exactly: `npx jest --selectProjects Meta` → `605 tests, 603 pass / 1 fail / 1 skip`, the pre-existing `genI18nGateScope.test.ts` A-17 drift, unrelated to this plan.
