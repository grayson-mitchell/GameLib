## Default-branch landing route

### Q1 — How should `build-runners-onedir-macos.yml` reach `gamelib/main`?

| Option | Description | Selected |
|--------|-------------|----------|
| Workflow-only commit | One commit on `gamelib/main` adding just the workflow file, then dispatch with `--ref fix/steam-native-install-stability` so the branch's full version runs. Blast radius: one file. | ✓ |
| Merge the branch into main | Make main the real GameLib; ends the 3830-commit divergence but is a whole-fork ship decision. | |
| Repoint the default branch | No commit; makes every branch workflow dispatchable, but changes PR bases and what "main" means. | |

**User's choice:** Workflow-only commit.

**Notes:** Grounded in the mechanism the 34.9 ledger records — GitHub refuses to dispatch a workflow
absent from the default branch *regardless of `--ref`*, but once registered there, a dispatch against
another ref runs **that ref's** version. That makes the minimum unblock one file, not a merge.

### Q2 — What should the copy on `main` contain?

| Option | Description | Selected |
|--------|-------------|----------|
| Verbatim + ref guard | Byte-identical plus a first step that hard-fails on the default branch, naming the correct `--ref`. Keeps copies diffable; mis-targeted dispatch fails in ~5s. | ✓ |
| Verbatim copy, no guard | Identical bytes, nothing else. A dispatch against main burns ~2 min of macOS runner time before a confusing "script not found". | |
| Minimal registration stub | Name + `workflow_dispatch` + an error step. Smallest footprint, but nobody reading main can tell what the workflow does. | |

**User's choice:** Verbatim + ref guard.

**Notes:** The guard goes into **both** copies so they remain byte-identical and drift shows up in a
plain `diff`. Necessary because `main` has neither `meta/buildRunnersOnedir.ts` nor the
`build-runners-onedir` script.

**Notes:** Matches the 34.9 ledger's own position that pushing to `main` is outside any plan's

## Guard arch coverage (items 12 and 13)

### Q1 — What shape should the widened invocation take?

| Option | Description | Selected |
|--------|-------------|----------|
| Two sequential invocations | `--arch=arm64 && --arch=x64`. Zero guard code change, fail-closed, each failure names its arch. | ✓ |
| Accept an arch list | `--arch=x64,arm64`. Tidier scripts; needs `parseCliArgs` changed and a non-empty-set assertion or a typo verifies nothing. | |
| Derive from the tree | Glob `build/bin/*/darwin`. Self-maintaining, but passes vacuously if the layout changes or the tree is empty. | |

**User's choice:** Two sequential invocations.

**Notes:** Grounded in a scout finding — `meta/verifyRunnerBundle.ts` already parses `--arch=x64`
(`parseCliArgs`, §515-527), so item 12 is a wiring problem, not a CLI gap. The tree-derived option was
rejected explicitly as the fail-open shape.

### Q2 — How should the guard visibly execute in CI (item 13)?

| Option | Description | Selected |
|--------|-------------|----------|
| Leave npm-script-level | Once `install-deps` stops throwing on the sentinels, the macOS leg reaches the build step and the guard runs. Guard cannot drift from the build it protects. | ✓ |
| Add an explicit CI step | Own green/red box in the run, fails ~2 min earlier — but a second invocation that can drift from `package.json`'s. | |
| Both, with the CI step as the pin | Maximum visibility and drift-proof; three places to change, for a workflow Phase 35 partially deletes. | |

**User's choice:** Leave npm-script-level.

**Notes:** Two findings were surfaced before this question. (a) Item 12's blocker dissolves the moment
digests are real, because `downloadOnedirAsset()` already fetches both arches — which makes
`electron-builder.yml:71-79`'s "Coverage is ARM64 ONLY" prose stale-by-behaviour on the same commit.
(b) The existing pin at `meta/__tests__/verifyRunnerBundle.test.ts:605-622` is `indexOf`-only and would
stay green if the x64 invocation were deleted.

### Q3 — Evidence bar for "the guard covers x64 and works"?

| Option | Description | Selected |
|--------|-------------|----------|
| Local RED on x64 + CI GREEN | Inject a broken symlink into a real downloaded x64 onedir tree, prove red naming `arch=x64`; CI proves execution. Reuses the guard-proof contract under AMENDMENT v2, no extra CI minutes. | ✓ |
| RED and GREEN both in CI | Strongest evidence that CI itself enforces it; costs two extra macOS runs and a deliberately-broken commit. | |
| CI GREEN only | Cheapest and satisfies item 13's literal wording, but proves only that the guard ran — the vacuous-gate shape. | |

**User's choice:** Local RED on x64 + CI GREEN.

## Digest pinning + drift (items 2 and 3)

### Q1 — How should the six real digests get into `meta/runnersOnedirDigests.json`?

| Option | Description | Selected |
|--------|-------------|----------|
| A pin script | `pnpm pin:runner-digests` fetches both `SHA256SUMS-{arch}` from the rolling release and records the source run id from `BUILD-MANIFEST-{arch}.json`. Repeatable, no transcription risk. | ✓ |
| Hand-pin from the run output | Fully auditable single commit, no new tooling — but error-prone and must be redone by hand on every rebuild. | |
| The workflow opens a PR | Pinning can never lag a rebuild; most machinery, and puts an automated writer on a file whose purpose is to be a human-reviewed pin. | |

**User's choice:** A pin script.

### Q2 — `--clobber` invalidates all six pins on every re-dispatch. How is drift handled?

| Option | Description | Selected |
|--------|-------------|----------|
| Let it throw, but name the run | Keep the mismatch as the drift detector (loud, fail-closed, writes nothing under `public/bin`), and add the pinned run id so the error says which run to re-pin from. | ✓ |
| Stop clobbering — version the assets | Old pins keep resolving and rebuilds never break checkouts, but the release grows forever and digest keys must carry a version. | |
| Let it throw, nothing more | Cheapest, no schema change; a developer must work out unaided that a rebuild happened. | |

**User's choice:** Let it throw, but name the run.

### Q3 — What proves items 2 and 3?

| Option | Description | Selected |
|--------|-------------|----------|
| Green fetch + RED digest + x64 executes | Clean-tree fetch transcript; a one-character digest corruption proving it throws and writes nothing; and running the extracted x64 runners under Rosetta. Proves fetch, verification, and payload. | ✓ |
| Green fetch + RED digest | Covers exactly what items 2 and 3 claim, in both directions — but leaves the x64 binaries' ability to run unobserved. | |
| Green fetch only | Lowest cost, but near-tautological since the pin script read those digests from the same publication. | |

**User's choice:** Green fetch + RED digest + x64 executes.
