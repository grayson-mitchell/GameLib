## Q1 — No-checkout commit to gamelib/main

**Constraint:** `.husky/post-checkout` runs `pnpm i && pnpm download-helper-binaries` on any checkout
in this worktree. Checking out anything based on `gamelib/main` fires it against a 3830-commit-old
tree; checking back to the feature branch fires it against the six `PENDING-CI-PUBLISH` sentinels,
which throws by design. **No checkout may occur in this worktree at any point in this recipe.**

### Verified: `gamelib/main` state at research time
- `gamelib/main` = `5ee2784ba`. HEAD is 3830 commits ahead of it; `main` is 4 commits ahead of the
  merge-base `9d45684d9` (2026-07-10). `main` carries 15 workflows;
  `build-runners-onedir-macos.yml` is **not** among them
  `[VERIFIED: git show gamelib/main:.github/workflows/build-runners-onedir-macos.yml → "fatal: path exists on disk, but not in 'gamelib/main'"]`.
- `main` has no branch protection rules configured
  `[VERIFIED: gh api repos/{owner}/{repo}/branches/main/protection]`. A plain ref push is not blocked
  by GitHub rules, but can still fail on non-fast-forward if `main` moves between research and push —
  the recipe below re-resolves `gamelib/main`'s tip immediately before building the tree, not from a
  cached value.

### Option A (recommended): `git commit-tree` plumbing

None of these commands touch this worktree's index, HEAD, or working tree. None of them fire git
hooks — hooks fire on `checkout`/`switch`/normal-flow `commit`, never on plumbing primitives operating
directly on the object database.

```bash
# 1. Resolve main's current tip fresh (never use a value captured earlier in the session)
MAIN_SHA=$(git rev-parse gamelib/main)

# 2. Hash the file to commit as a git blob object, writing it into the object database.
#    Precondition: the working-tree copy of the workflow file must already contain D-02's ref
#    guard and be otherwise final -- hash AFTER editing, never before.
BLOB_SHA=$(git hash-object -w .github/workflows/build-runners-onedir-macos.yml)

# 3. Build a new tree = main's tree + this one blob, using a scratch index file so the real
#    index (and therefore this worktree) is never touched.
export GIT_INDEX_FILE=$(mktemp)
git read-tree "$MAIN_SHA"
git update-index --add --cacheinfo 100644,"$BLOB_SHA",.github/workflows/build-runners-onedir-macos.yml
NEW_TREE=$(git write-tree)
unset GIT_INDEX_FILE

# 4. Create the commit object on top of main's tip, without checking anything out.
NEW_COMMIT=$(git commit-tree "$NEW_TREE" -p "$MAIN_SHA" -m "ci: publish build-runners-onedir-macos.yml to default branch")

# 5. Verify exactly one file differs between main and the new commit before pushing.
git diff-tree --no-commit-id --name-status -r "$MAIN_SHA" "$NEW_COMMIT"
# Expected output: exactly one line, "A       .github/workflows/build-runners-onedir-macos.yml"

# 6. HUMAN GATE (D-03) -- do not execute from a plan. Push only the constructed commit object,
#    never a local branch ref, and always to the `gamelib` remote, never `origin`.
git push gamelib "$NEW_COMMIT":refs/heads/main
```

**Byte-identity verification (D-02), post-push, still no checkout:**
```bash
git fetch gamelib main
diff <(git cat-file -p gamelib/main:.github/workflows/build-runners-onedir-macos.yml) \
     <(git cat-file -p HEAD:.github/workflows/build-runners-onedir-macos.yml)
# Exit 0 and no output = byte-identical
```
(`git rev-parse <ref>:<path>` alone only proves object-hash equality, which is equivalent to `diff`
returning clean for a single blob — either command is sufficient; `diff` is included because it is
self-documenting in a review.)

**Failure modes per step:**
| Step | Failure | Cause | Recovery |
|------|---------|-------|----------|
| 2 | `hash-object` succeeds but hashes stale content | Editing after hashing | Re-run step 2 after any further edit |
| 3 | `read-tree` fails "not a tree object" | `$MAIN_SHA` resolved before a `git fetch`, now stale/wrong | Re-run `git fetch gamelib` then re-resolve `MAIN_SHA` |
| 3 | Leftover `$GIT_INDEX_FILE` from a prior failed run | Forgot `unset` | Always `mktemp` a fresh path per attempt; never reuse |
| 5 | More than one line, or a `M`/`D` status | Tree built from wrong base or wrong blob path | Abort before push; do not proceed to step 6 |
| 6 | `! [rejected] ... (non-fast-forward)` | `main` moved after `MAIN_SHA` was resolved | Re-run steps 1-5 with a fresh `MAIN_SHA`, never `--force` |

**Verified live** in this session (2026-08-24): steps 1-5 were executed non-destructively against the
real repository (confirmed zero impact on this worktree's HEAD/index/branch via `git status` before
and after); step 6 was intentionally not executed, correctly deferred to the D-03 human gate.

**Verified this does not fire `.husky/post-checkout`:** `[VERIFIED: live clone + inspection, this session]`
`core.hooksPath` is a local, non-versioned git-config value. A fresh `git clone` starts with an empty
local config — `core.hooksPath` defaults to the (empty) `.git/hooks/` directory inside the new clone.
It is *never* set by `clone` itself; it is only ever wired to `.husky/` by package.json's
`"prepare": "husky install"` script, which npm/pnpm invoke automatically only on `pnpm install` — a
step this recipe deliberately never runs inside the scratch clone. Confirmed by inspecting the fresh
clone's `git config --local --list` (empty, no `core.hooksPath` entry) and `.git/hooks/` (only the
default `*.sample` files, no `post-checkout`). The clone's own `git commit` (a normal, non-plumbing
commit) is therefore also hook-free, since there is no `core.hooksPath` pointing at `.husky/` to fire.

**Tradeoff vs Option A:** Option B requires a network round-trip (full clone, even shallow) and a
second working directory outside this worktree; Option A is fully local and was more thoroughly
exercised in this session. Recommend Option A. Either is CONTEXT.md-compliant (Claude's Discretion
item 1).

### Layout-marker safety — the risk question D-11 depends on, definitively resolved

```typescript
// meta/downloadHelperBinaries.ts
export function computeLayoutMarker(layout: string, digests: Record<string, string>): string {
  const sortedKeys = Object.keys(digests).sort()
  const canonical = JSON.stringify({ layout, digests: Object.fromEntries(sortedKeys.map((key) => [key, digests[key]])) })
  return createHash('sha256').update(canonical).digest('hex')
}
export function darwinLayoutMarker(): string {
  return computeLayoutMarker(runnersOnedirDigests.layout, runnersOnedirDigests.digests)
}
```
`[VERIFIED: meta/downloadHelperBinaries.ts source, exact function bodies]` — `computeLayoutMarker()`
is called with exactly two arguments, `runnersOnedirDigests.layout` and `runnersOnedirDigests.digests`.
It is structurally incapable of seeing any other top-level key on the `runnersOnedirDigests` object,
because those two values are destructured out and passed positionally before the function ever sees
the parent object. **A new top-level field such as `runId` or `sourceRunId` added to
`meta/runnersOnedirDigests.json` cannot perturb the marker — this is a static code-structure fact, not
an inference from behavior.** No existing test explicitly proves this for a *sibling* key (see
Validation Architecture, Wave 0 Gaps), but the source-level guarantee is unambiguous.

**Consequence for the plan:** D-10's pin script may safely add a `runId` (or similarly named) field to
`meta/runnersOnedirDigests.json` without triggering an unwanted re-download for every developer on
every checkout — only `layout` or a `digests` value change does that, which is the intended trigger
for legitimate digest updates.

### The real gap: `BUILD-MANIFEST-{arch}.json` has no run id to record

D-10 states the pin script "record[s] the source run id from `BUILD-MANIFEST-{arch}.json`" — but as
shown above, that file currently has no such field. This is not a design choice available to the
planner; it is a missing prerequisite. Two ways to close it, both viable, left to planner/discretion
per D-10's own framing of the pin script as new tooling:

1. **Add a `runId` field to `writeBuildManifest()`'s output**, populated from `process.env.GITHUB_RUN_ID`
   (set automatically by GitHub Actions on every job) when present, `null` when run locally. This keeps
   the manifest self-describing and requires no extra API call from the pin script.
2. **Have `pin:runner-digests` separately query the GitHub Releases/Actions API** (`gh api
   repos/{owner}/{repo}/releases` or the runs API) to determine which run most recently published the
   asset it is pinning. More moving parts, and duplicates information the manifest could just carry.

Recommend option 1 — it is a small, localized addition to `writeBuildManifest()`, consistent with the
"provenance captured rather than remembered" rationale D-10 itself states, and keeps the pin script's
own logic to "fetch two files, parse, rewrite one file" rather than adding a second API surface.

## Q3 — x64 guard behaviour

**This question cannot be resolved by this research, and must not be.** Per CONTEXT.md constraint 3,
whether a real x64 onedir tree passes `verify:runner-bundle`'s structural checks "has never been
observed" and "this phase must preserve that." What follows is the full enumeration of what the guard
actually checks, and the evidence (not a verdict) for how likely each check is to be arch-neutral.

### Full enumeration of `meta/verifyRunnerBundle.ts` checks

| Check | Logic | Arch-neutral or arch-shaped? |
|-------|-------|------------------------------|
| `findDarwinBinRoot()` | Recursively searches for a directory ending `build/bin/{arch}/darwin`; throws naming root+arch if absent | Arch-neutral by construction — `arch` is a parameter, not a literal |
| `exists` | `existsSync` on each runner's binary path | Arch-neutral |
| `executable` | `mode & 0o111` on the binary | Arch-neutral — exec bit is not architecture-dependent |
| `isMachO` | Magic-byte sniff against `{0xfeedface, 0xfeedfacf, 0xcefaedfe, 0xcffaedfe, 0xcafebabe, 0xbebafeca}`, falls back to `file -b` | **Arch-neutral by design** — this magic set spans both x86_64 (`0xfeedfacf`/`0xcffaedfe` depending on endianness read direction) and arm64 thin/fat Mach-O headers; there is no arch-specific filtering |
| `FILE_COUNT_FLOOR = 20` | Plain integer literal, counts files under the runner's onedir tree | Arch-neutral literal, but **outcome-sensitive to packaging mode** — today's x64 tree fails this not because of arch but because it is still onefile (no `_internal`, no `Python.framework`); a real x64 onedir build should have a comparable file count to arm64's onedir build, but this has never been measured |
| `findFrameworks()` | Recursive `*.framework` directory search | Arch-neutral — generic glob, no version/slice names |

### Decision procedure once a real x64 onedir tree lands (D-07's local-RED evidence bar)

1. Run `pnpm download-helper-binaries` against real (post-D-11) digests to populate a genuine
   `public/bin/x64/darwin/{legendary,gogdl,nile}/` tree.
2. Run `pnpm verify:runner-bundle build --arch=x64` (or against `public/bin` per whatever root the
   guard is pointed at in the actual invocation) with **zero modification** to the tree.
3. **If PASS:** item 12 closes; proceed to injecting a broken symlink (below) to prove the RED
   direction, satisfying D-07 in full.
4. **If FAIL:** do not treat this as guard-vs-build ambiguous by default. Read the guard's own failure
   output — it names which specific check failed (`exists`/`executable`/`isMachO`/`FILE_COUNT_FLOOR`/
   `versionsCurrentIsSymlink`/etc., per `summarise()`'s per-item error tagging). Cross-reference:
   - If the failure is `FILE_COUNT_FLOOR` or a missing `Python.framework`/`_internal` entirely
     absent → **build bug** in `meta/buildRunnersOnedir.ts`'s x64 leg (the same failure mode
     documented for today's onefile x64 tree, constraint 3) — the onedir build itself did not produce
     the expected structure for x64.
   - If the failure is a symlink/`Versions/Current` check firing on a framework that visibly exists
     and looks structurally sound under manual `ls -la` inspection → **guard bug**, most likely the
     same F-34.9-01 class defect (a copy step somewhere dereferencing symlinks into real files) but
     now surfacing for x64 specifically, worth checking whether the x64 PyInstaller build path routes
     through a different copy mechanism than arm64's.
   - If uncertain from the message alone, manually inspect the reported path with `ls -la` and
     `file <path>` before concluding either way — do not guess from the check name alone.

## Common Pitfalls

### Pitfall 1: Resolving `gamelib/main`'s tip once and reusing it across a long session
**What goes wrong:** The push (step 6, Q1) fails non-fast-forward, or worse, a stale tip is used to
build a tree that silently drops a commit that landed on `main` in the interim.
**Why it happens:** `MAIN_SHA` was captured early in a planning/dispatch session and not refreshed.
**How to avoid:** Re-run `git fetch gamelib main` and re-resolve `git rev-parse gamelib/main`
immediately before building the tree, every time, especially right before the human-gated push.
**Warning signs:** Any gap of more than a few minutes between resolving `MAIN_SHA` and pushing.

### Pitfall 2: Treating a CI-green run alone as proof of D-07 or D-12
**What goes wrong:** A green `build-runners-onedir-macos.yml` run, or a green `verify:runner-bundle
--arch=x64` in CI, gets reported as "the guard is proven" when the evidence bar explicitly requires a
local RED-direction proof too.
**Why it happens:** Green CI is the easy, visible signal; the RED-direction injection is manual and
easy to skip under time pressure.
**How to avoid:** D-07 and D-12(b) are not optional — CI green is explicitly scoped as "execution
evidence only" in D-07's own text. Both directions must be demonstrated.
**Warning signs:** A LIVE-GATE document with only PASS transcripts and no injected-failure transcript.

### Pitfall 3: Assuming the pin script can be written exactly as D-10 describes today
**What goes wrong:** Implementing `pin:runner-digests` to "record the source run id from
BUILD-MANIFEST-{arch}.json" without first adding a run-id field to that manifest — the field simply
does not exist yet.
**Why it happens:** D-10's wording reads as if the field already exists.
**How to avoid:** Add the `runId` field to `writeBuildManifest()`'s output (from `GITHUB_RUN_ID`) as
an explicit prerequisite task before or alongside writing the pin script.
**Warning signs:** A pin-script implementation that reads `manifest.runId` and gets `undefined`.
