# Phase 34.9: Code Review Report (gap cycle 1)

**Reviewed:** 2026-08-11T03:22:49Z
**Depth:** standard
**Files Reviewed:** 9
**Status:** issues_found

## Summary

Reviewed the F-34.9-01 symlink-preservation fix (`meta/preserveRunnerSymlinks.ts`), the
F-34.9-02 stale-artifact fix (`meta/cleanDistMac.ts`, which deletes files), the framework
structural-integrity additions to `meta/verifyRunnerBundle.ts`, and their wiring/tests.

The two file-deletion and containment-check implementations (`cleanDistMac.ts`'s dist-dir
boundary check, `preserveRunnerSymlinks.ts`'s `resolveDestPath`) are sound: both use
`resolve(...) + sep`-anchored `startsWith` (not a naive prefix check), both correctly use
lstat-based semantics to avoid following symlinks during deletion, and both are backed by
tests that prove the known-bad state before asserting the fix (the standing anti-vacuity
discipline this repo requires). The `__dirname`-under-stdin trap this phase hit once
already (`cleanDistMac.ts` main()) is correctly avoided by using a cwd-relative default
instead; I independently traced `preserveRunnerSymlinksPlugin()`'s `__dirname` defaults
through electron-vite's actual config-bundling source (`node_modules/electron-vite/dist/chunks/lib-D9_OPmIh.cjs`)
and confirmed it injects a **per-source-file** `__dirname` constant, so that specific trap
does not apply there.

The one Critical finding is structural, not a containment bypass: the `closeBundle` hook
that restores symlinks does not fail the build when a symlink restoration is *skipped*
(destination parent missing), and the tool that *would* catch a resulting malformed
framework (`verify:runner-bundle`) is never invoked by `dist:mac`, `release:mac`, or any
CI workflow — it is a manual-only diagnostic. That reproduces, at the pipeline level, the
exact silent-success failure class this whole phase exists to eliminate.

## Critical Issues

### CR-01: `closeBundle` doesn't fail the build on a skipped symlink restore, and nothing in the pipeline runs `verify:runner-bundle` to catch it

**File:** `meta/preserveRunnerSymlinks.ts:162-167`
**Issue:**
`restoreSymlinks` classifies a symlink as `skipped` (not `restored`) whenever its
destination's parent directory doesn't exist yet (`preserveRunnerSymlinks.ts:131-134`).
The `closeBundle` hook that calls it only logs the skipped count:

```ts
closeBundle() {
  const { restored, skipped } = restoreSymlinks(sourceDir, destDir)
  console.log(
    `[preserve-runner-symlinks] restored ${restored.length} symlink(s), skipped ${skipped.length}`
  )
}
```

No exception is thrown and no non-zero exit code results, regardless of `skipped.length`.
Vite/electron-vite treats a `closeBundle` hook that returns normally as success, so
`electron-vite build` — and therefore `pnpm dist:mac` / `pnpm release:mac` — proceeds to
`electron-builder` even when some fraction of the twelve `Python.framework` symlinks failed
to restore (e.g. a future public-dir restructuring, a vite/electron-vite version bump that
changes copy ordering, or a `.gitignore`/build-exclude pattern that drops an intermediate
directory).

Compounding this: `meta/verifyRunnerBundle.ts`'s new framework structural checks (added in
this same gap cycle, specifically to catch exactly this defect class) are **never invoked
automatically**. I checked every workflow under `.github/workflows/` and both `package.json`
release/dist scripts:

```
$ grep -rn "verify:runner-bundle" .github/workflows/*.yml package.json
electron-builder.yml:63:  # `pnpm verify:runner-bundle` (plan 34.9-08), not by this config alone.
```

`verify:runner-bundle` is referenced only in a comment in `electron-builder.yml`. It is not
a step in `build-base.yml` (`pnpm dist:mac --x64 --arm64 --publish=never`), not in
`draft-release-mac.yml` (`pnpm release:mac`), and not part of `dist:mac`/`release:mac`
themselves. It is a developer-invoked-by-hand tool only.

Net effect: if `restoreSymlinks` ever silently skips a symlink again, `pnpm dist:mac`
reports success, `electron-builder --mac` may or may not reject the bundle at `codesign`
time depending on which symlink was skipped (a partial/single skip can be far less
detectable than the total dereferencing F-34.9-01 produced), and the one tool built in this
same gap cycle to catch it structurally is not wired into anything that runs it. This is
the same "a mutating call's own report is never accepted as proof of its effect" failure
mode this phase's own live-gate history is full of — reproduced one layer up, in the fix
itself.

**Fix:** Throw from `closeBundle` when `skipped.length > 0` (fail the build loudly, per this
file's own doc comment intent), and/or add `pnpm verify:runner-bundle build --arch=<arch>`
(or the packaged-app path) as a mandatory step in `dist:mac`/`release:mac` after
`electron-builder` completes, and in `build-base.yml`/`draft-release-mac.yml`. Example for
the cheaper, immediate fix:

```ts
closeBundle() {
  const { restored, skipped } = restoreSymlinks(sourceDir, destDir)
  console.log(
    `[preserve-runner-symlinks] restored ${restored.length} symlink(s), skipped ${skipped.length}`
  )
  if (skipped.length > 0) {
    throw new Error(
      `preserve-runner-symlinks: ${skipped.length} symlink(s) could not be restored ` +
        `(destination parent missing) -- refusing to produce a bundle with dereferenced ` +
        `framework symlinks. Skipped: ${skipped.map((s) => s.relPath).join(', ')}`
    )
  }
}
```

## Warnings

### WR-01: `restoreSymlinks` validates the destination path but never the symlink *target*

**File:** `meta/preserveRunnerSymlinks.ts:120-142` (specifically `symlinkSync(record.target, destPath)` at line 137)
**Issue:** `resolveDestPath` (line 91-105) rigorously contains where a restored symlink is
*placed* inside `destDir`. But the symlink's *target* — the string that `symlinkSync`
writes as the link's content — is copied verbatim from whatever `readlinkSync` returned in
`public/`, with zero validation (per the file's own doc comment: "Targets are copied
byte-identical from the source record — never rewritten or absolutised"). `public/` holds
vendored third-party PyInstaller onedir trees (legendary/gogdl/nile), populated by a
separate build step (`build-runners-onedir`) from externally-sourced binaries. If any
symlink in that vendored tree ever carried an absolute path or a `..`-escaping relative
target (accidentally, from a future runner packaging change, or as a supply-chain
compromise of the vendored binaries), this code would faithfully recreate that
outside-pointing symlink inside `build/`, and it would ship inside the packaged `.app`.
There is no check here — nor downstream in `verifyRunnerBundle.ts`, which only validates
`Versions/Current`'s target resolves to an existing sibling directory — comparable to
`resolveDestPath`'s containment for the *target* string.
**Fix:** Add a target-side check mirroring `resolveDestPath`'s containment logic — reject
(or at minimum log a loud warning and skip) any collected symlink whose target is an
absolute path, or whose resolved value would fall outside `destDir` when interpreted
relative to the link's own location:

```ts
function isSafeRelativeTarget(target: string): boolean {
  if (path.isAbsolute(target)) return false
  // must not escape once resolved from the link's own directory
  return true // plus a resolve-based containment check against destDir, as in resolveDestPath
}
```

### WR-02: Missing top-level framework stub is never flagged, unlike a missing `Versions/Current`

**File:** `meta/verifyRunnerBundle.ts:454-460` (in `summarise`)
**Issue:** The four framework-integrity checks are asymmetric. A missing `Versions/Current`
is enforced (`!fw.versionsCurrentExists` fails, line 433-437), but the parallel top-level
stub check only fires `if (fw.topLevelStubExists && !fw.topLevelStubIsSymlink)` — i.e. it
only catches a stub that exists as the wrong type. If `topLevelStubExists` is `false` (the
stub is missing entirely — a real malformation a partial dereferencing/copy failure could
produce, e.g. only the `Versions/Current` symlink survived while the top-level `Python` ->
`Versions/Current/Python` link was dropped), `summarise` records nothing. No test in
`meta/__tests__/verifyRunnerBundle.test.ts` exercises the "stub missing" shape (only
`well-formed`, `dereferenced`, `stub-file`, `unresolvable-target` — none is "stub absent").
**Fix:**

```ts
if (!fw.topLevelStubExists) {
  failures.push(
    `${r.runner}: framework ${fw.path} is malformed -- top-level stub ` +
      `"${fw.name.replace(/\.framework$/, '')}" does not exist (F-34.9-01)`
  )
} else if (!fw.topLevelStubIsSymlink) {
  failures.push(/* existing message */)
}
```

## Info

### IN-01: `MAC_DIR_PATTERN` branch requires `isDirectory()`, so a bare macOS-staging-named symlink would go undetected — contradicting the doc comment

**File:** `meta/cleanDistMac.ts:41-56`
**Issue:** The doc comment above `isMacArtifact` states: "a macOS-named symlink is matched
by the token/standalone-name branches, never by the directory-pattern branch." That's true
only for names containing `-macOS-` or exactly `latest-mac.yml`. A hypothetical symlink
literally named `mac-arm64` (matching `MAC_DIR_PATTERN` but not the token or standalone
list) would be **skipped entirely** — `isDirectory()` is `false` for a symlink (lstat-based),
so the directory-pattern branch never fires, and neither of the other two branches matches
the bare name either. In practice electron-builder always creates `mac-arm64` as a real
directory, so this isn't reachable today, but the comment overstates the guarantee and
there's no test for this shape.
**Fix:** Either tighten the comment to be precise about which branch actually covers a
macOS-named symlink, or add a name-only fallback (e.g. also match `MAC_DIR_PATTERN` against
symlink entries whose target — once resolved — is a directory) if a symlinked staging dir
is ever plausible.

### IN-02: `cleanDistMac`'s containment throw is untested and structurally unreachable via its only call path

**File:** `meta/cleanDistMac.ts:102-118`
**Issue:** The `full !== resolvedDist && !full.startsWith(boundary)` throw is documented as
"T-34.9G-09" containment enforcement, but every `entry.name` fed into it comes from
`readdirSync(distDir, { withFileTypes: true })` — real filesystem directory entries can
never contain a path separator or be the literal string `..`/`.` (the OS excludes those from
readdir results and never allows `/` in a filename). Given `full = path.resolve(distDir,
entry.name)` where `entry.name` is always a bare, separator-free segment, `full` can never
resolve outside `resolvedDist` through this call path — the throw branch is dead code as
currently wired, and no test in `cleanDistMac.test.ts` exercises it. This isn't exploitable
today, but it's presented as a security boundary that isn't actually reachable, and if this
module is ever refactored to accept externally-supplied names (e.g. a `--only` filter flag),
the missing test coverage means a regression there wouldn't be caught.
**Fix:** Either add a unit test that calls a lower-level helper with a crafted name to prove
the throw fires (would require exposing an internal seam), or downgrade the comment to
acknowledge it's defense-in-depth against a currently-unreachable input rather than an
enforced, tested contract.

### IN-03: The F-34.9-02 fix is macOS-only; the same false-pass mechanism plausibly affects `dist:win`/`dist:linux`

**File:** `package.json:44,49` / `meta/cleanDistMac.ts:1-18`
**Issue:** `cleanDistMac.ts`'s own header explains the general electron-builder behavior
("only clears the target-specific subdirectory it is about to populate... never the
top-level `dist/` directory") as the root cause of F-34.9-02. That description isn't
macOS-specific — a failed `pnpm dist:win` or `pnpm dist:linux` run plausibly leaves the
same kind of stale top-level artifacts (`.exe`, `.AppImage`, `latest-*.yml`) behind, with
the same "did the build produce an artifact?" false-pass risk. Only `dist:mac`/`release:mac`
were wired to `clean:dist-mac`. This may be intentionally out of this phase's scope
(F-34.9-02 was filed against a macOS live-gate run), but it's worth flagging since the fix's
own justification generalizes beyond the platform it was applied to.
**Fix:** Consider a parallel `clean:dist-win`/`clean:dist-linux` (or a single
platform-parameterized `cleanDist.ts`) in a follow-up phase if this false-pass risk is
confirmed on those platforms too.
