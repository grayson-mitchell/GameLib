### A blocking bug found and fixed while exercising the script for real (Rule 1)

34.9-06 deliberately never ran `pnpm download-helper-binaries` to completion ("this plan writes no
binaries and performs no real GitHub network calls... `pnpm download-helper-binaries` is
deliberately not run to completion"). This plan is the first real invocation, and it immediately
crashed with an unrelated, pre-existing bug:

```
$ pnpm download-helper-binaries
Error: Missing required --arch=<x64|arm64> argument
    at parseArgs ([stdin]:25272:11)
    at main ([stdin]:25291:28)
```

Root cause: `meta/downloadHelperBinaries.ts` does `import { archiveName } from
'./buildRunnersOnedir'`. esbuild bundles both files into one script executed via plain `node`.
`buildRunnersOnedir.ts`'s own trailing guard, `if (!process.env.JEST_WORKER_ID) { main().catch(...)
}`, fires as a side effect of merely being imported — not only when it is the actual entrypoint —
because bundling erases the module boundary and `JEST_WORKER_ID` alone cannot distinguish "the
script that was invoked" from "a dependency of the script that was invoked." `buildRunnersOnedir`'s
own `main()` requires `--arch=`, which `download-helper-binaries` never supplies (it takes no CLI
arguments at all), so it threw and `process.exit(1)`'d before `downloadHelperBinaries.ts`'s own
guarded `main()` ever ran. This is a genuine, in-scope bug directly blocking this task's own
required action ("run the vendoring script end to end"), not a pre-existing unrelated issue — it
was introduced by 34.9-06's new import and had never been exercised outside Jest (where
`JEST_WORKER_ID` correctly suppresses both guards) until this plan's first real invocation.

Fix (Rule 1): `buildRunnersOnedir.ts`'s guard now also requires `--arch=` to be present in
`process.argv` before auto-invoking `main()` — a no-op for every legitimate direct invocation
(`pnpm build-runners-onedir --arch=<x64|arm64>` always supplies it; verified via
`.github/workflows/build-runners-onedir-macos.yml:107`), and prevents the accidental auto-run when
merely imported for `archiveName`. Verified: `npx tsc --noEmit` clean;
`npx jest meta/__tests__/buildRunnersOnedir.test.ts meta/__tests__/downloadHelperBinaries.test.ts`
69/69 passing; `npm run test:ci` 235/235 suites, 4598/4598 tests, exit 0 (no regression).

`workflow_dispatch` API requires the workflow file to be present on the repository's default
branch before it can be run via `gh workflow run` (or the Actions "Run workflow" UI) against ANY
ref, including a ref that already contains the file. This plan's authorization is scoped to
pushing `fix/steam-native-install-stability` only, dispatching the workflow, and publishing the
release — it does not extend to pushing `main` or opening a pull request, so this blocker cannot
be resolved within this plan's authorized actions.

**To close this blocker:** get `.github/workflows/build-runners-onedir-macos.yml` onto `main` (a
PR merge is the normal path), then re-run this plan's Task 1/Task 2 sequence: `gh workflow run`
will succeed once the workflow is registered, the real x64 leg can finally be built (it has never
existed anywhere, on any machine, at any point in this phase), and the six sentinels in
`meta/runnersOnedirDigests.json` can be replaced with digests transcribed from that run's own
`SHA256SUMS-{arch}` assets.

Until then: `meta/runnersOnedirDigests.json` still throws by design on a clean checkout (verified
above), the x64 leg is entirely UNPROVEN with zero artifacts anywhere, and only arm64 (from a local,
non-CI, non-digest-verified build) is staged for plan 34.9-11's gate to exercise.
