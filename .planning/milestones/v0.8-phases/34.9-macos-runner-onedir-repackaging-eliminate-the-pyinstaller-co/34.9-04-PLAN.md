.github/workflows/build-crossover-index.yml — the rolling-release pattern to copy verbatim in
shape. Its three moves and the reason for each:

  gh release view crossover-index >/dev/null 2>&1 || \
    gh release create crossover-index --title "..." --notes "Rolling artifact... Not a GameLib release." \
      --prerelease --latest=false
  gh release edit crossover-index --prerelease --latest=false     # self-heal every run
  gh release upload crossover-index <assets> --clobber

`--prerelease` is load-bearing, not decorative: `--latest=false` alone is insufficient because
GitHub forces a repo's sole non-draft/non-prerelease release to "Latest" regardless. That comment
in the source file records a Phase 19 lesson (`prerelease-not-Latest`) — carry the reasoning across.

.github/actions/install-deps/action.yml — the project's composite setup action. Its LAST step is
`run: pnpm download-helper-binaries`. **This workflow MUST NOT use that composite action**: the
downloader (after plan 34.9-06) will try to fetch the very darwin archives this workflow has not
published yet, so using it would make the first run fail on a chicken-and-egg. Do the pnpm/node
setup inline instead.

src/backend/__tests__/helpers/workflowSteps.ts — existing shared helpers for workflow tests:

Create `.github/workflows/build-runners-onedir-macos.yml` named
`Build macOS onedir runners`, triggered by `workflow_dispatch` ONLY (no schedule, no `v*` tag
trigger — `RELEASE_TAGS` changes rarely and coupling this to a release cadence would rebuild all
three runners on every tag push for nothing). Declare `permissions: contents: write` at workflow
level and use `${{ github.token }}` as `GH_TOKEN` — never a PAT.

Two jobs.

`prepare-release` runs on `ubuntu-latest` and owns release creation exclusively, so the two build
legs cannot race each other into a duplicate `gh release create`. Its single `run: |` step does the
view-or-create, then the self-healing `gh release edit ... --prerelease --latest=false`, against
tag `runners-onedir-macos`, titled `macOS onedir runner builds`, with notes stating it is a rolling
build artifact consumed by `meta/downloadHelperBinaries.ts` and is not a GameLib release. Carry
across build-crossover-index.yml's comment explaining why `--prerelease` is required in addition to
`--latest=false`.

`build` declares `needs: prepare-release`, `strategy.fail-fast: false`, and
`strategy.matrix.include` with exactly two entries: `{ os: macos-13, arch: x64 }` and
`{ os: macos-14, arch: arm64 }`. It runs on `${{ matrix.os }}` with these steps:

  - `actions/checkout@v6`
  - `pnpm/action-setup@v4`
  - `actions/setup-node@v6` with `node-version-file: 'package.json'` and `cache: 'pnpm'`
  - `actions/setup-python@v5` with `python-version: '3.12'`
  - `pnpm install` (NOT the install-deps composite action, and no `download-helper-binaries` step)
  - a guard step that fails the leg with a clear `::error::` if `uname -m` does not match the
    matrix arch (`x86_64` for x64, `arm64` for arm64) — PyInstaller cannot cross-compile, so a
    GitHub image change that silently flips macos-13 to Apple Silicon must break the build loudly
    rather than publish a mislabelled x64 asset
  - `pnpm build-runners-onedir --arch=${{ matrix.arch }}`
  - an upload step whose `run: |` body uploads, with `--clobber`, the three
    `.build-tools/runners-onedir/out/*_onedir.tar.gz` archives for this arch plus
    `SHA256SUMS-${{ matrix.arch }}` and `BUILD-MANIFEST-${{ matrix.arch }}.json`. The sums and
    manifest filenames are arch-suffixed precisely so the two legs cannot clobber each other's.
  - a final step printing `shasum -a 256 -c SHA256SUMS-${{ matrix.arch }}` output so the published
    digests are visible in the run log for plan 34.9-09 to pin.

Add a file-header comment recording: that this workflow is the sole producer of the x64 onedir

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| GitHub Actions runner → GameLib's own GitHub Releases | this workflow gains write access to publish executable artifacts that end users' installs will later download and run |
| third-party GitHub Actions → the runner | each `uses:` step executes code this repo does not own |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-34.9-01 | Tampering | published runner archives | mitigate (partial, completed by plan 34.9-06) | The workflow emits `SHA256SUMS-${arch}` alongside the archives so the digests are recorded at build time in the same run log. The fetch-side control — verifying against digests committed IN-REPO, which is strictly stronger than `meta/downloadZig.ts`'s same-round-trip TOFU — lands in plan 34.9-06 and is pinned in plan 34.9-09. This workflow alone does not close the threat; it produces the material the closure needs. |
| T-34.9-08 | Information disclosure | `GH_TOKEN` | mitigate | `permissions: contents: write` declared at workflow level (least privilege for what publishing needs) and `${{ github.token }}` used rather than a personal access token, matching `build-crossover-index.yml`. No secret is echoed; the digest-printing step prints only `shasum -c` output. |
| T-34.9-09 | Tampering | third-party actions in `uses:` | mitigate | Pinned to the same major tags already vetted and in use across this repo's workflows (`actions/checkout@v6`, `pnpm/action-setup@v4`, `actions/setup-node@v6`, `actions/setup-python@v5`). No new action publisher is introduced by this phase. |
| T-34.9-16 | Spoofing | mislabelled arch artifact | mitigate | The `uname -m` guard step fails the leg when the runner image's actual architecture does not match its matrix label, so a GitHub image change cannot cause an arm64 build to be published under the x86_64 filename — which would produce a silently unlaunchable runner on Intel Macs. |
| T-34.9-17 | Denial of Service | two legs racing on `gh release create` | mitigate | Release creation is isolated in the `prepare-release` job that `build` declares `needs:` on, so exactly one create/self-heal happens per run; per-arch `SHA256SUMS` filenames prevent the legs' `--clobber` uploads from destroying each other's digests. |
| T-34.9-SC | Tampering | package installs in CI | mitigate | The workflow adds no npm/pip package of its own; `pnpm install` installs the already-committed lockfile, and every pip install is performed by `meta/buildRunnersOnedir.ts` under plan 34.9-01's pinned-requirements discipline. No `[ASSUMED]`/`[SUS]` package is introduced, so no legitimacy checkpoint is owed. |
</threat_model>
