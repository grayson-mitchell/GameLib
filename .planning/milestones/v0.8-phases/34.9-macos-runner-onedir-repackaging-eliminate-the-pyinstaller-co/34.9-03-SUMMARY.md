# Phase 34.9 Plan 03: Per-Runner Onedir Build + Measurement Summary

**All three runners (legendary, gogdl, nile) built for real as `--onedir` bundles on arm64 by the committed script -- three real Rule-1 bugs found and fixed live in the process -- then measured cold/warm against their own vendored onefile controls; the measurement's own validity anchor FAILED, so the run is declared INVALID rather than reporting a fabricated per-runner win.**

## Accomplishments
- **Task 1:** All three runners (legendary `0.20.43`, gogdl `v1.2.1`, nile `v1.1.2`) built as real `--onedir` bundles on this arm64 dev machine, using the committed `meta/buildRunnersOnedir.ts`. Every extracted binary verified executable AND functionally correct (`--version` succeeds and prints the expected version string) -- not merely "archive exists and file is executable," which the plan's own acceptance criteria would have accepted even for a runtime-broken binary.
- Three real, previously-undiscovered defects in the shared builder script were found and fixed live, since plan 34.9-01 only ever proved the path against nile (the other two runners' workflow shapes were inspected but never actually built):
  1. legendary declares its pyinstaller step identically in two committed workflow files (`python.yml` and `release.yml`) -- the extractor's "exactly one match" rule threw a false ambiguity error.
  2. legendary's real Build step runs with `working-directory: legendary`, which the extractor never captured -- the derived command failed with `Script file 'cli.py' does not exist` until the build's own spawn cwd (and dist/ lookup path) were corrected to fold in that sibling key.
  3. heroic-gogdl vendors `xdelta3` as a git submodule the plain clone never fetched (`ELIFECYCLE ... xdelta3/xdelta3.h file not found`), fixed with `--recurse-submodules`; and even after that, the resulting onedir gogdl binary crashed at runtime (`ModuleNotFoundError: No module named 'gogdl.xdelta3'`) until dependency install was switched from a regular `pip install .` to the editable `pip install -e .` upstream's own CI actually uses -- confirmed live, isolating the Python interpreter version (3.14 vs 3.11) as NOT the cause.
- **Task 2:** Ran the full six-pair cold/warm measurement harness to completion (all six raw samples captured, no hand-editing). Applied the harness's own binding validity anchor in writing: `nile-onefile`'s cold reading (7.91s) failed the required >=10s threshold, and this was corroborated by three additional independent same-protocol diagnostic reads (8.13s, 4.56s, 8.06s) taken before committing to the full 40-minute run -- a repeated, consistent condition, not a single misread. Per the plan's rule, the entire run is declared INVALID; no PASS/FAIL ratio is reported for legendary or gogdl, and `Assumption A3` / `Open Question 3` remain genuinely open.
- Bundle-growth figures were still recorded per runner (unaffected by the timing void): legendary ~2.3x (30M vs 13M), gogdl ~2.3x (25M vs 11M), nile ~3.6x (29M vs 8.1M) -- so the "2.2x cost" claim is no longer nile-only, even though the timing win claim could not be confirmed this run.

## Decisions Made
- **Declared the run INVALID rather than reporting per-runner ratios.** The plan's binding validity anchor exists precisely for this scenario. Continuing to report a 17.6x legendary / 3.0x gogdl / 2.3x nile ratio table as if it were a real finding, when the run's own control failed to reproduce a cold condition four independent times, would have been exactly the "fabricated confidence" threat (T-34.9-15) the anchor is designed to catch. The raw numbers are recorded in §4 of the MEASUREMENT.md for transparency, explicitly labeled as not-a-verdict.
- **Fixed the shared builder script's real bugs rather than working around them.** All four fixes are Rule 1 (bugs blocking the plan's own required real-build verification step) and all derive their corrected behavior from each upstream repo's own committed text (workflow YAML, `.gitmodules`, the exact `pip install -e .` step) -- none of them constitute the "hand-rolled pyinstaller invocation" the plan explicitly forbids.
- **Reported bundle-growth figures despite the void timing verdict.** `du -sh` disk-layout facts are static and not subject to the same machine-load/cache-state confound that invalidated the timing samples, so withholding them would have been overly conservative.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] Byte-identical pyinstaller invocation across two workflow files falsely treated as ambiguous**
- **Found during:** Task 1's real legendary build (first attempt)
- **Issue:** `extractUpstreamPyinstallerCommand` threw "found 2" -- legendary's `python.yml` (CI check) and `release.yml` (release job) both declare the exact same pyinstaller command. The extractor's "exactly one match" rule did not distinguish "one command, declared twice" from genuine ambiguity.
- **Fix:** Only throw when the DISTINCT command texts number more than one; the error message still names every matching file.
- **Files modified:** `meta/buildRunnersOnedir.ts`, `meta/__tests__/buildRunnersOnedir.test.ts` (added a positive test for this exact shape; existing ambiguous-case test, which uses genuinely different commands, still passes)
- **Verification:** 26/26 tests green after the fix; real legendary build proceeded past this step.
- **Committed in:** `03f8dc4a5`

**2. [Rule 1 - Bug] working-directory: step key never captured, breaking legendary's real build**
- **Found during:** Task 1's real legendary build (second attempt, immediately after fix 1)
- **Issue:** legendary's real `Build` step declares `working-directory: legendary`, so its `cli.py` / `../assets/windows_icon.ico` arguments (and PyInstaller's own default `--distpath`) resolve relative to `<repo>/legendary`, not the repo root. The builder always spawned pyinstaller with `cwd=repoDir`, failing with `Script file 'cli.py' does not exist`.
- **Fix:** `extractUpstreamPyinstallerCommand` now also walks backward from the `run:` key to capture a sibling `working-directory:` key within the same step's mapping (never crossing a prior step's `- name:` boundary), returning it alongside the command. `buildRunner` folds it into both the spawn cwd and the `dist/` lookup path. Recorded in `RunnerBuildResult`/`BUILD-MANIFEST-arm64.json` as `upstreamWorkingDirectory` for audit.
- **Files modified:** `meta/buildRunnersOnedir.ts`, `meta/__tests__/buildRunnersOnedir.test.ts` (added a positive capture test matching legendary's real shape)
- **Verification:** 27/27 tests green; real legendary build succeeded end to end, producing a 109-file/104-Mach-O archive.
- **Committed in:** `92d3ef49e`

**3. [Rule 1 - Bug] heroic-gogdl's vendored xdelta3 git submodule never fetched**
- **Found during:** Task 1's real gogdl build (first attempt)
- **Issue:** heroic-gogdl declares `xdelta3` (`jmacd/xdelta.git`, pinned commit) as a git submodule and its own CI checks it out with `submodules: 'true'`. The builder's plain `git clone --depth 1` left `xdelta3/` empty, so `pip install .`'s native-extension build failed: `xdelta3/xdelta3.h file not found`.
- **Fix:** Added `--recurse-submodules` to the clone invocation. Deliberately NOT `--shallow-submodules` -- the pinned submodule commit is not guaranteed to be the submodule's own branch tip, and a shallow submodule clone can fail to reach an older pinned commit.
- **Files modified:** `meta/buildRunnersOnedir.ts`
- **Verification:** Real gogdl build's dependency-install step succeeded after the fix.
- **Committed in:** `67703de71`

**4. [Rule 1 - Bug] gogdl onedir binary built successfully but crashed at runtime -- regular install instead of upstream's editable install**
- **Found during:** Task 1's own required post-build sanity check (`gogdl --version`), immediately after fix 3
- **Issue:** The archive built with exit 0 and the extracted binary was executable, but `--version` crashed: `ModuleNotFoundError: No module named 'gogdl.xdelta3'`. `pyinstaller`'s own `build/gogdl/warn-gogdl.txt` recorded `missing module named 'gogdl.xdelta3'` during analysis, even though the compiled `.so` was present in the venv's site-packages after a regular `pip install .`.
- **Fix:** heroic-gogdl's own CI runs this step as `pip3 install -e .` (editable), not a plain install. Confirmed empirically on this machine, isolating the Python interpreter as a variable (tested both 3.14 and 3.11): a regular install reproduces the missing-module warning on BOTH interpreter versions; only an editable install resolves it, on both. gogdl is the only `ONEDIR_RUNNERS` repo with no `requirements.txt`, so this only changes gogdl's build path; legendary/nile both declare one and use the `pip install -r` branch, untouched.
- **Files modified:** `meta/buildRunnersOnedir.ts`
- **Verification:** Rebuilt gogdl alone; extracted binary's `--version` now succeeds (`1.2.1`) with the compiled extension present at `_internal/gogdl/xdelta3.cpython-314-darwin.so`. Full clean three-runner rebuild afterward confirmed all three (`legendary --version`, `gogdl --version`, `nile --version`) succeed with exit 0.
- **Committed in:** `3694a48fa`

## Issues Encountered
- **Accidental literal NUL byte introduced into `meta/buildRunnersOnedir.ts` during an edit** (a tool-level artifact, not a logic bug): one edit's template-literal separator was written into the file as a raw `\x00` byte instead of the intended plain character, making `grep`/`file` treat the source as binary data. Caught immediately (`file` reported `data` instead of `ASCII text`), fixed by rewriting the byte to a plain space and then to a `JSON.stringify`-based pairing for robustness. Re-verified `file` reports `ASCII text`, `npx esbuild --bundle` succeeds, and the full test suite is green. No commit was ever made with the corrupted byte present.
- **Bash tool's `pgrep`-based polling loop hit the harness tool's 10-minute max timeout** once during the FIRST (later-discarded) measurement attempt, combined with a `grep -c ... || echo 0` bug that double-printed counts and broke the loop's integer comparison. Neither affected any committed artifact -- the first attempt's evidence file was discarded and the whole six-pair run was restarted cleanly with a corrected polling loop before the final, committed evidence was captured.
- **The measurement's own validity anchor failed** (see Deviations/Decisions above) -- not a bug in this plan's own work, but the central finding this plan exists to surface honestly. Four independent, correctly-executed 400s-idle cold reads of the identical vendored `nile` onefile binary all landed in the 4-8s range, well under both the 10s validity threshold and the ~20.84s/21.27s reference figure. System load average was elevated (5.2-6.2) and free memory low (~70MB) throughout the run, immediately following Task 1's own heavy build activity (three real clone/venv/pip/pyinstaller cycles) -- recorded as the leading candidate in 34.9-MEASUREMENT.md §3, but explicitly not proven, matching the debug session's own "do not over-fit the decay curve" caveat.
