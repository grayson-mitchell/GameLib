# Phase 34.9 Plan 18: Guard preserveRunnerSymlinks against silent partial restores and unsafe symlink targets Summary

**`closeBundle` now throws instead of logging-and-returning on any unrestored symlink, and a new `isContainedSymlinkTarget` guard rejects absolute or `..`-escaping symlink targets sourced from the untrusted vendored onedir trees before they can be written into `build/` — closing CR-01 and WR-01.**

## Accomplishments

- Guard A (CR-01): `preserveRunnerSymlinksPlugin`'s `closeBundle` throws an `Error` — `preserve-runner-symlinks: refusing to emit a bundle with unrestored symlink(s)` — whenever `restoreSymlinks` reports a non-empty `skipped` or `rejected` bucket, instead of printing a count and returning normally. This stops `electron-builder` from ever running over a partially-restored tree.
- Guard B (WR-01): new exported `isContainedSymlinkTarget(destDir, relPath, target)` rejects any symlink target string that is absolute, or that is relative but escapes `resolve(destDir)` when resolved from the link's own directory. `restoreSymlinks` now returns a third `rejected` bucket and applies this check strictly before `rmSync`, so a rejected record's destination is left untouched rather than deleted-and-not-replaced.
- Both guards' failing directions are proven with fixtures, each preceded by a vacuity-guard assertion that the fixture's own bad state genuinely exists before the guard under test is invoked. Both guards' passing directions are proven: all four real vendored target strings are accepted (zero false positives on the shipping shape), a healthy destination restores without throwing, and a symlink-free tree is a silent no-op.
- Guard A's passing direction is additionally proven at build level: a real `electron-vite build` on this checkout (which has the vendored darwin onedir trees present) restored all 12 symlinks with `skipped 0, rejected 0` and did not throw.

### Honesty statement (verbatim in spirit, per the plan's constraint)

**Guard A's FAILING direction is proven at unit level only.** It is not reachable from a real build today: `public/bin/.gitignore` git-ignores the vendored darwin onedir trees, so on a fresh checkout, on any Linux/Windows machine, and on any macOS machine that has not yet run `build-runners-onedir`, `collectSymlinks` returns `[]` and both `skipped`/`rejected` stay empty — there is nothing for the throw to fire on. This plan's build-level observation (above) proves only that the throw does **not** fire on a healthy build; it does not and cannot demonstrate the throw firing against a real, partially-restored build. ## Decisions Made

- Target-containment check is placed strictly before `rmSync` and before the parent-missing check in `restoreSymlinks`'s loop, so a rejected record's destination is left exactly as vite's copy left it rather than being deleted with nothing to replace it (T-34.9-18-02).
- `isContainedSymlinkTarget` resolves relative targets from the link's OWN directory (not from `destDir`), matching real symlink resolution semantics, and stays lexical (no `realpathSync`) so the check does not depend on the destination existing yet and cannot be skewed by a symlinked temp root — mirroring `resolveDestPath`'s existing idiom.
- Guard A's disposition (defense-in-depth, unit-proven only) is stated in both the code comment and this SUMMARY per the plan's honesty constraint, rather than being allowed to drift toward an overstated "build-level tripwire" claim.
