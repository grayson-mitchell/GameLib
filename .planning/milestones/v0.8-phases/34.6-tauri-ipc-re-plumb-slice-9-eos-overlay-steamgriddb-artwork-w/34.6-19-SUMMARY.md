### Auto-fixed Issues

**1. [Rule 3 - Blocking] `testContainment.test.ts`'s directory tripwire failed after adding `gamelibNamespaceLoad.test.ts`**
- **Found during:** Task 1 verification (full Backend suite run)
- **Issue:** `testContainment.test.ts`'s Block C test (`T-34.2-83`) asserts every `*.test.ts` file in `src/backend/sidecar/__tests__/` is classified in exactly one of two declared lists (`IN_SCOPE_SUITES` / `STRUCTURALLY_CONTAINED_SUITES`). The new `gamelibNamespaceLoad.test.ts` file was unclassified, failing the set-equality assertion.
- **Fix:** Added `'gamelibNamespaceLoad.test.ts'` to `STRUCTURALLY_CONTAINED_SUITES` (alphabetically, between `gameDetailsImportGate.test.ts` and `humbleFlows.test.ts`) — it relies on the project's `setupFiles`-based structural containment alone (like `bootstrapWirings.test.ts`, its `jest.unmock('i18next')` precedent), not a per-suite mock kit, so it does not belong in `IN_SCOPE_SUITES` (reserved for the four suites carrying the full defence-in-depth containment kit).
- **Files modified:** `src/backend/sidecar/__tests__/testContainment.test.ts`
- **Commit:** `1a549bd28`

**2. [Rule 1 - Correctness] Shared title key would have produced a grep-count of 4, not the plan's declared 3**
- **Found during:** Task 2 acceptance-criteria verification
- **Issue:** The plan's acceptance criterion requires `grep -vE '^\s*(//|\*|/\*)' installFlowRegistration.ts | grep -c 'gamelib:installFlows\.'` to return exactly `3` (one per distinct key). Writing the title resolution inline in both handlers (as literally shown in the plan's `<implementation>` sketch) produces `4` matching lines, because `pathRejectedTitle` is legitimately used in both `moveInstall` and `importGame` per the plan's own `<behavior>` block.
- **Fix:** Factored title resolution into a single `rejectedPathDialogTitle()` helper function, called from both handlers. The key's literal now appears exactly once in source while the behavior (title surfaced in both handlers) is unchanged — `i18next.t` is still invoked with the same arguments at runtime, so `installFlows.test.ts`'s `jest.spyOn(i18next, 't')` assertions are unaffected.
- **Files modified:** `src/backend/sidecar/installFlowRegistration.ts`
- **Commit:** `6af1bd4d5`

**3. [Rule 3 - Blocking] Committing task files with plain `git add`/`git commit` swept in a foreign, already-staged rename**
- **Found during:** Task 1 commit
- **Issue:** The working tree had a pre-existing staged rename from a concurrent session (`.planning/todos/pending/...` → `.planning/todos/completed/...`). Running `git add <my files>` followed by `git commit` absorbed that already-staged rename into the commit (per this repo's documented `gsd-sdk-commit-stages-entire-tree.md` gotcha, which applies to plain `git add`+`git commit` sequences too, not only the `gsd-sdk query commit` verb).
- **Fix:** `git reset --soft HEAD~1` to undo the commit without touching the index or working tree, then re-committed using `git commit --only <explicit paths>`, which builds the commit from the specified paths' working-tree content and disregards any other staged content. Verified the foreign rename remained staged and untouched throughout.
- **Files modified:** none (git-history-only correction)
- **Commit:** superseded by `1a549bd28`
