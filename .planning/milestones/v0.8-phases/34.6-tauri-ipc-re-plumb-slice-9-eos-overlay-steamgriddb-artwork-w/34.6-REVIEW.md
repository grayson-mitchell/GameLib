## Summary

This phase ports EOS overlay, SteamGridDB artwork (including a plaintext→keyring secret-store migration), and wine-tools channels onto the Tauri sidecar's curated `ipcMain` registration surface, and adds a shared `rendererPathGuard.ts` containment/shape primitive to harden three renderer-facing handlers (`moveInstall`, `importGame`, `runWineCommandForGame`) against path-traversal and shell-injection.

The security-critical work is genuinely well done: the SteamGridDB secret-store migration (`steamgridSecretStore.ts`) has a correct write→invalidate→raw-readback→exact-match discipline that never persists on an unverified round trip and never logs the secret; `bootstrap.ts`'s dev-vault-vs-keyring branch is a correct exclusive `if/else`; every `*FlowRegistration.ts` module registers its channels with the correct invoke/send kind and appropriate idempotency guards; and `main.rs`'s `sidecar_send` trace path never logs `args`, only channel names, as required.

However, the path-containment hardening added to `moveInstall`/`importGame` (Plan 11) has a functional defect that breaks the primary real-world use case of both features — filed below as CR-01. Three smaller Warning-level issues (an unvalidated string-cast on a secret-bearing param, a trim/whitespace behavior diff between the two `SteamGridDbSecretStore` implementations, and a stale/overconfident code comment) are also filed. Two items explicitly flagged as out of scope by the phase context — `winetricksInstall`'s underlying dead-button root cause, and `importGame`'s `winePrefix`/`wineVersion`/`wineCrossoverBottle` not being path-contained (already filed as `.planning/todos/pending/2026-08-24-importgame-wineprefix-wineversion-not-contained-by-34-6-11.md`) — are not re-reported here as new findings, consistent with instructions.

## Critical Issues

### CR-01: `moveInstall`/`importGame`'s new containment root rejects the primary real-world use case of both features

**File:** `src/backend/sidecar/installFlowRegistration.ts:258-282` (`moveInstall`) and `:342-374` (`importGame`)

**Issue:** Plan 34.6-11 hardened both handlers to require the renderer-supplied `path` to resolve *inside* `GlobalConfig.get().getSettings().defaultInstallPath`:

```ts
// moveInstall, line 264-268
assertContainedPath(
  GlobalConfig.get().getSettings().defaultInstallPath,
  path,
  'moveInstall'
)
```

```ts
// importGame, line 356-360
assertContainedPath(
  GlobalConfig.get().getSettings().defaultInstallPath,
  path,
  'importGame'
)
```

`assertContainedPath` (`rendererPathGuard.ts`) throws `PathContainmentError` whenever `path` does not resolve to a location nested under the given root. But for both features, the entire point of the operation is to reference a location that is normally **outside** `defaultInstallPath`:

- **`moveInstall`** — `src/frontend/screens/Game/GameSubMenu/index.tsx`'s `onMoveInstallYesClick` opens a native directory picker (`window.api.openDialog({ properties: ['openDirectory'], defaultPath: defaultInstallPath })`) and passes whatever the user selects straight to `window.api.moveInstall({ appName, path, runner })`. The picker only *starts* at `defaultInstallPath` — a user moving a game to a different drive, a second SSD, or an external disk (the entire real-world reason this feature exists) will pick a path outside `defaultInstallPath` and now receive a silent-to-the-user `PathContainmentError` rejection instead of a move.
- **`importGame`** — `src/frontend/screens/Library/components/InstallModal/ImportDialog/index.tsx` lets the user point at an **already-installed** game elsewhere on disk. By definition, an import target is normally not nested inside `defaultInstallPath` (if it were, there would be nothing to import — the game would already be a GameLib-managed install).

The plan's own residual analysis (`34.6-11-SUMMARY.md`, residual (b)) only considered the *security* consequence of `defaultInstallPath` being reconfigurable ("a user who deliberately reconfigures that setting widens the containment boundary by design"). It never asked whether legitimate, unmodified real-world inputs for these two specific features actually satisfy the new constraint at all — and they generally do not. This gap is invisible in `installFlows.test.ts`'s own fixtures: the "legitimate" pass-through specimens were retargeted to synthetic paths manually placed inside the mocked `defaultInstallPath` (e.g. `/home/deck/Games/Sid Meier's Civilization V/save`), which proves the containment *primitive* is correct but never exercises the shape of path a real move-to-another-drive or real import-of-an-existing-install actually produces.

This is a functional regression, not a bypass: every legitimate cross-drive move and out-of-tree import will now be silently rejected (the terminal `gameStatusUpdate: 'done'` is emitted with no distinguishing user-facing message beyond a generic error), for a public-facing feature whose entire value proposition is "your target is somewhere else."

**Fix:** The threat this guard defends against (per its own header and `rendererPathGuard.test.ts`) is a renderer that has been compromised/tampered with sending a `path` designed to escape a *trusted* root — not a legitimately-user-chosen destination via the native OS picker, which is inherently unconstrained by design. Containing `moveInstall`/`importGame` against `defaultInstallPath` conflates these two different threat models. Consider one of:
- Drop the containment requirement for `moveInstall`/`importGame` specifically (they are gated by an OS-native directory picker already, which is a stronger trust boundary than a config value the same process also writes), and instead validate only that `path` is a plausible absolute filesystem path (reachable, writable/readable) — mirroring what `assertContainedPath`'s own header calls out as the REQ-37-06 anti-pattern to avoid for *content*, but applied here to scope, not shape.
- If containment must be kept, widen the root to something that actually reflects "anywhere the user's OS file picker can reach" (effectively no containment) rather than the single configured install directory, and gate on a different signal (e.g. that the path was actually returned by a real `openDialog()` call in this same session) if tamper-resistance is still required.
- At minimum, add a live-gate/manual test that exercises `moveInstall` to a path outside `defaultInstallPath` and `importGame` from a path outside it, so this regression is caught before Live Gate rather than by a user's first move-to-external-drive attempt.

## Warnings

### WR-01: `steamgriddb.setApiKey` accepts an unvalidated `key` and can crash the write with a misleading "failed" log

**File:** `src/backend/sidecar/enrichmentFlowRegistration.ts` (the live Tauri-sidecar `steamgriddb.setApiKey` handler; the parallel Electron-only handler is `src/backend/steamgrid/ipc_handler.ts:` `addHandler('steamgriddb.setApiKey', async (event, key) => { await getSteamGridDbSecretStore().setApiKey(key) })`)

**Issue:** Both handlers forward the IPC argument to `SteamGridDbSecretStore.setApiKey(value: string)` with only a type assertion, never a runtime check. On the sidecar path this reaches `SidecarSteamGridDbSecretStore.setApiKey()` (`steamgridSecretStore.ts:86-88`) → `SLOT_STORE.setToken(value)` → `keyringTokenStore.ts:399-420`:

```ts
async setToken(token: string): Promise<void> {
  this.invalidateCache()
  try {
    await requestRustInvoke(RUST_KEYRING_SET, [token, this.slot])
    this.cachedToken = { value: token }
    logInfo(
      `SidecarKeyringSlotStore(${this.slot}).setToken(): ${RUST_KEYRING_SET} ok len=${token.length}`,
      LogPrefix.Steam
    )
  } catch (error) {
    logWarning(`...failed: ${errorMessage(error)}`, LogPrefix.Steam)
  }
}
```

If a malformed/non-string `key` (e.g. `undefined`, a number, an object) ever reaches this call — for example from a future caller, a preload-layer bug, or a malformed frontend payload — `requestRustInvoke` is awaited first (the write may actually be issued, e.g. as a JSON-serialized `null`), and only *then* does `token.length` throw a `TypeError`, which lands in the `catch` block and is logged as `RUST_KEYRING_SET failed`. This is misleading: the log claims the write failed when it may have actually succeeded with a corrupted value (e.g. the literal string `"null"`), and the caller (the IPC handler) never sees any rejection at all, since `setToken()` is a total method that swallows the error.

**Fix:** Validate `typeof key === 'string'` at the IPC boundary (both `ipc_handler.ts` and `enrichmentFlowRegistration.ts`) before calling `setApiKey()`, rejecting/no-op'ing on a non-string with a clear log line, e.g.:
```ts
addHandler('steamgriddb.setApiKey', async (event, key) => {
  if (typeof key !== 'string') {
    logWarning('steamgriddb.setApiKey: ignored a non-string key', LogPrefix.Backend)
    return
  }
  await getSteamGridDbSecretStore().setApiKey(key)
})
```
Alternatively, harden `setToken()` itself to guard `typeof token === 'string'` before the `requestRustInvoke` call, so the failure is caught before any keyring round trip is attempted.

### WR-02: `setApiKey` trims/normalizes whitespace on the Electron path but not the sidecar path

**File:** `src/backend/steamgrid/secretStore.ts:97-108` (Electron) vs. `src/backend/sidecar/steamgridSecretStore.ts:86-88` (sidecar)

**Issue:** `ElectronSteamGridDbSecretStore.setApiKey()` trims the incoming value and treats a whitespace-only string as an explicit clear:
```ts
async setApiKey(value: string): Promise<void> {
  const trimmed = value.trim()
  const stored = trimmed ? encryptApiKey(trimmed) : ''
  GlobalConfig.get().setSetting('steamGridDbApiKey', stored)
}
```
`SidecarSteamGridDbSecretStore.setApiKey()` does not:
```ts
async setApiKey(value: string): Promise<void> {
  await SLOT_STORE.setToken(value)
}
```
`secretStore.ts`'s own module header states the seam's explicit contract: "A behavior diff here is a REQ-34.6-06 failure" (referring to Electron/sidecar parity for this store). A user who pastes an API key with a trailing newline or leading/trailing spaces (a common copy-paste artifact from a browser) gets a silently-stored-with-whitespace key on the sidecar build, and a cleanly-trimmed key on the Electron build — divergent behavior for byte-identical user input, and on the sidecar build a whitespace-only "clear the key" gesture (submitting an empty/space string) does not clear the key the way it does on Electron.

**Fix:** Move the trim/empty-as-clear normalization into a shared helper both implementations call, or replicate `ElectronSteamGridDbSecretStore.setApiKey()`'s exact trim logic in `SidecarSteamGridDbSecretStore.setApiKey()`:
```ts
async setApiKey(value: string): Promise<void> {
  const trimmed = value.trim()
  if (!trimmed) {
    await SLOT_STORE.clearToken()
    return
  }
  await SLOT_STORE.setToken(trimmed)
}
```

### WR-03: Stale, overconfident comment in `SearchBar/index.tsx` asserts a disproven root-cause theory as fact

**File:** `src/frontend/components/UI/SearchBar/index.tsx:89-120`

**Issue:** The comment block above the `onMouseDown={(e) => e.preventDefault()}` guard states, in "DO NOT REMOVE THIS HANDLER" framing:

```
FOCUS RACE (Phase 34.6 Plan 16 — the cause of live-gate Step 4's FAIL).
DO NOT REMOVE THIS HANDLER.
...
The failure is completely silent and reads as a dead button. It cost a
live gate item and most of a debug session: `winetricksInstall` was
recorded as a broken IPC channel (the frame "never arrives") when in
fact nothing was ever sending one. Proven by measurement, both
directions -- driving the same button by KEYBOARD (Tab, then Enter),
which never blurs and so never collapses the list, fired the send and
ran winetricks end to end.
```

This asserts, with "Proven by measurement" confidence, that the `:focus-within`/mousedown-blur race is *the* cause of the `winetricksInstall` dead-button symptom. Per this phase's own later live re-drive, that specific causal theory has since been disproven — the underlying `winetricksInstall` dead-to-mouse cause is now recorded as unknown, not this mechanism. The comment was not updated to reflect that, and its "DO NOT REMOVE"/"Proven by measurement" language will mislead the next engineer who reads it into either (a) trusting a closed, explained root cause that isn't actually closed, or (b) being reluctant to touch/remove this `preventDefault()` guard while debugging the real cause, since the comment presents it as load-bearing and settled.

**Fix:** Update the comment to reflect current status — keep the mechanical description of what `preventDefault()` does (that part is still accurate and independently useful), but soften or remove the "Proven by measurement... fired the send and ran winetricks end to end" causal claim and the "DO NOT REMOVE" imperative, replacing them with something like: "This mitigates a genuine focus-race mechanism (still real and still worth keeping), but is NOT confirmed to be the cause of the `winetricksInstall` dead-button symptom — that root cause was later found to be unresolved by live re-drive; see [debug ledger reference]." This keeps the useful mechanical documentation while not overstating certainty about a closed investigation that is, in fact, still open.
