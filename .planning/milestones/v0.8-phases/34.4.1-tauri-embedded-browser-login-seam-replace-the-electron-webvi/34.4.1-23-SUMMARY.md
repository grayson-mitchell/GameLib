## Accomplishments

- Closed F-6 Defect B: the live gate (plan 20 item 3) measured 25 `delete_cookie()` calls, every one `Ok(())`, and the jar shrank by exactly 1 — all 23 Humble cookies survived. Two independent bugs are fixed: (1) the returned count used to be the pre-removal size of the matched set (`matching.len()`), computed before the delete loop ran, so it could never report failure; (2) on macOS, wry's `delete_cookie()` hands `WKHTTPCookieStore` a freshly reconstructed `NSHTTPCookie`, and its completion handler fires unconditionally regardless of whether anything was actually deleted (bugs.webkit.org #184938).
- Added two pure, unit-tested Rust helpers (`website_data_record_matches_domain`, `verified_delete_count`) proving the half of the fix that doesn't require a live WebKit — 8 new `#[cfg(test)]` cases, `cargo test` went from plan 22's 66 to 74.
- Rewrote `humble_login_clear_cookies`'s macOS branch to reach the live `WKWebsiteDataStore` through `with_webview()`, fetch records via `fetchDataRecordsOfTypes_completionHandler(allWebsiteDataTypes(mtm), ...)`, filter by `website_data_record_matches_domain`, and remove only the matching records' `WKWebsiteDataTypeCookies` data via `removeDataOfTypes_forDataRecords_completionHandler` — never the whole record (which would also drop localStorage/IndexedDB/caches plans 15/16 already handle separately), and never `clear_all_browsing_data()` (D-08, grep-asserted absent).
- Fixed the attempted-count bug on every platform, including Linux/Windows, which keep the existing (UNVERIFIED, DECLARED per D-09/REQ-34.4.1-13) `delete_cookie()` mechanism but now also return a measured, re-read count rather than the old attempted one.
- Updated `sidecarTransport.ts`'s `RUST_HUMBLE_LOGIN_CLEAR_COOKIES` doc comment to document the measured-count contract.
- Instrumented Epic's `clearEpicCookies` (`storeManagers/legendary/user.ts`) — the shared arm's second, already-shipped caller, carrying Defect B verbatim since Phase 34.5 plan 06 and never independently verified — with a measured-count log line and a distinct removed-nothing warning when the count is 0, plus an in-source note recording the shared-arm fact and the deliberate cross-phase edit into open Phase 34.5.
- Added a static `tauriShellSource.test.ts` guard against a future revert to the `matching.len()` attempted-count shape, proven load-bearing by a temporary reintroduction into `main.rs` that was observed to fail the new test, then reverted.

## Decisions Made

**Threading — the single highest-risk correctness decision in this plan, made by source inspection rather than by trusting the spike's raw measurement.** `humble_login_clear_cookies`'s real caller is `start_reader`'s `rustInvoke` dispatch, which always runs `dispatch_rust_channel` on a `thread::spawn`-created worker thread, never the tao main thread. Reading `tauri-runtime-wry-2.11.4`'s `send_user_message` (the function every `Dispatcher` method, including `with_webview()`, routes through) shows:

```rust
if current_thread().id() == context.main_thread_id {
    handle_user_message(...);  // runs the closure INLINE, synchronously
    Ok(())
} else {
    context.proxy.send_event(message)  // posts to the event loop, returns IMMEDIATELY
        .map_err(...)
}
```

Off the main thread, `with_webview()` returns `Ok(())` **before** its closure has run at all. Spike 016 measured `closure_ran_immediately_after_return=true`, but that measurement's trigger (`humble_login_open`'s `on_page_load` navigation-delegate hook, added by commit `57905a58f` because the throwaway probe arm had no reachable caller otherwise) genuinely does execute on the OS main thread — `thread_name=main` plus a successful `MainThreadMarker::new()` both confirm this — which is a **different call site** from `humble_login_clear_cookies`'s real one, and not representative of it. Trusting the spike's raw finding literally would have written code that reads the post-removal cookie count before the removal's completion handler had actually fired, silently reporting `0` deletions regardless of what really happened (or worse, a stale `before`-equal count masking a real failure).

The arm instead uses the exact `mpsc_channel::<()>()` + `rx.recv_timeout(CLEAR_COOKIES_TIMEOUT)` shape `humble_reveal_post`/`humble_login_clear_storage` already use — the same blocking-on-a-channel pattern `window.cookies()` already relies on internally (`webview_getter!`'s own `rx.recv()`, confirmed by reading `tauri-runtime-wry-2.11.4`'s `getter!` macro: `send_user_message(...)?; rx.recv()...`). This matches exactly the fallback PLAN.md itself anticipated ("if it was dispatched, use the same channel-plus-wait pattern"), reached via source verification of the real call path rather than by re-running spike 016 under worker-thread conditions.

**No `NSRunLoop` pump needed**, unlike the throwaway spike016 probe's `spike016_wait_for_records` helper: that helper existed because the spike ran **on** the main thread and would have deadlocked its own run loop by blocking on it with a plain `recv()`. This arm's worker thread can safely block — the main thread's own event loop keeps servicing the completion handler independently, exactly as it already does for `window.cookies()`'s internal wait.

**Domain-scoping was verified correct BEFORE deletion was made effective**, per this plan's own risk warning. `website_data_record_matches_domain` delegates to `cookie_domain_matches` (the file's own declared "ONLY domain comparison"), which Plan 22 already proved correct against Defect A (the clear-direction filter no longer matches every cookie in the jar). The suffix-lookalike guard (`nothumblebundle.com` must not match `humblebundle.com`) was proven load-bearing by temporarily dropping the `.`-separator requirement in `cookie_domain_matches`, observing `website_data_record_matches_domain_rejects_suffix_lookalike` fail, and restoring (recorded under Temporary-Break Experiments below).
