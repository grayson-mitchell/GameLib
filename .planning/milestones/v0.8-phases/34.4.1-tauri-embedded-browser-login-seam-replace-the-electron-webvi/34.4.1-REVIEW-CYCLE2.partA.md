## Summary

This lane reviewed the 5 Humble backend test suites (`library.test.ts` 3,926 lines,
`user.test.ts` 2,339 lines, `adapter.test.ts` 869 lines, `secretStore.test.ts` 255 lines,
`userAgent.test.ts` 53 lines) against a single governing question for every assertion: **does
this test actually prove what its name claims?** All 7,443 lines were read in full, sequentially,
end to end — no sampling, no skipped sections. Source files (`library.ts`, `user.ts`, `adapter.ts`,
`secretStore.ts`, `loginWindowSeam.ts`, `userAgent.ts`, `backend/platform/index.ts`) were read as
needed for cross-checking mock shapes and interface drift, consistent with the mandate that
findings be about test quality, not source correctness (a prior standard-depth pass already
covers the source).

**Result: zero Critical and zero Warning findings across the entire 7,443-line scope.** Four
Info-level findings were identified, all confirmed by direct line reads (below).

This is a genuinely clean outcome, not a rubber stamp. Specific evidence considered before
reaching it:

- **Mock-boundary integrity.** The `fakeSeam` mock of `LoginWindowSeam` in both `adapter.test.ts`
  and `user.test.ts` was cross-checked method-for-method against the real 8-method interface in
  `loginWindowSeam.ts` (`open`, `cookies`, `cookiesForDomain`, `takeEvents`, `close`,
  `clearCookies`, `revealPost`, `clearStorage`) — no drift found in either file. `classify.ts` and
  `dedup.ts` are explicitly NOT mocked in `library.test.ts`, so the ownership-overlay/dedup and
  D-42-01/D-42-02 auto-settle tests exercise real matching logic against fixture orders, not a
  mock echo.
- **No tautologies found.** Expected values in the reveal/redeem/audit and cookie-census tests are
  hand-constructed fixture literals, not derived from the same code path under test.
- **Redaction discipline is asserted, not assumed.** Every describe block touching session
  cookies, csrf tokens, revealed key values, or `error_msg` content includes a
  `JSON.stringify(call).not.toContain(SECRET)`-shaped assertion across `mockLogInfo`/
  `mockLogError`/`mockLogWarning`/`mockSendFrontendMessage`, including a strict-regex (not
  substring) variant in the cookie-census tests in `user.test.ts` that proves the log line
  contains only integers and fixed vocabulary.
- **Fake-timer usage is correct.** Every fake-timer test pairs `jest.useFakeTimers({ doNotFake:
  ['setImmediate'] })` with a `flushAsync` microtask drain, and concurrency-proving tests in
  `library.test.ts` use manually-controlled resolver arrays rather than misapplied real-time
  waits.
- **Liveness/undecidable handling is tested honestly.** Both `user.test.ts` (login-watch polling,
  cookie census) and `library.test.ts` (disconnect seam path) include explicit tests proving an
  `UNDECIDABLE` verdict is never silently collapsed into a clean zero.
- **Fake-HOME isolation:** none of the 5 files spawn a child process or touch HOME/XDG/APPDATA
  environment variables — the two-profile-rule convention does not apply to this lane's scope, and
  no violation was found.
- **Self-documented anti-pattern discipline.** `user.test.ts` contains at least two in-code
  comments where the team explicitly caught and re-pointed a test that had become a "FALSE PASS"
  after a prior refactor (the Phase 39 Plan 04/05/06 seam collapse left the driving mock
  unreachable in several tests; each was re-pointed with a comment naming the former defect). This
  is exactly the "green-check-proving-nothing" pattern this review was commissioned to hunt for —
  finding that the team already caught and fixed instances of it in-repo is a strong positive
  signal about the discipline behind this suite, not something to flag as a defect itself.

None of the four findings below rise above Info: none are false shipped claims, none silently
contaminate a measurement, and none affect the tests' ability to catch a real regression in the
code they cover.

## Info

### A-IN-01: Stale header doc comment references a file that no longer exists

**File:** `src/backend/humble/__tests__/userAgent.test.ts:1-21`
**Issue:** The suite's header doc comment states that it mocks `'electron'` and imports
`electronStub.ts` directly. Neither is true as written: `electronStub.ts` no longer exists — it
was moved to `src/backend/platform/index.ts` in Phase 35 Plan 13 (confirmed via read/grep) — and
there is no `jest.mock()` call anywhere in this 53-line file. The actual test bodies (UA regex
shape, a no-throw regression guard, and a platform-token match) are legitimate and exercise real,
unmocked production code from the current `userAgent.ts`/`platform/index.ts`, so this is a
documentation-accuracy defect only — it does not affect whether the tests prove what they claim.
**Confidence:** High (confirmed by direct read of the full file plus a targeted grep for
`electronStub` and `jest.mock` returning zero matches).
**Fix:** Update the header comment to reference `backend/platform/index.ts` and remove the claim
of a `jest.mock('electron', ...)` call, or add one if platform mocking was actually intended.

### A-IN-02: Test name claims a non-axios error case but only exercises an axios error

**File:** `src/backend/humble/__tests__/adapter.test.ts` — test titled `'non-axios / unmapped-status error rethrows'`
**Issue:** The test name advertises two distinct cases (a non-axios thrown error, and an axios
error with an unmapped HTTP status). The test body only constructs and throws an axios-shaped
error with an unmapped status (500); no genuinely non-axios error (e.g. a plain `Error`, a
TypeError from malformed JSON, etc.) is ever thrown or asserted against. The assertion made (that
an unmapped-status axios error rethrows through the C5 isolation wall) is real and correctly
proven — this is a naming-precision issue, not a vacuous assertion. It does mean the "non-axios"
half of the C5 isolation-wall guarantee has no direct coverage in this suite.
**Confidence:** High (confirmed by reading the test body against its title).
**Fix:** Either rename the test to drop the "non-axios" claim, or add a second case (or split into
two `it()`s) that throws a plain `Error` / non-axios-shaped rejection and asserts it rethrows
unmodified through the same wall.

### A-IN-03: Test for `getGamekeys` diagnostic logging is nested inside the `revealKey` describe block

**File:** `src/backend/humble/__tests__/adapter.test.ts` — test titled `'round 5: getGamekeys (no diagnostic context) does NOT log...'`
**Issue:** This test exercises `getGamekeys()` behavior but is physically nested inside the outer
`describe('revealKey', ...)` block rather than the `getGamekeys` describe block. It runs and
asserts correctly regardless of nesting (Jest does not scope assertions by describe placement), so
there is no functional impact — this is a cosmetic/organizational defect that could mislead a
future reader running `--testNamePattern` filters scoped to `revealKey` or skimming the file
structure to find `getGamekeys` coverage.
**Confidence:** High (confirmed by reading the surrounding describe block structure).
**Fix:** Move the test into the `getGamekeys` describe block.

### A-IN-04: Genuinely empty describe block (vestigial test scaffolding)

**File:** `src/backend/humble/__tests__/user.test.ts:441`
**Issue:** `describe('startLogin() — best-effort identity after gamekeys acceptance (D-02/D-16)', () => {})` contains zero test bodies — the block is entirely empty. This reads as either an
abandoned placeholder for coverage that was never written, or dead scaffolding left over from a
refactor that removed its contents without removing the block. Either way it currently provides no
coverage and no signal, despite naming a specific behavior (D-02/D-16 best-effort identity
resolution after gamekeys acceptance) that a reader would reasonably assume is tested somewhere in
this file.
**Confidence:** High (confirmed by direct read of lines 435-450 in this session).
**Fix:** Either populate the block with the D-02/D-16 best-effort-identity test(s) it names, or
delete the empty describe block if that coverage is genuinely provided elsewhere (search the file
for D-02/D-16 references to confirm before deleting).
