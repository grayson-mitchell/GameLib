<objective>
Close **F-6 (BLOCKING)**: make disconnect actually disconnect, on both paths that have the defect.

Purpose: the gate observed the operator dropped "straight into a signed in page" three seconds
after a successful cookie clear, with zero re-auth polls. The Tauri branch of `disconnect()` runs
1 wipe step where Electron's runs 5. **This is a functional AND privacy regression versus the
Electron build** — a user who disconnects Humble on a shared machine reasonably believes their
session is gone; the next login window signs the next person straight in.

**Plan 10's sweep found the same defect a second time, already replicated.**
`src/backend/storeManagers/legendary/user.ts:107-151` (Phase 34.5 plan 06) has the identical
shape: 5 Electron steps, 1 Tauri step, and its own in-source comment says so explicitly —
*"This is the same shape humble/user.ts's disconnect() uses (Phase 34.4.1 Plan 06, D-08)."* The
pattern was copied before anyone knew it was incomplete. Fixing only Humble would ship a known
twin defect.

Output: both paths clear browser-side storage as well as cookies, scoped to their own origin, and
plan 10's parity guard is upgraded from "gap declared" to "parity enforced."

**Scope note, stated rather than absorbed:** `storeManagers/legendary/user.ts` is Phase 34.5's
file. It is edited here because the defect is in 34.4.1's seam, the fix is 34.4.1's new
capability, and Phase 34.5 has not closed. The alternative — closing F-6 for Humble and filing an
identical known-broken twin against an open phase — is exactly the "declared partial carried for
a second phase running" that D-08 exists to prevent. Record the cross-phase edit in the summary
so 34.5's own gate inherits it knowingly.
</objective>

<interfaces>
The two branches to bring to parity. **Humble** (`src/backend/humble/user.ts:794-839`):
```
const seam = getLoginWindowSeam()
if (seam === null) {
  const ses = session.fromPartition(HUMBLE_LOGIN_PARTITION)
  wipeSteps = [ clearStorageData, clearCache, clearAuthCache, clearHostResolverCache, clearData ]   // 5
} else {
  wipeSteps = [ ['clearHumbleCookies', open(hidden) -> clearCookies(label,'humblebundle.com') -> finally close] ]  // 1
}
for (const [name, step] of wipeSteps) { try { await step() } catch (err) { logWarning(...continuing...) } }
```
**Legendary** (`src/backend/storeManagers/legendary/user.ts:107-151`): identical structure,
`persist:epicstore`, `EPIC_LOGIN_ORIGIN`, `EPIC_COOKIE_HOST`, step name `clearEpicCookies`.

Capability categories the Electron branch covers, and which Tauri step must now cover them:
```
clearStorageData        -> cookies + storage        (cookies: existing step; storage: NEW)
clearCache              -> cache                    (caches API, part of the new storage step)
clearAuthCache          -> HTTP auth cache          (no web-facing API — see below)
clearHostResolverCache  -> DNS cache                (no web-facing API — see below)
clearData               -> storage + cache          (subsumed by the above)
```
`clearAuthCache` and `clearHostResolverCache` have **no** in-page JavaScript equivalent: they are
network-stack caches, not web storage. They cannot be closed by this design and must be handled as
plan 10 defined — DECLARED, with an in-source comment and a threat ID — not silently dropped. That
is the distinction between this and F-6: the loss is chosen, recorded and reasoned about, exactly
as `getLiveCsrfToken`'s T-34.4.1-18 snapshot fallback is.

From plan 15 — `LoginWindowSeam.clearStorage(originUrl, userAgent)`, which REJECTS on structural
failure and resolves a per-category report where each category is a count or `unsupported`.

The ordering rule that must survive (`humble/user.ts:765-769`): the stored credential is removed
FIRST — *"so a failed partition-clear step can never leave the (possibly plaintext-degraded)
sessionCookie on disk after a user-confirmed disconnect (WR-02 / T-10-07)."* Legendary carries the
same rule at its L83-90 comment (ASVS V3: credential-side cleanup MUST run unconditionally, even
when every cookie-side step fails).
