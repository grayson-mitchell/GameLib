## Warnings

### E-WR-01: `.warning` renders with no color under the default theme and most others

**File:** `src/frontend/App.css:172-175`
**Issue:** `.warning { font-weight: var(--bold); color: var(--text-warning, var(--warning)); }`.
Neither half of this fallback chain resolves under the default theme. `--text-warning` is defined
exactly once in the whole stylesheet, at `src/frontend/themes.scss:223`, inside the
`body.classic, body.cyberSpaceOasis, body.cyberSpaceOasisAlt` block (`themes.scss:153-234`). A
bare `--warning:` custom property is defined **nowhere** in `src/frontend` (confirmed:
`grep -rn -- "^\s*--warning:" src/frontend` returns zero results; `_colors.scss`'s global
`colorSystem` mixin defines only `--status-warning`/`--status-warning-hover`, never a bare
`--warning`). So for the default theme (`midnightMirage`, `themes.scss:68`) and every other named
theme except the classic/cyberSpaceOasis/cyberSpaceOasisAlt group, the entire `var()` chain is
unresolved and the `color` declaration is dropped by the browser — the element keeps whatever
color it inherits from its ancestor. Live consumers:
`src/frontend/screens/Settings/components/WrappersTable.tsx:64` and
`src/frontend/screens/Library/components/InstallModal/DownloadDialog/index.tsx:729,745` (the
latter renders `"Error: Sandbox access not granted to this path, data loss will occur."` and a
low-disk-space message — both meant to read as warnings, both silently uncolored under the
default theme).
**Fix:** give `--warning` (or `--text-warning`) a value in the global `colorSystem` mixin
(`src/frontend/styles/_colors.scss`), the same way `--success`/`--danger` are theme-adaptive
globals per-theme, e.g. point `.warning`'s `color` at the always-defined raw
`var(--status-warning)` token directly instead of the two undefined intermediaries.

### E-WR-02: `.danger` renders with no color under 5 specific themes

**File:** `src/frontend/App.css:167-170`
**Issue:** `.danger { font-weight: var(--bold); color: var(--text-danger, var(--danger)); }`. I
mapped every `--danger:`/`--text-danger:` declaration in `themes.scss` (8 `--danger:` lines: 145,
180, 267, 308, 351, 387, 549, 712; the sole `--text-danger:` at 220) against every `body.<theme>`
selector block's line range (enumerated via `grep -n "^body\."`, cross-checked by reading each
block in full). Confirmed by direct read: the `body.marine, body.marine-classic` block
(`themes.scss:564-596`), the `body.zombie, body.zombie-classic` block (`themes.scss:598-630`), and
the `body.old-school` block (`themes.scss:638-669`) each define neither `--danger` nor
`--text-danger`. The shared secondary block at `themes.scss:680-686` (covering `classic`,
`cyberSpaceOasisAlt`, `dracula-classic`, `marine-classic`, `zombie-classic`) only sets
`--navbar-accent`, not `--danger`. Live consumers:
`src/frontend/screens/Settings/components/WineVersionSelector.tsx:158,166`
(`className="smallInputInfo danger"`) and `src/frontend/screens/ConsoleMode/index.tsx:462`
(`className="consoleQuitButton danger"`) — under `marine`, `marine-classic`, `zombie`,
`zombie-classic`, and `old-school`, this text has no explicit danger color.
**Fix:** same remedy as E-WR-01 — add a `--danger` declaration to each of these 5 theme blocks, or
switch `.danger`'s color to the always-defined raw `var(--status-danger)` token.

### E-WR-03: unscoped `.warning` selector collision between App.css and Settings/index.css

**File:** `src/frontend/App.css:172-175` and `src/frontend/screens/Settings/index.css:111-119`
**Issue:** Both stylesheets define a bare, unscoped, equal-specificity `.warning` class with
different rules — `App.css`'s (broken, see E-WR-01) `color: var(--text-warning, var(--warning))`
vs. `Settings/index.css`'s `color: var(--status-warning)` (an always-resolving raw token) plus
`font-size`, `width: 100%`, `max-width: 513px`, `white-space: break-spaces`, `padding-top`,
`font-weight: bold`. Neither is scoped (no parent selector, no CSS module). Which rule wins for
any `className="warning"` element depends entirely on stylesheet import/load order, not document
structure — the same class of bug this codebase has already hit once
(`unscoped-mui-selector-leaks-app-wide`). Confirmed no other local `.warning` override exists in
`DownloadDialog`'s own directory tree, so that consumer depends solely on whichever of these two
wins the cascade.
**Fix:** scope both rules to their owning surface (e.g. `.Settings .warning` / a class name that
doesn't collide), rather than relying on load order to pick the correct one.

### E-WR-04: MUI Tooltip theme uses a dead CSS custom property with no fallback

**File:** `src/frontend/muiTheme.ts:77-88` (specifically line 82)
**Issue:** `MuiTooltip.styleOverrides.tooltip` sets `color: 'var(--text-primary)'`.
`--text-primary` is documented elsewhere in this same codebase as a **dead token that must never
be reintroduced**: `src/frontend/screens/Login/components/SteamLogin/index.scss:84-86` states
"`--text-primary` is never defined anywhere in this codebase (verified: `grep -rn --
"--text-primary:" src/frontend` returns zero results)", and both
`src/frontend/screens/Login/components/SteamLogin/__tests__/steamLoginWindowChrome.test.ts:300-333`
and `src/frontend/components/UI/NavShell/__tests__/cssTokenSweep.test.ts:32-34` carry source-gate
tests specifically asserting `--text-primary` is absent from their respective stylesheets. I
independently re-ran the same grep and confirmed zero live declarations. `muiTheme.ts` — the
single app-wide MUI theme factory (`buildMuiTheme`, applied once in `App.tsx:86` to every MUI
component in the app, including every `<Tooltip>`) — was never brought in line with this
convention, and carries no fallback (`var(--text-primary, ...)`). `src/frontend/__tests__/
muiTheme.test.ts:86-96` locks this value in as a byte-for-byte "regression pin for the App.tsx
move," which pins the dead token rather than catching it.
**Fix:** replace with a token proven live everywhere, e.g. the same `var(--text-default)` already
used two lines above it for `MuiPaper` (`muiTheme.ts:72`).

## Info

### E-IN-01: `CachedImage` leaks its custom `fallback` prop onto the DOM `<img>` element

**File:** `src/frontend/components/UI/CachedImage/index.tsx:82-95`
**Issue:** `<img loading="lazy" {...props} .../>` spreads the full `Props` object (which includes
the component-only `fallback?: string | string[]` field, not a valid `<img>` HTML attribute) onto
the rendered native element. React (since v16) passes through unrecognized string-shaped
attributes verbatim, so a stray `fallback="..."` attribute can appear in the rendered markup; when
`fallback` is an array the attribute-coercion behavior is undefined/inconsistent across React
versions. No functional breakage observed (browsers ignore unknown attributes for rendering), but
it is dead weight in the DOM and a landmine if a future prop is added to `CachedImageProps` that
does collide with a real `<img>` attribute name.
**Fix:** destructure `fallback` out before spreading: `const { fallback, ...imgProps } = props`
and spread `imgProps` instead of `props`.

### E-IN-02: three preload/misc.ts exports have no live frontend caller

**File:** `src/preload/api/misc.ts:31` (`openGithubSponsorsPage`), `:102` (`getShellPath`),
`:103` (`getWebviewPreloadPath`)
**Issue:** all three have real, tested sidecar-side handlers (`shellFilesFlowRegistration.ts`,
`appShellFlowRegistration.ts`) but zero live callers in `src/frontend` — confirmed via a repo-wide
grep for `window.api.<name>`/`.api.<name>(` usage, which returned no hits for any of the three.
Each is a renderer-invokable IPC bridge function maintained and exposed with no first-party
caller, unlike the codebase's general practice of actively removing genuinely dead Electron-era
fallbacks (see `misc.ts`'s own D-01/CR-03 comments doing exactly that for ten other channels).
`getWebviewPreloadPath`'s own in-code comment ("That guard is now fully retired") in
`src/frontend/screens/WebView/index.tsx:417` suggests it may already be vestigial.
**Fix:** either wire these to a real UI affordance, or remove the bridge export (and, if truly
orphaned, its sidecar handler) the same way the ten D-01 window-chrome fallbacks were removed.

### E-IN-03: `getCustomCSS()` failure is swallowed silently, inconsistent with file's own style

**File:** `src/frontend/index.tsx:167-169`
**Issue:** `window.api.getCustomCSS().then(window.setCustomCSS).catch(() => {})` — any rejection
is discarded with no logging, unlike this file's otherwise careful, heavily-commented error
handling (e.g. the neighboring `hydrateStoreSnapshot` race, which logs on failure). Low severity
since custom CSS is a cosmetic, optional feature, but it's an inconsistency worth closing given
how deliberately the rest of this file documents its error paths.
**Fix:** at minimum `.catch((e) => window.api.logError(\`getCustomCSS failed: ${e}\`))` for parity
with the rest of the file.

### E-IN-04: `.material-icons.is-primary` colors "primary" as "danger", self-admittedly unused

danger/red.
**Fix:** confirm via usage grep whether `is-primary` is ever applied; if genuinely unused, remove
