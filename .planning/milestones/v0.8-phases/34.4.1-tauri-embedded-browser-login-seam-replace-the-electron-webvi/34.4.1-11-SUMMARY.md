# Phase 34.4.1 Plan 11: Multi-slot keyring allowlist Summary

**Compile-time keyring slot allowlist (`keyring_account()` in Rust, `SidecarKeyringSlotStore` in TS) that lets the sidecar address a `humble-session`/`humble-csrf` Keychain entry without ever being able to touch the Steam refresh token's entry — the prerequisite plan 13 needs to fix F-1's plaintext Humble session.**

## Performance

- **Duration:** ~35 min
- **Completed:** 2026-07-30T08:18:07Z
- **Tasks:** 2 completed (Task 2 was TDD: RED then GREEN)
- **Files modified:** 4

## Accomplishments

- Rust: `keyring_account(slot: &str) -> Result<&'static str, String>` — a pure, directly-tested
  function mapping `steam-refresh-token` / `humble-session` / `humble-csrf` to their constant
  Keychain account strings; any other slot name (including the empty string and plausible
  near-misses like `steam-refresh-tokens` or `humble_session`) returns `keyring:unknown-slot`
  with no fallback to a real account.
- All four Rust dispatch arms (`keyring_get`, `keyring_set`, `keyring_delete`,
  `keyring_available`) now resolve their account through `keyring_account()` instead of the bare
  `KEYRING_ACCOUNT` constant. Slot position: `args[0]` for get/delete/available; for set, secret
  stays `args[0]` and slot moves to `args[1]`. An absent/non-string slot arg defaults to
  `steam-refresh-token` (`keyring_slot_arg`), which is the entire backward-compatibility
  mechanism — every keyring frame sent before this plan carried no slot at all, and it keeps
  resolving to the exact same Keychain entry.
- 10 new `#[cfg(test)]` cases (50/50 total, up from the 40/40 baseline).
- TS side: `SidecarKeyringSlotStore` — a slot-parameterized `TokenStore` implementation. Its
  four methods forward the bound slot to the Rust arms at the positions above.
  `SidecarKeyringTokenStore` is preserved verbatim as an exported class with its original
  no-argument construction, now implemented as `class SidecarKeyringTokenStore extends
  SidecarKeyringSlotStore { constructor() { super(KEYRING_SLOT_STEAM_REFRESH_TOKEN) } }` —
  `bootstrap.ts`'s `new SidecarKeyringTokenStore()` needed zero edits.
- Three exported slot name constants (`KEYRING_SLOT_STEAM_REFRESH_TOKEN`,
  `KEYRING_SLOT_HUMBLE_SESSION`, `KEYRING_SLOT_HUMBLE_CSRF`) so plans 13/14 import the name
  rather than retype a literal that could drift from Rust's allowlist.

## Which slots the allowlist ended up containing, and why (for plan 14)

Three slots: `steam-refresh-token`, `humble-session`, `humble-csrf`. **No fourth (SteamGridDB)
slot was added.** Per `34.4.1-SEAM-PARITY-SWEEP.md`'s "steamgrid/secureKey.ts (F-1b)
sidecar-reachability" section (the paragraph immediately after the findings table, ~line 26):
`steamgrid/ipc_handler.ts` (the only importer of `secureKey.ts`'s encrypt/decrypt functions) is
imported only by `src/backend/main.ts` — Electron's own entry point — and does **not** appear in
`src/backend/sidecar/handlers.ts`'s registration-module import list, nor in
`electronReachLedger.test.ts`'s committed 34-entry `BASELINE_ELECTRON_REACHING_MODULES`. The
sweep's conclusion: `steamgrid/secureKey.ts` is unreachable from the sidecar's curated import
graph today — F-1b is dormant, not live. Plan 11's task text was explicit that a fourth entry
should be added "only if" the sweep classified it as sidecar-reachable; it did not, so plan 14
is responsible for adding the SteamGridDB slot at the point it actually wires `steamgrid` into a
sidecar registration module (per D-GAP-02's stated reasoning: settle the slot design once, with
all callers known, rather than adding capability nothing can exercise yet).

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug caught during RED] Jest's `toEqual` ignores `undefined` array items, letting
several updated tests pass before the implementation existed**
- **Found during:** Task 2, RED phase
- **Issue:** After extending `keyringTokenStore.test.ts` to reference the not-yet-exported slot
  constants (e.g. `KEYRING_SLOT_STEAM_REFRESH_TOKEN`, `undefined` at that point), several
  `callLog` assertions using `.toEqual([{ ..., args: [KEYRING_SLOT_STEAM_REFRESH_TOKEN] }])`
  passed anyway — Jest's `toEqual` documented semantics ignore `undefined` array items, so
  `args: [undefined]` (expected) and `args: []` (actual, pre-implementation) compared equal. Per
  the plan's fail-fast rule ("a test that passes unexpectedly during RED must be investigated
  before proceeding to GREEN"), this was caught and fixed rather than treated as an accidental
  early pass.
- **Fix:** Switched all `callLog` assertions in the file from `.toEqual(...)` to
  `.toStrictEqual(...)` (which does not ignore `undefined` items), and added an explicit
  `typeof slot === 'string' && slot.length > 0` sanity check for all three slot constants before
  asserting their pairwise distinctness, so an accidentally-undefined export cannot make a
  distinctness assertion vacuously true.
- **Files modified:** `src/backend/sidecar/__tests__/keyringTokenStore.test.ts`
- **Verification:** Re-ran the suite after the fix — the previously-silently-passing assertions
  now correctly failed (true RED) until the GREEN implementation landed.
- **Committed in:** `3342dc296` (RED commit)

**2. [Rule 1 - Bug] `steamAuthFlows.test.ts` Test 4 asserted a `keyring_set` args shape this
plan's design change makes categorically wrong**
- **Found during:** Task 2, GREEN phase (full-suite run after implementing
  `SidecarKeyringSlotStore`)
- **Issue:** Test 4 ("a successful QR poll writes the token through the TokenStore seam via
  rustInvoke") asserted `rustInvokeFrame?.args` equals `['QR-SESSION-TEST-TOKEN']` with no slot.
  Every `keyring_set` call now sends `[secret, slot]` by design (Task 1's Rust-side position,
  Task 2's TS-side forwarding) — the old assertion was directly falsified by the plan's own
  intended behavior, not an unrelated pre-existing issue.
- **Fix:** Updated the assertion to `.toStrictEqual(['QR-SESSION-TEST-TOKEN',
  KEYRING_SLOT_STEAM_REFRESH_TOKEN])`, importing the constant from `../keyringTokenStore` rather
  than retyping the literal.
- **Files modified:** `src/backend/sidecar/__tests__/steamAuthFlows.test.ts`
- **Verification:** `npx jest steamAuthFlows.test.ts` passes; full `npm run test:ci` green
  (174/174 suites, 3307/3307 tests).
- **Committed in:** `71960ff83` (GREEN commit)
