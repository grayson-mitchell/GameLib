# Phase 34.4.1 Plan 12: Humble secret-store seam (pure refactor) Summary

**Humble's credential encryption moved off a direct `safeStorage` import into a dual-build `HumbleSecretStore` seam (`secretStore.ts`), with `getCredentials()`/`getCsrfToken()` converted to async end-to-end — a pure refactor with byte-identical Electron behavior; the Tauri session is still PLAINTEXT until plan 13 installs the keyring implementation.**

## Accomplishments

- `src/backend/humble/secretStore.ts`: the `HumbleSecretStore` interface
  (`isAvailable`/`getSecret`/`setSecret`/`clearSecrets`) + module-scoped holder
  (`getHumbleSecretStore`/`setHumbleSecretStore`) + `ElectronHumbleSecretStore`, whose
  three private methods are the verbatim bodies of the former
  `encryptionAvailable`/`encryptCookie`/`decryptCookie` free functions that used to live
  in `user.ts`. Reads/writes the SAME `configStore` keys (`sessionCookie`/`csrfToken`)
  under the SAME `humble:v1:` prefix — Electron's on-disk `humble_store/config.json` is
  unchanged in every field. Contains no `backend/sidecar` import and no
  `encryptionDegraded` reference (both grep-verified at 0 occurrences).
- `user.ts`: `encryptionAvailable`/`encryptCookie`/`decryptCookie` deleted;
  `safeStorage` removed from the `'electron'` import (`session` kept — still used by
  `getLiveCsrfToken()`'s and `disconnect()`'s Electron branches). Added a
  `storeHumbleSecret(key, value)` helper that calls `setSecret()` then explicitly writes
  `encryptionDegraded` from `isAvailable()` (never merely "not set to true") — used at
  all 4 write sites (session cookie in `finishLogin`, csrf capture's two branches in
  `finishLogin`, csrf backfill in `checkHealthAndFlagExpiry`).
- `getCredentials()`/`getCsrfToken()` are now `static async`, mirroring
  `storeManagers/steam/user.ts`'s `SteamUser.getCredentials()` precedent (async since
  Phase 28 for the identical reason). Every non-already-async caller now awaits:
  `validation.ts:24`, `library.ts:790` (`runSync`), `library.ts:1160` (`doRevealKey`),
  `user.ts:654` (`checkHealthAndFlagExpiry`), `user.ts:697` (same function, csrf
  backfill gate). `getLiveCsrfToken()`'s two `return HumbleUser.getCsrfToken()` sites
  needed no edit — they were already inside an `async` function returning a `Promise`.
  **No call site required promoting its enclosing function to `async`** — all five were
  already `async` (three already-async, plus `finishLogin`/`checkHealthAndFlagExpiry`
  which were already `async` before this plan).
- `electronReachLedger.test.ts`'s `BASELINE_ELECTRON_REACHING_MODULES` extended with
  `src/backend/humble/secretStore.ts` (34 → 35 electron-importing modules) — this is a
  NEW edge (secretStore.ts's own direct `import { safeStorage } from 'electron'`), not a
  moved one; `user.ts` was already baselined for its (now `session`-only) direct import
  and stays baselined for that reason alone.

## Decisions Made

- `encryptionDegraded` stays in `user.ts`, not the seam — a UI concern, not a storage
  concern (see frontmatter key-decisions for the full reasoning).
- `storeHumbleSecret()` centralizes the "write secret, then explicitly set
  `encryptionDegraded`" pattern so all 4 call sites can't drift from WR-07's
  explicit-`false`-on-healthy-store requirement.
- `STORE_KEYS` typed to preserve the store schema's literal key types (see frontmatter) —
  a TypeScript-only decision with no behavioral effect, needed to keep `tsc --noEmit`
  clean against `TypeCheckedStoreBackend.set()`'s generic signature.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] `library.test.ts`'s single-flight-guard test assumed
`getGamekeys()` was reached synchronously before any `await`, which the async
conversion falsified**
- **Found during:** Task 2, full-suite verification (`npx jest src/backend/humble/`)
- **Issue:** `sync() — single-flight guard (round 2)`'s test calls
  `HumbleLibrary.sync()` twice back-to-back, then synchronously calls
  `resolveGamekeys(...)` to unblock the in-flight `getGamekeys()` promise. This worked
  before this plan because `runSync()`'s first `await` was `await getOrderDetail(...)`
  reached only after `getGamekeys()` was already dispatched — `HumbleUser.getCredentials()`
  was synchronous, so `runSync()` ran uninterrupted from its start through the
  `getGamekeys()` call before yielding. Converting `getCredentials()` to async inserted
  a NEW await point (`const cookie = await HumbleUser.getCredentials()`) BEFORE the
  `getGamekeys()` call, so `runSync()` now yields one microtask tick earlier — the test's
  synchronous `resolveGamekeys(...)` call fired before `mockGetGamekeys` had ever been
  invoked, so the local `resolveGamekeys` closure variable was still unassigned
  (`TypeError: resolveGamekeys is not a function`). Because this test's promise never
  settled as expected, `syncInFlight` (library.ts's module-level single-flight guard)
  stayed stuck non-null for the rest of the file, cascading into 37 further false
  failures (`Exceeded timeout of 5000ms`) in every OTHER test that calls
  `HumbleLibrary.sync()` afterward in file order.
- **Fix:** Inserted `await flushAsync()` (the file's existing microtask-flush helper,
  already used at 10+ other sites in this file) between the two `sync()` calls and the
  `resolveGamekeys(...)` call, giving `runSync()` the one extra tick it now needs to
  reach `getGamekeys()` before the test tries to resolve it.
- **Files modified:** `src/backend/humble/__tests__/library.test.ts`
- **Verification:** Full re-run of `src/backend/humble/__tests__/library.test.ts`:
  111/111 passing (previously 38 failed once this plan's async conversion landed,
  confirmed via a temporary revert-and-rerun to isolate the regression from any
  pre-existing flake).
- **Committed in:** `ff1ddf32a` (Task 2 commit)

Note: this file (`library.test.ts`) was NOT in this plan's `files_modified` frontmatter
or Task 2's `<files>` list — its own timing assumption broke as a DIRECT, necessary
consequence of the async conversion the plan explicitly required (`getCredentials()`
becoming `async`), not unrelated scope creep. Per Rule 1 this was fixed inline rather
than deferred.
