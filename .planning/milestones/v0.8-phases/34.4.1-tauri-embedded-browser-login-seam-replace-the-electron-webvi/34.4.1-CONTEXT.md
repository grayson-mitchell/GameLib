# Phase 34.4.1: Tauri embedded-browser login seam - Context

**Gathered:** 2026-07-27
**Status:** Ready for planning

<domain>
## Phase Boundary

Replace the **Electron-only embedded-browser login mechanism** — the single
`<webview partition="persist:…">` at `src/frontend/screens/WebView/index.tsx:488-503` (corrected
2026-07-27 by 34.4.1-RESEARCH.md — the `:467` inherited from ROADMAP.md predated 34.4's
`WebviewUnavailablePanel` addition, which shifted the element down ~21 lines) plus
`session.fromPartition()` — with a Tauri-workable equivalent, and port the **6 browser-auth
channels** carved out of Phase 34.4 by its **D-01/D-02**. Additive and reversible —
`npm start` (Electron) and `pnpm tauri:dev` must both work when the phase closes.

**The scouting finding that reshapes 34.4 D-07's assumption:** the five logins sharing that
one `<webview>` element do **not** share one capture mechanism. They split in two:

| Runner | Capture mechanism | Code |
|---|---|---|
| Epic (`legendary`) | OAuth code from redirect URL (`localhost?code=`) | `WebView/index.tsx:265-273` |
| GOG | OAuth code from redirect URL (`embed.gog.com/on_login_success?code=`) | `WebView/index.tsx:239-252` |
| Amazon (`nile`) | OAuth code from redirect URL (`openid.oa2.authorization_code`) | `WebView/index.tsx:253-262` |
| Zoom | Token via redirect URL (`return_li_token=true`) | `WebView/index.tsx:76-77` |
| **Humble** | **Cookie-jar read** (`_simpleauth_sess` on `persist:humble`) | `humble/user.ts:262+` |

So the mechanism needs **navigation observation** (4 runners) and **cookie read** (1 runner),
and only the second depends on the API 34.4 D-07 flagged as unverified. **Both still ship as
one mechanism** (**D-01**), but the risk is not evenly distributed and planning must not treat
it as though it were.

**In scope:**
- **One shared login-window mechanism** built on Tauri `WebviewWindow` (**D-01**), extending
  the fail-closed child-window scaffolding `tauriChildWindows.ts` already ships.
- **The 6 Humble browser-auth channels**: `humbleStartLogin`, `humbleReconnect`,
  `humbleStopLogin`, `humbleLoginNavigated`, `humbleGetLoginUserAgent`, `humbleRevealKey`.
- **Wiring the 4 OAuth runners to the new mechanism** — but *not* their backend auth channels
  (**D-04**).
- **Closing 34.4 D-05's `humbleDisconnect` partial** (**D-08**).
- **Splitting 34.4 D-04's `WebviewUnavailablePanel` branch** (**D-06**).
- **An executed spike before planning** (**D-11**) and a **blocking 4-item live gate**
  (**D-10**).
- `34.4.1-PORTED-CHANNELS.md` declared list + SEAM.md §3→§1 move + `IPC-PORT-INVENTORY.md`
  update; extending `electronReachLedger.test.ts` (the standing 34.3 **D-10** obligation).

**Explicitly OUT of scope:**
- **`login`, `authGOG`, `authAmazon`, `authZoom`** — Phase 34.5's channels (**D-04**). The
  mechanism is wired for them; their logins stay blocked until 34.5, **declared, not silently
  broken**.
- **In-app store and wiki browsing** (**D-05**): `/store/epic|gog|amazon|zoom|steam`, `/wiki`,
  and `store-page?store-url=` deep links. Same component, different requirements (chrome,
  last-url restore, adtraction workaround).
- **An open-ended fight with Cloudflare Bot Management** (**D-07**) — the reveal attempt is
  time-boxed, and rounds 1–6 of `humble-reveal-key-fails` are NOT to be re-run.
- **Live-proving Windows and Linux** (**D-09**) — verified by reading the crate and declared.
- Any change to the Electron build's *behavior*. As in 34.1/34.2/34.3/34.4 this phase may
  touch Electron-side files; the invariant is behavioral, not textual.

## Implementation Decisions

### The mechanism

- **D-01 — ONE child `WebviewWindow` serves all five logins.** Watch its navigation for the
  four OAuth runners; read cookies for Humble. This is the closest structural analogue to
  Electron's `<webview>`, keeps 34.4 **D-01**'s "one shared seam" premise true, and means
  Phase 34.5 inherits exactly one thing rather than two. **The scaffolding already exists:**
  `src/preload/api/tauriChildWindows.ts` (34.1 **D-12**) already creates real `WebviewWindow`s
  for **untrusted renderer-supplied remote content**, with generated labels that match no
  capability and therefore receive **zero** Tauri command access — and its own docstring
  states the login story was deliberately left out only because it had "no consumer to design
  against." That precedent also **already answers 34.3 D-02's landmine** (the
  `"windows": ["main"]` grant-inheritance hazard): the login window must be labelled by the
  same generated-never-derived scheme, never `main`, never `about`.
  Rejected: forking — system browser for the 4 OAuth runners (only one runner would then
  depend on the unverified cookie API, and the 4 would gain real SSO/password-manager
  support — but it is two mechanisms to maintain and 34.5 inherits both); system browser for
  all 5 (zero dependence on any Tauri webview API, but Humble's cookie handoff would be
  genuinely awkward and `humbleRevealKey` would lose its only in-app answer, **D-07**).

- **D-02 — WHO owns the window and the cookie/URL read is a RESEARCH call, settled
  empirically.** The tension is real and unresolved from the outside: `WebviewWindow`'s
  constructor is a webview-context-only JS API the headless Node sidecar **cannot call at
  all** (34.1 D-12's structural finding), yet `humbleStartLogin` today runs `watchForLogin()`
  in the *backend* and the project's standing rule is "Rust is the platform seam" (29
  **D-01**). Both shapes are defensible — Rust arms driven by the sidecar (consistent with 29
  D-01 and 34.3 D-02's Rust-side-call/zero-grant pattern, most new Rust in the series) or
  renderer-owned window feeding candidates down to the existing sidecar channels (least new
  Rust, reuses proven scaffolding, but splits orchestration and grows `main`'s grants).
  **Binding constraint either way: the 6 ported channels keep their current signatures**, so
  the frontend and `common/types/ipc.ts` are unaffected by the choice.

- **D-03 — If the cookie-jar read does not work on macOS, the phase STILL CLOSES.** The
  mechanism ships and is wired for the four OAuth runners — which is this phase's stated job,
  since **34.5 is what it blocks and 34.5 needs navigation observation, not cookies**. Humble
  login keeps an honest "not available on this build" surface naming the *specific* reason,
  declared per-row. This is the 34.4 D-04 / 34.4 D-05 / 34.3 D-08 declaration discipline:
  ship what genuinely works, name precisely what does not. Rejected: building a Humble
  paste/manual-handoff fallback in-phase (the store write and `finishLogin` validation already
  work in the sidecar, so it is technically cheap — but it is an unbudgeted second mechanism
  with a UX nobody has designed); refusing to close without all 5 (an open-ended hunt blocking
  34.5 on the one runner 34.5 does not need).

### The boundary

- **D-04 — Mechanism + Humble's 6 ONLY; the mechanism is proven end-to-end through HUMBLE.**
  The four OAuth logins cannot complete without `login`/`authGOG`/`authAmazon`/`authZoom`,
  which are **Phase 34.5's** channels and still return `UNPORTED_CHANNEL_MARKER`. So the
  mechanism can be structurally correct while those four logins still fail — and the only
  login whose backend is already ported is **Humble** (34.4 shipped its other 16 channels).
  Prove the mechanism there. The 4 get wired and declared-blocked; 34.5 then ports 4 auth
  channels into a mechanism that already works. Rejected: pulling the 4 auth channels forward
  (strongest evidence the mechanism is genuinely shared, and it would hedge **D-03** by
  leaving a live login even if Humble's cookie read fails — but it crosses the ROADMAP
  boundary and shrinks 34.5 to 53); porting just `authGOG` as a second proof point (a real
  middle path — GOG's redirect capture is the simplest — but still boundary-crossing for
  evidence **D-11**'s spike should produce more cheaply).

  **Note the consequence, stated plainly:** under **D-03** + **D-04**, the worst realistic
  outcome is a phase that delivers a working mechanism, unblocks 34.5, and ports 6 channels of
  which the login trio is declared degraded. That is an acceptable outcome, not a failure —
  but it must be *declared* as such, not discovered at review.

### The store surfaces

- **D-05 — In-app store and wiki browsing is OUT OF SCOPE; file it as its own work.** The
  ROADMAP scopes this phase to the login path, and the store routes have genuinely different
  requirements: the `WebviewControls` chrome (back/forward/reload/open-in-browser),
  `sessionStorage` last-url restore per store, `validStoredUrl` host validation, and the
  adtraction redirect workaround (`WebView/index.tsx:275-300`) — none of which login needs.
  Keeping them out holds this phase narrow, which is the whole reason 34.4 **D-01** split it
  off in the first place. Rejected: routing store links to the system browser (cheap, uses the
  already-built `open_external` arm, and would make store-search deep links work today — but
  it is a real UX divergence Phase 35 must reconcile or permanently accept); a full
  child-window replacement (closest to parity and retires the `<webview>` element entirely,
  but roughly doubles the phase — and 34.2 needed four gap cycles for less).

- **D-06 — SPLIT 34.4 D-04's `!webviewPreloadPath` branch; store routes keep a REWORDED
  panel with an open-in-browser affordance.** That branch currently covers login and store
  alike. Once login works under Tauri the login routes must stop rendering the panel and drive
  the new mechanism instead, while `/store/*`, `/wiki` and `store-page` keep it — with copy
  naming the *real* gap ("in-app store browsing isn't available on this build") plus an
  **Open in browser** button using the already-ported `openExternalUrl`. Honest per-surface
  messaging, and it keeps **D-05**'s deferral visible to users rather than only to the
  roadmap. **34.4 D-04's rider carries unchanged: Electron's behavior must not change, and
  that must be proven in a test, not asserted.** Rejected: splitting structurally but leaving
  the panel copy alone (minimum change, no drift into store UX — but the wording was written
  for the login case and reads wrong for stores).

### `humbleRevealKey`

- **D-07 — Attempt an IN-WEBVIEW fetch, TIME-BOXED; declare degraded if it fails.**
  `humblePostRequest` (`adapter.ts:264`) routes the reveal POST through Electron's
  `net.request` on `persist:humble` **specifically because** Cloudflare Bot Management 403s
  axios's TLS/HTTP fingerprint — and rounds 1–6 of the `humble-reveal-key-fails` debug session
  **falsified** cookie/header fidelity as the cause. Under Tauri the *only* structurally-new
  option is issuing the POST from **inside the webview's own JS context**, which is the one
  place a genuine WKWebView/WebView2 fingerprint exists; axios, reqwest and
  `tauri-plugin-http` are all expected to fail identically. Try it — it is cheap once the
  window exists — and if it 403s, port the channel with an honest failure surface and declare
  it per-row. **Do NOT re-run rounds 1–5.** Rejected: porting as a declared failure with no
  attempt (cheapest and loses nothing that works today, but leaves the v0.3 claim flow
  half-broken with no attempt made); treating reveal as phase-closing (an open-ended fight
  against Cloudflare inside a port phase, blocking 34.5 on a problem 34.5 does not have).

- **D-08 — Reveal opens a HIDDEN window ON DEMAND, per reveal; and `humbleDisconnect` clears
  `humblebundle.com` cookies SPECIFICALLY.** Reveal is triggered from `HumbleClaimWizard`
  (`index.tsx:112`), long after login closed, so the webview context must be created at reveal
  time: an invisible child window on humblebundle.com, POST from its JS context, return,
  close. Nothing persists between reveals — **no idle window holding an authenticated Humble
  session**, which is the same orphan-session concern Phase 34 **WR-03** raised about the
  sidecar. It must carry the same fail-closed labelling as **D-01**.
  This also closes **34.4 D-05's explicit obligation** ("`humbleDisconnect` must be revisited
  once 34.4.1 creates a real browser context"): under Tauri there are no partitions, so login
  cookies land in the **app-wide platform cookie jar**. Disconnect must delete the stored
  credential (already works — the real security boundary) **and** clear the jar's
  `humblebundle.com` entries so a re-login genuinely starts fresh. **Scoped by domain, never a
  blanket wipe** — the same jar will hold Epic/GOG/Amazon cookies once 34.5 lands, and
  clearing those would silently sign the user out of storefronts they never touched.
  Rejected: one persistent hidden Humble context (faster per reveal, closer to `persist:humble`
  semantics — but an always-alive authenticated session and a heavier teardown obligation);
  best-effort clear only (mirrors `user.ts`'s existing guarded `wipeSteps` shape and is the
  fallback if the API cannot scope a clear — but as the *goal* it re-declares D-05's partial
  for a second phase running, which **D-08** exists to prevent).

### Proof and sign-off

- **D-09 — macOS LIVE-PROVEN; Linux and Windows verified by reading the crate and DECLARED
  per-platform.** Tauri's webview is **WKWebView** (macOS), **WebKitGTK** (Linux),
  **WebView2/Chromium** (Windows) — three cookie-API stories, three navigation-event stories,
  three TLS fingerprints, and **macOS, the primary dev platform, is furthest from the Chromium
  stack that currently works** (34.4 D-07's "most likely way this phase gets surprised late").
  Matches every prior slice's precedent: 34.3 **D-12** and 34.4 **D-10** were macOS-only live
  gates. Record the per-platform finding in `34.4.1-PORTED-CHANNELS.md` so the omission reads
  as a decision. Rejected: additionally requiring test-proven safe degradation on the other two
  (a modest extra burden guarding against exactly the `navigator-clipboard-noops-under-tauri`
  failure shape, where an API resolved successfully *without doing anything* — **worth
  volunteering during planning if cheap**, see Discretion); live-proving all three (highest
  confidence, front-loads the divergence — but needs three machines and every IPC slice so far
  closed on macOS alone).

- **D-10 — A BLOCKING 4-item live gate under `tauri:dev`.** Carries 34.3 **D-13** and 34.4
  **D-08**. The items:
  1. **A Humble login completed FROM SCRATCH** — no Electron-captured session. This is
     precisely the thing 34.4 **D-09** had to declare impossible and write into its own gate
     as a manual precondition; making it work is this phase's headline deliverable.
  2. **The session survives a quit-and-relaunch**, proven at the persistence layer (the
     present-to-absent store proof 34.4-10 established is stronger than a UI check).
  3. **`humbleDisconnect` leaves no `humblebundle.com` cookie** and a re-login is genuinely
     fresh (**D-08**).
  4. **The `humbleRevealKey` attempt's real outcome recorded**, pass or 403 (**D-07**).
  **Failure is blocking**: findings become a gap cycle inside 34.4.1. **Preconditions must be
  written as explicit numbered steps** — 34.4 D-09's lesson is that an unstated precondition is
  exactly how a gate gets skipped and becomes UAT debt (Phases 21/30/34.2).
  Rejected: adding a mandatory stale-`isTauri()`-guard sweep as item 0 (**not chosen as a gate
  item, but see Discretion — the risk is real and cheap to cover in planning**); leaving gate
  composition to the planner.

- **D-11 — A THROWAWAY SPIKE MUST RUN BEFORE PLANNING.** Nothing in this repo has confirmed
  that Tauri's webview cookie API exists at 2.11.5, that it reaches the platform cookie jar, or
  that child-window navigation is observable. The spike must actually **execute**: open a child
  `WebviewWindow` on a live site, observe navigation, attempt a cookie read, and record what
  happened. **No plan may be written on an unverified API.** This is 34.3 **D-05**'s standing
  lesson ("an API inference is not a measurement") applied to the phase whose entire approach
  depends on the answer. The project has `/gsd-spike` and a `spike-findings-gamelib` skill for
  exactly this. Rejected: documented verification by reading the installed
  `tauri 2.11.5` / `wry 0.55.1` crate sources and generated permission reference (the same
  method that settled `core:window:default` in the capabilities file, and reading the crate IS
  reading the implementation — **do this too, it is complementary**, but it still cannot prove
  the API reaches the real macOS cookie jar at runtime, which is exactly what 34.3 D-05 got
  wrong); planning on the inference and verifying during execution (the precise failure both
  34.3 D-05 and 34.4 D-07 warn about).

### Claude's Discretion

- **The window/cookie ownership shape (D-02)** — Rust-arms-driven-by-sidecar vs
  renderer-owned. Settle it on the spike's evidence. Non-negotiable constraints: the 6
  channels keep their signatures; the login window matches **no** capability; nothing derives
  a window label from a caller-supplied URL (T-34.1-27).
- **A stale-`isTauri()`-guard sweep of the login path before human gate time.** Not adopted as
  a gate item, but **34.4's gate item 2 failed on exactly this** — a Phase 30 guard in
  `GlobalState.tsx` whose own comment asserted a premise a later plan had falsified, leaving a
  ported channel unreachable while every unit test, `tsc`, `cargo check` and the reach ledger
  stayed green. 34.4-10 *also* caught a bare-import build regression invisible to `tsc` and
  jest but fatal to `npm start`. **Both checks are cheap; fold them into planning as tasks.**
- **Whether to add test-proven safe degradation for Linux/Windows** (D-09's rejected option).
  If it is cheap, do it — `navigator-clipboard-noops-under-tauri` is the live reminder that an
  API can resolve successfully while doing nothing.
- **Whether 34.4 D-06's `electronStub.net.request` hardening is retired or kept.** 34.4 D-06
  made it emit an `'error'` naming the missing seam, specifically to stop *this* phase's owner
  being sent back into Cloudflare territory. If **D-07**'s in-webview path replaces
  `humblePostRequest` under Tauri, the stub's only caller changes — decide deliberately,
  do not leave a stale "missing seam" message pointing at a seam that now exists.
- **The curated-import rule, inherited unchanged** (30 **D-08** → 34.1 **D-09** → 34.2
  **D-04** → 34.3 **D-14** → 34.4): import the UNDERLYING module, never a feature module's
  `ipc_handler.ts`. **`humble/ipc_handler.ts` now registers 15 ALREADY-PORTED channels
  alongside this phase's 6** — side-effect-importing it would double-register them *and* drag
  `backend/ipc` in. Import `humble/user.ts`, `humble/adapter.ts` and `humble/userAgent.ts`
  directly.
- **Send-vs-handle discipline.** `humbleStopLogin` and `humbleLoginNavigated` are
  fire-and-forget relays; `humbleStartLogin`, `humbleReconnect`, `humbleGetLoginUserAgent` and
  `humbleRevealKey` return values. A mismatch **fails 100% silently**
  (`sidecar-send-channels-fail-silently`). Cross-check every registration against
  `humble/ipc_handler.ts`'s own `addHandler`/`addListener` call for that exact channel name.
- **`humbleGetLoginUserAgent` is a pure function** (`humble/userAgent.ts:26`) with no browser
  dependency at all — it travelled to this phase only because its consumer is the deferred
  `<webview>`'s `useragent` attribute (34.4 D-02). It ports trivially regardless of how
  **D-03** resolves. Note this so the phase is not mis-scored as "0 of 6" in the bad case.

<specifics>
## Specific Ideas

- **The five logins do NOT share one capture mechanism, only one element.** Four read an OAuth
  code out of a redirect URL; one reads a cookie jar. 34.4 D-07 framed this phase around "the
  cookie API," but **cookies are one runner's problem** — and the runner that blocks 34.5 is
  none of them. A planner that treats the cookie read as the critical path has the risk
  inverted.
- **The scaffolding is further along than 34.4 D-07 assumed.** Candidate 1's window creation,
  labelling, capability isolation and anti-phishing rules are already built and code-reviewed
  in `tauriChildWindows.ts`, and `core:webview:allow-create-webview-window` is already granted.
  34.3 D-02's landmine is already answered by that precedent. What is genuinely unknown is
  **navigation observation and cookie read** — nothing else.
- **`navigator-clipboard-noops-under-tauri` is the shape to fear, not an exception.** WKWebView
  resolved a write that never happened. A cookie read returning `[]` on macOS would be
  indistinguishable from "the user isn't logged in yet" to `watchForLogin`'s poll — it would
  spin silently forever. **The spike must distinguish "empty" from "unsupported."**
- **Do not re-run the Cloudflare investigation.** Six rounds established cookie/header fidelity
  is not the problem and the TLS/HTTP transport fingerprint is. The only new information is
  per-platform: WKWebView / WebKitGTK / WebView2 are three different fingerprints, and macOS is
  furthest from the Chromium stack that currently works.
- **Reveal is live-testable; redeem is not.** 34.4 D-08 refused a live `redeemSteamKey` because
  it burns a key irreversibly. Revealing a Humble key is irreversible *at Humble* but not
  destructive — per Phase 14's D-30 realignment, `redeemed_key_val` means **revealed, not
  activated**. Gate item 4 is legitimate.
- **34.4 D-09 said there is "no Tauri path to create a Humble session" and wrote it into its
  gate as a manual precondition.** Falsifying that statement is this phase's headline
  deliverable and gate item 1. When it lands, that precondition should be struck from the
  record rather than left standing.
- **The bad case is a legitimate outcome, but only if declared.** Under **D-03** + **D-04**,
  this phase can close having delivered a working mechanism, unblocked 34.5, and shipped
  Humble's login trio declared-degraded. Say so up front; do not let it be discovered at
  review.
