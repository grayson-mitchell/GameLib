## Accomplishments

### F-4 — visible login window sized, centered, raised (Task 1)

`humble_login_open`'s `WebviewWindowBuilder` chain now applies `.inner_size(900.0, 700.0)`,
`.center()` and `.focused(true)` — but ONLY when `visible` is true. The same arm also builds the
HIDDEN windows used by disconnect's cookie/storage clears and the reveal-POST transport; those stay
completely untouched (verified by reading the arm and stating the branch condition explicitly:
`if visible { ... }`, `src-tauri/src/main.rs`). `.title()` remains deliberately absent — the
existing WR-07 anti-phishing comment now also records the F-4 resolution, and the grep gate
(`grep -v '^\s*//' ... | grep -c '\.title('`) proves no `.title(` call was added to the arm itself
(the file-wide count of 2 is pre-existing, from the unrelated `dialog_message`/`notification_show`
arms, confirmed unchanged from `git show HEAD` before this plan touched the file).

### F-2 — rejection-log collapse with a liveness heartbeat (Task 2)

`watchForLogin()` gained a new `logRejectionStatus()` closure that tracks the last-logged rejection
status and a suppressed-count. `finishLogin()` no longer logs the rejection itself — it calls a new
`onRejected` callback the caller supplies, so the STATEFUL collapse logic lives where the state
already is (the watch's own closure), not threaded through `finishLogin`'s return contract.

- **Consecutive identical-status rejections** produce exactly ONE line:
  `Humble login validation rejected candidate session: <status>`
- **A status CHANGE** always logs again, naming how many were suppressed under the previous status:
  `Humble login validation rejected candidate session (status changed; N prior identical
  rejection(s) suppressed): <status>`
- **A 30-second elapsed-time liveness heartbeat** (`LOGIN_WATCH_LIVENESS_LOG_INTERVAL_MS`, a NEW
  constant) fires even when the status never changes:
  `Humble login still waiting (status unchanged; N rejection(s) suppressed since the last line):
  <status>`

`COOKIE_POLL_INTERVAL_MS` and `VALIDATION_THROTTLE_MS` are now exported and pinned by a new test
(`1500`/`3000`, unchanged) so a later "tidy" of this logging fix cannot alter timing under cover.
`LOGIN_WATCH_TIMEOUT_MS` is likewise pinned (`600000`).

### F-3 — identity-failure diagnostics name the endpoint (Task 3)

`getAccountIdentity` (`adapter.ts`) now opts into `mapAxiosError`'s pre-existing diagnostic-context
mechanism (`mapAxiosError<HumbleUserData>(err, '/api/v1/user/info')`) — the SAME mechanism `revealKey`
has used since round 5. Any caught failure — including an otherwise-unmapped status like the live
gate's 404 — now logs `Humble adapter: /api/v1/user/info HTTP failure diagnostic status=<code>
contentType=... bodyIsString=... bodyLength=...` before falling through to the existing generic
`unexpected request failure` rethrow. Structural-only: status/contentType/body-shape/length, NEVER
the response body, cookies, or headers. The 404 itself is NOT diagnosed or fixed (out of this gap
cycle's scope, per the plan's own instruction) — only made diagnosable from the next `gamelib.log`
capture alone.

### S-09 — checkHealthAndFlagExpiry's csrf backfill routed through the seam (orchestrator addendum, D-GAP-03)

Plan 10's sweep found a FIFTH silently-dropped site no other gap-cycle plan owned:
`checkHealthAndFlagExpiry()`'s opportunistic `csrf_cookie` backfill called `session.fromPartition()`
with no `getLoginWindowSeam()` guard anywhere in the function. Under Tauri this hit
`electronStub.ts`'s `{}`-returning stub, threw into the surrounding try/catch, and the self-heal
silently no-op'd on every health check — an account that connected before csrf capture shipped (or
whose `finishLogin()` capture missed) never healed, so every reveal POST omitted the
`csrf-prevention-token` header. Live-gate item 4 passed only because that account already held a
token from `finishLogin` — the defect was masked, not absent.

Per the addendum's instruction, the seam is NOT declared unreachable outside a login flow — it can
serve this read, the same way `disconnect()`'s `clearHumbleCookies` wipe step already opens a
temporary hidden window to reach the jar outside an active login. The fix now:

- Guards with `const seam = getLoginWindowSeam()`; the Electron branch is byte-identical to before.
- Under the seam: opens a hidden window (`seam.open(HUMBLE_BASE_URL, { visible: false, userAgent:
  standardBrowserUserAgent() })`), reads `csrf_cookie` via `seam.cookies(label,
  'www.humblebundle.com', ['csrf_cookie'])` (same host/name filter `finishLogin`'s own seam-path
  capture uses), stores it via `storeHumbleSecret('csrfToken', ...)` if present, and closes the
  window in a `finally` on every exit path (success, a rejecting cookie read, or a rejecting
  `open()` itself never attempts a close — nothing to leak).
- Best-effort/non-fatal throughout, matching the Electron branch and `finishLogin`'s own capture
  exactly — never blocks the health check, never logs the token value.

`34.4.1-SEAM-PARITY-SWEEP.md` was regenerated (the first regeneration since Plan 10 wrote the
instrument) and now shows **0 supplementary (unguarded-`session.fromPartition`) findings** — the
mechanical proof S-09 is closed, not merely a manual read of the diff. Regenerating required fixing
three unrelated, ACCUMULATED-DRIFT blockers in the script itself (never hand-editing the generated
`.md`, per the file's own docstring): 6 sites' line-number hints refreshed (shifted by plans 11-17's
own edits plus this plan's Tasks 1-3), `CONFIGSTORE_SET_RE` widened to also recognize Plan 12's
`storeHumbleSecret(...)` sink (which replaced the literal `configStore.set('csrfToken', ...)` shape
the script was originally written against), and a new `SITE_PROFILES` entry for Plan 17's
diagnostic-label ternary (`library.ts:1202`, a log-label choice, not a capability drop). Two
CONTENT-level staleness issues surfaced during this regeneration but are OUT of this plan's scope
(F-6/F-1's disposition text in the regenerated table lags their own already-shipped closures in
plans 16/13) — logged to `deferred-items.md` for plan 19 (declare/reconcile) rather than hand-edited
away.

`seamBranchParity.test.ts`'s `KNOWN_GAP` registry required NO update: S-09 was never modeled as a
`wipeSteps`-shaped dual-branch site in that file (it tracks the `disconnect()`/`logout()` category-
parity mechanism specifically) — S-09 is tracked solely in the sweep document's own supplementary
findings section, which now reports zero. `KNOWN_GAP` stays empty, exactly as plan 16 left it.
