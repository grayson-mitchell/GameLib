<objective>
Route Humble's credential encryption through a seam instead of a direct `safeStorage` call, and
give it the async shape a keyring requires — **without changing Electron's behavior and without
yet changing where the secret lands.**

Purpose: F-1's root cause is that `humble/user.ts:1` imports `safeStorage` from `'electron'`,
which in the sidecar resolves to `electronStub.ts:489` where `isEncryptionAvailable` is hardcoded
`false` and `encryptString`/`decryptString` throw. So `encryptionAvailable()` (`user.ts:78`) can
only return false under Tauri and the plaintext branch at `user.ts:88` is the only reachable
branch. Phase 28 already solved this exact shape for Steam with the `TokenStore` seam; Humble
never migrated.

Output: `humble/secretStore.ts` — the same seam shape as `humble/loginWindowSeam.ts` (interface +
module holder + nothing platform-specific), with the Electron `safeStorage` implementation
installed as the default so **this plan is a pure refactor with no behavior change on either
build.** Plan 13 installs the keyring-backed implementation and migrates existing users.

Splitting it this way is deliberate: the async conversion touches five call sites across three
files, and the migration has its own failure modes. Landing them together would make one plan
where a regression in either half is hard to attribute.
</objective>

<interfaces>
The seam template to copy — `src/backend/humble/loginWindowSeam.ts`. Its constraints are exactly
the ones this new module needs, and they are stated in its own header: it imports nothing from
`'electron'` and nothing from `backend/sidecar`, because it is compiled into BOTH the Electron
main process and the Tauri Node sidecar. `backend/sidecar/sidecarRpc` runs a Node
`readline`/stdio loop that does not exist in the Electron main process, so importing it from a
dual-build file would break Electron's build.

Note the ONE difference from `loginWindowSeam.ts`: that module's holder starts `null` and the
Electron build never installs anything, because `null` IS the Electron path. Here the Electron
implementation is real code that must run, so the holder defaults to the Electron
`safeStorage` implementation and the sidecar REPLACES it. Consequence worth stating: a sidecar
that fails to install its implementation degrades to the CURRENT behavior (plaintext), not to no
storage at all — plan 13 must therefore prove the install actually happened, not assume it.

Current synchronous surface being converted (`src/backend/humble/user.ts`):
```
function encryptionAvailable(): boolean            // L78  — try { safeStorage.isEncryptionAvailable() } catch { false }
function encryptCookie(plain: string): string      // L86  — plaintext branch at L88, prefix+base64 at L99
function decryptCookie(stored: string): string     // L108 — legacy non-prefixed plaintext read at L110
static getCredentials(): string | undefined        // L151
static getCsrfToken(): string | undefined          // L165
```
`HUMBLE_TOKEN_PREFIX` / `HUMBLE_TOKEN_STORE_KEY` come from `./constants`.

The `encryptionDegraded` flag semantics that MUST survive (`user.ts:96` and `user.ts:104`): set
`true` when storing plaintext, and **cleared to `false` on a healthy store** — WR-07, so a user
who once logged in with encryption unavailable and later re-logs in on a fixed system does not
keep seeing a stale warning.
