## Warnings

### D-WR-01: Self-vacuating log-hygiene assertion has no non-empty guard

**File:** `src/frontend/screens/WebView/__tests__/useTauriOAuthLogin.test.tsx:1041-1092` (the
vulnerable loop is at `1075-1091`)
**Issue:** The test `'every logInfo argument uses only the permitted key vocabulary -- never a
code, token, redirect URL, or raw username'` iterates `mockApi.logInfo.mock.calls` and asserts,
per call, that no forbidden secret substring appears and that every `key=` token belongs to a
fixed permitted vocabulary:

```js
for (const [line] of mockApi.logInfo.mock.calls) {
  expect(typeof line).toBe('string')
  for (const banned of forbidden) {
    expect(line as string).not.toContain(banned)
  }
  const keysInLine = permittedKeys.filter((key) =>
    (line as string).includes(`${key}=`)
  )
  const allTokens = (line as string).match(/(\w+)=/g) ?? []
  for (const token of allTokens) {
    const key = token.slice(0, -1)
    expect(permittedKeys).toContain(key)
  }
  void keysInLine
}
```

There is no assertion anywhere in the test — before, inside, or after the loop — that
`mockApi.logInfo.mock.calls.length > 0`. A `for...of` over an empty array runs zero iterations and
the test passes trivially. Today this is non-vacuous only incidentally: the `nile` capture flow
this test drives happens to produce ≥2 `logInfo` calls (`phase=preparing`, `phase=finalizing`,
plus more). But nothing in the test itself guarantees that remains true — a future refactor of the
hook that removed or gated logging on this exact path (e.g. moved the `nile`-specific `preparing`
log behind a flag, or changed the capture flow so this scenario short-circuits before any log
fires) would make this exact regression test — the one whose entire purpose is "never leak a
secret into a log line" — pass while asserting nothing. This is precisely the "a measurement is
silently contaminated" failure shape: the security property (no secrets in logs) would stop being
checked, without the test file or CI showing any red.
**Fix:** Add an explicit non-vacuity guard before or after the loop, e.g.:
```js
expect(mockApi.logInfo.mock.calls.length).toBeGreaterThan(0)
```
This mirrors the pattern already used correctly elsewhere in this same file (e.g. the `matching`/
`teardownLines`/`finalizingLines`/`preparingLines` filters at lines 543, 870, 951, 985, 1009,
1031, 1160, 1202, 1270, 1289, 1343 — several of which do assert on the filtered array's length
rather than looping blindly). Alternatively, use `expect.assertions(n)` with a computed minimum
count so Jest itself fails if fewer assertions ran than expected.

### D-IN-01: `WebviewUnavailablePanel.test.tsx`'s minted-key i18n gate covers 4 of the component's 6 keys (no live catalog defect — independently verified)

**File:** `src/frontend/screens/WebView/components/__tests__/WebviewUnavailablePanel.test.tsx:274-292`
**Issue:** `mintedKeyPaths` lists only:
```js
const mintedKeyPaths = [
  ['webview', 'unavailable', 'platform', 'heading'],
  ['webview', 'unavailable', 'platform', 'body'],
  ['webview', 'unavailable', 'epic', 'heading'],
  ['webview', 'unavailable', 'epic', 'body']
]
```
and runs `it.each` gates against `gamelib.json`/`translation.json` for only these four. The
component (`WebviewUnavailablePanel.tsx:91-100`) also calls `tGamelib('webview.unavailable.next-step', ...)`
and `tGamelib('webview.unavailable.open-in-browser', ...)` — two keys this test's catalog-placement
gate never checks. I independently verified via direct JSON inspection that both missing keys
**do** exist in `public/locales/en/gamelib.json` with matching default values and are **absent**
from `public/locales/en/translation.json`, so there is no live catalog defect today — this is a
test-completeness gap, not a shipped bug.
**Fix:** Add the two missing paths to `mintedKeyPaths`:
```js
['webview', 'unavailable', 'next-step'],
['webview', 'unavailable', 'open-in-browser']
```
so a future edit that moved either key to the wrong catalog would actually be caught.

### D-IN-02: Duplicate `.runnerList` selector

**File:** `src/frontend/screens/Login/index.scss:72-89`
**Issue:** Two separate rule blocks target the same `.runnerList` selector back-to-back:
```scss
.runnerList {
  display: flex;
  flex-direction: column;
  align-items: center;
  justify-content: center;
  position: relative;
  user-select: none;
  flex-wrap: wrap;
  background-color: var(--body-background);
  opacity: 0.96;
  padding: var(--wrapper-padding);
  border-radius: 10px;
  min-width: 400px;
}

.runnerList {
  width: 100%;
}
```
No properties overlap, so the cascade currently produces the same visual result as one merged
block — this is not a live bug — but it is dead weight and a maintenance trap: a future edit to
`width` in the first block would appear to have no effect (silently overridden by the second),
and a `git blame`/diff on either block in isolation loses the fact that they're the same rule.
**Fix:** Merge into a single `.runnerList { ... }` block.

### D-IN-03: Inert `grid-column` declaration (parent is not a grid container)

**File:** `src/frontend/screens/Login/index.scss:224-227` (immediately following the commented-out
block at 215-222)
**Issue:**
```scss
/* Enable when there have been more than 5 logins added */
/* .runnerGroup {
  display: grid;
  grid-template-columns: repeat(2, 1fr);
  overflow-y: unset;
  max-height: unset;
  padding-inline-end: 0;
} */

.runnerWrapper:nth-child(odd):last-child {
  grid-column: 1 / -1;
  width: 100%;
}
```
`.runnerGroup` (`index.scss:195-200`) is currently `display: inline-flex`, not `display: grid` —
the block that would make it a grid container is commented out immediately above this rule.
`grid-column` has no effect on a flex child (per CSS spec, ignored on non-grid-item boxes), so this
declaration is currently a no-op in every shipped theme/layout; only the accompanying
`width: 100%` does anything today. This is a latent trap two ways: (1) a future "dead code"
cleanup pass could delete the `grid-column` line without realizing it's meant to activate together
with the commented `display: grid` block above it, and (2) if the grid block is re-enabled without
re-reading this rule, the two are easy to lose track of as a pair since nothing ties them together
other than proximity and a stale comment.
**Fix:** Either comment out `grid-column: 1 / -1;` alongside the `display: grid` block it depends
on (leaving only `width: 100%` active), or add a one-line comment tying the two together
explicitly (e.g. `// grid-column here is inert until .runnerGroup above is re-enabled as display:
grid`).

### D-IN-04: Spurious `t` dependency in `Login/index.tsx`'s login-state-sync effect

**File:** `src/frontend/screens/Login/index.tsx:151-180`
**Issue:** The `useEffect` syncing `isEpicLoggedIn`/`isGogLoggedIn`/`isAmazonLoggedIn`/
`isZoomLoggedIn`/`isSteamLoggedIn`/`isHumbleLoggedIn` from context lists `t` in its dependency
array:
```js
}, [
  epic.username,
  gog.username,
  amazon.user_id,
  zoom.username,
  steam?.username,
  humble?.isLoggedIn,
  humble?.expired,
  openOverlay,
  t
])
```
but the effect body (lines 152-161) never calls `t(...)` — it only calls `setState` setters and
reads `steamConfigStore.get_nodefault(...)`. The comment at 170-177 explains in detail why
`openOverlay` belongs in this array but says nothing about `t`, suggesting it's leftover/copy-paste
rather than deliberate. Practically harmless today (React setters are no-ops when passed an equal
value, and effect re-runs here just recompute the same booleans), but it causes this effect to
re-run on every i18next language change for no functional reason, and could mislead a future
reader into thinking `t`'s value matters to this effect's correctness.
**Fix:** Remove `t` from the dependency array (or, if some hidden reason keeps it there, document
it the same way `openOverlay`'s inclusion is documented).
