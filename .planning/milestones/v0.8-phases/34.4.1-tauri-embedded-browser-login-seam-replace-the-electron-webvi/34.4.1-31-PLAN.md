## Task 1 — Read the site before classifying it

Read `src/backend/humble/library.ts:1211` and its enclosing function. Determine what the site
actually does with respect to the two sweep axes.

**Do not reach for the classification that silences the gate.** The hard stop exists because a
silently-skipped site is how a third F-1/F-6-shaped defect would slip through — a defect class that
this phase's fully-green 3387/3387 suite missed twice. If the honest reading is that the site is
**not** parity-relevant, say so and record why; if it is, it needs a real `SITE_PROFILES` entry.

## Task 2 — Classify it

Either extend a mechanical tier so the site matches on its genuine shape, or add a `SITE_PROFILES`
entry. Whichever you choose, the entry must carry a one-line justification naming the behaviour
that puts it in that class.

**A tier extension is the higher-risk option** — widening a tier to admit this site may silently
admit others. If you extend a tier, print the set of sites matching before and after and assert the
difference is exactly `{library.ts:1211}`.

## Task 3 — Prove the gate can still fail

Run `python3 seam-parity-sweep.py` and assert **exit 0** with a verdict.

Then prove non-vacuity in the other direction — the recorded rule is *prove a grep assertion in
BOTH directions*, and this project has broken it six times:

- Temporarily remove the new classification → assert the gate returns to **exit 1** with the same
  hard stop.
- Run `python3 seam-parity-sweep.py --self-test` → assert **exit 0**, and confirm
  `expected_case_count` matches the actual number of self-test cases. That count is exactly what
  D-29-10 was: *the guard that exists to prove every check can reject was the one check nobody was
  running.*

**Measure the real exit code.** `cmd | tail` reports `tail`'s status, not the script's — a mistake
made while diagnosing this very gate. Use `cmd > file; echo $?` or `PIPESTATUS`.

## Task 4 — Update the sweep's own record
