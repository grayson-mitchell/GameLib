<objective>
Make **F-9** — the intermittent 60-second `keyring_get` timeout that hit the `humble-csrf` slot —
observable and bounded, without pretending its cause is established.

Purpose: the observed error `rustInvoke timed out after 60000ms: keyring_get` is the **sidecar's own
RPC round-trip timeout** (`src/backend/sidecar/sidecarRpc.ts`'s `requestRustInvoke()`), not a
Rust-side timeout. The Rust call was still blocked and pending when the JS side gave up. Two
consequences follow, and both are real problems independent of the root cause:
1. **A blocking Keychain read consumes the entire RPC budget.** `main.rs:755-773` calls
   `Entry::new(KEYRING_SERVICE, account).get_password()` synchronously and inline in
   `dispatch_rust_channel`. Nothing bounds it. If assumption A2 holds — that the arms run on the
   thread that also pumps `NSRunLoop::mainRunLoop()` for `wait_for_blocking_operation` — a long
   Keychain read also stalls any cookie operation queued behind it, which is a direct interaction
   with this cycle's blocking work.
2. **The failure is unclassified.** A generic RPC timeout message is indistinguishable from a
   sidecar frame leak, from a hung cookie operation, or from a Keychain stall. It cost real time to
   rule out during the last gate, and the gate record itself had to correct F-9's scope from
   Steam-only to also hitting `humble-csrf`.

**This plan does not claim to fix F-9's cause (binding constraint 6).** Research rates it
LOW-MEDIUM: the "a lookup for a MISSING Keychain entry may block far longer than one for a present
entry" hypothesis is explicitly untested, and macOS has other legitimate multi-second-to-
tens-of-seconds Keychain stall sources (an ACL/trust re-evaluation, a `securityd`/`SecurityAgent`
hiccup, a first-access-after-boot path). Task 1 measures the hypothesis directly with a stopwatch
before Task 2 changes anything. Task 2's change is explicitly framed as **observability**, not a
root-cause fix: it converts a silent 60-second stall into a fast, named `keyring:timeout` the log
can attribute.

**Adjacent already-present code this plan verifies (binding constraint 1).** Three properties of the
`keyring_get` arm have been present since Phase 28 and never tested end to end: the
`Err(keyring::Error::NoEntry) => Ok(Value::Null)` branch (a missing entry is a healthy first-run
state and **must not** become an error — Pitfall 1 / D-06), the compile-time slot allowlist that
keeps T-28-03 intact, and the fact that `keyring_set`/`keyring_delete` sit on the same unbounded
synchronous shape. Task 1 measures the `NoEntry` path by name; Task 2 asserts it still resolves
null after the timeout wrapper lands, and states explicitly which of the sibling arms were and were
not wrapped, rather than leaving the reader to guess.

Output: a timed measurement of the missing-entry hypothesis, a bounded classified Keychain read, and
an RPC-side error message that names the Keychain rather than the generic transport.
</objective>

<interfaces>
**The unbounded call (`main.rs:755-773`):**
```
"keyring_get" => {
    let account = keyring_account(keyring_slot_arg(args, 0))?;
    match Entry::new(KEYRING_SERVICE, account) {
        Ok(entry) => match entry.get_password() {
            Ok(secret) => Ok(Value::String(secret)),
            Err(keyring::Error::NoEntry) => Ok(Value::Null),      // healthy first-run state
            Err(e) => { eprintln!(…); Err(format!("keyring:unavailable:{e}")) }
        },
        Err(e) => { eprintln!(…); Err(format!("keyring:unavailable:{e}")) }
    }
}
```
`keyring_set` (`:774-794`) and `keyring_delete` have the same unbounded synchronous shape.

**The existing error vocabulary this plan extends, not replaces:**
```
keyring:unknown-slot     rejected by the compile-time allowlist (T-28-03)
keyring:bad-args         malformed args
keyring:unavailable:{e}  the backend failed
Value::Null              NoEntry — healthy, not an error
```
The new classification is `keyring:timeout` and must sit alongside these, following the same flat
`String` convention (`.map_err(|e| e.to_string())`) the file uses throughout.

**The bounded-wait pattern already in this file.** `humble_reveal_post` (`main.rs:1273-1300`) uses
`mpsc_channel` plus `rx.recv_timeout(...)`, and closes its window on the timeout path as well as on
success. The keyring wrapper should follow the same shape rather than invent a second one: spawn the
blocking call on a worker thread, send the result over a channel, and bound the receive.

**The 60 000 ms that is NOT a Rust timeout.** `requestRustInvoke()` in
`src/backend/sidecar/sidecarRpc.ts` owns it. When it fires, the Rust side is still pending — the
frame is abandoned, not cancelled. That asymmetry is worth naming in the code, because a reader who
assumes the Rust call was cancelled will misdiagnose the next occurrence.

**The three allowlisted slots (`REQ-34.4.1-GAP-01`):** `steam-refresh-token`, `humble-session`,
`humble-csrf`. The gate's sweep found `steam-refresh-token` ABSENT from the Keychain at the moment
one Steam-slot timeout hit; the second occurrence hit `humble-csrf`. Both observations are
consistent with the missing-entry hypothesis and neither establishes it.

**Privacy register, unchanged (T-28-04 / T-34.4.1-39):** never log a secret. Timings, slot NAMES
(which are compile-time constants, not user data), error variants and fixed text only.
