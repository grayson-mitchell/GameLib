# Phase 34.4.1 Plan 03: Login-Window Seam Wiring for HumbleUser.watchForLogin() Summary

**Rewired `HumbleUser.watchForLogin()`, `finishLogin()`'s csrf capture, and `getLiveCsrfToken()` to drive the Phase 34.4.1-02 login-window seam when installed — opening/polling/closing a real Rust-owned login window under Tauri, classifying every cookie read through `classifyCookieRead` so a dead cookie channel aborts loudly instead of spinning silently, and leaving the Electron `session.fromPartition` path byte-for-byte unchanged.**

## Performance

- **Duration:** ~21 min
- **Tasks:** 2/2 completed
- **Files modified:** 2 (`src/backend/humble/user.ts`, `src/backend/humble/__tests__/user.test.ts`)

## Accomplishments

- `watchForLogin()` branches on `getLoginWindowSeam()`: Electron keeps the untouched `session.fromPartition(HUMBLE_LOGIN_PARTITION)` + `setUserAgent` + `ses.cookies.get()` path; the seam path opens a Rust-owned window on `HUMBLE_LOGIN_URL` with the standard Chrome UA and reads via `seam.cookies(label, 'www.humblebundle.com', ['_simpleauth_sess'])`.
- Every seam-path cookie read is classified through `classifyCookieRead({ total, everProvedLive })`: `UNDECIDABLE` and `UNSUPPORTED_OR_ERROR` both settle `{ status: 'error' }` with a `logWarning` and NEVER poll again; `SUPPORTED_BUT_EMPTY`/a `SUPPORTED_NONEMPTY` read with no matched cookie both keep the watch alive waiting for the real login.
- Nav-event relay (REQ-34.4.1-03): `seam.takeEvents(label)` is drained before every cookie read; a main-frame `'finished'` event calls `armDeadline()` and forces that tick's cookie read to bypass the poll-path throttle — the same effect `notifyLoginNavigated()`'s `forceRevalidate()` produces today, without a recursive `checkCookie(true)` call.
- `settle()` closes the seam-owned window exactly once on every exit path (done, waiting/stop, error, deadline), via a floated `.catch()` that only logs — never throws, never strands the resolved promise. A window that finishes opening AFTER the watch already settled (e.g. `stopLogin()` fired while `seam.open()` was still in flight) is closed immediately by the `.then()` callback instead of leaking.
- `finishLogin()` takes the seam window label as an explicit 4th parameter and reads `csrf_cookie` via the seam (same label as the accepted session cookie) when one is installed, falling back to the untouched `session.fromPartition` read otherwise.
- `getLiveCsrfToken()` short-circuits to the stored snapshot (`HumbleUser.getCsrfToken()`) with a `logInfo` line when a seam is installed, since there is no live login window at reveal time under Tauri — avoiding a throw into the Electron-only `session.fromPartition` branch.
- 10 new tests in a dedicated `login window seam path` describe block (fake `LoginWindowSeam` installed/cleared via `setLoginWindowSeam()`), covering: window-open call shape, `UNDECIDABLE` loud-abort + no further tick, liveness-proven-but-no-match keeps polling until a later matched value reaches `finishLogin`, a `'finished'` nav event bypassing the throttle and re-arming the deadline, `close(label)` called exactly once on both the done and stop/silent-cancel paths, a swallowed `close()` rejection, csrf capture reusing the same window label, `getLiveCsrfToken()`'s seam guard, and an explicit Electron-path regression check.
- Hand RED-proof performed exactly as the plan's acceptance criteria required: weakened the `UNDECIDABLE` branch to a bare `return`, confirmed the "does not tick again" test now fails (times out — the watch never settles because nothing ever calls `settle()`), restored the fix, re-verified all 56 tests green.

### Task-boundary adjustment (not a Rule 1-4 deviation, documented for traceability)

**Task 1's commit (`bde1c4285`) includes plan action items 2(a) and 2(b)** (the csrf-capture seam routing inside `finishLogin()`, and `getLiveCsrfToken()`'s seam guard) **in addition to Task 1's own scope.** Both action items require the `seamLabel` parameter Task 1's `watchForLogin()` rewrite introduces on `finishLogin()`'s signature — implementing them in a separate, later commit would have required either a second signature change (churn) or leaving `seamLabel` unused in Task 1's commit (an intermediate broken state). Task 2's commit (`a78536f95`) is therefore test-only: the new seam-path describe block, which exercises both Task 1's `watchForLogin()` behavior and Task 2(a)/(b)'s csrf-capture/getLiveCsrfToken() behavior. All of the plan's required source AND test changes are present; only their distribution across the two task commits differs from a strict 1:1 reading of the plan's task list.

**During test authoring**, two self-corrections were made before the final commit (not deviations from the plan's requirements, just test-design fixes caught by running the suite):
- A fake-timer test for the nav-event/deadline-rearm case initially advanced time to an exact multiple of both `LOGIN_WATCH_TIMEOUT_MS` (600000ms) and the 1500ms poll interval, causing a poll tick and the watch deadline to fire at the identical virtual millisecond — the deadline settled the watch first, so the tick's `settled` guard silently no-op'd the intended assertion (0 calls, not a thrown error). Fixed by advancing to a time comfortably short of that boundary before triggering the forced tick, documented as a `patterns-established` entry above for future timer tests against the same constants.
- Two tests exercising a natural (non-forced) poll tick were converted from real timers to fake timers with an explicit 1500ms advance, avoiding a ~1.5s real-time wait per test.

**Impact on plan:** None on correctness or scope — every `must_haves` truth, artifact, and acceptance criterion in the plan is satisfied. The only difference from a literal reading of the plan is which of the two task commits certain source lines landed in.
