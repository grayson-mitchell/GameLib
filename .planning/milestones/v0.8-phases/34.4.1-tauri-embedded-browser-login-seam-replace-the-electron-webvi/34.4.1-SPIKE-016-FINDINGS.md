## A2 — thread identity (research assumption A2)

`thread_name=main`, `mtm_before_with_webview=true`.

The arm already runs on Tauri's main thread, and `objc2_foundation::MainThreadMarker::new()`
returns `Some` **before** any `with_webview()` call is made.

**Conclusion: A2 holds. No `run_on_main_thread` hop is needed anywhere in this arm.**
`wait_for_blocking_operation`'s reliance on the main thread already being current is not a special
case requiring defensive plumbing — it is simply true at this call site.

## Q1 — `with_webview()` closure synchrony (research Open Question 1)

- `closure_ran=true`, `mtm_inside=true` — inside the closure, a `MainThreadMarker` is obtainable.
- `with_webview_ok=true`, `closure_ran_immediately_after_return=true` — the flag set inside the
  closure was already `true` immediately after `with_webview()`'s call returned.

**Conclusion: the closure runs SYNCHRONOUSLY INLINE, not dispatched.** Plan 23's fix can be written
directly inside the `with_webview` closure with no callback, channel, or async restructuring —
`dispatch_rust_channel`'s synchronous `Result<Value, String>` return contract survives unchanged.

## Defect A — both match directions counted on the SAME jar snapshot

```
total            = 33
census_direction (humble_login_cookies' argument order:       cookie_domain_matches(domain, c.domain())) = 29
clear_direction  (humble_login_clear_cookies' argument order: cookie_domain_matches(c.domain(), Some(domain))) = 33
```

**Defect A is PROVEN LIVE, and it is worse than research's original "undercounts" framing.**
`clear_direction` (33) **EQUALS the jar total** (33) — the clear-direction predicate matches
**every single cookie in the jar**, not just Humble's. This is not a mis-scoped filter that happens
to over-match some subdomains; **it does not filter at all.**

**Blocking sequencing note.** The two F-6 defects currently mask each other. Today, the clear arm's
predicate targets all 33 cookies in the jar, but the delete call itself reports success while
deleting nothing (see Retry, below) — so no visible damage occurs. **If plan 23's delete-fix lands
while the clear-direction predicate still matches everything (i.e., before plan 22 fixes Defect A),
a real Humble disconnect will delete EVERY cookie in the shared jar — Epic's, GOG's, everything —
not just Humble's.** The silent no-op becomes cross-store data loss the moment the delete call
starts actually deleting. **Plan 22 (Defect A fix) MUST land before plan 23 (Defect B fix).** This
is a hard ordering requirement, not a style preference: landing plan 23 first, or landing it without
first confirming plan 22 has already shipped, converts a narrow Humble-only bug into blanket
cross-provider data loss across Epic and GOG's cookies in the same jar.

## Record fetch — `WKWebsiteDataStore` reachability

`record_fetch_total=23`, `record_fetch_matching=1`.

From inside the (synchronous) `with_webview` closure, `fetchDataRecordsOfTypes_completionHandler`
against `allWebsiteDataTypes(mtm)` **is reachable** and **does** return a record whose
`displayName()` suffix-matches `humblebundle.com` — count only, no domain string logged.

**Conclusion: the fix path is reachable.** The `WKWebsiteDataStore` record fetch sees the target
domain's record from inside the `with_webview` closure, confirming plan 23's rewrite has a real
record to act on rather than an unreachable API surface.

**Note for plan 23:** a `WKWebsiteDataRecord` is coarse-grained — `removeData(for:)` against the
matched record drops **all** website data for that domain (cookies, localStorage, IndexedDB, caches,
service workers), not cookies alone. Scope the removal to `WKWebsiteDataTypeCookies` specifically
(pass a type set containing only that constant to
`removeData(ofTypes:for:completionHandler:)`) rather than removing the record wholesale, or plan
23's fix will silently widen F-6's clear scope beyond cookies into storage categories plans 15/16
already handle correctly via the separate JS-side storage clear.

## Retry experiment — delete → (wait) → re-read, on the EXISTING wry path

```
attempt=1  surviving=31
attempt=2  surviving=31
attempt=3  surviving=31
```

**Loop shape actually run** (recorded honestly — this is not the four-number shape Task 3's
acceptance criteria anticipated): **delete → [sleep ~500 ms, only when attempt < 3] → re-read**,
repeated three times, emitting one `(attempt, surviving)` pair per iteration. There is no separate
"post-wait" reading distinct from the attempt readings — the wait happens *before* the next
attempt's read, not as its own standalone checkpoint. Do not read a fourth number into this data;
the probe produced three pairs, not four.

**Result is flat: 31, 31, 31.** Three delete attempts, with ~500 ms waits between them, changed the
surviving count by exactly zero. This supports **identity mismatch, NOT a timing/race** — if the
deletes were racing WebKit's asynchronous completion handler, at least one of three attempts with
500 ms waits between them would be expected to show a reduced count. None did.

**Confound to record explicitly, not smoothed over:** the Defect A census (above) measured
`census_direction=29` at probe start, but this retry loop's first read counts `31` survivors. These
two numbers are **not directly comparable** — the probe fires on the FIRST `finished` event, and the
login page was still loading; it set roughly 2 more cookies between the census read and the retry
loop's first read (an artifact of the trigger firing on first-`finished` rather than after the page
had fully settled). The `29 → 31` delta is a page-still-loading artifact of the trigger's timing,
not evidence about anything the retry loop is testing. **It does not change the retry conclusion** —
the flatness *across* the three retry attempts (31/31/31) is what carries the identity-mismatch
conclusion, not the retry loop's starting value relative to the census — but the confound must be
stated plainly rather than left for a reader to assume the 29 and 31 describe the same measurement.

## RECOMMENDATION for plan 23

**Proceed with the `WKWebsiteDataStore` rewrite (`with_webview()` + `objc2-web-kit`), not the retry
pattern.** The flat 31/31/31 result across three delete-and-wait attempts on the existing wry path
rules out a timing/race explanation, so retrying the already-broken `delete_cookie()` call more
times or with longer waits cannot fix Defect B — only replacing the deletion mechanism with the
`WKWebsiteDataStore` API (record fetch proven reachable above, scoped to
`WKWebsiteDataTypeCookies`) can.
