## Summary

**F-6's mechanism is now established, not guessed.** Reading the vendored `wry-0.55.1` and
`tauri-2.11.5` crate sources (already present on disk at
`~/.cargo/registry/src/index.crates.io-*/wry-0.55.1` and `.../tauri-2.11.5` — no network fetch
needed) shows two independent, compounding defects, plus a process-level root cause that explains
why both shipped unverified:

1. **The delete itself is a round-tripped-object match against a live WebKit store, and the round
   trip is not proven faithful.** `src-tauri/src/main.rs`'s `humble_login_clear_cookies` arm calls
   wry's `window.delete_cookie(cookie)` once per matched cookie. On macOS this wraps
   `WKHTTPCookieStore.deleteCookie(_:completionHandler:)`, whose completion handler **fires
   unconditionally** — success means "the operation was processed," not "a cookie was found and
   removed." The cookie object passed in is not the *original* NSHTTPCookie WebKit is holding; it
   is a **freshly reconstructed** one (wry's `cookie_into_wkwebview()`), and WebKit's deletion match
   is an internal identity comparison this reconstruction is not proven to satisfy byte-for-byte.
   This exact bug shape — a Cookie↔NSHTTPCookie round trip losing a property and silently breaking
   `deleteCookie`'s match — is a **historically real, previously-filed WebKit bug**
   ([bugs.webkit.org #184938](https://bugs.webkit.org/show_bug.cgi?id=184938), fixed 2018 for the
   `HTTPOnly`-loss case specifically). Nothing prevents an analogous mismatch existing in this
   *different* round trip at this *different* wry version — and the live numbers are consistent with
   exactly that: 25 delete calls issued, all `Ok`, jar shrank by 1.
2. **A second, independent, source-confirmed bug**: the cookie-census read arm
   (`humble_login_cookies`, used by *both* the login-watch poll and the disconnect census) calls
   `cookie_domain_matches(host, c.domain())` with the arguments in the *opposite* order from the
   clear arm's `cookie_domain_matches(d, Some(domain))`. This is not cosmetic — it changes which
   cookies match. The read arm's direction only matches cookies whose domain attribute is the exact
   bare string `humblebundle.com`; it silently misses leading-dot or subdomain-scoped cookies
   (`.humblebundle.com`, `www.humblebundle.com`, etc). This fully explains the gate's own arithmetic
   (`total=25, matched=23` in the census, `deleted=25` reported by the clear) without requiring the
   delete bug alone to explain every number.
3. **Root cause of both #1 and #2 existing unverified: `delete_cookie()` was never spiked.** The
   phase's own D-11 precondition ("no plan may be written on an unverified API") produced spikes
   013/014a/014b/015, and `34.4.1-RESEARCH.md`/`IPC-PORT-INVENTORY.md` explicitly recorded, in
   writing, at planning time: *"[the spike] surfaced three APIs the spike never tested
   (`eval_with_callback()`, `delete_cookie()`, `on_document_title_changed`)."* The risk was named
   and then shipped anyway without a follow-up spike. F-6 and WR-07 are exactly the two named,
   flagged, unspiked APIs failing live. **This is the single most important framing fact for
   planning this gap cycle**: it is not a new defect class, it is the realization of a risk this
   project already wrote down and did not close.

**Primary recommendation:** Bypass wry's per-cookie round trip entirely. Use Tauri's documented
`WebviewWindow::with_webview()` escape hatch (confirmed present in tauri 2.11.5, confirmed to hand
back a raw `*mut c_void` castable to `objc2_web_kit::WKWebView` on macOS, per Tauri's own doc
example) to reach the webview's **live** `WKWebsiteDataStore` directly, and delete cookies via
`fetchDataRecordsOfTypes_completionHandler` + `removeDataOfTypes_forDataRecords_completionHandler`
(both confirmed present in `objc2-web-kit` 0.3.2, already resolved in `Cargo.lock` transitively — no
new crate needs fetching, only declaring as a direct dependency at the already-resolved version).
This is Apple's own purpose-built, domain-scoped ("by `WKWebsiteDataRecord.displayName`") mechanism
for exactly this operation, and it never reconstructs a cookie object, so the round-trip-identity
bug class cannot recur. It satisfies D-08's non-negotiable "never a blanket wipe" constraint (unlike
wry's only alternative, the all-types `clear_all_browsing_data()`).

## Item 1 (BLOCKING) — F-6: cookie deletion reports success, deletes nothing

### The located mechanism, with file:line

**Read arm (census + login-poll), `src-tauri/src/main.rs:1155-1186`, `"humble_login_cookies"`:**
```rust
let all = window.cookies().map_err(|e| e.to_string())?;
let total = all.len();
let matched: Vec<Value> = all
    .into_iter()
    .filter(|c| cookie_domain_matches(host, c.domain()))   // host = JS-passed target
    .filter(|c| names.is_empty() || names.contains(&c.name()))
    .map(...)
    .collect();
```

**Clear arm, `src-tauri/src/main.rs:1233-1259`, `"humble_login_clear_cookies"`:**
```rust
let matching: Vec<_> = window
    .cookies().map_err(|e| e.to_string())?
    .into_iter()
    .filter(|c| match c.domain() {
        Some(d) => cookie_domain_matches(d, Some(domain)),  // d = cookie's OWN domain (reversed!)
        None => false,
    })
    .collect();
let deleted = matching.len();          // <-- an ATTEMPTED count, computed BEFORE any delete runs
for cookie in matching {
    window.delete_cookie(cookie).map_err(|e| e.to_string())?;   // Ok(()) regardless of match
}
Ok(Value::Number(deleted.into()))
```

**The domain matcher itself, `main.rs:489-494`:**
```rust
fn cookie_domain_matches(host: &str, domain: Option<&str>) -> bool {
    match domain {
        Some(d) => host == d || host.ends_with(&format!(".{d}")),
        None => false,
    }
}
```

### Defect A (source-confirmed): the read arm's argument order is backwards for census use

`cookie_domain_matches` is directional: `host` must be the *narrower* string and `domain` the
*broader* one for the suffix check to ever fire (`host.ends_with(".{d}")`). It is used correctly
in `HumbleUser.watchForLogin()`'s call (`host = 'www.humblebundle.com'`, the page's own host,
`domain = c.domain()`, the cookie's set domain, e.g. the apex `humblebundle.com`) — this is the
*documented, comment-verified* fix for wry's `cookies_for_url()` `==`-only trap (see
`.claude/skills/spike-findings-gamelib/references/tauri-login-webview-cookies.md`).

It is used **backwards** at the disconnect-census call site
(`src/backend/humble/user.ts:984`, `seam.cookies(label, 'humblebundle.com', [])`), where the
fixed apex string is passed as `host` and each cookie's own domain as `domain`. Walking the
function with `host='humblebundle.com'` (fixed) against a cookie whose real domain is
`www.humblebundle.com` or `.humblebundle.com`: `host == d` is false, and `host.ends_with(".{d}")`
can **never** be true because the fixed target string is always shorter than the subdomain-scoped
`d` it would need to end with. **The census read only ever matches cookies whose domain attribute
is the exact bare string `humblebundle.com`** — it silently undercounts every subdomain- or
leading-dot-scoped Humble cookie.

The clear arm's direction is the reverse and is the *correct* one for "does this cookie belong to
domain X and its subdomains": `cookie_domain_matches(d, Some(domain))` where `d` = the cookie's own
domain, `domain` = the fixed target. This is arithmetically consistent with the live numbers:
census found `matched=23` (undercounting — bare-apex cookies only) while the clear arm's own
(correctly-directed) filter matched **all 25** cookies in the jar, meaning the "2 extra" cookies
census scored as `survivingNonHumble` were very likely genuine Humble cookies the census's
backwards filter simply couldn't see, not foreign cookies.

**This is a real, fixable, independent bug** — the read arm needs either (a) a second, purpose-built
Rust arm for "does this cookie's domain fall under target X" (the direction the clear arm already
uses correctly), or (b) the JS call site passing arguments in the direction the existing arm
expects (not viable here — the existing arm's *documented, comment-justified* direction is for the
login-poll's page-host-vs-cookie-domain check, and changing it would break that call site instead).
**Recommendation: give census/disconnect its own arm (or an explicit `mode` argument) with the
correct, clear-arm-matching direction, rather than reusing an arm whose direction was designed for
a different question.**

### Defect B (source-confirmed, primary/blocking): `delete_cookie()` doesn't reliably delete

Regardless of Defect A's counting, the delete loop issued **25** `delete_cookie()` calls (per the
clear arm's own, correctly-directed filter) and the jar shrank by **1**. All 23 (census-visible)
Humble cookies survived. This is the actual live-blocking defect.

**Located mechanism (`wry-0.55.1/src/wkwebview/mod.rs:1248-1267`):**
```rust
pub fn delete_cookie(&self, cookie: &cookie::Cookie<'_>) -> Result<()> {
  let (tx, rx) = std::sync::mpsc::channel();
  unsafe {
    let wkwebview_cookie = Self::cookie_into_wkwebview(cookie);   // <-- RECONSTRUCTED, not the original object
    self.data_store.httpCookieStore().deleteCookie_completionHandler(
      &wkwebview_cookie,
      Some(&block2::RcBlock::new(move || { let _ = tx.send(()); })),  // fires unconditionally
    );
    wait_for_blocking_operation(rx)
  }
}
```

`cookie_into_wkwebview()` (`wkwebview/mod.rs:1106-1175`) rebuilds an `NSHTTPCookie` from scratch via
`NSHTTPCookie.cookieWithProperties(_:)`, setting Name/Value/Path/Domain unconditionally, and
Secure/HttpOnly/SameSite conditionally — **but the Expires/MaxAge/Version block is only populated
`if let Some(max_age) = cookie.max_age()` or `else if let Some(dt) = cookie.expires_datetime()`; for
a pure **session** cookie (no explicit Max-Age/Expires — the common shape for auth session cookies
like `_simpleauth_sess`), `cookie.expires_datetime()` returns `None` and this entire block is
skipped, meaning `NSHTTPCookieVersion` is never set at all on the reconstructed object.**

**Apple's `WKHTTPCookieStore.deleteCookie(_:completionHandler:)` docs do not guarantee the passed
cookie must be object-identical to the stored one — but they also do not document exactly which
properties constitute a match, and the completion handler's contract is "the operation completed,"
not "a cookie was found."** This is corroborated by a real, historical, previously-filed and
previously-fixed WebKit defect of the identical shape:
[bugs.webkit.org #184938 — "`-[WKHTTPCookieStore deleteCookie:completionHandler:]` doesn't delete
cookies"](https://bugs.webkit.org/show_bug.cgi?id=184938) (root cause: the `HTTPOnly` property was
lost during a Cookie→NSHTTPCookie conversion nearly identical in shape to wry's
`cookie_into_wkwebview()`, breaking the store's internal match; fixed April 2018 by widening the
equality check AND adding a fallback "iterate and match manually" loop). **This establishes the bug
CLASS is real and has occurred in this exact API pairing before — it does not by itself prove
today's specific property is Version/Expires; that must be established empirically per the
Validation Architecture section below**, since WebKit's internal matching logic is closed-source
past the public headers.

### The correct fix, verified present and reachable without new package fetches

Tauri 2.11.5 exposes `WebviewWindow::with_webview()`
(`tauri-2.11.5/src/webview/webview_window.rs:2371`), whose doc comment states *"The closure is
executed on the main thread"* and gives an **official, in-source example** for macOS:
```rust
#[cfg(target_os = "macos")]
unsafe {
  let view: &objc2_web_kit::WKWebView = &*webview.inner().cast();
  // ...
}
```
`PlatformWebview::inner()` on macOS (`tauri-2.11.5/src/webview/mod.rs:200`) returns
`*mut std::ffi::c_void` — the raw `WKWebView*`. From there,
`view.configuration().websiteDataStore()` (standard WebKit API, reachable via `objc2-web-kit`)
gives the **live** `WKWebsiteDataStore`, which exposes (confirmed present in
`objc2-web-kit-0.3.2/src/generated/WKWebsiteDataStore.rs`):
```rust
pub unsafe fn fetchDataRecordsOfTypes_completionHandler(...) -> ...;   // line 75
pub unsafe fn removeDataOfTypes_forDataRecords_completionHandler(...) -> ...;  // line 91
```
and `WKWebsiteDataRecord::displayName()` (`objc2-web-kit-0.3.2/src/generated/WKWebsiteDataRecord.rs:103`)
returns the record's domain string (e.g. `"humblebundle.com"`), which can be filtered with the
**same** correctly-directed `cookie_domain_matches`-style suffix check already proven in the clear
arm, before calling `removeData` **only on the matching records**.

**Why this is structurally superior to patching `cookie_into_wkwebview()`:**
- It never reconstructs a cookie object — `fetchDataRecords` returns the *live* records WebKit
  itself is holding, and `removeData` is handed those same objects back, so there is no
  round-trip-identity question to get wrong.
- It matches the WebKit-recommended pattern for exactly this operation (confirmed via
  [the WebKit bug thread](https://bugs.webkit.org/show_bug.cgi?id=184938) and independent developer
  sources: *"If you want to delete all cookies [for a domain], it's easier to do that on the
  `WKWebsiteDataStore`"*).
- It remains domain-scoped (via `displayName` filtering), satisfying D-08's non-negotiable
  never-a-blanket-wipe constraint — unlike wry's only bulk alternative,
  `clear_all_browsing_data()` (`wry-0.55.1/src/lib.rs:2137`, `wkwebview/mod.rs:811`), which clears
  **all** website data types for **all** domains and is explicitly the shortcut this file's own
  comments say "MUST NOT appear anywhere in this file."
- No new crate needs to be fetched from the registry: `objc2` 0.6.4, `objc2-foundation` 0.3.2, and
  `objc2-web-kit` 0.3.2 are **already resolved in `Cargo.lock`** (transitive deps of `wry`), so
  adding them as **direct** dependencies in `src-tauri/Cargo.toml` pinned to those exact versions
  cannot trigger a new resolution or a supply-chain surprise — see Package Legitimacy Audit below.

**Fallback if `with_webview` + raw WebKit calls prove impractical during implementation:** retry
the existing `delete_cookie()` loop with a re-read-and-retry pattern (delete → `cookies()` re-read →
retry survivors up to N times with a short delay), using plan 17's existing census as the
confirmation oracle. This is weaker (does not fix the root cause, and the live evidence — jar
unchanged even in the *AFTER* census read, taken a full round-trip later — argues against this being

### How the fix can be PROVEN

**Plan 17's in-process cookie census (`Humble disconnect: cookie census before(...) after(...)
deleted=... survivingNonHumble=...`) is SUFFICIENT to prove or disprove the delete's real effect —
it already caught this defect on its first live run.** No new observability mechanism is needed;
what is needed is:
1. Fix Defect A first (or in the same plan) so the census's own `matched` count is trustworthy
   (currently undercounts) — otherwise a "PASS" on the census's three equalities could still hide

2. Re-run the existing three-equality check (`matched-after == 0`, `jar shrank by exactly
   matched-before`, `deleted == matched-before`) against the corrected counts.
3. **This can only be proven LIVE.** No automated (non-live) test can cover this — the actual

   discipline failure, it is a structural property of testing platform-native WebKit behavior from

## Item 3 — WR-07: login window title reads "Tauri app"

**Root cause, source-confirmed:** `humble_login_open` (`main.rs:1117-1144`) deliberately omits
`.title()` on `WebviewWindowBuilder`, on the (unverified, unspiked, now-falsified-by-the-live-gate)
assumption that omitting it causes the OS window title to track the loaded page's own
`document.title`. It does not. Tauri's default title (visible when no explicit `.title()` call and
no title-tracking hook is wired) is the crate/app-level default — observed live as literally
`"Tauri app"`.

**The correct fix, confirmed via Tauri's own documented API and in-source example**
(`tauri-2.11.5/src/webview/mod.rs:564-567,594-600`):
```rust
.on_document_title_changed(|window, title| {
    window.set_title(&title).unwrap();
})
```
`WebviewBuilder::on_document_title_changed` fires whenever the loaded page's `document.title`
changes, handing back a `Webview<R>` and the new title string; calling `.set_title()` on the
parent window propagates it to the OS title bar. This requires **no new dependency** (it is core
`tauri` API, already in use elsewhere in this file's builder chain) and needs only be added to the
`humble_login_open` arm's `WebviewWindowBuilder` chain, gated the same way `.inner_size()`/`.center()`/
`.focused(true)` already are (only for `visible` windows — a hidden reveal/clear window has no
title bar to matter).

**What already-present code has never been verified, per this phase's own process lesson:** the
comment at `main.rs:1114-1116` explicitly (and, per the live gate, incorrectly) asserts "WR-07
stays intact, enforced by the grep gate in this plan's own acceptance criteria, not by intent
alone" — i.e. a *static* grep-based gate (checking that `.title()` is never hard-coded) was treated
as sufficient proof of WR-07's *positive* requirement (the title shows Humble's real page title).
**A grep gate can only prove the absence of a hard-coded bad value; it cannot prove the presence of
the correct dynamic one.** This is the same "enumerates what is missing, not what is present"
failure shape the gate verdict named for F-6, applied to a static-analysis gate instead of a wipe
step. The fix must add a **live-observable** check (the title bar's actual text, read via
`window.title()` — a getter that DOES exist and return the live OS-level title, unlike the
`WebviewWindow::title()` JS-side confusion the spike's reference file warned about) rather than
relying on the grep gate alone.

## Item 5 — F-9: intermittent 60s `keyring_get` timeout, hits `humble-csrf`

**Located mechanism:** `main.rs:755-773`, the `"keyring_get"` arm, calls
`Entry::new(KEYRING_SERVICE, account).get_password()` (the `keyring` crate's synchronous macOS
Keychain call) directly, inline, in `dispatch_rust_channel` — the same function that, per Item 1's
`wait_for_blocking_operation`, may already be pumping/blocking a run loop for cookie operations.
**No explicit timeout wraps this call in `main.rs` itself** — the "60000ms" in the observed error
(`rustInvoke timed out after 60000ms: keyring_get`) is the **sidecar's own RPC round-trip timeout**
(`requestRustInvoke()` in `src/backend/sidecar/sidecarRpc.ts`), not a Rust-side timeout — meaning
the Rust call itself was still blocked/pending when the JS side gave up waiting, not that Rust
returned an error after 60s.

**Hypothesis (untested, correctly flagged as such in the gate record): a lookup for a MISSING
Keychain entry may block far longer than a lookup for a present one.** The gate's own sweep found
`steam-refresh-token` absent from the Keychain (`security find-generic-password` listed only
`steam-refresh-token-selfcheck`) at the moment the Steam-slot timeout hit. **This research adds one
mechanistic candidate not previously named**: macOS's `SecItemCopyMatching` (which the `keyring`
crate wraps) can legitimately block on a **Keychain unlock prompt or an ACL/trust decision** for
certain access-control configurations, and — separately — a background `security` daemon
(`securityd`/`SecurityAgent`) hiccup or first-access-after-boot ACL re-evaluation is a known, if
rare, source of multi-second-to-tens-of-seconds Keychain latency on macOS, independent of whether
the entry exists. **This is architecturally distinct from the WKWebView round-trip-identity bug
class (Item 1/2) — it is a synchronous OS Security-framework call blocking the Tauri command
dispatch thread**, and if `dispatch_rust_channel` runs on the **same** thread that pumps the main
run loop for `delete_cookie()`/`cookies()` (Item 1's `wait_for_blocking_operation` mechanism), a
long-blocking `keyring_get` call would ALSO stall any concurrent cookie operation queued behind it
— worth checking whether F-9 and F-6 ever co-occurred in the same session (the gate record does not
show them overlapping, but the next gate should watch for it).

**What would make this deterministic enough to fix and prove:** (1) reproduce with a **guaranteed-
missing** Keychain entry (delete a slot, then call `keyring_get` against it, timed, in isolation,
outside the full app) to test the "missing entry blocks" hypothesis directly, with a stopwatch, not
inferred from a busy live session; (2) if reproduced, wrap the Rust-side `Entry::new(...).get_password()`
call in an explicit, short (e.g. 5s) timeout using `std::thread` + a channel (the same pattern
`wait_for_blocking_operation` already uses for cookie ops), converting a silent 60s RPC-timeout into
a fast, classified `keyring:timeout` error the sidecar can log distinctly rather than let the
generic RPC-timeout message obscure it. This is a real code change candidate, not just an
observation task, but it is **not this cycle's blocking work** (F-9 is explicitly unassigned/open,
did not recur on the second boot, and did not cause F-10 — confirmed refuted by the gate's own
controlled experiment). Recommend: reproduce and fix IF cheap during this cycle (it shares the
"never verified" theme this cycle is already auditing), but do not let it block the F-6 fix.

## Common Pitfalls

### Pitfall 1: Trusting a wry/WKWebView API's `Ok(())` return as proof of effect
**What goes wrong:** `delete_cookie()`, and potentially other wry mutation APIs, return `Ok(())`
whenever the underlying WebKit completion handler fires — which happens **unconditionally**,
independent of whether the requested mutation actually matched anything.
**Why it happens:** WebKit's async completion-handler contract documents "the operation was
processed," not "a match was found." Rust's `Result<(), Error>` mapping conflates the two.
**How to avoid:** Any wry mutation call in this codebase that has an observable, re-readable side
effect (cookies, storage) must be followed by a **re-read** to confirm the mutation, exactly as
plan 17's census already does for cookies — this pattern should be the default, not a one-off.
**Warning signs:** A wry call returns `Ok` but a subsequent, independent read shows the state
unchanged.

### Pitfall 2: Treating "the spike never tested this API" as low-risk because it "looks similar" to a tested one
**What goes wrong:** `delete_cookie()` was shipped without a follow-up spike because it "looks like"
the sibling, well-tested `cookies()` API (same struct, same module, same general shape) — but read
vs. write/delete operations against WebKit's cookie store have entirely different failure surfaces
(a read either returns data or doesn't; a delete can silently no-op while still reporting success).
**Why it happens:** Convenience — spiking every individual API in a family feels redundant when one
sibling is proven.
**How to avoid:** D-11's own rule ("no plan may be written on an unverified API") should be read as
**per-API**, not per-module or per-crate-surface. `IPC-PORT-INVENTORY.md` already had the discipline
to name `delete_cookie()`/`on_document_title_changed`/`eval_with_callback()` explicitly as untested
— the miss was not naming them, it was not gating on that naming.
**Warning signs:** A code comment citing "the spike proved X" where X is a sibling API, not the
exact one being called.

### Pitfall 3: A static/grep-based acceptance gate proving a positive requirement
**What goes wrong:** WR-07's original acceptance criteria was a grep gate checking `.title()` is
never hard-coded to `"GameLib"` — this proves the *absence* of the prohibited value, not the
*presence* of the required one (Humble's real page title).
**Why it happens:** Grep gates are cheap and mechanical; verifying dynamic runtime behavior is not.
**How to avoid:** Pair every "must never show X" static gate with a "must actually show Y" live
observation in the gate document, and do not let the static gate's green result be read as closing
the live half.
**Warning signs:** An acceptance criterion phrased entirely as a negative ("never hard-coded X")
with no corresponding positive, live-observed claim.

### Pitfall 4: Assuming a shared Rust arm's bug is isolated to its first caller
**What goes wrong:** F-6 was diagnosed and reported purely in terms of Humble's disconnect; the
identical, shared `humble_login_clear_cookies` arm is also called by
`storeManagers/legendary/user.ts`'s Epic logout, carrying the exact same defect, unflagged until
this research.
**Why it happens:** Bug reports naturally center on the surface where they were observed.
**How to avoid:** When a shared Rust/backend primitive is found broken, grep for every other call
site of that exact primitive (not just "similar-shaped" code) before scoping the fix.
**Warning signs:** A `wipeSteps`/cookie-clear/storage-clear shape that appears more than once across
`storeManagers/*` or `humble/*` — this project already has this pattern in at least two places
(Humble, Legendary), and GOG/Amazon will inherit it in Phase 34.5.

## Open Questions

1. **Does `objc2`/`objc2-web-kit`'s `MainThreadMarker` requirement conflict with how
   `dispatch_rust_channel` is currently invoked?**
   - What we know: `with_webview()`'s closure "is executed on the main thread" per Tauri's own doc;
     `WKWebsiteDataStore::allWebsiteDataTypes(mtm)` and similar objc2-web-kit calls require a
     `MainThreadMarker` (confirmed present in the generated bindings signature at
     `WKWebsiteDataStore.rs:65`).
   - What's unclear: whether `with_webview()`'s callback is invoked *synchronously inline* (if
     already on main) or *dispatched* (if called from elsewhere) — this affects whether
     `dispatch_rust_channel`'s existing synchronous `Result<Value, String>` return contract can be
     preserved without restructuring the arm into an async/callback shape.
   - Recommendation: spike this specific question first (a minimal `with_webview` call from inside
     a new dispatch arm, confirming it returns synchronously and a `MainThreadMarker` can be
     obtained) before writing the full removeData implementation — this is the D-11 discipline this
     cycle is explicitly trying to restore, applied to the fix itself, not just the diagnosis.

2. **Are the "two extra" cookies in the census's `total - matched` gap (Defect A) genuinely
   subdomain/leading-dot Humble cookies, or could one be a real third-party cookie?**
   - What we know: the arithmetic is consistent with both being Humble-domain cookies the census's
     backwards filter missed (explaining why the clear arm's differently-directed filter matched all
     25).
   - What's unclear: this was reasoned from the numbers alone, not independently confirmed by
     reading the actual cookie domain strings (which the code deliberately never logs, per
     T-34.4.1-39/T-34.4.1-75 — a correct privacy discipline that also makes this specific ambiguity
     hard to resolve without a special-cased, explicitly-scoped debug capture).
   - Recommendation: once Defect A is fixed, the corrected census's `survivingNonHumble` count on a
     real gate run will settle this empirically (if it drops from 1 towards 0 with the same jar
     contents, the "extra" cookies were Humble's).
