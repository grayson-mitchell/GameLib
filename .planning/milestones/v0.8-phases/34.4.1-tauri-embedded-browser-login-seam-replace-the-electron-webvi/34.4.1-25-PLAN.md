<objective>
Establish, then close, **F-10**: Manage Accounts renders **blank** on the FIRST navigation to
`/login`, and renders correctly on a retry.

Purpose: this is not cosmetic. F-10 **already blocked a gate item once**, which makes it
gate-path-critical for plan 29 — a third gate run that stalls on a blank screen burns a live run
that requires the developer, real Humble credentials and a 2FA step. It is also the only finding in
this cycle whose cause is genuinely unknown.

**This plan diagnoses before it fixes, and says so in its own text (binding constraint 6).** Research
rates F-10 LOW-MEDIUM confidence: the gate's own controlled experiment established only what it is
NOT (zero new backend log lines over 90+ seconds of blank screen — no IPC call is even made, and the
F-9 keyring-stall hypothesis was explicitly tested and refuted). Task 1 instruments, Task 2 observes
live, Task 3 fixes what was observed. Task 3 deliberately does not prescribe a fix, because
prescribing one now would be exactly the "upgrade proof beyond evidence" this cycle exists to stop.

**A correction to the research this plan must carry forward.** Research assumption **A3 is wrong**,
and the correction changes the initial hypothesis materially. A3 states no per-route `lazy()`
boundary exists for Login and that the framing must therefore mean the single top-level `App`
`React.lazy()` boundary. In fact `src/frontend/App.tsx:147-150` registers
`{ path: 'login', lazy: makeLazyFunc(import('./screens/Login')) }` — a **react-router route-level
`lazy`**, not `React.lazy`, whose `import()` promise is created **eagerly at App module evaluation**
(`makeLazyFunc` at `App.tsx:129-136` receives an already-started `Promise`, not a thunk). So there
IS a per-route boundary, it resolves a promise started long before the navigation, and react-router
route-level `lazy` does not participate in the top-level `<Suspense fallback={<Loading />}>` at
`index.tsx:210-212`. That is a substantially better first hypothesis than A3's.

A second observation narrows it further: if the Login component mounted and simply had not finished
its own loading, it would render `<UpdateComponent />` (`Login/index.tsx:118-120`, a spinner) — not
nothing. **A truly blank window therefore points upstream of the component's own render**, at the
route resolution or at a boundary that renders nothing while pending.

**Adjacent already-present code this plan verifies (binding constraint 1).** Three boundaries on
this path are present and have never been questioned: (a) the top-level `<Suspense
fallback={<Loading />}>` at `index.tsx:210-212` — does `Loading` actually render visible content, or
is the "blank screen" simply an invisible fallback? (b) the route-level `lazy` at `App.tsx:147-150`,
which has **no `errorElement` anywhere in the router** — a rejected chunk import would surface as
what, exactly? (c) `Login/index.tsx:91-93`'s `useEffect(() => setLoading(false), [epic, gog])`,
whose dependencies are context OBJECTS, so its firing depends on referential stability nobody has
asserted. All three are checked here, not assumed.

Output: a recorded diagnosis, a fix or an evidenced declaration, and a standing guarantee that no
pending state on the `/login` path can present as a blank window.
</objective>

<interfaces>
**The route registration (`src/frontend/App.tsx:129-150`):**
```
function makeLazyFunc(importedFile: Promise<Record<'default', React.ComponentType>>) {
  return async () => { const component = await importedFile; return { Component: component.default } }
}
const router = createHashRouter([{ path: '/', element: <Root />, children: [
  { index: true, lazy: makeLazyFunc(import('./screens/Library')) },
  { path: 'login', lazy: makeLazyFunc(import('./screens/Login')) },
  …
```
Note: the `import()` runs when `App.tsx` evaluates, so every route chunk begins loading at app boot;
`lazy` merely awaits an already-started promise. A promise that REJECTED at boot will reject
identically on every retry — which is inconsistent with "renders on retry" and is itself a useful
discriminator.

**The Login screen's own loading gate (`src/frontend/screens/Login/index.tsx:48, 91-93, 118-120`):**
```
const [loading, setLoading] = useState(true)
useEffect(() => { setLoading(false) }, [epic, gog])
if (loading) { return <UpdateComponent /> }
```
`UpdateComponent` is visible. So `loading === true` produces a spinner, not a blank window.

**The only Suspense boundary in the tree (`src/frontend/index.tsx:204, 210-212`):**
```
const App = lazy(async () => import('./App'))
<Suspense fallback={<Loading />}> <App /> </Suspense>
```
`Loading` is `src/frontend/screens/Loading`. Whether it renders visible content is an open question
this plan answers.

**No `errorElement` or `HydrateFallback` exists anywhere in the router** — confirmed by grep across
`App.tsx` and `index.tsx`. What a rejected route `lazy` promise renders under this configuration is
an open question this plan answers.

**What the gate already established, and must not be re-derived:** zero new backend log lines across
90+ seconds of blank screen. No IPC call occurs. This is entirely a client-tier defect. The F-9
keyring hypothesis was tested and REFUTED by the gate's own controlled experiment.

**Diagnostic discipline.** Breadcrumbs log fixed text and booleans only — no usernames, no account
identifiers, no session state. Every breadcrumb added in Task 1 is removed in Task 3; a permanent
diagnostic is a different decision and is not this plan's.
