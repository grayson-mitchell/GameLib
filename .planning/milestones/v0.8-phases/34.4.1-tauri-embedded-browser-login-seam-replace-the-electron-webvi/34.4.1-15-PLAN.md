<objective>
Build the storage-clearing capability the Tauri seam has never had. This is **new capability, not
a patch** — `src-tauri/src/main.rs:1067-1092` (`humble_login_clear_cookies`) only enumerates
`window.cookies()`, filters by `cookie_domain_matches`, and `delete_cookie`s each match. It
contains no storage-clearing capability at all.

Purpose: **F-6 (BLOCKING).** Electron's disconnect runs 5 wipe steps
(`clearStorageData`, `clearCache`, `clearAuthCache`, `clearHostResolverCache`, `clearData`);
Tauri's runs 1 (cookies). So `localStorage`, `sessionStorage`, IndexedDB, service workers and
HTTP caches all survive a disconnect, Humble's web app restores a session from what remains, and
the operator was signed straight back in — 3 seconds from `cleared 27 humblebundle.com cookie(s)`
to a persisted valid session, with zero `session_expired` poll lines where a genuine from-scratch
login produced 36 across 2.5 minutes.

Output: a `humble_login_clear_storage` Rust arm and a `clearStorage()` seam method. Plan 16 wires
them into `disconnect()` and `logout()`.

**The constraint that makes this design work, and the reason it is not a compromise:** the clear
runs as JavaScript inside the target page's own origin context. Same-origin policy means that
script structurally *cannot* reach another origin's `localStorage`/IndexedDB/caches — so the
clear is domain-scoped **by construction**, exactly as `cookie_domain_matches` is for cookies. It
satisfies item 3's over-broad constraint (D-08/Pitfall 3: never a blanket wipe that signs the user
out of Epic/GOG/Amazon, whose cookies share this jar) and the under-broad constraint F-6 found, at
the same time. `clear_all_browsing_data()` remains banned and must not appear in this file.
</objective>

**The template to copy is `humble_reveal_post` (`src-tauri/src/main.rs:1107-1160`), not
`humble_login_clear_cookies`.** It already solves every hard part of running code inside a remote
page and getting a result back:
```
1111  WebviewWindowBuilder::new(app, &label, WebviewUrl::External(parsed.origin_url))
1116    .user_agent(&parsed.user_agent)
1117    .visible(false)                       // D-08: hidden, on-demand
1118    .on_navigation(move |url| {           // exfil intercept
1119       if url.host_str() == Some(REVEAL_EXFIL_HOST) { ...tx.send(payload)...; return false }
1127       true })
1144  window.eval(&script)                   // fire-and-forget; eval_with_callback does NOT await a Promise
1150  let outcome = rx.recv_timeout(REVEAL_POST_TIMEOUT);
1151  let _ = window.close();                // covers success, parse-failure AND timeout
```
And `reveal_post_script` (`main.rs:576-604`) is the script-builder template. Read its docstring in
full — three constraints are stated there and all three apply here verbatim:
  1. Every interpolated value goes through `serde_json::to_string`, producing a properly escaped
     JS literal. **NEVER `format!("'{}'", value)`** — that is the injection this guards against.
  2. `eval_with_callback`'s callback reports the script's IMMEDIATE completion value and a
     returned Promise is NOT auto-awaited. Results must come back via the navigation-intercept
     exfil, not a callback.
  3. The JS template is built via `concat!` of single-line pieces, each opening and closing its
     own `"` on the SAME source line, with single-quoted JS strings inside — because
     `longRunningChannels.test.ts`'s WR-08 stripper-integrity guard asserts every
     comment-stripped code line in `main.rs` carries an EVEN `"` count.

The seam interface to extend (`src/backend/humble/loginWindowSeam.ts:76-103`) — note
`clearCookies` is already there and this sits beside it:
```
open(url, { visible, userAgent }): Promise<string>
cookies(label, host, names): Promise<LoginWindowCookieRead>
takeEvents(label): Promise<LoginWindowNavEvent[]>
close(label): Promise<boolean>
clearCookies(label, domain): Promise<number>
revealPost(input): Promise<LoginWindowRevealPostResult>
```

Existing transport constants (`src/common/types/sidecarTransport.ts` L246-282, allowlist at
L323-327). A new channel must be added to BOTH the constant list and the allowlist array, or it
is rejected at dispatch.

**Origin vs domain — the honest limitation this plan must confront, not paper over.** Cookies
clear by DOMAIN suffix, so `humblebundle.com` covers the apex and `www.`. Web storage is scoped
per ORIGIN (scheme + host + port), so a script running on `https://www.humblebundle.com` does NOT
clear `https://humblebundle.com`'s `localStorage`. `HUMBLE_BASE_URL` is the www origin. Whatever
this plan does about that must be recorded as a decision, not left implicit — an incomplete clear
that looks complete is how F-6 happened the first time.
