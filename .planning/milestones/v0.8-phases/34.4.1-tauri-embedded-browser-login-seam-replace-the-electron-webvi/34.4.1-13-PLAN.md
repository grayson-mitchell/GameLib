<objective>
Close **F-1 (BLOCKING)**: stop the Humble session cookie being persisted in plaintext under Tauri.

Purpose: gate item 1 recorded the mechanism working and the session landing on disk as
`encryptionDegraded: true`, `sessionCookie` len 208 — plaintext, twice-logged as
`safeStorage unavailable — storing Humble session in plaintext (degraded encryption)`. The
Electron build encrypted this cookie; the Tauri build does not. Phase 34.5-15 is held partly on
this: its gate items mint real OAuth credentials over this same seam, and every credential this
seam persists currently lands in plaintext.

Output: the sidecar installs a keyring-backed implementation of plan 12's seam over the
`humble-session` / `humble-csrf` slots plan 11 allowlisted, migrates any existing plaintext
credential into it, and clears both slots on disconnect.

**Migration is in scope, not a follow-up (D-GAP-01).** Existing users hold a plaintext Humble
cookie written by the current build. The fix must read it, move it into the keyring, clear
`encryptionDegraded`, and remove the plaintext remnant — without stranding a user whose keyring
is genuinely unavailable. Phase 28's `PlatformFailure(-128)` / Keychain-Deny shape is a real,
documented case, not a hypothetical.
</objective>

<interfaces>
From plan 11 — the slot-parameterized keyring store in `src/backend/sidecar/keyringTokenStore.ts`,
with exported slot-name constants. Wire shapes:
```
keyring_available [slot]            -> boolean
keyring_get       [slot]            -> string | null      (null == no entry, healthy first run)
keyring_set       [secret, slot]    -> true
keyring_delete    [slot]            -> true               (already-absent is success)
```
An unrecognised slot returns the flat error string `keyring:unknown-slot`.

From plan 12 — the seam this implements (`src/backend/humble/secretStore.ts`):
```
isAvailable(): Promise<boolean>
getSecret(key: 'sessionCookie' | 'csrfToken'): Promise<string>
setSecret(key, value): Promise<void>
clearSecrets(): Promise<void>
```

The `configStore` keys holding the plaintext remnant today (`humble/electronStores.ts`), observed
live in the gate at `~/Library/Application Support/GameLib/humble_store/config.json`:
```
encryptionDegraded  boolean
sessionCookie       string   (len 208 plaintext under Tauri; len 314 prefixed ciphertext under Electron)
csrfToken           string   (len 29 plaintext under Tauri; len 58 under Electron)
isLoggedIn          boolean
expired             boolean
```
Only `sessionCookie` and `csrfToken` move. `isLoggedIn`/`expired`/`userData` stay in
`configStore` on both builds — they are not secrets and the UI reads them.

The install precedent to follow — `src/backend/sidecar/bootstrap.ts` already calls
`setTokenStore()` with `SidecarKeyringTokenStore` for Steam. `setHumbleSecretStore()` goes in the
same place, for the same reason, with the same no-env-var rule (Phase 28 REQ-28-07/D-08).

A discipline this project already learned the hard way — `tests-clobbering-real-steam-store`:
jest suites that `requireActual` electron-store reach the REAL
`~/Library/Application Support/GameLib`, and `afterAll` restore is NOT a safety net under worker
force-exit. Any test in this plan that touches a store must mock it, never `requireActual`.

  <behavior>
    - Given a plaintext `sessionCookie` in `configStore` and a working keyring, migration writes it
      to the keyring, reads it back, confirms the readback equals the original, THEN deletes the
      `configStore` key and sets `encryptionDegraded` to `false`.
    - If the keyring write rejects, the `configStore` plaintext is LEFT IN PLACE, the user stays
      signed in, `encryptionDegraded` stays/becomes `true`, and exactly one warning is logged.
    - If the readback does not equal the value written, the plaintext is LEFT IN PLACE and the
      migration is treated as failed — a mismatched readback must never be rounded up to success.
    - Migration runs at most once per successful move: with the `configStore` key already absent,
      it performs no keyring write.
    - A `csrfToken` present alongside is migrated by the same rules, independently — a failed
      `csrfToken` migration does not roll back a successful `sessionCookie` migration.
    - After a successful migration, `getCredentials()` resolves the same cookie value it resolved
      before, proving the move was lossless.
    - `disconnect()` clears the keyring slots in addition to its existing `configStore.clear()`.
    - A failing slot clear does not abort disconnect and does not throw — the stored-credential
      delete remains the security boundary and must still complete.
    - Electron is unaffected: with the Electron default store installed, no migration runs and no
      keyring call is made.

    installed. Order of operations is the whole design and must not be reordered:
    read the `configStore` plaintext -> write it to the keyring -> read it back -> compare ->
    only on an exact match, delete the `configStore` key and set `encryptionDegraded` false.

    **Never delete the plaintext before the readback confirms it.** A keyring that accepted a
    write and returns something else on read is exactly the
    `navigator-clipboard-noops-under-tauri` failure shape this project has already been bitten by
