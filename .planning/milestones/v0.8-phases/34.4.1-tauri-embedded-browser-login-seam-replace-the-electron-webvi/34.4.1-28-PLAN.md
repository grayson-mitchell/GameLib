<objective>
Build the **mechanical detector** the gate verdict asked for, and close the sweep staleness that has
now been re-forwarded **twice** with no plan owning it.

Purpose (the sweep, scope item 2): the gate verdict's own words — *"the same
resolves-without-doing-the-work shape as `navigator.clipboard` under WKWebView — the third instance
in this phase — which argues for a targeted sweep of that class rather than another point fix."*
Three confirmed instances exist (`navigator.clipboard.writeText` resolves without writing;
`queryLocalFonts` throws; `delete_cookie()` resolves without deleting), plus a fourth
process-level instance in the same shape (the login window title: an assumption about default Tauri
behaviour, never spiked, shipped as fact). This project already has two working sweep scripts in
this very directory (`seam-parity-sweep.py`, `ported-channels-gate.py`), so the tooling pattern is
established and proven — a third sibling is cheap.

**The sweep is deliberately BOUNDED, and the bound is the important part.** Research Item 2 is
explicit: static enumeration is mechanical and cheap, but **whether a flagged API degrades silently
versus throws versus works cannot be determined statically** — WebKit's behaviour is closed-source,
and reading wry's source only tells you what Rust asked WebKit to do, not whether WebKit did it.
So the sweep's output is a **worklist for future targeted spikes, filed as a backlog** — not a
verdict, and not something to resolve inline. Resolving every flagged item live in this cycle would
reopen exactly the scope creep D-04/D-05 exist to prevent. Any hit without a paired live
observation already recorded in a `34.4.1-LIVE-GATE*.md` or a project-skill spike file is marked
`UNVERIFIED-LIVE` and left there.

Purpose (item 7, the staleness): `seam-parity-sweep.py`'s regenerated output still reports S-07/S-10
as `SILENTLY-DROPPED` for `storage`/`cache` even though **plan 16 closed both**, and S-11 as
`SILENTLY-DROPPED` for `secretStore.ts` even though **plan 13 closed F-1**. Plan 18 found it and
routed it to plan 19; plan 19 declined because the file was not in its `files_modified`; plan 20's
scope did not include it either. It has been logged and re-forwarded twice for the same reason both
times — nobody put the file in scope. **This plan puts `seam-parity-sweep.py` and
`34.4.1-SEAM-PARITY-SWEEP.md` in `files_modified` explicitly**, which is the whole fix for the
process failure as well as the content one.

**Why this plan runs LAST among the code-touching plans, deviating from research Item 7's stated
ordering.** Research recommends fixing the script *before* this cycle's F-6 fix is regenerated into
it. But plan 18's SUMMARY records that getting the regeneration to complete at all required
refreshing line hints for six sites shifted by intervening plans. Plans 22-27 move code in
`main.rs`, `humble/user.ts`, `legendary/user.ts` and three frontend files. Regenerating before them
would guarantee a second refresh; regenerating after them costs one. The research's underlying
concern — that F-6's fix must not be recorded into a document already known-stale for unrelated
reasons — is satisfied either way, because both fixes land in the same regeneration.

**Adjacent already-present code this plan verifies (binding constraint 1).** Two things:
(a) `seam-parity-sweep.py`'s own **anti-vacuity self-tests** are present and are the only thing
stopping a mapping change from silently weakening the script — this plan proves the new mapping
entries are load-bearing by removing them and watching the self-test fail; (b)
`ported-channels-gate.py`, the sibling script, has not been run against this cycle's new Rust
channel (`humble_login_cookies_for_domain`) or its new seam method, and is re-run here with its
`--self-test`.

Output: a new sweep script with a filed backlog, a corrected and regenerated seam-parity sweep, and
a `deferred-items.md` entry that closes the twice-forwarded one instead of forwarding it a third
time.
