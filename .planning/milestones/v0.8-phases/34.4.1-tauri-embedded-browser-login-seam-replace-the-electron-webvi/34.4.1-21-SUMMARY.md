## Decisions Made

- **Plan 22 must land before plan 23** — the sequencing hazard found in Defect A (clear-direction
  predicate matches 100% of the jar) combined with Defect B (delete currently no-ops) means fixing
  delete before fixing the predicate would delete every cookie in the shared jar, including Epic's
  and GOG's, the first time a real disconnect runs after the fix.
- **Proceed with the `WKWebsiteDataStore` rewrite, not a retry pattern**, grounded in the flat
  31/31/31 retry result — a measured answer per research Item 1's "cheap experiment first"
  instruction, not an assumption.
- **Scope plan 23's `removeData` call to `WKWebsiteDataTypeCookies`**, not the whole
  `WKWebsiteDataRecord` — recorded as a note in the findings file so plan 23 doesn't silently widen
  F-6's clear scope into storage categories (localStorage/IndexedDB/caches) that plans 15/16 already
  handle correctly via the separate JS-side storage clear.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 - Blocking] Env-gated trigger added so the throwaway probe could actually be invoked**
- **Found during:** Task 3 (live checkpoint) — the orchestrator, resuming after the checkpoint returned
- **Issue:** Task 2 shipped `spike016_cookie_probe` as a `dispatch_rust_channel` arm with no way to
  invoke it: zero TS/JS callers, `dispatch_rust_channel` is reachable only from sidecar-initiated
  `rustInvoke` frames with no frontend passthrough by design (T-28-03), and the arm's window-label
  parameter is generated inside `humble_login_open` and never derived from the URL or handed back to
  any caller that could supply one. Task 3 could not be driven at all as shipped.
- **Fix:** Added an `eprintln!`-only, env-gated trigger (`GAMELIB_SPIKE016`) inside
  `humble_login_open`'s page-load closure, where the window label is already in scope, latched to
  the FIRST `finished` event only — the probe's retry experiment deletes cookies, so a per-navigation
  firing would destroy the jar mid-measurement.
- **Files modified:** `src-tauri/src/main.rs` (kept entirely inside this file, which plan 21 already
  declares in `files_modified`, rather than the more natural sidecar-side trigger in
  `humbleLoginFlowRegistration.ts`, which plan 21 does not declare — avoiding an undeclared-file
  edit for a throwaway trigger plan 22 Task 1 removes anyway).
- **Verification:** `cargo check` clean, `cargo test` 60/60, `tauriShellSource.test.ts` 29/29; probe
  ran live and produced the verbatim output recorded in the findings file.
- **Committed in:** `57905a58f`

**2. [Rule 2 - Missing Critical] F-9 Keychain-prompt-storm root-cause investigation logged during the live session**
- **Found during:** Task 3 — operator hit 20+ Keychain prompts on a single boot while preparing to
  drive the probe, an observation adjacent to but not part of spike 016's own scope.
- **Issue:** Not spike 016's answer, but a live signal too load-bearing to discard mid-session:
  source-verified that the keyring read path has no caching or in-flight dedupe, so every
  `getCredentials()`/`getCsrfToken()`/`isAvailable()` call is a fresh `keyring::Entry::get_password()`
  blocking on a modal prompt; queued behind ~20 prompts it exceeds the 60 s `RUST_INVOKE_TIMEOUT_MS`
  and rejects — matching F-9's recorded signature. Root mechanism further narrowed to an ad-hoc
  code signature (no `TeamIdentifier`) degrading the Keychain ACL's designated requirement to a bare
  cdhash match, which does not durably persist across `tauri:dev` recompiles.
- **Fix:** Not fixed here — this is out of plan 21's declared scope (F-9 belongs to plan 26).
  Recorded as three dated entries in `deferred-items.md` and explicitly forwarded to plan 26 as a
  scope note: caching alone cannot close F-9 because the first read still blocks on a dialog, so the
  60 s timeout path needs handling too.
