# Phase 34.4.1 Plan 15: Origin-scoped Storage-clear Capability Summary

**New `humble_login_clear_storage` Rust arm + `LoginWindowSeam.clearStorage()` give the Tauri seam a capability it never had — clearing `localStorage`/`sessionStorage`/IndexedDB/Cache Storage/service workers for one origin, scoped by same-origin-policy construction rather than a filter, with honest per-category `count | 'unsupported'` reporting. F-6 is NOT closed by this plan — nothing calls this capability yet.**

## Accomplishments

- Added `humble_login_clear_storage` to `dispatch_rust_channel`, mirroring `humble_reveal_post`'s hidden-window + navigation-intercept-exfil template (D-07/D-08) rather than `humble_login_clear_cookies`'s domain-filter shape — the clear runs as JS *inside* the target origin's own execution context, so same-origin policy makes any other origin structurally unreachable (T-34.4.1-66), satisfying both D-08/Pitfall 3's over-broad constraint and F-6's under-broad one at once.
- The injected script clears five categories (`localStorage`, `sessionStorage`, every IndexedDB database, every Cache Storage entry, every service-worker registration), each wrapped in its own `try`/`catch` so one missing/failing category never aborts the rest, and each reporting either a numeric count or the literal string `'unsupported'` — never a coerced `0` (T-34.4.1-67). All async categories (`indexedDB.databases()`, `indexedDB.deleteDatabase()`, `caches.keys()`/`caches.delete()`, `navigator.serviceWorker.getRegistrations()`/`.unregister()`) are `await`ed before the single `exfil()` call, proven by a test asserting `exfil(report)` runs after every `await` in the built script text.
- 10 new `#[cfg(test)]` cases (60/60 `cargo test` total) prove arg validation (missing args, non-https origin, non-string args all collapse to `humble_login_clear_storage:bad-args`) and the script builder: an escaping round-trip over a value containing a double quote, single quote, backslash and `</script>` sequence; presence of all five categories' clear calls and `'unsupported'` fallbacks; and the await-before-exfil ordering.
- `LoginWindowSeam.clearStorage(originUrl, userAgent)` added to the interface with `StorageClearCategoryResult`/`LoginWindowStorageClearResult` types shared by both builds; `createRustLoginWindowSeam()`'s implementation coerces each category to a finite number or `'unsupported'` (never silently to `0`) and, unlike every other method on this seam, **propagates rejection rather than swallowing it** — plan 16's guarded `wipeSteps` entry is meant to own that swallow.
- Followed TDD for Task 2: RED commit (`491bb7e79`) added 4 failing `humbleLoginFlows.test.ts` cases against an interface with no implementation (`seam.clearStorage is not a function`); GREEN commit (`0e07bf59d`) implemented `clearStorage()` and fixed 3 pre-existing `fakeSeam` fixtures (`adapter.test.ts`, `user.test.ts`, `oauthLoginCapture.test.ts`) plus `tauriShellSource.test.ts`'s `REQ-34.1-07` pre-existing-arms ledger, all of which the widened interface/new arm broke.

## The Per-category Result Shape (for plan 16 and plan 20)

```ts
interface LoginWindowStorageClearResult {
  localStorage: number | 'unsupported'
  sessionStorage: number | 'unsupported'
  indexedDB: number | 'unsupported'
  caches: number | 'unsupported'
  serviceWorkers: number | 'unsupported'
}
```

`clearStorage(originUrl, userAgent)` resolves this shape for any completed run (including one where several categories are `'unsupported'`), and rejects ONLY on a structural failure (`humble_login_clear_storage:bad-args`, `:window:<err>`, `:script:<err>`, or `:timeout`).

## Which Categories WKWebView Actually Supports (as measured by this plan)

This plan's own verification is structural/textual (`cargo test` proves the script text is correct and self-consistent; it cannot drive a real WKWebView, per this module's own `#[cfg(test)] mod tests` doc comment). No automated layer in this plan empirically observed which of the five categories are live-supported by the actual macOS WKWebView this app ships with — that is explicitly left to plan 20's blocking live-gate re-run, per this plan's own `<output>` instruction ("F-6 is NOT yet closed here"). What IS known from reading the crate/WebKit's public capability set (not from a live run):
- `localStorage`/`sessionStorage`: universally present on any WKWebView-hosted page; the script's `typeof` guard is defensive, not expected to ever hit the `'unsupported'` branch in practice.
- `indexedDB.databases()`: the one category flagged by name in the plan's own `<action>` block as "not universally available" — WebKit added it later than the base IndexedDB API. The script's `typeof indexedDB.databases === 'function'` guard exists specifically for this; if the shipped WKWebView lacks it, `indexedDB` reports `'unsupported'`, never a false `0`.
- `caches` (Cache Storage) and `navigator.serviceWorker`: both are modern WebKit features; guarded the same way for the same reason.

This is a plan-time literature/design note, not an empirical proof — treat it as a hypothesis for plan 20's live gate to confirm or falsify, not as a settled fact.

## Decisions Made

See `key-decisions` in frontmatter. Most consequential: the **origin-vs-domain gap is left open, not closed**, and is recorded as a decision rather than silently assumed away — `humble_login_clear_storage` clears exactly the origin its hidden window loads (`HUMBLE_BASE_URL`, the `www.` origin), and does not reach a hypothetical bare-apex origin's storage. Humble's web app is observed to run entirely on the `www.` origin in every transcript this phase has produced, but that observation has not been elevated to a proven invariant — plan 16/20 should treat "no apex-origin storage exists" as a claim still owed confirmation, not a closed question.
