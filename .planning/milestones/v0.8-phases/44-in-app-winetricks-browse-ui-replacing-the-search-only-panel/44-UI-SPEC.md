## Color

Scoped to this panel only, using existing per-theme custom properties — no new tokens invented, no raw `--status-*` consumed directly for text/icon color (see the project's own measured lesson: `--status-*` are raw Figma constants with no light-theme override; `--success`/`--danger` are the theme-adaptive aliases and are what text/icon color must read).

| Role | Token | Usage |
|------|-------|-------|
| Dominant (60%) | `--modal-background` | Dialog surface (inherited chrome, unchanged) |
| Secondary (30%) | `--input-background` | List's internal scroll container, row background, search bar fill |
| Accent (10%) | `--accent` (via the existing `var(--navbar-active, var(--accent-overlay, var(--accent)))` fallback chain where hover/selected text-color is involved) | See reserved-for list below |
| Destructive | not applicable this phase | No destructive action exists in this surface (no uninstall/remove verb is exposed by the data layer). If one is ever added, reuse `--danger`/`--danger-hover`, never raw `--status-danger`. |

**Accent reserved for, and only for:**
1. The per-row **Install** button fill/label (the primary CTA of this surface).
2. Category-group header and row **hover/keyboard-focus** text+caret color (reusing the exact chain already shipped and CR-03-hardened in `FilterFacetGroup/index.scss` — do not consume bare `--navbar-active`, it is undefined in 7 of 11 theme blocks and silently drops the whole declaration).
3. `:focus-visible` outline rings (`outline: 2px solid var(--accent)`), matching the rest of the app.
4. The inline per-row install progress bar fill (matches the already-shipped `.progressDialog.linearProgress > .MuiLinearProgress-bar { background-color: var(--accent) }`).

**Primary visual anchor.** At rest — before any typing, expanding, or installing — the first
accent-colored, actionable thing the eye should land on is the **curated group's row of Install
buttons**. That group is open by default specifically so this is true on panel open, not after an
interaction. Every other accent use above (hover chains, focus rings, progress fill) is
secondary/responsive — it appears in reaction to input, it is not a resting-state anchor.

**Explicitly NOT accent:** the "Cached" tag and the "Needs the Winetricks GUI" tag are neutral
informational badges, styled with `--text-secondary`, not accent — accent is reserved for
actionable/selected states, and a badge on every fourth row (cached is common) would dilute it to
noise.

**Non-colour signal requirement (C-3).** Every state below pairs its color with an icon and a text label — colour is never the only signal, because `--accent` alone measures 3.79:1 (dracula-classic) to 8.95:1 (sweet-dark) hover contrast and a same-hue background swap (the pattern the retired `SearchBar` `:hover { background-color: var(--accent) }` rule used, and which this project's own todo history could not cleanly rule in or out as a contributor to a "selection is temperamental" report) is not being repeated here.

**Est. new keys: 16** (`curatedGroup`, 5× `category.*`, `cachedTag`, `installedTag`,
`needsGuiTag`, `installingRow`, `installFailedTag`, `retry`, `emptyHeading`, `emptyBody`,
`zeroResultHeading`, `clearSearch`). Budget the localisation task for **16 new keys × 49
locales** — this number was previously stated inconsistently (11 in one place, 16 in another);
16 is correct and is now the only figure in this document.

**CTA note.** "Install" and "Retry" are bare verbs with no noun in the visible string — deliberate,
not an oversight. The row's own title (e.g. "Visual C++ 2019 libraries") sits immediately to the
button's left and supplies the object visually. That context does not reach assistive tech the
same way: a screen reader listing several same-labelled "Install" buttons out of that visual
context is genuinely ambiguous, so each button should carry a resolved `aria-label` built from the
row's own title (e.g. "Install Visual C++ 2019 libraries") — the *visible* label stays the short
verb, only the accessible name carries the object.

## Component Inventory (guidance for the planner, not a file layout mandate)

- `Winetricks/index.tsx` — **loses both gates that currently wrap `installWrapper`, not one.**
  The shipped code stacks two conditionals, not one:
  - **Outer** (`:156`): `{!declined && !loadingInstalled && (<div className="installWrapper"> ...`
  - **Inner** (`:158`): `{!installing && allComponents.length !== 0 && (<div className="actions">...`

  An earlier draft of this spec only named the inner one. That is not sufficient to satisfy C-1,
  because the **outer** gate is the one that fires on install *completion*, not just at
  panel-open: `onInstallingChange` (`:97-99`) calls `listInstalled()` whenever the reported
  `component` is `''`, and `listInstalled()` itself (`:37-38`) is what sets `loadingInstalled`
  back to `true` for the duration of that refetch. So the entire `installWrapper` subtree —
  search bar, curated group, every category, every row — unmounts and remounts on **every
  install's completion**, not only at initial load. This was never closed by 35-25
  (`366e719bb`); that commit addressed only the `installing` half, and the identical
  mousedown/mouseup-race mechanism this spec's Interaction Contract §1/§5 exists to prevent is
  exactly as reachable at install-*end* as it was at install-*start*. **Both `!installing` and
  `!loadingInstalled` must stop gating the mount of the browse list.** See the Loading state below
  for how the post-install refetch should render instead.
- **New:** a browse-list component (e.g. `WinetricksBrowse/`) replacing `WinetricksSearch/` as the thing rendered inside `installWrapper`. It owns: the search input (reusing `<SearchBar>` for chrome only, see Interaction Contract §1), the curated group, the five category groups, and per-row action-slot state.
- **New:** a per-row component (e.g. `WinetricksBrowse/Row.tsx`) implementing the 6-state action slot in the States section below.
- **New:** a category-group component, following the shipped `FilterFacetGroup` header/caret/badge *contract* (rotation, uppercase label, tabular-nums count, `--neutral-05` unchecked-equivalent border contrast fix) but declared under its **own** CSS scope (e.g. `.winetricksDialog .WinetricksBrowse__group`), **not** literally imported from `NavShell/components/FilterFacetGroup`. That component's styling is selector-scoped to `.NavShell__tier2Portal` and its `Dropdown` dependency carries unrelated `MainButton`-menu CSS that had to be out-specified once already (`FilterFacetGroup/index.scss`'s own `260815-mk1` comment) — reusing the pattern is right, reusing the component instance across an unrelated ancestor scope is the kind of cross-context CSS reuse this codebase has already been burned by (`Dropdown` styling its panel's *contents*, an unscoped `.MuiTabs-root` leaking app-wide). **(researcher discretion — flag for planner review if a shared primitive is preferred instead.)**
- `WinetricksSearch/index.tsx` — retired by this phase; its `install()`-on-`mousedown` race-fix pattern and comment history should migrate to the new Row component's Install button, since the underlying mouse-race mechanism (a remount tearing down the row mid-gesture) is exactly what C-1 exists to prevent structurally, but the *defensive* mousedown-capture technique is still good practice on any clickable list row and costs nothing to keep.
- `Winetricks/index.tsx`'s `installedWrapper` block (`:199-221`, the bottom "Installed
  components:" comma-joined summary) — **retired by this phase, not kept and not merged.** The
  per-row Installed badge (see States > Row-level) now surfaces the same fact — verb-by-verb, in
  place, the moment `listInstalled()` resolves — so keeping both would ship the identical piece of
  information twice in two different visual treatments in the same dialog, which is the exact
  redundancy this revision was asked to resolve rather than leave implicit. The one real argument
  *for* keeping it is that it is currently the only place that lists every installed component in
  one flat view regardless of which categories happen to be expanded or what the search box
  currently filters to — the inline badge only becomes visible once its row's category is expanded
  (or it survives an active search filter). That argument is judged not to win here: the curated
  group is open by default and is exactly the "commonly needed" set most likely to already be
  installed, categories are one click from any collapsed state, and a user who wants a full census
  of what's installed on this bottle can search-and-scan rather than read a bare comma-joined verb
  list with no per-item context (no category, no cached state, no way to act on an entry). If the
  planner disagrees and wants a standing "N installed" affordance, that is a small addition (e.g. a
  static count badge near the search input, not the full list) — but the full flat summary as
  currently shipped should not survive alongside the per-row badge unmodified.

## Layout

The dialog itself is unchanged (`ProgressDialog` → MUI `Dialog`, `scroll="paper"`, `max-width: min(700px, 85vw)`) — **C-6 is honored by not touching it.**

Inside `installWrapper`, top to bottom:

```
[ ⌕ Search components…                                    ]  <- reused SearchBar, input only
─────────────────────────────────────────────────────────────
  COMMONLY NEEDED                                     (open)
    vcrun2019   Visual C++ 2019 libraries        [Install]
    dotnet48    .NET Framework 4.8               [Install]
    ...
─────────────────────────────────────────────────────────────
▸ APPLICATIONS                                    57  (collapsed)
▸ BENCHMARKS                                        8  (collapsed)
▸ DLLS & LIBRARIES                                328  (collapsed)
▸ FONTS                                            42  (collapsed)
▸ SETTINGS                                        132  (collapsed)
```

- The whole block above (search + curated + categories) sits in its **own internal scroll
  container**: `max-height: min(50vh, 420px); overflow-y: auto;` — separate from the outer MUI
  dialog scroll. Rationale: without this, expanding "DLLs & libraries" (328 rows) pushes the
  progress/log box (which sits below `installWrapper`, unchanged) an arbitrary distance down the
  *dialog's* scroll, away from the row that triggered it. The search input is `position: sticky;
  top: 0;` **within this inner container**, so it stays reachable while scrolled into a long
  expanded category.
- A category's expanded body is **itself** independently bounded: `max-height: 240px; overflow-y:
  auto;`. **Correction from an earlier draft of this spec:** this bound is not guarding against a
  flaw in the shipped `Dropdown`/`FilterFacetGroup` precedent — that primitive already avoids
  silent clipping via `.dropdown.expanded { max-height: 50vh; overflow-y: auto; }`
  (`Dropdown/index.scss`), so nothing there clips. The silent-clip risk (`overflow: hidden` at a
  fixed `max-height`) exists only in the *sketch's* raw HTML mock
  (`references/library-filtering.md`'s `.grp-body { overflow: hidden; max-height: 600px }`), which
  this phase does not use verbatim. **240px is chosen tighter than the shipped primitive's 50vh
  specifically because of P-7 below** — this browse region already competes for vertical space
  with the fixed-height log box in the same dialog, and 50vh stacked on top of that would make an
  already-crowded modal worse, not because 50vh would clip anything. Collapsed state is the same
  rule at `max-height: 0`.
- **P-7 — acknowledged nested-scroll risk, not fully resolved by this spec.** `Dialog.tsx:101`
  sets `scroll="paper"` (the MUI Paper itself scrolls), `ProgressDialog/index.css:10-18` gives the
  log box a fixed `height: 25em` (400px) with its own `overflow: auto`, and this spec adds a
  `420px`/`50vh`-capped browse region plus a `240px`-capped expanded category on top of that —
  up to **four** independently-scrolling regions stacked in one modal. The numbers above each have
  their own justification and are kept, but this document does not claim the combination is
  comfortable on every supported screen size. That is a live-viewport check for the planner or
  executor to run (e.g. a ~768px-tall laptop viewport with a category expanded and the log box
  visible), not something a spec can settle on paper alone.
- Row anatomy, left to right: `[title, bold-off, 16px] [verb, 11px monospace-style secondary
  caption]` — flexible, truncates with ellipsis — then a fixed-width trailing action slot (see
  States) that is never narrower than the "Install" button's own width, so the row doesn't reflow
  horizontally when a tag appears next to it.
- **The action slot's height is fixed too, not only its width.** Give the row a single fixed
  height (e.g. `height: 44px` — matches the existing touch-target exception already in this
  document) and give every one of the six action-slot treatments (Available, Available+Cached,
  Installing-this-row, Installing-elsewhere, Installed, Needs GUI, Errored) the **same**
  line-height and vertical padding within that fixed row height, so none of them can make the row
  taller or shorter than any other. This matters specifically because the Installing→Installed
  transition (spinner+text → badge) fires at the exact moment the post-install
  stale-while-revalidate refresh resolves (see States > Loading) — if that swap is not metrically
  identical to the state it replaces, every row below the one that just finished shifts
  **vertically** at that instant. A vertical shift under the pointer at that moment is the same
  class of hazard Interaction Contract §5 exists to guard against for the horizontal
  mousedown/mouseup case: the click target moves out from under a user who was about to act on a
  different row. Metrically match the Installing and Installed treatments (and the rest) rather
  than styling each independently.
- `min-width: 0` on every flex row and every group body — this codebase has hit "a flex child with
  grid/flex content overflows its container without it" before; stated explicitly so it isn't
  dropped by omission.

## States

### List-level

| State | Trigger | Appearance |
|-------|---------|------------|
| **Loading** | Two distinct triggers, **both real and both common — not one edge case**: (a) initial mount, before `listAvailable`/`listInstalled` resolve for the first time; (b) **every install's completion** — `onInstallingChange` (`:97-99`) re-calls `listInstalled()` whenever the finishing component is reported as `''`, which flips `loadingInstalled` back to `true` for that refetch (`:37-38`). | **(a) First load:** no rows exist yet — the search input renders immediately (browse-first mandate, nothing gated on data), its search-icon slot shows the existing spinner treatment (`SearchBar`'s `loading` prop), and the list region shows centered "Loading components…" (reuse `winetricks.loading-available`). | **Empty** (no data at all) | `allComponents.length === 0` after load, independent of search | Centered icon (`faTriangleExclamation` or similar, already used for not-quite-error informational states in this codebase, e.g. `HumbleExpiryToast`) + `winetricksBrowse.emptyHeading` + `winetricksBrowse.emptyBody`. **No recovery action** — there is nothing to clear; this is a data-availability state, not a filter artifact. |
| **Default / browse** | Data loaded, search empty | Curated group open, all 5 category groups collapsed with counts, as drawn above. |
| **Zero-result** | Search has ≥2 characters (unchanged threshold from `WinetricksSearchBar`) and the filtered set is empty | The grouped structure (curated + categories) is replaced entirely by the flat results view (see Interaction Contract §2), and inside it: `winetricksBrowse.zeroResultHeading` (interpolating the query) + an inline `winetricksBrowse.clearSearch` button that calls the same clear handler as the search bar's own ✕ button. **This is the state this surface has historically got wrong by omission** — the old panel just showed nothing typed, no "why," no way out. |

## Interaction Contract

**1. The browse list is never the `SearchBar` suggestions overlay.** This is the single most
important interaction decision in this spec, and it is what actually satisfies C-1 architecturally
rather than just procedurally.

`SearchBar`'s `suggestionsListItems` prop renders into `.autoComplete`, a `<ul>` that is `display:
none` except `&:focus-within` — i.e. it structurally does not exist as a stable, always-visible
list; it is a focus-conditional overlay, and this exact mechanism is the shared primitive behind
the still-open Half B of the 2026-08-26 todo (`WinetricksSearch` and `LibrarySearchBar` both
inherit it). Building "browse-first" on top of that primitive would still leave the list's mount
lifecycle tied to focus state, which is adjacent to — not the same as, but adjacent to — the
`installing`/`loadingInstalled` remount class this phase exists to close.

Instead: reuse `<SearchBar>` for its **input chrome only** — pass no `suggestionsListItems` (or
leave it `undefined`), so `.autoComplete` never renders. The curated group, the category groups,
and the flat search-results list are all rendered as an **always-mounted sibling** below the
`<SearchBar>`, independent of its focus state. Typing filters what that sibling shows; it never
determines whether it exists. The same discipline applies to the two `installWrapper` gates named
in Component Inventory — a stable list means stable across *both* focus state and install
lifecycle, not just one of them.

**2. Search behavior.** At 0–1 characters: grouped browse view (curated + collapsed categories),
unchanged from Default. At ≥2 characters (same threshold `WinetricksSearchBar` already uses —
not revisited, it was a deliberate anti-noise choice for a 567-item set): the grouped structure is
replaced by a single flat list of matches (verb-or-title substring, case-folded — unchanged
matching logic from the existing implementation), each row additionally showing its category as a
small inline tag (since grouping is gone, that context would otherwise be lost), with a
`"{{count}} results"`-shaped header. Clearing the search (the existing ✕ button) returns to the
grouped view with prior category expand/collapse state preserved — collapsing a category to search
and back should not silently re-collapse a group the user had deliberately opened.

**3. Install is always a specific row's action.** There is no separate "select, then commit"
step and no shared "current selection" variable — clicking a row's own `[Install]` button installs
exactly that row's verb, always. This is what makes **C-2** ("Install must never be actionable
with no committed selection") true by construction rather than by a runtime check: the thing bound
to the click handler is always that row's own resolved `verb` string, never a value read out of
search-box state or a separately-tracked highlight. The three cases where the button is
non-actionable are handled by **not rendering an enabled Install button at all** rather than by a
silent no-op: Needs-GUI verbs never get one, an in-flight-elsewhere state disables it with an
explanation, and the build-declined state (existing `WINETRICKS_DECLINED_GUARD`) is unchanged and
still gates the whole surface.

**4. Category disclosure is keyboard-operable.** Each category header is a real `<button
aria-expanded>` (or the existing `Dropdown` primitive's own disclosure button), never a `<div
onClick>` — this codebase has already paid for the `<li onClick>` version of this mistake once
(`LibrarySearchBar`'s shared vulnerability, noted directly in `SearchBar/index.tsx`'s own
comments).

**5. Row mouse-down capture is worth keeping, not because it fixes anything new here, but because
it is free and correct.** `WinetricksSearchBar`'s pattern of capturing install intent on
`mousedown` (with a `suppressNextClick` guard so keyboard activation via `click` still works)
protects against a real, general mousedown→mouseup target-drift failure mode on any clickable row,
independent of whether the row-remount bug it was originally built to guard is still reachable
after C-1 ships in full (both gates, per Component Inventory). Carry the technique into the new
Row component's Install/Retry/Open-GUI buttons.
