# Phase 34.2 Plan 17: reportRepairFailure extraction (CR-01 renderer half) Summary

**Extracted GameSubMenu's repair-failure catch into a standalone, directly-testable `reportRepairFailure()` giving every repair failure three independent signals -- a transport-independent console line, the `window.api.logError` operator-log frame plan 34.2-16 made live on the sidecar, and an ERROR dialog the user actually sees -- proven by 4 direct unit tests including a pinned information-disclosure guard.**

## Accomplishments

- Closed the renderer half of verification gap #1 / GAP-CYCLE-1 CR-01's third `missing:` item
  (REQ-34.2-12): a repair failure now surfaces a user-visible ERROR dialog on both Electron and
  Tauri, instead of the confirmation dialog just closing with nothing else happening.
- `GameSubMenu/index.tsx:143-149`'s `onRepairYesClick` catch is now a single-line delegation to
  `reportRepairFailure({ appName, error, showDialogModal, t })` -- `handleRepair` and every other
  function in the file are byte-unchanged.
- `reportRepairFailure()` performs exactly three side effects, in order: `console.error` (transport-
  independent, always visible in webview devtools regardless of any IPC channel's health),
  `window.api.logError` (the pre-existing signal, made live on the sidecar by 34.2-16), and
  `showDialogModal` with `type: 'ERROR'` (the signal the user actually sees).
- T-34.2-52 (information disclosure): the dialog `message` is the FIXED translated string
  `box.repair.error` only -- it never interpolates the raw error. Pinned by a test that embeds a
  distinctive sentinel token in the thrown `Error`'s message and asserts the dialog message excludes
  it, while the console/log assertions confirm the same token DOES reach those two (local,
  already-privileged) destinations.
- Added `box.error.title` ("Error") and `box.repair.error` ("Repair failed. See the log for
  details.") to `public/locales/en/gamepage.json`, preserving the file's existing alphabetical key
  ordering (`error` inserted between `close`/`importpath`; `repair.error` inserted before
  `repair.message`).
- All 4 unit tests call `reportRepairFailure` directly with stubbed collaborators -- no rendering,
  no filesystem access, no sidecar start (`GamesSubmenu` itself carries a dozen hooks and cannot be
  invoked as a plain function the way `MainButton.steamIncomplete.test.tsx` does).

## Decisions Made

- **Merged the dialog-shape assertion and the information-disclosure guard into one test.** The
  plan's `<behavior>` block lists four bullets, and the acceptance criteria separately require (a)
  4+ tests total and (b) that deleting the single `showDialogModal` call fails EXACTLY one test.
  Since the info-disclosure assertion reads the same `showDialogModal` call as the dialog-shape
  assertion, keeping them as two separate `it()` blocks would fail 2 tests on that one revert,
  violating the RED-spot-check requirement verbatim. Merging them into one test satisfies both
  constraints; a 4th, genuinely independent test (non-Error thrown value, asserting only on
  `console.error`/`window.api.logError`) keeps the suite at 4 tests without touching the
  `showDialogModal` call, so it survives the same revert unaffected.
- **Dialog message is a fixed translated string, never interpolated with the raw error** — per the
  plan's own T-34.2-52 instruction and this codebase's existing convention
  (`EgsSettings.tsx:34-36`), reused verbatim for the `type: 'ERROR'` shape.
- **`box.error` inserted alphabetically between `close` and `importpath`; `repair.error` inserted
  alphabetically before `repair.message`** — preserves the locale file's existing key ordering so
  `pnpm i18n` does not reorder the file on its next run (per plan instruction).

## Issues Encountered

- First test-suite draft used 4 separate `it()` blocks (one per behavior bullet), with the
  information-disclosure assertion as its own test. The RED spot-check (delete `showDialogModal` in
  `repairFailure.ts`) failed 2 of 4 tests, not the required exactly-1, because both the dialog-shape
  test and the info-disclosure test read the same mock call. Resolved by merging those two into a
  single test (see Decisions Made above); re-ran the spot-check and confirmed exactly 1 of 4 tests
  failed, then restored the file and confirmed `diff` against the pre-spot-check version was empty.
- First draft of `repairFailure.ts`'s docstring repeated the literal strings `window.api.logError`
  and `type: 'ERROR'` in prose (describing the three side effects), which would have made this
  plan's own acceptance-criteria greps (`grep -c 'window.api.logError' repairFailure.ts` expecting
  1, `grep -c "type: 'ERROR'" repairFailure.ts` expecting 1) return 2 instead. Rephrased the
  docstring to describe the signals without repeating the exact code literals (Rule 3 — wording
  only, no behavior change, no separate commit needed since caught before the Task 1 commit).
