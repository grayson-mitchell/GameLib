## Summary

The slice does what it says structurally: 26 channels (18 game-details/settings/override + 8
enrichment) are registered onto the sidecar's `ipcMain` from two curated modules, backed by
Electron-free bodies extracted verbatim out of `main.ts`/`launcher.ts`/`crossover_index/ipc_handler.ts`.
`main.ts` genuinely delegates (verified against the diff), no channel is registered twice across the
nine sidecar registration modules, all three `send`-kind bodies are wrapped in `try`/`catch`, the
`send`-vs-`invoke` kind was correctly preserved for every channel, and all 159 new tests pass locally
(0.2s + 2.1s). No `require()`-of-alias regression, no unused-import residue in `main.ts`/`launcher.ts`,
no new lint errors in the extracted modules.

Three problems are serious enough to block:

1. **`repair` was ported without being added to `LONG_RUNNING_CHANNELS`.** It is now served over the
   60s-bounded `sidecar_invoke` path, so a real Epic/GOG repair produces a spurious
   `sidecar invoke timed out` rejection at the renderer while the repair keeps running — the *exact*
   failure class the exemption list was created for (CR-03, Phase 30). The renderer call site has no
   `.catch()`.
2. **`bootstrap.ts`'s re-homed anticheat listener does `void downloadAntiCheatData(...)` on a
   rejectable promise.** The sidecar has no `unhandledRejection` guard; the surrounding `try`/`catch`
   only wraps `backendEvents.on()`, which cannot throw. A single `EACCES`/`ENOENT` on
   `areweanticheatyet.json` kills the whole backend process.
3. **Two of the new test suites destructively write to and `rmSync(..., {recursive:true})` a path that
   is *not* guaranteed redirected.** Their only safety mechanism is a `jest.mock('os')` `homedir()`
   override, which `sidecar/pathShim.ts` bypasses on Windows (`env.APPDATA`) and on Linux
   (`env.XDG_CONFIG_HOME`). On Windows this deletes the real `%APPDATA%\GameLib\fixes` and wipes the
   real recent-games list and metadata-override store. This is the repo's own
   `tests-clobbering-real-steam-store` incident, re-armed.

The remaining warnings cluster around **gates and tests that assert less than their prose claims**:
two "byte-identical to HEAD" gates that are tautologies on any clean checkout, import gates that are
depth-1 textual matches while the docstrings promise transitive electron-freedom (and the transitive
claim is already false), and a vacuous i18next assertion that reproduces the exact 34.1 CR-01 blind
spot its own header says it exists to avoid.

### CR-01: `repair` is served over the 60s invoke bound — spurious timeout + unhandled renderer rejection

**File:** `src-tauri/src/main.rs:132-139`, `src/backend/sidecar/gameDetailsFlowRegistration.ts:197-201`

**Issue:** Plan 06 Task 2 audited the newly-reachable channels for the `INVOKE_TIMEOUT` bound and added
exactly one (`getCrossoverIndex`), plus a recorded measurement for `getWikiGameInfo`. `repair` was not
considered. `repair` is now a live `ipcMain.handle` on the sidecar, so it goes through
`SidecarState::invoke` → `timeout_for(channel)` → `Some(60s)`.

A real repair is a re-verification/re-download of a game's installed files. `LegendaryGame.repair()`
shells out to `legendary repair`, `GOGGame.repair()` to `gogdl repair` — both routinely run for
minutes on a multi-GB title. At 60s the Rust side:

```rust
Err(_) => {
    self.pending.lock().ok().and_then(|mut p| p.remove(&id));
    Err("sidecar invoke timed out".into())
}
```

removes the pending entry and returns an error, and the reader thread later logs the real response as
`response for unknown/timed-out id=... (dropped)` (main.rs:811-813). Meanwhile the repair keeps running
in the sidecar and eventually emits `gameStatusUpdate: done`. This is verbatim the symptom
`LONG_RUNNING_CHANNELS`'s own doc comment (main.rs:104-120) describes for `install`.

The renderer side has no error handling:

```tsx
// src/frontend/screens/Game/GameSubMenu/index.tsx:143-153
async function onRepairYesClick(appName: string) {
  await repair(appName, runner)          // helpers/library.ts:136 → window.api.repair(...)
}
...
{ text: t('box.yes'), onClick: async () => onRepairYesClick(appName) },
```

`onClick` returns a floating promise nobody catches → an unhandled rejection in the renderer, which is
precisely the CR-03 symptom recorded in main.rs:110-112.

`readConfig('library')` has the same shape (`libraryManagerMap['legendary'].refresh()` — the very
operation `refreshLibrary` is exempted for), though it currently has no frontend caller.

**Fix:** add `repair` (and, for symmetry with `refreshLibrary`, `readConfig`) to the exemption list, and
update the pinning test in the same commit — `longRunningChannels.test.ts:104-108` asserts the set is
*exactly* the current six, so it will fail loudly until updated.

```rust
const LONG_RUNNING_CHANNELS: &[&str] = &[
    "install",
    "updateGame",
    "uninstall",
    "checkGameUpdates",
    "refreshLibrary",
    "getCrossoverIndex",
    // A repair is a full re-verify/re-download of an installed game
    // (`legendary repair` / `gogdl repair`) and routinely exceeds 60s.
    "repair",
    // readConfig('library') calls legendary.refresh() — the same work
    // `refreshLibrary` above is exempted for.
    "readConfig",
];
```

```ts
// src/backend/__tests__/longRunningChannels.test.ts
const EXPECTED_LONG_RUNNING_CHANNELS = [
  'install', 'updateGame', 'uninstall', 'checkGameUpdates',
  'refreshLibrary', 'getCrossoverIndex', 'repair', 'readConfig'
]
```

### CR-02: `void downloadAntiCheatData(...)` can reject and crash the sidecar process

**File:** `src/backend/sidecar/bootstrap.ts:228-248`

**Issue:** Block A re-homes the `releasesInfoReady` listener into the sidecar:

```ts
try {
  backendEvents.on('releasesInfoReady', (releasesInfo) => {
    logDebug(...)
    void downloadAntiCheatData(                       // <-- rejection is unguarded
      isMac ? releasesInfo.anticheatFiles.shaMac
            : releasesInfo.anticheatFiles.shaLinux
    )
  })
} catch (error) {
  logWarning(`[bootstrap] Failed to register releasesInfoReady anticheat listener: ${error}`, ...)
}
```

The `try`/`catch` only wraps `backendEvents.on()` — an `EventEmitter.on` call that cannot throw. It
provides zero coverage for the listener body, which is invoked later, from the event emitter, outside
this stack frame.

`downloadAntiCheatData` (`anticheat/utils.ts:23-63`) is rejectable on a path *outside* its own
`try`/`catch`:

```ts
if (existsSync(anticheatDataPath)) {
  const localFileHash = await createMD5(anticheatDataPath)   // NOT inside a try
  ...
}
```

`createMD5` does `createReadStream(path)` + `await finished(rStream)`. `EACCES`, a TOCTOU delete
between `existsSync` and the open, or the path being a directory all reject here.

The sidecar has **no** `process.on('unhandledRejection')` handler (grep confirms: only comments
referencing its absence in `electronStub.ts:214`, `appShellFlowRegistration.ts:90`, and this slice's own
`gameDetailsFlowRegistration.ts:61`). On Node ≥15 the default is `--unhandled-rejections=throw`, so this
takes down the entire backend process — the same class as the recorded
`sidecar-dialog-reject-crashes` incident. This slice's own module docstrings identify this hazard for
`send` bodies and then leave it open one file over.

**Fix:** attach a rejection handler to the fire-and-forget call, not just to the registration.

```ts
backendEvents.on('releasesInfoReady', (releasesInfo) => {
  logDebug('Releases info ready, checking anticheat data', LogPrefix.Backend)
  downloadAntiCheatData(
    isMac ? releasesInfo.anticheatFiles.shaMac : releasesInfo.anticheatFiles.shaLinux
  ).catch((error) => {
    logWarning(
      `[bootstrap] downloadAntiCheatData failed: ${String(error)}`,
      LogPrefix.Backend
    )
  })
})
```

Consider also adding a process-level `unhandledRejection` guard in `src/sidecar/index.ts` as
defence-in-depth — this listener is one of several `void`-ed async calls the sidecar now owns.

### CR-03: New test suites destructively `rmSync` and overwrite paths that are not guaranteed redirected (data loss on Windows/Linux)

**File:** `src/backend/sidecar/__tests__/enrichmentFlows.test.ts:51-62, 360-366, 368-372, 659-662`;
`src/backend/sidecar/__tests__/gameDetailsFlows.test.ts:99-110, 422, 825`;
`src/backend/__tests__/knownFixes.test.ts:24-32, 50-52`

**Issue:** Every one of these suites relies on a single safety mechanism — overriding `os.homedir()` to
a tmp directory — and then performs destructive filesystem and store writes:

```ts
// enrichmentFlows.test.ts:360-366 (beforeEach — runs before EVERY test)
if (existsSync(fixesPath)) {
  rmSync(fixesPath, { recursive: true, force: true })
}
mkdirSync(fixesPath, { recursive: true })
...
configStore.set('games.recent', [])
```

```ts
// gameDetailsFlows.test.ts:422 / 825 (beforeEach)
gameOverridesStore.set('overrides', {})
```

But `enrichmentFlows.test.ts` and `gameDetailsFlows.test.ts` also do
`jest.mock('electron', () => jest.requireActual('../electronStub'))`, which routes
`constants/paths.ts`'s module-scope `app.getPath('appData')` at the **real** `sidecar/pathShim.ts`:

```ts
function resolveAppDataDir(): string {
  switch (platform) {
    case 'darwin': return join(homedir(), 'Library', 'Application Support')
    case 'win32':  return env.APPDATA || join(homedir(), 'AppData', 'Roaming')   // <-- env wins
    default:       return env.XDG_CONFIG_HOME || join(homedir(), '.config')      // <-- env wins
  }
}
```

On **Windows** `APPDATA` is always set, so the `homedir()` mock is completely bypassed:
`fixesPath` = `%APPDATA%\GameLib\fixes` (recursively deleted before every test in the file),
`appFolder` = `%APPDATA%\GameLib` (a real `areweanticheatyet.json` written and deleted),
`configStore` = the real `config.json` (recent-games list wiped), and `gameOverridesStore` = the real
user's title/art customizations (wiped). On **Linux** the same holds whenever `XDG_CONFIG_HOME` is
exported. Only macOS is safe, because `darwin` is the one branch that goes through `homedir()`.

This is the repo's own recorded `tests-clobbering-real-steam-store` incident (2026-07-22), and the
memory note for it explicitly says an `afterAll` restore is not a safety net. `bootstrapWirings.test.ts`
in this same slice got this right — it has an explicit assertion (`test 7`,
`expect(appFolder.startsWith(tmpdir())).toBe(true)`) that fails loudly on a mis-wired mock, and it
deliberately deletes nothing. `enrichmentFlows.test.ts` and `gameDetailsFlows.test.ts` have neither
property. `knownFixes.test.ts` does assert `fixesPath.startsWith(tmpdir())` — but as a *test body*,
while its `afterAll` `rmSync` runs unconditionally regardless of whether that test passed, and it also
runs even if the assertion test was filtered out by `-t`.

**Fix:** make the redirection unconditional and add a hard guard before any destructive operation.

```ts
// In every suite that writes/deletes under appFolder:
const TEST_HOME = join(tmpdir(), `gamelib-<suite>-test-home-${process.pid}`)
process.env.APPDATA = join(TEST_HOME, 'AppData', 'Roaming')   // set BEFORE any import
process.env.XDG_CONFIG_HOME = join(TEST_HOME, '.config')
jest.mock('os', () => { /* homedir() -> TEST_HOME, as today */ })

// Then fail loudly instead of deleting a real directory:
beforeAll(() => {
  if (!fixesPath.startsWith(tmpdir())) {
    throw new Error(
      `refusing to run: fixesPath resolved OUTSIDE tmpdir (${fixesPath}) — ` +
        'the config-dir redirect is not in effect'
    )
  }
})
```

Apply the same guard to `knownFixes.test.ts`'s `afterAll` `rmSync`.

### WR-01: Gate 7 and Gate 8 ("byte-identical to HEAD") are tautologies that can never fail in CI

**File:** `src/backend/sidecar/__tests__/gameDetailsImportGate.test.ts:279-303, 307-336`

**Issue:** Both gates read the working-tree file and compare it to `git show HEAD:<same path>`:

```ts
const working = readFileSync(filePath, 'utf-8')
headContent = execFileSync('git', ['show', 'HEAD:src/backend/sidecar/settingsFlowRegistration.ts'], ...)
expect(working).toBe(headContent)
```

On any clean checkout — i.e. every CI run, and every developer run after the change is committed — the
working tree *is* HEAD by definition, so this assertion is unconditionally true. The gate can only ever
fire against an uncommitted local edit, and the moment 34.2 was committed it stopped protecting
anything. The "do-not-touch" invariants REQ-34.2-10 and REQ-34.2-14 therefore have zero enforcement.

The fallback branch (used when `git show` fails) is a weak substring check (`/steamLibrary/`,
`/requestGameSettings/`), which is also all a full rewrite of the file would need to survive.

**Fix:** pin against a fixed baseline commit, not `HEAD`, or pin a content hash.

```ts
const BASELINE_SHA256 = '<sha256 of settingsFlowRegistration.ts at the 34.2 baseline>'
it('REQ-34.2-10 Gate 7: settingsFlowRegistration.ts is unchanged since the 34.2 baseline', () => {
  const digest = createHash('sha256')
    .update(readFileSync(join(__dirname, '../settingsFlowRegistration.ts')))
    .digest('hex')
  expect(digest).toBe(BASELINE_SHA256)
})
```

### WR-02: Import gates are depth-1 textual matches, but the docstrings claim transitive electron-freedom (and the transitive claim is already false)

**File:** `src/backend/sidecar/__tests__/gameDetailsImportGate.test.ts:52-97, 101-110`;
`src/backend/sidecar/__tests__/enrichmentFlows.test.ts:902-928`;
`src/backend/gamedetails/dispatch.ts:10-11`;
`src/backend/sidecar/enrichmentFlowRegistration.ts:84-92`

**Issue:** Every gate is a regex over the *file's own text*. The prose the gates back is stronger:

- `dispatch.ts:10-11`: "MUST NOT import `electron` (or anything that **transitively** reaches it) --
  including `backend/ipc`".
- `enrichmentFlowRegistration.ts:84-87`: "no file under `src/backend/sidecar/` may import it either
  directly **or transitively**."

The transitive property is already violated at depth 2, and no gate can see it:

| Reviewed file | depth-1 import | that file's own imports |
|---|---|---|
| `gamedetails/dispatch.ts:48` | `../dialog/dialog` | `dialog.ts:2` `import { dialog, Notification } from 'electron'`; `dialog.ts:5` `import { sendFrontendMessage } from '../ipc'` |
| `enrichmentFlowRegistration.ts:114` | `../storeSearch/cheapshark` | `cheapshark.ts:2` `import { app } from 'electron'` |

| `enrichmentFlowRegistration.ts:105` | `../utils` | `utils.ts:14` `from 'electron'`; `utils.ts:49` `from './ipc'` |

This works at runtime only because `installElectronHook`'s `Module._load` interception rewrites
`require('electron')`. That is a legitimate design, but the gates and docstrings currently claim a

```ts
const reached = resolveTransitiveImports('src/backend/sidecar/enrichmentFlowRegistration.ts')
```

Option (a) is honest and cheap; option (b) is what the prose currently promises.

### WR-04: Vacuous i18next assertion — the test computes its expectation from the same broken call

**File:** `src/backend/gamedetails/__tests__/gameDetailsModules.test.ts:342-358`

**Issue:**


Both sides call the *same* uninitialized `i18next.t()`. Verified against the installed version:

### WR-05: `bootstrap.ts` signals READY before `i18next.init()`'s resource load completes

**File:** `src/backend/sidecar/bootstrap.ts:167-194, 265`

**Issue:** `main.ts:482` awaits the initialization (`await i18next.use(Backend).init({...})`) before the
main window is created. `bootstrap.ts` fires it and moves on:

```ts
i18next.use(Backend).init({ ... }).catch((error) => { logWarning(...) })
...
output.write(`${READY_SENTINEL}\n`)
```

`i18next-fs-backend` loads locale JSON asynchronously. Between the READY sentinel (which is what
unblocks the renderer) and the resource load completing, every `i18next.t()` call site in the ported
surface — `repair`'s two notification bodies, `getLaunchOptions`'s synthesized default label — still
returns the key or `undefined`. D-02 narrows the window from "forever" to "the first few hundred ms of
startup", but does not close it, and `bootstrapWirings.test.ts:309` explicitly waits for
`isInitialized === true` before asserting, so no test covers the window.

**Fix:** hold the sentinel until initialization settles, matching main.ts's ordering.

```ts
const i18nReady = i18nInitialized
  ? Promise.resolve()
  : i18next.use(Backend).init({ ... }).catch((error) => { logWarning(...) })
...
void i18nReady.finally(() => output.write(`${READY_SENTINEL}\n`))
```

If holding the sentinel is unacceptable for boot latency, record the residual race explicitly in the
plan rather than leaving D-02 read as fully closed.

### WR-06: `readKnownFixes` builds a filesystem path from unvalidated renderer input with `join`

**File:** `src/backend/knownFixes.ts:29-35`; reached via
`src/backend/sidecar/enrichmentFlowRegistration.ts:151-155`

**Issue:**

```ts
export function readKnownFixes(appName: string, runner: Runner): KnowFixesInfo | null {
  const fixPath = join(fixesPath, `${appName}-${storeMap[runner]}.json`)
  if (!existsSync(fixPath)) return null
  ...JSON.parse(readFileSync(fixPath).toString())...
}
```

`appName` arrives straight off the wire (`args[0] as string`) with no validation. `join` normalizes
`..` segments rather than rejecting them, so `appName = '../../../../etc/hosts'` escapes `fixesPath`.
The parsed contents are returned to the renderer. This is a faithful port of the pre-existing
`launcher.ts` body, so it is not a regression — but this repo has an explicit, recorded convention from
Phase 18 that `path.join` is not containment and `resolve` + `relative` must be used, and this slice
newly exposes the function on the sidecar RPC surface where no typed-IPC layer sits in front of it.

Secondary: `storeMap[runner]` is `undefined` for an unrecognised runner, silently producing
`<appName>-undefined.json` rather than rejecting.

**Fix:**

```ts
import { join, resolve, relative, isAbsolute } from 'path'

export function readKnownFixes(appName: string, runner: Runner): KnowFixesInfo | null {
  const store = storeMap[runner]
  if (!store) {
    logWarning(`readKnownFixes: unknown runner '${runner}', ignoring.`)
    return null
  }
  const fixPath = resolve(fixesPath, `${appName}-${store}.json`)
  const rel = relative(resolve(fixesPath), fixPath)
  if (rel.startsWith('..') || isAbsolute(rel)) {
    logWarning(`readKnownFixes: rejected out-of-tree fix path for appName '${appName}'.`)
    return null
  }
  ...
}
```

### WR-07: `getCrossoverIndex` is now unbounded with no cancellation, on top of a known per-game rebuild

**File:** `src-tauri/src/main.rs:122-131, 132-139`; `src/backend/crossover_index/crossoverRatingMap.ts:39-61`

**Issue:** D-10 exempts `getCrossoverIndex` from the 60s bound while explicitly recording that
`buildCrossoverRatingMap()` calls `loadIndex`/`buildMaps` **once per game** rather than once overall,
and that fixing this is deferred. The two decisions compound: the loop is sequential (`await` inside a
nested `for`), there is no `AbortController`, and `timeout_for()` now returns `None`, so `rx.recv()`
blocks indefinitely. On a large macOS library this converts a slow call into a renderer promise that
may never settle, with no user-visible cancel path and no diagnostic. The doc comment's mitigation —
"a crashed sidecar still fails fast because the channel closes" — only covers sidecar death, not a slow
loop.

**Fix:** hoist the index build out of the per-game loop (it is a pure function of the index file, not of
the game), which likely removes the need for the exemption entirely:

```ts
export async function buildCrossoverRatingMap(): Promise<Record<string, number | null>> {
  const map: Record<string, number | null> = {}
  if (!isMac) return map
  await loadIndex()                       // once, not once per game
  for (const manager of Object.values(libraryManagerMap)) { ... }
  return map
}
```

If the exemption must stay for this slice, add a generous upper bound (e.g. 10 min) rather than `None`,
so a wedged call surfaces instead of hanging forever.

**Issue:** The factory supplies defaults:

```ts
jest.mock('../../online_monitor', () => ({
  initOnlineMonitor: jest.fn(),
  isOnline: jest.fn(() => true),
  runOnceWhenOnline: jest.fn((callback: () => unknown) => callback()),
  onConnectivityChange: jest.fn()
}))
```

The shared jest config sets `resetMocks: true`, which strips a factory `jest.fn(impl)`'s own
implementation before every test. `gameDetailsFlows.test.ts:395-401` knows this and re-arms
`mockedIsOnline` with a explanatory GOTCHA comment; `enrichmentFlows.test.ts`'s `beforeEach`
(lines 336-366) re-arms neither `isOnline` nor `runOnceWhenOnline`. Consequently, in every test in that
file, `isOnline()` returns `undefined` and `runOnceWhenOnline(cb)` **never invokes `cb`**. The
`(callback) => callback()` line reads as if the online path is exercised; it is dead.

No current assertion in the file depends on it, so this is latent rather than failing — but it is a
booby trap: the first test added that asserts on an online-gated path will silently pass against a
never-executed branch.

**Fix:** re-arm both in `beforeEach`, mirroring the sibling suite.

```ts
beforeEach(() => {
  ;(isOnline as jest.Mock).mockReset().mockReturnValue(true)
  ;(runOnceWhenOnline as jest.Mock)
    .mockReset()
    .mockImplementation((cb: () => unknown) => cb())
  ...
})
```
