<objective>
Close two test-quality warnings the developer explicitly opted into, both instances of the same
failure class this slice's own review named — **gates and tests that assert less than their prose
claims**:

**WR-01** — `gameDetailsImportGate.test.ts:279-336`. Gate 7 and Gate 8 read the working-tree file and
compare it to `git show HEAD:<same path>`. On any clean checkout — every CI run, and every developer
run after the change is committed — the working tree IS `HEAD` by definition, so the assertion is
unconditionally true. The gate could only ever fire against an uncommitted local edit, and the moment
34.2 was committed it stopped protecting anything. REQ-34.2-10's and REQ-34.2-14's "do-not-touch"
invariants for `settingsFlowRegistration.ts` and `electronUntouched.test.ts` therefore have **zero**
future enforcement. The `catch` fallback is a weak substring check (`/steamLibrary/`,
`/requestGameSettings/`) that a full rewrite of the file would survive.

**WR-04** — `gameDetailsModules.test.ts:342-358`. Both sides of the `toEqual` call the same
uninitialized `i18next.t()`:
`const expectedDefaultName = i18next.t('launch.default', 'Default', { ns: 'gamepage' })` then
`expect(result[0]).toEqual({ name: expectedDefaultName, ... })`. Independently reproduced: on
i18next 22.5.1 the uninitialized singleton returns `undefined` (it does not throw, and the inline
English default does not rescue it), and `toEqual` treats `undefined` object properties as absent — so
the assertion passes even if `result[0]` has no `name` at all. The file's own header frames itself as
the antidote to Phase 34.1's CR-01 ("asserting against a FAKE `t()` would prove nothing") and then
reintroduces the same blind spot one level over: asserting against a *real but uninitialized* `t()`
proves equally little.

Purpose: convert two assertions that cannot fail into two that can.
Output: digest-pinned do-not-touch gates and a translation assertion with real content behind it.
</objective>
