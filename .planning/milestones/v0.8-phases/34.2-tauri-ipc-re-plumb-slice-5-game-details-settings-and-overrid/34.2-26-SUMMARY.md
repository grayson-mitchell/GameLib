## Decisions Made

- **Sibling export over wrapper conversion.** The code review's literal suggested fix converts `logError` itself to an expression body. The plan explicitly diverges: `logErrorSettled` is added beside it. Rationale (measured, not assumed): 309 statement-position `logError(...)` call sites exist under `src/backend` (excluding `logger/`/`__tests__`), none awaited, and `@typescript-eslint/no-floating-promises` is `warn` — converting the shared wrapper's inferred return type would add ~309 new warnings for zero runtime behavior change. This is recorded in `deferred-items.md` ("From plan 34.2-20") and restated by plan 34.2-30, which will handle the four-wrapper change as its own scoped follow-up.
- **`flushUntil()` polling instead of a fixed 3-tick `flush()`.** The plan's action text says "await three setImmediate turns (mirror loggerFlows.test.ts's flush())". Test A's rejection depends on a REAL `fsPromises.mkdir()` settling via the libuv threadpool, not a mocked instant rejection like the WR-02 tests it replaces — a fixed tick count is not a reliable bound for real disk I/O. Verified this concern was warranted: the first Task 1 RED run demonstrated the real ENOTDIR rejection firing as a genuine `unhandledRejection`, caught only because a `process.on('unhandledRejection', ...)` listener was already attached; under-waiting before removing that listener risked a crashed jest worker instead of a clean test failure. Implemented a bounded (50-iteration, alternating `setImmediate`/`setTimeout(10)`) poll mirroring `loggerFlows.test.ts`'s own `pollForMarker` precedent for the identical underlying reason (real disk I/O). Applied to both Test A and (after discovering the same timing issue there) Test B.
- **`eslint-disable-next-line` for `prefer-promise-reject-errors`** on `Promise.reject(error)` where `error: unknown`. Wrapping the value (`new Error(String(error))`) was rejected because `String()` itself can throw for a null-prototype/hostile reason — reintroducing exactly the "a fix that adds a new throw path is worse than the bug it fixes" class this project's `sidecar-dialog-reject-crashes` incident already governs. The existing `.catch` handler already safely tolerates an arbitrary `unknown` value via its own try/catch and hardcoded fallback.
