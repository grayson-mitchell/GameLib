# Phase 34.2 Plan 25: CR-02 node:os containment gap closure Summary

Closed CR-02 (structural containment was specifier-dependent — `jest.mock('os')` never
redirected `require('node:os')`) plus WR-07/WR-09/WR-10/WR-11/WR-12 from the gap-cycle-3
code review, using a test-first RED/GREEN sequence: the detection gates were written and
observed failing against the unmodified containment module *before* the module itself was
changed.

## What was built

**Task 1** (commit `f05a1cbb`) added three gates to `structuralContainment.test.ts`:
- Test 7: `require('node:os').homedir()` must equal `require('os').homedir()`.
- Test 8: `os.userInfo().homedir` must equal `os.homedir()`.
- Test 9: a source gate walking `src/backend` for any `*.ts` file that references the
  `'node:os'` specifier alongside `homedir`/`userInfo`, backed by a declared 3-entry
  exclusion allowlist (`NODE_OS_GATE_EXEMPT_FILES`), two self-tests, and an anti-vacuity
  check proving the allowlist is load-bearing rather than decorative.

**Task 2** (commit `935e316a`) rewrote `jest.setupContainment.ts`:
- CR-02: a hoisted `mockOsFactory` function declaration registered via
  `jest.mock('os', mockOsFactory)` AND `jest.mock('node:os', mockOsFactory)`, also
  overriding `userInfo()` with a `homedir` override and a synthetic fallback if the real
  call throws `uv_os_get_passwd`.
- WR-07: `mkdtempSync(join(realTmpRoot, 'gamelib-jest-home-'))` + `chmodSync(root, 0o700)`
  replacing the predictable pid-based path and its check-then-act `existsSync`/`mkdirSync`
  pair.
- WR-09: `realHomeAtSetup` (captured before any mock, via the existing
  `jest.requireActual` handle) exported alongside `containmentRoot`.
- WR-10: a `setupFiles`-time precondition block that re-resolves both specifiers'
  `homedir()` and checks `containmentRoot` resolves inside `realTmpRoot`, throwing
  `[jest.setupContainment] REFUSING TO RUN` if any check fails — before any backend test
  file's own imports run.
- WR-12: corrected the `XDG_DATA_HOME`/`XDG_CACHE_HOME` comment to name
  `constants/paths.ts:21`'s `flatpakHome` as the first-party consumer it previously denied.
- Both `containmentRoot` and `realHomeAtSetup` are memoized on `globalThis` so re-evaluating
  the module (Task 3 imports both directly) cannot mint a second, disagreeing pair.

**Task 3** (commit `447b17c9`) edited Tests 1, 4, 6 of `structuralContainment.test.ts`:
- Added a top-level import of `containmentRoot`/`realHomeAtSetup`.
- Test 1: strengthened to exact identity (`homedir() === containmentRoot`).
- Test 4: added `flatpakHome` to the containment sweep (WR-12).
- Test 6: rewritten (WR-11) to drop the now-invalid `userInfo()`-as-independent-reference
  and the macOS-hardcoded log path, replaced with two platform-independent assertions.
- Removed `assertNotContained`, now dead code once Test 6 no longer needed it (an eslint
  `no-unused-vars` **error**, not merely a warning — fixed as part of this task).

**This changed from the plan's expectation of "5 of 6" to "1 of 12."** Root cause: Task 3
added a top-level `import { containmentRoot, realHomeAtSetup } from
'backend/jest.setupContainment'` to consume WR-09's export. That import alone triggers
`jest.setupContainment.ts`'s module body (including its `jest.mock` registrations)
regardless of whether `setupFiles` also loads it — so with `setupFiles` disabled, this
file now largely re-establishes its own containment by accident, via the WR-09 import.
Only Test 1's top-of-file `homedir` binding (captured via `import { homedir, ... } from
'os'`, evaluated *before* the `jest.setupContainment` import beneath it) still resolved to
the real, unmocked home. This does **not** mean `setupFiles` is unnecessary — every other
backend suite has no such direct import and depends on `setupFiles` entirely; only this
one file, uniquely, now carries a redundant containment path of its own. Documented at
length in the file's updated header docblock. Restored via `cp`; `git diff --exit-code
src/backend/jest.config.js` confirmed clean.
