## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] Test suite's own `require('i18next').default` returned `undefined`**
- **Found during:** Task 3 (writing the non-mocked i18next test)
- **Issue:** `bootstrap.ts`'s `import i18next from 'i18next'` compiles under TS `esModuleInterop` to `__importDefault(require('i18next')).default`, which only WRAPS the raw CJS module (`{ default: mod }`) — it does not add a literal `.default` property to the module itself. My test file's plain `require('i18next').default` (no TS interop applied to a raw `require()` call) therefore returned `undefined`, silently making `i18nextInstance.isInitialized` unreadable and hanging the test.
- **Fix:** Changed the harness to `const i18nextInstance = require('i18next')` (no `.default`), which is reference-identical, within the same isolated module registry, to the object `bootstrap.ts`'s `i18next` import resolves to.
- **Files modified:** src/backend/sidecar/__tests__/bootstrapWirings.test.ts
- **Verification:** Test 1 (`REQ-34.2-02`) passes deterministically across 5 repeated runs
- **Committed in:** 8ad8f5e5 (Task 3 commit)

**2. [Rule 1 - Bug] Project-wide `__mocks__/i18next.ts` automock silently defeated the "never mock i18next" requirement**
- **Found during:** Task 3 (i18next test hung; debugging traced it to `require('i18next')` returning `{ default, t }`, not the real npm package)
- **Issue:** `src/backend/__mocks__/i18next.ts` sits adjacent to the Backend Jest project's `roots` (`src/backend`), which Jest's manual-mock convention applies AUTOMATICALLY to every test file in that project for the `i18next` node module — with no `jest.mock('i18next', ...)` call required anywhere. Without defeating this, the suite would have silently proven nothing about the real singleton, regardless of never writing an explicit `jest.mock('i18next', ...)` line itself — a level further back than the exact CR-01 blind spot this plan's objective describes.
- **Fix:** Added `jest.unmock('i18next')` at the top of the test file — restores default (real) module resolution; it is not a substitution, so it does not violate the "never mock i18next" invariant test 2 guards.
- **Files modified:** src/backend/sidecar/__tests__/bootstrapWirings.test.ts
- **Verification:** After the fix, `i18nextInstance` exposes `.use`/`.init`/`.isInitialized`/`.t` matching a plain-Node standalone reproduction of the real package; test 1 passes
- **Committed in:** 8ad8f5e5 (Task 3 commit)

**3. [Rule 1 - Bug] `afterAll` tmp-directory cleanup crashed the whole Node test process**
- **Found during:** Task 3 (repeated full-suite runs)
- **Issue:** The plan's literal instruction ("Clean up the tmp home directory in afterAll with rmSync") reproducibly crashed the entire Node process with an uncaught `ENOENT`/`ENOTDIR`. `initLogger()` (real, run once per isolated `init()` call in this suite) queues its own log writes fire-and-forget — no caller in this codebase `await`s a `logXXX()` call — so a write could still be in-flight, mid-`mkdir`, when `afterAll`'s `rmSync` deleted the directory tree out from under it, producing an unhandled rejection outside any single test's scope.
- **Fix:** Removed the `rmSync` from `afterAll`, following `steamAuthFlows.test.ts`'s own established precedent (that suite also redirects `os.homedir()` to a disposable tmp directory and drives the real sidecar, and also performs no explicit cleanup). Per-test directory uniqueness (`mockTestHomeSuffix`) already prevents cross-test contamination without needing a delete step.
- **Files modified:** src/backend/sidecar/__tests__/bootstrapWirings.test.ts
- **Verification:** 5 consecutive full-suite runs (`npx jest bootstrapWirings.test.ts`) all report `Test Suites: 1 passed` with process exit code 0 and no unhandled-rejection crash
- **Committed in:** 8ad8f5e5 (Task 3 commit)

## Issues Encountered
- The idempotency test's literal acceptance criterion ("`backendEvents.listenerCount('releasesInfoReady')` is exactly 1") does not hold against the real, unmocked `./handlers` import graph, because `backend/tools/dxmt.ts` and `backend/wine/manager/ipc_handler.ts` also register their own legitimate `releasesInfoReady` listeners at module scope. Resolved by measuring `.on()` call count via `jest.spyOn` from the point the harness returns control (after those other modules have already registered), rather than the raw absolute listener count — this preserves the test's actual intent (no duplicate registration across repeated `init()` calls) without being coupled to unrelated features.
