# Phase 34.2: Tauri IPC re-plumb slice 5 — game details, settings and overrides - Research

**Researched:** 2026-07-25
**Domain:** Electron→Tauri sidecar IPC porting (internal refactor, zero new external dependencies)
**Confidence:** HIGH

## Summary

This is the fifth of five IPC re-plumb slices (34.1–34.5) splitting the Phase 35 Electron
cutover. Slice 5 ports 26 channels covering per-game info/settings/overrides, SDL selection,
launch options, install-path changes, version pinning, repair/kill, and six enrichment surfaces
(wiki game info, anticheat status, known fixes, CrossOver index, store search, recent games).

The phase's own `34.2-CONTEXT.md` (gathered during `/gsd-discuss-phase`, ~32KB, 11 lettered
decisions D-01..D-11) is unusually complete: every claim in it was cross-checked against the
live source tree during this research session and **every file:line citation verified exactly**
(see `## Code Examples` and the per-decision verification notes below) — no drift found. This
RESEARCH.md's job is therefore narrower than usual: confirm CONTEXT.md's claims against the real
code (done), mine the four prior slices (30/31/32/34.1) for the porting recipe and validate it
still applies, and answer the six research questions the orchestrator posed, especially the
send-channel silent-failure risk and the wave decomposition.

**The headline finding, unchanged from CONTEXT.md but worth restating plainly: this slice's real
difficulty is not the 26 channels — it is two startup wirings the sidecar never runs** (i18next
init, `fetchLastestReleases()`), both of which are **already-shipped defects** silently degrading
Phases 30 and 32's code today, and both of which this slice's channels are the first to expose
and require fixing for honest behavior. A planner that treats this as "26 mechanical
delegations" has under-scoped it.

**Primary recommendation:** Follow the D-03 extraction pattern from Phase 34.1 (`main.ts` handler
bodies → `src/backend/appshell/*.ts`-shaped Electron-free modules, `main.ts` reduced to one-line
delegations, new curated `src/backend/sidecar/gameDetailsFlowRegistration.ts`-shaped registration
module) verbatim for the 19 `main.ts`-hosted channels; import the 4 already-clean feature-module
exports (anticheat/wiki/recent/storeSearch) directly, never their `ipc_handler.ts` files; land
the two bootstrap wirings (D-02, D-07) in their own wave *before* the channels that depend on
them (`repair`, `getAnticheatInfo`); and give the three `send`-kind channels
(`addNewApp`/`setGameMetadataOverride`/`changeGameVersionPinnedStatus`) positive-side-effect
tests, not absence-of-marker tests.

## Architectural Responsibility Map

| Capability | Primary Tier | Secondary Tier | Rationale |
|------------|-------------|----------------|-----------|
| Per-game info/settings/overrides read (`getGameInfo`, `getExtraInfo`, `getGameSettings`, `getGameMetadataOverride`, `getAllGameOverrides`) | Backend (sidecar) | Database/Storage (`electron-store`/`gameOverridesStore`) | Pure reads dispatched through `libraryManagerMap[runner]`; storage already lives in an already-registered sidecar store |
| Per-game write (`setGameMetadataOverride`, `changeInstallPath`, `changeGameVersionPinnedStatus`, `setCyberpunkModConfig`, `addNewApp`) | Backend (sidecar) | Database/Storage | Mutates `electron-store`-backed state or manager in-memory state; must explicitly persist (established project gotcha) |
| Destructive/action (`repair`, `kill`) | Backend (sidecar) | — | Calls into `libraryManagerMap[runner]`'s process-control surface (`repair()`, `stop()`) + the already-ported abort-controller/launch halves |
| Enrichment/external (`getWikiGameInfo`, `getAnticheatInfo`, `getCrossoverIndex`, `searchStores`, `getStoreSearchDeals`, `getStoreSearchStoreMap`) | Backend (sidecar) | External network (GitHub raw, CheapShark API, ProtonDB/PCGamingWiki/etc.) | Network-fetching + locally cached; sidecar owns the fetch and cache, external services are unauthenticated read-only APIs |
| Bootstrap wirings (i18next init, `fetchLastestReleases()`) | Backend (sidecar bootstrap) | — | Process-lifecycle concern, not a channel; must complete before dependent handlers can behave honestly |
| Rust shell | — | — | **No new Rust code this slice**, except one string added to an existing array (`LONG_RUNNING_CHANNELS`, D-10) — zero new `dispatch_rust_channel` arms expected |

No capability in this slice belongs in the Browser/Client, Frontend-Server(SSR), or CDN/Static
tiers — this is purely a backend-process (sidecar) porting slice, consistent with every prior
34.x slice.

### Pattern 1: Extraction-to-enable-a-port (D-03/D-05/D-06)

**What:** Move a handler body from a file the sidecar can't import (`main.ts`, `launcher.ts`,
`crossover_index/ipc_handler.ts`) into a plain, Electron-free exported function in a new sibling
module; the origin file keeps a one-line delegation.
**When to use:** Every one of this slice's `main.ts`-hosted channels, plus `readKnownFixes` and
`buildCrossoverRatingMap`.
**Example (verbatim from `main.ts:988-995`, `readConfig` — the extraction target, unmodified body):**
```typescript
// Source: src/backend/main.ts:988-995 (verified during this research session)
addHandler('readConfig', async (event, configClass) => {
  if (configClass === 'library') {
    await libraryManagerMap['legendary'].refresh()
    return libraryManagerMap['legendary'].getListOfGames()
  }
  const userInfo = LegendaryUser.getUserInfo()
  return userInfo?.displayName ?? ''
})
```
Extract the closure body as `export async function readConfig(configClass: ...): Promise<...> { ... }`
in the new module; `main.ts` becomes `addHandler('readConfig', async (event, configClass) => readConfig(configClass))`.

### Pattern 2: Curated sidecar registration (D-03's registration half)

**What:** A new `src/backend/sidecar/gameDetailsFlowRegistration.ts` (name is planner discretion)
importing only the extracted functions it needs, registering them on `electronStub`'s `ipcMain`
directly (never `backend/ipc`'s typed `addHandler`), called once from `handlers.ts`.
**Example (verbatim shape, source: `src/backend/sidecar/appShellFlowRegistration.ts`, confirmed
to exist and match this shape — Phase 34.1):**
```typescript
import { ipcMain } from './electronStub'
import { getGameInfo, getExtraInfo, /* ... */ } from '../gamedetails/dispatch'

export function registerGameDetailsFlows(): void {
  ipcMain.handle('getGameInfo', async (_event: unknown, appName: unknown, runner: unknown) =>
    getGameInfo(appName as string, runner as Runner)
  )
  // send/listener kind — getting handle vs on WRONG fails 100% silently at
  // runtime (Phase 31 Pitfall 2, restated in every *FlowRegistration.ts module
  // this project has). Cross-check against main.ts's addHandler (invoke) vs
  // addListener (send) BEFORE writing each line.
  ipcMain.on('setGameMetadataOverride', (_event: unknown, ...args: unknown[]) => {
    setGameMetadataOverride(args[0] as MetadataOverrideArgs)
  })
}
```
Registration entrypoint (verified shape, `handlers.ts:67-87`):
```typescript
import { registerGameDetailsFlows } from './gameDetailsFlowRegistration'
// ... alongside the existing six register*Flows() calls, before ensureStoresRegistered() ...
registerGameDetailsFlows()
```

### Pattern 3: Bootstrap wiring with ordering discipline (D-02/D-07)

**What:** A new initialization call in `bootstrap.ts`'s `init()`, guarded the same way
`initOnlineMonitor()` already is (idempotent-guard boolean, since `bootstrap.test.ts` /
`*Flows.test.ts` call `init()` many times per file with fresh streams).
**Verified ordering constraint (source: `bootstrap.ts:112-126`, read in full this session):**
`initOnlineMonitor()` must run AFTER `startRpcServer()`/`bindTransport()` (so its immediate push
has a live transport) and BEFORE `READY_SENTINEL` is written. D-07's `fetchLastestReleases()`
must run AFTER `initOnlineMonitor()` specifically, because it depends on `runOnceWhenOnline`'s
online-status machinery being live.
```typescript
// src/backend/sidecar/bootstrap.ts — pattern to add (verified against real file structure)
import { fetchLastestReleases } from '../utils/releases'
// ... i18next import + init call, mirroring main.ts:460-472 ...

let releasesFetchInitialized = false
// (mirrors onlineMonitorInitialized's existing idempotent-guard shape, bootstrap.ts:93)

export function init(...): void {
  // ... existing steps ...
  if (!onlineMonitorInitialized) {
    initOnlineMonitor()
    onlineMonitorInitialized = true
  }
  if (!releasesFetchInitialized) {
    fetchLastestReleases()  // D-07 — AFTER initOnlineMonitor()
    releasesFetchInitialized = true
  }
  output.write(`${READY_SENTINEL}\n`)
}
```

### Anti-Patterns to Avoid

- **Mocking i18next (or `fetchLastestReleases`) away in the new tests.** Phase 34.1's own
  code-review CR-01 finding (verified: `34.1-REVIEW.md`) was invisible to its test suite
  *specifically because* the test mocked the exact call that was broken
  (`jest.mock('i18next', () => ({ changeLanguage: jest.fn()... }))`). D-02's fix cannot be proven
  by a test that takes the same shortcut — at least one test in this slice must exercise the

## Common Pitfalls

### Pitfall 1: i18next silently returns `undefined`, not a thrown error

**What goes wrong:** Calling `i18next.t(key, fallback)` on the uninitialized sidecar singleton
returns `undefined` — not the fallback string, not a throw. `repair`'s `notify()` calls
(`main.ts:1150`, `1154`) would ship `{ title, body: undefined }` under Tauri without D-02.
**Why it happens:** i18next's `changeLanguage`/`init` machinery sets internal state that `.t()`
depends on; without `init()` ever being called, that state doesn't exist, and the library's
error-handling path for that case is "return undefined" rather than "throw" for `.t()`
specifically (it DOES throw for `.changeLanguage()`, which is why Phase 34.1's CR-01 caught the
`changeLanguage` half but not the `.t()` half — verified against installed i18next 22.5.1).
**How to avoid:** D-02, land it first, and test it without mocking i18next.
**Warning signs:** A notification shows a blank body under Tauri; a jest test that mocks
`i18next` entirely will never surface this.

### Pitfall 2: `send`-kind channels fail with zero signal on a registration mistake

**What goes wrong:** A channel registered `addListener` in `main.ts` (fire-and-forget) but
mistakenly registered `ipcMain.handle` in the sidecar (or vice versa) does not error, does not
time out, and does not log — the frontend's call simply has no effect.
**Why it happens:** `ipcMain.handle`/`.on` and the renderer's `invoke`/`send` factories are
separate code paths with no cross-checking; a `send`-registered-as-`handle` (or vice versa) is a
type error the transport layer doesn't catch.
**How to avoid:** This slice has exactly 3 `send`-kind channels (verified via direct source read):
`addNewApp` (`main.ts:1526`, `addListener`), `setGameMetadataOverride` (`main.ts:1530`,
`addListener`), `changeGameVersionPinnedStatus` (`main.ts:1611`, `addListener`). The other 23 are
`addHandler` (invoke-kind), including — notably — `setCyberpunkModConfig` and `repair`, which
"feel" like they should be fire-and-forget but are actually `addHandler` in the real source.
Cross-check every channel's kind against `main.ts` before writing the registration line; never
assume from the channel's name/semantics.
**Warning signs:** A frontend action (e.g. "add non-Steam game") appears to do nothing under
Tauri, with no error anywhere.

### Pitfall 3: absence of `UNPORTED_CHANNEL_MARKER` proves nothing for `send` channels

**What goes wrong:** `invoke`-kind unported channels reject with `UNPORTED_CHANNEL_MARKER` and a
60s timeout (Invariant B) — an unambiguous "not ported" signal. `send`-kind channels have no such
signal by construction (fire-and-forget, no response frame) — an unported `send` channel and a
correctly-ported-but-buggy `send` channel look identical from the outside: nothing happens.
**Why it happens:** established project finding (see `sidecar-send-channels-fail-silently` in
prior project history) — this is not new to this slice, but this slice is the first to carry 3
such channels since Phase 32.
**How to avoid:** every `send`-kind channel in this slice needs a **positive-side-effect** test —
assert the actual state change (store write persisted, manager list grew, config value flipped),
never merely "the call didn't throw" or "no marker appeared."
**Warning signs:** A test suite that is 100% green while a `send` channel does nothing in
production — exactly the failure class this project has already hit once (G-30-01, `logoutSteam`).

### Pitfall 4: Steam-runner stubs are correct behavior to port, not bugs to fix

**What goes wrong:** A planner or reviewer sees `SteamGame.repair()` log "not implemented until
Phase 2" and assumes the port is incomplete or wrong.
**Why it happens:** the stub predates this phase (Phase 2/3 scaffolding) and is Electron's own
existing behavior — verified identical in the current `main` branch, not something Tauri makes
worse.
**How to avoid:** port the dispatch verbatim (D-01); declare the three known Steam-runner stubs
explicitly in `34.2-PORTED-CHANNELS.md` (`repair`, `changeVersionPinnedStatus`, `getLaunchOptions`)
so a later reader doesn't misdiagnose them as this phase's regression.
**Warning signs:** A gap-cycle plan gets opened to "fix Steam repair" when the real work is
already out of scope for this phase (tracked separately as future Steam-repair work, not a 34.2 gap).

### Pitfall 5: mocking away the exact thing D-02/D-07 fix hides the fix

**What goes wrong:** Following the existing `*Flows.test.ts` harness convention exactly (which
mocks most external dependencies) for `repair` or `getAnticheatInfo` tests would mock `i18next`
or `fetchLastestReleases`/`backendEvents`, silently re-creating Phase 34.1's CR-01 blind spot.
**Why it happens:** the harness convention (mock `os`/`electron`/`electron-store`, keep the real
handler logic) is correct for most channels, but D-02/D-07 are exactly the two places where "keep
the real logic, mock the environment" needs to include the environment piece under test.
**How to avoid:** at least one test per bootstrap wiring must run the REAL `i18next.init()` /
REAL `fetchLastestReleases()` → `backendEvents.emit()` path, not a mock.
**Warning signs:** 100% green tests, D-02/D-07 code present, but the underlying defect (verified
present today) still reproduces in a live `pnpm tauri:dev` boot.
