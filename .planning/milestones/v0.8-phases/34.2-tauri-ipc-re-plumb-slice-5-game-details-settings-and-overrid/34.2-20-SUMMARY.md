**Call-site `.catch()` on the sidecar's `logError` send listener, with a module-attributed stderr diagnostic, restoring `processGuards.ts`'s "not a substitute for call-site handling" invariant that WR-02 found violated.**

## Accomplishments

- `loggerFlowRegistration.ts`'s `logError` listener now normalises its call to `logError(...)`
  via `Promise.resolve(...)` and attaches a `.catch()` at the call site, so a real log-write
  failure (EACCES/ENOSPC/deleted log directory) is handled where it happens instead of leaning
  on `processGuards.ts`'s generic, defence-in-depth `unhandledRejection` absorption — which its
  own docstring explicitly forbids being relied on as the primary handler.
- The `.catch` handler mirrors `processGuards.ts`'s own documented CR-02 discipline: a hardcoded
  fallback literal initialised before its own `try`, reassigned inside that `try`; the stderr
  write is wrapped in its own swallowing `try`/`catch`; never rethrows, never exits, never
  touches stdout (the RPC frame transport).
- Dropped the `args[0] as string` assertion (review finding IN-05) — the declared transport
  contract (`src/common/types/ipc.ts:106`) is `logError: (message: unknown) => void`, and
  `LogWriter#logError` already accepts `unknown`.
- 4 new tests in `loggerFlows.test.ts` (WR-02 Test A-D) drive a REJECTING `backend/logger`
  `logError` spy through the real registered listener over the real sidecar RPC transport and
  assert the diagnostic carries the call-site prefix while explicitly NOT containing
  `processGuards.ts`'s generic `unhandled promise rejection` text — the load-bearing negative
  assertion that makes this proof fail against pre-fix code (unlike a positive-only "some
  diagnostic appeared" assertion, which would pass identically pre-fix since the process guard
  already produces a diagnostic).
- RED-PROOF performed by hand (not merely asserted): the pre-fix version of
  `loggerFlowRegistration.ts` was restored via `git show HEAD~1:... > file`, the suite re-run,
  and all 4 new tests failed; the fixed version was restored via `git checkout HEAD -- file`,
  confirmed byte-identical via `git diff --stat` (empty), and the suite re-run green.

## Decisions Made

- `Promise.resolve(logError(...)).catch(...)` rather than `await`, because `ipcMain.on`
  listener bodies must remain synchronous (per `dispatchSend`'s contract and the existing
  `processGuards.ts` precedent for this same discipline).
- Test mocks use `jest.spyOn(logger, 'logError').mockImplementation(() => Promise.reject(...))`
  rather than `.mockReturnValue(Promise.reject(...))`: `logger.logError`'s declared TypeScript
  return type is `void` (see Issues Encountered below), and `mockReturnValue`'s argument type is
  pinned to that declared return type, while `mockImplementation` accepts an implementation
  function whose return type can differ from `void` under TypeScript's void-return
  assignability rule.
- Non-Error rejection reasons in Tests B/C/D use targeted `as Error`/`as unknown as Error` casts
  to satisfy `@typescript-eslint/prefer-promise-reject-errors` without disabling the rule
  project-wide — the whole point of these tests is exercising non-Error rejection reasons, so a
  local, deliberate cast (not a rule suppression) documents that clearly.

### Discovery Logged (not auto-fixed — out of scope)

**`backend/logger/index.ts`'s four exported wrappers discard their writer's promise.**
`logDebug`/`logInfo`/`logWarning`/`logError` in `src/backend/logger/index.ts:16-27` are all
block-body arrow functions with no `return` statement, so each always synchronously returns
`undefined` at runtime — never the `Promise<void>` that `LogWriter`'s corresponding method
(`log_writer.ts:159-173`) actually produces. This plan's own `<interfaces>` context section
claimed `logError(...)` "returns `heroicLogWriter.logError(...)`" — that claim is currently
false against the real source. Practical effect: today, a real on-disk log-write failure's
rejection is dropped one level further back, inside `logger/index.ts` itself, before this
plan's new `.catch()` at the `loggerFlowRegistration.ts` call site could ever observe it (Task
1's guard is still correct and necessary — it becomes fully load-bearing the moment a future fix
makes the wrapper actually return the promise, and is harmless/no-op until then). Task 2's test
suite is unaffected because it `jest.spyOn`-overrides the exported `logError` function directly,
bypassing the wrapper's real body. Logged to `deferred-items.md` under "From plan 34.2-20"
rather than fixed here: touching `logger/index.ts` would change behavior for all four wrapper
exports project-wide (a much wider blast radius than this plan's declared
`loggerFlowRegistration.ts` + its test), which is exactly the kind of shared-module structural
change Rule 4 reserves for an explicit, separately-scoped decision.

## Issues Encountered

- TypeScript rejected the test file's initial `jest.spyOn(logger, 'logError').mockReturnValue(
  Promise.reject(...))` calls (`TS2345: Argument of type 'Promise<never>' is not assignable to
  parameter of type 'void'`), because `logger.logError`'s declared return type is `void` (see
  Decisions Made and the logged discovery above for why). Switched all 4 occurrences to
  `.mockImplementation(() => Promise.reject(...))`, which TypeScript accepts under its
  void-return assignability rule; re-verified `npx tsc --noEmit` clean and all 9 tests still
  green, then re-ran the full RED-PROOF against the corrected test file to confirm it still
  failed as expected pre-fix.
- `@typescript-eslint/prefer-promise-reject-errors` flagged the intentionally non-Error rejection
  reasons in Tests B/C/D (the whole point of those tests is hostile, non-Error rejection shapes).
  Resolved with local `as Error`/`as unknown as Error` casts at each site rather than a rule
  suppression, since the cast is honest about what's happening (a deliberately-non-Error value
  being passed to `Promise.reject` for test purposes) without weakening the rule elsewhere.
