## Decisions Made

1. **Task 1's literal RED-spot-check acceptance criterion did not reproduce as written.** The plan's acceptance criterion said removing the `pathShim` mock and exporting `XDG_CONFIG_HOME` to a value outside `os.tmpdir()` would make the tripwire fail "on this machine." Verified live: it does NOT fail on this macOS host, because `pathShim.ts`'s real `resolveAppDataDir()` switches on `process.platform` (real `'darwin'` here) and the `darwin` case reads only `homedir()` — never any of the four env vars — and `homedir()` is already safely redirected by the suite's own `os` mock. Substituted this repo's own established negative-control method from plan 34.2-10 instead (point the mock's own `'appData'` branch to a sentinel path outside `tmpdir()` directly) — this reproduces genuinely on any host and matches precedent (`34.2-10-SUMMARY.md`'s "temporarily pointing the mock's 'appData' branch outside tmpdir"). Both the pathShim-mock and logger/paths-mock negative controls were run this way, live, and reverted clean (all 11 tests failed with "REFUSING TO RUN", then passed again).
2. **Block A required forcing `process.platform`, not just the four env vars, to be genuine evidence.** For the same reason as decision 1 — real Windows/Linux resolution logic in `pathShim.ts`/`logger/paths.ts` is gated on `process.platform`, which the plan's four named env vars do not affect on a real macOS host. Added `Object.defineProperty(process, 'platform', { value: 'linux', configurable: true })` in Block A's `beforeAll`, restored in `afterAll`, mirroring this repo's own established `overrideProcessPlatform` helper in `src/backend/__tests__/constants.test.ts`. Documented explicitly in the suite's own docstring and inline comments so this isn't mistaken for scope creep.
3. **Replaced `sidecarRejectionGuard.test.ts`'s tripwire data source.** The plan flagged IN-03 (the tripwire calling the full `setupIsolatedBootstrapHarness()` — building the entire bootstrap graph and leaving an unrestored spy — just to read `appFolder`) and left it to plan-time discretion whether this could be cleanly replaced. It could: added a narrower `loadConstantsPaths()` helper using `jest.isolateModules(() => require('../../constants/paths'))`, and removed the now-unused `appFolder` field from `setupIsolatedBootstrapHarness()`'s return type (verified unused by Group 1's tests).
