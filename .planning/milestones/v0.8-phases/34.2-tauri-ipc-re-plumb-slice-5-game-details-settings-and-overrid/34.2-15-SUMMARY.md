# Phase 34.2 Plan 15: Harden installUnhandledRejectionGuard against hostile rejection reasons Summary

Moved `processGuards.ts`'s `String(reason)` message construction inside its own `try`/`catch`
with a hardcoded, non-interpolated fallback literal, closing gap-cycle-1's CR-02 regression
(a rejection reason with a null prototype or a throwing `toString`/`Symbol.toPrimitive` could
crash the whole sidecar via an escalated `uncaughtException`), and proved the fix with three new
hostile-reason tests.

## What Was Built

### Task 1 — `src/backend/sidecar/processGuards.ts`

The `target.on('unhandledRejection', ...)` listener body previously built its log message with
`const message = \`[sidecar] unhandled promise rejection: ${String(reason)}\`` **outside** any
try block — only the subsequent `logWarning(message, ...)` call was wrapped. `String(reason)`
throws `TypeError: Cannot convert object to primitive value` for a null-prototype object or an
object whose `toString`/`Symbol.toPrimitive` throws or is absent; a throw from a
`process.on('unhandledRejection')` listener escalates into an `uncaughtException` with no
handler installed anywhere in the sidecar, killing the process — precisely the crash class this
module exists to prevent, reintroduced by the guard.

Fixed shape (matching the review's CR-02 fix snippet exactly):

```ts
target.on('unhandledRejection', (reason: unknown) => {
  let message = '[sidecar] unhandled promise rejection: <unstringifiable reason>'
  try {
    message = `[sidecar] unhandled promise rejection: ${
      reason instanceof Error ? (reason.stack ?? reason.message) : String(reason)
    }`
  } catch {
    // keep the fallback message
  }
  try {
    logWarning(message, LogPrefix.Backend)
  } catch {
    try {
      process.stderr.write(`${message}\n`)
    } catch {
      // Nothing further we can safely do -- swallow. Never re-throw, never exit.
    }
  }
})
```

Only one statement now sits outside a `try`: the `let message = <hardcoded literal>`
declaration, which cannot itself throw. No `process.on('uncaughtException')` handler was added
(explicitly out of scope per the plan — that would mask real crashes rather than harden this
narrow path).

The module docstring (lines 16-40) was corrected: it previously claimed only the logging call
was wrapped in a try/catch. It now states plainly that **both** message construction and logging
are individually wrapped, names the CR-02 regression and gap cycle 2 by ID, and explains why the
fallback literal is non-interpolated (so it can never itself fail to produce a string).

### Task 2 — `src/backend/sidecar/__tests__/sidecarRejectionGuard.test.ts`

Added three cases to `Group 2: installUnhandledRejectionGuard contract`, each driving a fresh
`EventEmitter` (never the real `process`) via `loadFreshProcessGuards()`:

1. `Object.create(null)` reason — asserts `emit()` does not throw and `logWarningMock` was
   called with the **exact** fallback string
   `'[sidecar] unhandled promise rejection: <unstringifiable reason>'` (via `toHaveBeenCalledWith`
   on the literal, not `stringContaining`, so the assertion cannot pass vacuously against the
   interpolated form).
2. A reason object whose `toString` property throws — same assertions.
3. A reason object whose `[Symbol.toPrimitive]` throws — same assertions.

Group 2 grew from 4 cases to 7 (11 total in the file, up from 8).
