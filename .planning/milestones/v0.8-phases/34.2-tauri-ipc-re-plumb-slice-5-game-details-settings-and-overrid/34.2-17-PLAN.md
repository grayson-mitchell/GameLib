Close the renderer half of **verification gap #1 (GAP-CYCLE-1 CR-01, REQ-34.2-12)**. The gap's third
`missing:` item: *"Surface user-facing feedback (dialog/toast) on repair failure — today the repair
dialog just closes with nothing else happening on either build."*

`GameSubMenu/index.tsx:143-149`'s catch calls only `window.api.logError`. Under Tauri that is a
silent no-op today (plan 34.2-16 fixes the channel), and on BOTH builds the user sees the repair
confirmation dialog close and nothing else happen. This plan gives the failure three independent
signals with different failure modes — a console line that no IPC transport can swallow, the log
channel, and a dialog the user actually sees — so no single broken layer can reproduce the
zero-signal state the verifier found.

The handler body is extracted into its own module so it can be unit-tested directly. `GamesSubmenu`
itself carries a dozen `useState`/`useEffect` hooks and cannot be invoked as a plain function the way
`MainButton.steamIncomplete.test.tsx` invokes its component, and a source-text gate over the catch
block would be exactly the "passes if the fix is reverted" class this gap cycle exists to eliminate.
Extraction-with-a-one-line-delegation is this phase's own established shape (D-03).

Purpose: a repair failure a human can see. Output: `repairFailure.ts`, its unit test, the rewired
call site, and two English source strings.

| Threat ID | Category | Component | Disposition | Mitigation Plan |

| T-34.2-52 | Information disclosure | ERROR dialog message | mitigate | The dialog renders a FIXED translated string only; raw error text goes to console/log (local, already carrying that data class).
