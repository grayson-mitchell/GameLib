  Both flags STAY. `tauri-action` uploads `latest.json` (plus the per-platform installers) as
  assets of the release it creates at tag `v<version>`.

GitHub asset-URL semantics (the whole basis of this fix):
  - `/releases/latest/download/<asset>`  -> redirects to the newest NON-prerelease, NON-draft
    release. Permanently 404s for a prerelease-only pipeline. THIS IS THE BUG.
  - `/releases/download/<tag>/<asset>`   -> resolves for ANY published release at that tag,
    including prereleases. Only DRAFT releases' assets are non-public.
  => a fixed tag (`updater`) whose release is published-and-prerelease serves the feed while
     never becoming GitHub "Latest".

Tauri updater trust model (why relocating the asset is signature-neutral):
  `latest.json` carries a per-platform `signature` field (minisign/Ed25519, produced by
  tauri-action from TAURI_SIGNING_PRIVATE_KEY). `tauri-plugin-updater` verifies it client-side
  against the `pubkey` committed in tauri.conf.json BEFORE installing. Copying the file to a
  different URL changes nothing about that verification; a substituted feed still fails.
  The promotion workflow must therefore NEVER regenerate or edit latest.json, and must never be
  given TAURI_SIGNING_PRIVATE_KEY.

Why promotion must happen AFTER publish, not during the build:
  latest.json's per-platform `url` fields point at the versioned release's own installer assets.
  While that release is a draft those assets are not publicly downloadable. Promoting only on
  `release: published` therefore fixes two things at once — it preserves D-09's human gate AND
  guarantees the URLs inside the manifest resolve by the time the updater reads it.

Workflow-loop safety:
  `gh release create updater` will itself emit a `release: published` event. Two independent
  guards: (a) the promotion job is gated on `startsWith(github.event.release.tag_name, 'v')`, and
  the feed-holder tag is `updater`; (b) GitHub does not trigger workflow runs from events created
  with the default `GITHUB_TOKEN`.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| GitHub Releases -> installed app (updater) | `latest.json` is fetched over the network by every installed client and drives an installer download+execute |
| Published release assets -> feed-holder release assets | The promotion workflow copies an artifact across releases inside the same repo |
| GitHub Actions token -> release contents | `contents: write` lets the promotion job create/modify a release |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-34-23 | Spoofing | Relocated updater feed at `/releases/download/updater/latest.json` | mitigate | The trust anchor is unchanged and unweakened: `latest.json`'s per-platform minisign (Ed25519) `signature` is verified client-side by `tauri-plugin-updater` against the `pubkey` committed in `tauri.conf.json` before any installer is executed. The promotion workflow copies the manifest byte-for-byte and holds NO signing key — asserted by the criterion `grep -c "TAURI_SIGNING"` prints `0` and by the comment-stripped no-`jq`/no-`sed`/no-redirect test. A swapped or edited feed at the new URL cannot produce a valid signature. |
| T-34-24 | Tampering | Manifest rewriting during promotion | mitigate | No step transforms the file; a `sha256sum` audit line is logged so any future edit is visible in the run log. Test 7 blocks the introduction of a rewriting step. |
| T-34-25 | Elevation of privilege | Premature exposure of an unreviewed build to all users | mitigate | Promotion is bound to `release: types: [published]` only. A draft (which is what the pipeline creates) never fires that event, so D-09's human-review gate is structurally preserved rather than merely documented. `latest.json`'s inner installer URLs also only resolve post-publish, so a leaked manifest would be inert. |
| T-34-26 | Denial of service | Workflow self-retrigger loop via `gh release create updater` | mitigate | Two independent guards: the job-level `startsWith(github.event.release.tag_name, 'v')` condition (the feed-holder tag is `updater`, not `v*`), and GitHub's rule that events created with the default `GITHUB_TOKEN` do not trigger workflow runs. A `concurrency` group additionally serializes overlapping publishes. |
| T-34-27 | Information disclosure | Promotion job's credential surface | mitigate | The job declares only `GH_TOKEN: ${{ github.token }}` with `permissions: contents: write`; no `APPLE_*`, `WINDOWS_*`, or `TAURI_SIGNING_*` secret is referenced, so a compromised step in this workflow cannot reach code-signing or update-signing material. |
| T-34-28 | Repudiation | Which build the feed currently serves | mitigate | The promotion run logs the source tag and the manifest SHA-256, giving an auditable record linking each feed state to the release it came from. |
| T-34-SC | Tampering | npm/pip/cargo installs | n/a — accept | This plan adds NO package-manager install task and makes NO `package.json`/lockfile change. The Package Legitimacy Gate is not triggered. |
</threat_model>
