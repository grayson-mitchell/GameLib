hardcodes `POSTJECT_BIN`/`ESBUILD_BIN` as `join('node_modules', '.bin', ...)` and spawns them via
`spawnArgv()` with no `shell: true`. On Windows, pnpm materialises those as a POSIX shell shim plus
`.CMD`/`.ps1` siblings; `spawn()` with an explicit extensionless relative path performs no PATHEXT
resolution, so `CreateProcess` fails before either tool runs.

Purpose: the `windows-latest` leg dies inside `pnpm build:sidecar-sea` and never reaches
`tauri-action`, which makes 34-11's `sidecar_triple: 'x86_64-pc-windows-msvc'` matrix wiring
unreachable in practice. No Windows installer can be produced at all.

Output: `resolveEsbuildCli()`/`resolvePostjectCli()` that resolve the real CLI **modules** and
argv-builders that return `process.execPath` as the command, consumed by the real call sites so
the tested value IS the executed value (closes the WR-10 "tests assert argv the build never
executes" family for postject).

This plan is a **prerequisite** to resuming 34-07's deferred live gate. It does not re-own it.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Build script -> spawned child process | `spawnArgv()` constructs the argv for esbuild/postject; a shell-string or PATH-resolved form would let cwd/PATH contents influence what executes |
| node_modules tree -> build output | The resolved CLI modules are compiled into the shipped sidecar binary's toolchain path |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-34-19 | Tampering | `spawnArgv()` argv construction in `bundleForSea`/`injectBlob` | mitigate | Argv-form spawn is preserved verbatim (T-24-06): `command` + `args: string[]`, never an interpolated shell string, and `shell: true` is never introduced. The CLI path enters as a discrete `args[0]` element, so no path content can be reinterpreted as shell syntax. Asserted by the acceptance criterion `grep -c "shell: true"` prints `0`. |
| T-34-20 | Elevation of privilege | Tool lookup via a relative `node_modules/.bin` path | mitigate | `require.resolve` resolves against the installed, lockfile-pinned module tree and returns an absolute path, removing any dependence on process `cwd`, on `PATH` ordering, or on a shim file an attacker could drop into a `.bin` directory earlier in lookup order. `process.execPath` is the already-running interpreter, not a name looked up in `PATH`. |
| T-34-21 | Tampering | SEA bundle flags (`--alias:electron`, `--inject:sidecarSeaFsShim`, no `--packages=external`) | mitigate | The flags move into `buildEsbuildArgv()` unchanged and are asserted element-by-element by Task 1 test 5, so a future edit cannot silently drop the electron-stub alias (which would reintroduce the documented `ERR_UNKNOWN_BUILTIN_MODULE` startup crash) without failing the suite. |
| T-34-22 | Denial of service | Unresolvable esbuild/postject module | mitigate | Resolution failure throws a labelled `COMPILE GATE FAILED (D-06/CR-02)` error naming the specifier, instead of surfacing as an opaque `spawn ENOENT` late in the build — the fail-loud discipline from `buildSteamBridgeShims.ts::compileShim()`. |
| T-34-SC | Tampering | npm/pip/cargo installs | n/a — accept | This plan adds NO package-manager install task and makes NO `package.json`/lockfile change. `postject@1.0.0-alpha.6` and `esbuild` are already installed and already invoked by six existing npm scripts; only the invocation FORM changes. The Package Legitimacy Gate is not triggered. |
</threat_model>
