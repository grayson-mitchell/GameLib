# Phase 34.1: Tauri IPC re-plumb slice 4 — app shell and window chrome - Research

**Researched:** 2026-07-25
**Domain:** Tauri v2 window/tray/webview-window APIs, Electron `main.ts` handler extraction, sidecar curated-module porting
**Confidence:** HIGH for the mandatory D-04 capability verification and the D-01 renderer-side API surface (verified directly against the installed crate/package source on disk); MEDIUM-HIGH for D-07/D-08 extraction shape and D-10 gamepad mapping (derived from direct source reading, some judgment calls flagged); MEDIUM for D-11 tray and D-12 WebviewWindow (verified API surface, but scope/UX calls are explicitly left to the planner); LOW/ASSUMED only where explicitly marked (Linux tray system-dependency, macOS traffic-light aesthetics).

## Summary

This phase ports 33 app-shell/window-chrome channels from Electron's `main.ts`/`main_window.ts`/`tray_icon.ts` onto the Tauri build. The single most important research finding is that the mandatory D-04 capability-verification instruction resolves cleanly and in GameLib's favor: `core:window:default` in the installed Tauri crate (2.11.5) is confirmed, by reading the crate's own generated permission reference, to be a read-only/getter set — it contains none of the mutation commands (`minimize`, `maximize`, `unmaximize`, `close`, `set-fullscreen`, `set-decorations`, `start-dragging`, `toggle-maximize`) D-04 lists. Every identifier D-04 names is real and spelled correctly. The explicit per-command allow-list is therefore both necessary (default doesn't cover the mutations) and sufficient (every named identifier exists) as written — no changes needed to D-04's list itself, only to the plan's obligation to cite this proof rather than the discussing agent's recollection.

The second major finding reshapes how the planner should think about D-07/D-08 extraction: of the 28 `main.ts` handlers named in CONTEXT.md's canonical refs, exactly 10 are the D-01 renderer-side window-chrome channels (`minimizeWindow`/`maximizeWindow`/`unmaximizeWindow`/`closeWindow`/`isMaximized`/`isMinimized`/`isFullscreen`†/`setFullscreen`/`isFrameless`/`setZoomFactor`). Because D-01 moves these to the renderer with **no sidecar hop**, they do **not** need Electron-free module extraction for the sidecar's benefit at all — `main.ts`'s existing Electron bodies for these 10 can stay completely untouched. D-07/D-08's extraction work is therefore only mechanically required for the remaining ~18 sidecar-routed handlers (themes, version/changelog, tray color trigger, gamepad, new-window/about-window, connectivity, language, notify/quit/open*, lock/unlock, setTitleBarOverlay). This materially shrinks the D-07/D-08 blast radius versus a literal reading of "extract 28 handlers."

†`isFullscreen` needs its own callout: the *actual* `main.ts` implementation (`main.ts:747`) is **not** a real window-fullscreen query — it returns `isSteamDeckGameMode || isCLIFullscreen`, two Node-only environment/CLI signals (`XDG_CURRENT_DESKTOP === 'gamescope'` and `process.argv.includes('--fullscreen')`) that have no renderer-side (webview) equivalent under Tauri without new Rust work. This directly explains the Claude's-Discretion note "port the semantics as-is; do not improve it into a real window query" — and creates a genuine gap the planner must decide how to close (see Pitfall 1).

**Primary recommendation:** Implement D-01's 10 channels as `isTauri()`-branching bodies directly inside `src/preload/api/misc.ts` (mirroring the existing `storeGet`/`storeSet`/`storeNew` inline-branch pattern already in that file), calling `getCurrentWindow()` from `@tauri-apps/api/window` (bundler import, not `window.__TAURI__` global) for 9 of the 10, and `getCurrentWebview().setZoom()` from `@tauri-apps/api/webview` for the 10th (`setZoomFactor` — zoom is a **webview** API, not a window API, in Tauri v2). Scope D-07/D-08 extraction to only the 18 non-D-01 handlers. Reproduce `isFullscreen`'s env/CLI semantics honestly (hardcode both signals `false`/unreachable under Tauri, declared not silently regressed) rather than substituting a real `getCurrentWindow().isFullscreen()` call, which would change behavior.

### Pattern 1: D-01 inline `isTauri()` branch in `misc.ts` (not `ipc.ts`'s generic factory)

**What:** `src/preload/api/misc.ts` already contains a precedent for a channel needing genuinely different bodies per build: `storeGet`/`storeSet`/`storeNew`/`storeHas`/`storeDelete` each open with `if (isTauri()) { <tauri-specific> ; return }` before falling through to the Electron body. D-01's 10 channels are architecturally identical — same channel name, `window.api.<x>()`, called from the same frontend code (`GlobalState.tsx:1327-1328`, `App.tsx`), needing a completely different implementation per build with zero IPC hop under Tauri.

**When to use:** Whenever a channel needs a real (not `ipcRenderer`) implementation under Tauri while Electron keeps the existing `makeHandlerInvoker`/`makeListenerCaller` machinery.

**Example (concrete pattern to follow, adapted from the existing `storeNew` precedent at `misc.ts:97-108`):**
```typescript
// Source: src/preload/api/misc.ts (existing storeNew pattern, L97-108) + confirmed
// @tauri-apps/api/window.d.ts API surface (verified in node_modules on disk)
import { getCurrentWindow } from '@tauri-apps/api/window'
import { getCurrentWebview } from '@tauri-apps/api/webview'

export const minimizeWindow = () => {
  if (isTauri()) {
    void getCurrentWindow().minimize() // Promise<void> — fire-and-forget matches
    return                              // makeListenerCaller's existing sync signature
  }
  const { ipcRenderer } = require('electron') as typeof import('electron')
  ipcRenderer.send('minimizeWindow')
}

export const isMaximized = () => {
  if (isTauri()) {
    return getCurrentWindow().isMaximized() // already Promise<boolean> — matches
  }                                          // makeHandlerInvoker's PromiseOnce<T> contract
  const { ipcRenderer } = require('electron') as typeof import('electron')
  return ipcRenderer.invoke('isMaximized')
}

export const setZoomFactor = (zoomFactor: string) => {
  if (isTauri()) {
    // NOTE: zoom is a WEBVIEW API in Tauri v2, not a window API — different import,
    // different capability (core:webview:allow-set-webview-zoom, not core:window:*)
    void getCurrentWebview().setZoom(parseFloat(zoomFactor))
    return
  }
  const { ipcRenderer } = require('electron') as typeof import('electron')
  ipcRenderer.send('setZoomFactor', zoomFactor)
}
```
This REMOVES these 10 exports from using `makeListenerCaller('minimizeWindow')`/`makeHandlerInvoker('isMaximized')` — the generic `ipc.ts` factories stay used for every other channel, unchanged.

### Pattern 3: WebviewWindow creation (D-12)

**What:** Two viable approaches, both using already-installed `@tauri-apps/api` — no new package:
1. **JS-side** (recommended, matches D-01's renderer-owns-chrome direction, zero new Rust): `new WebviewWindow(label, options)` from `@tauri-apps/api/webviewWindow` [VERIFIED: `node_modules/@tauri-apps/api/webviewWindow.d.ts:20,43`], called from the sidecar-routed `createNewWindow`/`showAboutWindow` handler bodies — but note the sidecar is a headless Node process with no webview of its own, so `WebviewWindow` construction must happen **in the renderer** (it's a webview-side API), meaning `createNewWindow`/`showAboutWindow` may need to become D-01-style renderer-side channels too, not sidecar-routed. **This is a scope question for the planner**: CONTEXT.md places these under D-12 without explicitly saying renderer-side vs sidecar-side; the `WebviewWindow` constructor's actual location (`@tauri-apps/api/webviewWindow`, a JS-only export with no Rust command wrapper) means it can ONLY be called from a webview context (main window's renderer, or a Rust command). It cannot be called from the headless Node sidecar process.
2. **Rust-side**: `tauri::WebviewWindowBuilder::new(app, label, url).build()` inside a new `rustInvoke` arm — keeps the sidecar as the single caller (consistent with D-03's non-window-chrome-stays-sidecar principle) at the cost of one new Rust arm, which the Claude's Discretion note explicitly does NOT pre-approve for this pair (only quit/open*/notify are pre-approved as zero-new-arm reuses).

**Recommendation:** Given D-12's own text ("This is literally this slice's domain... establishing multi-window capability") and that `WebviewWindow` is structurally a webview-JS API, implement `createNewWindow`/`showAboutWindow` as **renderer-side (Tauri JS)**, the same "third kind" D-02 already establishes for window chrome — even though D-03 nominally scopes renderer-side "strictly to window chrome." Flag this as a genuine tension for the planner/discuss-phase to resolve explicitly (D-03's own wording says "everything else... keeps the sidecar seam," but the JS API surface makes a sidecar-side implementation architecturally impossible without a new Rust arm). This is the single most important open scoping question this research surfaces.

**Per-window-label capability scoping** [CITED: v2.tauri.app/security/capabilities/]: Tauri v2 capabilities' `"windows"` array supports glob patterns (the existing `default.json` uses `["main"]`; a wildcard `["*"]` form is documented). A new window label (e.g. `"about"`) needs either (a) inclusion in the existing `default.json`'s `windows` array, or (b) its own capability file scoped narrower than `main`'s. Given `default.json`'s own header comment stresses minimal-exposure ("GameLib renders untrusted remote surfaces... under Tauri there is no `<webview>` boundary"), a **separate, narrower capability** for the `about`/new-window labels (granting only what a static content window needs — likely nothing beyond `core:default`) is preferable to widening `main`'s grant surface. This directly serves D-04's own load-bearing rationale.

**`openWebviewPage` → `open_external`:** confirmed [VERIFIED: `src/backend/utils.ts:378`, `shell.openExternal(url)`] — Electron's `openUrlOrFile()` already just calls `shell.openExternal`, which the sidecar's `electronStub.ts` already forwards to the real `open_external` Tauri command (Phase 27/28). Zero new Rust work confirmed.

### Anti-Patterns to Avoid

- **Calling `getCurrentWindow().isFullscreen()` for the `isFullscreen` channel.** This changes documented behavior — the real Electron semantics are an env/CLI signal (`isSteamDeckGameMode || isCLIFullscreen`), not a window query. See Pitfall 1.
- **Registering D-01's 10 channels on the sidecar "just in case."** D-02 explicitly says the sidecar registers nothing for them — a stray registration risks silent double-implementation drift and violates D-09's curated-import minimalism for no benefit (the preload short-circuit means the sidecar handler is unreachable dead code).
- **Side-effect-importing `utils/ipc_handler.ts`** to get `abort`/`isIntelMac` (D-09 explicit warning) — it also registers slice-6/8 channels (`getLegendaryVersion`, `getSystemInfo`, `hasExecutable`), which would prematurely drag those imports into this phase's sidecar bundle.
- **Treating `changeTrayColor`/`createNewWindow`/`gamepadAction` as extraction candidates.** All three have deep, non-portable Electron closures (`Tray`/`nativeImage`, `BrowserWindow`, `Electron.MouseInputEvent`/`sendInputEvent`) — these are genuinely new Tauri-side implementations, not body moves.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Window minimize/maximize/close state | A custom sidecar-side window-state tracker | `getCurrentWindow()`'s own `isMinimized()`/`isMaximized()`/`isFullscreen()` | Tauri's `Window` object is the single source of truth for the real OS window; duplicating state in the sidecar risks drift the moment the user drags/resizes outside GameLib's own buttons |
| Tray icon lifecycle | Manual native tray bindings | Tauri's `TrayIcon`/`TrayIconBuilder` (Rust) or `@tauri-apps/api/tray` (JS) | Already a first-class, cross-platform Tauri v2 API gated behind one Cargo feature flag — no reason to shell out to platform-specific tray libraries |
| Multi-window creation | Manual `window.open()`/iframe tricks | `WebviewWindow`/`WebviewWindowBuilder` | D-12 already rejected iframe (`X-Frame-Options`); Tauri's real window primitive is the only viable path and is already installed |

**Key insight:** every "don't hand-roll" concern in this phase already has a first-party Tauri v2 API installed in the project's existing dependency tree — the entire phase is a **feature-flag + capability-grant + JS-import** exercise, not a from-scratch native-integration exercise.

## Common Pitfalls

### Pitfall 1: `isFullscreen`'s real semantics are an env/CLI signal, not a window query

**What goes wrong:** A naive D-01 implementation calls `getCurrentWindow().isFullscreen()` for the `isFullscreen` channel, because that's the obviously-named Tauri API and the channel is grouped with the other window-chrome getters. This silently changes behavior: real users are never in `--fullscreen` CLI mode or Steam Deck gamescope mode by using the OS's native fullscreen toggle, and `App.tsx`'s `fullscreen: isFullscreen` CSS class (which drives Console-mode-adjacent styling, not the OS window frame) would start reacting to real window state instead of the launch-time signal it currently tracks.

**Why it happens:** `main.ts:747`'s `addHandler('isFullscreen', () => isSteamDeckGameMode || isCLIFullscreen)` reads two Node-only constants from `backend/constants/environment.ts` (`XDG_CURRENT_DESKTOP === 'gamescope'` and `process.argv.includes('--fullscreen')`) — neither of which the renderer/webview can read directly (no `process.env`/`process.argv` in a webview). The channel name strongly suggests "is the window currently fullscreen," but it is not that.

**How to avoid:** Under Tauri, `window.isSteamDeckGameMode` is **already** hardcoded `false` in the existing `tauriAttach.ts` preload-global fallback (a declared, pre-existing Phase 27 stub — not new to this phase). `isCLIFullscreen` has no Tauri equivalent without new Rust work (reading the process's own argv is trivial in Rust, but would be a NEW `rustInvoke` arm, which the Claude's-Discretion "zero new arms" pre-approval does not cover). The pragmatic, honestly-declared path: implement the renderer-side `isFullscreen()` as `Promise.resolve(false)` (both underlying signals are false/unreachable under Tauri today), with a code comment naming the gap explicitly (mirrors the `isSteamDeckGameMode = false` precedent already in `tauriAttach.ts`). Do not silently substitute real window-fullscreen state.

**Warning signs:** Any implementation of `isFullscreen` that imports `getCurrentWindow` at all is suspicious — the correct implementation may need no Tauri window API call whatsoever, just a hardcoded/declared-false return.

### Pitfall 2: `electronUntouched.test.ts` does not test what its name (and CONTEXT.md's framing) suggests

**What goes wrong:** A planner reads CONTEXT.md's canonical_refs entry ("D-07 modifies `main.ts` by design; this test's contract may need to be re-expressed as behavioral rather than textual") and assumes the file contains an assertion on `main.ts`'s source text, git diff, or import graph that will need updating.

**Why it happens:** The file is actually Phase 28's keyring/`configStore` byte-identity proof — it asserts that `SidecarKeyringTokenStore`'s four operations (and `bootstrap.ts`) never write to the shared `configStore.refreshToken`/full snapshot, via real (unmocked) `configStore` + `fs.readFileSync` byte comparison, plus two by-construction source-string gates on `keyringTokenStore.ts`/`bootstrap.ts`/`electronStub.ts` (unrelated to `main.ts`). **Confirmed directly by reading the file in full** (317 lines) — there is no reference to `main.ts`, no git-diff check, no file-hash check, nothing about the Electron build's textual state at all.

**How to avoid:** Report this discrepancy to the planner explicitly rather than silently updating a test file that doesn't need it (see Assumptions Log A1). The actual "does the Electron build still work" invariant for this phase is exercised the way SEAM.md's Incremental-Port Checklist step 5 already prescribes: manually re-running `npm start` and confirming behavior, not an automated textual/hash test. **No existing jest suite in the repo does a source-diff/hash check on `main.ts`** (confirmed by grep across `src/backend/sidecar/__tests__/*.test.ts` — none reference `main.ts` by path). If the planner wants an automated guard for "main.ts's *registration* lines stay one-line delegations" (D-08's own acceptance bar), that would be a **new** test, not a modification of `electronUntouched.test.ts`.

### Pitfall 3: `setZoomFactor` needs a different Tauri API family than the other 9 D-01 channels

**What goes wrong:** Implementing `setZoomFactor` against `getCurrentWindow()` (like the other 9) fails to compile/silently does nothing — `Window` has no `setZoom` method in Tauri v2.

**Why it happens:** Zoom is a **Webview**-scoped concept in Tauri v2 (a window can host multiple webviews in principle, though GameLib only ever has one), not a Window-scoped one. `setZoom(scaleFactor: number): Promise<void>` lives on the `Webview` class (`@tauri-apps/api/webview`), reached via `getCurrentWebview()`, not `getCurrentWindow()`. This also means the capability identifier is `core:webview:allow-set-webview-zoom`, a different permission namespace (`core:webview:*`) than the other 9 grants (`core:window:*`) — confirmed both exist as real identifiers and neither is in its respective `default` set [VERIFIED: crate source `permissions/webview/autogenerated/reference.md:1-10,336-354`].

**How to avoid:** Import `getCurrentWebview` from `@tauri-apps/api/webview`, not `@tauri-apps/api/window`, for this one channel. `zoomFactor` arrives as a string (`processZoomForScreen(parseFloat(zoomFactor))` in Electron's body) — `setZoom` takes a raw `number`; replicate Electron's `parseFloat` + any `processZoomForScreen` clamping logic if that function is renderer-portable (it lives in `main.ts`, needs to be checked/ported at plan time — not verified in this research pass).

### Pitfall 4: `TrayIcon` requires an explicit Cargo feature flag not currently enabled

**What goes wrong:** Writing `TrayIconBuilder`/`TrayIcon` Rust code against the current `Cargo.toml` fails to compile — `tray-icon` is an **optional** feature of the `tauri` crate.

**Why it happens:** `src-tauri/Cargo.toml` currently declares `tauri = { version = "2", features = [] }` — an explicitly empty feature list. The `tauri` crate's own `Cargo.toml` [VERIFIED: read directly from the cached crate source] declares `tray-icon = ["dep:tray-icon"]` as an optional feature, and a Linux-specific `linux-libxdo` feature (`tray-icon/libxdo`) that may matter for AppImage/Flatpak tray click-menu behavior — not verified this session, flagged as [ASSUMED] below.

**How to avoid:** Change `features = []` to `features = ["tray-icon"]` in `src-tauri/Cargo.toml` as the first concrete task of any D-11 plan. Also grant `core:tray:default` (or narrower — `allow-new`/`allow-set-icon`/`allow-set-tooltip` if built entirely Rust-side with no JS `@tauri-apps/api/tray` calls) in `capabilities/default.json` if any tray control happens from JS.

### Pitfall 5: D-01's channels currently flow through `misc.ts`'s generic `makeHandlerInvoker`/`makeListenerCaller` — removing them changes the `AsyncIPCFunctions`/`SyncIPCFunctions` type-check surface

**What goes wrong:** Simply deleting the `makeHandlerInvoker('isMaximized')` line and replacing it with a new function risks a type mismatch if the new function's signature doesn't match what `common/types/ipc.ts`'s `AsyncIPCFunctions`/`SyncIPCFunctions` declare (`isFullscreen: () => boolean`, `isMaximized: () => boolean`, etc. — confirmed at `ipc.ts:198-201`).

**How to avoid:** Keep each replaced export's exported *name* and *call signature* identical to what `AsyncIPCFunctions`/`SyncIPCFunctions` declare — only the *body* changes. The return-type mismatch between the interface's declared `boolean` and the new Tauri-path's `Promise<boolean>` is not actually a problem: `ipc.ts`'s own `PromiseOnce<T>` type already handles this coercion for every existing `makeHandlerInvoker` call, and `misc.ts`'s existing hand-written `storeGet` (sync, not going through `makeHandlerInvoker` at all) proves hand-written bodies with matching call signatures already coexist fine in this file.
