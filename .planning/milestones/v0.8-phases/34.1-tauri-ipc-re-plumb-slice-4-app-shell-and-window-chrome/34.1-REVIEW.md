# Phase 34.1: Code Review Report

**Reviewed:** 2026-07-25T03:34:26Z
**Depth:** standard
**Files Reviewed:** 31
**Status:** issues_found

## Summary

This slice ports 33 app-shell/window-chrome channels onto three transports (renderer-side
Tauri JS, sidecar-routed, one new Rust `tray_set_icon` arm). The transport plumbing itself is
sound: `tsc --noEmit` is clean, `eslint` reports 0 errors on the changed files, no file under
`src/backend/sidecar/` imports the real `electron` module, no channel is double-registered
across the six `register*Flows()` modules, every `handle`/`on` kind matches `main.ts`'s own
registration for the same channel, and the child-window fail-closed claim
(`capabilities/default.json` scoped `"windows": ["main"]`, child labels `about` /
`external-<n>` never `main`, never url-derived) **does hold** — labels are a monotonic counter,
window-label matching is literal, and `main` already exists so it cannot be re-created.

The defects are in the **behavioural translation**, not the wiring. Four ported behaviours are
silently non-functional or wrong at runtime while their unit tests pass, in three cases because
the test mocks or pins the exact thing that is broken:

1. `changeLanguage` throws inside the sidecar on every call (i18next is never initialized
   outside Electron's `app.whenReady()`) — proven by executing the installed i18next 22.5.1.
2. The frameless-decoration pre-paint apply always reads an **empty** store snapshot, so it
   applies the default instead of the user's setting.
3. The `maximized`/`unmaximized` frontend pushes have no Tauri producer, leaving the ported
   window-controls restore button permanently unreachable.
4. `quit` → `handleExit()` is newly sidecar-reachable, invalidating a documented electronStub
   invariant and exposing an unlabelled confirm dialog plus a fail-**open** destructive default.

Security posture is otherwise unchanged from the Electron baseline: `openWebviewPage` /
`openReleases` reach the same unfiltered `openUrlOrFile()` Electron already used
(`main.ts:716/727/730`), and `getThemeCSS` is byte-identical to the extracted Electron body —
neither is widened by this slice, per T-34.1-12 / T-34.1-13. One capability grant does widen
the renderer's reach and is reported below as WR-07.

## Critical Issues

### CR-01: `changeLanguage` is dead on the Tauri path — i18next is never initialized in the sidecar

**File:** `src/backend/appshell/language.ts:25-31`, `src/backend/sidecar/appShellFlowRegistration.ts:190-194`

**Issue:** `i18next.use(Backend).init({...})` exists in exactly one place in the whole backend —
`src/backend/main.ts:460`, inside the Electron `app.whenReady()` block. The sidecar
(`src/backend/sidecar/bootstrap.ts`) never initializes i18next. Calling `changeLanguage()` on an
uninitialized i18next instance throws **synchronously**; verified against the installed
i18next 22.5.1:

```
$ node -e "const i=require('i18next'); i.default.changeLanguage('de')"
TypeError: Cannot read properties of undefined (reading 'toResolveHierarchy')
    at setLngProps (node_modules/i18next/dist/cjs/i18next.js:2276:58)
    at setLng   (…:2302:13)
    at I18n.changeLanguage (…:2320:9)
```

Because `changeLanguage` in `language.ts` is an `async function`, that throw becomes a rejection
which `appShellFlowRegistration.ts:191` swallows with `.catch(logSendFailure)`. Everything after
the `await` is therefore **never reached**:

```ts
await i18next.changeLanguage(language)          // <-- throws here, every time
gameInfoStore.clear()                            // never runs
GlobalConfig.get().setSetting('language', ...)   // never runs -> setting never persists
backendEvents.emit('languageChanged')            // never runs
```

Net effect under Tauri: changing the app language never persists (reverts on next launch), the
Legendary game-info cache is never invalidated for the new locale, and `languageChanged`
listeners never fire. The only signal is one `console.warn`.

This cannot be caught by the current tests: `src/backend/sidecar/__tests__/appShellFlows.test.ts:148`
replaces the whole `i18next` module with `{ changeLanguage: jest.fn().mockResolvedValue(undefined) }`,
i.e. it mocks away precisely the failing call.

**Fix:** Either initialize i18next headlessly in the sidecar bootstrap, or make the persist path
independent of the i18next call:

```ts
// src/backend/appshell/language.ts
export async function changeLanguage(language: string): Promise<void> {
  logInfo(['Changing Language to:', language], LogPrefix.Backend)
  try {
    await i18next.changeLanguage(language)
  } catch (error) {
    // Headless sidecar: i18next is only init()'d by Electron's app.whenReady().
    // A missing translator must not block persisting the user's choice.
    logWarning(['i18next.changeLanguage failed (uninitialized instance?):', error], LogPrefix.Backend)
  }
  gameInfoStore.clear()
  GlobalConfig.get().setSetting('language', language)
  backendEvents.emit('languageChanged')
}
```

and add a sidecar test that does **not** mock `i18next` (or asserts the real module is
uninitialized) so the regression cannot re-hide.

### CR-02: `applyFramelessDecorations()` at attach time always reads an empty store snapshot

**File:** `src/preload/tauriAttach.ts:100`, `src/preload/api/tauriWindowChrome.ts:31-36,149-158`

**Issue:** `tauriAttach.ts` is deliberately the first meaningful import of `src/frontend/index.tsx`
(index.tsx:19), and its module body calls `applyFramelessDecorations()` with no argument, which
resolves the value from `snapshotGet('configStore', 'settings')`. But the store snapshot is
hydrated by `await hydrateStoreSnapshot()` in index.tsx's **top-level statement body**
(index.tsx:58-63), which by ES-module semantics runs strictly *after* every static import has
evaluated. At attach time the snapshot map is empty, so:

```ts
const settings = snapshotGet('configStore', 'settings')   // undefined
return settings?.framelessWindow === true                 // always false
…
getCurrentWindow().setDecorations(!false)                  // always DECORATED
```

For a user with `framelessWindow: true` this produces a visibly broken window on every launch:
the native titlebar is restored, and because `App.tsx` reads `isFrameless` later (GlobalState.tsx:1328,
post-hydration) it correctly returns `true` and renders GameLib's **own** overlay window controls
on top — the user gets both chromes at once. Decorations are never re-applied afterwards; the
only other call site is the `setSetting` toggle.

`src/preload/__tests__/framelessRuntime.test.ts:132` pins this as expected behaviour
("with no settings snapshot calls setDecorations(true)"), so the suite is green while production
is wrong.

**Fix:** Re-apply after hydration, in addition to the pre-paint default:

```ts
// src/frontend/index.tsx, immediately after the hydrateStoreSnapshot() await
if (isTauri()) {
  const { applyFramelessDecorations } = await import('../preload/api/tauriWindowChrome')
  applyFramelessDecorations()   // now reads the real configStore.settings
}
```

(or have `tauriAttach` register a one-shot post-hydration callback). Add a test that hydrates the
snapshot *after* attach and asserts `setDecorations(false)` is eventually called.

### CR-03: `maximized` / `unmaximized` pushes have no Tauri producer — the restore button is unreachable

**File:** `src/preload/api/misc.ts:59-60`, `src/preload/api/tauriWindowChrome.ts:44-60,211-216`

**Issue:** Under Electron these two frontend pushes are emitted from real window events
(`src/backend/main.ts:240-241`: `mainWindow.on('maximize', () => sendFrontendMessage('maximized'))`).
This slice ports `maximizeWindow`/`unmaximizeWindow`/`isMaximized` renderer-side and adds a
double-click `toggleMaximize()` handler, but nothing — not the sidecar, not `main.rs`, not
`tauriWindowChrome.ts` — emits `maximized`/`unmaximized` under Tauri.

`src/frontend/components/UI/WindowControls/index.tsx` depends on those pushes for its only state
transitions after mount:

```tsx
useEffect(() => { window.api.isMaximized().then(setMaximized) }, [])   // once, at mount
useEffect(() => window.api.handleMaximized(() => setMaximized(true)), [])    // never fires
useEffect(() => window.api.handleUnmaximized(() => setMaximized(false)), []) // never fires
const handleMaximize = () => maximized ? window.api.unmaximizeWindow() : window.api.maximizeWindow()
```

So after the user maximizes once, `maximized` stays `false` forever: the icon/tooltip stay
"Maximize" and the button calls `maximizeWindow()` again. **The window can never be restored from
the titlebar button** — the exact control this slice exists to port. `handleDragDoubleClick`'s
`toggleMaximize()` desyncs it further. `handleFullscreen` has the same missing producer.

**Fix:** Emit the state changes renderer-side from Tauri window events, e.g. in
`tauriWindowChrome.ts` alongside `installDragRegionHandlers()`:

```ts
import { getCurrentWindow } from '@tauri-apps/api/window'
// dispatch into the same frontendListenerSlot registry the Electron push path feeds
void getCurrentWindow().onResized(async () => {
  const max = await getCurrentWindow().isMaximized()
  dispatchFrontendMessage(max ? 'maximized' : 'unmaximized')
})
```

Alternatively make `WindowControls` re-read `isMaximized()` on click, but the event path is the
faithful port.

### CR-04: `quit` makes `handleExit()` sidecar-reachable — unlabelled confirm dialog, and the failure default is the destructive branch

**File:** `src/backend/sidecar/appShellFlowRegistration.ts:204-206`, `src/backend/sidecar/electronStub.ts:218-221,269,286`, `src/backend/utils.ts:251-289`

**Issue:** This slice registers `ipcMain.on('quit', () => handleExit()…)`. `electronStub.ts`'s own
`showMessageBox` comment block asserts the opposite is true and reasons from it:

> "`handleExit`'s inverted sense (`response === 0` = safe "No") is moot: it is wired in `main.ts`
> via `app.on('before-quit')`, and `main.ts` is not in the sidecar's curated import graph, so
> `handleExit` never runs under the sidecar."

That statement is now **false**, and the reasoning it supports fails with it. Two concrete
consequences on the pending-operations branch (`isLocked || isRunning()`, i.e. a game running or
a download in flight — `mainWindow` is truthy because `electronStub`'s `fakeWindow` is returned):

(a) `handleExit` builds the dialog from `i18next.t('box.no')` / `t('box.yes')` /
`t('box.quit.message')`. Per CR-01 i18next is uninitialized in the sidecar, and an uninitialized
`i18next.t()` returns `undefined` (verified). Those `undefined`s cross the wire as JSON `null`,
and `main.rs`'s `dialog_message` arm does `btns[0].as_str().unwrap_or("")` (main.rs:484-489) plus
`message …unwrap_or("")` (main.rs:456-460) — the user is shown a **blank message with two blank
buttons** and no way to tell which one cancels.

(b) `electronStub.showMessageBox`'s failure default is `safeIndex = options?.cancelId ?? (buttons.length ?? 1) - 1`
= **1** for `handleExit`'s two-button array. But `handleExit` treats `response === 0` as the safe
"No"; index 1 is "Yes". So on any transport error/timeout the stub returns the **destructive**
answer: `killPattern('legendary'|'gogdl'|'nile')`, `callAllAbortControllers()`, then `app.exit()`
— killing an in-flight install/download. The stub's documented "fail-safe-to-decline" property
does not hold for this newly-reachable caller.

**Fix:** (1) Correct the stale `electronStub.ts` comment. (2) Give `handleExit` an explicit
`cancelId` so the stub's decline default is correct for its inverted sense:

```ts
// src/backend/utils.ts, handleExit()
const { response } = await dialog.showMessageBox(mainWindow, {
  buttons: [i18next.t('box.no'), i18next.t('box.yes')],
  cancelId: 0,                       // <-- safe/decline index; stub defaults here on failure
  message: i18next.t('box.quit.message', 'There are pending operations, are you sure?'),
  title: i18next.t('box.quit.title', 'Exit')
})
```

(3) The blank-label symptom is resolved by fixing CR-01 (sidecar i18n init); until then, pass the
English defaults through `t(key, fallback)` in a way that survives an uninitialized instance.

### WR-01: drag-region fallback selector `.WindowControls` never matches the rendered class

**File:** `src/preload/api/tauriWindowChrome.ts:193-200`

**Issue:** The `-webkit-app-region`-unsupported fallback excludes
`'a, button, [role="button"], input, select, textarea, .WindowControls'`. The component renders
`<div className="windowControls">` (`src/frontend/components/UI/WindowControls/index.tsx:33`) and
the stylesheet selector is `.windowControls` (`WindowControls/index.scss:1`). CSS class selectors
are case-sensitive in standards mode, so `.WindowControls` matches nothing — the exclusion is dead
code. On webviews that do not implement `-webkit-app-region` (the fallback's entire reason to
exist), a mousedown on the padding/gaps inside the window-controls container starts a window drag
instead of being ignored.

**Fix:** `'a, button, [role="button"], input, select, textarea, .windowControls'` — and add a test
using the real rendered class name rather than a hand-written one.

### WR-02: `doTab` ignores `preventDefault` and uses a pre-dispatch focusable list

**File:** `src/preload/api/tauriGamepadInput.ts:120-137`

**Issue:** `moveFocusDirectionally` correctly bails when the synthetic keydown was prevented
(`if (prevented) return`, line 302-303). `doTab` discards `dispatchKey`'s return value entirely,
so when the app handles Tab itself (a modal trap, a custom focus manager) the focus moves
**twice** — once by the app, once by this function. Separately, `const list = getFocusableElements()`
is captured *before* the dispatch, so any DOM change the app's own handler makes (closing a
dialog, opening a menu) leaves `list[nextIndex]` pointing at a detached/stale element.

**Fix:**

```ts
function doTab(shift: boolean): void {
  const current = activeElement()
  if (current && dispatchKey(current, 'Tab', { shiftKey: shift })) return   // app handled it
  const list = getFocusableElements()                                       // recompute AFTER
  if (list.length === 0) return
  …
}
```

### WR-03: directional focus can never move Up or Left when nothing is focused

**File:** `src/preload/api/tauriGamepadInput.ts:229-244, 299-322`

**Issue:** With no `activeElement`, `origin` is `zeroRectAtOrigin()` = `{top:0,left:0,right:0,bottom:0}`.
`isInDirection` then requires `rect.bottom <= 0` for `Up` and `rect.right <= 0` for `Left` — no
on-screen element can satisfy either (viewport coordinates are >= 0). So `padUp`/`padLeft`/
`leftStickUp`/`leftStickLeft` are permanent no-ops until something is focused, while `Down`/`Right`
work. For a gamepad-only user (the sole consumer of this module) that is a real dead input.

**Fix:** Seed the origin from the viewport edge opposite the movement direction, e.g. for `Up` use
`{top: window.innerHeight, bottom: window.innerHeight, left: 0, right: window.innerWidth}`, or
special-case "nothing focused" to focus the first/last element in document order.

### WR-04: `external-<n>` window labels collide after a renderer reload

**File:** `src/preload/api/tauriChildWindows.ts:36-58`

**Issue:** `externalWindowCounter` is module state in the **renderer** bundle. Child
`WebviewWindow`s are separate OS windows that survive a main-window reload (F5 / devtools reload /
`location.reload()`), but the counter resets to `0`. The next `createNewWindow` therefore requests
label `external-1`, Tauri rejects it as already-taken, and the failure surfaces only as a
`tauri://error` `console.warn` — the user clicks a ProtonDB/AppleWiki link and nothing happens.

**Fix:** Use a collision-free label, e.g. `external-${Date.now()}-${Math.random().toString(36).slice(2, 8)}`,
or check `WebviewWindow.getByLabel(label)` and increment past occupied labels.

### WR-05: `setSetting` destructures its argument unconditionally, on the Electron path too

**File:** `src/preload/api/settings.ts:17-23`

**Issue:** The comment claims "Never runs on the Electron path", but only the
`applyFramelessDecorations` call is guarded — `const [{ appName, key, value }] = args` executes on
**both** paths, after the IPC send has already gone out. `setSetting` was previously a pure
passthrough that could not throw; it is reachable from untyped renderer code (including anything
running in the `main` window, per this capability's own threat model), where
`window.api.setSetting()` or `setSetting(null)` now throws a `TypeError` synchronously into the
caller instead of being harmlessly forwarded. This breaks the "Electron path byte-identical"
invariant this slice asserts elsewhere.

**Fix:**

```ts
export const setSetting = (...args: Parameters<typeof setSettingIpc>) => {
  setSettingIpc(...args)
  if (!isTauri()) return
  const { appName, key, value } = args[0] ?? {}
  if (appName === 'default' && key === 'framelessWindow') {
    applyFramelessDecorations(Boolean(value))
  }
}
```

### WR-06: `About` window creation blocks on a full sidecar round-trip

**File:** `src/preload/api/tauriChildWindows.ts:70-92`

**Issue:** `showAboutWindowAsync` `await`s `window.api.getHeroicVersion()` — a `sidecar_invoke`
round-trip bounded by `INVOKE_TIMEOUT` (60 s, `src-tauri/src/main.rs:102`) — **before** creating
the window. With a slow or wedged sidecar the About menu item appears to do nothing for up to a
minute, then opens. The version is cosmetic; the window is not.

Related, same file: `win.once('tauri://error', …)` at lines 55 and 92 returns an unawaited,
uncaught promise (two `@typescript-eslint/no-floating-promises` warnings). Benign today only
because `bootErrorSurface` downgrades post-mount unhandled rejections to `console.error`.

**Fix:** Create the window immediately with `v=unknown` and update it (or race a ~1 s timeout on
`getHeroicVersion()`), and `void`/`.catch()` the two `once()` promises.

### WR-07: `core:webview:allow-create-webview-window` widens what untrusted content in `main` can do, and child windows are hard-titled "GameLib"

**File:** `src-tauri/capabilities/default.json:23`, `src/preload/api/tauriChildWindows.ts:47-54`

**Issue:** The fail-closed claim in the capability description is **correct and verified** — child
labels are `about` / `external-<n>`, never url-derived, `windows: ["main"]` matches literally, and
`main` cannot be re-created because it already exists. That is not the concern. The concern is the
grant itself: it is scoped to `main`, and per this file's own stated threat model GameLib renders
untrusted remote content *inside* `main` with no `<webview>` isolation boundary. That content can
call `plugin:webview|create_webview_window` directly (not just via `window.api`) with an arbitrary
URL and arbitrary window options. Under Electron the equivalent reach existed via
`window.api.createNewWindow`, so this is not a large step — but `tauriCreateNewWindow` additionally
hard-codes `title: 'GameLib'` on a window loading renderer-supplied remote content, whereas
Electron's `new BrowserWindow(...).loadURL(url)` (`main.ts:797-799`) let the remote page's own
`<title>` show. That is a new, small phishing affordance (an attacker-controlled page presented
under the app's own name).

**Fix:** Drop the hard-coded `title` (let the loaded page title itself, matching Electron), or set
it to something that cannot be mistaken for first-party chrome, e.g.
`title: 'GameLib — external page'`. Longer term, if the Humble/store surfaces move out of `main`
(Phase 34.4), re-evaluate whether this grant can be dropped from the `main` capability entirely.
