## Changed test contracts (called out explicitly, per instruction)

Three tests were **encoding the bug** and had to be corrected. None was weakened.

1. **`appShellFlows.test.ts` — `changeLanguage` failure test (CR-01).**
   It previously asserted that a failing `i18next.changeLanguage` produced a
   `[appShellFlowRegistration] changeLanguage failed:` warning — i.e. it *pinned* the
   rejection escaping `changeLanguage` and aborting the persist path. The contract is
   now the opposite: the failure is contained and the setting still persists. The
   surviving requirement ("a send-handler body must never crash the sidecar") is still
   asserted via the post-failure health check. A **second** test was added using a
   *synchronous* throw, which is the real uninitialized-i18next shape — a fix that
   merely appended `.catch()` to the call expression would pass the rejection test and
   fail this one.

2. **`framelessRuntime.test.ts` — empty-snapshot test (CR-02).**
   The assertion itself is correct *about the function in isolation* (no data ⇒
   decorated default), so it was **kept**, but retitled to "the pre-hydration paint" and
   commented to state that this is not the steady state. A new sequence test reproduces
   `index.tsx`'s real two-phase startup and pins that a `framelessWindow: true` user
   ends at `setDecorations(false)`.

3. **`appShellFlows.test.ts` — abort-handler mock (CR-04).**
   The suite's `jest.mock('.../aborthandler')` omitted `callAllAbortControllers`, which
   `handleExit`'s destructive branch calls. That branch therefore threw a TypeError
   partway through instead of running — which silently made any "did the destructive
   branch run?" assertion **vacuous**. I caught this by deliberately reverting the fix
   and confirming the new test still passed; the mock is now complete and the test
   verifiably fails without the fix (`Expected number of calls: 0, Received: 1`).

## Deviation from the review's suggested fixes

**CR-03: the reviewer's `dispatchFrontendMessage` does not exist.** As flagged in the
task brief, I verified this before using it — `src/preload/tauriTransport.ts` exports
`invoke` / `send` / `listen` / the snapshot primitives, and there is no renderer-side
entry point into the `frontendListenerSlot` registry under that or any other name. I
did **not** invent one. Instead the producer follows the pattern this slice already
established for the other ten D-01 channels: an `isTauri()` short-circuit in `misc.ts`
routing to a renderer-side implementation in `tauriWindowChrome.ts`. This needs no new
transport API and no new capability grant (`onResized` rides `core:event:allow-listen`,
already inside `core:default`).

**CR-03: `handleFullscreen` deliberately left as a no-op.** The reviewer noted it "has
the same missing producer". Wiring it to real OS fullscreen state would have been
*wrong*: `tauriIsFullscreen` deliberately returns the static `isSteamDeckGameMode`
gamescope signal (not a window query), and that is what `App.tsx`'s `fullscreen` CSS
class tracks. Pushing real fullscreen transitions into that slot would silently
redefine the class and put it permanently at odds with the value `GlobalState` seeds it
from. It is now an explicitly *declared* no-op with a test asserting it never queries
the Window API, rather than a silently-dead `frontendListenerSlot`.

**CR-01/CR-04: headless i18next init in the sidecar was NOT done** — see Residual gaps.

**No capability grants were changed.** `capabilitiesDefault.test.ts` (exact-grant-list)
and `appShellImportGate.test.ts` (by-construction import gate) are both untouched and
still pass.

### CR-03: `maximized` / `unmaximized` pushes have no Tauri producer

**Files modified:** `src/preload/api/tauriWindowChrome.ts`, `src/preload/api/misc.ts`,
`src/preload/__tests__/windowChrome.test.ts`
**Commit:** `7f11f791`
**Applied fix:** Added a renderer-side producer: one shared `getCurrentWindow()
.onResized(...)` watcher that polls `isMaximized()` and fans out to subscribers, with a
`lastMaximized` de-dupe cache (`onResized` fires per frame during an interactive resize

frame). `misc.ts`'s `handleMaximized`/`handleUnmaximized` now route through it under
`isTauri()`, exactly like the ten other D-01 channels. Seven new tests cover: single
shared watcher, transition into maximized, transition back out (the previously
unreachable restore path), de-duping, unsubscribe, Electron no-op, and the
`handleFullscreen` declared no-op.

### WR-03: directional focus can never move Up or Left when nothing is focused

**Files modified:** `src/preload/api/tauriGamepadInput.ts`,
`src/preload/__tests__/gamepadAction.test.ts`
**Commit:** `fa457040`
**Applied fix:** Replaced `zeroRectAtOrigin()` with `viewportOriginFor(direction)`,
which seeds a degenerate rect on the viewport edge *opposite* the movement direction
(Up ⇒ just below the viewport, Left ⇒ just right of it, etc.). `directionScore`'s
facing-edge term then naturally selects the bottom-most / right-most element, with the
perpendicular centre-offset term breaking ties toward screen centre — each direction the
exact mirror of its opposite. Guarded against a missing `window.innerWidth/Height` (the
preload jest project runs `testEnvironment: 'node'`). Four tests, including one pinning
that Down/Right behaviour is unchanged.

## Residual gaps (deliberate, not silently dropped)

1. **Headless i18next init in the sidecar was not added.** CR-01 offered two options;
   I took the "make the persist path independent" one. Rationale: the renderer runs its
   own i18next instance for every string the user sees, so the *user-visible* language
   change is fully restored by this fix. What is still degraded is **backend-side**
   strings (tray labels, dialog/notification text) under Tauri, which now fall back to
   English rather than being blank. Adding `i18next.init` to `bootstrap.ts` touches
   sidecar boot ordering — the area with the most scar tissue in this project
   (`initLogger` ordering, `GlobalConfig.get()` on the config-upgrade path,
   `setImmediate` deferrals) — and I could not hardware-test it here. Recommend it as a
   tracked follow-up, not a code-review fix.

2. **WR-07's longer-term half is not done.** The reviewer's second suggestion —
   re-evaluating whether `core:webview:allow-create-webview-window` can be dropped from
   the `main` capability once the Humble/store surfaces move out of `main` — is
   explicitly scoped to Phase 34.4 in the review itself. No capability file was touched.

3. **Two commits cover more than one finding each**, because the findings share a single
   source file and could not be split into independent working-tree states:
   `fa457040` (WR-02 + WR-03, both `tauriGamepadInput.ts`) and `101d9e50`
   (WR-04 + WR-06 + WR-07, all `tauriChildWindows.ts`).

4. **All fixes are unit-verified only.** Four of them (CR-02 frameless re-apply, CR-03
   maximize/restore, WR-01 drag regions, WR-06 About timing) are user-visible window
   behaviour under a real Tauri webview and warrant a live check during this phase's UAT.
   CR-04's safety property is proven by test but its dialog rendering (non-blank labels
   via `main.rs`'s `dialog_message` arm) has not been seen on screen.
