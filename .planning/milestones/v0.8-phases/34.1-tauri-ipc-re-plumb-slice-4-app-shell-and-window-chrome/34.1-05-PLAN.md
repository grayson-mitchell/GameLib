<objective>
D-10: re-implement `gamepadAction` renderer-side. Electron injects synthetic input via
`webContents.sendInputEvent` (`main.ts:1377`); Tauri has no equivalent, and the renderer
already reads the Gamepad API, so under Tauri the renderer dispatches its own synthetic
DOM events and focus moves instead of round-tripping.

Purpose: a logged no-op would silently remove a shipped feature from a launcher whose
audience includes Steam Deck and couch users, and there are real consumers — the
`/console` routes, `isSteamDeckGameMode`, and the `tab` calls
`components/UI/Dropdown/index.tsx` and `components/UI/Dialog/components/Dialog.tsx` make
directly.

**The cost D-10 accepted, stated plainly:** this is a re-derivation against DOM semantics,
not a mechanical port. Chromium's built-in spatial navigation — which is what made
Electron's synthetic `keyDown` with keyCode `Up`/`Down`/`Left`/`Right` actually move focus
— does not exist in WKWebView or WebView2. Dispatching an arrow-key `KeyboardEvent` alone
would do nothing. The directional actions must compute the focus move themselves.

Output: a `tauriGamepadInput.ts` module, one `isTauri()` branch on `misc.ts`'s
`gamepadAction` export, and a jsdom suite covering every action case.
</objective>

Create `src/preload/api/tauriGamepadInput.ts` exporting
`tauriGamepadAction(args: { action: string; metadata?: { x: number; y: number } }): Promise<void>`.
The module must import nothing from `electron` and nothing from `@tauri-apps/api` — it is
pure DOM. Every branch is total: wrap the body so a failure `console.warn`s and resolves
rather than rejecting (an unhandled rejection from `window.api.*` in the gamepad polling
loop would fire on every frame).

Implement a shared helper set first:
  - `getFocusableElements(): HTMLElement[]` — query the document for
    `a[href], button, input, select, textarea, [tabindex]:not([tabindex="-1"]), [role="button"]`,
    filter out elements that are `disabled`, have `aria-hidden="true"`, or have zero-area
    bounding rects, and return them in document order.
  - `activeElement(): HTMLElement | null` — `document.activeElement` narrowed to
    `HTMLElement`, treating `document.body` as "nothing focused".
  - `dispatchKey(target: EventTarget, key: string, opts?: { shiftKey?: boolean })` —
    dispatch a `keydown` then a `keyup` `KeyboardEvent` with `bubbles: true`,
    `cancelable: true`, and matching `key`/`code`/`keyCode`/`which` fields.

Then implement these actions:
  - `tab` — move focus to the next element in `getFocusableElements()` after the currently
    focused one, wrapping to index 0; call `.focus()` on it. If nothing is focused, focus
    index 0. Also dispatch a `Tab` keydown/keyup on the previously focused element first,
    so any app-level Tab handler still sees it.
  - `shiftTab` — the same, moving backward and wrapping to the last element, dispatching
    `Tab` with `shiftKey: true`.
  - `esc` — dispatch `Escape` keydown/keyup on `activeElement() ?? document`. Do not close
    anything directly; the app's own handlers own that.
  - `back` — `window.history.back()`. Comment that Electron used
    `webContents.goBack()`, which for a hash/BrowserRouter SPA is the same history stack.
  - `leftClick` / `rightClick` — require `metadata`; if absent, `console.warn` naming the
    action and return. Hit-test with `document.elementFromPoint(metadata.x, metadata.y)`;
    if null, return. Dispatch, on that element, `pointerdown`+`mousedown`+`mouseup`+
    `pointerup` and then `click` for the left button (`button: 0`), or
    `mousedown`+`mouseup`+`contextmenu` for the right button (`button: 2`), each with
    `bubbles: true`, `cancelable: true`, and `clientX`/`clientY` set to the metadata
    coordinates. Use `MouseEvent` for all of them (jsdom has no `PointerEvent` by default —
    construct `MouseEvent` with the pointer type names, and note that in a comment).
  - `rightStickUp` / `rightStickDown` — find the nearest scrollable ancestor of
    `document.elementFromPoint(innerWidth / 2, innerHeight / 2)` (walk up while
    `scrollHeight <= clientHeight` or the computed `overflow-y` is `visible`/`hidden`),
    falling back to `document.scrollingElement ?? document.documentElement`. Then adjust
    `scrollTop` by `-50` for `rightStickUp` and `+50` for `rightStickDown` — matching
    Electron's inverted `deltaY` convention documented in `<interfaces>`. Prefer
    `el.scrollBy({ top: delta })` when available, falling back to direct `scrollTop`
    assignment for jsdom.
  - default — an unknown action `console.warn`s once naming the action and resolves.

Implement `moveFocusDirectionally(direction: 'Up' | 'Down' | 'Left' | 'Right'): void` in
`src/preload/api/tauriGamepadInput.ts`, and route all eight directional actions to it by
deriving the direction with the same normalisation Electron used:
`action.replace(/pad|leftStick/, '')` yielding `Up`/`Down`/`Left`/`Right`.

Algorithm — geometric nearest-in-direction focus move, computed from
`getBoundingClientRect()`:
  1. Let `candidates = getFocusableElements()` minus the currently focused element.
  2. Let `origin` be the focused element's rect, or a zero-size rect at the viewport's
     top-left when nothing is focused (which makes the first press focus the top-left-most
     candidate).
  3. Keep only candidates strictly in the requested direction: for `Up`, `rect.bottom <= origin.top`;
     `Down`, `rect.top >= origin.bottom`; `Left`, `rect.right <= origin.left`;
     `Right`, `rect.left >= origin.right`.
  4. Score each survivor by `primary + 2 * secondary`, where `primary` is the distance
     along the movement axis between the facing edges and `secondary` is the centre-to-centre
     distance on the perpendicular axis. Weighting the perpendicular offset higher is what
     keeps the move in the intended column/row rather than skipping diagonally.
  5. Focus the lowest-scoring candidate. If there are none, leave focus unchanged and do
     NOT wrap — Electron's spatial navigation does not wrap either.
  6. Before moving, dispatch the corresponding arrow `keydown`/`keyup`
     (`ArrowUp`/`ArrowDown`/`ArrowLeft`/`ArrowRight`) on the currently focused element so
     any component with its own arrow handling still sees the input; if that keydown's
     `defaultPrevented` is true, skip the focus move entirely and return — the component
     claimed the input.

Add a module comment stating why this exists: Chromium's built-in spatial navigation,
which Electron's synthetic `keyDown` relied on, is not available in the platform webviews
Tauri uses (WKWebView / WebView2), so an arrow `KeyboardEvent` alone moves nothing. This
is the D-10 "re-derivation against DOM semantics" cost, made explicit.

Extend `src/preload/__tests__/gamepadAction.test.ts` with directional tests over a
fixture whose elements have stubbed `getBoundingClientRect` values laid out in a known
2x2 (or 3x3) grid. Cover:
  - from the top-left cell, `padRight` focuses the top-right cell and `padDown` focuses
    the bottom-left cell
  - `padLeft` from the leftmost cell leaves focus unchanged (no wrap)
  - `leftStickUp` and `padUp` produce identical results (the eight actions collapse to four
    directions)
  - the perpendicular weighting is honoured: given a near-but-offset candidate and a
    slightly-farther-but-aligned candidate, the aligned one wins
  - with nothing focused, a directional press focuses the top-left-most candidate
  - when the dispatched arrow `keydown` is `preventDefault()`ed by a listener, focus does
    not move
  </action>
