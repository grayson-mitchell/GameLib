<objective>
Close the frontend half of gap G4 (UAT test 9, DECISION REVERSAL, major): now that macOS drives the
titlebar from `settings.framelessWindow` — ON -> `titleBarStyle 'overlay'`, OFF -> `'visible'`, with
the native traffic lights present in BOTH states (plan 34.1-10) — the shell must clear those lights
whenever the bar is OVERLAID, must stop rendering GameLib's own duplicate buttons on macOS in
EITHER state, and must stop reserving trailing space for buttons that no longer exist there.

Purpose: `--traffic-light-inset: 0px` was never a design position — `NavShell/index.scss:24-33`
documents it as correct *because nothing overlaid the titlebar*, and says in its own words
"This exists as a token so that adopting overlay mode later is a value change, not a re-layout."
Overlay mode is exactly the trigger that flips it. 78px is not a guess: `Skill("sketch-findings-gamelib")`
lists it as one of exactly TWO constraints that OVERRIDE aesthetics — *"78px at the window's
top-left belongs to the macOS traffic lights whenever the Tauri titlebar is transparent or
overlaid. No top-mounted bar starts at x=0."*

Output: a 78px reserve scoped to the macOS-OVERLAID state, `WindowControls` gated off on macOS
unconditionally, the trailing reserve scoped away from that state, `shellTokens.test.ts` RETUNED
(never deleted), and the stale D-05 comment corrected.

**Two gates, two different conditions — this is the load-bearing distinction in this plan:**

| Gate | Condition | Why |
|------|-----------|-----|
| Hide `WindowControls` | `platform === 'darwin'` — UNCONDITIONAL | The native traffic lights exist in BOTH macOS titlebar states (in the bar when `'visible'`, over content when `'overlay'`). GameLib's own buttons are redundant either way. Native chrome never needs GameLib's own buttons. |
| Apply the 78px reserve | `platform === 'darwin' && isFrameless` — CONDITIONAL | The reserve exists to clear lights drawn OVER the webview. That only happens in `'overlay'`. In `'visible'` the native bar is its own strip above the webview, nothing overlays the content, and a 78px inset would be dead leading padding. |

An earlier draft of this plan made BOTH unconditional, because it inherited plan 34.1-10's
since-falsified premise that macOS was permanently overlaid. The `WindowControls` half survived
that correction; the 78px half did not, and was re-derived rather than carried forward.

**Depends on 34.1-09** because this plan rewrites `NavShell/index.scss`'s D-05 comment, which
currently asserts that `WindowControls` "keeps `grid-area: content`" — a claim 34.1-09 falsifies.
Correcting it before 34.1-09 lands would make the comment wrong in the other direction.
</objective>

<why_a_single_token_declaration>
`shellTokens.test.ts:55` asserts `--traffic-light-inset:` is declared EXACTLY ONCE across every
stylesheet under `src/frontend`. That gate is correct and stays. So the platform decision must NOT
be expressed as a second declaration of the token — express it in the CONSUMER instead:

  :root { --traffic-light-inset: 78px; }             <- the constant: what macOS traffic lights cost
  .App.macOverlayTitlebar .NavShell__navbar { padding-inline-start: var(--traffic-light-inset); }

The token means "what macOS traffic lights cost when they are overlaid on content", a fixed
quantity. Whether it APPLIES is a platform-AND-state question, and those belong on the selector.
</why_a_single_token_declaration>
