# Phase 34.1 Plan 03: Window chrome + frameless runtime Summary

Implemented the ten D-01 window-chrome IPC channels as renderer-side Tauri JS calls
(no sidecar hop, zero new Rust arms), and D-05/D-06's runtime `framelessWindow`
honoring — pre-paint decoration apply, on-toggle re-apply, and a drag region built on
the existing `-webkit-app-region` CSS with no frontend change.

## What Was Built

**Task 1 — `src/preload/api/tauriWindowChrome.ts`** (new module): ten faithful
Tauri-side implementations of `minimizeWindow`/`maximizeWindow`/`unmaximizeWindow`/
`closeWindow`/`isMaximized`/`isMinimized`/`isFullscreen`/`setFullscreen`/`isFrameless`/
`setZoomFactor` against `getCurrentWindow()` (`@tauri-apps/api/window`) and
`getCurrentWebview()` (`@tauri-apps/api/webview`, `setZoomFactor` only). Two are
deliberately NOT the "obvious" implementation:
- `isFullscreen` never calls the Window API — Electron's real body is
  `isSteamDeckGameMode || isCLIFullscreen`, two Node-only env/CLI signals with no
  Tauri renderer equivalent; this returns `window.isSteamDeckGameMode === true`
  (already hardcoded `false` by the Phase 27 `tauriAttach.ts` stub), never a real
  window-fullscreen query.
- `setZoomFactor` converts Electron's Chromium zoom *level* to Tauri's zoom *scale
  factor* via `Math.pow(1.2, level)`, where `level` is derived from `main.ts`'s
  `processZoomForScreen` formula using `window.screen.availWidth` in place of
  Electron's `screen.getPrimaryDisplay().workAreaSize.width`.

Also added (for Task 3) `applyFramelessDecorations(frameless?)` and
`installDragRegionHandlers()` in the same module, both total (never throw).

18 tests in `windowChrome.test.ts` (REQ-34.1-01) prove each export calls exactly its
own Tauri method with the right arguments, and that `getCurrentWindow` is never called
by `isFullscreen`/`isFrameless`/`setZoomFactor` while `getCurrentWebview` is never
called by the other nine. A spot-check (temporarily dropping `Math.pow`) confirmed the
zoom tests go red without the level→factor conversion.

**Task 2 — `src/preload/api/misc.ts`**: the ten exports now branch on `isTauri()`,
calling the new Tauri implementations under Tauri and the existing
`makeListenerCaller`/`makeHandlerInvoker`-constructed function (renamed to a private
`*Ipc` const, channel-name string literals unchanged) under Electron. No other export
in the file was touched.

**Task 3 — frameless runtime**:
- `src/preload/tauriAttach.ts`: inside the existing `if (shouldAttach)` block, after
  `window.api` and the six preload globals are set, calls
  `applyFramelessDecorations()` then `installDragRegionHandlers()`, each wrapped in a
  (deliberately redundant, since both callees are already total) try/catch that only
  `console.warn`s — SEAM Invariant A.
- `src/preload/api/settings.ts`: `setSetting` now re-applies decorations live via
  `applyFramelessDecorations(Boolean(value))` when the write is
  `{appName: 'default', key: 'framelessWindow'}` under Tauri — a deliberate superset
  of Electron parity (Electron's own Settings label for this toggle says "requires
  restart").
- Drag region: `installDragRegionHandlers()` installs one `mousedown` and one
  `dblclick` listener on `document` (capture phase, installed once). It reads the
  existing `-webkit-app-region: drag`/`no-drag` CSS via `getComputedStyle`, walking
  from the event target up through ancestors; if the property is unsupported by the
  webview (every ancestor's computed value empty), falls back to a
  `.Sidebar`-vs-interactive-element heuristic. A drag-region `mousedown` calls
  `startDragging()`; a drag-region `dblclick` calls `toggleMaximize()`.

17 tests in `framelessRuntime.test.ts` (REQ-34.1-03) cover decorated-by-default,
on/off toggling, rejection safety, one-time listener install, drag-region resolution
(including the fallback heuristic and the right-button exclusion), and the exact
trigger condition for `setSetting`'s re-apply (Tauri-only, `default` scope only,
`framelessWindow` key only).

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] `tauriAttach.test.ts` broke when Task 1/2 landed**
- **Found during:** Task 2, running the full preload jest suite per its own
  acceptance criterion ("`pnpm jest src/preload/__tests__/` is green, including the
  pre-existing `tauriAttach.test.ts`").
- **Issue:** `misc.ts`'s new static import of `tauriWindowChrome.ts` (Task 1) pulls
  the REAL `@tauri-apps/api/window`/`@tauri-apps/api/webview` packages into
  `tauriAttach.ts`'s import graph via `tauriAttach.ts -> ./api -> ./api/misc.ts`.
  Those packages' exported classes extend `Resource` from `@tauri-apps/api/core` at
  module-evaluation time; `tauriAttach.test.ts`'s existing minimal `@tauri-apps/api/core`
  mock (`{isTauri, invoke}`) doesn't provide `Resource`, so every test crashed with
  `TypeError: Class extends value undefined is not a constructor` before any
  assertion ran.
- **Fix:** Added matching `jest.mock('@tauri-apps/api/window', ...)` /
  `jest.mock('@tauri-apps/api/webview', ...)` calls to `tauriAttach.test.ts`,
  returning `getCurrentWindow`/`getCurrentWebview` stubs with a `jest.fn()` per
  window-chrome verb — the same shape `windowChrome.test.ts` uses.
- **Files modified:** `src/preload/__tests__/tauriAttach.test.ts` (not in the plan's
  `files_modified` list, but required by the plan's own Task 2/3 acceptance criteria
  that this suite stay green).
- **Commit:** `9b2c00e2`

### Notable adaptation (not a deviation from behavior, but from the plan's test-environment assumption)

Task 3's action text parenthetically labels the new test file "(jsdom)". This
project's preload jest project (`src/preload/jest.config.js`) sets no `testEnvironment`
override, so it defaults to Jest's `'node'` environment — `jest-environment-jsdom` is
not installed anywhere in this repo (confirmed: no match in `package.json`;
`src/frontend/jest.config.js` documents the same constraint for its own project).
Installing it would be a package-manager install, which is excluded from executor
auto-fix (Rule 3 carve-out) and would require a human package-legitimacy checkpoint
for a one-file test dependency. Instead, `framelessRuntime.test.ts` builds minimal
manual `document`/`Element`-shaped stubs (a `FakeElement` class with `parentElement`/
`closest()`/`matches()`, plus a `getComputedStyle` global returning
`-webkit-app-region`), mirroring `tauriAttach.test.ts`'s own established
`installWindowStub()` pattern for the same underlying reason. All 17 REQ-34.1-03 tests
pass against this stand-in DOM; the implementation code itself (`resolveDragRegion` in
`tauriWindowChrome.ts`) is written duck-typed against `parentElement`/`closest()`
rather than `instanceof Element`, so it works identically against the stub and a real
browser DOM.
