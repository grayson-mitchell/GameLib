<mechanism_decision>
READ THIS BEFORE WRITING ANY CODE. It is the design spine of this plan, and it corrects a false
claim an earlier revision of this plan carried.

**A prior draft of this plan asserted that Tauri v2 exposes no runtime setter for `titleBarStyle`.
That claim was FALSE and was verified false against the installed tree.** It is recorded here so
nobody re-derives it:

  node_modules/@tauri-apps/api/window.d.ts:71
    type TitleBarStyle = 'visible' | 'transparent' | 'overlay'
  node_modules/@tauri-apps/api/window.d.ts:1185
    setTitleBarStyle(style: TitleBarStyle): Promise<void>   // "macOS only", @since 2.0.0
  node_modules/@tauri-apps/api/window.js:1541-1546
    invoke('plugin:window|set_title_bar_style', { label: this.label, value: style })

It is a real, capability-gateable Tauri command. The autogenerated permission file exists at
`<cargo-target>/build/tauri-*/out/permissions/window/autogenerated/commands/set_title_bar_style.toml`
and declares `allow-set-title-bar-style` / `deny-set-title-bar-style`. It is simply not granted in
`src-tauri/capabilities/default.json` yet. Task 1 grants it.

**THE MECHANISM (one mechanism, not two competing ones):**

macOS titlebar state is a pure function of `settings.framelessWindow`:

  framelessWindow: false  ->  TitleBarStyle 'visible'  — normal native macOS title bar
  framelessWindow: true   ->  TitleBarStyle 'overlay'  — transparent bar overlaid on content

The native traffic lights are present in BOTH states. That is the whole point: D-06's reversal
demands the traffic lights never disappear, and REQ-34.1-03 demands the setting be honoured at
runtime and actually affect decorations. Both are satisfied simultaneously. There is no forced
consequence, no decoration-inert setting, and no dead-feeling control.

`setDecorations` is NOT used on macOS at all. `setDecorations(false)` strips the traffic lights —
that is the original defect, not an alternative implementation of it.

**OWNERSHIP SPLIT — which mechanism owns what:**

- `tauri.conf.json`'s `titleBarStyle` owns the CREATION state ONLY, i.e. the state the window is in
  before any JavaScript has run. Its value must therefore equal the state corresponding to
  `framelessWindow`'s DEFAULT, which is `false`. So the config value is `"Visible"`.
- `setTitleBarStyle` owns every state after creation: the pre-paint apply from `tauriAttach.ts`, the
  post-hydration re-apply from `index.tsx` (the CR-02 fix), and every user toggle.

**Why the config value is `Visible` and NOT `Overlay`.** `Overlay`-as-a-constant only made sense
under the false "no runtime setter" premise. `framelessWindow` is OFF by default, so creating the
window in `Overlay` and then immediately driving it to `visible` would introduce a startup flip for
the DEFAULT user — regressing UAT test 3 ("no startup flip"), which passes today and is explicitly
protected by this cycle. With `Visible` as the creation state, the default user's pre-paint apply is
a true no-op: the window is already in the state the setting asks for.

**The one case that still involves a transition** is a user who had `framelessWindow` ON from a
prior session: created `visible`, then driven to `overlay`. That is the SAME timing shape the
current code already has (created decorated, then `setDecorations(false)` pre-paint / post-hydration),
and UAT test 3 measured that shape as flip-free on this hardware — twice, most recently 2026-08-13
("done, no flip") with the CR-02 post-hydration re-apply in place. So there is a strong empirical
prior that this is fine. **It is a prior, not a measurement of the new call.** It goes to plan
34.1-14's live gate as a named item, not into this plan's SUMMARY as a claim.

**GENUINE OPEN QUESTIONS — route to plan 34.1-14, do NOT resolve them here and do NOT let a
plausible answer stand in for an observation.** These cannot be settled statically:

  L2. Does `setTitleBarStyle('overlay')` visibly take effect AFTER window creation, without a
      restart?
  L3. Does that ON transition flicker / jump / show a black frame?
  L4. Is `setTitleBarStyle('visible')` reachable at runtime — i.e. can Overlay be turned back OFF,
      or is it one-way once applied?
  L5. Does that OFF transition flicker?
  L6. With `framelessWindow` ON from a prior session, is there a visible startup flip
      (visible -> overlay)? UAT test 3 non-regression under the NEW mechanism.
  L7. With `framelessWindow` OFF, is startup completely flip-free? (Expected true by construction —
      config and setting agree — but expectation is not observation.)
  L8. In `overlay` state, does navbar DRAG still move the window, INCLUDING when the window is not
      focused? Tauri's own `TitleBarStyle::Overlay` doc comment names this caveat by name:
      "you can't drag the window when it's not in focus" (tauri-apps/tauri#4316). UAT test 4 is the
      highest-risk item in this slice and it passed twice — this is the specific way Overlay could
      regress it.
  L9. In `overlay` state, does the window TITLE string draw over the navbar? If yes,
      `"hiddenTitle": true` is the recorded remedy, applied then, not now.

Each is a SEPARATE numbered item. This phase's own recorded lesson: a compound test item resolves to
a single pass/fail and the un-run half disappears — UAT test 5 recorded a PASS across two sessions
while the branch it existed to cover was never exercised. Split at the branch boundary.

**IF LIVE INVESTIGATION PROVES `setTitleBarStyle` UNUSABLE** (L2 or L4 fails, or L3/L5 show an
unacceptable flicker), the finding must be recorded as **the actual evidenced reason, with the
observation quoted verbatim**. It must NEVER be recorded as a blanket "Tauri has no API for this" —
that claim is false and writing it into the ledger is the failure this revision exists to prevent.
Only in that case does the constrained option set in plan 34.1-14 Task 2 apply.
