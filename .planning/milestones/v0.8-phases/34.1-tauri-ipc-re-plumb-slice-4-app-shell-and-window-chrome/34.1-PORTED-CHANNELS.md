# Phase 34.1 — Declared Ported-Channel List

**Purpose:** The enumerated set the next Tauri phase (34.2+) starts from, mirroring how Phase 33
itself started from `32-PORTED-CHANNELS.md`. This is the artifact SEAM.md §1 cross-references by
filename. It describes what actually shipped in 34.1-01..34.1-07 — verified row by row against
all seven plan SUMMARY.md files, not against this phase's original planned intent. Reconciliation
findings are in section 7; no drift was found between the plan's declared 33-channel list and what
shipped.

---

## 1. Port kinds

This phase introduces a **third** kind to the vocabulary Phases 30–33 established. All three:

- **`sidecar invoke`/`send`** — the channel is registered on the sidecar's `ipcMain` and the
  renderer reaches it over the Tauri transport (Phases 30–33's kind).
- **`rustInvoke`** — the sidecar asks the Rust shell via `dispatch_rust_channel` (Phase 28+).
- **`renderer-side (Tauri JS)`** — **new this phase (D-02)** — the preload/`window.api`
  implementation calls a Tauri JS API (or, for `gamepadAction`, plain DOM APIs) directly with no
  transport hop. The sidecar registers nothing for the channel, and `UNPORTED_CHANNEL_MARKER` is
  never reached because the preload short-circuits first.

**The Phase 35 completion gate reads "the channel has real behavior under Tauri," not "the
sidecar owns it."** A renderer-side channel counts as ported on that reading — there is no
sidecar registration to point to for these 13 rows, and that absence is not a gap.

## 3. Declared logged no-ops and declared-empty returns

- **`lock` / `unlock`** — `powerSaveBlocker`, carried forward unchanged from Phase 33 D-08. The
  user-visible symptom: the system may sleep during long depot downloads. `unlock` logs a
  `console.warn` naming the gap every time it actually stops a tracked blocker; `lock` calls the
  no-op `powerSaveBlocker.start()` silently, matching the underlying Phase 33 stub's own behavior.
- **`setTitleBarOverlay`** — no native overlay left to target under D-06 (GameLib's own titlebar
  buttons render on every platform once frameless, so there is no OS overlay surface left to set).
  Declared logged no-op (D-13).
- **`getWebviewPreloadPath`** — declared-empty `''` return. Tauri has no `<webview>` tag; the
  login-webview story (navigation interception, OAuth redirect capture, session/cookie access) is
  Phase 34.4's, not this slice's.
- **`isFullscreen`** — declared-false under Tauri. The Electron body reads two Node-only env/CLI
  signals (`isSteamDeckGameMode || isCLIFullscreen`) with no webview equivalent; this channel
  returns `window.isSteamDeckGameMode === true` and nothing else. **This is NOT a
  window-fullscreen query and was deliberately not "improved" into one** — it never calls the
  Tauri Window API, by construction, proven by a dedicated test (plan 34.1-03).

## 4. Declared divergences from the Electron build

- **D-06** — when frameless is on, GameLib's own buttons render on ALL platforms under Tauri,
  where Electron uses native overlay controls on macOS/Windows. Declared, not discovered.
- **D-05 superset** — the Tauri path applies `framelessWindow` live (`setSetting`'s Tauri branch
  re-applies decorations on toggle), where Electron's own Settings label for the same toggle says
  "requires restart."
- **D-10** — gamepad directional navigation is computed geometrically by GameLib (a
  nearest-in-direction algorithm over `getBoundingClientRect()`) rather than by Chromium's spatial
  navigation, which WKWebView/WebView2 do not implement.
- **Frameless drag region — open question, not resolved.** Whether the drag region works at all
  depends on whether the platform webview exposes `-webkit-app-region` in computed styles; plan
  34.1-03 implements a `.Sidebar` selector fallback for webviews that don't expose it. Neither the
  primary path nor the fallback has been observed running against a real webview.

## 6. Sign-off — the honest statement

Every automated test in this phase proves **wiring**: that the right Tauri API was called with
the right arguments. **None proves the window on screen actually did the thing.** Nobody has run
this build and looked at it. The frameless toggle applying, the titlebar buttons moving the
window, the tray appearing and changing colour, gamepad navigation working, and how macOS traffic
lights versus custom buttons look are all **unobserved**. `cargo check` proves the tray code
compiles; it proves nothing about a tray existing. Do not read "wired and unit-proven" as "seen
working" — that is exactly how G-30-02 was declared fixed twice while the live build hung.

The channel count is **33**, matching `.planning/IPC-PORT-INVENTORY.md`'s corrected
`## Phase 34.1 — Slice 4 — app shell and window chrome (33 channels)` heading exactly — set
equality, not just count equality: every name in that heading's channel list appears exactly once

D-14-reassigned Wine-tooling channel (see §5) is confirmed absent from both.

  renderer-side exactly as planned.
- Plan 34.1-05's `gamepadAction` shipped renderer-side exactly as planned, with the added detail
  (not contradicting the plan) that it calls no Tauri API at all — pure DOM.
- Plan 34.1-07's `createNewWindow`/`showAboutWindow` shipped renderer-side exactly as planned,
  resolving 34.1-RESEARCH.md's Open Question 1.
- Plan 34.1-04's 18 sidecar-routed channels (8 invoke + 10 send) shipped exactly as planned, with
  `set-connectivity-online` confirmed live-without-re-registration rather than newly registered.
- Plan 34.1-06's `changeTrayColor` shipped as a sidecar send that forwards to the slice's one new
  `tray_set_icon` rustInvoke arm — a more specific claim than the plan's flat "sidecar send"

  `changeTrayColor`'s proof level in advance ("Rust half is compile-gate only").
