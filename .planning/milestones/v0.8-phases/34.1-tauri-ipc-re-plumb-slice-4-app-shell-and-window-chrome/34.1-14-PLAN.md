    option sets and which one applies is determined by observation, not in advance.**

    Background, verified against the installed tree (`@tauri-apps/api` 2.11.1):
    `Window.setTitleBarStyle(style: 'visible' | 'transparent' | 'overlay')` exists
    (`node_modules/@tauri-apps/api/window.d.ts:1185`, implemented as
    `invoke('plugin:window|set_title_bar_style', ...)` in `window.js:1541`), backed by a real Tauri
    command with its own capability permission, which plan 34.1-10 granted. So macOS CAN change its
    titlebar at runtime, and plan 34.1-10 wires `framelessWindow` ON -> `'overlay'`,
    OFF -> `'visible'`, with the native traffic lights present in both states.

    **A prior draft of this plan told the operator the opposite** — that no runtime setter existed,
    that macOS overlay was therefore permanent, and that `framelessWindow` was necessarily
    decoration-inert on macOS. That was false, and it would have forced a permanent, ledgered
    product decision (hide the toggle / ship apologetic copy / ship a dead-feeling control) to work
    around a limitation that does not exist. It is recorded here so the false framing is not
    reconstructed from memory. Do not present it as context.

    What the setting does on macOS if the mechanism works: exactly what it does on Windows and
    Linux — it changes the window's decorations. The macOS realisation differs (the OS keeps
    drawing the traffic lights either way, so GameLib does not draw its own), but the setting is
    honoured, which is REQ-34.1-03's actual intent.

    Relevant prior context, unchanged: the 2026-07-25 session resolved "stop investing in frameless
    — candidate for removal, not a committed removal." The D-06 reversal supersedes that stance ON
    MACOS specifically, because overlay mode moves work toward the OS providing the controls rather
