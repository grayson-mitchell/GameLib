## Pending row — blocking or not?

| Option | Description | Selected |
|--------|-------------|----------|
| Blocking — join D-25's disabled Install | User opened the options dialog to choose; letting them commit before the choice exists hands them the macOS install, which is what quick install would have done. Reuses the existing mechanism. Requires a bounded terminal state so offline never wedges. | ✓ |
| Non-blocking — Install stays live | Row shows pending, Install remains enabled targeting macOS native. Never wedges, but silently rewards impatience with the wrong platform and makes the pending row decorative. | |
| Blocking only when it can still change | Disable only on macOS where the answer alters the option set; never on Windows/Linux hosts. Narrower blast radius, more branches in an already 96-combination gate. | |

**User's choice:** Blocking — join D-25's disabled Install
**Notes:** Later reinforced by the D-02 finding — the eligibility probe already disables Install for exactly this window on macOS, so blocking costs zero additional dead time rather than introducing new latency.

## Live refresh vs. dialog-local fetch

**First framing was withdrawn.** The original question offered three ways for the dialog to *learn* the signal landed (dialog-local probe / subscribe to the shared store / rewrite the `gameInfo` snapshot). The user asked whether the eligibility probe already fetches `appdetails` — it does, which invalidated the premise that a new signal path was needed at all. Question reformulated.

| Option | Description | Selected |
|--------|-------------|----------|
| Widen the eligibility verdict | Add the depot signal to the verdict that already awaits its capture. No new IPC, no second fetch, both runtimes at once via the shared handler. Scope item (c) dissolves. | ✓ |
| Widen the verdict AND keep the `gameInfo` path | Verdict authoritative once resolved; `gameInfo` seeds the first frame. Framed at the time as two-sources drift. | |
| Separate dialog-local depot probe | Independent hook over its own IPC. Cleaner separation, but duplicates latency awaiting the same fetch. | |

**User's choice:** Widen the eligibility verdict
**Notes:** The user's question was the turning point of the discussion. Verified chain: `shouldProbeEligibility` → `isSteamBottleEligible` → `checkBottleEligibility()` → `await ensurePlatformsCaptured()` → `fetchMetadataIfNeeded()`, which is the same call that writes `is_windows_native`. Option 2's "drift" framing was later corrected — see the Rework entry below.

## Terminal state on fetch failure

| Option | Description | Selected |
|--------|-------------|----------|
| Fail open — offer Windows when unknown | Known-absent still omits Windows; only the unknown case offers it. Matches the null-set domain fact. Risk: a genuinely mac-only game gets an option that fails later at install time. | ✓ |
| Fail closed — `readonly-macos`, silent | Byte-consistent with `applyEligibilityFailure` and 34.13's UI-SPEC. Cost: preserves the current defect for offline users — exactly what the phase exists to end. | |
| Stay unresolved, re-enable Install, offer retry | Dialog stays honest and never wedges, but retry is new vocabulary 34.13 explicitly declined. | |

**User's choice:** Fail open — offer Windows when unknown
**Notes:** A deliberate departure from the house fail-closed default, documented as such so a later reviewer does not "correct" it back. Rationale: eligibility failing closed is safe (you get a native install); depot availability failing closed loses an option that exists. Flagged during discussion that `steamPlatformRow.test.ts`'s `treatsAbsentAsAvailable` saboteur must be reconciled, since "absent" now splits into captured-absent and uncaptured.

## Rework — how much of the phase should be async

**Triggered by the user's challenge:** *"we are talking about a probe to determine what platforms are supported. doesn't that info already exist? (when you look at your library it already states what platforms (OSs) are supported…)"*

Investigation found the premise refuted but productive:
- `PlatformSupport.tsx:23` renders the Windows glyph **unconditionally** and never reads `is_windows_native` — it asserts an assumption, not a signal. Its macOS/Linux glyphs share the same cold-cache blindness.
- **But** `GameInfo.steamPlatformsCaptured` *is* already populated for every game at library-sync time (`library.ts:791`), so the modal already has the distinguishing signal in scope. This made the earlier "widen the verdict" answer incomplete and required re-asking.

| Option | Description | Selected |
|--------|-------------|----------|
| Seed from `gameInfo`, resolve from the verdict | `gameInfo.steamPlatformsCaptured` decides the first frame; the widened verdict resolves live; fail open at timeout. Keeps all prior decisions intact. Mirrors `initialEligibilityState` → `applyEligibilityResponse`. | ✓ |
| Synchronous only — no probe, no pending row | Read the field; uncaptured offers Windows immediately. Smallest diff, correct on first frame, but drops the blocking decision and answers on an assumption when the truth was a second away. | |
| Synchronous, but block until the existing probe resolves | No verdict widening; block while pending then fall open. Cheapest middle path, but the row never learns the true answer, so a captured-Windows-less game still gets offered Windows. | |

**User's choice:** Seed from `gameInfo`, resolve from the verdict
**Notes:** This retroactively vindicates the "widen AND keep the `gameInfo` path" option rejected earlier — seed and resolution are the same fact at two times, not two competing sources, which is the pattern `steamEligibilityProbe.ts` already ships.

## UAT forcing procedure

| Option | Description | Selected |
|--------|-------------|----------|
| Cache surgery + network toggle | Quit, delete one appId key from `steam_metadata.json`, relaunch. Network up → resolves-captured; network down → fail-open branch. No product-code test seam; warm library stays warm. | |
| Dev-only env override | e.g. `GAMELIB_FORCE_UNCAPTURED=<appId>`. Scriptable and network-independent, but ships a test seam that must be proven inert in release builds. | |
| You decide | Claude's discretion — planning picks and writes it into the gate steps. | ✓ |

**User's choice:** You decide
**Notes:** Requirement retained regardless of mechanism (CONTEXT.md D-08): the gate must produce **both** outcomes at dialog-open time, since with one probe fired at open, reconnecting mid-dialog does not re-probe.

## Claude's Discretion

- Internal verdict shape — 5th `SteamPlatformRowMode` member vs. overlay field on the existing four.
- The pending row's rendered form — constrained to reusing an existing in-dialog pattern.
- UAT forcing mechanism — cache surgery recommended; dev-only override acceptable if proven inert in release builds.

## Deferred Ideas

- `PlatformSupport.tsx`'s hardcoded Windows glyph and its cold-cache-blind macOS/Linux glyphs — the same fact on a different surface with the opposite failure mode. Offered to the user as a scope expansion and declined in favour of holding the ROADMAP's route fence.
- Whether widening `SteamBottleEligibilityVerdict` disturbs the quick-install path (`startSteamQuickInstall` consumes the same type).
- Whether the phase adds zero new user-facing strings, which would take it outside the standing localisation gate.
- Retry affordance for a failed depot fetch — unnecessary under fail-open.
- Tri-state depot signal — rejected in favour of two booleans.
