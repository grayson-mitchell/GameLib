<domain>
## Phase Boundary

On macOS, the Steam **"Install with options…"** dialog stops silently withholding the
Windows/wine option from games that have a Windows build.

The install-modal gating layer learns the difference between *"this game has no Windows
depot"* and *"we have not fetched the depot signal yet"*, and stops collapsing both into
one `false`.

**Route fence (from ROADMAP, unchanged):** the **"Install with options…"** route only.
Per `34.13 D-23`, plain Install short-circuits to quick install
(`openInstallGameModal:321-324`); the options dialog is reached only via
`openSteamInstallOptions`. No other surface is in scope — see Deferred for the
`PlatformSupport.tsx` contradiction this discussion uncovered and deliberately fenced out.

**Not in scope:** forcing a Windows install of a game with a *confirmed* absent Windows
depot. `34.13`'s Deferred Ideas rules that out by construction and this phase does not
reopen it. 34.14 only addresses the case where the answer is **not yet known**.

</domain>

<decisions>
## Implementation Decisions

### Pending behaviour

- **D-01: While the depot signal is unresolved, the dialog's Install button is DISABLED,
  joining `34.13 D-25`'s existing mechanism rather than introducing a second one.**
  Rationale: the user opened "Install with options…" specifically to choose a platform.
  Letting them commit before the choice exists hands them the macOS install — exactly what
  quick install (`34.13 D-23`) would have done — which makes the dialog pointless.
  **This costs zero additional dead time:** on macOS the eligibility probe is *already*
  running and *already* disabling Install for precisely this window (see D-02's chain).

### Signal path

- **D-02: The depot signal reaches the platform row by WIDENING the existing
  `SteamBottleEligibilityVerdict` round-trip. No new IPC, no second probe, no additional
  fetch, no added latency.**

  Verified at HEAD during discussion — the eligibility probe *already forces and awaits the
  exact fetch that captures the depot signal*:
  1. `shouldProbeEligibility` (`steamEligibilityProbe.ts:62-72`) returns `true` for
     `runner === 'steam' && action === 'install'` on any non-`win32`/`linux` host — so it
     **always** runs on macOS for exactly this route.
  2. → `isSteamBottleEligible` → `getSteamBottleEligibilityVerdict` →
     `checkBottleEligibility()` (`games.ts:1628`) → `await ensurePlatformsCaptured()`.
  3. `ensurePlatformsCaptured()` (`games.ts:1655`) awaits `fetchMetadataIfNeeded()` and
     bounded-polls until `platformsCaptured === true` or `METADATA_FETCH_TIMEOUT_MS`.
     That is the same call that writes `is_windows_native` (`games.ts:647`).
  4. `installFormIpc.ts:42` states the link outright: *"the eligibility path can reach an
     outbound `appdetails` request built from the id."*

  Widening is the established idiom for this type, not a new pattern —
  `installFormIpc.ts:37-39`: *"One round-trip closes both — 34.13-11 reads `eligible`,
  34.13-09 reads `wineVersion` / `bottleName`."*

  **Both runtimes land at once.** `installFormIpc.ts` is one shared handler body imported by
  BOTH Electron `main.ts:944` and the Tauri sidecar, deliberately so the two are
  *"physically incapable of drifting."* Planning MUST NOT fork it.

- **D-03: The widened verdict carries TWO BOOLEANS — `hasWindowsDepot` and
  `platformsCaptured` — not a tri-state.** Mirrors what `SteamMetadataCacheEntry` already
  stores and matches the in-repo `AppleWikiInfo.tsx:67` precedent
  (`steamPlatformsCaptured === true`).

  **Obligation this shape creates:** the `(hasWindowsDepot: true, platformsCaptured: false)`
  combination is representable but meaningless. Planning MUST establish a single enforced
  seam — the `resolveSteamSectionGating` input is the natural one — that guarantees no
  consumer reads `hasWindowsDepot` without first checking `platformsCaptured`. A second
  reader anywhere is the drift `steamPlatformRow.ts`'s own header warns against
  (*"the single place in the codebase where Windows-depot availability is decided"*).

- **D-05: Seed synchronously from `gameInfo`, resolve live from the verdict.**
  `GameInfo.steamPlatformsCaptured` **already exists and is already populated for every
  game at library-sync time** (`library.ts:791` —
  `steamPlatformsCaptured: cachedMeta?.platformsCaptured ?? false`), so the modal already
  has it in scope at open.

  - **Seed:** `gameInfo.steamPlatformsCaptured` decides the FIRST frame, so an
    already-captured game never flashes a pending state at all.
  - **Resolve:** the widened verdict (D-02) supplies the live answer, because `gameInfo`
    is frozen at open time and can never self-heal (three writers, all write-at-open:
    `InstallGameModal.ts:293`, `:326`, `:336`).

  This is the shape `steamEligibilityProbe.ts` already ships — `initialEligibilityState`
  seeds synchronously, `applyEligibilityResponse` resolves. Seed and resolution are **the
  same fact at two times**, not two competing sources.

  **This RESOLVES ROADMAP scope item (c) by dissolution.** Nothing needs re-snapshotting,
  no fourth writer is added to `gameInfo`, and the shared-store staleness class that
  `closeInstallGameModal`'s comment records (*"A stale degrade record would show one game's
  library warning on the next game's dialog"*) is never reintroduced.

### Failure handling

- **D-04: FAIL OPEN on unknown. Confirmed-absent still omits Windows.**
  When the probe resolves terminally with `platformsCaptured` still `false` — offline,
  `appdetails` errored, or the 15s poll expired — the row **offers Windows**.

  - `platformsCaptured === true && hasWindowsDepot !== true` → genuinely absent → **omit**
    Windows (34.13's fence holds unchanged).
  - `platformsCaptured === false` → unknown → **offer** Windows.

  Rationale: per the operator-locked domain constraint below, fail-closed would withhold
  the Windows option from a game that almost certainly has a Windows build — i.e. applying
  34.13's fail-closed precedent faithfully would *reproduce the very defect this phase
  exists to end*, permanently, for offline users.

  **This deliberately diverges from `applyEligibilityFailure` (`steamEligibilityProbe.ts:126`),
  which resolves fail-CLOSED and silent with no retry per 34.13's UI-SPEC (T-34.13-11-01).**
  The divergence is intentional and must not be "corrected" toward the precedent: bottle
  eligibility failing closed is safe (you get a native install); depot availability failing
  closed is not (you lose an option that exists).

### Scope fences

- **D-06: Route fence holds — "Install with options…" only.** `PlatformSupport.tsx` is out
  of scope even though this discussion proved it contradicts the modal (see Deferred).

- **D-07: Write NO copy asserting a game is macOS-only.** Carried forward from ROADMAP
  scope item (d) and reaffirmed. Per the domain constraint that branch is near-dead; a
  sentence for it would be dead weight that reads as false whenever it appeared.
  Note this phase may add **zero** new user-facing strings — see Deferred.

### UAT

- **D-08: The UAT gate MUST specify a concrete, repeatable forcing procedure that produces
  BOTH outcomes at dialog-open time.** The cold-cache window is not reproducible on demand
  from a warm library, so a gate without an explicit forcing step is authored against a
  condition that never renders.

  Two branches need coverage, and note that with a single probe fired at open,
  **reconnecting mid-dialog does not re-probe**:
  1. resolves-captured → Windows entry appears, Install enables.
  2. resolves-uncaptured → fail open, Windows offered anyway.

  Mechanism is Claude's Discretion (below).

### Claude's Discretion

- **Internal verdict shape** — whether "pending" becomes a 5th `SteamPlatformRowMode`
  union member or an overlay field on the existing four. Lean recorded during discussion:
  the 5th mode makes TypeScript exhaustiveness find every consumer for you, at the cost of
  growing the 8-row matrix to 9. Either is acceptable; whichever is chosen must keep
  `readonly-macos` and the pending state **distinguishable**, since collapsing them is the
  exact defect being fixed.
- **The pending row's rendered form** — constrained to **reusing an existing in-dialog
  pattern** (`EligibilityLoadingRow` is the obvious analog) rather than inventing new
  visual vocabulary. `--skip-ui` was chosen for planning, so no UI-SPEC will arbitrate this.
- **UAT forcing mechanism** — recommended default from discussion: quit the app, delete one
  appId key from the on-disk `steam_metadata.json`
  (`CacheStore<SteamMetadataCacheEntry>('steam_metadata', …)`, `electronStores.ts:27`),
  relaunch, open "Install with options…"; run once with network up and once with network
  down / `appdetails` blocked. Targets one game so the warm library stays warm, and ships
  no test seam in product code. A dev-only env override was the alternative; if chosen, it
  must be proven inert in release builds.

</decisions>

## Existing Code Insights

### Reusable Assets
- **`steamEligibilityProbe.ts`** — a complete, shipping analog of everything this phase
  needs: a pure state machine, a synchronous seed, a reducer-level `appName` guard against
  stale cross-game responses (T-34.13-11-02), effect-cleanup as a secondary control, and a
  hook. Copy the shape; do not invent a parallel one.
- **`SteamBottleEligibilityVerdict`** — already an object designed to close multiple reads
  in one round-trip. Widening it is idiomatic here, not a workaround.
- **`GameInfo.steamPlatformsCaptured`** — already populated for every game at sync
  (`library.ts:791`); needs no backend work to become available to the modal.
- **`installFormIpc.ts`** — a single handler body shared by Electron and the Tauri sidecar,
  so one edit covers both runtimes.

### Established Patterns
- **Extract pure logic into a sibling module, not `index.tsx`.** The Frontend jest project
  has no jsdom and no CSS transform, and `index.tsx`'s first line is `import './index.scss'`
  — any test importing anything from it dies at that import. `steamPlatformRow.ts`,
  `steamSectionGating.ts`, `steamEligibilityProbe.ts` all exist for this reason. New logic
  must follow suit or it cannot be tested at all.
- **Explicit skip-lists over negated comparisons.** `shouldProbeEligibility` is written as
  an explicit `win32`/`linux` skip, never `platform !== 'darwin'`, so an unrecognised host
  still asks the backend. `resolveSteamSectionGating` uses the same convention.
- **Fail-closed as the house default** — which D-04 deliberately departs from for this one
  signal. The departure must be documented in code, or a later reviewer will "fix" it back.

### Integration Points
- `resolveSteamSectionGating`'s input struct gains the captured signal; its
  `SteamSectionGatingInput.hasWindowsDepot` doc-comment (`steamSectionGating.ts:107-115`)
  becomes stale on contact and must be rewritten, not left.
- The verdict flows: `installFormIpc` → `isSteamBottleEligible` → `useSteamBottleEligibility`
  → `index.tsx` → `resolveSteamSectionGating` → `selectSteamPlatformOptions`.

### ⚠ Planning landmines (each verified at HEAD during discussion)

1. **A green test currently certifies the defect.**
   `steamPlatformRow.test.ts` ships a saboteur named `treatsAbsentAsAvailable` that pins
   `gameInfo?.is_windows_native !== false` as *the wrong answer*. Under D-04, "absent"
   SPLITS: captured-and-absent must still omit Windows (that saboteur stays valid), while
   uncaptured must now offer it. If that test's fixtures are uncaptured, it will assert the
   old semantics and pass — the same trap as the cookie-domain leading-dot blindness, where
   a passing test asserted the blindness as correct. **Planning must reconcile this test
   explicitly and say which fixtures changed.**

2. **A shipped doc-comment states a premise this phase falsifies.**
   `steamEligibilityProbe.ts:161-163` says `platformRow` is *"deliberately NOT suppressed —
   it is genuinely synchronous (D-03/D-17/D-19)."* It is **not** synchronous:
   `hasWindowsDepot` rides an async `appdetails` fetch. That comment must be corrected, not
   worked around.

3. **The timeout path returns a verdict computed on uncaptured data.**
   `ensurePlatformsCaptured` polls to `METADATA_FETCH_TIMEOUT_MS` and then returns anyway;
   `checkBottleEligibility` proceeds regardless. So the widened verdict MUST carry the
   captured flag — widening with a depot boolean alone collapses the timeout case straight
   back into the false-negative this phase exists to fix.

4. **The 8-row / 96-combination matrix test is load-bearing.** `steamSectionGating.test.ts`
   proves the current verdict exhaustively. Any new mode or field expands it; a plan that
   adds a state without extending that proof has not shipped the state.

5. **`installFormIpc.ts` must not be forked.** It exists specifically so Electron and Tauri
   *"are physically incapable of drifting."* Two copies of the widened verdict would undo
   that guarantee.

<specifics>
## Specific Ideas

- **Operator-locked domain constraint (2026-08-16):** mac-only Steam games are effectively a
  **null set**. Games are either ported to macOS or dual-developed; a macOS-native-only
  title is unlikely to be sold on Steam at all. Therefore `platformRow: 'readonly-macos'` is
  in practice a **synonym for "the depot signal has not been fetched yet"**, and any copy
  asserting *"this game only has a macOS build"* would read as false nearly every time it
  rendered. This is the fact that superseded 34.13's B-WR-06 and created this phase.

- **The two surfaces already contradict each other.** Discovered during this discussion:
  `PlatformSupport.tsx:23` renders the Windows glyph **unconditionally** — its own
  doc-comment says *"Windows is the implicit baseline (always shown)"* — and never reads
  `is_windows_native`. So the game page asserts Windows exists while the install modal
  withholds the Windows option, for the same game, in the same session. One fails open, the
  other fails closed. This is a direct argument that D-04's fail-open makes the modal
  **consistent** with the app's existing stance rather than an outlier.

- **34.13 flagged this exact question and got the answer wrong.** `34.13 D-17` said:
  *"The form must only offer Windows when the game actually HAS a Windows depot. Planning
  must establish where that signal comes from; … whether Windows availability is already
  captured is an open planning question, not an assumption."* It was answered with
  default-deny. That answer is the defect 34.14 fixes — the question was asked correctly and
  resolved incorrectly.

- **34.13's review already fought half this battle and won it.** `library.ts:764-777`
  records WR-16: `is_windows_native` is deliberately NOT defaulted to `false` at the
  `GameInfo` boundary, precisely so *"the renderer could … tell a cold-cache game from a
  confirmed Windows-less one."* The three-valued contract was preserved correctly;
  `steamPlatformRow.ts` simply never reads the distinction. **This phase is largely about
  consuming a distinction the data layer already maintains.**

</specifics>

<deferred>
## Deferred Ideas

- **`PlatformSupport.tsx`'s hardcoded Windows glyph** — it asserts Windows support for every
  game without reading any signal, and its macOS/Linux glyphs share the same cold-cache
  blindness this phase fixes in the modal. Fenced out of 34.14 by D-06 (route fence). Worth
  its own follow-up so both surfaces tell the same truth.
- **Whether widening `SteamBottleEligibilityVerdict` disturbs the quick-install path** —
  `startSteamQuickInstall` consumes the same verdict type (`34.13 D-23`/`D-24` degrade
  logic). Raised but not explored in discussion. Planning should confirm the widened type is
  additive there; if it is not, that is a finding, not a scope change.
- **Whether this phase adds zero new user-facing strings** — D-07 forbids mac-only copy, and
  fail-open may need no copy at all. If the phase ships no new strings it falls outside the
  standing localisation gate entirely; if it ships even one, that gate is BLOCKING. Planning
  must state which.
- **Retry affordance for a failed depot fetch** — considered and not taken; D-04's fail-open
  makes a retry control unnecessary, and 34.13's UI-SPEC explicitly declined retry
  vocabulary for the sibling probe.
- **Tri-state (`'available' | 'absent' | 'unknown'`) for the depot signal** — considered and
  rejected in favour of D-03's two booleans, which match the existing store and the
  `AppleWikiInfo.tsx` precedent.
