- **D-01: While the depot signal is unresolved, the dialog's Install button is DISABLED,
  joining `34.13 D-25`'s existing mechanism rather than introducing a second one.**
- **D-02: The depot signal reaches the platform row by WIDENING the existing
  `SteamBottleEligibilityVerdict` round-trip. No new IPC, no second probe, no additional

  handler body imported by BOTH Electron `main.ts:944` and the Tauri sidecar. Planning MUST
  NOT fork it.

  `platformsCaptured` — not a tri-state.** Obligation: the `(hasWindowsDepot: true,
  platformsCaptured: false)` combination is representable but meaningless. Planning MUST
  establish a single enforced seam — the `resolveSteamSectionGating` input is the natural

  two competing sources. Resolves ROADMAP scope item (c) by dissolution — no re-snapshotting,
  no fourth `gameInfo` writer.
- **D-04: FAIL OPEN on unknown. Confirmed-absent still omits Windows.**
  `platformsCaptured === true && hasWindowsDepot !== true` → omit Windows (34.13's fence holds
  unchanged). `platformsCaptured === false` (terminal — offline, errored, or 15s poll expired)
  → offer Windows. Deliberately diverges from `applyEligibilityFailure`
  (`steamEligibilityProbe.ts:126`), which fails CLOSED. The divergence is intentional and must
  not be "corrected" toward that precedent.
- **D-06: Route fence holds — "Install with options…" only.** `PlatformSupport.tsx` is out of
  scope (Deferred).
- **D-07: Write NO copy asserting a game is macOS-only.** This phase may add **zero** new
  user-facing strings — see Deferred and this document's Open Question 4 answer below.
- **D-08: The UAT gate MUST specify a concrete, repeatable forcing procedure that produces
  BOTH outcomes at dialog-open time.** Two branches: (1) resolves-captured → Windows appears,
  Install enables; (2) resolves-uncaptured → fail open, Windows offered anyway. Reconnecting
  mid-dialog does NOT re-probe (single probe fired at open).

## Summary

This phase is a pure internal refactor of an already-shipped, already-tested gating pipeline
(`InstallModal/index.tsx` → `steamEligibilityProbe.ts` → `steamSectionGating.ts` →
`steamPlatformRow.ts`) plus one backend function (`installFormIpc.ts`'s
`getSteamBottleEligibilityVerdict`). No new library is introduced; no new IPC channel is
introduced; no new persisted field is introduced (`GameInfo.steamPlatformsCaptured` and
`SteamMetadataCacheEntry.platformsCaptured` already exist and are already populated for every
game). Every mechanism link CONTEXT.md's discussion verified at HEAD on 2026-08-16 still holds
byte-for-byte today — see the Drift Verification table below, which re-confirms all 24 cited
file:line references plus two additional nuances CONTEXT.md's own citations slightly
over-claimed (documented, not blocking).

This research resolves all 8 open questions CONTEXT.md left to planning with codebase
evidence rather than inference. The single most consequential finding: **`hasSteamWindowsDepot()`
itself does not need to change and its existing tests do not need new fixtures.** Its narrow
contract ("is a Windows depot CONFIRMED") is correct and untouched by this phase. The actual
defect — and the actual fix — lives one layer up, in `resolveSteamSectionGating`'s row-priority
chain, which today has no `platformsCaptured` input at all and therefore cannot distinguish
"never asked" from "asked and the answer is no." The `treatsAbsentAsAvailable` saboteur test
CONTEXT.md flags as risky stays exactly as written; a NEW test, at a NEW seam, is what actually
proves the fix.

The quick-install path (`startSteamQuickInstall`) is confirmed, by exhaustive grep of every
`SteamBottleEligibilityVerdict` consumer in the codebase, to never touch that type at all — it
consumes the plain-boolean `checkBottleEligibility()`/`isBottleEligible()` seam instead. Widening
the verdict is therefore provably additive, not merely assumed additive.

**Primary recommendation:** Choose the 5th `SteamPlatformRowMode` union member (`'pending'`),
not an overlay field — TypeScript's exhaustiveness checking on `selectSteamPlatformOptions`'s
switch statement will force every consumer of that function to make an explicit decision, which
is exactly the safety property D-03's "single enforced seam" obligation is asking for. Thread
`platformsCaptured: boolean` into `SteamSectionGatingInput` and insert one new priority branch in
`resolveSteamSectionGating`'s step 4, between the `effectiveBottleRequired` check and the
`hasWindowsDepot` check. Widen `getSteamBottleEligibilityVerdict()` to also read
`steamMetadataStore.get(appId)?.is_windows_native`/`?.platformsCaptured` AFTER awaiting
`checkBottleEligibility()` — no change to `checkBottleEligibility()`'s own `Promise<boolean>`
signature is needed, which is *why* the quick-install path is unaffected.

### Anti-Patterns to Avoid

- **Do not fold the `platformsCaptured` gate into `hasSteamWindowsDepot()`'s own signature.**
  That function's contract ("is a Windows depot CONFIRMED, given only `is_windows_native`") is
  correct and independently useful. Widening its signature to also take `platformsCaptured`
  would make it a second copy of the priority logic that belongs in
  `resolveSteamSectionGating` — the exact "second copy anywhere else... is precisely the drift"
  warning `steamPlatformRow.ts`'s own header already carries.
- **Do not re-derive `platformsCaptured` locally in `index.tsx`.** It flows from exactly two
  places per D-05: the `gameInfo` seed and the widened verdict resolve. A third local
  computation (e.g., inferring it from `is_windows_native !== undefined`) would be a second,
  driftable definition of the same fact, even though that inference happens to be equivalent
  today (see Common Pitfalls below for why it is fragile, not just redundant).
- **Do not change `checkBottleEligibility()`'s return type.** It is `Promise<boolean>` and
  used by the quick-install/native-install-routing path (`isBottleEligible()` composition,
  `games.ts` `.install()`/`.launch()`/`.uninstall()`), none of which need or want the depot
  signal. Widen only `getSteamBottleEligibilityVerdict()`'s return object, by reading
  `steamMetadataStore` directly after `checkBottleEligibility()` resolves.

## Common Pitfalls

### Pitfall 1 (CONTEXT.md landmine #1, resolved): The `treatsAbsentAsAvailable` saboteur does NOT need new fixtures — but a naive "fix" at the wrong layer would break it

**What's actually pinned:** `steamPlatformRow.test.ts`'s `treatsAbsentAsAvailable` block
(lines 180-190, `[VERIFIED: HEAD]`) exercises ONLY the "never captured" fixtures — `{}` and
`undefined` for `is_windows_native`. It does not touch the separately-tested
`{ is_windows_native: false }` case (lines 52-54, "captured, confirmed absent"). Both fixture
groups already exist as DISTINCT inputs to `hasSteamWindowsDepot`, because `is_windows_native`
is deliberately preserved as three-valued at the write site (`games.ts:647`,
`!!data.platforms?.windows`, always a definite boolean once written) and never defaulted at the
`GameInfo` boundary (WR-16, `library.ts:764-777`, `library.ts:780`).

**The trap:** `hasSteamWindowsDepot({})` correctly returns `false` today, and MUST keep
returning `false` after this phase ships — its contract is "is a Windows depot CONFIRMED
available," and "never captured" is not confirmed-available. If an executor "fixes" D-04's
fail-open requirement by changing THIS function to return `true` for the absent case, that
breaks the function's own contract (it would then conflate "never captured" with "confirmed
present," reopening exactly the hazard `steamPlatformRow.ts`'s own header warns against) AND
does not actually fix anything, because `hasWindowsDepot` alone is never sufficient to decide
fail-open — D-04's rule needs BOTH `hasWindowsDepot` and `platformsCaptured` jointly, and this
function only ever sees one of them.

**How to avoid:** Leave `steamPlatformRow.test.ts` UNCHANGED (fixtures and assertions both).
The fail-open behavior belongs in `resolveSteamSectionGating`'s new priority branch (or an
equivalent composing step), which has both booleans in scope. Prove IT with a new test — most
naturally an extension of `steamSectionGating.test.ts`'s existing matrix harness (see
Validation Architecture below), not a change to `steamPlatformRow.test.ts`.

**Warning sign this was done wrong:** if a diff touches `steamPlatformRow.ts`'s
`hasSteamWindowsDepot` function body or `steamPlatformRow.test.ts`'s existing assertions, stop
and check whether the change actually belongs in `steamSectionGating.ts` instead.

### Pitfall 2 (CONTEXT.md landmine #2, confirmed verbatim): stale doc-comment

`steamEligibilityProbe.ts:161-163` reads, verbatim at HEAD:

> "`platformRow` is deliberately NOT suppressed -- it is genuinely synchronous
> (D-03/D-17/D-19), and hiding it would make the dialog look empty on open, the D-20 corner
> this phase already decided not to create."

This is also echoed in code at `index.tsx:343` ("platformRow is genuinely synchronous and

Both must be corrected: `hasWindowsDepot` now rides an async `appdetails` fetch when

=== 'Windows')` branch — i.e. exactly the inputs that today classify as Row 2 or Row 3.

Two valid design choices, both mathematically precise from the confirmed sweep-construction
code, planner must pick one and state it in the plan:

1. **Naive full doubling:** add `platformsCaptured: [true, false]` as a new axis alongside the
   five existing ones, applied uniformly to all 96 combinations → **192 combinations, 9 rows**.
   Includes the meaningless `(hasWindowsDepot: true, platformsCaptured: false)` combination
   inside the primary sweep (48 of the 192, since `hasWindowsDepot` is a symmetric 2-valued
   axis).
2. **Recommended — clean sweep excludes the meaningless combination, covered separately as a
   defensive test (per OQ5):** exclude `platformsCaptured: false` combinations wherever
   `hasWindowsDepot: true` in the generator → **144 valid combinations, 9 rows**, PLUS 1-3
   dedicated tests in a `describe('defensive normalisation...')` block (matching the file's own
   existing pattern at line 654) proving the excluded combination still resolves safely
   (`platformRow` stays `'pending'`, never leaks into `'selectable'` from a stale
   `hasWindowsDepot: true` alone).

Either way, `ALL_COMBINATIONS.length` assertion (`steamSectionGating.test.ts:327-338`,
currently asserting exactly 96) must be updated to the new total, and the darwin/win32/linux
per-platform sub-counts (currently 48/24/24) must be recomputed and asserted the same way.

### The RED proof

For every new assertion, the plan must specify the known-bad input it fails against, matching
this file's existing "the matrix harness rejects known-bad gating functions"
(`steamSectionGating.test.ts:439`) convention. Concretely:

- **Row 9 (pending) assertion** must fail against a known-bad function that collapses
  `platformsCaptured: false` into `'readonly-macos'` — i.e. literally today's shipped
  `resolveSteamSectionGating`, unmodified. This is the single most important RED proof in the
  phase: **run the NEW Row 9 test against the CURRENT, unmodified `resolveSteamSectionGating`
  before making any code change, and confirm it fails.** If it does not fail against today's
  code, the test is not proving anything new.
- **`hasSteamWindowsDepot`'s existing saboteur tests** must continue to fail against
  `treatsAbsentAsAvailable`/`includesWindowsRegardless`/`readonlyRowLeaksDepot` exactly as they
  do today (unchanged, per Pitfall 1) — this is a NEGATIVE proof: these tests staying green
  and unmodified after this phase ships, with the SAME saboteurs still failing them, is itself
  evidence the fix landed at the right layer.
- **`getSteamBottleEligibilityVerdict`'s widened return** must fail against a known-bad
  implementation that omits `platformsCaptured` from the returned object (proving the field is
  actually read from `steamMetadataStore`, not hardcoded) — e.g. a mutation test asserting
  `platformsCaptured` differs between a mocked captured-cache-entry and a mocked
  uncaptured/absent one.

### What CANNOT be proven by jest

**The cold-cache window itself.** No amount of pure-function testing proves that a REAL,
freshly-opened dialog against a REAL uncaptured Steam library actually renders the pending row
on screen, actually disables the real Install button, actually recovers once the real
`appdetails` fetch lands, and actually falls open after a real 15-second timeout or a real
network failure. This repo has no jsdom (confirmed above) — nothing in `src/frontend`'s test
suite can mount a component tree. This is squarely 34.13's own "34.13-13's blocking manual gate
is the only evidence any of this actually renders" situation, carried forward unchanged.

### The UAT forcing procedure (D-08), verified executable

Confirmed the exact on-disk mechanics of CONTEXT.md's recommended default procedure:

- `steamMetadataStore` is a `CacheStore<SteamMetadataCacheEntry>('steam_metadata', null)`
  (`electronStores.ts:27-30`, `[VERIFIED: HEAD]`), which under the hood is an `electron-store`
  instance constructed with `{ cwd: 'store_cache', name: 'steam_metadata' }`
  (`cache.ts:33-38`, `[VERIFIED: HEAD]`). This resolves to the on-disk file
  **`<userData>/store_cache/steam_metadata.json`**, where `<userData>` is
  `app.getPath('userData')` — on macOS, `~/Library/Application Support/GameLib/` (product name
  `GameLib`, `[VERIFIED: HEAD package.json:24]`).
- The file's JSON shape (confirmed via `CacheStore.set()`/`.delete()`, `cache.ts:108-133`): a
  flat top-level map keyed by the literal appId string (e.g. `"1245620": { "is_windows_native":
  true, "platformsCaptured": true, ... }`), PLUS a separate top-level `"__timestamp"` object
  holding per-key timestamps (electron-store's `accessPropertiesByDotNotation` behavior,
  documented in `cache.ts:150-156`). **Deleting the single top-level `"<appId>"` key (leaving
  the stale `__timestamp` entry, which is harmless) is sufficient**: `steamMetadataStore.get(appId)`
  checks `this.current_store.has(key)` first and returns `undefined` if the key itself is
  absent, regardless of any stale timestamp — confirmed via `cache.ts`'s `get()` implementation.
  This makes `getGameInfo()`'s `cached?.platformsCaptured !== true` guard (`games.ts:538`) true
  again on next read, forcing the exact "never captured" code path.
- **Both runtimes confirmed to share this exact file.** The Tauri sidecar's own store-writing
  paths (`backend/sidecar/fileStore.ts`, `handlers.ts:298`, `storeWriteHandlers.ts:91,357`) all
  construct with the identical `{ cwd: 'store_cache', name: storeName }` pattern, resolved
  relative to the SAME `pathShim.getPath('userData')` (`[VERIFIED: HEAD]` across all four
  files). **The forcing procedure is therefore identical for Electron and Tauri** — no
  runtime-specific variant is needed, only the app-launch command differs (`npm start` vs.
  `pnpm tauri:dev`, per this project's own standing rule to never use bare `tauri dev`).
- **Reconnecting mid-dialog does not re-probe** — confirmed structurally: `useSteamBottleEligibility`'s
  `useEffect` dependency array is `[platform, runner, appName, action]` (`steamEligibilityProbe.ts:299`,
  `[VERIFIED: HEAD]`); none of these change when network state changes mid-session, so the probe
  fires exactly once per dialog-open and never re-fires from a network-state change alone. The
  UAT gate must therefore run each of the two forcing scenarios (network up / network down) as
  a SEPARATE dialog-open, not as a single session with a network toggle mid-dialog.

**Concrete forcing steps for the UAT ledger** (both runtimes, both scenarios):
1. Quit the app entirely.
2. Pick one already-synced, already-captured Steam appId from the library (any game whose
   platform icons already show correctly is captured).
3. Delete that appId's top-level key from `~/Library/Application Support/GameLib/store_cache/steam_metadata.json`
   (leave everything else — including the `__timestamp` object — untouched, so the warm library
   stays warm per CONTEXT.md's own stated goal).
4. **Scenario 1 (network up):** relaunch (`npm start` or `pnpm tauri:dev`), open "Install with
   options…" for that game, observe the pending row appear then resolve to the correct
   Windows-availability answer.
5. **Scenario 2 (network down / `appdetails` blocked, e.g. via OS-level firewall rule or
   `/etc/hosts` block on `store.steampowered.com`):** repeat steps 2-4 with connectivity to
   Steam's store API blocked, observe the pending row appear, then (after up to 15s) resolve to
   the fail-open state — Windows offered, Install enabled.

### Both runtimes

`installFormIpc.ts` is shared by Electron and the Tauri sidecar (Pitfall 5 above). Jest-level
proof (pure-function tests) is runtime-agnostic by construction — the module under test has no
Electron/Tauri-specific imports. The UAT gate, however, MUST run under BOTH runtimes explicitly
(per this project's own standing convention, carried from 34.13's UAT ledger structure: "72
rows = 36 items x electron/tauri"), because the manual-rendering proof jest cannot provide is
exactly where a runtime-specific regression (e.g. a Tauri sidecar IPC marshalling bug on the
widened verdict object) would surface first.
