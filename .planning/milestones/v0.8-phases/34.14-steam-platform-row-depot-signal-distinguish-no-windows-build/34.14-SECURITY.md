> Per-phase security contract: threat register, accepted risks, and audit trail.

`<threat_model>` block). The audit therefore *verified the listed mitigations exist*

## Trust Boundaries

| Boundary | Description | Data Crossing |
|----------|-------------|---------------|
| renderer → backend (`isSteamBottleEligible` IPC) | `appName` is untrusted renderer input crossing into `new SteamGame(...)` and template-literal paths | AppID string (untrusted until guarded) |
| backend → renderer (widened verdict) | Two new booleans flow OUTWARD; not a privilege-escalation direction | `hasWindowsDepot`, `platformsCaptured` — public store-derived booleans |
| gating verdict → rendered option list | Decides which install platforms are OFFERED, never which is executed | Booleans consumed by pure functions; nothing executed, no path built |
| IPC response → renderer state | Responses may arrive out of order or for a superseded game | Widened verdict object applied to component state |
| operator shell → system config (UAT only) | The D-08 procedure asks for two `sudo` edits to `/etc/hosts` plus a DNS flush | Host-resolution override, operator machine |
| operator editor → app cache file (UAT only) | One key deleted from an on-disk JSON store shared by both runtimes | `steam_metadata.json` cache entry |

## Accepted Risks Log

| Risk ID | Threat Ref | Rationale | Accepted By | Date |
|---------|------------|-----------|-------------|------|
| R-01 | T-34.14-02 (plan 01) | The widened verdict's two new booleans travel outward to the renderer. Both derive from public Steam-store `appdetails` platform data already cached on disk; neither carries a SteamID64, token, or path, so the standing Steam-identity redact-forward rule gains no new surface. No new log statement was added. | Grayson Mitchell | 2026-08-16 |
| R-02 | T-34.14-03 (plan 01) | A forged/malformed `appdetails` response can drive `platformsCaptured` to a false value. At worst this triggers D-04's fail-open, which ADDS a picker option; it cannot force an install, choose a path, or bypass the existing install routing's own validation. No branch in the touched code writes to disk or spawns a process. | Grayson Mitchell | 2026-08-16 |
| R-03 | T-34.14-06 (plan 02) | New frontend reads of `gameInfo` via `hasSteamDepotSignalCaptured`. Reads one boolean already present in every `GameInfo` object in renderer scope; no new data crosses any boundary and no logging is added. | Grayson Mitchell | 2026-08-16 |
| R-04 | T-34.14-08 (plan 03) | A probe that never settles could leave Install permanently disabled. Bounded by `METADATA_FETCH_TIMEOUT_MS` (15s) plus the promise's `.catch` → `applyEligibilityFailure`; both terminate. Worst case is a 15s disabled Install on a cold-cache game — the same bound 34.13 D-25 already shipped and accepted. Live-confirmed in UAT Run 2. | Grayson Mitchell | 2026-08-16 |
| R-05 | T-34.14-09 (plan 04) | Fail-open offers a Windows/wine install option for a game with no confirmed Windows depot. The offer is a picker entry, not an action: the user must explicitly select Windows and press Install, which remains gated by the unmodified `eligibility.pending` mechanism (D-01) and executed by the unmodified bottle-provisioning path. The failure mode is a failed download, not a privileged or destructive operation. Weighed against the certain, permanent option-withholding that fail-closed produces for every offline user — the defect this phase exists to end — this is the correct trade, and it makes the modal consistent with `PlatformSupport.tsx`, which already renders the Windows glyph unconditionally. | Grayson Mitchell | 2026-08-16 |
| R-06 | T-34.14-11 (plan 04) | New renderer-side depot state flows through `index.tsx`'s composition root. This plan adds no log statement; the two pre-existing `window.api.logError` sites in the touched file are unmodified and unrelated. | Grayson Mitchell | 2026-08-16 |
