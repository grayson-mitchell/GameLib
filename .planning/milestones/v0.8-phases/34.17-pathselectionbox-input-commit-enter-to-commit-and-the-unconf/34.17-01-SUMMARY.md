# Phase 34.17 Plan 01: PathSelectionBox Enter-to-Commit + Double-Commit Guard Summary

**Enter now commits a typed PathSelectionBox value through the same onPathChange path onBlur already used, guarded against double-firing egsSync by a two-part commit funnel (path-prop comparison + one-shot Enter/blur suppression) that RESEARCH.md's single-guard recommendation could not have closed.**

## Performance

- **Duration:** ~25 min
- **Tasks:** 2 completed (RED, GREEN)
- **Files modified:** 2 (1 created, 1 modified)

## Accomplishments

- `PathSelectionBox` now wires `onKeyDown` into the pre-existing `TextInputWithIconField` → `TextInputField` seam (no interface widening) so pressing Enter commits `e.currentTarget.value` via `onPathChange`, matching the house `SteamGridDBPicker` Enter idiom.
- All three commit routes (blur, Enter, icon-click Backspace/folder-picker) now funnel through one `commitPath` function, so the double-commit guard bookkeeping (`enterCommittedRef`) can never go stale for any of them.
- Non-Enter keys and auto-repeat Enter (`e.repeat === true`) commit nothing — closing the held-Enter DoS risk against `EgsSettings.tsx`'s real `egl-sync` subprocess spawn (threat T-34.17-02).
- Wrote and RED-proved an 8-case no-DOM jest suite (no jsdom / `render()` / `userEvent` — this project's frontend jest project is `testEnvironment: 'node'`) before writing the implementation, with a mandatory retry-after-rejected-commit control (case 8) and a differing-blur vacuity control (case 5) that a naive "ignore every blur after Enter" implementation would fail.
- `TextInputWithIconField/index.tsx`, `TextInputField/index.tsx`, and `EgsSettings.tsx` are byte-unchanged, confirmed via `git diff --stat`.

## RED / GREEN Record (per plan `<output>` requirement)

**RED run** (`/tmp/34.17-01-red.log`, before Task 2's implementation): `Tests: 6 failed, 2 passed, 8 total`. The 6 failures were cases 1, 3, 4, 5, 7, 8 — 5 of them (`props.onKeyDown` invocation throwing `TypeError: props.onKeyDown is not a function`) because `onKeyDown` did not exist yet, and case 7 because the unguarded `onBlur` at HEAD commits a value equal to the already-committed `path` prop. The 2 passing cases (2 and 6) are regression anchors, not defect pins: case 2 tolerates `onKeyDown` being `undefined` via optional chaining and asserts `onPathChange` was never called (trivially true when the handler doesn't exist yet); case 6 (bare blur, no preceding Enter) already worked at HEAD.

**GREEN run** (`/tmp/34.17-01-green.log`, after Task 2): `Tests: 8 passed, 8 total`. Full `Frontend` jest project run (`/tmp/34.17-01-fe.log`) afterward: `124 suites passed, 2051 tests passed` — no sibling suite regressed. `pnpm codecheck` (`tsc --noEmit`): exit 0.

**Why the two-guard shape, not RESEARCH.md's recommended one-guard shape:** `34.17-RESEARCH.md` recommends comparing the incoming value against the already-committed `path` prop alone (Guard G1 in this implementation) as sufficient. That recommendation is insufficient for the one non-idempotent call site, `EgsSettings.tsx`: its `path` prop (`egsPath`) is only updated *after* `window.api.egsSync` resolves, so `path` is stale for the entire duration of an in-flight commit. An Enter keypress immediately followed by a Tab (blur) in the same tick would have `path` still holding the pre-commit value when the blur fires, so G1 would not recognize the blur's value as already-committed — and `egsSync` would run a second time for the same string. Guard G2 (`enterCommittedRef`, a one-shot ref armed by `commitFromEnter` and consumed by the very next `commitFromBlur`) closes that gap independently of prop staleness, because it tracks what *this component* just sent, not what the parent has acknowledged. This finding — that the shape recommended by RESEARCH.md alone does not satisfy REQ-34.17-02 at the one real-risk call site — is why the implementation carries two guards, is recorded as a comment in `PathSelectionBox/index.tsx` itself, and is pinned by test cases 4/5/7/8 (case 8 specifically also proves G2 does not block a legitimate retry after a rejected commit).

## Decisions Made

- Two guards (G1 + G2), not RESEARCH.md's single-guard recommendation — see "RED / GREEN Record" above for the full rationale; this is the load-bearing finding of this plan.
- G2 is one-shot and value-scoped (compares the exact committed string, clears after one blur) rather than a boolean "ignore the next blur" flag, specifically so a second Enter after a parent-rejected commit still fires (test case 8) and so a genuine edit made between Enter and blur still commits (test case 5).
- Kept the pre-existing `setTmpPath(path)` calls inside `handleIconClick` exactly as they were — out of this phase's scope and untested by this plan, per the plan's explicit instruction not to touch them.
