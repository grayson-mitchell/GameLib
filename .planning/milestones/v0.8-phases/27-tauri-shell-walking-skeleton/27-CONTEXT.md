<domain>
## Phase Boundary

Phase 27 is the **walking skeleton** for GameLib's Rust/Tauri rearchitecture (Idea C, spiked
2026-07-20). It stands up the thinnest possible **end-to-end** working slice of the target
architecture and proves it runs on real macOS — it is the 5th integration spike, productionized.

**In scope (the thinnest E2E slice):**
- A native **Tauri v2** app shell (Rust) that hosts GameLib's **existing, unmodified** Vite React
  renderer in its webview.
- The **existing Node backend** running as a **Tauri sidecar** process (bundled Node), spawned and
  supervised by the Rust shell — NOT rewritten in Rust.
- `window.api` provided by **re-pointing the three preload factory functions** onto a Tauri↔sidecar
  transport, leaving all 379 renderer call-sites untouched.
- **One real read flow** end-to-end: the Steam library list renders in the Tauri window, sourced
  from the real store-manager / `steam-user` path inside the sidecar.
- **One real action flow** end-to-end: a `steam://` launch fires through the `shell.openExternal`
  parity path (`tauri-plugin-opener`).
- A **dev build that runs on macOS**, plus a documented seam boundary (what's ported vs stubbed) so
  later phases port the remaining ~217 IPC endpoints incrementally.

**Explicitly OUT of scope (deferred to later phases):**
- Porting all 220 IPC endpoints (only the 2–4 needed for the two E2E flows are wired here).
- Replacing `electron-store` project-wide (only the minimum token/config access the skeleton's read
  path needs — stub or a single keyring-backed value; the full swap is a later phase).
- The 44-file lifecycle/dialog/tray/updater/protocol cluster beyond app-launch + opener.
- Windows/Linux packaging, auto-update, code signing, notarization.
- Removing Electron from the repo (Electron build stays intact until the port completes).
- `session`/`powerSaveBlocker` shims; multi-account flows; the macOS Steam bridge (Idea B).

## Success Criteria

1. `npm run tauri:dev` (or equivalent) launches a native Tauri window showing the real GameLib UI.
2. The Steam library list in that window is populated by the Node sidecar (real data path), not mocked.
3. Clicking a Steam game's launch triggers a real `steam://` handoff via the opener parity path.
4. Zero changes to the 379 `window.api.*` call-sites; only the 3 preload factories + a new transport module change on the renderer side.
5. The Electron build still works (the port is additive, not destructive, this phase).

<decisions>
## Implementation Decisions (LOCKED — from spikes 009–012)

### Architecture shape (spike 009 + 010)
- **Target = Tauri/Rust shell + Rust platform seam + bundled Node sidecar for business logic + the
  existing React UI.** NOT a Rust rewrite. 80% of backend files (176/220) are Electron-free and port
  to a Node sidecar as-is.
- **Keep `steam-user` + the depot pipeline as-is in the Node sidecar.** It has 0 electron imports and
  runs headless (loads in 341 ms). Do NOT rewrite Steam in Rust — `steam-vent` 0.5.0 is auth-only and
  experimental (no PICS/depot/CDN). This preserves GameLib's differentiator at zero cost.

### The sidecar boundary (spike 009 — the sharp edge)
- **The backend faults at IMPORT time under bare Node**, not lazily: `app.getPath()` runs at module
  scope (Heroic constants) and `electron-store` throws at construction (`initRenderer` — it is
  inseparable from Electron). So the sidecar entrypoint MUST provide, before importing backend
  modules: (a) an `app.getPath`-equivalent path shim, and (b) a replacement for `electron-store`
  (for the skeleton, the minimum the read path needs — a keyring-backed or file-backed store; the
  full swap is deferred).
- Any Electron main API the skeleton's two flows transitively hit must be shimmed in the sidecar or
  bridged to the Rust shell; enumerate them from the 16-API / 44-file map in spike 009.

### The renderer bridge (spike 012 — the cheapest leg)
- The **entire `window.api` surface is generated by 3 factory functions** in `src/preload/ipc.ts`:
  `makeHandlerInvoker(channel)` → `ipcRenderer.invoke` (req/resp);
  `makeListenerCaller(channel)` → `ipcRenderer.send` (fire-and-forget);
  `frontendListenerSlot(event)` → `ipcRenderer.on` (backend→frontend push).
- **Port = rewrite ONLY these 3 factories** to route over Tauri: `invoke` → Tauri command → sidecar
  RPC; `send` → command/emit; `on` → Tauri `listen`. The 379 call-sites and the React tree are
  untouched. Proven live on a mock-Tauri transport with 0 Electron symbols (`012/bridge-shim-demo.html`).
- **5 renderer files import `electron` directly** — route them through `window.api`/a shim as part of
  this slice's cleanup (they bypass the clean seam today).

### Platform-API parity (spike 011 — proven live in compiled Rust)
- `shell.openExternal("steam://…")` → **`tauri-plugin-opener`** (shells `/usr/bin/open`; Steam.app is
  the registered steam:// handler). This is the action-flow path. PROVEN.
- `safeStorage` → **OS Keychain via the `keyring` crate** (`apple-native` feature) — same
  Security.framework store Electron uses. A 41-byte token round-tripped byte-identical. Use this for
  any token persistence the skeleton needs.
- 13/16 Electron APIs have full Tauri v2 parity (see `011/README.md` table); `session` +
  `powerSaveBlocker` are the only soft spots — both out of scope this phase.

### Sidecar transport
- Renderer talks to the Rust shell via Tauri commands; the Rust shell relays to the Node sidecar. The
  exact sidecar RPC (stdio JSON-RPC vs localhost) is the planner's to specify, but it must preserve
  the `invoke(channel, ...args) → Promise` and `on(event, cb)` contract shapes exactly.

<specifics>
## Specific Ideas
- Toolchain present: `cargo`/`rustc` 1.94.x. **No Tauri CLI installed** — planner must include a task
  to add `@tauri-apps/cli` + scaffold `src-tauri/`. `keyring` crate builds + round-trips the macOS
  Keychain today (verified in spike 011).
- Wine on macOS shares the host network namespace (relevant only if a loopback sidecar transport is chosen).
- The two E2E flows should reuse the real store-manager code paths, not reimplement them — the whole
  point is proving the existing logic runs unchanged behind the new transport.
</specifics>
