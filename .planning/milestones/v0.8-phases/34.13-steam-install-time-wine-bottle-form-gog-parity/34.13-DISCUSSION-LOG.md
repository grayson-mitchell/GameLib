## When the form appears

### How does the frontend learn a game needs a bottle?

| Option | Description | Selected |
|--------|-------------|----------|
| New IPC, backend authoritative | isSteamBottleEligible(appName) awaiting ensurePlatformsCaptured(); one source of truth | ✓ |
| Derive frontend-side from GameInfo | Read is_mac_native / mac_arch / steamPlatformsCaptured directly — a third copy of the predicate | |

**User's choice:** New IPC, backend authoritative
**Notes:** Presented with the finding that GameInfo *does* already carry all three fields, so a frontend derivation was genuinely possible — rejected because the predicate already exists twice in the backend and a cold cache reads as "not eligible", the exact shape of `steam-bottle-guided-setup-never-fires`.

### Which triggers open the form?

**First pass (multi-select):** user selected "Bottle required" only, then interrupted to ask whether retiring the picker loses the >1-library case.

**Clarification given:** yes — retiring the picker while triggering only on bottle-required drops the multi-library choice on every platform, a live D-09 regression with nothing picking it up. Verifying `installBottleNative` (`games.ts:827`) additionally showed the two triggers surface almost disjoint content, since a bottled install's destination is the bottle's steamapps dir and not a host library at all.

**Re-posed:**

| Option | Description | Selected |
|--------|-------------|----------|
| Both triggers open the form | Bottle-required OR >1 library (plus always-show); each section renders only when it applies | ✓ |
| Keep the picker; form is bottle-only | Reverses the retire decision; two surfaces, smaller phase | |
| Retire the picker, accept the loss | Multi-library users always get the primary library; a deliberate D-09 regression | |

**User's choice:** Both triggers open the form
**Notes:** This exchange was user-initiated and caught a real inconsistency between two of their own earlier answers.

## Where the choice lands

### Where does the chosen wine version get written?

| Option | Description | Selected |
|--------|-------------|----------|
| steamBottleConfigStore, shared | persistBottleWineVersion() — the store getSteamBottleSettings() actually reads; shared across all bottled Steam games | ✓ |
| Per-game GameConfig, like GOG | True mechanism parity, but getSettings() ignores GameConfig for bottle-eligible games — needs a precedence change amounting to Phase 22 | |
| This install only, nothing persisted | Extend InstallArgs with wine fields, use for provisioning only | |

**User's choice:** steamBottleConfigStore, shared
**Notes:** Presented with the `bottle.ts:291-306` bug note documenting a per-game `setSetting('wineVersion')` self-heal already being silently dropped on this exact path, and with the finding that `InstallArgs` carries no wine fields at all. The shared-across-all-games consequence needs stating in the form's copy.

### Overlap with the guided SteamBottleSetup (D-07)

| Option | Description | Selected |
|--------|-------------|----------|
| Form feeds guided setup | Form persists the choice; install() still defers; guided setup opens pre-filled instead of re-asking | ✓ |
| Provision inline from the form | Form becomes the consent surface and calls provisionBottle directly, following the bridge precedent | |
| Form only shows when bottle is ready | Unprovisioned games skip the form entirely | |

**User's choice:** Form feeds guided setup
**Notes:** Inline provisioning was distinguished from the bridge path's precedent — the bridge does a fast `cxbottle --create` needing no consent, whereas `provisionBottle` downloads and launches SteamSetup.exe.

## Framing

User's words: *"Steam's native experience is that you just click install and it works... and then
hidden away in menus you can change the game settings when you need to."* Initial proposal was a
button that toggles between quick and full modes, plus a library-screen indicator.

## Interaction Pattern

| Option | Description | Selected |
|--------|-------------|----------|
| Split button | Primary click = quick install; caret opens "Install with options…". No remembered mode, both paths one click, label always truthful | ✓ |
| Toggle button | User's original idea — button switches mode and remembers it | |
| Two separate buttons | Both always visible; too cramped for a library card | |

Counter-argument that carried: a remembered mode means the same control does different things on
different days, and the label must be re-read every time.
