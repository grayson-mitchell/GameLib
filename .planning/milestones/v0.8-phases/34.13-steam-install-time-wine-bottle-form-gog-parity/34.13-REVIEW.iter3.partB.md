### B-WR-01: The D-24 degrade notice still promises a picker that does not render — WR-11 fixed one of three corners

**File:** `src/frontend/screens/Library/components/InstallModal/SteamDialog/index.tsx:372-390`

**Issue:** WR-11 (and B-WR-05's token gate for it) made the "choose another below" copy conditional on `steamDegrade.onlyLibrary`. But `onlyLibrary` is computed by `startSteamQuickInstall` from **its own** library-list length (`InstallGameModal.ts:197,206` — `libraryCount <= 1`), and the thing that decides whether a picker actually renders is **`gating.libraryDropdown`**, which is `!wineSection && nativeInstallOn && libraryCount > 1` (`steamSectionGating.ts:234`). Those are different predicates, and `wineSection` breaks the implication.

Two reachable states where the notice says *"choose another below"* and there is nothing below — **neither requires an IPC failure**:

```
A) macOS, bottle-required game, 3 Steam libraries, primary drive unplugged
   quick path → degrade { reason:'library-missing', onlyLibrary: false }
   verdict    → { platformRow:'readonly-windows', wineSection:true,
                  libraryDropdown:false, freeSpaceLine:false }

B) macOS, mac-native game WITH a Windows depot, 3 libraries, user selects "Windows"
   verdict    → { platformRow:'selectable', wineSection:true,
                  libraryDropdown:false, freeSpaceLine:false }
```

(Both verified by re-running the resolver's ten steps against those inputs.) In both cases `onlyLibrary` is `false`, so the dialog picks `libraryMissingNotice` / `libraryFullNotice` — the sentences that end *"— choose another below."* — while `gating.libraryDropdown` is `false` and no `SelectField` is emitted at all. This is verbatim the defect WR-11 exists to eliminate ("the dropdown this copy points at does not render at all"), just in the `wineSection` corner rather than the `<=1-library` corner. It is also the more common corner: **every** bottle-eligible macOS Steam game lands in state A.

A third instance: with the library fetch unsettled or rejected (B-WR-02 below), `libraryCount` is 0 and `libraryDropdown` is `false` on **any** host, while a degrade record carrying `onlyLibrary: false` from the quick path's own successful fetch still selects the "choose another" copy.

**Fix:** Select the copy on the thing that actually governs the picker, not on a record field computed elsewhere:

```tsx
{steamDegrade.reason === 'library-missing'
  ? gating.libraryDropdown
    ? tGamelib('gamelib:steam.install.libraryMissingNotice', '…— choose another below.')
    : tGamelib('gamelib:steam.install.libraryMissingOnlyNotice', '…Reconnect the drive, then try again.')
  : gating.libraryDropdown
    ? tGamelib('gamelib:steam.install.libraryFullNotice', '…')
    : tGamelib('gamelib:steam.install.libraryFullOnlyNotice', '…')}
```

The two "Only" keys already exist and already say the right thing for "there is no alternative to offer", so this needs **no new catalog key and no UI-SPEC amendment** — only a change of selector. Then either keep `onlyLibrary` as a redundant record field or drop it; if it is kept, `steamDialogSource.test.ts`'s required-token list must swap `steamDegrade.onlyLibrary` for a gate proving the copy branches on `gating.libraryDropdown`, otherwise the token gate will pin the wrong field.

### B-WR-02: A rejected library fetch now permanently suppresses the only explanatory content — on Linux the dialog body is structurally empty

**Files:** `src/frontend/screens/Library/components/InstallModal/index.tsx:121-128,236`, `.../steamEligibilityProbe.ts:212-220`

**Issue:** The B-WR-02 fix correctly stops the first-frame lie, but it collapses two very different unsettled states into one permanent one. The rejection handler sets `setSteamLibraries(null)` (`index.tsx:236`) — i.e. it *returns the state to its initial value*. `steamLibrariesSettled` is `steamLibraries !== null`, so after a rejection it is `false` **forever**, and `applyLibraryFetchPending` suppresses `contentLightNotice` **forever**.

Traced through the resolver for a Linux host with a rejected fetch:

```
raw verdict  { platformRow:'absent', wineSection:false, libraryDropdown:false,
               contentLightNotice:true,  freeSpaceLine:false }
after suppression
             { platformRow:'absent', …, contentLightNotice:false, … }
```

`platformRow: 'absent'` → `platformSelection()` returns `null` (`index.tsx:378-380`). `eligibility.pending` is `false` (Linux is skipped by `shouldProbeEligibility`), so no loading row. `showWineSelector` is `false`. `libraryDropdown` is `false`. The notice is suppressed. **`<DialogContent>` renders nothing at all** — the user sees a title bar and an Install button, permanently, with no explanation and no retry. On Windows they see a title, a *disabled* one-option platform select, and Install.

Before `fe22a4340` this state showed the content-light sentence (arguably with the wrong half of the copy, but a sentence). The fix therefore strictly regressed the transport-failure path from "possibly-wrong explanation" to "no explanation, forever". `window.api.listSteamLibraryTargets` rejecting is not hypothetical here — this repo has ledgered sidecar channel failures repeatedly, and the handler exists precisely because that happens.

**Fix:** Distinguish "not yet known" from "asked and failed". A rejection is a settled — if unhelpful — answer, so it must not masquerade as pending:

```ts
type LibraryFetch =
  | { phase: 'pending' }
  | { phase: 'ok'; targets: SteamDialogLibraryOption[] }
  | { phase: 'failed' }

// suppress the notice only while `phase === 'pending'`;
// on 'failed', render a distinct "couldn't read your Steam libraries" line
```

If a third sentence is judged out of scope for a fix pass, the minimum acceptable behaviour is to treat a rejection as settled (`setSteamLibraries([])`) and accept the pre-fix copy on that path only — a possibly-wrong sentence beats an empty modal. Whichever is chosen, add a spec driving the rejection branch and asserting `steamLibrariesSettled` becomes `true`.

### B-WR-04: `handleInstall`'s `try/catch` spans the whole handler, so a *throwing* persist silently aborts the install — contradicting the D-15 rule stated ten lines above it

**File:** `src/frontend/screens/Library/components/InstallModal/SteamDialog/index.tsx:244-332` (specifically `283-286`, `300-320`, `321-332`)

**Issue:** The B-CR-01 fix correctly collapses a **rejected** persist into `{ status: 'error' }` and proceeds. But it then wraps *everything* — the destination resolution, `backdropClick()` and `installSteamGame(...)` — in one `try`, whose `catch` only releases the latch and logs. So for the **throw** class of failure the handler's stated contract inverts:

```ts
const persisted = window.api.persistBottleWineVersion(wineVersion)   // 283
const result = await persisted.catch(() => ({ status: 'error' }))    // 284-286
…
backdropClick()                                                      // 306
installSteamGame(…).catch(logSteamInstallDispatchFailure(appName))   // 315-320
} catch {
  setSubmitting(false)                                               // 328  ← install already skipped
```

If `window.api.persistBottleWineVersion` is missing or hollow (this repo has ledgered *"the `safeStorage` stub is dead"* and *"the `nativeImage` stub is hollow"* for exactly this preload surface under the Tauri sidecar), `persisted` is not a thenable, `persisted.catch` throws a `TypeError`, control jumps to the `catch`, and **`backdropClick()` and `installSteamGame()` never run**. The user's install is silently dropped. The comment at lines 290-293 states the opposite rule as the design: *"a failed persist degrades to today's behaviour rather than blocking the user's install."* The same applies to a synchronous throw from `persistBottleWineVersion` itself.

`assertSubmitLatchCanBeReleased` (`steamDialogSource.test.ts:166-191`) cannot see this: it checks that `.catch(` exists within 200 chars of the persist and that the strings `setSubmitting(false)` / `setSubmitting(true)` appear *anywhere* in the file. Neither obligation says anything about the `try`'s **scope**, which is the property that decides whether the install survives.

Separately, the `catch` is bare (`catch {`) — the thrown value is discarded entirely, so the log line at `329-331` names neither the cause nor the stage.

**Fix:** Scope the guard to the thing that may legitimately fail, and keep the install outside it:

```ts
if (gating.wineSection && wineVersion && isBottleCapableEngine(wineVersion)) {
  try {
    const result = await window.api.persistBottleWineVersion(wineVersion)
    if (result.status === 'error') { window.api.logError(/* … */) }
  } catch (e) {
    // D-15: the guided bottle setup derives an engine when nothing was
    // persisted, so NEITHER a rejection NOR a throw may block the install.
    window.api.logError(
      `34.13-10 SteamDialog: persistBottleWineVersion threw (${String(e)}) — continuing`
    )
  }
}

const destination = resolveSteamInstallPath(selectedPath, steamLibraries, gating.libraryDropdown)
backdropClick()
installSteamGame(appName, gameInfo, destination, gating.forceWindowsViaBottle)
  .catch(logSteamInstallDispatchFailure(appName))
```

Then extend `assertSubmitLatchCanBeReleased` with a **positional** obligation — `installSteamGame(` must not lie inside the persist's `try` block — and RED-prove it against a copy of the real source with the brace moved.
