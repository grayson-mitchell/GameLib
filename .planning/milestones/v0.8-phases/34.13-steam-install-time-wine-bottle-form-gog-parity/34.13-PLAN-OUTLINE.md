## Notes for the plan-writing Tasks

1. **CONTEXT.md's sidecar file is wrong; RESEARCH.md corrects it.** `isSteamBottleEligible` and
   `persistBottleWineVersion` belong in `src/backend/sidecar/steamAuthFlowRegistration.ts` (which
   hosts the "macOS CrossOver bottle trio" its own doc-comment names), **not**
   `installFlowRegistration.ts` (scoped to install/uninstall/update-check). This matches
   `main.ts:922-934`'s own physical grouping. A channel registered on only one runtime hangs the
   D-12 busy state under Tauri specifically and passes every Electron test.

2. **RESOLVED open question — the D-17 override signal.** `installSteamGame()` hardcodes
   `platformToInstall: 'Windows'` for **every** Steam install today, and the Steam backend reads
   that field nowhere. Therefore `platformToInstall === 'Windows'` **cannot** distinguish "the user
   chose Windows for a mac-native game" from "the legacy hardcoded default," and reinterpreting it
   would route every mac-native install into the bottle. Plan 34.13-01 declares a **separate,
   explicit** override field on `InstallArgs`; 34.13-06 reads only that field; 34.13-08 is the only
   place that sets it.

3. **RESOLVED open question — the D-17 Windows-depot-availability signal.** Windows availability is
   **not** captured today, but it is *free*: `games.ts:544` already reads `data.platforms?.mac` and
   `data.platforms?.linux` from an `appdetails` response that also carries `data.platforms.windows`.
   34.13-02 persists it as `is_windows_native` alongside `is_mac_native` — same response, no new
   network call, no PICS, no `buildDepotPlan`. `library.ts:689`'s hydration block is the mirror
   edit. This is the signal 34.13-12 gates the selectable Windows `MenuItem` on.

4. **No jsdom, no react-test-renderer anywhere in this repo** (`34.13-VALIDATION.md`, hard
   constraint). A test that imports a `.tsx` dialog fails at `import './index.scss'` before any
   assertion runs. Every frontend plan must prove its behavior through an extracted pure module
   (34.13-03's `engineFilter.ts`, 34.13-05's `steamSectionGating.ts`, 34.13-09's
   "which-default-wins" fn) or through 34.13-13's manual gate. A plan that claims to test a rendered
   dialog is wrong by construction.

5. **Named vacuous-assertion risks** (`34.13-VALIDATION.md`) each map to a specific plan boundary:
   store-flip ≠ dialog renders (34.13-08 vs 34.13-13); write ≠ read (34.13-07/10 vs 34.13-09);
   registration ≠ preload-wired (34.13-07 must verify `src/preload/api/steam.ts` in the *same*
   task); one click-through ≠ coverage (34.13-13 enumerates the matrix rather than sampling).

6. **Security enforcement is ENABLED** — every plan needs a `<threat_model>` block. RESEARCH.md's
   Security Domain section found no new auth/session/network/crypto surface: the one new read
   channel takes only an already-trusted internal `appName`, and `sanitizeBottleName` /
   `SAFE_INSTALLDIR` remain untouched. Expect mostly `accept` dispositions with explicit rationale,
   plus the standing `T-34.13-SC` supply-chain row (no package installs this phase, so the Package
   Legitimacy Gate is not applicable — state that explicitly rather than omitting the row).

7. **Standing project rules:** never raise upstream-Heroic mergeability as a concern; run
   `graphify query` before source exploration; every new user-facing string gets a `gamelib:` key;
   `pnpm tauri:dev` never `tauri dev`; and if a plan introduces new grid layout, no 1px border on a
   `1fr` track boundary (use an inset `::after`).
