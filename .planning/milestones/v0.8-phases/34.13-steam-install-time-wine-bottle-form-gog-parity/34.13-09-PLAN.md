<verified_findings>
Six claims were checked against source this session. They change what you build — do not re-derive
or contradict them.

1. **`useAwaited` cannot fetch the verdict.** `src/frontend/hooks/useAwaited.ts:11-22` runs its
   effect with a `[]` dep list — it fires **once, at mount, and never again**. `SteamBottleSetup` is
   mounted by `App.tsx` for the whole app lifetime and merely returns `null` when `!isOpen`
   (L121-123, *after* every hook). So at the moment `useAwaited` fires, `appName` is `undefined` and
   no session has opened. Copying the existing `useAwaited(() => window.api.requestAppSettings())`
   line (L50) for the verdict would fetch for the wrong game, exactly once, forever. Use a
   `useEffect` keyed on the session instead — the shape the engine-fetch effect at **L65-76**
   already uses, complete with its `cancelled` guard.

2. **The seeding effect fires exactly once per value of `wineVersion`.** Its guard is
   `if (!globalConfig || wineVersion || !enginesFetched) return` (**L79**). The moment it sets a
   non-`undefined` engine, it can never seed again. This is why the settle gate is load-bearing and
   not defensive polish: if the verdict resolves even one render *after* `globalConfig` and
   `enginesFetched`, the derived default is already latched and the persisted value is discarded.
   The failure is a race — intermittent in the field, invisible to every unit test.

3. **The existing session-reset effect does not clear the seed.** **L54-59** resets `phase`,
   `provisionError` and `provisioned` on `[isOpen, appName]`, but not `wineVersion`. Because of
   finding 2, a second guided-setup session in the same app run would keep session 1's engine and
   never consult session 2's persisted value. `close()` does not clear `appName` either
   (`state/SteamBottleSetup.ts:23`). The reset must be extended.

4. **The persisted value is authoritative and must be taken VERBATIM — it is not merely the form's
   echo.** `src/backend/launcher.ts:247-250` calls `persistBottleWineVersion(gameSettings.wineVersion)`
   after a successful `checkWineBeforeLaunch` self-heal. A persisted engine can therefore be a
   *correction* the backend made because the previous one did not work. Re-running it through
   `resolveSteamBottleEngine` would throw that correction away in favour of "the first CrossOver in
   the list".

5. **Do NOT consume the verdict's `bottleName`.** The seeding effect hardcodes
   `setCrossoverBottle(DEFAULT_STEAM_BOTTLE_NAME)` at **L91** under a comment naming the 17-06 UAT
   bug it fixes. D-05 makes the name read-only and fixed; editable/per-game bottle names are a
   Deferred Idea (Phase 22). The verdict carries `bottleName` for 34.13-10's read-only display, not
   for this file. Task 2 adds a source gate that this line survives.

6. **`persistBottleWineVersion` writes `wineVersion` only** (`bottle.ts:307-309`) — it never writes
   `wineCrossoverBottle` (`34.13-RESEARCH.md` Pattern 4, confirmed). There is no persisted bottle
   *name* originating from this phase to read back, which is the second, independent reason finding
   5 holds.
</verified_findings>
