## Critical Issues

### C-01: `SteamBridgeSetup` awaits a non-Promise — the fallback install's error path is now unreachable and `close()` fires before anything is dispatched

**File:** `src/frontend/screens/Game/GamePage/components/SteamBridgeSetup.tsx:87`
(with `src/frontend/state/InstallGameModal.ts:110-124`)

**Issue:**

```tsx
if (!gameInfo.is_installed) {
  await installSteamGame(appName, gameInfo)   // <- returns void
} else {
  await window.api.launch({ appName, runner: 'steam', args: [] })
}
close()
```

`installSteamGame` is declared `(appName, gameInfo, path = '', forceWindowsViaBottle = false) => { void window.api.install({...}) }` — it returns `undefined`, and it swallows the install promise internally with `void`. Consequences, all provable from source:

1. `await undefined` is a no-op. ESLint reports it as a hard error:
   `87:9  error  Unexpected 'await' of a non-Promise (non-"Thenable") value  @typescript-eslint/await-thenable`.
2. The enclosing `try/catch` can no longer catch an install rejection. The
   `catch` block's only remaining reachable trigger on this branch is
   `getGameInfo()` throwing. `bridge.setup.fallbackError` — "Falling back to
   bottled Steam failed: {{error}}" — is now dead copy for the not-installed
   path.
3. `close()` and `finally { setFallingBack(false) }` both run immediately, so
   the "Falling back..." button state is instantaneous and the dialog dismisses
   before the install IPC has even been answered. On a failed fallback the user
   sees the failure surface vanish and nothing happen.

This is a **regression**, not a pre-existing condition. `git show
77eb4b4b6^:src/frontend/screens/Game/GamePage/components/SteamBridgeSetup.tsx`
shows the pre-phase form was `await window.api.install({ ... })` — a real
promise whose rejection *was* caught and surfaced. The 34.13-08 commit comment
asserts "The outcome is byte-identical to the literal this replaces:
`installSteamGame`'s hardcoded fields are the same eight." The *fields* are
identical; the *return contract* is not, and that is the whole difference.

This is a failure-recovery surface. Silently swallowing the recovery's own
failure is the worst possible place for this defect.

**Fix:** Give `installSteamGame` a real return value rather than papering over
the call site — the same defect exists at every other `installSteamGame` caller
that wants to know whether the install started.

```ts
// src/frontend/state/InstallGameModal.ts
export const installSteamGame = (
  appName: string,
  gameInfo: GameInfo,
  path = '',
  forceWindowsViaBottle = false
): Promise<unknown> =>
  window.api.install({ /* …unchanged eight fields… */ })
```

Then the existing `await` in `SteamBridgeSetup` becomes correct as written, and
every fire-and-forget caller (`startSteamQuickInstall`, `InstallOverlay`)
explicitly opts out with `void installSteamGame(...)`. Add a regression test
asserting `handleFallback` sets `fallbackError` when `window.api.install`
rejects — there is currently no test covering this branch at all.

### C-02: `SteamBottleSetup.handleConfirm` has no rejection handling — a rejected provision IPC leaves an unhandled rejection and wedges the wizard in `provisioning` forever

**File:** `src/frontend/screens/Game/GamePage/components/SteamBottleSetup.tsx:215-226`
(with `src/preload/ipc.ts:37-46`)

**Issue:**

```tsx
const handleConfirm = async () => {
  setPhase('provisioning')
  setProvisionError(undefined)
  const result = await window.api.steamBottleProvision({
    bottleName: crossoverBottle || undefined,
    wineVersion
  })
  if (result.status === 'error') {
    setProvisionError(result.error)
    setPhase('error')
  }
}
```

`window.api.steamBottleProvision` is `makeHandlerInvoker('steamBottleProvision')`,
which returns `ipcRenderer.invoke(...)` under Electron and `tauriInvoke(...)`
under Tauri. Both **reject** on a backend throw, a dead sidecar, or a transport
timeout. `handleConfirm` has no `try/catch` and no `.catch`, and it is wired
directly as `onClick={handleConfirm}` (line 276), so nothing downstream handles
it either.

On rejection:
- an unhandled promise rejection is raised (under the Tauri sidecar this is the
  ledgered "sidecar send channels fail silently" failure mode);
- `setPhase('error')` never runs, so `phase` stays `'provisioning'`;
- the banner renders "Setting up Steam — this can take a while on first run."
  **permanently**, with no error, no retry affordance (the "Try again" button
  only exists in the `error` phase), and the 3-second poll armed;
- the only way out is the "Done" button, which closes the surface and leaves
  the poll running (see C-05).

WR-03's issue text in `34.13-REVIEW.iter1.md` named this exact symptom: "the
poll never surfaces the failure, so the banner sits on 'Setting up Steam…'
forever." Commit `e9930a1fe` added a `.catch` to the **poll**, which addresses
the unhandled-rejection-every-3s half but does nothing about the wedge, because
the wedge originates in a different, unguarded promise in the same file that
the fix did not enumerate. Three IPC round trips were audited; this fourth one
was not.

**Fix:**

```tsx
const handleConfirm = async () => {
  setPhase('provisioning')
  setProvisionError(undefined)
  try {
    const result = await window.api.steamBottleProvision({
      bottleName: crossoverBottle || undefined,
      wineVersion
    })
    if (result.status === 'error') {
      setProvisionError(result.error)
      setPhase('error')
    }
  } catch (error) {
    // A rejected provision IPC is a FAILED provision, unlike a rejected
    // status READ (the poll's .catch below) which is merely unknown.
    setProvisionError(error instanceof Error ? error.message : String(error))
    setPhase('error')
  }
}
```

and `onClick={() => void handleConfirm()}` so no promise floats off the JSX
attribute. Additionally, consider bounding the `provisioning` phase with a
timeout that flips to `error` — the surface currently has no terminal state
other than `provisioned === true`.

### C-03: A non-CrossOver engine can be seeded, hidden, and submitted to the `cxbottle`-only provisioner — the sibling bridge provisioner rejects exactly this input

**Files:**
`src/frontend/screens/Game/GamePage/components/steamBottleDefaults.ts:30-37,110-119`;
`src/frontend/screens/Game/GamePage/components/SteamBottleSetup.tsx:146-158,215-226`
(with `WineSelector/engineFilter.ts:27-47`, `WineSelector/index.tsx:145-217`,
`backend/storeManagers/steam/bottle.ts:570-618,755-775,1046-1058`)

**Issue:**

The re-review brief asked for an exhaustive enumeration of writers that can put
a non-CrossOver engine into the `cxbottle`-hardcoded Steam bottle. Here is the
complete set, and the hole is reachable **without any persisted value at all**.

**Writers of `steamBottleConfigStore.wineVersion` (exhaustive):**

| # | Site | Source of the value | Engine-type validated? |
|---|---|---|---|
| 1 | `bottle.ts:617` (`provisionBottle` step 2) | `opts.wineVersion` from `steamBottleProvision`, i.e. **this wizard's `wineVersion` state** | **No** |
| 2 | `bottle.ts:774` (`provisionBottle` step 6) | `getSteamBottleSettings().wineVersion`, which is `storedWineVersion ?? globalSettings.wineVersion` — i.e. **the global engine** when nothing is stored | **No** |
| 3 | `bottle.ts:308` `persistBottleWineVersion` ← `installFormIpc.ts:189` | the `SteamDialog` submission (CR-01-fixed path) | type is validated against the 4-literal union only, **not** narrowed to `crossover` (deliberate, deferred) |
| 4 | `bottle.ts:308` ← `launcher.ts:250` | `checkWineBeforeLaunch`'s self-heal result | **No** (the case `steamBottleDefaults.ts:99-104` cites) |

`steamBottleDefaults.ts`'s D-15 rationale justifies the verbatim-precedence
rule by naming writer 4 only ("a correction the backend made on purpose").
Writers 1 and 2 are not corrections at all — 2 is a straight pass-through of the
user's *global* engine, which `bottle.ts:995-1000` documents in this repo's own
words: "globalSettings.wineVersion, which on a machine with Game Porting
Toolkit (GPTK) set as the global default resolves to GPTK's 64-bit-only
`wine64`."

**But the seeding hole does not even need a persisted value.** Trace the wizard
on a macOS host with GPTK as the global engine and no CrossOver installed:

1. `SteamBottleSetup.tsx:146` →
   `resolveSteamBottleSeedEngine(undefined, globalConfig.wineVersion, wineVersionList)`
   → falls through `isUsablePersistedEngine` → `resolveSteamBottleEngine` →
   `wineVersionList.find(type === 'crossover')` is `undefined` → **returns
   `configuredWine`, i.e. the GPTK/`toolkit` global engine**
   (`steamBottleDefaults.ts:34-36`).
2. `WineSelector` is mounted with `runner="steam"` → `resolveCrossoverOnly`
   returns `true` → `engineOptions = filterWineEngines(list, true)` = **`[]`**.
3. `WineSelector/index.tsx:217` — `disabled={useSharedPrefix || engineOptions.length === 0}`
   → the engine `SelectField` is **disabled**, and its `value={wineVersion?.name}`
   is a name that exists in **no** `MenuItem`, so MUI renders it blank. The user
   can neither see nor change the armed engine.
4. `handleConfirm` (line 218) passes that engine verbatim to
   `steamBottleProvision`.
5. `provisionBottle` performs **no** engine-type check (writer 1 above), persists
   it, creates the bottle with `CXBOTTLE_BIN`, and runs `SteamSetup.exe` through
   `runWineCommand` with GPTK's `wine64` — which has no 32-bit loader.
6. The value is now persisted, so on **every subsequent session**
   `isUsablePersistedEngine` accepts it and `resolveSteamBottleSeedEngine`
   returns it **verbatim, ahead of** any CrossOver derivation. The bad engine is
   sticky and the wizard can never self-correct out of it.

The codebase already contains the verdict on whether this input is acceptable.
`bottle.ts:1046-1058`, the **bridge** bottle's provisioner:

```ts
// (2) D-08: CrossOver-only. Reject a non-CrossOver engine before any side
// effect — do not silently create a broken GPTK/toolkit bottle (T-24-09).
if (opts?.wineVersion && opts.wineVersion.type !== 'crossover') {
  logError(`provisionBridgeBottle: rejected non-CrossOver engine "${opts.wineVersion.type}" …`)
  return { status: 'error', error: `The bridge bottle requires a CrossOver engine, got "${opts.wineVersion.type}"` }
}
```

Two functions in the same file, both creating a bottle via the same `cxbottle`
mechanism; one rejects a GPTK engine outright as "a broken bottle," the other
accepts it silently. `WineSelector`'s own D-16 prop comment says the same thing:
"any other engine type would silently produce a broken bottle."

Note the D-16 filter this phase added is what removed the user's recourse.
Before it, the seeded GPTK engine was at least *visible and selectable* in the
dropdown. Now it is invisible, unselectable, and submitted anyway. The new
`showNoCrossoverEngineNotice` copy actively misleads here — it promises "GameLib
will set one up when the install starts," while the very next click provisions
with the wrong engine.

`steamBottleDefaults.test.ts:95-102` pins the verbatim-return behaviour as
intended, so the resolver itself is arguably correct in isolation. The defect is
that nothing between it and `cxbottle` closes the loop.

**Fix — three independent places, at least the first two:**

1. **Refuse to submit an engine the dialog's own filter rejects.** In
   `SteamBottleSetup.handleConfirm`, drop a non-CrossOver engine rather than
   forwarding it — `provisionBottle` already defaults to a sane engine when
   `wineVersion` is omitted:

```tsx
const submittedWine =
  wineVersion?.type === 'crossover' ? wineVersion : undefined
const result = await window.api.steamBottleProvision({
  bottleName: crossoverBottle || undefined,
  wineVersion: submittedWine
})
```

2. **Mirror the bridge guard in `provisionBottle`.** Copy `bottle.ts:1046-1058`
   verbatim into `provisionBottle` after the bottle-name sanitize and before the
   step-2 store writes. This closes writer 1 *and* makes writer 2's
   global-engine fallback fail loudly instead of silently. This is the
   `provisionBottle`-rejection half of the folded
   `steam-bottle-gptk-engine-produces-broken-bottle` todo that
   `steamBottleDefaults.ts:57-66` records as still open — the bridge half was
   already closed in Phase 24, so this is finishing an existing decision, not
   scope creep.

3. **Make the dialog honest about the state.** When
   `engineOptions.length === 0` and the armed `wineVersion` is non-CrossOver, the
   copy should say so rather than showing a blank disabled field.

If the phase owner wants to keep this deferred, it needs an explicit deferral
record naming writers 1 and 2 — the current `<deferred>` note only covers the
frontend-filter/backend-rejection split and reads as if the persisted value is
always a deliberate backend correction, which writers 1 and 2 falsify.

### C-05: The provisioning poll survives `close()` and runs every 3 seconds for the remaining life of the app

**File:** `src/frontend/screens/Game/GamePage/components/SteamBottleSetup.tsx:63-77,173-205`
(with `src/frontend/App.tsx:138`)

**Issue:** `<SteamBottleSetup />` is mounted permanently in `App.tsx`; `isOpen`
false only makes it `return null` (line 207), it never unmounts. The poll effect
is keyed on `[phase]` alone:

```tsx
useEffect(() => {
  if (phase !== 'provisioning') { if (pollRef.current) clearInterval(pollRef.current); return }
  …
  pollRef.current = setInterval(poll, STATUS_POLL_INTERVAL_MS)
  return () => { if (pollRef.current) clearInterval(pollRef.current) }
}, [phase])
```

`phase` is only reset by the session effect at line 63, which begins
`if (!isOpen) return` — so it resets on **open**, never on **close**. Clicking
"Done" (`handleDone` → `close()`) sets `isOpen` false and leaves `phase ===
'provisioning'`. The effect does not re-run, the cleanup does not fire, and
`window.api.steamBottleStatus()` keeps being invoked every 3 000 ms until the
user opens a *new* guided-setup session (which finally sets `phase = 'consent'`)
or restarts the app.

The interval only self-clears when `status.provisioned` becomes `true`. It never
does if the user cancels the Steam installer, if provisioning failed silently,
or if the channel is erroring — and the WR-03 `.catch` explicitly keeps polling
in that last case ("keep polling (the interval is still armed) and let the next
tick answer"), so a permanently-erroring channel is an unbounded, silent retry
loop.

**Fix:** Key the effect on the surface's liveness as well as its phase, and null
the ref:

```tsx
useEffect(() => {
  if (!isOpen || phase !== 'provisioning') {
    if (pollRef.current) { clearInterval(pollRef.current); pollRef.current = undefined }
    return
  }
  …
  return () => {
    if (pollRef.current) { clearInterval(pollRef.current); pollRef.current = undefined }
  }
}, [isOpen, phase])
```

Optionally also reset `phase` in `handleDone`. Consider a bounded retry count so
a permanently-erroring channel terminates into the `error` phase instead of
looping.

### C-06: The session reset clears four pieces of wizard state but not `enginesFetched` / `wineVersionList`, defeating the seed guard it exists to restore on a second session

**File:** `src/frontend/screens/Game/GamePage/components/SteamBottleSetup.tsx:63-94,134-166`

**Issue:** The reset effect's comment states its purpose precisely — the seeding
effect "latches on the first non-undefined engine it sets … without this reset, a
SECOND guided-setup session in the same app run would keep the FIRST session's
engine forever." It resets `phase`, `provisionError`, `provisioned`,
`wineVersion`, `persistedWineVersion` and `persistedLookupSettled`. It does
**not** reset `enginesFetched` or `wineVersionList`.

`enginesFetched` is the seed effect's guard against "seeding before the engine
list is known" (line 79-82: "otherwise a CrossOver engine that loads after
globalConfig would be missed"). On session 2 it is already `true` from session 1,
so the guard is inert: the seed effect can fire the instant
`persistedLookupSettled` flips, using session 1's **stale** `wineVersionList`,
before the re-issued `getAlternativeWine()` resolves. If the user installed
CrossOver between the two sessions, the derived default is computed against a
list that does not contain it — exactly the failure the guard was written for.

The window is narrow (both are IPC round trips racing), but it is real and the
fix is one line. Note `steamBottleSetupSeeding.test.ts` asserts only
`setWineVersion(undefined)` is present; nothing pins the completeness of the
reset set.

**Fix:**


### C-07: Two specs in `consoleSteamTarget.test.ts` measure a different property than their name claims

**File:** `src/frontend/screens/ConsoleMode/InstallOverlay/__tests__/consoleSteamTarget.test.ts:267-269,285-293`

**Issue:** The brief flagged that one such test (D4) was already caught in this
partition and told me to assume more of the same shape exist. Two do.

**B4** — "the function signature carries no blocked/degrade parameter":

```ts

```

`resolveConsoleActionIntent` takes a **single destructured object**
(`{ runner, focused }`), so `Function.prototype.length` is `1` no matter how
many properties that object gains. Adding `blocked: SteamQuickInstallDegrade` to
the destructured parameter — the exact drift the test names — leaves `.length`
at `1` and the test green. The assertion cannot fail for the reason the name
gives.

**C3** — "the mapping is exhaustive over every union member":

```ts
const reasons: Array<'library-missing' | 'library-full'> = ['library-missing', 'library-full']
```

observe it. This spec contributes nothing and its name claims otherwise.

```ts
const ALL_REASONS = ['library-missing', 'library-full'] as const
```

### C-08: Four "RED" gates in `consoleSteamTarget.test.ts` never run the real gate — they only assert that a hand-written literal contains a substring

**File:** `src/frontend/screens/ConsoleMode/InstallOverlay/__tests__/consoleSteamTarget.test.ts:303-318,356-367,392-402`

**Issue:** The project rule is that a source-scanning assertion must be proven to

```ts
it('D8-RED', () => {

    assertSteamBranchMarshalsThroughInstallSteamGame(
      "void install({ installPath: 'default', platformToInstall: 'Windows' })"
```
