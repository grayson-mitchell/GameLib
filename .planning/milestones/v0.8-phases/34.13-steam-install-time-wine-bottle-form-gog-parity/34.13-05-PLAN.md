executable, Jest-provable logic: given an already-open options dialog, which of platform row /
library dropdown / wine section / free-space line / content-light notice renders, and what state the

and it is the reason it exists as a separate file rather than an if/else chain inside
`SteamDialog/index.tsx` and `InstallModal/index.tsx`.

34.13-10 and 34.13-12 consume `resolveSteamSectionGating()`; 34.13-11 consumes its `wineSection`
field to decide where the D-25 loading row renders. Do not edit any dialog, store, or backend file
here.

## ⚠ This plan was REWRITTEN 2026-08-15 — read this before writing a line of code

The previous version of this plan built **two** exported functions: `steamInstallFormOpens()` (the
D-10 auto-open predicate `bottleRequired || (nativeInstallOn && libraryCount > 1) || alwaysShowOn`)
and a **six**-field verdict whose first field was `opens`. It swept **192** combinations over a
**16**-row matrix indexed by *(Host OS, Game kind, native install, always-show, library count)*.

**All of that is retired.** `34.13-CONTEXT.md` §"Amendments — quick-install model":

- **D-22** retires the auto-open triggers outright — *"The user is the trigger."* The dialog opens
  because the user clicked "Install with options…". Nothing computes whether it opens.
- **D-26** cuts the always-show setting (D-13) entirely, so `alwaysShowOn` has **no remaining
  source**: the `AppSettings` key it read is no longer created (34.13-01 is amended to drop it) and
  plan 34.13-04, which built the toggle, is **deleted from disk**.
- Consequently `steamInstallFormOpens()` has **no remaining caller** and the `opens` field has no
  remaining meaning. `34.13-RESEARCH.md` §"Amendment research" **Q5** states this as a verified
  conclusion and prescribes exactly the five-field shape below.

**What survives, and this is the point of the plan:** D-22's own text — *"D-11 survives in
substance"* — and Q5's verification of it. `hostPlatform`, `bottleRequired`, `libraryCount`,
`nativeInstallOn`, `hasWindowsDepot` and `selectedPlatform` all still decide **which sections
render**. Their arithmetic is unchanged; only their consumer changed. `libraryCount > 1` no longer
answers "does the form open" — it answers "is there more than one library to choose from", which is
the same expression serving its real purpose.

**One field is ADDED, not carried over.** The prior plan's acceptance criteria forbade any
`isEmpty` / `isDegenerate` / `contentLight` verdict field, on the reading that D-20 rejects an empty
state. That prohibition is **explicitly reversed** by the amended, checker-approved UI-SPEC: D-20's
expectation-setting copy lost its home when D-26 cut the always-show tooltip, and the UI-SPEC
resolves it onto the dialog itself (`ThirdPartyDialog`'s existing `.noticeIcon`/`.noticeInfo` slot,
key `gamelib:steam.install.contentLightNotice`) shown **only** on rows 5 and 7. A notice is not an
empty state — D-20's "build no empty state" ruling still holds and this module still carries no
empty-state field. Record the reversal in the module header so a future reader does not "fix" it
back.

**`34.13-UI-SPEC.md` §"Section-Gating Matrix" is the source of truth**, not this plan. It has
**8 rows numbered 1–8** with no gaps and **no "Form opens?" column**. If its row set has changed
again by execution time, follow the UI-SPEC and report the delta in the SUMMARY.
