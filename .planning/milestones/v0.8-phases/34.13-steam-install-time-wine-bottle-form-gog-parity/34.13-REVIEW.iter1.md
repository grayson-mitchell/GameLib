# Phase 34.13: Code Review Report

**Reviewed:** 2026-08-15
**Depth:** standard
**Files Reviewed:** 60
**Status:** issues_found

## Summary

The phase adds a Steam install-time Wine/bottle form across five seams: a new
`SteamDialog` sibling in `InstallModal`, a pure section-gating resolver, an
in-dialog eligibility probe, two new dual-registered IPC channels backed by a
single shared seam (`installFormIpc.ts`), a D-17 forced-Windows-via-bottle
install override with persisted durability, and Console Mode / menu entry
points.

The backend IPC seam is the strongest part of the change: it is genuinely
shared between the Electron and Tauri registrations, takes `unknown` on the
write channel, validates field-by-field, rebuilds a fresh object, and never
logs submitted values. `tsc --noEmit` is clean.

Two defects block shipping.

The first is a real behavioural hole in the phase's headline surface: the new
Steam options dialog mounts `<WineSelector>` **without** `hideSharedPrefixToggle`,
so the "Use shared Wine prefix" toggle renders on a path where Phase 17 CR-01
and this phase's own D-16 both say it must not. Flipping it writes the user's
*global* engine — commonly GPTK/`toolkit` on macOS — straight past the
CrossOver-only filter and into `persistBottleWineVersion`, which the backend
deliberately does not reject. That value then wins verbatim in
`resolveSteamBottleSeedEngine`, seeding the guided bottle wizard with an engine
`engineFilter.ts` itself describes as one that "would silently produce a broken
bottle." The guided setup path (`SteamBottleSetup.tsx:259`) passes the flag; the
new dialog does not, and no test asserts it.

The second is a localisation gap against the project's own standing blocking
gate: the dialog ships two `gamepage` keys that do not exist in the catalog at
all, and eight new user-facing frontend files were added without being added to
`meta/i18nGateScope.json` — the phase touched that file, but only to delete two
retired entries.

Beyond those, the recurring shapes are: floating promises on IPC round trips
inside effects (three sites), dead exports whose stated rationale is defeated by
the caller duplicating the logic inline (`steamBlockedMessageKey`), and a
"non-vacuity" test that does not exercise the assertion it claims to prove.

## Critical Issues

### CR-01: The Steam options dialog exposes the shared-prefix toggle, which bypasses the D-16 CrossOver-only engine filter and persists a broken engine

**File:** `src/frontend/screens/Library/components/InstallModal/index.tsx:394-413`
(also `WineSelector/index.tsx:110-120,255-266`; `SteamDialog/index.tsx:178-191`;
`installFormIpc.ts:100-104`)

**Issue:**

`InstallModal`'s Steam branch mounts `<WineSelector>` with `runner="steam"` and
`bottleNameReadOnly`, but **omits `hideSharedPrefixToggle`**. That prop is what
`SteamBottleSetup.tsx:259` passes for exactly this reason, and its own comment
states the rule: "the shared prefix/bottle must NEVER be selectable for the
dedicated Steam bottle."

Concrete failure chain, all on the new surface:

1. `WineSelector/index.tsx:255` — with the prop absent, the "Use shared Wine
   prefix" `ToggleSwitch` renders inside the Steam options dialog.
2. `WineSelector/index.tsx:113-116` — flipping it runs
   `setWineVersion(globalConfig.wineVersion)` and
   `setCrossoverBottle(globalConfig.wineCrossoverBottle)`. `globalConfig.wineVersion`
   is the user's **global** engine and is never passed through
   `filterWineEngines`/`selectDefaultEngine`, so a `toolkit` (GPTK) or plain
   `wine` engine lands in the parent's `wineVersion` state. D-16's whole purpose
   — `engineFilter.ts:8-25` — is defeated at the one place it is supposed to
   apply.
3. `SteamDialog/index.tsx:178-179` — `handleInstall` persists whatever is in
   `wineVersion` with no type check:
   `if (gating.wineSection && wineVersion) await window.api.persistBottleWineVersion(wineVersion)`.
4. `installFormIpc.ts:100-104` — the backend **deliberately** accepts `'toolkit'`
   ("backend engine rejection is an explicitly Deferred Idea"), so it is written
   to `steamBottleConfigStore`.
5. `steamBottleDefaults.ts:110-118` — `resolveSteamBottleSeedEngine` returns a
   persisted engine **verbatim, ahead of** the CrossOver-preferring derivation.
   The guided bottle wizard is now seeded with GPTK and `provisionBottle` runs
   with a non-CrossOver engine against a `cxbottle`-hardcoded mechanism.

This re-opens the exact 17-06 UAT finding that `installFormIpc.ts:52-63` cites as
its reason for reading `steamBottleConfigStore` directly. It also lets the shared
GOG/Epic bottle name reach `setCrossoverBottle` on the Steam path, which Phase 17
CR-01 closed.

No source gate covers it: `installModalSource.test.ts:266-272` counts
`runner="steam"` and `bottleNameReadOnly` occurrences but never asserts
`hideSharedPrefixToggle` is present.

**Fix:**

```tsx
// src/frontend/screens/Library/components/InstallModal/index.tsx (Steam branch)
<WineSelector
  appName={appName}
  winePrefix={winePrefix}
  wineVersion={wineVersion}
  wineVersionList={wineVersionList}
  title={gameInfo?.title}
  setWinePrefix={setWinePrefix}
  setWineVersion={setWineVersion}
  crossoverBottle={crossoverBottle}
  setCrossoverBottle={setCrossoverBottle}
  initiallyOpen
  runner="steam"
  bottleNameReadOnly
  // D-16 / Phase 17 CR-01: the shared GOG/Epic prefix+engine must never be
  // selectable for the dedicated Steam bottle — the toggle writes
  // globalConfig.wineVersion straight past the CrossOver-only filter.
  hideSharedPrefixToggle
/>
```

Add the matching gate to `installModalSource.test.ts`:

```ts
it('the Steam WineSelector hides the shared-prefix toggle (D-16 / 17 CR-01)', () => {
  expect(countOccurrences(stripped, 'hideSharedPrefixToggle')).toBe(1)
})
```

Belt-and-braces (recommended, cheap): make `SteamDialog.handleInstall` refuse to
persist a non-CrossOver engine rather than silently forwarding it, so a future
caller cannot re-create this hole through a different prop.

### WR-02: Console Mode validates one directory and installs to a different one, contradicting D-23

**File:** `src/frontend/screens/ConsoleMode/InstallOverlay/index.tsx:114-137`
(with `consoleSteamTarget.ts:63`)

**Issue:** `probeSteamQuickInstallTarget()` checks free space on
`target.steamappsDir` (the Steam primary library), but the install that follows
calls the **generic** `frontend/helpers` `install()` with `installPath: 'default'`.
`helpers/library.ts:77-81` resolves that to `AppSettings.defaultInstallPath` —
GameLib's generic install dir, not a Steam library — and forwards it as
`InstallArgs.path`.

D-23 (`InstallGameModal.ts:230-234`) is explicit: "NO path argument, ever …
passing a path here would create a second, driftable definition of 'primary'."
`InstallGameModal.ts:102` calls `installSteamGame` "the SOLE marshalling site for
`window.api.install` on the Steam path" — this call site falsifies that claim.

Not escalated to BLOCKER only because `installLocation.ts:201-218`'s
`resolveOverride()` rejects the unregistered path and falls back to primary — so
the bits land correctly, at the cost of a spurious
`rejected install-path override "…"` warning on **every** Console Mode Steam
install, and a check whose subject is not the write target.

**Fix:** Route the Console Mode Steam branch through `installSteamGame(game.app_name, game)`
(zero-arg `path`) instead of the generic `install()` helper, matching D-23 and the
desktop quick-install path.

### WR-03: Three IPC round trips inside effects are floating promises

**File:** `src/frontend/screens/Library/components/InstallModal/SteamDialog/index.tsx:167`;
`src/frontend/screens/Library/components/InstallModal/index.tsx:313`;
`src/frontend/screens/Game/GamePage/components/SteamBottleSetup.tsx:180-185`

**Issue:** ESLint confirms two (`@typescript-eslint/no-floating-promises` at
`SteamDialog/index.tsx:167` and `InstallModal/index.tsx:313`). The third is
`SteamBottleSetup`'s 3-second poll: `window.api.steamBottleStatus().then(...)`
with no `.catch`. Under the Tauri sidecar an unported/erroring channel rejects,
producing an unhandled rejection **every 3 seconds** for the life of the
provisioning phase — and the poll never surfaces the failure, so the banner sits
on "Setting up Steam…" forever.

Note the phase got this right elsewhere: `steamEligibilityProbe.ts:217-227` and
`InstallModal/index.tsx:200-211` both carry `.catch` handlers with explanatory
comments.

**Fix:**

```ts
// SteamBottleSetup.tsx
const poll = () => {
  void window.api
    .steamBottleStatus()
    .then((status) => { /* … */ })
    .catch(() => {
      // A rejected status read is not proof of failure; keep polling but
      // never leave an unhandled rejection behind.
    })
}
```
and `void getSpace()` / `void getWine()` at the other two sites (or `.catch`).

### WR-04: `contentLightNotice` copy tells the user to enable a setting that may already be enabled

**File:** `src/frontend/screens/Library/components/InstallModal/steamSectionGating.ts:248`,

this game — GameLib will install it into your Steam library."

### WR-05: `GameSubMenu`'s "Install with options…" appears for delisted and non-installable Steam games

### WR-08: The eligibility probe fires for the Steam **import** dialog, which discards the result

**File:** `src/frontend/screens/Library/components/InstallModal/steamEligibilityProbe.ts:45-63`,
called unconditionally at `InstallModal/index.tsx:95`

**Issue:** `shouldProbeEligibility` gates on `runner === 'steam'` and host
platform only. `isSteamManagedApp` (line 120) additionally requires
`action === 'install'`. So opening the **Import** dialog for a Steam game on macOS
fires `isSteamBottleEligible`, which reaches `checkBottleEligibility()` →
`ensurePlatformsCaptured()` → a real outbound `appdetails` fetch and a bounded
poll of up to `METADATA_FETCH_TIMEOUT_MS` (15 s) — for a verdict nothing on that
branch reads. The comment at `index.tsx:90-94` enumerates the no-op runners
("GOG/Epic/Amazon/sideload") and does not mention the Steam import case.

**Fix:** Thread the action into the gate so the probe matches the branch that
consumes it:

```ts
export function shouldProbeEligibility({ platform, runner, action }): boolean {
  if (runner !== 'steam' || action !== 'install') return false
  return platform !== 'win32' && platform !== 'linux'
}
```

### WR-09: A "non-vacuity" spec does not exercise the assertion it claims to prove

**File:** `src/frontend/screens/Library/components/InstallModal/SteamDialog/__tests__/steamDialogSource.test.ts:228-232`

**Issue:**

```ts
it('the disabled= count check is non-vacuous -- a specimen with a second disabled= trips it', () => {
  const specimen = 'disabled={eligibilityPending} ... disabled={notEnoughDiskSpace}'
  expect(specimen.split('disabled=').length - 1).toBe(2)
})
```

This asserts that `String.prototype.split` works. It never invokes the real gate
(the `expect(stripped.split('disabled=').length - 1).toBe(1)` assertion at line
224 is inline, not extracted into a callable helper), so it proves nothing about
the gate's ability to detect a second `disabled=`. Every other non-vacuity proof
in this file correctly uses `expect(() => assertX(specimen)).toThrow()` — this one
is the odd one out, in a repo whose memory ledger explicitly records "a gate can
be non-vacuous, correctly computed, RED-proven — and still guard NOTHING."

**Fix:** Extract the count check into a throwing helper (matching
`assertBoundedStatusDanger`'s shape) and drive both the real gate and the specimen
through it:

```ts
function assertSingleDisabledTerm(source: string) {
  const n = source.split('disabled=').length - 1
  if (n !== 1) throw new Error(`expected exactly 1 disabled= term, found ${n}`)
  if (!source.includes('disabled={eligibilityPending}')) throw new Error('…')
}
it('non-vacuous', () => {
  expect(() => assertSingleDisabledTerm(
    'disabled={eligibilityPending} disabled={notEnoughDiskSpace}'
  )).toThrow()
})
```

### WR-10: The Tauri registration casts `appName` to `string` while the write channel is documented as deliberately uncast

**File:** `src/backend/sidecar/steamAuthFlowRegistration.ts:259-261`

**Issue:** The block comment above these two handlers says "The write channel's
payload is passed through UNCAST — the seam takes `unknown` by design, and
casting here would defeat that guard at the type level." The read channel one
line up does exactly that: `getSteamBottleEligibilityVerdict(args[0] as string)`.

The runtime consequence is mild (the seam's `NUMERIC_APP_ID.test(appName)` at
`installFormIpc.ts:68` coerces, so `null`/`{}` fail closed) but not nil: a
**numeric** `123` coerces to `"123"`, passes the guard, and is then handed to
`new SteamGame(123 as unknown as string)`, where `this.appId` is a number for
every downstream `steamMetadataStore.get(this.appId)` / template-literal path.
The asymmetry also makes the comment above it false.

**Fix:** Change the seam's signature to `getSteamBottleEligibilityVerdict(appName: unknown)`
and add `typeof appName !== 'string'` to the existing guard, then drop the cast
in both registrations. One guard, both runtimes, no cast — the file's own stated
design.

### WR-11: `SteamQuickInstallDegrade.onlyLibrary` and `.freeBytes` are written but never read

**File:** `src/frontend/state/InstallGameModal.ts:36-42,53-54,166-167,177-178`

**Issue:** The doc comment says "`onlyLibrary` exists so the dialog can tell,
without re-deriving it, that it is in the UI-SPEC's flagged ≤1-library corner."
Verified by grep: no non-test reader of either field exists. `SteamDialog/index.tsx:230-238`
branches on `reason` alone, and the Console Mode failure card

### WR-16: `library.ts` collapses "never captured" into `false` for `is_windows_native`, discarding the distinction both type declarations insist on

**File:** `src/backend/storeManagers/steam/library.ts:698`

**Issue:** `is_windows_native: cachedMeta?.is_windows_native ?? false`. Both
`common/types.ts:229-239` and `electronStores.ts:48-55` document the field's
contract as three-valued: `undefined` means "never captured (pre-34.13 entry)",
`false` means "confirmed no Windows depot", and only `=== true` permits offering
a Windows install. Hydrating `undefined → false` destroys the first state at the
`GameInfo` boundary — the renderer (`steamPlatformRow.ts:54`) can no longer tell a
cold-cache game from a confirmed Windows-less one.

Behaviour is identical **today** (both collapse to "Windows absent" under
`=== true`), which is why this is a WARNING and not a BLOCKER. But it silently
forecloses the obvious future refinement (e.g. showing "checking…" for an
uncaptured game instead of hiding the option), and it contradicts two doc
comments that a reader will rely on.

**Fix:** `is_windows_native: cachedMeta?.is_windows_native` — the field is already
optional on `GameInfo`, and every consumer uses `=== true`, so preserving
`undefined` is behaviour-neutral and restores the documented contract. Update the
line's own comment, which currently asserts the `false` default "is load-bearing."
