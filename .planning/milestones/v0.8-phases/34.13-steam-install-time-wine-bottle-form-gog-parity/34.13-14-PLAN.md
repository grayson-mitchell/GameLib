<objective>
Make a D-17 forced Windows-via-bottle install **durable**. 34.13-06 teaches `install()` to honor the
override; this plan makes the choice survive the install, so the game is launchable, uninstallable,
and correctly configured afterwards.

Purpose: this closes `T-34.13-06-06`, the blocker 34.13-06 escalated (disposition `transfer`) and
deliberately did not absorb. Today, every successful forced install produces a game whose bits live
in the bottle's `steamapps` while `launch()` fires `steam://rungameid` at the host Steam client that
never had the game, and `uninstall()` takes the native path and leaks the bottle copy forever. That
is the guaranteed outcome of every use of the feature, not an edge case — and it contradicts D-17's
stated purpose and the UI-SPEC tooltip's promise ("you can install the Windows version instead
through a Wine bottle").

Output: one persisted per-app boolean, one widened predicate, one bridge pin, one carry-forward, one
clear-on-uninstall, and the specs that prove each is load-bearing.

**Scope fence.** This plan does NOT change *which* branch `install()` picks for a fresh install —
34.13-06 owns that and its 16-spec baseline must stay green, unmodified. This plan changes what is
TRUE about an appId *after* a forced install has committed.
</objective>

   So one edit to `isBottleEligible()` does make five surfaces consistent. The sixth is a hazard,
   not a benefit — see finding 2.

2. **⚠ The blocker did not name `isBridgeEligible()`, and widening it would ship a NEW mis-route.**
   `isBridgeEligible()` = `isBottleEligible() && bridgeAllowlist.has(appId) && !bridgeFailedThisSession`.
   A forced install writes into the **Phase 17 `GameLibSteam`** bottle (`installBottleNative` →
   `getBottleSteamappsDir`, or `tellBottledSteamToInstall`). The Phase 24 **`GameLibSteamBridge`**
   bottle is a different filesystem root. If a forced, allowlisted title became bridge-eligible,
   `launch()` would take `launchBridgeGame()`, `resolveBridgeLaunchExe()` would find nothing in the
   bridge bottle, and the D-UAT-24-02 guard (`games.ts:1556`) would fire `steamBridgeSetupRequired`
   and return `false` — a *different* broken launch, introduced by the fix. `isBridgeEligible()`
   must therefore be pinned to the platform-derived verdict.

3. **⚠ The blocker's "install-state detection" row is imprecise — that surface is already correct
   and needs NO edit.** `library.ts` does not call `isBottleEligible()` at all; it holds its own
   copy of the predicate in `isBridgeAuthoritativeForInstallState()` (`library.ts:145-151`).
   For a forced mac-native game that function returns `false` (it requires
   `is_mac_native === false` or `mac_arch === '32'`), so `refresh()` (`library.ts:667-677`) and
   `refreshInstallState()` (`library.ts:866-876`) fall through to
   `nativeInstalledData ?? bottleInstalledData ?? bridgeInstalledData`. The bottle map is built for
   **every** appId whenever `isMac && isBottleProvisioned()` — which a forced install guarantees —
   so a forced install already reconciles as installed with `install.platform: 'Windows'`
   (`installPlatformForSource`, `library.ts:112-113`). **Do not "fix" this. Pin it instead**, and
   pin that the bridge does not become authoritative once the flag exists.

4. **`steamMetadataStore.set` at `games.ts:588` is the ONLY whole-entry-replacing write in the
   tree.** Enumerated: `games.ts:506` (GAP-B delisted branch) spreads `...(existing ?? seed)`;
   `library.ts:554` (art migration) spreads `...meta`; `library.ts:1194`
   (`verifyMacArchGroundTruth`) spreads `...(existing ?? seed)`. Only `games.ts:588` enumerates
   fields explicitly — and its own T-18-02-04 comment (`games.ts:583-587`) already documents that
   any field not carried forward is silently dropped on the next fetch. **That call site is the one
   place the forced verdict can evaporate.** `existingMeta` is already in scope there
   (`games.ts:555`), so the carry-forward needs no new read.

5. **The bidirectional `games.ts` ↔ `library.ts` import already exists and works.**
   `library.ts:30` is `import SteamGame, { isNativeInstallInFlight } from './games'`, and
   `games.ts:40` imports from `./library`. Adding `clearForcedWindowsViaBottle` to that existing
   named-import list follows the established in-file pattern — it is not a new cycle.

6. **`pollUninstallOnce(appId, source)` already knows the source** (`library.ts:1956-1958`) and its
   `state === 'absent'` branch (`library.ts:1963`) is the confirmed-removal signal. ⚠ **The library
   Map update inside it is wrapped in `if (existing)` (`library.ts:1974`) and the in-repo debug note
   above it records that this can be a MISS.** A clear placed inside that guard would be silently
   conditional on an unrelated Map hit — put it before the guard.

7. **`installBottleNative()` (`games.ts:827-836`) delegates to `installDepotDownload()` and returns
   its `InstallResult`.** `install()`'s bottled-Steam dispatch terminal already has a WR-01 success
   guard (`games.ts:752-754`: `if (result.status !== 'done') return { status: 'error', ... }`), so
   the "dispatch was accepted" point is already isolated in source.

8. **`forceUninstall()` (`games.ts:1786`) touches only the library Map + `steamLibraryStore`, never

   the entry is deliberately kept for i386-recovery). It must **not** clear the forced verdict —
   the bits are still in the bottle. This is a deliberate non-edit, pinned by a spec.
