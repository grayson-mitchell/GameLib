## Decisions Made

- `resolveSteamBottleSeedEngine` takes `persistedWineVersion: unknown` (not `WineInstallation | undefined`) because the value originates in an on-disk `electron-store` file that may hold legacy/hand-edited content -- the compile-time type is a claim the runtime cannot be held to.
- The verdict-fetch effect ignores `verdict.eligible` (the wizard is already open because the backend decided it should be -- re-gating in the renderer would be a frontend re-derivation of an authority D-09 places in the backend) and `verdict.bottleName` (34.13-10's read-only concern, never this wizard's, per `<verified_findings>` item 5).
- Kept the multi-line `window.api\n.isSteamBottleEligible(appName)\n.then(...).catch(...)` method-chain style (matching the existing `getAlternativeWine()` effect immediately above it) rather than collapsing to one line -- adjusted the source-gate's regex to tolerate the line break (`\s*` between `window.api` and the method) instead of distorting the source formatting to fit a stricter regex.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] Task 2 spec (g)'s originally-planned regex was vacuous against pre-existing source**
- **Found during:** Task 2, running the RED baseline before the source edit
- **Issue:** The plan's literal instruction was `contains no occurrence of` the bare substring `bottleName`. `SteamBottleSetup.tsx`'s pre-existing (predates this plan) `handleConfirm` already contains `bottleName: crossoverBottle || undefined` as an object-literal key in the `steamBottleProvision` payload -- unrelated to the verdict's `bottleName` field this spec exists to guard against. A bare substring match would have failed this spec in the RED run for the WRONG reason and, worse, would have been satisfiable post-edit only by also renaming or removing that pre-existing, unrelated key -- a false positive baked into the gate from authoring.
- **Fix:** Narrowed the assertion to `.bottleName` (property-access form, i.e. `not.toMatch(/\.bottleName\b/)`), which targets consumption of a fetched verdict's field rather than any occurrence of the word. Documented the reasoning inline in the test file.
- **Files modified:** `src/frontend/screens/Game/GamePage/components/__tests__/steamBottleSetupSeeding.test.ts`
- **Verification:** Re-ran RED baseline with the fixed regex: spec (g) passes against the unmodified tree (as the plan predicted), and the mutation test (evidence item 5 above) still fails it on both halves when `verdict.bottleName` is actually consumed -- confirming the narrower regex is neither vacuous nor over-broad.
