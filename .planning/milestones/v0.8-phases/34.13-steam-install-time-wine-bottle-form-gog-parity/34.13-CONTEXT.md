# Phase 34.13: Steam install-time wine/bottle form (GOG parity) - Context

**Gathered:** 2026-08-14
**Status:** Ready for planning

<domain>
## Phase Boundary

A Steam install offers the user an explicit choice at the moment they start it: a one-click **quick
install**, or an **"Install with options…"** path that opens GameLib's install modal — platform row
plus wine/bottle choice — the way a GOG game does. Today it does neither: it installs silently with
hardcoded settings and no way to intervene.

**⚠ AMENDED 2026-08-15 by D-21..D-28 (see `## Amendments — quick-install model` below).** As
originally gathered, this boundary read: *"…opens GameLib's install modal … the same way a GOG game
does … Plus a global opt-in setting to always show the form for every Steam install."* The form no
longer opens on invisible triggers, and the always-show setting is **cut** (D-26). ROADMAP.md's
phase goal still carries the superseded wording and must be rewritten to match.

**In scope:** a new Steam-specific dialog inside the existing `InstallModal`; the split-button
control that routes to quick vs. options; a backend-authoritative bottle-eligibility IPC;
persistence of the chosen wine version; retirement of `SteamInstallLocationPicker` into the new
form; the CrossOver-only engine filter for Steam's `WineSelector`.

**Out of scope:** per-game bottles or an editable bottle name (Phase 22); implementing
`getInstallInfo()` or any download-size computation; changing how `SteamGame.install()` routes
between its four branches; the guided `SteamBottleSetup` surface itself (D-07, Phase 17) beyond
feeding it the form's chosen wine version.

</domain>

<decisions>
## Implementation Decisions

### Form content & shape

- **D-01: Steam gets a NEW lean sibling dialog inside `InstallModal`** — a fifth alongside
  `DownloadDialog` / `ImportDialog` / `SideloadDialog` / `ThirdPartyDialog`, reusing `WineSelector`,
  `platformSelection()` and the shared `Dialog` chrome. Do **NOT** add Steam branches to
  `DownloadDialog`; it is already dense with Epic/GOG-specific DLC, SDL, branch, build and language
  machinery that Steam has none of.

- **D-02: The Steam library location folds INTO the form** as a dropdown fed by
  `listSteamLibraryTargets()`, defaulting to the primary library.
  **QUALIFIED by the D-10 finding:** the dropdown renders **only when the destination is a host
  Steam library** — never for bottle-eligible games, because `installBottleNative()`
  (`games.ts:827`) overrides the write target to `getBottleSteamappsDir(...)`. A host-library
  dropdown on a bottled install would be a lie about where the game goes.

- **D-03: The platform row renders for Steam even when only one platform is available**, as a
  read-only "Windows", so the user can see *why* a bottle is being requested.
  Today `InstallModal/index.tsx:130` hides the selector unless `availablePlatforms.length > 1`, and
  a bottle-eligible macOS game has `is_mac_native === false` by definition — so Windows is the only
  entry and **the platform selector renders nothing for exactly the games this phase targets**.
  Without this decision, the "platform selection" half of the phase goal is a no-op.
  **⚠ AMENDED 2026-08-14 by D-17/D-18 (see `## Amendments` below) — the row is read-only only on
  Windows hosts. On macOS it is SELECTABLE; on Linux it does not render at all.**

- **D-04: `SteamInstallLocationPicker` RETIRES.** The form becomes the single Steam install surface.
  D-09's (Phase 21) 0/1-library zero-friction case is unchanged — nothing opens.

- **D-05: The CrossOver bottle name field is shown prefilled and READ-ONLY** (the dedicated
  `GameLibSteam` bottle). `WineSelector` renders it as free text today; for Steam it must not be
  editable. A name this phase cannot provision is a broken promise, and multi-bottle is explicitly
  Phase 22 scope.

### Download-size blocker

- **D-06: NO download/install size row for Steam.** The form opens instantly and the Install button
  is **never** gated on `diskSize`. Rationale, both halves independently sufficient: (a) with
  `enableSteamNativeInstall` OFF (the default) the install is delegated to `steam://install` or the
  bottled Steam client, so GameLib never computes a size and there is nothing to show, ever;
  (b) `buildDepotPlan` (`depot.ts:628`) requires an authenticated Steam CM connection and then does
  3× `getProductInfo` plus `getDepotDecryptionKey` + `getRawManifest` **per owned depot** — it
  already carries temporary timing instrumentation from the `steam-install-slow-start` debug session.

- **D-07: `SteamLibraryManager.getInstallInfo()` (`library.ts:771`) stays a stub.** The new Steam
  dialog never calls the frontend `getInstallInfo` helper, so the stub can never hang it. Its
  existing comment — which correctly explains that the modal would loop forever on "Geting download
  size…" — is **updated** to record that the Steam dialog deliberately does not consult it, rather
  than left implying the short-circuit is the only defense.

- **D-08: Disk info is FREE SPACE ONLY** on the selected Steam library drive. No "after install"
  projection, no not-enough-space blocking, no force-install label. Free space is still the useful
  number when choosing between two libraries, which is the decision D-02's dropdown asks for.

### When the form appears

- **D-09: New backend-authoritative IPC `isSteamBottleEligible(appName)`**, which internally awaits
  `ensurePlatformsCaptured()` and then returns the real verdict.
  **Do NOT create a third frontend copy of the eligibility predicate.** It already exists twice —
  `games.ts:1328` (`isBottleEligible`) and `library.ts:145`
  (`isBridgeAuthoritativeForInstallState`). `GameInfo` does carry `is_mac_native`, `mac_arch` and
  `steamPlatformsCaptured` (`types.ts:221/227/234`) so a frontend derivation is *possible*, but it
  would drift from the backend and a cold metadata cache reads as "not eligible" — which is the
  precise shape of `.planning/debug/steam-bottle-guided-setup-never-fires.md`.

- **D-10: The form opens on EITHER trigger** — bottle required, **OR** >1 Steam library — plus the
  always-show setting. Sections gate independently and are almost disjoint:

  | Trigger | Platform | Form shows | Destination |
  |---|---|---|---|
  | Bottle required | macOS only | wine version + read-only bottle name | the bottle's `steamapps` |
  | >1 Steam library | any | library dropdown | chosen host library |

  This is what keeps Phase 21's D-09 multi-library override alive after `SteamInstallLocationPicker`
  retires. A bottle-only trigger plus a retired picker would silently drop the multi-library case
  on every platform — that combination was considered and rejected as a D-09 regression.

- **D-11: On Windows/Linux the always-show setting renders the library dropdown + read-only platform
  row, and no wine section.** Same component, sections gated by relevance — the model D-10 already
  commits to.

- **D-12: Busy/disabled state on the Install button** while `isSteamBottleEligible` resolves. A cold
  cache can wait up to `METADATA_FETCH_TIMEOUT_MS`. No half-rendered modal that does not yet know
  whether it should show a wine section; and no silent multi-second dead click either.

- **D-13: The always-show setting is GLOBAL ONLY.** Follow `EnableSteamNativeInstall.tsx` /
  `nativeInstallSetting.ts` exactly — `isDefault`-gated UI, one `GlobalConfig` key, one backend read
  seam that is the only place reading it. No per-game override; the bottle-required and
  multi-library triggers already cover the per-game cases that matter.

### Where the choice lands

- **D-14: The chosen wine version is written via `persistBottleWineVersion()` into
  `steamBottleConfigStore`** — the store `getSteamBottleSettings()` (`bottle.ts:276`) actually
  reads. This is **shared across every bottled Steam game**, and that consequence must be stated
  plainly in the form's own copy.
  The GOG mechanism (write per-game `GameConfig`, then call install) **does not work here**:
  `SteamGame.getSettings()` returns `getSteamBottleSettings()` for bottle-eligible games and ignores
  `GameConfig` entirely. `bottle.ts:291-306` documents a real bug already caused by exactly that gap
  — a per-game `setSetting('wineVersion')` self-heal silently dropped. Note also that `InstallArgs`
  (`types.ts:402`) carries **no wine fields at all**, so nothing travels through the install call
  today.

- **D-15: The form feeds the guided setup; it does not replace it.** When the bottle is not
  provisioned, the form persists the wine choice, `install()` still fires `steamBottleSetupRequired`
  exactly as today, and `SteamBottleSetup` opens **already carrying that wine version instead of
  re-asking**. D-07 (Phase 17) stays intact and the user answers once.
  Inline provisioning from the form was considered and rejected: unlike the bridge path's fast
  `cxbottle --create` (`games.ts:installBridgeGame`, which provisions inline precisely because it
  needs no consent), `provisionBottle` downloads and launches `SteamSetup.exe` and needs the user to
  click through a real multi-GB installer — which is why the dedicated consent surface exists.

- **D-16: Steam's `WineSelector` is filtered to CrossOver-type engines only** when
  `runner === 'steam'`. Bottle creation is hardcoded to `cxbottle`, so any other engine silently
  yields a broken bottle. **Frontend filter only this phase** — the backend `provisionBottle`
  rejection and the `resolveSteamBottleEngine` silent-override half were considered and left on the
  todo (see Deferred).

### Folded Todos

- **`.planning/todos/pending/steam-bottle-gptk-engine-produces-broken-bottle.md`** (2026-07-17,
  area: steam) — "Steam bottle setup offers GPTK/Wine engines that produce a broken bottle."
  Bottle *creation* is hardcoded to CrossOver's `cxbottle`, but the run-path in `launcher.ts:434-442`
  treats engines as mutually exclusive prefix-vs-bottle models, so a `toolkit` (GPTK) Steam bottle
  drops the bottle binding, runs against a prefix with no Steam client, and `isBottleReady()` never
  passes — silently broken, no error surfaced.
  **Fits this phase because this phase creates a second surface that re-exposes the same affordance.**
  **PARTIALLY folded — D-16 takes the frontend-filter half only.** The todo is **re-scoped, not
  closed**: its `provisionBottle` rejection half and its `resolveSteamBottleEngine` silent-override
  half remain open and must survive this phase.

## Amendments

*Added 2026-08-14 during `/gsd-ui-phase 34.13`, after research verified the backend. These are user
decisions of the same standing as D-01..D-16 and they AMEND D-03.*

- **D-17: On macOS the platform row is SELECTABLE, not read-only — a mac-native game can be forced
  to install as Windows through the bottle.** This is the user-stated primary motivation: native
  Steam ports are frequently absent, outdated, or worse than the Windows build, and overriding a
  native install is the real reason to open the form for a game that does not strictly need it.

  **This is a scope EXTENSION beyond CONTEXT.md as originally written, and it is backend work, not
  a form change:**
  - `InstallArgs.platformToInstall` exists (`types.ts:402`) but **no code in the Steam backend
    reads it** — verified 2026-08-14, the only occurrences are test fixtures in
    `installLocation.test.ts`. Install routing today is 100% `isBottleEligible()` (`games.ts:1328`).
  - `SteamGame.install()` (`games.ts:701`) must therefore learn to honor an explicit platform
    choice, overriding the `isBottleEligible()` verdict for the mac-native → Windows direction.
    This narrows — but does not delete — the `<code_context>` note that "this phase does not
    restructure that tree": the four branches stay, an override input selects among them.
  - The form must only offer Windows when the game actually HAS a Windows depot. Planning must
    establish where that signal comes from; `steamMetadataStore` carries `is_mac_native` /
    `mac_arch` / `platformsCaptured`, and whether Windows availability is already captured is an
    open planning question, not an assumption.
  - **Consequence for D-13:** the always-show setting stops being decorative on macOS. Overriding a
    *native* install is only reachable if the form opens for a native game, and always-show is what
    opens it. This is now the setting's primary justification.

- **D-18: On Linux the platform row does NOT render.** GameLib owns no Windows-compat path for
  Steam on Linux — `isBottleEligible()` returns `false` for `!isMac` (`games.ts:1329`), and
  `isNative()`'s own doc-comment states it: *"Non-macOS (Linux/Windows) always returns true — those
  platforms keep the native `steam://` delegation unchanged; Proton is Steam's own concern."*
  A Windows option on Linux would be a control the delegated install discards — the same "lying UI"
  failure D-02's own qualification exists to prevent. Section gates off entirely, consistent with
  D-11's "sections render only when relevant" model.
  Building a real Linux Proton/wine path for Steam was considered and rejected as its own subsystem
  (see Deferred).

- **D-19: On Windows hosts the platform row stays read-only**, exactly as D-03 originally
  specified — there is only ever one option.

- **D-20: The "content-light form" question is resolved by D-17/D-18, not by an empty state.** With
  native install OFF and always-show ON, the form is content-free only on a *Windows host*
  (no library dropdown, no wine section, one read-only row). That combination is accepted as-is
  rather than special-cased — nothing it could show would be actionable, since the delegated
  `steam://install` path ignores both path and platform. Expectation-setting belongs in the
  always-show setting's own tooltip copy (already Claude's Discretion). Research's options 2
  (ungate `listSteamLibraryTargets()` for display) and 3 (expose `isSteamNativeInstallEnabled()` to
  the frontend) were both considered and rejected — see `34.13-RESEARCH.md`.

## Amendments — quick-install model

*Added 2026-08-15 during `/gsd-discuss-phase 34.13`, before any plan executed (14 planned, 0
executed). These are user decisions of the same standing as D-01..D-20. They AMEND D-04, D-10,
D-11, D-12 and D-20, and they RETIRE D-13.*

**Why this arrived:** the user's own framing — *"Steam's native experience is that you just click
install and it works, and then hidden away in menus you can change the game settings when you need
to."* D-01..D-20 decided **for** the user whether the form opened, through three invisible triggers
(bottle required, >1 library, always-show setting), and put the only user-facing control in
Settings — which is precisely the "hidden away in menus" model the phase exists to improve on.

**What made it cheap:** a safe default already exists for every case that previously force-opened
the form. >1 library → Phase 21's D-09 already defaults to Steam's primary. Bottle required →
`install()` already picks the bottle from `getSteamBottleSettings()` and fires
`steamBottleSetupRequired`, so consent is already asked at the right moment. The auto-open triggers
were compensating for the absence of a way to let the user ask.

- **D-21: The install control becomes a SPLIT BUTTON — primary = quick install, caret =
  "Install with options…".** A persisted toggle that changes what one button does was considered
  and REJECTED: the same control would do different things on different days and the label would
  have to be read every time. The split button gives both paths in one click each with no mode
  state. `src/frontend/components/UI/Dropdown/` already exists (with disclosure tests) and is the
  likely primitive — planning should confirm rather than build a new one.

- **D-22: The auto-open triggers RETIRE. The user is the trigger.** This amends **D-10** — its
  two-row trigger table (bottle required / >1 library) no longer governs *whether* the form opens.
  D-10's underlying insight survives in a different place: those two conditions are still what make
  the form *worth* opening, and they still decide which sections render once it is open.
  **D-11 survives in substance** — sections render only when relevant — but is reached by user
  intent instead of by the setting.

- **D-23: Quick install targets Steam's primary library, always.** Preserves Phase 21's D-09
  default exactly and adds no new persisted state; it also mirrors Steam's own default-library-folder
  concept. "Remember last used" was considered and rejected — it costs a new global key and
  introduces a "why did it go there?" failure mode when the remembered drive is disconnected.
  **Planning must verify what "primary" resolves to** — `libraryfolders.vdf` index 0 vs. a Steam
  default-designation flag. This is an open technical question, not an assumption.

- **D-24: If the quick-install target library is missing or full at click time, quick install
  DEGRADES into the options dialog** with the problem surfaced, rather than erroring out or
  silently picking another drive. Consequence: quick install needs a cheap **local** validity check
  (path exists, free space) before firing — no Steam CM round-trip, so this does not reintroduce
  the latency D-12 was written for.

- **D-25: The options dialog opens INSTANTLY; the wine section carries the eligibility loading
  state; the dialog's own Install button stays disabled until it resolves.** This amends **D-12**
  and **replaces `34.13-UI-SPEC.md`'s "D-12 Busy State Contract"**, whose premise ("where it
  renders: NOT inside the new dialog") was correct only while the click had to decide whether a
  form appeared at all. With an explicit "Install with options…" click the user has already asked
  for the dialog, so withholding it for up to `METADATA_FETCH_TIMEOUT_MS` is a dead click. The
  dialog already has dynamic sections — D-17's macOS platform switch reveals the wine section — so
  a loading state extends an existing mechanic rather than inventing one.
  **The quick path needs no eligibility probe at all**: the backend already resolves it inside
  `install()`. This removes the multi-second dead-click risk from the default path entirely.

- **D-26: D-13 is RETIRED — the global always-show setting is CUT.** The caret puts the form one
  click away on every surface, which is what the setting existed to guarantee. **Plan 34.13-04 is
  deleted, not reinterpreted.** Reinterpreting it as "which half is primary" was considered and
  rejected as redundant.
  Two knock-on effects:
  - **D-17's "Consequence for D-13" clause dies**, but D-17's substance is *better* served — forcing
    a mac-native game to Windows-via-bottle no longer requires finding a setting first; the caret
    reaches it directly. D-17 stands unchanged.
  - **D-20 survives, but loses its remedy.** Its content-free-form case (Windows host, native
    install OFF) is still reachable — now on demand via the caret — and its resolution (accept
    as-is, build no empty state) still holds. But D-20 parked expectation-setting in "the always-show
    setting's own tooltip copy," which no longer exists. **OPEN FOR PLANNING:** either the dialog
    carries that line itself or nothing does. Not decided here.

- **D-27: Entry-point map.** `openInstallGameModal` has **six** call sites, verified 2026-08-15.
  Only two gain the split; the rest route to one fixed behavior, keeping the diff small and
  removing any surface where the same intent produces a different result.

  | Call site | Behavior |
  |---|---|
  | `GamePage/components/MainButton.tsx:282,316` | **Split** — primary quick, caret options |
  | `Library/components/GameCard/index.tsx:322` | **Split** — button quick, context menu gains "Install with options…" |
  | `Library/index.tsx:474` | Fixed — quick |
  | `Game/GamePage/index.tsx:339` | Fixed — quick |
  | `Game/GameSubMenu/index.tsx:176` | Fixed — options; item relabels to "Install with options…" |
  | `InstallModal/DownloadDialog/index.tsx:305` | Fixed — options (already inside the modal) |

  `GameSubMenu`'s existing Install item becoming the deliberate path means the caret and the "…"
  menu agree; leaving it as a plain duplicate of the primary button was considered and rejected.

- **D-28: Quick install is STEAM-ONLY this phase.** GOG/Epic/Amazon keep always opening the modal.
  Extending the idiom to every runner needs a per-runner safe-default analysis this phase has no
  budget for (see Deferred). **Consequence:** the phase no longer delivers "GOG parity" — it
  overshoots it, and makes Steam the odd runner out in the opposite direction. The phase title and
  goal in ROADMAP.md carry the superseded framing and must be rewritten.

- **D-29: Console Mode gets D-24's check, but NOT an options path.** *(Added 2026-08-15 during
  `/gsd-plan-phase 34.13`, after plan 08's call-site re-verification found a surface D-21..D-28
  never considered.)* `ConsoleMode/InstallOverlay/index.tsx:96-117` is a **ninth** install entry
  point — the gamepad UI — outside D-27's map entirely. It fires the generic `install()` helper with
  `installPath: 'default'`, which `resolveOverride()` coerces to the primary library, so **D-23
  holds there by containment, accidentally rather than by design**. But **D-24's local validity
  check never runs on that path**, so a Console Mode install to a missing or full primary library
  fails in exactly the way D-24 exists to prevent.
  **Decision:** extend D-24's local check (path exists + free space) and its degrade signal to the
  Console Mode path, giving it quick-install parity. **No options dialog in Console Mode.**
  A gamepad-navigable options surface was considered and REJECTED for this phase: the approved
  `34.13-UI-SPEC.md` has no contract for one, and designing it would need another `/gsd-ui-phase`
  pass. Leaving the gap unfixed was also considered and rejected — it would ship a surface where
  D-24's protection provably does not apply.
  **Consequence:** D-24's degrade has two distinct shapes. On the six D-27 surfaces it degrades
  *into the options dialog*; in Console Mode there is no dialog to degrade into, so the failure must
  surface some other way. **OPEN FOR PLANNING:** what Console Mode shows when the check fails.

<specifics>
## Specific Ideas

- **"the same way a GOG game does"** is a parity target for the *user-facing experience* (a modal
  appears, you choose wine/bottle, you confirm), not for the *mechanism*. Three GOG mechanisms are
  explicitly not copied: the size-gated Install button (D-06), the free-directory path picker
  (D-02), and the per-game-config wine write (D-14). Planning should not treat divergence from
  `DownloadDialog` as a defect.
- The user caught a genuine inconsistency mid-discussion — retiring the picker while triggering only
  on "bottle required" would silently drop the multi-library case. The corrected model (D-10) is
  load-bearing; a planner that narrows the triggers back to bottle-only reintroduces the regression.
