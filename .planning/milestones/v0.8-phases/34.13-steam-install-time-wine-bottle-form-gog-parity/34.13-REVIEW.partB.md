## Critical Issues

### B-CR-01: A rejected `persistBottleWineVersion` permanently wedges the Install button and silently aborts the install

**File:** `src/frontend/screens/Library/components/InstallModal/SteamDialog/index.tsx:198-260` (specifically `210`, `217`)

**Issue:**
`handleInstall` sets the WR-13 latch and then awaits an IPC round trip that has **no rejection handler**:

```ts
setSubmitting(true)                                   // 210 — never reset
if (gating.wineSection && wineVersion) {
  const result = await window.api.persistBottleWineVersion(wineVersion)   // 217
  if (result.status === 'error') { /* logged, continues */ }
}
...
backdropClick()                                       // 237
installSteamGame(...)                                 // 241
```

The code handles a *resolved* `{ status: 'error' }` but not a **rejection**. `persistBottleWineVersion` is `makeHandlerInvoker('persistBottleWineVersion')` (`src/preload/api/steam.ts:28`), which is `ipcRenderer.invoke` under Electron and `tauriInvoke(SIDECAR_INVOKE, …)` under Tauri (`src/preload/ipc.ts:38-46`, `src/preload/tauriTransport.ts:92-99`). Both reject on a dead channel, a throwing handler, or a sidecar RPC failure — the exact class of failure this repo has ledgered repeatedly under the Tauri sidecar.

On rejection:
1. The `await` throws, so `backdropClick()` and `installSteamGame(...)` **never run** — the user's install silently does not happen.
2. There is no `try/finally`, so `submitting` stays `true` forever. `disabled={eligibilityPending || submitting}` (line 379) leaves the Install button **permanently dead** while the dialog is still open.
3. `handleInstall` is `async` and passed straight to `onClick` (line 378), so React discards the returned promise — this is an **unhandled promise rejection**, precisely what WR-03 (`e9930a1fe`) was created to eliminate on three sibling round trips.

The inline WR-13 comment asserts the latch is safe because *"`handleInstall` ends by closing the dialog, so the component unmounts; leaving it latched is what makes the double-click impossible"* (lines 140-143). That reasoning holds only on the success path. On the rejection path the component does **not** unmount, and the latch becomes a wedge instead of a guard. The fix therefore closed the double-click route while opening a dead-UI route.

The user's only escape is the header close button; there is no error surfaced anywhere, and the persisted-engine store is left in whatever state the failure produced while `installSteamGame` is skipped entirely.

**Fix:** Wrap the persist in its own rejection handler (matching the D-14 "a failed persist degrades to today's behaviour rather than blocking the install" rule already stated in the comment at lines 220-224) and release the latch on every non-success terminal path:

```ts
const handleInstall = useCallback(async () => {
  if (submitting) return
  setSubmitting(true)

  if (gating.wineSection && wineVersion) {
    // A REJECTION is the same class of outcome as `{ status: 'error' }`:
    // the guided bottle setup still derives an engine when nothing was
    // persisted (D-15), so neither may block the install.
    const result = await window.api
      .persistBottleWineVersion(wineVersion)
      .catch(() => ({ status: 'error' as const }))
    if (result.status === 'error') {
      window.api.logError(
        `34.13-10 SteamDialog: persistBottleWineVersion failed with status "${result.status}"`
      )
    }
  }

  const destination = resolveSteamInstallPath(
    selectedPath,
    steamLibraries,
    gating.libraryDropdown
  )
  backdropClick()
  installSteamGame(appName, gameInfo, destination, gating.forceWindowsViaBottle)
}, [...])
```

If you prefer to keep the latch as the sole double-click control, add a `try { … } catch { setSubmitting(false); return }` around the persist so the button can never be left dead. Add a spec driving a **rejecting** `persistBottleWineVersion` mock and asserting that `installSteamGame` is still called — the current `steamDialogSource.test.ts` is source-text only and cannot observe this at all.

### B-WR-01: `installSteamGame`'s `void window.api.install(...)` swallows a rejection — the install silently no-ops with zero feedback

**File:** `src/frontend/state/InstallGameModal.ts:114`

**Issue:** `void window.api.install({...})` silences `@typescript-eslint/no-floating-promises` but attaches **no handler**. This is the identical anti-pattern the fix report itself called out for `SteamBottleSetup`: *"the poll already had `void` — which silences the lint rule but attaches no handler, so it was still emitting an unhandled rejection every 3s under the sidecar."* The same shape was left on the phase's headline install call, which is reached by **both** entry points: the D-23 quick path (`startSteamQuickInstall` → `installSteamGame`) and the dialog's confirm handler. **Fix:**
```ts
window.api
  .install({ appName, path, runner: 'steam', /* … */ })
  .catch(() =>
    window.api.logError(
      `34.13-08 installSteamGame: install dispatch failed for appName "${appName}"`
    )
  )
```

### B-WR-06: `steamEligibilityWiring.test.ts` B3 — the non-vacuity spec is a tautology, and the real gate measures a different property than its name

**File:** `src/frontend/screens/Library/components/InstallModal/__tests__/steamEligibilityWiring.test.ts:168-180`

**Issue:** Two independent defects, both of the exact class WR-09 was written to eliminate in the sibling file.

1. **The gate cannot detect what it is named for.** B3 is titled *"`<EligibilityLoadingRow` precedes the Steam `<WineSelector` mount"*, but it searches with a start offset:
   ```ts
   const wineSelectorIndex = source.indexOf('<WineSelector', loadingRowIndex)
   expect(wineSelectorIndex).toBeGreaterThan(loadingRowIndex)
   ```
   Searching *from* `loadingRowIndex` makes the result mathematically incapable of being less than it. The assertion collapses to "a `<WineSelector` exists somewhere at or after the loading row" — it says nothing about the **Steam** mount specifically, and would pass just as happily if the loading row were placed above the ThirdParty arm instead of the Steam one. `installModalSource.test.ts`'s `assertSteamWineSelectorHidesSharedPrefix` shows the correct pattern: bound the search to the `<SteamDialog>…</SteamDialog>` arm.

2. **The non-vacuity proof never invokes the gate.** The B3-non-vacuity spec builds a hand-written literal and re-runs plain `indexOf` on it, asserting the opposite inequality. It exercises `String.prototype.indexOf`, not B3's logic, and the specimen is a replica that will drift from the real source. This is verbatim the WR-09 finding, left standing one directory away from where it was fixed.

**Fix:** Extract a throwing helper bounded to the Steam arm, then drive both the real source and a known-bad input **derived from the real source** through it:
```ts
function assertLoadingRowPrecedesSteamWineSelector(source: string): void {
  const start = source.indexOf('<SteamDialog')
  const end = source.indexOf('</SteamDialog>', start)
  if (start === -1 || end === -1 || end <= start) throw new Error('arm not found')
  const arm = source.slice(start, end)
  const rowIdx = arm.indexOf('<EligibilityLoadingRow')
  const wsIdx = arm.indexOf('<WineSelector')          // NO start offset
  if (rowIdx === -1 || wsIdx === -1) throw new Error('a required mount is missing')
  if (rowIdx > wsIdx) throw new Error('the loading row does not precede <WineSelector>')
}
// non-vacuity: real source with the two lines swapped, not a hand-built replica
```

### B-WR-07: `<details onChange={() => setDetailsOpen(detailsOpen)}>` is a no-op on a non-existent event — dead state, newly load-bearing on the Steam path

**File:** `src/frontend/screens/Library/components/InstallModal/WineSelector/index.tsx:189`

**Issue:** Two compounding defects on one line:
- `<details>` fires a **`toggle`** event, not `change`. React's `onChange` will never be invoked here.
- Even if it fired, `setDetailsOpen(detailsOpen)` writes the state back to **its own current value** — React bails out and nothing changes. The correct expression is `setDetailsOpen(!detailsOpen)`.

Consequence: `detailsOpen` is write-only dead state permanently pinned to `!!initiallyOpen`, and React's controlled `open` attribute can fight the browser's own toggling. This is pre-existing upstream code (`19ff38120`), but the Steam mount is a **new** `initiallyOpen` caller (`InstallModal/index.tsx:439`), so this phase is the first to make the "cannot collapse" path a default-open one on the headline surface.

**Fix:**
```tsx
<details
  open={detailsOpen}
  onToggle={(e) => setDetailsOpen((e.currentTarget as HTMLDetailsElement).open)}
>
```
…or drop `detailsOpen` entirely and use uncontrolled `defaultOpen`-style rendering (`<details open={initiallyOpen}>` written once at mount), which is what the current code actually behaves like.
