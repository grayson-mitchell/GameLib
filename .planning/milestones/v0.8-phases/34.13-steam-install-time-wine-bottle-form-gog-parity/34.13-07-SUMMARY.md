# Phase 34.13 Plan 07: Steam Install-Form IPC Seam (D-09/D-14/D-15 Exposure) Summary

**Added the phase's only new IPC surface -- `isSteamBottleEligible` (bottle-eligibility verdict + persisted wine engine/bottle name) and `persistBottleWineVersion` (validating write of the user's chosen engine) -- as one shared backend seam dual-registered on Electron and the Tauri sidecar, both proven live over the real sidecar RPC loop and both reachable from `window.api` on both transports.**

## Accomplishments

- `src/backend/storeManagers/steam/installFormIpc.ts` (new): the single shared handler body for both channels.
  - `getSteamBottleEligibilityVerdict(appName: string): Promise<SteamBottleEligibilityVerdict>` -- rejects a non-numeric `appName` (T-34.13-07-01, `/^\d+$/`) BEFORE constructing a `SteamGame`, fails closed with `{ eligible: false }`; otherwise awaits `new SteamGame(appName).checkBottleEligibility()` then reads the PERSISTED `wineVersion`/`wineCrossoverBottle` directly from `steamBottleConfigStore` (never `getSteamBottleSettings()` -- see key-decisions).
  - `persistInstallFormWineVersion(input: unknown): { status: 'done' | 'error'; error?: string }` -- structurally validates an untrusted payload (non-empty `bin`/`name` strings, `type` within the four-literal union, optional `lib`/`lib32`/`wineserver` string-typed when present), rebuilds a fresh object from known fields only, and calls `bottle.ts`'s `persistBottleWineVersion()`. Accepts `'toolkit'` (GPTK) on purpose.
- `src/common/types/ipc.ts`: two new `AsyncIPCFunctions` entries (`isSteamBottleEligible`, `persistBottleWineVersion`), `SteamBottleEligibilityVerdict` added to the existing `./steam` type import.
- `src/backend/main.ts` (Electron, lines 944-950): both channels registered inside the Phase 17 bottle block, immediately after `steamBottleStatus` and before the Phase 21 client-setup comment, delegating exclusively to the shared seam.
- `src/backend/sidecar/steamAuthFlowRegistration.ts` (Tauri, lines 259-265): both channels registered beside the bottle trio (NOT `installFlowRegistration.ts` -- the file CONTEXT.md wrongly names, per this plan's own `<falsified_briefs>` item 1), same delegation, module doc-comment extended with the two new entries.
- `src/preload/api/steam.ts`: `isSteamBottleEligible` and `persistBottleWineVersion` exported via `makeHandlerInvoker`, reaching `window.api` through the existing `* as Steam` spread.
- `.planning/IPC-PORT-INVENTORY.md`: both channels added to the "Already ported" bucket line (31 -> 33), Totals reconciled 222 -> 224, explanatory note added.

## Exact Channel Names, Preload Exports, and Shared-Seam Signatures (for 34.13-08/09/10)

- Channel `isSteamBottleEligible` -> preload export `window.api.isSteamBottleEligible(appName: string): Promise<SteamBottleEligibilityVerdict>` -> shared seam `getSteamBottleEligibilityVerdict(appName: string): Promise<SteamBottleEligibilityVerdict>` (`installFormIpc.ts`).
- Channel `persistBottleWineVersion` -> preload export `window.api.persistBottleWineVersion(wineVersion: WineInstallation): Promise<{ status: 'done' | 'error'; error?: string }>` -> shared seam `persistInstallFormWineVersion(input: unknown): { status: 'done' | 'error'; error?: string }` (`installFormIpc.ts`).
- `SteamBottleEligibilityVerdict = { eligible: boolean; wineVersion?: WineInstallation; bottleName?: string }` -- `wineVersion` is `undefined` when nothing was ever persisted (the signal 34.13-09 must treat as "fall back to `resolveSteamBottleEngine`"); `bottleName` is always defaulted to `DEFAULT_STEAM_BOTTLE_NAME`, never `undefined`.
- Worst-case latency: `METADATA_FETCH_TIMEOUT_MS` = 15000ms (`state.ts:30`), the bound `checkBottleEligibility()` inherits unchanged.

## Decisions Made

- Bare `jest.mock('../games')` automock (as the plan's `<action>` literally instructs) was NOT used for the unit test -- automocking `games.ts` would require loading its real ~20-module transitive import surface (axios, electron, backend/game_config, `./state`, `./library`, `./bottle`, `./nativeInstallSetting`, `./depot`, `./clientSetup`, `./installLocation`, the bridge cluster, etc.) purely to introspect its shape, duplicating `games.test.ts`'s entire mock harness. Used a lightweight factory mock instead (`default: jest.fn()`, re-implemented per-test in `beforeEach` per `resetMocks: true`), which the plan's own hedge language ("or `jest.mocked(SteamGame).mockImplementation(...)`, whichever the automock actually yields") anticipated. Still supports `expect(SteamGame).toHaveBeenCalledWith(...)` / `.not.toHaveBeenCalled()` directly, satisfying the T-34.13-07-01 discriminator requirement.
- Single-line channel registration format required for the plan's own exact-string verification gates 4/5 (`grep -c "ipcMain.handle('channelName'"` / `"makeHandlerInvoker('channelName')"`), which do not match this file's established multi-line style for other multi-arg handlers. Documented as a deviation (Rule 3, blocking issue) and applied narrowly to only the two new entries -- pre-existing handlers left untouched.
