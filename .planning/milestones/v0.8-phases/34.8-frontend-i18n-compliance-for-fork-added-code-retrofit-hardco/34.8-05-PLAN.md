<objective>
Turn the proven per-file scanner into a whole-scope gate: read the committed scope snapshot,
scan every listed file, reconcile the D-18 allowlist for the two deferred files, and fail loudly
when an exemption goes stale.

Purpose: D-12 requires the gate to block from day one, which is only viable because D-17 defers
`SteamLogin/index.tsx` and `useTauriOAuthLogin.ts` behind an explicit allowlist. D-18 requires
that allowlist to be self-expiring — when the eventual retrofit lands and a file's count drops,
the gate says "stale exemption — remove this entry" rather than quietly outliving its reason.

**Hard constraint for this plan:** the two deferred files are READ ONLY, for counting. Phase
34.4.2 is mid-`/gsd-debug` on that exact Login screen and Phase 34.5's gate fails at the
`useTauriOAuthLogin` render layer; a 34.4.2 gate run was already aborted once because a
concurrent session held uncommitted Login-screen edits.

Output: `scanScope()`, the seeded `meta/i18nGateAllowlist.json`, and the stale-exemption test.
</objective>

  <action>
    Extend `meta/hardcodedStringGate.ts` with the orchestration layer declared in this plan's
    `<interfaces>` block.

    `scanScope()`:
      - Loads the scope snapshot with the read-JSON-safely idiom. Throws `ScopeLoadError` when
        the file is missing, unparseable, or `files` is empty — an empty scope is a gate that
        passes everything, and it must be indistinguishable from a crash, not from a pass.
      - Reads each file from disk with `readFileSync` and hands `(path, text, { glossary })` to
        `scanSource()`. `scanSource` itself stays pure and disk-free; this function owns the I/O.
      - Concatenates violations from files that are NOT in the allowlist into
        `report.violations`.
      - For each `AllowlistEntry`: scans the file, records `{ file, measured, expected }` in
        `report.allowlisted`, keeps its violations OUT of `report.violations`, and pushes the
        path onto `report.staleExemptions` when `measured !== expected`. Note that both
        directions are stale: a count that DROPPED means the retrofit landed and the entry must
        go; a count that ROSE means new hardcoded strings were added to a deferred file behind
        the exemption, which is exactly what the gate exists to stop.
      - Populates `fileExempt` from each `ScanResult.fileExempt` and `totalCandidates` from the
        sum of `violations.length + exempted` — a report with `totalCandidates === 0` means the
        scanner never actually looked and must be treated as a failure, not a pass.
      - Accepts `extraFiles` so plan 06's audit run can widen coverage beyond the committed
        snapshot without editing the snapshot.

    `formatReport(report)` produces the human-readable failure text, following
    `lintTranslations.ts`'s convention of one line per finding, no early return:
      - one line per violation: `<file>:<line>:<column>  <kind>  "<text>"`
      - a trailing summary line with scanned-file count, violation count and candidate count
      - for each stale exemption, a line reading exactly
        `stale exemption — remove this entry: <file> (expected <n>, measured <m>) in meta/i18nGateAllowlist.json`
      - a closing hint naming the two remedies: wrap the literal in `t('gamelib:<key>', '<English default>')`,
        or add the term to `meta/i18nGlossary.json` if it is a brand or platform name

    Add `StaleExemptionError` whose message is built from `formatReport`'s stale-exemption lines,
    so the "stale exemption — remove this entry" phrasing exists in exactly one place.

    Do NOT add a `process.exit()` anywhere and do NOT add a `package.json` script. The gate is a
    jest test (plan 10 flips the assertion) riding the already-blocking `pnpm test:ci`;
    `expect(...)` IS the exit-code mechanism. `meta/lintTranslations.ts` has no `process.exit`
    either — do not copy an exit pattern from it, because it has none.
  </action>
