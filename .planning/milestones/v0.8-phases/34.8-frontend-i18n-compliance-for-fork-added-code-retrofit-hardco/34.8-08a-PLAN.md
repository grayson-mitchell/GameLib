<!-- The call shapes and test idiom already established in this repo. -->

Inside a React component (has or gains `useTranslation` in scope) — the `CrossoverBadge.tsx` form:
  `const { t } = useTranslation('gamelib')` then `t('gamelib:library.someKey', 'English default')`.
  A second hook call may be aliased where the component already has a `t` bound to a different
  namespace, as `GameCard/index.tsx:105` already does with `t2`. **Both files this plan touches
  already call `useTranslation()` for a different namespace** (`ThemeSelector` uses the default
  namespace; `SideloadDialog` uses `'gamepage'`) — add a second, aliased hook call for `gamelib`
  rather than repurposing the existing one, so upstream namespace usage in the same file is
  undisturbed.

Key convention: `gamelib:<feature>.<slug>`, `keySeparator: '.'`, `namespaceSeparator: ':'`. Every
call is TWO-argument `t(key, 'English default')`, never bare `t(key)`. Where the exact same English
string is repeated verbatim at multiple call sites within one file (e.g. SideloadDialog's `'All'`
filter-category label appears three times), reuse ONE `gamelib:` key across all of them rather than
minting near-duplicate keys — that is what keeps the generated catalog small and each string a
single translation unit.

**Test infrastructure constraint (read before writing any test):** this project has NO jsdom /
react-test-renderer installed (`src/frontend/jest.config.js`'s own docstring explains why — adding
one is a new npm dependency, out of scope, excluded from executor auto-fix). Component tests
therefore invoke the function component directly as a plain function and inspect the returned React
element's prop object graph — no DOM, no `render()`. `react-i18next` (and, where needed, `react`'s
`useContext`) is mocked at the module level with `jest.mock(...)`.
`src/frontend/screens/Game/GamePage/components/__tests__/HumbleOriginInfo.test.tsx` is the
reference pattern for this, including the `{{param}}`-interpolating mock `t`.
**Neither `ThemeSelector` nor `SideloadDialog` is safely invokable this way** — both call
`useState`/`useEffect`/`useContext` beyond what a `react-i18next`/`useContext` mock alone covers
(calling a stateful function component directly, with real `react` hooks not mocked, throws
"Invalid hook call"). Per this plan's `<behavior>` blocks below, the required fix is to EXTRACT each
file's retrofitted string-resolution logic into a small, named, exported pure function that takes
`t` as a parameter and returns the resolved value — mirroring how `repairFailure.ts`/`copy.ts`
extract logic to take an injected `TFunction` — and test THAT function directly. The component then
calls the extracted function inline; the component's own hook-heavy render path is not itself
under new test coverage, consistent with how every other stateful component in this codebase is
currently untested.

Namespace choice is NOT enforced by the gate (D-13) — but new fork strings go in `gamelib`, and
plan 09's D-05 no-churn assertion is the mechanical backstop that catches a mis-namespaced call
writing into an upstream catalog.
