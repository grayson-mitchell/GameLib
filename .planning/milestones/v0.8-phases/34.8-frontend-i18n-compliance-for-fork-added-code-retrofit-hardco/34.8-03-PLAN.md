  export interface Violation {
    file: string          // repo-root-relative POSIX path
    line: number          // 1-based
    column: number        // 1-based
    text: string          // the literal's own text, un-quoted
    kind: 'jsx-text' | 'jsx-attribute' | 'object-property' | 'return' | 'variable' | 'argument'
    attribute?: string    // set when kind === 'jsx-attribute'
  }

  export interface ScanResult {
    file: string
    violations: Violation[]
    exempted: number      // count of literals considered and exempted — proves the scanner
                          // actually looked, so a zero-violation file is distinguishable from
                          // an unscanned one
    fileExempt: boolean   // set by plan 04's comment-marker exemption
  }

  export interface GateConfig {
    glossary: string[]
  }

  export function scanSource(
    filePath: string,
    sourceText: string,
    config: GateConfig
  ): ScanResult

  export function loadGlossary(path?: string): string[]

  export const USER_FACING_ATTRIBUTES: readonly string[]
  export const EXCLUDED_ATTRIBUTES: readonly string[]

    Collect candidate literals by walking only these node kinds — this is what makes comment

    Classify each collected literal and DISCARD it (not a candidate at all, so it does not even
    count toward `exempted`) when any of these hold:
      - It is an argument to a `console.*` call. Excluding these is load-bearing: including them
        false-positives against the D-14-protected `repairFailure.ts`, whose design intent is
        that raw backend error text reaches the console and never a rendered dialog.
      - It is the argument of a `throw new Error(...)` / any `NewExpression` on an identifier
        ending in `Error`. Zero user-rendered instances exist in this codebase's measured
        pattern; these are dev/log-facing.
      - It is a JSX attribute whose name is in `EXCLUDED_ATTRIBUTES`.
      - It is an import/export module specifier, an `as const` type position, an object key, an
        enum member name, or a `SyntaxKind.PropertyAccessExpression` name.
      - It contains no letter at all (pure punctuation, digits, whitespace, CSS units).
      - It is a single character, or matches a technical-token shape: a path (`/` or `\` and no
        space), a URL scheme (`http:`, `https:`, `file:`, `steam:`, `tauri:`), a
        `kebab-case`/`snake_case`/`camelCase`-only token with no whitespace, a hex colour, a
        `data-*` value, or a bare file extension.

    Define the two exported attribute lists explicitly, from RESEARCH.md Open Question 1's
    measured answer:
      - `USER_FACING_ATTRIBUTES` = `title`, `aria-label`, `alt`, `placeholder`, `label`
      - `EXCLUDED_ATTRIBUTES` = `className`, `id`, `htmlFor`, `key`, `type`, `role`, `name`,
        `href`, `src`, `to`, `data-*` (match by `data-` prefix), and every `aria-*` OTHER than
        `aria-label` (`aria-describedby`, `aria-controls`, `aria-pressed`, `aria-hidden` are
        references and booleans, not text)
    Put a comment above both lists recording that this is the gate's v1 user-facing scope, that
    it is a deliberate visible decision rather than implicit scanner behaviour, and that
    changing it is a scope change requiring a new decision.

    refuse loudly rather than pass silently. An empty glossary that quietly exempts nothing (or,
    worse, a swallowed parse error) is exactly the failure mode that makes a gate untrustworthy.

    Apply the glossary exemption: a candidate literal whose `text.trim()` is an exact,
    case-sensitive member of `config.glossary` is exempt — increment `ScanResult.exempted`, emit

    D-14 exemptions will hook in, so plan 04 has an unambiguous insertion point.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| fork source text → scanner AST | Untrusted-shaped input (arbitrary TypeScript) parsed by a compiler API |
| glossary file → exemption decision | Any exemption here is a permanent hole in the gate |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-34.8-06 | Tampering | glossary exemption widened into substring matching | mitigate | Exact case-sensitive whole-string match only; the `near-miss` test asserts `'Steam client not found'` is still a violation while `'Steam'` is not, so a widening change goes red |
| T-34.8-07 | Repudiation | a scanned file reporting zero violations because it was never really scanned | mitigate | `ScanResult.exempted` counts literals actually considered; plan 05 asserts a nonzero total across the scope so an empty scan is distinguishable from a clean one |
| T-34.8-08 | Information Disclosure | scanner reading files outside the repo, or emitting source into logs | mitigate | `scanSource` is pure over `(filePath, sourceText)` with `useInMemoryFileSystem: true`; the only disk read in this file is `loadGlossary`'s fixed path; violation records carry only the literal's own text, never surrounding code |
| T-34.8-SC | Tampering | npm/pip/cargo installs | accept | Zero new packages — `ts-morph` 17.0.1 is a pre-existing devDependency (RESEARCH.md § Package Legitimacy Audit). If an install becomes necessary, STOP and raise a blocking-human legitimacy checkpoint. |
</threat_model>
