# Phase 34.15 Plan 07: Consume the Mac Signal in the Install Form Summary

**Widened the install form's ONE `resolveDepotAvailability` call with the mac seed/probe pair, un-froze the platform default so it re-derives (with a user-choice guard) once the signal resolves, and gated SteamDialog's entire header glyph row -- including the previously-unconditional Windows glyph -- on that same resolution moment; closed the last standing project-wide TypeScript error in the process.**

## Accomplishments
- `InstallModal/index.tsx`'s sole `resolveDepotAvailability` call now supplies `seedHasMacDepot`/`probeHasMacDepot` alongside the existing Windows pair and destructures `macDepotOffered`, closing the TS2345 error that stood since Plan 04.
- `getDefaultplatform` is no longer a `useState` initializer frozen at open -- it takes the resolved `macDepotOffered` value, and a `useEffect` (guarded by `userChosePlatformRef`, set inside the single `onChange` handler) re-derives the default once `depotSignalResolved` flips true. This fixes the observed Terraria (105600) symptom: a game shipping both Windows and native Mac builds defaulted to Windows and never corrected once the probe resolved.
- `SteamDialog`'s header glyph row is now gated on a new `depotSignalResolved` prop, computed by the parent and threaded down alongside `eligibilityPending`. While unresolved, the row renders NOTHING -- including the Windows glyph, which previously rendered unconditionally with no signal read at all.
- `steamEligibilityWiring.test.ts` Group E's E2 was widened from 5 properties/400 chars to all 7/600 chars, with an E2-RED proof showing it would have stayed green if the mac seed pair had been silently dropped (the exact reconciliation gap 34.15-04's own summary flagged). New E6 pins `depotSignalResolved={depotSignalResolved}` reaching the `<SteamDialog` mount. New Group F pins that 34.14's `readonlyPlatformValue('pending')` D-15 pin was not reopened.
- `steamDialogSource.test.ts` gained a D-13 describe block: the gate is present (whitespace-normalized), RED-proven against a known-bad derived from the real source, and a negative gate bans `availablePlatforms.filter` inside this dialog.
- `npx tsc --noEmit -p tsconfig.json` now exits with **ZERO** errors project-wide (confirmed after every task and again at the end).

## Decisions Made
- Followed D-12/D-13/D-14/D-15 exactly as CONTEXT.md specifies: one widened resolver call, a dialog-local suppression that never filters the shared `availablePlatforms` array, a re-deriving (not frozen) default guarded against overwriting a live user choice, and 34.14's pending-row pin left untouched.
- **Plan-vs-prettier conflict, resolved in favor of the project's formatting convention (CLAUDE.md-equivalent house rule):** the plan's Task 2 acceptance criteria specify a single-line grep match `"depotSignalResolved && availablePlatforms.map"` against `SteamDialog/index.tsx`. This project's prettier config wraps a JSX `condition &&` onto its own line ahead of a multi-line `.map()` return -- confirmed as the existing house pattern at `WineSelector/index.tsx:255` and `DownloadDialog/GameLanguageSelector.tsx:47`, and `prettier --write` reformatted my initial single-line version to match. I kept the prettier-formatted (two-line) version rather than fighting the formatter, and wrote Task 3's source gate against a whitespace-normalized copy of the source -- the exact `flatten()`-style technique Group E's own header comment in `steamEligibilityWiring.test.ts` already documents for this identical prettier behavior on `selectSteamPlatformOptions(...)`. The literal `grep -c` command in the plan's acceptance criteria, run against the raw (un-normalized) file, returns `0` for this reason; the underlying property -- the row IS gated on `depotSignalResolved` -- is proven and RED-tested. This is not a deviation from the plan's intent, only from one acceptance-criteria command's line-format assumption.
- **Plan Task 2 acceptance-criteria inconsistency, not applied:** the plan's Task 2 acceptance criteria also lists `grep -c "<EligibilityLoadingRow" SteamDialog/index.tsx` expecting `1`. Verified against `git show HEAD` that this file has ZERO occurrences of that token both before and after this plan (the mount lives in `InstallModal/index.tsx`, confirmed via `steamEligibilityWiring.test.ts`'s own B1 gate, which reads `InstallModal/index.tsx`'s source, not `SteamDialog/index.tsx`'s). Adding a mount here would violate the plan's own explicit instruction one line above ("Do NOT add or move any `<EligibilityLoadingRow` mount") and would reopen the exact D-15 pin this plan is required to leave alone. Treated as a plan-authoring inconsistency (likely a copy-paste of the D-15 property intended for `InstallModal/index.tsx`) and left `SteamDialog/index.tsx` at its correct, pre-existing 0 occurrences.
