In `src/common/types/ipc.ts`, add two exported type aliases near the `FrontendMessages` interface:

  export type SteamSyncStatus = 'idle' | 'syncing' | 'failed'
  export type SteamSyncFailureReason = 'client-not-ready' | 'owned-apps-failed' | 'sync-failed'

Reason vocabulary rationale (Claude's Discretion under D-07, comment it): three codes, one per
distinguishable backend failure, chosen so the inline notice can say something more useful than
"failed" — `client-not-ready` means the Steam session could not be re-established,
`owned-apps-failed` means the CM was reached but the owned-app list did not arrive (the cached
library is being served), `sync-failed` means the owned-app list arrived but hydration threw.
Both runtimes represent plain string unions identically, satisfying D-07's representability
constraint.

Add to `FrontendMessages`, immediately after `steamMetadataSyncing`, with a doc comment stating it
is emitted on EVERY exit path of `SteamLibraryManager.refresh()` (all four — see Plan 05) and that
`reason` is present only when `status === 'failed'`:

  steamSyncStatus: (payload: { status: SteamSyncStatus; reason?: SteamSyncFailureReason }) => void

In `src/preload/api/steam.ts`, add, mirroring `handleSteamMetadataSyncing`'s shape exactly:

  export const handleSteamSyncStatus = frontendListenerSlot('steamSyncStatus')

Comment it with the reason this entry is mandatory: for a backend->renderer push, the sidecar's
`electronStub.pushFrontendMessage` forwarder is channel-agnostic, so the EMIT side needs no
allowlist — the silent-failure risk is entirely here. Without this export (and `GlobalState`'s
subscription in Task 2) the backend emits fine, Rust forwards fine, and the renderer simply has
nobody listening: no compile error, no runtime error, nothing arrives. Ledgered as
`sidecar-send-channels-fail-silently`.
