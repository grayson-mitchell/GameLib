# Phase 34.15 Plan 05: Wire bulk platform capture + four-exit-path sync status into refresh() Summary

**`SteamLibraryManager.refresh()` now runs the D-01..D-04 bulk PICS platform capture inline and awaited before hydration, and reports itself on `steamSyncStatus` on all four exit paths -- including the previously undocumented, uncaught Steps 2-4 hydration span that was the actual root cause of the silent mount-time sync failure.**

## Performance

- **Duration:** ~50 min
- **Tasks:** 3 completed
- **Files modified:** 2 (`library.ts`, `library.test.ts`)

## Accomplishments
- `refresh()` gained a new Step 1.5: `await captureOwnedAppPlatforms(client as unknown as PlatformCapturePicsClient, appIds)`, placed between the owned-apps fetch and the ACF install-state hydration loop, with the D-03 (why here / why fail-soft) and D-05 (the non-consequence) rationale written into the code as a load-bearing comment block, naming all four durable paths that keep a platform signal unresolved for a visible game.
- `refresh()` now emits `sendFrontendMessage('steamSyncStatus', ...)` at five points: entry (`syncing`), the client-not-ready early return (`failed`/`client-not-ready`), the `getUserOwnedApps` catch — after the cached-library push loop (`failed`/`owned-apps-failed`), the newly try/catch-wrapped Steps 2-4 hydration span (`failed`/`sync-failed`, then re-throws), and the success return (`idle`). No `finally` is used anywhere, so a failed path can never be silently clobbered back to `idle`.
- The previously-uncaught ~140-line Steps 2-4 span (`buildInstalledMap`/`buildBottleInstalledMap`/`buildBridgeInstalledMap`/`buildIncompleteInstallSet`/the per-game hydration loop/`steamLibraryStore.set`) is now wrapped in `try { ... } catch (err) { logError(...); sendFrontendMessage('steamSyncStatus', {status:'failed', reason:'sync-failed'}); throw err }` -- this is the fourth, previously-undocumented exit path (`library.ts:705-847` at HEAD) reachable from `init()`'s unscoped `runOnceWhenOnline(() => this.refresh())`, which `online_monitor.ts` discards with no `.catch` anywhere in the chain. A hydration-loop exception there is no longer a silent unhandled rejection with zero UI signal.
- Six new forcing tests pin each exit path's exact ordered emit sequence (via a `steamSyncEmits()` helper that filters `sendFrontendMessage`'s calls to the `steamSyncStatus` channel) plus the D-03 fail-soft guarantee, including a negative gate proving path 4 never emits `idle` and a proven ordering assertion that path 2's cached-game pushes precede its failure emit.
- Full `src/backend/storeManagers/steam` suite: 30 suites, 1120 tests, all green. `npx tsc --noEmit` shows zero new errors -- only the pre-existing, out-of-scope `InstallModal/index.tsx:201` error (Plan 07's declared scope) remains.

## Issues Encountered
- Wrapping Steps 2-4 in try/catch required reindenting ~140 lines by one level. To satisfy the plan's own `git diff | grep -c "^-.*return {"` == `0` acceptance gate (no exit path's return shape changed), the try/catch boundary was placed to end immediately after `steamSyncStore.set('syncedAt', ...)` — the success `sendFrontendMessage('steamSyncStatus', {status:'idle'})` emit and the final, UNCHANGED `return { stdout: ..., stderr: '' }` statement sit after (outside) the try/catch, at their original indentation. This means the return line itself has zero diff (lines were only added around it), while Steps 2-4's body lines show as reindented — exactly matching the plan's literal scoping instruction ("wrap the span from the Step 2 banner comment through `steamSyncStore.set('syncedAt', ...)`").
- The D-03 "capture rejects" test required determining actual behavior rather than assuming it: because the bulk capture call sits BEFORE the Steps 2-4 try/catch (per the plan's own scoping), a hypothetical contract violation (a reject, which `captureOwnedAppPlatforms` is unit-tested in Plan 01 to never do) propagates un-emitted rather than surfacing as exit path 4. The plan anticipated this ambiguity explicitly ("If the reject propagates as path 4, assert that") — the test pins the actual observed behavior (`steamSyncEmits()` == `[{status:'syncing'}]` only, rejection propagates) with the reasoning documented inline in both the test and this summary.
