<task type="checkpoint:decision" gate="blocking-human">
  <name>Task 1: Confirm the one-time seed writes to persisted user data</name>
  <decision>
This is the only task in phase 48 that derives a value and persists it into a user's existing
`config.json`. Everything else in the phase is additive, read-only, or writes only what the user
just clicked.

**What will happen on first launch of the upgraded build**, for a profile with no `focusRow` key:

| stored `libraryTopSection` | seeded `focusRow` |
|---|---|
| `recently_played` | `{ kind: 'view', value: 'recentlyPlayed' }` |
| `recently_played_installed` | `{ kind: 'view', value: 'recentlyPlayed' }` **plus** installed-only semantics — see the open question below |
| `favourites` | `{ kind: 'view', value: 'favourites' }` |
| `disabled`, absent, or any unrecognised value | `null` (off) |

**Why this is a gate and not just a task.** The seed is read **once** and then the key is present
forever; there is no "undo the migration" path short of the user hand-editing `config.json`. It is
`one-way` in the reversibility sense. It is also low-blast-radius — it writes one key, destroys
nothing, and the worst outcome is a focus row the user did not ask for, which they can clear in one
click — so the gate is a confirmation, not a risk review.

**The open question.** `recently_played_installed` is specified as "a Recently-played focus row
**with installed-only semantics**". The new `{ kind, value }` shape has no slot for a modifier: it
is one kind and one value. One of the three options below has to be picked, and the SPEC does not
pick it.
  </decision>
  <context>
Three of the four legacy values map cleanly and are not in question: `recently_played` →
`{ kind: 'view', value: 'recentlyPlayed' }`, `favourites` → `{ kind: 'view', value: 'favourites' }`,
and `disabled` (or an absent/unrecognised value) → `null`.

Only `recently_played_installed` is ambiguous, because it is the one legacy value carrying *two*
facts — a pick and a qualifier — into a shape that holds one. Whatever is chosen, it affects exactly
one row of Task 2's migration table and its matching unit test; nothing else in the phase moves.

How many real profiles this touches is unknown and not measurable from here: `libraryTopSection`
defaults to `'disabled'`, so every affected profile is one where the user deliberately opened
Settings and chose this specific option.
  </context>
  <options>
    <option id="recency">
      <name>Map to `{ kind: 'view', value: 'recentlyPlayed' }` — keep recency, drop installed-only</name>
      <pros>The pick's defining character is recency, and that survives. Keeps the migration table total and the persisted shape clean. Installed-only content stays reachable through the grid's own `Installed` view, which this phase does not touch. Recommended.</pros>
      <cons>A user who specifically wanted installed-only sees uninstalled games in the row after upgrade. One click in the panel is not a fix for that, since the new section has no installed-only variant of the recency pick.</cons>
    </option>
    <option id="installed">
      <name>Map to `{ kind: 'view', value: 'installed' }` — keep installed-only, drop recency</name>
      <pros>Honours the qualifier the user explicitly opted into. Nothing in the row is a game they cannot launch.</pros>
      <cons>Loses recency ordering, which is the half of the old option's name that came first. The row becomes alphabetical, so it stops looking like a "recently played" shelf at all — arguably a bigger surprise than option `recency`'s.</cons>
    </option>
