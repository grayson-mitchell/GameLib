### The ruling

**R6 is reduced to a pure removal. The 20-entry storage bound is NOT introduced.** R6's Target keeps
sentence 1 ("The Settings control and its barrel export are removed") and sentence 3 ("Display count
is whatever fits the strip width"), and **drops** sentence 2 ("`recent_games.ts` bounds the stored
list by a fixed constant of 20").

The operator's reasoning, recorded: a phase whose own ROADMAP entry says *"this is mostly a move,
not a build"* is the wrong place to introduce an irreversible eviction policy on persisted play
history, and the only argument for the cap was the misreading of the code above. A bound on
`games.recent`, if ever wanted, is a cleaner standalone change judged on its own merits.

Consequence: R6 no longer writes persisted user data, so it is **not** a reversibility candidate and
earns **no** `checkpoint:decision`. R7's one-time migration (plan 48-05) still does, and still has
one.

**Two upstream documents are superseded on this point and must not be followed:**
`48-PATTERNS.md`'s `### recent_games.ts — fixed-constant bound` section (around line 238) specifies
exactly the `RECENT_GAMES_LIMIT = 20` write-path slice this ruling declines. It was a faithful
reading of the locked SPEC at the time it was written; it is now wrong. Likewise the ROADMAP's
phase-48 entry repeats the SPEC's `recent_games.ts:15` path and its "bounds what is stored" framing.
Neither is edited by this plan — the SPEC is locked and PATTERNS is a point-in-time map — so this
block is the authority. If you find yourself about to add a constant to `recent_games.ts`, you are
following a superseded document.

<negative_grep_method>
**Every "`grep -c X` is 0" criterion in this plan runs over COMMENT-STRIPPED source.** Where a
criterion below writes `codeonly <path>`, it means this, and never a bare `grep` over raw text:

`codeonly() { grep -vE '^[[:space:]]*(//|\*|/\*|<!--)' "$1"; }`

**Why this is load-bearing, not hygiene.** Several `<action>` blocks in this plan instruct the
executor to write a comment *explaining* why a token must not appear. An unfiltered `grep -c` counts
that explanation, so the gate goes red on correct code — or, in the other direction, a token present
only in prose satisfies a check that was supposed to measure code. This repo has measured both
directions: `SteamLogin/index.scss:86` carries a `//` comment whose text is literally a grep command,
and unstripped it made `cssTokenSweep` believe a dead token was declared, hiding five real undefined
references behind the very prose that documented them.

**Stated blind spot, same as `cssTokenSweep.test.ts`'s own:** this strips whole comment lines only.
A trailing `// note` appended to a code line survives, so a token inside one is still counted. That
is deliberate — a naive `s|//.*$||` pass truncates a code line containing `url(https://…)`, which is
a regression class this repo has already paid for. If a trailing comment ever bites, layer
`stripTrailingLineComment` from `backend/testUtils/stripSourceComments` on top; do not hand-roll a
stripper.
</negative_grep_method>
