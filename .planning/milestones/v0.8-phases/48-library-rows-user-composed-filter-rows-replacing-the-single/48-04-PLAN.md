Purpose: this is the one part of SPEC R3 the tracer deliberately left out, and it is the part with no
analog in this codebase at all. Nothing in GameLib scrolls games sideways, nothing is a circular

unreachable without a pointer, and D-06 records that `helpers/gamepad.ts` already navigates

a row holds more than fits.

cards, dim at the ends with the existing convention, and a horizontal scroll-into-view handler for
gamepad focus.

  <behavior>
    `pageScrollDelta(m: { clientWidth: number; scrollWidth: number; scrollLeft: number }, cardPitch: number): number`
    - 3 fully-visible cards at the current width → a forward delta of `3 * cardPitch`, not `cardPitch`
    - a width that fits 0 whole cards (narrower than one card) → a delta of exactly `cardPitch`, never 0, so a control can never be a no-op
    - `cardPitch <= 0` or a non-finite measurement → `cardPitch > 0 ? cardPitch : 0`, and never `NaN`
    - the returned delta is positive; the caller negates it for the back direction

    `canScrollForward(m)` / `canScrollBack(m)`
    - content narrower than the viewport (`scrollWidth <= clientWidth`) → both false, which is what
      makes "no affordance at all" expressible as a single condition
    - `scrollLeft === 0` with overflow → back false, forward true
    - `scrollLeft` at `scrollWidth - clientWidth` → back true, forward false
    - a sub-pixel residue (`scrollWidth - clientWidth - scrollLeft === 0.4`) → forward false, so a
      fractional layout cannot leave a permanently-enabled control that scrolls nothing

    `scrollFocusedCardIntoViewHorizontally(ev: FocusEvent)`
    - resolves the track by walking up from `ev.target` to the nearest `.focusRowTrack` **at call
      time**, and returns silently when there is none — the listener must never throw on a focus
      event from elsewhere
    - a focused card whose rect's `left` is left of the track rect's `left` scrolls the track so the
      card's left edge is flush with the track's, not to an `offsetParent`-derived offset
    - a focused card whose rect's `right` exceeds the track rect's `right` scrolls by exactly the
      overhang
    - a fully-visible card produces no `scrollTo` call at all
    - every destination is expressed as `track.scrollLeft + (card rect edge − track rect edge)`,
      which reduces to the card's offset in the track's own scroll space regardless of ancestry
  </behavior>
  <action>
Create `focusRowOverflow.ts` exporting `pageScrollDelta`, `canScrollForward`, `canScrollBack` and
`scrollFocusedCardIntoViewHorizontally`.

`pageScrollDelta` computes whole-card paging: `Math.max(1, Math.floor(clientWidth / cardPitch)) * cardPitch`.
Paging by a whole page rather than one card is UI-SPEC E6's rule and CONTEXT D-05's convention — a
control that barely moves content at a wide window size is the failure mode it names. The
`Math.max(1, …)` floor is what stops a window narrower than one card producing a zero-delta control
that looks live and does nothing.

`cardPitch` is passed in by the caller, derived from the track's own first child rather than
hardcoded: `track.firstElementChild` is `.gameList`, whose first child is a card wrapper, so
`wrapper.getBoundingClientRect().width + gap`. Read the gap from the computed style of `.gameList`
rather than restating `1.5rem` in TypeScript — a second copy of that value in a second language is
exactly the drift this repo keeps paying for. Fall back to `156` for the width and `24` for the gap
only when the measurement is unavailable (an empty track, which cannot happen because the strip
returns `null` at zero games, but the fallback keeps the function total).

**Do not reuse `FOCUS_ROW_MAX_CARDS` here.** That constant is R3's *display* cap — at most 20 cards
in the strip. This module's arithmetic is about pixels and viewport width and has nothing to do with
it. Keeping the two separate is deliberate: the phase has two different 20-ish numbers and
conflating them is the easiest wrong turn available.

`scrollFocusedCardIntoViewHorizontally` is the horizontal analogue of
`GamesList/index.tsx:47-79`, and is net-new code rather than a parameterisation of it. Resolve the
container by `(ev.target as HTMLElement).closest('.focusRowTrack')` at call time — a module-scope
lookup would run before the track exists, which is the exact mistake the vertical version's own
comment documents. Measure the focused element's `getBoundingClientRect()` against the **track's**
rect, never against `offsetParent.offsetLeft`: the vertical version warns in-source that keeping
that arithmetic while swapping the container turns a silent no-op into a silent wrong-offset scroll,
which is worse because it looks like it works. Scroll with `behavior: 'smooth'` to match
`.focusRowTrack`'s `scroll-behavior`.

Design every exported function to take plain measurement objects or a real `FocusEvent`, not a
`RefObject`, so the arithmetic is unit-testable in a `testEnvironment: 'node'` project with hand-built
rect stubs. Write `__tests__/focusRowOverflow.test.ts` first, watch it fail, then implement.
