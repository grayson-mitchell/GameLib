## Fix decision (stated before measuring; WR-02's first route)

**Adopted (F2): an explicit keyboard-mode body class.** `body.keyboardNav` is set by a trusted Tab
keydown and cleared by a real pointer move or a pointer press. The stale-focus suppression is scoped
`body:not(.controllerLayout):not(.keyboardNav)`. While keyboard mode is on, a hovered card that does
not hold focus returns to rest, the same treatment `body.controllerLayout` already gives a parked
cursor. Exactly one tile then rings in every input mode.

**Not adopted (F1): `:not(:has(:focus-visible))` on the suppression selectors.** Two reasons, both
recorded as a measured counterfactual in Task 2:

1. A `:focus-visible`-only rule cannot keep exactly one ring. With the pointer resting on card A
   while Tab focuses card B, A's hover ring and B's focus ring both show. After keyboard focus on B,
   a real pointer move onto C leaves B ringing until focus moves.
2. `themes.scss` (about lines 70-82) and 48-UI-SPEC.md already record that Tauri gamepad focus is a
   bare `.focus()` after untrusted synthetic key events, so whether it matches `:focus-visible` is
   an engine heuristic. A stale gamepad ring would then depend on the engine.

**Reversibility:** reversible. The change is one body class, two listeners and four selectors, all
behind tests, and it can be reverted by commit.

**Why same-coordinate pointer moves are ignored.** WebKit and Chromium dispatch a synthetic
`mousemove` to update hover after content scrolls under a stationary pointer. A Tab that scrolls the
page under a resting pointer must not end keyboard mode. 48-15 B11 saw the page scroll during the
Tab run, so the live gate will exercise this.

**Why untrusted keydowns are ignored.** `src/preload/api/tauriGamepadInput.ts` dispatches untrusted
synthetic `KeyboardEvent`s for gamepad navigation. Controller mode owns that path through
`body.controllerLayout`.
