</byte_identity_method>

<negative_grep_method>
**Every "`grep -c X` is 0" criterion in this plan runs over COMMENT-STRIPPED source.** Where a
criterion below writes `codeonly <path>`, it means this, and never a bare `grep` over raw text:

`codeonly() { grep -vE '^[[:space:]]*(//|\*|/\*|<!--)' "$1"; }`

**Why this is load-bearing, not hygiene.** Several `<action>` blocks in this plan instruct the
executor to write a comment *explaining* why a token must not appear. An unfiltered `grep -c` counts
that explanation, so the gate goes red on correct code — or, in the other direction, a token present
only in prose satisfies a check that was supposed to measure code. This repo has measured both
directions: `SteamLogin/index.scss:86` carries a `//` comment whose text is literally a grep command,
and unstripped it made `cssTokenSweep` believe a dead token was declared, hiding five real undefined
references behind the very prose that documented them.

**Stated blind spot, same as `cssTokenSweep.test.ts`'s own:** this strips whole comment lines only.
A trailing `// note` appended to a code line survives, so a token inside one is still counted. That
is deliberate — a naive `s|//.*$||` pass truncates a code line containing `url(https://…)`, which is
a regression class this repo has already paid for. If a trailing comment ever bites, layer
`stripTrailingLineComment` from `backend/testUtils/stripSourceComments` on top; do not hand-roll a
stripper.
</negative_grep_method>
