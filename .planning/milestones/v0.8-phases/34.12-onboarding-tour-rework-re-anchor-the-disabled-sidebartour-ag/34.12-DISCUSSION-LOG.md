## Tour entry point

### Q1 — Where should the launcher that starts the shell tour live?

| Option | Description | Selected |
|--------|-------------|----------|
| SettingsPanel row (Recommended) | Labelled row alongside Documentation / Ko-fi / Console Mode. Reads as a destination rather than a hidden icon, and keeps a single named entry point — `tourDisabled.test.ts` calls out the old "second, easy-to-miss" launcher on `HeroicVersion` as what made the tour hard to reason about. Cost: only reachable once the user opens Settings. | ✓ |
| Restore on HeroicVersion | Closest to retired behaviour; step 12's own copy says "access tours from here". Same reachability (version slot hidden unless Settings active), but an icon button rather than a labelled row. | |
| Navbar, beside DownloadsRing | Always visible on every tab. Cuts against UI-SPEC OQ6, which omitted a search icon and an avatar from that slot deliberately. | |
| No launcher — first run only | Auto-start once, never manually re-runnable. No chrome cost; unverifiable by hand without resetting state. | |

**User's choice:** SettingsPanel row → **D-01**

**Notes:** This choice is load-bearing for the rest of the phase — because the launcher sits
in the Settings tier-2 panel, that panel is open when the tour starts, which is what makes
D-03 (never switch tabs) viable.

### Q2 — Should the shell tour auto-start on first launch?

| Option | Description | Selected |
|--------|-------------|----------|
| Manual only (Recommended) | Launcher row is the only way in. Matches `LibraryTour`, adds no state. Cost: few new users will find it. | ✓ |
| Auto-start once, if never completed | Reuses `hasTourCompleted` / `completedTours`. Sharp edge: no existing install has completed this tour, so it would fire for every current user on upgrade, not just new ones. | |
| Auto-start only on a clean profile | Fires when there is no prior GameLib state at all. More faithful to intent, but depends on a signal outside `TourContext` that research would have to establish. | |

**User's choice:** Manual only → **D-02**

**Notes:** Auto-start preserved as a deferred idea, gated on finding a real first-run signal.

## Cross-tier steps

### Q1 — How should the tour reach the six steps inside the Settings tier-2 panel?

| Option | Description | Selected |
|--------|-------------|----------|
| Never switch tabs (Recommended) | Order steps against what is already on screen: tier-1 tabs always visible, Settings panel open because the launcher is there. All twelve stay anchorable; tour never touches navigation. | ✓ |
| Tour drives the shell | Auto-switch tabs to also show `GamesPanel` / `StoresPanel` contents. Richer, but the tour mutates navigation and must restore the user's tab on exit. | |
| Tier-1 surfaces only | Drop the six tier-2 steps for one summary step. Shortest, but drops steps for convenience rather than because their surface is gone. | |

**User's choice:** Never switch tabs → **D-03**

**Notes:** Raised during scouting and confirmed here — the roadmap assumed these steps would
be hard to reach, but D-01 makes the Settings panel open by construction, so the difficulty
dissolves.

### Q2 — A user can click a highlighted tab and pull the panel out from under later steps. How should the tour handle that?

| Option | Description | Selected |
|--------|-------------|----------|
| Lock interaction (Recommended) | `disableInteraction: true` for this tour — highlighted elements shown, not clickable. Makes "never switch tabs" structurally true. Cost: user can't try a control mid-tour; differs from `LibraryTour`'s defaults. | ✓ |
| Leave clickable, exit if the tab changes | Keep controls live, watch the active tab, end the tour cleanly if it stops being Settings. Costs a state subscription; tour can end abruptly. | |
| Leave clickable, accept the gap | Change nothing. Matches `LibraryTour`, but leaves intro.js coping with selectors that resolve to nothing — the exact breakage D-13 disabled this tour to avoid. | |

**User's choice:** Lock interaction → **D-04**

**Notes:** Applied per-tour through `Tour`'s existing `options` passthrough; `Tour.tsx`'s
shared defaults stay untouched because `LibraryTour` uses the same component.

## Step list shape

### Q1 — What should the rebuilt step set contain?

| Option | Description | Selected |
|--------|-------------|----------|
| All twelve, re-anchored (Recommended) | Every step keeps its position and key; only the selector changes, plus rewritten copy where it names the sidebar. Matches the roadmap's "re-anchored or dropped with a reason" bar exactly. | ✓ |
| Twelve plus a tier-2 step | Same twelve plus a new step for the tier-2 column — the biggest thing 34.10 changed. Alternative: fold that into the rewritten welcome step. | |
| Consolidate to a shorter tour | Collapse the four Settings rows into one or two steps. Retires steps for length rather than surface change, and drops i18n keys 34.8 already covers. | |

**User's choice:** All twelve, re-anchored → **D-05**

**Notes:** The tier-2 explanation is folded into the rewritten welcome step rather than
spending a thirteenth step on it.

### Q2 — How should the `tour.sidebar.*` i18n keys be handled, given several steps' copy is being rewritten?

| Option | Description | Selected |
|--------|-------------|----------|
| New keys where copy changed (Recommended) | Mint `tour.nav.*` for steps whose text actually changes; carry the rest across unchanged. A new key cannot inherit a stale translation. | ✓ |
| Rename every key to `tour.nav.*` | One consistent namespace, no mixed prefixes. Costs existing translations for steps whose English didn't change. | |
| Keep the existing keys | Zero catalog churn. But rewritten steps keep serving old translated text in every non-English locale, invisibly on an English machine. | |

**User's choice:** New keys where copy changed → **D-07**

**Notes:** The `t(key, default)` fallback-is-inert behaviour was surfaced during the question
rather than discovered later; it is recorded in CONTEXT.md D-07 as the rationale so the
planner does not "simplify" it back to editing defaults.

## Shell tour vs LibraryTour

### Q1 — How should the rebuilt shell tour relate to the existing LibraryTour?

| Option | Description | Selected |
|--------|-------------|----------|
| Keep them separate (Recommended) | Two tours, two launchers. Each anchored to surfaces on screen when its own launcher is reachable, so neither drives navigation. | ✓ |
| Chain shell → library | Better first-run narrative, but the handoff must switch to the Games tab — reintroduces the navigation-driving D-03 rejected. | |
| Merge into one app tour | One launcher, ~20 steps. Simplest mental model; requires tab switching and is long enough that most users will skip it. | |

**User's choice:** Keep them separate → **D-08**

### Q2 — What should happen to LibraryTour's two dead steps?

| Option | Description | Selected |
|--------|-------------|----------|
| Re-anchor to the filter panel (Recommended) | Point `library-categories` / `library-filters` at 34.11's replacements in the tier-2 `GamesPanel`. That panel is on screen whenever the library tour's button is reachable. Same job as the IN-01 cleanup already folded in. | ✓ |
| Drop both steps | Retire with a recorded reason. Honest and cheap; leaves the library tour silent about filtering. | |
| Leave LibraryTour untouched | Smallest diff, but knowingly leaves two selectors resolving to nothing in a tour users can run today. | |

**User's choice:** Re-anchor to the filter panel → **D-09**

**Notes:** Discovered during scouting, not recorded in the roadmap: `LibraryTour` is live
(`Library/index.tsx:1084`) and already ships two broken steps. Also found:
`data-tour="library-header"` sits on two elements and is referenced by no step at all.
