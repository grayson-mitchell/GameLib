# Phase 34.12 Plan 05: SettingsPanel tour anchors and the D-01 launcher row Summary

Landed the last four of D-05's twelve NavShellTour anchors on SettingsPanel rows (Wine Manager,
Accessibility, Documentation, Ko-fi), added D-01's "App Tour" launcher row that makes the rebuilt
shell tour reachable for the first time since phase 34.10, and hardened the persisted tour-state
read that the launcher's click handler newly makes reachable from user input.

## What was built

**Task 1 — Four D-05 anchors on labelled SettingsPanel rows.** Added `data-tour="nav-wine"` /
`"nav-accessibility"` / `"nav-docs"` / `"nav-community"` to the Wine Manager, Accessibility,
Documentation and Ko-fi `NavItem` rows respectively, matched by their existing `label`, not by
JSX position. The Wine Manager row's `{!isWin && ...}` guard was left untouched -- it already
agrees with the tour's own `!isWin`-gated Wine step (from plan 04). Five new assertions were
added to `SettingsPanel.test.tsx`: one per anchor (four) plus a win32 negative proving no element
carries `data-tour="nav-wine"` on that platform, which makes the row-guard/step-guard agreement
checkable rather than merely asserted in prose.

**Task 2 — The D-01 launcher row.** Inserted one new `NavItem` button row, `App Tour`
(`icon={faCircleQuestion}`, `data-tour="nav-launcher"`), positioned immediately after Ko-fi and
strictly before `<QuitButton />`. Its `onClick` ports `TourButton.tsx`'s `handleStartTour` logic
inline: if `hasTourCompleted(NAV_TOUR_ID)` then `resetTour(NAV_TOUR_ID)`, then always
`startTour(NAV_TOUR_ID)` -- the reset branch is what makes a previously-completed tour re-runnable
(`startTour` alone does not clear `completedTours`). `TourButton` itself was not imported or
modified; it keeps serving `LibraryTour` (D-08) untouched. `tour.nav.launcher` was minted in
`public/locales/en/translation.json` with the value `"App Tour"`. Three existing test contracts
were updated deliberately: `SettingsPanel.test.tsx`'s labels array (ten -> twelve, "eleven
entries" -> "twelve entries" in the test name) and its two new launcher-behaviour `it` blocks;
`destinationCoverage.test.tsx`'s exact 22-entry `toEqual` union (now 23, `App Tour` appended after
`Ko-fi`); the QuitButton-is-last-child assertion needed no code change and was re-run to confirm
it still passes.

**Task 3 — Defensive read of `heroic-tour-state`.** Task 2 made `hasTourCompleted()` reachable
from a user click for the first time in this shell. The prior `TourProvider` initializer
`JSON.parse`d the persisted `localStorage['heroic-tour-state']` value with no try/catch inside a
`useState` lazy initializer, and `hasTourCompleted` called `.includes()` on `completedTours`
unconditionally -- so a malformed value could take down the whole app tree, and a
well-formed-JSON-but-wrong-shape value (e.g. `{"completedTours": null}`) would throw at click
time. Extracted a new exported pure function, `readPersistedTourState(raw: string | null):
TourState`, that wraps the parse in try/catch (falling back to `defaultState`) and normalises
`activeTour` / `tourProgress` / `completedTours` shape at that same read boundary, matching this
project's established preference for self-healing at the read site rather than defending every
consumer. `isTourActive` and `hasTourCompleted` are unchanged one-liners. Covered by seven
named-input cases in the new `src/frontend/state/__tests__/tourContextState.test.ts`.

## Threat mitigation (T-34.12-05-01)

The threat register's `mitigate` disposition for `T-34.12-05-01` (DoS via unguarded `JSON.parse`
+ unchecked `.includes()`) is now closed. Pinned by `tourContextState.test.ts`; the RED proof
below shows the try/catch and shape-normalisation guards are independently load-bearing.

## RED proofs (all recorded and restored to green)

1. **Anchor swap (Task 1).** Swapped the `data-tour` values on the Accessibility and Documentation
   rows. Re-ran `SettingsPanel.test.tsx`: exactly two failures --
   `SettingsPanel > D-05 tour anchors > the Accessibility row carries data-tour="nav-accessibility"`
   (received `"nav-docs"`) and
   `SettingsPanel > D-05 tour anchors > the Documentation row carries data-tour="nav-docs"`
   (received `"nav-accessibility"`). Restored; full suite green (1977/1977 at that point).

2. **Launcher placement (Task 2).** Moved the launcher row to after `<QuitButton />`. Re-ran:
   `SettingsPanel > the QuitButton element is the last child of the panel` failed (`✕`). Restored;
   the same test re-passed.

3. **Restart path (Task 2).** Removed the `if (hasTourCompleted(...)) resetTour(...)` branch from
   `handleStartTour`, leaving only `startTour(NAV_TOUR_ID)`. Re-ran:
   `starts the tour without resetting when it has not been completed` still PASSED while
   `resets then starts the tour, in that order, when it was already completed` FAILED. Proves the
   two launcher tests cover different paths rather than duplicating one. Restored; both green.

4. **Shape-guard independence (Task 3).** Replaced `Array.isArray(candidate.completedTours) ? ... :
   defaultState.completedTours` with a bare `candidate.completedTours as string[]` (no runtime
   guard), leaving the try/catch in place. Re-ran `tourContextState.test.ts`: both wrong-shape
   cases FAILED --
   `normalises completedTours to [] when it is null` (received `null`) and
   `normalises completedTours to [] when it is a string, not an array` (received `"nav-tour"`) --
   while `returns defaultState and does not throw for malformed JSON` still PASSED (that case is
   caught earlier by the try/catch, unaffected by the guard removal). Restored; full guard back,
   all seven cases green.
