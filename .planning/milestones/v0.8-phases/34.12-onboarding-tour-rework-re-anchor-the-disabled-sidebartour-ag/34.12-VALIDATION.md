## Sampling Rate

- **After every task commit:** Run `pnpm jest --selectProjects Frontend NavShell/__tests__/` (add the specific touched suite path when the task is outside `NavShell/`).
- **After every plan wave:** Run `pnpm test` (all 5 projects — the retired `tourDisabled.test.ts` and the i18n churn guard live outside the `NavShell/__tests__/` scope).
- **Before `/gsd:verify-work`:** Full suite green **plus** the Manual-Only table below executed.
- **Max feedback latency:** ~15 seconds scoped.

**Per-step sampling is MANDATORY, not per-tour.** This repo has a recorded failure mode —
*an audit coarser than the defect's unit cannot find it* — and CONTEXT.md independently bans the
coarse form ("all twelve `nav-*` strings appear somewhere in the tree" is the vacuous version, do
not ship it). Each of the twelve anchors gets its **own** assertion naming its **own** component.
Twelve assertions, not one.

## Positive Gate Contract

The single hardest requirement in this phase. `tourDisabled.test.ts` must be **replaced**, not
deleted, and must not become vacuously true. The accepted design is a **composed two-layer proof** —
neither layer alone catches every failure mode:

**Layer A — correctness with identity (per-component, ×12).** Invoke the real parent component
function directly and assert the correct `nav-*` string arrives as a prop on the correct **named**
child, located by `element.type` identity or by its `label`. Example shape:
`findNavItem(SettingsPanel(), 'Wine Manager')?.props['data-tour'] === 'nav-wine'`.
*Property measured:* this specific source site carries this specific value on this specific row.

**Layer B — uniqueness (census, ×12).** For each of the twelve ids, exactly one source location in
`src/frontend` contains `data-tour="{id}"`. *Property measured:* uniqueness only — this is the
defect class that produced the original duplicate `sidebar-downloads`.

**Layer A+B closure.** Layer A alone cannot detect a duplicate. Layer B alone cannot detect
"exactly one occurrence, on the **wrong** element" — `nav-wine` landing once, on the Accessibility
row, passes B and fails A. Ship both.

**Plus one bridging assertion:** `NavItem.test.tsx` must assert that `NavItem` forwards its
`data-tour` prop onto the rendered `<NavLink>`/`<button>` props. Without it, Layer A proves
`SettingsPanel` *passes* the prop while `NavItem` silently eats it — the recorded
*"function is CALLED proves wiring, not behaviour"* failure mode. `NavItem`'s prop interface is
closed today and its docstring records that the anchor prop was **deliberately dropped**
(`NavItem/index.tsx:14-18`); re-adding it is real, scoped work.

**RED-proof obligation (blocking, per CONTEXT.md).** Every gate above must be proven red against a
deliberately broken input before it is accepted, and the proof recorded in the plan's evidence:
- Layer A: delete one `data-tour="nav-wine"` prop from the `SettingsPanel` JSX → suite red, failure message names the Wine Manager row.
- Layer B: paste a second `data-tour="nav-downloads"` elsewhere → census red for that id only.
- Bridge: remove the forwarding line in `NavItem` → `NavItem.test.tsx` red while Layer A stays green (this is the proof that the bridge is not redundant).

**Explicitly rejected — do not ship:** "all twelve `nav-*` strings appear somewhere in the tree."
Banned by CONTEXT.md. It is RED-provable yet ties no string to any element, so it cannot distinguish
twelve correct anchors from twelve anchors pasted onto one wrong element. This is the recorded
*"a gate can be non-vacuous, RED-proven — and guard NOTHING"* failure mode.

## Manual-Only Verifications

The automated layer proves every anchor is wired to the right component. It cannot prove the tour
*runs*. These are blocking for `/gsd:verify-work`.

| Behavior | Requirement | Why Manual | Test Instructions |
|----------|-------------|------------|-------------------|
| Tour launcher is reachable | D-01 | Requires a rendered app; no jsdom | Launch app → click Settings tier-1 tab → confirm the tour row is present in `SettingsPanel`, labelled, and styled like the Documentation / Ko-fi / Accessibility rows (not standing out) |
| Tour starts and completes | D-02, D-06 | intro.js overlay is runtime-only | Click the launcher row → tour starts → step through all twelve → confirm it ends cleanly and the new id lands in `localStorage['heroic-tour-state'].completedTours` |
| **Each of the twelve steps highlights the intended element** | D-05 (all 12) | Selector→element resolution is a live-DOM property | Step through and confirm **per step, individually** — record 12 separate outcomes, not one "tour works". A step whose selector matches nothing silently skips or mis-highlights; that is exactly the defect this phase exists to fix |
| Tier-1 tabs are not clickable mid-tour | D-04 | `disableInteraction` is an intro.js runtime behaviour | With the tour on a tier-1 tab step, attempt to click the highlighted tab → click must be blocked, `SettingsPanel` must stay mounted, remaining steps must still resolve |
| Tour never auto-starts | D-02 | Requires app launch with a fresh profile | Launch with a clean profile → confirm no tour appears; relaunch after completing the tour → still no tour |
| Non-English copy is not stale | D-07 | Catalog correctness is a translation-content property | Switch to German → confirm the version step does **not** read "Heroic-Version" (`de/translation.json:1084` carries the stale string today — this is live evidence, not hypothetical) |
| `LibraryTour`'s two re-anchored steps resolve | D-09 | Live-DOM selector resolution | Games tab → launch `LibraryTour` from `ActionIcons` → confirm the categories and filters steps highlight real filter surfaces. **Run once with zero connected stores** if the planner picks the representative-element option — `FilterStoreFacet` renders `null` when `connectedStores.length === 0` |

## Open Questions Carried Into Planning — BOTH RESOLVED 2026-08-22

- **OQ-1 resolved (plan `34.12-02`): wrap, not representative element.** `FilterStoreFacet` returns `null` at zero connected stores — exactly a first-run user's state — so a representative anchor would have reintroduced the missing-anchor defect. Both wrappers re-declare the flex/gap rule, checked by a brace-counted block-scoped grep with a per-wrapper RED proof. Selectors renamed to `library-views-collections` / `library-facets` so the census can tell a correct re-anchor from a resurrected dead string.
- **IN-01 resolved (plan `34.12-06`): all three dead attributes removed, ROADMAP wording corrected.** `library-header` ×2 and `humble-keys` — all three line references re-verified byte-exact at HEAD by the plan checker. Task 3 rewrites the false ROADMAP bullet behind a pre-edit `find` guard.

*Original statements of both questions, retained for the record:*



- **OQ-1 (blocking for D-09's test):** the two dead `LibraryTour` steps need exactly one matching element each, but D-09 names component *groups*. Research recommends **wrapping** `FilterViewList`+`FilterCollectionList` and the three `FilterFacetGroup`s in two new divs — with `display:flex; flex-direction:column; gap:var(--space-md)` copied onto each wrapper, because `.Header` applies that gap between **direct** children and a new wrapper changes what the gap applies between (`Header/index.css:1-9`).
