# Phase 34.12: Onboarding tour rework — re-anchor the disabled SidebarTour against the two-tier NavShell - Context

**Gathered:** 2026-08-22
**Status:** Ready for planning

<domain>
## Phase Boundary

Re-enable the onboarding tour against the two-tier `NavShell`. Phase 34.10 disabled the
sidebar tour under D-13 and deliberately did not rebuild it; this phase is that rebuild.
Every one of `SidebarTour.tsx`'s twelve `data-tour="sidebar-*"` steps is re-anchored to a
surface that exists in the new shell (all twelve survive — see D-05), the tour gets a
reachable launcher again, and `NavShell/__tests__/tourDisabled.test.ts` is replaced by a
positive gate rather than deleted.

**In scope:** the shell tour's steps, selectors, copy, i18n keys and launcher; the two dead
`LibraryTour` steps that 34.11 orphaned; the 34.10 IN-01 dead-`data-tour` cleanup; retiring
and replacing the tour-disabled gate.

**Out of scope:** the tour library itself (`intro.js-react` stays), `LibraryTour`'s seven
working steps, any new onboarding surface that isn't a re-anchor of an existing step.

</domain>

<decisions>
## Implementation Decisions

### Tour entry point

- **D-01: The launcher is a labelled row in `SettingsPanel`,** alongside Documentation,
  Ko-fi, Accessibility and Console Mode. Not an icon button. Rejected alternatives:
  restoring it on `HeroicVersion` (that is the "second, easy-to-miss entry point" that
  `tourDisabled.test.ts`'s own docstring calls out as the reason the old tour was hard to
  reason about — do not reintroduce a second launcher), and placing it in
  `.NavShell__navRight` beside `DownloadsRing` (cuts against UI-SPEC OQ6, which omitted both
  a search icon and an avatar from that slot on purpose to keep it minimal).
  **Consequence that the rest of this phase depends on:** because the launcher lives in the
  Settings tier-2 panel, the Settings tab is necessarily active and its panel open at the
  moment the tour starts. D-03 is built on this.

- **D-02: Manual only — the tour never auto-starts.** No first-run trigger, no new
  persistence, matching how `LibraryTour` behaves today. Explicitly rejected: auto-starting
  when `hasTourCompleted()` is false. No existing install has ever completed this tour, so
  that predicate is true for every current user and it would fire on upgrade, not on first
  run. If auto-start is ever wanted it needs a separate "already onboarded" marker — see
  Deferred Ideas.

### Cross-tier anchoring

- **D-03: The tour never switches tier-1 tabs.** Steps are ordered against what is already
  on screen: the tier-1 tab strip is always visible, and the Settings tier-2 panel is open
  because that is where the launcher is (D-01). This is what makes all twelve steps
  anchorable without the tour driving navigation — nothing to unwind, nothing to restore if
  the user abandons the tour mid-run. Rejected: auto-switching tabs to also demo
  `GamesPanel` / `StoresPanel` contents (the old tour pointed at nav *links*, not panel
  contents, so this would be new scope as well as new risk).

- **D-04: This tour runs with `disableInteraction: true`.** `Tour.tsx` currently passes
  `disableInteraction: false`, which leaves a highlighted tier-1 tab clickable — a user
  could click the highlighted Games tab, unmount `SettingsPanel`, and strand every
  remaining Settings-anchored step against a selector that resolves to nothing. The flag
  makes D-03 structurally true instead of merely intended. Set it per-tour via `Tour`'s
  existing `options` prop; **do not change `Tour.tsx`'s defaults** — `LibraryTour` shares
  that component and is not in scope.

### Step list

- **D-05: All twelve steps are re-anchored 1:1 — order preserved, none dropped.** Under D-03
  every original surface still exists, so "re-anchored or dropped with a reason" resolves to
  twelve re-anchors and zero drops. Verified target for each (this is the work-list, already
  scouted — do not rediscover it):

  | # | Old selector | New anchor |
  |---|---|---|
  | 1 | `sidebar-menu` | the tier-1 tab strip (`NavTabs`) — copy rewritten, see D-06 |
  | 2 | `sidebar-library` | Games tab |
  | 3 | `sidebar-stores` | Stores tab |
  | 4 | `sidebar-settings` | Settings tab |
  | 5 | `sidebar-downloads` | `DownloadsRing` in `.NavShell__navRight` |
  | 6 | `sidebar-wine` | Wine Manager row in `SettingsPanel` (stays non-Windows-only) |
  | 7 | `sidebar-manage-accounts` | Accounts tab |
  | 8 | `sidebar-accessibility` | Accessibility row in `SettingsPanel` |
  | 9 | `sidebar-docs` | Documentation row in `SettingsPanel` |
  | 10 | `sidebar-community` | Ko-fi row in `SettingsPanel` |
  | 11 | `sidebar-quit` | `QuitButton` (last child of `SettingsPanel`) |
  | 12 | `sidebar-version` | `HeroicVersion` in `.NavShell__versionSlot` |

  Step 5 also closes the known pre-existing defect named in `SidebarTour.tsx`'s header: the
  duplicate `data-tour="sidebar-downloads"` dies by construction, because `DownloadsRing` is
  a single element where the retired sidebar had two. Step 12's copy ("access tours from
  here") is now false under D-01 and must be rewritten — the launcher is the Settings row.

- **D-06: `data-tour="sidebar-*"` is renamed to `nav-*`.** This lands 34.10's explicitly
  deferred idea ("honest naming, but it belongs to the tour phase"). The component, its file
  and `SIDEBAR_TOUR_ID` are renamed to match; the `'sidebar-tour'` id string changes with
  them (it is only a `completedTours` entry in `localStorage`, so the cost is that anyone
  who completed the old tour is eligible for the new one — which is correct, it is a
  different tour).

- **D-07: New `tour.nav.*` i18n keys ONLY for steps whose copy actually changed;** steps
  whose English text is unchanged keep their existing key. Rationale, and the trap this
  avoids: in `t('tour.sidebar.welcome.intro', 'Welcome to GameLib! This sidebar contains…')`
  the second argument is a *fallback*, inert whenever the key exists in the catalog. Editing
  it is a silent no-op for every locale that already translated the key — every non-English
  user would keep seeing "this sidebar contains all the navigation options" with nothing in
  the build to flag it. A new key cannot inherit a stale translation. Rejected: renaming all
  twelve to `tour.nav.*` (throws away good translations for steps that didn't change) and
  keeping every key (ships the stale-translation defect above). A mixed
  `tour.sidebar.*` / `tour.nav.*` namespace is the accepted cost.

### Relationship to LibraryTour

- **D-08: Two tours stay separate, one launcher each** — the new `SettingsPanel` row for the
  shell tour, the existing `TourButton` in `ActionIcons` for `LibraryTour`. Rejected:
  chaining shell → library and merging into one ~20-step tour; both require switching to the
  Games tab mid-tour, which contradicts D-03.

- **D-09: `LibraryTour`'s two dead steps are re-anchored to 34.11's filter panel.**
  `[data-tour="library-categories"]` and `[data-tour="library-filters"]` match no element in
  the tree today — 34.11 replaced those controls — so that tour ships two broken steps to
  users right now. Re-point them at the tier-2 filter surfaces (`FilterCollectionList` /
  `FilterViewList` for categories, the `FilterFacetGroup` set for filters). No navigation
  driving is needed: the Games tab is active whenever `LibraryTour`'s own button is
  reachable. Its other seven selectors resolve today and are not touched.

### Claude's Discretion

- **Where the renamed tour component lives.** Recommended: move it under
  `NavShell/components/`, which empties the retired `Sidebar/` tree and lets that directory
  be deleted for real. ⚠ `git mv` plus a large content rewrite in one commit falls under
  git's 50% rename-detection threshold and shows up as delete+add — split the rename from
  the rewrite, and check `git show -M --summary`.
- **What the positive gate asserts** (D-10-shaped, left to planning). Constraint the planner
  must design around: the frontend jest project is `testEnvironment: 'node'` with **no
  jsdom** (see the docstring in `src/frontend/jest.config.js`), which is exactly why
  `tourDisabled.test.ts` is a source-text gate rather than a render test. A positive
  replacement therefore cannot simply render the shell and query selectors. **"All twelve
  `nav-*` strings appear somewhere in the tree" is the vacuous version — do not ship it.**
  The gate must tie each step selector to the specific component that carries the attribute,
  and must fail if an anchor is removed. Prove it red against a deliberately broken anchor
  before accepting it.
- Exact wording of the `SettingsPanel` row label and the rewritten step copy.
- Whether `library-header`'s duplicate attribute is removed as part of the IN-01 sweep
  (it is on two elements — `LibraryHeader/index.tsx:99` and `Library/index.tsx:1122` — and
  referenced by no step at all, so it is dead either way).

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- `src/frontend/components/Tour/Tour.tsx` — `intro.js-react` wrapper. Takes `steps`,
  `enabled` and an `options` passthrough that merges over its defaults, which is how D-04's
  `disableInteraction: true` is applied per-tour without touching the shared defaults.
- `src/frontend/components/Tour/TourButton.tsx` — existing launcher primitive (renders
  `data-tour-button={tourId}`); reuse it for the D-01 row rather than inventing one.
- `src/frontend/state/TourContext.tsx` — `startTour` / `endTour` / `hasTourCompleted`,
  persisted to `localStorage['heroic-tour-state']`. Already sufficient for D-02; no new
  state needed.
- `src/frontend/components/UI/NavShell/components/NavItem/index.tsx` — the row primitive
  `SettingsPanel` uses; the launcher row should match it, not stand out.

### Established Patterns
- Tours are mounted as siblings of the surface they describe and gated on
  `isTourActive(id)` — `LibraryTour` at `Library/index.tsx:1084` is the live example.
- `NavShell` returns a **fragment**, not a wrapper: `.NavShell__navbar` and
  `.NavShell__tier2` must stay direct grid children of `.App` or their `grid-area` breaks.
  Any new element must not be introduced between them.
- Frontend tests are source-text gates, not render tests — `testEnvironment: 'node'`, no
  jsdom (`src/frontend/jest.config.js`). This shapes the replacement gate; see Discretion.

### Integration Points
- `SettingsPanel/index.tsx` — the new launcher row. Note `SettingsPanel.test.tsx` already
  asserts `QuitButton` is the **last child**; inserting a row must respect that ordering
  assertion or update it deliberately.
- `NavShell` component files — where the `nav-*` attributes land. Every one of these files
  is currently covered by `tourDisabled.test.ts`'s `expect(source).not.toMatch(/data-tour/)`
  assertion, so that gate goes red the moment the first anchor is added. Retire it in the
  same plan that adds anchors, not later.
- `ActionIcons/index.tsx` — hosts `LibraryTour`'s existing `TourButton`; unchanged by D-08.

</code_context>

<specifics>
## Specific Ideas

- The old step 12 copy — "Check your current GameLib version and access tours from here" —
  is the one piece of the original tour that is now factually wrong rather than merely
  stale, since D-01 moves the launcher. It is the clearest example of why D-07 mints a new
  key instead of editing a fallback string.
- The duplicate-selector defect the roadmap flags for step 5 does not need a fix so much as
  a check: `DownloadsRing` is one element, so re-anchoring resolves it. Confirm that rather
  than writing code for it.

</specifics>

<deferred>
## Deferred Ideas

- **First-run auto-start for the shell tour** — wanted eventually, blocked on a reliable
  "this is a genuinely new install" signal. `hasTourCompleted()` is not that signal (D-02).
  Needs either a separate onboarded marker or a clean-profile check; own phase or a later
  polish pass.
- **Chaining shell → library into one continuous first-run narrative** (D-08) — attractive
  for onboarding, but it requires the tour to drive tier-1 navigation, which D-03 rules out
  for this phase. Revisit only if tab-driving is ever accepted.
- **Steps covering `GamesPanel` / `StoresPanel` contents** rather than just their tab
  buttons — genuinely new tour scope, not a re-anchor of anything the old tour had.
