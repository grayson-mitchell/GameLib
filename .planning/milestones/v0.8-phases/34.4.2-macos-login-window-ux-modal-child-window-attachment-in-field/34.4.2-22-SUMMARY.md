## The Mechanism, As Derived From Source

Confirmed by direct inspection at execution time (all three source anchors re-read in full, not trusted from planning-time line numbers):

1. **`src/frontend/screens/Login/index.tsx:151-242`** — all six `Runner` tiles (`epic`, `gog`, `nile`, `zoom`, `steam`, `humble`) pass `disabled={oldMac}` and nothing else. `oldMac` (`index.tsx:73-85`) derives solely from `systemInfo?.OS.platform === 'darwin'` plus a macOS-major-version check (`< 12`). **No login-in-flight, pending-login, or is-logging-in identifier feeds `disabled` anywhere in this file** — verified directly, not merely asserted (the absence check in the new test file's third assertion pins this).
2. **`src/frontend/screens/Login/components/Runner/index.tsx:60-73`** — `handleLogin()`, for any tile with no `primaryLoginAction` (the Amazon/GOG/Steam/Zoom/Humble shape — Epic under Tauri is the sole exception via `primaryLoginAction`, out of this plan's scope per the phase's own Epic-deferred boundary), terminates with `navigate(props.loginUrl)`.
3. **`src/frontend/App.tsx:157-250`** — `loginweb/:runner` (line 200) is registered as a SIBLING of `login` (line 168) inside the SAME top-level `children` array of the SAME single `createHashRouter` tree (confirmed: exactly one `createHashRouter(` call, exactly one `errorElement:` in that children array). Navigating there is therefore a full route replacement, not an overlay — React Router unmounts `NewLogin` (and with it the single `runnerGroup` container, confirmed to occur exactly once in the file) and mounts `WebView` in its place.

**Conclusion — this CORRECTS `deferred-items.md`'s and `ROADMAP.md`'s recorded characterisation** ("the frontend disables/clears the other login buttons while one login is in flight"). That is not what the source does. The correct wording, for plan 34.4.2-23's withdrawal reasoning and any future document: **"clicking a login tile navigates away from the Login screen, unmounting every tile — including the one the user would otherwise click next — not disabling or clearing any button."** This agrees exactly with plan 34.4.2-21's own independent re-derivation, recorded in its own SUMMARY, that `handleLogin()` calls `navigate(props.loginUrl)` and that this unmounts the whole `runnerGroup` container.
