# Phase 34.4.2 Plan 14: Single-Flight Guard on Visible Login Windows (T-34.4.2-39) Summary

**A `#[cfg(target_os = "macos")]` latch (`PENDING_VISIBLE_LOGIN_WINDOW`) refuses a second VISIBLE
Tauri-managed login window at the shell entry point while another visible flow is pending or
presented, with a 25s TTL (derived from the existing 15s sheet-attach watchdog) so the guard
cannot itself become a total-lockout denial of service -- closing T-34.4.2-39's origin-confusion
failure mode (typing one store's password into another store's just-arrived sheet) at the source
level, with live discharge explicitly deferred to the next gate's own item.**

## Decisions Made

- **TTL derived from the existing watchdog, not invented** -- `PENDING_VISIBLE_LOGIN_WINDOW_TTL =
  LOGIN_SHEET_PRESENT_WATCHDOG_TIMEOUT.as_secs() + 10` = 25s. The watchdog's own fallback path
  (the visible-fallback block) always runs and clears the latch within its own 15s bound, well
  before this 25s TTL could ever fire against a still-legitimate flow -- the two constants can
  never disagree because one is defined in terms of the other.
- **Boundary verdict at `age == TTL`: STALE** (`>=`, not `>`). Documented in
  `pending_login_entry_is_stale`'s own doc comment and pinned by its own cargo test
  (`pending_login_entry_exactly_at_ttl_is_stale`) -- matches this file's existing
  `LOGIN_SHEET_PRESENT_WATCHDOG_TIMEOUT`/`recv_timeout` convention (a bound that has been
  EXCEEDED, not merely reached, before the caller-side fallback runs).
- **`if visible == true {`, not `if (visible) {`** -- the parens form was tried first, compiled
  cleanly under `cargo test`, but `cargo check` flagged `unused_parens`, violating this file's
  zero-warnings acceptance bar. The `== true` comparison is functionally identical and produces
  zero warnings.
- **The refuse-or-arm check combines both incumbent sources into one lookup** (pending latch OR
  presented-sheets list) rather than two separate refusal branches -- simpler code, and the single
  log line naming "the incumbent" reads correctly regardless of which source produced it.
- **`clear_pending_visible_login_window` is never routed through `register_presented_login_sheet`**
  -- deliberately a separate function, per the plan's own explicit instruction, so Plan 11's
  exactly-three-call-sites test on that helper stays untouched and green.

## Per-Consumer-Path Refusal Trace (Task 1 step 6, quoted from code)

- **`captureOAuthLogin` (GOG/Amazon/Zoom via `oauthCaptureLogin`) -- SURFACES the refusal.**
  `src/backend/sidecar/oauthLoginCapture.ts:326-331`:
  ```
  activeSeam.open(loginUrl, {...}).then(...).catch((err) => {
    void settle({ status: 'error', message: err instanceof Error ? err.message : String(err) })
  })
  ```
  Confirms `oauthLoginFlowRegistration.ts`'s own comment ("captureOAuthLogin() itself never
  rejects") is accurate for this refusal specifically, not merely asserted -- verified by reading
  the await site, not trusted from the comment. The frontend
  (`src/frontend/screens/WebView/useTauriOAuthLogin.ts:283-287`) branches on
  `outcome.status === 'error'` and calls `safeSetState({ phase: 'error', message: outcome.message })`.
  `TauriLoginPanel.tsx` (line 188) renders that phase as `webview.login.oauth.error.heading` /
  `webview.login.oauth.error.body` with body text `Something went wrong while signing in:
  humble_login_open:login-already-in-progress` -- **the user sees an explicit, readable error.**

- **Humble's own `startLogin()`/`reconnect()` (via `humbleStartLogin`/`humbleReconnect`) --
  SWALLOWS the refusal silently.** `src/backend/humble/user.ts:573-579` has the identical
  `.open(...).catch((err) => { settle({ status: 'error' }) })` shape, so the refusal DOES reach
  the frontend as `{ status: 'error' }` -- but `src/frontend/screens/WebView/index.tsx`'s
  `runHumbleLoginWatch()` (lines 303-314) only branches on `result.status === 'done'`:
  ```
  const result = humble.expired
    ? await window.api.humbleReconnect()
    : await window.api.humbleStartLogin()
  if (!mounted) return
  if (result.status === 'done') {
    await humble.login(result)
    navigate('/login')
  }
  ```
  There is no `'error'` branch. **A refused Humble login produces no toast, no navigation, no
  state change of any kind** -- the effect completes silently and the user is left with zero
  indication a second login attempt was even made, let alone refused.

Both traces are quoted from code read during this plan's execution, not inferred. Recorded in
`deferred-items.md` under "Plan 14 -- ... a silently-swallowed refusal path", not fixed here:
REQ-34.4.2-08 requires all new behaviour to be `#[cfg(target_os = "macos")]`-gated, and the
frontend has no way to know which platform refused the login from that vantage point. This
phase has already recorded one standing wart against an un-gated cross-platform surface (the
Plan 09 autofill-glyph finding, closed 2026-08-05 by Plan 13's deletion) and must not acquire a
second. The new gate's single-flight item will measure what the user actually sees on both
paths; a silent refusal on the Humble path is a real, recordable outcome for that item.
