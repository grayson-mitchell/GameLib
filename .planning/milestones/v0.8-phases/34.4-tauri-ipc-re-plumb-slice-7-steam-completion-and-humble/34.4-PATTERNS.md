## Shared Patterns

### 1. send-vs-handle registration kind MUST match `main.ts`/`ipc_handler.ts` exactly, for every one of the 31 channels

**Confirmed kinds for this slice (cross-checked directly against source, not transcribed from CONTEXT.md — CONTEXT.md was wrong for one of three named channels):**
- `addListener`/`send`: **only** `logoutSteam` (`main.ts:939`) and `humbleDisconnect` (`humble/ipc_handler.ts:121`).
- `addHandler`/`handle`: **every other channel in this slice**, including `humbleRecordGiftLinkOpened` (CONTEXT.md incorrectly named this a `send`; confirmed `addHandler` at `humble/ipc_handler.ts:72`, `Promise<void>` in `common/types/ipc.ts:350`, `makeHandlerInvoker` in `preload/api/humble.ts:31`).

A mismatch **fails 100% silently** at runtime (`sidecar-send-channels-fail-silently`, Phase 31 Pitfall 2) — no reject, no timeout, no console line. This is the whole reason D-08's live gate exists (item 2, `logoutSteam`). Cross-check every registration against its exact `addHandler`/`addListener` call before writing it.

### 2. Curated imports — import the underlying module, never a feature module's `ipc_handler.ts`

**This slice's sharpest instance yet:** `humble/ipc_handler.ts` registers **6 channels this slice must NOT register** (the 5 channels deferred to Phase 34.4.1 plus, per its own docstring, the dev-only trigger's exclusion pattern) alongside the 15 it does own. A side-effect import of that file would prematurely register `humbleStartLogin`/`humbleReconnect`/`humbleStopLogin`/`humbleLoginNavigated`/`humbleGetLoginUserAgent`/`humbleRevealKey`, violating SEAM.md Invariant B. Import `humble/user.ts`, `humble/library.ts`, `humble/validation.ts` directly — exactly as `settingsFlowRegistration.ts` already does for `libraryManagerMap` (never `storeManagers/index.ts`'s own `ipc_handler.ts`-equivalent, if one existed).

### 3. The load-bearing `import '../storeManagers'`-first circular-dependency fix is per-file, not per-bundle

Every curated registration module that imports anything from `storeManagers/steam/*` (or transitively) directly must force `storeManagers/index.ts` to finish evaluating first — see `steamAuthFlowRegistration.ts:28-41`'s full docstring (already quoted above) for the exact `SteamLibraryManager is not a constructor` esbuild-bundle-only hazard this avoids. `humbleFlowRegistration.ts` (NEW) needs this too if it reaches anything through `storeManagers/index.ts`'s eager construction — verify at plan time whether Humble has an equivalent eager-manager hazard.

### 4. `electronStub` failures must resolve/reject asynchronously, never synchronously — and never REJECT a caller that cannot handle it

`sidecar-dialog-reject-crashes`: an unguarded fire-and-forget `await`er of a stub that rejects (rather than resolving a safe default, or emitting an async `'error'` event a caller has already wired a handler for) hard-crashes the sidecar process. D-06's `net.request` fix follows this exactly: it does not throw synchronously inside `request()` (which would be too early for `request.on('error', ...)` to have been registered), and it does not silently no-op (the pre-fix defect) — it emits an async `'error'` event via `setImmediate`, which `humblePostRequest`'s own already-wired `request.on('error', ...)` handler (`adapter.ts:328`) safely converts into a rejection with an accurate cause. `electronStub.session`'s existing D-09 no-op (`electronStub.ts:557-564`) is the sibling precedent for "logged, resolved, never rejected."

### 5. Every store this slice needs is ALREADY registered — zero new store plumbing

3 Steam stores (`storeRegistration.ts` L46-50: `_steamConfigStore`, `_steamBottleConfigStore`, `_steamSyncStore`) and all 9 Humble stores (`storeRegistration.ts` L88-97) are already wired. No new `storeRegistration.ts` edit is needed for this slice's channels.
