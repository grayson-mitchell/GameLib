# Phase 34.4: Tauri IPC re-plumb slice 7 — Steam completion and Humble - Research

**Researched:** 2026-07-27
**Domain:** Electron→Tauri sidecar IPC port (Steam credential/session/bottle/client-setup/private-branch/key-redeem channels + the portable half of Humble)
**Confidence:** HIGH (every channel, line number, and `handle`/`send` kind below was read directly from source, not inferred from CONTEXT.md's prose)

## Summary

This slice is cheap on code and expensive on verification discipline. Of the 31 channels, 29 are
one-line delegations to already-Electron-free (or already-hook-rescued) functions, every store
they touch is already registered, and the QR-login template (`steamAuthFlowRegistration.ts`)
already proves the exact registration shape for the credential-login trio. The real content is:
(1) get the `send`-vs-`handle` kind of all 31 registrations exactly right — one is silently wrong
in CONTEXT.md itself, see below; (2) correctly attribute two channels CONTEXT.md filed as Steam
that are actually GOG; (3) extend the electron-reach ledger with the correct set of new edges
(three, not two); (4) harden `electronStub.net.request` to fail fast; (5) add the honest
"not available on this build" login panel; (6) run and pass a blocking 5-item live gate.

**This research made three corrections to CONTEXT.md's own factual claims, verified directly
against source, that the planner MUST apply rather than trusting CONTEXT.md's prose verbatim:**

1. **`humbleRecordGiftLinkOpened` is a `handle` channel, not a `send`/`addListener` channel.**
   CONTEXT.md's Discretion section names it as one of three `send` channels alongside
   `logoutSteam` and `humbleDisconnect`. Direct source read of `humble/ipc_handler.ts:72`
   (`addHandler('humbleRecordGiftLinkOpened', async (e, machineName) => {...})`), confirmed by
   `common/types/ipc.ts:350` (`Promise<void>`, the `AsyncIPCFunctions`/handle-typed shape) and
   `preload/api/humble.ts:31` (`makeHandlerInvoker('humbleRecordGiftLinkOpened')`), proves it is
   a `handle`. **Only `logoutSteam` (`main.ts:939`, `addListener`) and `humbleDisconnect`
   (`ipc_handler.ts:121`, `addListener`) are `send` channels.** Registering
   `humbleRecordGiftLinkOpened` as a `send` on the sidecar would produce exactly the
   `sidecar-send-channels-fail-silently` defect class (G-30-01's own root cause) that this
   phase's entire live-gate rationale (D-08) exists to prevent.
2. **`getPrivateBranchPassword`/`setPrivateBranchPassword` are GOG channels, not Steam.**
   CONTEXT.md's domain table files them under "Steam (15) ... Private branches". Direct source
   read of `main.ts:1510-1515` shows both delegate to
   `libraryManagerMap['gog'].getGame(appName).getBranchPassword()/.setBranchPassword()` —
   `GOGGame.getBranchPassword`/`setBranchPassword` (`storeManagers/gog/games.ts:1398,1402`),
   backed by `privateBranchesStore` (`storeManagers/gog/electronStores.ts:36`, **already
   registered** at `storeRegistration.ts:62`). Nothing Steam-specific is involved. This changes
   the curated-import target (see Architecture Patterns) but not the channel count (still 15
   "Steam-labeled" channels in the inventory's list; 13 are genuinely Steam-domain, 2 are GOG).
3. **The electron-reach ledger gains THREE new edges this slice, not two.**
   `humble/user.ts` (`safeStorage`, `session`) and `humble/adapter.ts` (`net`) are correctly
   identified by CONTEXT.md's D-10/canonical-refs section. But `humble/library.ts` — the module
   CONTEXT.md itself names as a "clean import target" for the ported sync/key channels —
   statically imports `detectAndNotifyExpirationTransitions` from `./expirationAlerts`
   (`library.ts:22`), and `humble/expirationAlerts.ts:1` directly imports `Notification` from
   `electron`. This is a real, previously-unmeasured edge that will show up as a growth-tripwire
   failure in `electronReachLedger.test.ts` unless `src/backend/humble/expirationAlerts.ts` is
   added to `BASELINE_ELECTRON_REACHING_MODULES` alongside the two CONTEXT.md already named.

A fourth, softer correction: CONTEXT.md's D-tier item about the "live-`csrf_cookie` read at
`user.ts:438-445`" points at the wrong function and, more importantly, at dead code from this
slice's perspective — see Common Pitfalls/Pitfall 3 and Open Questions. `IPC-PORT-INVENTORY.md`
has ALREADY been edited to the corrected 31/6/57 split (verified by direct read — see below); the
planner does not need to re-do that edit, only verify it stayed correct through planning.

**Primary recommendation:** Follow `steamAuthFlowRegistration.ts`'s exact shape for the 13
genuinely-Steam channels (extend that file or add a sibling — Claude's Discretion, unchanged from
CONTEXT.md); route the 2 GOG private-branch channels through the **already-imported**
`libraryManagerMap` pattern `settingsFlowRegistration.ts` established for `requestGameSettings`
(zero new module, zero new reach edge); import `humble/user.ts`, `humble/library.ts`,
`humble/validation.ts` directly for the 14 clean Humble channels, never `humble/ipc_handler.ts`;
extend the ledger with 3 new baseline entries; hardened-fail-fast `electronStub.net.request`;
add the honest login panel; run the blocking 5-item live gate with the Humble
Electron-first-login precondition stated as an explicit numbered step.

### Pattern 1: Extending an existing curated registration module (credential login)

**What:** Add new `ipcMain.handle`/`.on` calls to `steamAuthFlowRegistration.ts`, matching the
QR trio's exact shape, and correct the file's own docstring.
**When to use:** For every genuinely-Steam channel in this slice.
**Example (mirrors the existing pattern at `steamAuthFlowRegistration.ts:51-63`):**
```typescript
// Source: src/backend/sidecar/steamAuthFlowRegistration.ts (existing file, read 2026-07-27)
export function registerSteamAuthFlows(): void {
  ipcMain.handle('checkSteamInstalled', async () => SteamUser.isSteamClientInstalled())
  ipcMain.handle('steamStartQR', async () => SteamUser.startQRLogin())
  ipcMain.handle('steamPollQR', async () => SteamUser.pollQRLogin())

  // NEW this slice — mirror the shape exactly:
  ipcMain.handle('steamStartCredentials', async (event, { username, password }) =>
    SteamUser.startCredentialLogin(username, password)
  )
  ipcMain.handle('steamSubmitGuard', async (event, code) =>
    SteamUser.submitSteamGuardCode(code)
  )
  ipcMain.handle('steamPollCredential', async () => SteamUser.pollCredentialLogin())

  // logoutSteam is a SEND channel — addListener/on, never handle:
  ipcMain.on('logoutSteam', async () => SteamUser.logout())
}
```
The docstring at `steamAuthFlowRegistration.ts:18-24` (not L19-25 as CONTEXT.md states — a
one-line offset, non-load-bearing) currently asserts these five channels are "deliberately does
NOT register" per Phase 30 D-02. **That sentence becomes false the moment this slice lands and
must be rewritten**, not left as a stale false invariant for a future reader to trust.

### Pattern 2: Reusing an ALREADY-IMPORTED barrel for a corrected-classification channel

**What:** `settingsFlowRegistration.ts` already imports `libraryManagerMap` from
`'../storeManagers'` (line 68, behind the load-bearing `import '../storeManagers'` first-import
fix at line 65) and already calls `libraryManagerMap['steam'].getGame(appName).getSettings()`

files like `humble/ipc_handler.ts` that register IPC channels as a side effect of import;
`storeManagers/index.ts` registers nothing, it only constructs library-manager instances).
**When to use:** For `getPrivateBranchPassword`/`setPrivateBranchPassword`.
**Example:**
```typescript
// Mirrors settingsFlowRegistration.ts:117's existing pattern
ipcMain.handle('getPrivateBranchPassword', (e, appName) =>
  libraryManagerMap['gog'].getGame(appName).getBranchPassword()
)
ipcMain.handle('setPrivateBranchPassword', (e, appName, password) =>
  libraryManagerMap['gog'].getGame(appName).setBranchPassword(password)
```

Since `settingsFlowRegistration.ts` is already one of `electronReachLedger.test.ts`'s
`ENTRY_POINTS` (added in Phase 34.2), and `libraryManagerMap`'s full transitive graph is already

is already a baseline member reached via the exact same `libraryManagerMap` import.

### Pattern 4: Fail-fast async stub error (D-06)

**What:** `electronStub.ts`'s `net.request()` currently returns an object whose `on()` is a
total no-op (`on: (): void => {}` — `electronStub.ts:594`) — registering an `'error'` listener
against it does nothing, ever. `humble/adapter.ts:328` already has
`request.on('error', (err) => { clearRequestTimeout(); reject(err) })` wired and ready to fire —
it just never does, so today `humblePostRequest`'s ONLY failure path under Tauri is its own
15-second `setTimeout` (`adapter.ts:282-287`), which then rejects with the misleading
`"Humble reveal request timed out"`.
**Example fix (must resolve/reject asynchronously, never synchronously — `sidecar-dialog-reject-crashes`):**
```typescript
// electronStub.ts — hardened net.request (D-06)
export const net = {
  request: () => {
    const handlers: Record<string, (arg?: unknown) => void> = {}
    // Fire asynchronously — never synchronously inside request(), which would make
    // `request.on('error', ...)` too late to have been registered yet.
    setImmediate(() => {
      handlers['error']?.(
        new Error(
          '[electronStub] net.request(): not implemented in the sidecar — ' +
          'this seam is Phase 34.4.1\'s (Humble reveal POST). See D-06.'
        )
      )
    })
    return {
      on: (event: string, cb: (arg?: unknown) => void): void => {
        handlers[event] = cb
      },
      end: (): void => {},
      write: (): void => {},
      setHeader: (): void => {}
    }
  },
  isOnline: (): boolean => true
}
```
Only caller of `net.request` in the whole backend, verified by grep: `humblePostRequest`
(`adapter.ts:270`) — the sole consumer of the deferred `humbleRevealKey` flow. No other caller
exists to regress.

### Anti-Patterns to Avoid
- **Side-effect-importing `humble/ipc_handler.ts`:** it registers 6 channels this slice does not
  own (5 deferred-to-34.4.1 + `humbleStopLogin`/`humbleLoginNavigated`), and importing it would
  register them on the sidecar prematurely, violating SEAM.md Invariant B.
- **Creating a new Steam module for the GOG private-branch pair:** they have nothing to do with
  Steam; forcing them into a Steam-named module both misrepresents the code and throws away the
  zero-reach-growth benefit of reusing `settingsFlowRegistration.ts`'s existing entry point.
- **Trusting CONTEXT.md's `send`/`handle` table without a source cross-check:** it was wrong for
  one of three named channels. Cross-check every registration against the exact
  `addHandler`/`addListener` call in `main.ts`/`ipc_handler.ts` for that channel name — do not
  transcribe from planning-time prose (the same discipline the reach-ledger docstring itself
  demands: "regenerate at execution time, not from planning-time prose").

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Steam credential/SteamGuard state machine | A custom login-poll loop | `steam-session`'s `LoginSession`, already wrapped by `SteamUser.startCredentialLogin`/`submitSteamGuardCode`/`pollCredentialLogin` | Already correct, already used by the ported QR flow; re-implementing risks diverging from the guard_required/poll contract the frontend depends on (`steam/user.ts:49-51`) |
| Refresh-token persistence | A new store or a hand-rolled encryption scheme | `getTokenStore()` (`steam/tokenStore.ts`, Phase 28 `SidecarKeyringTokenStore` seam) | Already proven by the QR flow; writes only `isLoggedIn`/`userData` to `steamConfigStore`, never the token itself |
| Sidecar failure signaling for an unimplemented network seam | A bespoke timeout/retry wrapper around `humblePostRequest`'s call sites | Harden `electronStub.net.request` once, at the shared stub layer (D-06) | `humblePostRequest` already has correct timeout + `on('error')` handling; the only missing piece is the stub actually firing events |
| GOG per-game store access from the sidecar | A parallel GOG data-access module | The already-imported `libraryManagerMap` in `settingsFlowRegistration.ts` | Zero new reach-ledger growth, and it is the established pattern for exactly this kind of per-game-manager method |

**Key insight:** every "build" temptation in this slice is actually a "reuse the sibling that
already solved this exact problem" opportunity — QR login for credential login, the settings
registration module for the GOG pair, `humblePostRequest`'s existing timeout logic for D-06.

## Common Pitfalls

### Pitfall 1: Trusting a planning-time `send`/`handle` classification without re-verifying at plan/execute time
**What goes wrong:** Registering `humbleRecordGiftLinkOpened` via `ipcMain.on` (send/listener)
instead of `ipcMain.handle`.
**Why it happens:** CONTEXT.md's Discretion section states it as fact; a planner who trusts prose
over source inherits the error.
**How to avoid:** Cross-check every one of the 31 channels against its EXACT
`addHandler`/`addListener` call in `main.ts` (Steam) or `humble/ipc_handler.ts` (Humble) before
writing the registration. This research already did that cross-check — see the Summary's
correction #1 and the exact line numbers in Sources.
**Warning signs:** A frontend caller that never resolves/rejects and produces no console line,
no error, nothing — the exact shape `sidecar-send-channels-fail-silently` documents.

### Pitfall 2: Misattributing a channel's domain because the inventory groups by file
**What goes wrong:** Building `getPrivateBranchPassword`/`setPrivateBranchPassword` inside a
Steam-specific module, or writing tests/docs that describe them as Steam functionality.
**Why it happens:** `main.ts` groups Steam and GOG handlers near each other by proximity, not by
a file boundary, and CONTEXT.md's own domain table inherited the mis-grouping. This is the exact
same failure class 34.1 D-14 (`callTool`) and 34.4's own D-03 (`isLoggedIn`) already caught for
OTHER channels in this same inventory — the inventory's file-grouping methodology is a known,
recurring source of misattribution.
**How to avoid:** For every channel, read its actual handler body, not just its position in
`main.ts`, before deciding which module family it belongs to.
**Warning signs:** A handler body that calls a completely different runner's library manager
than the group label suggests (`libraryManagerMap['gog']` inside a "Steam" section).

### Pitfall 3: Assuming CONTEXT.md's cited line range names the function it describes
**What goes wrong:** CONTEXT.md says "the live-`csrf_cookie` read L438-445 which already falls
back to the stored snapshot on failure" — but `user.ts:437-451` is actually the LOGIN-time
opportunistic capture block (which does NOT fall back to anything; on failure it just logs and
moves on). The REAL fallback-on-failure function is `HumbleUser.getLiveCsrfToken()`
(`user.ts:182-202`, falling back to `getCsrfToken()`'s stored snapshot at line 201). **More
importantly: `getLiveCsrfToken()`'s only caller is `revealKey()` in `library.ts:1172`, which
backs the DEFERRED `humbleRevealKey` channel.** None of this slice's 16 in-scope Humble channels
reach `getLiveCsrfToken()` at all.
**Why it happens:** Multiple near-identical `session.fromPartition(...).cookies.get({name:
'csrf_cookie'})` blocks exist in `user.ts` (login-time capture at ~L438, health-check backfill
at ~L544, and the actual fallback-wrapped read at L182) — easy to conflate.
**How to avoid:** Do not add a test obligation for `getLiveCsrfToken()` to this slice. It is dead
code from 34.4's ported-channel surface; its testing belongs to Phase 34.4.1 when
`humbleRevealKey` is actually reachable.
**Warning signs:** A plan that proposes "unit-prove the csrf fallback" as a 34.4 task — check
first whether the function is actually reachable from any of the 16 ported channels (it is not).

### Pitfall 4: A `send` channel registered as a `handle` (or vice versa) fails 100% silently
**What goes wrong:** (Restated from Phase 31/34.3's own pitfall catalog, directly load-bearing
here because this slice has the highest `send`-channel density of any slice so far — 2 of 31,
plus the corrected-away third.) A mismatch produces no reject, no timeout, no console line.
**Why it happens:** `send`/`handle` is an invisible property of the registration call, not the
channel name.
**How to avoid:** The two confirmed `send` channels this slice must register with
`ipcMain.on`/`addListener`, never `.handle`: `logoutSteam` (`main.ts:939`), `humbleDisconnect`
(`ipc_handler.ts:121`). Every other channel in this slice is a `handle`.
**Warning signs:** `logoutSteam` is this project's own canonical example (G-30-01) — the live
gate item 2 exists specifically because jest cannot distinguish "logged out" from "silently did
nothing" for a `send` channel with no reject path.

### Pitfall 5: The dev-only `humbleRunValidation` guard does not mean the same thing under Tauri
**What goes wrong:** `main.ts:969` gates `humbleRunValidation`'s registration behind
`if (!app.isPackaged)`. `electronStub.ts:178` hardcodes `isPackaged: false` **always** — the
sidecar has no real signal for "this is a packaged Tauri build" reachable through the Electron
`app` shim. Reusing the guard verbatim would register this dev-only validation trigger in EVERY
Tauri build, packaged or not — a real (if low-severity) behavioral divergence from Electron.
**Why it happens:** The stub impersonates Electron's `app.isPackaged` shape but has no
Tauri-native equivalent wired through it.
**How to avoid:** Either find a genuine packaged-vs-dev signal reachable from sidecar
registration code (candidate: an env var set differently by `main.rs`'s

```typescript
static async disconnect(): Promise<void> {
  invalidateSyncGeneration()
  // Credential wipe FIRST, synchronous, before any partition step can fail:
  configStore.clear()
  humbleLibraryStore.clear()
  humbleSyncStore.clear()
  // Best-effort partition wipe — EACH step individually try/caught, one
  // rejected Electron session call must not abort the rest:
  const ses = session.fromPartition(HUMBLE_LOGIN_PARTITION)
  const wipeSteps: Array<[string, () => Promise<unknown>]> = [
    ['clearStorageData', async () => ses.clearStorageData()],
    ['clearCache', async () => ses.clearCache()],
    ['clearAuthCache', async () => ses.clearAuthCache()],
    ['clearHostResolverCache', async () => ses.clearHostResolverCache()],
    ['clearData', async () => ses.clearData()]
  ]
  for (const [name, step] of wipeSteps) {
    try { await step() } catch (err) { /* log, continue */ }
  }
}
```
