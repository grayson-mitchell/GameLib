## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] Negative-scope guard test's inherited second `registerHumbleFlows()` call became unsafe**

- **Found during:** Task 3, while writing the total-registration-count test and reasoning about `ipcMain.on`'s push semantics.
- **Issue:** 34.4-04's version of the negative-scope guard test called `registerHumbleFlows()` a second time inside the test body, safe at the time because all 10 registrations were `ipcMain.handle` (map-overwrite semantics). This plan's `humbleDisconnect` registers via `ipcMain.on`, and `electronStub.ts`'s `on()` implementation (`listenerRegistry.get(channel) ?? []; listeners.push(listener)`) accumulates rather than overwrites. A second call would have stacked a duplicate `humbleDisconnect` listener for the remainder of the test file's process, causing `HumbleUser.disconnect()` to fire twice per `send` frame and corrupting every later "called exactly once" assertion in the file — exactly the hazard `clipboardFlowRegistration`'s own test docstring already names for modules that register listeners.
- **Fix:** Removed the second `registerHumbleFlows()` call; the registry state from the sole module-scope registration (already run via `handlers.ts`, reached through the file's own `import { init } from '../bootstrap'`) is sufficient to prove the negative-scope guard. Updated the test's comment to explain the hazard for future readers, mirroring `clipboardFlows.test.ts`'s own "registered once for this whole file" convention.
- **Files modified:** `src/backend/sidecar/__tests__/humbleFlows.test.ts`
- **Verification:** Full 35-test suite green with the fix in place; the added total-registration-count test asserts `humbleDisconnect`'s listener array has length exactly 1, which would have failed at 2 had the duplicate call remained.
- **Commit:** `f4315a72` (Task 3 commit)

**2. [Rule 1 - Bug] `plain require()` does not bypass a file-wide `jest.mock(...)` automock**

- **Found during:** Task 3, first attempt at the D-05 ordering proof.
- **Issue:** The first version of the D-05 ordering test used `require('../../humble/user')` (plain, dynamic) after `jest.resetModules()`, expecting it to return the real `HumbleUser` class. It did not — Jest's registered mock list persists across `resetModules()` (only the instantiated-module cache is cleared, not the mock configuration), so the dynamic require still resolved to a fresh instance of the SAME automock. The test failed immediately with `RealHumbleUser.disconnect()` returning `undefined` instead of a `Promise` — an automocked method's default return value, proving the automock was still active.
- **Fix:** Switched to `jest.requireActual('../../humble/user')`, the one call that genuinely bypasses a registered mock. Its internal imports (`electron` → real `electronStub`, `backend/logger` → the test's own scoped `jest.doMock`) still resolve through Jest's normal (and correctly still-mocked) module system, which is exactly the desired behavior.
- **Files modified:** `src/backend/sidecar/__tests__/humbleFlows.test.ts`
- **Verification:** Re-ran the D-05 ordering test — `HumbleUser.disconnect()` now genuinely executes, the three store `clear()` spies fire once each, and 5 partition-wipe-step warnings are observed (see below).
- **Commit:** `f4315a72` (Task 3 commit)
