Run the phase's **blocking** 5-item live gate under `pnpm tauri:dev` and record every result in
`34.4-LIVE-GATE.md`.

Purpose, stated specifically rather than inherited: **`logoutSteam` is the reason this gate exists.**
It is the G-30-01 channel — a `send` whose failure mode (`sidecar-send-channels-fail-silently`)
produces **no reject, no timeout and no console line**. It is structurally invisible to jest
assertions and it is already a known past defect in this codebase. The counter-argument that "these
channels have assertable return shapes, so unit tests suffice" is true for 14 of the 15 Steam channels
and **false for the one with a known past defect**. This slice therefore carries Phase 34.3's D-11/D-13
blocking-gate precedent rather than reverting to the 34.1 D-15 / 34.2 D-11 unit-only one.

The gate is deliberately narrow and scoped to **reversible** items. `redeemSteamKey` and
`steamBottleProvision` stay unit-proven and declared: the first burns a key irreversibly and cannot be
re-run on failure, the second downloads a real CrossOver bottle. **Phase 26's 5 deferred live-key UAT
items stay deferred and are explicitly NOT folded in.**

**Gate failure is BLOCKING (D-08).** A failed item means the phase does not close: findings become a
gap cycle inside Phase 34.4, exactly as Phase 33's D-13 gate surfaced and fixed three latent
Tauri-parity gaps in-phase. There is no advisory mode and no pre-authorized override path.

Output: `34.4-LIVE-GATE.md` with a pass/fail line and concrete observed evidence per item.

**D-10 — why there is deliberately NO packaged-build item, recorded so the omission reads as a
decision rather than an oversight.** Phase 34.3's D-12 required one because `main.rs` spawns a
different sidecar binary in dev vs packaged and `app.restart()` re-execs a different binary in each
mode — the question there was literally which child process gets killed. Nothing in this slice depends
on that path: these are login, sign-out, data reads and a status check, all build-independent. The
keyring path that genuinely does differ when the app is signed is already exercised by the previously
ported QR login. A full package cycle per gate re-run is expensive and would buy nothing here. Since
34.3 D-12 and the `publicdir-getapppath-chunking` family have made a packaged item the default
expectation, this rationale must appear IN the gate document.

**D-09 — item 4's numbered precondition.** There is **no Tauri path to create a Humble session** until
Phase 34.4.1 lands (the six browser-auth channels are deferred there). Both builds share the same
`appFolder` and the same encrypted `configStore` entry, so a session captured under Electron carries
across. This precondition is written into the gate as an explicit numbered step because **an unstated
precondition is exactly how a gate gets skipped and becomes UAT debt** — Phases 21, 30 and 34.2 each
did this.

**Item 5 advisory, flagged for whoever runs it.** A reviewed-but-deliberately-not-folded todo records
that Steam bottle setup offers GPTK/Wine engines that produce a broken bottle — GPTK is wine64-only
and aborts 32-bit executables (`phase-24-code-complete`). That is an **Electron-side behavior defect
in engine selection** and is explicitly out of scope for this transport-port slice. Do not fix it
here; equally, do not mistake it for a port regression.

**Known pre-existing automated failures that are NOT gate failures:**
`src/backend/sidecar/__tests__/rustInvokeChannel.test.ts` (a Phase 34.1-era documented baseline) and
the wine `rest.test.ts` path-depth bug. A non-deterministic `library.ts` leaked-timer flake can also
land on an arbitrary suite — re-run any failing suite in isolation before recording it as real.

**What is deliberately NOT tested live (D-08), for the tester's awareness:** `redeemSteamKey` (burns a
key irreversibly) and `steamBottleProvision` (downloads a real bottle). Do not run either. Both carry
declared unit-only rows in `34.4-PORTED-CHANNELS.md`.
