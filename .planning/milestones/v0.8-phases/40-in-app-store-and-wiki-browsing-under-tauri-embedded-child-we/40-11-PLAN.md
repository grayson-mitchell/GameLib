<planning_findings>
1. **Build the packaged binary, not the dev shell.** A debug build runs the sidecar from source rather
   than the packaged single executable, and this project has already shipped a defect that was
   invisible in the dev shell. Also: the dev command exits 0 without replacing a running instance, so
   a stale process can silently serve the whole run. Kill every existing instance and verify the kill
   before launching, and record the build command and the binary's timestamp.

2. **Screenshot the WINDOW, not the screen.** Full-screen capture repeatedly missed the app window in
   the spike sessions — wrong display, occlusion, unrelated windows swept in. Capture by window id.
   And capture files must not be dotfiles: the capture tool writes nothing to a dotfile and exits 0,
   which produces a run with no evidence and no error.

3. **Pixel-measure, do not eyeball.** Project memory records two occasions where "no layout shift"
   judged from screenshots was wrong. Any geometry claim in this gate — the embed sitting exactly in
   the slot, the placeholder occupying the same rect, no shift on hide or show — must be backed by
   measured pixel coordinates from the capture, compared against the slot's own reported bounding
   rect. State the tolerance and justify it: at scale factor 1.0 the spike measured integer px
   round-tripping exactly and fractional CSS px rounding to the nearest whole logical px, so the
   tolerance is one logical pixel, not "looks right".

4. **Do not drive the web inspector console.** It has been observed wedged and unpasteable on this
   project, and a wedged console runs nothing while looking like it ran something. If renderer state
   must be read, read it from the on-disk store directly rather than through the inspector.

5. **The two open questions are subjective by nature and must be scored as such.** Input and scroll
   feel, and drag-resize latency, cannot be reduced to a threshold the agent can assert. The human
   gives a verdict; the agent's job is to make the gesture unambiguous, capture what is capturable
   (frame timing, a screen recording, the measured resize duration), and record the verdict verbatim
   without paraphrasing it into a pass.

6. **The macOS result must not be allowed to close the Phase 38 items.** Plan `40-10` filed
   non-macOS versions of the retina, drag-resize and backend questions in Phase 38's ledger with an
   anti-conflation note. This gate's artifact must carry the matching statement from its own side, so
   the non-closure is recorded in both places rather than depending on a reader finding one of them.

7. **`autonomous: false`.** Two of the three items need a human on real hardware, and the third needs a
   human to perform a gesture and judge a visual outcome. This plan pauses. Do not let an auto-advance
   mode answer its own checkpoint — that failure mode is recorded in this project's tooling notes.

8. **Score by requirement PAIR, not only per item.** The live-gate contract reference's fifth test asks
   whether satisfying one requirement destroys another's evidence. Here the obvious pair is the
   suppression gesture and the geometry measurement: hiding the embed removes the thing being measured,
   so the geometry evidence must be captured BEFORE the overlay opens and again after it dismisses,
   not once.
</planning_findings>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| live run → recorded result | A run's evidence is the only thing a later reader has. Evidence that was never captured, or captured from the wrong window, produces a result indistinguishable from a real one. |
| subjective verdict → recorded status | A human's qualified report can be silently upgraded into an unqualified pass by paraphrase. |
| macOS result → non-macOS ledger | A passing macOS gate can be read as closing a non-macOS item unless the non-closure is stated on both sides. |
