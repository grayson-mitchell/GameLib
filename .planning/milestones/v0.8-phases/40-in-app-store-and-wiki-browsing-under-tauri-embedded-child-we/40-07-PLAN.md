<objective>
Rebuild the browser chrome against inverted control: back and forward availability become state Rust
reports, not something the renderer can synchronously ask a handle for.

Purpose: the retired controls bar called `webview.canGoBack()` on a live DOM handle. Under
`add_child` there is no such handle in the renderer and — per the vendored-source verdict — no
`go_back` on the Rust side either. So the chrome is rebuilt, not ported. The hard constraint is
D-22's: ZERO page-side JS injection, because document-side injection is the confirmed fingerprint
vector from the 2026-08-03 Talon root-cause. That rules out the obvious shortcut of evaluating a
history call in the page.

Output: four Rust navigation arms, their seam implementations, and a chrome component that receives
its whole state as props.
</objective>

<planning_findings>
1. **The D-25 verdict measured at plan time: no native history API exists.** `tauri::webview::Webview`
   in 2.11.5 exposes `url()`, `navigate(Url)`, `reload()`, `eval()`, `hide()`, `show()`, `close()`,
   `set_position()`, `set_size()`, `position()`, `size()` — and no `go_back`, `go_forward`,
   `can_go_back` or `can_go_forward`. `wry-0.55.1`'s `WebView` is the same: `load_url`,
   `load_url_with_headers`, `load_html`, `reload`. **So D-22 stands.** But read
   `40-EMBED-API-VERIFICATION.md` first and follow ITS verdict, not this note — plan `40-02` Task 1
   is the authority and may have found something this plan-time scan did not.

2. **The retired bar's dead pattern, for contrast only.** It held `webview: WebviewTag | null`,
   subscribed to `did-navigate` and `did-navigate-in-page`, and called `webview.canGoBack()` /
   `canGoForward()` synchronously inside those listeners to drive two state flags. None of that has
   an equivalent. Do not port it. The structural sibling to copy instead is the Tauri login panel,
   which receives its whole state as a prop rather than deriving it from a live handle.

3. **What IS reusable from the retired bar**: the JSX layout, the icon set, the existing translation
   keys `webview.controls.back` / `.forward` / `.reload` / `.openInBrowser` (in the default
   namespace — they already exist and are already localised, so REUSE them rather than minting
   duplicates in `gamelib.json`), the block-element class-naming convention, and the
   open-in-browser button's escape-hatch call shape. Any NEW string this plan mints — a host-display
   label, an accessibility label — goes in `gamelib.json` (D-37).

4. **`on_page_load` reports main-frame loads.** Plan `40-02` already wired it to push into the
   history registry. This plan adds the cursor semantics: a back or forward navigation must move the
   cursor rather than pushing a new entry, or every back press would append and the stack would grow
   forever while never actually going back. That distinction is the whole correctness of the feature
   and is the first thing to test.

5. **Accepted cost, recorded in D-22 and worth restating in the component's doc comment**: in-page
   state and scroll position are NOT restored the way true browser history would restore them,
   because a back press is a fresh navigation to a recorded URL. Say so in the code, so the next
   reader does not file it as a bug.

6. **D-23's host-only display is security-relevant, not merely tidy.** The user needs to know which
   origin the native view is showing. The retired bar showed the full URL including affiliate and
   session parameters. Show the host. Keep the retired bar's insecure-scheme warning treatment: a
   host reached over a non-https scheme must be visually distinguished, because that is exactly when
   knowing the origin matters most.
</planning_findings>

Add four dispatch arms: `store_embed_back`, `store_embed_forward`, `store_embed_reload`,
`store_embed_navigate`, matching the channel-name constants plan `40-05` already minted. All are
macOS-gated with the rest of the embed and all return a legible error on the non-macOS path.

Give the registry cursor semantics. The critical distinction: a back or forward navigation must MOVE
the cursor, not push a new entry. `on_page_load` currently pushes unconditionally — it must now
distinguish a user-initiated navigation (push, and truncate any forward entries beyond the cursor,
exactly as a browser does) from a history-driven navigation this code itself issued (move the cursor,
do not push). Implement that with a one-shot suppression flag set by the back/forward arms and
consumed by the next main-frame load. Without it, every back press appends and the stack grows
forever while never actually going back.

`store_embed_reload` calls the webview's reload and must NOT push a history entry.

`store_embed_navigate` is the arm the deep-link and route-change paths use in plan `40-09`. It pushes
and truncates forward entries, like a user-initiated navigation.

Every arm returns the navigation state the seam's read expects: the current URL, its host, and back
and forward availability derived from the cursor's position in the stack. Deriving availability from
the cursor is the whole point — there is no handle to ask.

ZERO page-side JS injection. Do not call `eval` and do not evaluate a history call in the page. The
2026-08-03 Talon root-cause identified document-side injection as the confirmed fingerprint vector,
and D-22 makes this a hard rule rather than a preference. Write that as a comment on these arms so a
future reader reaching for `eval` is told why not, in place.

Add Rust unit tests for the registry's cursor logic, driven purely through the registry's own methods
with no webview: push three URLs, go back twice, assert the cursor and the derived availability; go
forward once, assert; push a new URL from the middle of the stack and assert the forward entries were
truncated; reload and assert the stack is unchanged. These are pure state-machine tests and must not
need a running app.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| store page → the URL shown in the chrome | The current URL originates from a remote page's navigation, including redirect chains the page controls. It is displayed to the user as an origin signal. |
| Rust history stack → embed navigation | A back press causes the app to navigate the embed to a URL the stack recorded from a remote page's own navigation. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-40-07-01 | Spoofing | the chrome's URL display | mitigate | D-23: display the host only. A full URL invites a spoofing page to pad a long path so the real origin scrolls out of a fixed-width field. The host is short, always visible, and is the security-relevant part. A test asserts the query string is absent from the rendered output. |
| T-40-07-02 | Spoofing | a non-https origin shown as if trusted | mitigate | The insecure-scheme warning treatment is carried over from the retired bar and asserted by a test in both directions. |
| T-40-07-03 | Elevation of Privilege | page-side JS injection to drive history | mitigate | D-22 forbids it as a hard rule: document-side injection is the confirmed Talon fingerprint vector from the 2026-08-03 root-cause. Task 1 asserts no eval in the store-embed path and requires an in-place comment explaining why. |
| T-40-07-04 | Tampering | a history entry recorded from a page-controlled redirect | accept | The stack records main-frame URLs the embed actually loaded, so a back press can only return to a URL the user already visited. Navigating there re-applies the scheme policy from plan `40-04`, so a recorded entry cannot bypass containment. Recorded as accepted with that reasoning. |
| T-40-07-05 | Denial of Service | the history stack growing without bound | mitigate | Task 1's one-shot suppression flag makes a history-driven navigation move the cursor rather than push, and a push from mid-stack truncates forward entries. A state-machine test proves the append defect fails before the flag is added. |
| T-40-07-06 | Denial of Service | the store screen crashing on a malformed URL | mitigate | The host display returns empty rather than throwing on an unparseable URL, asserted by a test. A throw in the chrome would take the whole store screen down. |
| T-40-07-SC | Tampering | npm/pip/cargo installs | mitigate | This plan adds no package; the icon set and button component already exist. If either lockfile changes, stop for a blocking package-legitimacy checkpoint. |
</threat_model>
