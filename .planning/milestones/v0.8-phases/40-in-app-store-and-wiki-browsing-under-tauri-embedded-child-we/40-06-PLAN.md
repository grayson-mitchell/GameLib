<objective>
Build the one reference-counted suppression context every overlay routes through, the placeholder
that fills the slot while the embed is hidden, and wire both to the known overlay consumers.

Purpose: the embed is a native subview composited above the entire web layer. DOM stacking contexts
do not reach it, so this is not a z-index problem that CSS can solve. D-18 chose one rule — overlay
opens, embed hides — over "reserve a rect overlays avoid", because the latter would make every
present and future overlay's layout depend on the embed's position, failing silently the first time
an author forgets. D-20 makes the rule structural: an overlay acquires suppression by mounting.

Output: a context with an acquire hook, a placeholder component, and five wired consumers. The embed
host in plan `40-08` subscribes to this context; this plan does not touch the host or the WebView
screen.
</objective>

<planning_findings>
1. **No React context in this frontend does reference counting today.** `Tier2PortalContext` is a
   single-target, single-flag context — not a counter. The closest counted shape in the whole repo is
   Rust-side: an id-keyed registry behind one mutex with allocate / forget / holds methods. Its
   SHAPE translates ("pure bookkeeping; every mutation through one lock; the query answers 'is at
   least one still live'"), its domain does not. Build the counter fresh.

2. **The known consumers at ship time are five**, and each must be verified to still exist before
   wiring, because a wiring plan written against a stale component list produces silent gaps:
   `LoginWarning` (via the shared `Dialog`), the adtraction `Dialog` (also via the shared `Dialog`),
   NavShell's tier-2 portal dropdowns, the Humble expiry toast, and the onboarding tour.
   Wiring the shared `Dialog` component itself covers BOTH dialog consumers in one place, which is
   strictly better than wiring each call site — a call-site wiring is exactly the "author remembers"
   failure D-20 rejects.

3. **D-16 is already structurally satisfied and must not be regressed.** `LoginWarning` receives
   `warnLoginForStore` from state derived in the WebView screen from GameLib's own per-runner auth
   fields — the Epic username, the GOG username, the Amazon user id, the Zoom username. It does not
   parse cookies and must not start: the shared jar holds every store's session, and a per-store
   cookie heuristic would rot. This plan's obligation is to leave that derivation alone while adding
   suppression, and to record that it was checked.

4. **The tour has known paint pathology under WKWebView.** Project memory records that a visible
   child of a hidden ancestor is not painted but is still hit-tested, and that tour anchors have
   repeatedly broken silently. The tour's acquire must therefore key off the tour being ACTIVE, not
   off a single step's element being mounted — D-20's reference counting is what lets a multi-step
   lifecycle hold one acquisition across step transitions instead of releasing and re-acquiring
   between every step, which would make the embed flicker.

5. **Strict-mode double-invocation is a real hazard for a counter.** React 18 development mode mounts,
   unmounts and remounts effects. A naive increment-on-mount / decrement-on-unmount counter survives
   that correctly only if the effect's cleanup is symmetric and the acquire is keyed per hook
   instance rather than per component name. Test it explicitly rather than assuming.

6. **The placeholder needs no props and no button.** It is pure decoration matching the app surface
   while the embed is hidden. Follow the hookless static-panel convention its sibling panels in the
   same directory use — no hooks besides the translation hook, invocable as a plain function, with a
   DOM-less test. Keep the sibling panels' block-element class-naming convention.

7. **New strings go in `gamelib.json`, never `translation.json`** (D-37), and no gate catches a
   violation — the lint gate is blind to an absent key. The placeholder's string is minted here.
</planning_findings>

Create `StoreEmbedSuppressionContext.tsx` exposing a provider, a read hook and an acquire hook.

The provider holds a reference count. It exposes `suppressed`, which is true when the count is above
zero, plus acquire and release functions. Model the internal state on the Rust registry's shape: pure
bookkeeping, every mutation through one code path, and a single derived query. Use a reducer or a
ref-backed counter rather than raw `useState(count + 1)` arithmetic in a callback — concurrent
acquisitions from separate components must not lose an increment to a stale closure.

Reference counting is the requirement, not an optimisation: nested overlays (a dialog opened from a
dropdown) and the multi-step tour must compose. Releasing on the first unmount while a second overlay
is still open would un-hide the embed underneath a live modal, which is the exact user-visible defect
D-18 exists to prevent.

The acquire hook takes no arguments and acquires for the lifetime of the calling component: acquire
on mount, release on unmount, with a symmetric effect cleanup. Give each hook instance its own
identity so two instances of the same component each hold their own count. React 18 strict mode
mounts, unmounts and remounts effects in development — the cleanup must be exactly symmetric or the
count drifts negative or positive. Clamp the floor at zero and log a warning through the app's own
logging path if a release would take it below zero: that is a wiring bug and must be legible rather
than silently absorbed.

Write the file's doc comment in the style `Tier2PortalContext.tsx` uses — explain WHY the seam
exists before explaining what it does. State plainly that the embed is a native subview above the web
layer, that DOM stacking contexts do not reach it, and that this is therefore not a z-index bug that
CSS can fix. Without that paragraph a future reader will try to solve it with a z-index.

Mount the provider in `NavShell/index.tsx` high enough that every overlay in the app is inside it,
and note in a comment which subtree it must enclose. A consumer outside the provider falls back to
the default value and silently no-ops, which is exactly the hazard `Tier2PortalContext`'s own doc

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| app UI → native subview compositing | The embed renders above the entire web layer. Any app UI drawn over its rect is invisible to the user while still being hit-tested — a user can click a control they cannot see, or believe a modal is dismissed when it is merely occluded. |
| overlay author → suppression contract | If suppression is opt-in per call site, a future overlay ships without it and the failure is visual and silent. |

|-----------|----------|-----------|-------------|-----------------|
| T-40-06-01 | Spoofing | app UI occluded by the embed | mitigate | D-18's one rule, enforced structurally: the shared Dialog acquires by mounting, so an overlay cannot ship without suppression by forgetting a call. A user can never be shown a control that is invisible-but-clickable behind the embed. |
| T-40-06-02 | Denial of Service | reference-count drift | mitigate | A count stuck above zero leaves the embed permanently hidden; stuck below zero un-hides it under a live modal. Task 1 clamps the floor at zero, logs a warning on an underflow, and proves symmetric acquire/release under strict-mode double-mounting. |
| T-40-06-03 | Repudiation | consumer rendered outside the provider | mitigate | The default context value's acquire logs a warning instead of no-opping silently — the same class of hazard `Tier2PortalContext`'s doc comment records for a different context, where a no-op default made every interaction silently swallowed while nothing threw. |
