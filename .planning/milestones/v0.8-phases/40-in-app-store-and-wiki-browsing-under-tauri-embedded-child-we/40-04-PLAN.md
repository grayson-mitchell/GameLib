Read this section before writing a line. Finding 1 is a CORRECTION to D-26 measured against vendored
crate source at plan time, and it changes what the capability assertion must assert.

1. **D-26's stated control is verifiable but is NOT the control that actually holds.** D-26 says the
   assertion is "no capability lists the embed label or store origins". Measured against
   `tauri-utils-2.9.3/src/acl/capability.rs:150-163` and `tauri-2.11.5/src/ipc/authority.rs:459`:

   - `resolve_access` allows a command when the origin matches the command's execution context AND
     either the command's webview patterns match the webview label OR its window patterns match the
     window label. The window and webview legs are ORed.
   - The `windows` field's own doc comment states: *"If a window label matches any of the patterns in
     this list, the capability will be enabled on all the webviews of that window, REGARDLESS of the
     value of `webviews`. On multiwebview windows, prefer specifying `webviews` and omitting
     `windows` for a fine grained access control."*
   - `src-tauri/capabilities/default.json` is scoped to the `main` window with no webview key, and
     the store embed is a child webview OF the `main` window.

   **Therefore the embed DOES match `default.json` on the window leg**, and "no capability lists the
   embed label" is true but irrelevant. What actually holds the line is the ORIGIN leg:
   `Origin::matches` at `authority.rs:57-67` returns true only for a Local origin against a Local
   context, or a Remote origin against a Remote context whose URL pattern tests the URL.
   `default.json` declares no remote key, so all its resolved commands carry a Local context and a
   remote store origin matches NONE of them.

   **The correct assertion is a CONJUNCTION and the plan must assert both halves:**
     (i) NO capability file declares a remote-url grant at all — this is what denies eligibility;
     (ii) `default.json` is scoped so the embed does not inherit the `main` window's grants via the
          window leg, per the crate's own recommendation.
   Half (i) is the primary control. Half (ii) is defence-in-depth: today it changes nothing
   observable, but it means a future capability that DOES declare a remote grant cannot silently
   extend to the embed.

2. **`tauri.conf.json` declares the main window with label `main`**, and a config-created window's
   primary webview carries the same label — so a webview-scoped form is expected to be equivalent.
   VERIFY that against a running app before committing to it. Getting it wrong breaks every renderer
   window-chrome call and fails at runtime with an ACL rejection the renderer swallows. Half (ii) is
   an improvement, not a requirement: if verification shows the swap changes observable behaviour,
   KEEP the window scoping and record the falsification. Do not ship an unverified scoping change.

3. **The three containment hooks exist as first-class builder methods in tauri 2.11.5**, verified at
   plan time and re-verified by plan `40-02` Task 1 Q6:
   - `WebviewBuilder::on_navigation` takes a closure returning `bool`; returning `false` blocks the
     navigation. It fires for subframes too — which for a BLOCKER is a feature, not the hazard the
     013-015 rule names. That rule forbids `on_navigation` for DEADLINE-ARMED RELAYS, where a
     subframe could re-arm a deadline forever. Scheme blocking has no deadline. This distinction is
     load-bearing: D-29's control belongs in `on_navigation`, D-22's history belongs in
     `on_page_load`.
   - `WebviewBuilder::on_new_window` returns a `NewWindowResponse` with variants `Allow`,
     `Create { window }` and `Deny`. Documented unsupported on mobile; desktop only.
   - `WebviewBuilder::on_download` takes a closure returning `bool`; returning `false` prevents a
     requested download.

4. **D-15's tool already exists and is better than the one PATTERNS.md suggests.**
   `clear_default_data_store_cookies_for_domain(app, domain)` at `src-tauri/src/main.rs:3775` is
   label-independent (needs no window handle), clears at default-data-store level, and — critically —
   measures the delete with an INDEPENDENT all-cookies re-read before and after, reduced through

   second domain comparator — `cookie_domain_matches` at `main.rs:1823` is, per its own doc comment,
   deliberately the only one in the project.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| remote store origin → Tauri IPC | The Tauri global is injected into remote pages (spike 014b). Remote origins get eligibility only via a capability remote-url grant, which no capability declares. |
| remote store origin → OS | `window.open`, downloads and custom URL schemes are the three ways a store page reaches outside the webview. |
| store embed → shared cookie jar | One jar per process holds every store's session and is readable from any webview handle, including the embed's. |
| renderer → Rust logout path | The logout path deletes credentials and cookies; a partial failure that skips the credential is a security regression, not a cosmetic one. |

## STRIDE Threat Register
