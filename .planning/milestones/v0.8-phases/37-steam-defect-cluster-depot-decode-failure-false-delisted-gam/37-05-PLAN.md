<objective>
Stop a terminal Steam install failure from logging an ERROR that describes a bug that is not
happening, without going blind to the ERROR that describes one that is.

Purpose: Immediately after a terminal Steam install failure, in the same millisecond block:
```
[INFO]  [DownloadManager]: Aborting in-flight download for 259130 after terminal install failure
[ERROR] [Backend]: Aborting not possible. Could not find a matching abort controller for 259130
```
Logged at ERROR, so it is not a cosmetic notice — it sends the next reader looking for a teardown
race that is not there. It also fired on a plan-build failure that aborted in 1ms before any
download started, and again on a second click 16s later.

Output: an honest log line at the terminal-failure call site, `callAbortController` untouched for
every other caller, and a test pinning that user-cancel still aborts.

**The recorded first check is already answered and is NOT open.** `downloadqueue.ts`'s
`stopCurrentDownload()` calls `callAbortController(appName)` and
`libraryManagerMap[runner].getGame(appName).stop(false)` synchronously, back-to-back, with no
intervening `await` — by the time a user can click Cancel, the download and therefore its controller
registration already exist. User-cancel is a different, unaffected path. This plan pins that with a
test rather than re-investigating it.
</objective>

<competing_hypotheses>
`37-RESEARCH.md` names ONE mechanism: the controller is NEVER REGISTERED, because
`createAbortController` lives only inside `runNativeDepotDownload` and a pre-download throw in
`SteamGame.install()` reaches `utils.ts`'s unconditional `callAbortController` first.

Reading `games.ts` at plan time surfaced a SECOND, competing mechanism the research does not name:
`runNativeDepotDownload`'s own `finally` calls `deleteAbortController(this.appId)` (~:1738) before
its returned `InstallResult` ever reaches `installQueueElement`. On that path the controller WAS
registered and is then deleted — which is precisely the case `aborthandler.test.ts:72` already
classifies as "a genuine miss". This mechanism would explain EVERY terminal Steam install failure,
including the observed 1ms plan-build one (`buildDepotPlan` throws inside `downloadSteamDepots`,
which is inside `runNativeDepotDownload`, which registered the controller on its first line).

**Do not assume either.** A code-read PREDICTION in this repo once outlived its own same-day fix by
three days, read like an observation, failed a row, and misdirected a whole session. Task 1
MEASURES which mechanism fires and records the answer. The fix in Task 2 is correct under both, so
the measurement is for the ledger, not for choosing the fix.
</competing_hypotheses>
