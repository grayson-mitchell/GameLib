<objective>
Convert the Steam sign-in from the sibling route `loginweb/steam` into a co-mounted overlay on
`/login`, install the explicit `loginInFlight` guard that replaces the incidental unmount, and add
the crossfade motion — all in one plan, because they are one change.

Purpose: ROADMAP.md's Phase 36 goal plus its three coupled obligations. The navigation is what
unmounts the Login screen; that unmount is simultaneously (a) the reason there is no second surface
to cross with, and (b) the entire current frontend mitigation for T-34.4.2-39 and T-34.4.2-41. You
cannot remove it for the animation without replacing it for the security, and the operator approved
that trade on 2026-08-20.

Output: `SteamLogin` dismisses through a callback prop; `Login/index.tsx` owns the overlay lifecycle
and the guard; `loginweb/steam` is deleted; `Login/index.scss` carries the crossfade; three source
gates updated or created.

WHY THIS IS ONE PLAN AND NOT THREE. An earlier draft split this across three waves. That split
MANUFACTURED an interval in which the mitigation this phase exists to preserve was simply absent —
the route was gone but the guard had not landed — and made phase correctness depend on nobody
stopping between waves. Merged, the removal of the unmount (Task 2) and the installation of the
explicit guard (Task 2) happen in the SAME task, so the window is closed by construction and does not
exist even between commits. The three source files involved were also strictly serial anyway:
`Login/index.tsx` was edited by two of the three plans and `Login/index.scss` by two, so the split
bought no parallelism and cost three chances at inconsistent edits to the same file.

TASK COUNT NOTE FOR THE EXECUTOR: this plan carries five tasks rather than the usual two or three.
That is a deliberate, operator-approved consolidation, not an oversight. Tasks 1-3 are small and
tightly scoped; Tasks 4 and 5 are the mutation-proof-heavy ones. If context pressure builds, commit
after each task and continue — do NOT drop the falsifiability work to save room, and do not
"simplify" any task's scope.

<locked_decisions>
- **React 18 `inert` form.** This project pins `react@^18.3.1` / `react-dom@^18.3.1` (verified,
  `package.json` lines 116-117). Boolean `inert` landed in React 19 (facebook/react PR #24730); on
  React 18 the boolean form silently renders `inert="true"` and `inert={false}` emits a "Received
  `false` for a non-boolean attribute" console warning. REQUIRED FORM:
  `inert={loginInFlight ? '' : undefined}`. `36-PATTERNS.md` line 253 recommends the boolean form and
  claims "React 19/18 both support it natively" — that claim is WRONG for this project's pinned
  version. Operator-locked; do not revisit.

- **`tabIndex={-1}` — LOCK DROPPED 2026-08-20. DO NOT REINSTATE IT.** The operator originally locked
  a defensive `tabIndex={-1}` on the panel for the macOS 12.0–12.3 slice, on the assumption that the
  login tiles were focusable. That premise was then disproved from source (point 3 of the guard-layer
  analysis above: the tiles are bare `<div onClick>` with no `tabIndex` and no `role`, already
  outside the tab order), and separately `tabIndex={-1}` on a container does NOT remove its focusable
  descendants — so it protected nothing. The operator retired the lock on that basis. What actually
  holds on that slice is MUI's Dialog focus trap. Do NOT add `tabIndex` to `.loginContentWrapper`,
  and do not let a future pass "helpfully" reinstate it. The `Runner/index.tsx` focusability-premise
  assertion in Task 4 replaces it and is the thing that must go RED if those divs ever become real
  buttons.

- **No `aria-hidden`.** `aria-hidden` on a container holding focusable children is only safe when
  focus is provably managed. `inert` already removes the subtree from the accessibility tree where
  supported; on the slice where it is not, `aria-hidden` would hide the panel from assistive
  technology while `goToLibrary` and the `LanguageSelector` inside it remain focusable — the exact
  ARIA violation. Omit it and record the reason in a code comment at the site.

- **View Transitions API is OUT.** WebKit shipped it in Safari 18 (macOS 15+); this app's `oldMac`
  floor is macOS 12 (`Login/index.tsx:79-89`). `document.startViewTransition` is simply undefined
  there. Use plain CSS `transform`/`opacity` transitions on a state-toggled class. Operator-locked.

- **The motion MUST be a CSS `transition` (or `animation`) property.** A raw JS style mutation with no
  CSS transition property is structurally invisible to `App.css:116`'s global override and would
  silently break the in-app "disable animations" accessibility toggle. Implementation constraint, not
  a preference.

- **Do NOT add a `@media (prefers-reduced-motion: reduce)` rule.** 36-RESEARCH.md floats it as
  optional. Declining it: the codebase honours zero such queries today, so one scoped rule would
  imply partial support that does not exist, and the `disableAnimations` toggle already covers this
  transition completely. A deliberate non-goal, not an oversight.
</locked_decisions>
