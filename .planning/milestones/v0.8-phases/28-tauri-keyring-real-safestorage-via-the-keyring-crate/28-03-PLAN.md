<objective>
Introduce the `TokenStore` seam (D-09) so the Steam refresh token has exactly one owner module,
and route `user.ts`'s three token call sites through it. The Electron implementation moves the
existing `encryptionAvailable`/`encryptToken`/`decryptToken` bodies verbatim — behavior stays
byte-identical.

Purpose: this is the "by construction" half of D-04/REQ-28-02. After this plan, `TOKEN_STORE_KEY`
and `configStore` token access live in ONE module; plan 28-04's sidecar implementation is a
sibling that structurally cannot reach them. REQ-28-03 (no migration) is asserted here too: no code
path copies an Electron-stored token toward a keyring.

Output: `tokenStore.ts`, a refactored `user.ts`, and Wave 0 unit coverage.

**D-11 decision (planner's call): Electron's plaintext fallback is KEPT, not removed.**
`ElectronTokenStore.setToken()` retains the existing warn-then-store-plaintext behavior when
`safeStorage.isEncryptionAvailable()` is false, and `getToken()` retains the legacy non-prefixed
plaintext read. Rationale: REQ-28-07 requires the Electron build's behavior stay byte-identical
and that no existing user is silently signed out; removing the read fallback would sign out anyone
holding a legacy plaintext token, and removing the write fallback changes shipped Electron
behavior for zero benefit to this phase's goal. The divergence from D-06 is intentional and must
be documented in a comment so it does not read as a bug — the sidecar implementation (28-04)
categorically has no plaintext path.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Steam auth flow → persistent token storage | Session-equivalent credential material crosses into on-disk storage |
| Electron build ↔ sidecar build over a SHARED `configStore` file | Two processes with different crypto capabilities address the same store file (`pathShim` resolves `userData` to the same folder) |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-28-01 | Tampering | shared `configStore` `TOKEN_STORE_KEY` corrupted by a non-Electron writer, silently signing the real user out | mitigate | Structural containment: `TOKEN_STORE_KEY` and `configStore` token access exist in exactly one module (`tokenStore.ts`) reachable only through `ElectronTokenStore`. Enforced by the grep acceptance criteria in Task 2 (zero `TOKEN_STORE_KEY` in `user.ts`) and by 28-04 giving the sidecar a sibling implementation with no import of this key. Byte-comparison proof lands in plan 28-05. |
| T-28-02 | Information Disclosure | Electron plaintext fallback in `ElectronTokenStore.setToken()` | accept | Pre-existing shipped behavior, deliberately preserved per the D-11 decision above; removing it would silently sign out users holding a legacy token and would violate REQ-28-07's byte-identical-Electron constraint. Documented in the module docstring and asserted in tests so it reads as intent, not a defect. The sidecar implementation (28-04) has no equivalent path. |
| T-28-08 | Tampering | an untrusted caller invoking `setTokenStore()` to redirect token writes | accept | `setTokenStore` is a module-private-by-convention backend export with no IPC/renderer surface; the renderer cannot reach it (no `window.api.*` change, REQ-28-07). Any caller already has full in-process backend privileges. Logged on call so a swap is observable. |
| T-28-04 | Information Disclosure | token value in logs | mitigate | No new log statement includes the token; the only preserved warning names the condition, not the value. Tests assert the warning string, not a token value. |
