<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| renderer(webview) → sidecar | `setSetting`/`writeConfig` payloads (`appName`, `key`, `value`, `config`) cross from the untrusted webview into the Node sidecar over the RPC transport |
| sidecar → filesystem | per-game write is a raw `graceful-fs writeFileSync` at `join(gamesConfigPath, appName + '.json')`; global write goes through `configStore` |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-31-01 | Information disclosure / Tampering | `setSetting`/`writeConfig` → configStore | mitigate | Write path is confined to the config domain (`GlobalConfig`/`GameConfig.setSetting`); secrets travel a separate keyring/safeStorage path (Phase 28) and are never routed through setSetting. Task 1 asserts a normal settings key never passes `TOKEN_STORE_KEY` into configStore. `SECRET_STORE_KEYS` deny-list stays fail-closed (Phase 28 D-04). Severity: medium. |
| T-31-02 | Tampering | per-game raw write `join(gamesConfigPath, appName + '.json')` | mitigate | `appName` originates from the in-memory library Map / `libraryManagerMap`, not free-form user input (matches Electron parity, unchanged behavior). Type-guard rejects non-string `appName`/`key` before any write (Task 1). Traversal via a crafted `appName` is not reachable from any in-scope Settings caller; a defensive `appName`-known-entry check is noted as a Phase 33 hardening follow-up, not required here. Severity: medium (not high — no in-scope caller supplies attacker-controlled `appName`). |
| T-31-SC | Tampering | npm/cargo installs | accept | No new packages this phase (RESEARCH Package Legitimacy Audit: nothing to audit). No supply-chain surface added. |
</threat_model>
