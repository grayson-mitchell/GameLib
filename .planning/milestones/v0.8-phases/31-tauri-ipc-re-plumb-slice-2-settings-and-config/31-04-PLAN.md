CR-01: under the Tauri build, `dialog.showMessageBox` forwards a multi-button
confirm to an OK-only Rust dialog whose `blocking_show()` always returns `true`,
which `electronStub.ts` maps to `response: 0` — auto-confirming destructive
backend flows (`promptI386Recovery` force-uninstall+reinstall, `askForceUninstall`
remove-from-library) reachable via the already-shipped Phase-30 install path.

Remedy (user-locked): **DE-WIRE showMessageBox to a safe, non-destructive
sentinel that it RESOLVES (never rejects, never forwards to RUST_DIALOG_MESSAGE)**,
NOT implement the multi-button contract. The plan-checker proved a reject-based
de-wire would introduce a WORSE regression — a hard sidecar crash: the two live
callers (`promptI386Recovery` at library.ts:1265, fire-and-forget `void ...` at
:1236; `askForceUninstall` at utils.ts:292, reached fire-and-forget from
launcher.ts:1850/:1924) `await dialog.showMessageBox(...)` with NO try/catch and NO
`.catch()`, and the sidecar is plain `node` with NO `process.on('unhandledRejection')`
guard — so an always-rejecting showMessageBox unhandled-rejection-crashes the
process the first time a user hits the mac32-recovery or game-folder-deleted path.
Today's stub "never throws"; that safety must be preserved.

The safe sentinel is `{ response: -1, checkboxChecked: false }`: `promptI386Recovery`
declines on `response !== 0` and `askForceUninstall` declines on `response !== 1`, so
`-1` declines BOTH. `handleExit`'s inverted sense (`response === 0` = safe "No") is
moot: it is wired in `main.ts` via `app.on('before-quit')`, and `main.ts` is NOT in
the sidecar's curated import graph — `electronStub.ts`'s `app.on` is an inert no-op —
so handleExit never runs under the sidecar. Real multi-button `showMessageBox`
behavior is deferred to Phase 33.

WR-01: add a `resolve`+`relative` path-containment guard to the per-game write
branch of `setSetting` and `writeConfig`, mirroring the guard `storeLayer.test.ts`
already asserts for the store-fetch path.

Purpose: no destructive dialog auto-confirms without real user consent under Tauri
AND no crash-on-decline; per-game config writes are path-contained; both builds still
build; the docs stop claiming the dialog cluster is safely closed.
Output: de-wired (safe-sentinel-resolving) showMessageBox, containment guard,
updated/added tests, corrected SEAM.md / 31-PORTED-CHANNELS.md / REQ-31-03 status.

WR-02 (writeConfig type guard) and WR-03 (dialog_save directory drop) are OUT OF
SCOPE per the user — they remain accepted/deferred WARNINGs; no tasks here.
