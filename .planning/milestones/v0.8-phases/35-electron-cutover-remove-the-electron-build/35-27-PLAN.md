<objective>
Close live-gate criterion 16, the fourth and last FAIL. Its cause is `F-35-08-A` /
`D-35-08-02`: the download's `PreventUserIdleSystemSleep` assertion, labelled
`"GameLib: a download is in progress"`, is never released while a game is running — it outlived the
download it names by ~108 seconds on the packaged artifact, and cleared only when the GAME exited.

The mechanism is established in source, not inferred: `allowedPendingOps` contains BOTH `'launching'`
and `'playing'`, so a launch raises `pendingOps` to 1 while `playing` is still `false`, the
`!playing && !isSleepBlocked` branch fires, and `powerSaveBlocker.start('prevent-app-suspension')`
takes a system assertion for a game. `unlock()` then only fires once `pendingOps` reaches 0, which
is when the game exits.

`D-35-08-02` names what a fix has to decide, and defers that decision: `allowedPendingOps` is ONE
list serving TWO different questions — "is an operation pending?" and "which sleep kind should that
operation block?" — and those have come apart. It says to split the two rather than special-case one
status.

This defeats plan 35-08's own `success_criteria`: "a game running keeps the display awake; a
download running keeps the system awake; neither keeps the other awake." It is also a real power
regression — playing a game blocks system idle sleep for the whole session.

This plan is `autonomous: false`: task 1 is a blocking decision checkpoint, because `D-35-08-02`
explicitly says the split is not the discovering plan's call.
</objective>

  <decision>
    How to separate "is an operation pending?" from "which sleep kind should that operation block?",
    so a game stops taking a download-labelled system assertion and a finished download stops being
    held alive by a running game.
  </decision>

  <context>
    `D-35-08-02` states this decision is not the discovering plan's call and that whoever fixes it
    should split the two questions rather than special-case one status. The two questions are
    currently fused into one `allowedPendingOps` array, and `powerId` is shared state whose lifetime
    is governed by `pendingOps` rather than by the operation that took it.
  </context>

  <options>
    <option id="option-a">
      <name>Classify by kind at the source: two predicates over the same operation set</name>
      <pros>Directly implements `D-35-08-02`'s recommendation. `'launching'`/`'playing'` map to the
        display kind only; download-shaped operations map to the system kind only. `pendingOps` keeps
        its existing meaning for everything else that reads it.</pros>
      <cons>Requires enumerating every operation status and assigning a kind to each — an
        unclassified future status silently gets neither, so the classification must be exhaustive
        and fail loudly on an unknown value rather than defaulting.</cons>
    </option>
    <option id="option-b">
      <name>Per-kind reference counting in the sidecar: one counter and one assertion id per kind</name>
      <pros>Makes an assertion's lifetime belong to the operation that took it, which is the actual
        defect — the download's handle survived because a shared counter had not reached zero.
        Structurally prevents cross-kind extension regardless of what the renderer sends.</pros>
      <cons>A larger change in `appShellFlowRegistration.ts`, and it changes the `lock`/`unlock`
        wire contract, which has its own existing tests. Higher risk under a gate that must be
        re-measured.</cons>
    </option>
    <option id="option-c">
      <name>Both: classify at the source AND count per kind in the sidecar</name>
      <pros>Defence in depth; either layer alone would fix the observed symptom.</pros>
      <cons>Largest diff of the three, under a live gate re-run. Two changes make attribution
        harder if the re-measure still fails.</cons>
