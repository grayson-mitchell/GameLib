<objective>
Close verification gap 3, the EOS half of `REQ-35-17`. `eos_overlay.ts:162` and `:197` still call
`dialog.showMessageBox`, so two confirmations render as native system dialogs while the rest of the
app uses its own. The operator chose the real fix over an accepted-gap record.

`D-35-11-01` records why this is hard, and its analysis is the design input: the app-styled path
`showDialogBoxModalAuto` returns `void` and is one-way (`sendFrontendMessage('showDialog', ...)`); a
button's `onClick` does not survive the structured-clone hop; and the serializable replacement
`ButtonOptions.action` is a closed enum with exactly one literal, `'steamSignIn'`. There is no
mechanism to return a user's choice to the backend. So the gate must move to the renderer.

`D-35-11-01`'s open question — "may a settings-surface destructive confirmation be gated
renderer-side?" — is answered YES, with a condition the operator stated explicitly: **the failure
mode to design against is a gate that silently resolves "confirmed" when the IPC round-trip fails.
The destructive path must default to NOT removing.** So the backend does not become unconditional;
it gains an explicit confirmation parameter and fails closed on anything that is not literally
`true`.

`D-35-11-01` also corrects plan 35-11's own framing, and this plan inherits the correction: the ~14
census is the count of NATIVE `showMessageBox` sites (the ones that do NOT use the app pattern, of
which EOS is one); the app-styled population is the ~25 `Dialog` consumers. Do not repeat the
inversion.

Output: both EOS confirmations app-styled, with the destructive one fail-closed on every failure
path.

This plan is `autonomous: false`: task 3 is a blocking human gesture across two themes and must
exercise the cancel path.
