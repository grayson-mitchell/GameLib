<objective>
Make `powerSaveBlocker` real.

Purpose: it is a D-08 accepted no-op today, and its own comment schedules this phase for the fix.
The real effect of leaving it: the machine sleeps mid-depot-download, and `launcher.ts:190`'s
`prevent-display-sleep` does nothing while a game runs. Both are user-visible failures on any
machine with default power settings.

`33-RESEARCH` surveyed `tauri-plugin-nosleep` and `tauri-plugin-screen-wake-lock` and found neither
viable on maintenance grounds; `35-RESEARCH.md` found nothing changing that verdict but flagged its
own check as not re-run. So this is likely a small first-party Rust binding — three platform arms
over `IOPMAssertionCreateWithName`, `SetThreadExecutionState` and `systemd-inhibit`/logind.

Output: two Rust commands, a JS forwarder replacing the no-op, and a test proving `stop` releases
what `start` returned.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| sidecar -> Rust `wake_lock_start(kind)` | a string from JS selects which OS power assertion to take |
| app process -> OS power management | the app acquires a system-wide resource that outlives a careless release |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-35-31 | Denial of Service | A leaked assertion — `start` with no matching `stop`, or an id mismatch — keeps the user's machine awake indefinitely with no UI to release it, draining a laptop battery to zero unattended | mitigate | Ids are allocated from a registry and `stop` releases exactly its id, proven by a unit test asserting the pairing; a shutdown hook releases everything still held; Task 3 step 6 force-quits with an assertion held and checks nothing survives |
| T-35-32 | Tampering | An unrecognised `kind` string silently defaulting to one assertion type, so a download holds the display awake or a game lets the screen blank | mitigate | `wake_lock_start` rejects any value other than the two literals rather than defaulting, asserted by a Rust test; the JS test exercises BOTH kinds so an implementation that hardcodes one goes red |
| T-35-33 | Denial of Service | On Windows, `SetThreadExecutionState` is per-thread: setting it on a transient command-handler thread produces an assertion that evaporates when that thread ends, giving a silent no-op that unit tests cannot see | mitigate | Called out explicitly in the action so the implementer holds the flags on a thread that lives for the assertion's duration; verified live where Windows hardware exists, and recorded NOT ATTEMPTED where it does not |
| T-35-34 | Denial of Service | A power API unavailable on the host causing a panic out of a command handler and taking down the shell | mitigate | Every failure arm logs and returns `Err`; an `unwrap()`-count acceptance criterion measured before and after |
| T-35-SC | Tampering | Adding a wake-lock plugin or a platform-binding crate | mitigate | The plugin verdict is re-checked with a recorded command, and any crate addition must pass the Package Legitimacy Gate first — stated as a constraint and required in the summary |
