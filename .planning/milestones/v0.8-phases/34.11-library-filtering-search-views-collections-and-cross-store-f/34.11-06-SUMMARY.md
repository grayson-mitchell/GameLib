- `FilterViewList` renders exactly four rows (All games / Installed / Recently played / Favourites) as extended `NavItem`s bound to `LibraryContext`'s `libraryView`/`setLibraryView`. The empty state reuses `header.no_categories` verbatim; the two action rows only call `setShowCategories(true)`, never a mutation method (D-20); `CategoriesManager`'s own strings are untouched (D-18); no rule/predicate/smart-collection concept exists anywhere in the file (D-19) -- both D-19 and D-20 are pinned by source-text gates proven non-vacuous against a corrupted literal.
- Both components registered in `meta/i18nGateScope.json` (2 added lines, generated header untouched); `pnpm lint-translations:gamelib` exits 0.
- All 7 minted `gamelib:library.filterPanel.*` keys (`collections`, `manageCollections`, `newCollection`, `viewAll`, `viewFavourites`, `viewInstalled`, `viewRecentlyPlayed`) now exist in `public/locales/en/gamelib.json`, verified via two `pnpm i18n` extraction runs (see Deviations).

- `Header`, `CategoryFilter`, `LibraryFilters` and `CategoriesManager` are byte-identical to `HEAD` (verified via `git diff --name-only`). Neither new component is imported anywhere yet.
- Full suite: `pnpm test:ci` -- 225/225 suites, 4348/4348 tests pass, including the previously-flaky `helperProcess.test.ts` standalone in this run.

## Decisions Made
- Kept the Views/Collections rows as extended `NavItem`s rather than a forked row component, per the plan's explicit direction and plan 02's stated intent -- this is the only place both sections could drift from the tier-2 row spec, and they don't.
- `FilterCollectionList` mixes two `useTranslation` calls (`useTranslation('gamelib')` for the three newly-minted keys, `useTranslation()` default-namespace for the two reused `header.*` keys) rather than re-minting the reused keys under `gamelib:` -- re-minting would orphan every locale that already translates `header.no_categories`/`header.uncategorized`.
- See Deviations below for the FilterViewList literal-call-site rewrite and the `LibraryView` import-path correction -- both are Rule 1 fixes discovered during self-verification, not scope changes.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] FilterViewList's row labels were invisible to the i18n extractor -- rewrote to literal per-row `tGamelib()` calls**
- **Found during:** Task 3 self-verification (the i18n_contract's explicit instruction to confirm minted keys "actually landed in the catalog", not just assume a green jest run implies it)
- **Issue:** The plan's action text for Task 1 specified a module-scope `{value, key, defaultText}` lookup array mapped inside `.map()` via `label={t(row.key, row.defaultText)}`. Implemented as written (aliased to `tGamelib`), this compiles and passes every direct-invocation test (the mocked `t` echoes whatever `defaultValue` it's handed, so a test never notices whether the key argument was a literal or a variable). But `i18next-parser`'s `JavascriptLexer` (the tool behind `pnpm i18n`, which populates `public/locales/en/gamelib.json`) only resolves string-literal first arguments to `t()`/`tGamelib()` calls -- a call built from a variable (`tGamelib(row.key, row.defaultText)`) is structurally invisible to it. Confirmed empirically: running `pnpm i18n` with the lookup-array draft in place added 3 keys to `gamelib` (`FilterCollectionList`'s three literal calls) and 0 of the 4 `FilterViewList` keys, in the same run.
- **Fix:** Rewrote `FilterViewList` to build its `rows` array inside the component body with four literal `tGamelib('gamelib:library.filterPanel.viewXxx', 'Xxx')` call sites (one per row), each producing a `{value, label}` pair consumed by the JSX map. Re-ran `pnpm i18n` -- `gamelib: Added keys: 4`, all four keys now present in `public/locales/en/gamelib.json` alongside `FilterCollectionList`'s three.
- **Files modified:** `src/frontend/components/UI/NavShell/components/FilterViewList/index.tsx`, `src/frontend/components/UI/NavShell/__tests__/FilterViewList.test.tsx` (updated the label-gate assertion to count 4 literal `tGamelib('gamelib:` call sites via a comment-stripped source read, using the project's shared `stripSourceComments` util so the assertion isn't tripped by the component's own docstring mentioning the same pattern)
- **Verification:** `pnpm i18n` run twice (before/after), diff scoped to `public/locales/en/gamelib.json` only (the unrelated `translation`/`gamepage`/`login` catalog drift the same command touched was reverted via `git checkout --` before commit, since regenerating those is out of this plan's scope); `pnpm jest .../FilterViewList.test.tsx` and `pnpm jest .../FilterCollectionList.test.tsx` both green; `npx tsc --noEmit` clean; `pnpm lint-translations:gamelib` exits 0.
- **Committed in:** `848af7d86` (Task 3 commit)

**2. [Rule 1 - Bug] `LibraryView` type import path corrected**
- **Found during:** Task 1 self-verification (`npx tsc --noEmit`)
- **Issue:** The plan's `<action>` text instructed importing `LibraryView` from `frontend/screens/Library/filterEngine`, "do not redeclare the union". `filterEngine.ts` imports `LibraryView` from `frontend/types` for its own use but does not re-export it -- importing it from `filterEngine` therefore fails to compile (`TS2459: declares 'LibraryView' locally, but it is not exported`).
- **Fix:** Imported `LibraryView` from `frontend/types` (its actual declaration site) in both `FilterViewList/index.tsx` and `FilterViewList.test.tsx`.
- **Files modified:** `src/frontend/components/UI/NavShell/components/FilterViewList/index.tsx`, `src/frontend/components/UI/NavShell/__tests__/FilterViewList.test.tsx`
- **Verification:** `npx tsc --noEmit -p tsconfig.json` clean.
- **Committed in:** `d6d833dc2` (Task 1 commit)

**3. [Rule 1 - Bug] Comment-induced grep-count false positives, self-caught and reworded**
- **Found during:** Task 1 and Task 2 self-verification (acceptance-criteria grep checks)
- **Issue:** Explanatory docstring comments in both new components accidentally repeated literal strings a later exact-count acceptance check greps for -- `elementType="button"` appeared in `FilterViewList`'s docstring (pushing the real count from 1 to 2), and `customCategories.listCategories()` / `setShowCategories(true)` / the bare word `rule` appeared in `FilterCollectionList`'s docstring (pushing three separate counts over their stated values, and tripping `FilterCollectionList.test.tsx`'s own D-19 source gate against the component's own comment).
- **Fix:** Reworded each comment to describe the same intent without repeating the exact matched substring (e.g. "the button branch with plan 02's `active` prop" instead of naming the literal attribute; "category-listing accessor" instead of the literal method-call text; "condition or expression" instead of the word "rule").
- **Files modified:** `src/frontend/components/UI/NavShell/components/FilterViewList/index.tsx`, `src/frontend/components/UI/NavShell/components/FilterCollectionList/index.tsx`
- **Verification:** Re-ran every affected grep from the plan's acceptance criteria; all now match the plan's stated counts exactly (see below for the two counts that remain out of reach for a structural reason, not a comment).
- **Committed in:** `d6d833dc2` (Task 1), `dc0cb3ddf` (Task 2)

Two of Task 1's literal-count acceptance-criteria greps cannot both be satisfied by any single implementation, and the plan's own action text (a shared row-map call site) is incompatible with real i18n extraction (see Deviation 1). After the Rule 1 fix, `FilterViewList/index.tsx` has FOUR `tGamelib('gamelib:` call sites (matching the plan's literal `returns 4` criterion and, more importantly, matching what `pnpm i18n` actually extracts) rather than the single `label={tGamelib(` call site a shared-map design would have produced. The substantive intent -- four minted `gamelib:`-prefixed keys, reached through the aliased hook, landing in the real catalog -- is verified and holds; the specific `label={tGamelib(` grep window from the original plan text no longer applies to the corrected design.
