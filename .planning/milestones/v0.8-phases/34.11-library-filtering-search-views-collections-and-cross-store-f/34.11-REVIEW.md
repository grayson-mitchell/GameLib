# Phase 34.11: Code Review Report

**Reviewed:** 2026-08-10T08:15:06Z
**Depth:** standard
**Files Reviewed:** 40
**Status:** issues_found

## Summary

The filter engine (`filterEngine.ts`) is, in isolation, well-factored and well-tested.
The defects are almost entirely at the **integration seams** — the places where
`Library/index.tsx` wires the engine to the panel, and where the new stylesheets
consume theme tokens. Four of them are user-visible and provable:

1. Facet counts are computed over the **already-filtered** library, which defeats
   the exclude-your-own-facet rule the module's own header comment claims to enforce.
   Empirically reproduced: a store with 3 games reports `0`.
2. The new "Favourites" view returns **zero games for the default configuration**,
   because `engineDeps.favouriteKeys` is derived from a memo that only populates when
   an unrelated legacy toggle is on.
3. `var(--navbar-active)` is used with **no fallback** in five declarations across
   four new stylesheets; the token exists in only **4 of 11** theme blocks — the exact
   defect class the phase brief names as having caused three prior defects. Notably,
   the sibling `NavItem/index.scss` in the same directory *does* use a fallback chain
   for the same token, and the new files' own header comments discuss token survival
   while missing this one.
4. The `preset_uncategorized` sentinel leaks into user-facing chip and empty-state text.

Test coverage is broad but **structurally unable to catch findings 1 and 2**: the
`countFor` unit tests pass the *full* library where production passes the *filtered*
one, and no test in the phase exercises `engineDeps` construction at all. Two of the
source-text gates are narrower than their names claim, and one security-flavoured test
(i18next nesting injection) is vacuous because the i18next implementation is mocked out.

`tsc --noEmit` is clean. ESLint reports 22 warnings on `Library/index.tsx`, one of
which (`react-hooks/exhaustive-deps` at :707) independently corroborates WR-01.

## Critical Issues

### CR-01: Facet counts are computed over the already-filtered library — every unselected option reports 0

**File:** `src/frontend/screens/Library/index.tsx:784-806`
**Issue:**
`countForStore` / `countForRunnability` pass `gamesForAlphabetFilter` — the output of
`filterLibrary(library, engineState, engineDeps)` with **no skip** — into
`filterEngine.countFor`, which then re-runs `filterLibrary` with `{ skip: kind }`.
Skipping a facet on a list that has *already been narrowed by that facet* cannot
recover the excluded games. D-28 ("exclude your own facet") is therefore inert in the
shipped wiring, and every unselected Store/Runnability option renders a permanent `0` —
precisely the "counts that lie" failure `filterEngine.ts:11-16` and
`index.tsx:613-619` both claim to prevent.

Empirically reproduced against the real modules (library: 1 gog + 3 steam,
`stores: ['gog']`):

```
AS WIRED (Library/index.tsx):    0
AS UNIT-TESTED (full library):   3
```

The unit test at `__tests__/filterEngine.test.ts:184-200` passes the **full** library,
so it asserts the correct behaviour of a call shape production never makes.

The double-filter also means the "counts are computed over the fuzzy-matched set"
requirement (REQ-34.11-15) is currently satisfied only by accident of the same bug —
`engineState.searchMatchedKeys` is `null` at the `countFor` call sites.

**Fix:** pass the **unfiltered** union into `countFor`, and give it the search
constraint explicitly so REQ-34.11-15 is satisfied on purpose rather than by side
effect. Hoist the union and the search-key set out of the grid memo:

```tsx
// New memo, above gamesForAlphabetFilter:
const libraryUnion = useMemo(() => makeLibrary(), [/* see WR-01 for full deps */])
const searchMatchedKeys = useMemo(
  () => computeSearchMatchedKeys(libraryUnion, filterText),
  [libraryUnion, filterText]
)
const countState = useMemo(
  () => ({ ...engineState, searchMatchedKeys }),
  [engineState, searchMatchedKeys]
)

const gamesForAlphabetFilter = useMemo(
  () => filterEngine.filterLibrary(libraryUnion, countState, engineDeps),
  [libraryUnion, countState, engineDeps]
)

const countForStore = useCallback(
  (value: StoreFacetValue) =>
    filterEngine.countFor(libraryUnion, countState, engineDeps, 'store', value),
  [libraryUnion, countState, engineDeps]
)
// same change for countForRunnability
```

Add a regression test that reproduces the production call shape (filter first, then
count) — the existing unit test cannot fail on this.

### CR-02: The `Favourites` view returns zero games in the default configuration

**File:** `src/frontend/screens/Library/index.tsx:503-547, 559-581`
**Issue:**
`engineDeps.favouriteKeys` is built from `favouritesIds`, which is derived from the
`favourites` memo. That memo is **conditionally populated**:

```tsx
const favourites = useMemo(() => {
  const tempArray: GameInfo[] = []
  if (showFavourites || showFavouritesLibrary) {   // <-- gate
    ...push matching games...
  }
  return tempArray.sort(...)
}, [...])
```

- `showFavourites` = `libraryTopSection === 'favourites' && !!favouriteGamesList.length`.
  `libraryTopSection` defaults to `'disabled'` (`src/backend/config.ts:343`,
  `GlobalState.tsx:291`).
- `showFavouritesLibrary` reads `localStorage['show_favorites']`, default `'false'` —
  and its only UI (`LibraryFilters`) was **deleted by this phase**, so no user can
  turn it on any more.

For any default install, `favourites` is `[]` → `favouritesIds` is `[]` →
`deps.favouriteKeys` is an empty `Set` → `passesView(game, 'favourites', deps)`
(`filterEngine.ts:148`) is `false` for **every** game. Selecting the new
`Favourites` row yields an empty grid and "No games match Favourites."

The real source of truth (`favouriteGames.list` from `ContextProvider`) is already in
scope in this component and is unconditional.

**Fix:** derive the engine's favourite keys directly from the unconditional source,
independent of the top-section display memo:

```tsx
const favouriteKeys = useMemo(
  () =>
    new Set(
      favouriteGames.list.flatMap((fav) =>
        // favouriteGames.list is keyed by appName only; resolve the runner from the union
        libraryUnion
          .filter((g) => g.app_name === fav.appName)
          .map((g) => filterEngine.gameKey(g))
      )
    ),
  [favouriteGames, libraryUnion]
)
// engineDeps: { ..., favouriteKeys }
```

Add a test that builds `engineDeps` the way `Library/index.tsx` does and asserts the
`favourites` view is non-empty with `libraryTopSection: 'disabled'` — no current test
touches `engineDeps` construction.

### CR-03: `var(--navbar-active)` has no fallback and is undefined in 7 of 11 themes — the checked-checkbox indicator drops entirely

**File:**
`src/frontend/components/UI/NavShell/components/FilterFacetGroup/index.scss:72, 81, 117-118`
`src/frontend/components/UI/NavShell/components/FilterMoreGroup/index.scss:36`
`src/frontend/screens/Library/components/FilterChipRow/index.scss:62-63`
`src/frontend/screens/Library/components/FilterZeroResult/index.scss:39`

**Issue:**
`--navbar-active` is declared in only **4** theme blocks — `body.midnightMirage`
(themes.scss:92), `body.gruvbox_dark` (:210), `body.dracula-classic` (:290),
`body.nord-light` (:349) — and is **not** in the base `body` block or
`styles/_colors.scss`. It is therefore undefined in
`classic/cyberSpaceOasis/cyberSpaceOasisAlt`, `high-contrast`, `nord-dark`,
`marine-classic`, `zombie-classic`, `old-school` and `sweet-dark`.

An undefined custom property with no fallback is invalid at computed-value time and
drops the **entire declaration** (resolving to `unset`, which still beats the UA
stylesheet). Consequences in those 7 themes:

- `FilterFacetGroup/index.scss:117-118` — `.FilterFacetRow--checked .FilterFacetRow__box`
  loses **both** `background` and `border-color`. The checkbox's checked fill does not
  render at all; the box reverts to `transparent` + `currentColor` border. The primary
  state indicator for the Store/Runnability/More facets is gone.
- `:72` / `:81` — hover and checked row `color` drop, so hover/checked text is the same
  colour as an inactive row.
- `FilterMoreGroup/index.scss:36` — the `only` button's pressed colour drops.
- `FilterZeroResult/index.scss:39` / `FilterChipRow/index.scss:62-63` — the Clear-all
  affordances lose their distinguishing colour.

This is the phase brief's named recurring defect class. The sibling stylesheet in the
same directory already solves it correctly:
`NavItem/index.scss:21-24` uses
`var(--navbar-active, var(--accent-overlay, var(--accent)))`. The new files' header
comments explicitly discuss token survival (`--navbar-inactive` → `--navbar-accent`,
`--text-hover` → `--accent`) and cite that exact NavItem fallback chain — but never
apply it to `--navbar-active` itself.

**Fix:** use the same fallback chain NavItem already uses, in all five declarations:

```scss
// FilterFacetGroup/index.scss
.FilterFacetRow--checked .FilterFacetRow__box {
  background: var(--navbar-active, var(--accent-overlay, var(--accent)));
  border-color: var(--navbar-active, var(--accent-overlay, var(--accent)));
}
```

Prefer hoisting it once to a local custom property on the panel root
(`--facet-active-color: var(--navbar-active, var(--accent-overlay, var(--accent)));`)
so the chain is declared once rather than five times.

Then replace the single-theme spot check in `themeTokens.test.ts:74-76` with the
**census** form the same file already uses for `--divider` (see WR-13).

### CR-04: The `preset_uncategorized` sentinel renders as user-facing text in chips and the zero-result sentence

**File:** `src/frontend/screens/Library/components/FilterChipRow/chipLabels.ts:71-74`
**Issue:**
`describeActiveFilters` (`filterEngine.ts:359-365`) emits
`{ kind: 'collection', value: 'preset_uncategorized' }` when the Uncategorized row is
selected, and `chipLabelSpec` treats *every* collection value as opaque user data:

```ts
case 'collection':
  return { literal: descriptor.value }
```

`'preset_uncategorized'` is not user data — it is the internal sentinel that
`FilterCollectionList/index.tsx:70` correctly renders as `t('header.uncategorized',
'Uncategorized')`. Selecting Uncategorized therefore produces a chip reading
`preset_uncategorized` and a zero-result sentence reading
`No games match preset_uncategorized.` The chip row and the panel disagree about the
name of the same filter — the exact class of drift `chipLabels.ts`'s own header
comment says it exists to prevent.

The unit tests only exercise `collection: 'Backlog'`
(`FilterChipRow/__tests__/index.test.tsx:47-55`), so the sentinel path is untested.

**Fix:** special-case the sentinel before the literal branch, using the same key the
panel uses:

```ts
case 'collection':
  if (descriptor.value === 'preset_uncategorized') {
    return {
      ns: 'default',
      key: 'header.uncategorized',
      defaultText: 'Uncategorized'
    }
  }
  // A real collection name is user data -- no key lookup, no title-casing.
  return { literal: descriptor.value }
```

Export the `'preset_uncategorized'` string as a shared constant from `filterEngine.ts`
so the three sites (`filterEngine.passesCollection`, `FilterCollectionList`,
`chipLabels`) cannot drift. Add a test for the sentinel value.

### WR-02: Unguarded `JSON.parse` of localStorage inside render can white-screen the Library

**File:** `src/frontend/screens/Library/index.tsx:562-564` (also `:122`, `:149-151`, `:180-182`)
**Issue:** `nonAvailableAppNames: JSON.parse(storage.getItem('nonAvailableGames') || '[]')`
runs inside the `engineDeps` memo during render with no `try`/`catch` and no shape
validation. Corrupt or hand-edited localStorage throws during render and takes the whole
screen down. The result is also typed `any` (ESLint `no-unsafe-assignment` at `:562`) and
is fed straight into `Array.prototype.includes`. `filterEngine.migrateStoreFacetSelection`
already establishes the correct defensive pattern for exactly this input class.
**Fix:**

```ts
const parseStringArray = (raw: string | null): string[] => {
  if (!raw) return []
  try {
    const parsed: unknown = JSON.parse(raw)
    return Array.isArray(parsed) ? parsed.filter((v): v is string => typeof v === 'string') : []
  } catch {
    return []
  }
}
```

Apply the same guard to the three legacy parses at `:122`, `:149` and `:180` if that
block is kept (see WR-04).

### WR-03: `connectedStores` and `makeLibrary` gate Amazon on different fields

**File:** `src/frontend/screens/Library/index.tsx:287-295` vs `:620-632`
**Issue:** `connectedStores` pushes `'nile'` when `amazon.username` is set;
`makeLibrary` includes the Amazon library when `amazon.user_id` is set. The comment at
`:284-286` claims the memo reuses "the same gating expressions makeLibrary() already
uses" — false for Amazon. `GlobalState.tsx:251-252` sets these from two different config
keys (`userData.user_id` and `userData.name`), so they can diverge: Amazon games appear
in the grid with **no Store row to filter them by**, or a row renders for a store whose
games are absent.
**Fix:** derive both from one predicate:

```tsx
const storeConnected = useMemo(() => ({
  sideload: true,
  legendary: !!epic.username,
  gog: !!gog.username,
  nile: !!amazon.user_id,
  zoom: zoom.enabled && !!zoom.username,
  steam: !!steam?.username
}), [epic.username, gog.username, amazon.user_id, zoom.enabled, zoom.username, steam?.username])
```

and have `connectedStores` and `makeLibrary` both read it.

### WR-13: The `--navbar-active` theme gate checks one theme while the file already has a census idiom

**File:** `src/frontend/components/UI/NavShell/__tests__/themeTokens.test.ts:62-77`

the `--divider` census at `:152-187` iterates all 11 theme selectors. The narrow gate
