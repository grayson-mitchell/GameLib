# Phase 34.11 Plan 03: Navbar CR-01/CR-02 and Tier-2 Divider Source Gate Summary

**Fixed gruvbox_dark's missing `--navbar-active` (CR-01), restored the navbar's `-webkit-app-region: drag` surface with `no-drag` exclusions (CR-02), substituted the tier-2 column's no-fallback `var(--divider)` border for `var(--body-background)`, and pinned all three with a new jest source-text gate whose every assertion family was proven to fail against a reverted pre-fix specimen.**

## Accomplishments
- `body.gruvbox_dark` now declares `--navbar-active: var(--navbar-accent);`, closing CR-01. The theme's `NavItem` active-colour fallback chain (`var(--navbar-active, var(--accent-overlay, var(--accent)))`) always resolved to *something* — the bug was a wrong colour (`--accent-overlay`, a mustard), not a dropped declaration.
- `.NavShell__navbar` declares `-webkit-app-region: drag`, with `-webkit-app-region: no-drag` added to `.NavTabs` and to `.DownloadsRing` (scoped inside `.NavShell__navRight`) so the drag region cannot swallow tab or Downloads-link clicks (T-34.11-07). `WindowControls` already had `no-drag`, unchanged.
- `.NavShell__tier2`'s `border-inline-end` now reads `1px solid var(--body-background)` instead of `1px solid var(--divider)` — `--divider` is a no-fallback custom property defined in only 2 of 11 theme blocks, and both `gruvbox_dark` and `dracula` (mandatory stress-test themes) are among the 9 that never define it, so the divider silently disappeared in those themes rather than falling back to a default colour.
- New `src/frontend/components/UI/NavShell/__tests__/themeTokens.test.ts` — a source-text-only jest gate (no jsdom/CSS engine in this project) with three describes, one per fix, each with an explicit "guard against a vacuous pass" assertion and each proven to go RED against a hand-reverted pre-fix specimen before being trusted.

## Decisions Made
- Placed the new `--navbar-active` declaration directly after `--navbar-active-background` inside `body.gruvbox_dark`, matching how `body.midnightMirage` groups its own two navbar-active tokens together (plan instruction, followed exactly).
- For the census assertion in Task 3 ("declaration count strictly less than theme-block count"), used a hand-verified list of the file's 11 real theme root selectors rather than a generic regex counter. Verified by direct node script before writing the test (`node -e` snippet run against `themes.scss`, confirmed `themeBlockCount=11, dividerCount=2`) that a naive `body\.[\w-]+...\{` regex would over-count: `themes.scss:628-632` is a real cross-theme override block (`--navbar-accent` shared by `classic`/`cyberSpaceOasisAlt`/`dracula-classic`/`marine-classic`/`zombie-classic`) whose selector shape (comma-separated `body.X` list terminating in `{`) is indistinguishable from a genuine theme-definition block by regex alone. `cssBlock()`'s `indexOf` on each curated selector's literal `"${selector} {"` string correctly resolves to the intended theme block in every case because the *first* occurrence of that exact substring in the file is always the real theme block (verified per-selector, see the test's own comment).
- `-webkit-app-region: no-drag` for the Downloads click target was scoped as `.NavShell__navRight .DownloadsRing` (nested inside the existing `.NavShell__navRight` rule) rather than applied to the whole `.NavShell__navRight` container — matches the plan's "clickable descendant" framing and avoids widening the no-drag exclusion beyond the one interactive child that currently exists there.
