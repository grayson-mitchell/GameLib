# Phase 34.11: Library filtering — search, views, collections and cross-store facets - Research

**Researched:** 2026-08-09
**Domain:** Frontend filter-panel refactor (React/TypeScript, no backend/IPC surface, no new packages)
**Confidence:** HIGH

## Summary

This phase replaces the contents of an already-built tier-2 portal (`Header`, portalled into
`GamesPanel` by `Library/index.tsx`) with a new filter panel: search (unchanged) → single-select
views → single-select collections → two collapsed multi-select facets (Store, Runnability) → one
collapsed "More filters" group. It retires two components (`CategoryFilter`, `LibraryFilters`),
inverts two filter semantics (store/platform opt-out → opt-in), replaces a literal platform facet
with a derived "runnability" facet, adds a new removable-chip row above the grid, and fixes two
carried-forward theme defects (CR-01: `--navbar-active` missing in `gruvbox_dark`; CR-02: navbar
drag region never ported) plus a third, newly-found instance of the same no-fallback-custom-property
defect class (`--divider` undefined in `gruvbox_dark`/`dracula`, breaking the tier-2 column's own
right-edge divider).

Every piece of state this phase touches already exists in `Library/index.tsx` as
`useState`+`localStorage` pairs, or in `GlobalState.tsx` as `configStore`-backed `customCategories`.
No new library is required — `Dropdown`, `NavItem`, `LibrarySearchBar`, `ToggleSwitch`-adjacent
patterns, FontAwesome (`faChevronDown` already used elsewhere), and the existing SCSS custom-property
token system are all that this phase needs. The highest-risk items are (1) `NavItem`'s `button`
branch cannot currently render an `active` state at all — this is a **required**, not optional,
extension — and (2) the Windows-host runnability facet has genuinely zero backing data in the
current `GameInfo` type (confirmed: no `is_win_native` or equivalent field exists anywhere in
`common/types.ts`), which is a real product decision the plan must make explicitly rather than
inventing a signal that doesn't exist.

**Primary recommendation:** Build the new panel as a set of new sibling components inside (or
alongside) a reskinned `Header`, reusing `Dropdown` for all three collapsible groups and an
extended `NavItem` for Views/Collections rows; keep all filter persistence exactly where it is
(`localStorage`, same keys except the two D-02 migrations); write the exclude-your-own-facet count
function as a small pure helper unit-testable independent of React (this project has no jsdom, so
pure-function extraction is the only way to unit-test the counting logic directly rather than via
source-text assertions).

### Pattern 1: Filter state — `useState` + `localStorage`, read-once initializer

**What:** Every filter is a `useState` whose initializer reads `localStorage` once, paired with a
`handleX` wrapper that writes `localStorage` then calls `setState`.
**When to use:** Every new filter this phase adds (view, collection selection mirror, runnability
facet) — this is the existing, established pattern for nine filters already in `Library/index.tsx`.
**Example:**
```typescript
// Source: src/frontend/screens/Library/index.tsx:115-121 (existing pattern to replicate)
const [storesFilters, setStoresFilters_] = useState<StoresFilters>(initialStoresfilters)
const setStoresFilters = (newFilters: StoresFilters) => {
  storage.setItem('storesFilters', JSON.stringify(newFilters))
  setStoresFilters_(newFilters)
}
```

### Pattern 2: One-time `localStorage` migration (D-02)

**What:** Detect the legacy shape, discard it, reset to the new default — never translate old
values into new ones.
**When to use:** The store/platform-facet opt-in inversion (D-01/D-02).
**Example:**
```typescript
// Source: src/frontend/screens/Library/index.tsx:184-189 (existing precedent, migrateFilterMode)
const migrateFilterMode = (key: string, defaultValue: FilterMode): FilterMode => {
  const stored = storage.getItem(key)
  if (stored === 'show' || stored === 'only' || stored === 'off') return stored
  return defaultValue  // handles legacy 'true'/'false'/null/undefined — discarded, not translated
}
```
Applying D-02's "one-time reset to empty" rule to `storesFilters`: detect the OLD key's legacy
shape (an object with all-boolean values, opt-out semantics) — if present, **do not read it** into
the new opt-in state; just start empty and optionally clear the old key. The `migrateFilterMode`
precedent is a *format* migration (string enum); D-02 is a *semantics* migration (discard, not
translate) — do not conflate the two, and do not write code that tries to invert the old boolean
mask into an equivalent opt-in set (D-02 explicitly forbids this).

### Pattern 3: Exclude-your-own-facet counting

**What:** A count beside a facet option applies every active filter *except that facet's own*.
**When to use:** Store and Runnability facet row counts (D-28/D-29). NOT for views or collections
(D-28 — counts render on facet options only).
**Example:**
```javascript
// Source: .claude/skills/sketch-findings-gamelib/references/library-filtering.md:46-51 (sketch's validated engine)
function countFor(state, kind, value) {
  return filtered(state, { skip: kind })          // the whole trick
    .filter(g => matches(g, kind, value)).length;
}
```
**Adaptation for this codebase:** extract the existing `gamesForAlphabetFilter` pipeline's per-stage
filter predicates into named, individually-callable functions (`applyViewFilter`, `applyCollectionFilter`,
`applyStoreFilter`, `applyRunnabilityFilter`, `applySearchFilter`, `applyTriStateFilters`) so a
`countFor(library, skipKind)` helper can compose all of them except one. This is a **refactor of the
existing `useMemo` body**, not a parallel implementation — duplicating the filter logic in two places
(once for the visible list, once for counts) is the single most likely source of a counts-vs-grid
mismatch bug in this phase.

### Anti-Patterns to Avoid

- **Counting a facet against itself:** every unselected sibling row reads `0`, actively misleading
  the user (sketch's own "What to Avoid").
- **Reimplementing the filter pipeline twice** (once inline in the `useMemo`, once for counts) —
  extract shared predicate functions instead; two implementations WILL drift.
- **Treating D-02 as a format migration** — it's a semantics migration; do not attempt to translate
  old opt-out values into an equivalent opt-in set.
- **Adding a `max-height: 620px` anywhere** — UI-SPEC already resolved this: `.NavShell__tier2Portal`
  already has `height: 100%; overflow-y: auto` shipped by Phase 34.10 for exactly this reason.
- **A flex/grid child without `min-width: 0`** — sketch's own explicit warning; the grid container
  overflows the panel without it. `NavShell/index.scss:173`'s `.content` already carries this — verify
  `GamesList`'s own inner container doesn't reintroduce the overflow during this refactor.

## Common Pitfalls

### Pitfall 1: `NavItem`'s button branch cannot render `active` at all today
**What goes wrong:** Views and Collections rows use `elementType="button"` (they're not routes),
but `NavItem`'s `case 'button':` branch (`index.tsx:53-58`) renders `<button className="NavItem">`
with no `className` prop merge and no `active` class logic — only the default `NavLink` branch
applies `classNames('NavItem', className, { active: ... })`.
**Why it happens:** `NavItem` was ported from a route-based sidebar where every row was a link;
button rows were added later for non-route cases without carrying over the active-state logic.
**How to avoid:** Extend the `button` case to accept `className` and an `active`/`isActive` boolean
prop, mirroring the `NavLink` branch's `classNames()` call. This must land as an explicit task, not
a byproduct — without it, selected Views/Collections rows are visually indistinguishable from
unselected ones.
**Warning signs:** If the plan's task list has a task that renders Views/Collections using `NavItem`
without a task that first extends `NavItem`, the selected-state visual is unimplementable and will
be discovered late (likely during checker/verification, not during coding).

### Pitfall 2: `--divider` and similar no-fallback custom properties silently drop entire shorthand declarations
**What goes wrong:** `border-inline-end: 1px solid var(--divider)` — when `--divider` is undefined
in the active theme (confirmed: only defined at `themes.scss:97` `midnightMirage` and `themes.scss:145`
`classic`/`cyberSpaceOasis*` — **9 of 11 theme blocks, including both mandatory stress-test themes
`gruvbox_dark` and `dracula`, do not define it**), the CSS spec makes the *entire* `border-inline-end`
shorthand invalid at computed-value time — not "falls back to a default color", the declaration
disappears outright.
**Why it happens:** `var(--token)` with no fallback and an undefined custom property is invalid at
computed-value time per the CSS Custom Properties spec; this has already bitten this exact codebase
once before (`NavShell/index.scss:37`'s navbar border, fixed in Phase 34.10) and the fix comment at
that site explicitly flags this second occurrence (`NavShell/index.scss:149`) as deferred, not fixed.
**How to avoid:** Change `border-inline-end: 1px solid var(--divider);` to
`border-inline-end: 1px solid var(--body-background);` — the exact same token substitution already
proven present and non-colliding-with-navbar-background in all 11 theme blocks by the 34.10 fix.
**Warning signs:** Any new CSS in this phase that references `var(--divider)` without checking
`grep '^\s*--divider:' src/frontend/themes.scss` first. `[VERIFIED: direct file read, themes.scss]`
— confirmed the same census UI-SPEC already ran: `--divider` at lines 97 and 145 only.

### Pitfall 3: `CrossoverBadge`'s D-16 honesty invariant must be reused, not reinvented, for the runnability facet
**What goes wrong:** A naive runnability facet implementation might treat `rating === undefined`
(never looked up) the same as `rating === null` (looked up, no data) — but these are semantically
different (never-synced vs. synced-but-absent) and the existing `CrossoverBadge` component already
encodes the correct distinction (`undefined` → omit from all counts entirely; `null` → "Not yet
checked" row).
**Why it happens:** The `crossoverRatings` slice (`Record<string, number | null>`) uses `undefined`
(key absent from the map) and `null` (key present, value null) as two distinct states — easy to
collapse into one "no rating" bucket if the reader doesn't check the map access pattern carefully.
**How to avoid:** Reuse `CrossoverBadge.tsx:32-43`'s tier derivation verbatim (UI-SPEC's own
instruction) rather than re-deriving it for the facet.
**Warning signs:** A runnability facet that shows a 5th "unknown"/"not yet checked" row on Windows
or Linux hosts, where no CrossOver index exists at all — D-12 says hide rows the host can't compute,
so this row should only ever appear on macOS.

### Pitfall 4: i18n key extraction silently misses `tGamelib(...)` calls without the lexer fix already in place
**What goes wrong:** The default `i18next-parser` lexer only recognizes calls to the literal
identifier `t`. This codebase's `gamelib:` namespace idiom uses a second aliased hook
(`const { t: tGamelib } = useTranslation('gamelib')`), which the default lexer cannot see.
**Why it happens:** `[VERIFIED: direct file read, i18next-parser.config.js:47-72]` — this was
already discovered and fixed in Phase 34.8-09 (16/48 retrofit keys were silently absent from the
catalog before the fix). The fix (`functions: ['t', 'tGamelib']`) is **already live** in
`i18next-parser.config.js` for this phase — this is documented here so the plan does NOT re-diagnose
it as a new bug, and so any new call-site idiom this phase might invent (a third aliased hook name)
is checked against this same lexer list before being used.
**How to avoid:** Use exactly the `tGamelib`/`t` two-hook idiom already shown in
`LibraryFilters/index.tsx:24,217` — do not invent a third alias.
**Warning signs:** `pnpm i18n` / `lint-translations:gamelib` reports a key as missing from the
catalog despite the `t()`/`tGamelib()` call being present in source — check the lexer's `functions`
array first, not the call site, if this alias is anything other than `t` or `tGamelib`.

### Pitfall 5: New component files must be added to `meta/i18nGateScope.json`
**What goes wrong:** The i18n gate (Phase 34.8) checks a static, committed allowlist of in-scope
files (`meta/i18nGateScope.json`), not a live git-diff computation (avoiding a documented CI
limitation — `actions/checkout@v6` has no Heroic merge-base history). A new file with hardcoded
user-facing strings that isn't registered in this list will not be checked by the gate at all —
which sounds like a pass but is actually a silent gap.
**Why it happens:** `[VERIFIED: direct file read, meta/i18nGateScope.json]` — confirmed
`CategoryFilter/index.tsx`, `Header/index.tsx`, `LibraryFilters/index.tsx`, and
`NavShell/components/NavItem/index.tsx` are ALL already registered (added across Phases 34.8/34.10).
Any brand-new file this phase creates (`FilterViewList`, `FilterCollectionList`, `FilterFacetGroup`,
`FilterMoreGroup`, `FilterChip`, `FilterChipRow`) is NOT yet in that list.
**How to avoid:** Every new component file this phase creates must be added to
`meta/i18nGateScope.json`'s array as an explicit plan task — do not assume new files are
auto-covered.
**Warning signs:** `pnpm test:ci` passes green (the gate only checks registered files) while a new
component ships an untranslated hardcoded string — this is exactly the "green suite ≠ gate
satisfied" trap already recorded project-wide for this gate.

### Pitfall 6: This project has no jsdom — component tests must use direct function-invocation or source-text gates
**What goes wrong:** Writing a test that calls `render()` from `@testing-library/react` or mounts
via `react-test-renderer` will fail outright — neither is installed, and adding either is a new
package install requiring a human package-legitimacy checkpoint (out of scope for a UI-behavior
phase).
**Why it happens:** `[VERIFIED: direct file read, src/frontend/jest.config.js]` — `testEnvironment:
'node'`, explicit docstring confirms jsdom/jest-environment-jsdom/react-test-renderer are
deliberately not installed.
**How to avoid:** Two established patterns already exist in this exact directory tree:
1. **Direct function invocation** — call the component as a plain function (`ComponentName({ props })`)
   and inspect the returned React-element object graph's `.props`, no DOM needed. See
   `CrossoverBadge.test.tsx` (mocks `react-i18next` at module level, calls `CrossoverBadge({ rating })`
   directly, asserts on `element.props.className`/`.title`).
2. **Source-text gate** — read the raw `.tsx`/`.css` source with `fs.readFileSync` and assert on
   structural patterns (import order, selector presence, CSS property absence). See
   `tier2Portal.test.ts` (asserts `<Header />` is always wrapped in `createPortal(`, asserts CSS
   blocks match/don't-match certain patterns).
**Warning signs:** Any new test file importing `@testing-library/react`, `react-test-renderer`, or
`enzyme` — these are not installed and importing them will throw a module-not-found error at test
run time, not silently skip.

```typescript
// Source: src/frontend/screens/Library/index.tsx:191-197 (existing FilterMode state)
// A tri-state's chip '×' must call the setter with 'off' directly —
// never call a "cycle" function. Contrast with LibraryFilters/index.tsx's

const handleShowHidden = (value: FilterMode) => {
  storage.setItem('show_hidden', value)
  setShowHidden(value)
}
// Chip '×' onClick: () => handleShowHidden('off')   -- NOT toggleShowHidden()
```

## Open Questions

1. **Is `Fuse.js` removal from `Library/index.tsx`'s search path in scope for this phase's plan?**
