  <what-built>
`resetHeroic` is now ported to the Tauri sidecar. It deletes `config.json` + `GamesConfig/`, then
after a 1s delay calls `app.relaunch()` followed by `app.quit()`. Two things were done about that
sequence:

1. **No Rust change.** Research verified from a direct read of tauri 2.11.5's source (the version
   `Cargo.lock` pins) that `AppHandle::restart()`'s "skip the events" branch applies only on the main
   thread, and `dispatch_rust_channel` always runs on a spawned worker — so `app_relaunch` exits
   through the real event loop and the existing `RunEvent::Exit` handler kills the sidecar child
   *before* the process re-execs. The orphan sidecar was an **inference that research disproved**, not
   an observed defect. No `shutdown_child()` call was added.
2. **A JS-side ordering guard.** `electronStub.app` now sets a module-scope `relaunchInFlight` flag in
   `relaunch()`, after which `quit()`/`exit()` become logged no-ops — because the stub dispatches the
   two calls as independent fire-and-forget frames on spawned worker threads, so `app_exit` could
   otherwise be processed first and the app would quit instead of restarting, nondeterministically.

This item is the empirical confirmation of both, and it must run on a **packaged** build because
`main.rs` spawns a *different* sidecar binary in dev vs packaged and `app.restart()` re-execs a
different binary in each mode — the whole question is which child gets killed.
