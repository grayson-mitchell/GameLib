# Plan 34.3-09 Summary — Blocking Live Gate

## What this plan did

Ran the phase's blocking live gate (D-13): 5 named items proving the OS-level side effects that
jest structurally cannot observe. Items 1/2/3/5 under `pnpm tauri:dev`, item 4 on a packaged build.

**Verdict: all 5 items PASS.** Full record in `34.3-LIVE-GATE.md`.

## Why this gate existed

This slice deliberately broke the Phase 30 D-04 → 34.1 D-15 → 34.2 D-11 unit-proven-only precedent.
34.2 could honestly claim "data in / data out with assertable return shapes." This slice cannot:
most of its channels' entire purpose is an observable OS side effect, and it ships two Rust arms
that **no CI step in this repo compiles** (there is no cargo step in `.github/workflows/*.yml`).

The gate justified itself — it found two real defects that every automated layer had passed over.

## Defects found and fixed in-phase

### 1. SEA sidecar build broken since Phase 34.2 (commit `03145629`)

`pnpm build:sidecar-sea` failed with `Top-level await is currently not supported with the "cjs"
output format` in `i18next-fs-backend/esm/{writeFile,readFile}.js`.

A dual-package hazard, not an esbuild bug: `bootstrap.ts`'s `import Backend from 'i18next-fs-backend'`
(commit `a8e7c8093`, **Phase 34.2 plan 01**) made esbuild resolve the package `exports` map's
`import` condition to the ESM build regardless of this bundle's `--format=cjs` output.

Fixed with `--alias:i18next-fs-backend=i18next-fs-backend/cjs` in `meta/buildSidecarSea.ts`, forcing
resolution to the package's genuine CJS entry. Resulting SEA binary smoke-tested standalone with a
scrubbed `PATH` (no system Node, no reachable `node_modules`).

**Silently broken since 2026-07-25** — nothing re-ran that build between Phase 34.2 and this gate.
Worth remembering for whoever next touches `sidecar/bootstrap.ts`'s i18n init.

### 2. Clipboard parity break in the log-upload dialog (commit `44232d3e`)

Found by item 5. The dialog reported *"Uploaded to (URL copied to your clipboard)"* while the
clipboard was unchanged.

`LogFileUploadDialog/index.tsx:43` used `navigator.clipboard.writeText(url)` — the Web Clipboard
API, not this app's channel. Under Electron the Chromium renderer grants clipboard-write so it
works; under Tauri the renderer is WKWebView, which **resolves without writing**. It did not reject,
so `setUploadUrl(url)` still ran and the success message still rendered — the message was simply
false. Not a capability issue: D-02's zero-grant stance gates Tauri IPC, not Web APIs.

Fixed by routing both surviving `navigator.clipboard` call sites through the channels this phase
built and unit-proved:

| File | Was | Now |
|------|-----|-----|
| `LogFileUploadDialog` | `navigator.clipboard.writeText` | `window.api.clipboardWriteText` |
| `EditGameDialog` | `navigator.clipboard.readText` | `window.api.clipboardReadText` |

Both channels are registered in **both** builds (`main.ts:1425`/`1427` under Electron,
`clipboardFlowRegistration.ts:77`/`90` under the sidecar → the Rust arms), so the change is
parity-safe in each direction. Zero `navigator.clipboard` call sites remain.

This is exactly the defect class D-13 made the gate blocking for: jest asserts channel dispatch, and
this code path never touched a channel.

## Item 4 — what it confirmed

Empirically confirmed plan 34.3-03's Q1 finding (read directly from tauri 2.11.5 source): because
`AppHandle::restart()`'s "skip the events" branch applies only on the main thread and
`dispatch_rust_channel` always runs on a spawned worker, `app_relaunch` exits through the real event
loop and the existing `RunEvent::Exit` handler kills the sidecar child before re-exec.

**No Rust fix was written, and none was needed** — the orphan sidecar was an inference research
disproved, not an observed defect. Exactly one sidecar process after the reset; the app restarted
rather than quitting, so the D-06 `relaunchInFlight` guard held. Closes research Assumption A1 and
leaves threat T-34.3-33 unrealised on the packaged path.

## Plan defect found: item 4's acceptance criterion is unsatisfiable as written

The plan required both that the app **restart** and that `config.json` be **absent** afterward.
Those cannot both hold — a successful restart necessarily recreates `config.json` from factory
defaults on boot, so the literal criterion is only satisfiable on a build that FAILS the restart
check.

Recorded against the correct post-condition instead, and machine-verified: `GamesConfig/` absent;
`config.json` present but pristine-default (mtime at the restart moment, 1926 bytes vs the tester's
real 2587-byte config, every value matching `getFactoryDefaults()` including `verboseLogs: true`
and `enableSteamNativeInstall: false`). Together these prove the delete ran and the app recovered.

## Evidence strength — stated honestly

Item 4's post-conditions are machine-verified and reproducible. **Items 1, 2, 3, 5 and item 4's
process count are tester attestations without retained verbatim transcripts.** The acceptance
criteria asked for concrete captured strings (URLs, clipboard values, `pgrep` output); those were
not preserved. This is called out here and in `34.3-LIVE-GATE.md` rather than papered over, because
this plan's own threat T-34.3-36 names precisely this failure mode. The attestations come from the
person who ran the builds and are recorded in good faith — they are simply weaker than specified.
