## Decisions Made

- **`clearCache`'s `refreshLibrary` push rides `pushFrontendMessage` from `./sidecarRpc` directly**, per the plan's own interfaces section, rather than `sendFrontendMessage` from `../ipc` — both resolve to the identical `frontendMessage` frame under the sidecar (`getMainWindow()` always resolves electronStub's `fakeWindow`), but this keeps the channel's own dependency surface minimal and explicit.
- **No build-conditional branch anywhere.** `resetHeroic()` is called completely unmodified from `utils.ts`; the `app.relaunch()` → `app.quit()` ordering race is explicitly deferred to plan 34.3-05, exactly as the plan specifies.
- **The dialog title assertion targets the code's own inline i18next default ('Cache Cleared'), not the real locale file's value ('Cache cleared').** Under jest, `electronStub`'s `app.getAppPath()` resolves to `process.cwd()` — this jest project's root (`src/backend`), not the repo root where `public/locales/en/translation.json` actually lives (the `publicdir-getapppath-chunking` gotcha family). So `i18next.t()` genuinely runs (proven by NOT resolving to the raw key `box.cache-cleared.title`, which is what the project-wide `i18next` automock would produce), but its resource load never finds the real translation file, so `t()` falls back to its own provided default. This matches the plan's own acceptance criterion (`'Cache Cleared'`, not the key) exactly and is the correct assertion — the packaged-build half of this path is a named, pre-existing deferred-UAT item (34.3-RESEARCH.md), not something this plan can or should prove under jest.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 - Blocking] `clearCache`'s real body throws on its own dependencies without additional test mocking**
- **Found during:** Task 2 (initial test run — `clearCache(showDialog=false)` failed with `refreshFrame` undefined)
- **Issue:** `utils.ts`'s real `clearCache()` calls `.clear()` on `installStore`/`libraryStore` from `backend/storeManagers/legendary/electronStores`, but the existing (34.3-01-era) mock for that module only exposed `gameInfoStore`. The missing two threw synchronously, caught by `clearCache`'s own try/catch but BEFORE `pushFrontendMessage('refreshLibrary')` ever ran.
- **Fix:** Extended the mock to include `installStore: { clear: jest.fn() }` and `libraryStore: { clear: jest.fn() }` alongside the existing `gameInfoStore`.
- **Files modified:** `src/backend/sidecar/__tests__/shellFilesFlows.test.ts`
- **Verification:** `clearCache(showDialog=false)` test passes; `refreshFrame` now defined.
- **Committed in:** `188a9338` (Task 2 commit)

**2. [Rule 3 - Blocking] `clearCache`'s fire-and-forget legendary-cleanup dynamic import reaches real runner-spawn machinery**
- **Found during:** Task 2 (same run — subsequent `TypeError: createAbortController is not a function`, then unhandled-rejection cascades from `launcher.ts`'s real `callRunner`/`spawn()`)
- **Issue:** `utils.ts`'s `clearCache()` body (Electron parity, unmodified) ends with a fire-and-forget `import('./storeManagers').then(({ libraryManagerMap }) => libraryManagerMap['legendary'].runRunnerCommand({ subcommand: 'cleanup' }, ...))`. Without a mock, this reaches the REAL legendary runner machinery (`launcher.ts`'s `callRunner`, an actual `child_process.spawn()` attempt), which crashed on a missing `createAbortController` export from the existing (narrower) `aborthandler` mock and would otherwise have spawned a real process.
- **Fix:** Added a narrow `jest.mock('backend/storeManagers', () => ({ libraryManagerMap: { legendary: { runRunnerCommand: jest.fn() } } }))`, mirroring `gameDetailsFlows.test.ts`'s/`downloadQueueFlows.test.ts`'s own `backend/storeManagers` mock precedent. This keeps `clearCache`'s test coverage focused on its own behavior (store clears + `refreshLibrary` + dialog) rather than reaching real runner internals — a scope boundary this plan's own channel doesn't own.
- **Files modified:** `src/backend/sidecar/__tests__/shellFilesFlows.test.ts`
- **Verification:** All `clearCache`/`clearAchievementCache`/`resetHeroic` tests pass with zero unhandled rejections.
- **Committed in:** `188a9338` (Task 2 commit)

**3. [Rule 1 - Bug] `showDialogBoxModalAuto` mock's baked-in real implementation silently no-op'd after the first test**
- **Found during:** Task 2 (the `clearCache(showDialog=true)` test consistently failed to observe a `showDialog` frame, despite `jest.mocked(showDialogBoxModalAuto).mock.calls` proving the mock WAS invoked with the correct arguments)
- **Issue:** `src/backend/jest.config.js` sets `resetMocks: true` project-wide, which wipes ANY implementation set on a mock (including one baked into a `jest.mock(...)` factory via `jest.fn(realImpl)`) before EVERY test, replacing it with a no-op returning `undefined`. The original mock design assumed the factory's `jest.fn(realImpl)` would persist as the default across tests except where explicitly overridden — it does not, under this project's jest config. This was diagnosed by hand: an "always throw" stand-in implementation neither threw nor logged anything, while `mock.calls.length` still incremented, proving the call was recorded but the implementation itself was never invoked.
- **Fix:** Reduced the mock factory to a bare `jest.fn()` and added a `beforeEach` inside the new describe block that re-installs the real implementation (`jest.requireActual('../../dialog/dialog').showDialogBoxModalAuto`) AFTER jest's own automatic reset runs (Jest runs nested `beforeEach` hooks outer-to-inner, so this lands after the file's own top-level `beforeEach`). The one test that needs a synthetic failure still overrides it per-call via `mockImplementationOnce`, which is unaffected by `resetMocks` since it's set fresh inside the test body.
- **Files modified:** `src/backend/sidecar/__tests__/shellFilesFlows.test.ts`
- **Verification:** All 3 `clearCache` dialog-path tests pass; hand-confirmed by temporarily reverting to the "always throw" implementation and observing it silently fail to fire (the original bug reproduced), then restoring the fix.
- **Committed in:** `188a9338` (Task 2 commit)
