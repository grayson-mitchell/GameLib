## Summary

This slice ports 29 shell/files/logger/clipboard IPC channels onto the Tauri Node sidecar and
adds one new Rust seam (`tauri-plugin-clipboard-manager`, two dispatch arms). The port itself is
unusually well-executed: every registration was cross-checked against `main.ts`'s exact
`addListener`/`addHandler` call for parity (verified independently against `main.ts`,
`logger/ipc_handler.ts`, and `utils/ipc_handler.ts` during this review — every channel's
send-vs-invoke kind, argument shape, and body match their Electron counterpart exactly), the
`D-14` curated-import discipline holds (no accidental double-registration via a side-effect
import of `logger/ipc_handler.ts`/`utils/ipc_handler.ts`), and the test suites are unusually
rigorous — they assert real side effects (actual file deletion, actual log-file content, actual
send-vs-handle registry state) rather than "didn't throw," and several tests are explicit
RED-proof exercises against the exact defect class they exist to prevent (e.g.
`loggerCallSiteGuard.test.ts`'s stub-free ENOTDIR proof, `tauriShellSource.test.ts`'s
block-comment-survival self-tests). The clipboard capability claim ("zero renderer capability
grant") was verified directly against `src-tauri/capabilities/default.json`: no `clipboard`
string appears anywhere in the file, confirmed by that file's own test assertion.

One genuine BLOCKER was found in `electronStub.ts`'s new relaunch/quit race guard (D-06): a
failed or timed-out relaunch request permanently and silently disables `app.quit()`/`app.exit()`
for the remaining life of the process, and this exact failure path has zero test coverage (every
`lifecycleStub.test.ts` case programs the mock to resolve, never reject, for a relaunch). One
WARNING was found in the new clipboard read path: a normal, everyday clipboard state (the
clipboard holding an image, not text) is indistinguishable from a genuine transport failure in
the logs.

## Critical Issues

### CR-01: A failed/timed-out `app.relaunch()` permanently disables `app.quit()`/`app.exit()`

**File:** `src/backend/sidecar/electronStub.ts:170-227`

**Issue:** The D-06 race guard added by this phase sets the module-scope flag
`relaunchInFlight = true` **synchronously, before** dispatching the relaunch request, and by
design (per the code's own comment) **never resets it**:

```ts
let relaunchInFlight = false
...
relaunch: (): void => {
  relaunchInFlight = true
  requestRustInvoke(RUST_APP_RELAUNCH, []).catch((error) => {
    console.warn(`[electronStub] app.relaunch(): ${RUST_APP_RELAUNCH} failed:`, ...)
  })
},
```

`quit()`/`exit()` both check `relaunchInFlight` first and no-op (with only a `console.warn`) if
it is `true`. The design assumes a dispatched relaunch is always terminal for the process ("a
relaunch is terminal for this process ... the process is about to be replaced"). That assumption
does not hold for every failure mode of `requestRustInvoke(RUST_APP_RELAUNCH, [])`:

- `requestRustInvoke` is a real request/response round trip bounded by a 60-second timeout
  (`RUST_INVOKE_TIMEOUT_MS`, `sidecarRpc.ts:58,296-297`).
- Rust's `"app_relaunch"` dispatch arm (`src-tauri/src/main.rs:653-655`) calls `app.restart()`
  and **never writes a response frame** for this request under normal operation (`app.restart()`
  is documented as never returning on this call path) — so the JS-side promise is left pending
  for as long as the process survives.
- If the OS-level restart is ever delayed, silently fails, or the response frame is otherwise
  lost (a transport hiccup, a future Tauri/runtime regression, anything short of "the process was
  actually replaced within 60s"), `requestRustInvoke` rejects with a timeout error. The `.catch`
  above only logs a warning — `relaunchInFlight` is never reset.
- From that point forward, **every subsequent `app.quit()`/`app.exit()` call in that process is a
  permanent no-op** — including the ordinary "Quit" path (`handleExit()` → `app.exit()`,
  registered by `appShellFlowRegistration.ts`'s `quit` channel) and a second `resetHeroic()`
  attempt. The app becomes unkillable through the sidecar for the rest of that session.

This is exactly the failure mode the review brief asked to check for ("is there any path where
quit is permanently disabled?") — there is one, and it is reachable by any transport failure on
the one new call this phase added, not merely a theoretical edge case: `resetHeroic()`
(`utils.ts:466-476`, unmodified) calls `app.relaunch()` immediately followed by `app.quit()` in
the same tick, so this guard is exercised on every reset/relaunch attempt in production.

No test in `lifecycleStub.test.ts`'s `electronStub app.relaunch/quit race guard` describe block
covers a **failed** relaunch — `loadFreshApp()`'s `mockInvoke` is always programmed to
`Promise.resolve(null)`. A rejected-relaunch-then-quit test would fail against the current
implementation.

**Fix:** Only suppress quit while the relaunch is genuinely still pending, and clear the flag on
a confirmed failure, e.g.:

```ts
relaunch: (): void => {
  relaunchInFlight = true
  requestRustInvoke(RUST_APP_RELAUNCH, []).catch((error) => {
    // The relaunch demonstrably did not happen -- stop suppressing quit()/exit() so the
    // process remains killable through the ordinary paths.
    relaunchInFlight = false
    console.warn(
      `[electronStub] app.relaunch(): ${RUST_APP_RELAUNCH} failed:`,
      error instanceof Error ? error.message : String(error)
    )
  })
},
```

(The success path still never resolves/settles under normal operation, so this does not
reintroduce the original ordering race — it only removes the permanent-lockout failure mode.)

## Warnings

### WR-01: `clipboardReadText` logs a false-positive "failed" warning for ordinary non-text clipboard content

**File:** `src/backend/sidecar/clipboardFlowRegistration.ts:90-101`,
`src-tauri/src/main.rs` (`clipboard_read_text` arm / `clipboard_read_value`, ~lines 361-371,
616-618)

**Issue:** `tauri-plugin-clipboard-manager` (backed by `arboard`, per `Cargo.lock`) returns `Err`
from `read_text()` when the OS clipboard holds no text representation at all — e.g. the user
copied an **image** rather than text, a completely ordinary scenario for this codebase's own
caller (`EditGameDialog.tsx`'s "paste cover/square art URL from clipboard" button, which a user
is just as likely to trigger right after copying an image from a browser as after copying a
URL). `clipboard_read_value` propagates that `Err` unchanged, and
`clipboardFlowRegistration.ts`'s handler cannot distinguish it from a genuine RPC/transport
failure — both paths hit the same `catch` block and produce an identical
`console.warn('[clipboardFlowRegistration] clipboardReadText failed:', error)` before resolving
`''`:

```ts
ipcMain.handle('clipboardReadText', async () => {
  try {
    const text = await requestRustInvoke(RUST_CLIPBOARD_READ_TEXT, [])
    return typeof text === 'string' ? text : ''
  } catch (error) {
    console.warn('[clipboardFlowRegistration] clipboardReadText failed:', error)
    return ''
  }
})
```

Real Electron's `clipboard.readText()` never throws for non-text content — it simply returns
`''` silently. Under the sidecar, the exact same everyday user action now emits a warning-level
log line that reads as a transport/backend failure. This is purely a log-noise/diagnosability
issue (the functional result — an empty string, silently ignored by
`EditGameDialog.handlePasteFromClipboard`'s `if (!text) return` — is correct either way), but it
means a genuine transport failure is no longer distinguishable in the logs from routine clipboard
use, undermining the very diagnostic value this warning exists to provide.

**Fix:** Distinguish the two cases before logging, e.g. have the Rust arm resolve
`Ok(Value::String(String::new()))` for the "no text on clipboard" case (mirroring how an empty
clipboard is already handled) rather than an `Err`, reserving `Err` for actual plugin/transport
failures; or, on the TS side, only `console.warn` when the error does not look like arboard's
"content not available" class of error.

## Disposition (orchestrator, 2026-07-27)

**CR-01 — FIXED** in commit `bae2c4cd`.

Verified independently before acting: the finding is correct. `relaunchInFlight` was set
synchronously and never released, and reaching `relaunch()`'s `.catch` means the relaunch did NOT
happen (on the success path the promise never settles — Rust's `app_relaunch` arm sends no response
frame and the process is replaced first). So the process survives with the flag stuck `true`,
making `app.quit()`/`app.exit()` permanent no-ops including the ordinary Quit menu path —
force-quit only. `resetHeroic()` runs this guard on every reset.

Fix releases the flag in that `.catch`. Safe by construction: a rejected relaunch leaves no pending
relaunch frame for an exit frame to race against, which is the sole thing the guard prevents. The
success-path lifetime is unchanged.

Also added the missing test — every pre-existing race-guard case resolved the mock, so the
failed-relaunch path had zero coverage. RED-proved: removing the release line fails the new test.

**WR-01 — ACCEPTED, carried forward. Not fixed.**

Confirmed diagnostics-only, not a functional defect: `clipboardReadText` already resolves `''` on
any error, so there is no crash and no unhandled rejection (it correctly honors the recorded
"a rejecting stub hard-crashes the sidecar" gotcha). The real cost is that benign non-text
clipboard content (a copied image) emits the same `console.warn` as a genuine transport failure,
degrading that warning's diagnostic value on an everyday path via `EditGameDialog`.

Not fixed because the fix requires changing the Rust arm's error contract, which would invalidate
the packaged build that this phase's blocking live gate was just run against — a real cost for a
log-clarity gain. Carried as a documented warning, following this repo's established pattern
(Phase 32 carried three warnings into Phase 33).

Suggested fix when next touching that arm: have `clipboard_read_value` distinguish arboard's
"no text on the clipboard" case from a genuine failure, and have the JS side log the former at
debug level (or not at all) while keeping `warn` for real failures.
