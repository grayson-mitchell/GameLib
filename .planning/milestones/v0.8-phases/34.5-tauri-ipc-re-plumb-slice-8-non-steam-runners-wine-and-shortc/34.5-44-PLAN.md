## D-44-A — the single-instance guard is HAND-ROLLED and std-only. No crate is added.

**Chosen:** a `#[cfg(unix)]` `std::os::unix::net::UnixListener` / `UnixStream` pair on a socket file
under the app-support directory, with a `#[cfg(not(unix))]` no-op stub.

**Rejected:** `tauri-plugin-single-instance` and `tauri-plugin-deep-link`.

Three reasons, in order of weight:

1. **Functional, not merely hygienic.** `tauri-plugin-single-instance` registers itself as a Tauri
   plugin, so the secondary process must construct and run the Tauri application before the plugin
   can tell it that it is secondary. In this codebase `.setup()` calls `spawn_sidecar(app.handle())`
   as its **first statement** (`main.rs:5073`) — so a plugin-based guard would still spawn a second
   Node sidecar, which is precisely half of what gate 3 recorded. A guard that runs before
   `tauri::Builder::default()` and calls `std::process::exit(0)` cannot spawn anything.
2. **Supply chain.** `34.5-RESEARCH.md`'s `## Package Legitimacy Audit` reads "Not applicable — no
   new packages are installed by this phase (confirmed above). `slopcheck` was not run because there
   is nothing to check." A hand-rolled guard keeps that statement true, keeps this plan
   `autonomous: true`, and means threat `T-34.5-G6-SC` below stays a no-op assertion rather than a
   blocking human checkpoint. Per the outline's own instruction, this was the preferred branch.
3. **Attack surface.** A Unix socket inside a `0700` directory is guarded by filesystem permissions.
   The obvious cross-platform std alternative — a `127.0.0.1` TCP listener plus a port file — is
   reachable by **any** local process and by any web page the user has open, which would make
   `gamelib://launch` remotely triggerable. That is not acceptable at ASVS L1 (see T-34.5-G6-20).

**Accepted cost, recorded rather than hidden:** `std::os::unix::net` does not exist on Windows, so
the `#[cfg(not(unix))]` arm is a no-op that always reports "primary". Windows therefore keeps
**exactly today's behaviour** (a second launch starts a second instance) — this is not a regression,
but it is an unclosed hole and gets ledger row `U-34.5-18`. GameLib currently ships macOS-only
(Phase 34.9's x64 leg does not exist), so this is the correct place to spend the budget.

## D-44-C — `src/backend/shortcuts/shortcuts/shortcuts.ts` is NOT modified, and here is why.

Reading `generateMacOsApp` at planning time surfaced a **new defect the brief does not name**: the
`run.sh` body is built as an **unquoted** template — `${app.getPath('exe')} --no-gui
gamelib://launch?appName=${app_name}&runner=${runner}` (`shortcuts.ts:227-229`). In `bash`, the
unescaped `&` is a control operator: the shell backgrounds `<exe> --no-gui
gamelib://launch?appName=X` and then evaluates `runner=Y` as a standalone variable assignment. The
`runner` parameter is therefore **silently lost** from the macOS `.app` path, and the launch is
backgrounded.

This is NOT fixed here, deliberately. `U-34.5-12`'s retirement condition names the **unquoted** form
verbatim as the body it expects to observe; quoting it would move that row's own bar underneath it,
which is exactly the struck-precondition failure mode `34.5-UNTESTED-ITEMS.md`'s preamble exists to
prevent (Phase 34.4.1's gate passed 4/4 that way). Instead:

- The defect is recorded as ledger row **`U-34.5-19`** in Task 3.
- This plan's Rust parser and its tests are made **explicitly tolerant** of the runner-less
  truncated URL, so the macOS `.app` path still launches the right game via `findGame`'s all-runner
  search — a Rust test case and a `protocol.test.ts` case both pin that behaviour.

## D-44-D — `U-34.5-16` (`getInstallInfo` timeout) IS absorbed into this plan.

Plan `34.5-43` could not add `getInstallInfo` to `LONG_RUNNING_CHANNELS` because this plan owns
`src-tauri/src/main.rs` in wave 1, and transferred the hole to `U-34.5-16` (threat `T-34.5-C6-06`).

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Steam client / desktop `.app` → `gamelib-shell` argv | Fully attacker-influencable if the VDF or `run.sh` is writable by another local process; the string is Electron-shaped and carries flags this shell has no meaning for. First crossing of untrusted input. |
| Any local process → the single-instance Unix socket | **New in this plan.** A local peer can connect and write one line that becomes a `gamelib://` deep link inside the running instance. |
| Rust shell → sidecar stdin (newline-delimited JSON-RPC) | A control character inside a forwarded value could split or forge a frame. |
| `handleProtocol` → `handleLaunch` → `libraryManagerMap[runner].getGame(...)` | The deep link chooses which owned game is launched, and (via `altExe`) can name an executable path. |

|-----------|----------|-----------|-------------|-----------------|
| T-34.5-G6-20 | Elevation of privilege | a `gamelib://` URL arriving on the single-instance socket and reaching `handleLaunch` | mitigate | Three independent layers, none sufficient alone: (1) the socket lives inside a directory created `0700` via `DirBuilderExt::mode`, and the socket file itself is `set_permissions(0o600)`, so a different local user cannot connect at all; (2) the Rust accept loop re-validates every received line through the SAME `protocol_url_arg` allow-list used for argv, never trusting the socket because it is "internal"; (3) `bootstrap.ts`'s `handleProtocolUrl` handler independently re-checks `typeof url === 'string' && url.startsWith('gamelib://')` and throws otherwise.
