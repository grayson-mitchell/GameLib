### 34.5-43 — port `getInstallInfo`, reconcile the inventory

Closes **F-34.5-G6-10** and satisfies the first half of **U-34.5-14** (the second half is 34.5-49's
audit). `getInstallInfo` is a real preload channel (`src/common/types/ipc.ts:218`,
`src/preload/api/helpers.ts:43`) registered only on the Electron side at `src/backend/main.ts:843`
as `libraryManagerMap[runner].getInstallInfo(...)`; every details-screen open emits
`[GAMELIB_UNPORTED_CHANNEL] No handler registered for channel 'getInstallInfo'` and the page does not
render (12+ rejections across two GOG titles, installed and not-installed, so it is neither
target- nor state-specific). Register it in `src/backend/sidecar/gameDetailsFlowRegistration.ts` —
**not** `steamFlowRegistration.ts`, which plan 34.5-46 owns in wave 2 — mirroring that module's
existing `ipcMain.handle` argument-unpacking shape and the load-bearing `import '../storeManagers'`
first-import discipline. **Trap:** `ported-channels-gate.py` asserts the 38+3+16=57 split reconciles
internally against `IPC-PORT-INVENTORY.md`; adding a 39th ported channel breaks those assertions, so
the plan must extend the script's declared sets and arithmetic deliberately (and re-run
`--self-test`), never weaken an assertion to make it pass. Second trap: this adds a registration edit,
so `electronReachLedger.test.ts`'s baseline must be **regenerated by measurement**, never transcribed
(REQ-34.5-10). Four frontend callers exist (`GamePage`, `DownloadDialog`, `ModifyInstallModal/GOG`,
`DLCList/DLC`) — the port must satisfy all of them, not just the details screen.

### 34.5-44 — shortcut launch: argv, single instance, deep link

Closes **F-34.5-G6-09** / **U-34.5-13**. Gate 3 ran the VDF's own recorded invocation
(`gamelib-shell --no-gui --no-sandbox "gamelib://launch?appName=…&runner=gog"`) and it booted a
second full GameLib instance: `--no-gui` ignored, the deep link ignored (zero `handleProtocol`
lines), the running instance undetected. Confirmed at planning time: `src-tauri/src/main.rs` contains
**no** `gamelib://`, `--no-gui`, deep-link or single-instance handling of any kind, while the Node
side already has a complete `handleProtocol` (`src/backend/protocol.ts:46`, with `parseHeroicUrl`,
`handleLaunch` and `shouldHideWindowForProtocolArgs`) and `isCLINoGui`
(`src/backend/constants/environment.ts:35`) reads `process.argv` of the *sidecar*, not the shell.
The plan must extract pure Rust helpers (URL extraction, `--no-gui` detection, ignore `--no-sandbox`)
with `#[cfg(test)]` tests in the established `clipboard_text_arg` / `login_window_url_arg` style, add
a single-instance guard, and forward the URL to the sidecar so `handleProtocol` runs.
**Trap — supply chain:** `34.5-RESEARCH.md`'s `## Package Legitimacy Audit` reads "Not applicable —
no new packages"; prefer a hand-rolled std-only single-instance guard so that stays true. If the plan
instead adds `tauri-plugin-single-instance`/`tauri-plugin-deep-link`, it MUST update that audit and
carry a `checkpoint:human-verify gate="blocking-human"` before the `cargo add`, per the phase's
`T-34.5-*-SC` threat. Retirement bar to design against: a `handleProtocol` line in `gamelib.log`,
the named game launching, and **exactly one** `gamelib-shell` process.

### 34.5-46 — runner-aware `launch`, and the uninstall-reflection question

Closes the UAT gap *"Pressing Play on a GOG game launches it through its own runner"* (observed
twice: `[Steam]: SteamGame: launching appId 1207659037 via steam://rungameid/1207659037` for a GOG
title, once **after** the uninstall completed). Root cause located at planning time:
`src/backend/sidecar/steamFlowRegistration.ts:238`'s `handleLaunch` does
`const game = new SteamGame(appName)` unconditionally, ignoring `runner` entirely — structurally the
same runner-blind dispatch defect plan 34.5-33 fixed for `refreshLibrary` in the same file, and the
module docstring says so in its own words. The fix dispatches through
`libraryManagerMap[runner].getGame(appName)` (the shape `launcher.ts:111`'s `launchEventCallback`
uses) while respecting that module's deliberate curated-import fence — do **not** pull the whole
`launcher.ts` Wine/GameConfig/DownloadManager pipeline into the sidecar's import graph to solve it.
Second task: the routing file says **check first** whether `eb117d9e4` already fixes the
uninstall-not-reflected symptom rather than assuming it — `gogInstalledGamesStore` is a `BOOT_SET`
store and the resolved debug file names it explicitly, so prove the sidecar's uninstall write reaches
`notifyStoreChanged` with a test, and hand the live confirmation to the gate contract as an
observation. **Trap:** a non-Steam Steam shortcut is addressed by a computed 64-bit shortcut id,
never by the source store's appName, so "make the Steam path use the right id" is the wrong fix — the
defect is dispatch, before any shell invocation.

### 34.5-48 — EOS deferred cluster declines honestly

Closes the UAT gap *"A deferred/unported channel declares itself unavailable rather than simulating
success"*. The panel at `src/frontend/screens/Settings/sections/AdvancedSettings/index.tsx` renders
"not installed" + Install, shows an installing state with a Cancel button, and reverts on cancel,
while `grep -ic -E "eos|overlay"` over the whole session log returns **0** — not one
`[GAMELIB_UNPORTED_CHANNEL]` rejection for any of the 8 deferred EOS channels. The mechanism is
visible in the source: three bare `useEffect`s await `window.api.getEosOverlayStatus()`,
`getLatestEosOverlayVersion()` and `isEosOverlayEnabled()` with no catch, so a rejection leaves the
optimistic `useState(false)` defaults standing; and `installEosOverlay()` sets
`setEosOverlayInstallingOrUpdating(true)` before an `await` that throws, so the matching `false` never
runs — producing a permanent "installing" state whose Cancel reaches a real `abort` and logs
`Could not find a matching abort controller`. **First establish why zero rejections were logged**
when `getInstallInfo` logged 16 (the channels *are* exposed via `makeHandlerInvoker` in
`preload/api/settings.ts:40-41` and `menu.ts:10`) — that discrepancy is load-bearing and must not be
assumed away. Copy the model that already behaves correctly in the same session: the `[WebView]`
deferral names itself, names its deferral (D-05) and declines visibly. **Trap:** plan 34.5-13's SEAM
Invariant B test proves the 19 names are absent from the **registries**; both statements are true and
that is exactly why it cannot catch this class — the new assertion must target the **call site**, not
the registry, and must be shown RED against a known-bad input. This plan fixes how the 16 deferred
channels *decline*; it ports none of them (Phase 34.6 owns that).

## Standing rules every plan below inherits

1. **Ledger Rule 1** — a row retires ONLY by the observation named in its own cell.
2. **Ledger Rule 2** — any plan creating a new untested hole adds its row in the same commit.
3. **Ledger Rule 3** — the gate contract names every OPEN row its items would have covered.
4. **A green suite is necessary and never sufficient** — this phase's live gate has beaten a green
   suite three times. A test that reconstructs the call site instead of importing the production
   wiring is a replica and drifts silently.
5. **A gotcha comment at one call site is a debt marker, not a fix** — sweep the siblings.
6. **Weight test design over explanatory fit** — when two readings both fit, build the discriminator.
7. **`security_enforcement` is on (ASVS L1, block on `high`):** every PLAN.md carries a real
   `<threat_model>`. This cycle touches the keyring arm, shortcut launch targets carrying a
   `gamelib://` deep link, and an audit that enumerates the whole IPC attack surface — the registers
   must be specific, not boilerplate.
