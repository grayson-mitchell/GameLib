## Finding: T-34.5-G6-14 (row 24, plan 34.5-25) — CLOSED 2026-08-20 (quick-260820-fyl)

Declared mitigation: *"setToken/clearToken invalidate the success cache, the failure memo AND the
in-flight promise before issuing their underlying call."*

`SidecarKeyringSlotStore.invalidateCache()` (`src/backend/sidecar/keyringTokenStore.ts:435-440`)
clears `cachedToken`, `cachedAvailable`, `failedTokenAt` and `failedTokenReason` — but does **not**
touch `pendingToken`/`pendingAvailable`. The method's own doc comment (lines 428-433) states this
explicitly: *"Does NOT touch an in-flight `pendingToken`/`pendingAvailable` promise — that request
was already sent and will resolve (and cache) independently."* `fetchToken()` (line ~340) writes
`this.cachedToken = { value }` unconditionally when its in-flight read resolves, with no check for
an intervening `clearToken()`.

Concrete race: a `getToken()` call starts, sets `pendingToken`; `clearToken()` (sign-out) runs
concurrently, invalidates the (now-empty) cache, and issues `keyring_delete`; the earlier
`fetchToken()` then resolves with the **pre-signout** value and writes it into `cachedToken`,
resurrecting the signed-out session for every subsequent `getToken()` call until the next explicit
invalidation — exactly the threat class T-34.5-G6-14 is named for ("failure memo resurrecting a
signed-out session"), just via the success path rather than the failure-memo path the title names.

No test covers this. `keyringTokenStore.test.ts` has two `clearToken()`-invalidation tests (lines
599, 733) but both are strictly sequential (`await store.clearToken()` fully settles, *then*
`getToken()` is called) — neither drives a `getToken()` that is still in flight when `clearToken()`
starts, so the declared "in-flight promise" invalidation is asserted nowhere.

The cache/failure-memo halves of the declared mitigation ARE present and tested. Only the
"in-flight promise" clause is false against the code. Recommend either (a) implementing the
invalidation (e.g. a monotonic epoch counter checked by `fetchToken`/`fetchAvailable` before
writing back), or (b) re-registering this residual explicitly as `accept` with the same "abandoned,
not cancelled" rationale `bounded_keyring_read` already carries on the Rust side (main.rs:3061-3085)
— the code comment already gestures at this rationale but the register never adopted it as the
disposition.

**CLOSED 2026-08-20 (quick-260820-fyl).** Option (a) was implemented: a monotonic `cacheEpoch` on
`SidecarKeyringSlotStore`, bumped by `invalidateCache()`, captured at entry by
`fetchToken()`/`fetchAvailable()` and checked before every write-back. This gates FOUR sites, not
just the `cachedToken` write this finding cited — the failure-memo arm and clear, and the
`cachedAvailable` write, carried the identical unconditional-write defect and are closed by the
same guard.

This finding's own observation — *"No test covers this ... both are strictly sequential"* — is now
discharged: three concurrent tests were added to `keyringTokenStore.test.ts`, each driving a
genuinely in-flight read/probe across `clearToken()` rather than a sequential one, each RED-proven
by removing only its own guard and confirming the mapped test fails before restoring it. See
`.planning/quick/260820-fyl-fix-t-34-5-g6-14-keyring-cacheepoch-gene/SUMMARY.md` for the verbatim
failure output.
