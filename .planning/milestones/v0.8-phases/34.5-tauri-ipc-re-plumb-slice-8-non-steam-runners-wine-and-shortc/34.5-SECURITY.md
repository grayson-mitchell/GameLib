## How this register was built, and why the unit matters

**362 audit units across 281 distinct threat IDs.** The register is keyed by
**`(plan, threat_id)`**, never by threat ID alone and never by range.

Two census errors were caught while building it, both of which would have produced a
falsely-clean result:

1. **Namespace blindness.** A first pass grepping `T-34\.5-[0-9]+` found **67** IDs. The real
   register is **281**, because the gap cycles use namespaced IDs (`T-34.5-G6-*`, `-C4-*`,
   `-C5-*`, `-C6-*`, `-C7-*`) that the pattern cannot match. Auditing on 67 would have skipped
   **214 IDs — 76% of the phase.**
2. **Range-shaped coverage claims.** The SUMMARY files assert coverage as ranges
   (*"T-34.5-18 through T-34.5-22, all mitigate"*). A range is not per-ID evidence; it is the
   exact shape that lets an uncovered ID hide inside a passing statement. Every range was
   expanded and every ID scored on its own named mitigation.

30 threat IDs recur across plans with **different mitigation text each time** (`T-34.5-SC`
alone appears in 21 plans), which is why the ID alone is the wrong key.

**Also noted:** 41 of 61 SUMMARY files have no `## Threat Flags` section at all. Absence of a
flag was treated as *not* evidence of closure.

### R2 — CLOSED 2026-08-20 — A promised `grep` assertion that does not exist (2 rows, Elevation of Privilege)

| Threat ID | Plan |
|---|---|
| `T-34.5-17` | 34.5-05 |
| `T-34.5-32` | 34.5-09 |

The register states: *"`grep` asserts no `process.platform`/`isMac`/`isLinux` branch was
introduced outside comments"* in `src/backend/sidecar/wineToolsFlowRegistration.ts`.

The invariant is **true today** — a comment-stripped scan finds zero live occurrences (only
comment references at lines 207, 218, 222). **The assertion does not exist.** Searched
`wineToolsFlows.test.ts`, `runnerSliceRegistration.test.ts`, `testContainment.test.ts`,
`sidecarRejectionGuard.test.ts`. The `stripSourceComments` + `not.toMatch(/process\.platform/)`
pattern exists only in `humbleLoginFlows.test.ts`, guarding a **different module**
(`humble/loginWindowSeam.ts`) for a **different requirement** (REQ-34.4.1-13).

A future edit reintroducing a platform branch ships with zero CI signal. Classified OPEN on the
rule that *a grep assertion must be able to fail against a known-bad input* — here there is no
assertion to fail. "True today by inspection" is a coincidence, not a control.

**CLOSED 2026-08-20 (quick-260820-ic0).** The fix taken was to BUILD the declared control, not to
change the guarded module — `wineToolsFlowRegistration.ts` is byte-identical to its pre-task
state and the invariant it asserts was already true.

The control lives in Describe 6 of `src/backend/sidecar/__tests__/wineToolsFlows.test.ts`,
reading the module with `readFileSync` and the shared `backend/testUtils/stripSourceComments`,
asserting zero hits for `process.platform`, `\bisMac\b`, `\bisLinux\b`.

It is RED-proven by specimens derived by INSERTING real branch shapes
(`if (isMac) { return true }`, `if (!isLinux) { return }`,
`if (process.platform === 'darwin') { return true }`) into the real source text, run through the
same `platformTokenHits()` helper as the live assertion — so the RED-proof exercises the gate
itself, not a parallel copy of its regex.

Word-boundary decision: `isMac`/`isLinux` are short substrings, and this repo really does contain
`isMacNative`, `isMacOSUpToDate`, `isLinuxNative`, `isLinuxFamily` and `effectiveIsMacNative`; a
naive `includes()` would have matched all of them. Covered by a dedicated false-positive control
asserting all five are rejected.

Filled-specimen property: the raw module DOES contain all three tokens (in D-13 comments), so a
broken comment stripper turns the gate RED rather than silently vacuous — asserted explicitly.

Correction to this finding's own text: the comment references are at lines **204, 207, 218, 220,
222** — five lines, not the three listed above.

**What this gate does NOT prove:** it is a source-text gate over ONE file, keyed to the three
tokens the mitigation named. It does not cover `isWindows`, does not cover platform branching
reached indirectly (e.g. a helper in another module that itself branches), does not cover a token
appearing inside a string literal, and asserts nothing about runtime behaviour. A behavioural
adversarial-platform test was considered and deliberately NOT written: the declared mitigation is
a source-text grep and this closure delivers the mitigation as declared. If behavioural coverage
is wanted later it is new scope, not a gap in this closure.

### R3 — CLOSED 2026-08-20 — Keyring cache resurrects a signed-out session (1 row, Elevation of Privilege)

`T-34.5-G6-14` — plan 34.5-25. **The only open row that is a live code defect.**
Independently re-verified during this audit, not taken on the auditor's word.

Declared mitigation: *"setToken/clearToken invalidate the success cache, the failure memo
**AND the in-flight promise**."*

Implementation does the first two only. `keyringTokenStore.ts:435-440` clears `cachedToken`,
`cachedAvailable`, `failedTokenAt`, `failedTokenReason`; its own doc comment states it
*"Does NOT touch an in-flight `pendingToken`/`pendingAvailable` promise."*

The consequence is at `keyringTokenStore.ts:347`:

```ts
const value = typeof result === 'string' ? result : ''
this.cachedToken = { value }        // unconditional — no generation/epoch check
```

A read in flight when `clearToken()` fires resolves afterwards and writes its **pre-signout**
value back into `cachedToken`. Tests at `keyringTokenStore.test.ts:599,733` exercise
invalidation **sequentially only**; nothing drives a concurrent in-flight `getToken()`.

Two facts make this practical rather than theoretical: the race window is bounded by
`KEYRING_READ_TIMEOUT` = **45 seconds**, and `34.5-KEYRING-ARM-SESSION.md` recorded keyring
reads racing Keychain approval at roughly **9:1**. "Sign out while a Keychain prompt is still
pending" is a plausible sequence.

The code's rationale — mirroring `bounded_keyring_read`'s *"abandoned, not cancelled"* on the
Rust side — is defensible; you cannot un-send the request. **But it was never adopted as this
row's disposition, and the register still claims the in-flight promise is invalidated.**
Resolve by adding a generation counter so a stale resolve cannot write, or by amending the
register and logging an accepted risk. Do not leave the two disagreeing.

**CLOSED 2026-08-20 (quick-260820-fyl).** The fix taken: a monotonic `cacheEpoch` on
`SidecarKeyringSlotStore`, bumped by `invalidateCache()`, captured at entry by
`fetchToken()`/`fetchAvailable()`, gating FOUR write sites — the success cache (`cachedToken`),
the failure-memo arm (`failedTokenAt`/`failedTokenReason`), the failure-memo clear, and the
availability cache (`cachedAvailable`). This is one more write site than this finding's own
audit cited — the audit named only `cachedToken` at `keyringTokenStore.ts:347`; the failure-memo
arm/clear and the availability cache carried the identical unconditional-write defect and are
closed by the same fix.

Verified by three concurrent tests in `keyringTokenStore.test.ts` (`in-flight read superseded by
clearToken() -- cache epoch guard (quick-260820-fyl, T-34.5-G6-14)`), each RED-proven by removing
only its own guard and confirming the mapped test fails before restoring it — recorded verbatim
in `.planning/quick/260820-fyl-fix-t-34-5-g6-14-keyring-cacheepoch-gene/SUMMARY.md`. The two
pre-existing sequential invalidation tests this finding cited as insufficient (`keyringTokenStore.test.ts:599,733`)
still pass unchanged; they are joined, not replaced.

What was explicitly NOT done, so this register does not overclaim in the other direction: the
in-flight request is still not cancelled (it cannot be un-sent), and a caller already joined to
it before `clearToken()` fired still receives the pre-signout value it asked for — only the
durable cache is protected. The declared mitigation wording is corrected from "invalidate ...
the in-flight promise" to **"a stale in-flight result can no longer be written back over cleared
state."**

Commit: `f339137c6` (`fix(quick-260820-fyl): gate keyring cache writes behind a generation epoch
(T-34.5-G6-14)`).

### R4 — CLOSED 2026-08-23 — A `transfer` whose target retired without its own observation (1 row, DoS)

`T-34.5-C6-06` — plan 34.5-43, disposition as authored **`transfer`** → ledger row `U-34.5-16`.

A transfer is only closed if the target still carries the threat. `U-34.5-16`'s stated

observation appears in `34.5-LIVE-GATE-RERUN-3.md` or `-RERUN-4.md`.

This is a transferred threat closed against a bar it did not meet. Either run the live
observation `U-34.5-16` demands, or amend the row to state that structural proof was accepted

**CLOSED 2026-08-23 by the second branch — the disposition is CORRECTED from `transfer` to
`mitigate`, on evidence re-verified first-hand during this run rather than taken from the
2026-08-11 record.**

**The `transfer` was a bookkeeping error, not a deferral.** A transfer means "another party
carries this risk". Nobody ever carried it: plan 34.5-44 Task 4 **fixed it in code** three days
after plan 34.5-43 opened it. Pointing the row at a UAT ledger entry described where the work
was tracked, not who owned the residual risk — and that mis-instrument is the whole reason this
row read as unmet for three days.

Verified in the working tree on 2026-08-23, not cited from a SUMMARY:

- `"getInstallInfo"` is a `LONG_RUNNING_CHANNELS` member — `src-tauri/src/main.rs:229`, carrying
  an in-code comment that names `U-34.5-16` and `T-34.5-C6-06` by ID.
- `timeout_for()` — `src-tauri/src/main.rs:233-239` — returns `None` for any member, and `None`
  is documented as "wait indefinitely". The 60s `INVOKE_TIMEOUT` is never applied to this
  channel, so the DoS mechanism this row names (bounded reject at 60s **plus** the real late
  response dropped by the reader thread as an unknown id, making the outcome unreachable) can no
  longer occur.

Two independent controls, **both run green today** rather than quoted from the plan:

1. `cargo test every_long_running_channel_is_exempt_and_a_non_member_is_bounded` — **1 passed**.
   It ITERATES `LONG_RUNNING_CHANNELS`, so it cannot go stale as members are added, and it is
   non-vacuous in both directions: an unconditional `None` fails its negative control
   (`timeout_for("getGameSettings") == Some(INVOKE_TIMEOUT)`), an unconditional `Some` fails the
   loop.
2. `npx jest __tests__/longRunningChannels.test.ts` — **43 passed** (the record cited 34/34 on
   2026-08-11; the suite has since grown). It re-extracts the array from `main.rs` source and
   asserts **set equality** against an expected list containing `'getInstallInfo'`, guarding both
   silent widening and silent narrowing, and separately asserts `INVOKE_TIMEOUT` is still
   `Duration::from_secs(60)` — so the exemption cannot be faked by raising the global bound.

**A `cargo test` filter that matches nothing exits 0.** The first attempt here ran
`cargo test timeout_for` and reported `running 0 tests ... 156 filtered out` with exit code 0 —
a green that proved nothing, because `timeout_for` is the function's name and not any test's.
The passing result above is from the full test name. Recorded because this failure mode is
silent and would have been indistinguishable from success in a transcript.

**What this does NOT close.** `U-34.5-16` stays **OPEN** in `34.5-UNTESTED-ITEMS.md` and its bar
is **not** rewritten. Its question — does a live details page actually render size/version
fields for a real GOG title — is a FUNCTIONAL one, and it is not this threat's question. The
threat is DoS via a premature, unrecoverable timeout; that mechanism is gone at the source. The
two were only ever coupled by the mis-chosen `transfer`. **Closing the threat must not be read
as retiring the ledger row**, which is the exact move this document was written to prevent.

**Considered and rejected as evidence:** Phase 34.2's `34.2-HUMAN-UAT.md` records a live
`pnpm tauri:dev` run on 2026-08-22 driving a real `gogdl repair` on a GOG title (Endless Sky,
`1829678475`) — which implies a details page was open. It is **not** counted here. The record
does not state that size/version rendered, and no log was preserved and grepped for
`sidecar invoke timed out`. Inferring the observation from an adjacent one is precisely what
`U-34.5-16` forbids.

**Residual, recorded not counted:** the mitigation trades a bounded-but-lossy failure for an
**unbounded wait** — a wedged sidecar now leaves the caller pending forever with no error rather
than rejecting at 60s. That is a deliberate, phase-wide property of every one of the eleven
`LONG_RUNNING_CHANNELS` members, not a hole this row opened, and naming it here would be
new-threat scanning, which `register_authored_at_plan_time: true` forbids. Logged under Adjacent

### R1b — the residual that actually matters, now logged: the banner is spoofable

Not one of the 8 register rows — it is ledger row `U-34.5-31`, which would otherwise have
carried a real, undispositioned risk out of this phase inside a ledger nobody reads as a
security artifact. Logged here as `AR-34.5-03`.

The banner renders **inside the attacker-controlled document**. Reading
`login_origin_banner_script` (`main.rs:1597-1646`), the concrete mechanism is z-index headroom:

```
banner.style.zIndex = '2147482999'      // origin banner
                      '2147483000'      // cancel strip
                      '2147483647'      // CSS maximum
```

That ordering protects the cancel strip from the banner, but leaves **648 values above both**.
A hostile page setting `z-index: 2147483001` covers the banner *and* the cancel strip. The
debounced `MutationObserver` re-ensures the element **exists** and re-texts it; it never checks
**occlusion or z-order**. `pointerEvents: none` means the banner cannot even detect
interference. (`window.top !== window` does correctly limit the script to the top frame, and
`textContent` from the shell-resolved origin means page content can never write the string.)

Never tested against a page that actively fights it — the shipped mitigations are proven only
by Rust `#[cfg(test)]` assertions over the emitted script text.

## Adjacent Findings — recorded, NOT counted in the open/closed totals

`register_authored_at_plan_time: true` forbids scanning for new threats, so these are logged
rather than scored. They are not open rows.

**AF-34.5-01 — the `LONG_RUNNING_CHANNELS` exemption trades a bounded failure for an unbounded
wait.** Every member — eleven channels including `getInstallInfo`, `oauthCaptureLogin`,
`humbleStartLogin`, `humbleReconnect`, `repair`, `readConfig` — gets `timeout_for() == None`,
i.e. wait forever. A wedged or crashed sidecar therefore leaves the renderer's promise pending
indefinitely with no error surface, where a non-exempt channel would reject at 60s. The array's
own in-code comments acknowledge this explicitly ("trades a 60s rejection for a never-settling
promise if it ever wedges"), so it is a deliberate, documented, phase-wide design decision and
not a defect introduced by any one row. Noted because the availability property is real: the
mitigation for a premature-timeout DoS is itself an unbounded-wait DoS under a different
failure mode. If it is ever revisited, the shape to consider is a long-but-finite bound plus a
correlated late-response path, rather than `None`.
