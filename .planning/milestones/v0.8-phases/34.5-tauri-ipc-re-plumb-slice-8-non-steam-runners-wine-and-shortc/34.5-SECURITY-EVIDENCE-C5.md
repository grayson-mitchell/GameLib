## Open finding

### Row 20 — T-34.5-C5-13 (34.5-41), Spoofing — OPEN

**Declared mitigation:** "Items 1-3 require the login window's title-bar origin to be
transcribed; item 3 requires the `www.amazon.com` anchor to hold with a zero-count
`origin-mismatch` grep."

**What actually happened, per `34.5-LIVE-GATE-RERUN-2.md` itself:**
- Item 3 (Amazon/nile) was **NOT ATTEMPTED** — the live session ended during item 4's diagnosis
  before any Amazon login window opened. The `www.amazon.com` host-anchor claim (research
  Assumption A1) was never exercised this run and stays **UNTESTED**.
- U-34.5-05 (the ledger row this transcription requirement backs) stays **OPEN** — item 2's
  (GOG's) own evidence text explicitly states the title-bar text transcription was **not
  captured** this run. A log-level `nav host=` change was observed for GOG, but that is a
  different, weaker observable than the title-bar TEXT the row's own retirement bar requires.

**Assessment:** the underlying anti-phishing *mechanism* (origin/nav-host logging in
`oauthLoginCapture.ts`, exact-hostname check in `matchOAuthRedirect`) exists in code and is
independently verified elsewhere in this phase's register (`T-34.5-05`, BASE shard). What this
specific row (34.5-41's execution of the 34.5-40 contract) promised was **live proof** that an
operator can actually verify the login window's origin before typing credentials into it, for
all three storefronts. That proof was not obtained for Amazon at all, and was incomplete for
GOG. This was **not hidden** — it is honestly recorded as OPEN/UNTESTED in both the gate
document and the ledger, and is the documented reason gap cycle 5's gate FAILED 0/5 and Phase
34.5 does not close (routes to gap cycle 6). Per this audit's disposition rules, an honestly
recorded gap is still an open mitigation, not a closed one — the phase's own routing already
reflects this (`Phase 34.5 does NOT close`).

**Next action:** already tracked — U-34.5-05 (title-bar transcription) and item 3/Assumption A1
(Amazon anchor) are live ledger rows scoped into gap cycle 6 onward. No additional action is
being invented by this audit; it is confirmed as a genuine, already-acknowledged residual, not a
new discovery.

## Warning — related but out-of-shard finding (not one of the 29 register rows)

**A real Steam userdata account id (`userdata/35601368`) is committed in cleartext inside a git
commit message** (`d48b4d964`, `docs(34.5-42): close gap cycle 5 — STATE.md, next action, and
plan 42 summary`), written while this same plan's own SUMMARY was documenting a *different*,
pre-existing instance of the same leak inside four file bodies (`34.5-19-PLAN.md:191`,
`34.5-20-PLAN.md:160`, `34.5-LIVE-GATE.md:464/471`, `34.5-LIVE-GATE-RERUN.md:585`). Those four
file-body instances have since been redacted in the current working tree (confirmed:
`grep -r 35601368 . --include='*.md'` → 0 matches today), but the commit-message instance is
**immutable git history** and was never covered by this cycle's own credential-sweep discipline
(`grep -Ec "token=|code=|Cookie|userdata"` was run against file *content*, never against commit
messages). Per 34.5-42-SUMMARY.md's own analysis, `.planning/` is tracked and already published
on the fork remote, and a future push would publish this commit's message verbatim.

This is not one of the 29 rows in this shard's register (no row's `Component` names "commit
message"), so it is logged here as a **WARNING (unregistered_flag)** rather than folded into the
row-20 BLOCKER above — it is new attack surface (an information-disclosure instance) that arose
during this cycle's own implementation with no threat-ID mapping in the register. It directly
undermines the intent of `T-34.5-C5-06` (Steam userdata account id must not appear in a
public-fork document) one layer below where that threat's rows were scoped to check (file
content, not commit messages).

**Disclosure severity, per the project's own prior analysis (unchanged):** the value is a
SteamID3 account id — an identifier, not a credential; it grants no account access, only
identity linkage (GitHub commit author ↔ Steam profile). Not a BLOCKER-severity credential leak,
but real information disclosure that a strict audit must not silently pass over.

**Recommendation:** a developer decision on whether to rewrite `fd5a81fefa..HEAD` (per
34.5-42-SUMMARY.md's own note: 262 commits, none yet published) before the next push, is still
outstanding and should explicitly account for this commit-message instance in addition to the
four file-body instances already named.
