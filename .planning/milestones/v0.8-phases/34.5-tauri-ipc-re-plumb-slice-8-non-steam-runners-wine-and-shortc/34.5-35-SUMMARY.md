## Decisions Made

- **45s / 120s over any larger "safer" numbers.** 45s stays under `RUST_INVOKE_TIMEOUT_MS` with
  margin (the plan's own binding constraint); 120s is bounded by "comfortably more than 2x the new
  read bound and past the one observed interval," not padded further, so the accepted-cost tradeoff
  (a legitimate retry delayed up to two minutes) stays as small as the evidence supports.
- **Second log line, not a replacement.** The existing `getToken(): keyring_get failed: ...`
  warning is preserved verbatim; the new `keyring failure memoized slot=...` line is additive. This
  required updating 4 pre-existing test assertions across two test files from `toHaveBeenCalledTimes(1)`
  to `toHaveBeenCalledTimes(2)` for the getToken()-failure path specifically (setToken/clearToken
  failures, which don't touch the memo, were left unchanged at 1).
- **`main.rs`'s assert message rebuilt via `concat!` with named args.** The natural
  backslash-continued multi-line string literal compiled fine under `cargo test` but tripped
  `longRunningChannels.test.ts`'s pre-existing WR-08 per-line quote-balance guard in the full JS
  suite — found only by running `npm run test:ci`, not by Task 1's own narrower `cargo check &&
  cargo test keyring` verify command. Fixed via Rule 1 (bug directly caused by this task's own
  change) in a separate, clearly-labeled commit.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] `main.rs`'s new assert!() message broke the WR-08 quote-balance stripper guard**
- **Found during:** Task 1, discovered only when running the phase's full `npm run test:ci` after
  Task 1's own commit (Task 1's scoped verify command, `cargo check && cargo test keyring`, does
  not exercise the JS test suite and could not have caught this)
- **Issue:** The ordering-invariant assert message used a backslash-continued multi-line Rust
  string literal. `longRunningChannels.test.ts`'s existing WR-08 guard counts `"` occurrences per
  SOURCE line independently (it cannot see that a `\`-continuation resolves the quote balance
  across lines), so two of the five message lines each carried an odd (unbalanced) quote count and
  the guard correctly tripped.
- **Fix:** Rebuilt the message via `concat!` of six single-line, individually quote-balanced
  literal fragments, with the three interpolated `Duration` values passed as explicit named
  arguments (`read =`, `invoke =`, `margin =`) — Rust does not permit captured-identifier
  interpolation (`{IDENT}`) when the format string itself comes from a macro expansion like
  `concat!`.
- **Files modified:** `src-tauri/src/main.rs`
- **Verification:** `cargo check` / `cargo test` both still pass (92 passed, 1 ignored, 0 failed);
  `npx jest src/backend/__tests__/longRunningChannels.test.ts` — 28/28 passed.
- **Committed in:** `b1a450e8d`

**2. [Rule 1 - Bug] `humbleSecretStore.test.ts`'s `getSecret()`-rejection test broke on the new memo log line**
- **Found during:** Task 2, running `npm run test:ci` after `keyringTokenStore.test.ts` itself
  passed in isolation
- **Issue:** `SidecarHumbleSecretStore.getSecret()` delegates directly to
  `SidecarKeyringSlotStore.getToken()` (via the module-level `SLOT_STORES` singleton), so it
  inherits the new memo-bookkeeping log line on every `getToken()` failure — a direct, in-scope
  consequence of Task 2's own change, not an unrelated pre-existing issue.
- **Fix:** Updated the one affected test's `mockLogWarning` call-count expectation from 1 to 2,
  with a comment explaining the delegation.
- **Files modified:** `src/backend/sidecar/__tests__/humbleSecretStore.test.ts`
- **Verification:** `npx jest src/backend/sidecar/__tests__/humbleSecretStore.test.ts` — 28/28
  passed; full `npm run test:ci` — 3533/3533 passed.
- **Committed in:** `6b1171076` (bundled with Task 2's own commit, since it is the same root cause)
