# Phase 34.5 Plan 18: Boot-Time Receipt Logging + Asset-Root Self-Check Summary

**Made the sidecar log the `GAMELIB_SHELL_EXE` value it actually received (closing a gate-contract defect, not a code defect) and added a boot-time asset-root self-check that turns a wrong `publicDir` into one greppable `SIDECAR ASSET ROOT DEFECT` line instead of a `spawn ./legendary ENOENT` six layers away.**

## Accomplishments

- `bootstrap.ts`'s `init()` now logs `[bootstrap] GAMELIB_SHELL_EXE received=<value>` (info level,
  verbatim, no trimming/quoting) when the sidecar's own `process.env.GAMELIB_SHELL_EXE` is set,
  or `[bootstrap] GAMELIB_SHELL_EXE received=<UNSET>` (warning level) when it is unset or empty —
  the CHILD's observation, not the Rust shell's `eprintln!` claim at `main.rs:1231`, which only
  ever reaches the shell process's own stderr and can never distinguish "set on the child env"
  from "actually visible to `pathShim`". This is the exact prefix `34.5-LIVE-GATE.md`
  precondition 5 names as its required evidence source, closing the gate-contract defect that
  precondition 5 and precondition 2 (sidecar output must come from `gamelib.log`, never the
  terminal) could not previously both satisfy.
- Added a boot-time asset-root self-check, placed directly after the receipt log and before the
  i18next block (the first other startup diagnostic) so it cannot be outrun by a login attempt —
  on the 2026-08-01 live-gate run the `ENOENT` lines fired 6 seconds before the first login
  interaction. Logs the resolved app root and which source produced it
  (`GAMELIB_APP_ROOT`/`process.cwd`), the resolved `publicDir` with its `existsSync` result, and
  per-runner (`legendary`/`gogdl`/`nile`/`comet`) the resolved path and `existsSync` result,
  mirroring `archSpecificBinary`'s own arch-native-first/x64-fallback resolution without
  importing that private function. On any absence, emits exactly one
  `[bootstrap] SIDECAR ASSET ROOT DEFECT` error line naming the resolved `publicDir` and pointing
  at `34.5-APP-ROOT-SWEEP.md`.
- Extended the pre-existing `locales` `existsSync` warning's comment to name it as the (until now
  ungeneralised) first member of this diagnostic family — the implication ("`publicDir` can be
  wrong under the sidecar") was already known at that exact site and never followed through to
  `bin/`, the costliest consumer, which is what produced the 4th recurrence of the
  `publicdir-getapppath-chunking` family that cost live-gate items 1/2/3.
- Both blocks are wrapped in their own `try`/`catch` with a log-and-continue catch, and are NOT
  gated by a once-only boolean (unlike `loggerInitialized`/`i18nInitialized`) — they re-observe
  `process.env` on every `init()` call, so a diagnostic never goes stale and can never fail boot.
- New tests assert on the emitted log TEXT (not merely that a logger function was called): two
  for the receipt log (set/unset arms) and two for the self-check (healthy/missing-asset arms,
  the latter via a fresh module instance with `electron` swapped for the real `electronStub`,
  since this suite's default automocked `electron` always resolves `getAppPath()` to
  `os.tmpdir()` — the same "arithmetic trap" `appRootResolution.test.ts`'s own header already
  documents). All four new tests confirm `init()` still reaches `READY_SENTINEL`.
- Full suite: `npx tsc --noEmit` clean; `npm run test:ci` — **Test Suites: 179 passed, 179
  total; Tests: 3463 passed, 3463 total** (up from the 3459 baseline recorded in
  `34.5-17-SUMMARY.md` — 4 new tests, exactly the 4 added).

## Decisions Made

- Read `process.env.GAMELIB_SHELL_EXE` directly rather than `pathShim.getPath('exe')` — the
  latter throws by design on an unset/empty value (correct for its real callers, wrong for a
  diagnostic that must report the unset state rather than crash reporting it).
- Neither new block is gated by a once-only boolean — both must re-observe the current
  environment on every `init()` call, which is also what lets `bootstrap.test.ts`'s existing
  multi-call-per-file pattern drive independent arms with independent env values.
- The self-check's test coverage required the same "swap the automocked `electron` for the real
  `electronStub` inside `jest.isolateModules`" technique `appRootResolution.test.ts` already
  established, since `publicDir` is a module-scope constant fixed at import time and this suite's
  default automock always resolves `getAppPath()` to `os.tmpdir()`.
- Split the two tasks into two atomic commits by drafting both together, then temporarily
  reverting Task 2's additions to verify and commit Task 1 in isolation, then reapplying Task 2 —
  see Deviations below.

## Issues Encountered

- **Test-harness discovery, not a defect:** the first attempt at the asset-root self-check's
  "healthy arm" test used this test file's already-imported (top-level) `init`/`publicDir`
  directly, expecting no `SIDECAR ASSET ROOT DEFECT` line. It failed — `publicDir` resolved to
  `os.tmpdir()/public`, which does not exist, because `bootstrap.test.ts` (like every other
  backend suite that does not opt out) runs under Jest's automatic `electron` mock
  (`src/backend/__mocks__/electron.ts`), whose `getAppPath()` unconditionally returns
  `os.tmpdir()`, never the real repo root — and `constants/paths.ts`'s `publicDir` is a
  module-scope constant computed once, at import time, against whatever `electron` resolved to
  at that moment. Resolved by adopting `appRootResolution.test.ts`'s already-established pattern:
  `jest.isolateModules` + `jest.doMock('electron', () => jest.requireActual('../electronStub'))`
  + a fresh `require('../bootstrap')`, so both the healthy and missing-asset arms exercise the
  REAL `electronStub` against a controlled `GAMELIB_APP_ROOT`, never the automock. Not filed as a
  deviation since no source code needed correction — only the test harness design.
