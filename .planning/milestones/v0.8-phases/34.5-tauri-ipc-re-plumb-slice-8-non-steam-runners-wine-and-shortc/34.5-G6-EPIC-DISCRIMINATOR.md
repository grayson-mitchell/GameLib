# F-34.5-G6-01 — Epic ("greyed out" login form) discriminating experiment

**This document is a CONTRACT, written before any experiment runs, exactly as
`34.5-LIVE-GATE-RERUN.md` was written before its own live run.** It pre-registers two readings of
F-34.5-G6-01, a decision rule that maps every possible observed outcome to a verdict BEFORE the
outcome is known, and leaves every Result slot empty. Plan 34.5-24 (this plan) authors the
contract only. Plan 34.5-28 executes it, on real hardware, and fills in the Result slots. Plan
34.5-29 applies whichever fix the recorded verdict selects.

**Why this document exists.** This project has already spent nine live runs and eight falsified
hypotheses on F-10 by shipping the nicer of two readings that both fit a single measurement. The
lesson extracted from that: *when two readings of a measurement both fit, build the discriminator
instead of shipping the nicer one.* F-34.5-G6-01's symptom fits at least two mechanisms and the
existing evidence cannot separate them, because the capture driver logged only `label=` and
`status=` — never which pages the login window actually reached. Plan 34.5-24's Task 1 closed that
gap (`nav host=` logging) and Task 2 added a source-free user-agent override
(`GAMELIB_OAUTH_UA_LEGENDARY`) so the two arms below are ONE build, ONE variable — never a
hand-edit-and-rebuild between arms, which would make the two arms non-comparable.

## The two readings

- **R1 — user-agent gated.** Epic's login page gates its form on a recognised browser agent.
  GameLib currently sends `Mozilla/5.0 (Windows NT 10.0; Win64; x64) EpicGamesLauncher`, which
  carries no `AppleWebKit`/`Chrome` product token and was copied verbatim from a Chromium
  `<webview>` context (`WebView/index.tsx` L229-237) into a WKWebView one
  (`oauthLoginCapture.ts`'s `USER_AGENTS.legendary`). GOG and Amazon send a Chrome-shaped agent
  (`Mozilla/5.0 (Windows NT 10.0; Win64; x64) Chrome/200.0`) and both reached interactive forms
  (both reached `status=captured` in this same session — see `34.5-LIVE-GATE-RERUN.md` items 2/3).
  A server-side or client-side UA sniff on Epic's login page is the mechanism this reading names.

- **R2 — WKWebView API gated.** A Chromium-only web API called by Epic's login bundle THROWS
  under WKWebView, aborting the script that would otherwise enable the form. The standing project
  record already has one confirmed instance of exactly this shape:
  `.claude/skills/spike-findings-gamelib/references/tauri-chromium-only-web-apis.md` — Accessibility's
  font picker calls `queryLocalFonts`, which **throws** under WKWebView (not merely returns
  `undefined`), and the throw was silent enough that `bootErrorSurface` did NOT blank the mounted
  app around it. A login bundle could hit an equivalent throwing API during its own
  form-enablement script, leaving a form mounted (hence the "correct title" the developer
  observed) but never enabled ("greyed out").

Both readings predict the SAME macro-symptom (a form that renders but never becomes interactive,
0 of 3 captures) — this is exactly why neither prior gate run could separate them from the
evidence they collected. The instrument built by plan 34.5-24 Tasks 1/2 produces DIFFERENT,
unambiguous observable output under each reading, which is what makes this experiment a
discriminator rather than a repeat of the same inconclusive observation.

**What each reading predicts, concretely, for the observations below:**

| Reading | Predicted `nav host=` sequence | Predicted form interactivity |
|---|---|---|
| R1 | Window sits on Epic's login hostname for the WHOLE attempt in BOTH arms if the UA override does not change anything about navigation — the discriminating signal for R1 is INTERACTIVITY changing between arms, not the nav host sequence changing. If Epic's page performs a UA-gated CLIENT-SIDE redirect to a distinct "unsupported browser" page, the nav host sequence would show a SECOND hostname in arm A that arm B does not reach — record this if observed, it is additional evidence for R1 beyond the interactivity signal alone. | Non-interactive in arm A (stock Epic UA), interactive in arm B (Chrome-shaped UA) |
| R2 | Window sits on the SAME hostname in BOTH arms — the throwing API is unrelated to which UA string was sent, so the UA override changes nothing about which pages are reached | Non-interactive in BOTH arms (a UA change cannot fix a script that throws on an unrelated Chromium-only API) |

## The experiment — two arms, one build, one variable

**Precondition:** Epic signed out (per `34.5-LIVE-GATE-RERUN.md` precondition 5's aside procedure —
re-verify, do not assume). A single dev build (`pnpm tauri:dev`) is used for BOTH arms; only the
environment variable changes between them, so the two arms are directly comparable (never a
rebuild between arms).

**How to run each arm:**

1. Set (or unset) `GAMELIB_OAUTH_UA_LEGENDARY` in the shell BEFORE launching `pnpm tauri:dev` (or
   export it in the same terminal session before the launch command — the sidecar reads
   `process.env.GAMELIB_OAUTH_UA_LEGENDARY` at the moment `resolveUserAgent('legendary')` is
   called, which is every time `captureOAuthLogin('legendary', ...)` opens a window, so setting it
   before each attempt is sufficient; a full app relaunch is NOT required between arms as long as
   the variable is set/unset in the same shell/process environment the sidecar inherited).
2. Click Epic in Manage Accounts to open the login window.
3. Observe: does the form accept keyboard/mouse input (interactive), or does it stay "greyed out"
   as the developer described (non-interactive)?
4. Whether or not it becomes interactive, let the attempt run to completion (either a captured
   redirect or the 300-second timeout) and then read back `~/Library/Logs/GameLib/gamelib.log`.
5. Record the FULL `nav host=` sequence for the attempt: `grep -n "runner=legendary" gamelib.log`
   after the attempt, quoting every `label=`, `nav host=`, and `status=` line for that attempt's
   label, in order.
6. Repeat for the other arm.

**Arm A — unset (stock Epic agent):**
```
unset GAMELIB_OAUTH_UA_LEGENDARY
pnpm tauri:dev
```

**Arm B — set to the Chrome-shaped agent GOG/Amazon already use successfully:**
```
export GAMELIB_OAUTH_UA_LEGENDARY='Mozilla/5.0 (Windows NT 10.0; Win64; x64) Chrome/200.0'
pnpm tauri:dev
```
Confirm the override took effect by grepping for the Task 2 receipt line before clicking Epic:
`grep "runner=legendary user-agent-override len=" gamelib.log` must show `len=52` (the length of
the literal string above) — an ABSENT line means the variable was not read by this process and the
arm's own precondition is not satisfied; do not proceed to interpret Arm B's result until this
line is confirmed present.

**Where to write the result:** directly into this document's "Decision Rule" and "Result" sections

## Decision rule (filled in BEFORE the experiment runs)

| Arm | `GAMELIB_OAUTH_UA_LEGENDARY` | Observation | Selects |
|---|---|---|---|

**All four outcome combinations, decided in advance:**

- **Arm A non-interactive AND Arm B interactive → R1 SELECTED, R2 falsified for this defect.**
  The UA is the whole difference between the two arms; if that alone flips the form from
  non-interactive to interactive, the mechanism is a UA gate, not a throwing API (a throwing API
  would not care which UA string was sent).

- **Both arms non-interactive → R1 FALSIFIED.** R2 is NOT thereby confirmed — it is merely
  surviving. A UA change failing to fix the symptom rules out a simple UA gate, but does not by
  itself prove a specific throwing API is the cause; some third mechanism could also produce
  "both arms non-interactive." **The additional observation that WOULD confirm R2:** capture the
  embedded window's own console/script-error signal (not yet instrumented by this plan — would
  require a further capability, e.g. relaying a `console.error`/`unhandledrejection` event from
  the login window's JS context back to `gamelib.log`, analogous to how `on_page_load` events are
  already relayed) and confirm it names a Chromium-only API (e.g. `queryLocalFonts` or an
  equivalent) throwing during form initialization. Absent that additional observation, route to a
  further diagnosis cycle rather than shipping R2 as the fix on the strength of elimination alone
  — eliminating R1 is not the same evidence as confirming R2, and this project's own standing
  lesson is to build the discriminator rather than accept the nicer remaining reading.

- **Both arms interactive → NOT REPRODUCED.** Record NOT REPRODUCED and route to RE-RUNNING the
  arm that previously failed (Arm A, since that is the gate's original configuration) before
  concluding anything about the defect's status. A defect that vanishes without an identified
  change is an unexplained defect, not a fixed one — do not close F-34.5-G6-01 on a single
  both-interactive observation.

- **Arm A interactive AND Arm B non-interactive → NEITHER READING FITS.** STOP and escalate to a
  further diagnosis cycle. Do NOT invent a third reading to rescue the experiment inline in this
  document — a third reading, if warranted, gets its own pre-registered contract the same way R1
  and R2 did here.

**Nav host recording rule, unconditional.** The `nav host=` sequence must be recorded for BOTH
arms regardless of interactivity outcome. "Sat on one hostname for the whole attempt" versus
"reached a second, different hostname" is independent evidence that neither reading above predicts
identically (see the per-reading prediction table above) — recording it costs nothing extra (it is
already logged by Task 1) and may sharpen or contradict the interactivity-based verdict on a future

## Routing

**Plan 34.5-29 must address, in order of what the smoke half actually broke:**

1. **GOG library never lands** (new defect, blocks the smoke half's own success criterion). Auth
   succeeds end to end (`Login Successful`, `Saved username to config file`) but
   `No cache found, getting data from gog...` repeats four times and never produces a completion
   line, unlike Steam's `Steam: fetched N owned games` → `Steam library sync complete: N games` in
   the same session. This is why the GOG filter appears in the Library UI but no GOG games display.
2. **`Refreshing undefined Library`** (new defect). The login-completion path correctly logs
   `Refreshing gog Library` once (19:22:49, plan 34.5-26's own fix working as designed), but a
   DIFFERENT refresh caller passes `undefined` as the runner three times afterward (19:23:09,
   19:24:30, 19:25:30) — a separate call site from the one 34.5-26 fixed.
3. **Keyring read timeout races human Keychain approval** (new defect, falsifies plan 34.5-25 per
   (i) above). `KEYRING_READ_TIMEOUT` is 8s (`src-tauri/src/main.rs:640`); a human takes longer than
   8s to notice, read, and approve a macOS Keychain dialog, so the failed-and-uncached read repeats
   on every subsequent caller. Likely a dev-build-specific severity (ad-hoc code signing means the
   Keychain ACL is not persisted between runs) rather than an inherent property of Keychain access
   in a signed production build, but the live defect (two prompts in one session) is confirmed
   regardless of root-cause severity.
4. **Captured + authenticated but no propagation on some attempts (a race)** (new defect). Attempt 2
   (19:21:10) reached `status=captured` → `Login Successful` → `Saved username to config file` and
   produced NO `useTauriOAuthLogin` line, dumping the developer back to Manage Accounts. Attempt 3,
   an identical flow, DID propagate (19:22:49). Same code path, two different outcomes — a race, not
   a deterministic bug, and therefore harder to fix confidently without first instrumenting the
   gap between "backend captured" and "hook checked in."
5. **Epic (F-34.5-G6-01) further diagnosis**, per this document's own Result section: R1 is
   falsified, R2 is not confirmed. Plan 34.5-29 should NOT ship a UA-only fix for Epic; if it
   attempts Epic at all this cycle, it should pursue the concrete next discriminator named above
