# Phase 34.5 Plan 26: Route captured OAuth login through GlobalState's completion path Summary

**A captured Epic/GOG/Amazon/Zoom OAuth login now triggers `GlobalState`'s own `setState(username) + handleSuccessfulLogin(runner) -> refreshLibrary` path via a new, independently-tested `createOAuthLoginCompletion` factory — closing the layer-2 gap where auth could succeed while the library and account UI never refreshed.**

- **Completed:** 2026-08-01

## Accomplishments

- Closed F-34.5-G6-02's layer 2 (and with it F-34.5-G6-03, "GOG games are not showing in
  Library"/"account manager did not reflect that i had logged in"): `useTauriOAuthLogin.ts`
  still calls the raw `window.api.login`/`authGOG`/`authAmazon`/`authZoom` channels itself (so
  it keeps owning the `UNPORTED_CHANNEL_MARKER` catch), but now checks the resolved response's
  `status` before treating the login as successful, and on `status === 'done'` invokes an
  injected `onLoginSuccess` callback with `{ runner, username, user_id }`.
- Added `createOAuthLoginCompletion(deps)` (exported from `useTauriOAuthLogin.ts`), the single
  factory both `GlobalState.tsx`'s `completeOAuthLogin` context method AND this plan's own unit
  tests construct — it performs the runner-specific `setState` (username into the right slice)
  then routes through the **existing** `handleSuccessfulLogin` (which internally calls
  `refreshLibrary`), never a second, parallel refresh path.
- Fixed the previously-unhandled case where the auth channel resolves but is REFUSED
  (`{ status: 'failed' }`/`{ status: 'error' }`): this used to fall into the exact same `{ phase:
  'idle' }` branch as a real success (rendering the "not wired up yet" declared-blocked copy for
  a real backend refusal); it now settles `{ phase: 'error', message: 'Login failed for
  <runner>: status=<status>' }` with a distinct greppable log line, and `onLoginSuccess` is never
  invoked for it.
- Removed the falsified guard comment ("Resolved WITHOUT throwing -- Phase 34.5 has landed and
  this channel is real now. This hook's own job (capture) is done...") that made this gap look
  intentional — `grep -c "lands in Phase 34.5"` is 0.
- `GlobalState.tsx`'s three-hunk diff for this plan is 100% additive: one new import line, one
  new `completeOAuthLogin` class field, one new key in the context `Provider`'s `value={{...}}`.
  `epicLogin`/`gogLogin`/`amazonLogin`/`zoomLogin`/`handleSuccessfulLogin`'s bodies are
  byte-identical to before this plan (verified by `git diff`, quoted in full below).
- Proved the Electron path is behaviourally unchanged (Task 3): `npx electron-vite build` exits
  0 (`✓ built in 4.43s`), `electronUntouched.test.ts` 11/11, `useTauriOAuthLogin.ts`'s `isTauri()`
  guard is still the first, unconditional statement in its effect, and the stale-guard sweep
  found zero remaining falsified premises in this plan's diff.

## Decisions Made

See `key-decisions` in frontmatter above. In summary: Shape A over Shape B (avoids double-calling
the auth channel), a runner-agnostic completion payload (keeps `GlobalState.tsx` free of
per-runner response-shape imports), zoom's username fetched separately post-`done` (mirrors
existing `zoomLogin`), the completion-building factory lives in the hook file (not
`GlobalState.tsx`) so tests can import it without pulling in `GlobalState.tsx`'s heavy
side-effecting imports, and `completeOAuthLogin` is a new top-level context field rather than
four near-identical per-runner ones.

  triggers `onLoginSuccess` exactly once with the correct `{ runner, username, user_id }`.

  rejection all still correctly avoid invoking `onLoginSuccess`.

  passes, and the `isTauri()` guard is unconditionally first.

**NOT proven by unit tests, and requiring the live gate (34.5-31) to confirm:**
- Whether a REAL GOG/Epic/Amazon login, driven through the actual Tauri OAuth capture window and
  the real sidecar's `login`/`authGOG`/`authAmazon` handlers, produces a non-empty Library and a
  populated account-manager username in a live run — per this phase's own standing lesson, a
  green suite (now 3497/3497) is not evidence of live parity unless something asserts parity, and
  no unit test can substitute for a human driving the real UI end to end.
- Whether `GlobalState`'s `refreshLibrary` call, once triggered by a REAL captured login, actually
  populates the GOG-runner filter option and library grid in the real renderer (this plan proves
  the CALL happens with the right argument; it does not — and cannot, from a unit test — prove the
  real `refreshLibrary` implementation's network/IPC round trip succeeds against a live GOG
  backend).

  Phase 34.4.1) was NOT specifically re-exercised by this plan — it shares `handleSuccessfulLogin`
