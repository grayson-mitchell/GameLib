# Phase 34.5 Plan 16 — App Root Consumer Sweep (G-1)

Task 1 of `34.5-16-PLAN.md`. Written BEFORE any code changes in this plan — this document
enumerates every `publicDir` / `app.getAppPath()` consumer and records what happens to each. The
already-verified 7-step root-cause chain lives in `34.5-LIVE-GATE.md` § "Root cause" and is not
re-derived here.

Greps run (repo root, 2026-08-01):
```
grep -rn "publicDir" src/ --include="*.ts" --include="*.tsx"
grep -rn "getAppPath" src/ --include="*.ts" --include="*.tsx"
```
Import-only lines (`import { publicDir } from ...`) and doc-comment mentions are not separate
rows — they carry no resolution logic of their own. Every line that actually CALLS or DERIVES a
path from `publicDir`/`app.getAppPath()` is its own row below, even where the source plan's task
text grouped several lines of the same construct under one bullet (e.g. `utils.ts:506+:513`) —
splitting them one-row-per-line is stricter, not looser, and every named item in the task's
"at minimum" list appears here individually.

Reachability was decided by reading the module graph starting from the sidecar's real entry
points — `src/backend/sidecar/handlers.ts`'s own import list (the 20 `*FlowRegistration.ts`
modules it imports) plus `src/backend/sidecar/bootstrap.ts` (the sidecar's own `init()`) — and
following each curated import chain by hand with `grep -rn "^import" <file>`, never assumed from
a file's directory or its topic.

## Section 2 — Decision: one authoritative app root, not N patches

**Chosen mechanism:** the Rust shell sets `GAMELIB_APP_ROOT` on the sidecar child's environment
at spawn time, on **both** spawn paths (`spawn_sidecar_dev` and `spawn_sidecar_packaged`),
computed once per path — mirroring `GAMELIB_SHELL_EXE`'s existing handoff shape exactly.
`electronStub.app.getAppPath()` returns `process.env.GAMELIB_APP_ROOT` when it is set and
non-empty, falling back to `process.cwd()` (today's behaviour) when unset or empty.

**Why this repairs every `FIXED BY ROOT` row above at once:** every one of them derives from the
single expression at `paths.ts:73` (`publicDir = resolve(app.getAppPath(), ...)`), which itself
derives from the single `electronStub.ts:207` call. There is exactly one seam between "what the
sidecar thinks its app root is" and "every bundled-asset path the sidecar computes." Patching
that one seam cannot drift row-by-row the way N separate patches would, because there is no
second copy of the resolution logic anywhere in the sweep above to fall out of sync with it.

**Rejected alternatives:**

- **(a) Set the sidecar child's `cwd` from Rust instead of an env var.** This would repair
  `getAppPath()` by accident (`process.cwd()` would then already be correct) — but it would also
  silently change every OTHER relative-path resolution in the sidecar's 1.1 MB bundle, and in any
  process the sidecar itself spawns (`legendary`, `gogdl`, `nile`, `comet`, wine, `vulkan-helper`,
  the Steam bridge helper) that happens to resolve a relative path against its own inherited cwd.
  An env var changes exactly one named value; a cwd change is an invisible, blanket behavioural
  shift with no single point of review.
- **(b) Per-call-site `join(repoRoot, ...)` patches at each of the 15 `FIXED BY ROOT` rows.**
  N sites, N chances to miss one, N chances for a future addition to repeat the mistake. This is
  the literal, named cause of this being the FOURTH recurrence of the
  `publicdir-getapppath-chunking` failure family (`bootstrap.ts:156`'s own comment already
  documents the `getAppPath()`/`process.cwd()` equivalence and generalised it no further than
  `locales/` — precisely the row-by-row drift this option would repeat at a larger scale).
- **(c) `__dirname`-relative math.** `paths.ts:63-72`'s own comment already documents this as
  abandoned: electron-vite code-splits the main bundle into `build/main/chunks/*`, so `__dirname`
  is depth-dependent and the old `resolve(__dirname, '..', ...)` math landed one level off. The
  sidecar bundle has the same code-splitting exposure; nothing about the sidecar's build makes
  this option safer than it was when `paths.ts` itself abandoned it.

## Section 3 — What this does NOT resolve: the packaged asset root

`electronStub.app.isPackaged` stays `false` in this plan. Under the sidecar, `publicDir`
(`paths.ts:75`) therefore always appends `'public'`, never `'build'` — regardless of whether the
handed-down `GAMELIB_APP_ROOT` came from the dev path or the packaged path.

In a **dev** build (`pnpm tauri:dev`), the handed-down root is the repository root, and
`<repo>/public` exists — the runner binaries live there (verify: `ls public/bin/$(node -p
process.arch)/darwin`). This plan's fix is provably correct for dev.

In a **packaged** Tauri build, the handed-down root is `app.path().resource_dir()` — Tauri's
bundled resource directory — which has no `public/` child; the packaged resource layout has never
been defined by this project's Tauri build config in a way this plan's sweep touches. Appending
`'public'` to a packaged resource root will resolve to a path that does not exist, for the exact
same shape of reason `src-tauri/public` didn't exist before this plan.

This residual is named **`R-34.5-G1-PKG`**. Plan 34.5-18's boot self-check is what makes this
loud rather than silent (it asserts the resolved asset root exists and logs plainly if not,
rather than the current silent-ENOENT-on-first-spawn failure mode). The blocking gate this cycle
re-runs (`34.5-20`) is **dev-only** (`pnpm tauri:dev`, its own precondition 2) — a dev PASS from
that gate must never be read as covering packaging. This is the same class of limit
`34.5-LIVE-GATE.md` precondition 5 already records for `GAMELIB_SHELL_EXE`'s own packaged-path
correctness: proven live on the dev path, not proven live on the packaged path, and not
conflated with it.
