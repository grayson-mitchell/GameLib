# F-34.5-G6-02 — root-cause diagnosis

**Verdict in one sentence:** F-34.5-G6-02 is shape **(c)** — the consume path (`useTauriOAuthLogin.ts`
calling `login`/`authGOG`/`authAmazon` after a `status=captured` outcome) EXISTS and is written
correctly, but the captured outcome never reaches it, because `oauthCaptureLogin` is a
`sidecar_invoke`-routed channel bound by `src-tauri/src/main.rs:104`'s 60-second `INVOKE_TIMEOUT`
(it is absent from `LONG_RUNNING_CHANNELS`, `src-tauri/src/main.rs:134-145`) while its own internal
deadline is `DEFAULT_DEADLINE_MS = 300_000` (`src/backend/sidecar/oauthLoginCapture.ts:62`) — every
real-world login takes longer than 60 s to complete, so the Rust shell's `sidecar_invoke` command
rejects the renderer's promise at the 60 s mark, roughly 3-4 minutes before the backend actually
settles `status=captured` or `status=timeout`. That rejection lands on an `await` at
`useTauriOAuthLogin.ts:99` which is NOT inside a `try`/`catch` (the enclosing `try` block ends at
line 97), so it becomes a silently-swallowed unhandled promise rejection — the hook's own
`window.api.logInfo` calls (which fire on every terminal outcome) never execute, matching the
observed **zero** `useTauriOAuthLogin` log lines despite **six** real backend terminal outcomes this
session.

## (a) / (b) / (c) — decided from source

This is **NOT (a) missing**: `useTauriOAuthLogin.ts:133-172` calls `window.api.login`/`authGOG`/
`authAmazon`/`authZoom` on `outcome.status === 'captured'`, exactly as REQ-34.4.1-08 shipped it.

This is **NOT (b) present-but-still-stubbed**: `login`/`authGOG`/`authAmazon` are real,
Phase-34.5-ported `ipcMain.handle` channels now (`src/backend/sidecar/runnerAuthFlowRegistration.ts:136,157,195`)
— they are no longer the `UNPORTED_CHANNEL_MARKER` stub Phase 34.4.1 shipped. The `catch` block at
`useTauriOAuthLogin.ts:158-172` that turns that marker into `phase: 'blocked'` is legacy defensive
code from 34.4.1, not evidence of a live stub — REQ-34.5-04 already ported these three channels.

This **IS (c) exists-but-never-reached**: decided from `src-tauri/src/main.rs:288-326`
(`SidecarState::invoke`) — `timeout_for("oauthCaptureLogin")` returns `Some(INVOKE_TIMEOUT)` (60 s)
because `"oauthCaptureLogin"` is not a member of `LONG_RUNNING_CHANNELS` (`main.rs:134-145`, quoted
verbatim in evidence item 4 below), so `rx.recv_timeout(bound)` fires at 60 s and the command returns
`Err("sidecar invoke timed out".into())` — a REAL settle (a `#[tauri::command]` async fn that has
returned cannot leave the underlying Tauri IPC message unsent; see the R-A/R-B discrimination below).
That rejection reaches `tauriInvoke()` in `src/preload/tauriTransport.ts:92-97` and propagates to the
bare `await` at `useTauriOAuthLogin.ts:99`, which is structurally outside the `try` block that ends at
line 97 (evidence item 5).

## R-A vs R-B — which reading the evidence selects

Two readings both fit the symptom "UI stuck on Signing in…":

- **R-A** — the transport rejected at its bound (60 s) and the rejection was swallowed as an
  unhandled promise rejection.
- **R-B** — the promise simply never settled at all (a true hang).

**The evidence selects R-A**, not merely by absence of renderer log lines (both readings predict zero
renderer log lines — that alone does not discriminate) but by a **source-level structural fact**:
`sidecar_invoke` (`main.rs:332-343`) is a `#[tauri::command] async fn` that has already `return`ed a
value — `Err("sidecar invoke timed out".into())` — by the time `rx.recv_timeout(bound)` expires
(`main.rs:307-314`). Tauri's own command-invocation contract requires that a command function which
has returned MUST have its result value serialized and sent back over the IPC boundary; there is no
code path in `SidecarState::invoke` where the 60 s branch returns a value without that value reaching
the calling `tauriInvoke()` promise. A hang (R-B) would require the Rust-side future to never resolve
at all — but `rx.recv_timeout` is precisely a bounded, self-resolving primitive; it structurally
cannot leave `sidecar_invoke`'s `async fn` pending forever. **R-A is therefore not merely the nicer
reading — it is the one the source code makes possible; R-B is foreclosed by `sidecar_invoke`'s own
contract.**

**Falsifying observation for R-A** (what would overturn it): a future live run in which
`gamelib.log`'s `[Frontend]:`-prefixed lines contain a `sidecar invoke timed out` string reaching a
generic top-level unhandled-rejection logger (there is none currently wired for the renderer — see
"Implied fix" below), OR a run in which a `captured`/`timeout` outcome settles in UNDER 60 s and the
hook STILL never logs — either would mean the 60 s bound is not the actual blocking mechanism. Neither
was observed this session; all six outcomes exceeded 60 s and all six produced zero renderer log
output, which is exactly what R-A predicts and what R-B cannot be ruled in or out by (R-B is
foreclosed at the source level regardless).

## F-34.5-G6-06 — double Keychain prompt

**Verdict in one sentence:** GOG owns none of the two slots that prompted — signing out of GOG
calls `window.location.reload()` for reasons unrelated to Humble, that reload remounts
`GlobalState`, and `GlobalState`'s OWN mount-time effect unconditionally re-runs Humble's health
check (`getCredentials()` + `getCsrfToken()`, two distinct Keychain items) regardless of which
runner's sign-out caused the reload; the double prompt only recurs because a FAILED keyring read is
deliberately never cached (line 159's own comment), so the 8s `KEYRING_READ_TIMEOUT` racing a human's
approval time reproduces the same failure on every subsequent reload from ANY of five runners'
sign-out flows, not just GOG's.

### 1. Is the arm shared?

Every `SidecarKeyringSlotStore` instance in the process (three total, one per allowlisted slot):

- `steam-refresh-token` — `SidecarKeyringTokenStore extends SidecarKeyringSlotStore` bound in its
  constructor (`src/backend/sidecar/keyringTokenStore.ts:239-243`).
- `humble-session` and `humble-csrf` — `SLOT_STORES` map, one instance each, created once at module
  load (`src/backend/sidecar/humbleSecretStore.ts:61-64`).

A GOG sign-out reads **no** GOG-owned slot at all — there is no such slot. `GOGUser.logout()`
(`src/backend/storeManagers/gog/user.ts:140-147`) is fully self-contained: `clearCache('gog')`,
`configStore.clear()`, unlink `gogdlAuthConfig`, then `logInfo('Logging user out', LogPrefix.Gog)`.
Nothing in that file imports `keyringTokenStore.ts`, `humbleSecretStore.ts`, or anything Humble- or
Steam-related. The preserved log's `humble-csrf` line seventeen seconds after `Logging user out` is
**refuted as a direct causal link** and **confirmed as an indirect one**:

`gogLogout()` in the frontend (`src/frontend/state/GlobalState.tsx:647-656`) calls
`window.api.logoutGOG()` and then unconditionally `window.location.reload()`. That reload remounts
the whole renderer, including `GlobalState`'s constructor-time effect at
`GlobalState.tsx:1233-1234`:

```
if (this.state.humble.isLoggedIn) {
  void window.api.humbleCheckHealth().then(() => window.api.humbleSync())
}
```

This effect fires on **every** mount, unconditionally, with no gate on which runner's action caused
the reload. `HumbleUser.checkHealthAndFlagExpiry()` (`src/backend/humble/user.ts:720-764`) then
reads `getCredentials()` (`humble-session` slot) and, if that read is healthy, `getCsrfToken()`
(`humble-csrf` slot) as a backfill (line 764). Named code path end to end:

`gogLogout()` → `window.location.reload()` → `GlobalState` remounts →
`GlobalState.tsx:1233`'s mount effect → `HumbleUser.checkHealthAndFlagExpiry()` →
`getCredentials()`/`getCsrfToken()` → `SidecarKeyringSlotStore('humble-session'|'humble-csrf').getToken()`.

This is independently corroborated by a pre-existing comment naming the exact same mechanism,
written before this finding: `src/backend/humble/user.ts:64` — *"across window.location.reload()
(epic/gog/amazon/zoom/steam logout paths)"* — naming all five runners' sign-out flows as reload
triggers, none of them Humble-specific and GOG not privileged among them.

### 2. How many prompts does one liveness check cost?

`checkHealthAndFlagExpiry()` calls `getCredentials()` then `getCsrfToken()` **sequentially**, each
against a distinct Keychain account (`humble-session`, `humble-csrf`) under the same
service/application identity (`keyring_account()`'s allowlist, `src-tauri/src/main.rs`). Each
`SidecarKeyringSlotStore` instance's cache and in-flight promise are private instance state
(`this.cachedToken`, `this.pendingToken` — `keyringTokenStore.ts:100-108`); there is no cross-instance
coordination that could collapse a `humble-session` read and a `humble-csrf` read into a single
Keychain interaction even in principle. The preserved log shows only ONE of the two reads failing
this session (`humble-csrf` timeout, 11:14:34) — success is never logged (only failure is), so the
`humble-session` read either hit an already-successful cache or was itself approved inside the 8s
window with no log line either way. The developer's own report — *"was asked to approve keychain
twice"* — is direct testimonial evidence of two separate OS dialogs on the one reload, consistent
with two independently-gated Keychain items read one after another.

### 3. Why did the existing caching not prevent it?

Already present and already working as designed: `cachedToken`/`cachedAvailable` (the success cache)
and `pendingToken`/`pendingAvailable` (the in-flight dedupe, commit `2d1abe64a`) both exist today
(`keyringTokenStore.ts:99-148`) and correctly collapse concurrent same-tick callers to one request —
this is NOT the gap.

The gap is exactly where `fetchToken()`'s catch says it is (`keyringTokenStore.ts:150-162`): a
failed/unavailable read resolves `''` but is **never cached** ("NOT cached -- a failed/unavailable
read must not poison subsequent reads", line 159-160) — a deliberate and still-correct design
principle on its own terms. Combined with `KEYRING_READ_TIMEOUT = Duration::from_secs(8)`
(`src-tauri/src/main.rs:605`), which is shorter than the time a human takes to notice, read, and
approve a Keychain dialog, the observed sequence is confirmed: prompt shown → 8s elapses → read
reported `keyring:timeout` → failure NOT cached → the next caller (here, the next
`window.location.reload()`-triggered remount, from ANY of the five sign-out flows) reads again →
prompt shown again.

Total `keyring_get failed` lines in the preserved session
(`~/Library/Logs/GameLib/gamelib.log.34.5-g6-gate2`): **7**, split **4 `keyring:timeout`** and
**3 `keyring:unavailable`**:

### 4. Blast radius

Every user-triggerable, REPEATABLE path that can retry the same failed-and-uncached slot:

1. Epic logout — `epicLogout()`, `GlobalState.tsx:614-627` → `window.location.reload()`.
2. GOG logout — `gogLogout()`, `GlobalState.tsx:647-656` → `window.location.reload()`.
3. Amazon logout — `amazonLogout()`, `GlobalState.tsx:678-689` → `window.location.reload()`.
4. Zoom logout — `zoomLogout()`, `GlobalState.tsx:713-724` → `window.location.reload()`.
5. Steam logout — `steamLogout()`'s `onSignedOut`, `GlobalState.tsx:756-769` → `window.location.reload()`.

All five are independent, user-triggerable actions that each happen to call
`window.location.reload()` for their own unrelated reason, and all five land on the exact SAME
`humbleCheckHealth()` mount-time call site (`GlobalState.tsx:1233-1234`). None of the five is
Humble-owned; GOG is not privileged among them — any one of the five reproduces the identical
symptom.

6. Humble's own guided-reveal flow — `doRevealKey()` (`src/backend/humble/library.ts:1161,1173`)
   reads `getCredentials()` (session slot) on every reveal click, a separate user-triggerable
   repeatable action hitting the same uncached-failure defect on the same session slot (via
   `getLiveCsrfToken()` for the csrf half, a different read path — see that function's own doc
   comment — but the session-slot read is identical to path 1-5's).
7. The `humbleCheckHealth` IPC channel itself (`src/backend/humble/ipc_handler.ts:24`,
   `src/backend/sidecar/humbleFlowRegistration.ts:185`) is directly invokable by any future or
   existing caller (e.g. a manual refresh action), independent of any reload.

**Counting SEQUENTIAL repeat reads only** (concurrent callers are already collapsed by the
pre-existing `pendingToken` dedupe, per this plan's own instruction not to re-measure that): the
7-line session-wide count in section 3 already demonstrates the repeat-on-failure pattern is broader
than Humble's csrf slot alone — `steam-refresh-token` shows **three** separate uncached retries of
the identical failure in one session (10:45:53, 11:02:25, 11:02:33), from Steam's own callers, having
nothing to do with GOG or Humble. The blast radius is **not** "one slot on one path" — it is
`fetchToken()`'s failure-not-cached behavior applying uniformly to all three slots, reachable from at
least seven distinct call sites (five reload-triggering sign-out flows sharing one Humble call site,
Humble's own reveal flow, and Steam's own repeated callers of its own slot). Scoping a fix to "GOG's
sign-out" specifically would miss all of this — the Phase 34.2 failure mode this project has already
named and paid for once.

### K1 vs K2

**The evidence selects K1** (the failure-not-cached + 8s-timeout interaction), not K2 (two prompts
are the correct, unavoidable cost of two distinct Keychain entries).

K2 would predict the SAME two prompts on every single reload, forever, with no way for the behavior
to ever improve within a session — but the pre-existing SUCCESS cache already falsifies that: once a
read for a given slot SUCCEEDS, `cachedToken` is populated and `getToken()`'s first line
(`keyringTokenStore.ts:140`, `if (this.cachedToken) return this.cachedToken.value`) short-circuits
every future call for that slot for the rest of the process's life — no further Keychain interaction,
no further prompt, ever, for that slot in that run. The double-prompt is observed specifically in a
session where an EARLIER read of the SAME slot had already FAILED and was therefore never cached
(`humble-session` failed twice at cold boot with `keyring:unavailable`; `humble-csrf` had no
successful read logged anywhere before its own 11:14:34 failure) — the double-prompting is
conditioned on a PRIOR FAILURE, not merely on "two entries existing". That conditioning is exactly
K1's signature; K2 predicts no such conditioning (it would prompt twice on the very first reload
even with two clean, never-yet-failed slots, and would keep prompting twice on every reload
thereafter regardless of success). The log and the cache's own existing code both contradict K2.
