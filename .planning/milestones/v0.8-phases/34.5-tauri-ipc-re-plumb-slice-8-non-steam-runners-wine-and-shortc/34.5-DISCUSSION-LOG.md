## OAuth credential storage

Investigated before questioning, and the investigation redirected the area. The runners persist only
*profile* data via `configStore` (`legendary/user.ts:98`, `gog/user.ts:105`, `nile/user.ts:120`)
while real tokens live with the CLI binaries.

A prior note about a latent plaintext-token fallback was first dismissed here as disproved, then
**re-verified and found correct** — the initial `find` had been too narrow. `ElectronTokenStore`
(`storeManagers/steam/tokenStore.ts:64`) does intentionally keep a plaintext fallback (a documented
D-11 divergence, preserved byte-identical per REQ-28-07), it IS the module default at
`tokenStore.ts:123`, and only `bootstrap.ts:204`'s `installTokenStore()` call keeps the sidecar off
it — with no assertion enforcing that ordering. It is nonetheless **out of 34.5's scope** because it
is Steam's refresh-token path and these runners don't use it. See CONTEXT.md D-12 for the full,
corrected statement. The credential risk for *this* phase is **path resolution, not token
encryption**.

That surfaced the phase's most actionable finding: `pathShim.ts` implements 4 path names and throws
loudly on the rest, while the backend uses 5 — the missing `desktop`, `exe` and `documents` all sit
in the 7-channel shortcuts cluster, which will therefore throw the moment it's ported.

| Option | Description | Selected |
|--------|-------------|----------|
| `getPath('exe')` → the Tauri shell binary | Correct end-state; needs the shell to pass its path down | ✓ |
| Throw until explicitly designed | Safest, but drops 3 channels | |
| `process.execPath` (node binary) | Simplest, but writes node into the Steam VDF — advised against | |

**Notes:** this is a semantic divergence, not a stub gap — `nonesteamgame.ts:258` writes the value
into a Steam shortcut VDF as the launch command, so a wrong value creates shortcuts that launch the
wrong executable.
