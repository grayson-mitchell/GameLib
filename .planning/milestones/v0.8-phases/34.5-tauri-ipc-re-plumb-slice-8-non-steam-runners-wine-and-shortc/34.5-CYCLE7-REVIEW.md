# Phase 34.5 Cycle 7 Code Review (plan 34.5-57)

## Why this review runs at wave 3, not after the gate

This project has measured, on a sibling phase (34.9), **three consecutive gap cycles in which a
code review ran AFTER the reconciliation sweep and was therefore unledgered by construction** —
its findings had nowhere to land (`code-review-after-sweep-guarantees-unledgered-gap`). The fix is
the ORDERING, not more diligence in the sweep. This plan is wave 3, the propagation sweep is wave
6, and the blocking live gate is wave 5 — any finding here has two full waves in which to be
ledgered and acted on before either the gate or the sweep runs. That is the entire reason this
review exists as its own plan rather than as a footnote on plan 60.

## The halt decision

**`halt_gate: true`.** `F-34.5-G6-22` is the sole blocker and is the cause. Plan 34.5-59 (the
fifth blocking live gate) **must not launch** until:

1. `launcher.ts`'s `getRunnerCallWithoutCredentials` (or an equivalent fix) stops writing the raw
   PKCE `code_verifier` to `gamelib.log` on a real `NileUser.login()` call, and
2. this file is amended to `halt_gate: false` with the fix's commit hash recorded here.

**Why the fix is not made inline in this plan, despite the plan's own text allowing an
in-plan fix for a blocker "fixable within two files."** `launcher.ts` is a single file, which
technically satisfies that clause literally. Three things override it in this specific case: (a)
this plan's own Task 1 `<files>` tag states explicitly "(read-only review; no production file is
modified)"; (b) Task 2's own acceptance criteria requires `git diff --stat` from this plan to list
**exactly one file** (this REVIEW.md); (c) this execution session's own hard staging guard
instructs staging ONLY the files this plan's frontmatter `files_modified` declares, which is only
this REVIEW.md. Fixing `launcher.ts` here would violate all three. This is the same class of
same-task internal tension this cycle has already resolved twice (plan 52's innerHTML-vs-RED-proof
tension, plan 54's `not.toMatch(` comment-vs-literal-grep tension) — resolved here the same way:
correctness/scope-discipline over the literal secondary allowance, with the discrepancy recorded
transparently rather than silently exercised.

**Routing candidate:** a new plan must be inserted before wave 5 (before 34.5-59) — most naturally
between the existing 34.5-57 (this plan) and 34.5-58, or folded into 34.5-58's own scope if that
plan's author judges the one-line `sensitiveArg` fix trivial enough to piggyback — to apply the fix
above, add a regression test asserting `getRunnerCallWithoutCredentials` redacts
`--code-verifier` (mirroring the existing `--code`/`--token` test coverage, if any exists — not
independently verified by this review, since that would require modifying test files outside this
plan's scope), and update `F-34.5-G6-22`'s status here once landed.

`F-34.5-G6-23` does not halt anything — it is recorded as a note for Phase 34.6's own future
verification discipline, not a new untested hole requiring a `34.5-UNTESTED-ITEMS.md` row (the
channels it concerns are already tracked there via `U-34.5-25`/`U-34.5-32`, both opened by plan

## Closing statement

This review makes no claim about live behaviour. Every pass above is static: `tsc`, `cargo
check`/`cargo test`, `npm run test:ci`, two Python source-text gates, and direct reads of the
diffed source against the seven authoring-time defect classes this project has actually measured

because the green test mocks out exactly the code path the leak lives in.
