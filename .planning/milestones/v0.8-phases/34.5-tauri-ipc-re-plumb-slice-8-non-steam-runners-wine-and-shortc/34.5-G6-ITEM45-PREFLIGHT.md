### 2. Login-dependency analysis

**Read directly from source, both call sites:**

- `src/backend/shortcuts/nonesteamgame/nonesteamgame.ts:258` —
  `newEntry.Exe = \`"${app.getPath('exe')}"\``. The surrounding branches (`nonesteamgame.ts:261-268`)
  only re-assign `Exe` when `isFlatpak`, `!isWindows && isAppImage`, or
  `isWindows && process.env.PORTABLE_EXECUTABLE_FILE` — all three are packaging-format checks. **No
  branch reads `gameInfo.runner` or any auth/session state when constructing `Exe`.** `runner` is read
  only later (`nonesteamgame.ts:297`, `const { runner, app_name } = gameInfo`) to build the
  `gamelib://launch?appName=...&runner=...` deep-link *argument string* (`nonesteamgame.ts:299`), a
  value passed alongside `Exe`, never substituted into it.
- `src/backend/shortcuts/shortcuts/shortcuts.ts:227-229` —
  `` `${app.getPath('exe')} --no-gui gamelib://launch?appName=${app_name}&runner=${runner}` ``. Same
  shape: `app.getPath('exe')` is the executable half, `runner` appears only inside the query string of
  the argument that executable is launched with.

**Conclusion.** The VALUE written at both `exe` call sites is a pure function of `getPath('exe')`
(which itself depends only on `GAMELIB_SHELL_EXE`, set by the Tauri shell at spawn time — see
`pathShim.ts`) plus packaging-format env vars. It does not depend on the runner, on login state, or on
any live storefront session. **Item 4 is attemptable WITHOUT a fresh GOG login.** This is proven
doubly: by the source read above, and empirically — `34.5-LIVE-GATE-RERUN.md` precondition 5 recorded
GOG as SIGNED OUT for that entire session (`auth.json` absent, only the `.pre-34.5-15-gate.bak`
backup present), yet `installed.json` (re-read above, this session) still lists Alan Wake as
installed. **GOG Alan Wake's own install metadata already survives sign-out — it is its own
fallback**, and no `sideload`-runner substitute is needed. (If a fallback were ever required, the same
reasoning holds for any `sideload` game or any other installed non-Steam title: the call sites never
branch on runner or auth state, so any installed game's `appName`/`runner` pair read from its own
store's `installed.json` would work identically.)

### 6. Quit-Steam warning (numbered step, BEFORE the invocations)

1. **Quit Steam completely before running either invocation above.** Steam holds `shortcuts.vdf` in
   memory and rewrites it from memory on its own exit — a write made to the file while Steam is
   running will be silently clobbered the next time Steam quits, making the write look like it never
   happened even though it did.
2. Run the `addToSteam` invocation (or `addShortcut`, or both — see step 7 below for why both are
   required).
3. Only after both invocations have run, relaunch Steam and verify the entries there.

### 1. Which Wine action is actually reachable on macOS

`src/backend/tools/index.ts:228` — `if (isMac && tool !== 'dxvk') { return true }` — already excludes

**DXVK auto-install/restore toggle**, dispatched via `toggleDXVK`.

**UI path:** per-game Settings → **Wine** tab → **"Auto Install/Update DXVK on Prefix"** toggle

`src/frontend/screens/Settings/sections/GamesSettings/index.tsx:187`, inside `TabPanel value="wine"`).

**A newly-discovered, real eligibility trap — read directly from source, not assumed.**
`AutoDXVK.tsx:24-30` hides the entire toggle (`return <></>`) when
`wineVersion.type !== 'wine' || wineVersion.bin.includes('toolkit') || wineVersion.name.endsWith('-DXMT')`.

**without ever reaching `runWineCommand`** when `gameSettings.wineVersion.bin.includes('toolkit')`

### 6. Runner-eligibility question — answered explicitly, not resolved by substitution

`sideload` is a real, declared non-Steam runner
(`src/common/types.ts:195`, `'legendary' | 'gog' | 'sideload' | 'nile' | 'zoom' | 'steam'`) backed by
`src/backend/storeManagers/sideload/` (confirmed present: `electronStores.ts`, `games.ts`,

(`launching non-native sideloaded: ...`, immediately followed by `await runWineCommand({...})`), calls
`runWineCommand` **directly**, generically, for any "non-native sideloaded" app regardless of runner
identity.

**Does `sideload` satisfy item 5's own wording?** Item 5's wording (per
`34.5-LIVE-GATE-RERUN.md` and REQ-34.5-12) is *"`runWineCommand` succeeds for at least one NON-Steam
runner"* — `sideload` literally satisfies this; nothing in the wording requires the runner to be
*authenticated*. REQ-34.5-03's own framing (`34.5-RESEARCH.md`'s requirements table,
`REQ-34.5-07`/`REQ-34.5-03` rows) reads *"`runWineCommand` executes successfully for at least one
non-Steam runner under the sidecar (never previously proven, per Pitfall 2)"* — likewise no login
qualifier. **By the requirement's own text, `sideload` is eligible and is a genuine, login-independent
fallback** — unaffected by whichever way items 1-3 resolve this cycle (including item 1's BLOCKED
entry per D-CYCLE5-A).

**The trade that must be named, not silently resolved.** The existing gate contract's own **procedural**
"What to do" text (`34.5-LIVE-GATE-RERUN.md`, item 5) reads more narrowly: *"After a successful login
above (items 1-3), run a Wine tool action ... against a non-Steam game from **one of the
newly-authenticated runners**."* This ties the item to GOG/Amazon (post-login), which is also the
framing Pitfall 2 itself uses (`34.5-RESEARCH.md:467-471`: *"no non-Steam game has ever been
installable or launchable under the sidecar, because `login`/`authGOG`/`authAmazon` still reject
`UNPORTED_CHANNEL_MARKER`"*) — i.e. the historically-untested gap Pitfall 2 names is specifically about
the **storefront-authenticated** runners, not about non-Steam execution in the abstract. `sideload`
was, in fact, never blocked by that specific defect (it has no login channel to reject in the first
place) — so a `sideload`-only PASS, while satisfying the item's literal wording, would NOT be
exercising the same defect family Pitfall 2 was scoped around.

**Decision recorded, not invented:** name BOTH targets rather than silently picking the easier one.
  - **Primary, stronger target:** GOG (`gog` runner), if item 2 reaches a real signed-in,
    library-populated state this cycle — this is the target the gate's own procedural wording and

  - **Fallback, login-independent target:** `sideload`, usable regardless of item 1/2/3's outcome —
    satisfies the item's literal wording and REQ-34.5-03's framing, but does not retire the
    storefront-specific reading of Pitfall 2.

**Flag to plan 34.5-40, by name:** if items 2 and 3 both fail again this cycle (a real possibility —
