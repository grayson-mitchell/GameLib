## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] `registerShortcutsFlows()` lacked the idempotence guard its sibling modules already carry**
- **Found during:** Task 3, while running the full backend suite for the baseline comparison
- **Issue:** `runnerSliceRegistration.test.ts` (a pre-existing test from plan 34.5-04) calls each `registerXFlows()` three times total and asserts the registered-channel listener counts stay stable across the second/third calls. `electronStub.ts`'s `ipcMain.on` recorder appends to an array on every call (unlike `ipcMain.handle`'s `Map.set`, which naturally overwrites). `registerRunnerAuthFlows()` (plan 34.5-06) had already hit and fixed this exact failure mode for its own single send channel (`logoutGOG`) with a `let registered = false` guard. `shortcutsFlowRegistration.ts` — with THREE send channels, the highest send ratio in the slice — had no such guard, so calling it a second/third time tripled every one of `addShortcut`/`removeShortcut`/`processShortcut`'s listener counts (`[1,1,1]` → `[3,3,3]`), failing the idempotence test.
- **Fix:** Added the identical `let registered = false; if (registered) return; registered = true` guard at the top of `registerShortcutsFlows()`, mirroring `runnerAuthFlowRegistration.ts`'s own precedent verbatim (itself mirroring `storeRegistration.ts`'s original).
- **Files modified:** `src/backend/sidecar/shortcutsFlowRegistration.ts`
- **Verification:** `npx jest --selectProjects Backend` (full backend suite) went from 1 failing test (`runnerSliceRegistration.test.ts`'s idempotence case for `registerShortcutsFlows`) to 128/128 suites, 2682/2682 tests passing.
- **Committed in:** `299cb91ae` (part of Task 3's commit, alongside the new test file)

### Plan-Time Corrections (documented in test comments, not auto-fixes)

**1. "Directory listing unchanged" corrected to "run.sh specifically absent"**
- **Found during:** Task 3, writing the UNSET/EMPTY darwin exe-pin cases
- **Issue:** The plan's action item 5 instructed asserting "the directory listing is unchanged from before the call" for the UNSET/EMPTY cases. Tracing `generateMacOsApp`'s actual source order shows `mkdirSync(macOSFolder)` and `writeFileSync(plistFile, plist)` both execute BEFORE the `getPath('exe')` throw (which occurs while building the `launchCommand` template literal, the line immediately preceding the `run.sh` write) — so the `.app`/Resources/MacOS folder scaffold and `Info.plist` ARE written regardless of `GAMELIB_SHELL_EXE`'s state; only `run.sh` itself is gated on the throw.
- **Fix:** The UNSET/EMPTY test cases assert specifically that `run.sh` does not exist (the security-relevant guarantee: an empty/absent launch command is never written), rather than a byte-for-byte "nothing changed" comparison that would not hold against the real code path. Documented inline in both test cases and in the registration module's own doc comment.
- **Verification:** Confirmed via direct debugging against the real `shortcuts.ts` source and a `jest.spyOn` trace of `mkdirSync`/`logError` calls during test development; the corrected assertion passes and the CONTROL case (which must pass first) proves the negative cases are not vacuous.

## Issues Encountered

- **Debugging detour (resolved, no residual issue):** The darwin exe-pin CONTROL case initially failed silently (no error surfaced) because `jest.config.js`'s `resetMocks: true` wipes factory-supplied `jest.mock(...)` implementations before every test — including `nativeImage.createFromBuffer` and `IconIcns`'s mocked constructor, both defined inline in their `jest.mock(...)` factory bodies. This meant `convertPngToICNS` (inside the real, unmocked `shortcuts.ts`) called `nativeImage.createFromBuffer(...)`, got `undefined` back, threw `TypeError: Cannot read properties of undefined (reading 'resize')`, was silently caught by `convertPngToICNS`'s own try/catch, and returned `false` — so `generateMacOsApp`'s `.app` folder got created then immediately removed via its own `rm()` fallback, with zero visible signal until the mocked `logError`'s call arguments were inspected directly. Fixed by re-arming both mock implementations in the shared `beforeEach` (mirroring `steamAuthFlows.test.ts`'s own documented `mockRequestRustInvoke.mockImplementation(...)` re-wiring convention for exactly this `resetMocks` gotcha). Documented in the test file's own header comment as a GAP FIX so a future suite author isn't caught by the same trap.
