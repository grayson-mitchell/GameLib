# Phase 34.5 Plan 23: F-34.5-G6-02 Fix (60s Invoke Bound vs Human-Paced Login Deadlines) Summary

**Exempted `oauthCaptureLogin`, `humbleStartLogin` and `humbleReconnect` from the Rust shell's 60-second `INVOKE_TIMEOUT`, wrapped the renderer's previously-unguarded capture await in a try/catch that surfaces a greppable `capture-transport-failed` error state, and added a source-parsed standing guard proven load-bearing by an actual revert-and-observe-failure run.**

## Performance

- **Duration:** ~55 min
- **Completed:** 2026-08-01
- **Tasks:** 3 (all completed)
- **Files modified:** 4

## Accomplishments

- Closed F-34.5-G6-02's diagnosed root cause: `oauthCaptureLogin` inherited the default 60s
  `INVOKE_TIMEOUT` while its own `DEFAULT_DEADLINE_MS` is 300,000ms — every real OAuth login in
  the 2026-08-01 gate (GOG 68s, Amazon 91s, Epic 300s x3) exceeded 60s, so the Rust shell rejected
  the renderer's promise 3-4 minutes before the sidecar actually settled.
- Applied the SAME fix to `humbleStartLogin`/`humbleReconnect` (10-minute
  `LOGIN_WATCH_TIMEOUT_MS`), per 34.5-22 Task 2's recurrence count naming all three as sharing the
  identical defect shape — scoping the fix to only `oauthCaptureLogin` would have left 2 of 3
  known instances open, contrary to this project's standing "count before scoping" lesson.
- Wrapped `useTauriOAuthLogin.ts:99`'s previously-bare `await window.api.oauthCaptureLogin(...)`
  in its own try/catch — this was the ONLY await in `run()` outside a try block, and the direct
  cause of the observed defect (zero `[useTauriOAuthLogin]` log lines against six real backend
  terminal outcomes, per 34.5-G6-FINDINGS.md evidence item 1). A rejection now settles
  `{ phase: 'error', message }` and emits one `capture-transport-failed` log line, honouring the
  `cancelled` guard first so a post-unmount rejection produces neither.
- Added a standing guard (`longRunningChannels.test.ts`) that parses the real millisecond
  deadline out of `oauthLoginCapture.ts`/`humble/user.ts` (comment-stripped, reusing the file's
  existing shared stripping helpers) and asserts LONG_RUNNING_CHANNELS membership whenever that
  deadline exceeds `INVOKE_TIMEOUT` — proven to actually fail, not merely written to pass, by
  temporarily reverting Task 1's `main.rs` edit and observing the guard's own test throw
  `"oauthCaptureLogin's internal deadline (300000ms) exceeds INVOKE_TIMEOUT (60000ms) but is
  absent from LONG_RUNNING_CHANNELS"`, then restoring (`git diff --stat` confirmed zero residual
  change — the reverted state was never committed, and no `git stash`/`reset --hard` was used).

## Decisions Made

- **Recurrence-count scope honoured, not narrowed** — `oauthCaptureLogin`, `humbleStartLogin` and
  `humbleReconnect` were all exempted in Task 1's single commit, per 34.5-22 Task 2's explicit
  3-channel recurrence count and this plan's own action text ("if it named additional channels,
  add them here in the SAME edit").
- **No renderer-side timeout added** — the try/catch in Task 2 is defense-in-depth only; the
  sidecar's `DEFAULT_DEADLINE_MS`/`LOGIN_WATCH_TIMEOUT_MS` remain the sole deadline authority, so
  this fix structurally cannot reintroduce a second competing bound.
- **`capture-transport-failed` kept as a distinct literal** — never folded into the pre-existing
  generic `phase=error` line for a resolved `{status:'error'}` outcome, so a transport failure and
  a backend-reported failure stay greppable apart (T-34.5-G6-10's disposition).
- **Standing guard scoped to a declared table, not a source-wide scan** — mirrors 34.5-22's own
  scope note (unbounded-download channels like `installWineVersion` are a different risk shape and
  were deliberately excluded from the recurrence count this guard covers).
