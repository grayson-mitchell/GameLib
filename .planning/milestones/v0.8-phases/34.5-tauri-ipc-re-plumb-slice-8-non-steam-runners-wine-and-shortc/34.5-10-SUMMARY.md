# Phase 34.5 Plan 10: Complete the Auth Cluster with Amazon's Four Channels Summary

**Registers Amazon's four auth/sign-out channels (`getAmazonLoginData`, `authAmazon`, `getAmazonUserInfo`, `logoutAmazon`) onto the Tauri sidecar, completing the 11-channel auth cluster and closing T-34.4.1-44b's credential-mint half by making `authAmazon` provably dependent on plan 34.5-02's host anchor.**

## Performance

- **Duration:** ~35 min
- **Completed:** 2026-07-29
- **Tasks:** 2/2 completed
- **Files modified:** 2

## Accomplishments

- `registerRunnerAuthFlows()` now registers all 11 declared auth channels: Amazon's `getAmazonLoginData` → `NileUser.getLoginData()`, `authAmazon` → `NileUser.login(data)`, `getAmazonUserInfo` → `NileUser.getUserData()`, `logoutAmazon` → `NileUser.logout()` — all `addHandler`/invoke, matching `main.ts`'s registration kind exactly.
- `authAmazon` validates its payload against `NileRegisterData`'s real shape (`code`/`code_verifier`/`serial`/`client_id`, all required non-empty strings) BEFORE calling `NileUser.login`, returning `NileUser.login`'s own `{ status: 'failed', user: undefined }` failure shape on rejection and never logging the rejected payload — a captured authorization code is a credential.
- A comment above `authAmazon` records the ordering constraint: this channel mints a real Amazon credential from a value only reachable via `oauthLoginCapture.ts`'s `matchOAuthRedirect('nile', …)`, whose `www.amazon.com` host anchor (plan 34.5-02) is the input-validation control protecting it — and that the anchor's host value is itself only MEDIUM confidence pending live-gate item 3.
- `logoutAmazon` is an unmodified delegation to `NileUser.logout()` (confirmed no Electron `session` usage), with a comment recording why the inherited cookie-jar residual (T-34.4.1-47) is accepted rather than fixed here.
- `runnerAuthFlows.test.ts` extended from 23 to 30 assertions: bidirectional registration-kind coverage for all 11 channels, a strengthened sign-out asymmetry check naming `logoutLegendary`/`logoutAmazon` as the handle-kind siblings, a trust-boundary describe block for `authAmazon` (5 cases: non-object, missing field, empty string, null/undefined, valid payload), and an integration describe block importing the REAL (unmocked) `matchOAuthRedirect` proving a URL that would have matched the old host-free nile matcher now yields `null` and never reaches `authAmazon` — the anchor-plus-mint pair (T-34.5-34) fails together if either half regresses.
- Removed Amazon's 4 channels from the "never registered here" describe block (they now ARE registered by this plan) and updated its comment to state the cluster is complete at 11.

## Decisions Made

- **`authAmazon` reuses `NileUser.login`'s own failure shape** (`{ status: 'failed', user: undefined }`, `nile/user.ts:66-71`) on a rejected payload, rather than inventing a new one — consistent with `login`/`authGOG`'s established precedent of mirroring the runner method's own internal error path.
- **No ordering repair applied to `NileUser.logout()`** — read the full method and confirmed it contains no `session` call (unlike `LegendaryUser.logout()`, which plan 06 had to restructure); the faithful port is the unchanged body.
- **No cookie clear added to `logoutAmazon`** — Amazon cookies landing in the shared app-wide jar is the inherited, already-accepted T-34.4.1-47 residual (T-34.5-37, disposition `accept` in this plan's threat register); Electron's own `NileUser.logout()` never cleared them either, so adding a clear here would be a behaviour change, not a port.
