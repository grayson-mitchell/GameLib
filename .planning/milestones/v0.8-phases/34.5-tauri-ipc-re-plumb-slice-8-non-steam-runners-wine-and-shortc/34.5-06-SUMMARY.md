# Phase 34.5 Plan 06: Epic/GOG auth channel port + Epic sign-out defect fix Summary

**Ports Epic's and GOG's 7 auth/sign-out channels onto the Tauri sidecar, fixing a real defect along the way: Epic's sign-out previously aborted mid-cleanup under the sidecar's session stub, leaving the stored profile behind despite the CLI credential revocation succeeding.**

## Performance

- **Duration:** ~65 min
- **Completed:** 2026-07-29
- **Tasks:** 3/3 completed
- **Files modified:** 7 (2 created, 5 modified)

## Accomplishments

- `LegendaryUser.logout()` now runs its cookie-side cleanup through a guarded per-step loop (same shape as `humble/user.ts`'s `disconnect()`), so the credential-side cleanup (`configStore.delete('userInfo')` + `clearCache('legendary')`) runs unconditionally — even when the session API throws on the very first call, which is exactly what happens under the sidecar's `{}` `session.fromPartition()` stub.
- Under Tauri, Epic's cookie-side cleanup opens a hidden window on Epic's login origin and clears only `epicgames.com` cookies via the domain-scoped `LoginWindowSeam.clearCookies()` — never a blanket wipe.
- `registerRunnerAuthFlows()` now registers all 6 Epic/GOG invoke channels (`getEpicGamesStatus`, `getUserInfo`, `isLoggedIn`, `login`, `logoutLegendary`, `authGOG`) plus the one send channel (`logoutGOG`), with `login`/`authGOG` validating their credential payload at the trust boundary (never logging the rejected value) and `logoutGOG` guarding the synchronous `GOGUser.logout()` in a try/catch rather than a `.catch()` that would itself throw against a `void` return.
- A bidirectional registration-kind test suite (23 cases) proves all 7 channels' kind in both directions, the send/handle sign-out asymmetry, the trust-boundary rejection behavior, and the send-channel's fire-and-forget guard.
- First test file for `legendary/user.ts` (6 cases), directly proving the defect this plan fixes.

## Decisions Made

- **Epic cookie host = apex `epicgames.com`**: `EPIC_LOGIN_URL` (`frontend/screens/WebView/loginRoutes.ts:45`) is `https://www.epicgames.com/id/login?responseType=code`. The apex domain is used (not `www.epicgames.com`) so the domain-suffix match in `LoginWindowSeam.clearCookies()` covers any Epic subdomain that actually sets the auth cookie — mirroring `humble/user.ts`'s own choice of the apex `humblebundle.com` over `www.humblebundle.com`.
- **Idempotence guard added to `registerRunnerAuthFlows()`**: the four 34.5 registration modules (auth/wineTools/shortcuts/runnerMisc) share a pre-existing idempotence test in `runnerSliceRegistration.test.ts`. That test was vacuously true while all four modules were empty; implementing this plan's real `logoutGOG` (`ipcMain.on`, array-push semantics) is the first channel in this family to actually need the guard, since `ipcMain.handle` (`Map.set`) is naturally idempotent but `ipcMain.on` is not.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 — Bug] `runnerSliceRegistration.test.ts`'s idempotence test had an off-by-one baseline bug, invisible until a real send-kind channel existed**
- **Found during:** Task 3, running the plan's own required verification (`cd src/backend && npx jest sidecar/__tests__/runnerSliceRegistration.test.ts` must still exit 0).
- **Issue:** The test captured its "before" baseline listener count PRIOR to any call to `register()`, then compared it against the count AFTER TWO calls. This can only hold if the module registers zero listeners — true for all four modules while they were declared-but-empty (34.5-04), but structurally impossible once a real `ipcMain.on` channel exists (its listener array is appended to on every call, so even a single genuine registration makes the post-call count > 0, permanently unequal to a pre-any-call baseline of 0).
- **Fix:** Call `register()` once to establish the real baseline (matching the describe block's own documented intent — "must not stack a DUPLICATE listener," i.e. a second call must not add beyond what the first established), capture `before` at that point, then call once more and compare.
- **Files modified:** `src/backend/sidecar/__tests__/runnerSliceRegistration.test.ts`
- **Verification:** `npx jest sidecar/__tests__/runnerSliceRegistration.test.ts` — 27/27 passing (previously 26/27, the idempotence case for `registerRunnerAuthFlows` failing).
- **Committed in:** `467197835`

**2. [Rule 3 — Blocking issue] `registerRunnerAuthFlows()` needed its own idempotence guard**
- **Found during:** Task 3, same verification run as above.
- **Issue:** `ipcMain.on('logoutGOG', ...)` (`electronStub.ts`) pushes onto an array on every call. A second call to `registerRunnerAuthFlows()` (exercised by the pre-existing idempotence test) would double-register the `logoutGOG` listener.
- **Fix:** Added `let registered = false` guard at module scope, mirroring the existing precedent in `storeRegistration.ts`. The six `ipcMain.handle` calls were already naturally idempotent (`Map.set` replaces); only the guard was missing for the one send channel.
- **Files modified:** `src/backend/sidecar/runnerAuthFlowRegistration.ts`
- **Verification:** `runnerSliceRegistration.test.ts`'s idempotence case for `registerRunnerAuthFlows` passes; `runnerAuthFlows.test.ts` (which calls `registerRunnerAuthFlows()` once at file scope) still registers all 7 channels correctly.
- **Committed in:** `467197835`
