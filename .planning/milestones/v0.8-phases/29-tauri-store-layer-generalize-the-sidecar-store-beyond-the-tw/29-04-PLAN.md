<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| renderer → `sidecar:store-fetch` (`storeName` argument) | an arbitrary attacker-controlled string reaches store resolution |
| sidecar store values → renderer snapshot payload | the allow-list is the access-control mechanism (ASVS V4) |
| bundler → `storeRegistration.ts` imports | tree-shaking could silently un-register stores in the built sidecar |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-29-13 | Tampering | `STORE_FETCH_CHANNEL` handler's `storeName` | mitigate | Validate against `STORE_UNIVERSE` or `/^[A-Za-z0-9_-]{1,64}$/` BEFORE resolution, and resolve only via `getRegisteredStore()` / the fixed `{cwd:'store_cache', name, clearInvalidConfig:true}` CacheStore shape. Never reconstruct a path from the name (29-RESEARCH Pitfall 4), so `fileStore.ts`'s T-27-03 guard is not bypassed. Asserted by the `'../../etc/passwd'` test case. |
| T-29-14 | Information Disclosure | allow-list enforced eagerly but forgotten in the lazy fetch | mitigate | Both handlers call the same `filterStoreSnapshot()`; acceptance criterion requires ≥ 2 occurrences in `handlers.ts` and a test asserting `csrfToken` absent from BOTH paths. |
| T-29-15 | Information Disclosure | removing the T-27-09 `refreshToken` hand-strip weakens defense in depth | mitigate | The strip is not removed, it is GENERALIZED — `filterStoreSnapshot` excludes it for every store, and the renderer's own filter (plan 29-06) remains the second layer. `skeletonFlows.test.ts`'s existing "refreshToken absent" assertion must keep passing unchanged (acceptance criterion). |
| T-29-16 | Denial of Service | eager snapshot serializing unbounded caches past `index.tsx`'s 8000ms timeout | mitigate | The eager payload is exactly `BOOT_SET_STORES`; a test asserts `wikigameinfo`/`uploadedLogs`/`timestampStore`/`downloadManager` are absent. |
| T-29-17 | Repudiation | a store with no live instance silently yielding `{}` | mitigate | Every miss writes an stderr diagnostic naming the store (never a value), so a registration gap is observable in sidecar logs rather than presenting as empty config. |
| T-29-18 | Information Disclosure | stderr diagnostics leaking store values | mitigate | Diagnostics carry the store/field NAME only — same rule as T-28-04, which exists because token material lives in these payloads. |
| T-29-SC | Tampering | npm/pip/cargo installs | mitigate | Not applicable — zero new packages this phase (29-RESEARCH.md § Package Legitimacy Audit). |
</threat_model>
