<objective>
Close the silent hole: register real `storeSet`/`storeDelete`/`storeNew` handlers
behind a single write choke point that persists through the registry and announces
every write back to the renderer as a per-key change event.

Purpose: today `snapshotSet`/`snapshotDelete` emit `send`-kind frames that
`dispatchSend()` looks up in `listenerRegistry`, finds an empty array for, and
iterates zero times. No error, no log, no rejected promise — the write vanishes with
ZERO observable signal, worse than every other unported channel (which at least
rejects with `UNPORTED_CHANNEL_MARKER`). Meanwhile the renderer's optimistic snapshot
update makes the UI look like it worked until the next restart.

Output: `src/backend/sidecar/storeWriteHandlers.ts`, a small `handlers.ts` wire-up,
and extended `skeletonFlows.test.ts`.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| renderer → `storeSet`/`storeDelete`/`storeNew` (`storeName`, `key`, `value`, `options` all attacker-controllable) | this is a renderer-reachable arbitrary-write primitive into the config store — the single largest new surface in this phase |
| sidecar write → `frontend_message` push | write confirmations flow back to the renderer |
| sidecar write → Keychain-owned token key | Phase 28's boundary; a write here corrupts the shipped Electron app's session |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-29-26 | Tampering | `storeSet` with an unregistered/attacker-chosen `storeName` | mitigate | Guard (a): name must be in `STORE_UNIVERSE` or match `/^[A-Za-z0-9_-]{1,64}$/`; resolution only via `getRegisteredStore()` or the hardcoded cache-store shape. No path is ever reconstructed from the name, so `fileStore.ts`'s T-27-03 guard is not bypassable. Asserted with `'../../evil'`. |
| T-29-27 | Tampering | `storeNew` constructing a store from renderer-supplied `cwd`/`name` | mitigate | `storeNew` ignores the renderer's `options` and uses hardcoded `{cwd:'store_cache', name: storeName, clearInvalidConfig:true}` only. This is the direct continuation of T-27-03: `resolveStorePath()` is only safe while `cwd`/`name` never originate in an RPC frame. Acceptance criterion forbids assigning `cwd` from a handler argument. |
| T-29-28 | Elevation of Privilege | a `storeSet` writing `TOKEN_STORE_KEY` into `steamConfigStore`, reopening Phase 28 D-04 / REQ-28-02 | mitigate | Unconditional guard (b) keyed off the imported `TOKEN_STORE_KEY` constant, with a live regression test asserting the stored token is byte-identical after an attempted write and that no change event is emitted. Enforced by guard, not by discipline. |
| T-29-29 | Information Disclosure | write path admitting fields the read policy forbids (e.g. seeding `csrfToken`) | mitigate | Guard (c) applies `isAllowedStoreField` to writes too — one policy, both directions. |
| T-29-30 | Repudiation | a write silently dropped under error, relocating Pitfall 1's bug instead of fixing it | mitigate | Every rejection and every caught `set`/`delete` throw writes exactly one stderr line naming store+key (never the value). | T-29-31 | Information Disclosure | change-event payload or error log carrying secret values | mitigate | The value only reaches the renderer for allow-listed fields (guard (c) runs before emission); error logs carry names only (T-28-04). |
| T-29-32 | Spoofing | a write bypassing the choke point in future code | mitigate | Exactly one `pushFrontendMessage` call site in this file (acceptance criterion pins the count at 1) plus an explicit comment that any bypass silently diverges the renderer's snapshot. |
| T-29-SC | Tampering | npm/pip/cargo installs | mitigate | Not applicable — zero new packages this phase (29-RESEARCH.md § Package Legitimacy Audit). |
