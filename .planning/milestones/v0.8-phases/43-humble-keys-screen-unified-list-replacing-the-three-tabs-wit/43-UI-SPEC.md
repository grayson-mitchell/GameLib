# Phase 43 — UI Design Contract

> Visual and interaction contract for the Humble Keys unified list. Generated by
> gsd-ui-researcher, verified by gsd-ui-checker. Every locked decision below is cited back to
> `43-CONTEXT.md` (`D-43-NN`) — this document translates those decisions into pixels, tokens
> and copy, it does not re-decide them. Two dimensions (sort's third option, `gog_keyless`'s

## Screen Layout Contract

Top to bottom, per `43-CONTEXT.md`'s phase boundary (locked, not re-decided here):

1. **Title row** (`.humbleKeysHeaderTop`, unchanged flex row) — `Humble Keys` heading, **plus a
   new search box**, plus the existing refresh/last-synced control. Order left→right: title,
   search box, refresh button. Gap between search box and refresh button: `--space-sm` (12px).
   The search box does **not** go in the controls row — this ordering is explicit in
   `43-CONTEXT.md`'s domain block and is not discretionary.
2. **Controls row** (new, sits below the title row at `--space-lg` (24px) vertical gap) — sort
   picker (`SelectField`) then `Redeemable keys only` checkbox (`ToggleSwitch`), left-aligned,
   `--space-md` (16px) gap between them. No counts anywhere (D-43-04) — do not render a result
   count in this row even though the library-filtering sketch's own panel omits one too, for a
   different reason (that sketch has no count either; this alignment is coincidental, not
   copied).
3. **Column-header row** (new) — `TYPE` / `GAME` / `KEY`, static text, **not** clickable-to-sort
   (Claude's Discretion in CONTEXT, resolved here: the roadmap already specifies a separate sort
   picker, so a second, competing sort mechanism on the headers would be undeclared scope).
   Rendered as a CSS Grid row sharing the exact column template with each data row (see Column
   Geometry Contract) so the header's boundaries and the rows' boundaries are the same numbers,
   not independently eyeballed ones. `--text-xs` / `--semibold`, `--text-secondary` color,
   `border-bottom: 1px solid var(--divider)` beneath it (same divider token as row separators,
   heavier visual weight optional but not required).
4. **Rows** — one `<li class="humbleKeyRow">` per key, three-column CSS Grid (converted from the
   current flex layout — see Column Geometry Contract for why and how).

## Column Geometry Contract

**This is the single most load-bearing part of this spec** — the KEY column must render a
full-width single button, a side-by-side button pair, or bare multi-line text, without ever
changing the row's column boundaries. The rule that makes this possible:

> **Column WIDTH is fixed per column, identical on every row and on the header. Column CONTENT
> may wrap, stack, or vary in height — the column box itself never resizes to fit content.**

**Primary visual anchor:** the row's `GAME` title (`.humbleKeyRowTitle`, `--text-md`) with its
`UrgencyBadge` inline after it. It is the only element on the row at body size, the only one in a
flexible track, and the only one a scanning eye should land on first. `TYPE` is a fixed-width
identifier and `KEY` is an action target — neither competes for that role. Anything added to a row
in a later phase must not outweigh the title.

### Grid definition

Replace `.humbleKeyRow`'s current `display: flex` with `display: grid`, and give both the header
row and every data row the same explicit template:

```css
.humbleKeysColumnHeader,
.humbleKeyRow {
  display: grid;
  grid-template-columns: 6.5rem minmax(0, 1fr) 20rem;
  column-gap: var(--space-md); /* 16px */
  align-items: start;
}
```

Column-by-column:

| Column | Track | Width | Rationale |
|---|---|---|---|
| `TYPE` | 1 | `6.5rem` fixed (104px) | Holds the store-logo box (`calc(var(--text-md) * 1.2)` ≈ 19px square, unchanged sizing rule from `index.css`'s `.humbleKeyRowStoreLogo`) **or** a text-only label for no-logo platforms (Origin, Ubisoft Connect, Battle.net, Nintendo), left-aligned, wrapping onto up to two lines rather than widening the column. Empty (no icon, no text) for UNPICKED rows (D-43-02's `!isUnpicked` gate, unchanged) and reserves its full width anyway, so the `GAME` column's left edge never shifts row to row. **Needs live-gate re-verification per D-43-21** — this number is a code-level estimate, not a pixel measurement (no jsdom/browser automation exists in this repo's frontend jest project). |
| `GAME` | 2 | `minmax(0, 1fr)` flexible | Title (`.humbleKeyRowTitle`) plus `UrgencyBadge` inline after it (D-43-16), gap `--space-xs`. `min-width: 0` is required on this track — a flexible grid/flex child without it can overflow its column instead of wrapping (the same trap the library-filtering sketch's `min-width: 0` note names for its grid container). Title wraps, does not truncate (unchanged from current behaviour — no `text-overflow: ellipsis` exists on `.humbleKeyRowTitle` today, this phase does not add one). |
| `KEY` | 3 | `20rem` fixed (320px) | See KEY-column internal layout below. **Needs live-gate re-verification per D-43-21**, same basis as `TYPE`. |

### KEY column internal layout

```css
.humbleKeyColumnCell {
  display: flex;
  flex-direction: column;
  align-items: flex-start;
  gap: var(--space-2xs);
  width: 100%;
}

.humbleKeyColumnCell .humbleKeyActionRow {
  display: flex;
  flex-wrap: wrap;      /* pair wraps to two lines inside the SAME column width, never widens it */
  gap: var(--space-2xs);
  width: 100%;
}

.humbleKeyColumnCell .humbleKeyActionRow > button {
  flex: 1 1 8.5rem;      /* two buttons share the row; each wraps its own label rather than overflowing */
  min-width: 0;
}
```

- **Full-width single button** (scenarios 1, 3, 5): one `<button>` at `width: 100%` of the `KEY`
  column — this is the existing `.humbleKeyRowAction > .humbleKeyGiftButton { width: 100% }`
  rule, reused verbatim, just now scoped to the whole `KEY` cell instead of a dedicated
  fixed-basis flex child.
- **Side-by-side pair** (scenario 2): two buttons inside `.humbleKeyActionRow`, each
  `flex: 1 1 8.5rem`. At `20rem` column width minus one `--space-2xs` gap, both buttons fit on
  one line for short labels ("Activate" + "Gift on Humble"); a longer label ("Claim on Ubisoft
  Connect") wraps its own text within its half rather than pushing the pair onto two rows —
  and if a label is long enough that wrapping the text still isn't enough, `flex-wrap: wrap`
  lets the second button drop to its own line **within the same 20rem column**, never widening
  it.
- **Bare state text** (scenario 4 no-button case, UNREDEEMABLE): a stack of `<span>` captions
  inside `.humbleKeyColumnCell`, no button, `align-items: flex-start`, same `20rem` column width,
  text wraps normally.
- **Sub-case (Pitfall C carried forward):** an `UNREVEALED` key whose `keyindex` has not been
  resolved by a sync renders the existing non-interactive `humbleKeyClaimDisabledCaption` text
  ("Sync to enable claiming") in place of the scenario-2 button pair — same column, same width,
  no behavioural change from today, just relocated into the new grid cell.

**State badge + expiration placement inside `KEY`** (D-43-15): render as the **first** line of
`.humbleKeyColumnCell`, above whichever action content follows — `.humbleKeyStateBadge` +
(space) + expiration/annotation caption, then the button/pair/text below it at `--space-2xs` gap.
This applies uniformly across all five scenarios so the column's internal rhythm (status line,
then action) never changes shape between rows — only the second line's content varies. This
specific stacking order is this document's own specification (Claude's Discretion territory per
CONTEXT — D-43-15/17 mandate that the status text and every action live in `KEY`, but do not
mandate the exact internal order); it directly reuses the existing `.humbleKeyClaimGroup`
vertical-stack pattern (`flex-direction: column`, annotation above button) rather than
inventing a new one.

### The row-separator landmine (verified against `index.css:187-212`)

`.humbleKeyRow` currently carries `border-bottom: 1px solid var(--divider, rgba(255,255,255,
0.08))`. **Known GameLib trap:** a 1px border painted on a fractional (`1fr`) grid *track*
vanishes in WKWebView. This border must be kept on the **row container** (`.humbleKeyRow`
itself, i.e. the grid container, not any one of its three grid-item children) — it spans the
full row width regardless of how the three tracks divide it, so it never touches the vanishing
condition. Do not move this border onto the `GAME` column specifically. **Re-verify live per
D-43-21** before closing the two folded todos — this phase changes the layout mechanism (flex→
grid) around this exact declaration, so the prior "it renders as a hairline" assumption does not
automatically carry over.

## Search & Filter Contract

- **Search box** — reuses `components/UI/SearchBar` unchanged. Placeholder:
  `humbleKeys.searchPlaceholder` ("Search your keys"). Matches `.humbleKeyRowTitle`'s
  `displayTitle` **only** (D-43-10) — case-insensitive substring match, mirroring the
  library-filtering sketch's `q.toLowerCase().includes(...)` pattern, scoped to title alone (not
  store, not bundle origin). No debounce is specified as a new requirement — `SearchBar`'s
  existing native-input-listener behaviour (immediate, uncontrolled) is unchanged; this screen's
  list is small enough (tens of rows) that debouncing a client-side `Array.filter` is not
  warranted, unlike the store-search use case that motivated `SearchBar`'s `loading` prop.
- **Redeemable-only checkbox** — `components/UI/ToggleSwitch`, `htmlId="humbleKeysRedeemableOnly"`,
  label `humbleKeys.redeemableOnly` ("Redeemable keys only"), **checked by default** (D-43-09).
  Predicate: `REDEEMABLE_ONLY_STATES.has(key.state)` (`viewFilters.ts` = `{UNPICKED,
  UNREVEALED}`) — state-only, reads no ownership/platform/confidence field (D-43-08). Unchecking
  it shows everything, including REVEALED, REDEEMED and UNREDEEMABLE rows.
  **Superseded by 260911-t0p:** originally specified as `WAITING_STATES.has(key.state)`
  (`viewFilters.ts:20` = `{UNPICKED, UNREVEALED, REVEALED}`, "zero new predicate code"). A direct
  user instruction to that quick task reversed REVEALED's membership for this checkbox
  specifically — a REVEALED key is not itself "redeemable" — so a new, separate constant,
  `REDEEMABLE_ONLY_STATES`, now backs this predicate. `WAITING_STATES` itself is unchanged and
  still backs `selectKeysWaiting` and the per-row claim gate.
- **Nothing persists** (D-43-07) — search text resets to `''`, checkbox resets to `true`, sort
  resets to `Expiring soonest`, on every mount. No `localStorage`, no lifted route state.
- **Combination semantics** — search and the checkbox AND together (a row must match both to
  show), same convention as the library-filtering sketch's facet model, scaled down to two
  controls instead of many.

## Empty States

Two distinct states, per Claude's Discretion in CONTEXT (resolved here) and the library-filtering
sketch's zero-result recovery finding, which CONTEXT explicitly imports for this screen:

| State | When | Heading | Body | Recovery action |
|---|---|---|---|---|
| **Genuinely empty** | `humble.keys` is empty (user has synced, has zero Humble keys of any kind) | `humbleKeys.emptyHeading` — "No Humble keys yet" | `humbleKeys.emptyBody` — "Sync your Humble Bundle account to see your keys here." | None needed — the existing refresh button in the title row is the recovery path; do not duplicate it as a second button in the empty state body. |
| **Filtered to zero** | `humble.keys` is non-empty, but the current search text + `Redeemable keys only` checkbox combination matches nothing | `humbleKeys.filteredEmptyHeading` — "No keys match" | `humbleKeys.filteredEmptyBody` — "Try a different search, or turn off \"Redeemable keys only.\"" | **Inline `humbleKeys.clearFilters` button** ("Clear search and filters") that resets the search box to `''` and the checkbox to `false` (not to its `true` default — the point is to widen the result set, not just re-apply the default that likely caused the empty state) |

**Why this distinction matters here specifically:** D-43-09 checks the box by default, so a user
whose entire library is terminal (all REDEEMED/UNREDEEMABLE) hits the filtered-empty state on
their **very first visit** — that path must never read as "you have no keys," which would be
false. This is the exact failure mode the library-filtering sketch's "Zero-result state needs
recovery path" finding names, applied to a one-checkbox filter instead of a multi-facet panel.

Reuses `.humbleKeysEmptyState`'s existing chrome (`--space-xl` padding, centered text,
`--text-lg`/`--semibold` heading, `--text-sm`/`--regular` body, `--text-secondary` color) — no
new empty-state visual language, only new copy and the one new recovery button.

## Concerns (non-binding)

These do not change the contract above — they are flagged for the operator/planner's awareness,
not acted on here.

- **"Gift a friend" vs "Gift on Humble."** The roadmap's phase description names the scenario
  "Gift a friend," but this spec recommends keeping the existing, tested `humbleKeys.giftOnHumble`
  ("Gift on Humble") label rather than minting a new string, because (a) it is Claude's
  Discretion territory per CONTEXT, not a locked decision, (b) "Gift on Humble" is more literally
  accurate about where the click goes (matches this phase's own copy-accuracy standard, applied
  to itself), and (c) it avoids an unforced new-key mint. If the operator wants the literal
  roadmap wording, that is a one-string copy change with no geometry impact.
- **Column width numbers (`6.5rem`, `20rem`) are estimates, not measurements.** This repo's
  frontend jest project has no jsdom/browser automation, so nothing in this spec was pixel-
  verified. D-43-21 already requires a live-gate pass on this exact row's geometry before the two
  folded todos close — treat the numbers here as the starting point for that live gate, not as
  a substitute for it.
- **The `Log into {{store}} and claim` button (scenario 1) cannot verify its own premise.**
  D-43-12 states plainly that GameLib's login state is not the store's browser session — the
  button can only ever be honestly labelled as "connect this store to GameLib," never as a
  guarantee the subsequent redeem page will work. This spec keeps the roadmap's literal wording
  because CONTEXT does not override it, but flags that the wording is optimistic by construction
  and worth a second look if the operator wants the caveat surfaced in the UI itself (e.g. a
  tooltip) rather than left implicit.
