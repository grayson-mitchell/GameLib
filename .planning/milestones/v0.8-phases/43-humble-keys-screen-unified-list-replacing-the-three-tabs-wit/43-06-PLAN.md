<objective>
Turn the KEY cell from four independent optional-prop branches into the enumerated scenario set the
phase is named for, and mint the strings those scenarios need.

Purpose: today the row's behaviour is decided by which of four unrelated optional props the caller
happened to pass, which is why the same key rendered differently in three tabs. D-43-17 replaces
that with one rule: every action lives in KEY and is one of the enumerated scenarios. Plan 43-05
already moved the affordances into the KEY cell; this plan re-models what decides which one shows.

Output: a closed login-store table in the pure tier, one exhaustive scenario resolver, the new
buttons, and their i18n keys.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Humble-supplied `key_type` to scenario/redeem selection | An untrusted remote string chooses which button, label and destination render |
