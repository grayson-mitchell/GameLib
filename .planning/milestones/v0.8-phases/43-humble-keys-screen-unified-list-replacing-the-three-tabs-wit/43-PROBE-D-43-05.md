## Probe design

`describeZeroKeyOrder`'s existing `fieldNames(rawOrder)` diagnostic (`classify.ts:582-588`) only
fires on the `tpkd_dict` absent/null/mistyped branch — a branch that has never fired live — so it
cannot answer this question. A populated order (the common case) never reaches it.

`probeOrderFieldNamesD4305` (`classify.ts`, temporary) was added specifically to reach the
populated-order path: it takes the raw order object and returns `Object.keys(value).sort()`
joined into `[name,name,...]`, with **no slice and no reference to `MAX_DIAGNOSED_FIELDS`**. This
was necessary because `fieldNames`'s existing cap (`MAX_DIAGNOSED_FIELDS = 15`) truncates at 15
names and appends `,+N more` — a real order with more than 15 top-level fields would have hidden
a date field behind that suffix, and reading that suffix's absence-of-a-visible-name as
absence-of-the-field-entirely would have produced a false NEGATIVE verdict. The probe function
was pasted into the coordinator's review verbatim and independently confirmed to contain no
slice, no cap, and no reference to `MAX_DIAGNOSED_FIELDS`:

```ts
export function probeOrderFieldNamesD4305(value: object): string {
  const names = Object.keys(value).sort()
  return `[${names.join(',')}]`
}
```

`library.ts` called it once per successfully-committed order — immediately after
`humbleLibraryStore.set(gamekey, entry)` and before the `entry.keys.length === 0` branch — via
`logInfo` at `LogPrefix.Backend`, so it fired on the populated-order path unconditionally, not
just the zero-key path. Names only, never a value (module discipline, C5/T-11-04): the helper
calls `Object.keys()` and nothing else — it never indexes into the object.

**Truncation check:** `grep -c '+.*more'` across all 5 captured lines returns `0` — the `+N more`
suffix is absent. The list is exactly 15 names long, which numerically collides with
`MAX_DIAGNOSED_FIELDS = 15`. **This collision is coincidental, not truncation** — proven two
ways: (1) the deployed `probeOrderFieldNamesD4305` source contains no slice and no reference to
`MAX_DIAGNOSED_FIELDS` at all (confirmed by direct code read, quoted above), and (2) the capped
`fieldNames` helper appends its `,+N more` suffix only when `names.length > MAX_DIAGNOSED_FIELDS`
(strictly greater than 15) — at exactly 15 it would show all 15 with no suffix either, so the
absent suffix is consistent with both an uncapped read and a capped read landing on the same
number by chance. The uncapped source is what makes this scorable; a later reader must not
re-open the truncation question from the count alone.

**Secret-shaped token check:** `grep -ci 'code=\|key=\|gamekey_val\|redeemed_key_val'` across all
5 captured lines returns `0`.

**Date-like field observed:** `created` — present on all 5 orders. No other date-like name
(`created_at`, `purchase_date`, `order_date`, `timestamp`, `epoch`) appears in any captured line.

## VERDICT

**VERDICT:** POSITIVE — field `created` found

A source date field exists on the Humble order and survives today because every adapter schema
is `.passthrough()` (it is being discarded downstream, not rejected at parse). `Most recent` is
therefore buildable and is not a phantom sort option.

## Sort options to ship

`Expiring soonest, Alphabetical, Most recent` (three options) — but shipping the third option is
**NOT a frontend-only change**, and is **OUT of plan 43-07's scope**:

- `created` currently lives on the raw order (`OrderDetail`), not on `HumbleKey`
  (`src/common/types/humble.ts:93-126`). It must be captured into `HumbleKey` before any
  comparator can read it per-row.
- Capturing a new persisted field into `HumbleKey` requires bumping
  `HUMBLE_CLASSIFIER_VERSION` from `7` to `8` (`src/backend/humble/constants.ts:57`) to force a
  one-time reclassification of every frozen (already-cached) order — otherwise pre-bump cache
  entries would silently lack the field and sort as if it were absent.
- A new comparator (a `Most recent` equivalent to `compareWaiting`/`byExpiringSoonest`) is needed.
- **Important characteristic, not a defect:** `created` sits on the ORDER, not on the individual
  key. Every `HumbleKey` derived from the same order shares that order's single `created` value,
  so `Most recent` sorts by **purchase batch**, not per-key. A later reader must not assume
  per-key date precision that does not exist — two keys revealed from the same order at different
  times will still tie under this sort, because the underlying source data has no per-key
  timestamp, only a per-order one.

This work must be minted as a gap plan via `/gsd-plan-phase 43 --gaps`. Plan 43-07 ships the two
evidenced options (`Expiring soonest`, `Alphabetical`) until that gap plan lands, per
`43-UI-SPEC.md`'s § "Sort Picker Contract" branch table.

## Residual unknowns

- Whether `created` is a Unix epoch, an ISO string, or another format was not measured by this
  probe (a value-shape question, not a field-NAME-presence question, and the probe was
  deliberately scoped to names only per the module's no-value discipline, C5/T-11-04). The gap
  plan that captures the field must resolve its parse/comparator shape at that time.
- Only 5 orders were observed in this session. All 5 shared the identical 15-field shape with no
  variance, so no partial-population case (an order missing `created`) was observed. The
  `.passthrough()` schema means an order lacking the field would simply omit it from
  `Object.keys()` rather than error — the gap plan's comparator should treat a missing `created`
  defensively (e.g. sort undated orders last) rather than assume universal presence.
