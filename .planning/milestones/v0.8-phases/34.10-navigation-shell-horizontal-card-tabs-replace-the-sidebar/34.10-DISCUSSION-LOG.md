## Traffic-light inset & frameless mode

### Q1 — What to do about the 78px inset

| Option | Description | Selected |
|--------|-------------|----------|
| Adopt overlay titlebar on macOS | Set Tauri `titleBarStyle: Overlay` + `hiddenTitle` so traffic lights float over the navbar; reserve 78px. Delivers the sketch look exactly, but is a window-chrome change riding along in a nav phase; 34.1's frameless work already produced pre-paint/decoration bugs (CR-02). | |
| Conditional inset, no chrome change | Inset driven by whether traffic lights actually overlay (0px today under Tauri, 78px if overlay mode ever lands). Zero chrome risk. | ✓ |
| Drop the inset from this phase | No inset logic at all; revisit if overlay titlebar is adopted separately. Smallest diff, but the ROADMAP's 78px constraint goes unaddressed. | |

**User's choice:** Conditional inset, no chrome change
**Notes:** Scouting established the premise was wrong: `framelessWindow` defaults to `false` (`config.ts:367`); Tauri's `setDecorations(false)` removes macOS traffic lights entirely, while Electron's `titleBarStyle: 'hidden'` keeps them. The 78px reserve applies in neither Tauri mode today.

### Q2 — Window drag region after `.Sidebar` is retired

| Option | Description | Selected |
|--------|-------------|----------|
| The tier-1 navbar row | Navbar empty space drags; tabs/ring/controls stay no-drag. Matches conventional top-bar behaviour. | |
| Navbar row + tier-2 panel background | Larger target, closer in area to today's full-height sidebar; every interactive tier-2 child needs explicit no-drag. | |
| Navbar row only when frameless is on | Same as the first, explicitly gated on `isFrameless` so a decorated window never gets a surprise drag surface. | ✓ |

**User's choice:** Navbar row only when frameless is on
**Notes:** Surfaced a genuine landmine — `tauriWindowChrome.ts:333` falls back to `start.closest('.Sidebar')`, and since WKWebView lacks `-webkit-app-region` support that fallback is the *active* path under Tauri on macOS. Retiring `.Sidebar` without updating it silently kills window dragging.

### Q3 — How much the new nav should care about Electron

| Option | Description | Selected |
|--------|-------------|----------|
| Tauri is the target; keep Electron merely working | Design and verify against Tauri; cosmetic imperfection under Electron accepted and noted. | ✓ |
| Both shells must look correct | Inset resolves per shell as well as platform and setting, verified in both. Highest confidence, most work, on a shell scheduled for deletion. | |
| Tauri only — don't run the new nav under Electron | Gate the new shell so Electron keeps the old Sidebar. Zero Electron risk, but leaves two navigation systems alive until Phase 35. | |

**User's choice:** Tauri is the target; keep Electron merely working

### Q4 — Enforcing theme survival

| Option | Description | Selected |
|--------|-------------|----------|
| Blocking gate on 3 themes | `midnightMirage`, `dracula` (inverted), `gruvbox_dark` all visually confirmed before the phase closes. Matches the UI-SPEC's own wording. | ✓ |
| Blocking gate on every shipped theme | Full sweep of `themes.scss`. Catches more, long manual pass, diminishing returns. | |
| Verify the 3, but non-blocking | Same three checked, findings recorded, but a miss doesn't hold the phase open. | |

**User's choice:** Blocking gate on 3 themes

## Top-right cluster (Downloads ring vs window controls)

### Q1 — How they share the corner

| Option | Description | Selected |
|--------|-------------|----------|
| Ring in the navbar; navbar reserves space for the controls | Ring in a nav-right cluster; navbar adds trailing padding when frameless, reusing `--overlay-controls-width` (`index.scss:39-41`). `WindowControls` untouched. | ✓ |
| Fold `WindowControls` into the navbar | One flex row; overlap structurally impossible, but moves a component 34.1 owns out of `grid-area: content`. | |
| Reserve nothing; rely on the existing hide guard | Smallest diff, but the collision then appears exactly when a download runs in frameless mode. | |

**User's choice:** Ring in the navbar; navbar reserves space for the controls

### Q2 — What the ring displays with several downloads queued

| Option | Description | Selected |
|--------|-------------|----------|
| Ring = current download %, badge = queue count | Both sources already exist (`hasProgress` hook; `getDMQueueInformation`). Matches the ROADMAP's wording literally. | ✓ |
| Ring = aggregate progress, badge = count | More informative in principle, but no aggregate source exists and the number would move unevenly and sometimes backwards. | |
| Ring = current %, badge only when more than one | Less noise in the common case; more conditional rendering and its own small layout shift. | |

**User's choice:** Ring = current download %, badge = queue count

### Q3 — Idle behaviour

| Option | Description | Selected |
|--------|-------------|----------|
| Always present, dimmed and unfilled when idle | Holds its slot; no layout shift; Downloads becomes reliably findable. Changes today's behaviour. | ✓ |
| Keep hiding it, but reserve the slot | Preserves current behaviour; leaves a permanent gap that reads as a mistake. | |
| Keep hiding it entirely, no reservation | Unchanged from today; the right cluster reflows when a download starts or finishes. | |

**User's choice:** Always present, dimmed and unfilled when idle
