## Deviations from Plan

### Item 1 (hasProgress.ts seed fix) — deliberately NOT implemented, owed follow-up

`src/frontend/hooks/hasProgress.ts:14-19`:

```ts
const [previousProgress] = useState<InstallProgress>(
  JSON.parse(storage.getItem(`${appName}_${runner}_progress`) || '{}') as InstallProgress
)
const [currentProgress, setProgress] = useState<InstallProgress>(
  previousProgress ?? { bytes: '0.00MB', eta: '00:00:00', percent: 0 }
)
```

`storage.getItem(...)` returns `null` for every game today — a full-repo grep confirms the `${appName}_${runner}_progress` localStorage key is written nowhere in this codebase. `JSON.parse(null || '{}')` therefore always yields the object literal `{}`, and `{} ?? default` evaluates to `{}` (`??` only substitutes on `null`/`undefined`, and `{}` is neither) — so the intended default is never actually applied. `currentProgress`'s real runtime shape is `{}`, not the `InstallProgress` the type promises, until the first effect reconciliation runs. **All six `hasProgress` call sites carry this identical defect** (`ProgressHeader`, `RingProgress`, `GameCard`, `DownloadManagerItem`, `GamePage`, `DLCList`).

This is confirmed as a real, source-verified latent bug. It is deliberately NOT fixed in this plan: `hasProgress.ts` is not in this plan's `files_modified`, and it is shared by six consumers — widening a gap-closure plan to touch shared code risks spawning new gaps, per the orchestrator's explicit scope decision. **This is owed follow-up work for a future plan.**

### Two material risks surfaced during a post-implementation re-read — NOT resolved here

**Risk 1 — the `key` prop preserves the very remount the fix claims to remove.** `key={head?.params.appName ?? 'idle'}` changes from the literal string `'idle'` to the real `appName` at the idle -> active boundary. A `key` change forces React's reconciler to unmount the old element and mount a brand-new one — so `RingProgress`'s `hasProgress` hook instance is *still* freshly created at the moment a download starts, exactly as it was pre-fix. The unconditional-mount change stops `RingProgress` from disappearing from the *type* of the returned element (a bare `<span>` vs. `RingProgress`), but if the `key` value itself is what actually drives React's mount/unmount decision, the hook-instance lifetime this plan's whole premise rests on may not actually have changed at the one boundary that matters (idle -> first download). The new regression test cannot detect this: it calls `RingProgress(props)` directly as a plain function, never runs React's reconciler, and therefore never exercises `key` semantics at all. The test proves element *presence* in the returned tree, not hook *identity* survival across a real render cycle. This gap is real and unclosed by anything in this plan.

**Risk 2 — H3's mechanism does not survive a close re-read of `hasProgress.ts:42-56`.** The hook's `useEffect` reconciles `currentProgress` against `installationProgress` whenever they differ (`if (installationProgress) { if (currentProgress.percent !== installationProgress.percent) setProgress(...) }`), and this effect runs on every render where its dependencies change, including the first render after mount. A `{}`-seeded `currentProgress` should therefore produce, at most, ONE rendered frame at `percent: 0` before `setProgress` fires and the real value takes over — not a sustained, download-long `0turn`. The live diagnostic's own Q1/Q2 answers (34.10-F02-DIAGNOSIS.md) already proved `installationProgress` IS populated for the downloading key throughout the download (two independent consumers advance normally). If that reconciliation genuinely fires on mount as the code reads, H3 as documented explains a single transient frame of 0%, not the sustained flat arc the live gate actually observed.

**Honest conclusion:** the fix implements the diagnosis faithfully, within the scope assigned, and the code changes are correct on their own terms (unconditional mount, fallback args, no `return null`, `--dl-progress`/count-badge paths untouched, `pnpm codecheck` clean, full suite green). But the diagnosis's own mechanism is not confirmed to survive close reading, and Risk 1 raises real doubt that the mount-boundary behavior this plan targets has actually changed for the one transition (idle -> active) that matters. **This fix may not close F-34.10-02.** Nothing in this plan's own tooling (no jsdom, no live IPC, no download queue) can settle that question. Plan 34.10-16's live gate item 4 is the only adjudicator, and it must be treated as a genuinely open question, not a formality.
