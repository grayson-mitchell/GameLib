## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] Naive substring search for the `### 10.5` heading matched authoring prose that merely named it**
- **Found during:** Task 2, first run of the checker against the real file (17 spurious INVALID slots)
- **Issue:** §10's own preamble text (written by 34.10-25) contains the literal string `` `### 10.5 Run 4 — the items` `` inside backticks, describing what this plan would write. `content.indexOf("### 10.5")` matched that mention first, so the checker sliced from the wrong offset and picked up §10.3's own "Verdict" column (REACHABLE/UNREACHABLE values) as if they were §10.5's verdict slots.
- **Fix:** Anchored the heading match to line-start with `/^### 10\.5\b.*$/m`, matching only a real markdown heading.
- **Files modified:** `34.10-run4-contract-check.mjs`
- **Commit:** `476be0656`

**2. [Rule 1 - Bug] Three §10.5 verdict lines wrapped their PASS-condition parenthetical across multiple physical lines, breaking the per-line verdict parser**
- **Found during:** Task 2, second run of the checker against the real file (1 spurious INVALID slot)
- **Issue:** Item 1's, item 3's, and item 4's `**Item N verdict** (...)：` lines, as originally authored, wrapped the long PASS-condition text across 3-4 physical lines — mirroring the established shape used in §4/§6/§7/§9.5's own historical item bodies. The checker's line-based regex (`^\*\*Item \d+ verdict\*\*.*:\s*(.*)$`, matching the FINAL colon *on that line*) only saw the first wrapped line, whose own internal colon ("PASS only if:") read as the delimiter, producing a bogus non-empty "invalid" verdict value from the sub-check description text.
- **Fix:** Rewrote all three verdict lines as single physical lines (wording unchanged), matching item 2's and item 5's already-single-line form.
- **Files modified:** `34.10-LIVE-GATE.md`
- **Commit:** `476be0656`

**3. [Rule 1 - Bug] The checker's own diagnostic-logging line matched the acceptance criterion's literal `slice(a, b)` ban**
- **Found during:** Task 2, mechanical verification of the acceptance criteria
- **Issue:** `line.trim().slice(0, 60)` truncated a verdict line for a human-readable console report — not a finding-ID lookup and not F-34.10-07's collision (4) shape, but the acceptance criterion's grep is literal and matched it regardless.
- **Fix:** Replaced with `line.trim().match(/^.{0,60}/)[0]`, keeping the checker's source free of the pattern entirely, including in logging.
- **Files modified:** `34.10-run4-contract-check.mjs`
- **Commit:** `aa4650f0f`
