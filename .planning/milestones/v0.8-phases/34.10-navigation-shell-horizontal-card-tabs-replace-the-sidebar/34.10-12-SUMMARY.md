# Phase 34.10 Plan 12: F-34.10-02 Cause (b) Root-Cause Diagnosis Summary

**Live three-question discriminator (Q1/Q2/Q3 all YES) cleanly rejects five of six candidate causes for the Downloads ring's stuck-at-0turn arc, leaving hasProgress.ts's empty-object localStorage seed bug — amplified by RingProgress's uniquely conditional mount — as the sole surviving hypothesis, with three concrete fix directives handed to plan 34.10-15**

- **Tasks:** 2 (checkpoint:human-verify, then auto)

## Accomplishments

- Ran the three-question live discriminator against a real download on real hardware (Q1: DM screen's per-item percent readout advances past 0% — YES; Q3: `elements[0]` genuinely is the downloading item — YES; Q2: the Games grid card also shows advancing progress — YES), definitively proving the `progressUpdate` → `InstallProgress` → `hasProgress` data path is alive and that `DownloadsRing`'s queue-head binding is correct
- Evaluated all six prescribed hypotheses against that evidence plus direct source inspection (`hasProgress.ts`, `InstallProgress.ts`, `DownloadsRing/index.tsx`, `DownloadManager/index.tsx`, `ProgressHeader/index.tsx`, `GameCard/index.tsx`, `depot.ts:1698-1710`, `downloadqueue.ts`), rejecting five with path:line or Q-answer citations and recording exactly one surviving hypothesis (H3)
- Found and verified, via a full-repo grep, that `hasProgress.ts`'s `${appName}_${runner}_progress` localStorage key is never written anywhere in the codebase — the hook's `previousProgress ?? default` seed fallback is consequently dead code that silently leaves `currentProgress` as `{}` (not the declared `InstallProgress` shape) for every install
- Identified that `RingProgress` is the only one of `hasProgress`'s six consumers that is conditionally mounted (`head ? <RingProgress/> : <span/>` in `DownloadsRing/index.tsx:70-75`) rather than persistently mounted for its parent's lifetime, and has no downstream render gate (unlike `ProgressHeader`'s `progress.eta &&` check) before painting `--dl-progress` to a style property
- Recorded, per the plan's requirement, that `DownloadsRing.test.tsx` mocks `hasProgress` wholesale and never invokes `RingProgress` — structurally incapable of catching this defect class
- Wrote three concrete fix directives for plan 34.10-15, with exact file:line targets, rather than a direction

## Decisions Made

- **H3 survives by elimination, not by a proven mechanism.** The diagnosis is explicit that an empirical simulation of `hasProgress`'s own `useState`/`useEffect` logic (replayed against a synthetic tick sequence, both with a stable mount and with a full remount-and-reseed before every tick) converges to the correct value in both cases — it does not, by itself, reproduce a *persistent* 0. H3 is recorded as the surviving hypothesis because the other five are rejected with certainty (four by the plan's own Q-answer/code-identity criteria, one by an established working precedent in this codebase) and H3 is the one hypothesis pointing at a real, source-verified defect in the code path this diagnosis was scoped to. This distinction — surviving by elimination vs. surviving by a demonstrated mechanism — is preserved verbatim rather than upgraded to a stronger claim.
- **Fix scope for plan 34.10-15**, stated as concrete identifiers: (1) `hasProgress.ts:14-19` — seed `currentProgress` from the full default object whenever `previousProgress.percent === undefined`, not just when `previousProgress` is `null`/`undefined`; (2) `DownloadsRing/index.tsx:37-87` — mount `RingProgress` unconditionally (matching every other `hasProgress` consumer) and let it internally render the idle state, instead of conditionally mounting/unmounting the whole component on `head`'s truthiness; (3) add a `RingProgress`-level test that actually invokes the component under a real or simulated DOM.
- **REQ-34.10-08 stays Pending.** This plan is diagnosis-only per its own constraints (`git status --porcelain src` empty, `34.10-LIVE-GATE.md` byte-identical); no requirement can be marked complete until plan 34.10-15 implements the fix and a live gate measures it.
