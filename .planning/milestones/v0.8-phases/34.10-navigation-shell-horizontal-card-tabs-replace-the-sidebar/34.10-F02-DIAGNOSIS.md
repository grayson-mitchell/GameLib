# F-34.10-02 cause (b) — live discriminator diagnosis

Root-causing: `--dl-progress` never leaves `0turn` in `DownloadsRing` during a real, active
download (34.10-LIVE-GATE.md, Item 4, F-34.10-02 defect 2). This file does not re-measure the
already-recorded ring-visibility defect (defect 1 / cause (a), closed by plan 34.10-14). It
discriminates between six hypotheses for cause (b) using a live measurement taken BEFORE any
source is read for a fix, per this project's standing lesson ("when two readings both fit, build
the discriminator").

The gate author's own suggested cause — a keying/remount or timing difference vs. the retired
`CurrentDownload` — is already FALSIFIED at planning time: `git show 0559bc0d0^:src/frontend/
components/UI/Sidebar/index.tsx` shows the retired component subscribed to the identical channel,
took the identical `elements[0]`, and rendered with the identical `key={...params.appName}`. That
hypothesis is not re-tested below.

**What these answers mean, and what they FORECLOSE:**
- The `progressUpdate` -> `InstallProgress` store -> `hasProgress` path is ALIVE. Two independent
  consumers (`DownloadManagerItem/index.tsx:91`, `GameCard/index.tsx:147`) using the identical key
  shape both advance during the same download. Any hypothesis of the form "the transport is dead",
  "the store never updates", "the listener never registers", or "the key shape is wrong app-wide"
  is REJECTED by this live observation (Q1, Q2).
- `elements[0]` IS the downloading element (Q3). The hypothesis "the ring binds to the wrong queue
  element / a genuinely-zero-percent queued item" is REJECTED by this live observation.
- Combined with the two hypotheses already falsified at planning time (lost `appName` key;
  different remount behaviour — both dead per `git show 0559bc0d0^:src/frontend/components/UI/
  Sidebar/index.tsx`), the surviving cause MUST be local to `DownloadsRing/index.tsx` itself — in
  how `RingProgress` consumes/derives the percent, or in how `--dl-progress` is computed and
  applied from it.

## Surviving hypothesis

**H3 survives**, but the honest state of the evidence is: every other hypothesis is rejected with
certainty (four by the plan's own Q-answer criteria or direct code-identity comparison, one by a
precedent check, one by contrasting the idle-opacity rule against the active-state observation),
and H3 is the only one left standing — not because a fully deterministic, always-reproducing
mechanism was proven, but because it is the one place a *real, source-verified defect* exists in
exactly the code path this diagnosis was pointed at.

**The verified defect** — `src/frontend/hooks/hasProgress.ts:8-19`:

```ts
const [previousProgress] = useState<InstallProgress>(
  JSON.parse(storage.getItem(`${appName}_${runner}_progress`) || '{}') as InstallProgress
)
const [currentProgress, setProgress] = useState<InstallProgress>(
  previousProgress ?? { bytes: '0.00MB', eta: '00:00:00', percent: 0 }
)
```

`storage.getItem(...)` returns `null` for every game today (full-repo grep confirms this specific
key format is never written — see evidence above), so `JSON.parse(null || '{}')` always yields the
**object literal `{}`**. `{} ?? default` evaluates to `{}` — `??` only substitutes on `null`/
`undefined`, and `{}` is neither — so the intended default (`{ bytes: '0.00MB', eta: '00:00:00',
percent: 0 }`) is **never actually applied**. `currentProgress`'s real runtime shape is `{}`, not
the `InstallProgress` the type annotation promises, until the first `useEffect` reconciliation
against a live `installationProgress` value runs.

**Why this reaches `RingProgress` and not (visibly) the other five consumers**: `RingProgress`
(`DownloadsRing/index.tsx:70-75`) is the *only* one of `hasProgress`'s six call sites that is
conditionally mounted — `head ? <RingProgress .../> : <span .../>` — rather than persistently
mounted for its parent's whole lifetime. `ProgressHeader` renders unconditionally (`DownloadManager
/index.tsx:111-115`, using `?? ''`/`?? 'legendary'` fallbacks precisely so it never needs to
unmount), `GameCard` is mounted for as long as the game's library entry exists, and the same is
true of `DownloadManagerItem`, `GamePage`, and `DLCList`. Every one of those five carries the exact
same empty-`{}` seed defect, but their hook instance is never torn down mid-download, so the seed
defect resolves itself silently on the very first `useEffect` pass and is never observed again.
`RingProgress` is the one consumer whose entire hook lifetime can restart at a mount boundary
(first render where `head` flips from `undefined` to defined, or any subsequent queue-membership
change that alters the head's `appName` key) — and it renders its computed `--dl-progress`
directly, on every render, with no downstream gate (`ProgressHeader` gates on `progress.eta &&`
before rendering the percent bar at all; `RingProgress` has no equivalent gate), making it the one
place a `{}`-seeded, not-yet-reconciled `currentProgress` is guaranteed to be painted to the
screen rather than silently absorbed by a delayed render.

**What plan 34.10-15 should implement**, in concrete terms:
1. `src/frontend/hooks/hasProgress.ts:14-19` — replace `previousProgress ?? { bytes: '0.00MB', eta:
   '00:00:00', percent: 0 }` with a check that treats an *empty* `previousProgress` (no `percent`
   field, e.g. `previousProgress.percent === undefined`) the same as a missing one, so
   `currentProgress` is seeded with the full default object instead of `{}` for every install that
   has no real resume data — which today is every install, unconditionally.
2. `src/frontend/components/UI/NavShell/components/DownloadsRing/index.tsx:37-87` — stop
   conditionally mounting/unmounting `RingProgress` on `head`'s truthiness. Mount it unconditionally
   (matching the pattern every other `hasProgress` consumer already uses) and let it internally
   render the idle/static state when there is no head, so its `hasProgress` hook instance survives
   for the component's whole lifetime instead of being torn down and reseeded at queue-membership
   boundaries.
3. Add a `RingProgress`-level test that actually invokes `RingProgress` (not just `DownloadsRing`)
   under a real or simulated DOM, asserting the rendered `--dl-progress` value tracks a sequence of
   `hasProgress` return values — see `## Test-coverage gap` below for why the existing test cannot
   do this today.

## Test-coverage gap

`src/frontend/components/UI/NavShell/__tests__/DownloadsRing.test.tsx` mocks `frontend/hooks/
hasProgress` wholesale (`jest.mock('frontend/hooks/hasProgress', () => ({ hasProgress: jest.fn(()
=> [{ percent: progressPercent }, {}]) }))`, line 34-36) and only ever invokes the top-level
`DownloadsRing()` function directly against a hand-rolled `useState`/`useEffect` harness (no jsdom
/ react-test-renderer is installed in this project — see the test file's own docstring). Because
`RingProgress` is a nested function component, it is only ever *referenced* as
`{ type: RingProgress, props: {...} }` inside the returned React-element object graph — the test
never calls React's renderer, so `RingProgress`'s own body (the `hasProgress` call, the `percent`
derivation, the `--dl-progress` style computation) is **never executed** by any existing test. This
test class is structurally incapable of catching the defect class diagnosed above, or of verifying
plan 34.10-15's fix. Fix item 3, above, addresses this.
