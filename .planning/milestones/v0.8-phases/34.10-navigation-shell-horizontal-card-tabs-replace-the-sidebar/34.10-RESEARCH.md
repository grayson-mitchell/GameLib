## Summary

This phase deletes a 6-file `Sidebar` component tree (14 flat destinations + 2 footer widgets) and replaces it with a two-tier shell. Every design decision is already locked (CONTEXT.md D-01..D-13, UI-SPEC 6/6 checker-passed) — this research's job was to verify the code those decisions cite still says what they claim, and it does, byte-for-byte, in every case checked. Two silent-breakage traps are real and independently confirmed: the `.Sidebar` drag-region fallback (`tauriWindowChrome.ts:333`) is genuinely the active WKWebView path (its own test, `framelessRuntime.test.ts:234-254`, pins the literal class name and WILL fail the moment `.Sidebar` disappears unless updated in the same commit), and no config anywhere sets a macOS `titleBarStyle`/overlay — confirming the 78px inset is currently 0px, not 78px. A THIRD trap not previously flagged: `meta/i18nGateScope.json` is a static, human-regenerated snapshot (not a live glob), so brand-new nav component files will be invisible to the blocking i18n gate until someone runs `pnpm gen-i18n-gate-scope` — the plan must include that step explicitly. A FOURTH: `SidebarLinks/__tests__/index.test.tsx` pins exact label order/position (`labels[0] === 'GameLib'`, "Manage Accounts immediately before Accessibility") and WILL break on retirement — this is expected breakage, not a regression, but the plan must account for deleting/replacing this file. A FIFTH: `Login/__tests__/index.test.tsx` textually parses `.App .content` and `.App` CSS blocks out of `App.css` by selector name (F-10 regression gate) — the grid restructure must either keep those exact selectors or the test must be updated in the same commit. `pnpm test:ci` is freshly verified GREEN at 204 suites / 4069 tests as of this research session (not stale).

## Tab Pattern Recommendation

**MUI `<Tabs>`/`<Tab>` (`@mui/material`) is already in the tree**, used at `src/frontend/screens/WineManager/index.tsx:222-238`:
```tsx
<Tabs className="tabs" value={repository.value} onChange={(e, value) => { ... }} variant="scrollable" scrollButtons="auto">
  {repositories.map(({ type, value }) => <Tab value={value} label={type} key={value} />)}
</Tabs>
```
This usage is **state-driven** (`value`/`onChange` against a local `repository` variable), not route-driven — WineManager's tabs switch a data source, not a URL. Tier-1 tabs in this phase must be **route-driven** (`/`, `/login`, `/store/:store`, `/settings/:type`), which MUI `<Tabs>` also supports via `component={NavLink}`/`to` on each `<Tab>` (standard MUI + react-router integration pattern) — not exercised anywhere in this codebase today, so it would be new usage of an existing dependency, not a new dependency.

`components/UI/TabPanel/index.tsx` (24 lines, full file read) already exists:
```tsx
function TabPanel({ children, value, index, ...other }: TabPanelProps) {
  return (
    <div role="tabpanel" id={`tabpanel-${index}`} aria-labelledby={`tab-${index}`} {...other}>
      {value === index && <div>{children}</div>}
    </div>
  )
}
```
It is currently used by 6 other screens (`Settings/sections/GamesSettings`, `Humble/Keys/Spares`, `Humble/Keys/Waiting`, `Game/GamePage`, `Game/ModifyInstallModal/GOG`, `Login/components/SteamLogin`) as a **value-comparison show/hide wrapper**, not as a route boundary. This phase's tier-2 panel is NOT well-served by reusing `TabPanel` directly, because tier-2's content varies by *tab identity* (Games/Stores/Settings/none), not by a `value === index` comparison against a single shared state variable across 4 wildly different content shapes (filter controls vs. nav list vs. nav list vs. nothing) — a plain conditional render (`{activeTab === 'games' && <GamesFilterPanel />}`) inside the shell component is simpler and avoids forcing tier-2's four cases into `TabPanel`'s generic `index`/`value` string-matching contract for no accessibility benefit (tier-2 is not itself an ARIA tabpanel of the tier-1 tablist — UI-SPEC's own Accessibility section only requires `role="tablist"`/`role="tab"`/`aria-selected` on tier 1, with `TabPanel`'s `aria-labelledby="tab-{index}"` contract satisfied by whatever *does* function as the tier-1 tabs' single content panel, which per the "active tab merges into the content surface" design is arguably the `content` grid area, not the `tier2` panel).

**Recommendation:** reuse MUI `<Tabs>`/`<Tab>` for tier-1 only (roving `tabIndex`, arrow-key nav, `role="tablist"`/`role="tab"` for free), fully reskinned per the UI-SPEC's card/folder CSS (reject MUI's default indicator — already flagged as the rejected "underline" alternative in sketch 001 and reiterated in UI-SPEC/ROADMAP). Route each `<Tab>` via `component={NavLink}` + `to={...}`, matching the existing `NavLink`-based active-state pattern `SidebarItem` already uses (`isActive` classname callback). Do NOT reuse `TabPanel` for tier 2 — a plain conditional-render switch inside the new shell component is the better fit, matching D-08's framing that tier-2 content is "filters on one tab, navigation on two others" (an admitted deliberate inconsistency, not a generic tabpanel shape). Tier-2 rows themselves reuse `SidebarItem`'s existing `NavLink`/`<button>` switch (`elementType="button"` for actions) verbatim, per CONTEXT's own "Established Patterns" note.

**Routing:** confirmed `react-router-dom ^6.30.0`, single `createHashRouter([...])` at `App.tsx:164`, all routes as **direct children** of the root `/` route — no nesting beyond path-param segments already in use (`store/:store`, `settings/:type`, `humble-keys` with its own `waiting`/`spares`/`all` children). The two-tier structure does **not** imply new nested routes — it is a pure presentational layer over the existing flat table. No route table changes are needed by this phase.

## Traps and Corrections

### 1. The 78px inset premise is FALSIFIED by the actual code — CONTEXT.md's D-01 is correct, ROADMAP's constraint list is stale

Directly verified: `grep -n "titleBarStyle\|decorations\|transparent\|hiddenTitle\|overlay" src-tauri/tauri.conf.json src-tauri/src/main.rs` returns **zero matches for any titlebar/decoration configuration** — the only hits are unrelated (a tray-icon fallback comment, a keyring comment). `src-tauri/tauri.conf.json`'s `windows` array contains only `label`/`title`/`width`/`height`/`resizable` — no `titleBarStyle`, no `transparent`, no `decorations: false`. Decorations are instead toggled **dynamically at runtime** by `src/preload/api/tauriWindowChrome.ts`'s `applyFramelessDecorations()`, which calls `getCurrentWindow().setDecorations(!resolved)` where `resolved` comes from `readFramelessSetting()` reading `configStore`'s `settings.framelessWindow` — confirmed default `false` at `src/backend/config.ts:367`. **Conclusion: today, with the default settings, the window has a native decorated titlebar with the OS's own traffic lights at their normal OS position — not overlaid, not overlapping content, inset requirement is 0px.** ROADMAP.md's "Known constraints" section (`## Phase 34.10`, "macOS traffic lights occupy ~78px... whenever the Tauri titlebar is transparent or overlaid") is **not wrong as a conditional statement**, but its implicit framing (as if this condition is currently true) is stale — CONTEXT.md's D-01 already caught and corrected this, and this research independently reconfirms it from the actual config files, not just from CONTEXT's own citation.

### 2. The `.Sidebar` drag-region fallback is real, active, and pinned by its own test

`src/preload/api/tauriWindowChrome.ts:333`, exact code confirmed: `return start.closest('.Sidebar') !== null`. This is inside `resolveDragRegion()`, reached only when `getComputedStyle(el).getPropertyValue('-webkit-app-region')` returns an empty string for the entire ancestor chain (`propertySeen` stays `false`) — the function's own doc comment states this happens because "the platform webviews Tauri uses do not honor it" (WKWebView does not implement `-webkit-app-region`). The fallback also explicitly excludes `a, button, [role="button"], input, select, textarea, .windowControls` via an ancestor `closest()` check before falling through to the `.Sidebar` check. **`src/preload/__tests__/framelessRuntime.test.ts:234-254`** directly tests this exact fallback with a `FakeElement('div', { className: 'Sidebar' })` fixture and asserts `startDragging` is/isn't called — this is the test the plan must update in the same commit as the source change, not a separate cleanup task.

### 3. i18n gate scope snapshot is static — new files are invisible until manually regenerated (not previously documented anywhere in 34.10's planning trail)

Full detail in `## i18n Migration` above. This is the one finding in this research that does NOT trace back to an existing CONTEXT.md/UI-SPEC/ROADMAP claim — it was discovered independently by reading `meta/genI18nGateScope.ts` and `meta/i18nGateScope.json`. **Action required in the plan**: after creating any new nav-shell source files, run `pnpm gen-i18n-gate-scope` and commit the regenerated `meta/i18nGateScope.json`, verifying the new files appear in its `files` array, before treating `pnpm test:ci` green as proof the gate actually scanned the new code.

### 4. Three destinations are REPARENTED, not merely relocated — Wine Manager, Accessibility, Console Mode

### 5. `HeroicVersion`'s side effects, independently confirmed

`HeroicVersion/index.tsx` (119 lines, read in full): the cache-clear fires in a `useEffect` (`window.api.getHeroicVersion().then((version) => { if (version !== lastVersion) { ...; window.api.clearCache(false, true) } ...})`, lines 33-42) — confirmed independent of rendering, runs once on mount regardless of where the component is placed in the tree. ### 6. Duplicate `data-tour="sidebar-downloads"` value (minor, pre-existing, moot under D-13 but worth recording)

`Sidebar/index.tsx:142` (`<div className="currentDownloads" data-tour="sidebar-downloads">`) and `SidebarLinks/index.tsx:267` (the Downloads `SidebarItem`, also `dataTour="sidebar-downloads"`) both set the identical `data-tour` value on two different DOM elements. `SidebarTour.tsx`'s `element: '[data-tour="sidebar-downloads"]'` step (line 54) would only ever anchor to whichever matches first in the DOM.
