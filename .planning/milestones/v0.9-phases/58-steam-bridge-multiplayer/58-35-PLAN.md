<objective>
Make the native helper serve more than one connection at once, so the backend's invite control connection (slots 13/14) is answered while the game's shim connection stays open.

Purpose: this is the root cause of the failed 58-32 live invite leg (M-01 Direction A). `main()` in `native/steam-bridge/helper/bridge_helper.c` (about line 2991) runs `for(;;){ c = accept(...); setsockopt SO_RCVTIMEO; serve_connection(c); }`. That serves one connection until it closes. The shim's connection lasts the whole session, so `inviteBridge.ts`'s second connection sat in the backlog and timed out. The 58-29 and 58-31 harness tests never held a concurrent shim connection, so they could not catch this. ROADMAP Phase 24 already recorded the shape as WR-01 ("single-threaded helper serializes a 2nd concurrent bridge game"). That case was later dissolved by per-appId helpers, but this same-app second-client case was never served.

Target state, named concretely: one thread and one `poll()` loop. The loop watches the listen socket plus a fixed table of up to GL_MAX_CONNS connection slots. Each slot carries `fd`, `authenticated`, `helloLogged`, a reassembly buffer of LENGTH_FIELD_BYTES + MAX_FRAME_BYTES, `have`, and a monotonic `lastRxSec`. A slot dispatches exactly one complete frame at a time through the existing `dispatch_and_respond`. Steam thread affinity is kept because nothing leaves the main thread.

Output: the multiplexed loop in bridge_helper.c, and real-binary concurrency tests in helperIntegration.test.ts.
</objective>
