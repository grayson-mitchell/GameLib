### Locked Decisions

- **D-53-01:** **Export every method** of every manifest'd interface version as a flat `SteamAPI_ISteamX_Method` export, generated by `meta/gen_vtables.ts` from `meta/sdk/*.manifest.json`. A missing export is fatal (`EntryPointNotFoundException`), while an extra one is harmless, which is the existing R3 superset policy. No "measured union only" or minimum slice.
- **D-53-02:** **Flat-API generations are chosen by census.** Research reads DllImport entry points across the owned Unity library and targets every Steamworks.NET generation that appears (at least the pre-1.48 `SteamAPI_ISteamClient_GetISteamUser` style seen in Vampire's Fall and the 1.58+ `SteamAPI_SteamUser_v023`-style accessors behind Hell Clock's `InitEx`). Nothing is fixed ahead of the measurement.
- **D-53-03:** **The new interface versions are added as manifests that serve both the vtable and the flat path** (D-09 still holds: GameLib-authored manifests, never vendored Valve header text). Each new version is checked slot by slot against its SDK generation, never aliased from a neighbour.
- **D-53-04:** **Managed scan: Mono now, IL2CPP flagged.** Parse the ImplMap/DllImport tables of `<Game>_Data/Managed/*.dll` (e.g. `com.rlabrecque.steamworks.net.dll`, `Assembly-CSharp.dll`) and merge their `steam_api*` entry points into the required set. IL2CPP titles (no Managed dir) keep `@runtime-loaded` with an explicit "il2cpp: not scanned" reason. No second parser for `global-metadata.dat` / `GameAssembly.dll` this phase.
- **D-53-05:** **A flat export calls the proxy object's own vtable slot.** Flat and vtable behaviour are identical: forwarded where `meta/sdk/wire-policy.json` says so, the slot's stub otherwise. One source of truth, no separate flat-only stub table.
- **D-53-06:** **Wrong zeros are fixed when measured, not audited up front.** Stubs stay at their default. When a sampled title's log traces a hang or crash to one method, that method is forwarded to the helper's real Steam answer, or given a local constant only where Steam's real value is a constant on this platform (e.g. `ISteamUtils::IsSteamRunningOnSteamDeck` -> false on a Mac, the Rogue Waters case). The logged version names what to add next.
- **D-53-08:** **The x64 vtable path keeps its null-object fallback** (`SteamInternal_CreateInterface`, `FindOrCreate*`, bare `GetISteam*`). The NULL rule is for flat entry points only, because changing the vtable path would reopen CR-01 (restored by 52-14). Revisit only if a sampled title's crash is traced to the null object, as hypothesised for Manor Lords' 0x0 read.

- **D-53-11:** **The whole UE5 interface-versions todo is folded:** add the x64 versions still missing (Friends017, Utils010, UserStats012, Input006, GameServer015, GameServerStats001; User023, RemoteStorage016 and Networking006 already landed in 52-13), export x64 `SteamInternal_GameServer_Init` failing like `_V2`, and lift the 261024-j4l guard for 1363080, 427410 and 1119730 **only once the coverage scan reports them clean**.

## Summary

The shim source is generated: `meta/gen_vtables.ts` (2639 lines) reads `meta/sdk/*.manifest.json` and emits `native/steam-bridge/generated/steam_api_shim.c`, `steam_api.def`, `steam_api64.def` and the helper-side `bridge_dispatch.h`. Every interface version is a static singleton `struct { vfn *vptr; }` (e.g. `g_steamuser023_instance`) listed in `g_iface_table`. That is what makes the flat API cheap: a flat export `SteamAPI_ISteamUser_GetSteamID(self)` can identify the version by comparing `self` to the known instances, then call `self->vptr[slot]` with the manifest's real C parameter types. Slot numbers differ per version, so the generator must emit a per-flat-method switch over the versions that contain that method. Manifests come from the pinned Proton 9 `lsteamclient` tree via `pnpm extract-proton-inventory --versions ...` (acceptance entry first); that pinned SHA contains every version this phase needs (SteamClient020/021, SteamUser021, SteamFriends017, SteamUtils010, SteamUserStats012/013, SteamInput006, SteamGameServer014/015, SteamGameServerStats001) [VERIFIED: curl of ValveSoftware/Proton at 2c620c0f, 2026-10-25].

The most important findings come from a census I ran against the five Unity/Mono titles installed in the CrossOver bottles (a throwaway ImplMap parser, validated on 5 real assemblies). (1) All five Steamworks.NET builds are the same flat-API family (930-952 `steam_api64` DllImports each); there is no separate "pre-1.48 style" generation among the owned Unity set, only two build vintages: the `SteamAPI_Init` vintage and the `SteamInternal_SteamAPI_Init` vintage (Hell Clock). (2) The required **interface versions are not what D-53-11 lists**: the managed constants request SteamClient020 (x4) and SteamClient021 (Hell Clock, Mining Mechs), SteamUser021 (Rogue Waters), SteamFriends017, SteamUtils010, SteamUserStats012 (Unity) and 013 (Mining Mechs, Overlooting). **SteamClient020/021 and SteamUser021 are missing from the folded todo's list**, and without a SteamClient manifest the flat `GetISteamUser` has no recognised `self` and (per D-53-07) the game's context init returns NULL. (3) About 480 of ~880 distinct flat imports belong to families with no manifest at all (UGC, Input, Inventory, NetworkingSockets, HTTP, ...), and ~25 more are newer methods or overloaded names not in the existing manifests, so a managed-scan "required set" built from every import will report every Unity title as `miss` forever. That policy needs a decision (Open Question 1).

x86 measurement (D-53-09): of the 17 installed bridge titles, **0** have an x86 launch exe that needs the modern `SteamInternal_*` family or the flat API (the x86 launches are Avernum 4/6, XCOM, Grim Dawn's tool exes: legacy SDK). Unclaimed World's `.exe` is AnyCPU (CLR flags 0x1) and becomes x64 under D-53-10. Recommendation: defer x86 with count 0 attached, with the caveat that uninstalled owned titles cannot be measured locally.

**Primary recommendation:** Add a flat-export emitter to `gen_vtables.ts` that is driven by the existing manifests (x64 only, switch on `self`, typed call through `vptr[slot]`, explicit overload alias table, special-cased `GetISteamX` returning NULL on unknown version); extract the six-to-nine missing manifests from the pinned Proton tree (including SteamClient020/021 and SteamUser021); write a hand-rolled, bounds-checked ECMA-335 ImplMap + user-string reader in a pure module shared by `shimGenerate.ts` and `bridgeCensus.ts`; and extend the census with per-engine evidence plus a one-line-per-method game-originated call trace added to the helper.

### Pattern 1: Flat export generation (x64 only)
**What:** For each family F and each distinct flat method name M across F's x64 manifests, emit one export. The body switches on which F-instance `self` is and calls the matching slot with the manifest's real C types.
**When to use:** Every manifest'd method (D-53-01). SteamClient `GetISteamX` flat methods are the one special case (Pattern 2).
**Example (shape; generator emits it):**
```c
// Source: pattern derived from emitVtableStub/emitIfaceTableAndBareAccessors output in steam_api_shim.c
int32_t SteamAPI_ISteamUser_GetHSteamUser(void *self) {
  vfn *vt = *(vfn **)self;           // self must be non-NULL; check first
  if (self == (void *)&g_steamuser023_instance) return ((int32_t (*)(void *))vt[0])(self);
  if (self == (void *)&g_steamuser019_instance) return ((int32_t (*)(void *))vt[0])(self);
  /* unknown self: log once, return the type's zero */
  return 0;
}
```
Notes the planner must carry into tasks:
- x64 only (the Win64 ABI makes flat and vtable calling conventions identical for non-sret returns). All existing `class` returns have `structSize` 8 (CSteamID/CGameID), returned in RAX, so no RCX/RDX sret swap is needed for any current manifest. A generator assertion should refuse a `class` return with `structSize > 8` for a flat export, because MSVC x64 flat (sret in RCX) and member (this in RCX, sret in RDX) differ.
  > **Correction (2026-10-25, plan-checker revision):** the "no RCX/RDX sret swap is needed" claim is wrong for this repo. MSVC member functions return every class type through a hidden pointer, even an 8-byte CSteamID, and `meta/gen_vtables.ts` `isSretReturn` encodes that (`returnKind === 'class'`); the committed stub is `vt_SteamUser023_GetSteamID(void *self, void *sretOut)`. The flat C function returns the 8 bytes in RAX, so a flat body for any isSretReturn method must declare a zeroed `uint64_t out`, call the slot as `(self, &out, args...)` and return `out`. The guard stays `returnKind === 'class' && structSize > 8` -> refuse. See 53-04-PLAN.md.
- Use the manifest's real `cType` for each param (floats travel in XMM; the stubs' `uint32_t dummyN` params are only safe because the stubs ignore them).
- Slot-level identity: the call lands in the same stub the vtable would use (D-53-05). No second stub table.
- **Overload alias table.** Proton/manifest names overloads as `GetStat` / `GetStat_2`; the flat names are type-suffixed. Measured flat names: `GetStatInt32`, `GetStatFloat`, `SetStatInt32`, `SetStatFloat`, `GetUserStatInt32`, `GetUserStatFloat`, `GetGlobalStatInt64`, `GetGlobalStatDouble`, `GetGlobalStatHistoryInt64`, `GetGlobalStatHistoryDouble`, `GetAchievementProgressLimitsInt32`, `GetAchievementProgressLimitsFloat` [VERIFIED: ImplMap census of 5 assemblies]. Derive the suffix from the out-pointer param type (`int32*`->Int32, `float*`->Float, `int64_t*`->Int64, `double*`->Double) and pin it with a test that every census name in a served family resolves to an emitted export.

### Pattern 2: Flat `GetISteamX` and `SteamAPI_SteamX_vNNN` accessors (D-53-07)
`SteamAPI_ISteamClient_GetISteamUser(self, hUser, hPipe, pchVersion)` and siblings must not call the stub slot (the existing x64 stubs fall back to the null object, which is the vtable-path D-53-08 behaviour). Emit a dedicated body: validate `self` is a known SteamClient instance, call `resolve_iface_by_exact_version(pchVersion)`, return NULL on a miss, and log the version string (bounded, `FWD_VERSION_LOG_MAX_BYTES`-style) so the log names what to add next. The CR-01 comment at the `g_bridge_steamstub_path_active` flag shows the existing SteamClient lookup special cases; the flat bodies should not read that flag.

### Pattern 3: Managed scan, no managed code executed
Read, with ranged reads like `readPeMachineArch`: PE -> data directory 14 (CLR header) -> `Flags` at +16 -> metadata root `BSJB` -> streams (`#~`, `#Strings`, `#US`). Parse the `#~` header (heap-size bits, row counts), compute row sizes for tables 0x00..0x1C, then read **ImplMap (0x1C)**: `MappingFlags(2)`, `MemberForwarded(coded idx: Field|MethodDef, 1 bit)`, `ImportName(#Strings idx)`, `ImportScope(ModuleRef idx)`; map ModuleRef (0x1A) -> name. Algorithm validated end to end on 5 real assemblies (944/944/930/952/944 `steam_api64` imports; Rewired_Windows 115+115). Condensed reference:
```python
# Source: validated in this session against owned Unity assemblies (ECMA-335 II.22)
valid = u64(tilde+8); rows[t] for each bit set, 4 bytes each, starting at tilde+24
strIdx = 4 if hs&1 else 2; guidIdx = 4 if hs&2 else 2; blobIdx = 4 if hs&4 else 2   # hs = byte at tilde+6
idx(n) = 4 if n >= 65536 else 2
coded(tables, bits) = 4 if max(rows[t] for t in tables) >= 1 << (16-bits) else 2
# row sizes for 0x00..0x1C (only these are needed to reach ImplMap):
#  0 Module 2+str+3*guid | 1 TypeRef ResScope+2*str | 2 TypeDef 4+2*str+TypeDefOrRef+idx(Field)+idx(MethodDef)
#  3 FieldPtr idx(Field) | 4 Field 2+str+blob | 5 MethodPtr idx(MethodDef) | 6 MethodDef 8+str+blob+idx(Param)
#  7 ParamPtr idx(Param) | 8 Param 4+str | 9 InterfaceImpl idx(TypeDef)+TypeDefOrRef | 0xA MemberRef MemberRefParent+str+blob
#  0xB Constant 2+HasConstant+blob | 0xC CustomAttribute HasCA+CAType+blob | 0xD FieldMarshal HasFM+blob
#  0xE DeclSecurity 2+HasDS+blob | 0xF ClassLayout 6+idx(TypeDef) | 0x10 FieldLayout 4+idx(Field) | 0x11 StandAloneSig blob
#  0x12 EventMap idx(TypeDef)+idx(Event) | 0x13 EventPtr idx(Event) | 0x14 Event 2+str+TypeDefOrRef
#  0x15 PropertyMap idx(TypeDef)+idx(Property) | 0x16 PropertyPtr idx(Property) | 0x17 Property 2+str+blob
#  0x18 MethodSemantics 2+idx(MethodDef)+HasSemantics | 0x19 MethodImpl idx(TypeDef)+2*MethodDefOrRef
#  0x1A ModuleRef str | 0x1B TypeSpec blob | 0x1C ImplMap 2+MemberForwarded+str+idx(ModuleRef)
```
Coded-index table lists (tag bits): TypeDefOrRef(2): TypeDef,TypeRef,TypeSpec; ResolutionScope(2): Module,ModuleRef,AssemblyRef,TypeRef; HasConstant(2): Field,Param,Property; HasCustomAttribute(5): 22 tables per ECMA; HasFieldMarshal(1): Field,Param; HasDeclSecurity(2): TypeDef,MethodDef,Assembly; MemberRefParent(3): TypeDef,TypeRef,ModuleRef,MethodDef,TypeSpec; HasSemantics(1): Event,Property; MethodDefOrRef(1); CustomAttributeType(3): -,-,MethodDef,MemberRef,-.
Hardening required (untrusted game files): cap total bytes read, cap row counts and streams, reject any offset past EOF, never trust `e_lfanew`/stream offsets without bounds checks (same discipline as `peSteamDrm.ts`/`peSections.ts`, T-52-15).

Module names seen: `steam_api64`, `steam_api` (both in Rewired, which references both), and legacy `CSteamworks`/`CSteamworks64` (Unclaimed World's Steamworks.NET 2013-era; out of scope per the deferred todo, but the scanner must tolerate them without treating them as steam_api). Match case-insensitively, optional `.dll`. Pick symbols by arch: the x64 required set is the `steam_api64` module refs only.

### Pattern 4: Interface-version constants from the managed assembly
Steamworks.NET compiles the interface-version strings as literal constants (UTF-16, in `#US` / constant blobs). `readInterfaceVersionStrings()` scans latin1 and therefore **finds nothing in a managed assembly** (UTF-16 `S\0t\0e\0...`). Add a UTF-16LE variant (or read `#US` entries) and feed the result into the `exeVersions` input of `resolveRequiredInterfaceVersions`. Measured sets (see table below). Because the original Valve `steam_api64.dll` contains many versions per family, mixing it into the pool makes every family `@ambiguous`. For Mono titles the managed constants are the authoritative request list: when they exist, resolve from them alone (Open Question 2).

### Anti-Patterns to Avoid
- **Aliasing a neighbouring version** (D-53-03): SteamClient020 vs 017, Friends017 vs 015/018 differ in slots. Extract each.
- **Re-extracting an existing manifest**: it drops hand-added `helperInterface` and wire-policy overrides (51-15 commit 5e42afe5c, 52-13 plan). Hand-widen `arches` instead.
- **Changing the vtable-path fallback** to NULL: reopens CR-01 (D-53-08).
- **Reading engine logs from the helper side**: Mac Steam In-Game and helper-originated calls never count (D-53-13).

| Problem | Don't Build | Use Instead | Why |

## Common Pitfalls

### Pitfall 1: The managed-scan required set swamps the verdict
**What goes wrong:** D-53-04 merges every `steam_api*` DllImport into the required set. Steamworks.NET declares 930-952 imports; ~480 belong to families with no manifest (UGC 94, Input 48, NetworkingSockets 47, GameServer 41, HTMLSurface 37, Inventory 38, MusicRemote 32, HTTP 25, NetworkingUtils 27, ...). Every Unity title becomes `miss` with hundreds of names persisted into `steam_metadata.json` and the census detail.
**Why it happens:** P/Invoke binds lazily, so a missing entry only faults when called, but the static scan cannot know which calls happen.
**How to avoid:** decide the policy before coding (Open Question 1). Whatever is chosen, store a count plus a short head of names, not all names (the census strips entries over 128 chars or containing `/`, `\`).
**Warning signs:** `persisted missingSymbols` > 100 entries; census detail unreadable.

### Pitfall 2: `readInterfaceVersionStrings` cannot see managed constants
**What goes wrong:** latin1 scan of a .NET assembly finds zero versions; the family resolves as `@unknown-version`, or (mixed with the Valve DLL's pool) `@ambiguous`. Verdict wrong in either direction.
**How to avoid:** UTF-16 scan of the managed assemblies; resolve from the managed constants when present (Pattern 4). Test with the measured table.

### Pitfall 3: Flat names versus manifest names
**What goes wrong:** manifest `GetStat`/`GetStat_2` vs flat `GetStatInt32`/`GetStatFloat`; also methods newer than the pinned manifests (`IsSteamRunningOnSteamDeck` is in SteamUtils010, not 008; `ISteamClient_GetISteamInput/Parties/RemotePlay/GameSearch` need Client020+). Generating from existing manifests alone leaves 26 in-family imports unexported, including Rogue Waters' hang symbol.
**How to avoid:** alias table plus the new manifests; add a jest test that loads the census name list (a small committed fixture of flat names per generation, no game code) and asserts every served-family name is exported.

### Pitfall 4: Serving a family partially flips null-object-eligible into "unservable"
**What goes wrong:** `findUnservableInterfaceVersions` treats an unserved version as acceptable only if the family is entirely unserved (null-object-eligible). Adding SteamGameServer015 (D-53-11) while Rogue Waters requests SteamGameServer014, or SteamFriends017 without 018, creates version skew and the j4l guard **withholds the shim** (no HELLO at all).
**How to avoid:** for every title in the sample, run the coverage evaluation with the measured version table above after adding manifests; add GameServer014 together with 015, and widen Friends018 to x64.

### Pitfall 5: The hand-pinned export list will not scale
**What goes wrong:** `SHIM64_EXPORTED_SYMBOLS` is a hand-maintained 49-line list verified against the `.def` in `shimCoverage.test.ts`. Flat exports add on the order of 400-600 names.
**How to avoid:** have the generator also emit a committed `shimExports.generated.ts` (idempotent like the `.def`) that `shimCoverage.ts` imports; keep the both-directions test against the `.def`. `SHIM_EXPORT_SET_VERSION` derives from it automatically.

### Pitfall 6: Census Evidence depends on log rotation and bottle layout
**What goes wrong:** the census reads only `gamelib.log` and `gamelib.log.old`; HELLO lines for sampled titles already sit in rotated `gamelib.log.pre-51-29-*` files. Today most rows read `unverified (no HELLO)` for that reason. Only a per-game bridge bottle (`GameLibSteamBridge-<appId>`) is attributable.
**How to avoid:** read `gamelib.log*` siblings (bounded), and run the re-run sample in one session before rotation. The sample plan should record the log set used.

### Pitfall 7: No positive init marker for Unity; engine logs may be empty
**What goes wrong:** `classifyBridgeEvidence` calls a title `verified` when it finds no failure marker. A Unity run that crashes before logging anything would still read verified if the log exists and is clean. Godot's `godot.log` for Overlooting is **0 bytes** (file logging off by default), GameMaker has no persistent runner log, and Mining Mechs has no log at all.
**How to avoid:** D-53-13's bridge trace is the evidence for those engines; for Unity add a cheap positive check (e.g. `Player.log` modified after HELLO, or the absence of the failure strings plus at least one game-originated call). Define "clean" per engine explicitly in the plan.

### Pitfall 8: AnyCPU rule needs both CLR flags
**What goes wrong:** treating "machine 0x14c + CLR header" as AnyCPU misclassifies `Prefer32Bit` exes (`COMIMAGE_FLAGS_32BITPREFERRED` 0x00020000), which run as 32-bit on a 64-bit OS.
**How to avoid:** AnyCPU-as-x64 iff CLR header present AND machine is I386 AND flags lack `32BITREQUIRED` (0x2) AND lack `32BITPREFERRED` (0x20000). Measured: UnclaimedWorld.exe flags = 0x1 (ILONLY only) -> x64 [VERIFIED: local parse]. The `32BITPREFERRED` handling is `[ASSUMED]` from the CLR spec; D-53-10 literally says only "without 32BITREQUIRED", so confirm in Open Question 3.

### Pitfall 9: Game-originated trace needs a helper change
**What goes wrong:** D-53-13 says a game-originated call "recorded in gamelib.log" counts. Today the helper logs only `HELLO`, `FWD` (forwarded SteamClient calls) and error lines; ordinary wire requests (`GetSteamID`, `GetPersonaName`) are **not logged**.
**How to avoid:** add a once-per-(ordinal,slot) `CALL` log line in the generated dispatch (`emitDispatchCase` / `generateDispatchHeader`), bounded and carrying no SteamID or token (the 52-02 constraint "Logs carry no SteamID/token"). Wire requests all originate from the shim, so any wire request after HELLO is game-originated by construction; the helper's own init is not a wire request. The census regex must key to the appid (helper lines are prefixed `bridge helper [<appid>]:`). This is a Mach-O helper change, so it needs `pnpm build-steam-bridge` and a dev restart to take effect live.

### Pitfall 10: Live-test pitfalls from project memory
`tauri dev` does not rebuild the sidecar; check `sidecar.js` mtime before live runs. "Verified" is strict; do not reroute a known-bad title to bottled Steam to make the number look good. Do not run the Overlooting 322 MB exe through any read-all path (range-based reader only; the earlier "could not parse the exe as a PE" note is unexplained and needs the real binary: check in the Overlooting re-test).

1. **What does the managed scan do with the ~480 unserved-family names?**
