<objective>
This plan works on the one in-scope lever left for the done-when (VERIFICATION gap 1).

The 53-15 diagnosis covers why Overlooting 3410180 never reaches HELLO. Godot 4.4's NVIDIA driver-profile setup loads `nvapi64.dll` and calls through `nvapi_QueryInterface` results without a NULL check. CrossOver's builtin `nvapi64.dll` loads, but it cannot load its `nvapi.dll` backend (c0000135). QueryInterface therefore returns NULL, and the game faults at rip=0 before GodotSteam ever enters the shim. The fault is identical with the shim removed. Godot skips the whole NvAPI block when `LoadLibraryA("nvapi64.dll")` returns NULL, so disabling `nvapi64` for this game is the candidate fix.

Why the other two non-verified rows are not levers (measured while planning, 2026-10-25):
- **Avernum 6 206060.** `objdump -p "Avernum 6.exe"` shows the game imports only `SteamAPI_Init` and `SteamAPI_Shutdown` from steam_api.dll. The bridge-allowlist note already says "Init/Shutdown". The game writes no log. Under D-53-13 it can never produce a game-originated call beyond init, so it cannot verify without relaxing the criterion. Avernum 4 206020 is the same.
- **Ranch Simulator 1119730.** It is SteamStub `.bind` (53-15), which is Phase 52 scope.

That leaves Overlooting as the single in-scope row that can take the count from 9 to 10.

Scope note: this is a per-title DLL override in the title's own bridge bottle. It is not installing a Windows runtime component (that is the out-of-scope runtime-components todo), and it is not a reroute to bottled Steam.

Output: 53-19-NVAPI.md (measured), and, if a mechanism works, a tested per-appId override applier wired into the bridge launch.
</objective>
