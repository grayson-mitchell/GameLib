<objective>
Run the 60-15/60-17 instrument live and decide the G1 fix from evidence, the way 60-12 did, but
asking the question 60-12's data left open: with a working overlay open/close signal, does releasing
winemac's capture on open make the overlay usable in gameplay?

Verdict codes (60-19/60-20 implement the branch the code names):
- **X-RELEASE**: with `<signal>:release`, in gameplay the cursor appears, the overlay takes clicks,
  the camera does not turn while open (or `input-leak: yes` is recorded and `release+block` did not
  stop it), and mouse-look returns after close. Fix: release on open, defer while open, replay on close.
- **X-RELEASE+BLOCK**: `release` alone gives a cursor and clicks but the camera still turns;
  `cb:release+block` also stops the camera while the overlay still takes clicks and closes. Fix: the
  same plus np_overlay_shim_set_active on open/close. Only valid with `signal: cb`.
- **X-NOSIGNAL**: no source (cb or key) fires reliably at gameplay open and close. No fix can be
  scheduled; 60-19/60-20 stop.
- **X-NONE**: a signal fired and the release ran (an `experiment release` line at the open), but the
  overlay still could not be clicked, or mouse-look did not return after close on a run. 60-19/60-20
  stop.

Both CrossOver titles must agree for X-RELEASE / X-RELEASE+BLOCK (Planet Crafter D3DMetal and
Schedule I DXVK). The Staging run decides `fix routes:` (`tcp-clone,env` when it also passes, else
`tcp-clone` with the Staging result recorded as an open issue for 60-16).

Purpose: a guessed fix risks a third failed live gate. Output: 60-18-SUMMARY.md with the verdict.
</objective>
