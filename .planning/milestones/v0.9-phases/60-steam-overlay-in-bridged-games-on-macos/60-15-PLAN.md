<objective>
First plan of the replacement G1 chain (60-15 -> 60-17 -> 60-18 -> 60-19/60-20 -> 60-16). 60-12 returned
V-NONE: winemac holds a 1x1 confinement + hidden cursor (plus a warp and an associate call) in gameplay on CrossOver
AND Staging, opening the overlay never releases it, and the probe saw no overlay open/close marker.
The user chose a release-on-open experiment driven by a working open/close signal.

This plan builds the signal's cross-process half and the env plumbing for the experiment:
1. The bridge helper already receives Mac Steam's GameOverlayActivated_t (k_iCallback 331). Evidence
   gathered while planning: `CBQ unlisted iCallback=331 action=drop callresult=0` in the helper output
   at 18:03:29 (60-12 Run B, 1284190) and 18:14:32 (Run C, 3205720), both near the operator's
   main-menu overlay opens. It is logged once per helper (gl_cbq_note_unlisted dedupes) and dropped.
   Behind GAMELIB_OVERLAY_INPUT_PROBE=1 the helper now logs each transition and publishes it as a
   Darwin notification the in-game probe (60-17) listens to. Proton's lsteamclient uses this same
   callback for the same purpose (steamclient_main.c L1357, `HACK: Steam overlay activated, disabling
   all input events`).
2. The sidecar passes a validated GAMELIB_OVERLAY_RELEASE_EXPERIMENT value to the game process next
   to the probe, so 60-18 can arm the experiment that 60-17 builds into the probe dylib.

Opt-in only: nothing changes unless the dev sidecar is started with the probe flag. This plan runs in
parallel with 60-17 (no shared files). The notification name `com.gamelib.steambridge.overlay.<appid>`
is the contract between the two plans; both write it as the same literal.

Output: helper signal (header + pump wiring + compiled test), experiment env passthrough with tests.
</objective>
