<objective>
Build the DRM-mode launch-setup orchestrator, `drm/drmLaunchSetup.ts`, and the bottle-settings
variant that runs a title's existing bridge bottle under the cloned runner.

1. `drmLaunchSetup()` takes one bridge launch and decides, through 56-04's
   `resolveBridgeMode`, whether it is a DRM-mode launch. For a `.bind` title it runs the six
   setup steps in their fixed order. Each step returns a typed `DrmStepResult`. The first failure
   stops the run and is returned as is, so 56-12 can log `reason=drm-<step>` and show the notice.
   First-launch work is reported through the existing `redist` status with a context label.
2. In `bottle.ts`, `getDrmBridgeBottleSettings()` swaps `wineVersion` to the clone and follows the
   56-01 launch form. A per-appId runner registry makes `getBridgeBottleSettings(appId)` and the
   per-game wineserver stop paths use the same clone for every wine spawn of that appId.

Purpose: 56-12 wires one call, `drmLaunchSetup(...)`, into `launchBridgeGame` before
`placeShimForGame`. Every DRM failure then maps to one `DrmStep` (D-13), work happens only for
`.bind` titles and only once (D-05), and the title stays in its own bottle with the runner
swapped (D-11). The wineserver for the bottle is never started by one runner and joined by
another (RESEARCH "Runner clone").

Output: one orchestrator module and its jest file, plus an additive edit to `bottle.ts` and its
test file. `games.ts` is not touched; that is 56-12.
</objective>
