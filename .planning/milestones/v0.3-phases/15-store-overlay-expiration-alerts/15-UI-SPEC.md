# Phase 15 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Scope note:** This phase is 100% additive to an already-mature, hand-rolled SCSS design system (14 prior UI phases deep). It introduces **zero new colors, zero new spacing values, and zero new typography scale steps** — every visual element specified below is a prescribed *composition* of existing tokens/components (`_colors.scss`, `_typography.scss`, `_spacing.scss`, the Phase 13 pill-badge family, the Phase 13 group-heading pattern). Where this document says "reuse," that is a locked contract, not a suggestion.

## Color

**All colors reused verbatim from `_colors.scss`'s existing semantic status tokens.** This phase adds no new hex values anywhere.

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `var(--body-background)` | App background — unchanged by this phase |
| Secondary (30%) | `var(--gradient-gamecard)` (DiscountCard surface) / existing row/card backgrounds | `DiscountCard` background, Keys-waiting row surfaces — unchanged by this phase |
| Accent (10%) | `var(--status-success)` (Owned pill) · `var(--status-info)` (Key-available pill) · `var(--status-warning)` / `var(--status-danger)` (pinned-section urgency tiers, unchanged reuse from Phase 13) | See "Accent reserved for" below |
| Destructive | `var(--status-danger)` | Reused only as the ≤7-day urgency-tier pill background inside the pinned section (D-87, unchanged Phase 13 semantics) — this phase has **no destructive user action** |

**Accent reserved for** (explicit, exhaustive list — nothing else on these surfaces gets a new color this phase):
1. The **Owned** ownership pill on `DiscountCard` — `var(--status-success)` background, `var(--neutral-01)` text (D-83/D-85).
2. The **Key available** ownership pill on `DiscountCard` — `var(--status-info)` background, `var(--neutral-01)` text (D-84/D-85). Chosen because `--status-info` is the exact color already used for the `UNREVEALED` key-state badge on the Humble Keys screen — "a key exists, unclaimed" is the same concept in both places, so reusing the token keeps the app's color vocabulary consistent.
3. Urgency-tier pill backgrounds inside the pinned Expiring-soon section — `var(--status-warning)` (≤30 days) / `var(--status-danger)` (≤7 days) — **unchanged, direct reuse of Phase 13's `UrgencyBadge` component**, not a new color decision (D-87).

Color-per-card rule (D-85): **at most one** ownership pill renders per `DiscountCard`. Owned always wins over Key-available. A card with neither renders no pill at all (D-79) — no gray/neutral "unowned" placeholder pill exists.

## Interaction Contract

- **D-81 (badges are informational only):** the ownership pill must not be wrapped in a `<button>`, must not have `cursor: pointer`, must not have a hover state, and must not intercept `DiscountCard`'s existing click-through to the store page. It is a `<span>` sibling inside the existing clickable card, exactly like `.humbleKeyOwnedBadge` is a non-interactive sibling inside `HumbleKeyRow`.
- **D-88 (move, don't duplicate):** a key that qualifies for the pinned section must be *removed* from wherever it would otherwise render in the flat Keys-waiting list — never rendered twice. Implementation should partition `selectKeysWaiting(...)` output into `{ pinned, rest }` once, not filter twice independently (risk of a key appearing in both if the two filters drift).
- **D-89 (hidden entirely when empty):** the pinned section's DOM node (heading + list) must not render at all when `pinned.length === 0` — not a heading with zero rows, not a `display: none` container. Verify via DOM query in tests, not just visual inspection.
- **D-91 (notification click → focus + navigate):** clicking the OS notification must both restore/focus the app window AND navigate to `/humble-keys/waiting` — a user who only sees the window pop back up without landing on the right screen has not received the full contract.
- **D-92 (transition-based dedup):** this is a data-layer contract, not a visual one, but it directly determines *when* the notification fires — implementers must not treat "re-sync with the same expiration date" as notification-worthy. See RESEARCH.md Pattern 2 for the exact diff logic.
