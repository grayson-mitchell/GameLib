# Phase 14 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

## Design System

| Property | Value |
|----------|-------|
| Tool | none — GameLib is a 13-phase-deep Heroic fork with an established, hand-rolled SCSS custom-property design system (`src/frontend/styles/_colors.scss`, `_spacing.scss`, `_typography.scss`, multi-theme `themes.scss`). No `components.json`, no Tailwind, no shadcn anywhere in the repo. CLAUDE.md's mergeability constraint ("must remain Electron + React + TypeScript to stay mergeable with Heroic upstream") plus 13 shipped phases on this token system make introducing shadcn now actively harmful, not neutral. **shadcn gate: intentionally not offered — same resolution as Phase 13's UI-SPEC, carried forward unchanged.** |
| Component library | none — hand-rolled React components per screen. This phase reuses the global `showDialogModal`/`DialogModalOptions` modal primitive (`message: string \| React.ReactElement`, confirmed in `src/frontend/types.ts` and `MessageBoxModal/index.tsx`) as the wizard's chrome, and extends the existing `HumbleKeyRow` (Keys-waiting tab only) rather than forking it. |
| Icon library | FontAwesome (`@fortawesome/react-fontawesome` + `@fortawesome/free-solid-svg-icons`) — already the icon library for every sibling Humble Keys component (`faExternalLinkAlt` on the Gift button, `faSyncAlt`, `faChevronRight`). Use FontAwesome for the wizard's "Open Steam" / "Redeem on {platform}" external-link glyph and any step-transition affordance; do not introduce a second icon package. |
| Font | Primary (headings): `Rubik`. Secondary (body/UI): `Cabin`. Both already declared in `_typography.scss`; no new font-loading needed. |

## Spacing Scale

**Deviation from default 4px-multiple scale, by design — unchanged from Phase 13:** this project's spacing tokens are em-based with a 1.2 ratio, already in production across 13 shipped phases including the exact screen (`Keys/Waiting`) this phase extends. Do not introduce a parallel px-based 4/8/16/24/32 scale.

| Token | Value | Usage in this phase |
|-------|-------|----------------------|
| `--space-3xs` | 0.25em (~4px) | Badge internal padding (reused, unchanged), wizard step-indicator dot gaps |
| `--space-2xs` | 0.375em (~6px) | Badge padding, tight inline gaps (copy-key button icon gap) |
| `--space-xs` | 0.5em (~8px) | Wizard row-internal gaps (label-to-value, button-to-icon) |
| `--space-sm` | 0.75em (~12px) | Wizard step vertical rhythm within a single step |
| `--space-md` | 1em (~16px) | Wizard body block spacing (warning text to buttons, key display to action row), "Claim"/"Finish activation" button placement in `HumbleKeyRow` |
| `--space-lg` | 1.5em (~24px) | Modal content top/bottom padding between wizard steps |
| `--space-xl` | 3em (~48px) | Not used this phase (empty-state scale, inherited unchanged) |
| `--space-md-fixed` | 16px | Modal outer padding (inherited from existing `Dialog`/`DialogContent` chrome — do not override) |

Exceptions: none. The wizard modal reuses the existing `Dialog`/`DialogHeader`/`DialogContent`/`DialogFooter` padding conventions verbatim — no new modal-chrome spacing is introduced.

## Typography

Reuse the existing 4-size / 2-weight scale already exercised by `HumbleKeyRow`/`HumbleKeyGroup`/Phase 13's tab bar — do not add a 5th size or a 3rd weight.

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body / wizard step copy (warning text, instructions) | `--text-md` (16px) | `--regular` (400) | 1.5 — this phase's warning and instructional copy is genuinely multi-line, unlike Phase 13's single-line rows, so the 1.5 line-height matters in practice here |
| Label / caption / key-value display | `--text-xs` (11.11px) | `--regular` (400) plain captions; `--semibold` (600) the revealed key string itself (needs to be scannable/copyable, treat it like a badge-weight value, not throwaway caption text) | 1.2 |
| Wizard step title / modal title | `--text-lg` (19.2px) | `--semibold` (600) | 1.2 |
| "Claim" / "Finish activation" row button label | `--text-xs` (11.11px) | `--regular` (400) — matches the existing `.humbleKeyGiftButton` chrome this button is styled after | 1.2 |

Exactly 2 weights used across the whole phase: `--regular` (400) and `--semibold` (600) — matches the existing screen's convention exactly. No monospace font is introduced for the key display; `--semibold` at the existing default font stack is sufficient for scannability and keeps this phase's font inventory at zero new declarations.

## Color

Multi-theme app — **all colors below are semantic custom properties, never hex.** Hard cross-cutting constraint inherited unchanged from every prior Steam/Humble phase.

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `var(--body-background)` | Modal backdrop area outside the Dialog chrome (existing, unchanged) |
| Secondary (30%) | `var(--background)` | Dialog/modal surface background (existing `Dialog` component, unchanged) |
| Accent (10%) | `var(--accent)` | The "Open Steam" / "Redeem on {platform}" primary wizard action link only, plus the re-copy-key button's hover state — mirrors Phase 13's "accent = active interactive text/link, never a background fill" rule |
| Destructive / irreversible-action | `var(--status-danger)` via the existing `.button.is-danger` class | The C1 irreversibility warning step's primary confirm button ("Reveal key" — the point of no return) and the C2 owned-game block message. This is new usage of an *existing* button class (`_buttons.scss` `.button.is-danger`), not a new color token. |

**Accent reserved for:** the primary post-reveal action link ("Open Steam" / "Redeem on {platform}") and the re-copy-key button's hover state. **Never** used as a background fill, never on the "Claim"/"Finish activation" row button (that stays styled like the existing `.humbleKeyGiftButton` — bordered, `var(--text-secondary)` default, `var(--accent)` on hover only, per Phase 13's precedent), and never on the C1 warning confirm button (that is `.is-danger`, not accent — irreversibility gets the danger treatment, not the interactive-accent treatment).

**Status tokens reused unchanged (no new semantic color introduced this phase):**

| Tier | Token | Hex (current theme) | Applies to |
|------|-------|----------------------|------------|
| Danger | `--status-danger` | `#f97881` | C1 irreversibility confirm button (`.button.is-danger`), C2 owned-block message background/border |
| Warning | `--status-warning` | `#f8ae79` | `REVEALED` state badge (existing, unchanged) — the "Finish activation" row inherits this badge color as-is |
| Info | `--status-info` | `#2ceac7` | Passive "you already own this" note at the Finish-activation step (D-72) — reuses the same tone as the existing `UNREVEALED` state badge and Phase 13's fail-soft banner treatment (informational, not blocking) |
| Success | `--status-success` | `#0ce396` | `REDEEMED` state badge (existing, unchanged) — the row after "Mark as redeemed" |

| Wizard Step 2 primary action (Steam keys, HCLAIM-03) | **"Open Steam"** — opens `store.steampowered.com/account/registerkey?key=` pre-filled |
| Wizard Step 2 primary action (non-Steam keys, HCLAIM-05) | **"Redeem on {{platform}}"** — link-out only, no one-click activation |
| Wizard Step 2 confirm action | **"Mark as redeemed"** |

| Wizard ambiguous-outcome state (Pitfall B — reveal call timed out, no known key value) | **"We couldn't confirm this finished — sync to check"** with a manual sync-now action; never a second reveal attempt |
| Wizard failed-reveal state (D-78, definitive failure) | **"Couldn't reveal this key — nothing was used up. You can try again."** with a **"Try again"** retry action |

The non-Steam "Redeem on {{platform}}" action links to a generic "how to redeem a {{platform}} key" destination or, at minimum, surfaces the copy-key affordance prominently rather than fabricating a possibly-wrong deep-link to a page that would display a real secret.

## Phase-Specific UI Contract

*(Additional detail beyond the standard template — this phase is a modal wizard grafted onto an existing read-only row, not a new screen, so the contract needs to specify state-machine visuals the template's flat tables don't cover.)*

### Wizard as a single stateful `showDialogModal` message component

- One `HumbleClaimWizard` React component is passed as `DialogModalOptions.message` (confirmed pattern: `message: string | React.ReactElement`, `MessageBoxModal` renders it via `getContent()`'s default branch). It owns its own step index / loading / error state internally.
- Do **not** chain multiple discrete `showDialogModal()` calls for the steps — that would require lifting all wizard state into the row/caller and reopening/closing the Dialog per step, which flickers the backdrop and loses focus. One mount, internal step transitions.
- Reuses `Dialog`/`DialogHeader`/`DialogContent`/`DialogFooter` chrome as-is — no new modal shell, no new backdrop/close-button styling.

### Row-level entry points (Keys-waiting tab only, D-67)

- `HumbleKeyRow` gains one more optional prop (alongside Phase 13's `urgencyTier`/`giftAction`): a `claimAction` prop, rendered **only** on `/humble-keys/waiting`, never on `/humble-keys/all` or `/humble-keys/spares` (mirrors D-22's read-only-except-sanctioned-exceptions rule).
- Button chrome for "Claim" / "Finish activation": same bordered-button family as the existing `.humbleKeyGiftButton` (`border: 1px solid var(--text-secondary)`, `var(--accent)` on hover, `--text-xs`/`--regular`) — this is a sibling primary action to the Gift button, not a visually distinct new button style.
- `UNPICKED` pseudo-entries (D-27, Choice-month rows with no key to reveal) never render a `claimAction` — no entry point into the wizard exists for them this phase (per CONTEXT's Claude's Discretion resolution).
- A key whose cached `keyindex` is unresolved (Pitfall C — pre-Phase-14 cache, not yet re-synced) shows a disabled/no-op "Claim" state rather than opening a wizard that would fail — label unchanged, but disabled with a tooltip-equivalent caption: **"Sync to enable claiming"**.

### Step 2 visual hierarchy (post-reveal)

The revealed key string is the **primary visual anchor** of the post-reveal step: it renders at `--text-xs`/`--semibold` inside a visually distinct value container (subtle `var(--input-background, var(--background))` fill, `--space-3xs` radius — same pill chrome family as `.humbleKeyGroupCount`) with the "Copy key" button directly beside it. The "Open Steam" / "Redeem on {{platform}}" accent link and the "Mark as redeemed" button sit **below** the key as secondary elements — the user's eye lands on the key first, actions second. Rationale: the key IS the payload the whole flow exists to deliver (D-73), and clipboard auto-copy can silently fail, so the manual-read path must be the most prominent element on the step.

### Step-state visual mapping

| Wizard state | Primary color treatment | Icon |
|---|---|---|
| Step 1 — warning | `.button.is-danger` on confirm; body text default `var(--text-default)` | none required |
| C2 owned-block | `var(--status-danger)`-toned message panel (reuse the existing `WarningMessage`-style block treatment, tone-shifted to danger, not the Phase 13 fail-soft orange) | none required |
| Step 2 — key revealed, Steam | `var(--accent)` on "Open Steam" | `faExternalLinkAlt` beside "Open Steam", matching the Gift button's existing icon precedent |
| Step 2 — key revealed, non-Steam | `var(--accent)` on "Redeem on {platform}" | `faExternalLinkAlt`, identical treatment — one code path, D-68 |
| Finish-activation passive note | `var(--status-info)` toned caption, not a blocking panel | none required |
| Ambiguous-outcome | `var(--status-warning)` toned caption (uncertain, not failed) | none required |
| Definitive failure | `var(--status-danger)` toned caption + retry button styled `.button.is-secondary` (retry is not itself dangerous) | none required |
| Cooldown | Same treatment as the existing D-33 cooldown surface elsewhere in Humble Keys — do not invent a new cooldown visual language | none required |

### Icons

- `faExternalLinkAlt` — reused verbatim from the Gift button precedent, for both "Open Steam" and "Redeem on {{platform}}."
- No new icon package. If a distinct "copy" glyph is desired for the "Copy key" button, use FontAwesome's existing `faCopy` (already available in `@fortawesome/free-solid-svg-icons`, confirm at implementation time rather than adding a new import surface) — otherwise a text-only "Copy key" button is acceptable and simpler.
