<objective>
Make depot installs set the exec bit on `#!` shell-script launchers inside app bundles. Today GameLib installs Bastion (107100) on macOS and its launcher `Bastion.app/Contents/MacOS/Bastion`, a bash script, lands `-rw-r--r--`. When Steam launches it, macOS opens it in TextEdit. Steam then tracks TextEdit as the running game and refuses the next launch with `AppError_16`. The depot crate sets +x from two sources only: the manifest's Executable/CustomExecutable flags, and the Mach-O content fallback. Bastion's manifest does not flag the script, and the script is not Mach-O.

Purpose: close todo `2026-11-18-depot-install-misses-exec-bit-on-shell-script-launchers.md`, found at the Phase 81 live gate, item 3, launch L2.
Output: a shebang executable fallback in `post.rs`, built in the same shape as the Mach-O probe (bounded read, report counter). It is wired into `apply_modes_sync` and counted through `Outcome.stats` into the `[depot-rust] outcome` log line, and it has an end-to-end test and a unit matrix with shebang fixtures. When the code has landed, the todo moves to `completed/`.
</objective>

<scope_decision>
**Decision: the rule needs both conditions.** The file's first two bytes must be `#!`, and its resolved destination path must lie inside a `*.app/Contents/MacOS/` directory, at any depth and in any nested `.app`. It does not apply to `#!` files anywhere else. It does not parse `Info.plist`.

Reasoning, from how the Mach-O fallback scopes itself:

1. **The Mach-O fallback is content-gated and never path-gated, and that is a user-locked decision.** Phase 23-08 (`.planning/milestones/v0.7-phases/23-steam-full-ownership-install-stateflags-4/23-08-PLAN.md` lines 60-63 and 309-311) rejected a blanket "chmod +x everything under `.app/Contents/MacOS/`" safety net. The new rule keeps that invariant: **a path never grants +x by itself.** Content is always required, and the path only narrows which files are probed. Task 3 pins this with a test: a non-`#!` file under `Contents/MacOS` keeps its mode.
2. **Mach-O can rely on content alone because its signal is strict. `#!` is not.** The Mach-O probe checks magic plus filetype EXECUTE/DYLIB. It deliberately excludes MH_BUNDLE, because Phase 23's trace showed that Steam's own reference install is selective: `unitypurchasing.bundle` stays non-exec, and HUMANKIND's bits are set per file, with `.txt` excluded. `#!` is two ASCII bytes with no subtype to tell files apart. A content-only rule would mark every `#!`-headed library module or sourced fragment anywhere in a depot: Python/Perl stdlib in bundled runtimes, and Windows-depot payloads installed for the bridge. That over-applies compared with Steam, which is exactly the over-application 23-08 avoided by excluding MH_BUNDLE. The path condition does the job for `#!` that the MH_BUNDLE exclusion does for Mach-O: it narrows and never widens.
3. **`Contents/MacOS/` is where the defect actually happens.** LaunchServices opens a non-executable `CFBundleExecutable` as a document. `CFBundleExecutable` must name a file in `Contents/MacOS/`, so the directory rule already covers it. Leaving out the `Info.plist` parse also avoids a cross-file ordering dependency: files land concurrently (`file_concurrency`), so the plist may land after the launcher, and the heal and delta paths apply modes one file at a time.
4. **The gate reads the resolved on-disk destination, not the raw manifest name.** `resolve_contained_path` has already split backslash names (Mac depots name files `Civilization V.app\Contents\MacOS\...`, as seen in the spike 067a log). The same check also covers an installdir that is itself the bundle (`common/Game.app/Contents/MacOS/Game`). It keeps the same `(path, flags, report)` signature as `apply_macho_fallback`.
5. **Deliberately not covered:** `#!` scripts in `Contents/Resources/`, in a `.bundle` (dlopen'd, never launched), or outside any bundle (for example a Linux `start.sh`). No title shows a need for them. If one does, widen the rule using that title's evidence. Name this trigger in the SUMMARY.
</scope_decision>
