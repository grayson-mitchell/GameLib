<objective>
Stop the restart-on-Play note and the "Restart Steam now" button from flashing for 1-2 s at the end of a GameLib depot install (Phase 81 live gate item 7, launch L2, 2026-11-18). The page should only ever show the state it settles on.

Purpose: the page must not offer a Steam restart that is not needed (7a) or tell a signed-out user that Play will restart Steam (7b).

Output: two backend ordering fixes in the install-end branch, regression tests that fail on the old ordering, and the todo annotated with the owed live check.

Root cause (investigated during planning; the evidence is in the gate session `/tmp/gamelib-gate-20261118T063108Z`, `gamelib-launch-2.log` lines 780-790 and 887-900, `terminal.log` lines 117-131, and `operator-notes.txt`):

1. 7b (Machinarium 40700, signed out). The InstallApp verdict did come before the record (`InstallApp adoption of 40700 not used (library-lookup-unverified)` and then `recorded pending Steam adoption`, both at 21:48:54). So the orchestrator's hypothesis, that the record or notify comes before the verdict, is not the cause. The cause is that `recordAndWatchPendingAdoption` pushes the page status at once, and `getSteamAdoptionStatus` reads `steamSignedIn` from `steamInstallRuntime.adoption.signedIn`. That cache is only filled by the Rust watch's `adoptionState` event, and the watch's first tick comes up to `ADOPTION_TICK_MS` (5 s) after the watch starts. So the first push carries `steamSignedIn: null`. `AdoptionNote.tsx` treats only `false` as signed out (line 80), so null renders "Steam will restart once when you press Play." plus "Restart Steam now". The next push carries `false` and switches the page to the sign-in note.
2. 7a (Wildermyth 763890, signed in, InstallApp ok). No pending record existed at any point in that install. The only record for 763890 that launch, written at 21:35:50 by item 9, was cleared at 21:36:02 by the uninstall's `clearAndUnwatchPendingAdoption`, the sole caller of `steampoll_adoption_unwatch`. The note's `installedPending` arm therefore could not fire. "Restart Steam now" has exactly one other render path: `AdoptionNote.tsx` line 75, `is.installing && statusContext === 'steam-waiting-for-restart'`. That context has exactly one producer: `install_once.rs` line 268, `state_flags == 1026 && poll.handoff.is_native_handoff`. After InstallApp returned ok at 21:43:11, `gameInstallDepot.ts` line 326 still started the poll with `isNativeHandoff: true`. Its first tick is one 3 s period out (`install_loop.rs` line 457). Meanwhile Steam rewrites GameLib's ACF during its own InstallApp validation and repair, and a repair shows StateFlags 1026 (spike-findings `mac-steam-client-integration.md` section 3: "The UI must not read that as waiting for Steam restart"). So one tick reported waiting-for-restart, and the next tick saw 4 and completed. This is an inference by elimination over the two render paths: neither log sink records that tick, which is why the live check below is owed.

Chosen fix (backend ordering; the frontend is not changed):
- 7b: take the one-shot Rust reading (`readSteamAdoption`) after the InstallApp verdict and before writing the record. Seed the signed-in cache from it, so the record's single push is already settled. An already-adopted reading writes no record (the watch's first tick would clear it anyway, so this only removes a flash). The rule is the same one `migrateOneHold` already applies (RESEARCH Pitfall 5).
- 7a: when Steam has adopted the install (InstallApp ok, or the reading says so), start the poll with `isNativeHandoff: false`. Any 1026 after that point is Steam's own active state, and that is exactly the case the flag's comment at `gameInstallDepot.ts` lines 562-571 reserves for false.
- Rejected: holding the note in `AdoptionNote.tsx` while `steamSignedIn` is null. Null is also a steady state: on Windows and Linux the reading is reported only while Steam runs, and a failed Rust read answers null (D-10, "behave as before the watch existed"). A null-hold would hide the note for good in those cases, and a timed hold would add a frontend timer that guesses a duration. A frontend hold also cannot fix 7a, because there the backend genuinely reports a waiting context. The page should render what the backend tells it, and the backend should only say settled things.
</objective>
