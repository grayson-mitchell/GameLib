## Defect found

**Re-watching the adoption watch while a slow tick is in flight runs two evaluations at once.** The prediction in the plan holds. Test (NOT committed; file restored to `11e3c4308`):

```rust
/// Code reading predicts this fails. `unwatch` (adoption.rs:401-413) cancels the token and clears
/// `started` without waiting for the task. The in-flight tick body is not raced against the token
/// inside the select arm (adoption.rs:382-389), so the old task's slow probe keeps running.
/// `watch` (adoption.rs:356-396) then spawns a second task whose first tick probes while the old
/// call is still out. `RunningPoll::poll_once` (running.rs:336-341) guards this exact shape with
/// an `in_flight` flag; the adoption watch has no such flag.
#[tokio::test(start_paused = true)]
async fn rewatching_while_a_slow_tick_is_in_flight_never_runs_two_evaluations_at_once() {
    let (r, slow) = slow_rig(Platform::Linux, "pgrep", 1).await;
    r.script_linux_steam(&[500]);
    let lib = library();
    lib.write("480", &handoff_acf("480"));
    let args = lib.args("480", 0);
    let t0 = tokio::time::Instant::now();
    r.watch.watch(args.clone()).unwrap();

    // Tick1's slow pgrep runs [5000, 13000].
    tokio::time::sleep_until(t0 + Duration::from_millis(6_000)).await;
    assert_eq!(slow.in_flight_now(), 1, "{:?}", slow.log());

    // A cleared record followed by a new one, with no await between.
    assert!(r.watch.unwatch("480"));
    r.watch.watch(args.clone()).unwrap();

    // The in-flight assertion is decided at 11000 (the new task's first tick), before the old
    // tick ends, so it does not depend on the random select! branch choice afterwards.
    tokio::time::sleep_until(t0 + Duration::from_millis(22_000)).await;
    let log = slow.log();
    assert_eq!(
        slow.max_in_flight(),
        1,
        "two adoption evaluations ran at once: the re-watch spawned a new task while the old task's slow tick was still in flight: {log:?}"
    );
    assert_eq!(overlap_in(&log, t0), None, "{log:?}");
    assert!(r.active());
}
```

Command: `cargo test --manifest-path src-tauri/Cargo.toml -p gamelib-steampoll --test adoption -- --exact rewatching_while_a_slow_tick_is_in_flight_never_runs_two_evaluations_at_once`

Two probes were in flight, nested. After the old task's tick returns, ticks continue at 29951 and 29956 (+16000, +21000), which is a single-task cadence again.

Code refs: `adoption.rs:401-413` (`unwatch`: cancel token, `started=false`, `gen+=1`, no wait), `adoption.rs:382-389` (tick body awaited inside the select arm, not raced against `token.cancelled()`), `adoption.rs:356-396` (`watch` spawns a second task when `started` is false), `running.rs:336-341` (`poll_once` `in_flight` guard, the sibling that handles this).

Suggested todo triage for the orchestrator to file (not filed here): `severity: medium`, `platform: any`, `ready: code`. Fix shape: an `in_flight` guard on the adoption tick shared across the old and new task (as `RunningPoll`), or racing the tick body against the token so a cancelled task drops its in-flight probe.
