The truth reads: "The adoption watch never overlaps a slow tick: a slow helper or pgrep probe delays the next tick instead of running two evaluations at once (Phase 80 D-10 poll contract, applied to new background work)". The guarantee is currently structural only (`adoption.rs:379-381`), and no test drives a probe slower than one tick.

What this plan adds to `src-tauri/crates/gamelib-steampoll/tests/adoption.rs`, TEST-ONLY:
1. (Task 1) A slow fake `ProcessRunner` that wraps the rig's `ScriptedRunner`. It records an in-flight counter, the max in flight, and an ordered Start/Finish log in paused tokio time. The REAL `AdoptionWatch::watch` task runs on it. Two steady-state tests (Linux slow pgrep, macOS slow helper) assert: max in-flight 1, strictly ordered calls, the exact Delay cadence, and that the watch keeps ticking and still adopts afterwards. A negative control proves that the instrument catches a real overlap.
2. (Task 2) A re-watch race probe: unwatch the last entry, then watch again, while a slow tick is in flight. Code reading predicts this DOES run two evaluations at once, for three reasons. `unwatch` (adoption.rs:401-413) cancels the token and clears `started` without waiting. The in-flight tick body is not raced against the token inside the select arm (adoption.rs:382-389). `watch` (adoption.rs:356-396) therefore spawns a second task whose first tick probes while the old call is still out. `RunningPoll` guards this exact shape with an `in_flight` flag in `poll_once` (running.rs:336-341, 80-REVIEW). The adoption watch has no such flag. If the prediction holds, the executor STOPS and reports a real defect with the failing test. It does not fix anything and does not commit the red test.

No production code changes. No seam is needed: `Registry::new` already takes `Arc<dyn ProcessRunner>` and `Arc<dyn Clock>` (registry.rs:67-71), and the only change to existing test code is to let the rig builder accept the runner.
