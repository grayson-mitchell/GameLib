<objective>
Deliver the macOS-user-facing surface: (1) the guided bottle-setup + consent flow (D-07) that fires from EVERY Install/Play entry point when a confirmed-not-native Steam game has no bottle yet; (2) a lightweight guided-setup component that gets explicit consent for the multi-GB provisioning, kicks off `steamBottleProvision`, surfaces progress, and prompts the one-time bottled-Steam login (D-04/D-05, opaque); and (3) the D-08 game-page indicator that a game "runs via the Windows Steam bottle."

**Corrected architecture (checker BLOCKER 1 + 2):** The RESEARCH/PATTERNS claim that `InstallGameModal.ts` is "the single frontend chokepoint for every Steam install entry point" is FALSE against the current codebase — `GamePage/index.tsx::handleInstall` (line ~612), `GameCard/index.tsx::handlePlay` → `helpers/library.ts::install()`, and `MainButton.tsx` (which routes Steam to `handleInstall`, not the modal) all call `window.api.install()` DIRECTLY, bypassing `InstallGameModal.ts`. The true single point of truth is the backend: all four entry points funnel into `window.api.install`/`launch` → `SteamGame.install()`/`launch()`, which (per 17-05) already holds the platformsCaptured-aware eligibility (D-11) and emits `sendFrontendMessage('steamBottleSetupRequired', { appName })` when un-provisioned. So this plan drives the guided flow from a SINGLE global frontend listener on that backend signal — no per-entry-point patching, and no (buggy, D-11-violating) frontend eligibility check on raw `gameInfo.is_mac_native`. `InstallGameModal.ts` needs NO change (its existing steam short-circuit already calls `window.api.install`, which now funnels through the backend decision).

Per D-09 / RESEARCH.md Open Question 4, the guided setup is a consent-dialog + background-task pattern (NOT a blocking install modal — Steam owns its own installer/progress UI). Visual treatment is refinable by `/gsd-ui-phase`; keep it concrete but flag polish as open.

Purpose: Complete the D-07 consent gate + D-08 indicator so the always-on macOS flow (D-10) is real, visible, and fires from all entry points.
Output: a global setup store + listener + App mount, the SteamBottleSetup component, the AppleWikiInfo indicator row, i18n keys, and tests.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| main → renderer (steamBottleSetupRequired push) | Backend one-way signal carrying an appName; renderer only opens a dialog in response |
| renderer → main (provision IPC) | User-chosen bottle name + engine flow to the provisioning backend |
| bottled Steam login window → user | The user authenticates directly in Steam's own window; GameLib does not handle credentials (D-04) |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-17-01 | Tampering | bottle name from setup UI → provision IPC | mitigate | Backend `sanitizeBottleName` (17-02) is the authoritative guard; the setup UI passes the name through to `steamBottleProvision` which re-sanitizes — no trust placed in renderer input |
| T-17-06 | Information Disclosure | bottled Steam login | accept | D-04 — login happens in Steam's own window; GameLib only records a `loggedIn` boolean from the user completing setup, never reads credentials |
| T-17-09 | Spoofing (consent bypass) | D-07 provisioning consent | mitigate | The multi-GB provisioning only starts after explicit user confirm in SteamBottleSetup; the backend never auto-provisions — it only emits `steamBottleSetupRequired`, and provisioning is gated behind the consent surface |
| T-17-08 | Mis-routing (D-11) | eligibility decision | mitigate | Eligibility is decided solely by the backend `isBottleEligible` (platformsCaptured-aware); the frontend contains NO is_mac_native gate that could misroute a not-yet-captured game |
| T-17-SC | Tampering | npm/pip/cargo installs | accept | Zero new dependencies this phase |
</threat_model>
