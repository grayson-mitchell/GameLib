<objective>
Provision the NEW dedicated bridge bottle. Every spike ran inside the existing `GameLibSteam` bottle, which per Phase 17 already contains a full bottled Windows Steam client — this directly conflicts with R6's acceptance bar ("no Windows Steam client in the bottle"). This plan adds a distinct, shared bridge bottle (`GameLibSteamBridge`) created via the same `cxbottle --create --template win10_64` primitive `bottle.ts` already uses (D-08 CrossOver-only — GPTK/Wine-toolkit produces a broken Steam bottle), but WITHOUT the `SteamSetup.exe` download/run steps. One shared bridge bottle (not per-game) matches D-03's share-as-much-as-possible philosophy; the acceptance-set games install into their own `Program Files\<game>\` subdirs so shim placement never collides.

This is the single largest routing-shape correction the phase requires (RESEARCH Pitfall 1). It is built here as a self-contained bottle primitive so 24-08's `games.ts` integration consumes a ready interface. BLOCKER 1 (checker): `provisionBridgeBottle()` is invoked INLINE by 24-08's `installBridgeGame()` when the bridge bottle is not yet ready — that is its only caller (no frontend dialog/IPC provisions the bridge bottle; 24-09's on-demand provision covers only the D-11 Phase-17 `GameLibSteam` fallback bottle). This keeps a single, explicit owner for bridge-bottle creation.

Purpose: give bridge games a Windows-Steam-free CrossOver prefix.
Output: `provisionBridgeBottle()`, `getBridgeBottleSettings()`, `DEFAULT_BRIDGE_BOTTLE_NAME` in `bottle.ts` + tests.
</objective>
