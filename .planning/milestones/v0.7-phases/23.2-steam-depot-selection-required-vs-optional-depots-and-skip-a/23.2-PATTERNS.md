### 2. `src/backend/storeManagers/steam/depotErrors.ts` — D-01's trigger boundary already exists

```typescript
const NON_RETRYABLE_ERESULTS = new Set([8, 9, 15, 17, 40, 42, 43])

export function isNonRetryableDepotError(err: unknown): boolean {
  if (!err || typeof err !== 'object') return false
  const eresult = (err as { eresult?: unknown }).eresult
  return typeof eresult === 'number' && NON_RETRYABLE_ERESULTS.has(eresult)
}

export function classifyDepotError(err: unknown): ClassifiedDepotError {
  const text = errorText(err)

    if (eresult === 40) {

        'steam.download.error.depotBlocked',
        'This depot appears to be blocked for your account or region right now. The game may still be installable directly through the Steam client.'
      )
      return {
        key: 'steam.download.error.depotBlocked',
        message: `${base} (${text})`
      }
    }
    // ... generic depotUnavailable fallback for every other member of the set
  }
  // ...
}
```
**D-01 says only EResult 40 triggers skip-and-warn** — this `eresult === 40` check inside
`classifyDepotError` is ALREADY the exact boundary D-01 wants; **do not widen
`NON_RETRYABLE_ERESULTS`**, and do not add a new set. What must change is what happens when
EResult 40 is detected at the **key-resolution call site** (`wrapDepotKeyError`/`fetchDepotPlanEntry`
in depot.ts), not inside this classifier — `classifyDepotError` only runs on a terminal thrown

### 3. `src/backend/storeManagers/steam/depot.ts` — `wrapDepotKeyError` / `fetchDepotPlanEntry` (key-resolution failure site)

**Analog:** the function's own existing shape (lines 519-547) plus its two call sites (584, 601).

```typescript
function wrapDepotKeyError(
  err: Error,
  descriptor: DepotDescriptor,
  what: string
): Error {
  const wrapped = new Error(
    `couldn't get ${what} for depot ${descriptor.id} (app ${descriptor.ownerAppId}): ${err.message}`
  )
  const eresult = (err as Error & { eresult?: number }).eresult
  if (typeof eresult === 'number') {
    ;(wrapped as Error & { eresult?: number }).eresult = eresult
  }
  const ownershipNote =
    eresult === 40
      ? ' — GameLib selected this depot via the package-ownership gate; owning a depot does not guarantee Steam will issue its key'
      : ''
  logWarning(
    `fetchDepotPlanEntry: couldn't get ${what} for depot ${descriptor.id} (app ${descriptor.ownerAppId}): eresult=${eresult ?? 'unknown'}${ownershipNote}`,
    LogPrefix.Steam
  )
  return wrapped
}
```
Call sites (584, 601) both `reject(wrapDepotKeyError(err, descriptor, '...'))` inside a
`getDepotDecryptionKey`/`getRawManifest` callback — this is where an EResult 40 for ONE depot is
first observed, still per-depot, before the whole plan aborts. **This is the natural site to
catch-and-skip** rather than reject-and-abort the whole `fetchDepotPlanEntry` call for a
`eresult === 40` specifically (per D-01, ONLY 40; every other member of
`NON_RETRYABLE_ERESULTS` must keep aborting exactly as today — do not change this function's
reject behavior for any other eresult). The existing `ownershipNote`/`logWarning` call already
names depot id, owning appId, and eresult — reuse this exact log line's field set for any new
skip-specific log (never log the decryption key, per the file's own T-23-31 comment at :536).

`fetchDepotPlanEntry` (the caller, :563-625) currently has no catch around the `key`/`raw`
awaits — a skip-and-continue for EResult 40 means either this function or its own caller
(`buildDepotPlan`, which iterates depots and calls `fetchDepotPlanEntry` per descriptor) needs a
try/catch that, on an EResult-40-specific failure, omits that depot from the returned plan
instead of letting the rejection propagate. Locate `buildDepotPlan`'s depot-iteration loop
(depot.ts, function starts at :643) before altering call shape — CONTEXT.md's Claude's
Discretion section leaves the exact seam (selection vs. key-resolution-failure site) to the
planner, but the try/catch precedent to copy is `wrapDepotKeyError`'s existing eresult-narrowing
style: check `(err as Error & { eresult?: number }).eresult === 40` specifically, never a broader
`isNonRetryableDepotError` check at this narrower site (that set includes non-skippable codes).

### 4. `src/backend/storeManagers/steam/depot.ts` — `canWriteFullOwnership` / `finalizeToSteam` / `downloadSteamDepots` (plan reduction + D-08 fix)

**Analog:** `canWriteFullOwnership` itself — a single pure fail-closed predicate.

```typescript
export function canWriteFullOwnership(opts: {
  outcome: 'completed' | 'cancelled'
  failures: DepotDownloadFailure[]
  buildid?: string
  allFilesVerified: boolean
  allModesApplied: boolean
}): boolean {
  return (
    opts.outcome === 'completed' &&
    opts.failures.length === 0 &&
    !!opts.buildid &&
    opts.buildid !== '0' &&
    opts.allFilesVerified === true &&
    opts.allModesApplied === true
  )
}
```
D-04 is explicit: **every input here stays as-is** — a skip does not add a new bypass parameter
to this function. Per D-03, the reduction must happen **upstream** — the "plan" (the set of
depots `downloadSteamDepots` attempts) is reduced BEFORE `allFilesVerified`/`allModesApplied`/
`failures` are computed over it, so `canWriteFullOwnership` sees a plan that already excludes the
skipped depot and is unaware skipping ever happened. This mirrors the file's own header comment
discipline (:976-987): "This is the ONLY place this decision is made... rather than inlining the
check". Do not touch `canWriteFullOwnership`'s signature or body.

**`finalizeToSteam`** (lines 2468-2523) is the manifest-write call site — its `opts.depots` field
(`FinalizeDepotEntry[]`) already flows straight into `writeAppManifest`'s `installedDepots`

`sizeOnDisk` (line 2479, `measureInstalledBytes(installRoot)`) is a **real recursive directory

observation (the stub's `SizeOnDisk` equaled the selected-minus-blocked sum): that number came

for free, because it measures reality, not the plan. Confirm this assumption holds for the
skip-and-warn case too (a skip's install has genuinely fewer bytes on disk than an unreduced
plan would, and this function will measure that correctly with zero changes).

**`downloadSteamDepots`'s catch path — this IS the D-08 defect** (lines 2706-2855, catch block
2832-2855):
```typescript
const attempted: FinalizeDepotEntry[] = []
// ...
const finalize = (): Promise<void> => {
  const cancelled =
    lastResult?.outcome === 'cancelled' || opts.signal?.aborted === true

    installdir: opts.installdir,

    failures: lastResult?.failures,
    allFilesVerified: lastResult?.allFilesVerifiedThisRun,
    allModesApplied: lastResult?.allModesApplied
  })
}

try {
  const plan = await buildDepotPlan(appId, opts)   // <- can throw BEFORE any bytes download
  displayName = plan.name
  buildid = plan.buildid
  for (const d of plan.depots) { attempted.push(...) }   // <- never runs if buildDepotPlan throws
  // ... download, then finalize()
} catch (err) {
  // Any thrown failure — plan-build error, content-server resolution
  // failure, anything — still funnels through the SAME finalize path
  // (Pattern 5): write whatever landed, never rethrow.
  await finalize().catch((finalizeErr) => { logWarning([...], LogPrefix.Steam) })
  if (opts.signal?.aborted) { return { status: 'cancelled' } }
  return { status: 'error', error: classifyDepotError(err).message }

```
This confirms CONTEXT.md's D-08 exactly: when `buildDepotPlan(appId, opts)` throws (a plan-build
failure — network, PICS, or now a not-yet-skipped EResult 40 rethrown from `fetchDepotPlanEntry`),
`attempted` is still `[]` (the `for (const d of plan.depots)` loop never executed) and
`buildid` is still `undefined` — the catch block's `finalize()` call unconditionally writes a
manifest with `depots: []` (→ empty `InstalledDepots`) and no `buildid` (→ `"0"` per
manifest.ts's own default at :149), **clobbering whatever `.acf` was already on disk** —
regardless of whether that prior `.acf` described a complete, working install. The header
comment's own words at :2833-2835 ("still funnels through the SAME finalize path... write
whatever landed, never rethrow") is the exact place the D-08 fix must change: this path must
distinguish "genuinely nothing has changed since the last good manifest, so don't touch it" from
the legitimate 1026 verify-handoff cases `finalize()` correctly serves elsewhere (partial
downloads, cancels — sub-item 3's "do not regress the Phase 21 1026 verify-handoff, which
legitimately writes 1026 on paths that did download"). The natural signal to gate on: this catch
branch is reached via a THROW from `buildDepotPlan` itself — i.e., zero bytes were ever staged
for THIS run (`attempted.length === 0` AND no prior successful `downloadDepotFiles` call this
run) — versus the legitimate 1026 paths, which are reached via the NORMAL `finalize()` call at
line 2816 after `downloadDepotFiles` actually ran (even if it produced failures/cancellation).
Planner should design the distinguishing check around "did `buildDepotPlan` itself throw" (this
catch block) vs. "did a download attempt run and produce a result" (the main path's `finalize()`
at 2816) — these are already two different call sites in the source, not one shared branch that
needs new state threaded through it.

**Test analog for this exact code path:** `depot.finalize.test.ts`'s "REPRODUCTION" test (below)
