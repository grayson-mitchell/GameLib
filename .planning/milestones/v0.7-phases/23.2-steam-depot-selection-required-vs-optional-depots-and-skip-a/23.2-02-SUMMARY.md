# Phase 23.2 Plan 02: Close D-08 — gate the catch-path manifest write behind shouldFinalizeAfterThrow Summary

**A native install that fails before any depot download is attempted now leaves an existing `appmanifest_*.acf` byte-identical, closing a live data-destruction defect where a zero-byte plan-build failure could clobber a complete 90 GB install's manifest with a `StateFlags 1026`/`buildid 0`/empty-`InstalledDepots` stub — while the legitimate Phase 21 `1026` verify-handoff (a download that was genuinely attempted and then failed/cancelled) is untouched and now positively pinned.**

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 - Blocking issue] `depot.finalize.test.ts`'s `backend/utils` mock was missing `sendProgressUpdate`, causing an uncaught `TypeError` on every `emitProgress` heartbeat tick and a V8 heap OOM on any full-file run exceeding ~100s**
- **Found during:** Task 1, while establishing a clean baseline to verify the new RED cases in isolation.
- **Issue:** The file's `jest.mock('backend/utils', ...)` factory defined only `{ getFileSize: jest.fn() }`. `depot.ts`'s `emitProgress` heartbeat (`depot.ts:2208`, a `setInterval`) calls `sendProgressUpdate(...)` every tick; with it `undefined`, every tick threw `TypeError: (0 , utils_1.sendProgressUpdate) is not a function`, uncaught, for the remainder of any long-running test — accumulating heap until the process OOM'd (`FATAL ERROR: Ineffective mark-compacts near heap limit`). Confirmed via `git show HEAD~1:<path>` + a scratchpad `cp` swap (never `git stash`/`git checkout`) that this reproduced on the completely unmodified, pre-Task-1 file — a pre-existing bug, not something this plan introduced.
- **Fix:** Added `sendProgressUpdate: jest.fn()` to the mock, citing `depot.test.ts`'s own equivalent mock (which already includes it) as established precedent.
- **Files modified:** `src/backend/storeManagers/steam/__tests__/depot.finalize.test.ts`
- **Commit:** `93c8c3b77` (folded into the Task 1 RED commit, since it was required to obtain a trustworthy RED/GREEN signal for that same file)

**2. [Rule 1 - Bug in newly-authored test] A first draft of Task 3's Case-B pin test used `fetchChunk.mockRejectedValue(...)`, which drove `depot.ts`'s real host-rotation/stall-recovery retry loop into an unbounded loop against an always-rejecting mock and OOM'd the process**
- **Found during:** Task 3, verifying the new Case-B pin test in isolation before running the full suite.
- **Issue:** Unlike the existing SHA1-mismatch pattern (where `fetchChunk` *resolves* with wrong bytes), a mock that always *rejects* triggers depot.ts's genuine retry/host-rotation logic, which has no bound against a mock that never succeeds — the test hung and eventually OOM'd (`FATAL ERROR: Ineffective mark-compacts near heap limit`), reproducing the identical failure mode diagnosed in item 1.
- **Fix:** Rewrote the test to use the already-proven-safe pattern (SHA1-mismatch via a resolving `fetchChunk` returning wrong bytes), which still genuinely exercises Case B (`downloadAttempted` true, plan built, download attempted, then failed) without touching the unbounded retry path. Documented the reasoning in a code comment so a future reader does not "simplify" it back to a rejecting mock.
- **Files modified:** `src/backend/storeManagers/steam/__tests__/depot.test.ts`
- **Commit:** `13046609f`
