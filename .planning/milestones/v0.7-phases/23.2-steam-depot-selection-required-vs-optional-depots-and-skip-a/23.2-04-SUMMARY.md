# Phase 23.2 Plan 04: Depot-Skip Completion Notice Summary

**Steam installs that skip a depot (EResult 40, key refused) now fire a second, additive completion notice naming the skipped depot id, via a new `steam.download.notify.depotSkipped` i18n key and a dedicated fire-once guard on the install poller.**

## Accomplishments

- Registered `steam.download.notify.depotSkipped` in `translation.json` with `{{depots}}` interpolation, leaving the pre-existing `steam.download.error.depotBlocked` key byte-identical and documented as the residual all-blocked terminal path in `depotErrors.ts`.

## Decisions Made

- Kept the interpolation variable name `depots` (never `count`) — enforced twice: a catalog census assertion and a runtime assertion on the captured `i18next.t` options object.
- Used a dedicated `notifiedDepotSkipped` flag rather than reusing `notifiedWaiting`, specifically to avoid the two notices becoming mutually exclusive on the native-handoff-with-skipped-depot path.
- Left `steam.download.error.depotBlocked` untouched rather than repurposing it, since it remains reachable as the residual all-skipped abort path from 23.2-03's skip-and-warn policy.

## RED-Proof Evidence (shared-guard trap, per plan's explicit requirement)

Procedure: temporarily replaced both occurrences of `notifiedDepotSkipped` with `notifiedWaiting` in `library.ts`'s confirmed-installed skip-notice branch (the guard read `!poll.notifiedWaiting` and the write set `poll.notifiedWaiting = true`, mirroring what a careless reuse of the existing flag would look like), then ran only the coexistence test.

Observed failure:
```
● pollInstallOnce() › 23.2-04: fires all THREE notices in one confirmed-installed tick (finished, skipped, restart Steam) — this is the regression guard for the shared-guard trap

  expect(jest.fn()).toHaveBeenCalledTimes(expected)

  Expected number of calls: 3
  Received number of calls: 2
```

Root cause of the observed failure: the skip notice's guard-write (`poll.notifiedWaiting = true`) ran first and pre-empted the Restart-Steam notice's own `!poll.notifiedWaiting` read later in the same tick — collapsing what should be two independent notices into one. This is exactly the failure mode `notifiedDepotSkipped` (a genuinely separate flag) exists to prevent.

The substitution was fully reverted immediately after capturing this output; `git diff` against `library.ts` showed zero difference from the committed Task 2 state before Task 3 was committed.

## Issues Encountered

- `src/backend/jest.config.js` sets `resetMocks: true`, which strips `jest.fn()` implementations (not just call history) before every test. Converting the i18next mock from a plain function to `jest.fn()` (needed to inspect interpolation call args) initially broke 6 pre-existing tests elsewhere in `library.test.ts` whose `notify()` body assertions depend on the fallback-string return value. Fixed with a file-level `beforeEach` (outside all `describe` blocks) re-establishing `(i18next.t as jest.Mock).mockImplementation(...)`. Verified all 204 pre-existing tests passed with this infra change alone, before any new test case was added, per the plan's explicit ordering requirement.
