<objective>
Build the runtime mechanism that makes `lzma-native`'s native binding loadable inside
a compiled SEA sidecar: a CommonJS-callable shim that replaces `node-gyp-build` at
esbuild time, resolving the addon from the SEA asset plan 23.1-02 embedded and
`process.dlopen()`ing it — with an unchanged direct-from-`node_modules` path for
dev/Electron/jest.

Purpose: `lzma-native`'s JS wrapper calls `require('node-gyp-build')(__dirname)`,
which computes a `prebuilds/<platform>-<arch>/*.node` path at runtime. esbuild cannot
resolve a computed specifier and cannot bundle a `.node` binary at all (RESEARCH.md
Pitfall 4). Aliasing `node-gyp-build` to this shim is the same mechanism class as this
repo's existing `--alias:electron=./src/backend/sidecar/electronStub.ts` fix — a
build-time specifier rewrite, NOT the `pnpm.patchedDependencies` computed-require
rewrite used for `patches/lzma.patch`, which RESEARCH.md Pitfall 4 explicitly rules
out for a native addon.

Output: `lzmaNativeBinding.ts`, its unit tests, and the shared esbuild alias flag.
This plan does NOT import or call `lzma-native` anywhere — plan 23.1-04 owns that.

This plan ASSUMES 23.1-01's spike returned verdict `VALIDATED` with go/no-go
`proceed`, and that 23.1-02-SUMMARY records the `LZMA_NATIVE_ASSET_KEY` literal and
the observed on-disk prebuild `.node` filename. If the spike verdict is `REFUTED` or
`UNDECIDABLE`, STOP — this plan's entire mechanism is the thing that was refuted.

Runs in parallel with plan 23.1-04 (disjoint file sets).

        '--bundle',
        '--platform=node',
        '--target=node22',
        '--format=cjs',

Its three consumers (all get the new flag automatically):
  - meta/buildSidecarSea.ts  buildEsbuildArgv()        -> the SEA main sidecar bundle
  - meta/buildSidecarSea.ts  buildWorkerEsbuildArgv()  -> the SEA decompress-worker bundle
  - meta/buildDecompressWorkerDev.ts                   -> the dev/Electron worker bundle

The mechanism validated by spike 023 (.planning/spikes/023-sea-native-addon-dlopen/binding-shim.cjs):
  module.exports = function resolveNativeBinding(dir) { ... }   // directly callable CJS export
  SEA branch : require('node:sea').getRawAsset(<asset key>) -> fs.writeFileSync(tmp, Buffer.from(raw))
               -> const m = { exports: {} }; process.dlopen(m, tmp); return m.exports
  dev branch : process.dlopen(m, join(<lzma-native root>, 'prebuilds', `${process.platform}-${process.arch}`, <addon filename>))
  guard      : throw by name if `dir` does not belong to lzma-native
  note       : getRawAsset() returns the RAW backing buffer, not a copy -- never write into it

The official Node.js pattern (nodejs.org/api/single-executable-applications.html), for reference:
  fs.writeFileSync(addonPath, new Uint8Array(getRawAsset('myaddon.node')))
  const myaddon = { exports: {} }; process.dlopen(myaddon, addonPath); fs.rmSync(addonPath)

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| SEA blob -> OS temp directory | `getRawAsset()` bytes are written to a file in the world-writable `os.tmpdir()` and then loaded as executable code via `process.dlopen()` |
| bundled third-party code -> the aliased shim | `--alias:node-gyp-build` is global to each bundle, so any bundled package reaching `node-gyp-build` lands in this project's shim |
| liblzma native code -> sidecar process | Once `dlopen()`ed, the addon runs in-process with full sidecar privileges |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-23.1-03-01 | Elevation of Privilege | `nativeAddonTempPath()` + `process.dlopen()` | mitigate | The temp filename embeds `process.pid` AND 8 random bytes from `node:crypto.randomBytes`, and the file is written with mode `0o600`, so a local attacker cannot pre-place or swap a hostile `.node` at a path the sidecar will `dlopen()`. This is the production hardening plan 23.1-01's register explicitly deferred to this plan; the Node docs' fixed `myaddon.node` example is deliberately not copied. An acceptance criterion asserts two calls produce different paths |
| T-23.1-03-02 | Spoofing | the global `--alias:node-gyp-build` rewrite | mitigate | `resolveNativeBinding()`'s first action is an identity guard that throws by name when `dir` is not an `lzma-native` package directory, so a future bundled dependency that also uses `node-gyp-build` fails loudly at startup instead of silently receiving lzma-native's binding (or lzma-native receiving its). Verified today: no other installed package declares `node-gyp-build` as a dependency, so the guard is a forward-looking regression trap, not a live conflict |
| T-23.1-03-03 | Denial of Service | unbounded recursion via the aliased specifier | mitigate | The dev branch `process.dlopen()`s the computed prebuild path directly and never delegates to the real `node-gyp-build` module, which the alias would rewrite straight back into this shim. An acceptance criterion greps the non-comment source for `require('node-gyp-build')` and requires zero hits |
| T-23.1-03-04 | Tampering | `getRawAsset()`'s returned buffer | mitigate | The buffer is the raw backing store of the SEA blob, not a copy (Node docs warning, restated in RESEARCH.md). The shim only reads it through `Buffer.from(...)` and never writes into it, so it cannot corrupt other assets sharing the blob |
| T-23.1-03-05 | Tampering | native code executing in-process | accept | Inherited verbatim from plan 23.1-01's T-23.1-01-03: liblzma is a mature, widely-audited C library, and this project already accepted the identical class of risk by shipping `zstddec`'s WASM decoder and by trusting pure-JS `lzma` today. RESEARCH.md's Security Domain section explicitly declines further sandboxing. `decodeChunk()`'s existing sha1/size gate continues to reject wrong output |
</threat_model>
