# Phase 23.1 Context: Native LZMA depot decode via node-liblzma

## Why this phase exists

Debug session `.planning/debug/humankind-depot-full-stall.md` (still open, status `investigating`)
traced Steam native depot install throughput through several already-fixed bottlenecks:

- Phase 25 — multi-host fan-out (fixed)
- quick `260817-ihr` — in-flight limiter + demoted-host probe interval (fixed)
- quick `260817-pkx` — decode worker pool wasn't spawning at all on the SEA-packaged sidecar
  binary (companion-file `decompressWorker.js` never shipped); fixed by embedding it as a Node
  SEA asset instead of a `__dirname`-relative lookup

After all of those, live-hardware measurement (HUMANKIND appId 1124300, Age of Wonders:
Planetfall appId 718850) confirmed:

- Network fetch is fast and flat (~150-280ms/chunk) — NOT the bottleneck.
- Decode IS the bottleneck, running on the pure-JS `lzma` npm package (~5MB/s per thread).
- Decode is already maximally parallelized: a live A/B test this session
  (`GAMELIB_DECOMPRESS_POOL_SIZE=4` vs the default 10, on a confirmed 4P+6E Apple Silicon
  machine) showed capping workers to the P-core count made throughput ~2.37x WORSE, not
  better — confirming more workers helps up to the real core count and there's no more
  parallelism to extract that way. The pool default (`min(os.cpus().length, 16)`) is correct
  as-is; no worker-pool sizing work belongs in this phase.

- **`node-liblzma`** (npm, `github.com/oorabona/node-liblzma`) is the recommended candidate:
  actively maintained (v5.1.1, repo pushed same day as the research), ships prebuilt native
  binaries for `darwin-arm64`, `linux-x64`, `win32-x64` (the platforms that matter for this
  project's Node SEA sidecar build), and has a WASM fallback in the same API surface if native
  packaging proves too risky.
- The older, more commonly-referenced `lzma-native` (what `node-steam-user`'s own wiki
  recommends) is STALE — last published 2022-01-18, ~4.5 years ago at time of writing. Treat as
  a fallback option only, not the default choice, given native-addon prebuilds are tied to
  specific Node ABI versions.
- Rough magnitude: native LZMA decode benchmarks (lzbench, corroborated independently) run
  roughly **15-20x** this project's own measured pure-JS baseline (~88-107 MB/s vs ~5MB/s).
  WASM would likely land at roughly half-to-a-fifth of native — still a plausible 5-10x if
  native packaging doesn't pan out.
- No one has yet benchmarked `node-liblzma` against a real captured Steam depot LZMA chunk on
  this project's actual target hardware — the generic lzbench numbers are a strong prior, not a
  confirmed multiplier for this specific workload.

## Primary technical risk: Node SEA packaging, not the LZMA library itself

This project ships its backend logic as a Node SEA (Single Executable Application) binary
(`meta/buildSidecarSea.ts` → `src-tauri/binaries/gamelib-sidecar-<platform-triple>`, launched by
the Tauri shell). Native `.node` addons do NOT embed into a SEA blob the way JS does — Node's
own docs describe bundling them as SEA assets, extracting to a temp file at runtime, and loading
via `process.dlopen()` instead of `require()`.

This exact area of the codebase
(`src/backend/storeManagers/steam/depot/decompressPool.ts`,
`src/backend/storeManagers/steam/depot/decompressWorker.ts`, `meta/buildSidecarSea.ts`) has
already produced THREE separate SEA-packaging defects this debug arc:
1. Worker path resolution via `__dirname` never finding `decompressWorker.js` in the SEA binary
   (fixed by 260817-pkx's SEA-asset embedding).
2. A dev-mode-only variant: `worker_threads.Worker`'s isolated module registry never received
   `installElectronHook.ts`'s `Module._load` patch, crashing on `app.getPath` inside the worker.
3. (See debug file history for the full genealogy — multiple rounds of "looks correct on paper,
   wrong once measured on live hardware.")

**Treat SEA packaging as the primary planning risk for this phase**, not the LZMA library
integration itself, which is comparatively mechanical. Cross-platform (macOS/Windows/Linux) SEA
binary story needs explicit verification, not just macOS (the only platform this debug session
tested on).

## Recommended first step (not yet executed)

Spike `node-liblzma` standalone against a real captured Steam depot LZMA chunk on actual target
hardware, to confirm the throughput multiplier holds on real depot data (not just generic
lzbench corpora) BEFORE committing to the SEA-packaging integration work. Consider making this
Wave 1 / an explicit spike task in the eventual plan.

## Explicitly out of scope for this phase

- Valve's own zstd depot-chunk migration. GameLib already handles zstd chunks correctly via the
  existing WASM `zstddec` npm package (see `decompress.ts`'s `VS`/`VSZa` branch, added to fix a
  decode crash, not for speed) — that path is not the bottleneck and needs no work here. Zstd
  and LZMA are not competing choices for us: Valve decides the per-chunk compression format, we
  just decode whatever we're sent.
- Further worker-pool sizing / P-core-vs-E-core tuning — already investigated and closed this
  session (see the debug file's resolved blind_spots item 1). Current default sizing is
  confirmed correct.
