<objective>
Prove or refute this phase's single highest-priority unknown BEFORE any production
code is touched: can a native `.node` addon, embedded as a Node SEA asset, be
extracted with `sea.getRawAsset()` and loaded with `process.dlopen()` from inside a
worker spawned via `new Worker(source, { eval: true })` in a REAL compiled SEA
binary — which is exactly the shape `DecompressPool` uses in the packaged sidecar,
and a three-way combination (SEA x worker_threads x native addon) that neither this
codebase nor Node's own SEA documentation has ever exercised.

Secondary: measure the native-vs-pure-JS decode multiplier against REAL-entropy
Steam-format VZ chunk bytes on this machine (RESEARCH.md's ~47x number came from a
synthetic text+random payload and is an assumption, A3, not a measurement).

Purpose: RESEARCH.md Assumption A1 is rated HIGH risk — if `dlopen()` from an eval'd
worker fails, the entire native-addon approach must be redesigned (main-thread-only
decode, or a different packaging strategy). Discovering that AFTER integrating
`decompressWorker.ts` + `buildSidecarSea.ts` would burn the whole phase. This exact
code area has already produced THREE separate SEA-packaging defects this debug arc
(CONTEXT.md), every one of which "looked correct on paper, wrong once measured".

Output: A spike directory with a reproducible harness, a `run.log`, and a README
carrying an explicit verdict. NO production file is modified by this plan. The
package is installed ONLY inside the spike directory — `package.json` at the repo
root is NOT touched here (RESEARCH.md: "do not add to package.json before that").

Note on plan shape: this plan carries two checkpoints (a mandatory pre-install
package-legitimacy gate and a go/no-go decision gate). That is deliberate for a
spike — the two implementation tasks are shell/harness work, not production code,
and the plan's whole value is the gated verdict.
</objective>

    The mechanism under test (this is the candidate production design plans 23.1-03/04 will
    implement, so the spike must test THIS design, not a simplified stand-in): `lzma-native`'s
    JS wrapper resolves its native binding by calling `require('node-gyp-build')(__dirname)`,
    which computes a `prebuilds/<platform>-<arch>/*.node` path at runtime. esbuild cannot
    resolve a computed specifier and cannot bundle a `.node` binary at all (RESEARCH.md
    Pitfall 4). The candidate fix is to esbuild-bundle `lzma-native`'s JS wrapper normally
    while ALIASING `node-gyp-build` to a shim — the same mechanism class as this repo's
    existing `--alias:electron=./src/backend/sidecar/electronStub.ts` fix — where the shim
    returns the binding it obtained itself. Explicitly do NOT extend `patches/lzma.patch`'s
    `pnpm.patchedDependencies` computed-require rewrite to this package: RESEARCH.md Pitfall 4
    states that is the wrong mechanism class here, because a native addon must physically
    exist on disk to be `dlopen()`'d and cannot be inlined as JS text.

    (a) `binding-shim.cjs` — CommonJS, `module.exports = function resolveNativeBinding(dir)`.
    It must be a directly callable CJS export (lzma-native calls the module itself as a
    function, so an ES `export default` transpiled to `{ default: fn }` would NOT work — this
    is why the file is authored as `.cjs`). Behavior:
      - Guard: if `dir` does not end with `lzma-native`, throw a loud, named error. The alias
