# Phase 23.1 Plan 04: Native-First LZMA Decode Via a Shared Loader Summary

**Steam VZ depot chunks now decode through `lzma-native`'s native liblzma binding by default (via a single, smoke-tested, module-scope-memoized `lzmaLoader.ts` shared by both the pooled `worker_threads` decode path and `DecompressPool`'s main-thread inline fallback), degrading to the existing pure-JS `lzma` package — loudly, exactly once, never failing an install — whenever the native path can't be trusted.**

## Performance

- **Duration:** ~45 min active tool-driven execution
- **Tasks:** 2 (both `auto tdd="true"`, each RED → GREEN)
- **Files modified:** 7 (3 created, 4 modified)

## Accomplishments

- `lzmaLoader.ts`: `loadLzmaModule()` resolves `lzma-native`'s `createStream('aloneDecoder')`, adapted behind the exact `LzmaModule.decompress(input, callback)` shape `decompressChunk()`'s VZ branch already called — zero edits needed at that call site
- The adapter is smoke-tested against a known-good `lzma_alone` fixture (precomputed offline, hardcoded at module scope) before being trusted — catches a native module that imports fine but can't actually decode (RESEARCH.md's Pitfall 1 failure class), not just an import failure
- Verified empirically (not just by the smoke test) that `lzma-native`'s real decoder byte-identically matches the pure-JS `lzma` package's output on a real VZ-container fixture, and that it genuinely emits an `'error'` event (not a hang, not a silent empty resolve) on a garbage payload — both directly exercised by new tests against the REAL native module, not a mock
- `decompressWorker.ts`'s `getLzma()` and `decompressPool.ts`'s `inlineDecode()` both now delegate to the same `loadLzmaModule()` — the two consumers can no longer diverge on which decoder is actually engaged (this plan's own must_haves.truths)
- The worker resolves its decoder EAGERLY at spawn (before the `ready` handshake) so a native-load problem surfaces at pool init, not mid-download; a slow (pure-JS) worker still sends `ready` — `loadLzmaModule()` never rejects, so a worker is never mistaken for a failed spawn
- `DecompressPool.stats()` gained `nativeWorkers` (a `Set<Worker>`-backed count, never a bare counter — see key-decisions) alongside the five pre-existing fields
- `decompress.ts`'s only change is a doc-comment rewrite on `LzmaModule` — confirmed via the plan's own diff-gate command that every changed line in that file is a comment line
- Full suite: 288/289 test suites green (6087/6088 tests) — the one failing suite (`depot.finalize.test.ts`) OOMs even in complete isolation with an explicit 4GB heap and shares zero imports with any file this plan touches; logged as a pre-existing, out-of-scope defect (`.planning/phases/23.1-native-lzma-depot-decode-via-node-liblzma/deferred-items.md`)

## stats() shape

`DecompressPool.stats()` now returns:
```ts
{
  size: number
  busy: number
  idle: number
  queued: number
  inlineFallback: boolean
  nativeWorkers: number   // NEW this plan
}
```
`nativeWorkers` counts live workers whose `ready` handshake reported `lzmaKind: 'native'`, backed by a `Set<Worker>` (see key-decisions for why a bare counter was rejected). Purely observational — never read by any dispatch/queue/replace logic, same discipline as the five pre-existing fields.

## Pre-existing tests touched, and why

None of this plan's changes required editing any PRE-EXISTING test's assertions — every existing `decompressPool.test.ts` test (decodeChunk, handleDecodeMessage, DecompressPool round-trip/concurrency/throw/timeout/fallback, the env-override block, resolveWorkerSpec) passed unmodified both before and after this plan's implementation commits. Only additions were made: 2 new describe blocks (`lzmaLoader`, `stats().nativeWorkers`) and 1 new test inside the pre-existing `decompressWorker handleDecodeMessage` block (a VZ round-trip case, since the existing block only covered PK/bogus-container cases).

## Decisions Made

See `key-decisions` in frontmatter. Most consequential: `stats().nativeWorkers` is `Set<Worker>`-backed rather than the plan's literal "bare `nativeWorkerCount` field" wording, because a bare increment/decrement counter cannot safely decrement in `removeWorker()` without per-worker tracking of whether that specific worker was ever counted as native — the Set gives that correctness for free via a safe no-op `delete()`, while still exposing the exact field name and shape (`nativeWorkers: number`) the plan's acceptance criteria require.
