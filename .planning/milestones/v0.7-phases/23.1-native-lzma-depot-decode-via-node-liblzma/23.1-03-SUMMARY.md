# Phase 23.1 Plan 03: SEA-Aware `node-gyp-build` Binding Shim Summary

**`lzmaNativeBinding.ts` is a real, unit-tested, dependency-free CJS shim that resolves `lzma-native`'s native binding from a SEA-embedded asset (`getRawAsset()` + `process.dlopen()`) or from `node_modules/lzma-native/prebuilds/` in dev, aliased in at esbuild bundle time (`--alias:node-gyp-build`) across all three sidecar/worker bundles — the single unproven mechanism this phase rests on is now real production code, ported from spike 023's VALIDATED reference implementation with one load-bearing TypeScript-syntax correction the spike never had to make.**

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] The plan's literal `export = resolveNativeBinding` syntax does not compile under this repo's actual tsconfig.json**
- **Found during:** Task 1, before writing any implementation code
- **Issue:** Verified via a direct `tsc` probe (isolated scratch file, exact project compiler flags) that `export = fn` throws `TS1203: Export assignment cannot be used when targeting ECMAScript modules` under `"module": "esnext"` — this repo's real setting (`tsc --noEmit` is `pnpm codecheck`'s entire implementation, per `package.json`). The plan's action text also separately specified `export const` for three named values alongside `export = fn` for the function, which is independently invalid TypeScript (`export =` cannot coexist with other `export` statements, TS1231) — so the plan's literal design would not have compiled regardless of the module-target issue.
- **Fix:** Used a bare `module.exports = resolveNativeBinding` assignment with NO ECMAScript `export` keyword anywhere in the file (only plain `import` statements for Node builtins), and attached the named values as properties on the exported function object (`lzmaNativeBinding.LZMA_NATIVE_SEA_ASSET_KEY = ...`, etc.) via a typed interface + cast. Verified empirically (scratch esbuild probes, both before and after writing the real file) that: (a) this shape type-checks cleanly under the project's exact tsconfig flags; (b) it is the ONLY shape, among several tried, that survives esbuild's `--alias` bundling as a directly-callable `module.exports` value — any file with even one ES `export` keyword gets ESM-interop-wrapped by esbuild into `{ default: fn, __esModule: true }`, reproducing exactly the "not a function" crash the plan's own action text warns about.
- **Files modified:** `src/backend/storeManagers/steam/depot/lzmaNativeBinding.ts`, `src/backend/storeManagers/steam/__tests__/lzmaNativeBinding.test.ts` (reaches the shim via guarded `require()` + cast instead of an ES `import`, since an `import` from an export-less module fails with "has no default export")
- **Verification:** `pnpm codecheck` exits 0; 10/10 unit tests pass; the acceptance-criteria greps for `export = ` no longer apply (0 hits) but the functionally-equivalent `module.exports = ` shape was verified instead (1 hit, `grep -c "^module.exports = "`), and the deeper intent — "compiled CJS output is `module.exports = fn`-shaped, not `{ default: fn }`" — was proven directly via an isolated esbuild bundle-and-run probe.
- **Committed in:** `cddf260d1` (Task 1 GREEN commit)

**2. [Rule 1 - Bug] The identity guard's thrown error message contained the literal substring "node-gyp-build", which would have permanently broken this plan's own "no unresolved node-gyp-build string survives the bundle" acceptance criterion**
- **Found during:** Task 2, while verifying the alias mechanism via an isolated esbuild probe (built using the exact production flag set, since the real `decompressWorker-sea-bundle.js` does not yet reference `lzma-native` at all — see the "Known Gap" note below)

## Issues Encountered

**Known gap (expected, not a defect): the real compiled bundle does not yet contain `lzma_native.node`.** A real `pnpm build:sidecar-sea` run today produces `build/main/decompressWorker-sea-bundle.js` with ZERO occurrences of `lzma_native.node` — because nothing in the current `decompressWorker.ts`/`decompress.ts` import graph calls `require('lzma-native')` yet; this plan's own objective text explicitly scopes that out ("This plan does NOT import or call `lzma-native` anywhere — plan 23.1-04 owns that"). Since `--alias` is a resolve-time substitution that only activates for specifiers actually reached by the bundled code, the alias flag being present in the esbuild invocation is necessary but not sufficient for the literal string to appear in output — only an actual `require('lzma-native')` call site (routing through `lzma-native`'s own internal `require('node-gyp-build')(__dirname)`) will do that. This plan's Task 2 acceptance criteria (and `<verify>` block) literally require that grep to pass against the real bundle, which is not achievable at this point in the phase sequence without violating this plan's own scope boundary. Resolved by instead proving the alias MECHANISM correct via an isolated esbuild probe (see Deviations #2) using the exact production flag set, and documenting this gap explicitly so plan 23.1-04/05 do not mistake it for a regression — the real `lzma_native.node` bundle-presence check becomes meaningful, and should be re-run, the moment 23.1-04 lands its `require('lzma-native')` call site.
