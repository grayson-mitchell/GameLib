# Phase 08.1: Code Review Report

**Reviewed:** 2026-07-04T11:37:21Z
**Depth:** standard
**Files Reviewed:** 12
**Status:** issues_found

## Summary

Reviewed the Steam-backend `is_delisted` guard, the tri-state `FilterMode` migration and
union filter logic, the delisted GameCard treatment, and the "only"-mode empty-state
messaging. No security-critical defects (the appId chokepoints for `steam://` URLs and the
public store API are correctly guarded in the paths that matter most). However, four
robustness/correctness defects merit fixing before ship:

1. The `migrateFilterMode` fallback silently **discards** a user's previously-enabled
   filter (legacy `'true'` maps to the default `'off'` instead of `'show'`).
2. A delisted game that was **never enriched with artwork** re-triggers a Steam store API
   fetch (and a `pushGameToLibrary` broadcast) on *every* `getGameInfo` — the exact
   re-fetch loop the design comments claim to prevent.
3. `fetchMetadataIfNeeded` builds a network + CDN URL from `this.appId` **without** the
   `/^\d+$/` guard applied at every sibling chokepoint.
4. `isNonAvailable` does an unguarded `JSON.parse` of localStorage inside a per-game filter
   callback — a corrupt value throws and takes down the whole library render.

## Warnings

### WR-01: Filter migration silently resets a previously-enabled filter to "off"

**File:** `src/frontend/screens/Library/index.tsx:142-146`
**Issue:** The migration comment claims it "maps legacy 'true'/'false'/null to FilterMode",
but legacy `'true'` (the value written by the *old boolean* `handleShowHidden` /
`handleShowNonAvailable` via `JSON.stringify(true)`) is not in `['show','only','off']`, so
it falls through to `defaultValue` = `'off'`. A user who had **Show Hidden** or **Show
non-Available games** turned ON before upgrading will find it silently turned OFF after
migration — a preference data-loss, not a benign default. `'false'` → `'off'` is correct;
only the ON case is mishandled.

```ts
const migrateFilterMode = (key: string, defaultValue: FilterMode): FilterMode => {
  const stored = storage.getItem(key)
  if (stored === 'show' || stored === 'only' || stored === 'off') return stored
  // Preserve the legacy boolean "on" state instead of dropping it to default
  if (stored === 'true') return 'show'
  if (stored === 'false') return 'off'
  return defaultValue // null / undefined / garbage
}
```

### WR-02: Delisted game with no cached artwork re-fetches on every `getGameInfo` (re-fetch loop)

**File:** `src/backend/storeManagers/steam/games.ts:163-168` (guard) and `195-208` (delisted branch)
**Issue:** The self-heal guard is `if (!existing.art_cover || platformsNeverCaptured)`. The
`platformsNeverCaptured` term is correctly gated on `!is_delisted` to avoid a loop, but the
`!existing.art_cover` term is **not**. The delisted branch writes `is_delisted: true` via
`{ ...current, is_delisted: true }` and never populates `art_cover`, so a game that returns
`success:false` on its *first-ever* fetch stays delisted **and** art-less. Every subsequent
`getGameInfo` sees `!existing.art_cover === true` and fires another Steam store API request
(`success:false` again) plus another `sendFrontendMessage('pushGameToLibrary', …)`. The
`pendingFetches` set only dedups *concurrent* calls, not sequential ones, so this repeats on
every access — risking Steam rate-limiting (a documented concern in CLAUDE.md) and IPC spam.
The existing test only covers a delisted game that *already has* `art_cover`, so this gap is
untested.
**Fix:** Also exclude delisted games from the art-based trigger, mirroring the platform
guard:

```ts
const cached = steamMetadataStore.get(this.appId)
const platformsNeverCaptured =
  !existing.is_delisted && cached?.platformsCaptured !== true
const artNeverFetched = !existing.is_delisted && !existing.art_cover
if (artNeverFetched || platformsNeverCaptured) {
  void this.fetchMetadataIfNeeded(existing)
}
```

### WR-03: `fetchMetadataIfNeeded` builds network/CDN URLs from appId without the numeric guard

**File:** `src/backend/storeManagers/steam/games.ts:190` (and CDN URLs `216-220`)
**Issue:** `getSteamInstallSize` (line 102) and `buildSteamProtocolUrl` (line 40) both reject
non-numeric appIds with `/^\d+$/` before constructing any URL, citing threats T-06-01 and
T-03-01. `fetchMetadataIfNeeded` — a sibling chokepoint that also interpolates `this.appId`
directly into a `store.steampowered.com` query string and into `cdn.cloudflare.steamstatic.com`
image URLs that are then pushed to the frontend as `<img src>` — has no such guard. appIds
currently originate from Steam's owned-apps list (numbers), so real-world risk is low, but
this is a defense-in-depth inconsistency at exactly the kind of chokepoint the phase's threat
model treats as requiring validation.
**Fix:** Add the same guard at the top of `fetchMetadataIfNeeded` (after the `pendingFetches`
check), returning early and logging a warning for non-numeric appIds, consistent with the
sibling functions.

### WR-04: Unguarded `JSON.parse` of `nonAvailableGames` inside a per-game filter callback

**File:** `src/frontend/screens/Library/index.tsx:563-570`
**Issue:** `isNonAvailable` calls `JSON.parse(storage.getItem('nonAvailableGames') || '[]')`
inside the filter predicate, and this code path (lines 576-590) is **outside** the
`try/catch` that wraps the Fuse search (524-555). If `nonAvailableGames` in localStorage is
malformed (partial write, external tampering, or an older non-JSON format), `JSON.parse`
throws, the `gamesForAlphabetFilter` `useMemo` throws, and the entire Library screen fails to
render. Additionally the read+parse happens once per game in the library (re-read on every
predicate call), which is needless work regardless of the throw risk.
**Fix:** Parse once, outside the filter, inside a guarded block:

```ts
let nonAvailableGamesArray: string[] = []
try {
  nonAvailableGamesArray = JSON.parse(storage.getItem('nonAvailableGames') || '[]')
} catch {
  nonAvailableGamesArray = []
}
const isNonAvailable = (game: GameInfo): boolean =>
  nonAvailableGamesArray.includes(game.app_name) ||
  (game.runner === 'steam' && !!game.is_delisted)
```

## Info

### IN-01: Pre-existing CSS selector typo prevents sepia on installed-not-available logos

**File:** `src/frontend/screens/Library/components/GameCard/index.css:191`
**Issue:** `.gameCard.notAvailable .gameLog.installed` should be `.gameLogo.installed`
(`.gameLog` is not a class used anywhere). The installed-but-not-available game **logo**
therefore never receives the intended `sepia(100%)` treatment applied to the cover image on
line 190. This is upstream/pre-existing (git blame: 2022) and not introduced by this phase,
but it sits directly beside the new LIB-08 delisted styling and undermines the delisted
"greyed art" intent for installed delisted games that have a logo.
**Fix:** Rename the selector to `.gameCard.notAvailable .gameLogo.installed`.

### IN-02: `'only'` filter mode is not honored in RecentlyPlayed / Favourites lanes

**File:** `src/frontend/screens/Library/components/RecentlyPlayed/index.tsx:63` and `src/frontend/screens/Library/index.tsx:349-361`
**Issue:** Both lanes branch only on `showHidden === 'off'` (or `!== 'off'`). In `'only'`
mode — which the main grid interprets as "show *only* hidden games" — these lanes instead
show the full unfiltered recent/favourites list. Semantically inconsistent with the main
library's `'only'` treatment, though these secondary lanes are not the primary surface for
the hidden/non-available filters, so impact is cosmetic.
**Fix:** If lane consistency is desired, treat `'only'` explicitly (filter to hidden) rather
than collapsing it into the `!== 'off'` "show everything" branch.

### IN-03: Delisted badge can overlap the status/update badges

**File:** `src/frontend/screens/Library/components/GameCard/index.tsx:496-511`, `index.css:203-215`
**Issue:** `gameCardDelistedBadge` is positioned `top:5px; left:5px; z-index:3`, the same
corner as `gameCardStatus` (`z-index:5`) and `gameCardUpdateBadge` (`top:5px; left:5px`).
An installed-yet-delisted game that also has a status label will render both in the same
spot with the delisted badge behind. Unlike the update badge (which has a `:has()` offset
rule at css:69), the delisted badge has no offset rule, so it can be occluded.
**Fix:** Add a `:has(.gameCardStatus) .gameCardDelistedBadge` offset rule (mirroring css:69)
or move the delisted badge to a free corner.
