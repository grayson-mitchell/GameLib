# Spike 012: Does GameLib's React frontend survive under Tauri?

> Part of **Idea C — Rust/Tauri rearchitecture**. Closes the loop after 009 (backend), 010 (Steam),
> 011 (platform seam). The renderer question isn't "can a webview show React" (Tauri hosts any web
> frontend) — it's **how welded the renderer is to Electron's `ipcRenderer`**, and whether the
> preload bridge can be re-pointed at Tauri without touching the app. Run live 2026-07-20.

## What This Validates

**Given** GameLib's React renderer and its contextBridge preload, **when** the bridge is
reimplemented over a non-Electron (Tauri/sidecar) transport, **then** the renderer's `window.api`
contract is satisfied unchanged and calls round-trip. Observable proof: `bridge-shim-demo.html`
(live in a WKWebView-engine browser) + a headless contract check.

## Investigation Trail

1. **Renderer coupling measured.** The frontend reaches the backend through **379 `window.api.*`
   call sites** but only **1 direct `ipcRenderer`** call and **5 files** importing `electron`
   directly. The React tree is decoupled from Electron by Heroic's contextBridge design.
2. **The bridge is astonishingly narrow.** `src/preload/index.ts` does a single
   `contextBridge.exposeInMainWorld('api', api)`. The entire `window.api` (14 preload files, the
   whole 379-call surface) is generated by **three factory functions** in `src/preload/ipc.ts`:
   - `makeHandlerInvoker(channel)` → `ipcRenderer.invoke` (request/response)
   - `makeListenerCaller(channel)` → `ipcRenderer.send` (fire-and-forget)
   - `frontendListenerSlot(event)` → `ipcRenderer.on` (backend→frontend push)
   The whole backend transport funnels through **8 `ipcRenderer` calls total** in preload.
3. **Rebuilt those 3 factories on a mock-Tauri transport** (`bridge-shim-demo.html`) — line-for-line
   the same shape — and assembled a `window.api` exactly as GameLib does. A demo "renderer" calls
   `getHeroicVersion()` (invoke), `refreshLibrary()` (invoke), `openExternalUrl('steam://…')` (send),
   and receives a backend push (listener slot), with a live forensic log of each bridged call.
4. **Headless contract check** replicated the three factories under `node`: version/library/push all
   round-trip; `electron_symbols_used: 0`; `contract_ok: true`.

## How to Run

```bash
open bridge-shim-demo.html   # click the four buttons; watch the forensic bridge log
# headless contract check is inlined in the spike commit output
```

## What to Expect

Each button drives a real `window.api.*` call through the reimplemented factories into a mock
sidecar and logs `[invoke]/[send]/[on]/[transport]` events — the renderer has no idea it isn't
Electron. The macOS default browser uses the same WKWebView engine Tauri uses, so this is a faithful
preview of the frontend's runtime host.

## Results

**Verdict: VALIDATED — the React frontend is highly portable; only a narrow preload seam is rewritten.**

- ✓ **The UI + all 379 `window.api` call sites are untouched by the port.** They depend on the
  `window.api` contract, not on Electron.
- ✓ **Porting to Tauri = rewriting three factory functions** (`makeHandlerInvoker` →
  Tauri `invoke`/sidecar RPC; `makeListenerCaller` → command/emit; `frontendListenerSlot` →
  Tauri `listen`). Proven equivalent live, with zero Electron symbols.
- ⚠ **5 renderer files import `electron` directly** — small, must be routed through `window.api` or
  a shim (they bypass the clean seam today). Bounded cleanup, not architecture.
- ○ **Not claimed:** that the *entire* app boots end-to-end — that needs the full Vite build under a
  real Tauri shell. What's proven is the load-bearing risk: the renderer↔backend contract survives
  the shell swap through one narrow, mechanical seam.

**Impact on Idea C:** the frontend is the *cheapest* leg of the port, inverting the usual worry.
Combined with 009–011, all four legs are now characterized (see MANIFEST feasibility note).
